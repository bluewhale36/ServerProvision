§1. 이 슬라이스가 세운 것

E3-1 이 BIOS 를 써 넣고 재부팅해 확인한 뒤, 같은 FIRMWARE_SETTING phase 의 두 번째 step(BMC_SETTING) 으로 사내 표준 BMC 세팅 4종(DateTime · Cold Redundant · Fan Profile · Network Bond)을 AMI 웹 API 로 써 넣고 항목마다 되읽어 확인한다. 재부팅이 없고, 정의서 · 화면 · DDL 을 건드리지 않았다.

plan 의 약속코드에서 지탱하는 자리
계약의 자리 = 시스템 설정(D-1, 사용자 확정 C 안)BmcStandardSettings(provision.bmc.standard.*) + FanProfileResources(classpath bmc/fanprofile/<모델>.json 4 보드). 정의서(BasicSettingRequest) · 스냅샷 · 폼 무변경 — BASIC_SETTING 보유 = BIOS 뒤 BMC 도 밟는다
같은 phase 의 두 번째 step · 축 승격(D-2)SettingAxis{BIOS, BMC} · SettingCursor.afterAxis(다음 축이면 positionAt, 없으면 advanceOrComplete). E3-1 의 행 1 · 4 가 advanceOrComplete 대신 이것을 부른다 — BIOS 목표가 없어도 BMC 표준은 밟는다
항목은 enum 상수가 든다(D-3)BmcSettingItem 4 상수 — 상수별 write · verify, apply 가 거절을 REJECTED 로 흡수. 행(7)은 values() 순회만

§2. 진단 — 착수 시점에 없던 것과 있던 것

없던 것

  1. AMI 웹 API(/api/*)를 부르는 코드 — 인증 모델이 Redfish(Basic)와 달라(세션 + CSRF + 쿠키) 별도 클라이언트가 필요했다.
  2. BMC 세팅의 소비 입력 — Notion 은 "payload 계약 신설" 을 예정했으나 정본이 표준 4종으로 확정되며 자리가 옮겨졌다.
  3. BIOS 축 뒤 BMC 축으로 가는 커서 — E3-1 은 BIOS 에서 phase 를 닫았다.
  4. 보드별 Fan Profile 자원의 저장소 정본.

있던 재료

E3-1 의 WorkerStep · WorkerStepRegistry · SettingLedger(JSON meta) · BmcIdentityProbe · FlashTimeoutPolicy.returnLimit / E1.6 의 BmcCredentialsFallback · BmcCredentialsMemory / E1.5 의 redfishRestClient(자가서명 TLS 완화) / ProvisioningProgress.positionAt(같은 phase 안 이동) / ProvisioningPhaseStep.BMC_SETTING(자리만 있던 상수) / 앵커 세션의 실측(E0-3 · HAR · 레시피) — 성공 = 에코, 인증 실패 = cc:7, 데이터 거절 = error+code, DateTime PUT 21 필드, Fan Profile 3 보드 JSON(+사용자가 MS73-HB1 추가 → 4 보드).

7행 착수 절차

  1. 신원 대조(BmcIdentityProbe, Redfish Chassis).
  2. 원장 열기(openBmc, 첫 쓰기보다 먼저) 또는 bondAt 없는 RUNNING 행 이어받기.
  3. 세션(BmcCredentialsFallback.attempt(login) — 표준 → 공장 기본 사다리 · 캐시).
  4. BmcSettingItem.values() 순서로 apply(write → verify) · 결과를 markItem 으로 누적.
  5. 결과 종류에 따라 — APPLIED/SKIPPED 계속 · REJECTED → WRITE_REJECTED 닫음(뒤 항목 미수행) · MISMATCH → READBACK_MISMATCH · RECONNECT_PENDING → markBondAt 후 RUNNING 유지.
  6. 로그아웃(best-effort).
  7. 전부 끝나면 SUCCEEDED APPLIED(detail "N개 적용 · X 건너뜀(…)") + afterAxis(BMC) = phase 완주.

세션 · 연결 실패는 주기의 일이다 — AUTH 소진 → AUTH_REJECTED, CONNECT → 시한 안이면 RUNNING 유지(다음 주기 재개 · 항목 재쓰기), 시한 뒤 BMC_UNREACHABLE.

§7. 미수행 항목과 사유

미수행 없음 — 17 항목 전부 수행했고 증거가 1:1 로 붙는다. 수행했다는 것과 덮었다는 것은 다르므로, 이 CP5 가 확인하지 못한 것을 남긴다.

  1. 실기 미수행. 모의 BMC 는 E0-3 · HAR 계약의 재현이다. MS03 · MS04 · MS73 프로파일의 실기 전송(MS74 만 curl 200 실증), Bond 뒤 실제 단절 시간과 주소 변화, eth1 인터페이스명의 보드 공통 여부(T3 적립), 웹 세션 동시 상한과 TTL 정확값, UI 가 부수로 부르는 POST /api/settings/settingsItem 의 필요 여부 — 전부 CP7 실기 소관이다.
  2. plan 의 B9 bond.enable=false. 앱 재기동(설정 변경)이 필요해 하네스에서 뺐다. 단위 테스트 begin_disabledBondSkipped 가 SKIPPED(BOND_DISABLED)를 고정한다.
  3. 크래시 그 자체. 트랜잭션 도중 프로세스 종료는 재현하지 않았다. "bondAt 없는 RUNNING 행 이어받기" 는 단위 테스트 begin_resumesOpenRow 가, "실패 뒤 재시도의 재착수 · 멱등 재쓰기" 는 B8 이 각각 맡는다.
  4. 주소 재발견의 성공 경로. E3-1 과 같은 환경 조건(샌드박스에 DHCP lease 없음)이다. R1 에서 UNREACHABLE 분기는 밟았으나 "새 주소 없음" 가지만 지났다.
§8. 검증 중 발견한 것과 처리

F-1 — 단발 실패가 항상 BIOS_SETTING 에 적혔다 원장 정확성 테스트 발견

SettingLedger.instant 가 step 을 BIOS_SETTING 으로 못 박고 있어, failAtCursor(신원 불일치 · BMC 없음의 단발 실패)가 BMC 축에서도 BIOS_SETTING 행을 남겼다. E3-1 때는 축이 하나라 드러나지 않았고, BmcSettingStepExecutionTest.begin_identityMismatchOpensNothing 이 step_code=BMC_SETTING 을 요구하며 잡았다.

처리 — instant 가 step 을 받고 failAtCursor 는 progress.getCurrentStep()(커서 자리, ES-2 D-5 규약 그대로)을 넘긴다. SkipNoTargetStep 은 BIOS 축을 명시한다. 재검증 — 해당 테스트 green, 그리고 CP5 의 B4 가 step_code = BMC_SETTING 을 실측했다.

F-2 — Cold Redundant 바디만 키 순서가 비결정적이었다 계약 충실도 에이전트 관찰 ①

COLD_REDUNDANT.write 가 Map.of 를 써서 실전송이 {"set_cold_redundant_enable":0,"master_psu":0} 로 HAR 순서와 뒤집혀 나왔다(나머지 셋은 LinkedHashMap 이다). JSON 이라 실기 동작에 영향은 없을 가능성이 높지만 "HAR 정본을 그대로 싣는다" 는 원칙과 한 항목만 어긋났다. 처리 — LinkedHashMap 으로 바꿨다. 재검증 R2 에서 ['master_psu', 'set_cold_redundant_enable'] 을 확인했다.

O-1 — DateTime PUT 바디는 21 이 아니라 22 필드다 문서 정정 관찰 ②

HAR 의 요청 키 수가 22(id 포함)인데 plan 과 Javadoc 이 21 로 적었다. 코드는 처음부터 22 를 보냈다(A2 실측). 처리 — Javadoc 을 정정하고, plan 과의 어긋남은 §9 편차로 기록했다.

O-2 — 단발 기록 meta 에 axis 가 없었다 판독 일관성 관찰 ④ · 보완

열린 행을 닫는 경로에는 axis 가 있고 instant 경로에는 없어, A6 의 SKIPPED 행과 B4 의 IDENTITY_MISMATCH 행이 step_code 로만 축을 말했다. 처리 — instant 가 step 에서 축을 파생해 적는다. 재검증은 R3 이다.

O-3 — 한 주기에 끝난 BMC_SETTING 행은 started_at == finished_at 설계 귀결 관찰 ③

사이클이 now 하나를 쓰므로 착수와 종결이 같은 시각으로 남고 화면에 소요 0 으로 보인다(주기를 넘긴 행 B6 · B7 은 정상 표기다). 원장의 시각은 "워커가 그 주기를 시작한 시각" 이라는 뜻이며 실 소요(수 초)는 로그에 있다. 손대지 않는다 — E2-2 도 같은 규약이다.

O-4 — 재시도 직후 motion 이 AWAITING_BOOT 로 남는다 기존 경로 E2-4 · 재시도 UX

clearFailed 가 재부팅 대기로 되돌리는데 설정 워커는 motion 을 보지 않아 다음 주기에 곧바로 재착수한다(B8 이 정상 종결로 끝났다). 10초가량 표기와 실제가 어긋난다. E2-1-b 이전부터 있던 재시도 경로이고 E3-2 범위 밖이므로, 표기 정합은 후속(E2-4 · 재시도 UX)으로 넘긴다.

하네스 충실도 정정 — bond-drop 이 웹 경로만 끊었다 하네스

첫 수행의 B6 · B7 에서 Redfish 신원 대조는 매 주기 성공했고 대기를 만든 것은 POST /api/session 의 CONNECT 였다 — 실기라면 둘 다 끊긴다. 환경 특이사항으로 보고된 것을 세션이 처리했다. 모의 BMC 의 단절 게이트를 Redfish 경로에도 걸고(_dropped()), ReconnectReadbackStep 의 UNREACHABLE 분기 단위 테스트(reconnect_identityUnreachableWaits)를 더했으며, R1 로 그 분기를 실측했다.
