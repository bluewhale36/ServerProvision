핵심 한 줄 — 집행 메커니즘(가상 USB + UEFI Shell 로 BIOS · BMC flash)은 확보됐으나, E2 의 진짜 착수 본체는 이미지 빌드가 아니라 ‘진단 완주 후 커서를 FIRMWARE_UPDATING 으로 전진시키고 완료를 판정하는 phase 진행 골격’이며 이 골격은 현 코드에 통째로 없다. U3(할당 스냅샷의 ownedPhases 공급)가 엄격한 선행 의존이다.
§1. 조사 배경 · 목표

E2 = ProvisioningPhase.FIRMWARE_UPDATING 이다. 진단 리눅스 E1 직후, 펌웨어 설정 E3 직전에 위치한다. 게스트 서버에 할당된 세팅 정의서의 BasicUpdateRequest 를 resolve(보드 AUTO / 펌웨어 LATEST)해 BIOS · BMC flash 를 집행하는 단계다. E2-R 은 그 집행 게이트를 여는 조사 트랙이며, 산출물은 코드가 아니라 이 보고서다.

선행 결정 (E 로드맵 토론 종결)

결정내용
DEC-20 펌웨어 집행 = 가상 USB(FAT32 이미지) 방식 선행, Redfish UpdateService 후행 전환 목표. 기존 수동 방식의 유일한 불편 = 이미지를 리눅스 셸에서 사람이 수동 제작. → “가상 USB 제작 로직의 앱 내 구현 가능 여부”가 E2-R 1번 조사항목. .RBU(BIOS) / .ima_enc(BMC) 파일이 공식 번들에 실재함은 확인됨.
DEC-4 펌웨어 flash 실패는 자동 재시도 없음(운영자 명시 액션). “원인 미상 재-flash = 벽돌 리스크”.
검증 Tier T0 계약테스트 / T1 모의게스트 하네스 / T2 QEMU / T3 실기. E2 집행 검증은 T3 유보.

조사 3항목 (E2-R Notion)

  1. 가상 USB 방식의 앱 내 동적 생성 가능성 (→ §4)
  2. 대안 경로 비교(진단 리눅스 벤더 도구 / Redfish UpdateService) (→ §3)
  3. flash 성공 판정 절차 (→ §6)
MVP 수동 선례 (Notion ‘PXE Server 구축’ §6 · §8) — boot.ipxe 가 iPXE 내장변수 product(메인보드 모델명)로 모델 분기 → sanboot 로 FAT32 가상 USB(bios_update.img = UEFI Shell BOOTX64.EFI + startup.nsh + 펌웨어 롬) 부팅 → startup.nsh 가 BIOS → BMC 순 flash 후 재부팅.
§2. 조사 산출물 + 비목표

이 보고서가 E2-2(BIOS_UPDATING · BMC_UPDATING 집행)의 착수 게이트 입력이 된다. 단, 아래 §7 의 발견으로 착수 게이트는 아직 열리지 않는다 — 선결 배선이 필요하다.

비 목표
  • resolve 판정 로직(목표 보드 AUTO 결정 / 펌웨어 LATEST 선택)은 E2-1(FIRMWARE_RESOLVING) 소관 — 이 조사 밖.
  • BIOS 설정 값 적용은 E3(펌웨어 설정) — E2 는 펌웨어 바이너리 버전 갱신(flash)까지만.
  • 실제 flash 집행 성공 검증은 실기 T3 유보 — 이 조사는 “무엇이 가능하고 무엇을 지어야 하는가”까지.
🎬 미리보기 — 현 코드에서 게스트 커서는 FIRMWARE_UPDATING 에 도달하지 못한다

이 데모는 이 보고서의 핵심 발견(코드 실측으로 확증)을 상태 전이로 체험시킵니다. 게스트 프로비저닝 커서를 단계별로 밟아 보세요. U3 의 ownedPhases 공급 토글을 바꿔도 결과가 안 바뀌는 것이 관전 포인트입니다 — 규칙 함수는 FIRMWARE_UPDATING 을 반환할 능력이 있지만, 실제 호출부가 Set.of() 를 박아 넣어 그 능력을 못 씁니다. (판정 JS 는 서버 도메인 메서드와 드리프트 0)

§3. 세 집행 경로 비교 (조사항목 ②)

경로 A — EFI-Shell 가상 USB

sanboot FAT32 · 권장 · 확인된 사실

  • 전달: 서버는 부트스크립트 · 이미지를 HTTP 로 제공만(pull), 게스트가 스스로 UEFI Shell 로 부팅해 flash. BMC IP · 자격증명 전혀 불요.
  • pull-push 대칭: 완전 대칭(DEC-1 pull 엔진 · MVP BIOS → BMC 순 flash 와 0 비대칭).
  • BIOS: f.nsh → AfuEfix64.efi 확정(sysGen 문서 + GIGABYTE MC12-LE0 실전 후기). GigabyteEntrypointStrategy 의 f.nsh > flash.nsh 우선순위와 정확히 일치.
  • BMC: bmc_fw_update_uefi.nsh cs 0 flashall 공식 배포(GIGABYTE Firmware Upgrade Guide v0.04, AST2600). AMI YAFUKCS.efi(KCS)도 대체.
  • 관측성: flash 중 진행률 · 오류 회신 채널 없음(UEFI Shell 에 HTTP agent 없음) — 최대 약점. 완료 = 재부팅 후 버전 재대조.
  • 아키텍처 적합도: 최고(FirmwareUpdatingExecutor 빈 1개, DiagnoseLinuxExecutor 동형).

경로 B — in-band 벤더 도구

afulnx / YAFUFlash · 탈락

  • 이미 부팅된 Alpine 에서 직접 flash — 겉보기 간단하나 실현성 낮음(확인된 사실).
  • afulnx 는 amifldrv 커널 플래시 드라이버를 커널에 맞춰 컴파일해야 하는데 신형 커널에서 잦은 실패.
  • afulnx_64 는 glibc 의존 독점 바이너리라 musl + BusyBox Alpine 에서 gcompat shim 필요.
  • 커널모듈 빌드 + libc shim 이중 장벽. 실패가 곧 벽돌. → primary 배제.

경로 C — Redfish UpdateService

OOB · 후행 전환

  • BMC standby power 독립성 활용하나 서버가 BMC IP + 자격증명으로 능동 push → pull 대칭 파괴. (a) E1 에서 ipmitool lan print 로 bmcIp 수집 (b) 자격증명(admin + 시리얼 끝 11자, E3 소관) (c) 서버측 Redfish 클라이언트 TaskService 폴링 필요.
  • 관측성: 최고(FlashPercentage / UpdateStatus 실시간, Task Completed) — 경로 A 약점 정확히 보완.
  • BIOS: SimpleUpdate ImageURI=…RBU(UpdateComponent 는 AMI / GIGABYTE OEM 확장, DMTF 표준 아님). 커스텀 .RBU 의 Redfish 적용성은 DEC-20 이 이미 T3 유보.
  • 장기 안정성 근거: 일부 벤더(Supermicro)가 보안상 KCS in-band flash 차단 추세 → 경로 A 가 미래 BMC 펌웨어 버전에서 막힐 수 있음. Redfish 후행 전환의 근거.
요약 — 경로 A 가 이 pull-대칭 아키텍처에 가장 정합하고 BIOS · BMC 양쪽 커버(관측성만 열위). B 는 벽돌 위험 탈락. C 는 pull 비대칭 · 자격증명 · T3 유보로 DEC-20 대로 후행 전환.
§4. 가상 USB 앱 내 동적 생성 (조사항목 ①, 핵심)
결론 — 앱 내 가상 USB(FAT32 super-floppy) 동적 생성은 실현 가능(확인된 사실). 단, 신뢰도 분리: 라이브러리 능력 = 확인 / 생성 이미지의 UEFI 부팅성 = T2(QEMU+OVMF) 선검증 필요.

§5. BIOS · BMC flash 실행 메커니즘

BIOS (AMI Aptio V)

  • 진입 · 도구: f.nsh → AfuEfix64.efi(v5.10.00.1610). 무인 flash 플래그: /P(메인 BIOS) /B(부트블록) /N(NVRAM) /K(non-critical) /R(SMBIOS 보존) /X(ROM-ID 검사 생략) /Q(무음) /REBOOT /D(flash 없이 검증 dry-run) /O(백업). 예: AfuEfix64.efi BIOS.ROM /P /B /N /X /Q /REBOOT. 근거: openbmc-util AfuEfi64 readme.txt, holoto/efi_shell_flash_bios a64.txt.
  • UEFI Shell .nsh 는 %lasterror% + if / then / endif 로 성공 / 실패 분기 후 reset -c 가능(congatec AN48 예시). 확인
  • 함정 1 추정: GIGABYTE 순정 f.nsh 는 ROM-ID 불일치 시 대화형 프롬프트(‘E’ 입력) 가능(MC12-LE0 후기) → 진짜 무인화는 순정 f.nsh 의존 대신 AfuEfix64.efi 를 /X /Q 로 직접 호출. 단 /X 는 잘못된 모델 ROM flash 위험 → 앱 레벨에서 GuestServerDetail.boardModel ↔ BoardBIOS 대상모델 일치 사전 강제.
  • 함정 2 확인: AMI Aptio V Secure Flash 가 미서명 / 변조 ROM 을 error 18(‘secure flash rom verify fail’)로 거부 → 공식 서명 ROM 만 통과. 이는 코드 무결성 모델(manifestHash + HMAC markerSignature)이 보장하는 ‘변조 안 된 공식 번들만 집행’과 하드웨어 레벨에서 이중 정합. 근거: winraid MX32-4L0 스레드, StarLabs issue #305.
  • 포맷 추정: 공식 번들은 (a) .RBU(BMC / Redfish / Web-BIOS-Update 용, ROM 에 체크섬 / 서명 덧붙은 래핑) + (b) 원본 .ROM(UEFI-Shell AFU 용, 번들 내부 zi_ 중첩 아카이브 해제로 AfuEfix64.efi 와 함께 나옴) 동시 포함. UEFI-Shell 경로가 flash 하는 대상은 .RBU 가 아니라 원본 .ROM. 근거: MC12-LE0 블로그, ServeTheHome Web-BIOS-Update.
  • 복구 확인: 대상 보드류 BIOS 손상 복구 = 부트블록 리커버리(BIOS Recovery 점퍼 + USB 의 ROM + 리커버리 모드), 자동 듀얼 BIOS 전환 아님(MS03-CE0 매뉴얼 p.89). BMC(AST2600)가 전원 오프 시 SPI 직접 프로그램 가능(물리 프로그래머 유사). 이 수동성이 DEC-4 · isRetryBlocked 원천차단의 물리적 근거.
  • in-band 리눅스 대안: 실현성 낮음(위 경로 B, Alpine musl + 커널모듈 컴파일 + glibc shim 삼중 장벽).

BMC (AST2600 + AMI MegaRAC SP-X)

  • 핵심 판정 확인: BMC 는 Redfish 전용이 아니다. GIGABYTE 가 AST2600 서버용 UEFI Shell BMC flash 스크립트 bmc_fw_update_uefi.nsh(cs 0 flashall — cs = Active / Backup 이미지 선택, flashall = 경고 없이 BMC 전체 flash) 공식 배포(GIGABYTE Firmware Upgrade Guide v0.04). 실전 후기(MC12-LE0)도 web GUI 실패 시 FAT32 USB 로 UEFI Shell 부팅해 BMC 성공 flash. AMI YAFUKCS.efi(KCS 경유)도 대체 존재(Trenton / Supermicro 문서).
  • flash 메커니즘 2종 확인: (A) socflash = ASPEED P2A(PCI-to-AHB) 브리지로 SPI NOR 에 raw 직접 기록(검증 우회, raw .ima 필요, ASPEED ‘engineer / lab only’). (B) YAFU / YAFUKCS · web GUI · Redfish · IPMI = 살아있는 BMC 에 이미지 전달 → BMC 스스로 복호화 · 검증 · 기록(.ima_enc 암호화본 소비).
  • 미확정 미확정 · 벽돌 위험: UEFI Shell 경로가 소비하는 파일이 .ima_enc(암호화)인지 raw 인지, 하부 도구가 socflash(P2A)인지 YAFUKCS(KCS)인지 미확정. 암호화본을 raw-SPI(socflash)로 잘못 기록하면 BMC 벽돌 → 실기(T3)에서 대상 4종 동봉 BMC 파일 실체 + .nsh 참조 파일명 확정 필수.
  • 재부팅 확인: BMC 는 flash 완료 후 스스로 재부팅(5~10분, WebUI 무응답 → 재로그인). AST2600 센서 오독 시 서버 전체 cold boot 필요 가능. 듀얼 이미지: Image1 실패 시에만 Image2(Active / Backup). AST2600 ABR(2차 watchdog)로 주 이미지 부팅 실패 시 golden 이미지 자동 페일오버(추정, QEMU 문서) → BMC 벽돌 확률은 상대적으로 낮음.
§6. flash 성공 판정 + 버전 재수집 절차 (조사항목 ③)
원칙 — 성공 판정은 “flash 유틸 종료코드”가 아니라 “재부팅 후 재수집한 버전 == 목표 번들 버전”의 정규화된 등가 비교다. 근거 2가지:
  1. dmidecode -s bios-version 은 SMBIOS type0 테이블을 읽는데 이 테이블은 BIOS 가 POST 때 채운다 → flash 직후 재부팅 전에는 옛 버전이 그대로. 반드시 재부팅 후 재수집해야 새 버전이 보인다(확인).
  2. AFU 의 /D 는 flash 전 dry-run 호환성 검사일 뿐 flash 후 대조가 아니며, ‘Process completed’ / 성공 종료가 실제 버전 반영을 보장 안 함 (사일런트 실패 = 종료코드 성공인데 버전 그대로, 확인).

타이밍 — dmidecode 재수집은 flash → reset → 재부팅 후 부팅에서만 유효(직후 재수집은 옛 SMBIOS 오판). BMC 는 5~10분 자기 재부팅 → 재수집 전 충분한 WAIT 여유(너무 이르면 정상 flash 를 응답없음으로 오판).
§7. 엔진 매핑 + 착수 게이트 공백 【이 보고서의 핵심】

확장 자체는 정갈하다: FirmwareUpdatingExecutor implements ProvisioningPhaseExecutor 빈 1개 등록 → PhaseExecutorRegistry 가 phase()=FIRMWARE_UPDATING 수집 → BootScriptDispatcher 6행(HOLD)이 7행(위임)으로 자동 전환(분기 추가 없음, DiagnoseLinuxExecutor 동형). SPI = phase() + bootScript(server, progress, rebootQuery) + default onStepClosed(server, progress, step).

그러나 코드 실측(적대적 비판 + 세션 직접 확인)이 밝힌 4개 구조 공백 — 이것이 E2 의 진짜 착수 본체다.

치명 #1 — 커서가 FIRMWARE_UPDATING 에 도달하는 경로가 없다

advanceTo 호출자는 AgentReportService.checkin 의 BOOTSTRAPPING → DIAGNOSE_LINUX 단 하나(engine/AgentReportService.java:68-69). 그 외 어디서도 FIRMWARE_UPDATING 으로 전이하지 않는다. DiagnoseLinuxExecutor.onStepClosed 는 완주 판정에서 PhaseSequence.nextAfter(DIAGNOSE_LINUX, Set.of())(engine/DiagnoseLinuxExecutor.java:119)를 호출 — ownedPhases 를 빈 집합으로 하드코딩한다. nextAfter 는 empty 를 반환하고 markCompleted 만 한다(비어있지 않아도 advanceTo 를 호출하는 코드가 없다). 결론: 진단 완주 게스트는 무조건 PROVISIONED 종단되고 FIRMWARE_UPDATING 에 절대 진입 못 한다. ownedPhases 의 실공급자는 U3(할당 스냅샷)임이 PhaseSequence javadoc(engine/PhaseSequence.java:10-11)과 DiagnoseLinuxExecutor 주석(:117-118)에 명시. ⇒ U3 가 엄격한 선행 의존이며, U3 가 ownedPhases 를 공급해도 onStepClosed 의 Set.of() 하드코딩 제거 + 진단완주 → 펌웨어 전이 배선을 함께 지어야 한다.

중대 #2 — 완료 신호를 닫을 훅이 구조적으로 발화 못 한다

AgentReportService.closeStep 은 SUCCEEDED 종결 시 phaseExecutorRegistry.find(step.getStepCode().getPhaseType()) 로 onStepClosed 를 라우팅한다(engine/AgentReportService.java:129) — 훅은 오직 ‘닫힌 step 의 phaseType 실행기’로만 간다. flash 후 버전 재수집은 Alpine 재진입으로 INFORMATION_COLLECTING 을 보고하며 이 step 의 phaseType 은 DIAGNOSE_LINUX → DiagnoseLinuxExecutor.onStepClosed 만 발화, FirmwareUpdatingExecutor.onStepClosed 는 절대 호출 안 됨. 반대로 FirmwareUpdatingExecutor 훅이 발화하려면 BIOS_UPDATING / BMC_UPDATING step 이 SUCCEEDED 로 닫혀야 하나, UEFI Shell flash 환경엔 agent(HTTP 채널)가 없어 그 step 을 open / close 할 주체가 없다. ⇒ 완료 판정 주체 재설계 필요. 3안:

  • (a) 진단 실행기가 커서 보고 펌웨어 step 까지 닫음 = phase 경계 침범
  • (b) 별도 reconciliation 서비스 대조
  • (c) FirmwareUpdatingExecutor.bootScript 재진입 시점에 직전 재수집 결과 판정

plan CP1 에서 trade-off 비교 결정.

중대 #3 — 버전 재수집 directive 가 firmware 재진입에서 안 나간다

directiveFor 는 COLLECT 를 currentPhase==DIAGNOSE_LINUX && !isEnriched 일 때만 반환(engine/AgentReportService.java:156). flash 후 재진입 시 커서 = FIRMWARE_UPDATING, detail 은 이미 DIAGNOSTIC_ENRICHED → 두 조건 거짓 → WAIT 만. 재수집 트리거가 없으면 버전 대조 절차 전체가 성립 안 함. ⇒ firmware phase 재진입 시 재수집 지시하는 새 directive 판정 분기 또는 DiscoveryStage 에 ‘재수집 요구’ 상태 필요.

중대 #4 — 이미지 빌드를 bootScript 에 넣으면 읽기전용 dispatch(DEC-2)와 충돌

BootScriptDispatcher 는 ‘상태를 일절 바꾸지 않는 읽기 전용 판정(DEC-2)’로 명시(engine/BootScriptDispatcher.java:14). 이미지 생성(수십~수백 MB, 초 단위 I/O)을 /boot HTTP 응답 스레드에서 동기 수행하면 첫 폴에서 iPXE 타임아웃 · 스레드 점유. ⇒ 이미지 빌드를 boot dispatch 밖의 사전 async 스테이징(BackgroundJob / 전용 빌더 서비스)으로 분리, 준비 전엔 bootScript 가 HOLD 반환, bootScript 는 준비된 img 의 sanboot URL emit 만.

핵심 재정의 — E2 plan 의 실질 본체는 ‘가상 USB 이미지 빌드’가 아니라 ‘진단 완주 → FIRMWARE_UPDATING 커서 전진 배선 + ownedPhases 공급(U3) + 완료 판정 주체 + 재수집 directive’다. 이미지 빌드는 이 골격 위에 얹히는 부차 요소.
§8. 위험 등록부

각주 — #1 · #2 상세 (미결정 · E2 하위 단계 착수 시 결정)

아래 두 위험의 완화책은 지금 확정하는 설계 결정이 아니다. 조사 단계(E2-R)는 위험의 존재와 성격만 규명하고, 완화책을 어떤 형태로 넣을지는 E2 하위 단계(E2-1 / E2-2) 구현 진입 시 그 슬라이스의 plan CP1 에서 결정한다. 아래 각주는 두 위험을 쉬운 말로 풀어 그 결정의 입력으로 남겨두는 것이다.

[각주 1] 벽돌이 왜 특히 무서운가. 펌웨어(BIOS · BMC)는 보드가 전원을 넣고 부팅을 시작할 수 있게 하는 가장 밑바닥 소프트웨어다. flash 는 보드가 그 펌웨어 위에서 돌아가는 중에 그 칩을 통째로 덮어쓰는 작업이라 비행 중 엔진 교체에 가깝다. 도중에 전원이 나가거나 리셋되면 칩에는 옛것도 새것도 아닌 반쯤 쓰다 만 것이 남아, POST(전원 자가진단)조차 못 하는 ‘벽돌’이 된다. 보통 소프트웨어는 다시 깔면 되지만 벽돌 BIOS 는 프로비저닝 서버가 네트워크로 못 고친다 — 복구가 물리 작업이다. 이 4종 보드는 자동 듀얼 BIOS 전환이 없어, 사람이 점퍼(핀)를 꽂고 ROM 을 USB 에 담아 리커버리 모드로 직접 다시 구워야 한다(MS03-CE0 매뉴얼 p.89). BMC 는 AST2600 의 ABR 워치독이 backup(golden) 이미지로 자동 페일오버할 가능성이 있으나 활성 여부는 실기(T3) 확인 대상이다. 이렇게 중간에 끊긴 flash 를 소프트웨어로 못 되살리기 때문에, 시스템은 펌웨어 flash 를 절대 자동 재시도하지 않는다(DEC-4) — 원인도 모르고 다시 구우면 또 벽돌이 나기 때문이다. 대신 멈추고 사람을 기다리며, flash 에 충분한 시간(BIOS 2~5분 · BMC 5~10분)을 준다.

[각주 2] #1 의 안전장치가 낳는 함정. #1 때문에 ‘펌웨어 flash 자동 재시도 금지’ 안전장치(isRetryBlocked)를 넣는다. 방향은 옳지만, 여기에 세 균열이 있어 하드웨어가 멀쩡한데도 워크플로가 막힐 수 있다.

  • 균열 A — 서버가 ‘벽돌’과 ‘아직 굽는 중’을 구별 못 한다. 서버는 flash 를 직접 지켜보지 못하고(UEFI Shell 에 보고 채널이 없음), 오직 게스트가 재부팅해서 돌아와 새 버전을 보고할 때만 성공 · 실패를 안다. 진짜 벽돌은 재부팅 자체를 못 해 영영 안 돌아오니, 서버 관점에선 ‘대기(WAIT)’만 무한히 이어진다. 자동 실패 판정이 가장 필요한 상황(진짜 벽돌)에서 오히려 판정이 안 뜨는 셈이다 — 그 판정 로직이 ‘살아서 재부팅하는 게스트’를 전제하는데 벽돌엔 그 전제가 없기 때문이다.
  • 균열 B — 오탐(false alarm) 한 번이 멀쩡한 서버를 영구히 잠근다. 성공 판정은 ‘재수집한 버전 == 운영자가 등록해 둔 목표 버전’ 대조인데, 이 목표 버전은 사람이 손으로 입력한다(GIGABYTE 커스텀 .RBU 포맷이라 앱이 버전을 안정적으로 자동추출하기 어려움). 오타(예: 실제 문자열은 MS03CE0 F05 인데 F05 로 등록)가 나면 flash 가 성공했는데도 대조가 ‘불일치’라며 BIOS_UPDATING 을 FAILED 로 찍는다. 이제 안전장치가 엉뚱하게 작동해, 펌웨어 단계 실패라 isRetryBlocked 가 재시도를 막고 버튼이 사라진다. 보드는 완벽히 멀쩡한데 서류 대조에 걸린 것이고, 이를 소프트웨어로 풀 길이 없어 폐기 · 재온보딩만 남는다.
  • 균열 C — 되돌리기(rollback)가 없다. flash 에는 ‘실행 취소’가 없다. 새 펌웨어를 쓰기 시작하면 옛것을 자동으로 되돌려놓을 수 없어, 나쁜 상태에서 뒤로 물러나 복구하는 선택지가 없고 앞으로 나아가(물리 복구) 해결하거나 포기(폐기)하는 두 갈래만 남는다.

정리하면 #2 는 ‘#1 을 막으려는 안전장치(자동 재시도 금지)가, 하드웨어 고장이 아닌 두 상황 — ① 느린 flash 를 무한대기로 오인, ② 버전 오타로 인한 가짜 불일치 — 까지 소프트웨어 탈출구 없이 가둔다’는 문제다. 표의 완화 열(타임아웃 기반 실패 전이 · 벽돌/대기 구분 신호 · 운영자 오버라이드 경로 · 등록시점 version 검증)은 이 세 균열에 대응하나, 어느 것을 어떤 형태로 채택할지는 E2 하위 단계 plan 에서 결정한다.

§11. 후속 마일스톤

조사 완료로 E2-2 착수 게이트를 ‘기술적으로는’ 해제하나, §7 의 배선 공백 4건이 해소돼야 실질 착수 가능하다. 착수 순서 권고:

  1. U3(할당 스냅샷 ownedPhases 공급) 선행 — E2 의 엄격한 선행 의존.
  2. 진단완주 → FIRMWARE_UPDATING 커서 전진 배선 + 완료 판정 주체 결정(§9 Q1) + 재수집 directive(§7 #3).
  3. 이미지 빌드 async 스테이징(§7 #4).
  4. BIOS flash(경로 A) 먼저, BMC 는 T3 포맷 확정 게이트(§9 Q5) 후.

후속 슬라이스

  • E2-1(FIRMWARE_RESOLVING): 펌웨어 버전 VO 비교 규약 + 마커 무결성 게이트(무결성 실패 = FAILED 차단 / 파일 부재 = 경고성 SKIPPED 비차단). U3 완료 후.
  • E2-2(BIOS_UPDATING · BMC_UPDATING 집행): 가상 USB 빌드 + flash 후 재부팅 루프 + 버전 재수집. 실기 T3 유보 명기.
  • Redfish 후행 전환(DEC-20): BMC_UPDATING step 내부 격리 transport swap + async 폴링 job. E3+ 시점.
