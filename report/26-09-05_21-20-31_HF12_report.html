§0. 요약
결과 — CP5 항목은 계획 12 개에 수행 중 추가한 1 개(B4)를 더해 13 개다. 판정은 PASS 10 · 부분 2 · 미수행 1 · FAIL 0 — 부분 둘은 C1(리눅스 축 화면을 볼 수 없어 서버 산출물로 대체)과 B4(막기는 성립하나 안내가 소실 · 결함 F-1)이고 미수행 하나는 C2 의 화면 확인이다. HF12 가 고친 두 결함은 확인한 모든 경로에서 PASS 였다. 발견 결함 1 건(F-1)은 이번 변경이 만든 것이 아니어서 범위 밖으로 적립했고 관찰 6 건(O-1~O-6)을 함께 기록했다. 테스트 3,051 green(스킵 6 · 신규 7 · 갱신 0 · 클래스 신설 1) · DDL 0 · 설정 0 · 프론트엔드 0 · 신규 예외 0(기존 예외에 생성자 1 추가).
  1. 결함 A — 이름을 바꾸지 않은 수정에서 updated_at 이 멈춘다. 정의서 자신을 dirty 로 만드는 touch() 를 두어 단계만 고친 저장에도 수정 시각이 움직이게 했다.
  2. 결함 B — 리눅스 설치 단계의 "기존 비밀번호 유지" 가 저장 시 병합되지 않는다. Windows 축이 쓰던 병합 훅을 리눅스 중간층에 두어 유지 플래그가 켜진 항목이 저장본 값을 이어받게 했다.

검증 착수 직후 정의서 폼에 리눅스 상세 입력이 없다는 사실을 확인했다(R11 이 걷었다). 그래서 리눅스 항목은 REST 직접 호출로, 화면 항목은 Windows 정의서로 수행했다 — 근거는 §7 의 미수행 표와 §9 의 O-1 이다.

§1. 진단 (증상에서 코드까지)

두 결함은 도메인이 다르지만 JpaSettingCommandService.update 한 메서드를 함께 지나간다. plan §1 의 진단을 요지만 옮긴다.

1-1. 결함 A — 이름이 그대로면 부모 행의 UPDATE 가 없다

정의서 수정은 전체 교체 의미론이다(U2-3 D4). update 는 SettingDefinition.changeNameAndClearProcesses(name) 로 이름을 갱신하며 기존 단계 행을 떼고, flush() 로 삭제를 먼저 반영한 뒤 attachProcesses 로 새 행을 붙인다. 정의서 자신의 컬럼 중 바뀔 수 있는 것은 이름 하나뿐이라 단계만 고치면 부모 행에 바꿀 값이 없고, 이 연관이 단방향 @OneToMany + @JoinColumn 이라 자식 컬렉션의 변경도 부모의 dirty 로 잡히지 않는다. 그래서 Hibernate 가 부모의 UPDATE 를 내지 않고, @LastModifiedDate 를 채우는 AuditingEntityListener 의 @PreUpdate 콜백도 돌지 않아 updated_at 이 생성 시각에 멈춘다. 운영자가 정의서 상세의 "수정일시" 와 목록의 최근 수정 순으로 보는 값이 이것이다.

실측 근거 — E4-1-a-2 의 CP5 관찰 O-4 가 같은 증상을 기록했고, 2026-09-04 의 정의서 10 은 09:25 에 고쳤는데 updated_at 이 07:49 에 멈춰 있었다.

1-2. 결함 B — 리눅스에는 병합 훅이 없다

E4-1-a-2 의 D-11 은 비밀값 처리를 AbstractProcessRequest 의 다형 훅 둘로 정리했다 — 수정 폼 pre-fill 용 withoutSecrets() 와 수정 저장 병합용 withSecretsRetainedFrom(existing) 이며 기본 구현은 둘 다 this 다. LinuxInstallationRequest 는 앞의 하나만 구현했고 병합 훅은 override 하지 않아 기본 this 가 돌아온다. 프론트엔드는 유지 체크가 켜진 항목을 {password:null, keepExistingPassword:true} 로 보내므로 그 값이 그대로 새 저장본이 되고, 이 정의서로 설치가 돌면 Kickstart 의 rootpw 와 autoinstall 의 사용자 항목에 빈 비밀번호가 들어간다. 같은 자리의 Windows 축은 WindowsInstallationRequest.withSecretsRetainedFrom 이 저장본 값을 복사하고 복사할 값이 없으면 RetainedPasswordUnavailableException 으로 400 을 낸다 — 리눅스에 없던 것이 이 짝이다.

1-3. 접근 규칙과 호출 순서 — 여기서는 문제가 없다

RHELInstallationFamilyInspector 의 "root 도 사용자도 없으면 설치 후 접근 불가" 판정은 rootPassword == null, 즉 객체의 부재만 보므로 유지 플래그가 켜진 요청은 통과한다. 검증이 병합보다 먼저 돌지만 판정에 비밀번호 값이 관여하지 않아 순서 문제도 없다 — 검사기나 호출 순서를 손댈 이유가 없었다.

touch() 가 넣는 시각은 flush 전의 임시값이다 — 목적은 부모 행에 바뀐 컬럼을 하나 만들어 UPDATE 가 나가게 하는 것이고, 기록되는 값은 flush 시점에 감사 리스너가 다시 덮는다. D-2 는 비밀번호 제거와 보존을 같은 재조립 경로에 태운다 — 계열 구현은 자기 필드에 patch 를 적용한 사본만 돌려주면 된다.

LinuxInstallationRequest ├── interface PasswordPatch { user(u) · root(r) } ├── STRIP 값 제거 + 유지 플래그 ← withoutSecrets() ├── retainFrom(existing) 저장본 값 복사 · keep 해제 ← withSecretsRetainedFrom(existing) └── RHELInstallationRequest → patch.root(rootPassword) · patchUsers(patch) UbuntuInstallationRequest → patchUsers(patch) (root 필드 없음)

이어받을 값을 찾는 규칙은 축마다 다르다. 사용자는 저장본의 같은 username 에 값이 있을 때, root 는 저장본이 RHEL 계열이고 값이 있을 때 이어받으며, 못 찾으면 RetainedPasswordUnavailableException 이다(단계 신설 · 타입 변경으로 저장본이 리눅스 요청이 아닌 경우도 "값 없음" 이다).

C1 — 수정 폼 pre-fill 노출 규칙

조작: Windows 정의서 1 의 수정 화면에서 "기존 비밀번호 유지" 의 노출과 입력 상태를 보고, 리눅스 축은 서버가 화면에 내려보내는 pre-fill 산출물을 두 경우로 실측했다.
관찰: Windows 는 체크박스가 켜져 보이고 비밀번호 입력이 disabled · placeholder 가 "기존 비밀번호 유지 중" 이었다. 리눅스는 값이 있는 RHEL(id 3)이 rootPassword {password:null, keep:true} 로, root 를 잠근 정의서(id 5)는 rootPassword 자체가 null 로 내려갔다(둘 다 users[0] 은 값 없이 플래그만).
판정: 부분 — 규칙은 서버 산출물 수준에서 두 경우 모두 성립하나 화면 대조는 Windows 축 한 장뿐이다 · 증거: C1.jpg · C1.txt · A3.txt

C2 — 400 응답의 화면 인라인 매핑

조작: 화면 재현 대신 응답의 필드명 원문과 폼의 앵커 개수를 실측하고 resolveErrorTarget 을 읽어 판정했다.
관찰: 서버가 싣는 field 는 rootPassword · users 로 단계 인덱스 접두가 없다 — RetainedPasswordUnavailableException 이 FieldBoundBadRequestException(message, fieldName) 으로 이름을 그대로 싣기 때문이다(@Valid 계열만 processList[i].xxx 형태다).
판정: 미수행(화면) — 코드 판정으로는 앵커가 없을 때 메시지가 단독이면 상단 배너로 밀리고 복수면 카드 폴백에서 덮인다(F-1 이 그 복수 경우다). 어느 쪽도 무언 실패는 아니다 · 증거: C2.txt

§8. 정정 · 적립 (정정 0 · F-1 은 범위 밖)
정정 0 — HF12 변경분에서 발견한 결함이 없어 이번 CP5 에서는 코드를 고치지 않았고 재검증 회차도 없다. 아래 F-1 은 검증 중 드러났지만 이번 변경이 만든 것이 아니어서 적립한다.

F-1 — 리눅스 정의서를 화면에서 저장하면 서버 오류 3 건 중 2 건이 사라진다

재현: 리눅스 OS 설치 단계를 가진 정의서를 준비하고(이번 검증은 REST 로 id 5 를 만들었다. R11 이전에 만들어진 저장본도 같다) 그 수정 화면에서 아무것도 바꾸지 않고 저장한다.

관찰: 응답은 400 이고 fieldErrors 는 파티션 · 설치 환경 ID · 타임존 3 건인데, 화면에는 .field-error-message 가 1 개만 남고 상단 배너는 hidden 이다. 사용자는 파티션과 타임존이 문제라는 사실을 안내받지 못하고, 그 셋 다 화면에 입력이 없어 스스로 고칠 방법도 없다.

원인(static/provisioning/setting-form.js): resolveErrorTarget 이 세 경로 모두에서 앵커를 찾지 못해 같은 폴백 대상 .n-accordion-body 를 돌려주고, paintFieldError 는 칠하기 전에 기존 메시지를 지우므로 뒤가 앞을 덮는다. 셋 다 인라인으로 매핑됐다고 집계되어(mapped=3 · overflow=0) 요약 배너 생략 규칙까지 발동한다.

성격: HF12 변경분이 만든 결함이 아니다 — R11 이 리눅스 입력을 걷으며 그 입력에 붙어 있던 오류 앵커도 함께 사라진 데서 온다. HF12 가 고친 두 결함과 독립이고, 리눅스 정의서가 저장본에 있을 때만 도달하며, 저장본은 400 으로 보호되므로 조용한 손상은 없다.

처리: HF12 에서 고치지 않는다 — 범위는 저장 결함 둘이고 프론트엔드 변경은 0 이다. 폴백 대상이 겹칠 때 메시지를 누적하는 정정은 프론트엔드 공통 매퍼 소관이라 S16-2(문구 · 표시 표준) 또는 E4-L(리눅스 입력 부활 · 앵커 복원)에 적립한다. 증거는 §7 의 B4.jpg 와 B4.txt 다.
