§1. 배경 — 무엇이 발견됐나

2026-08-06 개발 머신에서 개발 데이터베이스와 휴지통 디렉토리(/opt/provisioning/.soft-deleted)를 대조하다가, 데이터베이스에 대응 행이 없는 실물 약 22 GB 가 휴지통에 잔존하는 것이 발견됐다. 휴지통 화면은 그동안 "휴지통이 비어있습니다" 를 표시하고 있었다 — 화면이 틀린 것이 아니라, 화면은 데이터베이스의 삭제 행을 조회하는데 그 행이 0 건이었기 때문이다. 디스크는 차는데 화면은 깨끗한 상태였다.

발견의 핵심 — purge_log 가 0 행이었다. 잔존 실물을 만든 다섯 건의 영구삭제는 감사 기록조차 남기지 않았고, 휴지통 화면 · TTL 자동 정리 · 자원 무결성 점검 · 드리프트 11종 · 미등록 마커 탐지 중 어느 기구도 이 상태를 보지 못했다. 휴지통을 점검 수색에서 제외한 결정은 타당했으나, 그 이면인 "휴지통 안의 실물과 데이터베이스는 누가 대사(對査)하는가" 에 아무도 배치되지 않았다.

원인은 세 겹이었다

#원인성질이번 슬라이스
①과거의 영구삭제가 휴지통 실물을 정리하지 않았다. 잔존 실물의 타임스탬프(6월 13일 ~ 6월 28일)가 전부 S6-2-3 보강 이전이고 purge_log 0 행(감사 배선 이전)과도 부합한다 이미 지나간 사건코드로 소급 불가
②PurgeExecutorImpl 의 deleteQuietly 가 Files.deleteIfExists 단일 호출이라 디렉토리형 자원의 트리를 지우지 못한다. DirectoryNotEmptyException 이 best-effort 설계에 따라 경고 로그만 남기고 삼켜졌다 살아 있는 결함 — 디렉토리형 자원을 영구삭제할 때마다 재현본 수정의 본체
③영구삭제 · 복원 모두 <루트>/<자원종류>/<ID>/ 껍데기를 남긴다. 용량은 0 이지만 운영자가 셸에서 휴지통을 열었을 때 혼란을 만든다 경미하나 지속 발생함께 해소

사용자 지시로 핫픽스 단계를 신설하고 CP1 부터 CP6 까지 무중단으로 진행했다. 개발 머신의 22 GB 는 앵커 세션이 이미 수동 정리했으므로(데이터베이스 참조 0 이라 애플리케이션 동작 영향 없음), 이번 검증은 샌드박스에서 같은 구조를 새로 만들어 수행했다.

비 목표 — 이번에 하지 않은 것 :

  • 이탈 실물의 소급 정리 — 본 수정은 신규 발생을 멈출 뿐 이미 남은 것을 지우지 않는다.
  • 잡파일 강제 정리 — .DS_Store 등이 든 ID 디렉토리는 보존한다(무분기 정책의 대가).
  • 격리 · 복원 경로 규칙(relocate) 변경 — 건드리지 않았다.
§3. 구현 — 정리 절차와 3중 가드
외부 표면 변경 0. 신규 엔드포인트 · 화면 · 요청 · 응답이 없다. 외부에 드러나는 유일한 변화는 PurgeExecutorImpl 생성자에 TrashPolicy 의존성 1개가 추가된 것(빈 배선)이다.

영구삭제 — 무엇이 달라졌나

수정 전 — deleteQuietly

Files.deleteIfExists(Path.of(rawPath));
  • 디렉토리형 자원 → DirectoryNotEmptyException → 경고 로그만 남고 트리 잔존
  • 경로가 어디를 가리키든 가드 없음
  • ID 디렉토리 껍데기 방치

수정 후 — 가드 → 재귀 → 껍데기 정리

가드 통과 확인
  → Files.walkFileTree(target, 삭제 visitor)
  → 부모가 비어 있으면 deleteIfExists
  • 디렉토리형 자원 트리 통째로 삭제
  • 휴지통 레이아웃 밖이면 아무것도 지우지 않고 경고
  • 껍데기가 비어 있을 때만 정리

3중 가드 — 재귀 삭제는 위험 연산이므로 앞에 세웠다

계획 단계에서는 "루트 밖 거부" 와 "루트 자신 거부" 두 겹이었는데, 구현하면서 세 번째 겹이 필요하다는 것이 드러났다. 경로가 <루트>/<자원종류> 나 <루트>/<자원종류>/<ID> 처럼 레이아웃보다 얕으면 루트 안쪽이라 앞의 두 겹을 통과해 버리고, 그 한 번의 재귀 삭제가 자원종류 트리 전체를 날린다. 오염된 경로값 하나로 그런 사고가 나지 않도록 깊이 조건을 추가했다.

겹거부 조건막는 사고
1정규화한 경로가 휴지통 루트의 하위가 아님데이터베이스 오염 · 변조 · 설정 변경으로 경로가 휴지통 밖을 가리킬 때 시스템 파일 삭제
2경로가 휴지통 루트 자신휴지통 전체 소실
3루트 기준 상대 경로의 이름 수가 3 미만 (자원종류 층 · ID 층 자체)오염된 값 하나가 자원종류 트리 전체를 삭제

판정은 문자열 비교가 아니라 정규화된 경로 객체 비교다. 문자열 접두사로 비교하면 /opt/provisioning/.soft-deleted-old 같은 이름이 통과해 버린다.

복원 — 그리고 이번 수정에서 가장 놓치기 쉬웠던 커플링

복원은 휴지통의 파일을 원위치로 되돌린 뒤 남는 빈 ID 디렉토리를 같은 규칙으로 정리한다. 문제는 복원 후속 작업이 실패했을 때 되돌리는 역보상 경로다. 역보상은 파일을 휴지통 안으로 다시 넣는데, 내부의 이동 로직은 부모 디렉토리를 만들지 않는다(소프트 삭제 경로만 디렉토리를 생성한다). 복원이 방금 ID 디렉토리를 지웠으므로, 역보상은 부모 부재로 연쇄 실패한다.

그래서 역보상에 부모 디렉토리 선행 생성을 넣고 같은 커밋에 묶었다. 정리만 먼저 들어가면 역보상이 깨진 채 배포된다. 이 커플링은 실환경에서 인위적으로 유발하기 어려워 단위 테스트로 고정했다(§5 · §8).
복원 요청 ──▶ 원위치로 이동 └─ 성공 ──────▶ [HF6] 빈 ID 디렉토리 정리 └─ 후속 실패 ──▶ 역보상 (휴지통으로 되돌림) └─ [HF6] 부모 디렉토리 재생성 후 이동

환경과 재현 구성

동시 세션과 겹치지 않도록 격리 샌드박스를 따로 띄웠다 — 데이터베이스 3327 · 애플리케이션 7808. 개발 머신의 22 GB 는 이미 수동 정리된 뒤였으므로, 같은 구조를 새로 만들어 재현했다.

디렉토리형 자원은 서브프로그램에 기존 디렉토리를 등록하는 방식으로 만들었다(파일 3개 + 하위 docs/). 소프트 삭제하자 휴지통에 아래 트리가 생겼고, 이것이 발견 당시 실측 22 GB 와 동일한 구조임을 확인한 뒤 조작을 시작했다.

<휴지통 루트>/ └── SUBPROGRAM/ └── 1/ ← ID 디렉토리 (껍데기가 되는 층) └── mlnx-bundle_260805-…_6a5ac107/ ← 개명된 디렉토리 = trashed_path ├── (파일 3개) └── docs/ ← 중첩 — 종전 구현이 걸리던 지점

#조작화면 · 시스템 결과파일시스템 채증
1디렉토리형 자원을 휴지통에서 영구삭제 — typed-name 입력 후 실행 302 리다이렉트로 휴지통 화면 복귀. purge_log 에 SUCCESS 1행(origin=USER_DIRECT). 서버 로그에 성공 라인 트리 전체 + ID 디렉토리 완전 소멸. 종전 구현이라면 여기서 트리가 그대로 남았을 자리다

#일부러 시도한 것애플리케이션의 대응파일시스템
4-a영구삭제 확인 입력란에 자원명과 다른 문자열("틀린이름") 을 넣고 제출 400 — 거절과 함께 기대하는 자원명을 안내한다. 사용자가 무엇을 입력해야 하는지 알 수 있는 형태로 막힌다 불변 — 대상 디렉토리의 파일 수가 3 그대로. 거절이 파일시스템에 도달하기 전에 끊긴다
4-b이미 영구삭제된 자원에 대해 영구삭제를 재시도 400 — 진입 자체가 거절된다. 존재하지 않는 대상에 대한 조작이 실행기까지 내려가지 않는다변화 없음
5가드 실증 — 데이터베이스에서 trashed_path 를 휴지통 밖 미끼 파일 (decoy/outside-trash-decoy.bin)로 직접 UPDATE 한 뒤 화면에서 영구삭제 302 — 영구삭제 자체는 정상 완료되고 감사 기록도 SUCCESS 로 남는다(기록 삭제는 성공했으므로). 서버 로그에 경고 휴지통 레이아웃 밖 경로 — 실물 정리 거부 미끼 파일 보존. 재귀 삭제가 휴지통 밖으로 한 발짝도 나가지 않았다
시나리오 5 의 판정이 왜 "성공" 인가. 이 조작은 데이터베이스가 오염된 상황을 흉내 낸 것이다. 이때 옳은 동작은 ① 데이터베이스 행과 기록은 정상적으로 정리하고 ② 신뢰할 수 없는 경로의 실물에는 손대지 않고 ③ 그 사실을 로그로 남기는 것이다. 실물 정리 실패를 purge 실패로 승격시키지 않는 best-effort 정책(§3)이 여기서 그대로 관측된다 — 사용자에게는 영구삭제가 완료되고, 남은 실물의 대사는 후속 기능이 받는다.

시나리오 6 — 역보상은 실환경에서 유발할 수 없어 단위 테스트로 대체했다

복원 후속 작업 실패로 인한 역보상은 정상 조작으로는 만들 수 없다. 그래서 이 항목만 브라우저 조작 대신 단위 테스트로 덮었다 — 복원이 ID 디렉토리를 정리한 뒤의 상태에서 역보상을 호출해, 부모가 재생성되고 파일이 휴지통으로 정상 복귀하는 것을 단언한다. 대체했다는 사실 자체를 여기 명시하는 것이 CP5 계획의 6번 항목이었다.

감사 기록 — 세 번의 영구삭제가 모두 남았다

검증 중 수행한 영구삭제는 시나리오 1 · 3 · 5 의 세 건이고, 셋 모두 감사 기록에 SUCCESS 로 남았다. 발견 시점의 purge_log 0 행과 대비되는 지점이다 — 그때는 다섯 건의 영구삭제가 아무 흔적도 남기지 않았다.

§9. CP5 중 발견 · 정정

계획서의 수치를 실측으로 정정했다

CP1 계획서는 발견 브리핑의 표를 따라 빈 ID 디렉토리를 13개로 적었으나, 삭제 직전에 다시 센 실측(find -type d -empty)은 14개였다. 계획서의 해당 수치 4곳을 실측값으로 정정했다. 규모의 결론은 달라지지 않지만, 보고 문서가 브리핑을 재인용하며 수치를 굳히면 이후 대사 기능 설계가 잘못된 기준선을 물려받는다.

결함 재수정은 없었다 — 그 사유

CP5 는 결함을 찾으면 그 자리에서 고치고 재검증하는 단계인데, 이번에는 재수정 항목이 발생하지 않았다. 수정 전 재현을 샌드박스에서 따로 하지 않은 것도 의도된 선택이다 — 디렉토리형 자원이 지워지지 않는다는 사실은 개발 머신의 실측 22 GB 가 이미 입증했으므로, 샌드박스는 수정 후 동작 검증에 집중했다. 다만 구현 도중 계획보다 강화한 지점이 하나 있고, 이는 §3 에 반영했다.

잔존 한계와 후속

  • 정리 실패의 가시성은 여전히 경고 로그뿐이다. best-effort 를 유지했으므로, 실물 정리가 실패하면 사용자 화면에는 아무 흔적이 없다. 이 한계는 휴지통 대사 기능이 생길 때까지 유지된다 — 그 기능이 MK4 개선 캠페인의 커버리지 축이 되고, 발견 브리핑이 제안한 진단 축 0 "화면에 뜨지 않는 불일치가 존재하는가" 의 본 해소다. 쟁점은 "휴지통은 수색 제외" 라는 기존 결정을 지키면서 대사만 얹는 경계 설계다.
  • 이미 이탈한 실물의 소급 정리는 범위 밖이다. 본 수정은 신규 발생을 멈출 뿐이다. 개발 머신 분은 수동 처리가 끝났고, 실서버 잔재 조사는 대사 기능의 입력으로 미룬다.
  • 경로 필드의 Value Object 화는 엔티티 · 스키마 무변경 전제를 깨므로 이연했다(§10).
  • CLAUDE.md 수정 없음 · 동반 수정 페이지 없음 — 새 규약 · 새 인벤토리 계열 · 새 디렉토리가 생기지 않았다.
  • CP7 사용자 브라우저 E2E 대기. dev 병합은 CP7 완료 통보 이후에 진행한다.
