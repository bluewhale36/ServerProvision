§1. 진단
실기 전 보고 : 이 보고서는 실기 검증 전에 쓴 것이다. 코드 정정과 테스트는 끝났고 실기 확인(§4)은 아직이다(2026-11-16).

요청

2026-10-23 사용자 요청이다. 설정 단계는 첫 시도에 실패했다가 다시 하면 되는 경우가 있으니, 실패하면 자동으로 다시 하게 한다(최대 3 회).

spv-01 DB 전수 조회 (11-16)

  • 10~11 월 설정 단계 실패는 7 건이고, 전부 BIOS 축의 READBACK_MISMATCH 였다. BMC 축 실패는 0 건이다.
  • 7 건 모두 재부팅 기록 뒤 36~48 초 만에 복귀로 판정됐다.
  • 정상 재부팅의 PXE 복귀는 MS74-HB0 에서 174~239 초, MS04-CE0 에서 325~346 초가 걸린다. 그래서 7 건은 모두 가짜 복귀다.
  • 다음 시도가 있던 6 건은 모두 성공했다.

원인

BeginSettingStep 이 재부팅 시각(rebootAt)을 워커 주기의 시작 시각으로 적었다. 설정 단계 동안 게스트는 iPXE 대기 루프에서 30 초마다 /boot 를 부른다. 재시작 명령보다 먼저 온 그 /boot 가 rebootAt 뒤로 잡혀 복귀로 읽혔다. 재시작이 걸린 뒤 POST 동안에는 /boot 가 오지 않는다.

결정 (CP1, 권장안으로 승인)

  • 원인을 정정하고, 자동 재시도를 더한다. 재시도 사유는 READBACK_MISMATCH 와 WRITE_REJECTED, 최대 3 회.
  • RETURN_TIMEOUT 은 재시도하지 않는다(Q-1).
  • 원인을 정정한 뒤에도 자동 재시도는 유지한다(Q-2).
  • CP1 중 사용자 지적으로 "최소 POST 60 초 하한" 장치는 뺐다. POST 중에는 /boot 가 없으므로 그 장치의 근거가 틀렸다.
§2. 구현

2-1. 바뀐 동작

무엇을어디서바뀐 뒤
재부팅 시각BeginSettingStepledger.markRebooted(row, LocalDateTime.now(clock)). 재시작 명령이 성공한 뒤의 시각이다. Clock 을 주입받는다
복귀 판정ReturnReadbackStep규칙은 그대로(lastBootAt 이 rebootAt 뒤). 주석의 오판 원인을 "진단 리눅스 체크인" 에서 "iPXE 대기 루프의 /boot" 로 정정
실패 처리BeginSettingStep, ReturnReadbackStep, BeginBmcSettingStep, ReconnectReadbackStep각자의 private fail, close 4 벌과 BeginSettingStep 이 직접 닫던 2 곳(VALUE_NOT_IN_REGISTRY, PATCH_REJECTED)을 새 협력자 SettingFailure 로 모음
자동 재시도SettingFailure재시도 가능 사유이고 회차가 남으면 SettingLedger.closeForAutoRetry 로 행만 FAILED 로 닫는다. 진행은 실패로 바꾸지 않는다. 상한 MAX_AUTO_RETRIES = 3
회차 세기SettingContext.autoRetriesUsed이 축의 FAILED 행 중 progress.lastTransitionAt 뒤에 닫힌 수. 새 컬럼 없음
시한 기점SettingContext.attemptSince, BeginSettingStep 과 BeginBmcSettingStep 의 BMC 미응답 시한lastTransitionAt 과 이 축의 마지막 닫힌 행 시각 중 늦은 쪽
설명ProvisioningProgress.clearFailed, ClockConfig Javadoc문구 정정(아래 설명)
  • 자동 재시도의 기록: 닫힌 행의 meta autoRetry 에 회차를 남기고, detail 끝에 "(자동 재시도 n/3)" 을 붙인다. 진행이 실패가 아니므로 다음 워커 주기가 새 행을 열어 축을 처음부터 다시 한다.
  • 회차의 기점: 축 진입, 운영자 재시도, 최종 실패가 lastTransitionAt 을 옮기므로 셈이 그 시점부터 새로 시작한다.
  • 시한 기점: 자동 재시도한 시도도 20 분 창을 새로 받는다. FlashContext.returnWaitSince 와 같은 결이다.
  • Javadoc: ProvisioningProgress.clearFailed 는 "실패 해제는 운영자 액션만이고, 설정 축 자동 재시도는 실패 상태를 거치지 않는다" 는 뜻으로 고쳤다. ClockConfig 는 Clock 을 쓰는 곳 목록에 BeginSettingStep 을 더했다.

2-2. HF15-7 과의 관계

HF15-7 은 한 행 안에서 BMC 항목 단위의 일시 오류를 3 번까지 다시 쓰고 넘어간다(meta retries). HF25 는 행이 실패로 닫힌 뒤 축 전체를 새 행으로 다시 한다. 새 행은 retries 를 0 부터 센다. 두 계층은 차례로 동작한다.

2-3. 재시도하지 않는 사유

사유재시도하지 않는 이유
RETURN_TIMEOUTHF24 이후 서버 전제가 깨졌다는 신호. 재시도하면 운영자 인지가 최대 1 시간 늦어짐
IDENTITY_MISMATCH다른 장비가 응답한 사건
VALUE_NOT_IN_REGISTRY템플릿 정정이 필요
AUTH_REJECTED계정 표준화가 안 된 장비
BMC_UNREACHABLE이미 20 분 기다린 뒤
PATCH_REJECTED대부분 데이터 거절
BMC_REQUIREDBMC 미검출

  • 미수행 범위: 전 항목(A1~A3, B1, B2, C1).
