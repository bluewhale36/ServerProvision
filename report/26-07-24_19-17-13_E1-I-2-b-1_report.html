§1. 무엇이 채워졌는가 (진단 대비 결과)

E1-I-2-a 의 교체는 순수 덮어쓰기였다. 새 파일이 원자적 스왑으로 옛 파일을 지웠고, 새 버전에서 부팅 실패나 버그가 나도 이전 버전으로 되돌릴 수단이 없었다. E1-I-2-a 는 이 공백을 알고 스왑 앞에 seam 을 예약해 두었다(Javadoc 이 명시). 이 슬라이스는 그 seam 을 이행한다 — 교체가 옛 파일을 덮어쓰기 전에 그 파일을 이력에 아카이브해, 추후 롤백(E1-I-2-b-2)의 재료를 남긴다.

능력E1-I-2-a 까지이 슬라이스가 채운 것
교체·재봉인원자적 스왑 + sealOne 자동 재봉인변경 없음 — 스왑 앞에 아카이브 한 단계만 삽입
이전 버전 보존없음 — 교체 즉시 옛 파일 소실자산별 최근 N개 이력 보존(기본 3, FIFO)

§2. 실현된 동작 + 비목표 확인

계획대로 구현된 5개 요구사항

#요구구현 상태
1범용 버전 저장소 global/history 완료 AssetVersionKey(최상위 record) · AssetVersion 엔티티 · AssetHistoryService(archive / list / openVersion / prune)
2비 web-served 이력 루트 완료 provision.asset.history.root 기본 /opt/provisioning/.asset-history — allowed-roots·pxe.assets.root 밖
3교체 시 자동 아카이브(seam 이행) 완료 DiagnosticAssetReplaceService.replace 의 스왑 앞에 archive(key, target) 삽입. 순서 = archive → 스왑 → sealOne
4보존 = 자산별 최근 N개 FIFO 완료 provision.asset.history.retention-count 기본 3. 초과분을 오래된 것부터 파일 + 행 삭제
5아카이브 실패 = 교체 중단 완료 AssetVersionArchiveFailedException(500) 시 스왑 전 중단 — 옛 버전 소실 방지
비 목표 (계획대로 미포함 — 후속 슬라이스로 이연)
  • 롤백 화면 · 복원(활성화) 액션 → E1-I-2-b-2. 저장소의 openVersion(key, id)(버전 바이트 경로를 여는 능력)은 b-1 에 두었으나, 그 버전을 스왑해 되살리고 재봉인하는 진단 특화 배선과 목록 UI 는 b-2 소관이다.
  • dhcpd/tftp 적용 → E1-I-3. 저장소가 범용이라 그 시점에 키만 바꿔 재사용한다.
  • 시간 기반 TTL — 이번엔 개수 기반(최근 N)만. 기간 만료는 필요 시 후속.
  • DB 보존 설정 화면 — config property 로 충분. DB 설정 엔티티는 과잉으로 판단해 도입하지 않았다.
🎬 미리보기 — 버전 저장소 시뮬레이터 (아카이브 · FIFO · 실패 시 스왑 차단)

한 자산(modloop-lts)을 반복 교체하며 옛 활성본이 이력에 쌓이고 최근 N개(기본 3)만 남는 것을 직접 본다. 「교체」마다 현재 활성본이 아카이브되고 활성본은 새 버전이 된다. N 을 넘으면 가장 오래된 버전이 FIFO 로 사라진다(파일 + 행). 「아카이브 실패 주입」후 교체하면 스왑이 진행되지 않아 활성본이 그대로 유지된다 — 옛 버전을 보존하지 못한 채 덮어쓰지 않는다는 요구사항 5 의 실제 동작이다.

보존 N :
modloop-lts 활성본
버전 이력크기해시아카이브 시각 (최근 → 오래)
↑ 롤백은 여기서 버전을 골라 되돌린다(b-2). 활성본은 이력에 없다 — 다음 교체 때 아카이브된다.
드리프트 0 — 시뮬레이터의 교체 순서(archive(복사→기록→prune) → 스왑 → sealOne)와 FIFO 규칙(count − N 초과분을 id 오름차순으로 삭제)은 §4 의 서버 구현(AssetHistoryServiceImpl · DiagnosticAssetReplaceService)과 1:1 이다. 아카이브 실패 시 스왑·재봉인을 실행하지 않는다.

§4. 도메인 모델 (구현)

AssetVersionKey — 도메인 무관 자산 식별 (최상위 record)

(category, name) 두 문자열로 한 자산의 버전 계열을 가리킨다. 진단 자산은 ("DIAGNOSTIC", "modloop-lts"), 나중 PXE 인프라는 ("PXE", "dhcpd.conf"). global.trash.ResourceKey 처럼 최상위 record 인데, Hibernate JPQL 의 new <fqcn>(...) 생성자 투영이 중첩 record 로는 해석되지 않아 그 선례를 그대로 따랐다.

FIFO 보존 규칙 (DriftReport prune 미러)

long over = countByCategoryAndName(cat, name) - retentionCount;   // 초과분
if (over > 0) {
    Page<AssetVersion> oldest = findByCategoryAndNameOrderByIdAsc(cat, name, PageRequest.of(0, (int) over));
    // 파일 먼저 삭제 — 삭제 실패는 로그만(고아 파일 무해), 행은 반드시 지워 카운트를 정확히 유지
    for (v : oldest) Files.deleteIfExists(root.resolve(v.archivedRelPath()));
    deleteAll(oldest.getContent());
}
// retentionCount = provision.asset.history.retention-count (기본 3)

§5. 채택한 설계 결정 (채택안 · 비채택 대안 · 탈락 사유)

CP1 plan 이 복수 대안을 비교해 확정한 결정을 코드가 그대로 실현했다. 아래는 채택안과 함께 탈락한 대안·사유를 남긴다.

① DB 엔티티 — 채택

  • AssetVersion 관계형 로그. 목록·정렬·개수·FIFO·소유권 조회에 유리
  • PurgeLog·DriftReport(append-only 로그) 선례 계승

① 대안 — 탈락

  • 마커 사이드카 / 파일시스템만
  • 순서·개수·정리 쿼리가 clunky, 소유권 조회 불리

② id(IDENTITY) = 순서 — 채택

  • 자동 증가 PK 가 삽입 순서를 단조·유일하게 담음
  • OrderByIdDesc(최신)·OrderByIdAsc(FIFO) 겸용

② 대안 — 탈락

  • per-asset seq 컬럼
  • max+1 조회 + 동시 아카이브 경합. id 로 충분

③ 아카이브 실패 = 중단 — 채택

  • 보존 못 하면 덮어쓰지 않음(fail-closed)
  • "롤백 가능하도록 보존" 요구와 정합

③ 대안 — 탈락

  • best-effort 아카이브 후 교체 강행
  • 보존 없이 스왑 = 롤백 자산의 조용한 손실

④ archived_at 명시 컬럼 — 채택

  • append-only 라 BaseTimeEntity 의 updated_at 무의미
  • PurgeLog 선례, timestamp(6) µs

⑤ FK 없음 · 문자열 키 — 채택

  • 도메인 무관 저장소라 자산 테이블에 결합하지 않음
  • AssetVersionKey(top-level record)로 시그니처·JPQL 전달

⑥ 비 web-served 격리 루트 — 채택

  • pxe.assets.root 밖 + allowed-roots 밖
  • 옛 버전이 게스트에 서빙되거나 reconciliation 스윕에 ORPHAN 으로 오탐되지 않음

⑦ SHA-256 유틸 승격 — 채택

  • private sha256File → 공용 FileDigest.sha256
  • 무결성·이력이 동일 해시 공유(E1-I-1/2-a 회귀 없음)

⑧ archive = 복사(move 아님) — 채택

  • 아카이브 시점의 현재 파일은 아직 활성본
  • 복사 → 행 저장 순서라 행은 항상 실재 파일을 가리킴

SHA-256 승격 — 전후 대조

BEFORE (E1-I-2-a)

// DiagnosticAssetIntegrityService
private String sha256File(Path p) { ... }
// 이 서비스만 사용 — 이력 저장소는 별도 필요

AFTER (b-1)

§6. 불가침 원칙 점검
원칙점검 결과
Primitive Obsession 금지 준수 자산 식별은 String cat, String name 를 흩뿌리지 않고 AssetVersionKey record 로 타입화해 시그니처·JPQL·상수에 일관 전달. 단, 저장소가 도메인 무관이라 category/name 은 의도적으로 원시 문자열이다 — 저장소는 어떤 자산이든 몰라야 하므로 도메인 enum 을 두지 않는다(값 자체는 AssetVersionKey 로 묶임).
네이밍 규칙 준수 AssetHistoryService(인터페이스) / AssetHistoryServiceImpl(service/internal) / AssetVersionRepository / AssetVersion(엔티티) / *Exception. 하우스 스타일(인터페이스 + internal 구현) 준수.
레이어 경계 준수 이 슬라이스는 컨트롤러·DTO 가 없다(엔드포인트 무추가). Service ↔ Repository 는 AssetVersion 엔티티 직접 사용, 도메인 무관 식별은 record. 뷰에 엔티티 노출 없음.
@Transactional 경계 준수 archive/prune = 쓰기, list/openVersion = readOnly. 모두 Service 경계에 위치. archive 내부에서 같은 트랜잭션으로 prune 을 자기 호출한다(프록시 우회는 의도된 동작 — 하나의 원자 단위로 복사·기록·정리).
조건분기 legacy 확장 금지 준수 도메인 invariant if-throw(파일 부재 → empty, 소유권 불일치 → 예외)만 사용. 분기 줄로 책임을 늘리지 않았다.
중복 금지 준수 SHA-256 중복을 FileDigest 로 승격해 무결성 서비스와 이력 저장소가 공유. FIFO prune·경로 합성은 DriftReport·TrashPolicy 관례를 재사용.

회귀 위험

  • 낮음 — 교체 흐름에 아카이브 한 단계만 스왑 앞에 얹었고, 아카이브 부재 시(최초 생성 교체) no-op 이라 기존 교체 경로는 불변. E1-I-2-a 회귀 7건 전부 green.

  • 디스크 사용량 — 자산별 최근 N개(기본 3). modloop 약 198MB × 3 ≈ 600MB/자산. 이력 루트는 자산 루트와 별개 볼륨 배치 가능(설정 분리).
