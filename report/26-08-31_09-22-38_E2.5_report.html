§1. 진단 — 왜 이 슬라이스인가 (실측 근거)
한 줄 요약 — 엔진이 게스트 전원을 넣거나 재부팅하기 직전에 Redfish 로 “다음 한 번은 PXE”(Once · Pxe · UEFI)를 무장해, 디스크에 OS 가 남은 서버도 부트 순서와 무관하게 프로비저닝 서버로 돌아오게 했다. 하네스 검증 10/10 PASS.

실기에서 실제로 벌어진 일

2026-08-27 실기 검증에서 OS 가 남아 있는 서버(아이티인포 (하) MD72-HB3)를 대상으로 BMC(Baseboard Management Controller — 보드 관리 컨트롤러) 펌웨어를 구운 뒤 PowerOnStep 이 전원을 넣었다. 서버는 프로비저닝 서버로 돌아오지 않고 디스크의 OS 로 부팅했고, 20분 복귀 시한이 만료돼 원장에 RETURN_TIMEOUT 이 기록됐다. 첫 PXE(Preboot Execution Environment — 네트워크 부팅) DHCP 요청은 그로부터 35분 뒤, 운영자가 콘솔에서 F12 로 수동 재시작한 시점에야 들어왔다. 그 보드의 실측 부트 순서는 FBO101='Hard Disk' 가 1순위였다.

이 결손이 그동안 드러나지 않은 이유는 대상이 대부분 빈 서버였기 때문이다. 디스크에 부팅 가능한 OS 가 없으면 디스크 부팅이 실패하고 부트 순서 폴스루로 PXE 에 떨어져, 결과적으로 돌아왔다. U6 회수 서버 재투입이 열리면서 OS 가 남은 서버를 다시 프로비저닝하는 경우는 늘어난다.

수동 설정으로는 성립하지 않는다. “랙킹할 때 BIOS 에서 PXE 를 1순위로 잡아 두면 되지 않나” 는 3호 실측(2026-08-19)이 이미 반증했다 — 펌웨어 flash 가 BIOS 설정을 기본값으로 되돌린다. 사람이 잡아 둔 부트 순서는 flash 한 번에 무효가 되므로, 부팅 직전에 시스템이 매번 다시 지정하는 길만 남는다.

강제 수단은 새로 발명한 것이 아니라 E0-4-1 이 실기에서 받아 둔 Systems/Self 전문에 이미 들어 있던 것이다. 아래가 그 전문에서 이번 구현이 근거로 삼은 필드다.

§2. 구현 — 무엇을 어디에 (plan D-1~D-10 이행)

plan 이 확정한 결정 D-1~D-10 을 코드로 옮긴 결과다. 결정 하나마다 어디에 어떤 형태로 앉았는지를 적는다.

결정이행
D-1 자리RedfishPowerService 안 — powerOnAndVerify(target, NextBoot) 와 reset(target, type, NextBoot) 로 무장 → 발행 순서를 고정했다. 화면이 쓰는 2-arg reset 은 AS_CONFIGURED 로 위임하므로 PATCH 가 나가지 않고 응답 문구도 바뀌지 않는다
D-2 의도NextBoot enum — 상수별 arm 구현. PXE_ONCE 가 Boot{Once · Pxe · UEFI} 바디 상수를 들고 있고, AS_CONFIGURED 는 아무 것도 하지 않는다
D-3 경로Systems/Self 직접 PATCH + If-Match 사다리(* 로 먼저 시도, 412 면 fresh ETag 를 받아 재시도). 사다리는 RedfishBiosService.patchPending 에 있던 것을 RedfishClient.patchJsonRefreshingEtag 로 추출해 공유했다(두 번째 사용처)
D-4 거절RedfishError.resourceSpecific()(상수 속성)로 경계를 그었다. 리소스 단위 거절은 BootOverrideOutcome.REJECTED 로 WARN 을 남기고 전원 명령은 계속, 연결 불가 · 자격증명 실패는 기존 FAILED · 폴백 경로를 그대로 탄다. PATCH 뒤 되읽기는 판정이 아니라 관찰이며 결과를 APPLIED / UNCONFIRMED 로 나눠 접두로 붙인다
D-5 시점전원 호출마다 직전 1회. PowerCycle 폴백으로 넘어갈 때는 폴백 직전에 다시 무장한다 — 앞선 시도로 Once 가 소진됐을 수 있기 때문이다
D-6 범위E2 의 PowerOnStep 과 E3 의 BeginSettingStep 둘만. 화면 전원 제어 · 진단의 REBOOT 지시 · FORCE_OFF 는 제외
D-7 동반FlashContext.returnWaitSince() 를 max(마지막 축 종료, 마지막 전이) 로 정의했다. 운영자가 clearFailed 로 재시도하면 전이 시각이 갱신되므로 복귀 대기 창이 다시 열린다. 종전 기점인 lastAxisClosedAt() 은 private 으로 봉인했고 guestReturned() 도 같은 기점을 쓴다
D-8 실기 판정 재료미실측 4건(K1-b · K1-d · Mode 필요 여부 · flash 뒤 flag 잔존)은 코드가 답하게 했다 — 무장 결과(APPLIED / UNCONFIRMED / REJECTED + 사유)가 결과 메시지 · 로그에 남아 CP7 실기의 판정 재료가 된다
D-9 · D-10PowerControlResult 필드 추가 0 · 원장 사유 추가 0 · 컬럼 · DDL 추가 0 · 설정 키 추가 0. 무장 결과는 기존 결과 메시지의 접두로만 드러난다

다른 스트림과 겹치지 않도록 포트를 전부 분리했다 — DB spv-sandbox-db-e25(3347, 로컬 3306 덤프에 DDL 6종을 --force 로 얹음) · 애플리케이션 sbx-e25/app.jar(7828 · Java 21) · 모의 BMC 8463. 대상 게스트는 MS03-CE0(모의 시리얼 QG260700082 · BMC 주소 127.0.0.1)이고 FW_UPDATE 와 BASIC_SETTING 을 할당했다. 실측 시한을 그대로 쓰면 한 항목에 20분이 걸리므로 복귀 시한은 2분, flash 워커 주기는 5초로 압축했다.

§5. CP5 수행 기록 — 10/10 PASS (증거 1:1)

A1 — 정상 E2 흐름 (무장 → PXE 복귀 → 반영 확인 → 전진)

조작: 게스트에 FW_UPDATE 를 할당하고 프로비저닝을 개시해, 굽기가 끝난 뒤 PowerOnStep 이 전원을 넣는 지점까지 하네스로 진행했다.
관찰: 모의 BMC 의 bootPatches 에 ifMatch "*" 와 {Once · Pxe · UEFI} 한 건이 기록됐고, 애플리케이션 로그는 “다음 부팅 PXE 강제 : 반영 확인” 접두를 붙여 전원 투입을 남겼다. 모의 게스트는 bootedVia = Pxe 로 부팅해 /boot 로 복귀했고, VerifyFlashStep 이 “반영 확인 완료” 를 찍은 뒤 BIOS_SETTING 으로 전진했다. 축이 둘(BIOS · BMC)인 첫 시도(08:50:55)와 축이 하나인 다른 게스트(08:53:29) 모두 같은 무장을 냈다.

A3 — If-Match 사다리

관찰: 모의 HTTP 로그에 PATCH 412 → GET → PATCH 204 가 순서대로 남았고, 실제 기록된 ifMatch 는 * 가 아니라 새로 받은 W/"7000" 이었다 — 사다리가 fresh ETag 로 갈아타 재시도했다는 뜻이다. plan 이 적어 둔 기대치(“bootPatches 2건”)와 다른 점은 §6 F-2 에서 정정한다.

A4 — pending 경유

조작: 모의 BMC 를 boot-override-pending 모드로 두었다. PATCH 는 받아들이되 Systems/Self 의 Boot 는 즉시 바뀌지 않고 pending 리소스에만 쌓이는, T3 K1-d 가 미실측으로 남긴 그 경우다.

§6. 검증 중 발견한 것 — 관찰 5건과 세션 판정

하위 에이전트는 발견을 고치지 않고 재현 기록과 함께 보고했고, 무엇을 고치고 무엇을 그대로 둘지는 세션이 판정했다. 다섯 건 중 코드 · 하네스를 손댄 것은 F-1 하나다.

F-1 — 모의 BMC 에 GET Managers/Self 가 없었다 세션이 정정

관찰: VerifyFlashStep 의 BMC 축이 “읽지 못함” 으로 실패했다. 원인은 제품 코드가 아니라 하네스 쪽 결손이다 — E2-3 이후 BMC 버전 판독 원천이 Managers/Self.FirmwareVersion 으로 옮겨졌는데(커밋 abfd28d) 모의 BMC 가 그 엔드포인트를 따라가지 못한 드리프트였다.
처리: 세션이 모의 BMC 에 해당 엔드포인트를 추가해(STATE['inventory']['BMC'] 반환) 재기동하고 curl 로 {"FirmwareVersion":"13.06.26"} 를 재검증했다. CP5 자체는 BMC 축 자원을 비활성으로 두어 SKIPPED 시킨 뒤 BIOS 축만으로 완주했는데, 두 축이 함께 있는 상태의 PowerOnStep 무장은 첫 시도(08:50:55)에서 이미 확인됐으므로 E2.5 검증에는 결손이 없다.

F-2 — plan 의 A3 기대치가 모의 구현과 어긋났다 기대 문구 정정

관찰: plan §9 의 A3 는 “bootPatches 2건” 을 기대했지만 실제로는 1건만 남는다. 모의 BMC 가 412 를 기록하기 전에 반환하기 때문이고, 이는 기존 BIOS 쪽 patch-412-once 모드와 같은 구조다.
처리: 모의 구현은 그대로 두고 기대 문구를 “기록 1건(fresh ETag) + 모의 HTTP 로그의 412 → 204” 로 정정했다. 이 report 의 A3 서술이 정정본이다. 사다리가 동작했다는 증명은 기록된 ifMatch 값이 W/"7000" 이라는 사실이 이미 담고 있다.

F-3 — B2 는 무장 코드에 닿기 전에 멈춘다 설계대로 · 기록만

관찰: 연결이 끊긴 상태에서 엔진은 무장보다 앞에 있는 신원 확인(BmcIdentityGuard — Chassis 도달 실패를 UNREACHABLE 로 판정)에서 이미 멈춘다. 따라서 NextBoot.arm 이 연결 실패를 다시 던지는 가지는 엔진 경로에서는 도달하지 않는다.
판정: 설계대로다 — 되돌릴 수 없는 조작 앞에 신원 확인을 두는 것이 D-11 의 요지이므로, 무장이 그 뒤에 있는 것이 옳다. 그 가지의 검증은 단위 테스트 pxeOnce_connectFailureBlocksReset 이 담당한다. 신원 확인을 거치지 않는 화면 경로에서는 여전히 실경로다.

F-4 — 재시도가 전원 사이클을 한 번 더 돈다 E2-4 로 적립

관찰: 운영자가 [재시도] 를 누르면 BeginFlashStep 이 다시 실행된다. clearFailed 가 motion 을 AWAITING_BOOT 로 되돌려 beforeStart() 가 참이 되기 때문이다. 다시 굽지는 않지만 ForceOff 가 한 번 더 나갔다(09:05:00 차단 → 09:05:08 투입).
판정: E2.5 와 무관한 ES-2 · R13 의 재개 규칙이다. 결과적으로 깨끗한 전원 상태에서 다시 시작하게 되는 이점도 있지만, 재시도마다 전원 사이클이 도는 것이 의도인지는 따로 판정할 문제다 — 집행 현황 상세화(E2-4 O-3)와 함께 판정하도록 §8 남은 일에 올렸다.

F-5 — 굽는 중에는 화면 전원 버튼이 먼저 막힌다 설계대로 · 기록만

관찰: flash 가 진행 중일 때 게스트 서버 상세의 전원 버튼 4개가 disabled 였고, 같은 요청을 직접 POST 로 보내면 409 로 거절됐다. UI 1차 차단과 서버 가드가 powerControlBlockReason 이라는 같은 SSOT(Single Source of Truth — 단일 진실 출처) 를 공유한다는 뜻이다.
판정: R13 후속 가드가 의도대로 동작함을 실지 확인한 것이라 기록만 한다.

부수 수확 — 샌드박스 레시피 갱신(누적 메모리 반영 완료)
  • PROVISION_MARKER_SECRET 은 dev 기본값이어야 한다 — 임의 값을 주면 서명 검증이 실패해 자원이 BLOCKED 로 뜬다.
  • PROVISION_BIOS_MATERIALS_DIR 가 없으면 상세 화면이 500 으로 끊긴다.

§7. 미수행 항목과 사유

계획한 10 항목은 모두 수행했다. 대신 “이번에 하지 않고 넘긴 것” 이 셋 있으며, 감추지 않고 사유와 함께 적는다.

BMC 축을 포함한 두 축 완주 재실시

F-1 정정(모의 BMC 의 Managers/Self 추가)은 curl 재검증까지만 하고 두 축 완주를 다시 태우지는 않았다. 두 축이 걸린 상태의 무장 자체는 08:50:55 실측으로 확인됐고, BMC 축의 반영 확인은 E2-2 의 검증 대상이지 이번 슬라이스의 항목이 아니기 때문이다. 다음 E 슬라이스의 CP5 가 이 경로를 자연히 밟는다.

실기에서만 확인 가능한 4건

모의 BMC 로는 “그렇게 동작하게 만든 것” 이상을 증명할 수 없는 항목들이다. CP7 실기 일괄(E 단계 CP7 합의) 소관으로 넘긴다.

  • K1-b — 실기 BMC 가 Once · Pxe · UEFI PATCH 를 수락하는가, 그 뒤 실제로 PXE 로 진입하는가, Once 가 한 번에 소진되는가
  • K1-d — 직접 반영인가 Systems/Self/SD 경유인가, If-Match 는 필요한가
  • Mode 를 UEFI 로 명시하는 것이 실기에서도 필요한가
  • BMC flash 뒤에 이 플래그가 잔존하는가

코드가 남기는 결과 로그(APPLIED / UNCONFIRMED / REJECTED)가 그대로 판정 재료가 되도록 해 두었다 — 실기에서 따로 계측할 필요 없이 로그만 읽으면 된다.

브라우저 검증의 범위

관리자 화면 변경이 없는 슬라이스라, 브라우저 확인은 E 단계 예외 규율대로 게스트 서버 상세 페이지 확인(A1 · A2 · A5 · B1 · F-5 의 스크린샷 6장)에 한정했다. 나머지 항목은 모의 BMC 상태 덤프와 애플리케이션 로그가 증거다.
