§1. 배경 · 진단

이 슬라이스의 자리 — E3.5 계열의 마지막 한 칸

바로 앞 슬라이스 E3.5-3 은 계획을 실제로 카드에 새기는 손을 붙였지만, 한 가지를 못 한 채로 끝났다. 카드에 우리가 만들지 않은 볼륨(외부 기존 볼륨)이 남아 있으면 집행하지 않고 보류했다. 그 볼륨을 지워도 되는지 물어볼 자리가 정의서에 없었기 때문이다. 원장에는 그 사정이 POLICY_UNDECIDED 라는 사유로 남았고, 사유 문구 자체가 “축이 도입되면 풀린다” 고 예고하고 있었다.

E3.5-4 는 그 축을 정의서에 만들어 보류를 걷어내는 슬라이스다. 다만 축 하나만 만들고 끝내지 않고, E3.5 계열이 남긴 인계 쪽 잔여를 함께 닫았다. 세 갈래다.

CP1 검수가 증보를 하나 더 붙였다 — 볼륨 WWN

계획 검수 중 사용자의 질문이 간극을 하나 드러냈다. RAID 볼륨을 만들어 두어도, OS 설치기가 그 볼륨을 어떻게 지목하는가 가 정해져 있지 않았다. 특히 Windows 의 무인 설치 응답 파일(autounattend)은 디스크를 정수 DiskID 로만 지목한다. 그 정수는 부팅할 때마다 달라질 수 있는 열거 순서이므로, 우리가 만든 볼륨을 안정적으로 가리키는 열쇠가 될 수 없다.

그래서 볼륨의 세계 유일 식별자인 WWN 을 채집해 기록하기로 했다. WWN 자체를 응답 파일에 넣는 것이 아니라, 설치 직전 WinPE 단계에서 WWN 으로 디스크를 조회해 그 시점의 DiskID 를 알아내는 조회 키로 쓴다. Linux 계열은 WWN 경로를 직접 받으므로 이 값이 그대로 쓰인다.

이 증보가 없었다면 어디서 드러났을까. E4 의 OS 설치 슬라이스에 가서야 “설치 대상 디스크를 무엇으로 지목하나” 라는 질문이 나왔을 것이고, 그때는 이미 지나간 진단 단계로 되돌아가 채집을 다시 붙여야 했다. 채집은 인벤토리를 읽는 시점에만 가능하기 때문이다.

Q2 미리보기가 축을 모를 때 무엇을 보여주나“보존이면 이렇게 · 파괴면 저렇게” 두 갈래를 병기하지 않고, 남은 것이 우리 것뿐이면 정책과 무관하게 결과가 하나이므로 단일 갈래로 통일한다항상 두 갈래 병기 — 실제로는 결과가 같은데도 사용자에게 고르게 만들어 혼란만 준다

Q1 이 중요한 이유는 재집행 때문이다. 우리가 앞서 만든 볼륨은 남의 데이터가 아니라 재구성 대상이다. 이 구분이 없으면 한 번 집행한 게스트는 두 번째부터 영원히 보류에 걸린다.

CP4 는 검수 없이 승인됐다. 사용자가 코드 검수 대신 “승인.” 으로 통과시켰으므로, 이 슬라이스에서 설계를 바꾼 지적은 전부 CP1 시점의 것이다(§7).

R1 — 축은 정의서 어휘로 두고, 값이 없는 저장본을 관용한다

선택지는 둘이다. 보존은 카드에 남아 있는 외부 기존 구성을 지키고, 파괴는 전부 삭제한 뒤 이 정의서대로 재구성한다. 기본값을 두지 않은 필수 선택이다 — 되돌릴 수 없는 삭제를 기본값으로 슬쩍 넣지 않는다.

PRESERVE("기존 구성 보존") · DESTROY("기존 구성 파괴") ← 화면 라벨은 U 도메인이 소유

실행측에도 같은 뜻의 타입이 있지만 정의서 어휘는 U 도메인이 따로 갖는다. 정의서를 직렬화한 결과가 실행 타입의 이름에 묶이면, 실행측이 이름을 바꾸는 순간 이미 저장된 정의서가 읽히지 않는다.

필수 선택이지만 무조건 필수는 아니다. RAID 로 묶는 규칙이 하나도 없는 정의서는 기존 구성을 건드릴 일이 없으므로 고를 것이 없다. 그래서 “RAID 묶음이 있으면 필수” 라는 조건부 검증(@AssertTrue)으로 뒀고, 폼의 잠금 조건과 서버 판정이 같은 재료를 본다. 그리고 축이 생기기 전에 저장된 정의서는 값이 null 인데, 이 값을 거절하지 않고 관용한다 — 기존 저장본이 갑자기 열리지 않게 되는 것이 축 도입의 대가가 되어서는 안 된다. 요청 객체에는 3-인자 보조 생성자를 두어, 축을 모르는 기존 호출 15 곳 이상이 그대로 컴파일된다.

R2 — 폼은 서버 판정을 미러하고, 고를 필요가 없을 때는 잠근다

세 가지가 붙었다.

  • 라디오는 기본 미선택이다. 미리 하나를 켜 두면 사용자가 고른 것과 시스템이 정해 준 것이 구분되지 않는다.
  • 구 저장본을 열면 값을 임의로 주입하지 않고 경고만 띄운다. null 인 축에 파괴든 보존이든 아무 값이나 채워 넣으면, 사용자가 선택하지 않은 값이 저장된다.
  • RAID 묶음이 하나도 없으면 라디오를 잠근다(applyExistingPolicyLock). 고를 필요가 없는 선택지를 열어 두면 사용자는 무엇을 골라야 할지 고민하게 된다 — 잠그면서 왜 잠겼는지 함께 알린다.

여기에 사각 규칙 실시간 미러(coversRule)가 더해졌다. 저장을 눌러야 알 수 있는 거절을 입력하는 동안 보여 준다. 미러가 서버와 다른 판정을 하면 그것 자체가 새 결함이므로, 서버 진리표와 드리프트 0 임을 코드 주석으로 못 박아 두었다.

R3 — 사각 규칙 : 겹침은 막지 않고 “완전히 가려진 것” 만 막는다

디스크 그룹 규칙은 위에서부터 순서대로 디스크를 흡수한다. 그래서 규칙끼리 조건이 겹치는 것 자체는 정상이다 — 앞 규칙이 다 가져가고 남은 것을 뒤 규칙이 받는 “후행 흘림” 이 동작 원리다. 문제는 후행이 볼 수 있는 경우의 수가 남김없이 선행에 덮이는 때다. 그 규칙은 어떤 디스크 구성에서도 발동하지 않는다.

그래서 종류 · 전송 · 용량 세 축이 전부 선행 ⊇ 후행이고, 개수의 수용집합까지 덮일 때만 거절한다. 개수 수용집합은 E3.5-2 결정 6 의 엄격 일치 기준을 그대로 쓴다 — EXACT n 의 수용은 {n}, AT_LEAST m 의 수용은 {m, m+1, …}. 여기서 포섭이 성립하는 형태는 셋뿐이다.

AT_LEAST m ⊇ AT_LEAST n (m ≤ n) AT_LEAST m ⊇ EXACT n (m ≤ n) EXACT n ⊇ EXACT n (같을 때만)

거절 문구는 무엇이 잘못됐는지가 아니라 무엇을 하면 되는지까지 말한다.

{후행}번 묶음은 {선행}번 묶음에 가려 도달할 수 없습니다 — 순서를 바꾸거나 조건을 좁히십시오.

R4 — 축을 실행측으로 넘기고, 보존 + 외부는 보류가 아니라 실패다

정의서의 축은 확장점(SPI — Service Provider Interface, 도메인이 구현해 끼우는 자리)의 policyOf 로 실행측에 전달된다. 구현체는 정의서 enum 을 실행측 enum 으로 1:1 번역만 한다. 실행기의 판정은 축의 유무로 갈린다.

가운데 줄이 이번 슬라이스의 판정 변화다. 사용자가 명시적으로 “보존” 을 골랐는데 카드에 외부 볼륨이 남아 있으면, 이 정의서로는 새 구성을 만들 수 없다는 것이 확정된다. 기다린다고 풀리지 않는다 — 사용자가 정의서를 고치거나 카드를 정리해야 한다. 그래서 보류가 아니라 실패로 승격한다(0-3 결정 D-7 원문). 반면 축이 null 인 구 저장본은 사용자가 아직 고르지 않은 상태이므로, 편집해 저장하면 저절로 풀린다 — 그래서 보류를 유지한다.

보류와 실패를 가르는 기준은 “가만 두면 풀리는가” 다. 풀릴 수 있는 상태를 실패로 찍으면 진행률에 낙인이 남아 운영자가 게스트를 버리게 되고, 풀리지 않는 상태를 보류로 두면 30 초마다 같은 판정을 되풀이하며 영원히 대기한다.

R5 — “우리 것” 을 판별하는 자리를 하나로 모았다

이름이 spvR 로 시작하면 우리가 앞서 만든 볼륨이다. 이 판단이 계획 산출 · 실행 판정 · 화면 미리보기 세 곳에서 필요한데, 세 곳에 각자 쓰면 기준이 갈린다. RaidExistingVolume.isProvisionOwned() 하나로 모으고 셋이 그것을 부른다.

계획 산출 쪽은 이 판별로 정밀해졌다. 종전에는 볼륨이 남아 있기만 하면 보존 정책에서 거절했는데, 이제 외부 볼륨이 있을 때만 거절한다. 그리고 선행 삭제 여부(deleteExistingFirst)는 잔여가 하나라도 있으면 참이다 — 우리 것이라도 재구성하려면 먼저 지워야 하기 때문이다.

세 번째가 Q2 판정의 실물이다. 우리가 만든 볼륨만 남은 카드라면 보존을 고르든 파괴를 고르든 재구성 결과는 같으므로, 두 갈래를 병기하는 것은 정보가 아니라 소음이다.

R7 — WWN 은 채집 · 매칭 · 기록 · 조회 넷이 한 줄로 이어진다

파서 채집 ──▶ RaidExistingVolume.wwn ──▶ 검증 매칭된 실물의 wwn ──▶ raid_volume.wwn ──▶ E4 조회

채집 원천은 계열마다 다르다. MegaRAID 는 VD{N} Properties 블록의 SCSI NAA Id 이고, IR 계열은 Volume wwid 다. 이름을 내지 않는 계열이 있으므로 노출하지 않는 카드에서는 NULL 이며, 기록은 검증에서 계획과 짝지어진 실물의 값을 쓴다 — 채집한 값을 아무 데나 붙이지 않는다.

E4 가 쓸 조회 계약은 findFirstByGuestServer_IdAndVolumeRole 이다. “이 게스트의 OS 역할 볼륨” 하나를 찾는 형태이므로, 설치 슬라이스는 볼륨 이름이나 슬롯을 몰라도 설치 대상을 지목할 수 있다.

R8 — 화면 둘

  • 정의서 상세에 축 행이 붙는다. 값이 없는 구 저장본은 빈칸이 아니라 “미지정 — 구 저장본” 으로 표기하고, 편집해 저장하면 선택이 필요함을 함께 알린다.
  • 게스트 상세에 “RAID 구성 실물” 표가 붙는다. 계획이 아니라 검증을 통과해 지금 카드에 있는 것이며, OS 역할 배지와 WWN 열을 함께 보여준다.
화면이 계획과 실물을 구분해 보여주게 됐다. E3.5-2 가 만든 미리보기는 “이렇게 만들 것이다” 이고, 이번 표는 “이렇게 만들어져 있다” 다. 둘이 한 화면에 나란히 있으므로 어긋남이 눈에 보인다.

정상 흐름 A — 항목별 확인 대상

  • A1 축 선택 저장 — RAID 묶음이 있는 정의서를 새로 작성하면서 축 라디오를 고르고 저장한다. 라디오가 기본 미선택으로 시작하는가, 고른 값이 실제로 요청에 실려 저장까지 도달하는가.
  • A2 상세 축 표시 — 저장한 정의서의 상세 화면에 축이 선택한 값 그대로 나오는가. 저장은 됐는데 화면에 안 보이면 사용자는 자기가 무엇을 골랐는지 확인할 방법이 없다.
  • A3 실물 표 — 집행 · 검증을 완주한 게스트의 상세에 “RAID 구성 실물” 표가 뜨고, OS 역할 배지와 WWN 이 함께 보이는가. R7 이 만든 채집 → 기록 → 표시의 한 줄이 화면 끝까지 이어지는지 보는 항목이다.
  • A4 미리보기 단일 갈래 — 축이 없는 게스트인데 남은 볼륨이 우리 것뿐일 때, 미리보기가 두 갈래를 병기하지 않고 단일 계획을 보여주는가. Q2 판정이 화면에서 실제로 그렇게 나타나는지 확인한다.

비정상 조작 B — 항목별 확인 대상

  • B1 축 미선택 저장 — RAID 묶음이 있는 정의서에서 축을 고르지 않은 채 저장을 누른다. 조건부 필수 검증이 걸리는가, 그리고 거절 뒤에 입력한 값과 추가한 행이 보존된 채 다시 그려지는가. 거절하면서 입력을 날리면 사용자는 처음부터 다시 써야 한다.
  • B2 사각 규칙 — 선행 규칙에 완전히 가려지는 후행 규칙을 만든다. 저장을 누르기 전에 입력하는 동안 문구가 뜨는가, 조건을 바꿔 포섭이 풀리면 문구가 사라지는가. 미러가 서버 진리표와 같은 판정을 하는지를 조작으로 확인한다.
  • B4 보존 + 외부 볼륨 — 외부 기존 볼륨이 남은 카드에 보존 정의서를 붙인 게스트를 체크인시킨다. 종전처럼 보류에 머무는 것이 아니라 실패로 승격되는가, 실패 사유가 사람이 읽어 조치할 수 있는 문장인가, 그리고 화면에 그 사정이 드러나는가.

막는 방식 · 경계 C — 항목별 확인 대상

  • C1 구 저장본 — 축이 생기기 전에 저장된 정의서를 연다. 오류로 막지 않으면서, 값이 없다는 사실과 편집해 저장하면 선택이 필요하다는 안내가 함께 나오는가. 관용과 안내가 동시에 성립하는지 보는 항목이다.
  • C2 묶음 0 잠금 — RAID 로 묶는 규칙이 하나도 없을 때 라디오가 잠기고 사유가 안내되는가, 그리고 규칙을 RAID 로 바꾸는 순간 잠금이 즉시 풀리는가. “UX 모순은 UI 가 1차로 차단한다” 는 원칙이 실제 화면에서 지켜지는지 확인한다.
식별자에 B3 은 없다. 계획 단계에서 비정상 항목은 B1 · B2 · B4 셋으로 확정됐고 B3 번호는 쓰이지 않았다. 결번이며 누락이 아니다 — §5 의 수행 기록도 같은 9 개 식별자로 대조된다.
§5. CP5 수행 기록 (9/9 PASS — 스크린샷 15 장)

계획한 9 항목을 전부 수행했고 9 건 모두 PASS 다. 항목마다 조작 · 기대 · 실제 · 판정 네 단으로 풀고, 실제 란에는 화면에 뜬 문구와 데이터베이스에 남은 행 · 원장 원문을 그대로 싣는다. 스크린샷은 각 항목의 수행 기록 옆에 붙는다.

C2 — 고를 필요가 없을 때는 잠그고, 필요해지는 순간 푼다

조작 : 새 정의서 폼에서 디스크 그룹 규칙을 RAID 로 묶지 않는 형태로만 둔 채 축 라디오의 상태를 확인하고, 이어서 한 행을 RAID1 로 전환했다.
기대 : 묶음이 없는 동안 라디오는 잠겨 있고 왜 잠겼는지 안내가 붙는다. RAID 로 바꾸는 순간 잠금이 풀리고 안내는 사라진다.
실제 : 라디오가 비활성 상태로 표시되며 아래 문구가 함께 떴다.

RAID 를 구성하는 묶음이 없어 선택이 필요하지 않습니다

RAID1 행으로 전환하자 같은 화면에서 즉시 라디오가 활성으로 바뀌고 안내 문구가 사라졌다.

판정 : PASS — 막는 방식이 온당하다. 고를 수 없는 선택지를 열어 두고 저장 시점에 거절하는 대신, 애초에 고를 필요가 없다는 사실을 화면이 먼저 말한다. 그리고 필요해지는 순간 사용자가 페이지를 새로 고치지 않아도 즉시 풀리므로, 잠금이 작업을 방해하지 않는다. 폼의 잠금 조건과 서버의 조건부 필수 검증이 같은 재료(RAID 묶음의 유무)를 보기 때문에 두 판정이 어긋날 자리가 없다.

B2 — 도달할 수 없는 규칙을 입력 중에 잡아낸다

조작 : 폼의 기본 두 행(같은 조건) 상태에서 시작해, 두 번째 행의 개수 조건을 AT_LEAST 3 으로 바꾸고(선행은 AT_LEAST 2), 마지막으로 첫 행을 EXACT 로 전환하며 문구의 등장과 소멸을 관찰했다.
기대 : 후행이 선행에 완전히 포섭되는 동안에만 문구가 뜨고, 포섭이 풀리면 사라진다. 저장을 누르기 전에 나타나야 한다.
실제 : 기본 두 행 상태에서 즉시 문구가 떴다.

2번 묶음은 1번 묶음에 가려 도달할 수 없습니다 — 순서를 바꾸거나 조건을 좁히십시오

후행을 AT_LEAST 3 으로 바꿔 두 규칙의 개수 조건을 다르게 만들어도 문구는 유지됐다. AT_LEAST 2 의 수용집합 {2,3,…} 가 AT_LEAST 3 의 {3,4,…} 를 여전히 덮기 때문이다.

첫 행을 EXACT 로 전환하자 문구가 사라졌다. EXACT n 의 수용집합은 {n} 하나뿐이라 후행을 덮지 못하고, 후행은 선행이 흘린 디스크로 발동할 수 있게 된다.

판정 : PASS — 미러가 서버 진리표대로 움직인다. 특히 포섭이 풀리는 방향으로 조작했을 때 문구가 사라진다는 것이 중요하다 — 겹치기만 하면 무조건 막는 구현이었다면 EXACT 전환에도 문구가 남았을 것이고, 그러면 정상적인 후행 흘림 설계까지 못 쓰게 된다. 막는 방식도 온당하다 : 저장을 눌러야 알 수 있는 거절을 입력하는 동안 알려 주고, 문구가 순서를 바꾸거나 조건을 좁히라는 다음 행동까지 지시한다.

B1 — 축을 고르지 않고 저장하면 거절하되 입력은 지키다

조작 : RAID 묶음이 있는 정의서를 작성하고 축 라디오를 고르지 않은 채 저장을 눌렀다.
기대 : 조건부 필수 검증에 걸려 필드 오류로 거절된다. 그리고 입력한 값과 추가한 규칙 행이 보존된 채 다시 그려진다.
실제 : 축 영역에 붉은 필드 오류가 붙어 재렌더됐고, 작성해 둔 값과 행은 그대로였다.

RAID 를 구성하는 묶음이 있으므로 기존 구성 처리를 선택해야 합니다.

판정 : PASS — 거절이 필드 단위로 붙어 어느 항목이 문제인지 즉시 보인다. 문구가 “필수 항목입니다” 류의 일반 문장이 아니라 왜 지금 필수인지(RAID 묶음이 있으므로)를 말하는 것도 의도대로다 — 같은 폼이라도 묶음이 없으면 필수가 아니기 때문에, 이유를 함께 말하지 않으면 사용자는 규칙이 일관되지 않다고 느낀다. 입력 보존까지 확인해 거절이 작업을 무르게 만들지 않음을 보았다.

A1 — 고른 축이 저장까지 실려 간다

조작 : B1 에서 거절된 폼에서 축 라디오로 기존 구성 파괴를 고르고 저장했다(정의서 4).
기대 : 검증을 통과해 저장되고, 고른 값이 그대로 실린다.
실제 : 라디오가 선택된 상태로 저장이 진행됐다.

판정 : PASS — 기본 미선택으로 시작해 사용자가 고른 값만 저장된다. B1 의 거절 뒤 같은 폼에서 축만 고르면 곧바로 통과했으므로, 거절이 남긴 상태에서 사용자가 이어서 작업할 수 있다.

A2 — 저장된 축이 상세에 그대로 보인다

조작 : A1 로 저장한 정의서 4 의 상세 화면을 열었다.
기대 : 축 행이 있고 값이 선택한 것과 같다.
실제 :

기존 구성 처리 : 기존 구성 파괴

판정 : PASS — 코드 값(DESTROY)이 아니라 사용자가 폼에서 본 것과 같은 라벨로 표시된다. 정의서 어휘를 U 도메인이 소유하도록 한 R1 의 결정이 화면에서 그대로 나타난다 — 폼의 라벨과 상세의 라벨이 같은 출처에서 나오므로 둘이 어긋날 자리가 없다.

C1 — 축이 없는 구 저장본을 막지 않고 안내한다

조작 : 축이 생기기 전에 저장된 정의서 1 의 상세를 열었다.
기대 : 오류로 막히지 않고 열리며, 값이 없다는 사실과 앞으로 필요하다는 안내가 함께 나온다.
실제 :

미지정 (구 저장본 — 편집해 저장하면 선택이 필요합니다)

판정 : PASS — 관용과 안내가 동시에 성립한다. 빈칸으로 두면 사용자는 화면이 깨진 것인지 값이 없는 것인지 구분하지 못하고, 오류로 막으면 축 도입 이전의 자산이 갑자기 못 쓰게 된다. “지금은 문제없지만 편집하면 골라야 한다” 는 것을 한 줄로 말해, 사용자가 다음에 무엇을 만나게 될지 미리 안다.

A3 — 게스트 상세에 실물이 WWN 과 함께 뜬다

조작 : 실물 표를 띄우려면 먼저 게스트가 집행 · 검증을 완주해 raid_volume 에 행이 남아 있어야 한다. 그래서 데이터 준비는 모의 게스트 하네스로 했다 — 집행 후 인벤토리 픽스처에 SCSI NAA Id 를 보강한 뒤 게스트(01a05a66…)로 한 바퀴를 완주시키고, 그 게스트의 상세 화면을 브라우저로 열었다.
기대 : “RAID 구성 실물” 표에 볼륨이 나오고, OS 역할 배지와 WWN 열이 채워져 있다.
실제 — 데이터베이스에 남은 행 :

spvR1V1 | OS | 600605b0…

그 값이 화면에 그대로 올라왔다 — spvR1V1 · RAID1 · 슬롯 252:0 · 252:1 · 479.6 GB · OS 영역 배지 · 상태 Optl · WWN 600605b00d18aa1e322807f9084a72aa.

판정 : PASS — R7 이 만든 파서 채집 → 검증 매칭 → 기록 → 화면 네 마디가 끊긴 데 없이 이어졌다. WWN 이 화면까지 올라온다는 것은 E4 의 조회 계약이 읽을 값이 실제로 채워졌다는 뜻이다. 픽스처에 SCSI NAA Id 를 보강해야 값이 나온다는 점도 함께 확인됐다 — 노출하지 않는 카드에서는 이 열이 비는 것이 정상이며, 그 경우에도 표는 깨지지 않는다.

A4 — 남은 것이 우리 것뿐이면 미리보기가 한 갈래로 통일된다

조작 : A3 과 같은 게스트다. 축은 null 이고 카드에는 앞서 우리가 만든 spvR1V1 만 남아 있다. 이 상태에서 계획 미리보기를 열었다. 인벤토리를 재적재한 뒤에도 같은 화면인지 함께 확인했다.
기대 : 보존 · 파괴 두 갈래를 병기하지 않고 단일 계획이 나온다.
실제 : 두 갈래 병기 대신 선행 명령 한 줄이 붙은 단일 계획이 나왔고, 규칙 소비 표가 함께 표시됐다.

선행 명령 — 기존 볼륨 전부 삭제(파괴 정책)

규칙 소비 : 매칭 2 · 소비 2 · 볼륨 1

판정 : PASS — Q2 판정이 화면에서 그대로 나타났다. 이 게스트는 축이 없으므로 규칙대로라면 두 갈래를 보여줄 수도 있는 상태지만, 남은 볼륨이 우리 것뿐이라 어느 정책을 골라도 결과가 같으므로 하나로 통일된다. 선행 삭제가 계획에 포함된 것은 R5 의 deleteExistingFirst 판단(잔여가 있으면 참)이 작동한 결과다 — 우리 것이어도 재구성하려면 먼저 지워야 한다. 인벤토리 재적재본에서도 같은 화면이 나와, 이 판단이 적재 시점에 굳은 값이 아니라 그때그때 다시 내려짐을 확인했다.

B4 — 보존을 골랐는데 외부 볼륨이 있으면 실패로 승격된다

조작 : 축을 보존으로 지정한 정의서 5 를 만들고(폼 작성은 브라우저), 외부 VD 2 개가 남은 MegaRAID 인벤토리를 가진 게스트(01a05a6a…)에 붙여 하네스로 체크인시켰다. 그 뒤 게스트 상세를 브라우저로 열어 화면에 어떻게 드러나는지 확인했다.
기대 : 종전의 보류(POLICY_UNDECIDED)가 아니라 실패로 전환되고, 사유가 사람이 읽어 조치할 수 있는 문장이며, 화면에도 그 사정이 드러난다.
실제 — 체크인 즉시 원장에 실패 행이 남았다.

RAID_APPLYING  FAILED
{"reason":"EXISTING_CONFIG","detail":"카드에 외부 기존 볼륨 2개가 남아 있습니다 — 보존 정책에서는 새 구성을 계획할 수 없습니다."}

progress : failed_at 1
이후 체크인 : 게이트 409

화면에서는 계획 섹션에 EXISTING_CONFIG 배지가 붙었고, 실물 표는 “검증 통과 전” 으로 비어 있었다.

준비 과정의 보조 컷 둘을 함께 남긴다. 보존 정의서를 작성하는 도중 RAID1 최소 2 대 기존 검증이 정상 발동했고(U4-1-1 이 만든 검증), 완성된 정의서 5 의 상세에 축이 “기존 구성 보존” 으로 표시됐다.

판정 : PASS — 판정이 보류에서 실패로 정확히 의도한 조건에서만 바뀌었다. 축이 null 인 구 저장본은 여전히 보류이고(R4), 사용자가 명시적으로 보존을 고른 경우에만 실패다. 이 구분이 중요한 이유는 가만 두면 풀리는가 가 다르기 때문이다 — 보존을 고른 이상 기다린다고 카드의 외부 볼륨이 사라지지 않으므로, 보류로 두면 30 초마다 같은 판정을 되풀이하며 운영자는 아무 신호도 받지 못한다. 사유 문장이 몇 개가 왜 걸림돌인지를 그대로 말해, 운영자가 카드에 붙지 않고도 다음 조치(정의서를 파괴로 바꾸거나 카드를 정리)를 정할 수 있다. 실패 후 체크인이 409 로 막히는 것까지 확인해, 실패한 게스트가 같은 요청을 반복해 원장을 부풀리지 않음을 보았다.

계획이 거절됐을 때의 보류 표시		계획을 거절되게 하려면 IR 계열의 한계에 걸리는 인벤토리를 시드로 따로 준비해야 하는데, 이번 검증 자산에 그 시드가 없다. 생략했다. 대신 단위 테스트가 이 경로를 덮는다(E3.5-2 의 V3 계열과 이번 W7), 화면 표시 자체는 E3.5-3 의 CP5 가 같은 보류 표시 계통으로 확인했다. 전 구간 왕복으로는 확인되지 않은 채 남는다.

실제 RAID 카드에 파괴 정책이 내려가는 층		브라우저와 하네스는 서버의 판정과 화면까지를 보증하며, 카드가 실제로 명령을 받아 기존 볼륨을 지우고 새로 만드는 층은 확인하지 않았다. CP7 실기 일괄로 이관한다. 다만 이번 축 도입으로 전제 하나가 해소됐다 — E3.5-3 은 실기에서 기존 볼륨을 사용자가 수동으로 먼저 지워야 집행 경로로 들어갈 수 있었는데, 이제 파괴를 고르면 그대로 집행이 관찰된다.
브라우저 검증은 실기 검증을 대체하지 않는다. 이번에 확인된 것은 정의서에 축이 실려 저장 · 표시되고, 그 축이 실행 판정을 갈라 원장에 남으며, 기록된 실물이 화면에 뜨는 데까지다. 실제 카드가 지시대로 움직이는 층은 여전히 미확인이다. 둘을 같은 것으로 읽으면 다음 사람이 파괴 정책을 검증된 것으로 착각한다.
§7. 발견한 것

관찰 1 — 폼 기본 두 행에서 사각 문구가 먼저 뜬다

새 정의서 폼의 기본 두 행은 조건이 같다. 이 상태는 서버 기준으로는 중복 규칙(규칙 4)에 걸리는데, 폼의 실시간 미러는 포섭(규칙 8)만 보므로 “2번 묶음은 1번 묶음에 가려 도달할 수 없습니다” 라는 다른 문구가 대신 뜬다.

서버 판정

같은 조건 두 행 → 중복 규칙으로 먼저 거절

정확한 사유를 지목한다

폼 미러 판정

같은 조건 두 행 → 포섭으로 판정(같은 것은 서로를 덮으므로)

“가려 도달할 수 없습니다” 문구

틀린 안내는 아니다 — 같은 조건이면 후행이 실제로 도달할 수 없는 것이 사실이고, 사용자가 취해야 할 조치(조건을 바꾼다)도 같다. 그리고 그 상태로 저장하면 서버가 정확한 중복 문구로 거절하므로 잘못된 정의서가 저장되지도 않는다. 중복 전용 미러를 추가하면 문구는 더 정확해지지만, 폼에 미러할 진리표가 하나 더 늘어 서버와 어긋날 자리도 함께 늘어난다.

조치 없이 관찰로 남긴다. 안내가 틀리지 않고 저장도 막히므로 지금 고칠 유인이 약하고, 미러를 늘리는 쪽이 드리프트 위험을 키운다. 사용자 마찰이 실제로 보고되면 그때 판단한다.

관찰 2 — 검증 도중 폼 작성 상태가 한 차례 소실됐다

B2 · B1 구간을 조작하는 중 작성해 둔 폼 상태가 한 번 사라졌다. 원인은 브라우저 자동화 절차 쪽이었고(좌표 재시퀀스로 회복), 애플리케이션 결함이 아니다. 같은 조작을 다시 수행해 항목을 완주했다. 기록에 남기는 이유는, 이후 CP5 에서 같은 증상이 나왔을 때 앱 결함으로 오인하지 않도록 하기 위해서다.

회귀 보너스 — 기존 검증이 새 폼 흐름에서도 그대로 발동한다

B4 의 보존 정의서를 작성하는 도중, RAID1 은 최소 2 대 라는 U4-1-1 의 기존 검증이 정상적으로 발동했다(§5 의 보조 컷). 이번 슬라이스는 폼에 축 라디오 · 잠금 · 실시간 미러 셋을 새로 얹었으므로 기존 검증 흐름을 밀어낼 위험이 있었는데, 계획하지 않았던 확인이 우연히 이루어진 셈이다. 새 미러가 기존 검증을 가로채지 않는다는 뜻이다.
