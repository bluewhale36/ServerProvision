§0. 배경 — 왜 오늘 이 작업을 했는가

MVP 출시선을 확정(필요조건 E3 · 충분조건 E4)한 뒤, 실제 배포 기기가 아직 없는 상태에서 배포 절차를 미리 검증할 무대가 필요했다. 개발 맥북 위에 만들어 둔 Rocky Linux 9.6 aarch64 minimal 가상머신을 스테이징으로 세우기로 했고, 이 작업을 기록하는 계열로 DPL(배포 실행) 을 신설했다.

단계내용시점
DPL-1스테이징 VM 테스트 배포오늘 (2026-08-15)
DPL-2실배포배포 기기 확보 후

절차의 SSOT(Single Source of Truth — 단일 진실 출처)는 저장소의 docs/staging-vm-bootstrap.md 런북이며, 오늘 세션은 그 런북의 첫 실측 수행이다. 목표는 셋이었다.

목표결과비고
① 프로그램을 VM 에 구축달성systemd 서비스로 상시 기동
② dhcp 준비부분설치 · 특권 위임 실검증까지. 실서빙은 의도적 보류(§8)
③ 맥북 브라우저에서 웹페이지 접속달성HTTP 200 확인(§7)
이 문서의 성격 — 코드 슬라이스의 CP6 보고서가 아니라 배포 세션의 수행 기록이다. 그래서 CP5 의 검증 항목 식별자(A · B · C)와 항목별 스크린샷 체계를 쓰지 않는다. 여기서 증거 역할을 하는 것은 터미널 실측값(오류 메시지 · ss 와 방화벽 출력 · HTTP 응답 코드)이며, 각 절에 코드 블록으로 인용한다.
§1. 통로 만들기 — ssh 가 열리기까지 (사용자 + 세션 협업)

작업 방식부터 정했다. VM 에 Claude Code 를 설치하지 않고, 맥의 세션이 ssh 로 VM 에 명령을 보내 원격으로 구축하기로 했다(설치는 필요가 실체화될 때 한다). 그러려면 맥에서 VM 으로 가는 비밀번호 없는 ssh 통로가 먼저 있어야 했다. 이 통로를 뚫는 데 세 번 걸렸다.

1-1. 키가 없었다

사용자가 ssh-copy-id spvadmin@192.168.1.5 를 실행하자 No identities found 가 떴다 — 맥의 ~/.ssh 에 키 자체가 없었다. 세션이 ed25519 키 쌍을 생성했다(~/.ssh/id_ed25519). passphrase 는 두지 않았다 — 비대화형 자동화에 쓸 키라서 명령마다 잠금 해제가 걸리면 원격 구축 자체가 성립하지 않는다.

1-2. 이번엔 연결이 안 됐다

키를 만들고 재시도한 ssh-copy-id 는 120초를 넘겨 실패했다.

connect to host 192.168.1.5 port 22: Operation timed out

비밀번호나 키 등록의 문제가 아니다. 인증 단계까지 가지도 못했다는 뜻이며, 패킷이 VM 까지 아예 못 가는 상태다.

1-3. 진단 — VM 의 IP 가 존재하지 않는 대역이었다

맥의 네트워크를 실측했다. 맥이 가진 대역은 셋뿐이었다 — 실 LAN 인터페이스 en0 의 172.30.1.21, 하이퍼바이저 가상 네트워크인 192.168.16.1/24(bridge100) 와 192.168.24.1/24(bridge101). VM 이 주장하는 192.168.1.5 는 이 중 어느 대역에도 속하지 않았다. 원인은 VM 안에 남아 있던 정적 IP 설정이다 — 192.168.1.x 는 사무실 BMC 망 대역과 같아, 그쪽 용도로 잡았던 값의 잔재로 추정된다.

맥이 가진 대역은 172.30.1.x(실 LAN) · 192.168.16.x · 192.168.24.x 셋이다. VM 이 주장하던 192.168.1.5 는 그중 어디에도 없었고, 그래서 맥에서 보낸 패킷이 VM 까지 가지 못했다.

1-4. 해법 — DHCP 전환

사용자가 VM 콘솔에서 nmcli con mod ... ipv4.method auto 로 전환하자 VM 이 bridge101 대역의 192.168.24.128 을 받았다. 이어 ssh-copy-id spvadmin@192.168.24.128 이 성공했고, 이후로 세션이 비밀번호 없이 VM 에 명령을 보낼 수 있게 됐다.

§2. sudo 관문

시스템 구축은 패키지 설치 · 계정 생성 · systemd 유닛 배치까지 전부 sudo 가 필요하다. 그런데 sudo 가 비밀번호를 요구하면 세션이 보내는 비대화형 명령이 전부 막힌다 — 원격에서 입력할 프롬프트가 없기 때문이다. 사용자가 VM 콘솔에서 /etc/sudoers.d/spvadmin-nopasswd 에 NOPASSWD 를 등록해 이 관문을 열었다.

스테이징 한정 편의 — 이 전면 개방은 오늘 무대에서만 쓴다. 실배포(DPL-2)에서는 OPS-3 D4 대로 명령을 한정한 sudoers 만 둔다. 원상 복귀 항목으로 §10 에 적립했다.
§3. 소스와 스키마 반입 — sudo 없이 되는 일 먼저

소스

GitHub 인증을 VM 에 새로 만들지 않기로 하고, 맥의 dev 작업 트리를 tar.gz 로 묶어 scp 로 보냈다 — 22.2M(build · .gradle · .git · .idea 제외). 그런데 VM 에서 풀려고 보니 minimal 설치에는 tar 조차 없었다. 기본으로 들어 있는 python3 로 대체했다.

tar 실행                                                  → exit 127 (명령 없음)
python3 -m tarfile -e ~/spv-src.tgz ~/ServerProvision     → 압축 해제 성공

런북에 적을 실측 수확 1호다 — minimal 이미지가 무엇을 안 갖고 있는지는 실제로 해 봐야 드러난다.

스키마

애플리케이션이 ddl-auto=validate 로 동작하므로 스키마가 먼저 들어가 있어야 기동한다. 맥 개발 DB(3306)에서 구조만 떴다.

mariadb-dump --no-data --skip-lock-tables --no-tablespaces
   → 726줄, CREATE TABLE 36개

이 덤프를 scp 로 VM 에 반입했다. 이 시점의 선택이 §5 의 첫 기동 실패로 이어진다.

§4. 시스템 구축 — 런북 절차의 일괄 실행

패키지 (약 3분)

시간대를 Asia/Seoul 로 맞추고, mariadb:10.11 모듈을 활성화한 뒤 tar rsync git acl java-21-openjdk-devel mariadb-server 를 일괄 설치했다. 설치 후 OpenJDK 21.0.12 와 MariaDB 10.11.18 을 확인했다.

이어 구축 스크립트 한 벌을 실행했다(런북 3 · 5 · 6 · 9 · 10 · 11절).

계정 (OPS-1 D3 · D4)

  • 서비스 계정 provisioning 생성 — system 계정, 셸 로그인 차단(/sbin/nologin), 홈 없음.
  • 운영자 그룹 spvadmin 은 로그인 계정의 기본 그룹으로 이미 존재해 새로 만들지 않았다.

디렉토리 (OPS-2 D1 · D2)

서빙되는 것과 절대 서빙되지 않는 것을 부모 디렉토리 수준에서 갈랐다. 경로 하나를 잘못 열어도 내부 자산이 노출되지 않게 하려는 배치다.

/var/lib/serverprovision/ ├── served/ ← 서빙되는 것 │ ├── resources/ provisioning:spvadmin 2775 + 기본 ACL (운영자 공유) │ └── pxe/ provisioning:provisioning 0755 └── internal/ ← 절대 서빙 안 되는 것 ├── uploads/ provisioning:spvadmin 2775 + 기본 ACL (운영자 공유) ├── upload-tmp/ ├── work/ ├── trash/ ├── quarantine/ └── history/ /opt/serverprovision/data → /var/lib/serverprovision (심볼릭 링크)

기본 소유는 provisioning:provisioning 0755 이고, 운영자와 공유해야 하는 두 곳(served/resources · internal/uploads)만 provisioning:spvadmin + setgid(2775) + 기본 ACL 을 얹었다. setgid 만으로는 부족한 이유가 OPS-1 D5 다 — setgid 는 그룹만 상속하고 권한 비트는 프로세스의 umask 를 타므로, 새로 생기는 파일이 그룹 쓰기 권한을 잃을 수 있다. 그 구멍을 기본 ACL 로 메운다.

DB

  • MariaDB 기동 후 server_provision 데이터베이스 생성(utf8mb4).
  • 앱 계정 spv_app 에는 DML(SELECT · INSERT · UPDATE · DELETE)만 부여했다. validate 모드에서는 앱이 스키마를 만들지 않으며 DDL 은 관리 계정 소관이다 — 로컬 개발에서 쓰는 계정 분리 관행과 같다.
  • 스키마 반입 후 테이블 36개 확인.

환경 파일 (OPS-3 D8)

/etc/serverprovision/env 를 0600 으로 두었다. DB 비밀번호(18바이트)와 마커 서명 비밀(48바이트)은 VM 안에서 openssl 로 생성해 어디에도 출력하지 않았다 — 세션 로그에도 남지 않는다.

OPS-2 가 정한 새 경로 배치는 코드를 한 줄도 고치지 않고 환경변수(UPLOAD_BASE_DIR · PROVISION_TRASH_ROOT 등)로 주입했다. 경로 설정이 전부 외부화돼 있었기에 가능했던 일이다.

§5. 기동 실패 1 — 개발 DB 가 코드보다 뒤처져 있었다

기동 후 90초를 폴링했는데 HTTP 응답이 오지 않았다. systemctl 이 보고하는 서비스 상태는 active 였다. 유닛에 넣은 Restart=on-failure 때문에 실패한 프로세스가 즉시 되살아나 겉보기 상태만으로는 정상과 구별되지 않았던 것이고, 실체를 드러낸 것은 재시작 카운터 22 였다 — 기동 실패와 자동 재시작이 무한히 반복되고 있었다. 로그에 원인이 있었다.

Schema validation: missing column [deleted_checked] in table [drift_report]

인과를 풀면 이렇다. deleted_checked 는 MK4-4-2 가 추가한 컬럼으로, 점검 회차가 "무엇을 어디까지 봤는가" 를 남기는 3컬럼 중 하나다. MK4-4 코드는 어제(8/14) PR #36 으로 dev 에 병합됐다. 그런데 그 DDL 스크립트는 맥의 개발 DB(3306)에 아직 적용되지 않은 상태였다. §3 에서 그 DB 를 그대로 덤프해 왔으니 VM 스키마에도 컬럼이 없었고, 반입한 dev 코드는 그 컬럼이 있다고 기대하므로 ddl-auto=validate 가 기동을 끊은 것이다.

증상

기동 후 90초 폴링에도 HTTP 무응답. 서비스는 active 로 보이나 재시작 카운터 22.

관찰

로그에 missing column [deleted_checked] in table [drift_report].

원인

MK4-4-2 컬럼. 코드는 8/14 dev 병합(PR #36), DDL 은 맥 개발 DB 미적용 → 그 덤프를 반입 → VM 스키마에도 부재.

해법

반입 소스의 ddl/MK4-4-2_drift_report_scan_scope.sql 적용 → drift_report 13컬럼 → 기동 성공.

적용 전에 다른 DDL 스크립트(reconciliation_setting 등)는 이미 적용돼 있음을 대조로 확인했다 — 빠진 것이 MK4-4-2 하나뿐임을 먼저 가려낸 것이다.

파장 — 맥의 개발 DB 도 같은 상태다. 지금 맥에서 dev 브랜치 앱을 3306 으로 띄우면 같은 오류로 기동에 실패한다. claude_code 계정은 ALTER 권한이 없으므로 사용자가 root 로 한 번 적용해야 한다(§10-1). "PR 병합 후 DDL 적용" 이라는 앵커 통합 절차의 빈틈이 스테이징 첫날 실측으로 드러난 셈이다.
§6. 기동 실패 2 — 루프백 전용 바인딩

스키마를 맞추자 애플리케이션이 떴다. 그런데 VM 안(localhost)에서는 응답하는데 맥에서의 접속은 여전히 거부됐다. 먼저 방화벽을 의심했으나 정상이었다 — 8080/tcp 개방, zone 은 public, 인터페이스는 enp2s0. 실체는 방화벽이 아니라 바인딩 주소였다.

LISTEN  [::ffff:127.0.0.1]:8080     ← 루프백에만 묶여 외부 요청을 받지 않음

원인은 application.properties 3행의 server.address=localhost 다. 개발 편의로 박혀 있던 값인데, 그 값이 jar 안에 그대로 패키징돼 스테이징까지 따라온 것이다. 방화벽이 포트를 열어 두어도 프로세스 자신이 루프백에만 귀를 기울이고 있으면 외부에서 온 연결은 애초에 받아들여지지 않는다.

해법은 환경 파일에 SERVER_ADDRESS=0.0.0.0 한 줄을 더하는 것이었다. 파일을 다시 빌드하지 않고도 덮어쓰기가 성립하는 근거는 Spring 의 설정 우선순위다 — OS 환경변수가 jar 안에 패키징된 properties 보다 높다.

BEFORE — jar 내 properties

server.address=localhost

LISTEN [::ffff:127.0.0.1]:8080
→ 맥에서 접속 거부

AFTER — 환경 파일 주입

SERVER_ADDRESS=0.0.0.0

LISTEN *:8080
→ 맥에서 접속 성립

증상

VM 안 localhost 는 응답. 맥에서의 접속만 거부.

관찰

방화벽 정상(8080/tcp · zone public · enp2s0). LISTEN [::ffff:127.0.0.1]:8080.

원인

application.properties 3행 server.address=localhost — 개발 편의 값이 jar 에 패키징됨.

해법

§7. 접속 성공

맥에서 http://192.168.24.128:8080/management/os 로 접속해 HTTP 200 과 OS 자원 관리 화면 HTML 을 정상 수신했다. 오늘의 목표 ③ 달성이다.

루트 경로 404 는 정상이다 — / 에는 매핑이 없다. 진입은 /management/* · /maintenance/* · /provisioning/* 경로로 한다.
§8. dhcp 준비 — 설치와 위임까지, 실서빙은 의도적 보류
  • dhcp-server · tftp-server 설치.
  • 특권 위임 (OPS-3 D4 · D5) — /etc/sudoers.d/serverprovision 에 코드 정본(AllowedCommand.sudoersLine)이 만들어 내는 두 줄을 넣고 440 으로 두었다.
    • dhcpd 문법 검사 — /usr/sbin/dhcpd -t -cf *
    • dhcpd 재기동 — systemctl restart dhcpd
  • 실검증 통과 — provisioning 계정이 비밀번호 없이 dhcpd -t 를 실행함을 확인했다. E1-I-3 의 dhcpd 조각 반영 기능이 실제로 쓰는 바로 그 경로다.
  • 유닛에 ReadWritePaths=/etc/dhcp 를 추가했다. 유닛 본문을 고치는 대신 drop-in(serverprovision.service.d/dhcp.conf)으로 얹었고, 재기동 후 웹이 정상임을 다시 확인했다.
dhcpd 는 disabled · inactive 로 남겼다. 공유 가상 네트워크에서 켜면 하이퍼바이저의 DHCP 와 충돌하고, 브리지에서 켜면 사내망에 불량 DHCP 를 뿌리는 사고가 된다. 실서빙은 격리된 랩 세그먼트를 확보한 뒤 한다(§10-3).
