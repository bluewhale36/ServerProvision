§0. 한 줄 요약

실기 3호(2026-09-08)에서 정상 종료가 세 번 모두 호스트를 끄지 못했다(F-10). 정정은 두 갈래다 — 화면이 발행 뒤 최대 60 초 동안 전원 상태를 스스로 확인해 결과를 문장으로 알리고, 진단 리눅스에는 전원 버튼 이벤트를 받아 poweroff 하는 acpid 를 넣었다.

자바 소스 · DDL · 서버 계약 변경이 0 이다. 고칠 곳은 서버가 아니라 화면의 관측과 게스트의 응답이었다.

CP5 는 4 항목(G1-a · G1-b · G1-c · G2)을 수행해 전부 PASS 했고 새로 발견한 결함은 없다. 파생 축 하나와 회귀 둘은 사유와 함께 미수행으로 남겼다(§6). HF15 묶음 전체 테스트 3,120 건 green(2026-09-09 14:40).

§1. 진단 — 실기 3호 실측

정상 종료(Redfish Reset · GracefulShutdown)를 세 번 발행했다. BMC 는 세 번 모두 Task 를 만들었고(state=null) 화면은 200 을 받았지만 호스트는 꺼지지 않았다. 그날 종료 7 건이 전부 강제였다(강제 종료는 7/7 즉시 성립).

원인은 두 겹이고, 두 겹이 겹쳐야 이 증상이 된다.

  • ① 받는 쪽이 없다 — 정상 종료는 BMC 가 ACPI 전원 버튼을 누르는 것이라 호스트 OS 가 그 이벤트를 받아 스스로 꺼야 성립한다. 진단 리눅스(Alpine)에 acpid 가 world 에도 런레벨에도 없었다.
  • ② 화면이 결과를 모른다 — E1.5 의 결정 D4(화면 경로는 폴링하지 않는다)에 따라 발행 결과만 표기했다. 운영자는 "전달됐지만 무시된 것" 과 "곧 꺼질 것" 을 구분할 수 없어 60 초쯤 지켜보다 포기했다.
F-10 의 성질 : 발행은 성공(200)인데 결과는 실패다. 응답 코드가 조작의 성패를 말해 주지 않는다. 다만 호스트가 전원 버튼을 무시하는 것은 프로그램 예외가 아니라 그 순간의 호스트 상태이므로, 서버 예외를 새로 만들 대상이 아니다.
§2. 구현 — 무엇을 어디에

화면 감시와 이미지 수정을 함께 채택했다. 둘은 겹치지 않는다 — 안내가 없으면 Windows 설치 화면에서 여전히 깜깜하고, 이미지를 고치지 않으면 진단 리눅스는 영원히 안내만 받는다. 서버가 폴링해 결과를 확정하는 안은 E1.5 D4 가 금지한 블로킹을 화면 경로에 얹으므로 탈락했다.

HF15-4 자체에서 CP5 가 새로 발견한 결함은 없다. 세 갈래가 계획대로 갈렸고 자산도 계획대로 실렸다. 정정은 plan 검토에서 나온 것 하나다.

설계상의 한계 : 감시는 화면이 열려 있는 동안만 산다 — 탭을 닫으면 안내가 뜨지 않는다(서버 상태에는 영향 0 · 다시 열어 [상태 조회]). Windows 설치 화면 · UEFI 셸이 전원 버튼에 응답하게 만드는 것은 우리가 고칠 수 없어 안내로 덮는 것이 이 슬라이스의 답이다.
