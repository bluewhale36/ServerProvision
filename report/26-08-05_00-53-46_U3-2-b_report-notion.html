§1. 슬라이스 개요

U3(세팅 정의서 → 게스트 할당)의 하위인 U3-2 를 2 분할한 두 번째 슬라이스다. 형제 U3-2-a 는 이미 할당된 정의서를 다른 정의서로 바꾸는 재할당(supersede-then-new)과 미소비 supersede 행 지연 purge reaper 를 다뤘다. U3-2-b 는 그 위에 서서 정의서 자체의 삭제 · 복원 · 영구삭제 를 담당한다.

이 슬라이스가 여는 것

  • 데이터베이스 전용 soft-delete — 정의서를 지우면 물리 삭제하지 않고 is_deleted=1 로 감춘다. 목록에서는 사라지고(활성 전용), 나중에 복원하거나 영구삭제(purge) 할 수 있다.
  • 삭제 시 참조 경고 — 삭제하려는 정의서를 현재 활성 할당으로 참조하는 게스트가 몇 개 인지 세어 사용자에게 알린다. "1 개 게스트에 활성 할당돼 있다" 는 사실을 보여주되, 소프트 참조라 삭제해도 스냅샷은 유지되므로 삭제를 막지는 않는다.
  • 목록 가시화 — 기본 목록은 활성 정의서만 보여주고, "삭제된 항목 포함" 토글로 soft-deleted 정의서를 "삭제됨" 배지 와 함께 드러낸다. soft-deleted 상세에서는 수정 버튼을 숨기고 복원 · 영구삭제 액션만 노출한다.
단일 슬라이스 · 교차 의존은 SPI 구현 1 개 — U3-2-b 가 새로 만든 도메인 간 연결은 provisioning.assignment 가 provisioning.setting 의 AssignmentUsageInspector 인터페이스를 구현하는 것 하나뿐이다. 방향이 assignment → setting 한쪽으로만 흐르므로 순환이 생기지 않는다(§8 에서 실측으로 확인).

§5. 실 데이터베이스 스키마 · 데이터 사고와 복구 개정 1

개정 1 에서 실 데이터베이스의 데이터가 실제로 손상된 사고가 났다. 원인 · 파급 · 복구를 여기 남긴다. 이것이 이 슬라이스에서 가장 중요한 기록이다 — 테스트가 전부 통과한 상태에서 벌어졌고, 사고를 부른 위험은 사전에 식별돼 보고까지 됐던 것이며, 안전한 순서도 이미 제시돼 있었기 때문이다.

사고 — ddl-auto=update 상태로 실 데이터베이스에 기동해 기존 정의서가 비활성으로 백필됐다
  • spring.jpa.hibernate.ddl-auto 가 update 인 채로 애플리케이션이 실 데이터베이스를 향해 기동했고, Hibernate 가 lifecycle 컬럼 3 개(is_deleted · is_enabled · is_deprecated)를 DEFAULT 없이 추가했다.
  • 그 결과 ① 세 컬럼의 기본값이 비었고, ② 기존 정의서 "공장 표준 세팅 (Rocky 9.7)" 의 is_enabled 가 0(비활성)으로 백필되어 그 정의서로는 신규 할당이 차단되는 상태가 됐다. 운영 데이터가 조작 없이 기능을 잃은 것이다.
사전 경고 이력 — 경고한 그대로 일어났다
구현 단계에서 이 위험("boolean 컬럼이 DEFAULT 없이 추가되면 기존 행이 전량 비활성으로 백필된다")이 식별돼 보고됐고, 안전한 순서(수동 DDL 을 실 데이터베이스에 선적용 → ddl-auto 를 validate 로 복원 → 기동)까지 함께 제시돼 있었다. 그 순서를 밟지 않은 채 기동한 것이 사고의 직접 원인이다. 위험을 알아낸 것과 그 순서를 지키는 것은 별개의 일이라는 점이 이 사고의 교훈이다.

동시에 드러난 누락 — 자동 반영이 만들 수 없는 것 2 가지

자동 반영은 엔티티 매핑에 있는 것만 만든다. 매핑으로 표현되지 않는 다음 둘은 실 데이터베이스에 존재하지 않았다.

  • 활성 전용 이름 유일성이 이행되지 않음 — DEC-B 가 제거하기로 한 무조건 UNIQUE(uk_setting_definition_name)가 실 데이터베이스에 그대로 남아 있었다. 이 상태에서는 soft-delete 된 정의서와 같은 이름으로 새 정의서를 만들 수 없다.
  • 할당 활성 유일성 장치가 없음 — 게스트당 활성 할당 1 건을 데이터베이스가 강제하는 장치 (생성 컬럼 active_guest_id + uk_active_assignment_per_guest)가 없었다. 생성 컬럼(generated column)은 JPA 매핑에서 유도되지 않으므로 자동 반영으로는 결코 생기지 않는다.

§6. CP5 샌드박스 검증 (핵심) 개정 2 · 전면 재수행

이 섹션이 본 보고서의 중심이다. 왜 CP5 를 처음부터 다시 했는지, 무엇을 확인하려 했는지(검증 항목 계획), 어떤 환경에서 했는지(샌드박스 구성과 픽스처), 검증 중 무엇을 발견해 어떻게 고쳤는지(결함 3 건), 실제로 어떤 조작을 했고 화면이 어떻게 응답했는지(증거 16 장), 그리고 무엇을 하지 못했는지를 순서대로 담는다.

1) 이 절을 다시 쓴 이유 최초 기록의 결함

전송 계층 확인이 UX 확인을 대신하면서 결함을 가렸다
  • 무엇을 했었나 — 최초 CP5 기록에서 항목 ⑤ "복원 시 활성 이름 충돌" 과 ⑥ "영구삭제 typed-name" 은 curl 로 요청을 직접 보내 상태코드만 확인하고 통과 처리했다(⑤ 409 · ⑥ 400/302). 증거 표에도 방법이 "direct POST" 라고 적혀 있었다.
  • 왜 그것으로는 부족했나 — curl 응답이 JSON 인 것은 정상이라 아무 이상이 없어 보인다. 그러나 브라우저에서 같은 버튼을 누르면 폼이 네이티브로 제출되고, 예외 advice 가 만든 JSON 이 그대로 화면에 렌더된다. 전송 계층에서는 보이지 않고 화면에서만 드러나는 종류의 결함이다.
  • 언제 드러났나 — CP7 확인 중 사용자가 삭제된 정의서의 복원을 눌러 raw JSON 페이지를 직접 목격했다. CP5 가 잡았어야 할 것을 CP7 이 잡은 것이다.
  • 규약이 요구하던 것 — 샌드박스 검증 규율은 "거절하는가" 가 아니라 "막는 방식까지 — UX 를 해치지 않고 유도하는가" 를 보라고 되어 있다. 사용자가 왜 막혔는지 아는가, 다음에 무엇을 해야 하는지 안내되는가를 보는 항목이다. curl 로는 이 질문에 답할 수 없다.
그래서 CP5 를 픽스처부터 새로 깔고 전 항목을 실제 클릭으로 다시 수행했다. 아래는 그 재수행의 기록이며, 최초 보고의 CP5 기록(7 항목 + 델타 5 항목)을 대체한다. 최초 기록에서 발견한 결함 1 건(파생 쿼리 프로퍼티 불일치)은 4) 에 그대로 보존한다.

4) 검증 중 발견 · 수정한 결함 (3 건) CP5 의 성과

결함 1 — 리포지토리 파생 쿼리 프로퍼티 불일치 (최초 CP5 에서 발견)

  • 증상 — 애플리케이션 부팅 시 PropertyReferenceException: No property 'isDeleted' 로 스프링 컨텍스트 기동이 실패했다.
  • 근본 원인 — SettingDefinition 의 필드가 private boolean deleted(@Column is_deleted)라 JPA 프로퍼티 이름은 deleted 인데, 리포지토리 파생 쿼리는 findByIdAndIsDeletedFalse 처럼 IsDeleted(프로퍼티 isDeleted)를 참조해 이름이 어긋났다.
  • 왜 테스트가 못 잡았나 — 단위 테스트와 @WebMvcTest 는 리포지토리를 mock 으로 대체해 파생 쿼리 문자열을 실제로 파싱하지 않는다. 그래서 green 이면서도 이 불일치를 통과시켰고, 쿼리 파싱이 일어나는 실 부팅에서만 드러났다.
  • 수정 — 엔티티 필드를 deleted → isDeleted 로 개명했다(프로젝트 LifecycleEntity 관례와 정렬). Lombok @Getter 는 boolean 의 is 접두를 처리해 게터가 isDeleted() 로 불변이라 호출부는 영향을 받지 않았다.

결함 2 — 거절 응답이 raw JSON 페이지로 노출 (CP7 확인 중 사용자가 발견)

  • 증상 — 삭제된 정의서의 상세에서 복원 을 누르면(활성 동명이 존재하는 상황) 화면 전체가 {"message":"같은 이름의 활성 정의서가 있어 …"} 라는 JSON 텍스트로 바뀌었다. 애플리케이션 화면이 사라지고 사용자는 돌아갈 길을 잃는다.
  • 근본 원인 — 세팅 정의서 상세의 lifecycle 폼 5 개에 data-async-submit 마커가 빠져 있었다. 이 마커가 있어야 폼이 ConfirmModal.approveAndSubmit → submitAsync 경로로 fetch 제출되고, 거절 응답이 ErrorModal 로 안내된다. 마커가 없으면 브라우저가 네이티브로 제출해 advice 가 만든 JSON 이 응답 본문 = 화면이 된다.
  • 왜 CP5 가 못 잡았나 — 위 1) 에 적은 그대로다. 이 경로를 curl 로만 확인했고, curl 은 마커의 유무와 무관하게 같은 JSON 을 돌려준다.
  • 수정 — 상세의 lifecycle 폼 5 개(활성 토글 · 사용 중단 · 권고 해제 · 복원 · 삭제 · 영구 삭제)에 data-async-submit 을 붙이고, 확인 모달이 없는 즉시 실행 폼(토글 · 사용 중단 · 복원)은 제출 이벤트를 가로채 같은 경로로 태웠다. 관리 도메인(os · board 등)의 lifecycle 폼이 이미 쓰고 있던 배선을 그대로 따른 것이며, confirm-modal-base.js 의 주석은 그 이유를 "거절 응답이 raw JSON 페이지로 노출되는 사고를 막기 위함" 이라고 적어 두고 있었다.

결함 3 — 영구 삭제 후 착지가 다시 raw JSON (결함 2 를 고친 뒤 재검증 중 자체 발견)

  • 증상 — 영구 삭제 자체는 성공하는데, 성공 직후 화면이 {"message":"세팅 정의서를 찾을 수 없습니다. id=…"} 로 바뀌었다.
  • 근본 원인 — 결함 2 의 수정이 만들어 낸 것이다. 전역 성공 처리는 "현재 페이지를 다시 읽는다" 인데, 영구 삭제는 지금 보고 있는 정의서를 없애는 조작이라 재적재가 사라진 상세를 다시 요청하고 그 404 응답이 화면이 됐다. 관리 도메인은 영구 삭제 폼을 네이티브 제출로 두어 서버 리다이렉트를 그대로 따라가므로 이 상황이 없다.
  • 수정 — 이 페이지에서만 성공 처리를 바꿔, 재적재 대신 서버가 지정한 최종 도착지(fetch 응답의 resp.url — 리다이렉트를 따라간 결과)로 이동하게 했다. 영구 삭제는 목록으로, 나머지는 상세로 각각 서버 의도대로 착지한다. 거절 · 네트워크 오류 처리는 전역 핸들러에 그대로 위임한다 (trash-action.js · reconciliation/list.js 의 페이지 로컬 재정의 선례와 같은 방식).
  • 이 결함이 말해 주는 것 — 마커 하나를 붙이는 수정도 착지 지점을 바꾼다. 고친 뒤 다섯 폼을 모두 눌러 본 덕분에 드러났고, 복원 하나만 확인하고 끝냈다면 그대로 남았을 결함이다.

확인 권장 동선

  1. 세팅 정의서 목록에서 개정된 표(가운데 정렬 # · 활성 열 · 사용 중단 열)와 배지 색을 확인한다.
  2. 상세로 들어가 활성 토글과 사용 중단 해제를 눌러 상태를 바꿔 본다.
  3. 게스트 서버 상세의 할당 드롭다운이 그 변화를 따라가는지 본다 — 비활성은 사라지고, 사용 중단은 접미 문구와 함께 남는다.
  4. 삭제 → 복원 → 영구 삭제(이름 직접 입력)까지 이어 확인한다.
  5. 거절 경로를 일부러 밟아 본다 — 삭제된 웹표준 정의서(14)를 복원하기 전에 같은 이름으로 새 정의서를 만들어 두면 복원이 409 로 거절된다. 이때 화면이 유지된 채 안내 모달이 뜨는지(raw JSON 이 아닌지) 확인한다. 이것이 개정 2 로 고친 부분이다.
새로고침 주의 — 개정 2 에서 setting-lifecycle.js 가 바뀌었다. 이전에 이 화면을 열어 본 브라우저라면 강제 새로고침(cmd+shift+r) 후 확인해야 수정본이 적용된다.
§8. 순환 0 확인

U3-2-b 가 새로 그은 도메인 간 의존이 순환을 만들지 않는지 실측으로 확인했다.

  • setting → assignment import = 0 (실측). 정의서 도메인은 할당 도메인을 이름으로 참조하지 않는다.
  • assignment → setting 은 기존 4 파일 그대로 유지된다.
  • AssignmentUsageInspector 인터페이스는 setting 이 소유하고, 구현(AssignmentUsageInspectorImpl)만 assignment 에 둔다. 의존 방향을 뒤집는(dependency inversion) 이 배치로 순환이 없다.
선례와 동형 — 이 SPI 역전 패턴은 execution.engine 의 OwnedPhasesProvider, BIOS 자원의 UsageChecker 와 같은 구조다. 인터페이스는 참조가 필요한 쪽이 소유하고 구현만 데이터가 있는 쪽에 두어, 두 도메인이 서로를 직접 import 하지 않게 한다.
§9. 남은 것 · 후속

의도적으로 미룬 항목

  • soft-deleted 정의서 TTL 자동 purge reaper (잔여 2) — 현재는 수동 영구삭제만. 시간 임계(TTL) 경과 후 자동 수거는 후속으로 미룬다.
  • 이름 부분 유일성의 데이터베이스 강제 (잔여 1) — 현재는 애플리케이션 술어(existsByNameAndIsDeletedFalse)로 활성 이름 유일성을 지킨다. 동시 생성 경합이 문제될 경우 generated-column 기반 부분 유니크 인덱스로 데이터베이스에서 강제한다.
  • 경고 카운트의 활성 기준 (잔여 3, 확정) — 삭제 경고는 활성 할당만 센다(supersede 이력은 제외). 이 기준은 확정이다.
  • 비활성 · 사용 중단의 목록 일괄 조작 (개정 1 신규 잔여) — 지금은 정의서 상세에서 한 건씩만 상태를 바꿀 수 있다. 정의서 수가 늘어 목록에서 여러 건을 한 번에 비활성화할 필요가 생기면 그때 일괄 조작을 넣는다.
  • 동시성 경합 미확인 (개정 2 신규 잔여) — 두 세션이 같은 정의서를 동시에 복원하거나 영구 삭제하는 상황은 브라우저 자동화로 시점을 겹치게 만들 수 없어 CP5 에서 확인하지 못했다(§6 8) 에 명시). 활성 이름 유일성을 애플리케이션 술어로 지키고 있어 경합에 취약할 수 있으며, 위의 "이름 부분 유일성의 데이터베이스 강제" 항목과 같은 뿌리다.
  • 정적 자원 캐시 무효화 (개정 2 신규 잔여) — 스크립트 · 스타일에 버전 질의나 해시가 붙지 않아 수정 후에도 브라우저가 이전 파일을 계속 실행한다. CP5 재수행 중 실제로 "고쳤는데 재현된다" 는 착시를 한 차례 겪었다. 개별 슬라이스가 아니라 정적 자원 배포 전반의 문제이므로 별도 인벤토리로 다룬다.
