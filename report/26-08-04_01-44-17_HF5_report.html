§1. 슬라이스 개요 · 결함 4건

MK4 reconciliation 사용성 진단(2026-08-02 ~ 08-03)에서 개선 후보 28건과 부수 관찰 3건을 뽑아 전부 채택했다. 그 가운데 화면 레이아웃 개편과 무관하고 전역에서 공용으로 쓰이는 문구 결함 4건만 떼어 HF5 로 처리했다. 나머지는 MK4 후속으로 남으며, 설계 토론 → 데이터 모델 → 레이아웃 개편 순서를 밟는다.

4건을 떼어낸 이유는 두 가지다. 첫째, 이 문구들은 reconciliation 화면 하나가 아니라 자원 관리 · 휴지통 · 오류 페이지 어디에서나 지금 그대로 노출되고 있어, 레이아웃 개편을 기다릴 이유가 없다. 둘째, 개편 결과가 어떤 모양이 되든 고치는 방식이 달라지지 않는다 — 문구를 만드는 자리와 보여주는 자리가 개편 대상 밖이기 때문이다.

§3. 구현 — 어디를 어떻게 고쳤나

① 오류 페이지 상태 표기 — 두 경로가 같은 표를 보게 한다

문제의 뿌리는 오류 화면에 도달하는 경로가 둘인데 문구 출처가 하나로 모여 있지 않았다는 점이다. WebExceptionHandler 는 자기가 잡은 예외에만 상태 문구를 채웠고, 핸들러가 없는 404 나 바인딩 실패 400 처럼 Spring Boot 기본 /error 로 흐르는 요청은 그 값이 비어 화면의 fallback 리터럴 "Internal Error" 가 그대로 나왔다.

경로언제 타는가BEFORE 문구 출처AFTER 문구 출처
advice도메인 예외를 WebExceptionHandler 가 잡을 때 호출부가 넘긴 영어 reason phraseErrorStatusLabels.of(status)
기본 /error매핑 없는 404, 바인딩 실패 400 등 advice 를 안 거칠 때 비어 있음 → 화면 fallback 리터럴

ErrorStatusLabels 는 상태 코드에서 한국어 문구를 찾는 조회표이고, 표에 없는 상태는 기본 문구로 떨어진다. 표 조회이므로 상태가 늘어도 항목만 더하면 되며 제어 흐름 분기가 자라지 않는다. 기본 /error 쪽은 ProvisionErrorAttributes 가 Spring 이 제공하는 DefaultErrorAttributes 대체 지점을 통해 statusLabel 을 항상 채운다.

Spring Boot 4 이관 주의 — DefaultErrorAttributes 는 org.springframework.boot.webmvc.error 로 옮겨져 있었다. 임포트를 그에 맞췄다.

② 병기형 조사 — 호출부가 아니라 표시 직전 길목에 건다

문구 템플릿은 여덟 곳에 흩어져 있다(자원 삭제 · 복구 · 영구삭제 · Deprecated 표시 · 보존 연장 · BIOS 세팅 상세 삭제 · 드리프트 적용 · 중복 해소). 여덟 곳을 각각 고치면 앞으로 새 확인창이 생길 때마다 같은 실수를 반복하게 된다. 그래서 문구가 화면에 닿기 직전 세 길목에만 해소 함수를 걸었다.

길목을 이렇게 잡은 덕에 템플릿을 거치지 않는 직접 조립 호출과 서버가 보낸 문구까지 함께 덮인다. 문구 템플릿 여덟 곳은 한 줄도 고치지 않았다. 해소 함수가 아직 로드되지 않았더라도 원문을 그대로 돌려주므로 문구가 깨지지 않고, 이미 해소된 문자열을 다시 넣어도 결과가 같다.

작업 중 되돌린 것 — 처음에는 확인 모달 fragment 와 BIOS 세팅 상세 페이지에 스크립트를 각각 넣었다. 그러면 같은 스크립트가 여러 번 실린다. 되돌리고 공통 레이아웃의 commonHead 에서 전역 1회 공급으로 모았다. 호출 시점이 사용자 조작 이후라 defer 로 안전하다.

③ 자원명 확인 입력 — 저장소 안에서 갈라져 있던 표기를 통일

휴지통 영구삭제 확인 모달은 이미 기대 이름을 본문에 텍스트로 노출하고 있었다. reconciliation 의 내용 수용 폼만 placeholder 에 넣어 두어 입력창 폭에 잘렸다. 같은 저장소 안에서 두 곳이 갈라져 있던 것이 결함의 실체이므로, 선례 쪽으로 맞췄다. 새 표기 방식을 발명하지 않았다.

④ 바인딩 오류 문구 — 설정 클래스 없이 기본 basename 으로

messages.properties 를 두면 Spring Boot 의 MessageSourceAutoConfiguration 이 기본 basename 으로 자동 등록한다. 별도 설정 클래스를 만들지 않았다. 이번에는 typeMismatch 계열과 값 자체가 전달되지 않은 경우만 한국어화했다.

해석 순서 : typeMismatch.<객체>.<필드> → typeMismatch.<필드> → typeMismatch.<타입> → typeMismatch 이번 슬라이스가 채운 범위 : ▲ 여기까지 (타입 단위)

필드 단위 항목을 비워 둔 것은 의도한 것이다. 필드 이름을 한국어로 어떻게 부를지는 그 필드가 놓인 화면 문맥에서 정해지므로, MK4 레이아웃 개편에서 화면과 함께 정한다.

§9. CP5 — 검증 중 발견한 결함과 처리
발견 1 — 새 오류 페이지가 자기 문구를 부정했다
상태 문구를 고치고 나서 404 페이지를 열어 보니, "페이지를 찾을 수 없습니다 (404)" 아래에 "알 수 없는 오류가 발생했습니다." 가 그대로 남아 있었다. 무슨 일인지 이미 알려 준 상황에서 모른다고 덧붙이는 꼴이라 두 줄이 서로 부정한다.

계획과의 차이 — 계획 단계에서는 이 fallback 을 유지하기로 했었다. 상태 문구만 고치면 아래 줄은 그대로 두어도 무해할 것이라 보았는데, 화면에서 두 줄을 나란히 보고서야 어색함이 드러났다. 빌드와 테스트로는 잡히지 않는 종류다.

처리 — 덧붙일 설명이 있을 때만 그 줄을 보여주도록 고치고, 다시 빌드해 §8 항목 1 의 네 경로를 모두 재확인했다.
발견 2 (계획 검토 중) — 라틴 문자 받침 판정표가 규칙과 모순이었다
처음 정한 표는 r · f · s · x · z 를 받침 있음으로 분류했다. 그런데 규칙 자체가 "그 글자의 한국어 읽기 끝소리로 판정한다" 이고, 그 읽기는 아르 · 에프 · 에스 · 엑스 · 제트로 전부 받침 없이 끝난다. 표가 자기 규칙을 어긴 것이다.

어떻게 잡았나 — 계획서의 데모 판정 함수를 Node 로 떼어 실행해 사례를 대조하다가 Mellanox OFED Driver 가 "Driver 을" 로 나오는 것을 보고 발견했다.

처리 — 받침 있음을 l(엘) · m(엠) · n(엔) 셋으로 줄이고, 계획서 본문과 데모 코드를 함께 정정했다. 이 표가 틀린 채 구현으로 넘어갔다면 확인창 문구가 어색한 채로 굳었을 것이다.
반려한 관찰 — 수용 버튼이 화면에서 닿지 않는다 (오탐)
MK4 진단 때, 상세 패널이 끝까지 스크롤된 상태에서 수용 버튼이 화면 밖에 있어 결함으로 보였다. 이번에 실측해 보니 페이지 배경 위에서 마우스를 굴리면 문서가 스크롤되어 버튼에 닿았다. 결함이 아니므로 목록에서 뺐다.
CP5 가 잡은 것의 성격 — 발견 1 은 빌드도 테스트도 통과한 상태에서 화면에서만 드러난 결함이다. CP4 의 green 이 완료가 아니라 검증 착수 조건이라는 규율이 실제로 값을 한 사례다.
§10. 불가침 원칙 점검
원칙판정근거
Primitive Obsession 금지해당 없음 도메인 값을 새로 도입하지 않았다. 조회표가 받는 상태 코드는 HTTP 프로토콜 값이며 Spring 이 HttpStatus · int 로 다루는 프레임워크 경계다 — 도메인 의미를 갖는 값이 아니라 Value Object 화 대상이 아니다. 엔티티 · Service 시그니처 · Request · Response 변경 0.
네이밍 규칙준수 ErrorStatusLabels 는 조회표 유틸이라 *Controller · *Service 등 접미사 규약 대상이 아니다. ProvisionErrorAttributes 는 Spring 확장점 DefaultErrorAttributes 를 대체하는 자리라 그 명명을 따랐다. 클래스 · 메서드 이름을 약어로 줄이지 않았다.
레이어 경계변경 0 Controller ↔ Service 는 여전히 Request · Response 만 오간다. 이번 변경은 예외 처리 advice 와 뷰, 그리고 정적 스크립트에 국한된다. 뷰에 엔티티를 노출한 곳이 없다.
@Transactional 경계변경 0 Service 를 손대지 않았다.
조건분기 legacy 확장 금지준수 상태 문구는 if · switch 사슬이 아니라 표 조회다. 상태가 늘어도 항목만 는다. 조사 판정도 병기형 쌍 배열과 숫자 · 라틴 판정표로 데이터화해, 새 쌍이 생겨도 판정 로직에 분기가 붙지 않는다.
예외 = 프로그램 예외 전용변경 0 예외를 신설하지도, 기존 예외의 발생 조건을 바꾸지도 않았다. 문구와 표시만 손댔다.
UX 모순은 UI 1차 차단강화 자원명 확인 입력(③)이 그 원칙의 문구판이다. 종전에는 "틀리게 입력 → 거절 → 기대값 학습" 이었는데, 기대 이름을 먼저 보여주어 틀릴 이유를 없앴다.
중복 · 가독성 금지준수 문구 템플릿 여덟 곳을 각각 고치는 대신 표시 직전 길목 세 곳으로 수렴시켰다. 자원명 표기는 새 방식을 발명하지 않고 휴지통 영구삭제 확인창 선례로 통일했다.
