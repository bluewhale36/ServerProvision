§0. 한 줄 요약

Windows 를 어느 디스크에 설치할 것인가 의 근거를 카드 CLI 의 나열 순서에서 볼륨을 만든 뒤 리눅스가 실제로 본 순서 로 옮기고, 설치 뒤 확증 기준을 카드 계열별 식별자 변환으로 바로잡았다. 함께 RAID 구성이 남은 시점의 준비도를 계획 으로 판정하고, 컨트롤러 뒤 볼륨 행에서 읽을 수 없는 값을 화면에 띄우지 않게 했다.

실기 3호(2026-09-08)에서 SAS3008 세 대가 전부 데이터 볼륨에 오설치되고 셋의 사후 확증이 어긋난 것이 출발점이다. 신규 URL 0 · 신규 예외 0 · DDL 0 — 이미 있는 네 창구에 재료 하나(OS 가시 디스크)와 기준 하나(계열 변환된 식별자) 만 실었다.

§2. 구현 — 무엇을 어디에

RAID 집행이 끝나면 진단 리눅스가 결과 검증을 위해 인벤토리를 다시 채집한다(E3.5-3 이 만든 자리). 이 리눅스는 방금 만들어진 볼륨을 이미 보고 있으므로, 여기에 lsblk 의 순서와 WWN 을 실으면 "OS 가 이 볼륨을 몇 번째로 보는가" 를 서버가 처음으로 알게 된다. 에이전트는 SCSI 재탐색 뒤 장치 수가 두 번 연속 같아질 때까지(최대 약 15 초) 기다린다.

§3. 강제 장치 · 원칙 점검 · 테스트

같은 결함이 다시 나려면 아래 중 하나를 깨야 한다. 규율이 아니라 타입 · 호출 구조가 막는다.

  • 변환이 한 곳 — windowsUniqueIdOf 하나가 ①의 WWN 매칭과 F-7 의 사후 확증을 함께 담당한다. 같은 식별자를 양쪽에서 읽은 것이라 어긋날 수 없다.
  • 세 값의 확신도 — CONFIDENT · DEFERRED · BLOCKED. "못 정했다" 와 "아직 정할 때가 아니다" 를 boolean 둘로 흩지 않아 F-1 처럼 미확정이 차단으로 둔갑하지 않는다.
  • 근거와 기준이 값 — Basis 가 wire()/fromWire 로 원장을 왕복해 화면이 근거를 지어내지 못하고, expectedUniqueId 는 서빙 시점에 박혀 이후 볼륨이 바뀌어도 흔들리지 않는다.
  • 실행기 안전망 — 선택이 CONFIDENT 가 아니면 WindowsInstallingExecutor 가 대기해 DEFERRED 가 빈 번호로 굽는 일이 없다(§7).

D1 · 검증 재채집에 lsblk 동봉

조작 — A1 을 등록 · 정의서 6 할당 · 개시하고 진단부터 RAID 집행까지 완주시킨 뒤, 검증 close 에 세 장치를 동봉했다: 가상 미디어를 흉내낸 sda(USB · 0B · WWN 없음), OS 볼륨 sdb(446.6G · 0x600605B00D18AA1E322807F9084A72AA — 대문자 · 0x 접두), sdc(18.2T · 소문자 WWN).

실측 — 커서가 OS_INSTALLING · AWAITING_BOOT 로 전진했고 hardware_spec.disks 3 행의 WWN 이 접두 제거 + 소문자로 정규화됐다(sda 는 wwn:null). "디스크 (OS 가시 장치)" 표는 2 행만 그렸다 — sdb 는 RAID 볼륨 · spvR1V1 배지를 얻고 종류 · 전송은 — 로 비었으며 sda 는 사라졌다. 카드는 디스크 0 · 근거 RAID 검증 재채집(lsblk 순서). PASS — 뒤섞인 실물 WWN 이 단일 통로에서 흡수됐고 표시와 번호 계산이 같은 걸러내기를 썼다.

D2 · 서빙 시점의 번호와 기준

실측 — DiskConfiguration · InstallTo 두 자리 모두 <DiskID>0</DiskID>. 원장 provisioning_history(OS_INSTALLING · RUNNING).status_meta 에 "targetDiskId":0 · "expectedUniqueId":"600605b00d18aa1e322807f9084a72aa" · "diskBasis":"lsblk". PASS — 굽는 번호와 나중에 대조할 기준이 같은 순간에 한 곳으로 들어갔다.

D3 · 설치 뒤 확증

조작 — 완료 보고를 대문자 UniqueId(600605B00D18AA1E322807F9084A72AA)로 올린 뒤, 같은 보고를 재전송하고 종단 뒤 옛 번들 토큰 URL 에 접근해 봤다(비정상 조작).

실측 — 첫 보고 {"closed":true,"provisioningCompleted":true}, 재전송은 {"closed":false} 로 흡수되고 원장 행이 불변. 다음 /boot 는 exit(종단)이고 옛 번들 5 파일은 전부 404. 카드는 설치된 디스크가 계획한 OS 볼륨과 일치합니다, SUCCEEDED 행 meta 에 "diskConfirmed":true. PASS — F-7 이 만들던 "맞게 설치됐는데 어긋났다고 표시" 의 정상 축이 성립한다.

D4 · 미동봉 → 계열 순서 규칙 폴백

조작 — 별도 게스트 A2 로 D1 과 같은 흐름을 VERIFY_DISKS 없이 수행했다(구 에이전트가 붙은 서버를 흉내낸 것).

실측 — 카드가 설치 대상 디스크 — 디스크 0 · 근거 카드 계열 순서 규칙 로 바뀌었고 서빙 meta 는 "diskBasis":"inventory-order"(번호와 기준 식별자는 D2 와 같은 값), DiskID 두 자리도 0 이다. PASS — 본안이 없으면 보조안으로 내려가되 근거 문구가 달라져 폴백이 조용히 일어나지 않는다.

D5 · 계획 기반 준비도 (F-1)

조작 — A1 이 RAID 단계에 들어와 인벤토리는 채집됐으나 볼륨 실물은 없는 시점의 카드를 열었다. 실기 3호에서 BLOCKED 가 뜨던 자리다.

실측 — 준비도 문제 없음 — 다음 부팅에서 설치를 시작할 수 있습니다, 설치 대상 디스크 RAID 구성 뒤 확정 — 계획의 OS 영역 spvR1V1. 한 단계 더 앞(인벤토리조차 없음)에서는 RAID 구성 뒤 확정 — 진단이 RAID 인벤토리를 채집하면 계획의 OS 영역을 보입니다 로 안내가 한 칸 물러섰다. PASS — 준비도가 정상 흐름을 막지 않으면서도 아직 확정이 아님을 숨기지 않는다.

C1 · 막는 방식과 안내

조작 — D5 · D1 · D4 의 문구를 운영자 관점에서 읽고, 각 문구가 ① 왜 지금 이런 상태인지 ② 다음에 무엇을 하면 되는지를 담는지 평가했다.

실측 — D5 문구는 "왜 번호가 없는지" 와 "무엇을 기다리면 되는지" 를 한 줄에 담고 계획 볼륨 이름을 그대로 써서 RAID 계획 표와 눈으로 이어진다 — 옛 BLOCKED 가 부르던 "내가 뭘 잘못했나" 를 없앴다. D1 과 D4 는 같은 번호라도 어떤 재료로 정했는지 를 구분해 준다. 볼륨 배지는 OS 가 보는 sdb 와 카드가 만든 볼륨을 잇고, 배지 없는 sdc 는 "카드 뒤인데 계획의 볼륨이 아니다" 로 읽힌다. PASS — 다만 서빙 뒤 근거 줄이 사라지는 관찰이 여기서 나왔다(§7 O-1).

§6. 미수행 항목과 사유
D6 — OS 영역 없는 정의서 → 준비도 BLOCKED os volume missing in plan : 미수행. 이 시나리오에 필요한 정의서를 만들 수 없다.

묶음 역할을 전부 Data 영역 으로 두고 저장하려 하면 폼이 OS 영역이 될 수 있는 묶음 … 이 없습니다 — OS 설치 단계가 있으면 저장할 수 없습니다. 를 띄우고 제출이 통과하지 않으며, 화면을 우회한 direct POST 도 SettingSaveRequest.isOsVolumeDeterminable 이 400 으로 거절한다.

준비도 BLOCKED 경로는 UI 1차 차단과 서버 가드가 같은 판정을 공유 해 정상 경로로 도달할 수 없고, 도달하려면 스냅샷(assigned_process_snapshot)을 손으로 위조해야 한다. 그래서 차단 자체를 두 경로로 확인한 것으로 갈음 하고 미수행으로 남긴다. os volume missing in plan 은 가드를 뚫은 저장본에 대한 안전망이며 판정은 WindowsInstallReadinessResolverTest 로 고정돼 있다.

§7. 발견 · 정정

CP5 는 결함을 발견해도 고치지 않고 보고만 했고, 세션이 그것을 검토해 둘을 정정하고 같은 샌드박스에서 다시 확인했다(09-09 14:40~14:45 KST). 새로 발견된 프로그램 결함은 0 건 이며, 하나는 관찰에서 승격된 표시 정정, 하나는 plan 검토에서 파생된 안전망 보강이다.

O-1 (관찰 → 정정) — 서빙 뒤 근거가 화면에서 사라진다

정정 전

상세가 targetDiskId 가 있으면 번호만 그리고, 근거(diskSelectionNote)는 targetDiskId 가 없는 분기에서만 그렸다.

근거는 원장 meta 에 남아 데이터 손실은 아니지만, "지금 굽고 있는 이 번호를 무엇으로 정했나" 를 확인해야 할 시점에 화면에서 읽을 수 없다.

정정 후

GuestServerQueryService.windowsInstallOf 가 서빙 뒤에는 원장 meta 의 diskBasis 로 근거를 되살려 "디스크 N" 줄 옆에 붙인다. 출처만 바뀌고 문구는 같다.

재검증 — 서빙 중인 A2 상세에서 설치 대상 디스크 디스크 0 근거 카드 계열 순서 규칙 확인.

DEFERRED 가 서빙에 닿을 가능성 (plan 검토 파생)

준비도가 DEFERRED 를 통과시키므로 "READY 인데 번호는 아직 없는" 상태로 서빙 창구에 닿을 수 있는가 하는 물음이 남는다. 그 경로를 확인한 뒤 WindowsInstallingExecutor 가 준비도와 무관하게 선택이 CONFIDENT 가 아니면 대기 하도록 안전망을 두었고(disk selection not confident · 착수 훅 동일), WindowsInstallingExecutorTest.deferredDiskSelection_holdsWithoutOpening 으로 고정했다.

CP5 는 결함을 새로 발견하지 못했다. 대신 O-1 처럼 "동작은 맞지만 화면이 그 순간 필요한 것을 안 보여준다" 는 관찰을 냈고, 그것이 이 슬라이스의 목적(근거를 사람이 읽게 한다)과 정면으로 닿아 정정 대상이 됐다. 판정 로직의 오류는 29 건의 단위 테스트가 실기 3호 실측 표본으로 앞서 걸렀다.
