§0. 이 보고서의 특수성 — CP5 를 브라우저가 아니라 단위 테스트 전수로 수행했다

통상의 report 는 CP5 샌드박스 브라우저 검증의 계획 · 수행 기록 · 스크린샷 증거가 본문의 중심이다. 이번 슬라이스는 CP4 승인 시점에 사용자가 검증 수단 자체를 지정했고, 그 지시에 따라 수단이 바뀌었다. 지시 원문은 다음과 같다.

“규칙에 따라 디스크가 raid 볼륨으로 잡히는 경우의 수를 모두 확인하는 테스트 케이스를 작성해서 진행한다. 다만 이 테스트는 굳이 브라우저 테스트로 할 필요는 없다. RaidPlanner 의 코드에 따른 테스트 결과를 보고자 하는 목적”

이 지시가 합리적인 이유는 이번 슬라이스의 산출물이 화면이 아니라 판정이기 때문이다. E3.5-2 가 만든 것은 “어떤 디스크가 어떤 볼륨으로 묶이는가” 를 결정하는 순수 함수(RaidPlanner)이며, 화면은 그 결과를 표로 옮겨 보여줄 뿐이다. 브라우저에서 한 번에 볼 수 있는 것은 특정 인벤토리 하나에 대한 결과 한 벌인 데 반해, “경우의 수를 모두” 는 규칙 축의 조합을 전수로 돌려야 확인된다.

그래서 이 보고서의 증거 구조는 다음과 같이 달라진다.

  • 검증 수단 — 브라우저 조작이 아니라 RaidPlanner 단위 테스트 전수(신규 61 건).
  • 증거 — 스크린샷 0 장. 항목마다 붙는 것은 그 항목을 덮는 테스트 그룹과 그 실행 결과다(§5).
  • 항목 식별자 체계는 유지 — 정상 A1~A7 · 비정상 B1~B4 · 경계와 막는 방식 C1~C3 의 14 항목을 먼저 계획하고(§4) 같은 식별자로 수행을 대조한다(§5).
  • 화면 확인은 이관 — 상세 화면의 “RAID 구성 계획” 섹션이 실제로 어떻게 렌더되는지는 확인하지 않았다. CP7 실기 일괄로 넘긴다(§6).
§6 이 이 보고서의 핵심이다. 검증 수단을 바꾼 슬라이스의 보고는 “그래서 무엇이 확인되지 않은 채 남았는가” 를 사유와 함께 적어야 성립한다. 감추면 다음 사람이 검증된 층과 검증되지 않은 층을 구분하지 못한다.
§1. 배경 · 진단

이 슬라이스의 자리 — 머리와 손의 분리

바로 앞 슬라이스인 E3.5-1 은 RAID 카드의 인벤토리를 적재하고 게스트를 WAIT 상태로 세워 두는 데까지 갔다. 카드에 어떤 물리 디스크가 몇 대 꽂혀 있고 기존 볼륨이 무엇인지는 알지만, 그것으로 무엇을 만들지는 아직 아무도 정하지 않은 상태다. E3.5-2 는 그 “무엇을 만들지” 를 정하는 머리(계획)를 만든다. 정해진 계획을 카드에 실제로 지시하는 손(집행)은 다음 슬라이스 E3.5-3 의 몫이며, 이번 슬라이스는 카드에 아무것도 쓰지 않는다.

CP1 검수에서 원안의 의미론 결함이 잡혔다

plan 의 🎬 미리보기로 규칙을 직접 조작해 보던 중 사용자가 원안의 결함을 발견했다. 원안은 개수 축 EXACT n 을 “일치하는 디스크에서 n 대를 잘라 쓴다” 는 슬라이싱으로 해석했는데, 이 해석에서는 960 GB 계급 3 대가 있고 규칙이 EXACT 2 이면 2 대만 떼어 볼륨을 만들고 남은 1 대가 고립된다. 사용자는 그 1 대가 아무 데도 속하지 않은 채 남는 것이 의도와 다르다고 지적했다.

원안 — 슬라이싱

960 GB 3 대 × EXACT 2

→ 앞 2 대로 볼륨 생성
→ 남은 1 대 고립

사용자가 의도하지 않은 잔여가 조용히 생긴다

개정 — 엄격 일치 (결정 6)

960 GB 3 대 × EXACT 2

→ 그룹 크기가 2 가 아니므로 통째로 미소비
→ 3 대 전부 다음 규칙으로 흘러감

소비되지 않았다는 사실이 화면에 표시된다

이 개정이 결정 6(엄격 일치) 이다. EXACT n 은 이제 “그룹의 크기가 정확히 n 일 때만 그 그룹을 통째로 소비한다” 를 뜻하고, 크기가 맞지 않으면 한 대도 건드리지 않은 채 다음 규칙으로 흘려보낸다.

여기서 파생되는 새 위험이 사각 규칙이다 — 엄격 일치로 바꾸면 어떤 규칙도 그룹 크기를 맞추지 못해 아무것도 소비하지 못하는 규칙이 생길 수 있고, 사용자는 그것을 모른 채 계획을 저장할 수 있다. 결정 7 이 그 방어를 둘로 나눴다 — 정의서 저장 시점의 정적 차단은 E3.5-4 로 배치하고, 이번 슬라이스는 계획 결과에 “이 규칙은 아무것도 소비하지 않았다” 를 표시하는 것까지 맡는다(항목 C2 가 이것을 검증한다).

이 결함이 코드 착수 전에 잡혔다는 점이 이 슬라이스의 특징이다. plan 의 미리보기 데모가 서버 규칙을 그대로 미러링하는 판정 JS 로 만들어져 있었기 때문에, 구현이 시작되기 전에 의미론 차원의 오류가 드러났다.
§2. 구현

계획 산출의 6 단계 파이프라인

구현의 중심은 RaidPlanner 하나다. 의존성이 0 인 순수 static 유틸리티이며, 입력(규칙 목록 · 우선순위 목록 · 인벤토리 · 기존 구성 정책)을 받아 결과 하나를 돌려준다. 내부는 여섯 단계가 순서대로 흐른다.

① 정책 게이트 PRESERVE 인데 기존 볼륨이 있다 ──▶ EXISTING_CONFIG 거절 │ DESTROY 이고 기존 볼륨이 있다 ──▶ 선행 삭제 플래그 true ▼ ② Candidate 정규화 상태 화이트리스트 · 종류/전송 enum 해석 · 표기 → 2진 바이트 │ (해석 실패한 디스크는 사유를 달고 미배정으로 이탈) ▼ ③ 규칙 순서 소비 축 필터 → 계급 그룹핑 → 엄격 일치(EXACT) / AT_LEAST │ 소비된 디스크는 풀에서 빠져 뒤 규칙이 볼 수 없다 ▼ ④ 칩 한계 memberCountBlockReason ──▶ MEMBER_COUNT 거절 │ maxVolumes 초과 ──▶ VOLUME_LIMIT 거절 ▼ ⑤ 역할 · OS 판정 OS 고정 규칙이 있으면 그것만 후보 → 없으면 우선순위 → CapacityOrder ▼ ⑥ 조립 RaidPlan(계획 볼륨 · 단독 디스크 · 규칙 소비 · 미배정 · OS 부재 사유)

④ 의 거절이 볼륨 하나를 빼는 것이 아니라 계획 전체를 거절하는 이유는, 일부만 집행하면 사용자가 의도하지 않은 상태가 실물 카드에 남기 때문이다. 계획은 통째로 성립하거나 통째로 거절된다.

구현 중 판정 1 건 — 거절 배지의 색

거절 배지에 n-badge-red 를 쓰려다 전역에 정의가 없는 클래스임을 실측으로 확인하고 n-badge-gray 를 채택했다. 정의 없는 CSS 클래스가 화면에 조용히 무효과로 남는 기존 사고 계열을 피한 것이다.

불가침 원칙 점검

  • Primitive Obsession — CLI 가 뱉는 용량 표기를 원시 String 으로 흘리지 않고 RaidReportedSize 가 바이트로 환산해 다룬다. 정책은 RaidExistingConfigPolicy, 판정된 역할은 PlannedVolumeRole, 칩 계열은 RaidChipFamily 로 각각 enum 이다.
  • 조건분기 legacy 확장 금지 — 칩 계열의 제약을 RaidChipFamily 의 method-per-constant 로 두었다. 계열이 늘어도 RaidPlanner 에 분기가 늘지 않고 상수 하나가 는다. 반환 규약(null = 통과, 문자열 = 거절 사유)은 SupportedRaidLevels.blockReasonFor 선례를 그대로 따랐다.
  • 레이어 경계 — 엔진의 계획 모델을 뷰에 직접 노출하지 않는다. 화면으로 나가는 것은 GuestServerDetailResponse 안의 뷰 record 6 종(RaidPlanPreview · RaidPlanBranch · PlannedVolumeView · PlannedPassthroughView · UnassignedDiskView · RuleOutcomeView)이다.
  • 네이밍 — 신규 클래스는 모두 도메인 의미를 직접 드러내는 명칭이다. Controller · Request 접미사 규약은 이번 슬라이스에 해당 대상이 없다(신규 컨트롤러 0 · 신규 URL 0).

별건 산출물

사용자 요청으로 RaidPlanner 의 내부 로직 해설 html 1 부를 별도 산출했다(세션 스크래치 — 6 단계 파이프라인 · 3 층 데이터 모델 · 불변식). 저장소 산출물이 아니다.

DDL 0 · 엔티티 변경 0 · 신규 URL 0 · Controller 변경 0 — 계획은 저장되지 않고 조회 시점에 재산출되는 파생물이므로 영속 스키마를 건드리지 않는다.

기존 테스트 수정 — fixture 6 곳 (3 파일)

응답 record GuestServerDetailResponse 에 raidPlan 파라미터가 하나 늘면서, 그 record 를 직접 생성하는 테스트 fixture 의 생성자 호출 6 곳(3 파일)에 null 인자를 추가했다. 로직 변경은 없다.

통합 테스트 4 범주(성공 2xx · 400 · 404 · 409)는 이번 슬라이스에 적용 대상이 없다 — 신규 엔드포인트가 0 이고 Controller 변경이 0 이다. 계획은 기존 게스트 서버 상세 조회에 딸려 나가는 파생물이라 새로 열린 HTTP 표면이 없다.

정상 흐름 A — 항목별 확인 대상

  • A1 축 필터 전수 — 종류 3 가지 × 전송 4 가지 중 유효한 11 조합(HDD × NVMe 는 정의서 검증 단계에서 이미 금지된다)이, 5 개 스펙 클래스를 섞어 만든 디스크 풀에서 정확히 기대한 클래스만 잡아내는가.
  • A2 용량 축 — 480 GB 지정이 그 계급만 골라내는가, 4 TB 지정이 같은 실물의 서로 다른 두 CLI 표기(3.637 TB 와 3815447 MB)를 같은 계급으로 묶는가, AUTO 가 계급별로 그룹을 나누는가.
  • A3 개수 축 전수 — EXACT 2 를 그룹 크기 {1, 2, 3, 4, 6} 각각에 적용해 2 일 때만 소비되는가(결정 6), AT_LEAST 2 를 {1, 2, 3, 5} 에 적용해 n 이상이면 그룹 전체를 흡수하는가.
  • A4 레벨 축 — RAID0 · RAID1 · RAID5 · RAID6 · RAID10 각각이 볼륨을 만들고 유효 용량이 레벨별 usableDisks 계수대로 계산되는가. “RAID 없음”(단독 디스크)에도 개수 축이 적용되는가.
  • A5 흐름 — 앞 규칙이 소비한 디스크를 뒤 규칙이 보지 못하는가(순서 소비), 앞 규칙이 소비하지 못한 그룹이 뒤 규칙으로 흘러가는가(CP1 검수 시나리오), 일치 디스크가 0 대인 규칙을 건너뛰는가.
  • A6 역할 · OS 판정 — OS 고정 규칙이 여러 볼륨을 만들면 첫 볼륨만 OS 인가, 우선순위 판정이 규칙 순위를 따르는가, 동순위에서 용량 정렬 기준이 적용되는가, 우선순위가 비어 있으면 열거 순으로 정해지는가, 단독 디스크와 “영역 할당 없음” 이 각각 처리되는가.
  • A7 실측 종단 — E3.5-1 이 남긴 실측 픽스처 원문을 파서에 넣어 얻은 인벤토리가 계획까지 통과하는가(MegaRAID · CRA3338 두 계열).

비정상 조작 B — 항목별 확인 대상

  • B1 보존 정책 + 기존 볼륨 — 카드에 볼륨이 남은 상태에서 보존 정책으로 계획하면 EXISTING_CONFIG 로 거절되는가. 합성 인벤토리와 실측 픽스처 양쪽으로 확인한다.
  • B2 칩 계열 한계 — MPT_IR 에 RAID1 3 대를 요구하면 MEMBER_COUNT, 볼륨 3 개를 요구하면 VOLUME_LIMIT 로 계획 전체가 거절되는가. 같은 입력을 MEGARAID 는 통과시키고 카드 미감지는 관용하는가.
  • B3 디스크 제외 5 종 — 상태 불량 · 상태 없음 · 미지의 종류 · 미지의 전송 · 용량 환산 불가, 다섯 가지가 각각 사유와 함께 미배정으로 떨어지고 같은 인벤토리의 정상 디스크는 그대로 볼륨이 되는가.
  • B4 표기 거절 — null · 빈 문자열 · n/a · 미지 단위(PB) · 숫자와 단위가 뒤집힌 어순, 다섯 입력이 전부 결과 없음으로 떨어지는가.

막는 방식 · 경계 C — 항목별 확인 대상

  • C1 ±3% 경계 — 허용률의 양쪽 경계가 정확히 물리는가(+2.9% 와 −2.9% 는 안, +3.1% 와 −3.1% 는 밖). 실물로 존재하는 인접 계급(500 GB · 512 GB)이 옆 계급으로 잘못 잡히지 않는가.
  • C2 소비 0 표시 — 아무것도 소비하지 못한 규칙이 결과에 그 사실을 남기는가. 결정 7 의 “표시로 막는다” 가 실제로 동작하는지 확인하는 항목이다.
  • C3 강하 없음 — OS 고정 규칙이 있는데 그 규칙이 볼륨을 하나도 만들지 못했을 때, OS 부재 사유만 남고 우선순위 판정으로 내려가지 않는가. 고정을 지정한 사용자의 의도를 시스템이 임의로 대체하지 않는지 보는 항목이다.

A5 — 후행 규칙으로 흘려보내는 흐름 (CP1 검수 시나리오)

조작 : 인벤토리 = 480 GB 급 SSD 2 대 + 960 GB 급 SSD 3 대 + 4 TB HDD 3 대. 규칙 = [규칙 1 : RAID1 · SSD · EXACT 2] → [규칙 2 : RAID5 · 용량 AUTO · AT_LEAST 3].
기대 : 규칙 1 은 480 GB 급 2 대만 소비하고, 그룹 크기가 2 가 아닌 960 GB 급 3 대는 손대지 않는다(결정 6). 규칙 2 가 남은 960 GB 급 3 대와 4 TB 3 대를 계급별로 각각 흡수해 볼륨 2 개를 만든다.
실제 : spv-r1-v1(멤버 s:0 · s:1) · spv-r2-v1(m:0 ~ m:2) · spv-r2-v2(h:0 ~ h:2), 미배정 0. OS 는 spv-r1-v1 로 판정됐다 — SATA SSD 동순위에서 SMALLER_FIRST 가 적용돼 480 GB 급이 이겼다.
판정 : PASS — CP1 검수 때 사용자가 지적한 기대와 정확히 일치한다. 고립되는 디스크가 없다.

A3 — EXACT 2 에 6 대 그룹 (결정 6 의 직접 증거)

조작 : 같은 계급 디스크 6 대만 있는 인벤토리에 EXACT 2 규칙 하나를 적용.
기대 : 슬라이싱이었다면 앞 2 대로 볼륨을 만들고 4 대가 남았을 것이다. 엄격 일치에서는 그룹 크기가 2 가 아니므로 한 대도 소비하지 않는다.
실제 : 볼륨 0 · 미배정 6 · 미배정 사유 “규칙 1 · 2개 조건에 6대라 미소비” · 규칙 결과에 소비 0 표시(consumedNothing).
판정 : PASS — 결정 6 의 새 의미가 코드에 실렸음이 산출값으로 확인된다. 같은 결과가 C2(소비 0 표시) 의 증거이기도 하다.

A7 — 실측 MegaRAID 원문의 종단 통관

조작 : E3.5-1 이 남긴 실측 픽스처 원문(SSD 446.625 GB × 2 + HDD 3.637 TB × 6 · 기존 VD 2 개)을 파서에 통과시켜 얻은 인벤토리로, 파괴 정책의 계획을 산출.
기대 : 기존 볼륨이 있으므로 선행 삭제 플래그가 서고, SSD 2 대가 RAID1 로 묶여 OS 가 되며, HDD 6 대가 RAID5 가 된다.
실제 : 선행 삭제 플래그 true · spv-r1-v1(멤버 252:0 · 252:1 · 역할 OS) · spv-r2-v1(HDD 6 대 · RAID5 · 유효 용량 = 5 × 3.637 TiB 환산 바이트) · 미배정 0.
판정 : PASS — 합성 인벤토리가 아니라 실제 장비가 뱉은 문자열이 파서와 계획을 연달아 통과했다.

B2 — 칩 계열 한계 (거절이 계열 판정임의 대조)

조작 : MPT_IR 카드에 RAID1 · EXACT 3 규칙을 주고, 별도로 계급 3 개 × EXACT 2 로 볼륨 3 개가 나오는 입력을 준다. 같은 입력을 MEGARAID 와 카드 미감지 상태에도 그대로 반복한다.
기대 : MPT_IR 에서만 거절되고, 나머지 둘은 통과한다.
실제 : MEMBER_COUNT — “spv-r1-v1 — MPT_IR 의 RAID1 은 정확히 2대로만 구성됩니다” / VOLUME_LIMIT — 계획 볼륨 3 개가 한계 2 개를 넘는다. 같은 입력을 MEGARAID 와 카드 미감지에 주면 거절 없이 통과했다.
판정 : PASS — 거절이 입력 자체의 문제가 아니라 계열 판정임이 대조로 드러난다. 카드를 감지하지 못한 경우에 관용하는 것도 의도대로다.

C1 — ±3% 경계와 인접 계급 차단

조작 : 지정값 대비 편차가 +2.9% · −2.9% · +3.1% · −3.1% 인 네 표기를 각각 대조하고, 실물로 존재하는 500 GB 디스크의 CLI 표기(465.661 GB)를 480 GB 지정과 대조한다.
기대 : 앞 두 점은 일치, 뒤 두 점은 불일치. 500 GB 실물은 480 GB 계급으로 잡히지 않는다.
실제 : 네 경계점이 모두 기대대로 갈렸고, 500 GB 실물은 편차 +4.2% 로 차단됐다.
판정 : PASS — 허용률이 양방향으로 못박혔다. 한쪽만 검증하면 반대쪽이 느슨해도 드러나지 않는데, 쌍으로 확인해 그 구멍을 닫았다.

§7. 발견한 것

결함 발견 0 — 다만 “잡을 것이 없었다” 는 뜻은 아니다

이번 검증 구간에서 새로 발견된 결함은 없다. 그런데 이 슬라이스에서 실제로 결함이 잡힌 시점은 구현 이전이었다 — CP1 검수에서 사용자가 부분 소비로 디스크가 고립되는 문제를 발견했고, 그것이 결정 6 으로 개정돼 코드에 처음부터 반영됐다(§1). plan 의 미리보기 데모가 판정 JS 를 서버 규칙의 미러로 만들어 두었기 때문에, 코드가 한 줄도 없는 상태에서 의미론 차원의 결함이 드러난 것이다. 같은 결함을 CP5 에서 잡았다면 구현 전체를 되돌려야 했다.

관찰 1 — 응답 record 의 성장 비용

GuestServerDetailResponse 외곽 record 에 파라미터를 하나 더한 것이 테스트 fixture 6 곳 수정을 유발했다(§3). 로직과 무관한 기계적 수정이지만, 이 record 가 앞으로도 계속 자랄 것을 감안하면 빌더 도입을 검토할 여지가 있다. 이번 슬라이스에서는 조치하지 않았다.

관찰 2 — 전역에 정의되지 않은 CSS 클래스

거절 배지에 쓰려던 n-badge-red 는 전역에 정의가 없는 클래스였다(§2). 사용 전 실측으로 확인해 n-badge-gray 로 회피했다. 기존에 적립된 “전역 미정의 CSS 클래스” 건과 같은 계열이나, 이번에는 쓰지 않았으므로 신규 적립은 없다.
