§3. 구현 — 상태 기계

워커(BiosSettingWorker)는 커서가 BIOS_SETTING 인 게스트를 집어 한 대씩 BiosSettingCycle.advance(독립 트랜잭션)에 넘긴다. 사이클은 재료를 SettingContext 에 모아 registry 에 묻고 위에서 처음 맞는 행을 실행한다.

#조건하는 일클래스
1RUNNING 행에 rebootAt 있음복귀(접촉 시각 > rebootAt)가 아니면 시한 안에서 대기하고, 시한을 넘으면 RETURN_TIMEOUT. 복귀면 신원 확인 → GET Bios → 원장의 목표와 대조 → APPLIED + 커서 전진, 어긋나면 READBACK_MISMATCHReturnReadbackStep
2목표 null (활성 할당 없음 · BASIC_SETTING 없음)아무것도 하지 않는다 — 창 밖이다SkipOutOfSettingWindowStep
3목표 비어 있음 (보드 일치 템플릿 0)SKIPPED NO_TARGET + 커서 전진. 열린 행이 있으면 그 행을 닫는다SkipNoTargetStep
4목표 있음 · BMC 없음FAILED BMC_REQUIREDFailNoBmcStep
5목표 있음 · BMC 있음신원 확인 → 원장 열기(재개면 기존 행) → PATCH 전체(If-Match:* → 412 면 fresh ETag) → pending 관찰 → 꺼져 있으면 On · 켜져 있으면 ForceRestart → rebootAt 기록BeginSettingStep

행 1 이 가장 위인 이유 — 이미 걸어 둔 재부팅의 결과를 무엇보다 먼저 거둔다. 창 밖 판정보다 위에 둔 것도 같은 이유로, 할당이 바뀌어도 굽은 것의 결과는 거둔다. 3 이 4 보다 위인 이유 — 할 일이 없는 게스트는 BMC 유무와 무관하게 건너뛴다. D-12 는 목표가 있을 때의 판정이다.

착수 재개 — 재부팅 명령이 실패하거나 워커가 죽으면 RUNNING 행이 rebootAt 없이 남는다. 다음 주기의 5행이 그 행을 이어받아(새로 열지 않고) 신원 대조부터 다시 한다.

원장 한 행의 생애 (SettingLedger)

open {origin:"setting", target} markPending + pendingSeen markRebooted + rebootAt close origin 을 사유로 덧쓰고 detail 추가 — target · rebootAt · pendingSeen 은 보존

닫힌 행은 불변이다 — ProvisioningHistory.updateRunningMeta 가 RUNNING 행만 받는다. 사유는 여덟이다 : APPLIED · NO_TARGET · BMC_REQUIRED · PATCH_REJECTED · READBACK_MISMATCH · RETURN_TIMEOUT · IDENTITY_MISMATCH · BMC_UNREACHABLE.

목표 공급 (BiosSettingResolutionProviderImpl, provisioning 측)

활성 스냅샷의 BASIC_SETTING 동결 템플릿 중 감지 보드와 boardModelId 가 같은 것만 선언 순서로 병합하고, 같은 속성은 뒤가 이긴다. 활성 할당이 없으면 Optional.empty(창 밖), 일치가 0 이면 빈 목표(NO_TARGET)다.

Redfish 층 (RedfishBiosService)

bios() 는 Attributes 와 ETag 를 함께 돌려주고, patchPending() 은 If-Match:* 로 먼저 쓴 뒤 PRECONDITION_FAILED 면 fresh ETag 로 한 번 더 쓴다 — 그래도 거절이면 예외를 그대로 올린다. pending() 은 404 를 empty 로 읽는다. 자격증명 폴백(BmcCredentialsFallback)을 그대로 지난다.

§7. 미수행 항목과 사유

미수행 없음 — 21 항목 전부 수행했다. 경로 변경이 하나 있다. B5 는 별도 게스트가 아니라 A1 게스트에서 그대로 성립했다. A2 의 35초 대기와 채증 사이에 복귀 시한(2분)이 먼저 지나 워커가 RETURN_TIMEOUT 으로 닫았고, 에이전트의 /boot 는 그 6초 뒤라 이미 닫힌 행에 영향이 없었다. 설계대로 동작한 결과이므로 그 게스트를 B5 의 증거로 채증하고 A3 은 새 게스트로 다시 했다.

수행했다는 것과 덮었다는 것은 다르다. 이 CP5 가 확인하지 못한 것 다섯을 남긴다.

  1. 실기 미수행. 모의 BMC 는 E0-4-3 실측 계약의 재현이지 장비가 아니다. 실제 BMC 의 Bios 리소스 갱신 시점, ForceRestart 뒤 POST 소요, 복귀 시한 20분의 적정은 CP7 실기(E 단계 일괄) 소관이다.
  2. 무변경 PATCH 의 pending 생성 여부(개정 2 의 미실측). 모의 BMC 는 값이 같아도 pending 을 만든다(A4 의 pendingSeen=true). 실 장비가 같은 값을 pending 으로 잡는지는 아직 모른다 — pendingSeen 관찰값이 그 답을 실기에서 준다.
