§1. 배경 · 진단
개정 안내 (2026-09-02) — §1~§5 는 CP6 제출 시점(09-01)의 기록이다. CP6 검수에서 값 모델이 개정되어(미지정 축 폐지 → 각 enum 의 HII 기본값이 기본 · 8축 항상 명시 전송) 본문의 “미지정(카드 기본값)” 서술은 개정 전 상태다. 개정 내용과 재실증은 §7 말미 “CP6 검수 반영 — 5. 설계 개정” 절에 있다.

2026-09-01 RAID CP7 실기 직후, 사용자가 요구를 확정했다. MegaRAID HII 화면의 “CONFIGURE VIRTUAL DRIVE PARAMETERS” 에서 지정할 수 있는 항목 전체 — 8 축을 디스크 묶음 규칙 행마다 지정할 수 있어야 한다는 것이다. 종전까지 세팅 정의서의 묶음 규칙은 RAID 레벨과 디스크 선택까지만 다뤘고, 볼륨을 어떤 정책으로 만들 것인가는 카드 기본값에 맡겨져 있었다.

제약 — 사내 표준값이 비공개다

어떤 값을 표준으로 쓰는지는 이번 슬라이스 시점에 공개되지 않았다. 그래서 표준값을 코드에 탑재하지 않는다. 각 축의 기본은 “미지정(카드 기본값)” 이고, 미지정이란 곧 storcli 옵션을 전달하지 않는다는 뜻이다. 표준이 정해지면 그때 값을 고르면 되고, 그 전까지 시스템은 카드가 원래 하던 대로 만든다.

CP1 토론에서 정리된 쟁점 — enum 확장성

사용자가 CP1 에서 제기한 쟁점이다. 축의 값을 storcli 어휘 그대로 enum 으로 굳히면, 다른 계열 카드(sas3ircu 등)를 다룰 때 어휘가 맞지 않아 enum 이 계열마다 갈라진다. 정리된 구조는 “중립 개념으로 명명하고, CLI 어휘는 계열 집행 계층이 소유한다” 이다. enum 은 개념(예: Write Back)을 가리키고, 그 개념을 어떤 문자열로 카드에 던질지는 집행 쪽 책임으로 내려간다.

§2. 구현 (R1 ~ R10)

도메인 — 값의 정의와 조립 (R1 ~ R4)

R1. provisioning.setting.enums 아래 Vd* enum 8 종을 두었다. 각 enum 이 cliToken(storcli 어휘)을 소유하고 UNSPECIFIED 를 포함한다. 여덟 축 중 Initialization 만 미지정의 의미가 다르다 — 다른 축의 미지정이 “카드 기본값” 인 반면, Initialization 의 미지정은 “정책 기본(fast force)” 이다. 실기에서 확립한 동작이라 여기에 맞춰 의미를 구분했다.

R2. VdParameters record 가 조립의 단일 진실 출처다. 8 축의 값을 어느 시점에 어떤 문자열로 내보낼지가 전부 여기 모인다.

R3. DiskGroupRuleRequest 를 7 축으로 넓혔다. 6-인자 호환 생성자를 남겨 구 저장본과 기존 픽스처가 마이그레이션 없이 그대로 읽힌다. 묶음 규칙의 중복 판정(identity)에는 VD 파라미터를 넣지 않았다 — 같은 디스크 묶음을 정책만 달리해 두 번 정의하는 것은 여전히 중복이다.

R4. 서버 가드는 DiskGroupRules 의 규칙 9 다. 두 경우를 400 으로 거절한다.

  • 비 RAID 묶음에 지정 — 팩토리 vdParametersOnNonRaid
  • 미지원 계열 카드에 지정 — 팩토리 vdParametersNotSupported
UI 차단과 서버 가드가 판정 하나를 공유한다. 화면의 잠금 조건과 서버 가드가 RaidChipFamily.supportsVdParameters() 하나를 함께 호출한다. 두 곳에 조건을 복붙하지 않았으므로 드리프트가 생길 자리가 없다.

배치 — 칩 계열을 자원 쪽으로 (R5 ~ R6)

R5. RaidChipFamily 를 execution 에서 management.raidcard.enums 로 옮겼다. plan 의 D3 배치를 정정한 것이다. 이유는 역류 방지다 — 카드 자원 엔티티가 이 enum 을 필드로 갖게 되는데, 그대로 두면 management 엔티티가 execution 을 참조한다. 옮긴 자리는 RaidLevel 과 나란하다. 참조 10 파일을 갱신했다. 함께 supportsVdParameters() 와 getDisplayName() 을 얹었다.

R6. RaidCard 에 chipFamily(NOT NULL enum 컬럼)를 추가했다. 등록 · 수정 폼의 select, nudge 경로(attributes), Response 까지 이어진다. DDL 은 ddl/E3.5-6_raidcard_chip_family.sql(ALTER + 실측값 UPDATE 2 문 + NOT NULL)이고 schema.sql 을 동기화했다. 로컬 dev DB 에 적용해 실측값을 채웠다 — CRA3338 = MPT_IR, 9361-8i = MEGARAID.

통과 계약과 집행 (R7 ~ R8)

R7. PlannedVolume 과 RaidApplyPayload.VolumeSpec 에 조립 3 필드(createOpts · setOps · init)를 실었다. 필드 순서가 곧 직렬화 순서이고 그것이 agent 파이프 계약이라 순서 자체가 계약의 일부다. RaidPlanner 는 규칙에서 값을 복사하며, 한 규칙이 배수로 분할돼 여러 볼륨이 되면 분할된 모든 볼륨에 같은 값을 부여한다.

R8. agent.sh 의 파이프 형식이 NAME|LEVEL|SLOTS|CREATEOPTS|SETOPS|INIT 가 됐다. add vd 에 createOpts 를 인라인으로 붙이고, per-VD set 을 돌리고, per-VD 로 초기화한다(none 은 생략 · full 은 force · 기본은 fast force). 종전의 vall 일괄 초기화를 per-VD 로 재편한 것이며, Failure 출력 검사는 그대로 유지했다.

화면 (R9 ~ R10)

R9. 규칙 행에 ⚙ 토글과 접이식 서브 행(8 축 2 열 grid, 기본 접힘)을 붙였다. 지정한 축 수를 배지로 표시한다. 잠금은 카드 계열 × RAID 구성 여부 진리표를 따른다. CP1 의 Q1 판정 — 잠기면 값은 보존하되 전송에서 제외(vdParameters 를 null 로 보낸다) — 를 구현했다. 수정 진입 시 pre-fill 은 addDiskGroupRow 를 경유한다. 서브 행이 규칙 번호를 오염시키지 않도록 diskGroupRows() 에 서브 행 제외 필터를 넣었고, 드래그로 행 순서를 바꾸면 reattachVdRows 가 서브 행을 따라 재정렬한다.

R10. 정의서 상세 카드에서는 규칙 행 아래에 “VD 파라미터 — (지정 축 나열)” 을 부기한다(toDisplay). 지정한 축이 없으면 줄 자체가 나오지 않는다.

§5. CP5 수행 기록 (조작 · 기대 · 실제 · 판정)

A1 — 서브 행 렌더 (⚙ 토글 · 8 축 · 미지정 기본)

조작: MegaRAID 카드를 고른 상태에서 RAID1 묶음 규칙 행의 ⚙ 를 눌렀다.
기대: ⚙ 가 활성이고, 클릭하면 서브 행이 펼쳐지며 8 축이 전부 미지정 기본으로 렌더된다.
실제: ⚙ 가 활성 상태였고 클릭에 서브 행이 펼쳐졌다. 8 축이 전부 “미지정 (카드 기본값)” 으로 렌더됐고, Initialization 만 “미지정 (정책 기본 — fast)” 으로 다르게 표기됐다.
판정: PASS — 기본이 미지정이고, 의미가 다른 축의 표기가 실제로 갈라져 보인다.

A2 — 4 축 지정 → 배지 → 저장 → 상세 부기

조작: Write Policy 를 Write Back, Drive Cache 를 끔, Background Init 을 끔, Initialization 을 Full 로 지정한 뒤 정의서를 저장했다(정의서 7).
기대: 지정 축 수 배지가 4 로 뜨고, 저장 후 상세 카드의 해당 규칙 아래에 지정 값이 부기된다. 지정하지 않은 규칙에는 부기가 없다.
실제: 배지가 4 로 표시됐다(js 실측 {"badge":"4","badgeShown":true}). 저장 후 상세에 “VD 파라미터 — Write Back · Drive Cache 끔 · BGI 끔 · Init Full Initialization” 이 부기됐고, RAID 를 구성하지 않는 규칙 2 에는 부기 줄이 나오지 않았다.
판정: PASS — 입력 → 배지 → 저장 → 상세 표시가 끝까지 이어진다.

부수 실증 — 400 왕복에서 서브 행 값이 보존된다. 첫 제출이 다른 규칙(규칙 8 — 포섭) 위반으로 400 재렌더됐는데, 이때 서브 행에 넣은 값(배지 4)과 파괴 선택이 그대로 남아 있었다. 계획에 없던 확인이지만 서버 왕복 후 폼 복원이 서브 행까지 미친다는 것을 보여준다.

A3 — 수정 pre-fill (8 축 복원 · 배지)

조작: 저장한 정의서의 수정 화면(/setting/7/edit)에 진입해 서브 행 상태를 js 로 실측했다.
기대: 지정했던 4 축이 값 그대로 복원되고, 지정하지 않은 축은 미지정을 유지하며, 배지가 다시 4 로 뜬다.
실제: 아래가 실측 원문이다.

{"wp":"WRITE_BACK","dc":"OFF","bgi":"OFF","init":"FULL","strip":"UNSPECIFIED","badge":"4","badgeShown":true}

판정: PASS — 지정 축은 값으로, 미지정 축은 UNSPECIFIED 로 복원됐고 배지가 함께 살아났다. pre-fill 이 addDiskGroupRow 를 경유하는 배선이 실제로 동작한다.

A4 — 카드 등록 폼의 칩 계열 select

조작: RAID 카드 신규 등록 폼을 열었다.
기대: chipFamily 를 고르는 “칩 계열” select 가 있고, 이 값이 무엇을 좌우하는지 안내된다.
실제: “칩 계열” select 에 MegaRAID (storcli 계열) 과 MPT IR (sas3ircu 계열) 두 항목이 있었고, 그 아래 안내 문구 “세팅 정의서의 VD 파라미터 지원 여부가 이 값에 걸립니다” 가 표시됐다.
판정: PASS — 등록 시점에 계열을 고르게 하고, 그 선택이 뒤의 어떤 동작을 결정하는지 그 자리에서 알려준다.

B1 — RAID 없음 행 잠금 (비정상 조작)

조작: 2 행의 RAID 레벨을 RAID 없음 으로 전환하고 ⚙ 상태를 js 로 실측했다. RAID 를 구성하지 않는 묶음에 볼륨 정책을 지정하려는 시도다.
기대: ⚙ 가 비활성이 되고 왜 막혔는지 tooltip 으로 안내된다.
실제: 아래가 실측 원문이다.

{"disabled":true,"title":"RAID 를 구성하지 않는 묶음에는 지정할 수 없습니다"}

판정: PASS — 거절이 아니라 애초에 누를 수 없게 막고, 사유를 tooltip 으로 붙였다. “UX 모순은 UI 1 차 차단” 원칙대로다.

B2 — IR 카드 잠금 · 값 보존 · 복귀 부활 (Q1 화면 실증)

조작: 4 축을 지정해 둔 상태에서 카드를 CRA3338(MPT IR) 로 전환했다가, 다시 MegaRAID 카드로 되돌렸다.
기대: IR 로 바꾸면 ⚙ 가 잠기고 서브 행이 숨는다. 그러나 입력한 값은 버리지 않고 보존하며(전송에서만 제외), MegaRAID 로 복귀하면 값과 배지가 되살아난다 — CP1 의 Q1 판정.
실제: IR 전환 직후 {"toggleDisabled":true,"title":"이 카드 계열은 VD 파라미터를 지원하지 않습니다","subRowHidden":true,"valueKept":"WRITE_BACK"} 이었고, MegaRAID 복귀 후 {"toggleEnabled":true,"valueRevived":"WRITE_BACK","badge":"4"} 였다.
판정: PASS — 잠긴 동안에도 WRITE_BACK 이 살아 있었고 복귀와 함께 배지 4 까지 부활했다. Q1(값 보존 · 전송 제외)이 화면에서 실증됐다. 카드를 잘못 골랐다가 되돌리는 사용자가 입력을 잃지 않는다.

C1 — direct POST 로 UI 를 우회한 지정 (서버 가드)

조작: 브라우저를 거치지 않고 curl 로 정의서를 제출했다. IR 카드를 지정한 묶음에 writePolicy 값을 실은 요청이다 — 화면에서는 만들 수 없는 조합이므로 UI 우회 경로다.
기대: 규칙 9(vdParametersNotSupported)가 400 으로 거절하고, 사유가 사용자 언어로 필드 오류에 담긴다.
실제: 아래가 응답 원문이다.

HTTP 400
fieldErrors[diskGroups] = "1번 묶음: MPT IR (sas3ircu 계열) 계열 카드는 VD 파라미터를 지원하지 않습니다 — 지정 값을 비우십시오."

판정: PASS — UI 잠금이 사라진 경로에서도 서버가 같은 판정으로 막았다. 메시지가 몇 번 묶음인지 · 어느 계열이라 안 되는지 · 무엇을 하면 되는지(“지정 값을 비우십시오”)까지 담아 다음 행동을 지시한다.

C3 — 드래그 후 서브 행 동반 (판정 방식 한계 명시)

조작: 모든 본 행의 다음 형제가 자기 서브 행인지를 js 로 실측했다.
기대: 행 순서를 바꿔도 서브 행이 자기 본 행을 따라다닌다(reattachVdRows).
실제: 부착 정합 실측은 아래와 같다.

{"attached":true}   // 모든 본 행의 nextSibling = 자기 서브 행

판정: PASS (한계 명시) — 부착 관계는 참이다. 다만 실제 드래그 발동은 자동화로 재현하지 못했다. RowDrag 가 HTML5 DnD(dragstart) 기반이라 computer 드래그와 이벤트 합성 모두 순서 변경을 일으키지 못한다(과거 실기에서도 같은 관찰이 있었다). 따라서 드래그 실조작 확인은 CP7 사용자 조작으로 이관하고, reattachVdRows 배선은 코드 경로(bindDiskGroupDrag 의 onDrop)와 위 부착 검증으로 갈음했다.

H1 — agent 파이프 분해 · 명령 조립 (하네스 재연)

조작: alpine 3.22 컨테이너에서 신형 payload 원문을 agent.sh 와 같은 sed · read 루프로 분해해, 어떤 storcli 명령 시퀀스가 만들어지는지 확인했다.
기대: VOL_LINES 가 볼륨 수만큼 정확히 분해되고, createOpts 는 add vd 인라인으로, setOps 는 per-VD set 으로, init 은 per-VD 초기화로 나뉜다. 전부 미지정인 볼륨은 옵션 없이 나간다.
실제: 아래가 재연 출력이다.

VOL_LINES → 2 행 정확 분해

[볼륨 1 — 4 축 지정]
add vd type=raid1 name=spvR1V1 drives=252:0,252:1 wb pdcache=off
/c0/v0 set bgi=off
/c0/v0 set accesspolicy=ro
/c0/v0 start init full force

[볼륨 2 — 전부 미지정]
옵션 없는 add vd
start init force        ← 기본(fast)

판정: PASS — VdParameters 의 조립 진리표와 실제 명령 시퀀스가 일치한다. 지정한 축만 명령에 나타나고, 미지정 축은 어떤 옵션도 남기지 않는다.

§6. CP5 가 잡은 결함
F-1 — agent.sh 의 for line in $VOL_LINES 워드 분리. createOpts 에 공백이 들어가는 순간("wb pdcache=off") 그 공백이 파이프 한 줄을 쪼개 파싱이 통째로 깨진다. 종전 파이프에는 공백을 담는 필드가 없었기 때문에 드러나지 않던 결함이며, 이 슬라이스가 공백 있는 필드를 처음 실어 표면화됐다.
항목내용
발견 경위H1 재연을 설계하던 중. 로컬 1 차 재연이 빈 결과를 냈고, BSD sed 방언 문제와 겹쳐 드러났다
정정heredoc while IFS= read -r 루프로 재작성. MEGARAID · IR 양쪽을 같은 방식으로 통일했고, 서브셸 변수 전파를 피하려 heredoc 을 택했다
재검증alpine 재연으로 정정 후 PASS (§5 H1 의 출력이 정정 후 결과다)
하네스가 실물 층의 결함을 CP5 에서 잡은 사례다. 이 결함은 단위 테스트가 볼 수 있는 자리에 있지 않다 — 셸 스크립트의 워드 분리는 Java 층에서 재현되지 않는다. CP7 실기까지 갔다면 게스트에서 볼륨 CREATE 오류로 나타났을 것이고, 원인이 셸 파싱이라는 것을 실기 현장에서 찾아야 했을 것이다.

관용 기록 — 앱 결함이 아닌 것

브라우저 computer 클릭이 카드 추가 버튼에 두 차례 미명중했다. js 진단으로 JS 무결(오류 0 · 핸들러 정상) 을 확인하고 진행했다. 자동화 조작의 좌표 문제이며 앱 결함이 아니다.

§7. 미수행 · 관찰

못 한 것과, 하다가 본 것을 사유와 함께 남긴다.

미수행 — 드래그 실조작 (C3 의 절반)

행 순서를 실제로 끌어 바꾸는 조작은 수행하지 못했다. RowDrag 가 HTML5 DnD 기반이라 자동화 수단(computer 드래그 · 이벤트 합성)이 모두 순서 변경을 일으키지 못한다. 부착 정합({"attached":true})과 onDrop 코드 경로로 갈음했고, 드래그 실조작은 CP7 사용자 조작으로 이관한다.

CP7 실기로 이관 — 실 카드에서만 확인되는 것

  • 실 카드 storcli 에서 createOpts 인라인 인자 순서(drives= 뒤에 정책 옵션이 오는 배치 — CP1 Q4 의 대소문자 문제 포함)
  • per-VD set 의 실동작
  • full init 의 실동작
  • 8축 상시 명시 전송(pdcache=default 인라인 · set bgi=on · set accesspolicy=rw)을 실카드가 그대로 받는지 (09-02 개정)

E 단계 관례에 따라 실기 검증은 일괄로 묶어 수행한다.

관찰 — 이 슬라이스와 무관한 스키마 불일치

validate 기동을 확인하던 중, 실 DB 의 drift 표에 구 컬럼 detected_at 이 잔존해 백그라운드 스캔의 INSERT 가 1 건 실패했다. 이 슬라이스와 무관한 기존 스키마 불일치이므로 여기서 고치지 않고 적립한다.

관찰 — Strip Size 의 카드별 지원 집합

plan 의 확장성 쟁점 ② 다. 카드마다 지원하는 Strip Size 집합이 다를 수 있는데, 미지원 값은 집행 단계의 storcli 오류 검사가 잡는 구조로 두었다. “지원 값 집합을 카드에 질의” 하는 확장은 갈라지는 시점에 한다 — 지금 만들면 쓰이지 않는 추상이 하나 더 생긴다.
