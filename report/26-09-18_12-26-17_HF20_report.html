§1. 무엇을 고쳤는가

Windows 설치를 마친 게스트와, 굽기 · 설정만 수행한 게스트가 다음 부팅에서 UEFI Shell 로 떨어지는 현상이 실기 3호(09-17)에서 드러났다. 앞선 HF19 는 "표준 Fixed Boot Order 를 매번 PATCH" 로 접근했으나 원인이 확인되지 않아 폐기했다.

HF20 은 AMI BIOS 의 거동을 계측으로 확정한 뒤 그 규칙 위에서 고쳤다. POST 때 BootOrder 첫 항목이 속한 그룹이 Fixed Boot Order 1순위와 맞바뀐다는 것이 그 규칙이며, 그러므로 BootOrder 의 첫 항목만 통제하면 Fixed Boot Order 를 직접 쓰지 않고도 다음 부팅의 행선지를 정할 수 있다. 조치는 둘이다 — ① Once 오버라이드를 무장하기 직전에 셸을 BootOrder 맨 뒤로 보내고(SHELL_LAST) ② 프로비저닝이 종단하는 자리에서 디스크를 맨 앞으로 보낸다(DISK_FIRST). 실기 도중 드러난 Windows Setup 자체 재부팅 결함(G-1)은 설치 착수 시 Once=Hdd 무장으로 보완했다.

HF19 — 폐기

매 시점에 Fixed Boot Order 를 표준값으로 PATCH

표류를 일으키는 원인이 확인되지 않은 채 결과만 되돌리려 했다. 2호기 계측에서 사이클 자체가 Fixed Boot Order 를 미는 것이 보여 판정이 서지 않았다.

HF20 — 채택

BootOrder 의 첫 항목을 정책(SHELL_LAST · DISK_FIRST)으로 통제

BIOS 가 맞바꿈 규칙대로 Fixed Boot Order 를 스스로 따라 세운다. PATCH 대상이 하나(Boot.BootOrder)로 줄고 POST 를 거쳐도 남는다.

검증은 실기 세 사이클(K-1 · K-2 · K-3)로 했고, 그 기록이 이 보고서의 본문(§5 · §6)이다.

§2. 진단 (실측 근거)

계측 방법. 2호기 BMC(10.1.1.9)에 30 초 폴러(/tmp/fbo-poll.sh)를 붙였다. 폴러는 Redfish 의 Systems/Self 에서 PowerState · BootSourceOverride · BootOrder 를, Systems/Self/Bios 에서 Fixed Boot Order 속성(FBO201~205)을 읽고 변화가 있을 때만 한 줄을 남긴다. 정의서 13 · 14 · 1 사이클(09-17)과 K-1 · K-2 · K-3(09-18)에서 관측했다.

그 결과 BIOS 거동 네 가지가 확정됐다. 넷 모두 추정이 아니라 폴러 로그로 관측한 것이다.

#거동내용
1맞바꿈 규칙POST 때 BootOrder 첫 항목이 속한 그룹(UEFI Hard Disk · Network · AP=내장 셸 · CD/DVD · USB)이 Fixed Boot Order 1순위 자리와 맞바뀌고, 되돌리지 않는다.
2목록 재구성항목 집합이 바뀌는 POST(BIOS 설정이 실제 적용되는 POST · 새 부팅 항목이 생기는 POST)에서 BIOS 가 BootOrder 를 셸(Boot0001) → 디스크 → NIC 순으로 다시 세운다. 셸이 첫 항목이 되므로 Fixed Boot Order 가 AP 1순위가 되고, 오버라이드 없는 다음 부팅은 셸로 간다. 이것이 원래 증상의 방아쇠다. 굽기 POST 는 번호만 옮기고 순서는 유지한다.
3Once 오버라이드정상 재부팅에서는 존중되어 그 부팅에 대상 그룹을 1순위로 올린다. 다만 굽기 POST 와 설정 적용 POST 는 Once 를 타지 않는다(4 분 미도착 → 재무장). 그리고 다음 POST 에서 오버라이드 직전의 그룹 순서가 복원된다(K-3 의 20:28 → 20:31 실측).
4BootOrder PATCH 는 유지Redfish Boot.BootOrder PATCH(If-Match ETag)는 POST 를 거쳐도 남는다(K-1 종단 뒤 재부팅 · K-2 수동 PATCH · K-3 종단 정착에서 각각 확인).
계측의 한계 — BMC 가 노출하는 Fixed Boot Order 속성(FBO201~205)은 매 POST 갱신이 아니라 BIOS 가 속성을 밀어 줄 때(setup 저장 · 설정 적용 · 굽기 · 일부 POST)만 갱신되는 지연 지표다. K-1 에서는 Windows 로 부팅한 뒤에도 AP 1순위로 남아 보였다. 그래서 판정은 Fixed Boot Order 표시가 아니라 BootOrder 값과 실제 부팅 결과로 한다.
§3. 구현

Redfish 층 — 부팅 항목 분류와 순서 정책

global/redfish/BootEntries 가 Systems/Self/BootOptions?$expand=. 를 읽어 SHELL · DISK · NETWORK · OTHER 로 분류한다. 분류 근거는 번호가 아니라 UEFI 장치 경로와 표시명이다 — 표시명 "EFI Shell" 또는 경로에 Fv( · FvFile( · VenMedia( · VenHw( 가 있으면 SHELL, MAC( 이나 "pxe" 가 있으면 NETWORK, HD( 가 위치 무관하게 있거나(Windows 는 짧은 경로, USB 는 PciRoot(…)/HD() 표시명이 "Windows Boot Manager" 이면 DISK 다. Id 가 없으면 @odata.id 꼬리를 쓰고, normalizeId("0005") 는 "Boot0005" 로 맞춘다.

BootOrderPolicy enum 은 두 상수를 갖는다. SHELL_LAST 는 셸만 맨 뒤로 보내고 나머지 상대 순서를 보존하며, DISK_FIRST 는 Windows Boot Manager → 다른 디스크 → 나머지 → 셸 순으로 세운다. 계산 결과가 현재 순서와 같으면 빈 값을 돌려 PATCH 자체를 생략한다(idempotent). 목록에 없는 id 는 OTHER 로 두고 자리를 지킨다.

RedfishPowerService.settleBootOrder(target, policy) 가 patchJsonRefreshingEtag(Systems/Self, {"Boot":{"BootOrder":[…]}}) 로 적용한다(If-Match * → 412 → fresh ETag 사다리). 결과 Settlement 는 적용(새 순서) · 무변경 · 실패(사유) 셋이다. 401 은 되던져 자격증명 폴백 사다리가 돌게 두고, 그 밖의 Redfish 실패는 FAILED 로 접어 로그만 남긴다(best effort).

무장 직전 훅 — 호출처를 건드리지 않는다

private arm() 한 곳에서, NextBoot.armsOverride() 가 참인 무장(AS_CONFIGURED 제외)은 오버라이드 PATCH 직전에 SHELL_LAST 를 먼저 지난다. 호출처 여섯 곳은 변경이 없다 — REBOOT 지시 직전의 RebootDirectiveArmer · BeginSettingStep · PowerOnStep · ReturnReadbackStep 재무장 · networkBoot · E2.5 화면 버튼.

종단 정착 — 이벤트로 끊는다

PhaseCursorAdvancer 가 종단을 확정하는 그 자리에서 ProvisioningCompletedEvent(guestServerId, completedAt) 를 발행하고, execution/engine/boot/BootOrderSettlement 이 @TransactionalEventListener(AFTER_COMMIT, fallbackExecution=true) 로 받아 상세의 BMC IP · 보드 시리얼로 DISK_FIRST 를 적용한다. BMC 가 검출되지 않은 서버는 건너뛰고, FAILED 와 예외는 삼킨다.

§4. 강제 장치
  • 정책은 enum 상수이고 소비처 분기는 0 이다. 무장 경로가 private arm() 하나뿐이라 새 호출처가 생겨도 SHELL_LAST 가 빠질 자리가 없다.
  • 종단과 BMC 부작용을 이벤트로 끊었다. 종단 규칙의 SSOT(Single Source of Truth, 단일 진실 출처)인 PhaseCursorAdvancer 에 Redfish 의존이 없고, AFTER_COMMIT 이라 롤백된 종단은 BMC 를 만지지 않는다.
  • 모든 정착 · 무장은 best effort 다. Redfish 실패가 프로비저닝 흐름(지시 · 스크립트 · 종단)을 깨뜨리지 않는다.
테스트 함정 기록 — 진단 실행기 테스트에서 발행기 mock 을 공유하면 종단 사건이 verify 횟수를 깨뜨린다. 커서에 no-op 발행기를 주는 것으로 해소했고, 같은 실수가 반복되지 않도록 여기 남긴다.

기준선 (09-18 18:08 · K-1 개시 전)

BootOrder 는 Boot0003 · Boot0004 · Boot0002 · Boot0001, Fixed Boot Order 는 HD · CD/DVD · USB · NET · AP 였다(사용자가 setup 에서 기본값으로 둔 상태). BootOptions 는 0001 = UEFI: Built-in EFI Shell(VenMedia), 0002 = Windows Boot Manager(HD 짧은 경로), 0003 · 0004 = UEFI: PXE IPv4 Intel I210 두 포트(MAC)다.

정의서 구성은 DB 실측으로 확인했다 — 1 번은 BASIC_UPDATE(BIOS · BMC LATEST) + BASIC_SETTING 템플릿 [1~5], 9 번은 BASIC_UPDATE + BASIC_SETTING [1~4] + RAID_CONFIGURATION + OS_INSTALLATION, 13 번은 RAID_CONFIGURATION + OS_INSTALLATION 이다. 2호기는 MS04-CE0 라 템플릿 4(BirchStream 5 속성)가 적용된다. 굽기는 버전이 같아도 굽는다(FirmwareAxisReason 의 SKIPPED 사유에 "같은 버전" 이 없고, sameVersion 은 반영 확인에만 쓰인다).

§7. 미수행 항목과 사유
  • K-2-2 실패 — HF20 의 두 훅은 "우리가 재부팅을 거는 순간" 만 덮었고, Windows Setup 이 스스로 거는 재부팅(BMC 를 거치지 않는다)에서 BIOS 의 목록 재구성이 셸을 첫 항목으로 올리는 지점(G-1)을 놓쳤다. 어제 분석이 설정 적용 POST 만 방아쇠로 본 것이 원인이다. 수동 개입(PATCH + exit)으로 완주시켰고, G-1 보완을 구현해 K-3 에서 검증했다. K-2 를 18차 jar 로 재실행하지는 않았다 — K-3 가 같은 Windows 경로를 덮고, 굽기 · 설정 경로는 K-1 · K-2 로 이미 검증됐기 때문이다.
  • K-1-3 · K-2-3 · K-3-1 의 "Fixed Boot Order 기본값" 문구는 BMC 표시로 확인하지 못했다 — 그 속성이 지연 지표이기 때문이다(§2). K-1 은 실제 Windows 부팅으로, K-3 은 20:28:25 의 Fixed Boot Order 갱신(HD 1순위)과 종단 정착 PATCH 로 판정했다. K-3 종단 뒤 재부팅(HF18 경로)에서 Windows 로 부팅됨은 사용자 화면 확인 대기다.
  • 모의 BMC 하네스(scripts/mock-guest/)로 종단 정착 · 무장 순서를 재연하지 않았다 — 단위 · 통합 테스트(모의 BMC 상태 포함)와 실기 3 사이클로 대체했다. 하네스 재연은 남은 일로 넘긴다.
  • 다이어그램 규약 미이행 — diagram/guest-provisioning-canvas.html 에 HF20 의 BMC 통로 상호작용(SHELL_LAST · DISK_FIRST PATCH · Once=Hdd)이 아직 반영되지 않았다. 남은 일이다.
  • plan html · 코드 미커밋 — 커밋 · PR · Notion plan/report 탭 임베드는 사용자 지시 대기 상태다.
