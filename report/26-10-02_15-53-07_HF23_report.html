§1. 요약
Windows Server 2025 무인 설치(보드 MS04-CE0)가 "게시자를 확인할 수 없습니다" 창에서 사람의 클릭을 기다리며 멈추던 문제를, 드라이버 변형의 진입점에 폴더를 지정해 설치 범위를 OS 폴더로 좁히는 방식(B)으로 해결했습니다. 실기에서 창 없이 설치가 끝났고 실패 INF 는 0 건입니다.
  • 함께 넣은 서명 정책 차단(A)은 Server 2025 에서 효과가 없어 제거했습니다.
  • 실패 INF 를 INF 단위 종료 코드로 모아 보고 · 화면에 보이게 했습니다.
  • 작업 중 운영 DB 의 MK4-1 잔재 컬럼 두 개(drift.detected_at · drift.drift_report_id)가 경로 점검 기록을 전부 막고 있던 것을 찾아 지웠습니다(§5).
  • 테스트 3,376 건 통과.

용어 — INF = 드라이버 설치 정보 파일 · CAT = 서명 카탈로그 · WHQL = Windows Hardware Quality Labs.

A — 서명 정책 차단 (제거)

설치 동안 서명 정책 BehaviorOnFailedVerify=2 로 확인 창을 막으려 했습니다.

3 차 실기에서 창이 그대로 떠 Server 2025 에서 무효로 판정했습니다.

B — 진입점에 폴더 (채택)

한 OS 버전에 여러 행을 두고 진입점에 대상 OS 폴더를 지정해, 그 폴더 안 INF 만 설치합니다.

4 차 실기에서 창 없이 완료 · 실패 INF 0 건이었습니다.

§2. 배경

드라이버는 어떻게 설치되는가

드라이버는 Windows 설치 직후 SetupComplete(SYSTEM 계정으로 한 번 도는 스크립트)가 pnputil /add-driver … /install 로 설치합니다. 드라이버 자원은 변형이 없으면 TREE(폴더 안 INF 전부)로, 변형이 있으면 진입점 확장자에 따라 INF · MSI · EXE 하나로 설치됩니다.

왜 확인 창이 실패보다 나쁜가

무인 설치에서 확인 창 대기는 실패보다 나쁩니다. 실패는 기록을 남기고 다음으로 넘어가지만, 창은 화면 앞에 사람이 없으면 SetupComplete 가 끝나지 않게 만들고, 그래서 첫 로그온 완료 보고까지 막힙니다.

예전 MS04 실기에서는 왜 없었는가

9 월 초의 MS04 실기에는 이 창이 없었습니다. 당시는 스테이징 VM 이었고, MS04-CE0 드라이버가 Chipset · QAT 둘뿐이었습니다(LAN 없음). spv-01 에는 09-23 에 Intel LAN 이 등록됐고, 10-02 가 spv-01 의 첫 Windows 설치였습니다. 즉 LAN 드라이버가 처음으로 설치 범위에 들어온 설치에서 창이 나타났습니다.

1 차 — 260915009 · QAT 예제 INF 를 의심

서버 보고의 로그 꼬리(60 줄)에서 두 가지를 확인했습니다. 하나는 QAT 예제 QAT2.0.W.2.2.0-0018/QuickAssist/Crypto/Sample/bin/x64/CpmBCryptSample.inf 가 "디지털 서명 정보가 없습니다" 로 실패한 것이고, 다른 하나는 QAT 단계에서 로그 시각이 약 13 분 멈춘 것입니다. 세 드라이버 폴더의 INF 263 개 중 서명 카탈로그(CAT)가 없는 것은 이 하나였습니다. 그래서 임시 대응으로 사용자가 QAT 를 INF 방식(진입점 icp_qat4.inf)으로 바꿨습니다.

2 차 — 260914017 · QAT 는 원인이 아니었음

QAT 는 exit 0 으로 해결됐지만 창이 3 회 그대로 떴으므로 QAT 는 원인이 아니었습니다. 카탈로그 서명자를 검사하니 LAN 77 · Chipset 92 · ASPEED · QAT 전부 WHQL 서명이었습니다. 서버 보고는 로그 꼬리만 담고 있어 원인 부분이 잘려 있었고, 그래서 사용자가 게스트의 C:\SPV\setupcomplete.log · C:\Windows\INF\setupapi.dev.log 를 공유 폴더(\\10.1.1.20\spvout)로 전달했습니다.

§5. 함께 처리한 운영 결함 — drift 잔재 컬럼

증상

배포 후 로그에서, 경로 점검(reconciliation) 스캔이 드리프트를 기록할 때마다 Field 'detected_at' doesn't have a default value 로 실패하는 것을 발견했습니다. 10-02 하루에 66 회였고 drift 테이블은 0 행이었습니다. 즉 경로 점검이 드리프트를 감지해도 아무것도 기록 · 표시되지 않던 상태였습니다.

원인

MK4-1 에서 엔티티가 detected_at 을 first_detected_at 으로 개명하고 회차 연결을 drift_observation 으로 옮겼습니다. 그런데 옛 컬럼 detected_at · drift_report_id(NOT NULL · 기본값 없음 · FK)가 ddl/schema.sql 에 남아 있어, 그 파일로 만든 DB(spv-01 · 스테이징)에서 INSERT 가 막혔습니다. 로컬 개발 DB 에는 이 컬럼들이 없었습니다.

처리 (사용자 승인 두 번)

  1. detected_at 을 삭제했습니다.
  2. 다음 스캔이 drift_report_id 로 실패했습니다.
  3. 로컬 ↔ 운영 전 테이블의 컬럼을 대조해, INSERT 를 막는 운영 전용 컬럼이 그 하나뿐임을 확인했습니다.
  4. FK · 인덱스 · 컬럼을 삭제했습니다. ddl/drift_drop_detected_at.sql · ddl/schema.sql 에 반영했습니다.

결과

이후 "스캔 실패" 는 0 입니다. 사용자가 QAT 어긋남 1 건을 해결 · 닫았고(drift RESOLVED 1), drift_report 에 회차가 누적되고 있습니다.
