§1. 실기 개요

E3.5-1(RAID 인벤토리) · E3.5-2(구성 계획) · E3.5-3(집행) · E3.5-4(인계) 네 슬라이스의 CP7 을 2026-09-01 하루에 묶어 실기했다. E 단계는 관례상 CP7 을 실기 일괄로 처리한다.

실기의 목적은 하네스와 픽스처가 통과할 수 없는 실물 층이다. 서버 코드의 판정은 픽스처로 재현되지만, RAID 컨트롤러의 CLI 문법 · 커널 드라이버 적재 · 펌웨어의 실제 동작은 실물에서만 드러난다.

§4. 실기가 잡은 결함 6 건
전부 당일 정정 · 재실증했다. 정정은 커밋 22b9045 에 담겼다. 아래 4-0 은 실기 전 사전 정비에서 드러난 것이라 결함 6 건에는 포함하지 않되, 같은 부류의 교훈을 남겼으므로 함께 적는다.

4-0 스테이징 DB 의 enum 사각 사전 정비

증상 : 개시가 Data truncated for column 'current_step' 로 500.
근인 : provisioning_progress.current_step 과 provisioning_history.step_code 가 구값(RAID_CONFIGURATION)을 담은 enum 정의를 그대로 갖고 있었다.
해소 : 정본 MODIFY 2 문.
교훈 : 배포 대조를 테이블 · 컬럼 단위로 하면 enum 값 집합의 차이는 보이지 않는다. 대조 절차에 enum 대조를 추가해야 한다.

4-1 도구 미동봉 결함

증상 : 채집이 TOOL_MISSING 으로 실패.

{"reason":"TOOL_MISSING","detail":"storcli64/storcli not found", "lspci_b64":…}

근인 : apkovl 이 RAID_TOOLS_DIR 없이 조립된 판이었다. build-assets.sh 는 이미 훅을 갖고 있었고, "미지정이면 TOOL_MISSING 으로 정직하게 실패한다" 는 계약이 설계대로 발동했다.
해소 : storcli64 와 sas3ircu 를 동봉해 재포장했다. 둘 다 정적 링크임을 실측했다.

4-2 커널 드라이버 미로드 결함

증상 : storcli 가 Controller 0 not found 를 반환. JSON 자체는 정상이고 Status 만 Failure 였다.
근인 : hwdrivers(sysinit)가 modloop(boot) 마운트보다 먼저 돌아 megaraid_sas 가 적재되지 않았다.
해소 : agent.sh 의 ensure_raid_driver — detect_raid_family 가 성공하면 modprobe 후 mdev -s 를 돌린다.

4-3 storcli 인자 순서 결함

증상 : add vd type=… drives=… name=… 이 unexpected TOKEN_NAME, expecting $end 로 거절.
근인 : storcli 에서 drives= 는 사실상 마지막 인자다.
해소 : name= 을 drives= 앞으로 옮겼다. pdperarray 류만 뒤에 오는 것이 허용된다.

4-4 sas3ircu 이중 확인 결함

증상 : you must answer "NO" or "no" to proceed; operation aborted!
근인 : 첫 질문은 "진행할까?" 라 YES 가 맞지만, 둘째 질문이 "중단할까?" 라서 같은 YES 가 중단을 뜻했다.
해소 : printf 'YES\nNO\n' 로 정정.

4-5 IR Volume Name 미파싱 결함

증상 : IR 계열 기록의 state · wwn 이 NULL.
근인 : 파서가 IR 의 Volume Name 을 읽지 않아 이름 매칭이 실패했다. 이는 기록 결손에 그치지 않고 보존 정책에서 자기 볼륨을 외부 볼륨으로 오판할 위험이었다.
실측 : 구 경로로 만든 볼륨은 이름 행을 내보내지 않았고(08-31), sas3ircu create 로 만든 볼륨은 내보냈다(09-01).
해소 : 파서가 두 형태를 모두 관용하도록 고치고 테스트를 두 벌로 고정했다.

4-6 E2-4 병합 잔재 결함

증상 : 신규 테스트 파일 GuestServerQueryServiceExecutionViewTest 가 구 생성자(12 인자)를 호출했다.
근인 : 병합 충돌 없이 유입됐다.
해소 : 14 인자로 정정.

§5. EXACT 의미론 개정 — 배수 분할

사용자 문제 제기에서 시작해 당일 개정하고 실기로 재실증한 항목이다.

제기

HDD SAS 4TB 6 대를 RAID5 두 볼륨으로 만들려면 EXACT 3 규칙이 두 개 필요하다. 그런데 포섭(규칙 8)이 후행 규칙을 차단하므로, 엄격 일치 해석으로는 만들 수 없는 구성이었다.

이전 — 엄격 일치

EXACT n 은 그룹 크기가 정확히 n 일 때만 소비한다.

HDD 6 대 + EXACT 3 → 매칭 없음. 규칙을 두 개 두어도 포섭이 후행을 차단한다.

이후 — 배수 분할

EXACT n 은 그룹 크기가 n 의 배수일 때 n 개씩 k 개 볼륨을 만든다. 배수가 아니면 미소비하고 후행으로 흘린다.

HDD 6 대 + EXACT 3 → 볼륨 2 개.

개정이 무엇을 건드리지 않았나

  • E3.5-2 가 근거로 삼았던 부분 소비 · 고립 결함 사례(960GB ×3 + EXACT 2)는 여전히 안전하다 — 3 은 2 의 배수가 아니므로 미소비 후 후행으로 흐른다.
  • 포섭 규칙 8 · JS 미러 · 서버 400 은 무변경이다. 동일 규칙 2 개는 여전히 무의미하다 — 첫 규칙이 배수를 전부 소비하기 때문이다.
원래 의도의 복원 : 폼 도움말은 이미 "같은 스펙 4 장 + RAID1 2 개 → 볼륨 2 개" 라고 안내하고 있었다. 배수 분할로 개정하고 나서야 도움말과 실제 동작이 정합해졌다.

재실증

규칙 하나로 HDD 6 대가 spvR2V1 · spvR2V2 두 볼륨이 됐다(연대기 12:52). 미소비 사유 문구에는 "(배수 아님)" 을 명시했다. 단위 테스트 쪽은 RaidPlannerTest 의 전수 표를 개정하고(4 대 → 2 볼륨 · 6 대 → 3 볼륨) T2 를 반전, T2b 를 신설했다.

§6. 표시 · 사용성 개정

실기 검수에서 파생한 지적을 당일 반영하고 화면으로 실증했다.

IR 용량의 사람 단위 표기

파서에 humanFromMb 를 두어 2 진 환산으로 MegaRAID 표기와 통일했다 — "3815447 MB" 가 "3.639 TB" 로 보인다. 여기에 더해 저장본 소급은 표시 직전 정규화(displayNormalized)로 처리했다. 채집 시점 정규화만으로는 이미 저장된 인벤토리에 소급되지 않는다는 검수 지적이 계기였다.

용량 정밀도

formatDecimalBytes 를 최대 소수 둘째 자리까지로 넓혔다. 종전에는 1.92TB 가 1.9TB 로 뭉개졌다. 뒤따르는 0 은 다듬어 4.00 이 4 로 보이게 했다.

SMBIOS UUID 강조 칩

id 를 노출하지 않는 체제에서 실질 식별자는 SMBIOS UUID 다. 헤더에서 바로 집을 수 있도록 라벨 + 굵은 모노 형태의 칩(n-uuid-chip)을 두었다.

선행 삭제 문구 중립화

"(파괴 정책)" 꼬리를 떼고 "카드의 기존 볼륨 전부 삭제 후 재구성" 이라는 사실 서술만 남겼다. 보존 정책이면서 spvR 잔여를 재구성하는 경우에도 참이 되어야 하기 때문이다.

§7. 관찰 · 미수행 (사유 포함)
실기가 통과했다는 사실보다 통과하면서 무엇을 보았고 무엇을 못 했는지가 다음 판단의 재료다. 감추지 않고 그대로 적는다.

MegaRAID 파괴 재구성 후에도 구 OS 데이터가 남는다

파괴 정책으로 삭제하고 같은 구성으로 다시 만들었는데, 구 OS(Rocky 10.2)의 데이터가 그대로 남아 있었다. del 후 동일 구성 재생성은 RAID 메타데이터만 재작성한다 — storcli add vd 는 기본적으로 초기화를 하지 않으므로 데이터 소거가 아니다.

두 가지가 따라온다. 하나는 경고 문구가 실물보다 강하다는 것이다("복구할 수 없습니다"). 다른 하나는 부팅 순서에 따라 구 OS 로 부팅될 위험이다.

이번에 고치지 않았다. 대응 후보는 생성 직후 fast init 이지만, OS 설치가 파티셔닝을 수행하는 E4 문맥과 얽힌 설계 결정이다. 실기 중 즉흥으로 정할 사안이 아니라고 판단해 설계 결정으로 적립했다(§8).

재시도는 재부팅이 아니다

실패한 단계의 재시도는 같은 부팅 세션의 재수행이다(11:31 에 DIAGNOSTIC_BOOTING 마일스톤이 새로 찍히지 않은 것이 근거다). 따라서 agent.sh 나 apkovl 같은 부팅 자산을 갈아 끼운 뒤에는 재부팅해야 반영된다. 자산 교체 화면의 안내 문구 후보로 남긴다.

자산 교체 폼의 첫 클릭이 간헐적으로 먹지 않았다

세 번의 자산 교체 중 두 번에서 첫 제출 클릭이 무시됐다. 파일 선택 상태는 유지됐고 좌표를 다시 클릭하니 회복됐다. 브라우저 자동화 절차 쪽 요인일 수 있어 결함으로 단정하지 않고 관찰로만 기록한다.

카드 대조가 전 사이클에서 생략됐다

raid_card 자원에 Subsystem 이 등록돼 있지 않아 CARD_MISMATCH 대조가 이번 실기의 모든 사이클에서 생략됐다. E3.5-5 의 관측 채움으로 해소할 예정이다.
