§1. 무엇을 만들었나

점검의 동작을 좌우하는 값 일곱이 설정 파일에 있어 운영자가 바꿀 수 없었다. 그중 실행 시점에 읽혀 즉시 효과가 나는 다섯을 데이터베이스로 옮기고 화면에서 조작하게 했다. 나머지 둘(점검 주기)은 스케줄이 시작 시점에 고정되어 저장해도 반영되지 않으므로 옮기지 않고 읽기 전용으로만 보여 준다 — MK4-3-2 가 실행 구조를 바꾸며 가져간다.

자동 처리 기본값을 켰다

무인 처리 대상으로 설계된 다섯 종류 중 되돌릴 수 있는 넷을 기본으로 켜고, 되돌릴 수 없는 유령 DB 기록만 껐다. 무인에 맡길지의 기준을 "잘못돼도 되돌릴 수 있는가" 한 문장으로 두었고, 새 축을 만들지 않고 종류가 이미 들고 있는 성질을 썼다.

시스템 해결이 꺼져 있으면 목록 화면이 계속 알린다

이 스위치는 탐지는 계속하되 고치는 행위만 전부 멈추는 비상 차단기라, 끈 사실을 잊으면 시스템이 조용히 아무것도 고치지 않는 상태로 남는다.

사용자 문구에서 설정 키 이름을 걷어냈다

설정 키 이름이 사용자 문구에 드러나던 자리도 정비했다 — 점검 범위 안내, 자원 소실의 "직접 해야 할 일", 그리고 검증 중 추가로 발견한 두 곳(비활성 버튼 안내 · 거절 메시지)이다.

§2. 설계 결정 — 저장 형태를 CP1 도중 뒤집었다

D1 — 화면에 올릴 자격은 "그 값이 실행 시점에 읽혀 즉시 효과가 나는가"

근거는 휴지통 선례의 실측이다. 그쪽은 영구삭제 주기를 데이터베이스에 저장하고 화면에서 바꾸게 해 두었으나 실행부가 시작 시점에 문자열을 고정해 저장된 값이 적용되지 않고, 그 한계가 코드 주석에만 남아 있다. 화면이 거짓말하는 상태를 하나 더 만들지 않는다.

D2 — 자동 처리 기본값은 "되돌릴 수 있는가" 로 정한다

비채택 — 다섯을 모두 켜기(되돌릴 수 없는 영구 삭제를 무인에 맡기게 된다) · 다섯을 모두 끄기(지금과 같아 이 단계의 목적이 사라진다).

D3 — 자동 처리 후보 목록은 종류의 해결 등급에서 파생한다

화면에도 설정에도 종류 이름을 하드코딩하지 않는다. 과거 네 종류를 화면 세 곳에 하드코딩했다가 서버 다섯 종류와 갈라져 버튼이 누락된 사고가 있었다.

D4 — 추가 점검 경로는 줄바꿈 구분, 자동 처리 대상은 콤마 구분

두 구분자가 다른 것은 값의 성질이 다르기 때문이다. 종류 이름은 콤마를 품을 수 없고, 파일 경로는 품을 수 있다. 실측으로 확인한 것은 어떤 인쇄 가능한 문자도 경로에 대해 안전하지 않다는 사실이다 — 세미콜론 · 콤마 · 줄바꿈이 전부 파일명에 들어갈 수 있다. 그래서 선택 기준을 안전성이 아니라 입력 방식으로 잡았다. 경로는 여러 줄 입력칸으로 받으므로 줄바꿈이 사용자가 실제로 만드는 구분자다. 세미콜론 통일안은 이 이유로 채택하지 않았다.

D5 — 저장 형태를 CP1 도중 뒤집었다 (단일행 → 항목별 행)

계획서는 휴지통 선례를 따라 고정 컬럼 단일행으로 잡았다. 구현 중 사용자가 확장성을 문제 삼았고, 따져 본 결과 뒤집는 것이 맞다고 판단해 항목별 행으로 결정을 개정했다.

계획 — 고정 컬럼 단일행

  • 휴지통 선례를 그대로 답습
  • 설정 하나 늘릴 때마다 DDL 스크립트 + 엔티티 필드 + 테스트
  • 컬럼 단위 데이터베이스 제약을 쓸 수 있음

개정 — 항목별 행 (채택)

  • 항목이 기본키, 값은 문자열 한 컬럼
  • 설정 하나 늘리는 비용이 열거형 상수 한 줄
  • 범위 · 형식 검증은 이미 요청 쪽이 담당

항목별 행을 택한 근거 셋.

  1. 키-값 저장이 흔히 욕먹는 이유는 "키가 무엇인지 아무도 모른다" 는 것인데, 여기서는 항목 카탈로그가 코드에 있어 그 약점이 성립하지 않는다. 그 열거형을 그대로 기본키로 쓰므로 오타가 들어갈 수 없고, 한 항목이 두 행을 가질 수 없다는 것도 데이터베이스가 지킨다.
  2. 잃는 데이터베이스 제약이 실질적으로 크지 않다. 범위 · 형식 검증은 이미 요청 쪽이 하고 있었다.
  3. 설정 하나 늘리는 비용이 "DDL 스크립트 + 엔티티 필드 + 테스트" 대 "열거형 상수 한 줄" 로 크게 다르다.
근거 하나는 도중에 철회했다 — 처음에는 "애플리케이션 계정에 변경 권한이 없어 스키마 변경마다 사람이 개입해야 한다" 를 근거로 들었는데, 사용자 지적으로 확인해 보니 claude_code 에게 ALTER 권한이 있었다(GRANT SELECT, INSERT, UPDATE, CREATE, REFERENCES, ALTER ON server_provision.*). 그 근거는 성립하지 않으므로 철회하고 나머지 셋으로 결정을 유지했다. 프로젝트 CLAUDE.md 의 "claude_code 는 ALTER 불가" 서술이 사실과 다르다 — 앵커에서 정정할 사안이다.
이 개정이 싸게 끝난 이유가 설계에 있다 — "노출 타입이 계약" 이라는 결정 덕분에 서비스가 돌려주는 타입(Set<DriftKind> · List<Path> · boolean · int)이 그대로였고, 저장 형태를 통째로 갈아엎었는데도 PathReconciliationService 는 한 줄도 바뀌지 않았다.

D6 — 행이 없는 항목은 오류가 아니라 손대지 않은 상태다

카탈로그 기본값으로 읽고 저장할 때 비로소 행이 생긴다. 그래서 설정을 늘려도 기존 환경에 이관 작업이 필요 없다. 다만 처음 한 번은 설정 파일 값을 옮겨 온다 — 이미 그 값으로 돌던 환경에서 갑자기 동작이 달라지지 않게 하려는 것이다.

§5. 정상 흐름 검증 (A1~A12)

A1 통과 — 항목별 뜻과 효과 시점

다섯 항목 모두 뜻 설명과 효과 시점이 붙는다(자동 처리 대상 = 다음 점검부터 / 시스템 해결 = 저장 즉시 / 보관 개수 = 다음 점검부터 / 추가 경로 = 다음 점검부터 / 기동 직후 점검 = 다음 기동부터).

A2 통과 — 후보 다섯과 되돌림 표시

후보 다섯이 전부 렌더되고 각각 "시스템이 무엇을 하는지" 와 되돌림 배지가 함께 붙는다. 채증은 A1 과 같은 화면이다(별도 스크린샷 없음).

A3 통과 — 기본값이 되돌릴 수 있는 넷

행이 0 개인 상태에서 되돌릴 수 있는 넷만 켜져 있고 유령 DB 기록은 꺼진 채 경고가 붙는다. 채증은 A1 과 같은 화면이다(별도 스크린샷 없음).

A4 통과 — 저장 유지와 항목별 행 생성

저장 후 ?saved 로 되돌아오며 값이 유지되고, 데이터베이스에 항목별 다섯 행이 생겼다.

A5 통과 — 저장한 대상이 다음 점검에 실제 적용 (핵심)

경로 이동됨을 켜고 점검하니 사람이 누르지 않았는데 자원의 등록 경로가 실제 위치로 갱신됐다. 저장한 값이 다음 점검에 실제로 반영된다 — 휴지통 설정이 어긋났던 지점이 반복되지 않았다. 다만 이 확인 과정에서 결함 1 이 드러났다(§8).

A6 통과 — 끄면 미적용

끄고 같은 드리프트를 새로 만들어 점검하니 자원 경로가 그대로였다.

첫 시도는 오염됐다. 설정을 저장하기 전 점검에서 이미 코드 기본값으로 자동 처리가 일어나 있었다. 드리프트를 새로 만들어 재실시한 결과가 위 판정이다.

A7 통과 — 해결 차단 배너와 버튼 비활성

해결을 끄니 상시 배너가 뜨고 [해결] 이 비활성이 됐다. 다시 켜니 배너가 사라졌다.

A8 통과 — 차단 시 자동 처리도 건너뜀

해결을 끈 상태로 점검하니 드리프트는 탐지됐으나 자원은 갱신되지 않았다. 차단기가 자동 처리까지 함께 멈춘다.

A9 통과 — 보관 개수 적용

보관 개수를 2 로 저장하고 점검을 두 번 돌리니 보고서가 20 건에서 2 건으로 정리됐다.

A10 통과 — 추가 경로가 범위에 편입

추가 점검 경로에 범위 밖 폴더를 넣으니 기존 자원 소실이 닫히고 경로 이동됨으로 다시 잡혔다. 화면 안내가 설명한 대로 동작한다.

A11 통과 — 안내에서 설정 키 제거

범위 안내에 설정 키 이름이 없고 설정 화면 링크만 있다.

A12 통과 — 주기 읽기 전용

주기 두 항목은 입력 요소가 아니라 텍스트이며 "설정 파일에서만 변경 가능" 이 붙는다.

§6. 비정상 조작 검증 (B1~B7)

B1 통과 — 보관 개수 0

보관 개수 0 은 브라우저가 먼저 막고(min=1), 클라이언트 검증을 우회해도 서버가 필드 메시지로 거절한다.

B2 통과 — 상대 경로

상대 경로는 "절대 경로로 입력해주세요" 로 거절되고 입력값이 보존된다.

B3 통과 — 직접 POST 로 알 수 없는 종류

직접 폼 POST 로 알 수 없는 종류를 보내도 타입 변환 500 이 아니라 안내 문구로 거절되고 데이터베이스가 변하지 않는다.

B4 통과 — 차단 상태에서 직접 해결

해결이 꺼진 상태에서 직접 해결 요청을 보내면 409 로 거절되고, 원문 JSON 이 아니라 오류 화면으로 보인다.

B5 통과 — 중복 제출

저장을 연달아 두 번 눌러도 항목별 upsert 라 중복 행도 오류도 없고 최종 값이 정확했다. 버튼이 제출 중 비활성화되지는 않는다.

B6 통과 — 저장된 알 수 없는 종류 표출

코드에 없는 이름을 데이터베이스에 직접 넣고 화면을 여니 이름까지 드러내며 알린다. 저장하니 정리됐다.

B7 통과 — 전부 해제

자동 처리 대상을 전부 해제해도 거절하지 않고 저장된다. 아무것도 자동으로 처리하지 않겠다는 것도 정당한 선택이다.

§7. 막는 방식 (C1~C3)

C1 부분 통과 — 거절 사유 전달 → 결함 3 으로 처리

어느 항목이 왜 틀렸는지 한국어로 알려 주고 입력값이 보존된다. 다만 보관 개수는 상단 요약과 필드 옆 둘 다인데 추가 점검 경로는 상단 요약만 있었다. 이 차이를 §8 결함 3 으로 처리했다. 채증은 B1 의 서버 거절 화면이 겸한다(별도 스크린샷 없음).

C2 통과 — 다음 행동 안내

해결 차단 배너가 "점검 운영 설정에서 다시 켤 수 있습니다" 로 다음 행동과 경로를 함께 안내한다.

C3 통과 — 되돌릴 수 없음 경고

되돌릴 수 없는 종류에 빨간 배지와 경고 문구가 체크 여부와 무관하게 항상 보인다.

§8. 검증 중 발견한 결함과 그 처리 — 4 건

네 건을 발견했고 넷 다 이 단계에서 고쳤다. 수행(에이전트)과 판정 · 수정(세션)이 분리된 규약대로 진행했다.

결함 1 — 자동 처리한 드리프트가 그 점검에서 닫히지 않았다 (주요)

재현 : 자동 처리 대상을 켜고 점검한다. 자원의 등록 경로는 갱신되는데 드리프트는 조치 필요 로 남고, 상세의 DB 기록 이 갱신 전 경로를 보여 준다 — 실제 데이터와 어긋난 값이다.

원인 : 자동 적용 루프가 해결 전략을 부르기만 하고 드리프트를 닫지 않았다. 코드 주석은 "해결돼도 보고서에 남긴다" 였는데, 드리프트가 회차마다 새로 생기던 시절에는 그것이 곧 기록 보존이었다. MK4-1 이 드리프트를 지속되는 문제로 바꾼 뒤로는 같은 코드가 "이미 고친 문제를 계속 열어 둔다" 가 됐다.

왜 이 단계에서 고쳤는가 — 이 코드는 이 슬라이스가 쓴 것이 아니다. 그런데 이 슬라이스가 자동 처리를 기본으로 켜면서 모든 설치에서 드러나게 만들었다. 기본값을 켜 놓고 화면은 "아직 조치가 필요하다" 고 말하면 이 단계의 목적 자체가 무너진다. 다음 점검에서 미관측으로 닫히기는 하지만, 그러면 원장에 "시스템이 처리했다" 가 아니라 "그냥 사라졌다" 로 적혀 감사 기록이 사실과 달라진다.

수정 : 수동 해결과 같은 방식으로 그 자리에서 닫고 처리 이력을 남긴다. 원장에는 새 항목 AUTO_APPLY("점검 중 자동 처리") 로 적는다 — 운영자가 눌러서 처리한 것과 시스템이 스스로 한 것은 나중에 "왜 이렇게 됐는가" 를 되짚을 때 전혀 다른 정보라 APPLY 와 가른다.

재검증 : 새 드리프트를 만들어 점검하니 같은 점검에서 해결됨 / AUTO_APPLY 로 닫히고 처리 이력에도 남았다. 목록 요약의 미해결 수도 3 건이 아니라 2 건으로 맞았다. 회귀 테스트를 함께 넣었다.

결함 2 — 차단 안내가 설정 키 이름을 노출하고 설정 화면을 가리키지 않았다

비활성 [해결] 버튼의 안내와 거절 메시지가 reconciliation.resolution-enabled 를 그대로 쓰고 있었다. 이 슬라이스가 그 값을 설정 파일에서 화면으로 옮겼으므로 지금은 틀린 안내다. 목록 화면에서 없앤 것과 같은 문제가 두 곳에 남아 있었다. 네 자리(버튼 안내 3 · 거절 메시지 1)를 "점검 운영 설정에서 켠 뒤 다시 시도하세요" 로 고쳤고, 옛 문구를 박제하던 테스트 3 건도 새 계약으로 갱신했다. 개발자용 주석의 키 언급은 그대로 두었다.

결함 3 — 추가 점검 경로 오류에 필드 옆 메시지가 없었다

형식 검증은 여러 줄을 한꺼번에 보는 것이라 클래스 수준 규칙으로 두었는데, 그 오류는 필드가 아니라 파생 이름에 붙어 상단 요약에만 나왔다. 폼이 길어 문제의 칸이 화면 밖일 수 있다. 필드 옆에도 함께 그리도록 고쳤고 자동 처리 대상도 같은 이유로 함께 처리했다.

결함 4 — 보관 정리로 기록이 사라진 것을 "한 번도 하지 않았다" 로 말했다

보관 개수를 줄이면 오래된 보고서가 정리되면서 정밀 점검 기록도 함께 사라진다. 그때 화면이 "아직 정밀 점검을 한 번도 하지 않았습니다" 로 바뀌는데 사실이 아니다 — 없는 것은 기록이지 점검이 아니다. "남아 있는 정밀 점검 기록이 없습니다" 로 고쳤다.

범위 밖 부수 관찰

  • 해결이 꺼진 상태에서도 중복 자원 해결 모달의 확인 버튼만 비활성이 아니다. 다만 여는 트리거가 비활성이고 서버가 거절하므로 실제 우회는 되지 않는다.
  • 오류 화면의 상단 메뉴 활성 표시가 원래 화면 맥락을 유지하지 않는다.
  • BIOS 트리 자원을 등록 폴더 밖으로 옮기면 경로 이동됨이 아니라 자원 소실로 잡힌다. 점검 루트가 등록 경로의 상위 폴더에서만 파생되기 때문으로 보이며, 추가 점검 경로로 풀리지만 그 안내가 BIOS 쪽에는 닿지 않는다.
