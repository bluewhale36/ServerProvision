§1. 슬라이스 개요

ES 계열(엔진 phase 전진 배선)의 첫 슬라이스다. ES-1 = 실행 엔진이 활성 할당의 소유 phase 집합(ownedPhases)을 실제로 소비해, 진단 리눅스를 완주한 게스트의 커서를 그 소유 phase 로 전진시키는 배선이다.

어떤 결손을 메우는가

U3-1(할당 core)은 엔진이 커서를 전진시키는 데 필요한 훅 3 개를 미리 정의만 해두고 아무도 부르지 않는 상태로 남겼다. 그 결과 진단을 완주한 게스트는 할당이 있든 없든 무조건 종단(markCompleted)해 버렸다 — 현행 코드가 소유 phase 집합을 Set.of() 로 하드코딩했기 때문이다. ES-1 은 이 세 훅을 엔진 판정 호출부에 연결해, 할당된 게스트는 소유 phase 로 전진하고 무할당 게스트만 종단하도록 바꾼다.

seam (U3-1 이 정의)역할ES-1 이 부르는 자리
OwnedPhasesProvider.ownedPhasesOf(guestId)게스트의 활성 할당이 소유한 phase 집합 조회커서 전진 협력자
PhaseSequence.nextAfter(current, owned)현재 phase 이후 소유 phase 중 첫 것을 반환 (없으면 empty)커서 전진 협력자
ProvisioningProgress.advanceTo(phase)진행 상태의 커서를 다음 phase 로 이동커서 전진 협력자
단일 슬라이스 · 교차 의존 0 — 새 알고리즘 · 새 도메인 타입 · 새 예외를 도입하지 않는다. 후속 phase 를 실제로 집행하는 executor (FirmwareUpdatingExecutor 등)는 이 슬라이스 밖이며 ES-n · E2 소관이다. ES-1 이후 할당 게스트는 소유 첫 phase 에서 명시 HOLD 로 대기한다.
§2. 구현 결과

§3. 결정 반영 (DES-1~DES-4)

plan §8 에서 확정한 설계 결정 DES-1~DES-4 를 구현이 그대로 반영했다.

#결정근거 · 반영
DES-1 전진 · 종단 판정을 PhaseCursorAdvancer 협력자로 추출 (inline 아님) 모든 후속 executor 가 공유할 커서 전진 SSOT(Single Source of Truth — 단일 진실 출처). 인라인하면 종단 규칙(DEC-25)이 executor 마다 복붙되어 drift 가 생긴다.
DES-2 directiveFor 에 "진단 이후 전진 → REBOOT" 추가 기존 결함(전진한 게스트가 WAIT 로 빠져 진단 리눅스에 갇힘)을 REBOOT 조건 확장으로 해소. 새 분기가 아니라 ordinal() 비교 하나를 조건에 더한 것.
DES-3 BootScriptDispatcher 의 무해한 Set.of() 주석만 명확화, provider 미주입 여기서까지 OwnedPhasesProvider 를 주입하면 over-wiring(과잉 배선). 실제 소비처는 PhaseCursorAdvancer 하나면 충분.
DES-4 소유 첫 phase 에서 멈추고 뒤 소유 phase 로 건너뛰지 않음 executor 가 아직 없는 phase 는 /boot 재폴링 시 명시 HOLD 로 응답. 한 번에 여러 phase 를 소비하지 않아 각 phase 집행이 후속 슬라이스에서 순서대로 붙는다.
신규 예외 0 · 409 없음 — ES-1 은 사용자 대면 충돌 경로가 없다. advanceTo 의 안전망 (역행 · 종단 위반 → IllegalStateException → 500)은 정상 흐름에서 발동하지 않으며, PhaseCursorAdvancer 단위 테스트의 가드 케이스로 커버했다.

§5. CP5 샌드박스 검증 (핵심)

ES 계열 슬라이스는 게스트가 화면 없이 HTTP 로만 상호작용하므로, CP5 검증은 모의 게스트 하네스(scripts/mock-guest 방식 curl 재연) + 브라우저 계획 rail 확인으로 수행한다. 아래가 이 슬라이스의 본문 중심이다.

1. 검증 항목 계획

즉흥 클릭이 아니라 아래 3 항목을 먼저 세우고 착수했다.

  1. 무할당 게스트 (회귀) — 진단 완주 → 종단(markCompleted) → close 응답 REBOOT → /boot = awaitingIntake. 커서 DIAGNOSE_LINUX · completed. U3 이전 동작이 그대로 보존되는지.
  2. 할당 게스트 (ownedPhases = {FIRMWARE_UPDATING}) — 진단 완주 → 소유 phase 로 전진(advanceTo) → close 응답 REBOOT (DES-2) → /boot = HOLD (FIRMWARE_UPDATING). 커서 FIRMWARE_UPDATING · not completed.
  3. 계획 rail 반영 — server-detail 의 계획 phase rail 이 전진(펌웨어 업데이트 = 현재(실제))을 반영하는지.

2. 샌드박스 구성 + 실측 정정 3 건

Docker MariaDB(3307) + bootJar(7788, ddl-auto=update, PXE_ASSETS_ROOT=/tmp/spv-assets) + mock-guest 하네스(curl 재연) + Chrome. board_model(GIGABYTE / MS03-CE0) 시드. U3-2-a DDL(generated column)이 이미 적용된 DB 를 재사용했다.

정상 흐름을 못 얻다가 코드 · 로그를 읽어 해결한 실측 정정 3 건 — 모두 ES-1 코드 결함이 아니라 검증 환경 · 하네스 규약 문제였다. 정직하게 남긴다.
#증상원인처리
① 진단이 전진하지 않고 HOLD 로 귀결 DiagnoseLinuxExecutor 는 @ConditionalOnProperty("pxe.assets.root") 라 PXE_ASSETS_ROOT 없이 부팅하면 미로드 → 진단 phase executor 부재 → onStepClosed(전진 판정) 자체가 안 붙음 PXE_ASSETS_ROOT=/tmp/spv-assets 설정. onStepClosed 는 자산 파일이 불필요하고 빈 로드로 충분.
② 게스트 등록이 "server error"(500)로 실패 host_nic_binding.host_mac 에 UNIQUE 제약 — MAC 재사용 시 충돌 UUID 파생 MAC(하네스 규약)으로 매 게스트를 고유화.
③ 개시(start)가 무효화(트랜잭션 롤백) 수동 삽입한 할당 행의 version 이 NULL → 개시 시 markConsumed 의 낙관 락 갱신이 롤백 version=0 으로 삽입. 정상 앱 경로는 @Version 이 0 을 부여하므로 무관 — 수동 시드 한정.

§6. 남은 것 · 후속 · 회귀

후속 슬라이스로 미룬 것

  • 후속 phase executor(FirmwareUpdatingExecutor 등) = ES-n · E2. ES-1 이후 게스트는 소유 첫 phase 에서 명시 HOLD 로 대기한다.
  • 소유 phase HOLD 무한 대기의 추가 운영 가시성 = 후속. 계획 rail 은 이미 커서를 표시하므로 최소 가시성은 확보돼 있다.
  • 관련 슬라이스 — U3-2-b(원본 정의서 삭제 lifecycle) · U3-3(가시화).

회귀 위험

  • 무할당 경로 — Case A 로 확인. 종단 동작이 U3 이전과 동일해 회귀 없음.
  • directiveFor 변경 — REBOOT 조건을 확장(ordinal() 비교 추가)만 했다. 진단을 완주한 무할당 게스트는 이전과 동일하게 REBOOT 를 받으며, 새로 REBOOT 를 받는 것은 전진한 할당 게스트뿐이다.
  • BootScriptDispatcher — 주석만 바꿔 동작 변경 0.
§7. CP7 안내 (사용자 E2E)

CP7(사용자 단독 E2E)은 두 방향을 병행한다.

① qemu 실행 관찰

  • scripts/pxe-lab/run-guest.sh 가 QEMU 내장 DHCP + TFTP 로 실 게스트를 PXE (Preboot Execution Environment — 네트워크 부팅) 부팅시킨다.
  • 진단 리눅스 체인 → 커서 전진 → 소유 phase HOLD 를 시리얼 로그(console=ttyS0) · 서버 로그로 관찰.
  • 앱은 PXE_ASSETS_ROOT · PXE_SERVER_BASE_URL=http://10.0.2.2:PORT 로 기동.

② 브라우저

  • server-detail 계획 rail 로 커서 전진을 확인.
  • §5 스크린샷과 같은 화면에서, 실 게스트 전진이 반영되는지 관찰.
macOS Apple Silicon 은 TCG (Tiny Code Generator — QEMU 의 순수 소프트웨어 에뮬레이션) 라 스모크(smoke) 용도다. 전체 OS 설치 E2E 는 Rocky + KVM 환경에서 수행한다.
