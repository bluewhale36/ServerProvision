§1. 무엇을 고쳤는가

U3-2-b 의 CP7 사용자 브라우저 E2E 에서, 삭제된 세팅 정의서를 복원할 때 서버가 거절한 응답의 JSON 원문이 화면에 그대로 노출됐다. 이 슬라이스는 그 결함을 고치고, 같은 부류가 재발할 수 없도록 기본값을 뒤집었다.

이전

폼마다 data-async-submit 마커를 붙여야 fetch 로 나갔다.

마커를 잊으면 → raw JSON 노출
조용하고 사용자에게 도달

이후

상태 변경 폼은 기본으로 가로채인다. 뷰를 재렌더하는 폼만 opt-out.

표기를 잊으면 → 모달로 안내
시끄럽고 CP4 테스트가 먼저 잡음

서버 쪽으로는, 문서 이동으로 들어온 요청이 도메인 예외를 만나면 error.html 이 렌더되도록 Accept 협상의 입력을 바로잡았다. advice 의 @Order 와 produces 는 건드리지 않았다.

§2. 진단 (실측 근거)

착수 브리핑은 @ExceptionHandler(Exception.class) 최종 폴백 부재를 원인으로 지목했다. 조사 결과 사실이 아니었다 — 예외는 정상적으로 잡혀 409 로 매핑됐고 형식만 틀렸다. 실제 원인은 content negotiation 이었다.

요청 Accept*/* 포함선택된 advice응답
text/html없음Webtext/html, view=error
text/html,application/xhtml+xml;q=0.9없음Webtext/html
text/html,*/*;q=0.8있음Apiapplication/json
실제 크롬 내비게이션 헤더있음Apiapplication/json
기전 : advice 선택은 Accept 의 선호도(q값)를 보지 않는다. 등록 순서대로 "요청이 받아줄 수 있는 형식이면 채택" 하고, */* 는 모든 형식과 호환되므로 JSON advice 가 무조건 먼저 합격한다. 실제 브라우저는 */*;q=0.8 을 항상 붙이므로 WebExceptionHandler 는 도달 불가능했다.

당시 테스트는 전부 통과하고 있었다. Accept: text/html 이라는 순수값으로만 검증했기 때문이다. 브라우저는 그런 값을 보내지 않는다.

혼동하기 쉬운 지점 — 실패 경로가 둘이다

CP1 검토 중 사용자가 "없는 경로로 진입했더니 오류 페이지가 정상 렌더된다" 고 관찰했고, 이것이 서술을 정정하게 했다.

경로 A — advice 가 잡는 예외경로 B — advice 가 못 잡는 예외
예/management/os/999/edit/management/os/3 (매핑 없음)
처리두 advice 의 content negotiation기본 /error → BasicErrorController
고치기 전JSONHTML (정상)

BasicErrorController 는 평범한 컨트롤러라 정상 요청 매핑을 타고, 정상 매핑은 선호도를 제대로 지킨다. 같은 프레임워크 안에서 두 메커니즘이 다르게 동작하는 것이 이 결함의 뿌리다. 이 슬라이스는 경로 A 를 경로 B 와 같은 결과로 맞춘다.

§3. 구현

서버 — DocumentNavigationAcceptFilter

Sec-Fetch-Dest: document 요청의 Accept 를 text/html 로 좁혀 보고하는 필터다. 브라우저가 문서 이동에만 보내는 헤더라 Accept 같은 모호성이 없고, fetch(empty)와 비브라우저 클라이언트(헤더 없음)는 그대로 JSON 에 남는다.

협상 입력 (이전)

Accept: text/html, …,
        */*;q=0.8, …

협상 입력 (문서 이동일 때만)

Accept: text/html

조건 분기가 한 줄도 늘지 않았다. advice 는 로직 변경 0 이고, 판별은 Spring primitive(필터 + 요청 래퍼)가 떠맡는다. 과거 두 차례 사고를 낸 @Order 조정을 재현하지 않는다.

프런트 — 기본값 반전

분류수처리
액션 폼 (redirect 전용)55전역 form-submit.js 가 기본 가로채기
입력 폼 (BindingResult 재렌더)11data-native-submit 으로 사유와 함께 opt-out
XHR (@ResponseBody)70e.defaultPrevented 로 자동 회피 — 페이지 전용 JS 가 계속 담당

폐기한 data-async-submit 마커는 18곳에서 제거했다. 전송 구현은 FormSubmit.sendAsync 하나로 모아 확인 모달 경로와 전역 경로가 공유한다 — 두 진입점이 갈라지지 않게 하기 위함이다.

구현 중 확정한 분류. plan 은 부류를 둘로 봤으나 코드를 읽어 셋임을 확인했다. 생성 폼처럼 @ResponseBody 로 JSON 을 돌려주고 페이지 전용 JS 가 처리하는 부류가 따로 있었고, 이들은 e.defaultPrevented 가드로 자연히 비켜간다. 판정 기준도 "문자열 뷰 반환" 이 아니라 BindingResult 수령 여부로 바로잡았다 — 헬퍼 메서드로 재렌더하는 addIso 를 앞선 기준이 놓쳤기 때문이다.

§6. CP5 수행 기록 (조작과 증거)

B4 — 주소창에 없는 자원 id 직접 입력

조작: 주소창에 /management/os/999/edit 를 직접 입력해 진입. 매핑은 있으나 자원이 없어 OSMetadataNotFoundException(도메인 예외 = 경로 A)이 발생한다.
결과: 오류 페이지가 렌더됐다. 상태 표기 "페이지를 찾을 수 없습니다 (404)", 도메인 메시지 "OS 버전을 찾을 수 없습니다. id=999", 그리고 [이전 페이지로] · [홈으로] 복귀 동선(C3). 네트워크 기록상 GET 404. 고치기 전이라면 JSON 원문이 화면이 됐을 경로다.

스크린샷: B4 · C3 — 경로 A 의 404 가 오류 페이지로 수렴하고 복귀 동선이 제공된다 — 정본(_report.html)에서 확인

스크린샷: B1 · C1 · C2 — 거절이 raw JSON 이 아니라 안내 모달로 수렴하고, 사유가 사용자 언어로 표시되며 페이지 상태가 보존된다 — 정본(_report.html)에서 확인
