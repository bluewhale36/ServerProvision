§1. 진단 — 실기 4호가 드러낸 둘

결함 ① — 되읽기 오류 한 번이 축을 통째로 실패시켰다

2026-09-10 실기 4호(사이버 웨이브) 10:37 · 10:38 에 BMC 세팅 착수 단계가 COLD_REDUNDANT 항목을 쓴 뒤 되읽기로 GET /api/cold_redundant-status 를 호출했고, BMC 가 {"error":"Error in Getting Cold Redundant Status","code":1334} 를 돌려줬다. 당시 구현은 이 응답을 항목 REJECTED 로 바꾸고, 단계는 그것을 WRITE_REJECTED 로 읽어 BMC 축을 닫았다.

같은 요청이 10:46 세 번째 시도에서 통과했다. 값이 거절된 것이 아니라 읽기가 일시적으로 실패한 것이었는데도 축이 실패로 닫혀, 운영자가 화면에서 [재시도] 를 두 번 눌러야 다음으로 넘어갔다.

문제의 성격 : 쓰기는 이미 성공한 뒤였다. 확인 차 읽는 호출 하나가 흔들렸다고 해서 그 값이 잘못 적용된 것은 아니다. 그런데도 판정이 "값 거절" 과 같은 자리로 떨어져, 사람이 개입해야 진행되는 상태가 됐다.

결함 ② — 전원 제어 섹션이 새로고침 전까지 "BMC 미검출" 로 남았다

게스트 서버 상세 페이지의 전원 제어 섹션은 페이지를 열 때 bmcDetected 값에 따라 버튼 묶음 또는 "BMC 미검출" 문구를 서버가 그린다. 이 페이지는 서버가 변경 신호를 보내면 [data-live] 가 붙은 영역만 다시 받아 바꿔 끼우는데, 전원 제어 섹션에는 그 속성이 없었다. 그래서 진단이 BMC 를 찾아낸 뒤에도 화면은 "BMC 미검출" 인 채였고, 운영자가 직접 새로고침해야 버튼이 나타났다(실기 4호 사용자 지적).

속성 하나를 붙이는 것으로 끝나지 않는다. server-power.js 는 문서 로드 시점에 섹션 안 버튼을 찾아 리스너를 직접 붙이고, 정상 종료 감시 상태(감시 세대 · 타이머)를 클로저에 들고 있었다. 영역을 갈아 끼우면 그 리스너가 통째로 사라진다.

§2. 구현 ① — 되읽기 오류를 실패가 아니라 재시도로 다룬다

항목 결과에 "일시 오류" 자리를 만든다

항목 하나의 처리 결과는 BmcItemOutcome 이 표현한다. 여기에 상태 TRANSIENT 와 정적 팩터리 transientError(detail) 를 더했다. 기존 rejected · mismatch 와 같은 층에 놓인 값이며, 예외 계층은 늘리지 않았다 — BMC 의 일시 오류는 워커가 다음 주기에 흡수할 정상 운영 경로이지 프로그램 예외가 아니기 때문이다.

D-2. 세 번까지 기다리고, 세 번째에는 그 항목만 건너뛴다

단계는 항목이 TRANSIENT 를 돌려주면 원장의 재시도 횟수를 올린다. 횟수는 원장 meta 의 retries.<ITEM> 에 항목별로 쌓이며, 읽고 올리는 길은 SettingLedger.bumpRetry · retriesOf 하나로 모았다.

TRANSIENT ──▶ bumpRetry(item) = n n < 3 행을 RUNNING 으로 둔 채 주기를 끝낸다 ──▶ 다음 워커 주기가 그 항목부터 다시 쓴다(멱등) n = 3 items.<ITEM> = "SKIPPED:되읽기 오류 3회 — <detail>" ──▶ 다음 항목으로 계속 ──▶ 축은 SUCCEEDED

임계 3 은 매직 상수로 두지 않고 TRANSIENT_MAX_ATTEMPTS 로 선언했다. 건너뛴 항목은 종결 요약에 실린다 — 실제 문구는 3개 적용 · COLD_REDUNDANT 건너뜀(되읽기 오류 3회 — …) 형태다.

§6. CP5 수행 기록 — 브라우저 (A4 · B2 · C1 · C1-b)

A4 — 전원 섹션 실시간 갱신

게스트 한 대를 등록만 하고 상세를 열었다. 전원 제어 섹션은 문구 한 줄뿐이었다 — "BMC 미검출 — 원격 전원 제어를 쓸 수 없습니다 (진단 수집이 BMC 를 찾지 못했습니다)".

그 페이지를 그대로 둔 채 BMC 를 포함한 진단 보고를 실행했다. 0.6 초 만에 문구가 사라지고 [상태 조회] · [켜기] · [강제 끄기] · [재시작] · [정상 종료] 다섯 버튼이 전부 활성 상태로 나타났다. 섹션 DOM 에 미리 심어 둔 표식이 사라진 것으로 요소가 통째로 교체됐음을 확인했고, 메인 프레임 내비게이션은 최초 진입 1 건뿐이었다 — 새로고침이 없었다.

B2 — 교체된 영역의 버튼이 동작하는가

A4 로 방금 교체된 바로 그 영역에서 버튼을 눌렀다. 문서 위임 리스너가 새로 그려진 요소에도 닿는지 보는 항목이다.

  1. [상태 조회] → 배지가 회색 "미조회" 에서 "Off" 로 칠해지고 문구가 "현재 전원 상태 : OFF" 로 바뀌었다. 모의 BMC 의 전원도 Off 였다.
  2. [켜기] → 배지가 초록 "On" 으로 바뀌고 "켜기(On) 명령이 전달되었습니다 — [상태 조회] 로 결과를 확인하세요." 가 떴다. 모의 BMC 의 전원이 On 으로 바뀌었다.

앱 로그에도 대응하는 GET …/power 200 과 POST …/power/reset 200 이 남았다. 교체된 DOM 의 버튼이 실제 요청을 만들어 낸다.

C1 — 감시 도중 영역이 교체되면

같은 페이지에서 [정상 종료] 를 눌렀다. 확인 모달이 떠 무슨 명령인지와 "실행 중인 작업이 중단될 수 있습니다" 를 알린 뒤 [정상 종료 실행] 을 받았다 — 되돌릴 수 없는 조작을 한 번 더 묻는 자리가 그대로 동작한다.

실행 1.4 초 뒤 같은 게스트로 /boot 를 재호출해("이미 등록된 서버 재부팅" 경로) 영역을 교체시켰다. 관찰은 다음과 같다.

t+0.9s  배지 Off · 문구 "정상 종료(GracefulShutdown) 명령이 전달되었습니다…"
t+1.4s  /boot 재호출
t+1.8s  영역 교체됨 (심어 둔 표식 소실 — 요소가 통째로 바뀜) · 배지 "미조회" · 문구 비워짐
t+5.4s  배지 Off · 문구 "정상 종료가 완료됐습니다 (PowerState Off 확인)."

교체 뒤에도 감시가 살아 있었다. 클로저에 남은 감시 사슬이 다음 주기에 깨어나 배지와 문구 요소를 새로 그려진 DOM 에서 다시 찾아 결과를 칠했다. 요소를 한 번만 잡아 두던 옛 구현이라면 여기서 조용히 죽었을 지점이다. 앱 로그의 교체 이후 GET …/power 200 이 감시가 실제로 BMC 를 다시 조회한 흔적이다.

C1-b — 감시 문구가 떠 있는 동안 교체 (추가 수행)

위 결말이 5 초 만에 끝나 "호스트 응답을 기다립니다 (N초)…" 가 표시 중일 때의 교체는 확인되지 않았다. 계획의 1차 기대가 그것이라 조건을 만들어 한 번 더 했다 — 모의 BMC 를 앱 밖에서 매 주기 On 으로 되돌려 호스트가 꺼지지 않는 상황을 재연했다(화면 JS 는 건드리지 않았다).

t+5.3s  문구 "정상 종료 요청 전달 — 호스트 응답을 기다립니다 (5초)…"   ← 감시 문구 표시 중
t+5.5s  /boot 재호출
t+6.0s  영역 교체됨 — 배지 "미조회" · 문구 비워짐
t+10.4s 문구 "정상 종료 요청 전달 — 호스트 응답을 기다립니다 (10초)…"  ← 교체 4.4 초 뒤 복귀

교체 4.4 초 뒤, 곧 다음 감시 주기에 문구가 되살아났다 — 계획이 요구한 "다음 틱에 복원" 을 충족한다. 다만 이 과정에서 배지와 문구가 어긋나는 구간이 드러났다(§8 F-1).

§7. 미수행 항목과 사유

계획한 브라우저 항목(A4 · B2 · C1)은 전부 수행했다. 나머지 넷은 계획 단계에서부터 테스트로 갈음하기로 한 항목이며, 그 사유와 대체 증거는 다음과 같다.

항목대체 수단사유

§8. 발견한 것 — 결함 F-1 · 정정 · 재검증

F-1 (경미) — 교체 직후 배지가 "미조회" 로 되돌아가 문구와 어긋난다

어떻게 드러났나 — C1-b 에서 감시 문구가 떠 있는 동안 영역을 교체시켰더니, 교체 직후 배지는 서버가 그린 기본값 "미조회" 로 돌아가고 문구는 비워졌다. 다음 감시 주기에 문구만 복원되고 배지는 "미조회" 로 남았다.

t+6.0s   배지 "미조회"  문구 ''
t+10.4s  배지 "미조회"  문구 "정상 종료 요청 전달 — 호스트 응답을 기다립니다 (10초)…"

왜 문제인가 — 한 화면에서 두 표기가 서로 다른 이야기를 한다. 문구는 감시가 돌고 있다고 말하는데 배지는 아직 아무것도 조회하지 않았다고 말한다. 잘못된 조작을 유발하지는 않지만(버튼은 정상이고, 종료 · 시한초과의 종결 분기는 배지를 바로잡는다) 어긋남이 감시가 끝날 때까지 최대 60 초 이어진다.

원인 — 감시 주기의 카운트다운 갱신 분기가 문구 요소의 텍스트만 바꾸고, 배지를 칠하는 공통 그리기 함수를 부르지 않았다. 교체 전에는 섹션이 살아 있어 배지가 이전 값을 유지했으므로 이 경로가 드러나지 않았다. data-live="power" 를 붙여 영역이 교체 가능해지면서 처음 드러난 결함이다.

정정 — 마지막으로 칠한 전원 상태를 lastPower 로 기억하고, 카운트다운 분기도 문구 대입 대신 공통 그리기 함수를 부르게 바꿨다. 문구만 쓰던 자리를 배지까지 칠하는 경로로 옮긴 것이라 어긋남의 원인이 그대로 제거된다.

R1 — 정정 뒤 재검증

정정한 코드로 앱을 다시 띄우고 C1-b 와 같은 절차를 되풀이했다. 먼저 [켜기] 로 마지막 조회값을 On 으로 만든 뒤 [정상 종료] → 확인 모달 → 실행, 그리고 앱 밖에서 모의 BMC 를 매 주기 On 으로 되돌려 감시가 계속 돌게 했다. 교체 직후 구간을 0.4 초 간격으로 표본했다.
