§1. 슬라이스 개요

U3(세팅 정의서 - 게스트 할당)를 3분할한 첫 슬라이스다. U3-1 = 할당 core + 할당 시점 스냅샷 + ownedPhases 도출 · 공급(OwnedPhasesProvider Service Provider Interface, 도메인이 구현해 끼우는 확장점) + 상세 화면 계획 phase rail.

세팅 정의서를 게스트 서버에 할당하면 정의서 내용을 스냅샷으로 복사하고, SettingProcessType → ProvisioningPhase 매핑으로 그 서버가 밟을 phase 집합(ownedPhases)을 확정 · 저장해 실행 엔진에 공급한다.

이 슬라이스가 여는 것

  • 실행 엔진(ES-1 · E2)의 엄격한 선행 의존을 푼다 — 게스트가 진단 완주 뒤 어떤 phase 로 커서를 전진시켜야 하는지의 권위 출처가 U3-1 이 공급하는 ownedPhases 다.
  • 서버 상세 화면에 밟을 예정 phase 를 계획 rail 로 노출한다.
후속 슬라이스
  • U3-2 — 재할당 · 삭제 lifecycle.
  • U3-3 — 목록 cross-server 가시화.
§2. 구현 결과
패키지 배치 정정 (plan §4/§10 정정) — 스냅샷이 ProcessPayload(provisioning.setting)와 GuestServer(execution)를 동시 참조하므로, 스냅샷 엔티티를 execution 에 두면 R7 이 제거한 provisioning ↔ execution 순환을 재생성한다(실측: execution → provisioning import = 0, 일방). 따라서 할당 엔티티 · VO · 서비스 · provider 구현체는 provisioning.assignment 에 두고, OwnedPhasesProvider 인터페이스만 execution.engine 에 둔다(dependency inversion). 빌드로 순환 미생성 확인.

데이터 모델

SettingAssignment(1:N AssignedProcess, BaseTimeEntity 상속)를 신규 정의했다. 상태 컬럼 없이 파생 state() 로 상태를 계산한다.

  • OwnedPhasesConverter = 안정 코드 CSV(FW_UPDATE 등, enum name 아님) 로 저장 — 불멸 행의 하위호환 보장.

deep-freeze

BASIC_SETTING 의 biosSettingTemplateIds 를 할당 시점에 resolve 해 FrozenBiosSettings{templateId, boardModelId, BiosSettingValues}로 동결한다. 템플릿 FK 없이 자족하므로 원본 정의서 · 템플릿 편집 · 삭제와 무관하게 할당 시점 값이 보존된다(DEC-18).

markConsumed

AssignmentStartService 가 execution 개시(REQUIRED 조인) + 활성 assignment.markConsumed 를 한 트랜잭션으로 원자 실행한다. 이 wrapper 가 execution → provisioning 순환을 회피한다.

UI

  • 할당 controller — POST /provisioning/server/{id}/assignment(XHR JSON).
  • server-detail 계획 phase rail — 밟을 예정 phase + '계획(assigned) vs 실제(started)' 라벨.

수행 · 증거

V1 — 할당 전 화면. 세팅 정의서 할당 섹션과 할당 폼이 렌더되고, 계획 phase 는 아직 비어 있다.

V2 / V3 — 할당 후 화면. 정의서를 선택해 할당하면 할당된 정의서가 ACTIVE_UNCONSUMED 로 붙고, 계획 phase rail 이 밟을 예정 phase 를 표로 노출한다. BASIC_UPDATE → ownedPhases=[FIRMWARE_UPDATING] 이므로 rail = DIAGNOSE_LINUX + FIRMWARE_UPDATING.

V4 — 스키마 · 소프트참조 · 개시. SHOW CREATE TABLE 로 소프트참조(definition_id FK 부재) · owned_phases 안정 코드 컬럼을 확인했다. 개시하면 consumed_at · started_at 이 동시에 기록된다 (원자 markConsumed). 400 / 404 / 409 는 실 HTTP 로 확인.

정상 흐름과 비정상 조작

  • 정상 — 할당 폼에서 정의서 선택 → 할당 → 성공, 계획 rail 갱신, 개시 시 consumed_at · started_at 동시 기록.
  • 비정상(의도적 시도) — 400(필드 검증 실패) / 404(자원 부재) / 409(충돌)를 실 HTTP 상태코드로 트리거해 advice 매핑 확인.
CP5 에서 발견 · 수정한 버그 — 할당 폼(id="assignment-form")이 data-live="assignment" 영역 안에 있었다. server-stream.js(SSE)가 changed 신호에 [data-live] 영역을 replaceWith 로 교체하면, 새 폼 DOM 에는 server-assignment.js 가 붙인 submit 핸들러가 없어 핸들러(와 선택 입력)가 소실되고 폼이 네이티브 GET 으로 falls back 해 할당이 되지 않는다. server-detail.html 규약(§S7: "수정 폼은 [data-live] 미마킹 = 입력 보존")을 위반한 것으로, curl · mock 테스트로는 드러나지 않고 SSE 재렌더가 있어야 나타나는 버그다.

수정 — 할당 섹션의 data-live="assignment" 제거(입력 폼을 SSE 교체 대상에서 제외 — 할당 · 개시는 모두 리로드라 이 섹션에 SSE-only 변화 없음).
재검증 — SSE 재렌더(5개 data-live 영역 replaceWith)를 재현한 뒤에도 할당 폼이 생존하고 submit 핸들러가 유지됨(handlerSurvived = true)을 브라우저에서 확인. 이 수정은 커밋 c7daf9a 후속으로 반영.
