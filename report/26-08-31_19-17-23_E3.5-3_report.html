§0. 이 보고서의 특수성 — CP5 를 브라우저가 아니라 모의 게스트 하네스로 수행했다

통상의 report 는 CP5 샌드박스 브라우저 검증의 계획 · 수행 기록 · 스크린샷 증거가 본문의 중심이다. 이번 슬라이스는 E 단계 예외에 해당한다 — 실행 엔진(E*) 슬라이스는 게스트가 화면 없이 HTTP 로만 서버와 상호작용하므로, CP5 의 샌드박스 검증을 브라우저 대신 모의 게스트 하네스(scripts/mock-guest/) 실행으로 수행한다는 것이 프로젝트 규약에 명시된 예외다.

이번 슬라이스가 그 예외에 정확히 들어맞는 이유는, 여기서 새로 만들어진 것이 화면이 아니라 게스트와 서버가 주고받는 지시 · 보고의 왕복이기 때문이다. 서버는 집행 지시(RAID_APPLY)와 검증 지시(RAID_VERIFY)를 내리고, 게스트 에이전트는 그것을 계열 CLI 명령으로 번역해 실행한 뒤 결과를 보고한다. 이 왕복에는 사람이 클릭할 화면이 없다.

그래서 이 보고서의 증거 구조는 다음과 같이 달라진다.

  • 검증 수단 — 브라우저 조작이 아니라 모의 게스트 하네스가 게스트의 HTTP 행동(체크인 → 지시 수신 → step close 보고)을 재연한 것이다.
  • 증거 — 스크린샷 0 장. 항목마다 붙는 것은 서버가 실제로 돌려준 API 응답 원문과 그 결과로 DB 에 남은 원장 · 표의 행이다(§5).
  • 항목 식별자 체계는 유지 — 정상 A1 · A2, 비정상 B1~B4, 막는 방식 C1 의 7 항목을 먼저 계획하고(§4) 같은 식별자로 수행을 대조한다(§5).
  • 실물은 이관 — 실제 RAID 카드에 storcli64 · sas3ircu 가 명령을 내리는 층은 확인하지 않았다. 하네스는 CLI 를 흉내 낸 보고를 올릴 뿐이다. CP7 실기 일괄로 넘긴다(§6).
CP7 실기의 전제 조건이 하나 붙어 있다. 이번 슬라이스는 외부 기존 볼륨이 남아 있으면 집행하지 않고 보류한다(§2 판정 ③). 따라서 실기에서 집행 경로를 타려면 기존 볼륨을 사용자가 수동으로 먼저 삭제해야 한다 — CP1 검수에서 확정된 사항이다. “기존 구성 : 보존 / 파괴” 선택 축이 도입되는 E3.5-4 이후에는 이 수동 절차가 사라진다.
§6 이 이 보고서의 핵심이다. 검증 수단이 브라우저가 아닌 슬라이스의 보고는 “그래서 무엇이 확인되지 않은 채 남았는가” 를 사유와 함께 적어야 성립한다. 감추면 다음 사람이 검증된 층과 검증되지 않은 층을 구분하지 못한다.
§1. 배경 · 진단

이 슬라이스의 자리 — 계획을 세우는 머리에 손을 붙인다

바로 앞 슬라이스 E3.5-2 까지의 상태는 계획을 산출해 화면에 미리보기로 보여주는 데까지였다. 카드에 꽂힌 디스크로 어떤 볼륨을 만들지는 정해졌지만 카드에는 아무것도 쓰이지 않았고, 게스트는 WAIT 지시를 받으며 대기하고 있었다. E3.5-3 은 그 계획을 실제로 카드에 새기는 손이다.

구조는 0-3 토론에서 확정된 하이브리드(결정 D-1) 를 따른다 — 머리(무엇을 만들지 정하는 계획과, 만들어진 것이 계획과 같은지 판정하는 검증)는 서버가 갖고, 손(실제 CLI 명령 실행)은 게스트 에이전트가 갖는다. 서버는 카드 계열에 무관한 중립 명령을 내려보내고, 에이전트가 그것을 자기 카드 계열의 CLI 문법으로 번역한다. 계열이 늘어도 서버의 판정 로직은 그대로다.

CP1 검수에서 개정 2 건이 확정됐다

plan 검수에서 사용자가 두 가지를 바로잡았다.

첫째, 볼륨 이름의 형식이다. E3.5-2 가 만든 이름은 spv-r1-v1 처럼 하이픈을 포함했는데, RAID 카드 중에는 볼륨 이름에 하이픈을 받지 않는 것이 있다. 집행 단계에 와서야 카드가 이름을 거절하면 계획 전체가 무의미해지므로, 영숫자만 쓰는 형식으로 미리 바꿨다.

E3.5-2 원안

spv-r1-v1

하이픈 포함 — 계획을 화면에 보여주기만 할 때는 문제가 없다.

집행 단계에서 하이픈 미지원 카드가 이름을 거절할 수 있다

CP1 개정

spvR1V1 = spvR{규칙번호}V{순번}

영숫자만 — 카드 계열을 가리지 않는다.

이미 병합된 E3.5-2 의 이름 생성부와 테스트 어서션 12 곳을 함께 갱신했다

둘째, CP7 실기의 진입 조건이다. 이번 슬라이스는 카드에 우리가 만들지 않은 볼륨이 남아 있으면 집행하지 않고 보류한다. 실기 장비에는 기존 볼륨이 남아 있으므로, 실기에서 집행 경로를 확인하려면 기존 볼륨을 사용자가 수동으로 삭제한 뒤 시작하기로 확정했다. 보존 · 파괴를 사용자가 고르는 축은 E3.5-4 의 몫이다.

CP4 검수에서 설계 개선 1 건이 반영됐다

main 구현을 검수하던 사용자가 칩 판별 로직이 두 곳에 하드코딩돼 있다는 점을 지적했다. 서버의 인벤토리 파서도 1000:0097 같은 PCI 식별자를 자체 패턴으로 들고 있었고, 게스트 에이전트 스크립트도 같은 식별자를 자기 안에 적어 두고 있었다. 새 칩이 추가되면 두 곳을 함께 고쳐야 하고, 한 곳을 빠뜨리면 서버와 에이전트의 판정이 어긋난다.

이 지적으로 결정 6(칩 판별 SSOT) 이 신설됐다. 구현은 §2 의 R8 이다.

§2. 구현

지시 판정 5 가지 (R3)

RAID 구성 단계에 커서가 온 게스트가 체크인하면 RaidConfigurationExecutor.directiveFor 가 다음 순서로 판정한다.

순서상황지시원장
①인벤토리가 아직 적재되지 않았다RAID_INVENTORY— (E3.5-1 현행 유지)
②집행이 성공 close 됐고 검증이 아직 커서를 전진시키지 못했다RAID_VERIFY—
③외부 볼륨이 남아 있고 보존 · 파괴 축이 아직 없다WAITPENDING POLICY_UNDECIDED
④계획 산출이 거절됐다WAITPENDING PLAN_REJECTED
⑤계획이 성립했다RAID_APPLYPENDING PLANNED (계획 동결)

③ 의 “외부” 라는 한정이 중요하다. 카드에 볼륨이 남아 있어도 그 이름이 spvR 로 시작하면 우리가 앞서 만든 것이므로, 재구성 대상이지 남의 데이터가 아니다. 그래서 잔여 판별을 거쳐 우리 것이 아닌 볼륨이 있을 때만 보류한다. 이 구분이 없으면 재집행이 영원히 보류에 걸린다.

③ 과 ④ 는 실패가 아니라 보류다. 원장에 PENDING 으로 남고 진행률에 실패 낙인을 찍지 않는다. 사용자가 정의서를 고치거나(④) 축이 도입되면(③) 저절로 풀리는 상태이기 때문이다. 보류는 30 초마다 같은 판정을 받으므로, 같은 사유가 이미 최신 행이면 다시 쌓지 않는다.

계획이 성립했지만 묶을 볼륨이 하나도 없는 경우(RAID 규칙이 없는 정의서)는 집행할 것도 검증할 것도 없으므로 phase 를 완주 처리하고 전진한다.

계획을 왜 “동결” 하는가 (R2)

검증은 “실물이 계획과 같은가” 를 보는 일이므로 대조 기준이 되는 계획 한 벌이 집행 시점에 고정돼 있어야 한다. 계획은 조회할 때마다 다시 산출되는 파생물이라(E3.5-2), 검증 시점에 다시 산출하면 그 사이 정의서가 바뀌었을 때 엉뚱한 기준과 대조하게 된다. 그래서 집행 지시 직전에 계획 JSON 을 원장에 동결한다.

동결을 어디에 둘지는 두 안이 있었고, PENDING 단발 행을 채택했다.

기각 — RUNNING 행에 동봉

집행 중 행의 statusMeta 에 계획을 싣는 안.

원장 close 가 메타를 결과로 덮는다 — 게스트가 집행 결과를 보고하는 순간 계획이 사라진다.

E2-2 에서 실측으로 겪은 결함 계열이다

채택 — PENDING 단발 행

집행 행과 별개의 PENDING 행에 {"reason":"PLANNED","plan":…} 로 싣는다.

close 가 덮을 대상이 아니므로 집행이 끝난 뒤에도 남는다.

검증과 payload 파생이 같은 행을 읽는다

같은 계획을 두 번 동결하지 않도록, 최신 행이 이미 동결(PENDING PLANNED)이거나 집행 중(RUNNING)이면 다시 쌓지 않는다. 응답이 유실돼 게스트가 체크인을 되풀이해도 원장이 부풀지 않는다.

검증이 대조하는 4 축 (R4)

RaidResultVerifier 는 의존성이 0 인 순수 static 이다. 재채집한 원문을 인벤토리 수집과 같은 파서(RaidInventoryParser)로 해석한 뒤, 동결 계획과 네 축을 대조한다 — 볼륨 수 · 레벨 · 멤버 슬롯 집합 · 이름. 이름을 내지 않는 계열(IR)이 있으므로, 이름이 비어 있으면 레벨과 멤버 집합으로 폴백해 짝을 찾는다.

일치 ──▶ raid_volume replace 기록 + 인벤토리 재적재(화면 = 실물) + 커서 전진 불일치 ──▶ RESULT_MISMATCH 실패 (기록 없음)

일치했을 때 인벤토리를 재적재하는 이유는 화면 때문이다. 적재된 인벤토리는 집행 전의 실물이므로, 갱신하지 않으면 화면이 이미 사라진 구성을 계속 보여준다. 검증에 쓴 재채집 원문이 곧 집행 후 실물이므로 그것으로 덮는다.

칩 판별의 단일 출처 (R8 — CP4 검수 반영)

PCI 식별자와 카드 계열의 대응을 RaidChipFamily 의 상수별 메서드(chipPciIds()) 하나로 모았다. 서버의 파서는 fromLspci() 로 이 목록을 쓰고, 게스트 에이전트는 agentChipHint() 가 만들어 지시에 동봉해 준 맵으로만 판별한다.

agentChipHint() ──▶ "1000:0097=MPT_IR 1000:005d=MEGARAID" ──▶ 지시 응답의 raidChips ──▶ agent.sh

결과로 agent.sh 안에 칩 식별자 리터럴이 하나도 남지 않는다. 새 칩이 추가되면 서버 enum 한 곳만 고치면 되고, 스크립트는 손대지 않는다. 파서가 들고 있던 자체 패턴도 제거해 판별이 이중화돼 있던 것을 해소했다.

기각한 대안 : “정의서에 지정된 카드 계열을 확정해서 동봉한다” 는 안. 이렇게 하면 에이전트가 실물을 보지 않고 서버가 시킨 계열로 동작하므로, 실물이 다른 카드일 때 그 불일치를 영영 잡지 못한다. 후보 맵을 주고 실물로 판별하게 하는 지금 방식은 카드 불일치 탐지를 유지한다.

계획 개정의 파급

볼륨 이름 형식 개정(§1)과 기록에 필요한 규칙 번호 때문에, 이미 병합된 E3.5-2 의 산출물을 함께 고쳤다. PlannedVolume 과 PlannedPassthrough 에 ruleNo 를 더했고(raid_volume 기록의 원천), RaidPlanner 의 이름 생성부와 상세 화면 템플릿, 그리고 이름을 검사하던 테스트를 갱신했다.

CP5 하네스 자산

모의 게스트 하네스에 raid-apply-cycle.sh 를 추가했다. 정상(ok) · CLI 실패(clifail) · 검증 불일치(mismatch) 세 모드로 게스트의 행동을 갈라 재연한다. 기존 raid-inventory-cycle.sh 에는 볼륨이 하나도 없는 카드를 재연하는 mrclean 모드를 더했고, 그에 필요한 채집 원문 픽스처 3 개를 합성했다.

불가침 원칙 점검

  • Primitive Obsession — 집행 payload 의 레벨은 RaidLevel enum, 기록된 볼륨의 역할은 PlannedVolumeRole enum, 칩 계열은 RaidChipFamily enum 이다. 원장 사유는 RaidLedger 의 명명 상수로 고정돼 있어 문자열이 호출부에 흩어지지 않는다.
  • 조건분기 legacy 확장 금지 — 칩 식별자를 RaidChipFamily 의 상수별 메서드로 두었으므로, 칩이 늘어도 파서와 에이전트에 분기가 늘지 않고 상수의 목록 한 줄이 는다(R8). 집행 payload 를 지시에 싣는 통로도 ProvisioningPhaseExecutor 의 default 메서드로 두어, 그 지시를 내는 실행기만 재정의하고 나머지 phase 실행기는 손대지 않는다.
  • 레이어 경계 — 게스트로 나가는 것은 응답 record(AgentCheckinResponse · StepCloseResponse)이며 엔티티가 아니다. 집행 payload 는 계획 모델에서 필요한 것만 추린 별도 record(RaidApplyPayload)로, 미배정 디스크나 규칙 소비 내역 같은 판정 부산물은 게스트에게 내려가지 않는다.
  • 네이밍 — 신규 클래스는 도메인 의미를 직접 드러내는 명칭이다(RaidApplyPayload · RaidResultVerifier · RaidVolume · RaidVolumeRepository). Controller · Request 접미사 규약은 이번 슬라이스에 대상이 없다 — 컨트롤러 변경 0 · 신규 URL 0 이고, 지시와 payload 는 기존 체크인 · step close 응답에 실려 나간다.

§4. CP5 검증 계획 (항목 식별자)

수행 전에 항목을 계획하고 식별자를 붙였다. 아래가 그 목록이며, §5 의 수행 기록이 같은 식별자로 1:1 대응한다.

검증 수단은 브라우저 조작이 아니라 모의 게스트 하네스다(§0 — E 단계 예외). 환경은 E3.5 계열이 쓰던 e35 샌드박스를 재사용했고(애플리케이션 7838 · 데이터베이스 3357), 이번 구현이 실린 새 jar 로 재기동한 뒤 수행했다.

정상 흐름 A — 항목별 확인 대상

  • A1 정상 완주 — 볼륨이 하나도 없는 카드를 가진 새 게스트에, RAID1 · SSD · 480 GB · 정확히 2 대를 요구하는 시드 정의서를 붙인다. 체크인 응답에 집행 payload 가 실려 나가는가, 집행 성공 close 가 검증 지시를 받는가, 검증 통과가 raid_volume 기록과 phase 종단으로 이어지는가. 한 바퀴 전체가 끊기지 않고 도는지를 보는 항목이다.
  • A2 재적재 — 검증을 통과한 뒤 게스트에 적재된 인벤토리가 집행 후 실물로 갱신되는가. 갱신되지 않으면 화면이 이미 사라진 구성을 계속 보여주게 되므로, 화면과 실물이 어긋나지 않는지를 데이터 층에서 확인한다.

비정상 조작 B — 항목별 확인 대상

  • B1 외부 볼륨 보류 — 우리가 만들지 않은 볼륨이 남아 있는 실측 인벤토리를 가진 게스트로 두 번 체크인한다. 두 번 다 대기 지시를 받는가, 그리고 보류 원장이 정확히 한 행만 남는가. 30 초 주기 체크인에서 같은 사유가 무한히 쌓이지 않아야 한다.
  • B2 CLI 실패 — 하네스의 clifail 모드로 게스트가 CLI 실행에 실패했다고 보고하게 한다. 실패 사유와 어느 명령에서 실패했는지, 그리고 실행 로그 원문이 원장에 보존되는가. 진행률이 실패로 전환되는가.
  • B3 검증 불일치 — 하네스의 mismatch 모드로 집행 전 원문을 그대로 재채집 결과인 양 보고하게 한다. 대조가 어긋난 사실을 사유로 남기고 실패하는가, 그리고 실물이 계획과 다르므로 아무것도 기록하지 않는가. 검증이 통과 도장이 아니라 실제 대조임을 보는 항목이다.
  • B4 게이트 — 아직 진단 단계에 있는 게스트가 집행 step 을 열려고 하면 거절되는가. 단계 순서를 건너뛴 요청이다.

막는 방식 · 경계 C — 항목별 확인 대상

  • C1 재시도 멱등 — B2 로 집행에 실패한 바로 그 게스트를 재시도시킨다. 실패한 채로 굳지 않고 새 계획이 다시 동결되어 재집행이 완주하는가. 실패가 되돌릴 수 없는 종착점이 되면 운영자는 게스트를 버리고 처음부터 다시 등록해야 하므로, 실패에서 빠져나오는 길이 실제로 열려 있는지 보는 항목이다.

A1 — 집행 한 바퀴의 정상 완주

조작 : 볼륨이 하나도 없는 카드(mrclean)를 가진 새 게스트를 세우고, RAID1 · SSD · 480 GB · 정확히 2 대를 요구하는 시드 정의서를 할당한 뒤 하네스의 ok 모드로 한 바퀴를 돌렸다.
기대 : 체크인 응답이 집행 지시와 payload 를 싣고, 집행 성공 close 가 검증 지시를 받고, 검증 통과 close 가 재부팅 지시를 받는다. 그 사이 원장에 동결 → 집행 → 검증이 순서대로 쌓이고 raid_volume 한 행이 남는다.

실제 — 체크인 응답 :

{"directive":"RAID_APPLY","raidApply":{"deleteExisting":false,"volumes":[{"name":"spvR1V1","level":"RAID1","slots":["252:0","252:1"]}],"jbod":[]},"raidChips":"1000:0097=MPT_IR 1000:005d=MEGARAID"}

집행 step 을 성공 close 하자 응답이 RAID_VERIFY 로 바뀌었고, 검증 step 을 성공 close 하자 REBOOT 이 돌아왔다. 원장에는 네 행이 순서대로 쌓였다.

RAID_INVENTORY_COLLECTING   SUCCEEDED
RAID_APPLYING               PENDING     {"reason":"PLANNED","plan":{ … }}     ← 계획 동결
RAID_APPLYING               SUCCEEDED   {"log_b64":"…"}                       ← 게스트 집행 로그 원문
RAID_VERIFYING              SUCCEEDED

raid_volume 에 남은 행과 진행률 :

name      raid_level  member_slots         usable_bytes    volume_role  rule_no  state
spvR1V1   RAID1       ["252:0","252:1"]    479559942144    OS           1        Optl

progress : completed 1 · failed 0

판정 : PASS — 지시 · 집행 · 검증 · 기록 · 전진이 끊긴 데 없이 이어졌다. 볼륨 이름이 CP1 개정 형식(spvR1V1)으로 나갔고, 그 이름이 payload · 원장 · 기록 표 셋에서 같은 값으로 관통한다. 역할이 OS 로 기록된 것은 E4 의 OS 설치가 설치 대상 볼륨을 찾는 축이 실제로 채워졌다는 뜻이다.

A2 — 검증 통과 후 인벤토리 재적재

조작 : A1 이 완주한 게스트의 적재 인벤토리를 조회해, 집행으로 새로 생긴 볼륨 이름이 그 안에 들어 있는지 확인했다.
기대 : 집행 전 인벤토리에는 볼륨이 0 개였으므로, 갱신되지 않았다면 새 이름이 나올 수 없다.
실제 :

raid_inventory_json LIKE '%spvR1V1%'  →  1 건 (1,462 B)

판정 : PASS — 검증에 쓴 재채집 원문이 그대로 적재본을 덮었다. 화면이 읽는 인벤토리가 집행 후 실물과 같아졌으므로, 사용자가 상세 화면에서 사라진 구성을 보게 되는 어긋남이 생기지 않는다.

B1 — 외부 볼륨이 남아 있으면 집행하지 않는다

조작 : 우리가 만들지 않은 볼륨 2 개가 남아 있는 실측 인벤토리를 가진 기존 게스트로 두 번 연속 체크인했다.
기대 : 두 번 다 대기 지시를 받고, 보류 원장은 중복 억제로 한 행만 남는다.
실제 : 응답은 두 번 다 WAIT 였고, 집행 step 의 PENDING 행은 정확히 1 개였다.

{"reason":"POLICY_UNDECIDED","detail":"외부 기존 볼륨 2개 — \"기존 구성 : 보존 / 파괴\" 축 도입(E3.5-4) 전에는 집행하지 않습니다"}

판정 : PASS — 남의 데이터를 임의로 지우지 않는 방어가 실제로 작동한다. 그리고 막는 방식이 두 가지 면에서 온당하다 — 첫째, 실패가 아니라 보류(PENDING)라서 진행률에 실패 낙인이 찍히지 않는다. 둘째, 사유 문구가 “왜 멈췄고 무엇이 도입되면 풀리는지” 를 그대로 말해 준다. 30 초마다 같은 판정을 받아도 원장이 부풀지 않는 것까지 두 번째 체크인으로 확인했다.

B2 — 게스트가 CLI 실행에 실패했을 때

조작 : 하네스 clifail 모드 — 집행 지시를 받은 게스트가 볼륨 생성 명령에서 실패했다고 보고한다.
기대 : 실패 사유 · 실패한 명령 · 실행 로그 원문이 원장에 남고, 진행률이 실패로 전환된다. 커서는 실패한 지점에 머무른다.
실제 — 실패 close 의 응답과 원장 행 :

close 응답 : {"directive":"REBOOT", …}

원장 RAID_APPLYING  FAILED
{"reason":"CREATE_REJECTED","detail":"storcli64 add vd rc=255","log_b64":…}

progress : failed_at 1 · 커서 RAID_APPLYING (실패 지점)

판정 : PASS — 실패가 조용히 삼켜지지 않는다. 사유 코드만이 아니라 어느 명령이 몇 번 코드로 실패했는지와 실행 로그 원문이 함께 남으므로, 운영자가 카드에 직접 붙지 않고도 원인을 좁힐 수 있다. 커서가 실패 지점에 머무는 것은 C1 의 재시도가 그 자리에서 다시 출발할 수 있게 하는 전제다.

B3 — 만들어진 것이 계획과 다를 때

조작 : 하네스 mismatch 모드 — 검증 지시를 받은 게스트가 집행 전 원문(기존 볼륨 2 개가 그대로 있는 상태)을 재채집 결과인 양 보고한다.
기대 : 재채집 보고 자체는 정상 close 지만, 서버가 동결 계획과 대조해 어긋남을 잡아내고 실패로 남긴다. 실물이 계획과 다르므로 기록은 남기지 않는다.
실제 :

RAID_VERIFYING  SUCCEEDED    ← 재채집 보고 자체의 close
RAID_VERIFYING  FAILED       {"reason":"RESULT_MISMATCH","detail":"볼륨 수 불일치 — 계획 1개 · 실물 2개"}

progress : failed 1        raid_volume : 0 행

판정 : PASS — 검증이 형식적인 통과 도장이 아니라 실제 대조임이 드러난다. 특히 보고의 성공과 판정의 성공이 분리돼 있다 — 게스트는 시킨 일(재채집)을 정상 수행했으므로 그 close 는 성공이고, 그 내용을 대조한 서버의 판정이 별도 행으로 실패를 남긴다. 두 사실이 한 행에 뭉개지지 않는다. 어긋난 상태를 “구성됨” 으로 기록하지 않는 것도 의도대로다.

B4 — 단계를 건너뛴 요청

조작 : 아직 진단 단계에 있는 게스트로 집행 step(RAID_APPLYING)을 열려고 시도했다.
기대 : 현재 단계가 아닌 step 은 개시할 수 없다.
실제 : HTTP 409.
판정 : PASS — 단계 게이트가 지시 판정과 별개로 서버 쪽에서 한 번 더 막는다. 게스트가 오래된 지시를 들고 뒤늦게 오거나 순서가 뒤엉킨 요청을 보내도, 집행 원장이 엉뚱한 단계에 열리지 않는다.

C1 — 실패한 게스트의 재시도

조작 : B2 로 집행에 실패한 바로 그 게스트를 재시도시키고, 하네스로 다시 한 바퀴를 돌렸다.
기대 : 실패 상태에서 빠져나와 새 계획이 다시 동결되고, 재집행과 검증이 완주해 기록이 남는다.
실제 : 재시도 요청이 302 로 처리된 뒤 원장이 다음처럼 이어졌다.

RAID_APPLYING   PENDING     (PLANNED)      ← 최초 동결
RAID_APPLYING   FAILED      (CREATE_REJECTED)
RAID_APPLYING   PENDING     (PLANNED)      ← 재동결
RAID_APPLYING   SUCCEEDED

raid_volume : spvR1V1 · 역할 OS        progress : completed 1 · failed 0

판정 : PASS — 실패가 되돌릴 수 없는 종착점이 아니다. 주목할 점은 재시도가 낡은 동결본을 재사용하지 않고 계획을 다시 동결한다는 것이다. 실패와 재시도 사이에 사용자가 정의서를 고쳤을 수 있으므로, 다시 세운 계획으로 집행해야 검증의 대조 기준이 실제 집행 내용과 같아진다. 원장에는 네 행이 모두 남아 “한 번 실패하고 다시 해서 성공했다” 는 경위가 사라지지 않는다.
