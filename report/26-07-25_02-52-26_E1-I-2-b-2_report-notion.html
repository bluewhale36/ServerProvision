§1. 슬라이스 개요 — 무엇을 만들었나

이 슬라이스는 처음에 진단 리눅스 자산 화면 하나에 무결성 현황표, 상단 보존 개수 인라인 폼, 슬롯마다 접히는 버전 이력과 롤백 버튼, 봉인·재검증 버튼을 전부 얹었다. 그 설계로 서비스 계층(활성화·롤백·버전 저장소·보존 설정)은 이미 구현·검증까지 끝났다. 그런데 사용자 지시로 화면 구조만 다시 나눴다 — 서비스·엔티티·DDL 은 한 줄도 손대지 않고, 뷰와 컨트롤러 배선만 세 관심사로 갈랐다. 이 보고서가 그 최종 형태를 기록한다.

대시보드 (status-only)

  • GET /system/diagnostic-asset
  • 6슬롯 무결성 현황표 + 서빙 배너 + okCount/total
  • 상태 변경 액션 0 — 재검증(비변경 새로고침)과 운영 설정 → 링크만
  • 각 행 클릭 → 그 자산 상세

자산 상세 (자원 액션)

  • GET /system/diagnostic-asset/{slot}
  • 자산 메타 표
  • 교체 가능 슬롯 : 교체 폼 · 버전 이력 · 행별 되돌리기
  • 비교체 슬롯(apkovl · repo) : 읽기전용 + 빌드 스크립트 안내

운영 설정 (전역 튜너블)

  • GET · POST /system/diagnostic-asset/settings
  • 이력 보존 개수 폼 + 현재값
  • 무결성 봉인(seal-all) 카드 — 전 슬롯 기준선 확립
본질 — 이 슬라이스는 한 화면에 조회와 변경을 섞음 을 현황 · 자원 액션 · 전역 튜너블 세 관심사로 분리 한 재배치다. 새 도메인 능력은 없다. 서버 판정(FIFO 정리 · 롤백 승격·제거 · 서빙 게이트)은 재사용한 그대로다. 재구성 도중 코드 리뷰를 받아, 상세 데이터 조회를 6종 전량 재해시에서 단일 슬롯 해시로 최적화한 것이 유일하게 계획을 넘어선 변화다(§4 D4).

구현된 요구 규칙 (전부 충족)

  1. 대시보드 mutation 버튼 0 — 교체 · 롤백 · 봉인 · 보존 수정 중 어느 것도 대시보드에 없다. 남은 상호작용은 재검증(비변경 새로고침)과 링크(행→상세, "운영 설정 →")뿐이다.
  2. 상세 = 슬롯 단위 액션의 집 — 교체 가능한 4슬롯(VMLINUZ · INITRAMFS · MODLOOP · AGENT)은 교체 폼 · 버전 이력 · 행별 되돌리기를 상세에서 제공한다. 비교체 2슬롯(APKOVL · REPO)의 상세는 읽기전용이며 빌드 스크립트 안내만 둔다.
  3. 봉인(seal-all)은 설정으로 — 6슬롯 마커를 일괄 기록하는 전역 mutation 이고, 비교체 2슬롯에는 seal-all 이 유일한 기준선 확립 수단이라 설정 카드가 자연스러운 집이다.
  4. 보존 개수는 별도 설정 폼 — 인라인 폼을 없애고 GET /settings 폼에서 고쳐 POST /settings 로 저장한다. retentionCount 는 @Min(1) @Max(20).
  5. redirect 규약 — 교체 · 롤백 성공은 redirect:/{slot}(상세 복귀), 봉인 · 보존 저장 성공은 redirect:/settings(self-PRG), 재검증은 redirect:/(대시보드 잔류).
  6. 서빙 비활성 UI 1차 차단 — 서빙이 꺼져 있으면 상세의 교체 · 되돌리기와 설정의 봉인 버튼을 disabled + tooltip 으로 막는다. 조건은 서버 가드 requireServingRoot()(409)와 단일 SSOT(servingActive / isServing()).
  7. 인라인 style 청산 + native confirm 미사용 — 재구성 전 dashboard.html 의 인라인 style 약 28곳을 페이지 CSS + 전역 클래스로 바꿨다. 롤백은 현재 활성본을 archive 하므로 가역이라 native confirm() 대신 버튼 title 경고로 안내한다.
비 목표 (의도적으로 제외) :
  • 서비스 계층 변경 — 활성화 · 롤백 · 버전 저장소 · 보존 설정은 b-1/b-2 백엔드에서 이미 결정 · 구현됐다. 이번엔 배선만 다시 했다.
  • dhcpd · tftp 등 PXE 인프라 자산 화면 — E1-I-3.
  • 활성화 코어의 SPI 일반화 — dhcpd/tftp 구현자가 실재하는 E1-I-3 이후 단계 신설 없는 리팩토링(R* 계열)으로 미룬다.
🎬 미리보기 — 3화면을 실제로 오가며 확인

아래 위젯 하나에 대시보드 · 상세 · 설정 세 화면이 들어 있고, 한 번에 한 화면만 보입니다. 대시보드의 자산 행을 클릭하면 그 자산 상세로, 운영 설정 → 로 설정 화면으로 갑니다. 상세에서 교체 · 되돌리기, 설정에서 보존 개수 · 전 슬롯 봉인을 눌러 결과를 보세요. 공유 상태 하나(서빙 · 보존 개수 · 슬롯별 활성본/이력/무결성)를 세 화면이 함께 읽습니다. 판정 로직(FIFO 정리 · 롤백 승격·제거 · 서빙 게이트)은 서버 구현과 1:1 입니다.

전역 서빙 : 현재 화면 : 대시보드

표기 주의 : 미리보기의 버전 #N 은 어느 바이트인지 눈으로 따라가기 쉽게 붙인 미리보기 전용 라벨이며, 실제 화면에는 세대 번호가 없습니다. 실제 상세는 버전을 아카이브 시각 · 크기 · 해시로 표시하고(AssetVersionView), 식별 키는 재사용되지 않는 자동 증가 asset_version.id 입니다. 미리보기의 번호도 같은 성질을 따르도록 단조 증가시켜 롤백 뒤에도 번호를 재사용하지 않습니다.

위젯 캡션 : 대시보드에는 상태를 바꾸는 버튼이 없습니다. 교체 · 롤백은 각 자산 상세에서, 봉인 · 보존 개수는 설정에서 합니다. 서빙을 비활성으로 바꾸면 상세의 교체 · 되돌리기와 설정의 봉인 버튼이 disabled + tooltip 으로 막히는데(UI 1차 차단), 이 조건은 서버 requireServingRoot() 가드(409)와 같은 SSOT 입니다.

드리프트 0 — 미리보기 판정 = 서버 도메인 규칙. FIFO 정리 = versions.size > N → id 오름차순 (size−N)개 삭제 = 서버 AssetHistoryService.prune(). 롤백 불변식 = archive(현재) → 활성=X → remove(X) = 서버 DiagnosticAssetActivationService.rollback()(openVersion 이 temp 로 바이트를 먼저 실체화해 순서 안전). UI 버튼 disable = !servingActive = 서버 requireServingRoot() throw(409).

§4. 설계 결정 (채택 · 비채택 · 탈락 사유)

화면 3분할은 사용자 지시였다. 그 지시 아래에서 각 액션을 어느 화면에 두느냐, 상세 데이터를 어떻게 조회하느냐를 결정했다. 아래는 채택안과 탈락 대안, 탈락 사유다.

D1 · 재검증(recheck)은 대시보드 잔류
채택 재검증은 서비스를 호출하지 않고(GET 재렌더가 곧 재검증) 상태를 바꾸지 않는 현황 새로고침이라 status-only 대시보드에 속한다. redirect:/ 무변경.
탈락 설정으로 이동 — 재검증은 mutation 이 아니라 조회 갱신이라 전역 튜너블 화면에 둘 이유가 없다.

D2 · 봉인(seal-all)은 설정 페이지
채택 6슬롯 마커를 일괄 기록하는 전역 mutation 이라 status-only 대시보드에서 제거했다. per-slot 개념이 없어 상세로도 못 간다. 특히 비교체 2슬롯(apkovl · repo)은 교체 경로가 아예 없어 seal-all 이 유일한 기준선 확립 수단이므로 설정 페이지가 자연스러운 집이다. 봉인 후 redirect:/settings(self-PRG)로 카드의 okCount/total 이 새 값으로 피드백된다.
탈락 ⓐ 대시보드 잔류 — status-only 원칙 위배.
탈락 ⓑ per-slot seal(각 상세에서 봉인) — 초기 6슬롯 기준선을 세우려면 상세를 6번 순회하는 회귀 + 신규 엔드포인트 churn + 읽기전용 슬롯의 상세에 mutation 버튼을 놓는 의미 충돌이 생긴다.

D3 · replace / rollback 성공 redirect = /{slot}(상세 복귀)
채택 교체 · 롤백을 상세에서 개시하므로 직후 새 버전이 그 상세 이력에 뜨는 것이 자연스럽다(GuestServer 액션의 redirect:/{id} 선례와 동형). flash 메시지로 결과를 안내한다.
탈락 대시보드 복귀 — 상세에서 시작한 액션이 현황 화면으로 튕겨, 방금 만든 버전을 다시 상세로 들어가 확인해야 한다.

D4 · 상세 데이터 = 단건 조회 loadSlot (코드 리뷰로 계획 초과)
채택(최종) 상세는 loadSlot(slot) 로 단일 슬롯만 해시하고, listVersions(slot) 로 그 슬롯 이력만 읽으며, isServing() 으로 버튼 게이트 플래그를 얻는다. 세 조회 모두 단건이다.
탈락(초안 = 계획의 Detail-A) 상세 진입마다 loadDashboard() 로 6종 전량을 재해시한 뒤 key 로 1행을 필터. 대시보드가 이미 그렇게 하니 신규 회귀는 아니지만, 208MB 급 자산 6배를 매 상세 진입마다(행 클릭 · 교체/롤백 PRG 로 잦음) 재해시하는 낭비다.
전환 사유 적대적 코드 리뷰가 이 낭비를 Warning 으로 지적했다. 즉시 loadSlot · isServing · listVersions 단건 API 로 최적화했다. loadSlot 은 loadDashboard 가 쓰던 private 프리미티브(probe · verify · toResponse · offSlot)를 그대로 재사용해 entity-free 를 유지하고 로직 중복이 없다. 계획의 §비목표(loadSlot 이연)를 앞당겨 실현한 셈이다.

D5 · 대시보드 행 → 상세 = 행 전체 클릭
채택 행에 data-href 를 붙이고 document 위임 JS 로 행 전체 클릭 시 상세로 이동한다(provisioning/server-list.js 미러). 셀 내부의 링크 · 버튼 · 폼 클릭은 e.target.closest('a, button, input, form') 로 걸러 중복 내비게이션을 막는다. 별도 "상세 →" 앵커 셀은 두지 않는다.
탈락 명시적 링크 셀 — 이미 provisioning 영역이 행 전체 클릭 관례를 확립했고, 그 관례를 미러하는 편이 화면 간 일관성이 낫다. CP1 plan 의 Q2 는 열어 뒀으나 최종은 행 클릭으로 확정됐다.

D6 · 부수효과 (전부 준수)
채택 신규 예외 0(parseSlot 재사용, forging 404) · navbar 무변경(단일 "진단 자산" 링크 · active 키 유지) · integrityService entity-free 유지 · 인라인 style 약 28곳을 페이지 CSS + 전역 클래스로 청산 · 서빙 비활성 시 버튼 disabled(= servingActive/isServing 플래그로 서버 가드 409 와 SSOT) · native confirm() 미사용. /settings 리터럴이 /{slot} 보다 우선 매칭됨을 테스트로 고정.

③ 자산 상세 — 메타 + 교체 폼 + 버전 이력 + 롤백 승격

상세에 자산 메타(원본 유지)와 자산 교체 폼, 버전 이력표가 뜬다. 이력은 아카이브 시각 · 크기 · 짧은 해시 · 되돌리기 버튼으로 구성된다. 상세에서 롤백하면 현재 활성본이 이력으로 archive 되고, 고른 버전이 활성 파일로 앉으며(활성 파일 = 되돌린 버전), 그 버전은 이력에서 제거된다(승격). 활성 파일이 되돌린 세대로 바뀌고 asset_version 행 id 가 재배치됨을 DB 로 확인했다.

④ 운영 설정 — 보존 개수 + 무결성 봉인

대시보드의 운영 설정 → 로 설정 화면에 들어간다. 이력 보존 개수 폼(현재 적용 3개)과 무결성 봉인 카드(서빙 활성 · 무결성 4 / 6 · 전 슬롯 봉인 버튼)가 분리돼 있다. 보존 저장은 self-PRG(/settings), 봉인도 설정으로 PRG 되어 카드 값이 갱신된다.

검증 결론 — 3화면 네비게이션 · 롤백 승격 · 보존/봉인 · 서빙 게이트가 실환경에서 코드와 일치한다. loadSlot 최적화로 상세는 단일 슬롯만 해시하며, ddl-auto=validate 통과로 스키마 무변경이 확인된다.
