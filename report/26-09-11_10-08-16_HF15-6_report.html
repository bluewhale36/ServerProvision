§1. 무엇을 고쳤는가

게스트 서버 상세 화면의 PCIe 표는 진단 리눅스가 보낸 lspci 원문만으로 만들어진다. 그래서 보드에 붙박인 온보드 NIC 두 개와 운영자가 슬롯에 꽂은 카드가 같은 표에 같은 모양으로 섞였다 — 실기 4호(2026-09-10)에서 사용자가 지적한 지점이다. 어느 것이 추가 장착인지 화면만 보고는 가릴 수 없었다.

HF15-6 은 진단이 끝난 뒤 BMC 의 시스템 인벤토리를 한 번 더 읽어 장치마다 온보드 · 추가 장착 · 미확인 중 하나를 붙인다. 결과는 두 곳에 쓰인다 — 상세 화면의 새 "장착" 열, 그리고 목록을 묶는 스펙 그룹 키(온보드는 보드마다 같으므로 뺀다).

결과 — CP5 검증 항목 7 건 전부 기대대로 동작했고 기능 결함은 0 이었다. 대신 화면이 사실을 제대로 말하지 못하는 관찰 2 건(묶음 라벨 · 툴팁 문구)을 찾아 그 자리에서 정정하고 재검증 2 항목으로 확인했다. 테스트 3,135 green, DDL 0 · 환경변수 0.

조회가 실패해도 프로비저닝은 멈추지 않는다. BMC 가 아직 답할 준비가 안 되었으면 30 초 간격으로 다섯 번까지 다시 묻고, 끝내 못 받으면 "미확인" 으로 두고 원장에 실패를 남기지 않는다 — 장착 구분은 설치를 막을 근거가 아니기 때문이다.

§2. 진단 (실측 근거)

무엇이 섞였는가

진단 리눅스 에이전트는 lspci 원문을 그대로 보내고 서버 파서가 장치 클래스로 걸러 담는다. 온보드 Intel I210 두 개도 Ethernet 클래스라 SAS3008 같은 추가 장착 카드와 나란히 담긴다. 원문에는 "보드에 붙박여 있다" 는 사실이 아예 없으므로 파서를 고쳐서는 구분이 나오지 않는다.

BMC 가 그 사실을 갖고 있다 (2026-09-10 HAR · E0-3 계열)

BMC 웹 API GET /api/system_inventory_gbt/pci_info 는 장치마다 다음을 준다. 로그인(POST /api/session)과 세션 헤더는 기존 AmiWebClient 가 이미 구현해 둔 경로다.

필드예시쓰임
hexBusNumber"0x00AE"lspci 슬롯의 버스 번호
hexDeviceNum"0x0000"lspci 슬롯의 장치 번호
iOnBoard0 / 1판정 축 — 온보드 여부
strSlotDesignation"PCIE_1" / "Onboard"추가 장착일 때 보드에 인쇄된 표기

lspci 의 ae:00.0 은 버스 0xAE · 장치 0 · 기능 0 이라 버스 + 장치 번호 로 BMC 항목과 1:1 로 이어진다. 기능 번호는 키에 넣지 않는다 — 듀얼 포트 NIC 의 .0 과 .1 은 같은 카드의 포트이므로 같은 태그를 받아야 한다.

제약 (사용자 실측) — 이 조회는 BMC 최초 접속 뒤 일정 조건이 차기 전에는 오류를 낸다. 즉시 실패로 다루면 정상 장비가 실패로 기록된다 — 재시도가 요건이 된 이유다.
사용자 결정 (2026-09-11) — 온보드 장치는 같은 보드 모델이면 언제나 같다. 그러므로 스펙 그룹 키에서 빼도 같은 하드웨어가 갈리지 않는다.

§4. 강제 장치 (테스트)

이 슬라이스는 신규 HTTP 엔드포인트가 0 이다 — 아웃바운드 조회와 내부 이벤트로만 이루어져 있다. 그래서 검증 부담이 단위 테스트와 CP5 로 옮겨간다. 아래 단위 14 건과 §5∼§7 의 항목이 실제 그물이다.

통합 테스트 4 범주 — 전부 해당 없음. 성공 2xx · 400 · 404 · 409 · 500 모두 대상이 0 이다. 상세 화면은 경로 · 응답 구조가 바뀌지 않았고(회귀는 CP5 A1 · A2 가 본다), 사용자 입력 경로와 신규 조회 경로를 건드리지 않으며, 충돌 판정을 신설하지 않았다(낙관적 잠금 충돌은 사용자에게 노출되지 않고 다음 시도로 넘어간다). BMC 조회 실패는 요청 스레드 밖이라 500 으로 새지 않고 UNKNOWN 으로 수렴한다.

§6. CP5 수행 기록 (조작과 증거)

A1 — 태깅 전 표시

조작: MOCK_BMC_IP 를 빼고 게스트 …0602 를 등록 · 진단했다(lspci 4 행). BMC 접점이 없으므로 보강기가 깨어날 신호 자체가 없는 상태다.
결과: PCIe 표 4 행 모두 "장착" 열이 — 였고, DOM 을 직접 읽어 네 행 전부에 title 툴팁이 붙어 있음을 확인했다. DB 도 bmc_ip = NULL · mount 네 개 모두 UNKNOWN. 앱 로그의 [pcie-mount] 줄은 진단 전후로 한 줄도 늘지 않았다 — BmcEndpointDiscoveredEvent 가 없으면 보강기가 깨어나지 않는다는 설계 그대로다.

A2 — 태깅 성공

조작: 모의 BMC 를 붙여 태깅이 끝난 게스트 01a08ddf…(…0601) 상세를 열고, 화면 표기 · DB 저장본 · 앱 로그 · 모의 BMC 카운터를 대조했다.
결과: 기대한 세 표기가 모두 나왔다 — ae:00.0 은 mono PCIE_1, 34:00.0 · 35:00.0 은 회색 배지 "온보드", BMC 목록에 없는 01:00.0 은 —. DB 저장 형태도 ADD_IN/PCIE_1 · ONBOARD/null ×2 · UNKNOWN/null 로 일치해, "온보드는 슬롯 표기를 갖지 않는다" 는 규칙이 저장본에서 지켜졌다. 앱 로그는 장착 구분 반영(시도 1) 한 줄, 모의 BMC 카운터는 logins=1 · pciInfoGets=1 · logouts=1 — 한 번 열고 한 번 읽고 한 번 닫는다(세션을 열어 둔 채 끝내지 않는다).

A3 — 온보드 제외 그룹 키 계획 조정

조작: 원안(기존 태깅 게스트와 새 게스트를 같은 묶음으로)은 그대로는 관찰할 수 없었다. 목록의 묶음이 스펙만이 아니라 등록 시각 구간 × 스펙 2 단 구조라(1 시간 안은 1 분 눈금), 등록 시각이 12 분 벌어진 두 게스트는 스펙과 무관하게 다른 칸에 놓이기 때문이다. 그래서 같은 분 안에 3 대를 연달아 등록해 시각 구간을 맞췄다 — BMC 있는 2 대(…0607 · …0608)와 BMC 없는 1 대(…0609).
결과: 태깅된 2 대가 한 묶음, 미태깅 1 대가 따로 갈렸다. 온보드 2 장이 키에서 빠진 쪽끼리 묶이고 온보드가 키에 남은 쪽은 갈라진 것으로, plan §8 이 "설계대로 · 과도기 현상" 으로 못박은 비대칭이 그대로 나타났다. 다만 화면이 그 이유를 전혀 말해 주지 않았다(§9 관찰 O-1 → 정정 → §7 R2).

B1 — BMC 미준비 · 5 회 재시도 뒤 포기
