§1. 슬라이스 개요

U3(세팅 정의서 → 게스트 할당)의 하위인 U3-2 를 2분할한 첫 슬라이스다. U3-2-a = 재할당(supersede-then-new) + 미소비 supersede 행 지연 purge reaper(화면 없는 DB 전용 정리 작업).

U3-1(할당 core)은 재할당 · 대체 이력에 쓰려고 훅을 미리 정의만 해두고 아무도 부르지 않는 상태로 남겼다 — 도메인 메서드 SettingAssignment.supersede(), 상태 값 AssignmentState.SUPERSEDED, 그리고 활성 스냅샷을 가리는 술어 supersededAt IS NULL 이다. U3-2-a 는 이 셋을 실제 흐름에 연결한다.

이 슬라이스가 여는 것

  • 재할당 — 아직 프로비저닝을 개시하지 않은 게스트라면, 할당된 정의서를 다른 정의서로 바꿀 수 있다. 기존 할당은 그 자리에서 supersede(대체)로 이력 종료하고, 지금 정의서 내용으로 새 스냅샷을 만들어 활성 할당으로 세운다.
  • 지연 purge — 재할당으로 대체됐지만 한 번도 소비되지 않은 supersede 스냅샷은 실행에 다시 쓰일 일이 없다. 이런 행만 TTL 경과 후 스케줄러가 hard-delete 로 수거하고, 소비된 이력 · 활성 할당은 절대 건드리지 않는다.
후속 슬라이스
  • U3-2-b(형제, 별도 CP1) — 원본 정의서 삭제 lifecycle. 세팅 정의서 자체를 지울 때 그 정의서를 할당한 게스트가 있으면 어떻게 처리할지. setting ↔ assignment 순환은 AssignmentUsageInspector Service Provider Interface(도메인이 구현해 끼우는 확장점, 이하 SPI)로 회피할 계획.

활성 유일성 — DB 강제 (DA2)

"한 게스트에 활성 할당은 최대 1개"라는 불변식을 서비스 가드에만 맡기지 않고 MariaDB PERSISTENT generated-column + UNIQUE 제약(uk_active_assignment_per_guest)으로 DB 가 강제한다. generated-column(active_guest_id)은 활성 행에만 게스트 식별자 값이 채워지고 대체된 행에서는 NULL 이라, UNIQUE 가 게스트당 활성 1개를 물리적으로 보장한다. 서비스 계층 가드는 없앤 것이 아니라, 사용자에게 친절한 409 를 주기 위한 UX 용으로 유지한다.

샌드박스 구성

Docker MariaDB(포트 3307) + bootJar(포트 7788, ddl-auto=update) + Chrome 브라우저 자동화. Hibernate 가 생성한 setting_assignment 테이블(게스트 식별자 컬럼은 MariaDB 네이티브 uuid 타입) 위에 ddl/U3-2-a_active_uniqueness.sql 을 수동 적용했다. ddl-auto=update 는 JPA 가 매핑하지 않은 generated-column 을 만들지 않으므로, 이 수동 적용이 DA2 를 실환경처럼 검증하는 핵심이다. 시드: board_model(GIGABYTE / MS03-CE0) · 세팅 정의서 2종(A · B) · /boot 로 게스트 등록.

샌드박스 착수 중 실측 정정 3건 (참고 — U3-2-a 결함 아님) — 정상 흐름을 못 찾다가 코드를 읽어 해결한 게스트 등록 규약 관련 사항이다.
  • docker exec 에 -i 누락으로 heredoc 시드가 stdin 으로 전달되지 않음 → -i 로 해결.
  • /boot 의 vendor 파라미터는 enum 이름("GIGABYTE")이 아니라 Vendor.ipxeName("Giga Computing")으로 매칭 — VendorNotFoundException(404)를 겪고 Vendor.java 를 읽어 정정.

수행 · 증거 (정상 + 비정상 각각)

V1 · V4 — 정상 재할당. 브라우저에서 정의서 A 를 할당(스크린샷 2)한 뒤 B 로 재할당(스크린샷 3)했다. DB 결과: A → SUPERSEDED(active_guest_id NULL) · B → ACTIVE(active_guest_id = guest) · 활성 행 1개. 앱 로그 reassigned … superseded=1 new=2 … status=200. DA2 generated-column 이 활성 행에만 값을 채우는 것을 확인. DDL 이 적용된 샌드박스에서 status 200 · UNIQUE 위반 0 · 활성 1개 — 아래 결함 수정이 실제로 작동함을 여기서 확인했다.

V2 — 개시 후 차단. "프로비저닝 개시"를 클릭해 B 를 소비(markConsumed, status 302)한 뒤 재렌더하면, 재할당 버튼이 disabled "재할당 (차단됨)" + 사유 텍스트로 바뀐다(스크린샷 4, UI 1차 차단). 이어 UI 를 우회한 direct POST(curl)로 재할당을 시도하면 409 {"message":"이미 개시되어 재할당할 수 없습니다(회수 후 재등록 필요) guestId=…"} (ReassignAfterStartException) — 메시지가 reassignBlockReason SSOT 와 동일하다(가드와 뷰가 같은 소스).

V3 — 활성 없음. 활성 할당이 없는 게스트에 direct POST 로 재할당을 시도하면 409 {"message":"재할당할 활성 세팅 정의서 할당이 없습니다. guestId=…"} (NoActiveAssignmentToReassignException).

V5 — reaper 선별 수거. id=1(A, SUPERSEDED 미소비)의 superseded_at 을 47시간 전으로 backdate 하고, 대조군으로 합성 소비 이력 행(id=3, SUPERSEDED 소비 47h)을 삽입했다. :45 cron 발동 로그 [assignment-reaper] 미소비 supersede 스냅샷 1 건 수거(hard-delete). ttl=PT24H. 결과: id=1 삭제 · id=2(ACTIVE) 보존 · id=3(소비 이력) 보존 — 술어 SUPERSEDED ∧ 미소비 ∧ TTL 경과 의 선별성을 실제로 확인.

검증 중 발견 · 수정한 결함 — 재할당 flush 순서 (CP1 급, 숨기지 않음)

결함 — AssignmentCommandService.reassign() 이 active.supersede(now) 직후 곧바로 새 스냅샷을 save 했다. Hibernate 는 flush 시 INSERT 를 UPDATE 보다 먼저 실행하고 (IDENTITY 전략이라 save 가 즉시 INSERT), 그러면 새 활성 행이 INSERT(active_guest_id = guest)되는 순간 기존 행이 아직 active_guest_id = guest 라서 uk_active_assignment_per_guest(DA2)를 위반한다. Mockito 단위 · slice 테스트는 실 DB 제약이 없어 green 이라 못 잡고, 실 MariaDB + DDL 적용 시에만 터진다.

수정 — supersede 후 assignmentRepository.flush() 를 넣어 UPDATE(active_guest_id → NULL)를 새 행 INSERT 전에 DB 에 먼저 반영했다. 원자성은 같은 @Transactional 이라 유지된다(이후 실패 시 함께 롤백).

재검증 — CP5 의 V1 · V4 에서 DDL 이 적용된 샌드박스에 재할당 → status 200 · UNIQUE 위반 0 · 활성 1개로 확인. 수정이 없었다면 이 지점이 duplicate-key 500 이었을 것이다.

불가침 원칙 점검

  • Primitive Obsession — 게스트 식별자는 UUID, 차단 사유는 도메인 메서드 reassignBlockReason() 로 표현하며 원시 boolean 플래그 복붙을 두지 않았다. TTL 은 Duration(PT24H) 로 다룬다.
  • 네이밍 — *Service / *Repository / *Request / *Response / *Exception 접미사 준수(요청 DTO 에 DTO 접미사 없음).
  • 레이어 경계 — controller ↔ service 는 DTO(재할당 JSON), service ↔ repository 는 엔티티. @Transactional 은 service 경계(reassign() supersede + save 원자 실행).
  • 조건분기 확장 금지 · UI 1차 차단 — 개시 후 재할당은 UI 가 disabled + tooltip 으로 먼저 막고 (reassignBlockReason() SSOT), 서버 가드는 direct POST · 동시성 같은 비정상 경로의 409 안전망으로만 발동.
  • DB 불변식 — 활성 유일성을 서비스 가드 + DB UNIQUE 이중으로 강제(DA2), 실 DB 에서만 드러나는 flush 결함을 CP5 에서 포착.
