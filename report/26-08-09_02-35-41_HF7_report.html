§1. 무엇을 고쳤는가

비활성(disabled) 버튼에 마우스를 올리면 활성 색으로 되돌아가, 누를 수 있는 것처럼 보이던 횡단 CSS 결함을 고쳤다. .n-btn 계열 hover 선택자 11 개에 :not(:disabled):not(.n-btn-disabled) 가드를 달아 차단했다. 순수 CSS 1 파일 수정이며 마크업 · 스크립트 변경은 없다.

이 보고서는 간소본이다. 사용자 지시에 따른 빠른 트랙으로, 절 순서는 표준 report 골격을 유지하되 분량을 줄였다. 해당 없는 절은 사유와 함께 한 줄로 닫는다.
§2. 진단

S11-1 의 CP5 검증 중 발견했다(그 report §8 발견 1, 스크린샷 C2b). 비활성 상태를 확인하려고 버튼에 마우스를 올린 순간 색이 되돌아온 것이 단서였다.

static/global/style.css 에서 .n-btn:disabled 의 중립 회색 정규화 규칙과 flavor 별 :hover 규칙의 명시도가 (0,2,0) 으로 동률이고, hover 쪽이 뒤에 오므로 캐스케이드에서 이긴다. danger 계열만 :hover:not(:disabled) 가드를 갖고 있어 이 문제가 없었다 — 고치는 방법은 이미 코드 안에 있었고 나머지 flavor 에만 빠져 있었다.

링크형 비활성인 a.n-btn.n-btn-disabled(provisioning 템플릿 2 곳 실사용)도 같은 동률 구조다.

왜 핫픽스인가 : 이 프로젝트는 "UX 모순은 UI 가 1차 차단한다" 를 불가침으로 두고, 그 차단을 사용자에게 알리는 수단이 disabled 의 시각 신호다. hover 에서 신호가 사라지면 차단은 유효한데 차단으로 보이지 않는 상태가 되어 원칙의 실효를 깎는다.
§3. 구현

이전

.n-btn-primary:hover {
  background: var(--n-blue-hover);
}

이후

.n-btn-primary:hover:not(:disabled)
  :not(.n-btn-disabled) {
  background: var(--n-blue-hover);
}
대상처리
primary · secondary · ghost · info · warning · success · outline-success · outline-danger · outline-info · outline-warning가드 신설 10 개
danger보강 기존 :not(:disabled) 에 .n-btn-disabled 제외 추가
레거시 .btn-* 계열불변 템플릿 사용 0 건이라 손대지 않음

disabled 정규화 규칙의 주석에 재발 방지 문구를 병기했다 — 명시도 동률의 기전을 설명하고 "새 flavor 의 hover 규칙을 추가할 때 반드시 같은 가드를 단다" 를 남겼다. 다음 사람이 hover 규칙을 추가할 때 바로 위에서 읽게 되는 자리다.

대안 비교와 탈락 사유(규칙 순서 이동 · !important)는 plan(plan/26-08-09_02-27-03_HF7_plan.html) §8 에 있다.

§4. 강제 장치

해당 없음 — CSS 캐스케이드는 JUnit 의 검증 대상 밖이라 테스트 코드를 만들 수 없다. 재발 방지는 ① §3 의 disabled 규칙 경고 주석 ② plan 의 종전 · 수정 CSS 대조 체험 데모가 대신 담당한다.

§6. CP5 수행 기록

V1 — 비활성 버튼 hover (핵심 항목)

조작: 닫힌 드리프트(드리프트 12, 해결됨)의 비활성 [해결] 버튼에 실제 커서를 올린 채 캡처했다.
확인: 스크린샷만으로는 hover 가 등록됐는지 알 수 없으므로 DOM 으로 교차 확인했다. 커서 아래 요소가 BUTTON.n-btn.n-btn-primary · disabled=true · matches(':hover')=true 인 상태에서 계산 배경색이 rgba(0, 0, 0, 0.1)(회색)로 유지됐다. primary 파란색 rgb(0, 117, 222) 로의 복귀는 없다. 서빙 중인 CSS 에 가드가 실려 있음을 curl 로 확인해, 관측된 회색 유지가 이 수정 덕임을 귀속 확정했다.

V2 — 활성 버튼 hover (부작용 없음)

조작: 활성 상태인 [지금 점검] 버튼에 hover.
확인: hover 전 rgb(0, 117, 222) → hover 중 rgb(0, 91, 171) 로 정상 변화했다. 가드가 정상 hover 까지 죽이지 않았음을 확인한 것이며, 이 항목이 없으면 "hover 를 전부 없애 버린" 수정과 구분되지 않는다.

V3 — 링크형 비활성 hover (이중 합성)

조작: provisioning 실데이터가 없어 링크형 비활성 요소를 합성 삽입했다. 그런데 .n-btn-disabled 의 계산값이 pointer-events: none 이라 커서가 요소에 닿지 못했다. CSS 가드만 분리해 시험하려고 인라인 pointer-events: auto 로 덮어쓴 뒤 hover 했다.
확인: matches(':hover')=true 상태에서 회색이 유지됐고, 옆의 활성 링크는 파란색으로 대조됐다. 검증 후 삽입한 요소를 제거했으며 클릭은 0 회다.

이 항목은 이중 합성이다. 요소 자체를 만들어 넣었고, 그 위에 pointer-events 까지 덮어썼다. 따라서 실화면에서 일어난 일이 아니라 가드 규칙이 작동한다는 사실만 보인 것이다. 근거의 강도가 V1 · V2 와 다르므로 구분해 읽어야 한다.

제약내용
V3 의 근거 강도실화면이 아니라 이중 합성 검증이다(§6). 링크형 비활성이 실제로 쓰이는 provisioning 화면에서의 확인은 CP7 로 넘어간다.
부수 상태 변화애플리케이션 기동 시 자동 점검이 1 회 돌아 스캔 이력 1 행이 추가됐다(탐지 5 건). 재현 상태가 보존됐는지 확인한 데 따른 부수 효과이며, 드리프트 해결 상태는 무변경이다.
§8. 검증 중 발견한 것

링크형 .n-btn-disabled 는 pointer-events: none 이라 hover 규칙 자체가 도달하지 못한다. 즉 링크형에서 이번 CSS 가드는 1차 방어선이 아니라 2차 방어선이다.

반면 실제 button[disabled] 는 pointer-events: auto 여서 hover 가 도달한다. 원래 증상이 버튼에서만 파란색 복귀로 드러난 이유가 여기에 있다 — 결함의 형태를 설명해 주는 부수 발견이다.

조치 불요 : 현행 동작이 이미 안전한 방향(링크형은 애초에 hover 가 닿지 않음)이므로 추가 수정 없이 그대로 둔다.
