§1. 무엇이 문제였나
한 줄 요약 : 중복 확인 창에서 이름과 버전이 같은 휴지통 후보 둘이 똑같이 보여 어느 쪽을 영구 삭제할지 고를 수 없었습니다. 후보 줄 보조 글자에 휴지통 이동 시각을 늘 함께 보이고, 긴 경로는 상자 안에서 접히고 시각은 한 덩어리로 서게 고쳤습니다. 출처: HF30-4 CP5 관찰 O-1, 디자인 세션(SPV_Design) 판정 두 차례.
  • 자원(BIOS · BMC · 드라이버 · ISO)을 등록할 때 같은 자원이 휴지통에 있으면 중복 확인 창이 뜨고, 후보를 골라 [기존 영구 삭제 후 등록] 할 수 있습니다.
  • HF30-4 CP5 에서 같은 BIOS R01 을 두 번 등록 · 삭제하자 창에 MZ73 BIOS R01 (휴지통) 두 줄이 똑같이 나왔습니다. 줄 이름은 자원명 입력이 맞춰야 하는 displayName 이라 두 후보가 같은 글자입니다. 그래서 자원명 입력도 둘을 구별해 주지 못합니다.
  • 서버 응답(NudgeConflictEntry)에는 시각 필드 registeredAt 이 있었지만 응답을 만든 순간(Instant.now())이라 후보마다 같은 값이고, 화면도 쓰지 않았습니다.
  • 디자인 세션 판정: "보조 글자에 '휴지통 이동 시각' 을 더한다. 서버 응답 변경이 필요하므로 후속 단계." 늘 보이고(조건부 아님), 휴지통 목록과 같은 시각 형식, ISO 는 경로를 유지하고 시각을 뒤에 붙입니다.
  • 휴지통 목록(/maintenance/trash)은 같은 자원을 이동 시각 열(trashedAt, yyyy-MM-dd HH:mm:ss)로 구별합니다. 이 값은 모든 자원 엔티티의 공통 부모 LifecycleEntity 에 MK3 부터 있습니다(DDL 불요).

§6. 미수행 항목과 사유
  • BMC · 드라이버 등록 화면의 창은 보지 않았습니다. 같은 NudgeConflictEntry.of 와 같은 창 JS 를 쓰고, 컨트롤러 테스트가 응답을 덮습니다.
  • 1024 폭은 보지 않았습니다. 창 카드는 고정 폭이고 계획이 1400 · 390 을 요구했습니다.
  • O-1 의 두 번째 창에서 등록을 끝까지 하지 않았습니다(이번 변경과 무관한 흐름).
  • scripts/design-audit/ 의 node 스캐너는 URL 을 열기만 해서 조작 뒤에 뜨는 창을 보지 못합니다. 같은 판정 함수를 창 카드 범위로 좁혀 하네스 안에서 돌렸습니다(HF30-4 선례).
  • 첫 CP5 의 390 폭(A4)은 BIOS 후보만 봤습니다. ISO 390 폭의 경로 잘림은 디자인 세션이 찾았고 재검증 R2 에서 메웠습니다.
