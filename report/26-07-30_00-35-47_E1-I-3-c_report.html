§1. 무엇을 했나 — 관측(b)에서 쓰기(c)로

E1-I-3 은 "프로비저닝 서버가 PXE 부팅에 쓰는 dhcpd(DHCP 서버) 구성을 관리 화면에서 다룬다"는 우산 작업이고, c 는 그 마지막 조각이다. 앞선 b 는 dhcpd 상태를 관측만 했다(읽기 대시보드, 신규 예외 0). c 는 쓴다 — 관리자가 폼에 서브넷·리스풀·라우터·DNS·부트 서버를 입력하면 앱이 그 값을 dhcpd 가 읽는 설정 조각 파일로 렌더해 실제로 반영한다.

쓰기가 되면서 실제로 생긴 실패 모드

  • 렌더한 조각이 문법 오류일 수 있다 → dhcpd 문법 검사(dhcpd -t)가 거절한다.
  • 반영 후 dhcpd 재기동이 실패할 수 있다.
  • 실패해서 이전 조각으로 되돌리는 것마저 실패할 수 있다.
핵심 설계 난제 — 이중 쓰기(dual-write)
DB 의 PxeNetworkConfig 1행은 @Transactional 로 롤백되지만, 조각 파일 쓰기(파일시스템)와 systemctl restart(외부 명령)는 트랜잭션이 아니다. 이 셋을 잘못 엮으면 "화면(DB)은 새 구성인데 dhcpd(파일시스템)는 옛 구성" 같은 괴리가 생긴다. c 설계의 절반은 그 괴리를 어떻게 없애느냐였고, 그 답이 §2 의 파이프라인 순서다.
결과 — 관리자가 폼을 저장하면 조각을 원자적으로 교체하고 dhcpd -t 게이트를 통과할 때만 재기동하며, 재기동·검증이 실패하면 이전 조각으로 자동 복원한다. 성공이든 실패든 마지막 귀결을 DB 한 행에 남겨 화면이 "저장된 desired 와 지금 서빙 중인 조각이 갈렸는지"를 설명한다. 전체 테스트 스위트는 1521건 통과(신규 58건)이며, 실 Rocky Linux 재기동·include 반영을 확인하는 T3 검증(CP5)만 사용자 합동으로 남겨 두었다.
§2. 설계 실현 (결정 D1~D12)

CP1 에서 확정한 결정 D1~D12 가 커밋 4c0fdd5 에 그대로 구현됐다. 축별로 무엇을 했는지 정리한다.

파이프라인 · 이중 쓰기 해소 (D1 · D2 · D3)

DhcpdConfigApplyService(트랜잭션 없음 + ReentrantLock)가 렌더 → temp → 원자 교체 → dhcpd -t 게이트 → 재기동 → 검증 → (실패 시) 자동 복원을 수행해 ApplyOutcome 만 반환한다. 그 뒤 PxeNetworkConfigService(이 슬라이스의 유일한 @Transactional)가 desired + appliedResult + appliedVersionId + appliedAt 를 1회 종단 커밋 한다. DB 쓰기가 파일시스템·명령 파이프라인의 귀결(복원 포함) 뒤에 오므로 2단계 커밋(2PC, two-phase commit)·saga·보상 트랜잭션이 없다 — DB 는 조율자가 아니라 이미 귀결된 결과의 기록자다.

왜 throwIfNotApplied() 를 트랜잭션 밖에서 부르나(D3) — 트랜잭션 안에서 던지면 RuntimeException 이 프록시 경계를 뚫어 방금 기록한 REJECTED 행을 롤백 시킨다. 그래서 실패도 커밋으로 남긴 뒤(D2), 락·트랜잭션 밖 컨트롤러에서 승격한다. 이렇게 남긴 실패 기록이 화면의 "DB(desired) vs FS(옛 조각 서빙 중)" 괴리 설명을 가능하게 한다.

판정 SSOT · 예외 (D8)

적용 귀결의 판정 SSOT 는 ApplyResult enum 네 상수({APPLIED / REJECTED / ROLLED_BACK / RESTORE_FAILED})다. 각 상수가 method-per-constant(상수별 메서드)로 "적용 안 됨을 어떤 예외로 알릴지"를 스스로 안다 — switch/if-else 분기가 없다. 신규 예외 3종은 전부 DomainException 을 상속하므로, 기존 WebExceptionHandler.handleDomain 이 @ResponseStatus 유무만으로 400/500 을 매핑한다. 신규 advice 0 · 컨트롤러 try/catch 0.

게이트 dhcpd -t (D4)

관측용 DhcpdConfigInspector 를 재사용하지 않고 SystemCommandRunner.run(DHCPD_SYNTAX_CHECK, dhcpdConf) 를 직접 소비한다. 두 가지 때문이다 — (a) dhcpd -t 원문(stdout·stderr)을 REJECTED 메시지에 그대로 실어 화면에 노출하려고, (b) COMPLETED & exit≠0 은 REJECTED(400 사용자 입력 오류)로, NOT_FOUND/TIMED_OUT 은 게이트 실행 불능(500 인프라)으로 구분하려고. 게이트는 조각 단독이 아니라 원자 교체 후 dhcpd 가 실제 로드하는 dhcpd.conf 전체 트리에 실행하므로, 조각 단독 검증이 못 잡는 교차 선언 충돌까지 포착한다.

원자 교체 · 복원 (D5 · D7)

진단 자산 활성화가 쓰던 원자 스왑 3단(현재본 archive → ATOMIC_MOVE → 권한)을 AtomicAssetSwap(global/asset 무상태 부품)으로 추출·일반화했다. 복원은 materialize-then-move — archive 바이트를 복사해 temp 로 만든 뒤 ATOMIC_MOVE 하고, 이력 파일 자체는 move 하지 않는다(다른 파일시스템 간 이동 실패·dangling 이력 방지). 최초 적용에서 실패하면(이전본 없음) 조각을 삭제하지 않고 주석만 있는 유효한 빈 조각을 쓴다 — include 가 dangling 되어 dhcpd 가 재기동 불능이 되는 것을 막기 위함이다.

엔티티 · 검증 (D10 · D12)

PxeNetworkConfig(단일행, BaseTimeEntity 상속)에 신규 Value Object(값 객체) SubnetCidr·LeaseSeconds 를 더하고 IpAddressVO 를 재사용한다. 검증 술어의 SSOT 는 SubnetCidr 의 containsRange/netmask 로, 클래스레벨 제약 @ValidPxeNetworkConfig(400 필드에러)와 정적 팩토리 PxeNetworkConfig.create() 의 if-throw 안전망이 같은 술어를 호출한다. 잘못된 CIDR/range·IPv6 입력은 예외가 아니라 @Valid + BindingResult 필드에러로 떨어진다.

렌더러 (D11)

DhcpdConfigRenderer.render(PxeNetworkConfig):String 은 순수 함수다(IO·throws 0). 같은 입력이면 항상 바이트 단위로 같은 조각을 낸다 — 정적 머리말, 리터럴로 고정한 삽입 순서, prefix → dotted netmask 결정 변환, 항상 trailing newline, secondaryDns/domainName 유무 4조합 분기가 그 결정성을 지킨다. 부트 로더 파일명 filename "ipxe.efi" 는 자산 계약 상수로 한 곳에 두었다(T3 보정 대상).

동시성 · 명령 (D6 · D9)

ReentrantLock 이 apply() 와 persist() 를 함께 감싸 last-writer 괴리를 차단한다 (단일 프로세스·단일 행이라 @Version 낙관적 락은 거짓 안심이라 두지 않았다). 외부 명령 화이트리스트에 DHCPD_SERVICE_RESTART 를 추가했고, 타임아웃은 20초다 (dhcpd -t 의 3초를 답습하지 않는다 — 재기동은 더 오래 걸린다). DNS 는 primary(필수) + secondary(nullable) 2필드다(E1). SELinux 는 disabled 전제라 restorecon·보안 컨텍스트 복원 명령·sudoers·단계가 전무하다(E3).

§4. 도메인 모델 (SSOT)

extends BaseTimeEntity(id·created·updated 만). 자원이 아니라 구성 1행이므로 lifecycle·marker 는 상속하지 않는다. Repository = findFirstByOrderByIdAsc()(단일행 조회). 최초 삽입 방어는 서비스 계층 조회 + 프로세스 락으로 하고 @Version 은 두지 않았다(단일 프로세스·단일 행이라 낙관적 락 충돌 지점이 없다).

Primitive Obsession(원시값 집착) 차단 — VO / Enum

MAC/IP/버전/CIDR/리스 시간처럼 도메인 의미가 있는 값은 모두 Value Object 또는 Enum 으로 타입화했다. 원시 String mac/int seconds 를 엔티티 필드·서비스 시그니처·Request/Response 어디에도 노출하지 않는다.

record SubnetCidr(String value) {          // 신규 — 교차불변·파생의 SSOT
    boolean contains(IpAddressVO ip);      // range ⊆ subnet 검사
    boolean containsRange(IpAddressVO start, IpAddressVO end);
    String  netmask();                     // prefix → dotted netmask (결정적 순수 함수)
    String  networkAddress();              // 렌더러의 subnet 선언에 사용
}
record LeaseSeconds(long value) {          // 신규 — 양수 가드
    static LeaseSeconds of(long v);        // v ≤ 0 → IllegalArgumentException
}
enum ApplyResult { APPLIED, REJECTED, ROLLED_BACK, RESTORE_FAILED }  // 판정 SSOT (method-per-constant)

SubnetCidr·LeaseSeconds ↔ DB 는 각각 SubnetCidrConverter·LeaseSecondsConverter(@Converter(autoApply=false)) 로 매핑하고, IpAddressVO/IpAddressConverter 는 재사용한다.

검증 술어의 단일 SSOT (D12) — 클래스레벨 @ValidPxeNetworkConfig(400 필드에러) 와 정적 팩토리 PxeNetworkConfig.create()/updateDesired() 의 서버 안전망 if-throw 가 같은 SubnetCidr 술어(containsRange/contains)와 LeaseSeconds 비교를 호출한다. UI 1차 차단(Validator)과 서버 가드(if-throw)가 한 소스를 공유하므로 drift 가 없다.
