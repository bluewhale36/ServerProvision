§1. 진단
실기 전 보고 : 이 보고서는 실기 검증 전에 쓴 것이다. 코드 정정과 테스트는 끝났고, 실기 확인(§4)은 사용자 일정으로 아직 하지 못했다(2026-11-16). HF 규약상 해결 확인은 실기에서 한다.

E2.5 이후 프로비저닝 도중 부트 순서가 바뀌어 게스트가 UEFI 셸에 떨어지는 결함이 이어졌다. 그동안 다섯 번 정정했지만(E2.5 의 Once, HF15-1 의 Continuous, HF17 의 Once 회귀와 4 분 재무장, HF19 의 FBO 강제 보류, HF20 의 BootOrder 정착) 결함은 계속됐다.

기록된 순서 변화는 모두 오버라이드(Once, Continuous)나 재무장이 걸린 동안 일어났고, 오버라이드가 없을 때는 순서가 유지됐다(10-26 실측: 오버라이드 없는 POST 3/3 유지). PXE 서버를 도입하기 전의 기존 공정에서는 순서 변경이 없었다(사용자 확인, 11-16). 빈 서버는 공장 순서(디스크, CD/DVD, USB, 네트워크, 셸)에서 빈 디스크를 건너뛰어 네트워크로 부팅한다.

그래서 결론은 엔진의 순서 장치를 빼는 것이다. 상세 근거는 plan §2 의 실측 표와 discussion/26-11-16_12-58-38_HF24-observe-recover_discussion.md 에, 용어 정의는 discussion/26-11-16_13-13-45_HF24-boot-order-terms.md 에 있다.

2-2. 삭제한 클래스

일곱 개를 지웠다. 모두 이번 정정 뒤 쓰는 곳이 없어진 클래스다.

  • NextBoot, BootOverrideOutcome, BootOrderPolicy, BootEntries, RebootDirectiveArmer, BootOrderSettlement
  • ProvisioningCompletedEvent: HF20 이 BootOrderSettlement 에 종단을 알리려고 만든 이벤트다. 받는 곳이 그것 하나뿐이라 함께 지우고, PhaseCursorAdvancer 의 발행과 ApplicationEventPublisher 의존도 뺐다(§7 F-4).

RedfishPowerService 에서는 settleBootOrder, Settlement, settle, armBootOverride, arm, 3-인자 reset 을 삭제했고, networkBoot 를 powerOnOrRestart 로 바꿨다.

2-3. 남긴 것

  • FlashLedger.PXE_REARM 상수. DB 에 이미 있는 과거 재무장 행을 phase 수준 사건으로 읽기 위해 PHASE_LEVEL_REASONS 에 남겼다. 빼면 그 행이 축의 결과로 읽혀 성공한 축이 실패로 보인다(E2-4 CP5 F-2).
  • Windows 설치 중 재PXE 의 exit 처리, 종단 completedExit, 복귀 시한 20 분.

2-4. plan 밖에서 한 판단

  • SettingLedger.markRebooted 의 3-인자 판(무장 요약을 arm meta 로 남김)을 삭제했다. 남는 내용이 재시작 메시지뿐이라 키 이름이 사실과 어긋나고, 이 키를 읽는 main 코드가 없다.
  • FlashLedger Javadoc 의 "무장 요약 포함" 문구를 삭제했다.

2-5. 규모

src 기준 42 파일. 삭제 1,775 줄, 추가 159 줄이며, 삭제분에는 클래스와 테스트 파일 13 개를 통째로 지운 줄이 포함된다. 미커밋 상태다.

§4. CP5 계획 (실기)

HF 는 CP5 를 실기 검증으로 대체한다. 실기 절차 문서는 discussion/26-11-16_14-30-51_HF24-v2_fieldwork.md 다.

  • 정의서: 전 단계(굽기, 설정, RAID, Windows Server 2025).
  • 선행: spv-01 에 HF24 v2 배포(방식 미정). /etc/serverprovision/env 의 pxe-rearm-delay 항목 정리(남아도 해는 없다).

§6. 미수행 항목과 사유
  • 미수행 범위: 전 항목(A1~A9, B1, B2, C1, C2).
  • 사유: 사용자가 지금 당장 실기를 진행하기 어렵다(2026-11-16). spv-01 배포 방식(작업 트리에서 빌드할지, 커밋 뒤 빌드할지)도 아직 정하지 않았다. spv-01 의 에이전트 교체가 R17 에서 미완인 점도 배포 전에 확인해야 한다.
  • 대신 확인한 것: §3 의 단위 테스트와 통합 테스트(무장 PATCH 0 건, 재무장 없음, 시한 실패 유지, 화면 문구).
  • 남는 위험: 오버라이드가 없을 때 BIOS 가 스스로 순서를 바꾸는 경우. 재생성은 09-17 MS04-CE0 와 10-23 MS74-HB0 에서 관측됐지만 둘 다 오버라이드를 쓰던 실행이었다. 이런 일이 일어나면 셸 낙하 뒤 시한 실패로 드러난다.
