# 드리프트 픽스처

12 종 드리프트를 반복 재현하는 자산이다. 자원 무결성 점검 화면의 배치 후보를 비교할 때
**후보마다 같은 상태를 보여 주기 위해** 만들었다 — 후보 A 를 4 건에서 보고 후보 B 를 12 건에서
봤다면 그 비교는 성립하지 않는다.

모의가 아니라 실물을 심는다. 진짜 파일을 옮기고 진짜 마커를 남기고 진짜 데이터베이스 행을 만든다.
거기서 나오는 드리프트는 시뮬레이션이 아니라 애플리케이션이 실제로 탐지한 것이다.
그래서 이름이 `mock` 이 아니라 `fixture` 다.

## 명령 다섯

| 명령 | 하는 일 | 앱을 통과하는가 |
|---|---|---|
| `seed.sh` | 자원을 등록한다. 멱등 | ○ |
| `perturb.sh` | 12 종 상태로 어긋뜨린다 | ✕ |
| `verify.sh` | 점검을 돌려 12 종이 잡혔는지 대조한다 | ○ |
| `reset.sh` | 씨앗만 있는 상태로 되돌린다 | ○ |
| `purge.sh` | 픽스처가 만든 것을 전부 지운다 | ✕ |

애플리케이션을 통과하는 것은 `seed` 와 `verify` 다. 앞은 **마커를 앱이 만들게 하려는 것**이고,
뒤는 실제 점검을 돌려 결과를 받아야 하기 때문이다. 나머지는 파일과 데이터베이스를 직접 만진다 —
상태를 어긋나게 하는 일에는 앱이 제공하는 정상 경로가 없다.

## 쓰는 법

```sh
./seed.sh              # 씨앗 등록 (한 번만 — 멱등이라 다시 돌려도 늘지 않는다)
./perturb.sh           # 12 종 상태로 어긋뜨린다
./verify.sh            # 정밀 점검 후 대조 — 12 종이 전부 나와야 한다

./reset.sh             # 씨앗만 있는 상태로 (후보를 바꿔 볼 때)
./verify.sh --expect-none   # 되돌리기가 끝났는지 확인

./perturb.sh --count 5 # 종류당 5 건 — 목록이 길어졌을 때의 배치를 보려면
./purge.sh             # 전부 제거
```

## 종료 코드

자동화에 엮으려면 종료 코드가 사실을 말해야 한다.

| 명령 | 0 | 1 |
|---|---|---|
| `verify` | 12 종 전부 확인 | 빠진 종류가 있다 — 이름을 찍는다 |
| `verify --expect-none` | 픽스처 드리프트 없음 | 남은 것이 있다 — 무엇이 남았는지 찍는다 |
| `perturb` | 하나라도 교란했다 | 하나도 못 했다 |
| `seed` · `reset` · `purge` | 정상 | 앱 · 데이터베이스에 닿지 못했거나 인자가 틀렸다 |

`perturb && verify` 로 엮어도 실패가 걸러진다. 처음에는 `perturb` 가 아무것도 못 해도 0 을 돌려줘
`verify` 까지 가서야 "12 종 전부 빠짐" 으로 나타났다 — 원인에서 먼 곳에서 드러나는 실패였다.

## 12 종을 어떻게 만드는가

### 활성 자원 여섯

| 종류 | 조작 |
|---|---|
| 경로 이동됨 | 파일과 마커를 점검 범위 안 다른 위치로 함께 옮긴다 |
| 자원 소실 | 파일과 마커를 점검 범위 밖으로 옮긴다 |
| 미등록 마커 | 등록한 뒤 데이터베이스 행만 지운다 |
| 마커 서명 불일치 | 마커의 `attributes` 에 값을 더한다 |
| 내용 변경 감지 | 파일에 바이트를 덧붙인다 |
| 자원 중복 존재 | 원본을 둔 채 파일과 마커를 다른 위치로 복사한다 |

**미등록 마커**는 마커를 손으로 만들지 않는 것이 요점이다. 등록으로 생긴 진짜 마커를 남기고 짝이
되는 기록만 지우면, 서명은 유효한데 데이터베이스에 짝이 없는 상태가 정확히 만들어진다.

**마커 서명 불일치**는 서명 필드가 아니라 서명 대상을 바꾼다. 서명은 그 내용을 포함해 계산되므로
자동으로 어긋나고, JSON 자체는 온전해 읽기 오류가 아니라 서명 불일치로 잡힌다.

### 휴지통 잔여 하나

| 종류 | 조작 |
|---|---|
| 잔여 마커 정리 필요 | 소프트 삭제 전에 마커를 떠 두었다가 휴지통 자원 옆에 되돌려 놓는다 |

### 삭제 자원 다섯 — 진리표의 단독 칸

`PathReconciliationTruthTableTest` 가 확정한 24 칸 중 **한 종류만 낳는 칸**을 고른다.
두 종류를 동시에 낳는 칸을 쓰면 어느 자원이 어느 종류를 대표하는지 흐려진다.

| 종류 | 칸 | 상태 |
|---|---|---|
| 삭제 자원 복귀 | `[A · ⓜ0]` | 기록 없음 · 원위치 본체 있음 · 마커 없음 |
| 유령 DB 기록 | `[B · ⓜ0]` | 기록 없음 · 본체 없음 · 마커 없음 |
| 삭제 자원 위치 이탈 | `[B · ⓜ2]` | 기록 없음 · 본체 없음 · 마커가 다른 위치에 본체와 함께 |
| 미아 마커 | `[C · ⓜ1]` | 정상 보관 · 원위치에 마커만 |
| 휴지통 자원 소실 | `[F · ⓜ0]` | 기록 있음 · 실물 없음 · 원위치 없음 · 마커 없음 |

## 전제 두 가지

**자동 처리를 끈다.** 되돌릴 수 있는 네 종류(경로 이동됨 · 삭제 자원 복귀 · 미아 마커 ·
잔여 마커 정리 필요)는 기본으로 자동 처리 대상이다. 켜 둔 채 교란하면 다음 점검이 그것들을 스스로
해소해 픽스처가 만든 상태가 사라진다. `perturb` 가 원래 값을 적어 두고 끄며, `reset` 과 `purge` 가
되돌린다.

**보관소는 점검 범위 밖에 둔다.** 기본값은 `$TMPDIR/reconciliation-fixture-stash` 다. 범위 안에 두면
'자원 소실' 이 '경로 이동됨' 으로 잡히고, 자동 처리가 켜져 있으면 데이터베이스 경로가 보관소로
갱신돼 픽스처가 스스로 무너진다.

## 실측으로 알게 된 것

**`reset` 은 지우고 다시 심는다.** 계획은 "교란만 되돌리는 빠른 명령" 이었으나 그 전제가 무너졌다.
교란 여럿이 마커를 지우는데 마커는 애플리케이션만 만들 수 있고, 이미 등록된 자원의 사라진 마커를
다시 쓰게 하는 경로가 없다 — 마커 서명 재발급도 없는 마커를 만들어 주지 않는다. 파일과 데이터베이스만
되돌리면 마커 없는 자원이 남아 다음 점검이 새 드리프트로 잡는다. 열두 건 등록에 수 초라 실제 부담은 없다.

**가짜 ISO 는 내용 추출에 실패한다.** 자원 파일은 수십 바이트짜리 텍스트라 진짜 ISO 이미지가 아니다.
등록과 마커 발급은 정상이지만 패키지 목록 추출이 실패해 앱 로그에 오류가 남는다 — 픽스처의 결함이
아니라 가짜 파일을 쓰는 대가다. 파일을 작게 두는 편이 용량 부담이 없어 그렇게 두었다.

**BIOS 는 같은 보드에 같은 버전을 두 번 등록할 수 없다.** 대량 모드에서 회차마다 버전을 달리한다.

**일반 점검만 돌리면 열한 종만 나온다.** 내용 변경 감지는 파일 내용을 다시 계산해야 잡힌다.
`verify` 는 기본으로 정밀 점검을 돌리며, `--quick` 은 그 차이를 확인할 때 쓴다. 다만 이미 열려 있는
드리프트는 일반 점검으로 사라지지 않으므로 되돌린 직후에 써야 차이가 보인다.

## 환경변수

경로와 접속 정보는 환경마다 다르므로 전부 환경변수로 받는다. 기본값은 샌드박스 기준이다.

| 변수 | 뜻 |
|---|---|
| `FIXTURE_BASE_URL` | 앱 주소 |
| `FIXTURE_ROOT` | 자원을 심을 루트 |
| `FIXTURE_STASH` | 점검 범위 밖 보관소 |
| `FIXTURE_TRASH` | 휴지통 루트 |
| `FIXTURE_DB` · `FIXTURE_DB_USER` · `FIXTURE_DB_PASS` · `FIXTURE_DB_NAME` | 데이터베이스 접속 |
| `FIXTURE_OS_ID` · `FIXTURE_BOARD_ID` | 씨앗이 매달릴 부모 |

## 이 자산을 쓰는 곳

MK4-4-2 의 후보 비교가 첫 사용자다. 전수 재현 감사(R)도 같은 픽스처를 입력으로 쓴다 —
모든 데이터베이스 · 파일시스템 불일치를 재현해 드리프트와 대조하는 단계라 하는 일이 같다.
