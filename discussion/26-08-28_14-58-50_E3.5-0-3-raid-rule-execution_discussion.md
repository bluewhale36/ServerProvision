# E3.5-0-3 : 요구사항 적용 — RAID 구성 규칙을 카드 제어 방식으로 집행하는 방법

작성 2026-08-28 (KST). E3.5-0 사전 조사의 세 번째 항목이자 이 시리즈의 **첫 토론 문서**라 전체 그림을 담는다. 코드를 쓰지 않는 단계이며, 산출물은 "E3.5 본 슬라이스(E3.5-1 이후)를 어떻게 자를 것인가" 에 대한 결정이다. 입력은 셋이다 — **E3.5-0-1**(사용자 실측 `lspci`: CRA3338 은 클래스 `0107` · `Subsystem: Gigabyte … Device 3008`, 9361-8i 는 클래스 `0104` · `Subsystem: … MegaRAID SAS 9361-8i`), **E3.5-0-2**(`discussion/26-08-28_14-03-10_raid-card-management_briefing.md` — 칩 계열이 제어 계열을 정한다: SAS3008 IR = `sas3ircu`, SAS3108 MegaRAID = `storcli64`; Redfish 는 GIGABYTE BMC 실측 전엔 기대 없음), 그리고 **U4-1-1 · U4-1-2 · U4-1-3** 이 세팅 정의서에 넣은 RAID 구성 규칙 모델이다.

정정 하나를 먼저 적는다. 0-2 브리핑 §1-1 · §6 은 진단 파서 `DiagnosticReportParser.kindOf` 가 SAS 클래스를 RAID 로 잡지 못한다고 썼으나, 현행 코드는 이미 `serial attached scsi` 를 RAID 로 분류한다(MS74-HB0 실측 반영, E1-2 정정 #51). 그 항목은 닫힌다.

## 1. 현행 실태 — 집행이 발 디딜 자리

### 1-1. 정의서가 실행에 넘기는 것
`RaidConfigurationRequest` 는 세 가지를 갖는다.
1. `raidCardId` — MA7 RAID 카드 자원의 **소프트참조**(카드 엔티티 `RaidCard` 는 `vendor · modelName · supportedRaidLevels · cacheCapacity · pciSubsystemId` 를 갖는다)
2. `diskGroups[]` — 묶음 규칙 `{raidLevel | null = RAID 없음, diskType SSD/HDD/AUTO, transport SATA/SAS/NVME/AUTO, capacity AUTO/SPECIFIED(size · GB/TB 십진), count EXACT/AT_LEAST n, role BY_PRIORITY/OS/DATA/NONE}`
3. `volumePriorities[]` — 행 순서가 우선순위인 `{diskType, transport, capacityOrder}`. 규칙의 뜻은 U4-1 토론이 정했다: **묶음은 볼륨 하나의 명세가 아니라 규칙**이라 조건에 맞는 조합 전부에 적용되고(E18 · E19), `AUTO` 는 "정하지 않음" 이 아니라 **"같은 스펙끼리 프로그램이 묶는다"**(E4), `AT_LEAST n` 은 "그 스펙이 n 개 이상 있으면 있는 대로 다 묶는다"(E19), OS 영역 판정은 `OsVolumeTargets.describe`(고정 1 규칙 또는 우선순위 1 순위)다.
정의서 저장 시 `DiskGroupRules` 7 규칙과 `SupportedRaidLevels.blockReasonFor` · `RaidLevel.minimumDisks(cardHasCache)` 가 카드 기준으로 검증하므로, **실행이 받는 규칙은 "그 카드가 만들 수 있는 레벨 · 최소 디스크" 를 이미 통과한 것**이다.

할당 시 정의서는 `AssignedProcessSnapshot.payload` 로 동결된다(BIOS 템플릿만 별도 deep-freeze). 실행 쪽이 이것을 읽는 통로는 `BiosSettingResolutionProvider`(execution 이 선언 · provisioning 이 구현하는 SPI, Service Provider Interface — 도메인이 구현해 끼우는 확장점) 선례다. RAID 도 같은 모양의 SPI 하나로 규칙 묶음을 받으면 된다.

### 1-2. 실행 엔진의 두 집행 모델
- **게스트 주도(E1)**: 게스트가 진단 Alpine 으로 부팅해 `agent.sh` 가 `POST /agent/checkin` → `POST /agent/steps`(RUNNING 행 열기) → `POST /agent/steps/{id}/close`(SUCCEEDED/FAILED + statusMeta) 를 돌리고, 응답의 `AgentDirective`(`WAIT · COLLECT · REBOOT`)에 따라 다음 일을 한다. 지시 판정은 `AgentReportService.directiveFor` 한 곳이고, 성공 close 의 소비는 `ProvisioningPhaseExecutor.onStepClosed` 훅(phase 마다 실행기 빈)이다. 커서 전진 · 종단은 `PhaseCursorAdvancer` 하나가 활성 할당의 `ownedPhases` 로 판정한다.
- **서버 주도(E2 · E3)**: 게스트는 대기 스크립트만 받고, 30 초 워커(`FirmwareSettingWorker`)가 게스트마다 `FirmwareSettingCycle.advance` 를 돌려 `WorkerStep` 체인(`order() · matches() · execute()`)에서 처음 맞는 행을 집행하며, `SettingLedger` 가 원장 행과 사유 코드(`APPLIED · NO_TARGET · VALUE_NOT_IN_REGISTRY · RETURN_TIMEOUT …`)를 관리한다.

RAID 구성은 둘의 성격을 반씩 갖는다 — 카드에 명령을 내리는 손은 **게스트 리눅스 안의 CLI** 뿐이지만(BMC 경로 없음), 무엇을 만들지 정하는 머리(규칙 × 인벤토리 매칭)는 **서버**가 갖는 편이 맞다(규칙 모델 · 카드 자원 · 정의서 판정 SSOT 가 전부 서버에 있다).

### 1-3. 지금 없는 것
- **카드 뒤 물리 디스크 인벤토리.** 진단 수집 `HardwareSpec.DiskInfo` 는 `lsblk -d` 가 보는 장치뿐이라 MegaRAID 뒤의 물리 디스크는 보이지 않고(VD 만 보인다), IR 모드 카드도 볼륨 멤버는 감춘다. `DiskInfo` Javadoc 이 OPEN-1 로 남겨 둔 공백이다.
- **게스트에게 "무엇을 만들라" 를 실어 보내는 지시.** `AgentDirective` 는 값만 있고 payload 가 없다.
- **진단 이미지의 CLI.** `build-assets.sh` 는 Alpine 공식 아티팩트 + `apkovl`(에이전트 · 키) 이고 `storcli64` · `sas3ircu` 는 없다.
- **RAID phase 의 하위 step.** `ProvisioningPhaseStep` 에는 `RAID_CONFIGURATION` 하나뿐이다(ENUM 컬럼 → DDL 동반).
- **만든 볼륨을 다음 단계(E4 OS 설치)에 넘기는 기록.**

## 2. 집행이 답해야 할 질문과 대안

각 질문에 대안을 비교하고 권장안을 적는다. ✅ 는 세션 권장, ❓ 는 사용자 결정이 필요한 지점이다.

### Q1. 누가 어디서 집행하는가
| 대안               | 내용                                                        | 평가                                                            |
| ---------------- | --------------------------------------------------------- | ------------------------------------------------------------- |
| A 게스트 전담         | 에이전트가 규칙을 받아 스스로 매칭 · 생성                                  | 매칭 로직이 셸 스크립트에 들어가 테스트 불가 · 규칙 해석 SSOT 가 둘                    |
| B 서버 전담(Redfish) | BMC Storage 스키마로 서버가 직접 생성                                | GIGABYTE BMC 지원 미확인(0-2 §2-3) · IR 카드 노출 불확실                  |
| **C 하이브리드** ✅    | 에이전트 = 인벤토리 수집 + 계획 집행(명령 실행) / 서버 = 매칭 · 계획 산출 · 검증 · 원장 | 매칭은 순수 함수라 단위 테스트 가능, 에이전트는 "받은 명령 목록을 순서대로 실행하고 결과를 보고" 만 한다 |

C 의 흐름: 게스트가 `RAID_CONFIGURATION` phase 로 부팅(진단 Alpine 체인로드, E1 과 같은 스크립트) → 체크인 → 서버 지시 `RAID_INVENTORY` → 에이전트가 CLI 로 카드 · 물리 디스크 · 기존 볼륨을 JSON 으로 보고 → 서버가 규칙 × 인벤토리로 **계획(plan)** 을 세워 다음 체크인/close 응답에 실어 보냄 → 에이전트가 계획의 명령을 실행하고 결과 보고 → 서버가 결과 검증 · 볼륨 기록 · 커서 전진 → `REBOOT`(다음 phase 로 iPXE 폴링 복귀).

> C 안 진행.

### Q2. 지시 판정을 어떻게 늘리는가 (조건분기 확장 금지)
현행 `directiveFor` 는 진단 phase 의 사정만 안다(`커서 > 진단 → REBOOT`). RAID phase 가 들어오면 "커서가 RAID 인데 REBOOT" 가 되어 버린다. 대안:
(a) `directiveFor` 에 RAID 분기 추가 — 금지 패턴
(b) ✅ **`ProvisioningPhaseExecutor` 에 `directiveFor(server, progress)` 기본 메서드**를 두고 접수 서비스는 "커서 phase 의 실행기에게 묻는다" 로 바꾼다. 진단 실행기가 지금 규칙(COLLECT/WAIT)을 옮겨 갖고, 종단 · phase 이탈 → REBOOT 만 공통에 남긴다. 지시에 payload 가 필요하므로 `AgentDirective` 는 enum 값 + **지시 본문**(예: `directive: "RAID_APPLY", plan: {...}`)으로 응답 DTO 를 넓힌다(E1-2 Javadoc 이 "신규 지시 = 값 추가 + agent.sh 갱신" 으로 예고한 자리).

> b 안 진행.

### Q3. 인벤토리는 무엇을 어떤 형식으로 모으는가
에이전트가 카드 계열별 CLI 로 모으고 **서버 파서가 정규화**한다(진단 수집의 "원문 보고 · 서버 파싱" 관례 그대로).
- 카드 식별: `lspci -nn` 의 Vendor:Device(칩) + Subsystem → 서버가 MA7 `RaidCard.pciSubsystemId` 와 대조(0-1 실측: CRA3338 `1458:3008`(추정 — `-nn` 재실측 필요), 9361-8i `1000:9361`).
- 물리 디스크: MegaRAID 는 `storcli64 /c0/eall/sall show all J`(JSON — `EID:Slt · Med(SSD/HDD) · Intf(SAS/SATA) · Size · State(UGood/Onln/JBOD) · DG · Model · SN`), IR 은 `sas3ircu 0 display`(텍스트 — `Enclosure# · Slot# · State(Ready/Optimal) · Size(MB) · Protocol(SATA/SAS) · Drive Type(SATA_HDD/SAS_SSD) · Serial`).
- 기존 볼륨: `storcli64 /c0/vall show all J` · `sas3ircu 0 display` 의 IR Volume 절 — 멱등 · 기존 구성 정책(Q6)의 입력.
- 정규화 결과(서버 VO): `PhysicalDisk{slotId, type SSD/HDD, transport SAS/SATA, capacityBytes, state, serial}` · `ExistingVolume{id, level, memberSlots, name}` · `DetectedCard{chipFamily MPT_IR/MEGARAID, subsystemId, firmware}`.
❓ 실측 선행: 두 실서버(Oracle Linux 9.7)에서 위 명령 출력을 채집해 파서 픽스처로 삼는다(§4).

### Q4. 규칙 → 물리 디스크 매칭(계획 산출)
서버의 순수 함수(`RaidPlanner` 가칭)로 둔다. 입력 = 규칙 목록(정의서 순서) + 물리 디스크 목록, 출력 = 계획(볼륨 생성 명령 목록 + 규칙별 배정 + 미배정 디스크) 또는 실패 사유.
1. **디스크 정규화**: type · transport 는 CLI 값에서, 용량은 바이트로. **십진 표기 정합**: 정의서 `480 GB` = 480·10⁹ B, CLI 는 `446.625 GB`(GiB 혼용) 또는 `457,862 MB` 로 보고하므로 **표기 용량 계급(marketing size class)** 으로 환산해 비교한다 — 실제 바이트를 10⁹ 단위로 올림하되 SSD/HDD 의 관례(480/500/960/1000/1920/2000/3840/4000 …)로 스냅. 허용 오차는 실측 픽스처로 정한다(❓).
2. **규칙 순서대로 소비**: 정의서의 규칙 순서가 곧 소비 우선순위. 각 규칙은 `type · transport · capacity` 조건에 맞는 **미배정** 디스크를 모은다(AUTO 축은 "무엇이든" 이되 같은 그룹 안은 같아야 함).
3. **AUTO 그룹화**: 조건에 맞는 디스크를 `(type, transport, capacityClass)` 로 나눠 **그룹마다** 규칙을 적용한다(E4 "같은 스펙끼리").
4. **개수 적용**: `EXACT n` → 그룹 안에서 n 개씩 잘라 볼륨 여러 개(6 대 · EXACT 2 · RAID1 → 볼륨 3), 나머지는 미배정. `AT_LEAST n` → 그룹 전체를 볼륨 하나(6 대 · AT_LEAST 3 · RAID5 → 볼륨 1), n 미만이면 그 그룹은 건너뜀.
5. **RAID 없음 규칙**(`raidLevel == null`): 볼륨을 만들지 않고 디스크를 **패스스루/JBOD 로 보장**한다 — MegaRAID 는 `set jbod` 필요(personality 에 따라), IR 은 볼륨 미소속이면 자동.
6. **카드 한계 검증**: 계획이 카드 한계를 넘으면 계획 자체를 실패로 — IR 볼륨 최대 2, RAID1 정확히 2 대(EXACT 4 RAID1 은 볼륨 2 로 쪼개짐), RAID 1E/10 3~10 대, MegaRAID VD 64. 정의서 검증이 못 잡는 것(볼륨 수)은 여기서 잡는다.
7. **역할 · 우선순위 부여**: 만들 볼륨(과 RAID 없음 규칙의 단독 디스크)에 `role` 과 `VolumePriorityRules.rankOf` 순번을 매겨 OS 영역 볼륨을 결정(`OsVolumeTargets` 와 같은 판정)한다.
❓ 결정 요청: (a) 규칙에 맞는 디스크가 **0 대**일 때 — 규칙 건너뜀(관대) vs 실패(엄격). `AT_LEAST` 는 규칙 문구상 건너뜀이 자연스럽고, `EXACT` 는 실패가 자연스럽다 — 이 비대칭을 채택할지. (b) 어느 규칙에도 안 잡힌 **잔여 디스크** — 그대로 둔다(권장) vs 경고.

> a : 지금은 '건너뜀'. 추후 os 설치를 본격적으로 구현할 때 다시 논의한다.
> b : 그대로 둔다.

### Q5. 계열별 집행 명령 (계획 → 명령)
계획은 카드 계열 무관한 중립 명령(`CreateVolume{level, slots[], name}` · `EnsurePassthrough{slots[]}`)으로 적고, **에이전트 쪽 계열 어댑터**가 CLI 로 번역한다(셸 함수 둘: `mr_create` / `ir_create`). 서버가 CLI 문자열을 만들어 보내는 안은 탈락 — 셸 인젝션 표면이 생기고 서버 테스트가 CLI 문법에 묶인다.
- MegaRAID: `storcli64 /c0 add vd type=raid{n} drives=E:S,E:S name=spv-r{규칙}-v{순번}` (+ RAID10 은 `pdperarray=2`), 캐시 정책은 **카드 기본값 유지**(정의서에 축이 없다 — 후속 U 축 후보 ❓), `/c0/vall show J` 로 결과 확인.
- IR: `sas3ircu 0 create RAID{0|1|1E|10} MAX E:S E:S … spv-r{규칙}-v{순번}` — RAID5 는 정의서 검증이 이미 막는다.
- 볼륨 이름에 규칙 번호 · 순번을 박는 이유: 멱등(Q6)과 E4 인계(Q7)의 열쇠.

> 승인.

### Q6. 멱등과 기존 구성 ❓
재시도("실패 지점부터 다시 하기") · 재투입 서버(U6) · 이전에 사람이 만든 RAID 가 있을 수 있다. 대안:

| 대안 | 내용 | 평가 |
|---|---|---|
| A 보수 | 기존 볼륨이 하나라도 있으면 실패(`EXISTING_CONFIG`) — 운영자가 지우고 다시 | 데이터 보호 최우선, 재투입 서버마다 사람 손이 든다 |
| B 파괴 | 계획 실행 전 전부 삭제 후 재구성 | 자동화는 완전하지만 되돌릴 수 없는 조작 — E2-2 "굽기 전 신원 확인" 급의 안전장치 필요 |
| **C 인식 + 정의서 축** ✅ | 이름 규약 `spv-r*-v*` 인 볼륨은 "우리가 만든 것" 으로 인식해 계획과 같으면 건너뜀(멱등). 그 외 기존 볼륨은 **정의서 RAID 구성 단계의 새 축 "기존 구성 처리: 실패 / 삭제"** 로 정한다(기본 실패) | 멱등은 공짜, 파괴는 사용자가 정의서에 적어야만 일어난다 — "UX 모순은 UI 1차 차단" 과 같은 결 |
C 를 택하면 U4-1 계열에 작은 후속(축 추가)이 생긴다.

> 세팅 정의서에서 RAID 구성 섹션에 기존구성보존/파괴 를선택할 수 있도록 만든다. raid 를 재구성하는 경우는 흔히 기존 디스크에 있던 데이터를 날리기 위해서가 가장 큰 이유이기도 하다.
> 현재 사내 작업 흐름 상 provisioning server 를 통해 생성된 raid 볼륨 만을 보존해야 하는 등의 특별한 사유는 크게 없을 것으로 보인다.
> 다만 이름을 남기는 것은 그대로 진행한다.
> 
> 한편 볼륨 이름을 특정하는 것이 정확히 어떤 형태인지 잘 모르겠다. Linux 등에서 LVM 을 생성할 때 볼륨에 이름을 지정하는 것과 유사한 것인지 모르겠다. 실무에서는 한번도 RAID 볼륨을 생성하는 데에 이름을 붙인 경험이 없다.

### Q7. 결과 기록과 E4 인계
집행 뒤 에이전트가 최종 상태를 보고하면(`storcli /c0/vall show J` · `lsblk -o NAME,WWN,SERIAL,SIZE`) 서버는 **볼륨 기록**을 남긴다 — 규칙 번호 · 순번 · 레벨 · 멤버 슬롯 · 용량 · 역할 · 우선순위 순번 · 리눅스 식별자(`/dev/disk/by-id/wwn-…` — MegaRAID VD 는 NAA WWN 을 갖고, IR 볼륨도 WWID 를 낸다; 단독 디스크는 시리얼). 저장 위치 대안: (a) 원장 `statusMeta` JSON 만 (b) ✅ **전용 표 `raid_volume`**(guest_server FK · 위 필드) — E4 가 "이 서버의 OS 영역 볼륨은 무엇인가" 를 묻는 조회 경로가 되고 상세 화면에도 그린다. E4 kickstart 는 `ignoredisk --only-use=/dev/disk/by-id/wwn-…` 로 그 볼륨을 받는다.

> b 진행.

### Q8. 검증 · 동기화 대기
생성 직후 MegaRAID 는 fast init 으로 즉시 사용 가능하고 IR 은 백그라운드 동기화 중에도 사용 가능하다. ✅ **대기하지 않고** 상태(`Optl/Dgrd`, 동기화 %)만 기록한다. 검증은 두 층 — 에이전트가 생성 명령의 종료 코드와 결과 목록을 보고하고, 서버가 계획과 대조(볼륨 수 · 레벨 · 멤버)해 불일치면 `RESULT_MISMATCH` 실패.

> BIOS/BMC 세팅과 RAID 구성이 같이 적용된 세팅 정의서의 경우 `BIOS/BMC 세팅 → RAID 구성 → 재부팅 → 결과 확인` 의 프로세스로 진행할 수 있도록 해도 좋을 것 같다. 다만 언급했던 방식이 정확도가 보장된다면 그대로 진행해도 무방.

### Q9. 원장 · 실패 사유 · 재시도
E3 `SettingLedger` 와 같은 결의 `RaidLedger` — 사유 코드 후보: `PLANNED`(계획 수립) · `APPLIED` · `NO_RULES`(단계 없음) · `CARD_NOT_DETECTED` · `CARD_MISMATCH`(정의서 카드 ≠ 감지 Subsystem) · `TOOL_MISSING`(CLI 없음/실행 불가) · `NO_MATCHING_DISKS` · `VOLUME_LIMIT` · `EXISTING_CONFIG` · `CREATE_REJECTED`(CLI 실패, 원문 동봉) · `RESULT_MISMATCH` · `RETURN_TIMEOUT`. 실패는 커서 = `RAID_CONFIGURATION`(또는 하위 step)에 남고 "실패 지점부터 다시 하기" 가 인벤토리부터 재수행한다(멱등이 Q6 로 보장).
❓ step 분할: `RAID_CONFIGURATION` 하나로 원장 행을 여러 번 열 것인가, `RAID_INVENTORY_COLLECTING · RAID_APPLYING · RAID_VERIFYING` 으로 쪼갤 것인가(ENUM DDL 동반, 상세 진행 레일에 셋이 보인다). 세션 권장은 **셋으로 분할** — E2-4 가 "집행 현황 상세화" 를 요구하는 방향과 같다.

> 분할안 승인.

### Q10. 진단 이미지와 도구 동봉
`storcli64`(정적 링크) · `sas3ircu` 를 `apkovl` 에 넣는다(`build-assets.sh` 의 자산 목록 + Broadcom 라이선스 파일 확인 ❓). Alpine(musl)에서의 실행은 실측 항목이며 안 되면 `gcompat`. 카드 계열 판별은 에이전트가 `lspci -n` 의 Device ID(`0097` → IR, `005d` → MegaRAID)로 하고, 미지 ID 는 `TOOL_MISSING` 계열 실패로 정직하게 멈춘다.

> 도구 동봉 승인. 실측 후 되지 않을 경우 다른 후보를 검토(진단 리눅스 자체를 변경하거나 하는 등).

## 4. 실측 선행 목록 (사용자 · 실서버, 코드 없음)
1. 두 서버에서 `lspci -nn -d 1000:` 로 Subsystem 의 **숫자 ID** 채집(0-1 은 이름만 있다).
2. 9361-8i 서버: `storcli64 /c0 show all J`, `/c0/eall/sall show all J`, `/c0/vall show all J`, `/c0 show personality` 원문 저장 → 파서 픽스처.
3. CRA3338 서버: `sas3ircu list`, `sas3ircu 0 display` 원문 저장. `RAID Support: Yes` 확인.
4. 각 서버 `lsblk -o NAME,WWN,SERIAL,SIZE,ROTA,TRAN,MODEL` — 볼륨의 리눅스 식별자 형태 확인(Q7).

6. Alpine 진단 이미지에서 두 바이너리 실행 여부(`file` · 실행) — 세션이 샌드박스 qemu 로 가능.
