# U4-1 : 디스크 관련 기능 — 토론 (2회차)

1회차의 답으로 **판단 하나가 뒤집혔고 하나가 확증됐다.** 그 둘을 먼저 정리하고, 그 위에서 남은 쟁점을 묻는다.

## 1. 받은 도메인 사실

|     | 사실                                                                                                                                                         |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | 게스트 서버에는 **같은 스펙의 디스크를 둘 이상** 넣는다                                                                                                                          |
| D2  | **OS 영역** = OS 가 설치되는 디스크. Linux 는 `boot` · `efi` · `swap` · `root` 가 들어가는 디스크, Windows 는 C 드라이브. **보통 SSD 로 구성된 RAID 1**                                  |
| D3  | **Data 영역** = 그 외 디스크. **RAID 구성 개수만큼 Data 영역이 생긴다.** Linux 는 `/data1` · `/data2` … 로 파티션, Windows 는 **OS 설치 이후** D · E … 드라이브. RAID 0/1/5/6, **없을 수도 있다** |
| D4  | RAID 를 잡는 로직은 **E 영역**이 맞으나, **어떻게 구성할지는 세팅 정의서가 정의**해야 한다                                                                                                 |
| D5  | **관례** — 동일 스펙 디스크 2개면 RAID1, 3개 이상이면 RAID5                                                                                                                |
| D6  | **장착 순서** — SSD → HDD, 용량 작은 것 → 큰 것                                                                                                                       |
| D7  | RAID 카드는 대체로 장착. 같은 스펙 3개 이상이면 **캐시 있는 모델**, 아니면 캐시 없는 모델                                                                                                  |
| D8  | **작업 순서** — RAID 구성 → OS 설치 시 RAID 디스크 지정. **단계 번호가 이 순서를 따른 것**                                                                                           |
| D9  | LVM 은 범위 외                                                                                                                                                 |

**예시** — SSD 480GB ×2 + HDD SATA 4TB ×2 → 각각 RAID1 → SSD RAID1 = **OS 영역**, HDD RAID1 = **Data 영역**

## 2. 뒤집힌 것 · 확증된 것

### 2-1. 뒤집힘 — `diskName` 은 잘못된 층에 있다

1회차 §1-1 은 "U4-1-3 이 이미 절반 구현돼 있다" 고 봤다. **그 판단을 철회한다.**

D2 · D3 이 말하는 것은, RAID 를 잡고 나면 **OS 가 보는 것은 물리 디스크가 아니라 RAID 볼륨**이라는 사실이다. `sda` 는 RAID 카드가 만들어 낸 가상 장치이지 운영자가 꽂은 물리 디스크가 아니다. 그러면 파티션이 가리켜야 할 대상은 `sda` 라는 **이름**이 아니라 **"OS 영역"** 이라는 **역할**이다.

즉 지금의 `diskName` 은 "동작하는 절반" 이 아니라 **한 층 아래를 가리키는 필드**다. 이미 있다는 사실은 여전히 참이지만, 그것을 개선하는 것이 U4-1-3 이라는 판단은 틀렸다.

### 2-2. 확증 — 단계 번호가 옳다

1회차 Q-5 는 "난이도가 번호와 반대이니 순서를 뒤집자" 고 제안했다. **그 제안을 철회한다.**

D8 이 근거를 준다 — 현장 작업 순서가 RAID 구성 → OS 설치이고, 세 단계는 그 순서를 따른 것이다. 그리고 실제로 **뒤 단계가 앞 단계의 산출물을 입력으로 받는다**:

```
U4-1-1   물리 디스크 묶음  →  RAID 볼륨        무엇을 묶고 어떤 레벨로
U4-1-2   RAID 볼륨        →  역할(OS / Data-n)  어느 볼륨이 무슨 용도
U4-1-3   역할             →  파티션 배치        그 안에 무엇을 만들지
```

난이도로 순서를 정하려 한 것이 잘못이었다. **의존이 순서를 정한다.**

### 2-3. 방향 — B 도 C 도 아니라 둘의 결합

1회차 §2 는 A(장치명) · B(역할) · C(규칙) 셋을 놓고 U4-1-2 를 B 라고 봤다. 실제 답은 **B 와 C 의 결합**이다.

- **역할(OS / Data-n)** 은 B — 정의서가 적는 것은 역할이다
- **어느 물리 디스크가 그 역할이 되는가**는 C — D5 · D6 의 규칙(같은 스펙끼리 묶고, SSD 먼저, 작은 용량 먼저)이 실행 시점에 결정한다

**정의서는 서버를 모른다**(1회차 §2)는 전제가 이 결합으로 풀린다. 정의서는 "SSD 480GB 2장" 을 적지 않고 **"첫 번째 묶음을 RAID1 로 잡아 OS 영역으로 쓴다"** 를 적는다. 그 "첫 번째" 를 실제 디스크로 푸는 것이 D6 의 장착 순서다.

## 3. 남은 쟁점

앞의 정리를 받아들이면, 정의서가 무엇을 적을지가 아직 갈린다. 아래 넷이 남는다.

### R-1. 정의서는 RAID 구성을 **얼마나 구체적으로** 적는가

D5 가 관례를 준다(2개=RAID1, 3개+=RAID5). 그러면 정의서가 적을 것이 셋 중 하나다.

| | 안 | 정의서에 적는 것 | 장점 | 약점 |
|---|---|---|---|---|
| ① | **관례 위임** | 아무것도 안 적는다. 실행이 D5 · D6 대로 자동 구성 | 정의서가 가장 단순. 대부분의 서버에 그대로 맞는다 | 관례를 벗어나야 할 때 손댈 자리가 없다 |
| ② | **묶음별 명시** | "1번 묶음 RAID1, 2번 묶음 RAID5" 처럼 순번마다 레벨 | 통제 가능 | 서버마다 묶음 수가 달라 정의서가 구성을 전제하게 된다 |
| ③ | **관례 + 예외** | 기본은 관례, 필요할 때만 특정 묶음의 레벨을 덮어쓴다 | 흔한 경우는 비워 두고 드문 경우만 적는다 | 두 표현이 공존해 화면이 복잡해진다 |

**추천은 ③이다.** ①은 "동일 스펙 4장을 RAID10 으로" 같은 요구가 오면 막히고, ②는 정의서를 특정 하드웨어 구성 전용으로 만든다. ③은 U3-5-a 가 `RequiredBoardModel` 을 "요구하지 않으면 null" 로 둔 것과 같은 형태다 — **비어 있으면 자동, 적혀 있으면 그대로.**

> **R-1 답변:**
> {RAID level, SSD/HDD(HDD 의 경우 SATA/SAS), 용량, 개수} 를 하나의 묶음으로 해서 여러 개 추가할 수 있도록 한다. 관례를 미리 지정해두지 않는다.
> 다만 RAID level 과 개수를 제외한 나머지 스펙은 '자동 탐지' 옵션을 넣는다. 개수의 경우 숫자 입력 또는 'n 개 이상' 옵션을 넣는다. 이 경우 '자동 탐지' 옵션이 선택된 RAID 구성 정의는 동일한 스펙인 디스크끼리 프로그램에서 자동으로 개수별로 묶어서 RAID level 에 따라 구성한다.
> 구성에서 유효성은 단계 진입 시 별도 기술한다.

### R-2. Data 영역이 몇 개인지 정의서가 아는가

D3 이 "RAID 구성 개수만큼 Data 영역이 생긴다" 고 했고 "없을 수도 있다" 고 했다. 즉 **Data 영역 수는 서버가 정한다.** 그런데 Linux 파티션은 `/data1` · `/data2` 처럼 **이름에 번호가 붙는다.**

| | 안 | 뜻 |
|---|---|---|
| ① | **자동 생성** | 정의서는 "Data 영역은 전부 XFS 로, 전체 용량" 같은 **규칙 한 줄**만 적고, `/data1`…`/dataN` 은 실행 시점에 개수만큼 만든다 |
| ② | **명시 나열** | 정의서에 `/data1` · `/data2` 를 직접 적는다. 서버에 그만큼 없으면 할당을 막거나 건너뛴다 |

①이면 정의서가 서버 무관을 지키고, ②면 정의서가 "Data 영역 2개 이상인 서버 전용" 이 된다.

**추천은 ①이다.** D3 의 "없을 수도 있다" 를 ②로 표현하면 정의서가 서버 구성마다 갈라진다.

> **R-2 답변:**
> 게스트 서버에서 OS 영역은 반드시 1개 존재하며, 이 외의 RAID 볼륨은 모두 Data 영역이다. Linux 에서 Data 영역의 파티션 명칭은 Data 영역에 대한 규칙이라기보다는 파티셔닝 과정에서 명시하는 것이 적절하다는 생각이다.

### R-3. Windows 의 Data 영역은 어느 단계인가

D3 이 결정적인 비대칭을 말한다 — **Linux 는 OS 설치 시 `/data1` 을 만들고, Windows 는 OS 설치 이후 D · E 드라이브를 잡는다.**

지금 `SettingProcessType` 은 넷이다: `BASIC_UPDATE` · `BASIC_SETTING` · `OS_INSTALLATION` · `OS_SETTING`.

그러면 Data 영역 파티셔닝이 계열마다 다른 단계에 들어간다.

- Linux → `OS_INSTALLATION` (설치기가 함께 만든다)
- Windows → `OS_SETTING` (설치 후 디스크 관리)

`OSInstallationRequest` 가 이미 2단 다형(`LinuxInstallationRequest` 중간층 + 추후 `WindowsInstallationRequest`)이라 **표현은 가능**하다. 다만 "Data 영역 정의" 가 계열에 따라 다른 단계에 나타나면 **화면에서 한자리에 모아 보여주기 어렵다.**

`project_mvp_release_line` 은 Windows 를 "한참 뒤" 로 두었다. **이번 U4-1 은 Linux 만 다루고 Windows 는 표현 가능성만 열어 두는 것**으로 충분해 보인다.

> **R-3 답변:**
> Data 영역은 Linux 에서도 OS Installer 에서 설치 시 지정하지 않는다. 설치 이후 별도로 잡는다.

### R-4. RAID 카드의 유무 · 캐시 유무를 정의서가 요구하는가

D7 이 "RAID 카드는 대체로 장착되며, 같은 스펙 3개 이상이면 캐시 있는 모델" 이라고 했다. 이것이 **정의서의 요구 조건**이 될 수 있다 — `RequiredBoardModel` 처럼 "이 정의서는 RAID 카드가 있어야 한다" 를 표현하고 할당 시점에 막는 것이다.

진단은 이미 RAID 카드의 **존재**를 수집한다(`PcieDevice.kind == "RAID"`). 다만 **캐시 유무는 수집하지 않는다** — 모델명 문자열만 있다.

| | 안 |
|---|---|
| ① | 아무 요구도 하지 않는다. RAID 구성이 실패하면 실행 단계에서 드러난다 |
| ② | **RAID 카드 존재**만 요구한다(수집되는 것으로 판정 가능) |
| ③ | 캐시 유무까지 요구한다 — 진단 수집 확장이 선행돼야 한다 |

**추천은 ②다.** 지금 수집되는 것으로 판정할 수 있고, U3-5-a 의 하드웨어 대조에 축 하나를 더하는 형태라 선례가 있다. ③은 진단 수집(E 계열) 확장이 붙어 이 슬라이스가 커진다.

> **R-4 답변:**
> 같은 스펙이 3개 이상인 경우에는 반드시 캐시가 있는 RAID 카드가 장착된다. RAID5 이상을 구성하기 위함.
> MVP 구현 기준으로 캐시가 있는 카드와 없는 카드는 모델이 한정되어 있는 상황이다.
> 캐시가 있는 모델과 없는 모델의 두 개가 진단 리눅스에서 raid 구성 시 사용해야 하는 명령이 다른 것으로 알고 있다.

## 4. 이 정리가 맞다면 세 단계는 이렇게 된다

R-1 ~ R-4 의 추천안을 그대로 받으면 각 단계의 범위가 이렇게 잡힌다. **확정이 아니라 검토용 스케치다.**

| 단계                    | 정의서에 더해지는 것                                  | 화면                | 무게  |
| --------------------- | -------------------------------------------- | ----------------- | --- |
| **U4-1-1** RAID 구성 지정 | 묶음별 RAID 레벨(비우면 관례) + RAID 카드 요구 여부          | OS 설치 단계 폼에 절 하나  | 중   |
| **U4-1-2** 디스크 분류     | 어느 묶음이 OS 영역인지(기본 = 첫 묶음) · Data 영역 공통 규칙    | 위 절에 이어짐          | 소   |
| **U4-1-3** 파티션 디스크 지정 | 파티션의 대상을 **장치명 → 역할**로 (`diskName` 의 층을 올린다) | 파티션 표의 '디스크' 열 교체 | 중   |

그리고 **집행(E 영역)** 은 이 셋과 별개로 남는다 — D4 가 정한 대로다. 실 장비 확보가 전제이므로 `project_mvp_release_line` 의 일정 제1 변수에 걸린다.

> **§4 스케치에 대한 의견:**
> RAID 레벨을 비워둘 경우 RAID 를 구성하지 않는 것으로 인식한다. RAID 구성은 반드시 RAID 카드를 요구한다.
