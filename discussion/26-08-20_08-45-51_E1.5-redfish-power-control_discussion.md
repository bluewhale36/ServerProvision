## 1. 이 단계가 왜 생겼나

2026-08-08 E2 pivot 토론에서 확정했다 — 전원 제어를 E2-3 안에 두지 않고 **공용 선행 슬라이스로 분리**한다. 소비처가 여럿이라 각자 만들면 인증과 오류 처리가 여러 벌로 갈리기 때문이다.

| 소비처 | 무엇을 쓰나 | 그 단계가 정한 것 |
|---|---|---|
| **E2-3** BMC 펌웨어 업데이트 | flash 전 `ForceOff` · 후 `On` | BMC 업데이트 흐름이 `BIOS flash → ForceOff → BMC flash → On → 검증` — 전원 제어 없이는 시작도 종료도 못 한다(착수 게이트) |
| **E3** BIOS 설정 | pending 적용 재부팅(`ForceRestart`) | 3호 실측이 `PATCH Bios/SD → ForceRestart → 반영` 전 왕복을 실증 |
| **MA6** Attribute Registry 조회 | 클라이언트 기반(인증 · TLS · 오류 처리) 재사용 | 조회 전용 — Reset 은 안 쓴다 |
| **UC-2** 즉시 강제 정지 | `ForceOff` | 운영자가 게스트를 즉시 세우는 유스케이스 — 화면 버튼이 필요할 수 있다(R-6) |
| *(합류 후보)* **UC-4 → 프로비저닝 필수 배선** | `BootSourceOverride` | 4호 관찰 — OS 설치 서버는 boot priority 가 OS 1순위라 "상시 PXE 우선" 전제가 실기에서 깨졌고, flash 가 설정을 리셋하므로 수동 PXE 우선 설정은 구조적으로 불가. 재부팅 지시 직전 override 가 표준 절차가 된다(R-3) |

범위는 확정 당시 **"Redfish 클라이언트 기반 + `ComputerSystem.Reset` 까지"** 였고, BootSourceOverride 는 "지금 막는 것이 없다" 로 제외였다 — 그 전제가 4호 실측으로 바뀌어 R-3 에서 다시 묻는다.

## 2. 실측이 확정해 준 계약 (E0-4 1~4호 — 구현은 조사값이 아니라 이 실측을 따른다)

- **인증** — Basic 우선 + Task 추적용 단기 세션 병용(사용자 결론과 일치). 세션은 `SessionTimeout` 30초 · 상한 10 · 발급 = `POST /redfish/v1/SessionService/Sessions` + JSON body + `Content-Type: application/json` 필수(누락 시 415) · 종료는 개별 세션 URI 에 DELETE(컬렉션에 보내면 405).
- **Reset 허용값 5종** — `ForceOff` · `ForceRestart` · `GracefulShutdown` · `On` · `PowerCycle`. 조사값에 있던 `GracefulRestart` 는 **부재** — 허용값은 `ResetActionInfo` 를 읽어 판정하는 것이 맞다.
- **On 실패 모드(실측 1회)** — "IPMI 명령은 성공했으나 전원 상태 불변" Critical Exception, 수동 cold boot 후 재시도 성공. → **On 발행 후 `PowerState` 폴링 검증 + 실패 시 `PowerCycle` 폴백 + 운영자 알림**이 설계에 들어가야 한다(T3 완료 기록의 명시 입력).
- **ETag 규율** — fresh ETag + `If-Match`(계정 PATCH 204 실증). `Bios/SD` 는 `If-Match: *` 실증. 412 시 fresh ETag 로 1회 재시도.
- **TLS** — BMC 는 자가서명 인증서(실측 전부 `curl -k`). 신뢰 저장소에 안 잡힌다.
- **환경** — RedfishVersion 1.15.1 · AMI OEM(`Oem.Ami`). 진행형 작업은 TaskService(`/TaskService/Tasks/{id}`) 폴링.

## 3. 현행 코드 실태 (2026-08-20 실측)

- **실 Redfish HTTP 호출은 0 이다.** `BmcPasswordService` 는 "적용 계획 산출"(로그 · 화면 표기 전용, 실제 호출 없음) — Redfish 는 문자열 상수로만 존재한다.
- `global/config/RestClientConfig` 의 전역 `RestClient` 빈 — comps.xml/repomd.xml 추출용 기본 설정("타임아웃 · 인터셉터 · 재시도가 필요해지면 확장한다" 주석). 자가서명 신뢰는 못 한다.
- `GuestServerDetail.bmcIp · bmcMac` — E1-2 in-band 수집으로 채워지는 구조화 컬럼. **QEMU 등 BMC 미검출 환경은 null(정상 degrade)**. 주석이 "E3-0 이 자격증명과 함께 별도 binding 엔티티로 승격할 여지" 를 남겨 뒀다.
- **자격증명 저장소는 어디에도 없다.** 실측은 표준 계정(사내 공통)의 Basic auth 로 진행됐다.
- `AgentDirective.REBOOT` 는 **in-band**(진단 리눅스 안 에이전트에 내리는 지시)다 — E1.5 의 out-of-band(BMC 경유) 제어와 층이 다르고 서로 대체하지 않는다.

## 4. 단계 스케치 (제안)

| 부분 | 내용 | 근거 |
|---|---|---|
| **클라이언트 기반** | `RedfishClient` — Basic 인증 · 자가서명 TLS · 타임아웃 · 오류 분류(연결 불가/인증 실패/412/멱등 재시도) · Task 폴링. 소비처는 이 인터페이스만 본다 | 소비처 4곳의 공통분모 |
| **전원 제어** | `ComputerSystem.Reset` 5종 + `PowerState` 조회 + **On 검증 폴링 · PowerCycle 폴백 · 운영자 알림** | 실측 계약 §2 |
| **(R-3 판정 대상)** BootSourceOverride | 다음 1회 부팅 PXE 강제 | 4호 관찰 — 단 K1(Once/Continuous · `Systems/Self/SD` 경유 · If-Match) 미실측 |

집행 executor(E2-3 · E3)와 화면(UC-2 버튼)은 이 슬라이스의 산출물 위에 얹는 각자의 몫이다 — E1.5 는 기반과 전원 제어 동작까지.

## 5. 열린 질문

### R-1. BMC 자격증명을 어디에 어떻게 두나
실측은 사내 표준 계정 1벌(Basic)로 진행됐다. 선택지:

| | 안 | 뜻 | 비용 |
|---|---|---|---|
| ① | **전역 설정 1벌** — 환경변수/운영 설정(`BMC_USERNAME`/`BMC_PASSWORD`) | 사내 표준 계정이 모든 게스트에 동일하다는 실무를 그대로 | 게스트별 예외(신품 공장 기본 비밀번호 = 시리얼 끝 11자 정책 미확정) 못 다룸 |
| ② | 게스트별 저장 — `GuestServerDetail` 컬럼 또는 별도 binding 엔티티(주석의 승격) | 게스트마다 다른 비밀번호 표현 가능 | 암호화 저장 · 화면 · 수명주기가 통째로 붙는다 |
| ③ | ① 지금 + ② 는 E3-0(계정 표준화 슬라이스)에서 | 지금 막힌 것만 뚫고 승격은 자격증명을 실제로 바꾸는 단계와 함께 | 전환기 비대칭 |

**내 판단은 ③.** E1.5 의 소비처들은 전부 "표준 계정으로 접속" 이면 움직인다. 신품의 공장 기본 비밀번호 정책은 아직 실측도 안 됐다(T3 잔여) — 모르는 요구를 위해 엔티티를 미리 만들지 않는다. 단 ①의 값 주입 경로는 지금 정해야 한다(application 설정 키 · 미설정 시 fail-fast 인지 degrade 인지).

> 신품의 공장 기본 비밀번호는 M/B 의 시리얼 11자이다. 이는 실측된 정보로 예외는 없다. 진단 리눅스 또는 Redfish API 를 통해 수집하는 정보에 포함된다.
> BMC 비밀번호는 그간 예외 없이 모두 동일한 값으로 세팅되어 왔다. username 은 기본 값인 admin 을 무조건 사용.

### R-2. 클라이언트가 사는 곳과 모양
| | 안 | 비고 |
|---|---|---|
| ① | **`global/redfish`** — 도메인 무관 인프라(marker · job 과 같은 결) | 소비처가 execution(E2-3 · E3) + management(MA6) 로 영역을 가로지른다 |
| ② | `execution/redfish` | MA6 이 execution 을 참조하게 된다(방향 어긋남) |

**내 판단은 ①.** 구현은 전역 `RestClient` 빈을 그대로 쓰지 않고 **전용 빌더**(자가서명 신뢰 + 짧은 타임아웃)를 쓴다 — comps 추출용 클라이언트에 insecure TLS 를 섞지 않는다.

> 1 진행.

### R-3. BootSourceOverride 를 이번에 합류시키나
| | 안 | 뜻 |
|---|---|---|
| ① | 합류 — E1.5 범위에 포함 | "재부팅 지시 직전 override" 가 표준 절차라면 Reset 과 한 몸 |
| ② | **후속 분리 — K1 실측 후 E1.5-2 로** | Once/Continuous · `Systems/Self/SD` pending 경유 여부가 미실측이라 지금은 계약을 확정할 수 없다 |

**내 판단은 ②.** U4-1 에서 배운 그대로 — 실물을 보지 않고 규칙을 짜면 조용히 안 맞는다. K1 실측이 게이트이고, 클라이언트 기반이 먼저 있으면 합류 비용은 메서드 하나다.

> 2 진행.

### R-4. BMC 미검출(bmcIp = null) 게스트의 degrade 흐름
소비처가 Reset 을 요구했는데 대상 게스트에 bmcIp 가 없으면? 예외로 거절(호출자가 처리) vs "지원 안 됨" 결과 타입으로 반환. QEMU 하네스 검증(CP5 대체)과도 얽힌다 — **판단을 구한다.** 내 성향은 결과 타입(전원 제어는 실패가 일상 사건이라 예외보다 결과가 다형 처리에 맞다).

> 결과 타입 처리.

### R-5. On 검증 폴링의 파라미터와 알림 경로
간격 · 총 타임아웃 · PowerCycle 폴백 횟수(1회?) · "운영자 알림" 의 실체(게스트 상세의 이벤트 로그? BackgroundJob 상태? 별도 알림 채널?). 실측은 1회 실패 사례뿐이라 값은 운영 감각의 영역 — **기본값 제안 후 판단을 구한다**(예: 5초 간격 · 60초 타임아웃 · PowerCycle 1회 · 실패 시 SetupStep/이벤트 기록).

> `ComputerSystem.Reset` 명령 입력 시 Task 경로가 반환된다. request 가 제대로 전달되었는지, 어떻게 실행에 옮겨졌는지(성공/실패) 나타난다.
> 켜짐/꺼짐 여부는 `GET  /redfish/v1/Systems/Self` 의 `PowerState` 에 나타난다(`On`, `Off`).
> 프로비저닝을 진행하는 도중에 알림은 우선 추후의 기능으로 한다. Background Job 은 사용자의 프로그램 기용 시 background 로 돌리는 작업에 대한 알림이지, 프로비저닝 과정의 로그나 알림은 아니다. 후자에 대한 기능은 별도 기능으로 개발할 예정.

### R-6. 화면(UC-2 수동 전원 제어)을 이 슬라이스에 넣나
넣으면 CP5 를 브라우저로 할 수 있고 UC-2 가 바로 열린다. 빼면 슬라이스가 얇아지고 CP5 는 하네스 대체(E 단계 예외). **판단을 구한다** — 내 성향은 포함(게스트 상세에 전원 상태 표시 + 제어 버튼, 실 BMC 없는 환경에선 R-4 의 degrade 표시가 그대로 화면 검증 재료가 된다).

> 포함. 실 게스트 서버도 존재하므로 테스트를 돌려볼 수 있다.

| **P6** | UC-2 수동 전원 제어 **화면 포함** — 실 게스트 서버가 존재해 실 테스트 가능 | R-6 |
