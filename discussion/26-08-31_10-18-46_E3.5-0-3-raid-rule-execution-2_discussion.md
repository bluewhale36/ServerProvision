## 2. 첨언이 남긴 질문의 답 — RAID 볼륨의 "이름" 이란 무엇인가

LVM 볼륨 이름과 **비슷한 자리의 다른 물건**이다. 차이를 층으로 풀면:

- **어디에 저장되는가.** LVM 이름은 OS 가 디스크의 LVM 메타데이터에 쓴다. RAID 볼륨 이름은 **카드가** 자기 구성 메타데이터(컨트롤러 NVRAM + 멤버 디스크 끝의 구성 영역, DDF 형식)에 쓴다. OS · 파일시스템과 무관하고, OS 를 설치하기 전에도 존재하며, 디스크를 다른 같은 계열 카드에 꽂아도 따라간다.
- **어떻게 붙이는가.** 생성 명령의 선택 인자다 — `storcli64 /c0 add vd type=raid1 drives=… name=spv-r1-v1`, `sas3ircu 0 create RAID1 MAX 1:0 1:1 spv-r1-v1`. 실무에서 안 붙였다면 그냥 빈 이름/기본 이름(VD0 …)으로 만들어진 것이다 — 기능 차이는 없다. 길이 한계가 있다(MegaRAID VD 이름 15자 — `spv-r1-v1` 9자라 여유. sas3ircu 쪽 한계는 실측 §3 에서 확인).
- **어디서 보이는가.** OS 의 장치명(`/dev/sda`)에는 나타나지 않는다. `storcli /c0/vall show` · `sas3ircu 0 display` · BIOS 셋업의 카드 메뉴에서 보인다.
- **우리가 쓰는 이유.** 재시도 · 재투입 때 에이전트가 CLI 로 기존 볼륨을 조회하면 이름이 그대로 읽히므로, **"이 볼륨은 프로비저닝 서버가 규칙 1 번으로 만든 첫 볼륨"** 을 OS 도 DB 도 없이 카드만 보고 알 수 있다. 멱등(D-7)과 `raid_volume` 기록 대조(D-8)의 열쇠가 이것이다. 사람이 붙이는 라벨이 아니라 기계가 남기는 꼬리표라고 보면 된다.

## 3. Q8 첨언(통합 프로세스)의 처리 — 원안 확정 + 최적화 후보 적립

첨언 요지: BIOS/BMC 세팅과 RAID 구성이 함께 있는 정의서는 `세팅 → RAID 구성 → 재부팅 → 결과 확인` 한 사이클로 묶어도 좋겠다, 다만 원안의 정확도가 보장되면 그대로 무방.

분석해 두면 — 이 아이디어는 실제로 **재부팅 1 회를 절약**한다. BIOS 설정은 POST 를 다시 돌아야 적용되는데, 현행 설계는 `PATCH → 적용 재부팅 → readback → (재부팅 없이 체인로드) 진단 리눅스에서 RAID 구성 → 다음 phase 로 재부팅` 이라 재부팅 2 회이고, 통합안은 `PATCH(pending) → 진단 리눅스에서 RAID 구성 → 재부팅 한 번으로 BIOS 적용 → readback + RAID 확인` 으로 1 회다. 대신 비용이 있다 — 서버 주도(E3 워커 · BMC)와 게스트 주도(RAID 에이전트)의 상태기계가 한 재부팅에 얽혀, 실패했을 때 "BIOS 가 안 먹은 것인가, RAID 가 틀어진 것인가" 의 지점 분리가 어려워지고, phase 별 독립 성패(축별 독립 성패의 연장) 원칙과 충돌한다. 첨언의 위임("정확도가 보장된다면 그대로") 에 따라 **원안(phase 분리)을 확정**하고, 통합은 **재부팅 절약 최적화 후보**로 적립한다 — 실기에서 재부팅 1 회가 수 분씩 걸려 아프다는 것이 확인되는 시점에 다시 꺼낸다.
