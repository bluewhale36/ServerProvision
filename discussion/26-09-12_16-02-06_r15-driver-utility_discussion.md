# R15 드라이버 · 유틸리티 관리 개편 — 토론 아카이브

- 기간: 2026-09-11 제기 → 2026-09-12 종결(Notion `R15 : 드라이버 · 유틸리티 관리 개편(OS · 보드 · 버전 축)` 페이지의 `## 토론` 절에서 진행, 답변은 사용자 인용문)
- 시리즈: 이 문서가 첫 문서이므로 전체 그림(현행 · 쟁점 · 결정 · 슬라이스 분할)을 담는다. 후속 상세는 각 슬라이스의 plan html 로 넘긴다.
- 인과: 이 개편은 E4-1-a-4(Windows `$OEM$` 조립 · 완료 보고)가 만든 조립 · 설치 경로 위에 놓인다. E4-1-a-4 는 Subprogram 에 OS 구분이 없어 "트리에 INF 가 있으면 대상" 으로 판별했고(당시 CP1 후속으로 명시), 실기 4호 뒤 사용자가 그 한계를 문제로 제기했다.

## 1. 왜 개편인가 — 현행 실태(2026-09-11 코드 · 실 DB 실측)

| 층 | 현행 | 문제 |
|---|---|---|
| 모델 `Subprogram` | 종류(DRIVER · UTILITY) × 보드(없으면 공용) × 이름 · 버전 · 트리 경로 · `entrypointRelativePath` | OS 축 · OS 버전 축이 없다. `entrypointRelativePath` 는 BIOS · BMC 와 같은 필드인데 Windows 경로에서 쓰지 않는다 |
| 조립 `WindowsOemPayloadAssembler` | 활성 DRIVER 중 트리에 INF 가 하나라도 있으면 전부 `$OEM$\$1\SPV\Drivers\<id>_<슬러그>` 로 복사 | 보드 · OS 를 보지 않는다. `$OEM$` 은 설치 원본당 하나라 게스트별 선별이 없다. 실 DB 기준 MS74-HB0 용 Intel Chipset 이 MS04-CE0 게스트에도 실린다 |
| 설치 SetupComplete.cmd | 폴더마다 `pnputil /add-driver *.inf /subdirs /install` | ASPEED 트리의 WIN2016~WIN2025 · WIN10 · WIN11 INF 폴더가 한꺼번에 pnputil 에 들어가고, `WDDM Installer/*.msi` 는 한 번도 실행되지 않는다 |
| 실 DB | DRIVER 4(MS04-CE0 ASPEED 1.15.03 · Intel Chipset · Intel QAT / MS74-HB0 Intel Chipset) · UTILITY 0 | 전부 Windows 용이지만 모델에는 그 사실이 없다 |
| OS 모델 | `OSName` = UBUNTU · CENTOS · ROCKY_LINUX · WINDOWS · WINDOWS_SERVER(계열 `OSFamily`) | Windows 설치 요청(E4-1-a-2)은 이미지 · 에디션을 알므로 대상 OS 버전은 서빙 시점에 확정된다 |

사용자 제기(2026-09-11): ① OS 에 따라 드라이버가 다르면서 보드에 따라서도 다른데 분류 기준이 보드뿐이다 ② 같은 OS 라도 버전에 따라 실행할 파일이 다르다(ASPEED 의 Win10 · 11 · Server 2022 · 2025 MSI). 단순 "등록 후 조립 자동화" 가 아니라 관리 · 사용성 개편 단계.

## 2. 쟁점과 결정

### Q1 분류 축 — **결정 (c)**
- (a) `OSName` 하나만 자원 단위에 추가 — 버전 차이를 표현 못 해 탈락.
- (b) `OSName` + OS 버전 범위를 자원 단위에 — ASPEED 처럼 한 패키지가 여러 버전을 품으면 자원을 쪼개야 해 탈락.
- **(c) 채택** — OS 축(`OSName` · null = OS 무관)은 자원 단위, 버전 축은 변형 단위. 패키지는 OS 계열까지만 알고 버전은 변형이 안다. (사용자 답변: c)

### Q2 벤더 패키지와 변형 — **결정 (b) · (c) 미채택**
- (a) 변형마다 따로 등록(ASPEED 9 건) — 운영 부담 · 마커 9 벌. 탈락.
- **(b) 채택** — 패키지 하나 + 변형 목록 선언(OS 버전 범위 → 진입점 상대 경로 · 인자). 등록은 한 번, 선택은 규칙. (사용자 답변: b 로 진행)
- (c) 폴더명 규칙으로 자동 추정 — 사용자가 "더하지 않는다" 로 배제. 등록 폼 보조로도 넣지 않는다.

### Q3 설치 방식 — **결정: 진입점 명시 방식(BIOS · BMC 규약 재사용) · INF · MSI · EXE**
- 사용자 답변: "과거 bios, bmc 에서 진입점을 명시하던 것을 그대로 사용한다. INF, MSI, EXE."
- 해석: 변형마다 `entrypointRelativePath` 를 명시하고, 설치 방식은 진입점 확장자가 정한다 — `.inf` → `pnputil /add-driver <진입점> /install`(같은 폴더 하위 포함), `.msi` → `msiexec /i <진입점> /qn /norestart [인자]`, `.exe` → `<진입점> [인자]`. 별도 "설치 방식" 선택 필드를 두지 않는다(진입점이 SSOT).
- 권고 중 답변에 없어 권고대로 가져가는 것: 변형마다 선택 인자(EXE · MSI 추가 인자) 문자열 1 개, 재부팅 요구 플래그 1 개. 한 변형에 INF 와 MSI 가 둘 다 있으면 운영자가 진입점으로 하나를 고른 것이므로 "우선순위" 규칙은 필요 없다.
- 자원 단위의 기존 `entrypointRelativePath` 는 변형 목록으로 옮긴다(변형이 하나뿐인 패키지도 변형 1 행으로 표현) — 자원과 변형에 진입점이 둘 있으면 SSOT 가 갈라진다.

### Q4 선별 시점과 자리 — **답변 없음 → 권고 (c) 채택**
- (a) 게스트별 `$OEM$` — 설치 원본을 게스트마다 분기해야 해 인프라 변경이 크다. 탈락.
- (b) 전체 적재 + 게스트가 보드 · OS 빌드를 읽어 선택 — 판단이 게스트 스크립트에 숨고 서버 화면 · 로그에 남지 않는다. 탈락.
- **(c) 채택** — 서빙 시점에 서버가 게스트의 보드 모델과 대상 OS(이미지 · 버전)로 설치 목록을 계산해 게스트에 전달한다(FirstLogonCommands 인자 또는 게스트별 작은 목록 파일). `$OEM$` 은 전체 패키지를 싣되 SetupComplete 는 목록에 있는 진입점만 실행한다. 판단 결과는 원장 meta 와 상세 화면에 남는다.

### Q5 사용성 범위 — **답변 없음 → 권고 채택**
- 등록 폼의 OS · 변형 선언 UI(표 편집) · 대시보드의 보드 × OS 적용 현황표 · 정의서 · 할당 시점 누락 경고(막지 않고 안내) · 변경 뒤 자동 조립과 미반영 표시(수동 [조립] 유지). 넷 다 범위에 넣되 슬라이스 셋으로 나눈다(§3).

### Q6 마이그레이션 — **답변 없음 → 권고 채택**
- 기존 4 건은 OS 를 Windows(계열)로 일괄 지정하고 변형은 비운 채 시작한다. 변형이 없는 패키지는 현행과 같이 트리 전체 INF 로 다룬다(회귀 없음). ASPEED 는 운영자가 변형(Server 2025 → `WDDM Installer/Win2025.msi` 등)을 선언하는 순간부터 새 규칙을 탄다.

## 3. 슬라이스 분할(결정)

| 슬라이스 | 범위 | 결정 근거 |
|---|---|---|
| **R15-1 모델 · 등록** | `Subprogram` 에 `osName`(nullable) 추가 · 변형 엔티티(`SubprogramVariant`: OS 버전 범위 · 진입점 상대 경로 · 인자 · 재부팅 플래그) · 등록 · 수정 폼의 변형 표 편집 · 자원 단위 `entrypointRelativePath` 의 변형 이관 · 마이그레이션 DDL(기존 4 건 Windows) | Q1 · Q2 · Q3 · Q6 |
| **R15-2 조립 · 설치 선별** | 서빙 시점 선택 목록 계산(보드 × OS 버전 → 변형) · 게스트 전달 · SetupComplete 의 진입점별 실행(INF · MSI · EXE) · 원장 meta · 상세 표시 · 변형 없는 패키지의 현행 경로 유지 | Q4 |
| **R15-3 현황 · 경고 · 자동 조립** | 보드 × OS 적용 현황표 · 정의서 · 할당 시점 누락 안내 · 변경 뒤 AFTER_COMMIT 자동 조립 · 미반영 표시 | Q5 |

검증 줄기 기준(슬라이스 분할 규율)으로 셋이 서로 다른 CP5 이야기다 — R15-1 은 등록 화면, R15-2 는 설치 하네스 · 모의 게스트, R15-3 은 대시보드 · 할당 화면.
