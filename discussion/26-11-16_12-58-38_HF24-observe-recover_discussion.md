# HF24 토론: 부트 순서를 예측하지 않고 관측과 복구로 다룬다

작성 2026-11-16 12:58 KST. HF24 의 후속 토론 문서다. 로드맵과 실측 절차는 다시 적지 않고, 새 관측과 그에 따른 방향 전환만 다룬다. 실측 절차는 `discussion/26-10-27_08-38-11_HF24-netfirst_fieldwork.md`, 10-26 실측 기록은 `sbx-hf24/evidence/2026-10-26-swap/observations.md` 에 있다.

## 1. 새 관측

10-26 실험 뒤 PXE 서버 동작 테스트에서 메인보드 2 종, 서버 8~10 대를 돌렸다. 아래 관측은 폴링이나 모니터가 아니라 변화가 보인 시점의 순간 관측이다.

| 그룹 | 정의서 범위 | 관측 |
|---|---|---|
| 1 | 펌웨어 굽기, 설정, RAID 구성 | 마지막에 UEFI 셸로 떨어졌다 |
| 1 | RAID 구성만 다시 실행 | 정상 부트 순서로 돌아왔다 |
| 1 | 펌웨어 굽기, 설정 | 부트 순서가 Disk, CD, USB, UEFI Shell, Network 였다 |
| 2 | 전 단계 (Windows Server 2025 설치 포함) | 일부 서버는 Windows 설치의 마지막 부팅에서 부트 순서가 바뀌었다. 나머지는 바뀌지 않아 중단 없이 Windows 완료 보고까지 갔다 |

PXE 서버가 개입하면서 부트 순서가 어떻게 바뀌는지가 뒤섞였고, 예측도 매우 어려워졌다. 그래서 바뀌는 방식을 예측하기보다 더 쉬운 해결책을 새로 구상하는 편이 낫다고 판단했다.

## 2. 이전 실험 결과로 읽은 새 관측

### 그룹 1: 셸에 떨어진 것은 순서 표류다

10-26 에 BIOS 셋업 화면에서 확인한 공장 기본 FBO 는 `HD, CD, USB, NET, AP(셸)` 이다(`observations.md` 30 행). 관측된 순서 Disk, CD, USB, Shell, Network 는 여기서 NET 과 셸의 자리만 서로 바뀐 것이다.

공장 순서였다면 OS 가 없는 디스크를 건너뛴 뒤 네트워크로 가므로 셸에 닿지 않는다. 그러므로 이 셸 낙하는 OS 가 없어서 생긴 당연한 결과가 아니라 순서가 표류한 결과다. HF19 때 2호기 계측에서 본 NET 과 AP 의 맞바뀜과 같은 모양이다.

RAID 구성만 다시 실행했을 때 원래대로 돌아온 경로는 순간 관측이라 단정할 수 없다.

### 그룹 2: Windows Setup 의 쓰기가 Once 세션 경계에 걸린다

지금 엔진은 Windows Setup 을 HDD_ONCE 오버라이드 세션 안에서 진행한다. 10-26 R3 에서 확인한 것처럼, 오버라이드 세션 안에서 OS 가 쓴 BootOrder 는 다음 되돌림 POST 에서 버려진다(`observations.md` 120 행).

따라서 Setup 이 순서를 쓰는 시점이 세션 경계의 어느 쪽에 걸리느냐에 따라 서버마다 결과가 갈렸다고 보면 설명이 된다. 일관된 해석이지만 증명된 것은 아니다.

### 공통점: 순서 변화는 오버라이드 주변에서만 기록됐다

| 상황 | 기록된 결과 |
|---|---|
| 오버라이드 POST (R1) | 오버라이드 대상 그룹이 FBO 1 번과 자리를 바꾸고, BootOrder 가 그 순서로 다시 모인다 |
| 그 다음 POST (되돌림) | 세션 전 순서로 돌아가고, 세션 안에서 쓴 값(OS 의 쓰기, Redfish PATCH)은 버려진다 |
| 오버라이드 없는 POST (R2) | 세션 밖에서 쓴 BootOrder 가 유지된다 (3/3) |

엔진이 오버라이드 직전에 `settle(SHELL_LAST)` 로 BMC 의 BootOrder 를 읽어 다시 쓰는 동작이 세션 중의 임시 순서를 굳힌다는 가설(`observations.md` 149 행)도 오버라이드가 있어야 성립한다.

정리하면, 뒤섞임의 주된 출처는 Once 세션이다. Once 세션과 BIOS 가 스스로 하는 POST, Windows Setup 의 쓰기가 겹치기 때문에 예측이 안 된다. Once 를 쓰지 않으면 남는 규칙은 R2 하나다.

## 3. 제안

1. **Once 를 쓰지 않는다.** 네트워크 부팅이 필요하면 부트 순서 자체를 네트워크 우선으로 바꾼다.
2. **순서를 넣는 시점을 확실히 한다.** BIOS 는 POST 때 자기 값을 BMC 로 밀어 넣는다. 그러므로 우리가 재시작을 보내기 직전에 순서를 넣는다.
3. **재시도와 네트워크 부팅으로 복구한다.** 의도하지 않은 부팅(UEFI 셸 등)이 감지되면 네트워크로 다시 부팅시킨다.
4. **프로비저닝이 개시되면 서버마다 감시를 돌린다.** 감시는 Provisioning Server 와 값을 주고받는다. 문제가 생기면 사용자에게 바로 알리거나 자동으로 복구한다.

10-27 에 제안한 네 정착 시점(개시, Windows 착수, 완료, 실패)은 그대로 유지한다.

## 4. 요소별 검토

| 요소 | 이전 실험의 근거 | 의견 |
|---|---|---|
| 재시작 직전에 순서 넣기 | BMC 는 PATCH 받은 값을 다음 POST 까지 들고만 있다가 BIOS 에 넘긴다. 시험 A 에서 이 값이 덮인 것은 그 POST 가 되돌림 POST 였기 때문이다. 오버라이드가 없으면 그 POST 는 R2 를 따르므로 값이 적용될 것으로 예상한다. 직전에 넣으면 그 사이에 BIOS 가 스스로 POST 할 틈도 줄어든다 | 유효하다. 단 오버라이드 없는 상태에서 Redfish PATCH 가 적용되는지는 아직 재지 않았다 (netfirst 시험 1) |
| 적용 확인 | BIOS 는 매 POST 마다 실제 BootOrder 를 BMC 로 밀어 준다. 그래서 POST 뒤에 읽은 BMC 값은 믿을 수 있고, PATCH 직후에 읽은 값은 믿을 수 없다 | 순서 넣기, 재시작, POST 뒤 다시 읽어 비교하기를 한 묶음으로 한다 |
| 네트워크 부팅으로 재시도 | 복구 동작을 "네트워크 우선 PATCH 후 강제 재시작"으로 하면 Once 가 필요 없다. 셸에 떨어진 상태에서도 BMC 로 리셋하면 빠져나온다 (10-26 실증) | 유효하다 |
| 셸 낙하 감지 | 10-26 폴러 기록에서는 Redfish 로 셸 상태를 따로 구분해 주는 신호를 찾지 못했다. 또 셸 말고도 멈춤, iODD 부팅, 엉뚱한 디스크 부팅이 같은 증상을 낸다 | 셸을 직접 잡지 않고 **와야 할 연락이 시간 안에 오지 않는 것**으로 감지한다. 연락은 PXE 요청, 진단 에이전트 체크인, Windows 완료 보고처럼 엔진이 이미 받는 것들이다 |
| 감시의 형태 | Redfish 클라이언트, 자격 증명 읽기, SSE 알림, 단계 상태가 이미 엔진 안에 있다. 별도 Python 프로세스로 두면 배포 방법, 자격 증명 처리, 엔진과의 통신, 프로세스 수명을 새로 만들어야 한다 | 엔진 안의 스케줄러로 둔다. `sbx-hf24/boot-poll.py` 는 진단 도구로 남기고, BootOrder 변화 기록만 엔진이 함께 남긴다. 그러면 앞으로의 실기 관측이 순간 관측이 아니라 기록이 된다 |

이 방식은 BIOS 동작을 모형으로 맞히는 대신 결과를 관측해 고친다. 순서가 왜 바뀌었는지 몰라도, 와야 할 연락이 오지 않으면 같은 복구를 하면 된다. 그래서 아직 원인을 모르는 후보들(굽기 뒤 초기화, Setup 이 새 항목을 만들 때)도 따로 풀지 않고 함께 덮인다.

## 5. 열린 질문

각 질문 아래 인용문으로 답을 적는다.

### Q1. 감시는 엔진 안에 두는가, 별도 프로세스로 두는가

4 절의 이유로 엔진 안 스케줄러를 제안한다. 별도 프로세스가 필요한 사정(엔진 재시작과 무관하게 돌아야 한다 등)이 있으면 알려 달라.

> 답: claude 를 통해 python 으로 모니터링 했을 때 boot order 등을 확인한 것에 기반한 아이디어다. 스케줄러의 경우 일정 간격으로 확인하는 것이지만, python 으로 할 경우 listening 이 되는 것으로 생각했다. 동일한 엔진 내에서도 listening 을 통한 실시간 감지가 가능하면 그렇게 하는 방향 검토.

### Q2. 감지 기준을 "연락 부재"로 해도 되는가

셸을 직접 감지하지 않는 대신, 단계마다 기다릴 연락과 시한을 정한다. 예를 들어 재시작 뒤 PXE 요청이 몇 분 안에 오지 않으면 잘못 부팅한 것으로 본다. 시한은 단계마다 다르게 둔다.

> 답: 안된다. 이 기준은 조금 더 상세하게 세워야 한다. 단순 연락 부재는 사내 상황에 따라 다양하게 해석될 여지가 있다.

### Q3. 감시가 멈춰야 하는 구간

BIOS 와 BMC 를 굽는 동안, BMC 가 재부팅하는 동안, 설정 적용으로 BIOS 가 스스로 재시작하는 동안에는 감시 시한을 늘리거나 감시를 멈춰야 한다. 감시가 단계를 모른 채 리셋을 보내면 보드를 망가뜨릴 수 있다. 이 구간 목록이 맞는지, 빠진 것이 있는지 확인이 필요하다.

> 답: 우선은 맞는 듯하다.

### Q4. 재시도 상한과 실패 처리

상한을 넘으면 실패로 처리하고 사용자에게 알린다. PATCH 가 계속 무시되는 보드에서 재시작이 끝없이 반복되지 않게 하려는 것이다. 상한 횟수와, 알림을 화면 표시로 할지 다른 경로로 할지 정해야 한다. 재시도 로직 공통화가 이뤄지면 그 상한을 따른다.

> 답: 알림은 추후 microsoft teams 의 workflow 카드 또는 메일 발송 등을 이용한다. 사용자는 화면을 지속적으로 보고 있지 않는 다는 전제 하에 개발이 이루어졌다.

### Q5. "네트워크 우선"의 정의

표준 순서에서 연결된 NIC 하나만 맨 앞으로 옮긴 것으로 정의하기를 제안한다.

- 표준으로 되돌릴 때는 그 NIC 만 원래 자리로 옮기면 된다.
- 나머지 NIC 가 바로 뒤에 붙지 않으므로, PXE 시간 초과를 NIC 수만큼 기다리는 일이 생기지 않는다.

netfirst 실측 문서의 정의(연결된 NIC, 나머지 NIC, 셸 맨 뒤)와 다르므로, 채택하면 그 문서도 고친다.

> 답: 그냥 네트워크 부트 자체를 옮겨도 무방하다. 기다리는 시간이 길지 않고, 현재 개발하는 서버 외 네트워크 연결로 PXE 부팅을 해야 하는 경우가 없다. 하나의 NIC 만 넣는 경우는 오히려 BIOS 에서 추후 사람이 수동으로 검증하고 원복시킬 때 더 귀찮아질 우려가 있다.

### Q6. Windows 단계에서 표준 순서로 되돌리는 시점

표준 순서로 되돌리는 PATCH 와 Windows Setup 의 순서 쓰기가 같은 POST 에 겹치지 않아야 한다. 그래서 wimboot 를 받기 전에 되돌리고, 그 POST 뒤에 확인하기를 제안한다. 10-27 제안의 2 번 시점과 같다.

> 답: Windows 설치 과정에서는 netboot 가 굳이 이루어지지 않아도 되므로, RAID Config 단계 완료 이후 Win 설치로 넘어갈 때부터는 boot order 변경 patch 를 보내지 않는다. 현행의 'windows 설치 도중 netboot 시 exit 처리'만 있어도 충분.

### Q7. 마지막 표준 순서의 확인

완료나 실패 때 표준 순서를 PATCH 해도, 그 뒤 POST 가 한 번도 없으면 값은 BMC 에만 걸려 있다. 확인하려면 재시작이 한 번 필요하다. 확인용 재시작을 넣을지, 확인 없이 넘길지 정해야 한다.

> 답: 불요. 어차피 수동 QC 공정 수행을 위해 사람이 직접 재시도를 몇번이고 더 한다.

## 7. 첫 관문

감시와 재시도는 시험 결과와 무관하게 쓸모가 있다. 하지만 복구 동작 자체가 "PATCH 후 재시작"이므로, netfirst 실측 문서의 시험 1 이 통과해야 이 방식 전체가 성립한다. 새 MS74-HB0 서버가 준비되면 시험 1 부터 진행한다.

> 아울러, 더이상 PXE 서버의 본격적인 사용을 지체할 수 없는 상황이다.
> 최대한 임시방편으로라도 boot order 에 대한 문제를 해결하고, 필요한 부가 기능을 서둘러 구현한 뒤 사용 매뉴얼 작성 등 후속 작업을 진행해야 한다. 일정이 이렇다는 사실을 인지해둘 것.

| Q7 마지막 확인     | 확인용 재시작은 넣지 않는다. 수동 QC 에서 사람이 여러 번 재부팅한다                                                                          |
| 일정            | PXE 서버 본격 사용을 더 늦출 수 없다. 임시방편이라도 부트 순서 문제를 먼저 해결하고, 부가 기능, 사용 매뉴얼 순으로 간다                                          |

Q6 에 따라 10-27 의 네 정착 시점 중 "Windows 착수" 는 빠진다. 남는 정착 시점은 개시, 완료, 실패 셋이다.

### 더 다룰 것

- **Q1 감시 방식.** 10-26 의 `boot-poll.py` 는 이벤트를 받은 것이 아니라 10 초마다 BMC 를 조회해 바뀐 값만 기록한 것이다. 엔진 안에서도 같은 방식이 가능하다. PXE 요청, 에이전트 체크인, Windows 완료 보고는 엔진이 직접 받으므로 원래부터 실시간이다. BMC 가 값을 밀어 주는 Redfish 이벤트 구독은 이 BMC 에서 지원 여부와 부트 순서 변화가 이벤트로 오는지를 재 보지 않았다.
	> 이벤트 방식이 아니면 엔진에 통합시켜서 진행. redfish event 방식과 같은 복잡한 방식은 요구되지 않으며, 일정에 맞지도 않는다.
- **Q2 감지 기준.** 연락 부재만으로는 사내 네트워크 문제와 부트 순서 문제를 가르지 못한다. BMC 쪽 사실(POST 뒤 BootOrder 첫 항목)과 서버 쪽 사실(PXE 요청 도착 여부)을 함께 보고, 부트 순서 문제일 때만 자동 복구하고 그 밖에는 알림만 보내는 기준을 따로 세운다. 이 BMC 는 BootProgress 를 주지 않아(10-26 폴러 기록에서 값 없음) 순서가 바뀌지 않은 POST 는 BMC 조회만으로 보이지 않는다는 제약이 있다.
- 일정상 감시와 자동 복구는 부트 순서 정정과 분리해 후속으로 둘지 정해야 한다.

> 임시방편으로 한다는 의미는 다음과 같다: boot order 변경이 필요했던 이유는 '기존에 디스크에 무언가 설치되어 있던 서버를 프로비저닝'할 때 디스크 부팅이 아닌 네트워크 부팅이 우선되도록 하기 위함이었다. 그러나 대부분의 경우 아무것도 설치되지 않은 서버를 프로비저닝 하므로, boot order 를 건들이지 않는다 하더라도 기본 순서에 따라 netboot 가 shell 에 당연히 우선되며 window 설치 도중에도 이 문제는 자연히 해결된다. 이 경우 사용자에게 알림을 보내야 하는 경우는 오직 프로비저닝이 도중에 실패했을 경우 뿐이다.
## 9. 임시방편 결정 (2026-11-16 후속 첨언 반영)

### 정해진 것

| 항목    | 결정                                                 |
| ----- | -------------------------------------------------- |
| Q1 감시 | 이벤트 방식이 아니면 엔진에 통합한다. Redfish 이벤트 구독 같은 방식은 쓰지 않는다 |
| 부트 순서 | **건드리지 않는다.** Once 도 BootOrder PATCH 도 보내지 않는다     |
| 알림    | 프로비저닝이 도중에 실패했을 때만 보낸다                             |

근거는 사용자 판단이다. 부트 순서를 바꿔야 했던 이유는 디스크에 이미 무언가 설치된 서버를 프로비저닝할 때 네트워크 부팅을 앞세우기 위해서였다. 그러나 대부분은 빈 서버를 프로비저닝한다. 공장 순서(디스크, CD/DVD, USB, 네트워크, 셸)에서 빈 디스크는 건너뛰므로 네트워크가 셸보다 먼저 온다. Windows 설치 중에도 Setup 이 디스크 항목을 만들고 나면 디스크로 부팅하므로 문제가 생기지 않는다.

이전 실험 결과와도 맞는다. 오버라이드 없이 설치한 09-04 실기와 사람이 iODD 로 설치한 경우는 무사했고, 기록된 순서 변화는 모두 Once 나 Continuous 를 쓰는 동안 일어났다. 오버라이드가 없으면 Windows Setup 이 쓴 순서도 유지된다(R2). 그룹 2 의 원인으로 추정한 "되돌림 POST 가 Setup 의 쓰기를 버리는 일"도 함께 사라진다.

### 이 방식의 전제와 전제가 깨질 때

| 전제 | 깨지는 경우 | 결과와 대응 |
|---|---|---|
| 서버의 순서가 공장 순서다 | 지난 시험에서 이미 순서가 흐트러진 서버 (11 월 그룹 1 처럼 셸이 네트워크 앞) | 셸에 떨어져 복귀 시한 뒤 실패로 끝난다. 다시 쓰기 전에 BIOS 셋업에서 순서를 공장 순서로 한 번 되돌린다. 매뉴얼에 넣는다 |
| 디스크가 비어 있다 | 기존 OS 가 남은 서버 (회수 재투입 등) | 디스크로 부팅해 PXE 가 오지 않고 실패로 끝난다. 매뉴얼에서 디스크를 비우거나 BIOS 에서 네트워크를 앞세우게 안내한다 |
| USB, CD 에 부팅 매체가 없다 | iODD 등이 꽂혀 있다 | 네트워크보다 먼저 부팅한다. 매뉴얼에서 분리하게 안내한다 |
| BIOS 가 스스로 순서를 바꾸지 않는다 | 재생성 (셸이 맨 앞, 09-17 MS04-CE0 과 10-23 MS74-HB0) | 오버라이드를 쓰던 실행에서만 관측했고, 뒤에 FBO 그룹 순서를 따르는 것으로 재해석했다. 공장 FBO 에서 일어나면 셸에 떨어져 실패로 끝나고 알림이 간다 |

### 실패 감지는 이미 있다

굽기 뒤 전원 투입과 설정 적용 뒤 재시작을 기다리는 단계에는 복귀 시한(`provision.execution.return-timeout`, 기본 20 분)이 있고, 넘으면 실패로 닫힌다. 그러므로 감시를 새로 만들지 않아도 실패는 잡힌다. 새로 필요한 것은 실패를 사용자에게 보내는 알림(Teams 워크플로 카드나 메일)이고, 이것은 부트 순서 정정과 별개의 부가 기능이다.

### 코드에서 빠지는 것 (plan 에서 확정)
