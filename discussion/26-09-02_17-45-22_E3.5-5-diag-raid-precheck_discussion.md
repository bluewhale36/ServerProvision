# E3.5-5 토론 아카이브 — 진단 시점 RAID 사전 파악 · 카드 관측 채움 (2026-09-02, KST)

토론은 Notion 단계 페이지 `E3.5-5`(https://app.notion.com/p/3ceef0e868f98140991fdaa70fb99544)의 `## 토론` 절에서 진행했다. 후속 문서이므로 E3.5 로드맵은 재기술하지 않는다(`discussion/26-08-28_14-58-50_E3.5-0-3-raid-rule-execution_discussion.md`).

## 1. 출발점
2026-09-01 RAID 실기(CP7)에서 두 공백이 드러났다 — ① 최초 진단의 디스크 수집이 lsblk 가시분이라 RAID 카드 뒤 물리 디스크가 비어 나온다(원장 `disks: []`) ② raid_card 자원에 PCI Subsystem 이 등록돼 있지 않아 집행의 카드 대조(CARD_MISMATCH)가 전 사이클에서 생략됐다. E3.5-7-b(집행 전 확인 게이트)는 plan 만 산출한 채 보류하고 이 단계를 선행한다(사용자 지시).

## 2. 실태 (2026-09-02 코드 실측 — dev 8ee80fb)
1. 진단 수집 보고는 JSON 한 벌(`build_report_json` → `DiagnosticReportParser` → `HardwareSpec`). PCIe 행 분류로 RAID 카드의 존재 · 모델은 이미 알지만 lspci 를 `-nn` 없이 돌려 PCI id 는 없다.
2. 카드 뒤 디스크 채집은 RAID phase 의 step 에서만 — `collect_raid_report` 봉투(`tool · lspci_b64 · pd_b64 · vd_b64 · c0_b64 | display_b64`) → `RaidInventoryParser` → `guest_server_detail.raid_inventory_json`. 상세의 RAID 인벤토리 · 계획 카드는 JSON 이 있으면 phase 무관 렌더.
3. raidChips 힌트는 RAID 지시 응답에만(`AgentReportService.raidChipsFor`).
4. 카드 대조는 RAID phase 인벤토리 소비에서, 자원에 Subsystem 이 있을 때만(`cardMatches` — null 이면 대조 생략 WARN).
5. 자원 Subsystem 은 관리 폼으로만 들어가고 HMAC 마커 manifest(ATTR_PCI)에 포함 — 갱신은 관리 서비스 경유 재서명.
6. 도구(storcli64 · sas3ircu)는 apkovl 동봉, `ensure_raid_driver` 관용 로드. agent.sh 변경 = apkovl 재포장(KEYS_DIR 함정).
7. 하네스 `diagnose-cycle.sh` 는 수집 JSON 을 문자열로 이스케이프 — RAID 봉투를 같은 방식으로 덧붙일 수 있다.
