## 0. 이 단계가 왜 생겼는가

OPS-1 이 "누가 무엇을 만질 수 있는가" 를, OPS-2 가 "무엇이 어디에 놓이는가" 를 정했다. 그런데 그 둘은 약속일 뿐 강제되지 않는다. 애플리케이션이 침해당하거나 코드가 실수하면 약속 밖으로 나갈 수 있다. **약속을 OS 기능으로 강제할 수단을 정하는 것**이 이 단계다.

착수 시점의 열린 부채가 셋이었다. E1-I-3-c 가 SELinux 를 비활성 상태로 전제하고 컨텍스트 복원 단계를 두지 않은 것, 특권 위임이 dhcpd 용 sudoers 두 줄로만 서 있어 E2와 E3 이 오면 자랄 것이라는 것, 그리고 OPS-2 에서 넘어온 loop 마운트 분기의 처분이다.

## 1. 확정된 결정

**D1. SELinux 는 enforcing 을 유지하고 애플리케이션은 제약 없는 도메인에서 돌린다.**

전용 정책 모듈은 만들지 않는다. 이 선택의 성질을 분명히 해 둔다 — 애플리케이션 자신은 SELinux 로 가둬지지 않는다. 얻는 것은 dhcpd 와 tftp 같은 시스템 데몬의 배포판 정책이 그대로 살아 있어 그쪽이 우리 파일을 읽는 경로가 정책으로 검증된다는 것, 그리고 사내 보안 정책이 SELinux 활성을 요구해도 충돌하지 않는다는 것이다.

정책 모듈은 새 경로나 새 특권 동작이 생길 때마다 함께 고쳐야 해 슬라이스마다 부채가 붙는다. 지금 규모에서 값이 맞지 않는다고 판단했다. 애플리케이션을 가두는 자리는 D2 가 맡는다.

**D2. systemd 하드닝을 걸되 `NoNewPrivileges` 는 포기한다.**

```
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
ReadWritePaths=/var/lib/serverprovision
ReadWritePaths=/var/log/serverprovision
ReadWritePaths=/etc/dhcp
```

`NoNewPrivileges=yes` 는 하드닝에서 가장 강력한 항목이지만 켜면 `sudo` 가 동작하지 않아 dhcpd 문법 검사와 재기동이 전부 막힌다. 특권 동작이 셋뿐이고 그마저 `AllowedCommand` 화이트리스트를 반드시 거치므로, 이 항목이 막으려는 위험은 이미 상당 부분 코드 구조가 막고 있다고 보았다.

**D3. 업로드 실행 파일 정책은 현행 허용을 유지한다.**

OPS-2 에서 자원 볼륨에 `noexec` 를 걸기로 했으므로 업로드된 실행 파일이 서버에서 돌지 못하는 것은 마운트 옵션이 보장한다. 드라이버와 유틸리티에는 실행 파일이 정상적으로 들어 있어 막으면 오히려 정상 자원을 거절한다.

**D4. 특권 위임은 현행 sudoers 방식을 유지한다.**

`AllowedCommand` 에 상수를 추가하고 sudoers 에 줄을 더하는 방식을 계속 쓴다. 특권 헬퍼를 별도 서비스로 분리하는 안은 특권 동작이 셋인 지금 구조 비용만 먼저 치르는 것이라 채택하지 않았다. "미래에 갈라질 수 있으니 미리 분리" 를 금지하는 원칙과 같은 판단이다. 동작이 열 개를 넘거나 앱 본체를 강하게 가둘 이유가 생기면 그때 옮긴다.

**D5. sudoers 의 단일 진실 출처를 `AllowedCommand.sudoersLine()` 로 모은다.**

지금 같은 두 줄이 코드와 설치 문서 두 곳에 각각 적혀 있어 명령이 늘 때 한쪽만 고치면 조용히 어긋난다. `sudoersLine()` 은 이미 데이터로 존재하므로 설치 절차가 그 데이터에서 sudoers 파일을 생성하게 한다. 배선은 OPS-4.

**D6. loop 마운트 분기를 걷어내고 압축 해제를 `repodata` 부분 추출로 좁힌다.**

`mount` 를 sudoers 에 여는 것은 채택하지 않았다. `dhcpd -t` 는 검사만 하고 `systemctl restart dhcpd` 는 대상이 고정돼 있는 반면, `mount` 는 임의의 파일시스템을 임의의 위치에 붙일 수 있어 사실상 root 승격 경로가 된다.

그리고 호출자를 확인한 결과 훨씬 싼 해법이 있었다. `IsoPreparationService` 를 쓰는 곳은 `CompsExtractionService` 하나뿐이고, 하는 일은 ISO 안의 `repodata/repomd.xml` 을 찾아 거기가 가리키는 `comps.xml(.gz)` 을 읽는 것이다. 12 GB 를 통째로 푸는 이유가 수백 KB 파일 두어 개를 읽기 위해서였다.

```
지금   7z x <iso> -o<임시디렉토리> -y                 → 12 GB 전부
바꾸면 7z x <iso> -o<임시디렉토리> -y "*/repodata/*"   → 수 MB
```

추출 뒤 `repodata` 를 찾아 훑는 로직은 그대로 두고 뽑는 범위만 좁힌다. 계약도 구조도 바뀌지 않으며 변경은 한 파일에 국한된다. 12 GB 가 수 MB 가 되므로 OPS-2 의 `internal/work/` 용량 문제도 사실상 해소된다.

**D7. 자바로 ISO 를 직접 읽는 것은 조건부 후속 슬라이스로 세운다.**

압축 해제 자체를 없애는 근본 해법이다. 계약을 "탐색 가능한 로컬 경로" 에서 내용 접근자로 바꾸고 구현 셋을 둔다.

```
interface IsoContent extends AutoCloseable
    ├─ 하위 항목 나열(경로)
    ├─ 존재 여부(경로)
    ├─ 열기(경로) → InputStream
    └─ close()

구현
    ├─ DirectoryIsoContent   이미 풀린 디렉토리
    ├─ Iso9660IsoContent     .iso 파일 직접 읽기
    └─ HttpIsoContent        HTTP(S) 미러
```

`RHELCompsExtractor` 안의 local과 http 분기가 이 다형으로 흡수되므로 조건분기가 오히려 줄어든다. `IsoPreparationService` 는 구현을 고르는 팩토리로 축소되고 마운트와 압축 해제와 정리 콜백이 사라진다. 유일한 호출자가 하나라 영향 범위도 작다.

다만 착수 전 실물 Rocky ISO 로 라이브러리를 검증해야 한다. 확인할 것이 셋이다. ① Joliet 과 Rock Ridge 확장을 읽는가 ② 4 GB 초과 파일의 분할 저장을 다루는가 ③ 하이브리드 ISO 에서 UDF 쪽에만 있는 파일이 없는가. 하나라도 걸리면 이 슬라이스는 접고 D6 으로 충분하다.

**D8. 비밀은 `EnvironmentFile=` 로 주입한다.**

유닛 파일과 비밀이 분리되고 파일 권한을 0600 으로 좁힐 수 있다. DB 비밀번호도 같은 파일에 둔다. systemd `LoadCredential=` 이 더 좁지만 익숙하지 않아 실제로 지켜지기 어렵다고 판단했다. 운영자가 이해하고 다룰 수 있는 것이 실제로 지켜지는 것이라는 기준을 따랐다.

**D9. 마커 비밀의 기본값을 제거한다.**

지금은 기본값이 두 겹으로 있다. `application.properties` 의 대체값과 `@Value` 어노테이션의 대체값이다. 그래서 아무 설정 없이도 비밀이 채워지고, 기동 가드는 활성 프로파일이 비어 있으면 개발 환경으로 간주해 경고만 남기고 통과시킨다. 현재 기동 방식이 정확히 그 상태라 실서버에서 그대로 띄우면 기본 비밀로 서명이 시작된다.

두 겹의 기본값을 모두 없앤다. 그러면 환경변수가 없을 때 Spring 이 자리를 채우지 못해 애플리케이션이 시작조차 하지 못하고, "기본값으로 서명이 시작되는" 상황 자체가 성립하지 않는다. 가드 메서드와 프로파일 판정 필드도 함께 삭제된다.

판정만 뒤집는 안보다 이쪽을 택한 이유가 셋이다. ① 판정을 고쳐도 프로파일이라는 간접 지표로 환경을 추측하는 것은 남아, 운영 서버에 `dev` 가 실수로 들어가면 다시 뚫린다. ② `DB_URL` 과 `DB_PASSWORD` 와 `SERVER_PORT` 는 이미 기본값이 없어 환경변수 없이는 앱이 뜨지 않는다. 마커 비밀만 기본값을 갖는 것이 예외였다. ③ 분기를 고치는 대신 분기가 필요한 상황을 없애 코드가 줄어든다.

운영 기동 시 프로파일을 지정하는 것도 승인됐으나, D9 를 택하면 그것은 비밀 가드와 무관해진다. 환경별 설정을 가르는 용도로 별개로 유지한다.

## 2. 조사하며 바로잡은 것

**"앱이 만든 dhcpd 조각을 SELinux 때문에 dhcpd 가 못 읽는다" 는 성립하지 않는다.** OPS-1 에서 부채로 기록했으나 부정확했다. SELinux 에서 새 파일의 타입은 프로세스가 아니라 부모 디렉토리를 따르고, `DhcpdConfigApplyService` 는 `/etc/dhcp` 안에 임시 파일을 만들어 같은 디렉토리에서 원자적으로 이름을 바꾼다. 라벨이 깨질 경로가 아니다.

이 정정으로 SELinux 논의의 초점이 "파일 라벨을 어떻게 맞출 것인가" 에서 "애플리케이션 자신을 가둘 것인가" 로 옮겨 갔고, 그것이 D1의 구도를 만들었다.

**마커 비밀의 기동 가드는 이미 있었다.** 경고만 하는 줄 알았으나 운영 프로파일에서는 예외를 던져 기동을 막는다. 문제는 가드의 부재가 아니라 판정식의 구멍이었다.

## 3. 검토했으나 채택하지 않은 것

**SELinux disabled.** 시스템 데몬 보호까지 잃고 사내 보안 정책과 충돌할 수 있다. 이 프로그램이 세팅 정의서에서 게스트의 SELinux 모드를 지정하는 기능을 이미 갖고 있어, 게스트에는 설정해 주면서 서버 자신은 끄는 구성이 설명하기 어렵다는 점도 걸렸다.

**SELinux 전용 정책 모듈.** 보호는 가장 강하나 정책을 슬라이스마다 갱신해야 해 부채가 누적된다.

**`NoNewPrivileges=yes` 채택.** `sudo` 와 양립하지 않아 특권 동작을 앱 밖으로 빼야 하는데 그 구조 비용을 지금 치를 이유가 약하다.

**특권 헬퍼 서비스 분리.** 앱 본체를 강하게 가둘 수 있으나 프로세스가 늘고 요청 통로와 인증을 새로 설계해야 한다.

**capability 부여.** dhcpd 재기동이 capability 로 대체되지 않아 부분적 해법에 그친다.

**`mount` 를 sudoers 에 등록.** 사실상 root 승격 경로가 되어 특권 하나의 값으로 너무 크다.

**인자를 제한한 sudoers 로 `mount` 살리기, 그리고 `fuseiso` 등 비특권 마운트 도구.** 전자는 패턴 매칭의 우회 여지를 없애기 어렵고, 후자는 패키지 의존이 늘고 Rocky 기본 저장소 제공 여부를 확인해야 한다. D6 의 부분 추출이 훨씬 싸게 같은 목적을 달성해 둘 다 불필요해졌다.

**기동 가드의 판정만 뒤집기.** 추측이 남아 D9 로 대체했다.

## 4. 이 단계 밖으로 넘어간 것

- **설치 자산 일체** → OPS-4. systemd 유닛(D2 의 하드닝 지시자, D8 의 `EnvironmentFile`, OPS-2 의 마운트 의존), sudoers 파일을 `sudoersLine()` 에서 생성하는 절차(D5), 자원 볼륨 마운트 옵션과 EFI 파티션 이중화(OPS-2), 초기 디렉토리와 권한 생성.
- **코드 변경 두 건** → 별도 슬라이스. `IsoPreparationService` 의 loop 마운트 제거와 부분 추출(D6), 마커 비밀 기본값 제거와 가드 삭제(D9). 둘 다 작고 서로 무관하다.
- **자바 ISO 직접 읽기** → 조건부 후속 슬라이스(D7). 착수 전 라이브러리 실물 검증이 선행한다.
- **`DB_FS_CONSISTENCY.md` 갱신** → DOC 계열. 드리프트를 "12 종" 으로 적고 있으나 현재 코드는 11 종이다. 파일명 변경 관련 2 종은 S6-1 에서 삭제됐고 자원 중복 1 종이 HF4-5 에서 추가됐다.
- **T3 실기 검증** → 실 Rocky 호스트 확보 시점. SELinux enforcing 상태에서 dhcpd 가 조각을 실제로 읽는지, `dhcpd -t` 와 `systemctl restart dhcpd` 의 종료 코드와 소요 시간이 설정한 타임아웃 안에 드는지.

## 5. 남은 미확정

없다. 다섯 질문이 모두 답을 받았다.

다만 D1 은 "앱 자신은 SELinux 로 가둬지지 않는다" 는 상태를 의식적으로 수용한 것이므로, 사내 보안 정책이 나중에 애플리케이션 도메인 격리까지 요구하면 전용 정책 모듈을 다시 꺼내야 한다. 그때의 비용은 지금과 같지 않다. 경로와 특권 동작이 늘어난 만큼 커진다.

## 6. 부산물

토론 중 사용자가 마커와 비밀과 reconciliation 의 동작을 이해하기 어렵다고 밝혀, 개념 설명 문서를 Notion 'Provisioning Server' 아래에 만들었다(`마커와 자원 무결성 점검 — 동작 원리`). 단계 페이지 아래가 아니라 상위에 둔 것은 reconciliation 사용성 진단(MK4)의 배경 자료로도 쓰이기 때문이다.

그 문서를 쓰며 확인한 구조적 사실 하나를 여기 옮겨 둔다. **이 도메인이 헷갈리는 데에는 이유가 있다** — 진실의 출처가 항목별로 다르게 정해져 있어서, 자원의 위치와 내용은 파일시스템이 진실이라 운영자가 옮기면 시스템이 DB 를 고쳐 따라가고, 자원의 상태는 DB 가 진실이라 휴지통에 파일을 던져 넣어도 삭제로 해석되지 않는다. 각각은 타당한 이유가 있지만 두 규칙이 한 화면에서 동시에 작동하면 사람이 예측하기 어렵다. MK4 진단에서 먼저 볼 지점이다.
