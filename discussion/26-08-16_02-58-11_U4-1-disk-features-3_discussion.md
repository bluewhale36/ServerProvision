## 2. 내 추천 셋이 기각된 이유

정확히 짚어 두는 편이 다음 판단에 쓰인다.

### 2-1. R-1 ③(관례 + 예외) 기각 — 관례는 코드가 아니라 사람의 것

나는 D5(2개=RAID1, 3개+=RAID5)를 **기본값으로 박고 예외만 적게 하자**고 했다. 기각의 뜻은 이렇게 읽힌다 — 그 관례는 **업무 관습**이지 시스템이 강제할 규칙이 아니다. 박아 두면 관습이 바뀌었을 때 코드를 고쳐야 하고, 정의서를 보는 사람은 **왜 RAID1 인지가 화면에 없어** 기본값을 신뢰해야 한다.

대신 나온 E1~E4 는 더 낫다. **레벨은 반드시 적되, 어느 디스크에 적용할지는 '자동 탐지' 로 비워 둔다.** 즉 비워 두는 축이 "무엇을 할지" 가 아니라 **"무엇에 할지"** 다. 정의서는 여전히 서버를 모르지만 의도는 분명하다.

### 2-2. R-3 의 전제 오류 — 비대칭은 없었다

나는 "Linux 는 설치 시 `/data1` 을 만들고 Windows 는 설치 후 D 드라이브를 잡는다" 는 비대칭을 전제하고, 그것 때문에 단계가 갈린다고 봤다. **E8 이 그 전제를 지웠다** — Linux 도 Data 영역은 설치 후에 잡는다.

이게 이번 회차에서 가장 크게 바뀐 것이다. 비대칭이 없으므로 **계열별로 단계를 가를 이유도 사라졌다.** 대신 다른 것이 드러난다 — §3-1.

### 2-3. §4 의 "비우면 관례" 기각 — 비움은 부재를 뜻한다

나는 RAID 레벨을 비우면 관례대로 자동이라고 스케치했다. E5 는 반대다 — **비우면 RAID 를 구성하지 않는다.** 이쪽이 옳다. 빈 값이 "알아서 해라" 를 뜻하면 화면을 보는 사람이 결과를 예측할 수 없고, `PartitionRequest.diskName` 이 "비우면 설치기가 자동 선택" 인 것과도 층이 다르다. **비움 = 없음**이 일관된다.

## 3. 새로 드러난 쟁점

### R-5. Data 영역 파티셔닝은 **어느 단계**에 사는가 (가장 큰 것)

E8 · E9 가 이것을 강제한다. 지금 파티션은 `LinuxInstallationRequest.partitions` 에 있고 그것은 `OS_INSTALLATION` 단계다. 그런데 Data 영역 파티셔닝은 **설치 이후**다.

현행 단계 넷 — `BASIC_UPDATE` · `BASIC_SETTING` · `OS_INSTALLATION` · `OS_SETTING`.

| | 안 | 뜻 | 걸림돌 |
|---|---|---|---|
| ① | **`OS_SETTING` 확장** | 기존 후처리 단계에 'Data 영역 파티셔닝' 절을 더한다. `OSSettingRequest` 는 이미 2단 다형이고 하위가 `RHELOSSettingRequest` 하나뿐이라 자리가 있다 | 후처리 단계가 "OS 설정" 과 "디스크 작업" 두 성격을 갖게 된다 |
| ② | **새 단계 신설** | `DATA_PARTITIONING` 같은 5번째 `SettingProcessType` 을 만든다 | `ProvisioningPhase` 매핑(`SettingProcessPhaseMapper`)과 실행 순서가 함께 늘어난다. E 단계 골격에 영향 |
| ③ | **OS 설치 단계에 두되 실행만 뒤로** | 정의서 표현은 `OS_INSTALLATION` 에 함께 두고, 집행 시점만 설치 후로 미룬다 | 정의서가 "설치 단계" 라 적어 놓고 실제로는 설치 후에 하는 것이라 **화면과 실행이 어긋난다** |

**내 판단은 ①이다.** ②는 phase 골격(ES 계열이 방금 배선한 것)을 건드려 파장이 크고, ③은 U3-5-d 에서 겪은 "화면이 사실과 다른 말을 하는" 형태다. ①의 걸림돌인 "두 성격" 은 절을 나눠 보여주면 해소된다 — 이미 `OS_SETTING` 은 계열별 다형이라 RHEL 후처리 안에 디스크 절을 두는 것이 부자연스럽지 않다.

> **R-5 답변:**
> 1 진행.

### R-6. OS 영역을 **어느 묶음**으로 정하는가

E7 이 "OS 영역은 반드시 1개" 라고 했다. 그러면 여러 묶음 중 **어느 것이 OS 인가**를 정하는 방법이 셋이다.

|     | 안                   | 뜻                                                                             |
| --- | ------------------- | ----------------------------------------------------------------------------- |
| ①   | **첫 묶음 고정**         | 목록의 첫 줄이 OS 영역. D6(SSD → HDD, 작은 → 큰 장착 순서)과 D2(OS 는 보통 SSD RAID1)가 맞물려 자연스럽다 |
| ②   | **명시 지정**           | 묶음마다 '역할' 을 고른다(OS / Data). 정확히 하나만 OS 여야 한다는 검증이 붙는다                         |
| ③   | **첫 묶음 기본 + 변경 가능** | ①을 기본으로 두되 옮길 수 있다                                                            |

①이면 U4-1-2 가 **거의 사라진다**(순서가 곧 역할이므로 적을 것이 없다). ②·③이면 U4-1-2 가 "역할 지정" 이라는 제 일을 갖는다.

**내 판단은 ②다.** ①은 화면에 역할이 보이지 않아 목록 순서를 바꾸면 OS 영역이 조용히 옮겨간다 — 되돌리기 어려운 조작에 표시가 없다. ②는 한 줄 늘 뿐이고 검증(정확히 하나)이 명확하다.

> **R-6 답변:**
> 2로 진행. 간혹 OS 영역이 단일 NVMe SSD 인 경우가 있다. 디스크는 가장 변동 폭이 큰 하드웨어 스펙이므로 기본 값은 어디에도 두지 않는다.

### R-7. 캐시 있는 RAID 카드를 **어떻게 판정**하는가

E10 · E11 · E12 가 이어진다 — 3개 이상 묶음이면 캐시 있는 카드가 필요하고, 모델이 한정돼 있으며, 캐시 유무에 따라 집행 명령이 다르다.

진단이 지금 수집하는 것은 `PcieDevice(slot, kind="RAID", vendor, model)` 로 **모델명 문자열**뿐이다.

|     | 안                      | 어디에 사는가                                                 |
| --- | ---------------------- | ------------------------------------------------------- |
| ①   | **모델 목록을 코드에 둔다**      | enum 또는 상수 표. 모델이 늘면 배포가 필요하다                           |
| ②   | **management 자원으로 등록** | 관리자가 화면에서 캐시 유무를 등록. `BoardModel` · `Subprogram` 과 같은 결 |
| ③   | **이번엔 판정하지 않는다**       | U4 는 "3개 이상이면 RAID5 가능" 만 적고, 카드 판정은 E 집행 단계로 미룬다       |

E12("명령이 다르다")는 **집행의 문제**라 U4 범위가 아니다. 다만 **정의서 유효성**(이 서버에 이 정의서를 붙일 수 있나)에서는 판정이 필요할 수 있다.

**내 판단은 ③이다.** MVP 기준 모델이 한정돼 있다면 지금 목록을 만드는 값이 크지 않고, ②는 새 관리 자원 하나가 통째로 붙는다. **U4-1-1 은 "RAID 카드가 있는가" 까지만 요구**(E6)하고, 캐시 판정은 E 집행이 붙을 때 함께 설계하는 것이 범위를 지킨다.

### R-8. '자동 탐지' 묶음이 여럿일 때 **어느 디스크가 어느 묶음**인가

E3 · E4 의 결과로 생기는 문제다. 예를 들어 정의서에 이렇게 적혔다고 하자.

```
묶음 1 : RAID1 · 자동 탐지 · 자동 탐지 · 2개
묶음 2 : RAID5 · 자동 탐지 · 자동 탐지 · 3개 이상
```

서버에 SSD 480GB ×2 + HDD 4TB ×4 가 있으면 배정은 자명하다. 그런데 **SSD 480GB ×2 + SSD 960GB ×2 + HDD 4TB ×3** 이면 묶음 1 의 후보가 둘이다.

D6 이 답을 준다 — **장착 순서가 SSD → HDD, 작은 용량 → 큰 용량**이다. 그 순서로 나열해 위에서부터 묶음에 배정하면 결정적이다.

- 정렬 : SSD 480 ×2 → SSD 960 ×2 → HDD 4TB ×3
- 묶음 1(2개) ← SSD 480 ×2
- 묶음 2(3개 이상) ← 남은 것 중 같은 스펙끼리 → HDD 4TB ×3 (SSD 960 ×2 는 3개가 안 되므로 건너뜀)
- 남는 SSD 960 ×2 는 **미배정**

**미배정 디스크를 어떻게 다룰지**가 남는다.

| | 안 |
|---|---|
| ① | 그대로 둔다(OS 가 보지만 아무 파티션도 만들지 않는다) |
| ② | 할당을 막는다 — "정의서가 이 서버의 디스크를 다 쓰지 않는다" 를 오류로 |
| ③ | 경고만 하고 진행 — U3-5-a 의 하드웨어 대조가 '막지 않고 알리는' 축을 이미 갖고 있다 |

**내 판단은 ③이다.** ②는 디스크를 일부러 남기는 정상 운용(예비 슬롯)을 막고, ①은 조용해서 실수를 못 잡는다.

> **R-8 답변:**
> '자동 탐지'의 경우 구성할 RAID 볼륨의 개수 자체를 명시적으로 지정하는 것이 아닌 규칙의 성격에 가까워진다고 생각한다.
> 만일 `묶음 1 : RAID1 SSD 480GB 2개` 와 `묶음2 : RAID5 HDD SATA 4TB 3개이상` 이라면 960GB 2개는 구성하지 않는 것이 맞으나, `묶음 1 : SSD 자동탐지 2개` 의 경우 위 사례에서 그룹핑 할 수 있는 조합이 2개가 되므로 (480GB 2개, 9600GB 2개) 두 개 모두 RAID1 로 구성하게 된다.
> 이해가 가지 않는 부분이 있다면 추가 질문할 것.

## 4. 여기까지의 단계 스케치 (갱신)

R-5 ~ R-8 의 내 판단을 그대로 받으면 이렇게 된다. **확정이 아니다.**

| 단계 | 정의서에 더해지는 것 | 사는 곳 | 무게 |
|---|---|---|---|
| **U4-1-1** RAID 구성 지정 | RAID 묶음 목록 — `{레벨, 종류, 용량, 개수}` × N. 자동 탐지 · 'n개 이상' 지원. RAID 카드 요구는 레벨 유무에서 도출 | `OS_INSTALLATION` 단계 폼에 절 하나 | **중~대** |
| **U4-1-2** 디스크 분류 | 묶음마다 역할(OS / Data). 정확히 하나가 OS | 위 절의 열 하나 | **소** |
| **U4-1-3** 파티션 디스크 지정 | OS 영역 파티션의 대상을 장치명 → **역할**로. Data 영역 파티셔닝은 `OS_SETTING` 에 신설 | 파티션 표 + 후처리 단계 | **대** |

U4-1-3 이 커진 것은 E8 때문이다 — **Data 영역 파티셔닝이 다른 단계에 새로 생긴다.** 쪼갤 여지가 있다(`U4-1-3` = OS 영역 파티션 / `U4-1-4` = Data 영역 파티셔닝).
