## 1. 토론에 들어간 이유

scope 원천이 넷(착수 브리핑 · Notion 페이지 · 실기 decisions · 선행 슬라이스 적립)으로 흩어져 있었고, 항목 중 일부는 이미 다른 슬라이스가 풀었으며, 순수 표시를 넘어 정책 판단(원장에 기록을 늘릴 것인가 · 재시도의 전원 사이클을 의도로 볼 것인가)이 필요한 것이 섞여 있었다. CP1 로 바로 가면 이 판단들이 plan 승인 한 번에 뭉쳐 들어가므로, 착수 전에 질문 8개로 갈라 확정했다.

## 2. 실태 대조가 정리한 것 (코드 실측 결과)

- **기해소 2건**: 서버 상세의 계획 phase rail 진행 결합은 U3-5-a(2026-08-13, cd370e1)가 이미 완료(실제) · 현재(실제) · 예정(계획) 배지로 구현했다 — 잔여는 정의서 선택 폼의 미리보기 rail 안내 문구뿐. flash 시작 시 상세 무갱신(decisions 3)은 `FirmwareFlashCycle` 의 `GuestServerChangedEvent` 발행(2026-08-25 정정)으로 해소 추정 — CP5 확인 항목으로만 남긴다.
- **타 단계 이관 1건**: 서버 목록의 SSE 미반영은 앵커 S7-1 이 원인(nginx 프록시 버퍼링 — 업스트림 HTTP/1.0 + proxy_buffering)을 확정하고 앱의 `X-Accel-Buffering: no` 선언으로 정정 중이다. E2-4 범위에서 제외.
- **표시 결함 발견 1건**: `GuestServerQueryService.flashRemainingMinutes` 가 복귀 대기 구간에서도 축 시한(`limitFor(axis)`)과 `lastTransitionAt` 을 쓴다 — 복귀 대기는 복귀 시한(20분)과 마지막 축 종료 기점(E2.5 `returnWaitSince` 와 같은 결)이어야 한다. E2-4 가 고친다.
- **재해석 1건**: E2.5 F-4(재시도가 `BeginFlashStep` 을 재실행해 ForceOff 1회 추가)는 결함이 아니라, E2.5 D-7 이 표식 문제로 비채택했던 "재시도 뒤 켜진 서버 강제 재시작" 을 기존 재개 규칙이 이미 수행하는 것이다(E2.5 CP5 B3 실측 — 전원 차단 09:05:00 → 무장 + 투입 09:05:08).

## 4. 구현 범위 요약 (CP1 plan 의 입력)

1. 집행 현황 카드의 phase 무관 일반화(펌웨어 축 + 설정 축 — BIOS_SETTING 재부팅 · readback, BMC_SETTING 항목별 결과 · Bond 재접속 대기).
2. 워커 관측 하트비트 표시 — 인메모리 최신 관측(상태 · 시각), 저장 없음.
3. 재부팅~검증~종단 구간 문구 + 복귀 대기 남은 분 계산 정정(복귀 시한 · 축 종료 기점).
4. 전원 · 무장 사건의 원장 instant 행(차단 · 투입 + outcome) — `FlashLedger.isPhaseLevel` 에 새 사유 등록으로 축 상태 계산 오염 방지.
5. 실패 · 대기 사유 표시 — 세부 단계 이력의 `status_meta`(flash 계열 · setting 계열 판독 통일) + `BeginSettingStep` 침묵 대기의 조회 시점 파생.
6. `자원이름 (버전)` 표기(계획 · 집행 카드), BMC 라벨 보강, '집행 중 · 전원 꺼짐'(상세 + 목록), 재시도 버튼의 전원 사이클 안내, 정의서 미리보기 rail 문구 보강.
7. 비목표 개정: "집행 로직 변경 없음" → "판정 · 전이 로직 변경 없음(기록 추가는 허용)".
