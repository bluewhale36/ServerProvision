# E4-1-b-7 OS 후처리 설정 (리눅스 전용) 토론

2026-11-21 Notion 단계 페이지 `E4-1-b-7 : OS 후처리 설정 (리눅스 전용)` 의 토론 절에서 진행했고, 같은 날 종결했다. 이 문서는 그 토론의 아카이브다. 질문마다 대안, 권고, 사용자 답을 남기고 끝에 결정을 정리한다. 본격 명세는 CP1 plan 이 맡는다.

## 배경

R11(세팅 정의서 OS 섹션 표적 축소)은 실행하는 곳이 없다는 이유로 OS 후처리 설정(OS_SETTING) 단계를 정의서의 단계 추가 목록에서 뺐다. RHEL 자동 설치(E4-1-b)가 kickstart 생성과 첫 부팅 완료 보고(b-5)까지 갖추면서, 설치된 서버에 후처리 설정을 적용할 자리가 생겼다. 이 단계는 그 자리를 실제 실행 경로로 연결한다. 옛 E5(OS 후처리)의 교훈도 함께 따른다. 레거시에는 %post 생성 로직이 있었지만 실행 경로에 연결되지 않아 한 번도 실행되지 않았다.

## 토론 시점의 현행 실태 (코드 실측)

| 자리 | 상태 |
|---|---|
| 계약 `RHELOSSettingRequest` | SELinux 모드(enforcing, permissive, disabled), systemd 서비스 지시(이름과 ENABLE 또는 DISABLE), 추가 패키지 이름 목록. 계열은 RHEL 하나만 등록 |
| 정의서 화면 | OS 후처리 단계가 단계 추가 목록에 없고 카드 마크업도 없음(R11). JS 의 수집, 복원 코드는 남아 있음 |
| 저장 검증 | OS 설치와 OS 후처리가 함께 있으면 같은 OS 여야 함(`isOsSelectionConsistent`) |
| 실행 | OS_SETTING phase 실행기 없음. 커서가 OS_SETTING 에 닿으면 PXE `/boot` 가 HOLD 대기 스크립트만 돌려줌 |
| 설치 뒤 서버 | 디스크로 부팅해 설치된 OS 안에서 돎. PXE 를 다시 타지 않으므로 PXE 실행기로는 OS 안 설정을 바꿀 수 없음 |
| kickstart 생성기 | `%packages` 절(환경, 그룹)이 있음. 고유 명령 `selinux`, `services` 는 아직 내지 않음 |
| 첫 부팅 보고(b-5) | 설치된 OS 가 첫 부팅에서 한 번 보고해 OS_INSTALLING 을 닫고 커서를 다음 phase 로 옮김. 서빙 토큰 회수와 설치 트리 반납도 이때 |
| Ubuntu | 설치 계약은 있으나 설치 실행 없음. 후처리 계약 없음 |

## 1차 질문

### Q1. 설정을 어디서 적용하는가

- (a) kickstart 고유 명령으로 설치 중에 적용(권고). `selinux`, `services --enabled/--disabled`, `%packages` 를 쓴다. 쉘 스크립트가 없고 Red Hat 문법 검사기(ksvalidator)로 확인할 수 있으며, 패키지는 우리 서버가 서빙하는 설치 트리에서 받으므로 외부망이 필요 없다.
- (b) 첫 부팅 스크립트가 설치된 OS 안에서 적용. 설치가 끝나면 설치 트리 토큰을 회수하므로(b-5) 추가 패키지를 받을 곳이 없고, SELinux 를 disabled 에서 켜면 재부팅과 relabel 이 필요하다.
- (c) 서버가 SSH 로 들어가 적용. 자격 증명, 접속 경로, 실패 처리를 새로 만들어야 한다.

사용자 답: a 와 b 의 혼합. 고유 명령 세 항목은 RHEL 계열 정의서의 OS 설정 영역에서 작성하고, 여기에 사용자가 쉘 스크립트를 올려 kickstart `%post` 에서 실행하게 한다. 2026-11-19 결정("사용자 쉘 스크립트는 만들지 않는다")을 이 답으로 바꾼다. 스크립트를 자원으로 등록하는 방안이 논의된 적이 있다는 확인 요청이 있었으나, 저장소, 메모리, Notion 어디에서도 기록을 찾지 못해 Q7 로 다시 물었다.

### Q2. OS_SETTING phase 를 어떻게 진행하는가

- (a) 첫 부팅 보고 한 번으로 OS_INSTALLING 을 닫고 OS_SETTING 도 열고 닫는다(권고). 정의서 단계와 진행 레일이 1:1 로 남고, 원장에 OS 설정 행이 따로 생긴다.
- (b) OS_SETTING 을 소유 phase 에서 빼고 OS 설치 결과에 합친다. 레일에서 OS 설정이 사라져 정의서와 화면이 어긋난다.
- (c) OS 설정 보고 창구를 따로 둔다. 같은 부팅에서 보고를 두 번 보내야 해 실패 지점이 늘어난다.

사용자 답: 사용자 스크립트는 적용 여부를 일일이 확인하기 어렵다. 설정 스크립트와 확인 스크립트를 사용자가 함께 정의하게 하는 것은 무리이므로, 종료 코드(0 인지 아닌지)만 확인하고 실제 적용 여부는 사용자가 직접 확인해야 한다는 것을 화면에 분명히 보인다. 그 문구는 디자인 세션이 거절해도 사용자 허가로 통과시킨다. phase 진행은 (a) 를 따른다.

### Q3. 관측값이 정의서와 다를 때

- (a) OS_SETTING 을 실패로 닫고 다른 항목만 실패 사유에 적는다(권고).
- (b) 사실만 기록하고 성공으로 닫는다. 화면에서 놓치기 쉽다.
- 덧붙임: 없는 패키지 이름이 있으면 anaconda 는 기본으로 설치를 멈춘다. `--ignoremissing` 으로 넘기고 관측에서 실패로 잡는 쪽을 권고했다(설치를 처음부터 다시 하지 않아도 됨).

사용자 답: 적용되지 않았으면 실패로 닫는다. SELinux, 서비스 활성 여부, 패키지 설치 여부는 확인 로직이 정해져 있어 성패를 판단할 수 있다.

### Q4. Ubuntu 후처리

- (a) 이번에는 RHEL 계열만 열고 Ubuntu 정의서에서는 OS 후처리를 잠근다(권고). Ubuntu 설치 실행이 아직 없어 후처리를 넣어도 돌 곳이 없다.
- (b) 이번에 Ubuntu 후처리 계약을 만든다. 저장은 되지만 실행에서 막혀 쓸 수 없는 정의서를 만들 수 있게 된다.

사용자 답: a 채택.

### Q5. 정의서 화면에서 OS 를 어떻게 고르는가

- (a) OS 후처리의 선행 단계를 OS 설치로 두고, OS 는 OS 설치 단계의 값을 따른다(권고). HF34 가 만든 선행 단계 선언(`SettingProcessType.requiredStep`)에 한 줄을 더하면 OS 후처리를 넣을 때 OS 설치가 함께 들어가고 OS 설치를 빼는 것은 막힌다. OS 를 두 번 고르지 않으므로 같은 OS 검사가 화면에서 필요 없어지고(서버 안전망은 유지), R11 이 지적한 식별 정보 중복도 풀린다.
- (b) R11 이전처럼 OS 후처리 카드에 OS 선택을 따로 두고 OS 설치 쪽 값으로 고정한다.

사용자 답: a 채택.

### Q6. 옛 E5 페이지

- (a) E5 본문에 RHEL 계열 이관을 적고 남은 범위(Ubuntu, Windows 후처리)를 E5 에 남긴다(권고).
- (b) E5 를 취소하고 남은 범위를 각 OS 설치 슬라이스로 넘긴다.

사용자 답: 본문에 이관을 적고 단계를 취소로 바꾼다(반영 완료).

## 2차 질문

### Q7. 사용자 쉘 스크립트를 어디에 보관하는가

- (a) 정의서 안에 내용으로 저장(권고). 정의서를 할당하면 그 순간이 스냅숏으로 고정되므로(U3), 할당 뒤 스크립트가 바뀌거나 지워져도 할당 때 내용이 실행된다. 재사용은 정의서 복제로 한다. 크기 상한을 둔다.
- (b) 관리 자원으로 등록. 여러 정의서가 공유하고 마커, 휴지통, 무결성 점검을 받는다. 대신 자원 도메인을 새로 만들어야 하고, 할당 뒤 자원이 바뀌거나 지워지는 경우를 실행 준비도와 개시 가드에서 따로 막아야 한다.
- (c) 정의서가 서버 디스크의 파일 경로를 가리킨다. 파일이 바뀌어도 알 수 없어 탈락.

사용자 답: a 채택. 정의서 복제 기능이 없으므로 구현이 간단하면 b-7 구현 전에 선행한다. 이에 따라 U9(세팅 정의서 복제)를 먼저 진행했다(PR #131).

### Q8. 스크립트 개수, 순서, 실행 조건

- 여러 개를 정의서에 적은 순서대로 실행한다(권고). 하나만 허용하면 사용자가 스크립트를 한 파일로 합쳐야 한다.
- 실행 위치는 설치된 시스템으로 chroot 한 `%post` 다(권고). 망과 설치 트리 저장소를 쓸 수 있지만 systemd 가 돌지 않아 `systemctl start` 같은 즉시 실행 명령은 동작하지 않는다(`enable` 은 됨).
- 순서는 설치 본체(고유 명령), 사용자 스크립트들, 첫 부팅 보고 장치 심기(b-5) 순이다. 보고 장치를 마지막에 두어 사용자 스크립트가 무엇을 하든 보고가 남게 한다.
- 인터프리터는 bash 하나로 고정한다(권고). python 등은 최소 설치에 없을 수 있다.

사용자 답: 권고안 채택.

### Q9. 스크립트가 실패하면

- 설치를 멈추지 않는다(권고). 스크립트마다 `%post` 를 따로 두고 `--erroronfail` 을 붙이지 않는다. 멈추면 서버가 설치 화면에 서고 첫 부팅 보고도 오지 않아 시한 실패로만 보인다.
- 하나라도 종료 코드가 0 이 아니면 OS_SETTING 실패다(권고). 모두 0 이면 성공으로 닫고 적용 여부는 직접 확인해야 한다는 문구를 보인다.
- 각 스크립트의 종료 코드를 설치된 시스템의 결과 파일에 적고 첫 부팅 보고가 함께 보낸다.
- 출력은 스크립트마다 `/root/spv-script-<번호>.log` 에 남기고 보고 뒤에도 지우지 않는다(권고). b-5 의 자기 삭제는 우리가 심은 파일만 지운다.

사용자 답: 권고 채택.

### Q10. 업로드 검증과 권한

- 권한: 정의서를 작성, 수정할 수 있는 지금 권한 그대로 둘지, 관리자 이상으로 좁힐지.
- 내용 검증(권고): UTF-8 텍스트만, 크기 상한, `%` 로 시작하는 줄 거부(kickstart 절 표지라 `%end` 같은 줄이 있으면 kickstart 가 깨진다). `bash -n` 문법 검사는 서버에 bash 가 있어야 해서 넣지 않는다.
- 주의: 스크립트 내용은 설치된 서버의 `/root/anaconda-ks.cfg`, `/root/original-ks.cfg` 에 그대로 남는다. 비밀값을 쓰지 않도록 화면에 안내할지.

사용자 답: 권한은 그대로, 내용 검증과 주의 안내는 권고대로.

### Q11. 정의서 화면의 OS 후처리 카드

- (a) 카드 하나에 두 영역(권고). 위 '기본 설정'(SELinux, 서비스, 추가 패키지), 아래 '추가 스크립트'(업로드, 순서 바꾸기, 삭제, 직접 확인 안내).
- (b) 정의서 단계를 OS 후처리와 추가 스크립트 둘로 나눈다. 정의서 단계와 phase 대응이 늘어 레일과 원장이 복잡해진다.

사용자 답: a 채택.

## 결정

1. 적용 매체는 kickstart 고유 명령과 사용자 쉘 스크립트의 혼합이다.
   - 고유 명령: `selinux`, `services --enabled/--disabled`, `%packages` 에 개별 패키지(`--ignoremissing`).
   - 사용자 스크립트: chroot `%post`, bash, 여러 개를 순서대로, 스크립트마다 `%post` 하나, `--erroronfail` 없음.
2. 실행 순서는 설치 본체, 사용자 스크립트들, 첫 부팅 보고 장치 심기(b-5) 순이다.
3. 첫 부팅 보고 한 번으로 OS_INSTALLING 을 닫고 OS_SETTING 도 열고 닫는다.
4. 판정
   - 고유 명령 세 항목은 관측값(SELinux 현재 모드, 서비스 활성 여부, 패키지 설치 여부)이 정의서와 다르면 실패다.
   - 스크립트는 종료 코드가 하나라도 0 이 아니면 실패다.
   - 모두 맞으면 성공으로 닫고 "스크립트 실행은 끝났지만 적용 여부는 직접 확인해야 합니다" 류 안내를 보인다. 이 문구는 디자인 검수에서 거절돼도 사용자 허가로 통과한다.
5. 스크립트 출력은 `/root/spv-script-<번호>.log` 로 남기고 지우지 않는다.
6. 스크립트는 정의서 안에 내용으로 보관하고(할당 스냅숏으로 고정), 재사용은 정의서 복제(U9)로 한다.
7. 검증과 권한
   - 권한은 정의서 작성 권한 그대로다.
   - UTF-8 텍스트, 크기 상한, `%` 로 시작하는 줄 거부.
   - 비밀값을 쓰지 말라는 안내(내용이 `/root/anaconda-ks.cfg` 에 남음)를 둔다.
   - chroot 에서 `systemctl start` 류가 동작하지 않는다는 안내도 둔다. 이 안내는 세션 판단이며 CP1 에서 확인받는다.
8. 화면은 OS 후처리 카드 하나에 '기본 설정' 과 '추가 스크립트' 두 영역이다. OS 후처리의 선행 단계는 OS 설치(HF34 `requiredStep`)이고 OS 는 설치 쪽 값을 따른다.
9. 범위는 RHEL 계열만이다. Ubuntu, Windows 정의서에서는 OS 후처리를 잠근다.
10. 선행 조건은 HF34(PR #128) dev 병합과 U9(정의서 복제) 완료다. 둘 다 채웠고 이 브랜치는 2026-11-21 origin/dev 를 받았다.
11. E5 는 이관을 적고 취소했다.
