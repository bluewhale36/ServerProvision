## 2. R-9 — 내 안보다 나은 이유

나는 ①("OS 묶음 결과가 2개면 할당을 막는다")을 냈고, ③("첫 매칭만 쓴다")을 **"조용히 정해진다"** 는 이유로 물렸다.

주신 안은 ③의 결정 방식을 쓰되 그 약점을 지운다 — **우선순위를 화면에 명시**하면 조용하지 않다. 어느 볼륨이 OS 가 될지가 규칙으로 보이고, 그 규칙을 고칠 수 있다.

①과 비교하면 이렇다.

| | ① 차단 | E23 우선순위 |
|---|---|---|
| 볼륨이 여럿 나올 때 | 할당을 막는다 | **결정적으로 하나를 고른다** |
| 운영자가 할 일 | 정의서를 그 서버에 맞게 고친다 | 없다(예외일 때만 커스텀) |
| 화면에 보이는 것 | "붙일 수 없습니다" | "이 순서로 고릅니다" |

**E16("기본값은 어디에도 두지 않는다")과 충돌하지 않는다.** E16 이 금한 것은 **디스크 스펙의 기본값**이고, 우선순위는 스펙이 아니라 **해석 규칙**이다. 층이 다르다.

그리고 E24 가 말하는 순서는 **하드웨어의 성질에서 나온다** — 빠른 것이 OS 로 가고, 작은 것이 OS 로 간다. 관습이 아니라 물리에 가깝다. D5(2개면 RAID1)를 기본값으로 박는 것을 거부한 것과 사정이 다른 이유가 이것이다.

## 3. 남은 물음 하나

### R-11. 우선순위 규칙은 **어디에 사는가**

E23 을 구현하려면 그 순서가 어딘가에 적혀야 한다. 자리가 셋이다.

|     | 안                    | 뜻                                      | 값                  | 비용                                     |
| --- | -------------------- | -------------------------------------- | ------------------ | -------------------------------------- |
| ①   | **시스템 고정**           | E24 의 순서를 코드에 두고 바꿀 수 없다               | 가장 단순              | E25("커스텀 경로 필요")를 못 지킨다                |
| ②   | **정의서마다 적는다**        | 정의서 안에 우선순위 목록을 둔다                     | 정의서가 자기 완결적이 된다    | 대부분의 정의서가 **같은 값을 되풀이**해 적는다           |
| ③   | **시스템 기본 + 정의서 재정의** | 기본 순서는 코드(또는 운영 설정)에 두고, 필요한 정의서만 덮어쓴다 | 흔한 경우는 비우고 예외만 적는다 | 두 자리에 값이 있어 "지금 무엇이 적용되나" 를 화면이 말해야 한다 |

**내 판단은 ③이다.** E24 가 "거의 모든 경우" 라고 했으니 되풀이를 피하는 값이 크고, E25 가 요구하는 커스텀 경로도 열린다.

다만 U3-5-d 에서 배운 것이 하나 걸린다 — **"비어 있으면 자동" 을 화면이 말하지 않으면 사용자가 결과를 예측할 수 없다.** 그래서 ③을 택하면 정의서 화면이 **적용 중인 순서를 항상 보여줘야** 한다(비웠을 때도 "기본 순서: NVMe SSD → SATA SSD → HDD, 용량 오름차순" 처럼).

**그리고 E5 와 구분된다.** E5 는 "RAID 레벨이 비면 RAID 를 구성하지 않는다" 로 **비움 = 부재**였다. 여기서는 **비움 = 기본 적용**이다. 두 규칙이 같은 화면에 있으므로 **비움의 뜻이 축마다 다르다는 것**을 화면이 분명히 해야 한다.

> **R-11 답변:**
> 2번으로 가되, 생성될 때 기본 값으로 둔다. 이 경우 언제든 사용자가 다시 수정할 수 있다. RHEL 리눅스 OS 설치 섹션에서 파티션 생성 시 '기본 파티션 생성' 버튼처럼.

### R-12. 우선순위는 **무엇의 순서**인가

E24 가 "NVMe SSD → SATA SSD → HDD, 작은 용량 → 큰 용량" 을 준다. 이것을 무엇에 적용하는지가 두 가지로 읽힌다.

|     | 안          | 뜻                                             |
| --- | ---------- | --------------------------------------------- |
| ①   | **볼륨의 순서** | 규칙이 만들어 낸 RAID 볼륨들을 이 순서로 세우고, 그중 첫 번째가 OS 영역 |
| ②   | **묶음의 순서** | 정의서에 적힌 묶음 여럿 중 어느 것을 OS 로 볼지의 순서             |

E18(묶음 = 규칙, 볼륨 여럿)을 생각하면 **①이 맞아 보인다** — 실제로 OS 가 되는 것은 볼륨이지 묶음이 아니고, 한 묶음이 볼륨을 여럿 낳는 경우가 바로 R-9 가 다룬 상황이다.

①이면 Data 영역의 순서도 자연히 정해진다 — 같은 순서로 세워 `/data1` · `/data2` 가 붙는다(E9 는 명칭을 파티셔닝에서 정한다고 했으므로, 여기서 정해지는 것은 **순번**이다).

> **R-12 답변:**
> 1번으로 진행하되, RAID 볼륨으로 잡히지 않은 디스크(NVMe SSD 의 경우 보통 1개만 장착된다)도 함께 고려한다.

## 4. 정정 — R-7 의 근거가 실측과 어긋난다 (결론은 유지)

R-7 답변에 이런 근거가 있었다.

> 어차피 세팅 정의서는 부트스트래핑이 끝나고 하드웨어 수집이 완료된 다음에야 할당할 수 있도록 로직을 이전에 수정한 것으로 기억한다.

**실측 결과 그렇지 않다.** 할당은 **하드웨어 수집 전에도 된다.**

`AssignmentBlockKind` 가 막는 것은 둘뿐이다 — `DECOMMISSIONED`(회수된 서버)와 `BOARD_MISMATCH`(정의서가 요구하는 보드와 서버 보드가 다름). 그리고 수집 전 서버는 `BOARD_MISMATCH` 에 걸리지 않는다:

```java
/**
 * 정의서가 보드를 요구하는데 서버 보드를 아직 모르는가 — 막지는 않되 대조하지 못했다는 사실을
 * 화면이 표식으로 알리는 데 쓴다. 조용히 통과시키는 것과 구분하기 위한 값이다.
 */
public boolean boardUnverified() { … }
```

즉 U3-5-a 는 **"수집 전이면 막지 않고 표식만 남긴다"** 로 정했다.

**그런데 이 정정이 R-7 ③의 근거를 오히려 강화한다.** 수집 전에도 할당되므로, 캐시 유무를 할당 시점 검증에 걸어도 **수집 전 서버에는 판정할 것이 없다.** 검증을 넣어도 원하는 만큼 잡히지 않는다는 뜻이다. **③(이번에 판정하지 않는다)이 맞다.**

### 덤 — U3-5-a 가 이 순간을 내다봤다

`AssignmentEligibility` 의 javadoc 에 이렇게 적혀 있다.

> `GuestServerDetail` 을 통째로 드는 것이 요점이다. … 서버가 가진 하드웨어는 전부 이 엔티티 하나에 모여 있다. 보드 식별자만 풀어 담았다면 **U4 의 디스크 구성 대조가 들어올 때** 이 record 의 서버 쪽을 다시 열어야 한다.

디스크 대조를 붙일 자리가 **이미 준비돼 있다.** 요구사항 쪽(`requiredBoard`)에 축을 하나 더하면 되고, 서버 쪽은 손댈 필요가 없다. U4-1 이 U3-5-a 의 판정 골격을 그대로 쓴다는 뜻이다.
