# 세팅 정의서 OS 섹션의 범위 재조정 — 축소인가 간략화인가

> **문서 종류**: discussion (결정형 — 산출물은 코드가 아니라 결정). 시리즈 최초 문서라 전체 그림을 포함한다.
> **작성**: Claude, 사용자 상담(2026-08-20)을 입력으로.
> **목적**: 동료 피드백("세팅 정의서를 엄청 많이 만들게 될 것 같다")의 구조적 원인을 진단하고, 기능 축소 / 간략화 / 구조 재편 중 하나를 실측 근거로 결정한다.
> **연결**: MVP 축소 개정(2026-08-20 — OS 설치 E4 를 MVP 에서 제외, Notion `E4 : OS 설치` 페이지 상단 기재) · U2(세팅 정의서 CRUD 완료 — OS 섹션 포함 구현 상태) · U4-1(ue 세션 진행 중 — 디스크 분류 · RAID 구성).

## 1. 제기된 문제

사내 동료 검토에서 나온 의견(2026-08-20):

- 세팅 정의서의 OS 설치 섹션이 구체적이어서 **사용하기 복잡해 보인다**.
- 실제 사내 주문의 OS 설치 요청사항은 매우 다양하므로, **주문마다 정의서를 새로 만들게 될 것 같다**(정의서 폭발 우려).
- 서버가 수백 대 규모가 아니고, **마지막 수작업이 어차피 반드시 진행**되므로, 현재 수요 대비 기능이 과하다.

## 2. 문제의 구조 — 재사용 추상과 주문별 변동의 축 불일치

세팅 정의서는 **재사용 가능한 표준 템플릿**이다. 정의서 하나를 여러 서버에 할당하는 구조(U3)가 성립하려면 담긴 값이 서버가 달라져도 유지되는 "회사 표준"이어야 한다.

- **성립하는 영역**: 펌웨어 버전 · BIOS 설정 · BMC 설정 · RAID 구성 — 사내 표준 값이 실재함이 확인돼 있다(E0-1 실측: 사내 표준 BIOS 세팅 존재. 2026-08-19 실측: 펌웨어 업데이트가 그 설정을 리셋하므로 재적용 자동화의 이득도 실재).
- **깨지는 영역**: OS 설치 — 요청사항이 주문마다 달라, 주문별 값을 재사용 템플릿에 담으면 주문 수만큼 정의서가 생긴다. 정의서 폭발은 이 축 불일치의 증상이지 도구 자체의 결함이 아니다.

이 경계는 **2026-08-20 확정된 MVP 축소선(펌웨어 · BIOS · BMC · RAID 까지, OS 설치 제외)과 정확히 일치**한다. 동료 피드백과 MVP 결정이 독립적으로 같은 선에 수렴했다.

## 3. 현행 실태 (코드 실측, 2026-08-20)

정의서의 프로세스 팔레트는 4종이다(`SettingProcessType`):

| 타입 | 표시명 | MVP 경계 | 실행 엔진 소비처 |
|---|---|---|---|
| `BASIC_UPDATE` | 펌웨어 업데이트 | **안** | E2 계열(구현 예정) |
| `BASIC_SETTING` | BIOS 설정 | **안** | E3 계열(구현 예정) |
| `OS_INSTALLATION` | OS 설치 | **밖** (E4 이연) | 없음 — E4 가 출시 후로 이연되어 소비할 코드가 MVP 에 없다 |
| `OS_SETTING` | OS 후처리 설정 | **밖** (E4 이연) | 없음 — 동일 |

`OS_INSTALLATION` 의 입력 깊이(2단 다형 — `OSInstallationRequest` → `LinuxInstallationRequest` → `RHELInstallationRequest`/`UbuntuInstallationRequest`):

| 계층 | 입력 항목 |
|---|---|
| 베이스 | OS 메타데이터 선택 · ISO 선택 |
| 리눅스 공통 | 타임존(IANA + RTC-UTC) · **파티션 목록** · **사용자 목록** |
| RHEL 전용 | root 비밀번호 · 패키지 환경 그룹 · 추가 패키지 그룹 목록 |

Kickstart 생성에 필요한 수준의 상세다. 동료가 지적한 "구체적"의 실체는 파티션 · 사용자 · 패키지 층이고, 주문별 변동도 주로 이 층에서 일어난다.

참고 미확인 사항: RAID 구성(U4-1)이 정의서의 새 프로세스 타입으로 추가되는지, 별도 모델인지는 ue 세션의 U4-1 진행에서 확정된다 — 본 토론은 그 결정을 침범하지 않는다.

## 4. 판단 기준 — 항목별 3검사와 주문 실측

"전반 축소 vs 간략화"를 통으로 정하지 않고, 항목 단위로 검사한다:

1. **소비처 검사** — 실행 엔진의 어느 phase 가 이 입력을 소비하는가? 소비처 없는 입력은 사용자 부담만 남는 무게다. §3 표에서 OS 계열 2종은 현재 소비처가 없다.
2. **변동성 검사** — 최근 사내 주문에서 이 항목의 값이 몇 가지였는가? 1~3가지 수렴 = 표준(정의서 소속), 주문마다 상이 = 정의서 밖 소속.
3. **수작업 대체 검사** — 자동화가 절약하는 시간 > 정의서 작성 · 관리 비용인가? 수십 대 규모 + 필수 수작업 잔존 조건에서는 역전이 실제로 일어난다.

2번은 추측이 아니라 실측으로 한다. **최근 주문 10~20건**을 놓고 아래 표를 채운다(사내 자료라 사용자만 가능):

| 항목              | 주문에서 관측된 서로 다른 값 수 | 판정(표준/주문별) |
| --------------- | ------------------ | ---------- |
| OS 종류 · 버전      | 대체로 다르다.           | 주문별        |
| 파티션 구성          | 유사한 방향을 가진다.       | 표준50 주문별50 |
| 사용자 계정 구성       | 대체로 동일하다.          | 표준         |
| root 비밀번호 정책    | 대체로 동일하다.          | 표준         |
| 패키지 환경 · 추가 패키지 | 대체로 동일하다.          | 표준         |
| 타임존             | 동일하다.              | 표준         |

## 5. 선택지 비교

| 안            | 내용                                                        | 정합성                   | 비용 · 위험                                                |
| ------------ | --------------------------------------------------------- | --------------------- | ------------------------------------------------------ |
| **A. 표적 축소** | OS 계열 2종을 정의서 화면에서 숨김(또는 최소화). 자동화 범위 = RAID 까지, OS 는 수작업 | MVP 축소와 정합 · 폭발 원인 제거 | 기존 OS 섹션 데이터 · 코드의 처리 결정 필요                            |
| **B. 구조 재편** | 정의서 = 표준 템플릿 + 할당 시점 주문별 오버라이드 층                          | 폭발 해소 + 자동화 유지        | 구현 복잡도 상승. E4 이연 상태에서 소비처 없는 구조를 미리 지음 — "미리 분리 금지" 위배 |
| **C. 간략화**   | OS 섹션 유지하되 얕게(OS · ISO 선택 수준)                             | 폭발 완화                 | 소비처 없는 입력이 잔존 — A 대비 이점 불명                             |

**잠정 권고(미확정)**: A. "과하다"는 지적의 실체가 OS 섹션에 집중돼 있고, MVP 에 남는 영역(펌웨어 · BIOS · RAID)은 표준 반복 작업이라 수십 대 규모에서도 이득이 실재하므로(flash 1회 10~30분 · 설정 리셋 후 재적용 필수 — 실측), 전반 축소가 아니라 표적 축소가 맞다. B 는 E4 를 되살리는 시점에 §4 실측 표를 들고 재검토한다 — 갈라지는 시점에 분리한다.

## 6. 열린 질문 (각 질문 아래 인용문으로 답변)

**Q1. OS 섹션의 잔존 수준** — A 를 택할 때 어디까지 남기는가?
- ⓐ 완전 숨김: "단계 추가" 선택지에서 `OS_INSTALLATION` · `OS_SETTING` 제거
- ⓑ 식별만 잔존: OS 메타데이터 · ISO 선택까지만 남기고 상세(파티션 · 사용자 · 패키지) 숨김 — "이 서버에 무엇이 깔릴 예정인가"의 기록 가치
- ⓒ 현행 유지

> b 정도로 진행한다.
> MVP 에서 자동화를 대상으로 하는 모든 서버의 공통된 특징이 있다면, 설치 후 Windows Server 2025 를 거의 무조건 설치하는 과정이 있다는 점이다.
> 이는 Test 단계로, 게스트 서버의 하드웨어를 가지고 stress test 를 돌리는 것이다.
> MVP 를 RHEL 리눅스가 아닌 Windows Server 2025 설치 자동화 단계로 둔다면 OS Installation 대신 Testing 단계를 포함시켜 MVP 배포가 가능할 것이다. 설치 과정에서 별도의 추가 커스텀 되는 부분이 없고 오직 사용자가 선택해야 하는 것은 Administrator 비밀번호(이마저도 alt L 로 건너뛰거나 표준 비밀번호 고정)와 설치 디스크 선택 뿐이다. 설치 디스크는 현재 U4-1-3 에서 OS영역/Data영역 으로 구분하는 로직을 만들어는 놨으므로 세팅 정의서에서 재활용도 가능하다.
> 다만 Windows Server 2025 의 설치 자동화는 단 한번도 경험이 없으므로 실제로 MVP 에 포함시킬 수 있을지는 불명. 그러나 OS 설치 또는 유사한 기능으로써 남겨두려면 이 방향은 MVP 배포 이후 업데이트로 지원되어야 할 기능 1순위가 될 수 있겠다.

> 여지껏 테스트 데이터밖에 없었고 배포는 진행하지 않았으므로 크게 의미 없다.

**Q4. 주문 실측** — §4 표를 누가 · 언제 · 몇 건으로 채우는가? (권고: 결정 전에 10건 이상)

## 8. 결정 정리 (2026-08-20 토론 종결)

- **D1 — A 표적 축소 확정, 잔존 수준 = ⓑ**: `OS_INSTALLATION` 은 식별(OS 메타데이터 · ISO 선택)만 남기고 상세(타임존 · 파티션 · 사용자 · root 비밀번호 · 패키지)를 화면에서 숨긴다. `OS_SETTING` 의 처리 수준은 답변에 명시되지 않았으므로 R 슬라이스 plan(CP1)에서 ⓑ 준용 여부를 확정한다.
- **D2 — 코드 · 스키마 보존**: 화면 노출 차단만 한다. E4 부활 또는 Windows 방향 전환 시 재노출.
- **D3 — 기존 데이터**: 테스트 데이터뿐이고 미배포 상태라 마이그레이션 불요.
- **D4 — 실측 결과(최근 약 20건 주문, 사용자 직접)**: OS 종류 · 버전 = 주문별 / 파티션 = 표준 반 · 주문별 반 / 사용자 계정 · root 정책 · 패키지 · 타임존 = 표준. 단 20건 중 RHEL 설치 자체가 많지 않아 항목 비교의 정밀도는 제한적. **핵심 발견 — RHEL 의 실 수요는 크지 않다**(자동화 방법을 일찍 인지해 먼저 구현했을 뿐이다). 반면 **Windows Server 2025 를 설치해 하드웨어 stress test 를 돌리는 Test 과정은 대부분의 게스트 서버가 거치는 실 공통 과정**이고, 설치 커스텀이 없다 — 사용자 선택은 Administrator 비밀번호(표준 고정 또는 생략 가능)와 설치 디스크뿐이며, 설치 디스크는 U4-1-3 의 OS 영역/Data 영역 구분 로직을 세팅 정의서에서 재활용할 수 있다. 다만 Windows Server 2025 설치 자동화는 실행 경험이 전무해 MVP 포함 가능성은 불명 → **MVP 배포 후 업데이트 1순위 후보**로 기록한다(테스트 · 종단 = E6 계열과 연결). 이번 토론에서 MVP 범위를 재개정하지는 않는다.
- **D5 — 슬라이스 배정**: R 계열 신설, 결정 즉시 착수(앵커 스트림 소관). 번호는 Notion DB 의 R 계열 사용 현황을 대조한 뒤 확정한다(S12 번호 충돌 선례의 재발 방지).
- 본격 명세(폼 · 요청 계약 · 검증의 구체 변경 — 상세 필드를 숨기면 현행 `@NotNull`/`@NotEmpty` 검증과 충돌하는 문제 포함)는 해당 R 슬라이스의 plan html 로 넘긴다.
