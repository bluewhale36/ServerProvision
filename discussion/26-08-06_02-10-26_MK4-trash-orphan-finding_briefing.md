# MK4 입력 — 휴지통 실물 22 GB 가 어떤 기구에도 잡히지 않는 상태로 남아 있다

> **문서 종류**: MK4(reconciliation 사용성 진단) 입력 브리핑. 앵커 세션(`ServerProvision-dev`)이 개발 머신 디스크 정리 중 실측으로 발견해 원인을 코드 · DB · 파일시스템 삼면에서 규명한 기록이다.
> **작성**: 2026-08-06 02:10 KST.
> **위상**: 사용자가 "MK4 에서 중요하게 다룰 것" 을 지시했다. 킥오프 브리핑(`26-08-02_15-38-25_MK4-kickoff_briefing.md`)의 진단 축 여섯 개가 전부 **화면에 뜬 것을 사람이 판단할 수 있는가**를 묻는데, 이 발견은 그보다 앞선 층위다 — **화면에 뜨지조차 않는 상태가 있다.**

---

## 1. 무엇이 발견됐는가 — 실측 (2026-08-06, 개발 머신)

개발 DB(`localhost:3306/server_provision`)와 휴지통 디렉토리(`/opt/provisioning/.soft-deleted`)를 대조했다.

| 디스크 | 크기 | DB 행 | 해석 |
|---|---|---|---|
| `OS_ISO/27/dvd_… .iso` | 11 GB | **없음** | 영구삭제된 자원의 실물 잔존 |
| `OS_ISO/31/dvd_… .iso` | 11 GB | **없음** | 영구삭제된 자원의 실물 잔존 |
| `BIOS_BUNDLE/4/` (파일 41개) | 447 MB | **없음** | 영구삭제된 자원의 실물 잔존 |
| `BIOS_BUNDLE/17/` (파일 23개) | 150 MB | **없음** | 영구삭제된 자원의 실물 잔존 |
| `BMC_FIRMWARE/7/` (파일 23개) | 150 MB | **없음** | 영구삭제된 자원의 실물 잔존 |
| 빈 ID 디렉토리 13개 (`OS_ISO/28` · `30`, `BIOS_BUNDLE/6~16` 일부, `BMC_FIRMWARE/2~5`, `SUBPROGRAM/1`) | 0 B | **활성 행 존재** | 복원(restore)이 남긴 빈 껍데기 |

**합계 약 22 GB.** 그리고 휴지통 화면은 "자원 없음" 을 표시한다 — 화면이 틀린 것이 아니다. 화면은 DB 의 삭제 행을 조회하는데 삭제 행이 0 건이기 때문이다.

대조의 정합성은 두 방향에서 확인된다. **빈 디렉토리의 ID 는 전부 DB 에 활성 상태로 존재**한다(삭제했다가 복원한 자원 — `TrashService.moveBack` 이 파일만 꺼내고 ID 디렉토리는 남긴다). **실물이 남은 ID 는 전부 DB 에 없다.** 그리고 `iso` 테이블의 현재 ID 가 28 · 29 · 30 · 32 로 **27 · 31 을 건너뛰며 연번이 이어지므로**, 테이블 초기화가 아니라 **개별 행의 hard-delete(영구삭제)** 가 일어난 것이다.

`purge_log` 는 **0 행**이다. 즉 이 다섯 건의 영구삭제는 감사 기록도 남기지 않았다.

## 2. 원인 — 코드에서 세 겹으로 규명됐다

### 2.1 과거의 영구삭제는 휴지통 실물을 정리하지 않았다 (주 원인)

`PurgeExecutorImpl.execute()` 안에 S6-2-3 이 남긴 주석이 이 사실을 그대로 자인한다.

> 도메인 purge 는 원위치 부산물만 정리한다(soft-delete 가 원위치 경로를 보존하는 설계라 실물은 휴지통에 있음). **여기서 휴지통 실물을 함께 정리하지 않으면 영구삭제가 끝나도 파일이 휴지통(점검 수색 제외 구역)에 영원히 남는다**

즉 **S6-2-3(2026-07 완료) 이전의 영구삭제 경로는 DB 행과 원위치 부산물만 지우고 휴지통 실물은 건드리지 않았다.** 잔존 실물 다섯 건의 타임스탬프(6월 13일 ~ 6월 28일)가 전부 그 이전이고, `purge_log` 0 행(감사 배선 이전)과도 부합한다. 다섯 건은 그 시기의 영구삭제가 남긴 것이다.

### 2.2 현행 코드도 디렉토리형 자원에는 무력하다 (살아 있는 결함)

S6-2-3 의 보강이 넣은 정리 로직은 이렇다.

```java
// PurgeExecutorImpl.deleteQuietly
java.nio.file.Files.deleteIfExists(java.nio.file.Path.of(rawPath));
```

`Files.deleteIfExists` 는 **비어 있지 않은 디렉토리를 지우지 못한다** — `DirectoryNotEmptyException` 을 던진다. 그런데 BIOS 번들과 BMC 펌웨어는 **디렉토리 트리**다(실측: `BIOS_BUNDLE/17/` 은 파일 23개). 그리고 그 예외는 best-effort 설계에 따라 **경고 로그만 남기고 삼켜진다**.

> 휴지통 실물 정리는 best-effort. 실패해도 purge 자체(기록 삭제)는 성공으로 유지하고 로그만 남긴다.

즉 **지금 이 순간에도 디렉토리형 자원(BIOS · BMC)을 영구삭제하면 휴지통 트리가 통째로 남는다.** 단일 파일인 ISO 만 정리에 성공한다. 이것은 과거 잔재가 아니라 재현 가능한 현행 결함이다.

덧붙여 정리가 성공하는 경우에도 `deleteQuietly` 는 `trashedPath`(파일)만 지우고 **`<자원종류>/<ID>/` 부모 디렉토리는 지우지 않는다.** 빈 껍데기가 누적되는 두 번째 경로다(복원과 동일한 잔재).

### 2.3 빈 ID 디렉토리는 복원의 잔재다 (경미)

`TrashService.moveBack` 은 파일을 원위치로 옮길 뿐 비워진 ID 디렉토리를 지우지 않는다. 용량은 0 이라 실해는 없으나, 운영자가 휴지통 디렉토리를 셸에서 열었을 때 **"화면엔 없다는데 디렉토리가 잔뜩 있다"** 는 혼란을 만든다.

## 3. 왜 어떤 기구에도 잡히지 않는가 — 이것이 MK4 에 넘기는 이유다

이 상태를 잡을 수 있는 기구를 전수 대조했다. **전부 못 잡는다.**

| 기구 | 못 잡는 이유 |
|---|---|
| 휴지통 화면 | DB 삭제 행 기준 조회 — 행이 없다 |
| TTL 자동 정리(`trash.ttl.*`) | DB 행 기준으로 만료를 계산 — 대상 자체가 없다 |
| 자원 무결성 점검(quick · deep) | 스캔 범위가 **활성 자원의 부모 디렉토리 + extra-roots** — 휴지통은 설계상 "점검 수색 제외 구역" 이다(S6-2-3 주석의 표현 그대로) |
| 드리프트 11종 | `TRASH_LOST` 는 반대 방향(행은 있는데 파일이 없음), `GHOST_DB_ROW` 도 반대(행만 있고 파일이 없음). **"파일만 있고 행이 없음 × 휴지통"** 조합은 어느 종류에도 없다 |
| 미등록 마커(`ORPHAN`) | 정상 소프트 삭제는 마커를 지우므로 휴지통 실물에는 마커가 없다 + 애초에 스캔 범위 밖 |

주목할 것은 **이것이 개별 버그가 아니라 설계 공백**이라는 점이다. 휴지통을 점검 범위에서 뺀 것 자체는 타당한 결정이었다(휴지통 안 파일이 `MISSING` 이나 `ORPHAN` 으로 오탐되면 안 되므로). 그런데 그 결정의 이면 — **"그러면 휴지통 안의 실물과 DB 는 누가 대사(對査)하는가"** — 에 아무도 배치되지 않았다. 영구삭제가 실물 정리에 실패하면(2.1 · 2.2) 그 파일은 **영원히, 어떤 화면에도 뜨지 않고, 어떤 자동 정리에도 걸리지 않은 채** 디스크만 차지한다.

## 4. 실서버에서의 함의 — 왜 지금 다뤄야 하는가

**첫째, 재현 조건이 흔하다.** 디렉토리형 자원의 영구삭제(2.2)는 현행 코드로 매번 재현된다. DB 복원 · 마이그레이션 사고로 행과 파일이 어긋나는 경우도 같은 상태를 만든다.

**둘째, OPS-2 의 결정과 정면으로 맞물린다.** OPS-2 는 자원 본체를 백업에서 제외했고(재생성 가능), 휴지통 보존 기간은 넉넉히 잡는 방향으로 정했다. 그 전제는 **휴지통이 정리 기구(TTL · 영구삭제)에 의해 관리된다**는 것이다. 그런데 관리에서 이탈한 실물이 별도로 쌓인다면 용량 계획의 전제가 흔들린다. 이번 실측이 그 규모를 보여준다 — **활성 자원 35 GB 에 이탈 실물 22 GB.** 대략 활성분의 60 % 급이다.

**셋째, D1 결정의 대가가 커진다.** OPS-1 은 운영자 직접 쓰기를 허용했고 그 대가로 reconciliation 이 주력 기구여야 한다고 확정했다. 그런데 그 주력 기구의 수색 범위 밖에 이런 사각이 있다면, "직접 쓰기를 허용해도 시스템이 따라잡는다" 는 약속이 휴지통 구역에서는 성립하지 않는 것이다.

## 5. MK4 에 제안하는 것

### 5.1 진단 축에 추가하라 — "기계가 볼 수조차 없는 상태"

킥오프 브리핑의 여섯 축은 전부 "화면에 뜬 것" 을 전제한다. 그 앞에 하나를 더 세울 것을 제안한다.

> **0. 화면에 뜨지 않는 불일치가 존재하는가** — DB 와 파일시스템의 어긋남 중 어떤 기구의 시야에도 들어오지 않는 조합이 있는가. 본 문서의 휴지통 사례가 실증이다.

사용자가 "reconciliation 이 제 구실을 하는지 의문" 이라고 말한 배경에 이 종류의 경험 — **디스크는 차는데 화면은 깨끗하다** — 이 있었을 가능성이 있다. 진단 인터뷰에서 확인할 가치가 있다.

### 5.2 개선 후보 세 갈래 (진단 후 슬라이스 설계의 입력)

**① 영구삭제의 실물 정리를 고친다 (작은 수정, 즉효).** `deleteQuietly` 를 재귀 삭제로 바꾸고 `<자원종류>/<ID>/` 부모 디렉토리까지 정리한다. 현행 결함(2.2)의 직접 수정이며 분량이 작다. 다만 **이미 이탈한 실물은 소급 정리되지 않는다** — ② 가 필요한 이유.

**② 휴지통 대사 기능을 만든다 (설계 판단 필요).** 휴지통 디렉토리의 실물 목록과 DB 삭제 행을 대조해 "DB 에 없는 실물" 을 보고하는 기능. 두 형태가 가능하다 — 드리프트 종류를 신설해 기존 점검 화면에 얹거나(예: `TRASH_ORPHAN`), 휴지통 화면에 별도 대사 절을 두거나. **전자는 "휴지통은 수색 제외" 라는 기존 설계 결정과 충돌하므로 신중해야 한다** — 수색 제외의 취지(오탐 방지)를 지키면서 대사만 추가하는 경계 설계가 쟁점이 된다. 이중 의도 검증 명제와의 정합도 확인할 것.

**③ 감사 공백을 기록으로 남긴다.** `purge_log` 0 행이 보여주듯 과거 영구삭제는 추적 불가다. 소급은 불가능하므로, 현행 배선이 세 진입 경로(화면 · TTL · 드리프트 해소) 전부를 실제로 지나는지 통합 테스트로 못 박는 것이 남은 일이다.

### 5.3 검증 시나리오 (CP5 샌드박스에서 재현 가능)

1. 디렉토리형 자원(BIOS 번들)을 등록 → 소프트 삭제 → 영구삭제.
2. `purge_log` 에 SUCCESS 가 남고 화면에서 사라지는 것을 확인.
3. **휴지통 디렉토리를 열어 트리가 그대로 남아 있는 것을 확인** — 결함 2.2 의 재현.
4. 경고 로그(`휴지통 실물 정리 실패`)가 남는지 확인 — 지금은 이 로그가 유일한 흔적이다.

## 6. 개발 머신의 22 GB 처분에 대해

앵커 세션이 디스크 정리의 일환으로 **이 실물들을 수동 삭제할 예정**이다(DB 참조 0 이므로 앱 동작에 영향 없음). 실물이 사라져도 본 문서의 인벤토리(1절)와 재현 시나리오(5.3)로 진단 · 검증에는 지장이 없다. **다만 MK4 가 삭제 전 실물 상태에서 직접 확인하고 싶은 것이 있다면 지금 알려 달라** — 그때까지 삭제를 보류한다.
