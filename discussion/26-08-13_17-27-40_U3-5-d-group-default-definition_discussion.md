# U3-5-d : 그룹에 세팅 정의서를 붙여 두기 (그룹 기본 정의서)

작성 2026-08-13 17:27 KST · 브랜치 `feat/U3-5_group-batch-assignment`
선행 U3-5-a · U3-5-b · U3-5-c(CP6 승인 대기) · **U3-5 우산의 네 번째 조각으로 편입 제안**

이 주제의 **최초 문서**라 전체 그림을 담는다. 후속 문서는 쟁점과 응답만 담는다.

---

## 1. 무엇을 하려는가 (제안 원문 요지)

그룹 자체에 세팅 정의서를 **할당해 둔다.** 그러면 둘이 가능해진다.

- **(a) 자동 적용** — 그룹을 미리 만들어 두고, 게스트 서버가 그 그룹에 새로 들어올 때마다 정의서가 자동으로 붙는다.
- **(b) 일괄 적용 간소화** — 지금처럼 정의서를 다시 찾아 고를 필요 없이 `[일괄 적용]` 한 번으로 끝낸다.

제안된 스키마 방향은 `setting_assignment.guest_server_id` 를 소프트참조 `guest_id` 로 바꾸고
`guest_type` enum(`SERVER` · `GROUP`)을 더하는 것이다.

### 왜 U3-5 의 하위로 두는가
U3-5 우산 자체가 **"그룹 단위 세팅 정의서 일괄 할당"** 이다. a(판정) · b(고르는 화면) · c(일괄 실행)가
"그때그때 고르는" 흐름을 완성했고, 이 제안은 같은 우산 안에서 **"미리 정해 두는"** 축을 더한다.
별도 인벤토리 코드를 새로 파기보다 **U3-5-d** 가 맞다.

## 2. 현재 상태 (실측)

### 있는 것
- `SettingAssignment` — 할당 시점 **derive-then-freeze 스냅샷**. `AssignedProcess` payload 무변환 복사,
  BIOS 는 `FrozenBiosSettings` deep-freeze, `ownedPhases` 도출 후 동결
- `AssignmentBlockKind.evaluate` — 회수 · 하드웨어 대조 판정 (U3-5-a)
- `GroupAssignmentService` — 미리보기 → 통과분만 → 결과 보고 (U3-5-c)
- `MemberApplyOutcome` — 그룹 문맥의 멤버 분류 (U3-5-c)
- U3-5-c 의 2 열 miller 모달 — 정의서를 고르고 적용 결과를 미리 본다

### 없는 것
- 그룹이 정의서를 **기억하는** 자리. 지금 그 정책은 운영자 머릿속에만 있다

### 스키마 실측
```
setting_assignment
  guest_server_id  uuid NOT NULL         ← guest_server(id) 로 가는 실제 FK
  active_guest_id  uuid GENERATED ALWAYS AS (IF(superseded_at IS NULL, guest_server_id, NULL)) STORED
  UNIQUE KEY uk_active_assignment_per_guest (active_guest_id)

guest_server.id        uuid
guest_server_group.id  bigint(20)
```
`setting_assignment` 을 읽는 파일 **9 개** — `AssignmentQueryService` · `AssignmentCommandService` ·
`AssignmentStartService` · `AssignmentReapService` · `OwnedPhasesProviderImpl` ·
`AssignmentUsageInspectorImpl` · `ResourceUsageQueryImpl` · 엔티티 · 리포지토리.

## 3. 쟁점 1 — 스키마 (가장 되돌리기 비싼 결정)

### 안 ① 다형 테이블 (제안 원안)
`setting_assignment(guest_id, guest_type)` 하나로 서버 할당과 그룹 할당을 함께 담는다.

**얻는 것** — 할당을 다루는 서비스 · 화면을 한 벌로 쓸 수 있다.

**치르는 것 넷** (전부 실측 근거)

1. **성질이 다르다.** 서버 할당은 *얼린 실행 계약*이고 그룹 할당은 *정책 참조*다. U3-1 이 스냅샷을
   만든 이유는 "정의서가 나중에 바뀌어도 이 서버가 밟을 것은 얼린 그 값" 이기 때문인데, 그룹에는 그
   이유가 없다. **오히려 반대다** — 정의서가 개정되면 그룹은 최신을 따르는 편이 자연스럽다.
2. **절반의 컬럼이 절반의 행에서 죽는다.** `consumed_at` 은 GROUP 행에서 영원히 null,
   `owned_phases` 는 소비자 없음, `AssignedProcess` 자식은 얼릴 이유 없음,
   `AssignmentReaper`(superseded + 미소비 TTL 수거)와 `markConsumed` 는 SERVER 전제.
   → `guest_type` 분기가 도메인 의미마다 자란다(불가침 "조건분기 legacy 확장 금지" 와 충돌).
3. **id 타입이 물리적으로 다르다.** `uuid` vs `bigint`. 한 컬럼에 담으려면 `VARCHAR` 로 뭉개야 하는데
   불가침 "Primitive Obsession 금지" 와 충돌한다.
4. **DB 동시성 불변식을 다시 짜야 한다.** U3-2-a 의 생성 컬럼 + UNIQUE 는 TOCTOU 도 `@Version` 도 못
   막는 "활성 0 → 2 동시 삽입" 을 막는 장치다. 복합키로 재설계하고 9 개 소비 파일을 함께 봐야 한다.

### 안 ② 소프트참조 컬럼 하나 (대안)
```
guest_server_group.default_definition_id  BIGINT NULL   -- 소프트참조, FK 없음
```
실제 할당은 기존 경로(`AssignmentCommandService.assign`)를 그대로 쓴다.

**근거** — 그룹이 갖는 것은 "할당" 이 아니라 **"기본값"** 이다. 이름이 다르면 타입도 달라야 한다.
U3-5-c 가 `ALREADY_ASSIGNED` 를 `AssignmentBlockKind` 에 넣지 않은 것(DEC-G)과 같은 판단이다 —
**그룹 문맥에서만 뜻이 있는 것은 따로 둔다.**

| | ① 다형 테이블 | ② 소프트참조 컬럼 |
|---|---|---|
| 스키마 변경 | 타입 변경 · FK 제거 · 생성 컬럼 재설계 | 컬럼 1 추가 |
| 영향 파일 | 9 + 엔티티 + reaper | 그룹 엔티티 · 화면 |
| 기존 스냅샷 의미 | 흔들림 | 무변경 |
| 정의서 개정 반영 | 얼려서 안 됨 | 자동으로 최신 |
| 되돌리기 | 어렵다 | 컬럼 하나 |

> **세션 판정(미확정 — 사용자 결정 대기)**: **② 를 권한다.** ①의 이득(서비스 한 벌 재사용)이 작다 —
> 그룹은 `assignmentForm` 이 아니라 U3-5-c 의 멤버별 미리보기를 쓰므로 공유할 화면이 애초에 다르다.

> 2번 방식 진행.

## 4. 쟁점 2 — 자동 적용의 강도

U3-4 는 **"그룹은 하드웨어 구성이 아니라 운영자의 묶음"** 이라고 못 박았다. 운영자가 서버를 그룹에
넣는 이유가 항상 "정의서를 붙이려고" 는 아니다. 자동 적용은 **멤버 추가라는 가벼운 조작에 되돌리기
어려운 부수효과**를 붙인다.

| 안 | 동작 | 위험 |
|---|---|---|
| ① 항상 자동 | 넣는 즉시 붙음 | 의도치 않은 할당. 되돌리려면 개별 해제 |
| ② 자동 + 그룹 설정으로 끄기 | 기본 자동, 끌 수 있음 | 무명 boolean 이 하나 늘어남 |
| ③ 넣은 뒤 안내 + 원클릭 | "2 대가 들어왔습니다 — 기본 정의서를 적용할까요?" | 없음. 클릭 한 번이 늘 뿐 |

> **세션 판정(미확정)**: **③ 을 권한다.** 미리보기를 거치므로 U3-5-c 의 "부분 적용을 미리 알고 승인"
> 계약이 그대로 유지되고, 자동의 편의도 거의 다 얻는다.

> 우선은 3번.

## 5. 쟁점 3 — 파생 질문들 (답이 정해지면 설계가 따라온다)

아래는 전부 **미확정**이다. 각 항목에 세션 의견을 붙였으니 인용문으로 답해 주면 된다.

### Q1. 그룹 기본 정의서를 바꾸면 이미 붙은 서버는?
> 세션 의견 — **소급하지 않는다.** U3-5-a 가 하드웨어 불일치를 소급 무효화하지 않은 것과 같은 결이다
> (진행 중인 서버의 계획이 사라지고, 대량 소멸 위험이 있다). 바꾼 뒤 원하면 일괄 적용을 다시 누른다.

### Q2. 서버가 그룹에서 빠지면 할당은?
> 세션 의견 — **남는다.** 할당은 서버의 것이고 그룹은 그것을 정해 준 계기일 뿐이다. 그룹 삭제 시
> 멤버의 할당이 사라지지 않는 것과 같다(U3-4 가 이미 그렇게 확인 문구를 쓴다).

### Q3. 서버가 그룹 A → B 로 옮기면 B 의 기본값이 자동 적용되나?
> 세션 의견 — **적용하지 않는다.** 이미 할당이 있으면 갈아엎어야 하는데 그것은 파괴적이다
> (U3-5-c DEC-C 가 일괄 재할당을 금한 것과 같은 이유). 미할당이면 쟁점 2 의 답을 따른다.

### Q4. 그룹 기본으로 지정한 정의서가 삭제 · 비활성되면?
> 세션 의견 — 소프트참조라 행은 남고 **화면이 "사용할 수 없는 정의서" 로 표시**한다. 판정은
> `SettingDefinition.assignBlockReason()` 재사용(U3-2-b SSOT). 일괄 적용 버튼은 잠근다.

### Q5. 그룹 기본값을 어디서 정하나?
> 세션 의견 — **U3-5-c 모달을 재사용**한다. 이미 정의서를 고르고 적용 결과를 미리 보는 화면이므로,
> 거기에 `☐ 이 정의서를 이 그룹의 기본으로 두기` 한 줄을 더하는 것이 가장 작다. 그룹 상세에는
> 현재 기본값을 보여주는 자리를 하나 둔다.

### Q6. 혼재 그룹에서 "기본 정의서" 라는 말이 오해를 부르지 않나?
> 세션 의견 — 부를 수 있다. 하드웨어가 갈린 그룹에서는 기본 정의서가 **일부에만** 붙는데
> "기본" 은 "전부에 적용" 처럼 읽힌다. 미리보기가 실제 결과를 보여주므로 동작은 안전하나
> **화면 문구를 주의**해야 한다(예: "기본 정의서" 대신 "이 그룹의 표준 정의서" + 붙는 수 병기).

### Q7. 그룹 기본값이 있으면 서버 개별 할당 화면(U3-5-b)에도 표시할까?
> 세션 의견 — **표시한다.** 그 서버가 속한 그룹의 표준이 무엇인지 알면 개별 할당에서 다른 것을 고를 때
> 의식적으로 고르게 된다. 다만 강제하지 않는다.

> 전체 권장안 진행.

### 확정 후 세션이 발견한 보완점 (plan CP1 에서 해소한다)

**Q5 의 "모달 재사용" 만으로는 핵심 유스케이스가 막힌다.** 제안 (a) 의 요지가 **"그룹을 미리 만들어
두고"** 인데, U3-5-c 의 모달은 **멤버가 0 이면 열리지 않는다**(OQ-3 — 조작할 것이 없는 화면을 열어
주지 않는다). 즉 서버가 아직 없는 빈 그룹에 표준을 정해 둘 길이 없다.

→ 보완 방향은 **표준을 정하는 자리를 그룹 상세의 전용 절로 두고**, 그 자리에서 같은 picker 모달을
**"표준 지정" 모드**로 여는 것이다. 할당/재할당이 한 모달을 공유한 U3-5-b DEC-E 와 같은 형태다
(제목 · 제출 대상 · 버튼 문구만 다르다). 모달 안의 체크박스는 "고르는 김에 표준으로도" 하는 지름길로
함께 둘 수 있다.

이 보완은 확정을 뒤집는 것이 아니라 **확정을 실제로 쓸 수 있게 만드는 것**이므로 plan 에서 결정으로
기록하고 진행한다.

## 참고 — 이 문서가 왜 plan 앞에 오는가

스키마 판단은 **되돌리기 비싼 결정**이다. `setting_assignment` 은 실행 엔진(ES · E 계열)이 소비하는
테이블이라, 구조를 잘못 잡으면 그 뒤 모든 단계가 그 위에 쌓인다. plan 은 "어떻게 만들까" 를 적는
문서라 "무엇이 옳은가" 를 다투기에는 형식이 맞지 않는다.
