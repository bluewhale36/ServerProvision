## 1. 저장소와 세션 배치가 바뀌었다

**브랜치가 3 계층이 됐다.** 예전의 `renew/main` 단일 라인은 사라졌다. 지금은 `main`(실 배포 소스, GitHub 기본) ← `dev`(개발 완료 도달점) ← `<type>/<인벤토리코드>_<슬러그>`(작업) 구조다. type 은 conventional 어휘(`feat` · `fix` · `refactor` · `docs` · `chore`)를 쓰고, 인벤토리 코드에 하이픈이 들어가므로 코드와 슬러그의 경계는 언더스코어로 나눈다.

**당신의 기억에 있는 `ServerProvision-renew/main` 경로는 전부 과거다.** 트랜스크립트 안의 옛 `cwd` 기록을 근거로 파일을 찾지 말 것.

**워크트리가 "단계" 가 아니라 "스트림" 에 고정됐다.** 예전에는 캠페인마다 워크트리를 새로 파고 끝나면 지웠는데, 그러면 작업 디렉토리가 바뀔 때마다 세션 맥락이 0 에서 다시 시작한다. 실제로 그 비용을 치렀고(당신이 12 일간 잠들어 있던 이유이기도 하다), 그래서 **디렉토리는 고정하고 브랜치만 그 안에서 회전**하도록 바꿨다.

현재 세 스트림이 있다.

| 워크트리 | 상주 · 현재 브랜치 | 역할 |
|---|---|---|
| `ServerProvision-dev` | `dev` 상주 (앵커) | 통합(PR 병합 · 배포 · DDL) · 규약과 AI 사용 설계 · S/R/HF 산발 작업 |
| `ServerProvision-ue` | `feat/U3_setting-assignment` | U · E 실행 엔진 본류 |
| **`ServerProvision-m`** | **`feat/MK4_reconciliation-usability`** | **M · Maintenance 본류 — 지금 당신이 있는 곳** |

**다음 캠페인으로 넘어갈 때 디렉토리를 새로 만들지 않는다.** 이 자리에서 `git switch -c <type>/<코드>_<슬러그> origin/dev` 로 브랜치만 갈아끼운다. 그 전환은 당신이 직접 수행한다.

**핫픽스도 여기서 처리한다.** 작업 중 결함을 발견하면 이 홈에서 `fix/HF*_…` 로 갈아타 고치고 원 브랜치로 돌아온다. 새 워크트리를 파거나 세션을 옮기지 않는다.

## 2. 작업 규약이 바뀌었다

**체크포인트가 CP1~CP5 에서 CP1~CP7 로 늘었다.** 빌드와 테스트가 통과해도 화면에서만 드러나는 결함이 있다는 것이 전수 점검에서 실증됐기 때문이다.

| CP | 범위 |
|---|---|
| CP1 | plan html 산출 |
| CP2 | 뷰 · Controller · DTO · Service 시그니처 |
| CP3 | Repository · Entity(+VO/Enum) |
| CP4 | Service 본체 · 테스트 · 스키마 — **여기까지가 빌드/테스트 green** |
| **CP5** | **샌드박스 브라우저 검증 — 검증 항목 계획 후 수행, 스크린샷 채증** |
| **CP6** | **report html 산출 — CP5 의 기록이 본문의 중심** |
| CP7 | 사용자 단독 브라우저 E2E |

**CP4 의 green 은 완료가 아니라 검증 착수 조건**이다. CP5 에서는 정상 흐름만 보지 않고 **의도하지 않은 조작을 일부러 시도**해 애플리케이션이 어떻게 막는지, 그리고 막는 방식이 UX 를 해치지 않고 유도하는지까지 본다. 이 규율이 이번 작업의 성격과 직접 맞닿아 있으니 `CLAUDE.md` 의 해당 절을 정독할 것.

**plan/report html 은 저작 SSOT 가 생겼다.** `.claude/plan-report-html-spec.md`(명세)와 `plan/plan_template.html`(기준 구현)을 따른다. **최근 파일을 복제하지 않는다** — 그게 드리프트의 원인이었다. 카탈로그에 없는 디자인 객체가 필요하면 명세에 먼저 추가한 뒤 쓴다.

**discussion 규약이 일반화됐다.** 코드 착수 전 토론 비중이 큰 작업은 **진행을 Notion 단계 페이지 본문에서 하고, 종결되면 저장소 `discussion/` 으로 아카이브**한다. 아카이브에는 결정만이 아니라 쟁점과 탈락 대안까지 담는다. 모바일에서 답할 수 있고 알림이 온다는 것이 Notion 에서 진행하는 이유다.

**Notion 단계 페이지 골격이 개편됐다.** 최상단 tabs 블록 + 그 아래 4 항목 본문(① scope ② 비 목표 ③ 잔존 책임/임시 비대칭 ④ 후속 마일스톤)이다. 코드 슬라이스는 탭이 `요약`/`plan`/`report`, OPS 같은 설계 계열은 `discussion 요약`/`final decision 요약` 이고 실제 토론과 결론은 본문에 둔다(탭 안의 제목 블록은 목차에 잡히지 않기 때문). **DB 속성은 생성 · 수정 · 삭제하지 않는다.**

**출력 규칙 하나가 불가침으로 추가됐다.** `·` 문자를 쓸 때는 **앞뒤로 공백을 한 개씩** 넣는다. 답변 · 커밋 메시지 · 문서 · Notion 전부에 적용된다.

**새로 생긴 인벤토리 계열이 둘 있다.** `DOC*`(문서화)와 `OPS*`(서버 운영 설계 — 배포 대상 OS 위에서 애플리케이션을 어떤 계정 · 권한 · 배치로 돌릴지). **`OPS` 는 산출물이 코드가 아니라 결정이므로 CP 체계를 따르지 않고, 토론에서 결정이 확정되면 완료로 닫는다.**

## 3. 이번 작업 — MK4 reconciliation 사용성 진단

### 3.1 어디서 나온 요구인가

OPS-2(파일시스템 배치와 디스크 운영) 토론 중 사용자가 이렇게 말했다.

> reconciliation 은 솔직히 아직도 제 구실을 할 수 있는 기능인지 의문이어서 정상적으로 돌고 있는 상황에서도 drift 를 잡고 해결하는 데에 도움이 될지 알 수 없는 상황이다. 개념이나 의도는 좋으나 실제로 이게 어떤 도움이 될지, 사용자가 사용하기 편할지 등이 의문인 것.

그리고 다음 라운드에서 한 번 더.

> 이 문제는 이전부터 꾸준히 느끼고 있던 지점인 만큼 지금부터라도 재착수해서 개선시켜 나가고 싶으나 **어느 부분에서 구체적으로 내가 답답한 상황인 것인지 정리가 잘 되지 않는 상황이다.**

**두 번째 문장이 이번 작업의 핵심**이다. 개선 요구가 아니라 **"무엇이 불편한지 말로 만들어지지 않는 상태"** 다.

### 3.2 폐기 여부는 이미 결론이 났다 — 필요성은 확정됐다

당신이 잠든 사이 OPS-1 과 OPS-2 에서 reconciliation 의 위상이 확정됐다. **이 논의를 다시 열지 말 것.**

- **OPS-1 D1 — 운영자의 자원 디렉토리 직접 쓰기를 허용한다.** 사내 도구이므로 어떤 경우에도 거친 접근이 가능해야 한다는 판단이다. 그러면 **드리프트는 가능성이 아니라 예정된 사건**이 된다. reconciliation 이 없으면 운영자가 파일을 옮긴 순간 애플리케이션은 옛 경로를 정답으로 알고 있고, 그 서버의 프로비저닝은 조용히 실패한다.
- **OPS-1 D8 — 변경 감지 방식은 현행 유지.** inotify 이벤트 감지는 검토 후 탈락했다(하위 디렉토리 자동 추적 불가, 감시 슬롯 상한, **결정적으로 어느 프로세스가 바꿨는지 알려주지 않아 앱과 사람을 구분하지 못함**, 네트워크 파일시스템 미동작). 이미 기동 직후 1 회 + 1 시간 quick + 24 시간 deep 의 3 중 스캔이 있다.
- **OPS-2 D10 — 자원 본체를 백업 대상에서 제외한다.** 다시 만들 수 있다는 이유다. 그러면 디스크 사고 후 자원을 다시 채워 넣을 때 **DB 와 파일을 맞춰 줄 유일한 기구가 reconciliation** 이다.

즉 **지금 구조에서 reconciliation 은 선택 기능이 아니라 위 결정들의 대가로 반드시 있어야 하는 것**이다. 진입 시 예상했던 "접근 통제를 강하게 걸면 reconciliation 이 안전망으로 격하된다" 는 시나리오는 **일어나지 않는다** — 주력 기구로 그대로 유지된다.

두 단계의 전문은 Notion 에 있다. 저장소 아카이브(`discussion/26-08-02_13-16-50_OPS-1-access-control_discussion.md`, `discussion/26-08-02_15-11-33_OPS-2-filesystem-layout_discussion.md`)는 **아직 `dev` 에 병합되지 않아 이 브랜치에서는 보이지 않는다.** 병합 전에는 Notion 페이지를 보라.

- OPS-1 : 실행 주체와 접근 통제 — https://app.notion.com/p/3afef0e868f981cfbceff661899d9b69
- OPS-2 : 파일시스템 배치와 디스크 운영 — https://app.notion.com/p/3afef0e868f98105b6b0ea5e0a876eb3

### 3.3 그래서 이번에 할 일은 개선이 아니라 진단이다

사용자가 백지에서 불만을 떠올리는 것보다 **후보를 늘어놓고 고르는 편이 훨씬 쉽다.** 그래서 합의된 진행 방식은 이렇다.

**reconciliation 화면과 그 뒤 흐름을 운영자 입장에서 처음부터 끝까지 훑어, 마찰이 생길 만한 지점을 목록으로 뽑아 제시한다.** 사용자는 "이건 맞고 저건 아니다" 를 고른다. 그 선택이 답답함의 정체를 확정하고, 개선 슬라이스의 입력이 된다.

후보의 축으로 이미 제시해 승인받은 것이 여섯이다. **이 여섯에 갇히지 말고 훑는 과정에서 더 나오면 추가할 것.**

1. 화면에 뜬 드리프트가 **무슨 뜻인지 바로 읽히는가** — 용어가 내부 개념 그대로는 아닌가
2. 이걸 **지금 처리해야 하는지 나중에 해도 되는지** 판단할 근거가 화면에 있는가
3. 해결 버튼을 누르면 **정확히 무엇이 바뀌는지** 예측 가능한가
4. 여러 건이 한꺼번에 뜰 때 **어디부터 손대야 하는지** 알 수 있는가
5. 잘못 눌렀을 때 **되돌릴 수 있는가**
6. 애초에 **사람이 판단할 일이 맞는가** — 기계가 정해도 되는 것까지 묻고 있지 않은가

### 3.4 이 진단이 왜 지금까지 안 됐는지도 기록해 둔다

사용자가 OPS-1 에서 밝힌 사정이다.

> 현재 개발 중인 provisioning server 를 비롯해서 유사한 프로그램의 실사용 전례에 대한 기록이 사내에 전무하므로 해당 부분은 불명이다. 가능한 상황을 우리가 상정해서 발생할 수 있는 애로사항을 최대한 제거하는 것을 목표로 현재는 개발을 진행해야 할 것이다. **reconciliation 도메인을 위한 M 단계 및 S 단계가 유난히 많고 복잡했던 것도 이 이유.**

**실사용 전례가 없어서 "이 판단을 사람이 실제로 할 수 있는가" 를 아무도 확인하지 못했다.** 그것이 지금의 공백이고, 그래서 이 진단은 상상이 아니라 **실제로 화면을 띄우고 드리프트를 만들어 본 결과**여야 한다.

## 4. 진행 방식 제안 (당신이 판단해 조정할 것)

**첫째, 코드와 화면의 현재 상태를 파악한다.** 당신이 마지막으로 본 이후 reconciliation 은 R9 캠페인과 S6, 그리고 HF4 핫픽스 묶음을 거쳤다(2026-07-20 완료 처리). 정보구조가 재배치되고 명칭이 '자원 무결성 점검' 으로 단일화됐으며, 전용 확인 modal 과 async 전환이 들어갔다. **기억에 있는 화면과 다를 수 있으니 반드시 현재 코드를 읽을 것.**

- 백엔드 — `src/main/java/com/example/serverprovision/maintenance/reconciliation/` (`controller` · `service`(+`resolution` · `recheck`) · `repository` · `entity` · `dto/response` · `exception`)
- 화면 — `src/main/resources/templates/maintenance/reconciliation/list.html`, `src/main/resources/templates/fragments/maintenance/reconciliation-modals.html`
- 인접 영역 — `maintenance/trash/`(`list` · `purge-log` · `settings`), `maintenance/quarantine/list.html`
- 스캔 주기 설정 — `reconciliation.scan.startup-enabled` · `interval-ms`(1 시간) · `deep-interval-ms`(24 시간)
- 배경 문서 — 저장소 루트의 `DB_FS_CONSISTENCY.md`

**둘째, 샌드박스를 띄우고 드리프트를 일부러 만든다.** 말로만 하는 진단은 근거가 약하다. 누적 메모리에 샌드박스 레시피가 있다(Docker MariaDB + bootRun + Chrome 자동화). **동시 세션과 포트가 겹치지 않게 이 스트림 전용 포트를 쓸 것** — `ServerProvision-ue` 세션이 동시에 돌고 있다.

**셋째, 후보 목록은 화면 캡처와 함께 낸다.** 사용자가 "이건 맞고 저건 아니다" 를 고르려면 무엇을 보고 하는 말인지가 화면으로 보여야 한다.

**넷째, 이 진단 자체는 코드 산출물이 없다.** `CLAUDE.md` 가 "CP 체계는 코드 슬라이스에만 적용한다" 고 못 박았으므로, 진단은 discussion 규약으로 진행하고 **개선 슬라이스가 정해지면 그때 CP1(plan html)로 들어가는 것**이 규약에 맞다. 다만 MK4 는 코드 개선까지 이어질 캠페인이므로 브랜치 type 을 `feat` 으로 잡아 두었다.

이 문서를 쓴 세션이 대신 정할 수 없는 항목이다. **작업 착수 전에 물을 것.**

1. **Notion 단계 페이지가 아직 없다.** `MK4` 로 신설할지, 제목과 설명을 무엇으로 할지 확인한다. 규약상 임의 신설은 금지다. 신설한다면 토론은 그 페이지 본문에서 진행하게 된다.
2. **진단 범위.** reconciliation 화면만인지, 아니면 휴지통 · 격리까지 묶어 Maintenance 영역 전체를 볼 것인지. 사용자의 불만은 reconciliation 을 지목했으나 운영자가 실제로 겪는 흐름은 세 화면을 오간다.
3. **이번 캠페인의 종착점.** 진단 목록 제출까지인지, 개선 슬라이스 구현까지 이어갈 것인지.
