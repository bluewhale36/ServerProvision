## 2. 표현은 이미 있는 형태를 그대로 쓴다

E29 의 "지정하거나 자동 탐지" 는 **이 저장소에 선례가 있다.** `BasicUpdateRequest` 가 메인보드를 그렇게 다룬다.

```java
/**
 * 메인보드 모델 선택 — {"mode":"AUTO"} 또는 {"mode":"SPECIFIED","boardModelId":1}.
 *
 * "자동 = null id" 같은 의미 있는 null 대신 선택 의도를 타입으로 명시한다(Primitive Obsession 금지).
 * AUTO 해석(실행 시점 보드 감지)은 execution 도메인의 몫이다.
 */
public record BoardModelSelectionRequest(BoardModelSelectionMode mode, Long boardModelId)
```

`@AssertTrue` 로 정합까지 지킨다 — SPECIFIED 는 id 필수, AUTO 는 id 금지.

RAID 카드도 같은 모양이면 된다. **새 패턴을 만들지 않는다.**

그리고 **카드 모델은 enum 이 맞다.** 모델이 둘로 한정돼 있고(E30), 캐시 유무가 상수 속성이 되며(`hasCache()`), CLAUDE.md 의 "enum method-per-constant 다형" 원칙에 그대로 얹힌다. `BoardModel` 처럼 management 자원으로 만들면 CRUD 화면 한 벌이 통째로 붙는데, 두 모델을 위해 그 비용을 치를 이유가 없다. 모델이 늘어 관리가 필요해지면 그때 자원으로 승격한다.

## 3. 실측으로 찾은 위험 — '자동 탐지' 가 동작하지 않을 수 있다

E29 의 자동 탐지가 성립하려면 **진단 수집값으로 두 모델을 구분할 수 있어야 한다.** 그것을 확인하러 파서를 열었고, **보장되지 않는다**는 것을 알았다.

### 3-1. 지금 수집되는 것

`DiagnosticReportParser.classifyPcie` 가 lspci 한 줄을 이렇게 쪼갠다.

```
"01:00.0 RAID bus controller: Broadcom / LSI MegaRAID 9560-8i"
   slot  = "01:00.0"
   kind  = "RAID"                              ← className 에 raid 가 있으면
   vendor= "Broadcom / LSI"                     ← KNOWN_VENDORS 접두 매칭
   model = "Broadcom / LSI MegaRAID 9560-8i"    ← descriptor 원문 전체
```

즉 `model` 은 **파싱되지 않은 lspci 서술 문자열**이다.

### 3-2. 그것으로 E30 의 두 모델을 가릴 수 있는가

**확신할 수 없다.** 이유가 둘이다.

1. **lspci 는 카드 상품명이 아니라 칩셋을 말하는 경우가 많다.** AVAGO 9361-8i 는 SAS3108 칩을 쓰므로 `Broadcom / LSI MegaRAID SAS-3 3108 [Invader]` 로 보고될 수 있다 — 문자열에 `9361-8i` 가 없다.
2. **GIGABYTE CRA3338 은 `KNOWN_VENDORS` 에 없다.** 목록은 `Broadcom / LSI` · `Broadcom` · `LSI` · `Intel` · `NVIDIA` · `QLogic` · `Emulex` · `Mellanox` · `Marvell` · `Realtek` · `Samsung` · `Micron` · `AMD` · `ASPEED` 로 **GIGABYTE 가 빠져 있다.** 리브랜드 카드면 원 칩 제조사로 보고될 수도 있어, 어떤 문자열이 오는지 실물 없이는 모른다.

그리고 저장소에 있는 유일한 RAID 표본은 mock 데이터 한 줄뿐이다 — `scripts/mock-guest/diagnose-cycle.sh` 의 `"01:00.0 RAID bus controller: Broadcom / LSI MegaRAID 9560-8i"`. **E30 의 두 모델 어느 것도 아니다.**

### 3-3. 그래서 갈라지는 것

| 할 일 | 지금 가능한가 |
|---|---|
| 정의서에 RAID 카드를 **지정**(SPECIFIED)하고 화면에 표현 | **가능** — §2 의 선례를 그대로 쓴다 |
| **자동 탐지**(AUTO) 로 두고 실행 시점에 카드에 맞는 명령을 고르기 | E31 대로 **E 단계** — 이 슬라이스 밖 |
| **자동 탐지 결과를 할당 시점에 판정**(이 서버 카드가 정의서 전제와 맞나) | **미검증** — 수집값이 모델을 가리는지 모른다 |

앞의 둘은 문제가 없다. **셋째가 걸린다.**

## 4. 남은 질문 하나

### R-13. 카드 모델 판정을 U4-1-1 이 어디까지 할까

§3 의 위험을 받아들이면 선택이 셋이다.

|     | 안               | U4-1-1 이 하는 일                                                               | 남는 것                                                                                        |
| --- | --------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| ①   | **표현까지만**       | 정의서에 `AUTO` / `SPECIFIED(모델)` 를 적고 화면에 보인다. 서버 카드와의 대조는 하지 않는다              | 대조는 E 단계에서 명령 조사와 함께. `docs/T3-checklist.md` 에 "lspci 로 CRA3338 · 9361-8i 를 구분할 수 있는가" 를 적립 |
| ②   | **문자열 포함 판정까지** | 수집된 `model` 문자열에 모델명 조각이 들어 있는지로 대조한다(예: `9361` · `CRA3338` · `SAS-3 3108`) | 실기에서 문자열이 예상과 다르면 **조용히 안 맞는다**. 규칙을 나중에 고쳐야 한다                                             |
| ③   | **수집 확장까지 함께**  | 진단 스크립트가 카드 모델을 정확히 보고하도록 고치고(벤더 CLI 등) 그 값으로 대조                            | E 계열(진단 수집)을 함께 건드려 이 슬라이스가 커진다. 실 장비 없이는 검증 불가                                             |

**내 판단은 ①이다.** 근거 셋 —

- **E31 이 이미 경계를 정했다.** "명령어 조사는 E 단계, 지금은 정의서에 남기는 것" 이라면, 대조도 그 조사와 함께 가는 편이 자연스럽다. 어떤 문자열이 오는지 알아야 대조 규칙을 쓸 수 있다.
- **②는 U3-5-d 에서 배운 실패 형태다.** 실물을 보지 않고 규칙을 짜면 "맞는 줄 알았는데 안 맞는" 상태가 조용히 남는다. `KNOWN_VENDORS` 에 GIGABYTE 가 없다는 것이 이미 그 징후다.
- **③은 실 장비가 전제다.** `project_mvp_release_line` 이 "실 장비 확보 = 일정 제1 변수" 로 두었고, 여기 묶으면 U4-1-1 이 그 변수에 걸린다.

①로 가면 U4-1-1 은 **실 장비 없이 완결**된다 — 정의서가 카드를 적고 화면이 그것을 보이는 것까지. 대조와 집행은 실 장비가 오는 시점에 한 묶음으로 간다.

> **R-13 답변:**
> 우선은 AUTO 기능은 비활성화 해두고 추후 개발. SPECIFIED 로만 개발을 진행한다.
> RAID card 부분은 추후 반드시 자원이든 다른 무엇인가로든 가변적인 형태로 승격처리 되어야 한다. 지금 당장 Enum 에 박아두는 설계도 솔직히 마음에 들지는 않는다. 주력으로 사용하는 것만 그 두가지일 뿐, 다른 raid card 도 충분히 많이 사용하고 있고, 특히 이번 MVP 대상인 GIGABYTE 서버급 4종 메인보드를 사용하지 않는 다른 서버는 대부분 다른 카드를 쓰기 때문. 다만 이를 위해서는 아래의 내용들이 선행될 필요가 있다고 생각한다 :
> 우선, notion E0-3 단계의 PCI 섹션에서 GIGABYTE 4종 보드의 BMC 내부 api 경로를 통해 PCIe system inventory 를 조회하는 경로와 그 결과르 넣어두었다. 현재 해당 섹션의 `Serial Attached SCSI controller` 는 GIGABYTE CRA3338 이다.
> 한가지 궁금한 것이 있는데, BIOS 에서도 GIGABYTE CRA3338 로 뜨지 않고 LSI SCSI controller 등으로 표시가 되는데, BIOS 랑 Linux lspci 에서는 이 RAID card 의 정확히 어떤 값을 읽어와서 렌더링을 하는지, BIOS setup menu 에서 Advanced 탭의 해당 RAID card 메뉴로 들어가서 raid 구성 등을 하는 건 어떻게 각 카드별로 커스텀되어서 가능한건지가 궁금하다.
> 특히 3-2 의 1번에서 `SAS3108 칩을 쓰므로...` 의 부분에서 궁금해진 것은, 같은 유형의 칩을 사용하면 lspci 에서 동일한 결과가 뜨는지, BIOS setup menu 의 설정이 동일한지 등이다.
