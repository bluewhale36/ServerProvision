## 1. 현행 실태 — 실측

착수 전에 무엇이 이미 있는지부터 쟀다. **셋 중 하나는 이미 절반이 구현돼 있다.**

### 1-1. 파티션 계약에 `diskName` 이 이미 있다

`PartitionRequest` (정의서 OS 설치 단계의 파티션 한 줄):

```java
/** 대상 디스크 장치명(선택). 비우면 설치기가 자동 선택. */
@Pattern(regexp = "^[A-Za-z][A-Za-z0-9]*$")
private final String diskName;
```

그리고 이것이 **끝까지 배선돼 있다** —

| 층 | 실측 |
|---|---|
| 입력 | `setting-form.js` 에 `.pDiskName` 입력칸(행마다 하나) |
| 저장 | `diskName: row.querySelector('.pDiskName').value.trim() \|\| null` |
| 표시 | `setting-process-cards.html` — 비어 있으면 "자동", 있으면 장치명을 monospace 로 |
| 검증 | `LinuxPartitionRules.validateGrowPerDisk` — **같은 디스크에 grow 파티션은 하나만**(`diskName` null/공백은 '자동 할당 그룹' 으로 묶어 함께 판정) |

즉 **U4-1-3 이 말하는 "특정 디스크에 특정 파티션 지정" 은 이미 동작한다.** 다만 **자유 텍스트**다 — 운영자가 `sda` 를 손으로 친다. 실존하는 디스크인지 확인하지 않고, 어떤 디스크가 있는지 화면이 알려주지도 않는다.

### 1-2. 디스크 인벤토리는 수집된다

`HardwareSpec.DiskInfo` — 진단 리눅스(E1)가 슬롯 단위로 적재한다.

```java
/** 디스크 1개 — SSD/HDD 구분 + 전송 방식(SAS/SATA/NVMe) + 용량. */
public record DiskInfo(String device, String type, String transport, String size) {}
```

`DiagnosticReportParser.parseDisks` 가 채우고 `guest_server_detail.hardware_spec` JSON 에 들어간다.
**U4-1-2 가 필요로 하는 입력(디스크 목록 · 종류 · 용량)이 이미 있다.**

### 1-3. RAID 는 "있다는 사실" 만 수집된다

`HardwareSpec.PcieDevice.kind` 가 `RAID` 값을 가질 수 있고, `DiagnosticReportParser` 가 lspci 원문에서 분류한다:

```java
if (cls.contains("raid") || desc.contains("megaraid")) return "RAID";
```

**그러나 RAID 를 구성하는 수단은 없다.** 그리고 `DiskInfo` 주석이 한계를 명시한다:

> RAID 카드 뒤 물리 디스크는 OS 불가시 — OPEN-1(벤더 CLI 동봉) 후속에서 확장

### 1-4. 실행 엔진에 OS 설치 executor 가 아직 없다

```
DiagnoseLinuxExecutor      ← 유일한 구현
PhaseExecutorRegistry
ProvisioningPhaseExecutor  ← 인터페이스
```

정의서에 무엇을 적든 **집행하는 코드는 진단 리눅스뿐**이다. OS 설치도 RAID 구성도 실행 주체가 없다.

## 2. 관통하는 긴장 — 정의서는 서버를 모른다

이 셋을 한데 묶는 문제가 하나 있다.

**세팅 정의서는 특정 서버를 모른 채 작성된다.** U3-1 이 derive-then-freeze 로 못 박았듯, 정의서는 템플릿이고 서버에 붙는 순간 스냅샷이 뜬다. 그래서 정의서에는 "이 서버의 sda" 같은 것이 원리적으로 들어갈 수 없다 — **`sda` 는 서버마다 다른 것을 가리킨다.**

지금 `diskName` 이 자유 텍스트인 것이 그 증거다. 어떤 서버에 붙일지 모르는 상태에서 장치명을 적으니, 그 정의서는 **디스크 구성이 같은 서버 묶음에만** 쓸 수 있다.

정의서가 하드웨어를 요구하는 선례는 이미 있다 — `RequiredBoardModel` 이 "이 정의서는 MS03-CE0 전용" 을 표현하고, U3-5-a 가 할당 시점에 대조해 막는다. 디스크도 같은 길을 갈 수 있지만, 보드는 **모델명 하나**인 반면 디스크는 **개수 · 종류 · 용량의 조합**이라 훨씬 넓다.

**해법의 방향은 셋이다.**

| | 방향 | 정의서에 적는 것 | 해석 시점 |
|---|---|---|---|
| **A** | 장치명 직접 (현행) | `sda` · `nvme0n1` | 없음 — 그대로 전달 |
| **B** | **역할 기반** | "OS 영역" · "Data 영역" | 실행 시점에 실제 디스크로 해석 |
| **C** | 규칙 기반 | "가장 작은 SSD" · "NVMe 중 첫 번째" | 실행 시점에 규칙 평가 |

**U4-1-2 의 'OS 영역 / Data 영역' 은 정확히 B 다.** 그리고 U4-1-3 은 A 를 개선하는 것이다.
그렇다면 둘은 **같은 문제의 두 해법**이고, 함께 설계해야 서로 어긋나지 않는다.

## 3. 열린 질문

### Q-1. U4-1-3 은 무엇을 더 하는 단계인가?

`diskName` 이 이미 있고 화면·검증까지 배선됐다는 실측(§1-1)을 보면, U4-1-3 의 남은 일은 셋 중 하나로 보인다.

1. **고르게 하기** — 자유 텍스트 대신 그 서버의 디스크 목록에서 선택. 다만 정의서는 서버를 모르므로(§2) **어느 서버의 목록을 보여줄 것인가**가 곧바로 문제가 된다
2. **검증 강화** — 형식만 보는 지금(`^[A-Za-z][A-Za-z0-9]*$`)에서 나아가, 할당 시점에 그 서버에 실제로 있는 장치명인지 대조(U3-5-a 의 하드웨어 대조와 같은 자리)
3. **표현 자체를 바꾸기** — 장치명을 버리고 역할 기반(B)으로 옮기며, U4-1-3 을 U4-1-2 에 흡수

### Q-2. 'OS 영역 / Data 영역' 은 무엇을 정하는 개념인가?

"디스크를 OS 영역과 Data 영역으로 나눈다" 가 가리킬 수 있는 것이 둘이다.

1. **디스크 단위 분류** — 디스크 A 는 OS 용, 디스크 B · C 는 Data 용. OS 설치는 A 에만 손대고 B · C 는 건드리지 않는다
2. **파티션 배치 규칙** — `/` · `/boot` 같은 OS 파티션은 어느 디스크로, `/data` 같은 것은 어느 디스크로 가는지의 규칙

전자면 **디스크마다 역할 라벨**을 붙이는 일이고, 후자면 **파티션마다 목적지 역할**을 적는 일이다. 데이터 모델이 달라진다.

또 하나 — 그 분류를 **어디에 저장하는가**도 갈린다.

| | 저장 위치 | 뜻 |
|---|---|---|
| ㄱ | **정의서** | "이 정의서는 OS 디스크 1개 + Data 디스크 N개 구성을 전제한다" (서버 무관 템플릿) |
| ㄴ | **서버** | "이 서버의 sdb 는 Data 용이다" (서버마다 운영자가 지정) |
| ㄷ | **둘 다** | 정의서가 역할을 요구하고, 서버 쪽에서 실제 디스크에 역할을 매긴다 |

ㄷ 이 B 방향의 완성형이지만 가장 무겁다.

> **Q-2 답변:**

### Q-3. RAID 구성은 **누가 집행**하는가?

U4-1-1 이 가장 무겁다. 정의서에 "RAID 1 로 묶어라" 를 적는 것과 **그것을 실제로 수행하는 것**은 다른 문제이고, 지금은 수행할 주체가 없다(§1-4).

RAID 구성을 거는 경로는 실무적으로 셋이다.

| | 경로 | 필요한 것 | 걸림돌 |
|---|---|---|---|
| ① | **BIOS/UEFI 설정** | BIOS 세팅 템플릿에 RAID 항목 | 벤더마다 항목이 다르고, 이미 BASIC_SETTING 이 담당하는 영역 |
| ② | **벤더 CLI**(storcli · perccli 등) | 진단 리눅스에 바이너리 동봉 | `DiskInfo` 주석의 OPEN-1 이 가리키는 그것. 벤더별 바이너리 관리가 붙는다 |
| ③ | **Redfish / BMC** | BMC 연동 | E2-R 이 BMC-Redfish 로 피벗한 것과 같은 길. 지원 여부가 모델마다 다르다 |

그리고 §1-3 의 한계가 여기서 되돌아온다 — **RAID 카드 뒤 물리 디스크는 OS 에서 안 보인다.** 즉 RAID 를 구성하려면 먼저 **RAID 카드에게 물어봐야** 하고, 그건 ②나 ③ 없이는 안 된다.

> **Q-3 답변:**

### Q-4. RAID 는 정말 U4(정의서 기능)인가?

Q-3 의 답이 ② 또는 ③이면, U4-1-1 의 대부분이 **E 단계(실행 엔진)** 의 일이 된다. 정의서에는 "RAID 1" 이라는 의사만 적히고, 그것을 읽어 집행하는 코드는 executor 다.

그렇다면 U4-1-1 을 이렇게 나눌 수 있다.

- **U4 쪽** : 정의서에 RAID 의사를 적는 계약과 화면 (가볍다)
- **E 쪽** : 그 의사를 집행하는 executor + 벤더 CLI 자산 (무겁다. 실 장비 없이는 검증 불가)

`project_mvp_release_line` 이 정한 MVP 선(필요조건 E3 · 충분조건 E4)과의 관계도 함께 봐야 한다 — RAID 가 MVP 안인가 밖인가.

### Q-5. 세 하위 단계의 순서는 지금이 맞는가?

Notion 의 번호는 `U4-1-1 RAID → U4-1-2 분류 → U4-1-3 파티션 지정` 이다. 그런데 실측(§1)이 말하는 난이도와 의존은 반대에 가깝다.

```
U4-1-3  파티션 디스크 지정   ← 계약·화면·검증이 이미 절반 있다
U4-1-2  OS/Data 영역 분류    ← 입력(DiskInfo)은 수집되나 개념이 없다
U4-1-1  RAID 구성            ← 집행 주체 자체가 없다
```

그리고 §2 가 말했듯 **U4-1-2 와 U4-1-3 은 같은 문제의 두 해법**이라 따로 하면 어긋난다.

제안 — **순서를 뒤집고 앞 둘을 묶는다.**

| 새 순서 | 내용 | 근거 |
|---|---|---|
| 1 | **디스크 지정 체계**(현 1-3 + 1-2 통합) | 같은 문제라 함께 설계해야 어긋나지 않는다 |
| 2 | **RAID 의사 표현**(정의서 쪽만) | 집행과 분리하면 가볍고 지금 할 수 있다 |
| 3 | RAID 집행 | E 단계로 이관 — 실 장비 확보가 전제 |

번호를 바꾸면 Notion 페이지도 함께 고쳐야 한다.

### Q-6. LVM 은 이 범위에 들어오는가?

`project_mvp_release_line` 이 "RHEL 간단 세팅만, **LVM 은 뒤로**" 로 정해 두었다. 그런데 디스크 여러 개를 다루기 시작하면 LVM 이 자연스럽게 따라온다 — 여러 디스크를 하나의 볼륨 그룹으로 묶는 것이 바로 그 용도다.

이번 U4-1 은 **LVM 없이 물리 파티션만** 다루는 것으로 두고, LVM 은 확정대로 뒤에 두는 것이 맞다고 본다. 다만 지금 만드는 데이터 모델이 나중에 LVM 을 받을 수 있는 모양인지는 봐 둘 가치가 있다.

> **Q-6 답변:**
> LVM 구성은 해당 범위 외로 한다.


> 제안된 상기 질문들에 각각 답변하는 것이 어려우므로 아래 문단으로 답한다 :
> 일반적으로 게스트 서버에는 같은 스펙의 디스크를 둘 이상 넣는다.
> OS 영역은 OS 가 설치되는 디스크를 말한다. linux 의 경우 boot, efi, swap, root 파티션이 들어가는 디스크, windows 의 경우 C 드라이브다. 보통 SSD 로 구성된 RAID 1 이다.
> Data 영역은 이 외 디스크를 말한다. 이 경우 각 디스크(RAID 구성) 개수만큼 Data 영역이 생긴다. linux 의 경우 이를 /data1, /data2, ... 로 파티션을 생성하며, windows 의 경우 os 설치 이후 D, E, ... 드라이브로 잡는다. SSD, HDD 의 RAID0, 1, 5, 6 이며, 존재하지 않을 수도 있다.
> RAID 를 잡는 로직 자체는 E 영역이 맞으나, 이를 어떻게 구성할지는 세팅 정의서에서 정의를 해줘야 한다. 동일한 스펙의 디스크가 2개, 3개 이상으로 갈 경우 각각 RAID1, RAID5 로 잡는 업무 상 관례가 있다.
> 서버에 디스크는 SSD → HDD 순서로, 용량이 작은 것에서 큰 것 순서로 장착된다.
> RAID 카드는 대체로 장착되며, 같은 스펙의 디스크가 3개 이상 존재하는 경우 캐시가 있는 모델을 사용, 그렇지 않은 경우 캐시가 없는 모델을 주로 사용한다.
> 일반적으로 작업 순서는 RAID 구성 → OS 설치 시 RAID 디스크 지정 이므로 단계 구성은 이 프로세스를 따른 것이다.
> 예시를 들어 설명한다. SSD 480GB 2개와 HDD SATA 4TB 2개가 게스트 서버에 있는 경우, SSD 480GB 2개와 HDD SATA 4TB 2개를 각각 RAID1 로 구성한다. SSD 480GB 2개 RAID1은 'OS 영역', HDD SATA 4TB 2개 RAID1은 'Data 영역'으로 구분하는 것이다.
