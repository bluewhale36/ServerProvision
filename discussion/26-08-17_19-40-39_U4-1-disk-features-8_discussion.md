## 2. 기술 질문 셋에 대한 답

세 질문이 하나의 사실로 이어진다 — **PCI 장치는 자기를 두 겹으로 소개한다.**

### 2-1. lspci 와 BIOS 가 읽는 값 — PCI Configuration Space

모든 PCI 장치는 설정 공간(Configuration Space)에 네 개의 식별자를 갖는다.

| 필드 | 무엇을 가리키나 | 예 |
|---|---|---|
| **Vendor ID** | **칩**을 만든 회사 | LSI / Broadcom = `0x1000` |
| **Device ID** | **칩** 모델 | SAS3108 = `0x005d` |
| **Subsystem Vendor ID** | **카드**를 만든 회사 | GIGABYTE = `0x1458` |
| **Subsystem Device ID** | **그 회사의 카드** 모델 | 벤더마다 다름 |

앞의 둘은 **칩**을, 뒤의 둘은 **완제품 카드**를 가리킨다. GIGABYTE CRA3338 처럼 남의 칩을 쓰는 카드는 **Vendor/Device 는 Broadcom 것이고 Subsystem 만 자기 것**이다.

`lspci` 는 **기본적으로 앞의 둘만** `pci.ids` 데이터베이스에서 이름으로 바꿔 보여준다. 그래서 칩 이름이 나온다. 카드 상품명을 보려면 옵션이 필요하다.

```
$ lspci                    ← 우리가 지금 쓰는 것
01:00.0 RAID bus controller: Broadcom / LSI MegaRAID SAS-3 3108 [Invader] (rev 02)

$ lspci -nn                ← Subsystem 이 함께 나온다
01:00.0 RAID bus controller [0104]: Broadcom / LSI MegaRAID SAS-3 3108 [Invader] [1000:005d] (rev 02)
        Subsystem: Broadcom / LSI MegaRAID SAS 9361-8i [1000:9361]
```

**BIOS 도 같은 값을 읽는다.** `LSI SCSI controller` 로 뜨는 것은 Vendor/Device(=칩)를 보고 있거나, 카드 드라이버가 등록한 이름을 그대로 쓰기 때문이다.

**실측** — 우리 진단 에이전트는 옵션 없이 부른다.

```sh
# scripts/diag-image/agent/agent.sh:94
lspci 2>/dev/null | awk '…'
```

즉 **Subsystem 을 수집하지 않는다.** §7-3 에서 "두 모델을 구분할 수 있을지 모른다" 고 한 위험의 정확한 정체가 이것이다 — 구분에 필요한 값을 **애초에 안 가져오고 있다.**

### 2-2. BIOS setup 의 카드 메뉴는 어떻게 카드마다 다른가

**BIOS 가 카드를 아는 것이 아니라, 카드가 자기 메뉴를 들고 온다.**

RAID 카드의 flash 에는 **UEFI Driver** 가 들어 있고, 그 안에 **HII(Human Interface Infrastructure) 폼**이 함께 있다. 부팅 순서는 이렇다.

1. BIOS 가 PCI 버스를 훑어 카드를 찾는다
2. 카드 flash 의 UEFI Driver 를 메모리에 올려 실행한다
3. 그 드라이버가 자기 **HII 폼**을 BIOS 에 등록한다
4. BIOS setup 의 Advanced 탭이 등록된 폼들을 목록으로 그려 준다

그래서 **BIOS 를 업데이트하지 않아도 카드를 바꾸면 메뉴가 바뀐다.** 메뉴의 항목 · 문구 · 동작은 전부 카드 드라이버가 정한다. GIGABYTE 카드에서 `LSI` 이름이 보이는 것도 같은 이유다 — **LSI 가 만든 드라이버를 그대로 싣고 Subsystem ID 만 자기 것으로 바꾼 리브랜드**이기 때문이다.

### 2-3. 같은 칩이면 결과가 같은가

|                         | 같은가           | 이유                                      |
| ----------------------- | ------------- | --------------------------------------- |
| 기본 `lspci` 출력           | **같다**        | Vendor/Device 가 같으므로                    |
| `lspci -nn` 의 Subsystem | **다르다**       | 여기서 갈린다                                 |
| BIOS setup 메뉴           | **대체로 같다**    | 같은 드라이버를 실으므로. 벤더가 커스텀 펌웨어를 넣으면 다를 수 있다 |
| RAID 구성 CLI 명령          | **칩 계열이 정한다** | `storcli` 는 MegaRAID 칩 계열 전체를 다룬다       |

**마지막 줄이 중요하다.** 6회차에 "캐시 유무에 따라 명령이 다르다" 로 적었는데, 더 정확히는 **칩 계열과 동작 모드**가 명령을 가른다. 같은 MegaRAID 계열이면 캐시가 있든 없든 `storcli` 로 다룬다.

### 2-4. 다만 CRA3338 은 확인이 필요하다

E35 가 준 단서가 하나 있다 — BMC inventory 에서 CRA3338 이 **`Serial Attached SCSI controller`** 로 잡힌다는 것이다. `RAID bus controller` 가 **아니다.**

PCI 클래스 코드가 다르다는 뜻이고, 이는 그 카드가 **RAID 컨트롤러가 아니라 HBA(호스트 버스 어댑터)** 로 동작하고 있을 가능성을 가리킨다. HBA 는 디스크를 OS 에 그대로 노출하고 RAID 를 만들지 않거나, IR 모드에서 RAID 0/1/10 정도만 지원한다.

**그렇다면 D7("3개 이상이면 캐시 있는 모델")의 진짜 이유가 캐시가 아니라 RAID5 지원 여부일 수 있다.** 캐시는 그 카드들이 함께 갖는 성질이고, 가르는 것은 **RAID5 를 만들 수 있는 컨트롤러인가**다.

**이것은 내가 실물로 확인하지 못했다.** 두 가지가 실기 확인 대상이다.

1. CRA3338 이 HBA 인가 RAID 컨트롤러인가 — RAID5 를 만들 수 있는가
2. 두 카드의 구성 명령이 실제로 다른가(같은 `storcli` 로 되는가)

우리 진단 파서에도 이 사실이 이미 걸려 있다 — `kindOf` 는 `className` 에 `raid` 가 있거나 서술에 `megaraid` 가 있을 때만 `RAID` 로 분류한다. **`Serial Attached SCSI controller` 는 그 조건에 걸리지 않아 `ETC` 로 분류된다.** 즉 지금 코드로는 CRA3338 이 RAID 카드로 잡히지 않는다.

## 3. 이 답이 바꾸는 것

### 3-1. 자동 탐지가 '불가능' 이 아니라 '옵션 하나' 였다

7회차에서 나는 자동 탐지 판정을 **③(수집 확장이 필요해 무겁다)** 으로 보고 미루자고 했다. **그 판단이 과했다.**

필요한 것은 `agent.sh` 한 줄이다.

```diff
- lspci 2>/dev/null | awk '…'
+ lspci -nn 2>/dev/null | awk '…'
```

그러면 Subsystem 이 문자열에 함께 오고, 서버 파서가 `[1458:xxxx]` 같은 id 를 뽑아 카드를 **정확히** 식별할 수 있다. 이름 매칭이 아니라 **숫자 id 대조**라 문자열 변덕에 흔들리지 않는다.

다만 이것은 **진단 자산(E 계열) 변경**이라 U4 슬라이스가 자기 안에서 할 일은 아니다. 그리고 실기 표본 없이 옵션만 바꾸면 파싱 규칙을 검증할 수 없다.

**E33(AUTO 비활성)은 그대로 두는 것이 맞다고 본다.** 다만 미루는 이유가 "무거워서" 가 아니라 **"실기 표본이 없어서"** 로 바뀐다. 표본이 생기는 즉시 열 수 있다.

### 3-2. enum 이 아니라 자원이 맞다

E34 가 "추후 반드시 승격되어야 한다" 고 했고, 나도 §2-1 을 쓰면서 생각이 바뀌었다. **지금 자원으로 만드는 편이 낫다.**

근거 셋 —

- **식별 키가 문자열이 아니라 PCI Subsystem ID 다.** 카드 목록이 `{subsystemVendorId, subsystemDeviceId, 이름, 캐시 유무, 칩 계열}` 같은 **여러 필드의 행**이 된다. enum 상수에 담기에는 필드가 많다.
- **모델이 늘어난다는 것이 이미 확정이다**(E34). enum 이면 정의서에 상수 이름이 저장되고, 나중에 자원으로 승격할 때 **그 값을 마이그레이션**해야 한다. 처음부터 id 참조면 그 비용이 없다.
- **선례가 있다.** `BoardModel` 이 정확히 그 형태이고, `BasicUpdateRequest` 가 `boardModelId` 로 참조한다. RAID 카드도 같은 모양이면 화면 · 검증 · 참조가 전부 같은 길을 간다.

비용은 관리 화면 한 벌이다. 다만 **필드가 적어** BoardModel 보다 가볍다 — 이름 · 제조사 · Subsystem ID · 캐시 유무 정도.

## 4. 남은 질문

### R-14. RAID 카드를 management 자원으로 만들 것인가, 만든다면 어느 슬라이스에서

§3-2 의 판단을 받아들이면 자원 하나가 생긴다. 그것을 어디서 만들지가 갈린다.

| | 안 | 뜻 |
|---|---|---|
| ① | **U4-1-1 안에서** | RAID 구성 지정과 함께. 슬라이스가 커지지만 한 흐름으로 완결된다 |
| ② | **선행 슬라이스로 분리**(`MA*` 계열) | 자원 등록은 Management 영역이므로 그쪽 번호로. U4-1-1 은 그것을 참조만 한다 |
| ③ | **이번엔 enum, 나중에 자원** | E34 가 승격을 예고했지만 지금은 가볍게 간다 |

**내 판단은 ②다.** RAID 카드 등록은 성격상 **Management**(자원 관리)이지 Provisioning(정의서)이 아니다. `os` · `board` · `bios` · `bmc` · `subprogram` 이 사는 자리에 하나 더 붙는 형태이고, U4-1-1 은 `BasicUpdateRequest` 가 `BoardModel` 을 참조하듯 id 로 참조하면 된다.

②로 가면 U4-1-1 의 CP1 앞에 작은 슬라이스가 하나 선행한다. 그 대신 U4-1-1 자체는 정의서 표현에만 집중한다.

> **R-14 답변:**
> 2로 진행한다.
> 다만 RAID card 의 자원 등록은 조금 다른 특징을 가지고 있어야 한다. BoardModel 도 사실은 이 과정을 어느 정도 거칠 필요는 있었으나 크게 문제되지 않을 듯해서 생략했다.
> RAID card 는 상기 설명된 내용에 따라 수집해야 하는 정보가 상대적으로 많은데 비해 이를 실 사용자에게 직접적으로 노출시켜주지 않는다. 따라서 **사용자가 직접 자원을 등록할 때 작성할 수 있는 것은 모델명, 캐시 유무, Subsystem Vendor** 정도일 뿐, 다른 세세한 정보는 일일이 등록하라면 할 수는 있겠지만 매우 귀찮아진다. UX 가 저하되는 것.
> 향후 MVP 배포 이후에도 이런 기능을 구현하고 싶었는데, RAID card 는 자원으로 등록한 다음 '정밀 등록' 또는 '직접 관측' 등의 이름으로 기능을 하나 추가하면 좋을 듯하다. 등록한 RAID card 를 장착한 guest server 에 연결해서, 프로비저닝을 돌리듯이 하드웨어 스펙을 관찰하는 기능이다. 자원으로 GIGABYTE CRA3338, no cache 등으로 등록해두고 해당 카드를 장착한 서버에 연결해서 정밀 등록을 실행하면 프로그램에서 필요한 추가 정보를 알아서 등록시키는 것이다.
> 선행하는 MA 슬라이스를 위해 브리핑을 하나 작성하라. 위치는 `../ServerProvision-m/discussion/` 아래다.

### R-15. 실기 확인 항목을 어디에 적립할까

§2-4 가 남긴 확인 대상 둘 + §3-1 의 표본 문제를 `docs/T3-checklist.md` 에 적립하려 한다. 적을 내용은 이렇다.

- `lspci -nn` 출력에서 CRA3338 · 9361-8i 의 **Subsystem ID 실측값**
- CRA3338 이 **RAID 컨트롤러인가 HBA 인가** — RAID5 를 만들 수 있는가
- 두 카드의 **구성 명령이 실제로 다른가**(같은 `storcli` 로 되는가)
- BMC inventory 의 `Serial Attached SCSI controller` 분류가 **우리 파서의 `kindOf` 에서 `ETC` 로 떨어지는 문제**(지금 코드로는 CRA3338 이 RAID 카드로 안 잡힌다)

마지막 항목은 **지금 코드의 결함에 가깝다.** 실기 확인 없이도 `kindOf` 에 SAS 컨트롤러 분류를 더할 수 있지만, 그것이 RAID 카드인지 단순 HBA 인지 구분하려면 결국 실물이 필요하다.

> **R-15 답변:**
> CRA3338 은 RAID5 이상을 만들지 못한다. 최소 2개 디스크에서의 RAID0, RAID1 만 지원된다.
> 두 카드의 구성 명령은 다른 것으로 알고는 있으나 정확히 알지 못한다. 이 부분은 E 슬라이스에서 WebSearch 를 통해 조사해야 하는 부분.
> 또한 PCIe 카드 수집 시 `lspci -nn` 옵션으로 진행하도록 수정도 해야 한다.
