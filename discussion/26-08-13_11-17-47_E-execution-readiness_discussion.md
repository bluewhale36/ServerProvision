# E 실행 유효성 검증의 자리 — 별도 검증 단계인가, 하위 단계 내장인가

## 1. 무엇을 정하려는가

E 단계(진단 리눅스 이후 — 펌웨어 업데이트 · 펌웨어 설정 · OS 설치 · OS 설정)를 구현할 때, 실행의 유효성 검증을 어디에 둘 것인가.

- **안 A** — 각 phase 앞(또는 실행 전체 앞)에 검증 단계를 별도 신설해 한 곳에서 확인한다.
- **안 B** — 각 phase 의 하위 단계를 구현하면서 그 안에서 유효성을 각자 확인한다.
- **안 C** — 검증 지식은 phase 실행기가 다형으로 소유하되, 판정 시점과 판정 어휘라는 틀은 엔진이 한 곳에서 제공한다.

이 문서의 권고는 **안 C** 다. 근거는 §3~§5, 권고안의 골자는 §6, 사용자 판단이 필요한 열린 질문은 §7 이다.

## 2. 실측 — 유효성 검증의 현재 배치

지금 코드에서 유효성을 보는 지점은 네 곳이고, 성격이 전부 다르다.

| 시점                | 걸려 있는 것                                        | 성격                                    |
| ----------------- | ---------------------------------------------- | ------------------------------------- |
| 정의서 저장 (U2)       | `ProcessReferenceInspector.validateReferences` | 하드 가드 — 실존 404 / enabled 409 / 정합 400 |
| 정의서 조회 (U2)       | `ExecutionWarningResponse`                     | 안내만 — 저장을 막지 않는 조회 시점 판정              |
| 할당 (U3-5-a)       | `AssignmentBlockKind.evaluate`                 | 하드 가드 — 회수 서버 · 보드 불일치                |
| 개시 · phase 진입 (E) | **없음**                                         | —                                     |

마지막 줄의 공백이 이 토론의 대상이다. `AssignmentStartService.startProvisioning` 은 미개시 · 미회수 가드만 통과하면 스냅샷을 소비하고, `BootScriptDispatcher.dispatch` 는 회수 · 실패 · 종단 · 미개시를 거른 뒤 실행기에 위임할 뿐 — 게스트가 phase 로 들어가는 어느 지점에서도 "그 phase 의 재료가 지금 유효한가" 를 묻지 않는다.

한편 조회 시점 경고에는 이미 실행 의미론이 확정돼 있다(2026-07-06). `ExecutionWarningResponse` 원문 —

> 실행 의미론: `blocking=false` 는 해당 축만 skip + PARTIAL_SUCCESS(펌웨어 부재), `blocking=true` 는 단계 수행 불가 = 실행 실패(ISO 소실 — OS 설치는 건너뛸 수 없는 본체 단계).

즉 "실행이 결손을 만나면 어떻게 행동해야 하는가" 의 어휘는 이미 있고, 그것을 **집행하는 자리** 가 없다.

## 3. 전제가 되는 구조적 사실 셋

**첫째, 단일 시점 검증은 이 시스템에서 성립하지 않는다.** 프로비저닝 실행은 재부팅을 넘나들며 길게 이어지고, 그 사이에 자원 세계는 계속 움직인다 — soft-delete, 드리프트 격리, deprecated 전환, 파일 소실. 개시 직후 검증 단계를 한 번 통과시켜도 세 번째 phase 도달 시점엔 그 결과가 낡아 있을 수 있다. 검증과 소비 사이의 시간차 문제(TOCTOU — Time-of-check to time-of-use)가 실행 전 구간에 깔려 있으므로, 검증은 **소비에 가장 가까운 지점** 에서 해야 의미가 있다.

**둘째, phase 마다 검증할 것의 성격이 극단적으로 다르다.**

- **FIRMWARE_SETTING** — 할당 시점에 `FrozenBiosSettings` 로 deep-freeze 된다(U3-1 결정 D-C). 템플릿이 나중에 지워져도 스냅샷이 자족적이라 E 시점에 검증할 외부 의존이 거의 없다.
- **FIRMWARE_UPDATING** — 정반대다. "최신 버전" 모드는 실행 시점에야 해소되는 소프트 참조라 검증할 것이 전부 E 시점에 있다. E2 재편이 확정한 **E2-1 resolve** 가 바로 그 해소 로직이고, 그 로직이 곧 이 phase 의 유효성 검증 그 자체다.
- **OS_INSTALLING** — ISO 실존이 전부이고, 건너뛸 수 없는 본체 단계(blocking=true)다.

**셋째, `ProvisioningPhase` 는 게스트 작업의 체크포인트라는 영속 계약이다.** `SettingAssignment.ownedPhases` CSV 컬럼에 얼려지고, `ProvisioningProgress` 커서가 그 위를 걷고, `SetupStep` 원장이 phase 단위로 쌓이고, 화면의 phase 레일(`PlannedPhaseRailResponse`)에 그대로 노출된다.

## 4. 안 A 를 기각하는 이유 — 검증은 게스트가 하는 일이 아니다

검증 phase 를 신설하면 §3 의 셋째 사실과 정면 충돌한다. 검증은 서버가 자기 DB 와 파일시스템을 들여다보는 행위이지 게스트가 수행하는 작업이 아닌데, 이를 phase 어휘에 끼우면 — 게스트가 한 일이 없는 phase 가 원장에 남고, 사용자가 할당한 적 없는 단계가 레일에 그려지고, `ownedPhases` 파생 규칙(`SettingProcessPhaseMapper`)에 "모든 할당에 검증 phase 강제 삽입" 같은 특례가 생긴다.

첫째 사실과도 충돌한다. 실행 앞 단일 검증은 시간차 문제를 못 없애므로, 검증 phase 를 두더라도 각 phase 진입 시점의 재확인이 **또** 필요하다 — 그러면 검증 phase 는 중복 계층이 된다.

둘째 사실은 phase 앞 균일 검증의 실익을 깎는다. 어떤 phase 에선 확인할 것이 없고(FIRMWARE_SETTING), 어떤 phase 에선 그 phase 의 내부 지식(펌웨어 해소 규칙)을 중앙 검증기가 다 알아야 한다. 후자는 `instanceof` 사다리의 자석이 되어 "신규 phase 지원 = 분기 추가가 아니라 빈 등록" 이라는 `ProvisioningPhaseExecutor` SPI 의 설계 의도(DEC-6)를 거스른다.

## 5. 안 B 를 기각하는 이유 — 틀 없는 분산은 의미론을 가른다

하위 단계를 구현하면서 실행기마다 즉흥적으로 유효성을 확인하면, 판정 어휘와 결손 처리 방식이 실행기마다 갈라진다. §2 에서 봤듯 skip / 실패의 의미론은 2026-07-06 에 이미 확정됐는데, 이를 실행기들이 제각각 재해석하면 U 화면이 경고한 것과 E 실행이 실제로 한 행동이 어긋난다 — UI 차단 조건과 서버 가드 조건의 SSOT 공유 원칙(불가침)의 실행판 위반이다. 또한 결손 시 게스트에게 무엇을 줄지(대기 스크립트 / 실패 전환)와 운영자에게 어떻게 알릴지가 실행기마다 다르게 발명된다.

## 6. 권고안(안 C)의 골자 — 실행기 소유 + 엔진 제공 틀

세 번 반복된 해법 구조가 있다. **문제 자체는 서로 다르다** — 드리프트 분류(maintenance) · 할당 차단(provisioning) · 자원 생명주기(전 도메인)는 도메인도 목적도 다르다. 같은 것은 문제의 **구조**다: ⓐ 종류가 앞으로 늘어난다는 것이 확정된 열린 변형 집합이 있고, ⓑ 그 종류들을 소비하는 지점이 여럿이며, ⓒ 분기문으로 짜면 종류 하나가 늘 때마다 소비 지점 수만큼 분기가 복제된다. 이 3요소를 갖춘 문제에 대해 세 곳이 독립적으로 같은 해법 구조에 도달했다 — 종류별 지식은 종류 자신이 다형으로 소유하고, 시점 · 순서 · 어휘라는 틀은 단일 지점이 소유하며, 새 종류 추가 = 상수/빈 추가(소비 지점 무변경).

| 사례 | 늘어나는 축 | 종류가 소유하는 것 | 틀 1곳 |
|---|---|---|---|
| `DriftKind` | 드리프트 종류 (12종째 S11-1) | 라벨 · 해결 가능 · 가역 | 화면 enum SSOT 배선 (R9-2) |
| `AssignmentBlockKind` | 차단 사유 (U4 디스크 예정) | 판정 · 예외 · 표시 색 | `evaluate` 순회 (소비 지점 4곳) |
| `LifecycleService` | 자원 도메인 | 동작 구현 (cascade · 마커) | 공통 계약 7동작 |

검증 문제도 같은 3요소를 갖췄다 — 준비도 기준은 phase 마다 다르고 phase 는 늘어나며(ⓐ), 판정을 소비할 자리가 dispatcher · 서버 상세 화면 · (Q4 채택 시) 개시 경고로 여럿이다(ⓑ). 그리고 `ProvisioningPhaseExecutor` SPI 자체가 이미 이 구조의 네 번째 실물이므로(`bootScript` · `onStepClosed` 두 훅이 "phase 별 지식은 실행기 소유, dispatch 는 엔진 틀" 로 동작 중), 준비도는 새 패턴의 도입이 아니라 **기존 실물에 세 번째 훅을 더하는 것**이다. 변형이 데이터와 순수 판정만 들면 enum, 의존성을 들고 행동하면 interface + bean 이라는 기구 선택 규칙에서도 준비도는 후자 — 셋 중 가장 가까운 친족은 `LifecycleService` 다.

**① 계약** — `ProvisioningPhaseExecutor` 에 준비도(readiness) 판정을 추가한다. default 는 "준비됨" — 정의서 payload 를 소비하지 않는 phase(진단)는 구현하지 않는다. 신규 phase 의 검증 = 분기 추가가 아니라 이 훅 구현이다(`onStepClosed` 와 같은 확장 방식).

**② 판정 어휘 3값** — 2026-07-06 의미론과 정렬한다.

| 판정 | 뜻 | 게스트가 받는 것 |
|---|---|---|
| READY | 재료 온전 | 정상 phase 스크립트 |
| DEGRADED | 일부 축 결손 | 진행 — 결손 축 skip, 종결은 PARTIAL_SUCCESS |
| BLOCKED | 본체 재료 결손 | 진행 불가 — 처리 방식은 §7 Q1 |

**③ 판정 지점** — `BootScriptDispatcher` 의 실행기 위임 직전, 즉 **게스트가 그 phase 로 부팅해 들어오는 재진입 순간** 이다. 이 지점이 정확한 이유가 셋이다.

1. 소비에 가장 가까워 검증-소비 시간차가 최소다.
2. 게스트는 폴링으로 계속 재진입하므로, BLOCKED 에 대기 스크립트를 주면 운영자가 자원을 되살리는 순간 다음 폴링에서 저절로 풀린다. `ExecutionWarningResponse` 가 경고를 저장 차단으로 만들지 않은 이유("정의서 = 재사용 템플릿 — 실행 전 등록되면 자동 해소")가 E 에서 "재등록되면 자동 재개" 로 자연 연장된다. `IpxeScripts.hold` · `awaitingIntake` 라는 대기 프리미티브도 이미 있다.
3. 커서를 오염시키지 않는다. `PhaseCursorAdvancer` 전진 판정에 검증을 끼우는 대안은 "커서는 게스트 사실 신호에만 움직인다"(DEC-2)는 원칙에 자원 세계 상태를 섞고, 전진 후 부팅까지의 시간차도 못 없애므로 기각한다.

**④ 판정 기준의 거처** — "이 자원 참조를 지금 실행에 쓸 수 있는가" 라는 축별 술어가 진짜 SSOT 다. 펌웨어 축이라면 그 술어는 E2-1 resolve 의 부수효과 없는 시운전이다 — 별도 검증 로직을 새로 짓는 것이 아니라 resolve 를 진입 시점에 미리 한 번 돌려 보는 것. U 화면 경고와 E 준비도 판정이 이 술어를 공유하면 "화면이 경고한 것 = 실행이 거절한 것" 이 구조로 보장된다. 입력은 다르다 — U 는 살아 있는 정의서를, E 는 동결 스냅샷 + 현재 자원 세계를 본다. 공유되는 것은 자원 쪽 술어다.

**⑤ 운영자 가시성** — 대기는 게스트만 조용히 기다리는 상태라, 서버 상세 화면에 "무엇 때문에 대기 중인가" 를 노출해야 한다. `GuestServerChangedEvent` + `GuestServerStreamService` 실시간 배선이 이미 있다.

이렇게 하면 "검증 단계" 는 사라지는 것이 아니라 세 겹으로 분해된다 — 각 겹이 잡는 결함의 시점이 달라 어느 하나로 대체되지 않는다.

```
U — 사람 결정 지점        정의서 저장 가드 · 조회 경고 · 할당 가드 (전부 실재)
E — phase 진입 준비도     부팅 재진입 시 실행기 판정 (이번 토론의 신설분)
서빙 — 최후 방어          자산 서빙 시점 가드 (SystemAssetServingDisabledException 류 일부 실재)
```

## 7. 열린 질문

### Q1. BLOCKED 진입 결손 — 대기(hold)인가 즉시 실패인가

2026-07-06 결정 원문은 blocking=true → "실행 실패" 다. 그러나 그 결정은 대기 프리미티브(`awaitingIntake` 폴링, DEC-26 개시 게이트)가 성숙하기 전의 것이다. 정제안 —

- **진입 전 결손은 대기.** 아직 아무것도 시작하지 않았고, 폴링이 공짜 재시도라 운영자가 ISO 를 재등록하면 자동 재개된다. 아무 일도 안 했는데 FAILED 딱지가 붙고 수동 재시도 절차를 밟는 것보다 낫다.
- **실행 중 결손은 실패.** phase 가 실제로 착수한 뒤의 결손은 진짜 실패이므로 기존 markFailed 경로를 탄다.

즉 "실행 실패" 는 착수 후에만 적용되도록 결정을 정제한다. 대안은 원문대로 진입 결손도 즉시 실패(명시성 우선 — 실패 목록에서 발견됨, 대신 조용한 장기 대기 위험은 없음). **과거 확정의 수정이므로 재확정을 요청한다.**

> 수용. 단 진입 전 결손도 TTL 을 둔다.

### Q2. DEGRADED 의 skip 사실을 어디에 기록하는가

축 결손으로 건너뛴 사실은 감사 기록으로 남아야 한다("처리 이력은 사실과 다른 줄 0" — S11 D3 와 같은 요구). 후보 —

- ⓐ `SetupStep` 원장에 skip 표시 스텝을 남긴다 — 게스트 관점에서도 "이 축을 안 했다" 는 사실이므로 원장 자격이 있다는 해석. 반론: 게스트가 보고하지 않은 행을 서버가 만들면 "원장 = 게스트 사실 신호" 의 순도가 깨진다.
- ⓑ phase 종결 상태를 PARTIAL_SUCCESS 로 두고 결손 사유를 progress 수준에 기록한다.
- ⓒ 별도 실행 이력 축을 신설한다.

방향만 여기서 합의하고 세부는 E2-1 plan 에서 확정해도 된다. 세션 권고는 ⓑ — 원장 순도를 지키면서 스키마 신설 없이 감사 요구를 채운다.

> 현재 execution 도메인 관련된 DB table 설계 및 관계를 정확히 인지하지 못하고 있는 상황이다. 가능하다면 관련된 테이블 그리고 그 관계에 대한 설명을 별도 문서로 설명 진행할 것.

### Q3. 슬라이스 배치 — 준비도 계약을 언제 만드는가

- ⓐ 독립 슬라이스(ES 계열)로 선행 — 계약 + dispatcher 배선 + 대기 스크립트 + 화면 노출을 먼저. 반론: 현재 등록 실행기가 진단뿐이라 구현자가 default 뿐이고, 소비자 없는 추상을 미리 만드는 것은 "갈라지는 시점에 분리" 원칙 위반이다.
- ⓑ E2-1 동반 — 첫 실소비자(펌웨어 resolve 시운전)와 함께 계약이 태어난다. 계약의 모양이 실측으로 검증되고, E2-1 의 "진입 골격 + resolve" scope 와 자연스럽게 겹친다.

세션 권고는 ⓑ. 이 경우 E2-1 의 scope 문장에 "준비도 계약 신설 + FIRMWARE_UPDATING 첫 구현" 이 명시적으로 들어간다.

### Q4. 개시 시점의 사람 결정 지점을 보강하는가

U3-5-a 는 할당 시점까지 왔고, 개시는 여전히 무검사다(회수 · 중복 개시 가드만). 개시 버튼을 누르는 순간 "현재 할당의 재료에 결손이 있다" 를 **비차단 경고** 로 보여줄지 — UI 1차 차단 원칙의 연장으로, 운영자가 대기에 빠질 실행을 알고 시작하게 한다. 차단은 하지 않는다(진입 준비도의 대기가 받아 주므로 흐름이 끊기지 않고, "실행 전 등록되면 자동 해소" 흐름도 유효하다). 시기는 E2-1 동반이 아니어도 되므로(U 화면 소관) 별도 판단 대상이다.

> 개시 전 결손에 대해서는 프로비저닝의 개시를 하지 못하도록 차단한다.
> 프로비저닝 진행 도중에 발생한 결손일 경우 대기하다가 TTL 만료 시 중단된다. 가령, 펌웨어 업데이트 → BIOS 설정 → OS 설치 의 세팅 정의서를 할당받은 게스트 서버가 펌웨어 업데이트를 하는 도중 설치될 OS 의 ISO 파일에 드리프트가 발생한 경우 BIOS 설정까지는 진행하고 대기한다. TTL 이전에 드리프트가 해결되어 자원의 결손이 해소되는 경우 OS 설치를 진행하며, 그렇지 못한 경우 도중에 중단(PARTIAL_SUCCESS)처리한다.

## 8. 1차 첨언 반영 (2026-08-13) — 확정과 파생

### 확정 D1. 결손 대응 사다리 — 지점마다 다른 처리 (Q1 + Q4 종합)

두 첨언을 합치면 결손을 만나는 **지점**에 따라 처리가 갈리는 사다리가 확정된다. 개시는 사람 결정 지점이라 차단하고, phase 진입은 기계 지점이라 대기가 어울린다는 분업이다.

| 지점 | 처리 | 근거 첨언 |
|---|---|---|
| 개시 전 | **개시 차단** | Q4 |
| phase 진입 (개시 후) | **대기 + TTL** — 해소 시 자동 재개 | Q1 · Q4 |
| TTL 만료 | **실패 전환** — `failed_at` + 막힌 step 을 가리키는 커서, `clearFailed` 재시도로 회복 가능 (4차 첨언 개정) | Q1 · Q4 · 4차 |
| phase 착수 후 (실행 중) | **실패** (기존 markFailed 경로) | Q1 |

Q4 첨언의 예시가 이 사다리의 판정 지점이 phase 별임을 확정한다 — 펌웨어 업데이트 중 OS ISO 에 드리프트가 나도 BIOS 설정까지는 진행하고, **OS 설치 진입에서** 대기한다. 즉 준비도 판정은 실행 전체가 아니라 §6-③ 대로 각 phase 의 부팅 재진입 시점이다.

파생 두 가지 —

- **개시 차단은 UI 1차 차단 + 서버 가드의 SSOT 공유로 구현한다**(불가침). 현재 개시 가능 판정 SSOT 인 `ProvisioningProgress.isStartableWith`(뷰 버튼 플래그 + 409 가드 공유) 자리에 재료 결손 판정이 합류하는 그림이다. U3-5-a 가 "그 가드는 E 계열 소관" 으로 이연한 것이 "막는다" 로 확정된 셈.
- **2026-07-06 결정("blocking=true = 실행 실패")은 이 사다리로 대체된다** — 결손은 결국 실패로 수렴하되, 진입 결손에는 대기 + TTL 이 유예를 준다. **(4차 첨언 개정)** TTL 만료의 종결은 당초 "중단(PARTIAL_SUCCESS)" 이었으나 **실패 전환**으로 확정했다 — `completed_at` = 완주 전용이라는 타임라인 의미와 충돌하지 않고, 기존 `clearFailed` 재시도 경로로 자원 복구 후 회복이 가능하며(중단-종결은 회복 경로가 없었다), 부분 성공 개념은 DEGRADED 축 skip 완주에만 남는다. 부수 이득: 중단이 `completed_at` 를 쓰지 않으므로 `osInstalled` 커서 프록시가 깨질 시나리오 자체가 소멸한다(완주 종단에서 "커서 통과 = 실제 수행" 이 복원).

### 확정 D2. 준비도 계약은 E2-1 동반 신설 (Q3)

ⓑ 채택. E2-1 의 scope 에 "준비도 계약 신설 + FIRMWARE_UPDATING 첫 구현" 을 명시한다.

### 확정 D3. progress · 원장 테이블 정비 방향 (2026-08-13 2차 첨언)

스키마 브리핑 검토 과정에서 `provisioning_progress` 설계 자체에 대한 토론이 파생됐고, 다음이 확정됐다. **두 테이블의 분리와 구조는 유지한다** — phase × status 2축 전면 재설계는 채택하지 않으며, 추가 컬럼 필요 여부는 Q2 첨언으로 정한다.

- **`phase_meta` 는 제거한다.** 실측 결과 작성자 0 · 소비자 0(응답 DTO 의 미표시 pass-through 1갈래뿐)이고, 이 컬럼이 가질 뻔했던 유일한 용도(개시 · 실패 · 종단 신호의 JSON 은닉)는 E1-0a 에서 이미 기각됐다. 응답 필드까지 함께 정리한다.
- **`setup_step` 은 개명한다.** 이름이 무엇의 step 인지 · 이력인지 계획인지를 말하지 않는다. `provisioning_history` 류가 후보이며 확정 명칭은 이행 시점에 정한다(M0 리네임 계열 선례).
- **`current_phase` 의 기록 단위를 `ProvisioningPhase`(7값) → `ProvisioningPhaseStep`(13값)으로 바꾼다.** 커서와 원장이 같은 어휘로 말하게 되고(원장의 §D7 관용구와 동형 — phase 는 `getPhaseType()` 파생이라 정보 손실 없음), 현재 위치가 조인 없이 step 단위로 읽힌다.

**이행 plan 이 다뤄야 할 파생 유의점 4건** — ① step 커서만으로는 진입-완료 모호(D1 에서 확인한 `osInstalled` 프록시 교훈)가 해소되지 않는다 — Q2 의 상태 표현 결정과 합쳐져야 완결된다. ② `failed_step_code` 가 step 커서와 부분 중복이 된다(실패 시 커서가 이미 그 step 을 가리킴) — 존폐와 수동 실패 전환의 null 표식 의미론을 재검한다. ③ 역행 금지 가드가 step ordinal 비교가 되면 enum 선언 순서 = 실행 순서라는 결합이 생기고, 보류 상수 `IPMI_SETTING` 의 건너뜀을 처리해야 한다. ④ 컬럼명 `current_phase` 도 개명 대상이 된다. 이행 슬라이스(E2-1 동반 / 별도 정비)는 Q2 확정 후 판단한다.

**4차 첨언 보강 (2026-08-13)** — 명칭 · 존폐 확정: `setup_step` → **`provisioning_history`**. **`failed_step_code` 는 제거**(유의점 ② 해소) — `failed_at` 이 채워진 시점의 step 커서가 실패 지점을 답한다. 성립 조건 = 커서 전진 시점이 step 시작 보고 시일 것(D4 의 STEP_RUNNING 진입과 같은 사건). 종전 null 값이 담당하던 운영자 수동 실패 전환 표식은 소멸하므로, 그 구분 요구의 새 거처(원장 기록 후보 — 운영자 액션도 사실)는 이행 plan 에서 정한다. `setting_assignment` · `assigned_process` 는 할당 스냅샷 의미를 이름에 싣는 개명 확정(제안 `setting_assignment_snapshots` · `assigned_process_snapshots` — 기존 테이블 전부가 단수 명명이라 단수형과의 정합만 이행 시 확정). 1:N 관계 명시는 실측과 일치한다(활성 1 + superseded 이력).

### 확정 D4. progress 에 내부 상태 컬럼 신설 — 3 timestamp 와 맞물리지 않는 의미 설계 (2026-08-13 3차 첨언)

hold · 재부팅 대기 같은 "특정 시점의 유효한 상태" 의 거처를 검토했다. `setup_step.status` 의 PENDING 활용(실측: PENDING 은 작성자 0 인 U1 예약 어휘)과 `status_meta` JSON 세분화(E1-0a 가 기각한 JSON 은닉의 재현)를 기각하고, **progress 에 상태 컬럼을 신설하는 안을 채택**했다 — 소비자(dispatch 매 폴링 · 화면 · TTL 처리자)가 전부 "현재 상태" 소비자라 조인 없는 한 행이 거처로 맞다.

기존 3 timestamp 와의 이중 권위를 막는 의미 설계는 3중 방벽이다:

- **어휘 계층** — 값은 "진행" 국면 내부의 운동 양태만: `AWAITING_BOOT`(정상 재부팅 · 폴링 대기) / `STEP_RUNNING`(step 실행 중) / `HOLD`(자원 결손 대기, TTL 가동). 거시 국면(개시 전 · 실패 · 종단)을 뜻하는 값은 어휘에 없다 — stale 값이 남아도 timestamp 와 모순을 표현할 수 없다.
- **값 계층** — 불변식 `status ≠ NULL ⇔ 실행 창 안(started_at ≠ NULL ∧ failed_at = NULL ∧ completed_at = NULL)`. `start()` 가 넣고 `markFailed` · `markCompleted` · TTL 중단이 비우고 `clearFailed` 가 되넣는다. 수동 DDL 의 CHECK 로 이중 방어(validate 는 CHECK 미검사). **금지 전이: STEP_RUNNING → HOLD** — D1 의 "착수 후 결손 = 실패" 가 전이 제약으로 구조화되고, dispatch 의 hold 진입 적격 판정이 원장 조회 없이 끝난다.
- **소비 계층** — 거시 질문은 timestamp(`GuestServerStatus.derive` 유지), 미시 질문은 status 만 답한다. TTL 기점 = HOLD 진입 전이가 찍는 `last_transition_at`(HOLD 중 다른 전이 불가라 안정). DEC-2 무접촉 — 커서는 게스트 사실 전용 유지, status 는 커서가 아니다.

탈락 대안: 전 국면 포괄 어휘(이중 권위 그 자체) · HOLD 단독 최소 어휘(hold 적격 판정이 매 폴링 원장 조회가 되고 금지 전이의 자리가 소멸). STEP_RUNNING · AWAITING_BOOT 는 원장 사실의 같은 트랜잭션 투영(비정규화)임을 명시한다 — 사실의 원본은 원장. 값 · 컬럼 · enum 명칭은 가칭이며 이행 plan 에서 확정한다.

### 확정 D5. Q2 종결 — skip 은 원장 사실, 판정은 파생, 사유는 사건 시점 기록 (2026-08-13)

## 9. 결정 요약 (종결)

열린 질문 4개가 모두 답을 받아 토론을 종결한다. 확정 5건 —

- **D1. 결손 대응 사다리** — 개시 전 결손 = 개시 차단(UI 1차 차단 + `isStartableWith` SSOT 합류) / phase 진입 결손 = 대기 + TTL(해소 시 자동 재개) / TTL 만료 = **실패 전환**(`clearFailed` 재시도로 회복 가능 — 4차 개정, 당초 중단안 대체. `osInstalled` 프록시 결함 시나리오 소멸) / 착수 후 결손 = 실패. 2026-07-06 의 "blocking=true = 실행 실패" 를 대체.
- **D2. 준비도 계약은 E2-1 동반 신설** — `ProvisioningPhaseExecutor` 에 준비도 훅(READY / DEGRADED / BLOCKED), 판정 지점은 부팅 재진입(§6).
- **D3. progress · 원장 정비** — `phase_meta` 제거(작성자 · 소비자 0) / `setup_step` → **`provisioning_history`** 확정 / 커서 기록 단위 `ProvisioningPhase` → `ProvisioningPhaseStep` / **`failed_step_code` 제거**(step 커서가 실패 지점을 답함 — 수동 전환 표식의 새 거처는 plan) / 할당 2테이블은 스냅샷 명칭으로 개명(단 · 복수형은 이행 시 확정). 구조는 유지, 유의점은 §8 D3.
- **D4. progress 내부 상태 컬럼 신설** — 어휘 3값(AWAITING_BOOT / STEP_RUNNING / HOLD, 가칭) · 실행 창 밖 NULL 강제 · 금지 전이(STEP_RUNNING → HOLD)로 3 timestamp 와 이중 권위 불가 구조. TTL 기점 = HOLD 진입의 `last_transition_at`.
- **D5. skip 기록** — 원장 SKIPPED 행(사실) + statusMeta(사유), 부분 성공 판정은 파생, 별도 축 불요.

**후속** —
① D2 · D5 세부(준비도 술어 형태 · SKIPPED 행 작성 주체)와 D1 의 TTL 값 거처는 E2-1 plan 에서 확정(§8 이연 목록).
② **D3 · D4 의 스키마 정비는 독립 슬라이스 ES-2(가칭 "실행 데이터 모델 정비")로 확정**(2026-08-15 채택) — MK4-5 완료 후 ue 스트림에서 `refactor/ES-2_…` 브랜치로, E2-1 직전에 수행한다.
- 근거: 검증 줄기 분리(회귀 이야기 vs 신기능 이야기) · E2-1 이 새 모델 위에서 시작(자기 발밑 재배선 회피) · ES 계열 정의 부합. HOLD 는 ES-2 에서 값만 선언하고 작성자는 E2-1 이 데려온다. **명세서 작업에서 발견한 실 DB 불일치 5건(`system_uuid` 유니크 부재 · assignment FK 이름 · CASCADE 부재 등)도 ES-2 의 DDL 마이그레이션 창에 합류**한다 — reconciliation 과 무관한 execution 스키마 결함이라 R 감사 입력이 아니다. 앵커의 R 전수 감사와 도메인이 갈려 병행 가능. Notion 단계 페이지는 착수 시점에 신설한다.
③ Q4 의 개시 차단 화면 반영(버튼 disabled + tooltip)은 U 화면 소관으로 별도. 본 토론은 CP1 plan html 을 대체하지 않으며, 해당 슬라이스 진입 시 plan 이 이 결정들을 입력으로 받는다.
