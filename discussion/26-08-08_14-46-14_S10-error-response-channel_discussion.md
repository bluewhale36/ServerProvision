## 1. 이 문서가 남기는 것

착수 브리핑은 원인을 지목했고, **그 지목이 틀렸다**. 조사가 다른 원인을 찾아냈고 설계가 그에 맞춰 바뀌었다. 결정만 적으면 "왜 폴백을 안 넣었나" 를 다음 사람이 다시 물을 것이므로, **탈락한 가설과 그 탈락 사유**를 함께 남긴다.

## 2. 브리핑의 가설과 그 반증

브리핑 §2 는 이렇게 판정했다.

> `ApiExceptionHandler` 와 `WebExceptionHandler` 어디에도 최종 폴백(`@ExceptionHandler(Exception.class)`)이 없다. (…) 두 advice 가 열거한 타입에 걸리지 않는 예외는 advice 를 그냥 통과해 Spring 기본 오류 처리로 떨어지고, 그것이 raw JSON 으로 보인다.

**반증.** 사고를 일으킨 `RestoreNameConflictException` 은 `ConflictException` 하위이고 `ConflictException` 은 `@ResponseStatus(CONFLICT)` 를 달고 있다. `handleDomain(DomainException)` 이 계층 탐색으로 이를 흡수해 **정상적으로 409 를 만들었다.** 예외는 advice 를 통과한 적이 없다. 폴백이 있었어도 이 사고는 그대로 났다.

브리핑이 세운 다른 관찰(예외 121 개 중 명시 등록 17 개가 결함이 아니라 다형 흡수 설계라는 것, 계층 밖 예외가 2 개뿐이라 규율이 지켜져 왔다는 것)은 조사에서도 그대로 확인됐다. 틀린 것은 **누출 경로의 지목**뿐이다.

## 3. 실측으로 찾은 진짜 원인

`@WebMvcTest` 로 `BoardModelLifecycleController` 와 `BoardModelMetadataController` 를 측정했다. `Accept` 헤더에서 `*/*` 조각 하나만 넣고 빼며 비교했다.

| 요청 `Accept` | `*/*` 포함 | 선택된 advice | 응답 |
|---|---|---|---|
| `text/html` | 없음 | Web | `text/html`, view=`error` |
| `text/html,application/xhtml+xml;q=0.9` | 없음 | Web | `text/html` |
| `text/html,*/*;q=0.8` | **있음** | Api | `application/json` |
| 실제 크롬 내비게이션 헤더 | **있음** | Api | `application/json` |
| 헤더 없음 | **있음** | Api | `application/json` |

`text/html` 이 q=1.0 으로 맨 앞에 있는데도 `*/*` 를 붙이는 순간 뒤집힌다. 다른 조건은 전부 같다.

**기전.** advice 선택은 `Accept` 의 선호도(q값)를 보지 않는다. 등록 순서대로 훑으며 "요청이 받아줄 수 있는 형식이면 채택" 하고 처음 맞는 것에서 멈춘다. 두 advice 가 모두 `@Order(HIGHEST_PRECEDENCE)` 로 동순위라 등록 순서로 결정되고 `ApiExceptionHandler` 가 앞이다. `*/*` 는 모든 형식과 호환되므로 JSON advice 가 무조건 먼저 합격한다. **실제 브라우저는 `*/*;q=0.8` 을 항상 붙인다.**

### 왜 오래 드러나지 않았나

두 가지가 겹쳐 가리고 있었다.

**프런트엔드가 우회하고 있었다.** 관리 도메인 폼은 `data-async-submit` 마커를 달고 `fetch` 로 보냈다. `fetch` 는 페이지를 이동시키지 않으므로 JSON 을 받아도 화면이 안 바뀌고 `ErrorModal` 이 그 `message` 를 모달로 띄운다. **JSON 이 오는 것이 오히려 편한 경로**였고 결함이 결함으로 보이지 않았다. 템플릿의 POST 폼 68 개 중 마커가 붙은 것은 13 개였다.

**테스트가 브라우저를 흉내내지 않았다.** `AdviceExceptionMappingTest` 는 `Accept: text/html` 이라는 순수값으로 검증했다. 그 값에는 `*/*` 가 없으니 HTML 이 나오고 테스트는 통과한다. 브라우저는 그런 값을 보내지 않는다. SSR lifecycle 의 `@WebMvcTest` 들도 상태코드만 볼 뿐 응답 형식을 단언하지 않았다.

U3-2-b 는 마커 없이 SSR lifecycle 폼을 추가한 첫 슬라이스였다. 가려주던 것이 없어지자 잠복 결함이 그대로 드러났다.

### CP1 검토 중 정정한 서술

사용자가 "존재하지 않는 경로로 창을 띄웠더니 오류 페이지가 정상 렌더된다" 고 관찰했고, 이것이 내 서술을 정정하게 했다. **실패 경로가 둘이다.**

| | 경로 A — advice 가 잡는 예외 | 경로 B — advice 가 못 잡는 예외 |
|---|---|---|
| 예 | `/management/os/999/edit` → `OSMetadataNotFoundException` | `/management/os/3` (매핑 없음) → `NoResourceFoundException` |
| 처리 주체 | 두 advice 의 content negotiation | 기본 `/error` → `BasicErrorController` |
| 결과 | JSON — 결함 | HTML — 정상 |

`BasicErrorController` 는 평범한 컨트롤러라 **정상 요청 매핑**을 타고, 정상 매핑은 선호도를 제대로 지킨다. **같은 프레임워크 안에서 두 메커니즘이 다르게 동작하는 것**이 이 결함의 뿌리다. 따라서 `error.html` 템플릿은 죽어 있지 않았고, 죽어 있던 것은 `WebExceptionHandler` advice 다. S10 은 경로 A 를 경로 B 와 같은 결과로 맞추는 일이 됐다.

## 4. 서버 판별 방식 — 대안 넷과 탈락 사유

| 안 | 내용 | 판정 | 사유 |
|---|---|---|---|
| **A** | 필터가 문서 이동 요청의 `Accept` 를 `text/html` 로 좁혀 보고. advice 무변경 | **채택** | 조건 분기가 한 줄도 안 는다. 기존 협상 구조를 그대로 두고 입력만 바로잡는다. `@Order` 를 건드리지 않아 v1 · v2 사고 재현 여지가 없다 |
| B | `Accept` 품질값을 존중하도록 advice 순서 · 구조 변경 | 탈락 | v2 가 시도해 `Accept: */*` 테스트 28 건 회귀. Spring 의 선택 알고리즘 자체를 제어해야 해 통제가 어렵다 |
| C | `X-Requested-With` 로 역판별(없으면 HTML) | 탈락 | 우리 `fetch` 코드가 보내는 헤더에 의존한다. PXE 게스트처럼 그 헤더가 없는 정당한 JSON 클라이언트가 전부 HTML 을 받게 되어, 경로별 예외 분기를 다시 만들어야 한다 |
| D | 두 advice 를 하나로 합치고 핸들러 안에서 분기 | 탈락 | "조건분기 legacy 확장 금지" 불가침 정면 위배. 도메인이 늘 때마다 분기가 자란다 |

**A 에 대한 자기 비판과 답.** 정규화가 정상 응답의 협상까지 바꾸므로, 문서 이동으로 도달하면서 HTML 이 아닌 응답을 내는 엔드포인트가 있으면 406 이 난다. 전수 조사로 그런 경로가 없음을 확인했다 — 다운로드 엔드포인트 0 건(`Content-Disposition` · `OCTET_STREAM` · `Resource` 반환 없음), 비 HTML 생산자는 SSE 스트림(`EventSource` 는 `Sec-Fetch-Dest: empty`)과 PXE `/boot`(비브라우저)뿐이다. **이 전제 자체를 테스트로 고정**해, 나중에 다운로드를 추가하면 테스트가 먼저 깨지게 했다.

## 5. 프런트 기본값 반전 — 이것이 이 슬라이스의 본질

사고의 직접 원인은 "`data-async-submit` 을 붙이는 걸 잊었다" 였다. **잊을 수 있는 관례는 다시 잊힌다** — 규약은 이미 CLAUDE.md 에 있었고 지켜지지 않았다는 것이 이 작업의 출발점이었다. 그래서 마커를 잘 기억하게 만드는 대신 **마커를 없앴다.**

| | 표기를 잊으면 |
|---|---|
| 이전 | raw JSON 노출 — 조용하고 사용자에게 도달 |
| 이후 | 모달로 안내 / 검증 표시 깨짐 — 시끄럽고 CP4 테스트가 먼저 잡음 |

**대상 분류 기준을 구현 중 두 번 바로잡았다.** 이 과정을 남긴다 — 기준 자체가 테스트의 근거이기 때문이다.

1. 첫 스캔은 `@ResponseBody` 가 낀 핸들러를 정규식이 놓쳐 XHR 부류 70 건을 통째로 누락했다.
2. 두 번째 스캔은 "문자열 뷰 반환" 을 재렌더 신호로 봤는데, 헬퍼 메서드로 재렌더하는 `IsoUploadController#addIso` 를 놓쳤다.
3. 최종 기준은 **`BindingResult` 수령 여부**다. 재렌더가 그 파라미터의 유일한 목적이므로 신호가 정확하다.

결과적으로 부류가 둘이 아니라 셋이었다.

| 부류 | 수 | 처리 |
|---|---|---|
| 액션 폼(redirect 전용) | 55 | 전역 인터셉터가 기본 가로채기 |
| 입력 폼(`BindingResult` 재렌더) | 11 | `data-native-submit` 으로 사유와 함께 opt-out |
| XHR(`@ResponseBody`) | 70 | `e.defaultPrevented` 로 자동 회피 |

**가로채기 배치**는 전역 레이아웃으로 정했다. `confirm-modal-base.js` 확장안은 탈락했는데, 그 파일이 일부 페이지에만 적재되므로 적재되지 않은 화면이 그대로 구멍으로 남기 때문이다 — **이번 사고의 구조를 그대로 재생산한다.**

## 6. 채택하지 않은 것

- **최종 폴백 도입.** §2 의 이유로 이번 사고와 무관하다. 두 advice 를 모두 빠져나가는 예외의 사용자 노출은 별도 사안으로 남긴다. `RequestCorrelationFilter` 가 이미 최후 기록 안전망이고, HF5 의 `ProvisionErrorAttributes` 가 기본 `/error` 경로의 문구를 맞춘다.
- **예외 121 개 전수 명시 등록.** 다형 흡수가 설계 의도이며 "조건분기 대신 다형성" 불가침에 어긋난다.
- **예외 계층 이탈 검출 테스트.** 브리핑이 후보로 들었으나 현재 위반이 0 이라 넣어도 곧바로 green 이고 이번 사고와 무관하다. "테스트가 있으니 안전하다" 는 잘못된 안심만 준다. 실제로 이탈이 발생한 뒤 도입해도 늦지 않다.
- **입력 폼까지 fetch 전환.** 검증 오류 표시 · 포커스 · 스크롤 복원을 직접 재구현해야 해 얻는 것보다 깨질 것이 많다.
- **harness hook.** 아키텍처 테스트로 얻는 것이 더 확실하고 hook 은 설정 영역이라 별도 판단이 필요하다.

## 8. 미해소로 남긴 것

- **A5 재조정 검증** — 샌드박스 스키마를 `ddl-auto=update` 로 부트스트랩한 부작용으로 스캔이 실패해 확인하지 못했다. CP7 로 넘긴다.
- **B7 중복 클릭 검증** — 수행하지 못했고 대체 근거도 없다. CP7 확인 항목.
- **`Sec-Fetch-*` 를 지우는 프록시 환경** — 보조 판별을 두지 않기로 했다. 그 경우 현재 동작(JSON)으로 떨어져 회귀가 아니며, 보조 판별은 분기를 늘리고 오탐 위험이 있다. 실제 환경에서 관측되면 그때 추가한다.
- **체크리스트의 나머지 도메인 항목** — 자원 도메인 · 드리프트 종류 · 특권 명령 · phase 는 예외 항목만 확정하고 후속으로 넘겼다.
