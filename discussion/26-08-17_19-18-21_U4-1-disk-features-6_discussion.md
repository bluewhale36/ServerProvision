## 1. 이번에 확정된 것

| | 결정 | 출처 |
|---|---|---|
| **E26** | 우선순위는 **정의서가 값으로 갖는다**(5회차 R-11 ②). 다만 **정의서를 만들 때 기본값이 채워지고** 사용자가 언제든 고칠 수 있다 — `기본 파티션 자동 생성` 버튼과 같은 방식 | R-11 |
| **E27** | 우선순위의 대상은 **볼륨**이다. RAID 볼륨뿐 아니라 **RAID 로 묶이지 않은 단독 디스크도 함께** 줄 세운다(NVMe SSD 는 보통 1장만 장착된다) | R-12 |

**E26 은 내 ③보다 낫다.** 나는 "시스템 기본 + 정의서 재정의(비우면 기본 적용)" 를 제안하며 *"비움의 뜻이 축마다 달라진다"* 를 걱정했다 — E5 는 비움이 **부재**인데 여기서는 비움이 **기본 적용**이 되기 때문이다. E26 은 그 걱정을 **없앤다.** 정의서에는 언제나 값이 들어 있고, 기본값은 *저장된 값* 이지 *비어 있을 때의 해석* 이 아니다. 비움의 뜻이 하나로 유지된다.

그리고 이미 있는 것을 그대로 쓴다 —

```
setting-new.html:325   [기본 파티션 자동 생성]  버튼
GET /provisioning/setting/default-partitions?osName=…
PartitionPresetResponse  →  폼에 채움  →  사용자가 고침  →  정의서에 저장
```

새 개념이 아니라 **같은 형태를 하나 더 두는 것**이다.

## 2. 5회차 §4 가 무엇을 말하려 했는가 (요청받은 해명)

**§4 에 답변 칸을 둔 것이 잘못이었다.** 그 절은 판단을 구하는 자리가 아니라 사실 두 개를 적은 자리였는데, 답변 칸이 있으니 무언가 결정을 요구하는 것처럼 보였다. 무엇을 말하려 했는지 풀어 쓴다.

### 2-1. 적은 사실 — "수집 전에도 할당된다"

R-7 답변에 *"하드웨어 수집이 완료된 다음에야 할당할 수 있도록 이전에 수정한 것으로 기억한다"* 가 있었고, 코드를 열어 보니 **그렇지 않았다**. 할당을 막는 것은 회수(`DECOMMISSIONED`)와 보드 불일치(`BOARD_MISMATCH`) 둘뿐이고, 수집 전 서버는 보드를 대조할 수 없으므로 **막지 않고 표식만 남긴다**(`boardUnverified()`).

그 사실 자체는 결정 대상이 아니다. 다만 **U4-1-1 에 숙제를 하나 남긴다.**

### 2-2. 그래서 남는 숙제 — 수집 전 서버에 디스크 조건을 어떻게 다룰까

U4-1-1 이 정의서에 디스크 요구를 붙이면(E6 — RAID 를 구성하면 RAID 카드가 필요하다), **하드웨어를 아직 수집하지 않은 서버**에는 그 요구를 판정할 수 없다. 디스크 목록도 RAID 카드 유무도 모르기 때문이다.

그때 화면이 무엇을 할지 세 갈래다.

|     | 안                                        | 뜻                                  |
| --- | ---------------------------------------- | ---------------------------------- |
| ①   | **보드와 같게** — 막지 않고 "대조하지 못했다" 는 표식만 남긴다  | U3-5-a 가 이미 그렇게 정했고, 축이 하나 느는 것뿐이다 |
| ②   | **막는다** — 디스크 요구가 있는 정의서는 수집 전 서버에 못 붙인다 | 디스크는 보드보다 실패 비용이 크다는 판단이면          |
| ③   | 아무 표식도 없이 통과                             | U3-5-a 가 이미 배제한 형태(조용한 통과)         |

**내 판단은 ①이다.** 새 규칙을 만들지 않고 이미 정한 규칙에 축을 더하는 쪽이며, 수집 전 서버에 정의서를 미리 붙여 두는 것이 정상 운용이기 때문이다(그래서 U3-5-a 가 막지 않기로 했다).

> **§2-2 답변:**
> 1로 진행. 다만, RAID card 의 경우 정의서에 정의한 내용에 불일치할 경우 RAID 구성 자동화가 불가하므로(사용할 명령어가 다른 것으로 알고 있다), 수집 단계에서 RAID card 의 정확한 수집이 필요하고, 이를 정의서에서 선택할 수 있어야 한다.
> 현재 사내에서 사용되는 가장 주력의 RAID card 는 GIGABYTE CRA3338 (no cache), AVAGO raid 9361-8i (cache 2GB) 의 두 개 모델이다.
> 두 카드의 RAID 구성 자동화를 위한 명령어 조사는 E 단계에서 진행하고, 지금 단계에서는 세팅 정의서에서 이 두 RAID card 를 지정하거나, 자동 탐지해서 정의서에 남기는 기능을 구현해야 한다.

### 2-3. 적은 사실 둘 — 붙일 자리가 이미 있다

`AssignmentEligibility`(U3-5-a 가 만든 판정 입력 묶음)의 javadoc 에 이렇게 적혀 있다.

> `GuestServerDetail` 을 통째로 드는 것이 요점이다. … 서버가 가진 하드웨어는 전부 이 엔티티 하나에 모여 있다. 보드 식별자만 풀어 담았다면 **U4 의 디스크 구성 대조가 들어올 때** 이 record 의 서버 쪽을 다시 열어야 한다.

이 말이 뜻하는 것은 실무적으로 이렇다 — **U4-1-1 은 판정 구조를 새로 만들지 않아도 된다.**

- **서버 쪽 입력** : 손댈 것이 없다. `GuestServerDetail` 안에 `hardware_spec` JSON 이 있고 디스크가 거기 들어 있다
- **요구사항 쪽** : `requiredBoard` 옆에 디스크 요구 축을 **하나 더한다**
- **판정 자체** : `AssignmentBlockKind` 에 상수를 하나 더한다(`BOARD_MISMATCH` 옆에 디스크 축)

즉 §2-3 은 **결정이 아니라 CP1 의 출발점**이다. 설계를 처음부터 그리지 않고 기존 골격에 축을 더하는 것으로 시작한다는 뜻이며, 그래서 U4-1-1 의 무게가 내가 4회차에 적은 "중~대" 보다 가벼울 수 있다.

## 3. 용어 정리 — '볼륨'

E27 이 대상을 넓혔으므로 말을 정해 둔다. 앞으로 **볼륨**은 아래 둘을 아우른다.

|         | 무엇                   | 예                                         |
| ------- | -------------------- | ----------------------------------------- |
| RAID 볼륨 | 묶음 규칙이 만든 RAID 배열    | SSD 480GB ×2 → RAID1                      |
| 단독 디스크  | RAID 로 묶이지 않은 디스크 하나 | NVMe SSD 1장(E5 — 레벨을 비우면 RAID 를 구성하지 않는다) |

**역할(OS / Data)은 볼륨에 매겨진다.** 우선순위도 볼륨을 줄 세운다. `/data1` · `/data2` 의 순번도 그 줄에서 나온다.

이 정리가 E7("OS 영역은 반드시 1개")과 맞물린다 — 볼륨 중 정확히 하나가 OS 영역이고 나머지가 Data 영역이다. NVMe 1장짜리 OS 영역(E17)도 이 정의 안에 자연히 들어온다.

> 승인.

## 4. 토론 결과 — 결정 전체

여섯 회차의 결정을 한자리에 모은다. 이것이 각 슬라이스 CP1 의 입력이다.

### 도메인 (D)

D1 같은 스펙 디스크를 둘 이상 넣는다 · D2 OS 영역은 보통 SSD RAID1 · D3 Data 영역은 RAID 구성 개수만큼, 없을 수도 있다 · D4 RAID 집행은 E 영역이되 구성 정의는 정의서 · D5 관례(2개 RAID1 / 3개+ RAID5) · D6 장착 순서 SSD→HDD, 작은→큰 · D7 RAID 카드는 대체로 장착, 3개+ 는 캐시 있는 모델 · D8 작업 순서가 단계 번호 · D9 LVM 범위 외

### 표현 (E1~E5 · E19 · E22)

- 묶음 목록으로 적는다. 묶음 하나 = `{RAID 레벨, type, transport, capacity, count}`
- 관례를 박아 두지 않는다. **레벨과 개수는 운영자가 적는다**
- 레벨 · 개수 외 축은 **자동 탐지** 가능. 개수는 숫자 또는 **'n 개 이상'**
- 묶음은 **볼륨 하나가 아니라 규칙** — 매칭되는 조합을 **전부** 구성한다
- **레벨을 비우면 RAID 를 구성하지 않는다**(단독 디스크)

### 역할 (E7 · E15~E17 · E23 · E24 · E26 · E27)

- **볼륨** 중 정확히 하나가 OS 영역, 나머지는 전부 Data 영역
- 역할은 **명시 지정** + **우선순위 조건식**으로 결정
- 기본 우선순위 — **NVMe SSD → SATA SSD → HDD**, **작은 용량 → 큰 용량**
- 우선순위는 **정의서가 값으로 갖되 만들 때 기본값이 채워진다**
- 디스크 스펙에 **기본값을 두지 않는다**(변동 폭이 가장 크다)

### 배치 (E8 · E9 · E14 · E21)

- **Data 영역 파티셔닝은 OS 설치기에서 하지 않는다** — Linux 도 Windows 도 설치 이후
- `OS_SETTING` 확장으로 담는다
- Data 영역 파티션 명칭은 **파티셔닝 과정에서 명시**한다

### 범위 (E6 · E10~E13 · E20)

- RAID 를 구성하면 **RAID 카드를 요구**한다
- **캐시 있는 카드 판정은 이번에 하지 않는다** — 집행이 붙을 때 함께
- 유효성 규칙은 각 단계 진입 시 별도 기술
- **집행(RAID 를 실제로 거는 것)은 E 영역** — 실 장비 확보가 전제

### 단계 (E21)

| 단계 | 무엇을 더하나 | 사는 곳 |
|---|---|---|
| **U4-1-1** RAID 구성 지정 | 묶음 규칙 목록 + RAID 카드 요구 | `OS_INSTALLATION` 폼 |
| **U4-1-2** 디스크 분류 | 볼륨 역할 + 우선순위 + OS 유일성 | 위 절에 이어 |
| **U4-1-3** OS 영역 파티션 지정 | 파티션 대상을 장치명 → 역할로 | 파티션 표 |
| **U4-1-4** Data 영역 파티셔닝 *(신설)* | Data 볼륨별 파티션 정의 | `OS_SETTING` 절 신설 |
