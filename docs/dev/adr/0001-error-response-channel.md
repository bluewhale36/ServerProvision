## 배경

같은 도메인 예외라도 사용자가 무엇을 하던 중이었는지에 따라 보여야 하는 화면이 다르다. 화면 안에서 버튼을 눌렀다면 그 화면을 유지한 채 안내 모달을 띄우는 것이 맞고, 주소로 페이지에 진입하다 실패했다면 머무를 화면이 없으므로 전체 오류 페이지가 맞다. 서버는 이 둘을 구분해 JSON 과 HTML 중 하나를 골라야 한다.

종전에는 이 구분을 두 예외 어드바이스의 `produces` 와 요청의 `Accept` 헤더가 담당한다고 보았다. 그러나 그 방식은 실제 브라우저에서 동작하지 않았다.

어드바이스 선택은 `Accept` 의 선호도 값을 보지 않는다. 등록 순서대로 훑으면서 요청이 받아들일 수 있는 형식이면 채택하고 거기서 멈춘다. 두 어드바이스가 같은 최우선 순위라 등록 순서로 결정되며 JSON 어드바이스가 앞이다. 브라우저는 `Accept` 에 모든 형식을 허용하는 항목을 항상 덧붙이므로, 그 항목이 JSON 어드바이스와 무조건 먼저 맞아떨어졌다. 결과적으로 HTML 어드바이스는 실제 브라우저에서 선택될 수 없었고, 페이지 이동 중 발생한 도메인 예외의 JSON 응답 본문이 사용자 화면에 그대로 노출되었다.

측정으로 확인한 내용은 다음과 같다. `Accept` 에서 모든 형식 허용 항목 하나만 넣고 빼면 다른 조건이 같아도 결과가 뒤집힌다.

| 요청 `Accept` | 선택된 어드바이스 | 응답 |
|---|---|---|
| `text/html` | HTML | `text/html` |
| `text/html,application/xhtml+xml;q=0.9` | HTML | `text/html` |
| `text/html` 에 모든 형식 허용 항목을 덧붙인 값 | JSON | `application/json` |
| 실제 브라우저가 보내는 값 | JSON | `application/json` |

이 결함이 오래 드러나지 않은 이유가 두 가지다. 첫째, 관리 도메인의 폼은 마커를 달아 `fetch` 로 제출했고 그 경로에서는 JSON 이 오히려 필요한 응답이라 문제가 보이지 않았다. 둘째, 테스트가 `Accept: text/html` 이라는 순수한 값으로만 검증했는데 브라우저는 그런 값을 보내지 않는다.

## 결정

문서 이동으로 들어온 요청의 `Accept` 를 `text/html` 로 좁혀 보고하는 서블릿 필터를 둔다. 판별 기준은 `Sec-Fetch-Dest` 헤더가 `document` 인지 여부다. 두 어드바이스의 `@Order` 와 `produces` 는 바꾸지 않는다.

브라우저는 주소창 이동, 링크 클릭, 폼의 기본 제출에 `Sec-Fetch-Dest: document` 를 보내고 `fetch` 와 `XMLHttpRequest` 에는 `empty` 를 보낸다. 이 구분을 위해 표준화된 헤더라 `Accept` 같은 모호함이 없다. 비브라우저 클라이언트는 이 헤더를 보내지 않으므로 자동으로 JSON 기본값에 남는다.

구현은 `DocumentNavigationAcceptFilter` 이며 내부 요청 래퍼가 `Accept` 만 덮어 보고한다. 나머지 헤더는 원본 그대로다.

## 근거

이 방식은 협상의 입력만 바로잡고 나머지는 기존 구조가 처리한다. 조건 분기가 한 줄도 늘지 않으며, 판별은 프레임워크가 제공하는 확장점인 필터가 떠맡는다. 분기문을 늘리지 않는다는 설계 원칙에 부합한다.

어드바이스의 순서 값을 건드리지 않는 것도 중요하다. 그 값은 과거 두 차례 사고를 낸 자리다. 한 번은 최우선 상수에서 뺄셈을 해 정수 언더플로로 사실상 최하위가 되었고, 다른 한 번은 덧셈으로 모호한 `Accept` 케이스의 테스트 회귀를 일으켰다.

## 검토한 대안

**`Accept` 선호도를 존중하도록 어드바이스 순서나 구조를 바꾸는 안.** 과거에 실제로 시도해 테스트 28건이 회귀했다. 프레임워크의 선택 알고리즘 자체를 제어해야 하므로 통제가 어렵다.

**`X-Requested-With` 헤더의 유무로 역판별하는 안.** 우리가 작성한 `fetch` 코드가 보내는 헤더에 의존한다. 그 헤더를 보내지 않는 정당한 JSON 클라이언트, 예를 들어 네트워크 부팅으로 접속하는 게스트 서버가 전부 HTML 을 받게 되어 경로별 예외 분기를 다시 만들어야 한다.

**두 어드바이스를 하나로 합치고 핸들러 안에서 분기하는 안.** 분기문을 늘리지 않는다는 원칙에 정면으로 어긋난다. 도메인이 늘 때마다 분기가 함께 자란다.

## 전제와 그 보호

`Accept` 정규화는 정상 응답의 협상에도 영향을 준다. 문서 이동으로 도달하면서 HTML 이 아닌 응답을 내는 엔드포인트가 있으면 그 요청은 406 이 된다.

현재 그런 경로는 없다. 파일 다운로드 엔드포인트가 없고, HTML 이 아닌 응답을 내는 것은 서버 전송 이벤트 스트림과 네트워크 부팅 스크립트뿐이다. 전자는 `EventSource` 가 `Sec-Fetch-Dest: empty` 를 보내고 후자는 브라우저가 아니다.

이 전제는 `FormSubmissionConventionTest` 가 고정한다. 서버 렌더링 컨트롤러에 다운로드 응답이 추가되면 그 테스트가 먼저 실패해, 필터의 적용 범위를 함께 결정하게 만든다.

## 함께 정한 것

응답 형식만 고쳐서는 사고가 재발한다. 폼 제출 방식이 마커를 붙이는 방식이었고 마커를 잊는 것이 곧 노출 사고였기 때문이다. 그래서 기본값을 뒤집었다.

상태를 바꾸는 폼은 전역 스크립트가 기본으로 가로채 `fetch` 로 보낸다. 실패 시 뷰를 다시 렌더하는 입력 폼만 `data-native-submit` 으로 빠져나가며 그때 사유를 함께 적는다. 그 폼을 가로채면 서버가 돌려준 재렌더 결과를 버리게 되어 필드별 오류 표시가 사라지기 때문이다.

빠져나갈 폼을 가리는 기준은 핸들러가 `BindingResult` 를 받는지 여부다. 재렌더가 그 파라미터의 유일한 목적이라 신호가 정확하고, 테스트가 기계적으로 검증할 수 있다.

## 결과

경로에 따라 다음과 같이 갈린다.

| 사용자의 행동 | 전송 방식 | 응답 | 화면 |
|---|---|---|---|
| 화면 안 액션 버튼 | `fetch` | JSON | 안내 모달, 페이지 유지 |
| 입력 폼 저장 | 기본 제출 | HTML | 검증 실패 시 폼 재렌더 |
| 주소로 페이지 진입 | 기본 제출 | HTML | 오류 페이지 |
| 비브라우저 클라이언트 | 직접 호출 | JSON | 클라이언트가 해석 |

어드바이스가 잡지 못하는 예외, 예를 들어 매핑이 없는 주소는 종전대로 기본 오류 흐름을 타며 이미 HTML 로 응답하고 있었다. 이 결정은 어드바이스가 잡는 예외를 그 결과에 맞추는 것이다.

## 남긴 것

두 어드바이스를 모두 빠져나가는 예외를 사용자에게 어떻게 보일지는 이 결정에서 다루지 않았다. 착수 시점에는 그것이 원인으로 지목되었으나 조사 결과 사실이 아니었다. 현재 요청 상관관계 필터가 최후 기록 안전망 역할을 하고, 기본 오류 경로의 문구는 `ProvisionErrorAttributes` 가 맞춘다.

`Sec-Fetch-Dest` 를 제거하는 중계 서버 뒤에서는 정규화가 동작하지 않는다. 그 경우 종전 동작인 JSON 으로 떨어지므로 회귀는 아니다. 보조 판별을 두면 분기가 늘고 오탐 위험이 있어 두지 않았다. 실제 환경에서 문제가 관측되면 그때 다시 판단한다.
