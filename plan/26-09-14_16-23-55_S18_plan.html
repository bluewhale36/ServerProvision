§0. 배경 — 무엇이 들어왔고 v2 에서 무엇이 정해졌는가

dev 의 a63c0ac(PR #81 · 사용자가 직접 작성)로 Spring Security 기반 로그인 · 가입이 global/security/springsecurity/ 한 패키지로 들어왔다(클래스 12 · 템플릿 2). 전부 최소 골격이다 — 템플릿은 레이아웃과 디자인 시스템 밖의 맨 HTML 이고, 가입 요청에는 검증 어노테이션이 하나도 없으며, 비밀번호 불일치는 서비스가 조용히 return 한 뒤 컨트롤러가 로그인으로 redirect 한다(실측은 §1).

지금은 드러나지 않는 두 충돌 — 화면을 규약대로 고치는 순간 표면화한다

하나는 정적 자산이다. 로그인 화면은 비인증 상태에서 렌더되는데, 전역 CSS · 스크립트가 놓인 경로가 permitAll 목록에 없다. 레이아웃의 commonHead 를 쓰는 순간 시트와 스크립트 요청이 인증 리다이렉트로 되돌아온다. 지금 보이지 않는 이유는 하나 — login.html 이 레이아웃을 쓰지 않아 아무것도 요청하지 않기 때문이다.

다른 하나는 제출 경로다. 전역 인터셉터 static/global/form-submit.js 는 POST 폼을 가로채 fetch + FormData(multipart)로 보내는데, 로그인 필터는 서블릿 핸들러 앞에서 request.getParameter 로 값을 읽으므로 multipart 본문을 읽지 못한다. 즉 레이아웃을 쓰는 순간 로그인 폼은 반드시 네이티브 제출이어야 한다(D-3).

FormSubmissionConventionTest 가 세는 것은 개수다 — "BindingResult 를 받는 재렌더 핸들러 수 = data-native-submit 폼 수". 로그인 폼은 핸들러가 아예 없는 네이티브 폼이라 이 등식이 정당하게 깨진다. new-form.md 가 허용한 "정당하게 관계가 깨지는 변경" 이므로 사유와 함께 고치되, 숫자를 올리는 것이 아니라 허용 목록을 두어 등식을 다시 세운다(D-3) — 목록에 없는 폼은 종전 등식에 그대로 걸려야 다음 사람이 마커를 빠뜨렸을 때 여전히 실패한다.
§2. 요구사항 (v2 확정) + 비목표
  1. 화면을 디자인 시스템 안으로 들인다 — 로그인 · 최초 관리자 등록은 가운데 카드(auth shell), 관리자의 사용자 등록은 앱 레이아웃 안이다(D-1 · D-13).
  2. 로그인 상태를 화면이 안내한다 — 실패와 로그아웃을 배너 한 줄로 알린다. 계정 존재 여부는 드러내지 않는다(D-2).
  3. 가입 검증을 다른 폼과 같은 방식으로 — @Valid + BindingResult + 필드 아래 n-error · 한 상태에 메시지 하나(D-4).
  4. 중복 아이디는 판정 하나를 둘이 함께 쓴다 — 컨트롤러의 사전 거절과 서비스 가드가 같은 usernameTaken(String) 을 부른다(D-5).
  5. silent return 을 없앤다 — 불일치 · 중복은 invariant if-throw 로 막고 트랜잭션 어노테이션을 Spring 것으로 맞춘다(D-6).
  6. 접근 정책을 부트스트랩 판정 하나로 세운다 — ROLE_ADMIN 이 없으면 익명 가입(최초 관리자 · 역할 ADMIN 고정), 생긴 뒤에는 ROLE_ADMIN 만(D-11 · D-12 · D-13).
  7. 관리자가 만든 사용자는 초기 비밀번호를 바꿔야 들어온다 — 첫 로그인에서 변경 화면으로 보내고 그 전에는 다른 화면이 열리지 않는다(D-14 · D-15).
  8. 자기 계정을 다룰 자리를 만든다 — 사이드바 "계정" 묶음에 이름 · 비밀번호 변경 · (관리자에게만) 사용자 등록 · 로그아웃(D-16).
  9. 기동과 렌더의 전제를 갖춘다 — 없는 스키마를 세우고(D-7) 비인증 화면이 자원을 받게 한다(D-8).
  10. 인가 경계 · 강제 변경 · 가입 검증을 테스트로 잠근다 — 지금은 0 이다(D-9).
비 목표 — 아래는 이 슬라이스에서 하지 않는다.
  • 이름 · 패키지 정리 — 밑줄 명명(UserDetails_Impl 등) · domain/ → enums/ · BaseTimeEntity · Boolean → boolean · RoleConverter 중복. Users 이름은 지적 자체를 철회한다(예약어 회피).
  • CSRF 활성화 · 운영 스크립트 인증 · PXE 채널 인증 · 세션 정책 — 별도 슬라이스. 다만 로그아웃을 처음부터 POST 로 두어(D-16) CSRF 를 켤 때 화면을 다시 고치지 않게 한다.
  • 비밀번호 만료 · 재사용 이력 · 잠금 정책 — 이번은 "초기 비밀번호를 한 번 바꾼다" 까지다.
  • 인증 판정 — formLogin · UserDetailsService · PasswordEncoder 는 손대지 않는다(지시 ②).

§4. 도메인 모델 (SSOT)

SignUpRequest — 검증 규칙 (D-4 개정 · 한 상태에 메시지 하나)

필드제약메시지
username@NotBlank아이디를 입력하십시오.
@Size(max=64)아이디는 64자 이하로 입력하십시오.
password@NotBlank비밀번호를 입력하십시오.
@Pattern("^$|^[A-Za-z0-9!@#$%^&*()\-_=+.,?]{8,72}$")비밀번호는 영문 대소문자 · 숫자 · 특수기호(! @ # $ % ^ & * ( ) - _ = + . , ?)로 8자 이상 72자 이하로 입력하십시오.
retypedPassword@NotBlank비밀번호를 한 번 더 입력하십시오.
passwordConfirmed@AssertTrue (교차 필드)비밀번호가 일치하지 않습니다.
name@NotBlank이름을 입력하십시오.
@Size(max=20)이름은 20자 이하로 입력하십시오.
roles@NotEmpty — 관리자 모드만역할을 하나 이상 고르십시오.

아이디에 형식 규칙을 두지 않는 것은 v2 에서 사용자가 정한 것이다 — 사내 메일 도메인 앞부분을 그대로 쓰기 때문이다(Q4). 남는 것은 빈 값과 길이뿐이다. 비밀번호는 반대로 문자 집합을 좁혔다. @Pattern 이 ^$| 로 시작하는 것은 빈 값에 침묵시키기 위해서이고(그 자리는 @NotBlank 가 말한다), 집합을 ASCII 1 바이트로 묶은 것은 bcrypt 의 72 바이트 한계를 글자 수와 일치시키기 위해서다 — 한글은 한 글자가 3 바이트라 글자 수로만 재면 뒷부분이 조용히 잘린다.

모드는 요청 필드가 아니라 서비스 인자로 넘긴다. DTO 는 SignUpRequest 하나로 두고 SignupMode enum(BOOTSTRAP_ADMIN · ADMIN_CREATES_USER)을 인자로 준다 — 무명 boolean 금지 규약이자, "요청 본문이 스스로 자기 권한을 주장하게 두지 않는다" 는 뜻이다. 부트스트랩에서는 요청의 roles 를 읽지 않는다.

PasswordChangeRequest — 검증 규칙 (D-15)

필드제약메시지
currentPassword@NotBlank현재 비밀번호를 입력하십시오.
newPassword@NotBlank새 비밀번호를 입력하십시오.
@Pattern — 위와 같은 집합새 비밀번호는 영문 대소문자 · 숫자 · 특수기호(! @ # $ % ^ & * ( ) - _ = + . , ?)로 8자 이상 72자 이하로 입력하십시오.
retypedPassword@NotBlank새 비밀번호를 한 번 더 입력하십시오.
newPasswordConfirmed@AssertTrue (교차 필드)새 비밀번호가 일치하지 않습니다.
newPasswordDifferent@AssertTrue (교차 필드)새 비밀번호는 현재 비밀번호와 다르게 정하십시오.
(서비스 대조)PasswordEncoder.matches현재 비밀번호가 올바르지 않습니다.

현재 비밀번호 대조만 서비스로 내려가는 이유는 저장된 해시가 있어야 판정되는 것이라 요청 하나만 보고는 알 수 없기 때문이다. 결과는 필드 직결 예외로 올라와 currentPassword 칸 아래에 선다(§7).

교차 필드 — 두 값이 모두 있을 때만 판정한다

@AssertTrue(message = "비밀번호가 일치하지 않습니다.")
public boolean isPasswordConfirmed() {
    if (password == null || password.isBlank()) return true;   // @NotBlank 가 이미 말한다
    if (retypedPassword == null || retypedPassword.isBlank()) return true;
    return password.equals(retypedPassword);
}

빈 값일 때 true 를 돌려주는 이유는 같은 상황을 두 문장이 말하지 않게 하기 위해서다(선례 PowerResetRequest.isScreenAllowed). PasswordChangeRequest 의 두 교차 필드도 같은 모양이다.

비밀번호 불일치를 한 예외로 묶고 필드만 달리 드는 이유는, 두 자리가 말하는 것이 같은 사실("들어온 비밀번호가 기대와 다르다")이고 다른 것은 어느 칸 아래에 붙느냐뿐이기 때문이다. 예외를 둘로 쪼개면 클래스는 늘고 처리는 똑같아진다. 그래서 필드 이름을 생성자 인자로 받는다.

두 예외를 필드 직결 계열로 고른 것은 이 프로젝트가 이미 그 층을 갖고 있기 때문이다 — 컨트롤러는 ex.fieldName() 으로 rejectValue 를 부르고(IsoUploadController 선례), XHR 경로는 advice 가 fieldErrors 바디로 내린다.

로그인 실패와 인가 거부는 새 예외를 만들지 않는다. 로그인 실패는 failureUrl 이 화면을 되돌리고 배너 한 줄이 말하는 것이 이미 정상 흐름이며, 인가 거부는 프레임워크가 익명이면 로그인으로 보내고 권한 부족이면 403 을 낸다 — 둘 다 우리가 분기를 늘릴 자리가 아니다.

(b) 별도 Validator 클래스 — 규칙이 필드 단위라 어노테이션으로 충분하다. (c) 세 어노테이션 쌓기 — 빈 값 하나에 세 문장이 달려 무엇부터 고칠지 모르게 된다. (d) 부트스트랩 전용 DTO — 필드가 같고 모드만 다른데 DTO 를 나누면 검증 규칙도 둘로 갈라진다
D-5 중복 아이디 = 판정 하나를 사전 거절과 서버 가드가 공유. 컨트롤러가 검증 통과 뒤 usernameTaken 으로 rejectValue 하고, 서비스가 같은 메서드로 재판정해 DuplicateUsernameException 을 던진다. DB UNIQUE 는 최후 방어선 DB UNIQUE 위반을 잡아서 변환(현행이 사실상 이것의 실패판) — 예외 메시지에 기대는 판정이라 드라이버 · 버전에 흔들리고, 사용자에게는 이미 500 이 나간 뒤다
D-6 서비스 정리. silent return 제거 — @Valid 를 거친 요청만 받는다는 전제 위에서 불일치 · 중복을 invariant if-throw 로 막는다. jakarta.transaction.Transactional → Spring @Transactional 서비스를 그대로 두고 컨트롤러에서만 막기 — 화면을 거치지 않는 호출(direct POST · 후속 API)에 가드가 없어진다
D-7 v2 개정 DDL = ddl/S18_users.sql + schema.sql 동기. 두 테이블을 현행 엔티티 매핑 그대로 세우고 v2 에서 must_change_password 를 더한다 ddl-auto=update 로 넘기기 — 실 배포 정책이 validate 이고, 스키마를 런타임이 정하게 되면 ddl/ 의 이력이 끊긴다
D-8 v2 개정 자원 경로 permitAll(화면 렌더의 전제). /global/** · /css/** · /fonts/** · /vendor/** · /favicon.ico + dispatcherTypeMatchers(DispatcherType.ERROR).permitAll(). v2 — /password/change 는 기본값인 authenticated 로 두고, /signup 만 D-12 의 정책 빈이 맡는다 (a) 정적 자산 전부 열기 — 컨트롤러 경로까지 함께 열릴 위험이 있다. (b) 자산을 /resources/** 로 옮기기 — 이미 열린 경로에 맞추려고 모든 템플릿 링크를 고치는 것이다
D-9 v2 개정 테스트 여섯 파일 · 33 시나리오(§6) — 가입 · 변경 컨트롤러, 서비스 단위, 인가 진리표, 인터셉터 허용 목록, 인증 경계, 규약 통합 테스트 하나로 갈음 — 인가 · 강제 변경 · 재렌더는 성격이 달라 실패했을 때 원인이 섞인다
D-10 v2 개정 CP5 = 샌드박스 브라우저 검증 — 빈 DB 에서 시작해 A1~A11 · B1~B9 · C1~C3 을 밟는다(§9). 항목마다 스크린샷 1:1 curl 확인으로 갈음 — 화면에서만 드러나는 결함을 잡는 것이 이 단계의 존재 이유이고, 이 슬라이스는 화면이 본체다
D-11 v2 신규 부트스트랩 상태 SSOT = UserRegistrationService.bootstrapOpen() = !existsByRole(Role.ADMIN). 이 판정 하나를 ① 인가 규칙(D-12) ② 화면 모드 선택(D-13) ③ 로그인 화면의 링크 노출이 함께 쓴다 — "UI 차단 조건과 서버 가드 조건은 단일 SSOT" 규약 그대로다 (a) users 0 행 = 부트스트랩 — ADMIN 없이 USER 만 있으면 아무도 들어올 수 없게 잠긴다. (b) 설정 플래그 — 수동으로 닫아야 하고 잊으면 열린 채 남는다
D-12 v2 신규 /signup 인가 = 프레임워크 primitive AuthorizationManager. .requestMatchers("/signup").access(signupAccess) 에 빈 SignupAccessPolicy(AuthorizationManager<RequestAuthorizationContext>)를 물린다 — bootstrapOpen() 이면 허용, 아니면 hasRole("ADMIN") 위임. 인증은 그대로다 (a) 컨트롤러에서 if (…) throw — 인가가 컨트롤러로 새고, GET 은 화면까지 렌더된 뒤에 막힌다. (b) permitAll + 서비스 가드 — 같은 이유. 분기를 늘리지 말고 프레임워크가 떠맡게 한다는 규약의 적용이다
D-13 v2 신규 가입 화면 두 모드 · 폼 fragment 하나 — 같은 URL /signup. 부트스트랩 모드(익명) = auth 카드 · "최초 관리자 등록" · 역할 선택 없음(ADMIN 고정) · 성공 → redirect:/login + flash. 관리자 모드(ROLE_ADMIN) = 앱 레이아웃 안 n-page-md · "사용자 등록" · 역할 체크박스(Role.description 라벨) · 초기 비밀번호 · 성공 → redirect:/signup + flash. 항목 · 오류 표시는 fragments/security/signup-form.html 하나를 두 템플릿이 포함한다 (a) 관리자 모드도 auth 카드 — 앱 안 기능이 앱 밖 화면처럼 보이고 돌아갈 곳이 없다. (b) 템플릿 하나에 th:if 로 골격 분기 — body shell 규칙을 조건부로 만들면 사이드바가 조건부로 사라지는 화면이 된다
D-14 v2 신규 초기 비밀번호 · 강제 변경 = 플래그 + 성공 핸들러 + 인터셉터. Users.mustChangePassword(부트스트랩 관리자 false · 관리자가 만든 사용자 true). 로그인 성공 시 MustChangePasswordSuccessHandler(SavedRequestAwareAuthenticationSuccessHandler 확장)가 /password/change?first=1 로 보내고, 그 밖의 요청은 MustChangePasswordInterceptor(허용 = /password/change · /logout · /login · /error · 정적 자산)가 되돌린다. 변경 성공 = 플래그 해제 + 새 해시 저장 + 세션 principal 갱신 (a) isCredentialsNonExpired=false — Spring 이 로그인 자체를 거절해 초기 비밀번호로 들어와 바꾸는 흐름이 성립하지 않는다. (b) 인가 규칙으로 403 — 왜 막혔는지 모른 채 막힌다. (c) 인터셉터 없이 성공 핸들러만 — 주소창 입력으로 우회된다
D-15 v2 신규 비밀번호 변경 화면 /password/change(인증 사용자 누구나). 규칙은 §4 표. 현재 비밀번호 대조는 서비스(PasswordEncoder.matches)가 하고 틀리면 PasswordMismatchException("currentPassword") → 컨트롤러가 필드 오류로 재렌더(IsoUploadController 선례). 앱 레이아웃 안 n-page-md 이고, 강제 변경(?first)일 때만 안내 배너를 위에 둔다 (a) 강제 변경 전용 화면 — 하는 일이 같고 다른 것은 배너 한 줄뿐이다. (b) 현재 비밀번호를 묻지 않기 — 자리를 비운 사이 세션을 잡은 사람이 비밀번호를 갈아 끼울 수 있다
D-16 v2 신규 사이드바 계정 영역. fragments/layout :: navbar 의 배경 작업 버튼 위에 n-nav-group "계정" — 사용자 이름(sec:authentication="name") · "비밀번호 변경" · ADMIN 에게만 "사용자 등록"(sec:authorize) · "로그아웃"(POST 폼). activePage 키 'users' · 'password' (a) 상단 바 — 이 앱에 없는 층을 계정 하나 때문에 만들지 않는다. (b) 사용자 등록은 URL 직접 입력 — 발견할 수 없는 기능은 없는 기능이다. (c) GET 로그아웃 — CSRF 를 켜는 순간 막혀 화면을 다시 고쳐야 한다

  2. CSRF 활성화 · 세션 정책 — 로그아웃을 POST 로 둔 것(D-16)이 그 준비다. 켜는 순간 전역 제출 경로(form-submit.js)가 토큰을 실어야 하므로 별도 슬라이스로 다룬다.
  3. 운영 스크립트 인증 · PXE 채널 — /api/pxe/v1/** 의 무인증 허용은 게스트가 쓰는 통로라 별도 설계가 필요하다. 그 전까지는 httpBasic 우회를 런북에 적는다.
  4. 구조 정리 — 밑줄 명명 · domain/ 패키지 · Boolean · RoleConverter 중복(Q3 에서 제외한 것들). 이번에 테스트를 세워 두므로 그때 회귀를 잡을 그물이 생긴다.
  5. Q5 · Q6 의 후속 — 특수기호 집합을 바꾸면 정규식 한 곳과 데모 상수를 함께 고친다. 초기 비밀번호를 시스템이 생성하는 방식(Q6 (b))으로 가려면 전달 수단이 먼저 있어야 한다.
