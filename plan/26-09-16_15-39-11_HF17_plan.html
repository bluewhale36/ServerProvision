§1. 배경

이 문서는 버그 수정(HF) 슬라이스의 CP1 산출물이다. 표준 11 섹션 대신 상황 파악과 해결책 탐색에 필요한 다섯 절만 둔다 — 배경 · 실측 · 결론 · 수정 방향 · 검증이다.

1-1. 보고 (2026-09-16 · 사용자)

프로비저닝을 돌린 서버의 BIOS 셋업에서 부트 순서 1번이 네트워크로 고정되고 디스크가 4번으로 내려가 있다. 원래 disk → cd → usb → network → shell 이던 것이 network → cd → usb → disk → shell 로, 1번과 4번이 서로 자리를 바꾼 모양이다. 셋업에서 순서를 바꿔 저장 · 재부팅해도 되돌아가지 않고 CMOS 클리어 점퍼만 복구한다. BMC Redfish 로 Boot 를 조회하면 BootSourceOverrideEnabled=Disabled 로 정상이다.

1-2. 이력 — 어떻게 여기까지 왔나

시점단계한 일
08-27 실기— OS 잔존 서버가 BMC flash 뒤 전원 투입에서 디스크 OS 로 부팅 → 20분 복귀 시한 만료. 부트 순서 FBO101='Hard Disk' 1순위
08-28 ~ 08-31E2.5 NextBoot.PXE_ONCE(Boot{Once · Pxe · UEFI}) 를 PowerOnStep(펌웨어) · BeginSettingStep(설정) 재부팅 직전에 무장
09-08 실기 3호F-2 · F-2b F-2: BIOS 설정 적용의 내부 재시작이 Once 를 첫 POST 에서 소비 → 두 번째 POST 는 부트 순서대로 → UEFI 셸(1/1). F-2b: RAID → OS 전이의 에이전트 자기 reboot 경로에는 무장이 아예 없음(5/5)
09-09 · 7차 재배포HF15-1 PXE_CONTINUOUS(Continuous · Pxe · UEFI) 를 "PXE 보장 창"(개시 ~ wimboot 서빙 전) 안에 세우고 밖에서 RELEASE(Disabled). 조정자 BootOverrideReconciler 가 상태 변화마다 ProvisioningProgress.isPxeGuaranteeWindow() 에 맞춤
09-10 실기 4호K5 종단 뒤 Redfish Disabled 3/3 확인 → O 판정. BIOS 셋업의 부트 순서는 보지 않았다

HF15-1 은 두 구멍(F-2 · F-2b)을 "창 안에서는 어떤 경로의 재부팅이든 PXE" 라는 한 장치로 덮었다. 그 장치가 Continuous 였고, 이번 결함은 그 선택의 부작용이다. K5 가 BMC 쪽만 확인해 그때 잡히지 않았다.

1-3. 영향

  • 09-09 7차 재배포 이후 PXE 보장 창을 한 번이라도 지난 서버 전부(종단 · 실패 · 회수 무관).
  • 자체 LAN 에서는 매 부팅 PXE → /boot → 종단 서버는 iPXE exit 폴스루로 로컬 부팅되므로 서비스는 되지만 부팅이 늦다.
  • 고객 LAN 으로 나간 서버는 그쪽의 PXE 서버를 먼저 만난다. 셋업에서 순서를 고칠 수 없고 CMOS 클리어가 필요하다. 출고 전 복구가 필요하다.
§2. 실측 (2026-09-16)

실측 환경 — 2026-09-16 · 사용자 · 맥(Homebrew ipmitool · curl) · 대상 = 종단된 서버 1대(Windows 설치 완료 · AMI MegaRAC BMC · MD72-HB3 계열). 다섯 실측을 순서대로 적는다. 항목마다 보낸 명령 그대로 · 그 뒤에 한 일(재부팅 · 셋업 확인 · 없으면 없음) · 본 것 · 가른 것 을 나눈다. $BMCIP · $USER · $PW 는 BMC 주소와 credential 이다(값은 적지 않는다).

2-1-1. 현재 IPMI boot flag 읽기

ipmitool -I lanplus -H $BMCIP -U $USER -P $PW chassis bootparam get 5

그 뒤에 한 일 — 없음(조회만).

본 것 — Boot parameter data: 0000000000 · Boot Flag Invalid · Options apply to only next boot · BIOS PC Compatible (legacy) boot · Boot Device Selector : No override.

가른 것 — 앱의 Disabled 가 IPMI 비트까지 다 지웠다. "BMC 가 안 지웠다" 가설은 탈락하고, 남는 것은 BIOS 가 스스로 무엇을 기억한다는 가설이다.

2-1-2. 한 번짜리 flag(Once · Hdd)로 저장값이 바뀌는가

curl -sk -u $USER:$PW -X PATCH -H 'If-Match: *' -H 'Content-Type: application/json' \
  https://$BMCIP/redfish/v1/Systems/Self \
  -d '{"Boot":{"BootSourceOverrideEnabled":"Once","BootSourceOverrideTarget":"Hdd","BootSourceOverrideMode":"UEFI"}}'

그 뒤에 한 일 — ① Windows 안에서 재부팅 → BIOS 셋업 진입 → Boot Option 순서 확인. ② 아무 flag 도 보내지 않고 한 번 더 재부팅 → 셋업 진입 → 순서 확인.

본 것 — ① 재부팅 뒤 셋업: disk 1번으로 원복(network 4번). ② 다음 재부팅 뒤 셋업: 다시 network 1번 · disk 4번.

가른 것 — Once 는 그 POST 만 덧씌우고 BIOS 의 기억을 바꾸지 못한다. flag 가 소진되면 기억(Pxe)이 다시 적용된다.

2-1-3. persistent 이면서 장치 없음(Continuous · None)으로 기억이 지워지는가

curl -sk -u $USER:$PW -X PATCH -H 'If-Match: *' -H 'Content-Type: application/json' \
  https://$BMCIP/redfish/v1/Systems/Self \
  -d '{"Boot":{"BootSourceOverrideEnabled":"Continuous","BootSourceOverrideTarget":"None"}}'
curl -sk -u $USER:$PW https://$BMCIP/redfish/v1/Systems/Self | jq .Boot
ipmitool -I lanplus -H $BMCIP -U $USER -P $PW chassis bootparam get 5

그 뒤에 한 일 — PATCH 수락 확인(응답 본문 없음) → GET 으로 Boot 되읽기 → ipmitool 로 IPMI 비트 확인 → 재부팅 → 셋업 진입 → 순서 확인.

본 것 — 되읽기: BootSourceOverrideEnabled=Continuous · Target=None · Mode=UEFI(2-2 의 Boot 객체 전문은 이때 채집). IPMI: Boot parameter data: e000000000 · Boot Flag Valid · Options apply to all future boots · BIOS EFI boot · No override. 재부팅 뒤 셋업: 변화 없음(network 1번 그대로).

가른 것 — persistent 이더라도 device 가 "No override" 이면 BIOS 는 아무 일도 하지 않는다. 기억을 "없음" 으로 갱신해 주지 않는다.

2-1-4. persistent + 실제 장치(Continuous · Hdd)로 기억을 바꾼 뒤 비우면 순서가 남는가

curl -sk -u $USER:$PW -X PATCH -H 'If-Match: *' -H 'Content-Type: application/json' \
  https://$BMCIP/redfish/v1/Systems/Self \
  -d '{"Boot":{"BootSourceOverrideEnabled":"Continuous","BootSourceOverrideTarget":"Hdd","BootSourceOverrideMode":"UEFI"}}'
# 재부팅 → 셋업 확인 뒤
curl -sk -u $USER:$PW -X PATCH -H 'If-Match: *' -H 'Content-Type: application/json' \
  https://$BMCIP/redfish/v1/Systems/Self -d '{"Boot":{"BootSourceOverrideEnabled":"Disabled"}}'

그 뒤에 한 일 — ① 첫 PATCH 뒤 재부팅 → 셋업 진입 → 순서 확인. ② Disabled PATCH 로 BMC flag 를 비움 → 재부팅 → 셋업 진입 → 순서 확인.

본 것 — ① disk 1번으로 원복. ② flag 를 비운 뒤 재부팅에도 disk 1번 유지.

가른 것 — persistent + 실제 장치 flag 는 기억을 Hdd 로 바꾼다. 순서가 돌아온 것은 기억이 지워졌기 때문이 아니라 대상이 바뀌었기 때문이다(2-1-5 가 확정).

2-1-5. 기억이 Hdd 로 남았는지 — 셋업 편집이 유지되는가

(명령 없음 — BIOS 셋업 화면에서 Boot Option #1 을 UEFI USB Device 로 바꾸고 저장 · 종료)

그 뒤에 한 일 — 저장 뒤 재부팅 → 셋업 진입 → 순서 확인.

본 것 — USB 가 아니라 disk 1번으로 되돌아옴(편집 무효).

가른 것 — BIOS 는 이제 매 POST "디스크를 1번으로" 를 덧씌운다. 기억을 지운 것이 아니라 Pxe → Hdd 로 옮긴 것이다(세미핀).

2-1-6. 실측하지 않고 이전 실기에서 빌려 온 근거

Once · Pxe 만 쓰던 E2.5 시절(08-27 ~ 09-08)에 이 현상이 없었다는 것은 이번에 따로 실측하지 않았다. 근거는 실기 3호 기록(09-08)에 "부팅 순서가 디스크 우선인 서버" 가 그대로 남아 있다는 것과, 2-1-2 에서 Once 가 기억을 바꾸지 못한 것 둘이다. 이번 정정 뒤 실기(CP7)에서 Once 만 지나간 서버의 셋업 순서를 직접 확인하는 것이 이 빈칸을 채운다.

2-2. 함께 채집한 것

  • GET /redfish/v1/Systems/Self 의 Boot: BootOrder=["Boot0003","Boot0004","Boot0005","Boot0001"] · BootOrderPropertySelection=BootOrder · BootNext=null · BootSourceOverrideTarget@Redfish.AllowableValues 14개(None · Pxe · Floppy · Cd · Usb · Hdd · BiosSetup · Utilities · UefiShell · UefiTarget · SDCard · UefiHttp · RemoteDrive · UefiBootNext) · Mode 허용값 Legacy · UEFI.
  • E3-3 이 채집한 BIOS 레지스트리(sbx-e33/materials/BiosAttributeRegistry_MD72-HB3*.json)에 Fixed Boot Order 가 속성으로 있다: UEFI FBO201~FBO205(기본 UEFI Hard Disk · UEFI CD/DVD · UEFI USB Device · UEFI Network · UEFI AP), legacy FBO101~FBO104. 관측 순서 = FBO201 과 FBO204 의 교체.
  • 이전 실기 대조: E2.5 시절(Once · 08-27 ~ 09-08)에는 이 현상이 없었다. 실기 3호 기록에 "부팅 순서가 디스크 우선인 서버" 가 그대로 남아 있다.
§3. 결론 — BIOS 동작 모델과 결함의 뿌리

3-1. 모델

보낸 flagBIOS 의 반응BIOS 기억(persistent device)
Continuous · Pxe적용 + 저장Pxe
Disabled아무것도 보지 못함유지
Once · Hdd그 POST 만 적용유지
Continuous · None무시유지
Continuous · Hdd적용 + 저장Hdd

이 BIOS(AMI Aptio · IPMI boot 모듈)는 IPMI boot flag 를 두 층으로 본다. 이번 POST 에 적용할 값과, persistent 비트가 켜진 flag 를 받을 때 갱신되는 장기 기억이다. 매 POST 에 기억된 장치의 Fixed Boot Order 그룹을 1번과 교체해 표시 · 적용한다. 셋업에서 사용자가 저장한 순서는 그 다음 POST 에 다시 덧씌워진다. 기억을 갱신하는 것은 persistent + 실제 장치 flag 뿐이고, 기억을 지우는 Redfish 어휘는 없다. 지우는 길은 CMOS 클리어 또는 Load Defaults(Redfish Bios.ResetBios 액션이 같은 효과)뿐이다.

3-2. 결함의 뿌리

HF15-1 이 채택한 Continuous 가 이 기억을 만든다. 조정자가 보내는 Disabled 는 BMC 쪽 flag 만 비우고 BIOS 의 기억에는 닿지 않는다. E2.5 의 Once 는 기억을 만들지 않는다(실측 2 · 이전 실기 대조).

정정의 원칙은 하나다 — Continuous 를 어디서도 보내지 않는다. 이미 기억이 생긴 서버는 앱이 지울 수 없고 서버별 복구 절차가 필요하다(§4-3).

§4. 수정 방향 (간단)

4-1. 원칙

Once 로 회귀한다. HF15-1 이 Continuous 로 함께 덮었던 두 구멍(F-2 · F-2b)은 각각 자기 자리에서 막는다. 조정자와 PXE 보장 창 판정은 역할이 없어져 철거한다.

4-2. 변경 다섯 가지

#자리변경
1AgentReportService 의 지시 계산(REBOOT) REBOOT 을 돌려주기 직전, 진행 중(개시 · 미실패 · 미종단 · 미회수) + BMC 검출이면 동기로 Once · Pxe 무장. 새 협력자 1개(execution.engine.boot — 조정자 자리). best effort(E2.5 D-4) · 로그 [pxe-once]. 종단 · 실패의 REBOOT 은 무장 없음
2BeginSettingStep · ReturnReadbackStep 재부팅 무장을 PXE_ONCE 로. 미복귀 분기에 미도착 재무장 추가 — rebootAt 뒤 N분(설정 키 · 기본 4분) 안에 /boot 가 없고 아직 재무장하지 않았으면 Once · Pxe 재무장 + On/ForceRestart 1회 (RedfishPowerService.networkBoot 재사용) · 행 meta rearmAt 기록 · 이후 복귀 시한(20분)까지 대기는 그대로
3PowerOnStep(펌웨어) 전원 투입 무장을 PXE_ONCE 로. 같은 미도착 재무장 규칙 — 기점 returnWaitSince() · FlashLedger phase 사건 pxe-rearm(PHASE_LEVEL_REASONS 등재 — 축 판정 오염 방지)
4RedfishPowerService.networkBoot(O-10)PXE_ONCE 로
5철거 BootOverrideReconciler(+ 테스트) · ProvisioningProgress.isPxeGuaranteeWindow()(+ 테스트) · NextBoot.PXE_CONTINUOUS · NextBoot.RELEASE. GuestServerChangedEvent 는 SSE 가 쓰므로 유지

왜 1 이 동기 호출인가 — 에이전트는 REBOOT 응답을 받는 즉시 reboot 한다. 무장이 응답보다 먼저 끝나야 한다. Redfish 클라이언트 시한은 연결 3초 · 읽기 10초라 30초 폴링 에이전트에 무해하다. 같은 부팅에서 REBOOT 이 여러 번 계산되어도(재전송) PATCH 는 멱등이다.

왜 2 가 "미도착 뒤 재무장" 인가 — 설정 적용의 내부 재시작이 Once 를 소비하는 것은 피할 수 없다(F-2). 두 번째 POST 를 Redfish 되읽기로 잡는 방법은 F-4 교훈(재부팅 중 되읽기는 이르게 읽힘)에 걸린다. 우리가 믿는 유일한 신호는 /boot 도착이므로, 그것이 N분 안에 없으면 한 번 더 세우고 다시 켠다. N 의 근거: POST 1~2분 + iPXE 30초 → 정상 PXE 도착은 3분 안. 비용은 설정 단계에 최대 N분 + POST 1회.

왜 3 도 같은 규칙인가 — BIOS flash 뒤 첫 POST 가 내부 재시작을 하는지 미실측이다. 실기 3호에서는 Once 로 PXE 가 왔지만(17:32:26 → 17:36:33) 한 표본이다. 같은 규칙을 두는 비용이 작다.

화면 — 변경 0. 재무장은 원장 meta(rearmAt · pxe-rearm 행)에만 남고 상세 화면의 기존 meta 투영 규칙을 따른다.

설정 키 — provision.execution.pxe-rearm-delay(기본 4m) — FlashTimeoutPolicy 에 같은 방식(DurationStyle)으로 읽는다.

모의 BMC(scripts/mock-redfish/mock-redfish.py) — ① 설정 pending 이 있으면 POST 재연이 Once 를 소진한 뒤 두 번째 POST 를 부트 순서로 재연하는 모드 ② PATCH 된 BootSourceOverrideEnabled 값 이력 — CP5 가 "Continuous 0회" 를 단언한다.

4-3. 이미 영향 받은 서버의 복구 (앱 밖 · 서버별 · 운영 절차)

  • 순서 복구(기억은 Hdd 로 남음): Redfish PATCH Boot{Continuous · Hdd · UEFI} → 재부팅 1회 → PATCH Boot{Disabled}. 셋업 편집은 여전히 막히지만 부팅은 디스크 1번이다.
  • 완전 정리: CMOS 클리어 점퍼, 또는 원격이면 Redfish Bios.ResetBios 액션. 둘 다 E3-1 이 넣은 BIOS 설정도 지우므로 재적용이 필요하다.
  • 대상: 09-09 이후 PXE 보장 창을 지난 서버 전부. 출고 서버는 순서 복구 이상을 권한다.
