§1. 현재 상태 (진단)

E1-I-1 로 진단 자산 대시보드는 조회·봉인·재검증까지 한다. 그러나 자산을 바꾸는 경로가 전무하다 — Alpine 버전 업그레이드(vmlinuz/initramfs/modloop 교체)나 진단 에이전트 수정(agent.sh)이 필요하면 운영자가 서버에 접속해 셸로 파일을 덮어쓴 뒤 대시보드에서 다시 [무결성 봉인]을 눌러야 한다.

능력있음 (E1-I-1)비어 있음 (이 슬라이스가 채움)
조회 · 무결성6 슬롯 존재·크기·수정시각·HMAC 마커 대조 + 봉인/재검증—
자산 교체—화면에 교체 수단 없음 — 셸 접속 + 수동 덮어쓰기 + 수동 재봉인의 2단 수작업
교체 중 안전—보장 없음 — 셸 cp 로 208MB modloop 을 덮어쓰는 도중 게스트가 부팅하면 잘린 파일을 받는다(torn read)
마커 사이드카 노출봉인 시 <자산>.provision.json 생성 — 서빙 디렉토리에 있어 /api/pxe/v1/assets/*.provision.json 로 게스트에 노출(E1-I-1 known item, 비밀 누출은 없음)이 슬라이스에서 서빙 제외로 정리(동반)
핵심 진단 — 대시보드가 "보기"만 하고 "고치기"를 못한다. 이 슬라이스는 가장 자주 바뀌는 단일 파일 4종을 화면에서 업로드 교체하게 하되, 208MB 자산을 게스트가 실시간으로 받는 환경이므로 원자적 스왑으로 torn read 를 원천 차단하고, 교체된 파일을 자동으로 신뢰 기준으로 재봉인한다. 조립 자산(apkovl·repo)은 내부 구조·서명 때문에 임의 업로드 교체 대상에서 뺀다(빌드 스크립트 소관).
§2. 요구사항 (확정) + 비목표
  1. 단일 파일 4종 UI 교체 — vmlinuz-lts · initramfs-lts · modloop-lts(Alpine 업그레이드 주 케이스) + agent.sh(에이전트 수정). 대시보드의 해당 슬롯 행에서 파일을 골라 업로드하면 교체된다.
  2. 조립 자산은 비대상 — diag.apkovl.tar.gz(서명 공개키 동봉 tar) · repo/(서명된 apk 저장소 디렉토리)는 UI 교체 불가. 대시보드는 "빌드 스크립트(build-assets.sh)로 교체" 를 안내한다. 임의 tar/zip 을 신뢰해 덮어쓰면 부팅이 깨질 수 있어(내부 구조·서명 검증 불가) 의도적으로 제외(사용자 확정).
  3. 원자적 스왑(불가침) — 업로드 바이트를 자산 루트 안 임시 파일에 먼저 쓰고 Files.move(temp, target, ATOMIC_MOVE, REPLACE_EXISTING) 로 교체. 208MB modloop 교체 중 부팅하는 게스트가 잘린 파일을 받지 않게 한다. 임시 파일이 같은 파일시스템(자산 루트 하위)이라 atomic move 가 성립.
  4. 교체 = 스왑 + 자동 재봉인 — 운영자가 교체를 택한 순간 그 파일이 새 신뢰 기준이므로, 스왑 직후 그 슬롯의 마커를 재기록한다(재검증 시 즉시 ORIGINAL). 수동 재봉인 불요.
  5. 가드(슬롯 경로변수 신설) — POST /system/diagnostic-asset/{slot}/replace 의 {slot} 검증: 없는 슬롯 → 404 / 조립 자산(비대상) → 409 / 서빙 비활성 → 409 / 빈 파일 → 400. UI 는 정상 경로를 1차 차단(비대상엔 버튼 없음, 서빙 비활성 시 disabled)하고 서버 가드가 안전망.
  6. 동반 — 마커 사이드카 서빙 제외 — PxeAssetsConfig 자산 핸들러가 *.provision.json 을 서빙하지 않게 한다(PathResourceResolver 확장). E1-I-1 이 남긴 노출 항목 정리(비밀 누출은 없었으나 내부 마커를 게스트에 줄 이유가 없다).
비 목표 :
  • apkovl · repo UI 교체 — 빌드 스크립트 소관(요구사항 2). 사전조립 결과물 업로드 방식은 필요 시 후속 슬라이스.
  • 대시보드 다중 자원 일반화 — E1-I-3. 이 슬라이스는 대시보드를 진단 리눅스 전용으로 유지한다(갈라지는 시점에 분리 — 두 번째 자원 종류는 E1-I-3 에서 온다).
  • PXE 인프라 dhcpd/tftp — E1-I-3.
  • 배경 업로드(Service Worker) — 208MB 는 동기 multipart POST 로 충분(격리망 · 단일 운영자). 초대형 자산 · 불안정 회선이면 후속에 BackgroundUpload 도입.
  • 이력 보존 · 롤백 — E1-I-2-b. 이 단계(a)는 순수 덮어쓰기(이전 파일 미보존)다. 교체 후 버그로 롤백이 필요한 상황은 b 가 담당한다 — 범용 버전 저장소(global/history, dhcpd/tftp 도 재사용)를 b-1 이 신설하고, b 가 a 의 스왑 앞에 archive(현재→이력) 단계를 끼운다. a 의 replace()는 그 삽입이 깨끗하도록 swap→reseal 순서로 둔다(seam).
🎬 미리보기 — 교체 시뮬레이터 (스왑·재봉인·가드를 직접 굴린다)

아래는 대시보드 미니어처다. 단일 파일 4종에는 「교체」버튼이 있고, 조립 자산(apkovl·repo)에는 "빌드 스크립트로 교체" 안내만 있다. 「교체」를 누르면 업로드→원자적 스왑→자동 재봉인이 흘러 크기·시각이 갱신되고 무결성이 원본 유지로 남는다. 「서빙」을 끄면 교체가 막히고(가드), 드리프트 상태의 슬롯을 교체하면 새 파일이 기준이 되어 복구되는 것도 본다.

서빙 :
진단 리눅스 자산
슬롯크기무결성교체
드리프트 0 — 시뮬레이터의 교체 판정(서빙? → 대상? → 스왑 → 재봉인 → ORIGINAL)은 §4 서버 규약과 1:1 이다. 비대상(apkovl·repo)은 버튼이 아예 없고(UI 1차 차단), 서빙 비활성이면 버튼이 disabled — direct POST 는 서버 가드가 409/409 로 받는다. "교체 = 스왑 + 자동 재봉인" 이라 교체 후 즉시 원본 유지가 된다.

교체 데이터 흐름

POST /system/diagnostic-asset/{slot}/replace   (multipart: file)
  1. slot 파싱 — 없는 이름 → 404 (DiagnosticAssetSlotNotFoundException)
  2. servingActive 아님 → 409 (SystemAssetServingDisabledException 재사용)
  3. !slot.replaceable() (apkovl·repo) → 409 (DiagnosticAssetNotReplaceableException)
  4. file.isEmpty() → 400
  5. 원자적 스왑:  temp = root/.tmp-
                  file.transferTo(temp)                       (multipart → 임시)
                  Files.move(temp, root/, ATOMIC_MOVE, REPLACE_EXISTING)
                  fileSystemHardener.applyDefaultPermissionsForFile(target)
  6. 자동 재봉인:  integrityService.sealOne(slot)             (새 해시 → 마커 재기록)
  → redirect /system/diagnostic-asset  (flash "교체 완료 — <자산> 새 파일로 갱신·재봉인")
왜 원자적 move 인가 — 자산 루트는 /api/pxe/v1/assets/** 로 게스트에 실시간 서빙된다. Files.copy(in, target, REPLACE_EXISTING) 로 직접 덮어쓰면 208MB 를 쓰는 수 초 동안 target 이 반쯤 쓰인 상태가 되어, 그때 부팅하는 게스트가 잘린 modloop 을 받는다. 임시 파일에 완성한 뒤 원자적 rename 하면 게스트는 항상 옛 파일 아니면 새 파일 — 중간이 없다.
§4. 도메인 모델 (SSOT)

DiagnosticAsset — replaceable 플래그 추가

// 교체 가능 여부는 layout 으로 유도할 수 없다: apkovl 은 단일 파일(SIDECAR)이지만 조립물이라 비대상.
// 명시 속성으로 둔다.
enum DiagnosticAsset {
  VMLINUZ  (..., replaceable=true),   INITRAMFS(..., replaceable=true),
  MODLOOP  (..., replaceable=true),   AGENT    (..., replaceable=true),
  APKOVL   (..., replaceable=false),  REPO     (..., replaceable=false);
  // 조회는 6종 전부, 교체는 replaceable=true 4종만.
}

교체 판정 규약 (분기 아닌 순차 가드 — 도메인 invariant if-throw)

slot 파싱 실패        → 404   // 없는 자산 이름(forging)
!servingActive        → 409   // 자산 위치 불명 (SystemAssetServingDisabledException 재사용)
!slot.replaceable()   → 409   // apkovl·repo (DiagnosticAssetNotReplaceableException)
file.isEmpty()        → 400   // 빈 업로드
그 외                 → 스왑 + 재봉인
// 이건 "케이스 추가로 분기 늘리기" 가 아니라 도메인 invariant 의 imperative if-throw(정당). UI 가 정상 흐름을 1차 차단.

재봉인 재사용 — seal() 을 sealOne(slot) 으로 분해

// E1-I-1 의 seal() 은 전 슬롯 루프. 교체는 한 슬롯만 재봉인하므로 단위 메서드를 뽑아 양쪽이 공유(SSOT).
DiagnosticAssetIntegrityService:
  SealResult seal()            { for (slot) sealOne(slot); }   // 기존 동작 = sealOne 루프로 재정의
  void       sealOne(slot)     { 존재하면 해시 계산 → 마커 write → 0644 }   // 교체가 호출
// 교체 서비스는 스왑만 담당하고 재봉인은 integrityService.sealOne 위임 — 마커 조립 로직 복붙 금지.

§8. 예상 부산물 / 주의 / 결정 사항

잔존 책임 · 주의 (정직 기록)

  • 교체는 덮어쓰기 — 이전 버전 미보존(a 한정). 롤백을 위한 이력 보존은 E1-I-2-b. a 의 replace()는 스왑 → sealOne 2단으로 두어, b-1 이 맨 앞에 archive(현재 파일 → 버전 저장소)를 끼우면 archive → 스왑 → sealOne이 되도록 확장 seam 을 남긴다(a 에서 archive 는 구현하지 않는다 — 갈라지는 시점에 분리).
  • 업로드 크기 상한 — Spring multipart(provision.upload.max-file-size=15GB) 재사용. modloop 208MB 는 여유. 임시 저장은 spring.servlet.multipart.location. 자산 루트 하위 임시 파일(atomic move 용)은 자산 루트가 multipart temp 와 다른 FS 여도 동작하도록 자산 루트 안에 만든다(cross-device rename 회피).
  • 마커 사이드카 제외의 부수효과 — *.provision.json 서빙 차단은 진단 자산에 한정(자산 핸들러만). 다른 자원의 마커는 애초에 web-served 아님. 회귀 없음.
  • 비대상 자산의 교체 요구가 잦아지면 — 사전조립 번들 업로드(apkovl tar / repo zip) 방식을 후속에서 재고. 지금은 빌드 스크립트 안내로 충분(교체 빈도 낮음).
  • 동시 교체 — 같은 슬롯 동시 POST 는 원자적 move 가 마지막 승자로 수렴(중간 없음). 단일 운영자 규모라 락 불요.
