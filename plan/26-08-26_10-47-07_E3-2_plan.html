§1. 배경 · 유래 — 지금 이 슬라이스인 이유
개정 이력 (파일 경로는 Notion 임베드 · 후속 report 참조를 지키려 고정한다)
  • 개정 1 (2026-08-26 KST · CP1 승인 반영) — 승인으로 확정된 넷을 반영했다. ① D-1 은 (C) 채택 확정이고, 정의서가 항목을 고르는 (A) 계열은 BMC 세팅 정의서 CRUD = U2-7 로 MVP 출시 이후에 둔다(§4 행선지 갱신). ② 표준값 확정 — Cold Redundant 는 set_cold_redundant_enable: 0 · master_psu: 0, Fan Profile 은 보드별 고정이며 자원 파일은 4 보드다(사용자가 discussion/e0-3-fanprofile/ 에 BMC 웹 UI 업로드 파일 4종을 두었다 — 파일명 · 보드 대응은 CP2 에서 확인해 §10 에 반영). ③ Bond 는 설정값 자체가 보드 공통이나 인터페이스 이름 eth1 이 모든 보드에서 같은지는 미확인이라 재실측 항목으로 남긴다(§9 에 적립). bond.enable 기본값 true 는 유지한다. ④ D-6 의 항목 SKIPPED 확정. 개정 1

E3-1 이 끝나면 커서는 BIOS_SETTING 에서 phase 를 종결하거나 다음 phase 로 간다. BMC_SETTING 은 enum 에 자리만 있고 아무도 밟지 않는다. E3-2 는 그 자리를 채운다 — 같은 FIRMWARE_SETTING phase 의 두 번째 step 으로 사내 표준 BMC 세팅 4종을 AMI 웹 API 로 써 넣고, 항목마다 되읽어 확인한다. BIOS 와 달리 재부팅은 없다.

정본이 바뀌었다

Notion E3-2 페이지(2026-08-25 재편)는 "BASIC_SETTING payload 에 BMC 설정 출처가 없으니 계약 신설부터" 라고 적었고, 계약 대안 셋(항목별 Redfish PATCH · 프로세스 등록 재생 · 골든 복원)을 사전 기록했다. 그 뒤 앵커 세션의 실측(2026-08-25)이 사내 표준 BMC 세팅의 정본은 Redfish 가 아니라 AMI 웹 API 4종임을 확정했다(E0-3 이 원장 · 브리핑 §1). 5호의 N1~N3(Redfish NTP · eth0 · syslog)는 사용자 확정 없이 상정된 후보였고 폐기됐다.

따라서 이 plan 의 출발점은 "정의서가 무엇을 고를 것인가" 가 아니라 "이미 정해진 표준 4종을 어떻게 안전하게 써 넣고 확인할 것인가" 다. D-1 이 이 해석을 결정으로 굳힌다.

실측이 준 계약 (브리핑 §2 · HAR 대조 2026-08-26 세션 확인)

  • 인증 — POST /api/session(form username · password) → 응답 JSON 의 CSRFToken. 이후 모든 요청에 X-CSRFTOKEN + X-Requested-With: XMLHttpRequest + 세션 쿠키. 쓰기는 Content-Type: application/json.
  • 성공 = 200 + 요청 바디의 에코(4종 모두 — HAR 에서 request == response 확인). cc · ok 필드는 없다(ok:0 은 로그인 · 로그아웃 응답에만 나온다).
  • 실패 두 모양 — 인증 {"cc":7,"error":"Invalid Authentication"}(HTTP 상태와 무관하게 바디로 판독) / 데이터 {"error":"Invalid Data","code":1010}.
  • 세션 TTL 약 10분(유휴 추정). 코드는 TTL 에 기대지 않고 cc:7 을 받은 그 자리에서 재로그인 1회 재시도한다. 끝에 DELETE /api/session(→ {"ok":0}, 실패해도 무해).
  • Bond — PUT 200 뒤 UI 가 로그아웃하고 14초 뒤 같은 주소로 재로그인 200. 주소 변경도 단절도 관찰되지 않았다(auto_configuration · active-backup 이라 IP 가 유지된다). 정식 왕복(W4)은 콘솔 미확보로 미실측이다.
추가 준비 불요 — ES-3 같은 선행 정비가 필요하지 않다. E3-1 이 세운 워커 골격(WorkerStep · WorkerStepRegistry · SettingLedger · BmcIdentityProbe)과 E1.6 의 자격증명 폴백을 그대로 쓴다.

Fan Profile 자원 — 세 출처 바이트 대조

보드별 JSON 3종(MS03-CE0 · MS74-HB0 · MS04-CE0)은 앵커 산출로 확보돼 있고(discussion/e0-3-fanprofile/), 세션이 세 출처(HAR 의 실전송 바디 · 앵커 파일 · Notion E0-3 의 기계 추출)를 바이트 단위로 대조해 전부 일치함을 확인했다(탭 · NBSP 0). 구조는 strVersion · arrProfile[2] · strMode 이고, MS74-HB0 은 curl 로 200 을 실증했으며 나머지 둘은 구조 동일 · 실기 전송 미검증이다. 개정 1 CP1 승인 시점에 사용자가 같은 디렉토리에 BMC 웹 UI 업로드 파일 4종을 두어 자원은 4 보드가 된다 — 파일명과 보드 대응은 CP2 에서 확인해 §10 에 반영한다.

§3. 설계 결정 D-1 ~ D-13 · 진리표 v2

D-1. 소비 입력 = 시스템 표준(설정 + 자원 파일). 정의서 계약은 넓히지 않는다 개정 1

세 갈래를 비교했다.

(A) 정의서 payload 확장

탈락

  • BasicSettingRequest 에 BMC 항목 선택 · 값을 더한다.
  • 4종은 사내 표준이라 정의서마다 같은 값이 복제돼 drift 의 원천이 된다.
  • 폼(U2) · 스냅샷 동결(U3-1 D-C) · Layer A 검증까지 churn 이 크다.
  • 정의서마다 다르게 할 요구가 아직 없다 — 갈라지는 시점이 아니다.

(B) 관리 자원 신설

탈락

  • BMC 세팅 프로필 CRUD · 보드별 파일 업로드.
  • 화면 · lifecycle · 마커가 따라붙는 MA 급 슬라이스다.
  • E3-2 는 집행 능력을 만드는 자리다. 이 후보는 MA6 으로 보낸다.

(C) 채택 — 설정 + 자원 파일

채택

  • provision.bmc.standard.* 설정 + 보드별 Fan Profile 자원 파일.
  • 정의서 관점의 계약: BASIC_SETTING 프로세스를 가진 정의서는 FIRMWARE_SETTING phase 를 보유하고, 그 phase 는 BIOS_SETTING 다음에 BMC_SETTING 을 반드시 밟는다.
  • 표준이므로 항목 opt-out 이 없다.

적대적 검토 — Notion 의 "payload 계약 신설" 과 어긋나지 않는가. 그 문장은 BMC 설정을 정의서의 선택 사항으로 봤을 때의 전제였고, 정본이 "사내 표준 4종" 으로 확정되면서 계약의 자리가 정의서에서 시스템 설정으로 옮겨진다.

확정 개정 1 — CP1 승인으로 (C) 채택이 확정됐다. 계약의 자리는 정의서가 아니라 시스템 설정이다. 정의서가 항목을 고르는 (A) 계열은 폐기가 아니라 이연이며, 후속 슬라이스 이름과 시점이 함께 정해졌다 — U2-7 (BMC 세팅 정의서 CRUD) · MVP 출시 이후.

잔존 비대칭 — BMC 표준은 BASIC_SETTING 을 가진 정의서에만 적용된다(biosSettingTemplateIds 가 NotEmpty 라 BIOS 템플릿 선택과 묶여 있기 때문이다). BMC 만 원하는 정의서가 필요해지는 시점에 (A) 의 얇은 판(항목 opt-in)으로 승격한다 — 그 자리가 U2-7 이다. 개정 1

D-2. 실행 형태 = 같은 phase 의 두 번째 step · SettingAxis 승격 (E3-1 D-10 이행)

  • SettingAxis { BIOS(BIOS_SETTING), BMC(BMC_SETTING) } — 순서 · step · next() 를 든다. 축이 둘이 되는 시점이라 지금 만든다.
  • SettingCursor.afterAxis(axis, progress, guestId, now) — 다음 축이 있으면 progress.positionAt(next.step)(같은 phase 안 이동 · motion STEP_RUNNING), 없으면 PhaseCursorAdvancer.advanceOrComplete.
  • E3-1 의 행 1(APPLIED) · 행 3(NO_TARGET)이 advanceOrComplete 대신 이것을 부른다 — BIOS 목표가 없어도 BMC 표준은 적용한다.
  • 워커 하나가 두 step 을 sweep 한다. BiosSettingWorker → FirmwareSettingWorker, BiosSettingCycle → FirmwareSettingCycle 로 개명한다(둘 다 이 브랜치 안의 미병합 코드다 — 이름이 축을 하나만 가리키면 거짓이 된다). 진리표는 하나(아래 v2)이고, SettingContext 에 axis()(커서 step 에서 파생) · bmcTarget() 을 더한다.
BIOS_SETTING ──afterAxis(BIOS)──▶ BMC_SETTING ──afterAxis(BMC)──▶ advanceOrComplete (전진 / 종단)

탈락 대안 — step 별로 워커 · 사이클 · registry 를 따로 두고 맵으로 라우팅한다. 워커 껍데기가 셋째로 복붙되고(flash · bios · bmc) 행 판정이 두 표로 갈라진다. E2-2 가 두 축을 한 진리표로 다룬 선례를 따른다.

D-3. 항목 = BmcSettingItem enum, 상수별 메서드

DATE_TIME(1) · COLD_REDUNDANT(2) · FAN_PROFILE(3) · NETWORK_BOND(4). 상수가 드는 것은 넷이다 — 순서, write(session, target, now)(바디 조립 + 요청), verify(session, target)(readback 대조), disruptive()(Bond 만 true — 마지막에 두고 재접속을 기다린다). 소비처(행 6)는 values() 를 순회할 뿐 항목 이름으로 분기하지 않는다(E2-2 의 FirmwareAxis 와 같은 결이다).

Notion 이 적어 둔 "프로세스 등록 · 재생 모델" 은 이 enum 이 코드로 고정한 형태다. 그 모델이 안고 있던 쟁점 둘은 이렇게 풀린다 — ① 자격증명은 항목에 저장되지 않고 실행 시 BmcCredentials 로 주입된다 ② 펌웨어 갱신으로 계약이 깨지면 readback 이 항목 이름과 함께 실패로 드러낸다. 관리자가 URL · 바디를 직접 등록하는 DB 등록형은 항목이 늘거나 보드별 편차가 생기는 시점의 MA6 후보다.

D-4. 웹 API 클라이언트 = global/bmcweb/ 신설, 폴백은 공통 상위 예외로 공유

  • AmiWebClient(빈) — login(bmcIp, credentials) → AmiWebSession(CSRF 토큰 · 쿠키 · 발급 시각), get/put/post(session, path, body) → JsonNode, logout(session)(best-effort). 헤더 3종을 부착한다.
  • 응답 판독 — HTTP 가 200 이 아니면 PROTOCOL / 바디에 cc 가 있으면 7 일 때 AUTH, 그 밖은 PROTOCOL / error + code 면 DATA(code) / 그 밖은 성공.
  • RestClient 는 redfishRestClient 빈을 재사용한다(같은 BMC · 같은 자가서명 완화 — 이름은 유래를 남긴다).
  • AmiWebRequestException(kind AUTH · DATA · PROTOCOL · CONNECT, message, code) — 내부 전용이다(advice 미매핑 · 컨트롤러까지 새지 않음, RedfishRequestException 과 같은 자리).

자격증명 폴백 공유 — BmcCredentialsFallback.attempt 는 지금 RedfishRequestException 을 잡아 AUTH_FAILED 일 때만 다음 후보로 간다. 두 클라이언트가 이 사다리를 공유하도록 global/redfish/BmcRequestException(추상 상위 · boolean authFailure())를 두고 RedfishRequestException 과 AmiWebRequestException 이 상속한다. 폴백은 상위를 잡고 authFailure() 로 판정하므로 분기 추가가 0 이고, E1.5 쪽 코드 변경은 extends 한 줄이다.

탈락 — 이름이 거짓이 되는 길

웹 로그인 실패에도
  throw new RedfishRequestException(AUTH_FAILED)

→ Redfish 를 부른 적이 없는데
  Redfish 예외가 난다

   ├─ RedfishRequestException
   └─ AmiWebRequestException

BmcCredentialsFallback
  catch (BmcRequestException e)
    if (e.authFailure()) 다음 후보

또 하나의 탈락 대안은 폴백 루프를 클라이언트마다 복제하는 것인데, 중복 금지 원칙에 정면으로 어긋난다. E1.6 의 BmcCredentialsMemory 는 이 구조에서 그대로 수혜를 받는다 — 성공한 자격이 캐시된다.

D-5. 세션 생애 = 한 주기 한 세션, 만료는 cc:7 로만 안다

행 6 의 한 주기는 로그인 → 항목 순서대로 write + verify → 로그아웃이다. 도중에 cc:7 을 받으면 재로그인 1회 후 그 호출을 재시도한다. 이 재시도는 AmiWebClient 안에서 일어나므로 항목 코드는 세션이 끊겼다는 사실을 모른다. TTL(약 10분)에 기대지 않는 이유는 그것이 유휴 추정값이고, 시각으로 세션 수명을 예측하면 추정이 틀린 순간 조용히 실패하기 때문이다. 로그아웃 실패는 무해하므로 로그만 남긴다.

D-6. Fan Profile 부재 = 항목 SKIPPED, step 은 계속 개정 1

보드 모델명으로 classpath:bmc/fanprofile/<modelName>.json 을 찾는다. 없으면 그 항목만 SKIPPED(NO_FAN_PROFILE) 로 meta 에 적고 다음 항목으로 넘어간다. step 은 나머지 항목이 전부 반영되면 SUCCEEDED 이고, detail 에 무엇을 건너뛰었는지 명시한다.

탈락 대안은 FAILED — 표준이 정의되지 않은 보드는 위반이 아니라 미정의이고, 카탈로그 7 보드 중 프로파일이 확보된 것은 4 뿐이라 나머지가 전부 눕는다. 운영자 인지는 원장 detail 과 WARN 로그가 맡는다.

자원 배치는 저장소 classpath 로 한다(git 추적 · 테스트가 4 파일 파싱을 검증 · 보드 추가 = 커밋). redfish_materials 식의 외부 디렉토리를 쓰지 않는 이유는 이 파일이 실행 중 생성되는 산출물이 아니라 표준 데이터이기 때문이다 — SSOT 를 저장소에 두는 편이 맞다. 운영자가 교체하고 싶다는 요구가 생기면 그때 외부 override 를 연다(미리 분리 금지).

확정 개정 1 — CP1 승인으로 항목 SKIPPED 안이 확정됐다. 프로파일이 없는 보드는 실패로 세우지 않고 그 항목만 건너뛰며, step 은 나머지 항목으로 계속한다.

D-7. 신원 확인 = 착수 직전 · 재접속 readback 직전 (E3-1 D-6 · E2-2 D-11 과 동일)

BmcIdentityProbe(Redfish Chassis 의 보드 시리얼)를 웹 세션을 열기 전에 지난다. MISMATCHED 면 세션도 열지 않는다 — 남의 장비에 로그인 시도조차 남기지 않기 위해서다. UNREACHABLE 은 시한 안에서 대기하고, 주소 재발견은 Probe 가 한다. Bond 뒤의 재접속 readback(행 1b)도 같은 순서를 지난다.

D-8. Bond = 마지막 · 즉시 readback 시도 · 실패면 bondAt 기록 후 다음 주기

Bond 쓰기가 200 을 받으면 곧바로 GET 을 시도한다(HAR 실측에서 단절이 관찰되지 않았기 때문이다). 연결이 실패하면 원장 meta 에 bondAt 을 적고 행을 RUNNING 으로 남긴다. 그러면 진리표의 행 1b 가 매 주기 신원 → 재로그인 → GET 을 다시 하고, returnLimit(20분)을 넘기면 BMC_UNREACHABLE 로 닫는다.

시한은 E2 의 복귀 시한을 그대로 재사용한다 — 별도 키를 만들지 않는다. 값이 둘로 갈라지면 어느 쪽이 진짜인지 모르게 되고, 지금은 두 상황("재부팅 후 게스트가 안 돌아온다" 와 "Bond 뒤 BMC 가 안 돌아온다")의 허용 대기가 다를 이유가 없다. 주소가 바뀌는 경우는 Probe 의 재발견이 받는다(실측상 바뀌지 않는다).

통합 테스트는 규율 대상이 없다 — 신규 엔드포인트가 0 이라 HTTP 계층에서 검증할 사용자 액션이 생기지 않는다. 대신 그 자리를 CP5 의 하네스 검증(§8)이 맡는다. SettingLedger 의 close 가 items 를 덮지 않는지 확인하는 항목은 E2-2 의 F-1(원장 close 가 meta 를 덮은 결함)에서 배운 것이다 — 열림 시점에 적은 사실에 기대는 판정은 닫힌 뒤에도 남는지 반드시 확인한다.

§7. 예외 계층
예외자리구분
BmcRequestExceptionglobal/redfish/ — 추상 상위 · boolean authFailure()신규 내부
AmiWebRequestExceptionglobal/bmcweb/ — kind AUTH · DATA · PROTOCOL · CONNECT신규 내부
RedfishRequestException상위를 extends 하도록 한 줄 수정수정

신규 공개 예외는 0 이다. 두 신규 예외 모두 advice 에 매핑하지 않으며 컨트롤러까지 새지 않는다 — 워커가 잡아 원장 사유로 번역하는 것이 종착점이다. 그래도 .claude/domain-conventions/new-exception.md 관문은 CP2 착수 시 연다. 규약을 몰라서가 아니라 빠뜨려서 사고가 났기 때문에 두는 관문이라, 내부 예외라는 이유로 건너뛰지 않는다.

§9. 위험 · 미해결
#미해결지금 어떻게 다루는가
①Cold Redundant · Bond 표준값 미확정 → CP1 승인으로 확정Cold Redundant 0 · master_psu 0 · Bond 설정값 보드 공통 개정 1
②MS03-CE0 · MS04-CE0 프로파일 실기 전송 미검증구조는 MS74-HB0 과 동일하고 바이트 대조를 마쳤다 · 실기는 CP7
③Bond 정식 왕복 미실측 — 단절 · 주소 변경 가능성행 1b 가 재접속을 거두고 주소 변경은 Probe 의 재발견이 받는다
④POST /api/settings/settingsItem(UI 부수 호출) 필요 여부 미상코드는 부르지 않는다 · 실기에서 readback 이 통과하면 불필요로 확정
⑤웹 세션 동시 상한 미측주기마다 로그아웃해 슬롯을 반납한다
⑥redfishRestClient 빈 이름이 두 프로토콜을 가리킨다이 슬라이스에서 개명하지 않는다 — CH 후보
⑦eth1 인터페이스명이 모든 보드에서 같은지 미확인 개정 1재실측 항목 · T3 적립. 지금은 bond.ifc 공통 기본값 하나로 두고, 편차가 드러나면 보드별 키로 승격한다(D-11)
