이 문서의 성격 — plan 은 확정 계약이 아니라 제안-수정-정합의 매개다. 결정 DEC-A ~ DEC-G(§8) 는 채택안 + 비채택 대안 + 탈락 사유를 담은 확정 제안이고, 잔여 4건(§8 후반) 은 후속 이월이다. 이 슬라이스는 형제가 아니라 U3-2 의 나머지 반쪽 — 완료된 U3-2-a(재할당 · reaper) 위에 선다. 승인하면 얼어붙는 계약이 아니라 미리보기로 체험시키는 검토 매개로 읽어달라.
개정 이력 — 개정 1 (2026-08-07 KST · DEC-G)
  • 무엇을 바꾸는가 — 정의서에 활성/비활성(isEnabled) · 사용 중단 권고(isDeprecated) 축을 추가한다. 부모 관련 값(own/effective 분리 · parentLifecycle cascade)은 도입하지 않는다 — 정의서는 부모 없는 루트라 재계산할 effective 가 없고 운영자 의도가 곧 실효 상태다. DEC-A(LifecycleEntity 미상속)의 "상태축 없음" 전제만 부분 개정되고 미상속 자체는 유지된다. 채택안 · 비채택 대안 4 건 · 탈락 사유는 §8 DEC-G 에 있다.
  • 왜 지금인가 — CP6 보고를 마치고 CP7 사용자 확인을 기다리던 중, 사용자가 "세팅 정의서에도 isEnabled · isDeprecated 가 있어야 한다고 본다. 다만 부모 관련 값은 불요" 라는 방향을 제시해 나온 scope 개정이다.
  • 승인 전 선행 반영 사실 — 이 개정분은 승인 전에 워킹트리에 선행 반영됐다(세션이 설계 방향 제시를 확정 지시로 오독한 체크포인트 규약 위반). 현재 전량 미커밋이며, 이 plan 개정본이 승인 판단의 근거다 — 승인 시 검증 재개 · 기각 시 선별 롤백.
§0. U3-2-b 의 위치 · 단일 슬라이스 근거 · setting↔assignment 순환 회피(Service Provider Interface 역전)

U3-2 는 원래 세 관심사를 예고했다 — ① 재할당 이력 ② 원본 정의서 삭제 lifecycle ③ 지연 purge reaper. U3-2-a 가 ①·③(재할당 + 미소비 supersede 행 reaper, provisioning.assignment 도메인 내부의 correctness 축) 을 마쳤다. U3-2-b 는 남은 ② — SettingDefinition 에 삭제 lifecycle 을 도입하고, 정의서 삭제 시 "이 정의서를 참조하는 활성 할당 N개" 를 경고한다.

왜 더 쪼개지 않고 단일 슬라이스인가

U3-2-b 가 담는 것은 한 도메인(provisioning.setting) 의 lifecycle 하나다 — soft-delete(논리 삭제) · restore(복원) · purge(영구 삭제) · 활성 전용 유일성 · includeDeleted 목록. 이 다섯은 모두 is_deleted 술어와 정의서 이름 유일성을 공유해 함께 가야 반쪽이 안 된다(soft-delete 만 있고 복원 없음 / 목록 필터만 있고 삭제 없음 은 무의미). 범위는 management 의 os · board lifecycle 슬라이스 하나와 동급이다.

브랜치 — feat/U3-2-b_definition-deletion(U3-2-a 커밋 포함, ES-1 제외). U3-2-a 가 provisioning.assignment 를 손댔고 U3-2-b 는 주로 provisioning.setting 을 손대므로 파일 충돌 표면이 작다.

순환 회피가 CP1 의 핵심 판단이다

assignment → setting 의존은 이미 존재한다(AssignmentCommandService 가 SettingDefinition · SettingDefinitionRepository 를 import). setting → assignment 는 없다. 정의서 삭제 시 "할당 역참조 경고(N개)" 를 setting 도메인이 assignment 를 직접 호출해 만들면 setting ↔ assignment 순환(R7 이 제거한 종류) 이 재생성된다.

해소는 Service Provider Interface(SPI, 도메인이 구현해 끼우는 확장점) 역전이다 — 인터페이스 AssignmentUsageInspector 는 provisioning.setting 이 소유하고, 구현 AssignmentUsageInspectorImpl 은 이미 setting 에 의존하는 provisioning.assignment 가 제공한다. 이렇게 하면 컴파일 의존은 assignment → setting 한 방향만 유지된다. U3-1 의 OwnedPhasesProvider(execution.engine 인터페이스 · assignment 구현) 와 BIOS 세팅 템플릿 SettingProcessTemplateUsageChecker(biossetting 인터페이스 · setting 구현) 가 같은 형태다.

DB 전용 soft-delete 인가, LifecycleEntity 상속인가

결론은 DB 전용(플래그 컬럼 + 도메인 메서드), LifecycleEntity 미상속이다(상세 · 대안은 DEC-A). SettingDefinition 은 부모가 없고 · 디스크 파일이 없는 순수 DB 엔티티다. LifecycleEntity 를 상속하면 9 컬럼 중 대부분(trashed_path · ttl_extension_days · own/effective 이원 컬럼 등) 이 dead 이고, own/effective cascade 머신(recomputeEffective · parentLifecycle) 과 Markable 파일 메서드를 no-op 스텁해야 하는 misfit 이 된다.

개정 1 로 축 2 개가 생겨도 이 결론은 바뀌지 않는다 — 이유는 §8 DEC-A 각주와 DEC-G 비채택 ①·④ 에 있다.

§1. 현재 상태 (진단)

쉬운 말 요약

세팅 정의서(SettingDefinition) 는 지금 만들고 고치는 것만 된다 — 지우는 기능이 아예 없다. 클래스 주석에도 "상태 개념이 없다 … 삭제 · 참조 차단은 U3 에서 도입" 이라고 미리 적혀 있다. 목록은 전체 건을 그대로 보여줘 걸러낼 방법도 없다.

한편 정의서를 서버에 할당하면 그 시점의 값이 스냅샷으로 복사되고(소프트 참조), 할당은 정의서를 외래 키(Foreign Key, 이하 FK) 로 붙들지 않는다. 그래서 정의서를 지워도 이미 걸린 할당은 멀쩡히 남는다. 즉 "이 정의서를 지우면 할당이 깨진다" 같은 무결성 근거가 없어서, 삭제를 막을 이유가 없다. 이번 슬라이스는 그 정의서에 지우기(논리 삭제 → 복원 → 영구 삭제) lifecycle 을 붙이고, 지울 때 "이 정의서를 N개 게스트가 쓰고 있다" 는 안내만 곁들인다(막지는 않는다).

개정 1 에서 더한 이야기 — 지우는 것 말고도 운영자가 쓸 수 있어야 하는 표현이 둘 더 있다. 하나는 "당분간 새로 고르지 못하게 막아 두기"(비활성), 다른 하나는 "골라도 되지만 이제 권하지 않는다고 알려 주기"(사용 중단 권고) 다. 지금은 이 둘이 없어서 지우거나 그냥 두거나 둘 중 하나뿐이다. 그래서 정의서에 이 두 표시를 붙이고, 서버에 새로 붙일 정의서를 고르는 화면이 그 표시를 그대로 반영하게 한다. 이미 서버에 붙어 있는 것은 어느 표시를 켜도 바뀌지 않는다 — 붙는 순간 값이 복사돼 원본과 따로 살기 때문이다.

할당 시 정의서 로드 안전망 공백AssignmentCommandService 의 assign · reassign 이 정의서를 findById 로 로드한다 — 삭제 여부를 보지 않는다. U3-2-b 본체가 할당 화면 드롭다운에서 soft-deleted 정의서를 걸러내도, direct POST 로는 삭제된 정의서가 그대로 할당된다. 화면 차단만 있고 서버 가드가 없는 상태다.
이 개정에서 발견한 기존 안전망 공백 — 프로젝트 불가침 원칙은 "UX 모순은 UI 1차 차단, 서버 가드는 안전망으로 유지" 이고 두 조건은 단일 SSOT 를 공유해야 한다. 현재 할당 경로는 그 중 UI 차단만 있고 서버 가드가 비어 있어, direct POST · stale 화면 · 동시성 상황에서 삭제된 정의서가 할당된다. 개정 1 은 새 축(비활성)을 넣는 김에 이 공백도 같은 판정 메서드(assignBlockReason())로 함께 막는다 — 삭제됨은 findByIdAndIsDeletedFalse 로 404, 비활성은 DefinitionNotAssignableException 으로 409.
핵심 진단 — 정의서에는 삭제 개념이 아예 없고(create · update 만), 정의서 → 할당은 FK 없는 소프트 참조라 삭제를 막을 근거가 없다. 그래서 U3-2-b 는 (1) 정의서에 DB 전용 soft-delete lifecycle 을 도입하고 (2) 삭제 시 참조 할당 수를 차단이 아닌 경고로 안내한다. 선례는 둘 — biossetting(BaseTimeEntity + hard delete + 409 in-use 차단) 과 os · board(LifecycleEntity soft-delete → 휴지통 → typed-name purge + includeDeleted 목록 토글). U3-2-b 는 두 선례의 중간 형태(파일 없는 DB 엔티티의 soft-delete + typed-name purge, 마커 · 휴지통 없이) 를 택한다(DEC-A).
§2. 요구사항 (확정) + 비목표

scope — SettingDefinition DB 전용 soft-delete lifecycle + 활성/비활성 · 사용 중단 권고 축(개정 1 · DEC-G):

  1. soft-delete — is_deleted 토글로 활성 목록에서 감춘다. setting-detail 에서 수행.
  2. 삭제 시 경고 — AssignmentUsageInspector.countReferencing(definitionId) 로 "N개 게스트에 활성 할당됨 — 삭제해도 할당 스냅샷은 유지됩니다" 를 정보성 안내로 표시(차단 아님).
  3. restore — soft-deleted → 복원. 복원 시 활성 name 충돌 가드.
  4. purge — 영구 삭제 = hard delete, typed-name 확인. 자식 setting_process 는 orphanRemoval / CASCADE 로 동반 삭제.
  5. 목록 — 활성 전용 기본 + includeDeleted 토글로 삭제분 표시(복원 · purge 액션).
  6. 활성 전용 name 유일성 — create · update · restore.
  7. 활성/비활성 토글 · 사용 중단 권고 표시 · 해제 개정 1 — 운영자 액션 3 개(toggleEnabled · deprecate · undeprecate). 비활성은 신규 할당만 차단하고, 사용 중단 권고는 차단하지 않고 경고만 표시한다. 두 축은 서로 · 삭제 축과 독립이다.
  8. 신규 할당 판정 SSOT(assignBlockReason()) 와 서버 가드 개정 1 — 할당 화면 드롭다운 필터 · 배지(뷰)와 AssignmentCommandService 의 assign · reassign 거절(서버)이 같은 근거 한 메서드를 호출한다. 비활성 정의서 할당 시도는 DefinitionNotAssignableException(409) 이고 메시지는 UI 안내와 같은 문자열이다.
  9. 기존 안전망 공백 수정 개정 1 — 삭제된 정의서의 direct POST 할당을 차단한다(findByIdAndIsDeletedFalse → SettingNotFoundException 404). §1 에서 발견한 공백이다.
비 목표 (순수 DB 엔티티라 불요 / 다음 슬라이스로):
  • 파일 / 마커 / 휴지통(.soft-deleted/) 이동 · ResourceType / PurgeLog 편입 — SettingDefinition 은 디스크 파일이 없는 순수 DB 엔티티라 불요(DEC-A).
  • own/effective 이원축 · 부모 parentLifecycle cascade — 정의서는 부모 없는 루트라 재계산할 effective 가 없고 운영자 의도가 곧 실효 상태다. (단순 boolean 축 2 개 isEnabled · isDeprecated 는 이 개정으로 도입 — DEC-G)
  • deprecatedAt 시각 컬럼 미도입 개정 1 — 최소 원칙. 최종 변경 시점은 BaseTimeEntity.updatedAt 으로 추적하고, 언제 누가 권고했는지에 대한 감사 요구가 실제로 생기면 후속에서 컬럼을 더한다.
  • 재할당 · reaper — U3-2-a 에서 완료.
  • 서버 목록 cross-server 가시화 — U3-3.
  • 정의서 비활성 · 사용 중단의 목록 다중 선택 일괄 조작 — 현재는 상세 화면 단건. 후속(§8 잔여 4).

신규 할당 차단 판정 SSOT — assignBlockReason() 개정 1

public String assignBlockReason() {          // null = 할당 가능
    if (isDeleted)  return "삭제된 정의서는 할당할 수 없습니다";
    if (!isEnabled) return "비활성화된 정의서는 신규 할당이 차단됩니다(활성화 후 재시도)";
    return null;                              // deprecated 는 차단 사유가 아니다 — 경고만
}
UI 차단 조건과 서버 가드 조건의 단일 SSOT — 서버 가드(AssignmentCommandService.loadAssignableDefinition) 와 뷰(할당 드롭다운 옵션 필터 · 배지) 가 이 한 메서드를 함께 호출한다. 반환 문자열이 그대로 DefinitionNotAssignableException 의 메시지이자 화면 안내 문구이므로, "화면이 막는 이유" 와 "서버가 거절하는 이유" 가 문자열 수준까지 같다. 두 곳에 조건을 복붙하면 drift 가 나는데, 이 방식은 구조적으로 그것이 불가능하다. SettingAssignment.reassignBlockReason() 선례와 동형이다.

직교 축 병기 개정 1

위 다이어그램은 삭제 축 하나만 그린다. 개정 1 의 두 축은 삭제 축의 상태가 아니라 그와 나란히 있는 별개 축이라, 상태 기계 하나에 억지로 밀어 넣으면 상태 수가 3 × 2 × 2 로 곱해져 오히려 관계를 감춘다. 그래서 mermaid 는 삭제 축 전용으로 두고, 세 축의 직교 관계는 아래 표기로 병기한다.

삭제 축 : ACTIVE ──softDelete──▶ SOFT_DELETED ──purge(typed-name)──▶ (제거) ◀──restore──── 활성 축 : enabled ◀──toggleEnabled──▶ disabled (삭제 축과 독립) 권고 축 : normal ◀──deprecate/undeprecate──▶ deprecated (두 축과 독립) ※ 세 축은 서로 재계산하지 않는다(부모 없는 루트 — own/effective 분리 불요). ※ 어느 축을 어떻게 조합해도 기존 할당 스냅샷은 불변이다(소프트 참조).

// SettingDefinition — U3-2-b 신규 (LifecycleEntity 미상속, 플래그 3개 자체 보유)
public void softDelete() {   // 멱등 — is_deleted = true
    this.isDeleted = true;
}
public void restore() {      // 멱등 — is_deleted = false
    this.isDeleted = false;  // 활성 name 충돌 가드는 repository 조회가 필요해 Service 소관
}

// ── 개정 1 (DEC-G) — 부모가 없으므로 recomputeEffective · parentLifecycle 없이 자기 값만 바꾼다 ──
public void toggleEnabled() {    // 활성 ↔ 비활성 반전. 운영자 의도가 곧 실효 상태
    this.isEnabled = !this.isEnabled;
}
public void deprecate() {        // 멱등 — 상태 전이가 아니라 표시 플래그
    this.isDeprecated = true;
}
public void undeprecate() {      // 멱등
    this.isDeprecated = false;
}
// assignBlockReason() 은 위 "신규 할당 차단 판정 SSOT" 참고 — 뷰 필터와 서버 가드가 공유
가드는 Service 에 둔다 — 복원 시 활성 name 충돌과 purge 시 typed-name 검증은 repository 조회 또는 입력값 비교가 필요해 엔티티가 아니라 JpaSettingCommandService 에 둔다. restore: if (existsByNameAndIsDeletedFalse(name)) throw new RestoreNameConflictException(...)(409). purge: if (!entity.getName().equals(typedName)) throw new TypedNameMismatchException(...)(400) → repository.delete(entity). TypedNameGuard.verify 는 Markable(파일 자원) 전용이라 파일 없는 정의서에는 쓰지 않고, name.equals(typedName) 3 줄로 직접 검증한다.

개정 1 각주 DEC-G 로 축 2 개가 실제로 생겨 "상태축 없음" 이라는 근거 하나는 더 이상 성립하지 않는다. 그러나 결론(미상속)은 유지된다 — 나머지 근거(부모 없음 · 파일 없음)가 그대로이고, 새 축은 own/effective 이원 컬럼도 parentLifecycle 재계산도 요구하지 않는 단순 boolean 2 개이기 때문이다. 상세는 DEC-G 비채택 ①·④.		 ① LifecycleEntity 상속(os · board 선례 일관성) — os · board 는 enabled · deprecated 축과 파일 자식을 실제로 가져 그 프레임워크가 맞지만, SettingDefinition 은 그 축이 전무해 dead weight + 스텁만 늘어난다. 일관성보다 misfit 비용이 크다. ② hard-delete only(biossetting 선례) — 되돌릴 수 없고 이름이 즉시 해방된다. "lifecycle"(복원 · 2 단계 삭제) 요구에 미달. soft-delete + purge 가 프로젝트 휴지통 기조와 정합.
DEC-B 치명 활성 전용 name 유일성 — UNIQUE(name) 제거 → existsByNameAndIsDeletedFalse. 현 uk_setting_definition_name UNIQUE(name) 은 soft-delete 행이 이름을 영구 점유해 재사용을 차단한다. os · board 선례대로 DB UNIQUE 제거 + 서비스 가드로 활성 전용 유일성(create · update). 추가로 restore 시 name 충돌 가드: soft-deleted(name=X) 를 복원하려는데 그새 활성 정의서가 name=X 를 점유했으면 복원 거절(409, "같은 이름의 활성 정의서가 있어 복원 불가 — 이름 변경 필요"). ① UNIQUE(name) 유지 — soft-delete 행이 이름을 영구 점유(치명). ② MariaDB generated-column 부분 유니크(활성일 때만 name 을 파생 컬럼에 UNIQUE, U3-2-a DA2 와 동형) — DB 가 강제해 더 강하나 os · board 선례(서비스 가드) 와 갈리고 실기(T3) 검증 항목이 는다. admin 이 생성하므로 동시 충돌 위험이 낮아 서비스 가드로 충분(강제가 필요해지면 후속 승격).
DEC-C 치명 삭제는 차단이 아니라 경고(소프트 참조 생존). 정의서를 N개 게스트가 활성 할당으로 참조 중이어도 삭제를 허용한다 — 소프트 참조라 삭제해도 스냅샷이 생존한다(DEC-18). 삭제 확인 모달에 AssignmentUsageInspector.countReferencing 로 "N개 게스트에 활성 할당됨 — 삭제해도 할당 스냅샷은 유지됩니다" 를 정보성 경고로만 표시한다. in-use 차단(BIOS 세팅 템플릿 선례, 409) — BIOS 템플릿은 실 FK / 조인이라 차단이 무결성 근거를 갖지만, 정의서 → 할당은 FK 없는 소프트 참조라 막을 무결성 근거가 없다. 차단은 오히려 "삭제 불가" 라는 오해를 낳는다. 경고가 옳다.
DEC-D 중대 AssignmentUsageInspector Service Provider Interface — 인터페이스는 provisioning.setting 소유, 구현은 provisioning.assignment 제공. 인터페이스: long countReferencing(Long definitionId)(경고 문구용) + boolean isReferenced(Long definitionId)(저비용 분기). 구현 AssignmentUsageInspectorImpl: SettingAssignmentRepository 파생 쿼리 countBySourceDefinitionRef_DefinitionIdAndSupersededAtIsNull(활성 할당만 카운트). 순환 없음 — assignment → setting 이 이미 존재. OwnedPhasesProvider · BIOS SettingProcessTemplateUsageChecker 와 동형. setting 이 SettingAssignmentRepository 를 직접 주입 — setting → assignment 순환(R7 이 제거한 종류) 을 재생성한다. 금지.
DEC-E 중대 purge = typed-name + hard delete. soft-deleted 정의서만 purge 대상(활성 정의서는 직접 purge 불가 — soft-delete 선행). typed-name(정의서명 재입력) 확인 → name.equals(typedName) 불일치 시 TypedNameMismatchException(400) → settingDefinitionRepository.delete(entity)(자식 setting_process 동반 삭제). 파일 삭제 단계 없음. purge 시에도 경고(N개 할당) 를 재고지(스냅샷은 여전히 생존). soft-delete 없이 즉시 hard-delete — 되돌릴 수 없다. 2 단계(soft-delete → purge) 가 안전하다.

DEC-G 치명 개정 1 정의서에 isEnabled · isDeprecated 두 boolean 축 추가(부모 관련 값 미도입). 의미론은 자원 도메인 선례와 동형이다 — disabled = 신규 할당만 차단(기존 할당 스냅샷 무영향), deprecated = 할당 허용 + "사용 중단 권고" 경고 표시. 판정은 SettingDefinition.assignBlockReason() SSOT 하나를 화면(할당 드롭다운 필터 · 배지)과 서버 가드(AssignmentCommandService 의 assign · reassign)가 공유한다 — 반환 문자열이 곧 UI 안내이자 예외 메시지라 두 곳이 갈라질 수 없다. 엔드포인트는 os lifecycle 규약 동형(POST /{id}/toggle · /deprecate · /undeprecate · SSR 302). 이 개정에서 기존 안전망 공백도 함께 차단한다 — assign · reassign 의 정의서 로드를 findById 에서 findByIdAndIsDeletedFalse 로 바꿔 삭제된 정의서의 direct POST 할당을 404 로 끊는다(§1 진단). 왜: 운영자가 "이제 쓰지 마라" 를 표현할 수단이 삭제 하나뿐이면, 아직 참조 가치가 있는 정의서를 지우거나 방치하는 양자택일이 된다. 두 축은 그 사이의 중간 강도(권고 → 차단)를 준다. ① own/effective 이원 컬럼 + parentLifecycle cascade(LifecycleEntity 관례) — 정의서는 부모가 없어 재계산할 effective 가 없다. 운영자 의도가 곧 실효 상태이므로 컬럼이 2 배로 늘고 재계산 로직이 붙는 것은 순손실이다.
② deprecatedAt 시각 컬럼 — LifecycleEntity 는 보유하나 최소 원칙상 미도입. BaseTimeEntity.updatedAt 으로 최종 변경 시점을 추적하고, 언제 누가 권고했는지에 대한 감사 요구가 실제로 생기면 후속에서 추가한다("갈라지는 시점에 분리" 원칙).
③ deprecated 도 할당 차단 — 자원 도메인 선례(선택지에 노출하되 경고) 와 어긋나고 "권고" 를 "금지" 로 격상시킨다. 차단이 필요하면 disabled 축이 이미 있다 — 두 축을 하나로 뭉개면 표현력이 준다.
④ 이 기회에 LifecycleEntity 상속으로 전환 — 축이 3 개가 돼도 마커 · 휴지통 · 파일 경로 · cascade 는 여전히 무관해 dead weight 다. DEC-A 결론 유지.
