§1. 배경 — 실기 통합 테스트에서 확인된 문제

2026-08-24 실 베어메탈(MS74-HB0)을 대상으로 한 통합 테스트에서 사용자 결정(decisions.rtf) 두 가지가 확인됐다. 이 문서는 그중 첫째만 다룬다.

비 목표 :
  • decisions.rtf 의 둘째 결정은 이 문서의 범위 밖이다 — 별도 슬라이스로 다룬다.

현행 동작

게스트가 PXE 로 등록되어도 운영자가 '프로비저닝 개시' 버튼을 눌러야만 진단 리눅스가 내려간다. BootScriptDispatcher 5행이 !progress.isStarted() 조건일 때 30초 대기 폴링 스크립트(waitingForStart)만 반환하기 때문이다. 즉 게스트는 등록된 순간부터 운영자가 화면에서 개시 버튼을 누르기 전까지 아무 하드웨어 정보도 수집하지 못한 채 대기만 반복한다.

요구

하드웨어 정보 수집까지는 개시 없이 자동으로 진행하고, 그 다음 단계에서만 대기하도록 바꾼다. 여기에는 화면 표시의 정합 문제도 함께 걸려 있다 — 진행 배지는 게스트의 phase 커서를 그대로 노출하는데, 커서는 등록과 동시에 DIAGNOSTIC_BOOTING 으로 놓인다. 그런데 실제로는 개시 전까지 아무 동작도 일어나지 않으므로, 배지가 가리키는 '진단 리눅스' 라는 문구와 게스트가 실제로 대기만 하고 있는 사실이 어긋난다. 자동 진행이 도입되면 커서가 가리키는 phase 에서 실제로 부팅과 수집이 진행되므로, 이 표시가 사실과 일치하게 되어 함께 해소된다.

부수 발견 (같은 날 실측)

무할당 게스트가 진단을 완주하면 markCompleted 로 종단되는데, 종단을 해제하는 경로가 없다(재시도는 failed 상태 전용이다). 즉 종단은 원래 회복 불가능한 최종 상태로 설계돼 있는데, 진단이 성공적으로 끝났다는 사실 하나만으로 게스트가 이후 어떤 정의서를 할당받아도 더 이상 펌웨어 단계로 넘어갈 수 없는 상태에 고정되는 것이다. 실기 게스트 "안양시 IPCC (상)" 이 실제로 이 상태에 놓였다.
§2. 설계 대안 비교 (3안, 채택 = C′)

진단 자동 진행을 들여오는 방법으로 세 가지 설계 대안을 검토했다. 세 안 모두 "커서가 언제 다음 phase 로 전진하고 언제 종단으로 판정되는가" 를 다르게 다루며, 채택안은 C′안이다.

A안 — 완주 판정 지연 + 커서 고정

개시 시점에 완주 판정을 미루되 커서는 진단에 고정한다.

기각 사유 — 개시 트랜잭션이 엔진 협력자를 알아야 하고, "완주했는데 커서가 진단에 머무는" 비사실 상태가 생긴다. 커서를 진단에 묶어 두면, 실제로는 수집이 끝나 있어도 화면과 다른 컴포넌트가 여전히 진단 진행 중으로 읽게 된다.

B안 — 등록 시 자동 개시

startedAt = 등록 시각으로 즉시 기록하고, 진단 후 별도 승인 신호를 신설한다.

기각 사유 — startedAt 이 등록 시각과 같아져 신호로서 죽고, DEC-26(운영자 명시 개시)의 의미가 소멸하며 새 신호 컬럼이 필요해진다. 즉 "개시" 라는 개념 자체가 등록과 분리되지 않아, 운영자가 명시적으로 프로비저닝을 승인한다는 기존 결정의 취지가 사라진다.

C′안 (채택) — 완주 판정만 미룬다

진단 실행 창은 미개시에 개방하되, 완주 판정(전진 · 종단)만 개시 뒤로 미룬다. 커서 이동 자체는 게스트가 실제로 겪는 진행을 그대로 따라가고, 다음 phase 로의 전진이나 종단 판정만 개시 시점까지 보류한다.

C′안 상세

  1. 미개시 게스트도 /boot 에서 진단 스크립트를 받아 부팅 · 수집 · 적재까지 자동 진행한다. 커서는 게스트의 사실대로 움직이되, 진단 phase 안에서만 허용한다(도메인 가드). 즉 미개시 게스트가 진단 phase 를 벗어나는 이동은 여전히 막힌다.
  2. 수집 close 소비(DiagnoseLinuxExecutor.onStepClosed)에서 미개시면 커서를 INFORMATION_PERSISTING 에 두고 완주 판정을 유보한다 — 이 상태가 "수집 완료 · 대기" 다. 게스트는 진단 리눅스 안에서 30초 checkin WAIT 루프로 상주 대기한다(directiveFor: 수집 완료 + 진단 커서 → WAIT, 기존 로직 그대로 유지). 새 상태를 판정하기 위해 directiveFor 자체를 바꿀 필요가 없다는 뜻이다.
  3. 개시 버튼을 누르면 startedAt 을 기록하고, 커서가 INFORMATION_PERSISTING 이면 유보된 완주 판정(PhaseCursorAdvancer.advanceOrComplete)을 소급 집행한다. 할당이 있으면 다음 phase 로 pre-position 하여 다음 checkin 이 REBOOT 지시를 받아 /boot 를 거쳐 펌웨어로 진행하고, 무할당이면 그 시점에 종단한다(입고 검수 완료 — 현행 의미를 유지한다). 개시라는 하나의 동작이 "기록" 과 "유보됐던 판정의 집행" 두 가지를 함께 수행하는 셈이다.
  4. 초기 함정 차단 — 원안(무조건 전진 · 종단)이었다면 등록 직후 자동 수집이 돌아 무할당 게스트가 몇 분 안에 종단(회복 불가)됐을 것이다. 이는 자동 진행을 켜자마자 §1 의 부수 발견과 같은 함정에 새 게스트마다 반복해서 빠지는 결과였을 것이다. 완주 판정을 개시 뒤로 미루면 미개시 게스트는 절대 종단되지 않으므로, 수집 완료 후 언제든 할당 → 개시가 가능하다.
§3. 변경 지점 (파일별)

§2 의 C′안을 실제 코드에 대응시키면 아래 10곳이 바뀐다. 앞의 세 가지(1~3)는 ProvisioningProgress 자체의 가드를 손보는 것이고, 4~7 은 그 가드가 바뀐 결과로 호출부의 분기를 정리하는 것이며, 8~10 은 부수적으로 필요한 예외 문구 · DDL · 화면 문구다.

상세

  1. ProvisioningProgress.positionAt — 미개시 가드를 "미개시 && 커서 phase ≠ DIAGNOSE_LINUX → 예외" 로 완화한다. 미개시 진단 창의 커서 이동을 허용한다.
  2. ProvisioningProgress.markCompleted — !isStarted() 면 예외를 추가한다(미개시 종단은 표현 불가 상태로 명문화).
  3. ProvisioningProgress.isStartableWith — !isFailed() 를 보강한다. 미개시 진단 창에서 게스트가 FAILED 를 보고하면 "미개시 실패" 상태가 새로 생기는데, 그 게스트에 개시 버튼이 뜨면 안 된다(재시도 버튼이 옳은 경로). advanceToEntry 의 !isStarted() 가드는 유지한다(신설계에서 미개시 advanceToEntry 호출은 없음 — invariant 로 남긴다).
  4. BootScriptDispatcher — 5행(미개시 → waitingForStart)을 제거한다. 미개시 커서는 도메인 가드에 의해 항상 진단 phase 이므로 7행 위임이 곧 자동 진행이다. IpxeScripts.waitingForStart 도 삭제한다(도달 불가 죽은 코드 — R11 CP5 의 잔존 코드 교훈).
  5. AgentReportService — checkin/openStep 의 requireProvisioning 과 closeStep 인라인 게이트에 "미개시 + 진단 phase 커서" 수리 창을 추가한다(작은 공유 판정 메서드로 추출해 두 곳이 같은 단일 진실 출처를 쓰게 한다).
  6. DiagnoseLinuxExecutor.onStepClosed — advanceOrComplete 호출을 progress.isStarted() 조건부로 바꾼다. 미개시면 유보 로그를 남긴다.
  7. GuestServerCommandService.startProvisioning — start() 후 커서가 INFORMATION_PERSISTING 이면 PhaseCursorAdvancer.advanceOrComplete 를 소급 집행한다(협력자 주입 추가 — execution 영역 내부 단방향 의존이라 순환은 없다).
  8. ProvisioningStartRejectedException — failed 사유 팩토리를 추가한다(실패 게스트가 direct POST 로 개시를 시도할 때의 정확한 메시지).
  9. DDL ddl/R13_motion_window_unstarted.sql — chk_progress_motion_window CHECK 제약을 재정의한다. 구 제약은 motion NOT NULL 이면 started_at NOT NULL 이면서 failed/completed 는 NULL 이어야 한다고 강제했다. 신 제약은 motion IS NULL OR (failed_at IS NULL AND completed_at IS NULL) 이다 — 실행 창의 정의가 "개시 후" 에서 "실패 · 종단 밖" 으로 넓어진다(미개시 진단 창 개방의 DDL 대응). 같은 파일에서 chk_progress_completed_after_start(completed_at IS NULL OR started_at IS NOT NULL)를 함께 세운다 — "미개시 종단 표현 불가" 도메인 가드(markCompleted)의 DB 이중 방어다.
  10. server-detail.html UC-3 힌트 문구 — "게스트가 연결되어 있습니다 — [프로비저닝 개시] 를 눌러야 진행됩니다" 는 자동 진행 세계에서 거짓이 된다. "하드웨어 수집은 자동으로 진행됩니다. 수집이 끝난 뒤 다음 단계는 [프로비저닝 개시] 를 눌러야 진행됩니다." 로 교체한다(국면 분기 없이 두 국면 모두 참인 문구).
§4. 무변경 확인 (왜 안 건드리는가)

§3 의 변경이 미개시 진단 창을 여는 데 집중된 만큼, "이 컴포넌트도 같이 손대야 하는 것 아닌가" 하는 질문이 자연히 따라온다. 아래 네 컴포넌트는 검토했지만 그대로 둔다 — 각각 왜 그런지를 밝힌다.

컴포넌트무변경 사유
PhaseEntryGateisInExecutionWindow 가 미개시를 조기 반환하므로 미개시 대기 게스트에 자원 결손 사다리(HOLD · TTL 실패)가 발동하지 않는다. 결손 판정은 개시 후 phase 진입부터 시작되며, 이는 의도와 정합한다.
GuestServerStatus.derive미개시 상태는 REGISTERED 로 유지된다. 수집 중과 수집 완료 대기 모두 "등록됨" 으로 표시된다. 운영 상태 축의 세분(예: 수집 중 표시)은 이번 범위 밖이다.
PhaseCursorAdvancer · PhaseSequence전진 규칙 자체는 무변경이다. 호출 시점만 이동한다.
directiveFor무변경이다. 미개시 수집 완료는 WAIT(상주 대기)를, 개시 이후 소급 전진으로 커서가 진단을 초과하면 REBOOT 을 그대로 반환한다. 기존 판정이 신 상태를 그대로 소화한다.
§5. 신 상태 흐름 (한 장 표)

§2~§3 에서 결정한 가드 · 호출부 변경을 게스트가 실제로 거치는 국면 순서로 다시 정리하면 아래 표와 같다. startedAt 과 커서 두 값의 조합만으로 게스트가 지금 어느 국면에 있는지, 다음 checkin 에서 어떤 지시를 받는지가 정해진다.

국면startedAt커서게스트 동작
등록 직후NULLDIAGNOSTIC_BOOTING/boot → 진단 스크립트 → 부팅 · 수집 자동
수집 완료 대기NULLINFORMATION_PERSISTING진단 리눅스 상주, checkin WAIT 루프
개시 (할당 있음)기록펌웨어 진입 step 으로 소급 전진다음 checkin REBOOT → /boot → 펌웨어

표 밖 설명 — 미개시 상태에서 게스트가 FAILED 를 보고하면 "미개시 실패" 상태가 된다. 이 상태는 위 네 국면 중 어디로도 자연스럽게 이어지지 않으므로 별도로 다룬다. 화면의 재시도 버튼으로 회복한다(clearFailed → 진단 재실행). 개시 버튼은 isStartableWith 보강으로 이 상태에서 숨겨진다 — §3 의 3번 항목이 이 가드를 담당한다.

§6. 검증 계획

단위 · 통합 테스트를 다음 항목으로 갱신한다. 앞의 여섯 항목은 §3 에서 바뀐 지점 하나하나에 대응한다 — dispatch 매트릭스는 4번(BootScriptDispatcher), agent 게이트는 5번(AgentReportService), ProvisioningProgress 가드는 1 · 2 · 3번, onStepClosed 유보는 6번, startProvisioning 소급 전진은 7번, 미개시 실패 개시 거절은 3번과 8번을 함께 검증한다.

마지막 항목인 실기 검증은 이 문서의 CP 게이트가 생략된 것과 별개로, VM 재배포 후 사용자가 직접 진행하는 시나리오 ④ 통합 테스트로 흡수된다. 즉 자동화된 테스트는 빌드 green 까지를 담당하고, 실제 베어메탈에서 자동 진행 → 대기 → 개시 → 펌웨어 전이로 이어지는 전체 흐름의 최종 확인은 사용자 몫으로 남는다.

§7. 남은 일 · 한계

R13 은 §1 의 함정(무할당 게스트가 진단 완주만으로 회복 불가 상태에 빠지는 것)을 없애는 데 집중한 긴급 수정이며, 그 함정과 맞닿아 있지만 이번 범위에 넣지 않은 것들이 있다. 아래 세 가지를 남은 일 · 한계로 명시한다.

  1. 종단(completed) 게스트의 할당 재개(reopen)는 여전히 없다 — E1-3 로드맵 소관이다. R13 은 이 재개 기능 자체를 만든 것이 아니라 "미개시면 종단되지 않음" 으로 함정 진입 자체를 없앤 것이다. 즉 앞으로는 이 상태에 새로 빠지는 게스트가 없어지지만, 재개 기능이 생기는 것은 아니다.
  2. 운영 상태 배지 세분("수집 중" 등)은 미도입이다 — §4 에서 밝힌 대로 GuestServerStatus.derive 를 손대지 않았으므로 REGISTERED 로 뭉뚱그려진다. 화면에서 "자동 수집 중" 과 "수집 완료 대기" 를 구분해 보여주는 것은 필요 시 후속 슬라이스에서 다룬다.
  3. 기존 실기 게스트("안양시 IPCC (상)")는 이미 종단된 상태다 — R13 의 가드 완화는 신규 게스트의 진입을 막을 뿐 과거에 이미 종단된 게스트를 소급해서 되돌리지는 않는다. 삭제 후 재등록이 필요하다(재등록하면 PCIe 필터 신판으로 재수집되는 부수 이득이 있다).
