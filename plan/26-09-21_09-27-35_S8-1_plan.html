S8-2 의 입력으로 적어 둡니다 — 게스트 서버의 도출값 둘은 SQL 술어로 풀립니다. 현재 단계는 ProvisioningProgress.currentStep.getPhaseType(), 운영 상태는 GuestServerStatus.derive(progress, decommissionedAt)(started_at · failed_at · completed_at · decommissioned_at 의 null 조합)입니다. 이번 슬라이스에서는 건드리지 않습니다.

§2. 요구사항 (확정) + 비목표

2-1. 공통 부품 (전역)

  1. R1 조회 띠는 <form method="get"> 한 줄입니다. 검색 입력 · 라디오 칩 · 셀렉트 · 체크박스가 모두 폼 필드이고, 질의 문자열은 브라우저가 조립합니다.
  2. R2 칩 · 셀렉트 · 체크박스는 바뀌는 즉시 제출하고, 검색 입력은 Enter 또는 검색 버튼으로만 제출합니다(글자마다 요청을 보내지 않습니다).
  3. R3 제출 시 빈 값 파라미터를 제거해 URL 을 깨끗하게 둡니다(?q=&enabled= 잔존 금지). 스크립트가 없으면 빈 파라미터가 남지만 동작에는 무해합니다.
  4. R4 필터 · 검색 · 정렬 · 페이지 크기 변경은 모두 폼 제출이라 첫 페이지로 복귀합니다. 페이지 이동만 링크이고 나머지 상태를 유지합니다. 초기화는 기본 목록으로 돌아갑니다.
  5. R5 쪽 이동 줄(n-pagination)은 표가 든 판 바닥에 둡니다. 구성은 ← 이전 · 2 / 4 · 총 37건 · 다음 → · 표시 개수 [20▾] 입니다. 결과가 한 쪽이면 이동 링크는 흐린 글자입니다(현행 관례).
  6. R6 정렬 파라미터는 원시 속성명을 바인딩하지 않습니다. 정렬 항목은 화면별 enum(SortField)이 화이트리스트이고, 방향은 Spring Sort.Direction 입니다.
  7. R7 page · size 는 Spring Data Pageable 리졸버가 받습니다. 기본 20, 상한 100(spring.data.web.pageable.max-page-size=100)이고, 음수 page 나 비수치는 리졸버가 기본값으로 정정합니다.
  8. R8 빈 결과는 두 갈래로 구분합니다 — "조건에 맞는 것이 없음 + 초기화 유도" 와 "아예 없음 + 작성 유도".
  9. R9 현재 요청 URL 에서 page 만 바꾼 링크와 초기화 링크를 컨트롤러 인자(ListLinks)로 받습니다. 나머지 축은 전부 폼 필드라 링크가 필요 없습니다.
  10. R10 정렬 UI 는 조회 띠의 셀렉트 둘(항목 · 방향)입니다(CP1 확정).

정렬 항목 enum 은 각자 defaultDirection() 을 가집니다 — ID 는 ASC, NAME 은 ASC, CREATED_AT 은 DESC, MEMBER_COUNT 는 DESC 입니다. dir 파라미터가 없으면 그 항목의 기본 방향을 씁니다. 그래서 "최근 생성순" 이나 "멤버 많은 순" 처럼 사람이 먼저 기대하는 방향이 항목을 고르는 것만으로 나옵니다.

비 목표 — 아래는 이 슬라이스에서 하지 않습니다.
  • 게스트 서버 목록(보기 전환 · 최초 등록 시각 범위 · SSE 와 조회 띠의 상호작용) → S8-2 가 받습니다.
  • 자원 관리 목록 여섯(OS · 보드 · BIOS · BMC · 드라이버 · RAID 카드) → S8-3(가칭)으로 둡니다.
  • 기존 pager 둘(감사 로그 · 점검 이력)을 새 조각으로 이관 → 후속 housekeeping. 범위 밖 공통화는 사용자 명시 요청이 있을 때만 합니다.
  • include-deleted-toggle.js 를 폼 방식으로 흡수 → 자원 관리 목록이 조회 띠를 얻는 S8-3 에서 함께 합니다.
  • 검색 필드 선택 드롭다운 · 저장된 필터 · 무한 스크롤 · 열 표시 설정 — 하지 않습니다.
  • 스키마 변경 · 인덱스 추가 — 없습니다(수백 행 규모). 필요가 실측되면 별도로 다룹니다.
🎬 미리보기 — 조회 상태 · URL · Specification 시뮬레이터

이 데모는 네 가지를 한 자리에서 보여줍니다. ① 조회 띠 · 표 · 쪽 이동 줄의 디자인 골격, ② 정렬 셀렉트 둘(항목 · 방향)의 거동, ③ 화면 상태가 URL 과 Specification 술어로 어떻게 번역되는지, ④ 같은 부품으로 세팅 정의서와 서버 그룹 두 화면이 그려진다는 것입니다.

맨 아래 두 줄이 판정 캡션입니다. URL 줄은 R3 · R4 규칙대로 조립한 경로이고(빈 값과 기본값은 쓰지 않습니다), Specification 줄은 지금 살아 있는 술어의 합성과 PageRequest 입니다. 축이 "전체" 면 술어가 빠지고, 삭제 포함이 꺼져 있으면 deletedIs(false) 가 항상 붙습니다. 포함 단계를 여럿 고르면 고른 수만큼 hasProcessType(…) 이 AND 로 이어집니다. 표를 거르고 정렬하는 것도 이 술어 목록 하나이므로, 캡션과 표가 어긋날 수 없습니다.

한 가지 더 눈여겨보실 점이 있습니다. 칩 · 셀렉트 · 체크박스는 폼을 제출하므로 입력칸에 쳐 둔 검색어를 함께 싣고, 쪽 이동만 링크라서 아직 제출하지 않은 검색어를 싣지 않습니다. 검색어를 입력만 해 두고 칩과 쪽 이동을 각각 눌러 보시면 그 차이가 그대로 드러납니다.

화면 :

BEFORE — 컨트롤러가 목록 전체를 넘긴다

@GetMapping
public String list(
    @RequestParam(name = "includeDeleted",
                  defaultValue = "false") boolean includeDeleted,
    Model model) {
  model.addAttribute("settings",
      settingQueryService.findAll(includeDeleted));
  model.addAttribute("includeDeleted", includeDeleted);
  return "provisioning/setting-list";
}

AFTER — 질의 · 쪽 · 링크가 인자로 들어온다

@GetMapping
public String list(
    @ModelAttribute SettingListQuery query,
    @PageableDefault(size = 20) Pageable pageable,
    ListLinks links, Model model) {
  model.addAttribute("page",
      settingQueryService.search(query, pageable));
  model.addAttribute("query", query);
  model.addAttribute("links", links);
  return "provisioning/setting-list";
}

Paging 이 한 곳에서 Sort 를 버리는 이유 — Spring Data 의 Pageable 리졸버는 sort 파라미터를 속성명으로 읽습니다. 우리는 같은 이름의 파라미터를 화면별 enum 으로 받으므로, 리졸버가 만든 Sort 는 NAME 이라는 존재하지 않는 속성을 가리킵니다. 그 Sort 가 저장소까지 흘러가면 오류가 되므로, Paging.of 한 곳에서 버리고 항목 enum 의 property() 와 방향으로 만든 Sort 로 갈아 끼웁니다. 파라미터 이름을 바꾸는 전역 프로퍼티 대신 이 방식을 고른 이유는 §8 D4 에 있습니다.

8-2. 탈락 사유

D1 — 머리는 페이지 동작이 있는 자리입니다(DESIGN.md §5). 판 머리는 서버 목록처럼 판이 여럿인 화면에서 붙을 곳이 모호해지고, 별도 필터 판은 축이 1~3 개뿐인 화면에 비해 무겁습니다.

D2 — 컨트롤러가 URL 을 조립하면 축 × 값만큼 링크가 곱해져 자랍니다. JS 로 조립하면 상태를 만드는 책임이 JS 로 넘어가 스크립트가 죽으면 조회 자체가 안 됩니다. GET 폼은 브라우저가 이미 하는 일을 그대로 쓰는 방식입니다.

D3 — #request 는 Thymeleaf 3.1 에서 제거됐습니다. 정적 헬퍼는 RequestContextHolder 에 의존해 테스트와 호출 맥락이 얽히고, advice 의 @ModelAttribute 는 XHR 을 포함한 모든 요청에서 실행됩니다. argument resolver 는 그 인자를 선언한 컨트롤러에서만 돕니다.

D4 — 자체 PageQuery record 를 만들면 이미 Pageable 을 쓰는 감사 로그와 페이징 방식이 이원화됩니다. sort 파라미터명을 바꾸는 프로퍼티는 전역 부작용이라 다른 화면까지 영향을 받습니다. 리졸버가 만든 Sort 는 Paging.of 한 곳에서 버리므로, 원시 속성 정렬이 저장소에 닿을 길이 그 한 곳에서 막힙니다.

D5 — 원시 속성명을 그대로 바인딩하면 화이트리스트가 없어 저장소 내부 속성이 URL 에 드러나고, 존재하지 않는 속성이 들어오면 실행 시점에야 터집니다(R6).

D6 — 메서드명 조합은 축이 4 개면 조합이 16 개가 됩니다. null-or JPQL 은 축이 늘수록 읽기 어려워지고, QueryDSL 은 의존성 추가가 필요합니다. Specification 은 이미 감사 로그에서 5 축을 합성하고 있는 검증된 선례입니다.

D7 — Specification 안에서 orderBy 를 걸면 정렬 기구가 Pageable 과 둘이 됩니다. 집계 JPQL 은 동적 필터와 상충하고(필터마다 쿼리를 다시 써야 합니다), 메모리 정렬은 DB 페이징의 전제를 깹니다.

D8 — 현행 전수는 그룹 목록을 그리려고 전 서버를 끌어옵니다. 쪽 단위로 보이는 그룹만 판정하면 한 쪽에 20 개라도 조회 범위가 그 안에서 닫힙니다.

D9 — 서버가 리다이렉트로 URL 을 정리하면 조회 한 번에 요청이 둘이 됩니다. 방치하면 ?q=&enabled= 같은 잔존 파라미터가 링크와 이력에 그대로 남습니다.

D10 — 머리글 링크는 링크라서 검색어를 입력하던 중이면 그 상태를 싣지 못하고, 정렬 가능한 열마다 조각 호출이 하나씩 붙습니다. 단일 셀렉트는 항목 × 방향 조합만큼 enum 상수가 늘어나 3 항목이면 6, 4 항목이면 8 이 되고 화면이 늘수록 곱으로 자랍니다. 항목과 방향을 가르면 항목 enum 은 화면당 3~4 상수로 닫히고 방향은 Spring Sort.Direction 을 그대로 씁니다.

D11 — 토글이 폼 필드가 되면 setting-list.js 가 하던 일(URLSearchParams 로 키 하나 토글)이 남지 않습니다. 스크립트를 남겨 두면 같은 일을 하는 자리가 폼과 스크립트 둘이 됩니다.

D12 — 조회 띠 오른쪽에 두면 쪽 이동과 떨어져 있어 "몇 개씩 볼까" 를 정하려는 순간에 눈에 띄지 않습니다. 링크 셋(20 · 50 · 100 을 각각 링크로)은 선택지가 늘면 그만큼 곱해집니다.

D13 — 조회 띠는 화면마다 축의 수와 종류가 달라, 조각으로 만들면 인자가 화면 수만큼 늘어나는 DSL 이 됩니다. "갈라지는 시점에 분리" 원칙대로 지금은 클래스 어휘만 공유하고, 세 번째 · 네 번째 화면이 붙어 같은 모양이 확인되면 그때 조각으로 올립니다. 정렬 셀렉트 둘은 두 화면의 마크업이 이미 같아 조각으로 둡니다 — 갈라지는 시점이 아니라 같은 시점이기 때문입니다.

D14 — 기존 pager 둘을 새 조각으로 옮기는 것은 이 슬라이스의 요구가 아닙니다. 범위 밖 공통화는 사용자 명시 요청이 있을 때만 합니다.

D15 — 필터 띠의 다른 축은 고를수록 결과가 좁아집니다. OR 는 고를수록 넓어져 같은 띠 안에서 방향이 어긋납니다. 상관 서브쿼리 exists 를 단계마다 AND 로 이으면 구현도 한 술어의 반복이라 특별한 장치가 필요 없습니다. 다만 이 해석은 세션 판단이므로 사용자 확인 대상입니다(Q5).

8-3. 주의

빈 문자열이 null 이 되는 것에 기댑니다 — @ModelAttribute record 생성자 바인딩에서 빈 문자열은 Boolean 과 enum 모두 Spring 기본 컨버터가 null 로 바꿉니다. "전체" 칩의 value="" 가 바로 이 동작에 기대고 있으므로, 통합 테스트(§6 의 "빈 문자열 → null")로 계약을 고정합니다.
@BindParam("processType") — record 구성요소 이름(processTypes)과 URL 파라미터 이름(processType)이 다르므로 Spring 6.1+ 의 @BindParam 으로 둘을 잇습니다. 파라미터 이름을 복수형으로 바꾸지 않은 것은 URL 에 같은 키가 여러 번 반복되는 모양(processType=A&processType=B)에서 단수 키가 더 자연스럽게 읽히기 때문입니다.
@Formula 안의 id — Hibernate 가 소유 엔티티의 alias 로 한정합니다. m.group_id 는 서브쿼리에서 명시한 alias 라 그대로 남습니다.
:has() 는 Chrome 105+ 입니다 — 칩의 활성 표시에 씁니다. n-chip-all("전체")의 활성 표시도 같은 선택자로, 그룹에 :not(:has(input:checked)) 를 걸어 하나도 안 골랐을 때만 켭니다. DESIGN.md §1 원칙 7(Chrome · Edge 전제)에 따라 허용됩니다.
서버 목록은 회귀 대상입니다 — 칩 CSS 는 이동이지 개명이 아니므로 승격된 전역 클래스로 그대로 그려져야 합니다. 확인은 CP5 의 C4 항목입니다. 같은 이유로 감사 로그 · 점검 이력의 pager 도 C5 에서 봅니다.
Notion — S8 페이지는 현재 설명 한 줄뿐입니다. CP1 뒤 상태를 진행 중으로 바꾸고 시작 일자와 본문 4 항목을 채우는 일은 세션이 notion-sync 에 위임합니다. S8-1 하위 페이지 신설은 사용자 지시가 있을 때만 합니다.

8-4. Open Questions — CP1 판정 결과

#질문판정
Q1 정렬 UI 를 어느 안으로 고정할 것인가 — H(표 머리글 링크) 대 S(조회 띠 셀렉트) 확정 — 셀렉트 둘(항목 · 방향), 2026-09-21. 정렬 모델도 항목 enum + Sort.Direction 으로 갈라집니다(D10)
Q2 정의서의 기본 정렬 — 번호순(ID · ASC) 유지인가, 최근 작성순으로 바꿀 것인가 승인(2026-09-21) — 현행 유지. 목록의 첫 열이 번호이고 지금 사용자가 익힌 순서가 그것입니다. 바꾸려면 첫 열의 의미도 함께 봐야 합니다
Q3 그룹의 기본 정렬 — 만든 시각 최신순(CREATED_AT · DESC) 유지 여부 승인(2026-09-21) — 유지. 현행 주석이 "만든 시각 최신순" 을 명시하고 있고 그룹은 최근 것을 먼저 보는 화면입니다
Q4 @DataJpaTest 를 도입할 것인가 — 프로젝트 첫 선례가 된다. 술어가 실제 SQL 로 도는지를 보는 유일한 수단이지만, H2 가 엔티티 그래프를 만들지 못할 위험이 있다 승인(2026-09-21) — 시도. 실패하면 사유를 report 에 남기고 CP5 샌드박스 검증으로 대체합니다. 시도 자체가 다음 슬라이스의 자산이 됩니다
Q5 포함 단계 다중 선택은 AND 인가 OR 인가 — 둘을 고르면 "둘 다 든 정의서" 인가 "둘 중 하나라도 든 정의서" 인가 세션 판단 AND 로 구현 착수 · 사용자 확인 대기. 뒤집는 비용은 hasAllProcessTypes 의 결합자 하나이고 URL · UI · 테스트는 그대로입니다(D15)
