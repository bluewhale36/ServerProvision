§0. 배경 — 토큰이 있는 요청은 막혔고, 토큰이 생기기 전의 요청이 남았다

S19-1 이 /api/pxe/v1/** 를 전용 게스트 체인으로 분리하고 토큰 인증을 필터로 승격했다(CP6 완료 · 2026-09-14). 그 결과 토큰을 들고 오는 요청은 전부 AuthenticationFilter 를 지나고 위조 · 누락 · 회수 토큰은 401 JSON 으로 끝난다. 그런데 토큰이 아직 없는 요청 둘 — /boot 와 /assets/** — 은 그 체인 안에서 permitAll 로 남겨 두었다.

/boot 는 이름과 달리 읽기 전용이 아니다 — 이 요청 하나가 게스트 서버를 등록하고 · 이력을 쓰고 · 게스트 토큰을 발급한다. 그래서 사내망의 누구든 curl 한 줄로 존재하지 않는 서버를 등록할 수 있다. 가정이 아니라 실제로 일어난 일이다 — S19-1 의 CP5 스모크에서 확인용 curl 한 번이 게스트 하나를 등록했다. /assets/** 도 진단 리눅스 자산 전부를 누구에게나 내준다.

이 슬라이스가 겨냥하는 것 — 목표는 완벽한 보안이 아니다. ① 사내망의 의도되지 않은 접근(확인용 curl · 잘못된 스크립트)을 막고 ② 외부망 노출 시의 악의적 접근에 최소한의 문턱을 두는 것이다. 모든 결정이 "이 값을 아는 기계만, 이 대역에서만" 으로 수렴한다.

이 문서는 S19 의 2단계다(Notion S19-2 · 시작 전 → CP1). 1단계가 넘긴 숙제 — "/boot 는 모든 예외를 200 재시도 스크립트로 바꾸는 채널인데, 자격을 요구하면 필터가 컨트롤러보다 앞이라 401 본문이 그대로 iPXE 에 닿는다" — 가 이 문서의 D-5 다.

§1. 현재 상태 (2026-09-14 코드 · 인프라 실측)

첫 접촉 흐름 — 전원이 들어온 뒤 앱에 닿기까지

게스트가 /boot 에 닿기까지 네 손을 거치고, 그 중 앱이 만드는 것은 둘뿐이다 — D-4(자격 배포)의 전제다.

단계만드는 주체실측
① DHCP 응답앱(조각 렌더) DhcpdConfigRenderer — user-class 가 "iPXE" 면 filename "boot.ipxe", 아니면 filename "ipxe.efi"
② tftp boot.ipxe앱이 아니다 — 인프라 파일 런북이 배치한다. 저장소에는 랩 사본만 있다 — scripts/pxe-lab/tftp/boot.ipxe 의 chain http://10.0.2.2:@PORT@/…/boot?… 를 run-guest.sh 가 치환한다
③ /boot 응답앱 IpxeScripts(대기 계열 · 재진입은 상대 경로) · DiagnoseLinuxChainload(pxe.server.base-url 기반 절대 URL)
④ 자산 수신앱(정적 서빙) PxeAssetsConfig 가 /api/pxe/v1/assets/** 를 pxe.assets.root 에 매핑한다

체인로드 스크립트가 지시하는 자산 URL — 다섯 곳

DiagnoseLinuxChainload.script(...) 가 assets = baseUrl + "/api/pxe/v1/assets" 를 다섯 자리에 꽂는다. 누가 그 URL 을 부르는지가 서로 다르다 — 자격을 어디에 실을지가 여기서 갈린다.

커널 인자 · 지시어부르는 주체자격을 실을 수 있는가
kernel %s/vmlinuz-lts · initrd %s/initramfs-ltsiPXE (HTTP) URL 의 user:pass@ 를 지원한다
modloop= · apkovl= · alpine_repo=Alpine initramfs 의 busybox wget · apk URL 의 user:pass@ 를 지원한다
provision_base=%sagent.sh 가 API 기준 URL 로 쓴다 실을 필요가 없다 — 에이전트는 X-Guest-Token 헤더로 인증한다
이 표가 D-4 의 근거다 — 자산을 받는 주체는 iPXE 와 busybox wget 둘뿐이고 둘 다 사용자 정의 헤더를 붙이지 못하지만, URL 안의 user:pass@(userinfo — URL 에 자격을 적는 표준 표기)는 둘 다 해석한다. 자격의 운반 수단은 헤더가 아니라 URL 이 된다.

핵심 진단 — 막아야 할 지점은 둘인데 그 둘을 부르는 클라이언트는 사람이 아니라 펌웨어와 busybox 다. 로그인 화면도 토큰 발급 왕복도 사용자 정의 헤더도 쓸 수 없고, 쓸 수 있는 것은 URL 에 적을 수 있는 자격 하나뿐이며 그 자격은 평문으로 남는다. 이 제약을 인정한 위에서 "그럼에도 무엇이 나아지는가" 를 설계하는 것이 이 슬라이스다.
§2. 요구사항 (확정) + 비목표
  1. /boot · /assets/** 에 PXE 부팅 계정 — 아이디 · 비밀 한 쌍(Basic 인증 — 사용자명과 비밀을 요청 헤더에 담는 HTTP 표준 인증)으로 첫 접촉을 막는다. 게스트 개별 신원이 아니라 채널 자격이다.
  2. 게스트 채널 전체에 프로비저닝 LAN 출발지 제한 — 자격을 아는 것만으로는 부족하고 정해진 대역에서 와야 한다.
  3. 자격의 배포 경로를 전부 잇는다 — tftp · 체인 스크립트 · 랩 · 하네스 · 런북. 한 곳이라도 빠지면 부팅이 멈춘다.
  4. 인증 판정(웹)과 게스트 토큰 인증(S19-1)은 무변경 — 화면 로그인도, 에이전트의 X-Guest-Token 왕복도 이 슬라이스로 달라지지 않는다.
  5. 진단 이미지 재포장 없음 — apkovl 과 agent.sh 를 건드리지 않는다.
  6. DDL 0 — 테이블 · 컬럼 · 인덱스 변경이 없다. 추가되는 것은 설정값과 클래스뿐이다.
비 목표 :
  • 완벽한 보안 — PXE 부팅하는 기계는 자격을 어차피 커널 인자로 받는다. 그 경계는 카탈로그 보드 검사와 운영자 개시 승인이 맡는다.
  • 상호 TLS 인증(mTLS — 서버와 클라이언트가 서로 인증서로 신원을 증명하는 방식) — 공개키 기반구조(PKI) 운영과 이미지에 키를 심는 일이 따라온다. 외부망 노출이 현실이 되면 별도 판단한다.
  • nginx 의 allow / deny 로 대역 제한 — 보조 수단으로는 유효하나 앱이 자기 경계를 모르게 된다(D-3 탈락 사유).
  • tftp boot.ipxe 를 앱이 렌더 · 배치하는 것 — 후속 슬라이스로 넘긴다(Q3).
  • 접근 로그 포맷 전반의 정비 — userinfo 마스킹만 확인 대상이다(Q5).
🎬 미리보기 — 첫 접촉 시퀀스 시뮬레이터 (자격 × 출발지 × CIDR → 단계별 HTTP · 콘솔 · 체인로드 스크립트)

              (a) 전역 AuthenticationManager 에 공급자를 추가한다
(b) 커스텀 헤더(X-PXE-Key)를 쓴다		
              (a) S19-1 CP5 F-1 의 재현이다 — 공급자 빈이 전역 AuthenticationManager 를 독점해 웹 formLogin 을 끊는다.

                (b) iPXE 는 사용자 정의 헤더를 붙이지 못하고, busybox 쪽도 결국 URL 에 담아야 하므로 표준 Basic 을 두고 자체 규약을 만드는 셈이 된다		
            

            

              D-3
인가 규칙		
              LAN ∧ 역할. ProvisioningLanPolicy implements AuthorizationManager<RequestAuthorizationContext> —
                pxe.guest.allowed-cidrs(IpAddressMatcher · getRemoteAddr())에 하나라도 맞으면 허용,
                비면 제한 없음 + 기동 WARN. 인가는 첫 접촉 = allOf(lan, hasAuthority("ROLE_PXE_BOOT")) ·
                나머지 = allOf(lan, hasAuthority("ROLE_GUEST")), LAN 밖은 403 PXE_LAN_FORBIDDEN.
                실제 출발지가 보이도록 server.tomcat.remoteip.remote-ip-header=X-Forwarded-For ·
                internal-proxies=127\.0\.0\.1 를 기본값으로 둔다 — 같은 호스트의 nginx 만 신뢰한다
              (a) 애플리케이션 전체에 IP 필터를 건다
(b) nginx 의 allow / deny 로 막는다		
              (a) 웹 화면은 사무실 대역에서 써야 하므로 전체에 걸면 운영자를 막거나 경로별 예외 분기가 다시 생긴다.

                (b) 앱이 자기 경계를 모르게 되어 테스트 · 샌드박스 · 랩 어디서도 확인할 수 없다(보조 수단으로는 유효 — 배제가 아니라 "앱이 먼저 안다" 를 고른 것)		
            

            

              D-4
자격 배포		
              URL 의 userinfo(http://사용자:비밀@호스트/… — URL 에 자격을 적는 표준 표기)로 나른다. 세 경로:

                ① tftp 의 boot.ipxe — chain http://pxe:<secret>@<서버>/…/boot?….
                런북 항목으로 적고, 랩은 @PXE_AUTH@ 를 run-guest.sh 가 PXE_BOOT_AUTH 로 치환한다.

                ② 앱이 렌더하는 체인 스크립트 — 신규 PxeBootUrls 를 execution/engine/boot/ 에 둔다
                (소비자 옆 · 자격은 PxeBootProperties 를 주입받아 조립 · 의존 방향 execution → global 유지).
                DiagnoseLinuxChainload 의 다섯 자리와 IpxeScripts 의 재진입 chain(Q4)이 쓴다.
                provision_base 는 자격 없이 그대로 — 에이전트는 토큰으로 인증한다.

                ③ 진단 이미지는 무변경 — 자격이 커널 인자로 오므로 이미지 안에 비밀이 없다		
              (a) 상대 URL 을 유지하고 iPXE 의 자격 상속에 기댄다
(b) 상호 TLS 인증(mTLS)		
              (a) iPXE 의 자격 상속은 문서화된 바가 없고, busybox wget 은 상대 URL 자체를 몰라 modloop · apkovl 이 그 자리에서 끊긴다.

                (b) 공개키 기반구조(PKI) 운영 · 이미지에 키 배치 · 인증서 회전이 통째로 따라와 이번 목표에 비해 비용이 압도적이다(외부망 노출이 현실이 되면 재판단 · 비목표)		
            

            

              D-5
첫 접촉 거절 응답		
              /boot · /assets/** 의 진입점은 401 + WWW-Authenticate: Basic realm="provision-pxe" + text/plain 한 줄이다
                (사람이 읽는 메시지 — iPXE 는 401 을 실행하지 않고 콘솔에 거절을 내며, 운영자는 그 한 줄에서 고칠 자리를 얻는다).
                나머지 경로는 S19-1 의 JSON 그대로이고 DelegatingAuthenticationEntryPoint 가 둘을 가른다.
                ExecutionRestController 의 예외 변환은 401 에 닿지 않으므로 그대로 둔다 — S19-1 §11 의 충돌은 이렇게 정리된다
              (a) 401 본문에 #!ipxe 재시도 스크립트를 담는다
(b) 첫 접촉만 200 + 안내 스크립트로 거절한다		
              (a) iPXE 는 2xx 본문만 실행하므로 401 본문의 스크립트는 버려지고 읽는 사람에게는 혼란만 남는다.

                (b) 거절을 200 으로 위장하는 셈이라 자격이 틀린 채 영원히 풀리지 않는 폴링 루프가 되고 접근 로그에도 정상 요청으로 남는다		
            

            

              D-6
하네스 · 랩

                boot-register.sh 에는 위조 · 무자격 401 확인 단계를 덧붙인다.
                run-guest.sh 는 boot.ipxe 의 @PXE_AUTH@ 를 치환하고, 샌드박스 실행 스크립트에 PXE_BOOT_SECRET 를 더한다
              —
              대안이 아니라 D-1 ~ D-5 를 적용하면 따라오는 작업 목록이다 — 하네스는 git 추적 자산이라 기대값과 주석을 함께 고친다

                nginx 설정은 무변경 — 출발지를 보이게 하는 것은 앱 속성(server.tomcat.remoteip.*)이지 nginx 가 아니다.

#질문권고

          
            
Q1
              secret 을 필수로 할 것인가 — 채택안은 "자산 루트가 설정돼 있으면 필수"(D-1), 대안은 "비면 열어 두고 WARN"
              권고 — fail-fast. 배포 실수가 곧 무인증이 되는 쪽은 되돌릴 방법이 없고,
                조건을 자산 서빙 여부에 걸어 관리 전용 인스턴스는 면제된다

            
Q2
              허용 대역 미설정을 어떻게 다룰 것인가 — 채택안은 "제한 없음 + 기동 WARN" 이다(D-3). 대안은 필수화다
              권고 — 제한 없음 + WARN. 필수화하면 샌드박스 · 랩 · 테스트마다 값을 맞춰야 한다.
                Q1 과 갈리는 이유 — secret 이 비면 누구나 열리지만 대역이 비면 여전히 secret 을 알아야 한다

            
Q3
              tftp boot.ipxe 를 앱이 렌더 · 배치할 것인가 — 지금은 인프라 파일이라 자격을 바꿀 때 사람이 손으로 고쳐야 한다.
                PXE 네트워크 화면이 dhcpd 조각을 렌더하듯 이 파일도 렌더할 수 있다
              권고 — 후속 슬라이스. 앱이 렌더하려면 배치(tftp 루트 쓰기)까지 책임져야 하고
                배치 권한 · 경로 설정 · 드리프트 탐지가 따라온다 — 이번 검증 줄기와 다른 이야기다

            
Q4
              재진입 chain 을 절대 자격 URL 로 바꿀 것인가 — 지금은 상대 경로이고,
                주석은 "서버 주소 지식을 스크립트에 심지 않는다" 를 이유로 적고 있다
              권고 — 절대 자격 URL 로 바꾼다. 그 원칙의 실익은 이미 사라졌다 — pxe.server.base-url 이
                자산 서빙의 필수 설정이라 서버 주소는 어차피 스크립트에 들어가고, 상대 경로를 유지하면 확인되지 않은 자격 상속에 부팅이 걸린다.
                고치는 자리는 waitAndChain 공통 골격 한 곳이지만 그 한 줄이 대기 계열 9 종
                (decommissioned · failed · awaitingIntake · shortageHold ·
                awaitingFirmwareFlash · awaitingFirmwareVerification · awaitingBiosSetting ·
                hold · windowsInstallFailed)와 retryAfterError 에 한꺼번에 걸린다 — 그래서 별도 판정을 받는다

            
Q5
              접근 로그의 URL userinfo 를 마스킹할 것인가 — 앱의 접근 로그 · RequestCorrelationFilter 계열이
                요청 URL 을 남기면 비밀이 평문으로 적립된다
              권고 — 지운다. 다만 userinfo 는 연결 단계에서 Authorization 헤더로 바뀌므로 남지 않을 수 있다 —
                CP5 C2 에서 실측해 report 에 적고, 남는다면 그 자리를 정정한다

            
Q6
              브랜치를 어디서 딸 것인가 — S19-1 이 미커밋이고 이 슬라이스는 같은 GuestSecurityConfig ·
                GuestAccessDeniedHandler 를 고친다
              권고 — S19-1 PR 을 먼저 열고 그 위에 스택한다. dev 병합을 기다리면 같은 파일을 두 브랜치가 만지는 기간이 길어진다

          
        


        
주의 · 부산물

        
    
          
  • 배포 순서가 부팅을 끊을 수 있다 — ① boot.ipxe 자격 → ② env 파일 → ③ 앱 재기동 순서를 런북에 적는다.
            ①을 먼저 해도 부팅은 계속 되지만, 반대로 하면 그 사이 전원이 들어온 게스트가 전부 401 을 받는다.
    • 
          
  • 자격 회전 시 tftp 파일도 함께 회전해야 한다 — 어긋나면 스윔레인 ②의 상황이 된다. 자동화는 Q3 의 후속이다.
    • 
          
  • 비밀은 평문으로 여러 곳에 남는다 — tftp 파일 · iPXE 콘솔 · /proc/cmdline · 접근 로그(Q5).
            설계가 받아들인 대가다 — 진짜 경계는 보드 검사와 개시 승인이 맡으므로 사용자 계정 비밀과 같은 등급으로 다루지 않는다.
    • 
          
  • PxeBootUrls 의 자리 = execution/engine/boot/ (결정) — 유일한 소비자 옆에 둔다.
            자격은 global/security/springsecurity/config/PxeBootProperties 를 주입받아 조립하므로 의존 방향은
            execution → global 단방향으로 유지되고, URL 조립이라는 부팅 도메인의 관심사가 보안 패키지로 새지 않는다.
            toString 마스킹으로 실수로 로그에 실어도 비밀이 새지 않는다.
    • 
          
  • Windows 설치와 펌웨어 굽기는 이 자격과 무관하다 — 더해지는 것은 LAN 조건뿐이다.
            다만 펌웨어 이미지를 부르는 주체는 BMC 이므로 BMC 의 IP 도 허용 대역 안에 있어야 한다 — 런북에서 빠뜨리기 쉽다.
    • 
          
  • 샌드박스 포트는 스트림마다 다르게 쓴다. 이 슬라이스는 PXE_ASSETS_ROOT · PXE_SERVER_BASE_URL 에 더해
            PXE_BOOT_SECRET 가 있어야 기동한다(D-1 fail-fast).
