§1. 배경

버그 수정 plan 형식이라 표준 11 섹션과 인터랙티브 데모를 두지 않는다. 배경, 실측, 결정, 구조, 테스트와 CP5, 범위 밖과 조율, Critical Files 순으로 적는다.

한 줄 요약 : 세팅 정의서가 저장할 때 보는 조건과 실행할 때 보는 조건이 달라, 저장은 되는데 실제 서버에서 막히는 경우가 세 갈래 있었다(C-23, D-1과 D-5, D-6). 정의서만으로 실패가 확정되는 경우는 실행 쪽과 같은 판정으로 저장에서 막는다. 서버의 디스크 구성을 봐야 정해지는 경우는 폼에 안내만 둔다.

§3. 결정 (채택 · 비채택 · 탈락 사유)
판정 기준 (모든 결정의 바탕) : 저장에서 막는 것은 "그 요소를 쓰는 실행은 반드시 실패하고, 쓰이지 않으면 아무 효과가 없는" 경우뿐이다. 서버의 디스크 구성에 따라 성패가 갈리는 경우는 막지 않고 안내한다. 근거: RaidPlanner 는 맞지 않는 규칙을 건너뛴다. 그래서 서로 다른 서버를 위한 대안 규칙을 여러 개 둔 정의서(SSD 서버용 규칙, HDD 서버용 규칙)가 정상이다. 규칙 수 같은 단순 비교로 막으면 이런 정상 정의서를 거짓으로 거절한다.
ID결정채택비채택탈락 사유
D-1OS 설치의 디스크 전제를 어디서 판정하나 지금 4 분기 SSOT 인 OsVolumeTargets.describe · OsVolumeTargetKind 를 넓힌다. 분기마다 "OS 설치를 막는가" 를 enum 상수 메서드로 두고, 저장 가드(SettingSaveRequest), 폼(osVolumeTargetMessagesJson 으로 이미 내려가는 표), 정의서 상세가 같이 쓴다. 계열 공통 규칙이다 ① provisioning OSFamily 상수마다 디스크 요구를 둔다
② 실행 쪽 OsVolumeLocator(UE 신설 예정)를 정의서가 부른다
③ 할당 때 막는다		 ① UE 확인: RHEL 도 OS 영역 볼륨을 인벤토리 WWN 으로 지목하므로 이 전제는 계열과 무관하다. 갈라지는 시점(직결 디스크 지원)에 분리한다
② 진단 인벤토리가 있어야 판정되고, provisioning 이 execution 에 의존하는 방향이 거꾸로다
③ 할당은 저장보다 늦고, 폼 1 차 차단이 생기지 않는다
D-2막는 분기 OS 설치 단계가 있을 때 막는 분기: ① RAID 단계 없음 또는 묶음 0 개(NONE) ② OS 후보 없음(NO_CANDIDATE, 기존) ③ 새 분기: OS 후보 묶음이 전부 RAID 없음(직결).
막지 않는 분기: OS 고정(FIXED)과 우선순위에 따름(BY_PRIORITY, 우선순위 행 필수는 기존 그대로).
OS 설치 단계가 없으면 어느 분기도 막지 않는다		 후보 중 하나라도 직결이면 막기 우선순위에 따른 후보에 RAID 와 직결이 섞이면, 어느 쪽이 OS 가 될지는 서버에 따라 정해진다(판정 기준 밖)
D-3Data 영역 직결 묶음과 Windows 저장은 막지 않는다. OS 설치가 Windows 인 정의서의 폼에만 주의 안내를 둔다(문구를 "Windows 설치" 로 한정) 계열 공통 저장 거절 UE 확인: Data 직결을 막는 것은 Windows 디스크 번호 순서가 미실측이라는 Windows 쪽 사정이다. RHEL kickstart 는 OS 디스크만 지목해 막을 이유가 없다. 계열별 판정은 RHEL 이 Data 직결을 받는 E4-1-b-6 에서 둔다
D-4정의서가 고를 수 있는 레벨(C-23) 새 도메인 메서드 RaidCard 에 "정의서에서 만들 수 있는 레벨" 판정을 둔다(이름은 CP2 에서 확정, 예: definableLevelBlockReason(RaidLevel), definableLevels()). 내용은 칩 계열이 못 만드는 레벨이면 계열 사유(RaidChipFamily.creatableLevelsHint 재사용), 아니면 카드 지원 레벨 사유(SupportedRaidLevels.blockReasonFor)다. DiskGroupRules.validateRaidRule 과 SettingRaidCardOptionResponse.of(blockReasons, 지원 레벨 목록과 표시, memberRules, spanMemberRules)가 이것만 부른다 ① 카드 데이터를 DDL 로 정리
② RaidPlanner 에서만 거절		 ① 카드 지원 레벨은 운영자가 등록한 사실이라 앱이 조용히 고치지 않는다(R17-2 판단, UE 추정). 이미 저장된 정의서는 DDL 로 고쳐지지 않는다. 판정을 교집합으로 하면 데이터와 무관하게 저장과 집행이 맞는다
② 진단 뒤에야 드러나 늦다
D-5이미 저장된 정의서의 안전망(C-23) RaidPlanner 에 새 거절 RaidPlanRejection.LEVEL_NOT_CREATABLE 을 둔다. RaidChipFamily.canCreate(D-4 와 같은 계열 판정)가 거짓이면 계획 전체를 거절한다. 기존 거절과 같이 진단 뒤 미리보기에 드러나고, RAID phase 는 실패가 아니라 보류가 된다(RaidConfigurationExecutor 의 ④ 분기 그대로) 실패 낙인 정의서를 고치면 풀리는 문제라 기존 VOLUME_LIMIT 과 같은 보류가 맞다
D-6카드 상세의 남은 레벨 RAID 카드 상세에 주의 안내: 저장 레벨 중 계열이 못 만드는 것이 있으면 그 레벨과 "수정 화면에서 정리" 를 보인다. 판정은 D-4 메서드 안내 없음 운영자가 정의서 폼에서 레벨이 왜 잠겼는지 카드 쪽에서 확인할 수 있어야 한다
D-7볼륨 수 상한(D-6) 저장에서 막지 않는다. 폼의 카드 선택지 표시에 볼륨 상한을 더하고, RAID 를 만드는 규칙 수가 상한보다 많을 때 묶음 표 곁에 주의 안내를 둔다. 상한 SSOT 는 RaidChipFamily.maxVolumes 그대로이고, SettingRaidCardOptionResponse 에 값을 싣는다 ① 규칙 수 > 상한이면 저장 거절
② 아무것도 안 함		 ① 대안 규칙을 둔 정상 정의서를 거짓 거절한다. '개씩' 규칙은 1 개만으로도 디스크 장수에 따라 넘으므로 규칙 수로는 판정되지 않는다
② 작성 때 상한을 알 길이 없다는 docs 지적이 남는다
D-8문구 정정 "설치기가 자동 선택" 류 문구 세 곳을 실제 동작에 맞춘다: OS 설치가 없으면 "RAID 구성을 바꾸지 않습니다", OS 설치가 있으면 D-2 의 차단 문구. 대상은 OsVolumeTargetKind.NONE 문구, 폼 MSG_NO_OS_CANDIDATE, setting-process-cards.html 상세 표시
D-9서버 가드 문구 저장 가드의 @AssertTrue 문구는 분기 공통 한 문장으로 둔다. 분기별 구체 문구는 폼 1 차 차단이 같은 enum 에서 받는다 분기마다 다른 예외 @AssertTrue 는 문구가 고정이다. 서버 가드는 direct POST 안전망이라 공통 문장으로 충분하다(UX 모순은 UI 1 차 차단 원칙)
D-10데이터 정리 DDL 없음. 배포 전 읽기 전용 점검 SQL 만 둔다(§5). 정리 DML 이 필요하면 배포 때 사용자가 정한다

같은 자리, OS 설치 없음 + 묶음 0 개결과RAID 구성을 바꾸지 않습니다.
정의서 상세 RAID 단계, 묶음 0 개빈 값미지정(RAID 구성 유지)
정의서 폼, Windows 설치 + RAID 없음 묶음주의Windows 설치는 RAID 없음 묶음이 있으면 설치 디스크를 정하지 못해 설치 단계에서 멈춥니다.
정의서 폼, 카드 선택지라벨(기존 표시) + 볼륨 최대 2개
정의서 폼, RAID 규칙 수 > 상한주의규칙이 한 서버에서 모두 맞으면 볼륨이 2개를 넘어 실행 계획에서 거절됩니다.
RAID 카드 상세주의등록된 RAID5, RAID6 은 이 칩 계열이 만들 수 없어 정의서에서 고를 수 없습니다. 수정 화면에서 정리할 수 있습니다.
저장 가드 @AssertTrue(direct POST)차단 사유OS 설치 단계가 있으면 RAID 구성 단계에서 RAID 로 만드는 OS 영역 볼륨을 정해야 합니다.

§5. 범위 밖 · 조율

5-1. UE 세션(E4-1-b) 합의 (2026-11-17)

  • b-1(설치 작업 트리)은 정의서 쪽 파일을 건드리지 않는다.
  • b-2(정의서 RHEL 활성화)는 HF32 가 병합된 뒤 그 위에서 시작한다. b-2 의 대상은 OsInstallTargetPolicy, JpaSettingQueryService.toOSOption, RHEL 요청 계열, rhel 화면 조각이다. HF32 는 이것들을 건드리지 않는다.
  • Data 직결 판정은 계열별 출력 소관이다. RHEL 은 막지 않는다는 결정을 UE 가 b-6 plan 에 적는다.
  • 직결 디스크(RAID 카드 없는 서버)는 E4-1-b 와 가까운 후속 범위에 없다. 받게 되면 OsVolumeTargetKind 의 차단 상수 하나를 푼다.

5-2. 범위 밖

  • 할당 화면의 경고, 정의서 목록의 "실행에서 막힘" 표시: 범위 밖. 서버 상세 준비도가 할당 직후 BLOCKED 를 이미 보인다.
  • MPT_IR.memberCountRule 의 RAID5 · 6 관용 분기 정리: 범위 밖(D-5 거절이 먼저 막아 닿지 않는다).

5-3. 배포 전 읽기 전용 점검 SQL (운영과 스테이징, 배포 때 사용자 지시로)

-- 계열이 못 만드는 레벨이 남은 카드
SELECT id, vendor, model_name, supported_raid_levels FROM raid_card
WHERE chip_family = 'MPT_IR' AND (FIND_IN_SET('RAID5', supported_raid_levels) OR FIND_IN_SET('RAID6', supported_raid_levels));
-- 그 카드를 RAID5 · 6 묶음으로 쓰는 정의서 단계
SELECT sp.id, sp.setting_definition_id, JSON_VALUE(sp.payload_json,'$.raidCardId') AS card, JSON_EXTRACT(sp.payload_json,'$.diskGroups[*].raidLevel') AS levels
FROM setting_process sp JOIN raid_card rc ON rc.id = JSON_VALUE(sp.payload_json,'$.raidCardId')
WHERE sp.process_type = 'RAID_CONFIGURATION' AND rc.chip_family = 'MPT_IR'
  AND (JSON_CONTAINS(JSON_EXTRACT(sp.payload_json,'$.diskGroups[*].raidLevel'), '"RAID5"') OR JSON_CONTAINS(JSON_EXTRACT(sp.payload_json,'$.diskGroups[*].raidLevel'), '"RAID6"'));

정의서 FK 컬럼 이름은 SettingProcess 엔티티 기준 setting_definition_id 다.

5-4. 디자인 스트림 확인

디자인 PR #110(dev beb3260) 병합 뒤라 화면 문구는 DESIGN.md 7절과 DesignConventionTest 를 따른다. 재사용할 RaidChipFamily.creatableLevelsHint 와 SupportedRaidLevels.toDisplay 는 레벨 나열을 ' · ' 로 잇는다(Java 문자열이라 DesignConventionTest 검사 밖). 7절 표기 2(가운뎃점 금지)와 어긋나므로 CP2 에서 쉼표로 바꿀지 디자인 스트림과 확인한다.
