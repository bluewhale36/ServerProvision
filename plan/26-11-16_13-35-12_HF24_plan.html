§1. 배경

버그 수정 plan 형식이라 표준 11 섹션과 인터랙티브 데모를 두지 않는다. 배경, 실측, 결론, 수정 방향, 결정과 열린 질문, 전제, 검증, Critical Files, 남은 일 순으로 적는다.

1-1. 이 문서의 용어

정의 전문은 discussion/26-11-16_13-13-45_HF24-boot-order-terms.md 에 있다. 여기서는 본문에 나오는 것만 한 줄로 푼다.

용어뜻
BootOrder부팅 항목(Boot0001 등)의 순서 목록. BIOS 는 이 순서대로 부팅을 시도한다
FBOFixed Boot Order. AMI 가 항목을 묶는 그룹(HD, CD/DVD, USB, NET, AP(셸))의 순서. 셋업 Boot 탭에 보이는 순서다
공장 순서디스크, CD/DVD, USB, 네트워크, 셸
오버라이드Redfish 로 "다음 부팅은 이 장치로" 를 거는 설정. 순서 목록과는 별개의 층이다
Once오버라이드를 한 번의 POST 에만 적용한다. 엔진이 써 온 방식(PXE_ONCE, HDD_ONCE)
Continuous오버라이드를 계속 적용한다. AMI 가 BIOS 안에 저장해 풀어도 남는다
오버라이드 POST (R1)Once 가 걸린 상태의 POST. 대상 그룹이 FBO 1 번과 자리를 바꾸고 BootOrder 가 그 순서로 다시 모인다
되돌림 POST오버라이드 POST 바로 다음 POST. 오버라이드 전 순서로 통째로 돌아가며 그 사이에 쓴 값을 버린다
오버라이드 없는 POST (R2)오버라이드가 없고 직전도 오버라이드 POST 가 아닌 POST. 쓰인 BootOrder 가 유지된다
셸 낙하부팅할 것이 없어 순서상 셸까지 내려가 UEFI 셸 화면에 멈추는 것

1-2. 다섯 번의 정정

E2.5(2026-08 말) 이후 프로비저닝 중 부트 순서가 바뀌어 UEFI 셸에 떨어지는 결함이 계속됐다. 정정은 다섯 번 있었다.

  1. E2.5 Once
  2. HF15-1 Continuous
  3. HF17 Once 회귀와 4 분 재무장
  4. HF19 FBO 강제 (보류)
  5. HF20 BootOrder 정착 (SHELL_LAST, DISK_FIRST, Windows 착수 때 Once Hdd)

다섯 번 모두 "프로그램이 순서를 세우면 유지된다" 는 전제였다. 이 AMI BIOS 에서는 오버라이드, BootOrder, FBO, BIOS 의 재구성이 서로 덮어써 예측이 되지 않았다.

1-3. 2026-11 시험의 새 양상

PXE 서버 동작 테스트(메인보드 2 종, 8~10 대)에서 새 양상이 나왔다.

  • 그룹 1: 굽기, 설정, RAID 뒤 셸 낙하. 굽기, 설정만 한 서버의 순서는 Disk, CD, USB, Shell, Network 였다 (공장 순서에서 네트워크와 셸이 맞바뀐 모양).
  • 그룹 2: 전 단계 실행에서 일부 서버만 Windows 설치 마지막 부팅에서 순서가 바뀌었다.

1-4. 방향 전환 (2026-11-16 토론)

토론 기록은 discussion/26-11-16_12-58-38_HF24-observe-recover_discussion.md 9 절이다.

부트 순서를 바꿔야 했던 이유는 디스크에 이미 OS 가 있는 서버를 네트워크로 부팅시키기 위해서였다. 그러나 대부분은 빈 서버를 프로비저닝하고, 공장 순서에서 빈 디스크는 건너뛰므로 네트워크가 셸보다 먼저 온다. Windows 는 Setup 이 만든 디스크 항목으로 부팅한다. 그래서 엔진은 부트 순서를 아예 건드리지 않는다.

일정: PXE 서버 본격 사용을 더 늦출 수 없어 임시방편이라도 먼저 해결한다(사용자, 11-16).

§3. 결론
결함의 원인은 엔진이 순서를 세우려고 넣은 장치들(Once 무장, 재무장, SHELL_LAST, DISK_FIRST) 자체다. 이 장치들은 드문 경우(디스크에 OS 가 있는 서버)를 위해 들어왔지만 흔한 경우(빈 서버)를 망가뜨렸다.

정정은 장치를 빼는 것이다. 빈 서버는 공장 순서만으로 네트워크로 부팅한다.

실패 감지는 이미 있다. 굽기 뒤 전원 투입과 설정 적용 뒤 재시작을 기다리는 단계에 복귀 시한 (provision.execution.return-timeout, 기본 20 분)이 있어, 넘으면 실패로 닫힌다(PowerOnStep, ReturnReadbackStep). 셸 낙하와 디스크 OS 부팅도 이 시한으로 실패로 드러난다.

§4. 수정 방향

4-1. 빼는 장치

#무엇을어디서바뀐 뒤
1굽기 뒤 전원 투입의 Once Pxe PowerOnStep (powerOnAndVerify(target, NextBoot.PXE_ONCE)) 무장 없이 전원만 켠다
2설정 적용 재시작의 Once Pxe BeginSettingStep (reset(target, reset, NextBoot.PXE_ONCE)) 무장 없이 재시작만 한다
3에이전트 REBOOT 지시 직전의 Once Pxe RebootDirectiveArmer.armIfReboot (호출: AgentReportService 2 곳) 호출 제거. 에이전트는 그냥 재부팅한다
4Windows 착수 때의 Once Hdd RebootDirectiveArmer.armForWindowsSetup (호출: WindowsInstallingExecutor) 호출 제거
5무장 직전 SHELL_LAST RedfishPowerService.arm 안 무장 자체가 없어져 함께 사라진다
6종단 DISK_FIRST BootOrderSettlement (완료 이벤트 리스너) 클래스 제거
74 분 미도착 재무장 PowerOnStep.rearmIfOverdue, ReturnReadbackStep.rearmIfOverdue, FlashTimeoutPolicy.pxeRearmDelay, FlashContext.pxeRearmedSinceWait, SettingLedger.markRearmed · rearmAtOf, 속성 provision.execution.pxe-rearm-delay 제거. 복귀 시한(20 분)까지 기다리고 넘으면 실패
8운영자 [재시도 후 네트워크 부팅] GuestServerController.retryAndNetworkBoot → RedfishPowerService.networkBoot Once 없이 꺼져 있으면 켜기, 켜져 있으면 재시작. 버튼 문구 조정(결정 D-4)

4-2. 삭제

이후 쓰이지 않게 되는 것은 삭제한다.

  • 클래스: NextBoot, BootOverrideOutcome, BootOrderPolicy, BootEntries, RebootDirectiveArmer, BootOrderSettlement
  • RedfishPowerService 의 settleBootOrder · Settlement · settle · armBootOverride · arm · reset(target, type, nextBoot) 오버로드
  • powerOnAndVerify 의 NextBoot 인자
  • 테스트: NextBootTest, BootOrderPolicyTest, BootOrderSettlementTest, RebootDirectiveArmerTest, RedfishPowerServiceBootOrderTest

나머지 테스트는 "무장 없음 · 재무장 없음" 으로 고친다(§7).

4-3. 남기는 것

  • FlashLedger.PXE_REARM 상수는 PHASE_LEVEL_REASONS 안에 남긴다. 이미 DB 에 있는 과거 재무장 행을 phase 수준 사건으로 읽어야, 그 행이 축의 결과로 잘못 읽혀 성공한 축이 실패로 보이는 일(E2-4 CP5 F-2)이 생기지 않는다. 새로 쓰는 곳은 없다.
  • Windows 설치 중 재PXE 의 exit 처리(IpxeScripts.localBootFallthrough)와 종단 completedExit 는 그대로다.
  • 복귀 시한 return-timeout 20 분 그대로.
§5. 결정과 열린 질문

5-1. 결정

결정채택안비채택 대안과 탈락 사유
