§0. 요약 — 스코프 재정의 동기

세팅 정의서에서 OS 계열 프로세스의 입력 표면을 축소한다. OS_INSTALLATION 은 식별(OS 메타데이터 · ISO 선택)만 남기고, OS_SETTING 은 팔레트에서 제거한다. 남긴 식별의 선택 대상은 Windows Server 2025 뿐이며 리눅스 기반 OS 는 선택할 수 없다(D-R8, 2026-08-20 사용자 확정).

축소이지 제거가 아니다 — 코드 · 스키마 · 기존 계약은 그대로 보존한다. 계열 상세 계약은 direct POST 로 여전히 수락되며, 이 슬라이스가 바꾸는 것은 사용자에게 노출하는 입력의 범위다.

§1. 현재 상태 (진단)

동료 검토 피드백 (2026-08-20)

  1. OS 설치 섹션이 구체적이라 복잡해 보인다.
  2. 사내 주문의 OS 요청사항이 다양해 주문 수만큼 정의서를 만들게 될 것이다(정의서 폭발 우려).

구조적 원인 — 추상 축과 변동 축의 불일치

세팅 정의서는 재사용하는 표준 템플릿이다. 그런데 OS 상세(파티션 · 사용자 · 패키지)는 주문마다 달라지는 변동 값이다. 변동 값을 재사용 템플릿에 넣으면 템플릿이 주문 단위로 복제될 수밖에 없다 — 피드백 ②의 폭발 우려는 이 불일치의 결과다.

소비처 부재 — MVP 축소 (2026-08-20)

OS 설치(E4)가 MVP 에서 제외되면서, 지금 받는 상세 입력을 실제로 소비하는 실행 경로가 없다. 소비처 없는 입력은 정확성을 검증할 방법도 없이 사용자 부담만 남긴다.

주문마다 달라지는 것은 OS 종류 · 버전 하나뿐이고, 그것은 정의서가 이미 식별 정보로 갖고 있다. 파티션만 표준과 주문별이 섞이는데, 섞인 값을 표준 템플릿에 고정하면 절반은 매번 틀린 값이 된다.

추가 실측 — RHEL 실 수요 자체가 작다. 계열 상세 입력이 커버하는 실사용 폭이 좁다는 뜻이며, 지금 노출을 유지할 이유가 더 줄어든다.
§2. 요구사항 (확정) + 비목표
  1. OS_INSTALLATION 카드의 입력은 OS 선택 + ISO 선택 둘만 남긴다. 계열 파생과 상세 pane 은 렌더하지 않는다. D-R5
  2. 남긴 식별의 선택 대상은 Windows Server 2025(Windows 계열) 뿐이다. 리눅스 기반 OS 는 옵션 disabled + 사유 tooltip 으로 UI 에서 1차 차단하고, 서버 가드가 안전망을 잡는다. D-R8
  3. OS_SETTING 은 팔레트에서 완전히 제거한다(비활성이 아니라 숨김). D-R2
  4. 계열 상세 계약은 유효한 계약으로 남는다 — direct POST 는 여전히 수락된다. D-R3
  5. 식별 전용 요청은 판별자 부재 = 식별 전용 규칙으로 해석한다(등록 테이블 신설). D-R1
  6. 팔레트 노출 여부의 SSOT 는 SettingProcessType 의 enum 속성이다 — 컨트롤러 하드코딩 목록을 두지 않는다. D-R4
  7. 축소 카드에 안내 문구 1줄을 신설한다("상세 설치 설정은 MVP 이후 지원 예정" 류). D-R7
  8. 과거 상세 payload 로 저장된 정의서의 조회가 깨지지 않는다 — 계열 상세 카드 fragment 는 잔존한다. D-R6
비 목표 :
  • 계열 계약 폐지 — RHEL · Ubuntu 설치 요청과 RHELOSSettingRequest 는 그대로 둔다(전체 보존 목록은 §10 유지).
  • 엔티티 · 스키마 변경 — payload 가 다형 JSON 이라 DDL 이 필요 없다(§8 스키마, Step 9 = N/A).
  • U3 할당 · 스냅샷 경로 변경 — 스냅샷은 payload 원문을 그대로 얼리므로 영향이 없다.
  • OS 설치 실행(E4) 구현 — MVP 제외 상태이며, 그 부재가 이번 축소의 전제다.
  • 리눅스 기반 OS 의 설치 예정 기록 — 상세 설치가 E4 로 이연되므로 기록도 함께 봉인한다(D-R8).

§4. 도메인 모델 (SSOT)

계약 표현 — 설계 대안 비교

화면에서 상세 입력을 숨기기만 하는 방법은 성립하지 않는다. 현행 계열 구현체가 타임존에 @NotNull, 파티션에 @NotEmpty 를 걸고 있어, 상세를 비운 요청은 검증에서 거절되기 때문이다. 계약 표현 자체를 정해야 한다.

안내용판정
(a)OSFamily.UNSPECIFIED 상수 추가 후 식별 전용 구현체 매핑탈락
(b)판별자 부재 = 식별 전용 등록 테이블 조회채택
(c)계열 구현체의 상세 검증을 완화(optional)하고 화면만 숨김탈락

(a) 탈락 — OSFamily 축의 오염이다. "계열 미정" 은 계열이 아니라 상태이며, enum 주석 스스로 "소비자가 생기는 시점에 상수를 추가한다" 는 원칙을 갖고 있다(현행 상수는 RHEL_BASED · DEBIAN_BASED 둘뿐이고 Windows 도 예약만 한 채 추가하지 않았다).

(c) 탈락 — 계약이 "빈 상세 허용" 으로 느슨해진다. E4 가 부활했을 때 빈 파티션으로 kickstart 가 생성되는 류의 조용한 결함 위험이 남고, 임시 비대칭이 계열 구현체 전체로 번진다.

(b) 채택 — 도메인 사실("정의서 작성 시점에 계열 상세를 정하지 않는다")과 표현이 일치한다. ProcessRequestDeserializer 가 이미 "새 타입 추가 = 맵 한 항목 등록" 을 공식 확장점으로 명시하고 있어(클래스 Javadoc "판별자 등록 지점 (SSOT)"), 분기 추가가 아니라 등록 테이블 확장으로 끝난다.

D-R1 — 식별 전용 계약

osFamily() 가 null 이라 직렬화 왕복 시에도 판별자가 없는 상태로 나가고, 다시 읽을 때 부재 판별 경로로 재해석된다 — 왕복이 일관된다.

비고 — 계보 : 이 계약이 계열에 무관한 식별 타입이라는 점은 Windows 방향과도 정합하지만, 그것이 당초 (b) 채택의 근거는 아니었다. 채택 근거는 "정의서 작성 시점에 계열 상세를 정하지 않는다" 는 도메인 사실이었고, Windows 정합성은 2026-08-20 사용자 확정(D-R8)으로 명시 요구로 승격됐다 — 같은 표현 하나가 두 요구를 함께 만족한다.

D-R4 — 팔레트 노출의 SSOT

SettingProcessType.values() ← 현행 (SettingController 78행 부근) ↓ SettingProcessType 의 노출 속성 필터 ← R11 (예: paletteExposed)

노출 여부를 컨트롤러의 하드코딩 목록으로 두면 화면마다 목록이 복제되어 갈라진다. enum 속성 한 곳에 두면 팔레트 · 다른 화면 · 서버 가드가 모두 같은 값을 읽는다 — "UI 차단 조건과 서버 가드 조건은 단일 SSOT 공유" 원칙의 적용이다.

D-R8 — 선택 가능 대상은 Windows Server 2025 뿐

식별을 남기더라도 선택할 수 있는 OS 는 Windows Server 2025(Windows 계열) 하나다. 리눅스 기반 OS 는 선택 대상이 아니다.

층동작성격
UI리눅스 옵션 disabled + 사유 tooltip1차 차단 — 사용자가 애초에 고를 수 없다
서버Planned 요청의 OS 참조가 Windows 계열이 아니면 거절안전망 — direct POST · stale 요청만 도달
차단 조건 = 단일 SSOT 도메인 메서드 1개 ├── 뷰모델 : 옵션 disabled 플래그 + 사유 문구 ← UI 1차 차단 └── 서버 : Planned 참조 검증에서 거절 ← 안전망

두 층이 같은 도메인 메서드를 호출한다 — 조건을 두 곳에 복붙하면 갈라지기 때문이며, childEnableBlockReason() 과 blocksChild*() 가 이미 쓰는 원칙과 같다.

근거 — 주문 실측에서 "설치 예정 기록" 의 가치가 실재하는 것은 Windows Server 2025 뿐이다(대부분의 출고 서버가 실제로 거치는 공통 과정). 리눅스 상세 설치는 E4 로 이연되므로 기록도 함께 봉인한다 — 소비처도 없고 선택 가치도 없는 항목을 열어 두면 §1 의 "복잡해 보인다" 를 그대로 남기게 된다.

안내 문구 — "Windows Server 2025 설치 자동화는 추후 지원 예정" 취지로 둔다. 문구 확정은 .claude/domain-conventions/new-user-copy.md 관문을 연 뒤이며, D-R7 의 축소 안내와 한 벌로 다듬는다.

D-R2 — OS_SETTING 을 남기지 않는 이유

식별만 남기는 처리를 OS_SETTING 에도 적용하면 담을 정보가 osMetadataId 하나인데, 그 값은 OS_INSTALLATION 잔존분과 중복이다. 중복된 식별만 남은 단계는 기록 가치가 없으므로 팔레트에서 제거한다. 계약(RHELOSSettingRequest)은 보존하므로 direct POST 는 계속 수락된다.

승인 게이트는 CP1 · CP4(중간 승인) · CP6 · CP7 넷이다. 무중단 구간은 둘 — ① CP1 승인 → CP4 게이트 지점(main 구현, 경계 보고만) ② CP4 승인 → CP6 제출(테스트 작성 · CP5 검증 · report 산출).

브랜치는 refactor/R11_setting-os-scope-reduction 이며 origin/dev 를 기점으로 CP2 진입 시 생성한다.

신규 예외는 0 이다. 새 예외 클래스가 없으므로 .claude/domain-conventions/new-exception.md 관문은 해당하지 않는다. 다만 기존 예외가 실제로 트리거되는지는 확인해야 하며, 그 책임은 §6 의 ⑤ · ⑥ 이 진다. D-R8 의 계열 가드도 기존 참조 검증 예외를 재사용하는 것을 원칙으로 하며, CP2 실측에서 재사용할 예외가 없다고 판명되면 그때 관문을 열고 신설 여부를 판단한다.

열어야 하는 관문 — D-R7 의 안내 문구는 새 사용자 문구이므로, 작성 전 .claude/domain-conventions/new-user-copy.md 를 먼저 연다(작업 전 체크리스트 규약).
§8. 예상 부산물 / 주의 / 결정 사항

D-R5 — 신규 폼 축소 범위

  • setting-new.html 의 OS_INSTALLATION 카드에서 계열 파생(data-osFamily)과 상세 pane 렌더를 제거하고 OS · ISO 선택만 남긴다.
  • setting-form.js 의 OS_INSTALLATION serializer(954행 부근)는 type + osMetadataId + isoId 만 조립하고 osFamily 를 넣지 않는다.
  • OS_SETTING 카드 마크업은 팔레트 제거로 진입 자체가 차단되므로 잔존해도 무해하다. 정리 여부는 구현 시 판단한다.

D-R6 — 기존 데이터와 수정 폼

상세 payload 로 저장된 정의서는 테스트 데이터뿐이고 미배포 상태다(토론 D3). 따라서 로컬 테스트 데이터 정리로 처리한다. 조회 카드(setting-process-cards.html)에는 Planned 표시 케이스를 추가하고, 계열 상세 카드(detail-rhel 등)는 잔존시킨다 — 과거 데이터의 조회가 깨지지 않게 하기 위해서다. 수정 폼은 축소 카드 기준으로 동작한다.

D-R7 — 안내 문구

축소 카드에 "상세 설치 설정은 MVP 이후 지원 예정" 류 안내 1줄을 둔다. 무엇이 사라졌는지와 언제 돌아오는지를 함께 전달해야 사용자가 결손으로 오해하지 않는다.

미확정 — CP2 진입 시 실측

#확인 대상미달 시 대응
Q1참조 검사기(OSInstallationReferenceInspector 계열)의 계약이 Planned 를 그대로 받는가시그니처가 계열 구현체에 결합돼 있으면 식별 전용 검사 경로 분리
Q2수정 폼 pre-fill(withPatchedPasswords 경로)이 Planned 에서 no-op 으로 성립하는가성립하지 않으면 Planned 분기 처리
Q3setting-detail.html 의 OS 카드 배지(setting-process-cards.html 36행)가 Planned 에서 자연 동작하는가배지 라벨 케이스 추가
Q4OSMetadata · OSName 이 Windows 계열을 표현할 수 있는가 (Windows Server 2025 값의 실재 여부)없으면 enum 값 추가가 CP2 범위에 합류

Q1 ~ Q3 은 구현 방식의 세부이고 슬라이스 범위를 바꾸지 않는다. Q4 는 실측 결과에 따라 enum 값 추가가 CP2 범위에 합류할 수 있으며, 그 경우 D-R8 의 전제를 만족시키는 최소 추가로 한정한다 (OSFamily 의 "소비자가 생기는 시점에 상수를 추가한다" 원칙과 같은 방향 — 이번에 소비자가 생겼다). CP1 의 결정은 D-R1 ~ D-R8 로 확정된 것으로 본다.
