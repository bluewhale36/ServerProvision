§1. 현재 상태 (2026-09-27 · dev 4b58b96 실측)

자원 관리 목록 여섯은 모두 Miller 3 열(C1 묶음 → C2 항목 → C3 상세) 화면이고, 페이징 없이 전부 읽은 뒤 서버에서 묶습니다. 검색 · 필터 · 정렬 UI 는 없고, 조건처럼 쓰이는 것은 "삭제된 항목 포함" 체크박스 하나뿐입니다.

§2. 요구사항 (확정) + 비목표

2-1. 사용자 전제

  1. S8 = 조회 화면 기능 강화입니다. S8-1(공통 부품 · 세팅 정의서 · 서버 그룹)과 S8-2(게스트 서버)가 끝났고, S8-3 은 자원 관리 목록 여섯입니다.
  2. S8-4(시작 전)는 모든 목록의 기본 필터 "생성 일시 1 년 이내" · '검색' 버튼이 여는 상세 조회 창 · 조회 띠의 필터를 그 창 안으로 옮기기 · 보드 · 그룹처럼 자기 조회 화면이 있는 대상의 필터 표현 재설계입니다.
  3. 검색 입력은 Enter 가 주 경로이고 '검색' 버튼은 남깁니다(S8-4 에서 상세 조회 창을 여는 버튼이 됩니다).

2-2. 요구 (여섯 화면 공통)

  1. R1 조회 띠(S8-1 의 GET 폼)를 Miller 위에 둡니다 — 검색 입력(Enter · '검색' 버튼) · 활성 칩(전체 · 활성 · 비활성) · 사용 중단 칩(전체 · 권고 · 정상) · 삭제된 항목 포함 체크박스 · 결과 건수 · 초기화.
  2. R2 조건은 C2 항목(자원 한 건)에 겁니다. 조건에 맞는 항목이 없는 C1 묶음은 숨깁니다. C1 머리에 맞는 항목 수를 보입니다(기존 개수 표시가 있으면 그것을 조건 뒤 값으로).
  3. R3 폼 제출 때 선택 파라미터를 숨은 필드로 보존합니다(화면별 selectKey · selectId · selectBoardId · selectKind). 선택한 항목이 조건에 걸려 사라지면 C3 는 빈 상태("선택한 항목이 조건에 맞지 않습니다." + 조건 초기화 링크)입니다.
  4. R4 조건이 하나라도 걸리면 BIOS · BMC 의 순위 드래그를 끕니다(삭제 포함 때와 같은 게이트). 끈 이유를 드래그 핸들 자리에 안내합니다(툴팁 또는 한 줄).
  5. R5 검색 대상은 부분 일치 · 대소문자 무시이고 아래 2-4 표와 같습니다. ISO 는 검색 대상이 아닙니다(OS 버전 아래 아코디언 — 한 단계 더 안쪽).
  6. R6 Driver/Utility 는 조회 띠 하나가 두 Miller 모두에 걸립니다(삭제 포함이 이미 페이지 전역입니다).
  7. R7 include-deleted-toggle.js 를 폼 필드로 흡수하고, 사용처가 0 이 되면 파일을 지웁니다.
  8. R8 알 수 없는 값(enabled=maybe 등)은 바인딩 400 입니다(S8-1 과 같은 경로).

가짜 데이터(결정적 · 난수 없음)로 메인보드 / BIOS / Driver · Utility 세 화면을 그립니다. 제조사 3(Gigabyte · Asus · Fujitsu) · 보드 8 · 보드당 BIOS 0 ~ 4 · 드라이버 5 · 유틸리티 5(공용 포함)입니다. 셋이면 형태가 다 나옵니다 — 제조사 묶음형 · 보드 묶음 + 순위형 · Miller 둘형입니다.

C1 · C2 항목을 누르면 선택이 바뀌고(URL 의 선택 파라미터가 따라 바뀝니다), 조회 띠의 검색(Enter 또는 '검색') · 칩 · 체크박스를 바꾸면 Miller 와 캡션이 함께 바뀝니다. BIOS 화면의 ▲ ▼ 는 드래그를 대신하는 버튼입니다. 조건이 걸리면 핸들이 꺼지고 마우스를 올리면 이유가 뜹니다. '보이는 순서로 PATCH 직접' 버튼은 조건 중에 걸러진 목록을 서버에 보냈을 때 reorderVersionRanks 가 무엇을 돌려주는지 재현합니다(§9 B4).

캡션 첫 줄은 URL(빈 값 · 기본값 생략, 선택 파라미터는 숨은 필드로 보존), 둘째 줄은 서버 판정입니다. 항목을 거르는 함수는 demoMatches 하나이며, 그 본문은 §4-2 의 ResourceListQuery.matches 와 같습니다. 활성 · 사용 중단은 effective 값으로 판정합니다 — 부모 보드가 비활성이면 그 BIOS 도 비활성으로 보이고 걸립니다(LifecycleEntity.recomputeEffective 와 같은 결합).

4-2. ResourceListQuery

public record ResourceListQuery(
        String q,
        Boolean enabled,          // null = 전체
        Boolean deprecated,       // null = 전체
        Boolean includeDeleted) {

    // 압축 생성자: 공백 q → null · includeDeleted null → false

    /** q · enabled · deprecated 중 하나라도 — includeDeleted 는 별도 축(기존 의미 유지). */
    public boolean isFiltered() { … }

    /** 삭제 제외(includeDeleted 아니면) · 활성 · 사용 중단은 effective 값 · 검색은 searchable 중 하나라도 소문자 부분 일치. */
    public boolean matches(LifecycleEntity e, String... searchable) { … }
}
판정 순서조건엔티티 값
1includeDeleted 가 아니고 삭제됨 → 제외isDeleted()
2enabled 가 있고 다름 → 제외isEnabled() (effective)
3deprecated 가 있고 다름 → 제외isDeprecated() (effective)
4q 가 있으면 searchable 중 null 아닌 값 하나라도 toLowerCase().contains(q 소문자)도메인이 넘긴 문자열

삭제 판정은 저장소가 이미 삭제 제외 조회(...IsDeletedFalse...)를 쓰는 곳은 그대로 두고, matches 도 방어적으로 같은 판정을 합니다. 활성 · 사용 중단을 effective 로 보는 이유는 화면 표시와 같게 하기 위해서입니다 — 부모 보드가 비활성이면 그 BIOS 는 화면에 "비활성" 으로 보이고, 비활성 칩에도 걸려야 합니다(§8 Q3).

4-4. 서비스 안의 순서 (BIOS 예)

findAllGrouped(query) ├── boards = query.includeDeleted ? 전체 보드 : 삭제 제외 보드 (저장소 · 기존) ├── allBios = findAllByBoardModel_IdIn(boardIds) (저장소 · 기존) └── 보드마다 ├── ofBoard = includeDeleted 필터 → versionRank 순 (기존) ├── latest = latestOf(ofBoard) (거르기 전 — F-1 · 세션 판정) ├── shown = ofBoard.filter(b → query.matches(b, 보드 모델명, 이름, 버전)) └── query.isFiltered() 이고 shown 이 비면 → 이 보드 묶음 제외 (조건 중에만 — F-3 · 세션 판정)

shown 은 ofBoard 의 순서를 그대로 두고 거르기만 하므로 순위 순서가 유지됩니다(§6 단위 테스트가 고정).

거르기가 메모리 판정인 이유 — 여섯 화면은 페이징이 없고 묶음을 이미 메모리에서 만듭니다. SQL 로 옮기면 도메인마다 Specification 이 한 벌씩(6 벌) 생기는데 얻는 것이 없습니다. S8-1 · S8-2 가 SQL 로 간 이유는 페이징의 총 건수가 DB 에서 세어져야 했기 때문이며, 이 화면에는 그 조건이 없습니다.
Primitive Obsession 점검 — 검색어 q 는 형식이 없는 사용자 입력이라 S8-1 과 같이 String 으로 둡니다. 활성 · 사용 중단은 Boolean 축(null = 전체)이고, 선택 파라미터는 기존 타입(Long · SubprogramKind 등)을 그대로 씁니다. 새 도메인 의미값은 생기지 않습니다.

8-2. 탈락 사유

D1 — Miller 는 고른 것의 하위만 보여 열이 작습니다. 쪽 이동이 세 열에 겹치면 선택 복원이 쪽 좌표까지 떠안아야 합니다.

D2 — C1 의 묶음 순서와 BIOS · BMC 의 운영자 순위가 그 자체로 뜻입니다. 정렬을 걸면 그 뜻이 흐려집니다.

D3 — 페이징이 없고 묶음을 이미 메모리에서 만듭니다. SQL 로 옮겨도 총 건수 같은 이득이 없고 Specification 6 벌만 생깁니다(§4 callout).

D4 — 축이 생명주기 플래그로 여섯 도메인에서 같습니다. 도메인마다 다른 것은 검색 필드뿐이고 그것은 서비스가 넘깁니다. 도메인별 record 는 같은 필드 넷을 여섯 번 복붙하게 됩니다.

D5 — S8-1 D13 은 "조회 띠는 화면마다 축이 달라 조각화하지 않는다" 였습니다. 이번에는 여섯 화면의 축이 정확히 같아 판단이 반대입니다. "갈라지는 시점에 분리" 원칙의 반대편 — 이미 같은 시점이므로 묶습니다.

D6 — 검색의 단위는 자원 한 건입니다. 조건에 맞는 항목이 없는 묶음을 그리면 눌러도 아무것도 없는 줄이 늘어나 소음이 됩니다.

D7 — 조건을 어기는 항목을 C3 에 계속 보이면 조건이 거짓말이 됩니다. 조용히 선택을 풀면 사용자는 왜 상세가 사라졌는지 모릅니다. 빈 상태 문구와 초기화 링크가 이유와 다음 행동을 함께 줍니다.

D8 — 걸러진 목록에서 끌어 놓으면, 보이지 않는 항목과의 상대 순서가 어떻게 되는지 사용자가 알 수 없습니다. 서버도 부분 목록을 받으면 누락 400 으로 거절합니다(F-2) — UI 가 먼저 막고 서버 검사는 안전망으로 남습니다.

D9 — 클릭 선택은 replaceState 로 URL 만 바꿔서, 서버가 렌더한 숨은 필드 값은 첫 클릭부터 낡습니다.

D10 — S8-2 이후 사용처가 이 여섯 화면뿐이고, 이번에 전부 폼 필드로 옮기므로 사용처가 0 이 됩니다.

D11 — ISO 는 OS 버전 아래 아코디언으로 한 단계 더 안쪽입니다. C2 에 걸리는 조건으로 ISO 를 찾으면 어느 항목이 왜 걸렸는지 화면에 드러나지 않습니다. S8-4 의 상세 조회 창에서 필드별 조건으로 봅니다.

8-3. 코드 대조에서 나온 보강 (전사 에이전트 발굴 · CP1 세션 판정 완료)

F-1 latest 표시는 거르기 전 목록으로 계산 — CP1 세션 채택 — BiosService 의 latest 는 BoardBiosCatalog.latestEnabled 이고, 같은 술어를 실행 엔진의 굽기 대상 해석이 부릅니다("화면이 보여주는 것과 실행이 고르는 것이 어긋나지 않는다" — 클래스 Javadoc). 브리프대로 "묶기 전에 거르기" 를 latestOf 앞에 두면, 검색으로 1 위 버전이 걸러진 순간 2 위 버전에 latest 가 붙습니다. 실행은 여전히 1 위를 고르므로 화면이 실행과 어긋납니다. 그래서 4-4 와 데모는 latestOf(ofBoard) 를 거르기 전에 두었습니다. BMC 도 같은 구조임을 세션이 확인했습니다(BmcService.latestOf — 순위 1 위 활성 · BIOS 와 대칭) — 둘 다 적용합니다.
F-3 빈 묶음 숨김은 조건이 걸렸을 때만 — CP1 세션 채택 — BIOS · BMC · Driver/Utility 는 지금 항목이 0 개인 보드도 C1 에 그리고, BIOS 는 그 보드의 C2 에 "+ BIOS 등록" 버튼을 둡니다. 조건이 없을 때도 빈 묶음을 숨기면 그 보드에 첫 BIOS 를 등록하는 진입점이 목록에서 사라집니다. 4-4 · 데모는 query.isFiltered() 일 때만 빈 묶음을 뺍니다. 삭제 포함만 켠 경우는 조건이 아니므로 숨기지 않습니다. Driver/Utility 의 공용 행도 같은 규칙(조건 중 비면 숨김 · 보이면 첫 행)으로 적었습니다.
F-2 순위 PATCH 의 서버 가드 — "조건 중" 을 아는 가드는 없습니다(서버는 조건을 모릅니다). 조건 중 화면이 보낼 수 있는 부분 목록은 누락 400(InvalidVersionRankRequestException.incomplete())으로 거절됩니다. 조건과 무관하게 살아 있는 행 전부를 담은 직접 PATCH 는 정당한 요청이라 204 입니다. 새 가드는 더하지 않습니다(§9 B4 가 이 판정을 확인).
F-4 BIOS · BMC 의 C1 개수 — R2 의 "C1 머리에 맞는 항목 수" 는 BIOS C1 에 기존 표시가 없어 신설이 됩니다. 조건이 걸렸을 때만 보입니다(CP1 세션 판정 — 평소 화면은 지금과 같게 두고, 개수는 "조건에 몇 개가 맞았나" 를 알려 줄 때만 뜻이 있다). 데모는 설명을 위해 항상 보입니다.
F-5 목록 밖 호출부 — BoardModelMetadataService.findAllGrouped(false) 를 BIOS 보드 선택 폼과 Driver/Utility 신규 폼이 부릅니다. 시그니처를 바꾸면 이 호출부가 "조건 없음 · 삭제 제외" 를 표현할 방법이 필요합니다 — 정적 생성자 ResourceListQuery.unfiltered(boolean includeDeleted) 로 호출부가 "조건 없음" 을 표현합니다(CP1 세션 판정 — 오버로드를 두면 같은 조회가 두 입구를 갖는다).

8-4. 주의

effective 값으로 판정합니다 — 부모가 비활성이면 자식도 비활성으로 보이고 비활성 칩에 걸립니다(화면 표시와 같음). Driver/Utility 의 공용 범위 묶음은 첫 행 고정을 유지합니다. BIOS · BMC 의 selectedBoardId 호환 파라미터는 유지합니다.

Q1상태 변경 뒤 조건 유실 — 여섯 도메인의 리다이렉트를 "조회 조건 + 선택 보존" 으로 맞출지 / 알려진 비대칭으로 남길지이번에 맞춘다 — 상태 변경 폼에 숨은 필드 returnQuery 하나 · *ControllerSupport 에 한 인자

Q3활성 칩의 판정 기준effective (대안 own)

Q1 풀이 — 활성화 · 삭제 같은 조작 뒤 리다이렉트가 도메인마다 선택 상태를 다르게 잃습니다(OS 만 3 축 보존 — §1 callout). 여기에 조건이 붙으면 조작 한 번에 필터가 풀립니다. 권고안은 상태 변경 폼에 현재 목록 질의를 숨은 필드 returnQuery 하나로 싣고, 각 컨트롤러가 리다이렉트에 붙이는 방식입니다. 비용은 도메인 여섯 × 조작 5 ~ 6 입니다.

Q3 풀이 — own 으로 판정하면 부모 보드가 비활성이라 화면에 "비활성" 으로 보이는 BIOS 가 "활성" 칩에 걸립니다. 보이는 것과 걸리는 것이 달라지므로 effective 를 권고합니다.
