§1. 현재 상태 (진단)

이 문서는 상위 계획서 plan/26-08-10_12-43-50_MK4-3_plan.html 아래의 구현 슬라이스 계획서다. 진단 · 기준 · 분할 결정은 그 우산 문서가 담고 있고, 여기서는 그 결정 위에서 실제로 무엇을 만들지를 다룬다.

점검의 동작을 좌우하는 값 일곱이 application.properties 에 있어 운영자가 바꿀 수 없다. 그중 실행 시점에 읽혀 즉시 효과가 나는 다섯이 이 슬라이스의 대상이다.

설정 키무엇을 정하나기본값값을 언제 읽나이 슬라이스
reconciliation.auto-apply.kinds점검 도중 시스템이 사람 확인 없이 스스로 처리할 드리프트 종류. 여기 없는 종류는 발견만 하고 그대로 둔다빈 값점검마다대상
reconciliation.resolution-enabled드리프트를 고치는 행위 전체의 차단기. 끄면 수동 [해결] 과 점검 중 자동 처리가 모두 멈추고 탐지만 계속한다true해결 요청마다 · 점검 자동 처리 직전대상
reconciliation.report.retention-count점검 보고서를 몇 회분까지 남길지. 넘으면 오래된 것부터 지운다100점검 끝 정리 시대상
reconciliation.scan.extra-roots기본 점검 범위(활성 자원이 등록된 폴더들) 밖에서 추가로 뒤질 경로. 백업 폴더처럼 자원을 옮겨 두는 자리를 범위에 넣어 '자원 소실' 대신 '경로 이동됨' 으로 잡히게 한다빈 값점검 시작 시대상
reconciliation.scan.startup-enabled애플리케이션이 뜬 직후 한 번 점검할지. 꺼져 있는 동안 디스크가 바뀌었을 수 있어 기동 시 한 번 맞춰 본다true기동 시 1 회대상 (효과 시점 명시)

reconciliation.scan.deep-interval-ms정밀 점검을 얼마나 자주 돌릴지. 정밀 점검은 파일 내용의 지문까지 다시 계산해 변조를 잡는다24 시간기동 시 고정MK4-3-2

두 가지가 더 있다.

자동 처리가 사실상 꺼져 있다

다섯 종류가 무인 처리 대상으로 설계돼 있는데(해결 등급 AUTO) 기본값이 빈 값이라 아무것도 자동으로 처리되지 않는다. 그런 선택지가 있다는 사실조차 화면에 없어, 마커 한 장 지우면 끝나는 정리까지 매번 손으로 눌러 왔다.

설정 키 이름이 사용자 문구에 드러난다

첫 화면의 점검 범위 안내가 reconciliation.scan.extra-roots 를 코드 조각으로 보여 주면서 정작 바꿀 방법은 주지 않는다. 같은 키가 자원 소실 종류의 "직접 해야 할 일" 문구에도 하드코딩돼 있다.

선례의 구멍이 이 슬라이스의 전제다 — 상위 계획서가 밝힌 대로, 휴지통 설정은 주기를 데이터베이스에 저장하고 화면에서 바꾸게 해 두었으나 실행부가 시작 시점에 값을 고정해 실제로는 적용되지 않는다. 화면이 거짓말하는 상태를 하나 더 만들지 않는다.
§2. 요구사항 (확정) + 비목표

요구사항

#내용
R1§1 표의 다섯을 데이터베이스로 옮기고 설정 화면에서 조작하게 한다.
R2자동 처리 기본값을 켠다. 되돌릴 수 있는 네 종류를 켜고 되돌릴 수 없는 하나는 끈다.
R3자동 처리 후보 목록은 종류의 해결 등급에서 파생한다. 화면에도 설정에도 종류 이름을 하드코딩하지 않는다. 각 후보 옆에는 그 종류를 자동으로 맡기면 시스템이 무엇을 하는지와 되돌릴 수 있는지를 함께 보인다 — 문구는 종류가 이미 들고 있는 값(DriftKind 의 해결 설명 · reversible)에서 온다.
R4설정 키 이름이 드러나는 두 자리를 설정 화면 안내로 바꾼다.
R5시스템 해결 차단이 꺼져 있으면 목록 화면에 상시 배너로 알린다.
R6기동 직후 점검은 화면에 두되 "다음 기동부터 적용" 을 명시한다.
R7점검 주기 두 항목은 화면에 읽기 전용으로 보여 주고 바꾸는 방법을 안내한다. 조작 가능한 모습으로 두지 않는다.
R8각 항목 옆에 그 설정이 무엇을 정하는지 한 문장으로 적는다. 설정 이름만으로는 무엇이 달라지는지 알 수 없는 항목이 대부분이라(예 : "해결 차단" 이 탐지까지 멈추는지 아닌지), 문구가 없으면 운영자가 값을 바꾸기를 주저하거나 잘못 바꾼다. 문구는 §1 표의 "무엇을 정하나" 열을 그대로 쓴다 — 문서와 화면이 같은 문장을 보게 해 드리프트를 만들지 않는다.
비 목표 :
  • 점검 주기를 바꿀 수 있게 만들지 않는다. 실행 구조를 바꾸어야 하므로 MK4-3-2 소관이다.
  • 점검 로직 자체는 바꾸지 않는다. 무엇을 어떻게 탐지하고 해결할지는 그대로 두고, 그 동작을 좌우하는 값을 운영자가 다루게 하는 데까지다.
  • 화면 배치와 디자인은 최소로 한다. MK4-4 가 화면을 전면 개편하므로 휴지통 설정 화면의 폼 관례(n-form-group · n-form-banner)를 그대로 쓰고 새 배치를 고안하지 않는다.
  • 휴지통 설정과 통합하지 않는다.
  • 휴지통의 주기 미적용 문제를 고치지 않는다.
🎬 미리보기 — 라이브 UX 데모

두 가지를 체험시킨다. 데모 A 는 자동 처리 기본값을 어디까지 켤 것인가(R2 · D2), 데모 B 는 해결 차단을 끄면 화면에서 무슨 일이 벌어지는가(R5 · D6)다. 두 데모의 판정 JS 는 서버가 같은 자리에서 내리는 판정과 같은 식을 쓴다.

데모 A — 자동 처리 기본값을 어디까지 켤 것인가

해결 등급이 AUTO 인 다섯 종류다. 각 행의 [켬] · [끔] 을 눌러 보면 저장될 목록이 아래에서 라이브로 바뀐다. 되돌릴 수 없는 종류를 켜면 경고가 뜬다.

묶음 조작 : 
// 서버 기본값 산정과 동일 — 되돌릴 수 있는 것만 기본으로 켠다
function demoDefaultOn(kind) { return kind.reversible; }
드리프트 0 — 데모의 기본값 판정 = 서버의 초기 행 산정 = DriftKind.isReversible() 단일 소스. 후보 목록 자체도 DriftKind.isAutoApplicable() (해결 등급 AUTO)에서 파생하므로 종류가 늘면 화면이 저절로 따라온다(R3).

데모 B — 해결 차단을 끄면 무슨 일이 벌어지는가

아래 [해결 허용] · [해결 차단] 을 바꾸면 배너 · [해결] 버튼 · 점검 중 자동 처리 셋이 함께 바뀐다. 차단 상태에서 [배너 없이 보기] 를 눌러 배너만 지워 보면, 화면 어디에도 꺼져 있다는 단서가 남지 않는다는 것을 볼 수 있다. 이 데모의 목적이 바로 그것이다 — 왜 배너가 필요한가.

시스템 해결 :
화면 (체험용) :
드리프트 0 — 데모의 버튼 disable 판정 = 서버 가드 = ReconciliationSettingsService.isResolutionEnabled() 단일 소스. UI 가 먼저 막고(사유 tooltip), 서버 가드는 direct POST 같은 비정상 경로의 안전망으로 남는다.

§4. 도메인 모델 (SSOT)

ReconciliationSettings — 단일행 엔티티

maintenance/reconciliation/entity. 휴지통의 TrashSettings 와 같은 모양이며 BaseTimeEntity 를 상속한다.

필드타입뜻
idLong단일행 고정 식별자
autoApplyKindsString자동 처리 대상 종류 이름의 콤마 구분 목록
resolutionEnabledboolean시스템 해결 전체 허용 여부
reportRetentionCountint보고서 보관 개수
extraScanRootsString추가 점검 경로의 줄바꿈 구분 목록
startupScanEnabledboolean기동 직후 1 회 점검 여부
문자열은 저장 형식일 뿐 계약이 아니다. 컬럼은 문자열이지만 서비스가 노출하는 타입은 Set<DriftKind> 와 List<Path> 이고 호출부는 문자열을 보지 않는다. 파싱과 조립은 서비스 안에 가둔다. 휴지통 설정이 알림 D-day 목록을 같은 방식으로 다루는 선례가 있다.

DTO

  • ReconciliationSettingsRequest — 요청 record. @NotNull · @Min(1) · 경로 형식 검증.
  • ReconciliationSettingsResponse — 화면용. 현재 값 + 자동 처리 후보 목록(종류 · 라벨 · 되돌릴 수 있는가 · 해결이 하는 일) + 읽기 전용으로 보여 줄 주기 두 값을 담는다.
    항목 설명 문구도 이 응답이 싣는다(R8). 템플릿에 문장을 직접 쓰면 문서 · 화면 · 코드가 각자 다른 말을 하게 되므로, 설명은 항목을 정의한 자리 하나에서 온다 — 자동 처리 후보의 설명은 DriftKind 가 이미 들고 있는 값을 그대로 쓰고, 나머지 다섯 항목의 설명은 설정 항목을 열거하는 자리에 둔다. 새 항목이 늘면 설명도 같은 자리에서 함께 늘어난다.

§8. 결정 · Open Questions

상위에서 내려온 확정 (근거는 상위 계획서 §8)

#결정
D1화면에 올릴 자격은 "그 값이 실행 시점에 읽혀 즉시 효과가 나는가". 휴지통 선례가 주기를 저장하고도 적용하지 못한 채 남아 있다. 화면이 거짓말하는 상태를 하나 더 만들지 않는다.
D2자동 처리 기본값은 "되돌릴 수 있는가" 로 정한다. 새 축을 만들지 않고 종류가 이미 든 성질을 쓴다.
D3자동 처리 후보는 종류의 해결 등급에서 파생한다. 과거 네 종류를 화면 세 곳에 하드코딩했다가 서버 다섯 종류와 갈라져 버튼이 누락된 사고가 있었다.
D4추가 점검 경로는 줄바꿈 구분. 콤마는 경로에 콤마가 들어가면 깨진다. 존재하지 않는 경로는 거절하지 않고 경고만 표시한다 — 아직 마운트되지 않은 백업 경로를 미리 등록하는 것이 정당한 운영이다.
두 목록의 구분자가 다른 것은 값의 성질이 다르기 때문이다. 자동 처리 대상은 열거형 이름이라 콤마가 값 안에 들어올 수 없어 콤마로 두고, 경로는 콤마를 품을 수 있어 줄바꿈으로 둔다. 한쪽으로 통일하면 경로가 깨지거나(콤마) 열거형 목록이 이유 없이 여러 줄이 된다(줄바꿈).
이관 규칙 — 현행 설정 파일의 경로 값은 콤마 구분으로 파싱되고 있다. 초기 행을 만들 때 그 값을 콤마로 끊어 줄바꿈으로 다시 잇는다. 이관은 초기 행 생성 시 한 번뿐이며, 이후 입력은 줄바꿈만 받는다.
D5저장 형태는 단일행 엔티티. 자동 처리 대상은 조인 테이블 대신 이름 목록 문자열. 종류는 코드의 열거형이 SSOT 라 테이블로 정규화해도 참조 무결성을 얻지 못한다.

이 슬라이스의 결정

D6 — 해결 차단은 상시 배너

해결 차단이 꺼진 사실을 목록 화면에 상시 배너로 알린다. 이 스위치는 탐지는 계속하되 고치는 행위만 전부 멈추는 비상 차단기다. 수동 [해결] 과 점검 중 무인 처리 양쪽을 막고, 삭제 거절 뒤의 "위치 정정 후 삭제" 흐름만 사용자 명시 액션이라 통과한다. 비상 차단기는 켤 수 있어야 의미가 있으므로 설정 파일에 남기지 않고, 켜 둔 사실이 계속 보여야 잊히지 않으므로 배너로 알린다.

비채택 — 확인 창으로만 알리기(끈 순간에만 보이고 이후 잊힌다) · 설정 파일에 남기기(비상시에 못 쓴다).

D7 — 기동 직후 점검은 효과 시점 명시

값이 다음 기동에만 효과가 난다는 점에서 D1 의 기준과 부딪히는 것처럼 보이지만, 효과 시점이 분명히 안내되면 화면은 거짓말하지 않는다. 조작 가능한 모습으로 두되 "다음 기동부터 적용" 을 붙인다.

D8 — 점검 주기는 읽기 전용

아예 감추면 운영자가 그 값의 존재를 모르고, 입력 요소로 두면 바꿀 수 있다고 오해한다. 값을 보여 주되 조작 요소가 아니게 하고 "이 항목은 다음 단계에서 화면으로 옮겨진다" 를 안내한다.
