§1. 현재 상태 (진단)

OS 설치 단계의 파티션 행(PartitionRequest)은 대상을 장치명 자유 문자열 diskName(선택 — 비우면 설치기 자동)으로 가리킨다. 폼 ‘디스크명’ 열 · 상세 ‘디스크’ 열 · LinuxPartitionRules.validateGrowPerDisk(같은 그룹당 grow 1) 만이 사용처이고 정의서 밖 소비자는 없다(kickstart · autoinstall 렌더는 E 영역). 운영자가 sda 를 손으로 치지만 그 장치의 실존 여부는 아무도 확인하지 않는다(U4-1 토론 1 회차 §1-1). 사용자 확인(2026-08-19) — 값이 든 저장본은 전부 테스트 데이터다.

U4-1-1 · U4-1-2 로 정의서는 볼륨과 역할을 갖게 됐고, 역할(OS 고정 / 우선순위에 따름 / Data / 없음)과 우선순위가 OS 볼륨 하나를 고른다. 토론 E8 · E14 는 OS 설치기가 OS 영역만 파티셔닝하고 Data 영역은 설치 이후 OS_SETTING(U4-1-4)이라고 정했다 — 그래서 파티션이 놓이는 곳은 언제나 OS 영역 볼륨 하나이고 행마다 고를 값이 없다.

토론이 남긴 정의는 “파티션 대상을 장치명 → 역할로, 파티션 표의 ‘디스크’ 열 교체”(2 · 4 · 6 회차)였다. 실측하니 ‘역할’ 은 OS 영역 하나뿐이라, 열을 교체할 것이 아니라 없애고 표 위에 대상을 밝히는 것이 층을 올리는 일이다.

붙일 자리

PartitionRequest · LinuxPartitionRules · InvalidPartitionException · 폼 파티션 표 · 상세 fragment · JS(onGrowChange · builder · prefill). 용량 사전 제한이 RaidLevel(MA7 자원 enum) · DiskGroupRuleRequest · RaidConfigurationRequest · LinuxInstallationRequest · SettingSaveRequest 를 더 건드린다. DDL · phase · 자원 신설은 없다.

§2. 요구사항 (확정) + 비목표
  1. 파티션 표에서 ‘디스크명’ 열 제거 — 대상은 OS 영역 볼륨(상수).
  2. 표 위 대상 볼륨 안내 줄 — 네 문구(RAID 구성 없음 · 묶음 0 → “설치기가 자동 선택” / OS 고정 N번 묶음 / 우선순위 1 순위 볼륨 / OS 후보 없음 → 저장 불가). 폼은 즉시 갱신하고 상세도 같은 문구.
  3. grow 규칙을 “OS 영역 볼륨은 하나 → grow 는 목록에 1 개” 로.
  4. diskName 은 필드 · 열 · 검증을 전부 제거한다. 구 payload 에 값이 있어도 역직렬화가 무시한다(테스트 데이터뿐).
  5. OS 영역 용량 사전 제한 — 하한을 알 수 있을 때만 고정 파티션 크기 합이 그 하한을 넘으면 막고, 자동 탐지 · RAID 구성 없음이면 “실행 시 확인” 으로 안내만 한다.
  6. 왕복 보존 · 판정 메서드 미유출.
비 목표
  • OS 영역 볼륨 → 설치기 장치(kickstart --ondisk 등) 매핑 — E 영역.
  • Data 영역 파티셔닝 — U4-1-4.
  • 파티션의 다중 볼륨 분산 — LVM 범위 밖(D9).
  • Windows — 파티션 없음.
🎬 미리보기 — 라이브 UX 데모

왼쪽 RAID 구성 단계 상태를 바꾸면 오른쪽 대상 볼륨 안내 줄이 즉시 바뀐다. 파티션 표에는 디스크명 열이 없고, Grow 를 두 곳에 켜면 두 번째 행이 오류가 된다. 크기는 직접 고칠 수 있다 — ⓒ 에서 합을 500 GiB 로 올리면 OS 영역 최소 용량(480 GB ≈ 447 GiB)을 넘어 막히고, 용량이 자동 탐지인 ⓔ 에서는 같은 값도 통과한다. 규칙 → 볼륨 매칭과 볼륨 → 설치기 장치 매핑은 E 의 몫이라 데모는 정의서가 적는 것까지만 그린다.

§3. URL / 데이터 흐름
새 URL 없음. POST · PUT /provisioning/setting 의 OS 설치 항목에서 partitions[].diskName 이 사라진다 — 폼은 보내지 않고, 구 payload 에 남아 있어도 역직렬화가 무시한다. 단계 간 정합 검사가 하나 늘어 400 의 필드가 partitionsWithinOsVolume 로도 온다.

payload 예 (저장 그대로)

{"type":"OS_INSTALLATION","osFamily":"RHEL_BASED","osMetadataId":1,"isoId":1,
 "partitions":[{"mountPoint":"/boot/efi","fileSystem":"EFI","size":1,"sizeUnit":"GB","isGrow":false},
               {"mountPoint":"/","fileSystem":"XFS","size":0,"sizeUnit":"GB","isGrow":true}], "...":"…"}

흐름

  1. 폼 — RAID 카드의 역할 · 용량 · 개수 · 행 추가 · 삭제 · 카드 유무(applyDiskGroupConstraints 끝)와 파티션 표의 크기 · 단위 · grow 가 바뀔 때마다 refreshOsVolumeTargetHint() 가 안내 줄 두 줄을 다시 쓴다. 재료는 두 카드의 DOM — 레벨 옵션의 data-usable-a · data-usable-b 포함.
  2. 제출 — stepBuilders.OS_INSTALLATION 이 diskName 을 싣지 않고, precheck 가 grow 2 개와 용량 초과를 막는다.
  3. 서버 — PartitionRequest 에 diskName 이 없다(구 payload 의 값은 Jackson 기본 FAIL_ON_UNKNOWN_PROPERTIES=false 로 무시). validateSingleGrow → InvalidPartitionException.multipleGrow 400 · isPartitionsWithinOsVolume → 400.
  4. 상세 — SettingDetailResponse.osVolumeTarget() 이 안내 줄(용량 하한 포함)을 주고, 파티션 표는 4 열.

용량을 알 수 있는가 (사전 제한의 적용 범위)

  • OS 고정 묶음 · 용량 직접 지정 → 하한 = usableDisks(n) × 1 장 용량.
  • 우선순위에 따름 · 후보 전부 직접 지정 → 하한 = 후보 하한의 최솟값(어느 볼륨이 뽑혀도 그만큼은 된다).
  • 후보 중 하나라도 용량 ‘자동 탐지’ · RAID 구성 없음 → 모른다. 검사 없이 “실행 시 확인” 만 안내.
단위와 정밀도 — 파티션은 이진 단위(MiB · GiB · TiB), 디스크는 십진 단위(GB · TB)라 바이트로 환산해 비교한다. RAID 메타 · 파티션 테이블 · 파일시스템 오버헤드는 셈하지 않는다 — 명백한 초과만 막는 1 차 관문이고 실제 볼륨으로 하는 최종 검사는 E 의 몫이다.

§7. 예외 계층

신규 예외 클래스 없음. InvalidPartitionException(400 · field partitions — 폼의 파티션 그룹 컨테이너가 받는다) 의 팩토리를 교체한다 — multipleGrowOnDisk 제거 → multipleGrow 신설. 용량 사전 제한은 Bean Validation(@AssertTrue)으로 400 — isOsVolumeDeterminable 과 같은 자리라 별도 예외를 두지 않는다.

D3grow 규칙목록당 1디스크 그룹당 1 유지
D4안내 줄의 재료OsVolumeTargets.describe(서버) · 폼 JS 는 같은 4 분기폼 문구 하드코딩만
D5상세 파생SettingDetailResponse.osVolumeTarget()컨트롤러 모델 속성 · fragment 안 Thymeleaf 계산
D6스키마DDL · phase 없음—
D7용량 사전 제한정의서가 아는 하한까지만(자동 탐지 · RAID 없음은 실행 시)검사 없음(실행 시에만) · 자동 탐지도 막기

D1 — 대상이 OS 영역 하나라 select 는 선택지가 하나인 노이즈이고, 장치명 병기는 정의서를 다시 하드웨어에 묶는다. D2 — 실 저장본에 값이 없으니 지킬 것이 없다. 남기면 코드만 남는다. D3 — 볼륨이 하나면 “디스크당” 은 뜻이 없다.

D4 — 같은 4 분기를 서버가 갖고 폼이 따라 하면 데모 · 상세 · 폼 문구가 한 SSOT 다(hasOsFixedRule · hasByPriorityRule 재사용). D5 — 응답 record 의 파생 메서드가 fragment 에서 가장 가깝고, 컨트롤러가 도메인 판정을 하지 않는다.

D7 — 검사를 실행으로 미루면 저장하고 한참 뒤 프로비저닝에서 실패한다. 반대로 자동 탐지까지 막으면 근거 없이 막는 것이다 — 계산할 수 있는 하한이 있을 때만 1 차로 거르고 나머지는 실행이 본다.
