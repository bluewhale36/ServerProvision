§1. 배경

사용자 지시 (2026-11-21)

프로비저닝 단계를 추가할 때 'OS 설치' 를 쓰면, 'RAID 구성' 이 없을 경우 자동으로 추가합니다.

이어서 사용자 결정: OS 설치가 있는 동안 RAID 구성의 [단계 제거] 를 비활성 + 사유 tooltip 으로 막습니다(UX 모순은 UI 1차 차단).

왜 둘이 묶이는가

OS 설치는 설치 디스크를 RAID 구성의 OS 영역 볼륨(그 볼륨의 인벤토리 WWN)으로 정합니다(Windows · RHEL 공통). 그래서 HF32(PR #112)가 SettingSaveRequest.isOsVolumeDeterminable 로 RAID 구성 없는 OS 설치 정의서를 저장 때 거절합니다.

지금 겪는 일

  • 사용자가 OS 설치만 추가하고 [저장] 을 눌러야 OS 설치 카드의 안내 줄(oiOsVolumeRequirementHint)과 강조로 막혔음을 압니다. RAID 구성을 찾아 다시 추가해야 합니다.
  • RAID 구성을 빼도 아무 표시 없이 빠지고, 저장 때 다시 막힙니다.

§3. 결론 (요구사항)
ID요구
R1사용자가 [+ OS 설치] 를 누르면, RAID 구성 카드가 없을 때 RAID 구성 카드를 먼저 연 뒤 OS 설치 카드를 연다. 둘 다 펼친 상태. RAID 구성은 처음 열 때의 기본값(우선순위 기본 행)을 그대로 채운다
R2OS 설치 카드가 있는 동안 RAID 구성 카드의 [단계 제거] 는 비활성 + tooltip "OS 설치 단계가 있으면 이 단계를 제거할 수 없습니다. OS 설치 단계를 먼저 제거해야 합니다."
R3OS 설치를 제거하면 RAID 구성의 [단계 제거] 가 다시 활성. RAID 구성 카드는 남는다(자동으로 빼지 않음)
R4수정 화면이 저장본을 불러올 때는 자동 추가하지 않는다. 저장본을 조용히 바꾸지 않기 위함. 옛 정의서(OS 설치만)는 지금처럼 저장 때 HF32 안내로 막힌다. 제거 잠금(R2)은 불러온 뒤에도 같은 규칙으로 맞춘다
R5서버 저장 검증(HF32 가드)은 바꾸지 않는다
R6묶음 규칙 · OS 볼륨 후보는 채우지 않는다. RAID 구성만 추가된 상태로 저장하면 지금처럼 묶음 안내로 막힌다
§4. 설계 · 결정
채택 : 선행 단계를 enum 에 선언하고 폼이 그 선언을 읽습니다.

SettingProcessType

  • 선행 단계 속성 추가: OS_INSTALLATION 의 선행 = RAID_CONFIGURATION, 나머지는 없음.
  • 접근자는 Optional<SettingProcessType> requiredStep().
  • Javadoc 은 "실행이 이 단계를 하려면 앞서 있어야 하는 단계. 폼이 추가 · 제거 때 맞춘다. 서버 저장 검증은 HF32 isOsVolumeDeterminable 이 내용까지 본다." 정도로 짧게.

템플릿

  • 단계 추가 버튼에 th:data-step-requires="${type.requiredStep().map(...).orElse(null)}" 류로 선행 타입 이름, data-step-name 에 화면 이름. 정확한 식은 구현 때. 템플릿의 T(...) 정적 호출은 DesignConventionTest 가 막으므로 쓰지 않음.
  • 카드 4 개의 [단계 제거] 를 조각 하나 stepRemoveButton 으로 추출(같은 마크업 4 번 복사 해소). 조각은 <span class="n-btn-tooltip-wrap" data-tooltip-active="false" data-step-remove-wrap> 안에 버튼을 둔다.
  • 사유 문구는 메시지 키 하나 setting.process.remove.blocked = "{0} 단계가 있으면 이 단계를 제거할 수 없습니다. {0} 단계를 먼저 제거해야 합니다." 를 폼 요소의 data 속성으로 한 번 내리고, JS 가 {0} 을 뒤따르는 단계의 화면 이름으로 채운다.

setting-form.js

  • 추가 버튼 클릭 → addStepWithRequired(type): 선행 타입이 있고 그 카드가 닫혀 있으면 선행부터 addStep. 클릭 경로만 이 함수를 쓰고 pre-fill 은 지금처럼 addStep 직접(R4).
  • syncRemoveLocks(): 열린 카드마다 "열린 카드 중 이 타입을 선행으로 둔 것" 이 있으면 [단계 제거] 비활성 + tooltip 켬, 없으면 해제. addStep · removeStep 끝과 pre-fill 말미에서 부른다.
  • 단계 이름 · 선행 관계를 JS 에 적지 않는다(타입 문자열 분기 없음).

비채택 대안

대안탈락 사유
B. JS 에 if (type === 'OS_INSTALLATION') addStep('RAID_CONFIGURATION') 하드코딩선행 관계가 화면 코드에만 있게 됨. 팔레트 노출을 enum 속성으로 옮긴 R11 D-R4 와 반대. 의존이 늘 때마다 분기가 자람(분기 확장 금지)
C. 서버가 저장 때 RAID 구성을 끼워 넣기사용자 데이터를 조용히 바꿈. 묶음이 없어 어차피 HF32 에 막힘
D. RAID 구성을 빼면 OS 설치도 함께 빼기(연쇄 제거)사용자가 입력한 OS 설치 내용을 잃음. 사용자 결정은 막기(R2)
E. 수정 화면 pre-fill 에서도 자동 추가저장본과 다른 화면을 보여 줌. 옛 정의서는 저장 때 HF32 안내가 원인을 알려 줌
F. 서버 가드를 enum 선행 관계로 다시 쓰기가드는 RAID 구성의 내용(묶음 · 후보 · 직결)까지 보며 존재 여부는 그 일부. 고칠 이유가 없는 코드를 건드림(R5)

적대적 점검

  • SSOT: 폼의 선행 관계는 enum 하나에서 옵니다. 서버 가드는 존재 여부를 포함한 더 강한 조건이라 어긋날 수 없습니다(폼이 RAID 를 넣어도 묶음이 없으면 서버도 폼도 같은 문구로 막음).
  • 자동 추가가 사용자를 놀라게 하는가: RAID 구성 카드가 OS 설치 카드 바로 위에 펼쳐져 보이고, OS 설치 카드의 기존 안내 줄이 RAID 묶음을 정하라고 말합니다. 새 안내 문구는 더하지 않습니다.
  • <summary> 안 버튼을 span 으로 감쌀 때: 기존 클릭 처리(preventDefault · stopPropagation)는 버튼에 그대로 걸립니다. 비활성 버튼은 클릭이 오지 않으므로 카드 접힘 토글만 일어나는지 CP5 에서 확인합니다.
