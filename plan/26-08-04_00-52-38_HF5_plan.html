§1. 현재 상태 (진단)

이 슬라이스가 어디서 나왔는가

MK4 reconciliation 사용성 진단(2026-08-02 ~ 08-03)에서 개선 후보 28 건과 진단 범위 밖 부수 관찰 3 건이 나왔고, 사용자가 전부 채택했다. 그중 reconciliation 화면 레이아웃 개편과 무관하고 전역 공용인 결함 4 건을 먼저 떼어 처리하는 것이 이 슬라이스다. 나머지 후보는 MK4 후속 슬라이스에서 정보 정의 → 데이터 모델 → 레이아웃 개편 순서로 다룬다.

4 건 모두 샌드박스에서 실제로 화면을 조작해 확인한 것이며, 추정이나 코드 읽기만으로 잡은 것이 아니다.

결함 4 건 — 관찰과 원인

#화면에서 보이는 것원인
① 없는 주소로 가면 404 Internal Error, 잘못된 폼을 보내면 400 Internal Error. 본문은 둘 다 "알 수 없는 오류가 발생했습니다." error.html 이 ${statusLabel} ?: 'Internal Error' 로 렌더한다. statusLabel 은 WebExceptionHandler.populate 만 채우므로, Spring Boot 기본 /error 경로(핸들러가 없는 404, 바인딩 실패 400 등)로 들어온 요청은 이 값이 비어 fallback 리터럴이 그대로 나온다. 상태 코드는 맞게 표시되는데 라벨만 항상 "Internal Error" 라서 서로 모순된 한 줄이 된다.
② 확인창에 '경로 이동됨' 드리프트 을(를) 적용할까요, Ubuntu 24.04 Ubuntu-24.04-live.iso 을(를) 복구할까요 문구 템플릿이 여덟 곳 이상에 흩어져 있다. 다만 그중 bios-setting-detail.js 를 뺀 전부가 ConfirmModal.composeMessage(form, template, defaultMessage) 한 함수를 거쳐 {resource} 를 자원명으로 치환한다 — 치환 지점이 하나인 것이 이 결함의 지렛대다.
③ 내용 변경 수용에서 입력해야 할 이름은 Rocky Linux 9.6 Rocky-9.6-x86_64-dvd.iso 인데 입력창에는 자원명 입력 : Rocky Linux 까지만 보인다. 보이는 대로 입력하면 거절되고, 그 거절 메시지가 기대값 전문을 알려준다. 이 폼만 기대 이름을 placeholder 에 넣었다 (th:placeholder="|자원명 입력 : ${drift.displayName}|"). 같은 저장소에 올바른 선례가 이미 있다 — 휴지통 영구삭제 확인 modal 은 기대 이름을 <code th:text="${expectedName}"> 로 화면 본문에 노출한다. 두 곳이 갈라진 것이 결함의 실체다.
④ 폼 마커(_allowCreateDirectory)가 빠진 직접 요청에서 배너에 … allowCreateDirectory — Failed to convert value of type null to required type boolean; … 저장소에 messages.properties 도 MessageSource 설정도 없다. 그래서 Spring 의 기본 typeMismatch 메시지가 영어 원문 그대로 나온다.
④ 에서 정상 동작하는 부분 — 오류가 조용히 삼켜지지 않고 배너로 표면화되는 것은 이전에 고쳐진 부분이 제대로 동작하는 것이다. 남은 문제는 문구가 영어 원문이라는 것뿐이며, 이번 슬라이스는 그 한 가지만 다룬다.
공통 성격 — 4 건 모두 도메인 로직이 아니라 사용자에게 보이는 문구의 문제다. 엔티티 · Repository · 스키마 변경이 없고, 신규 URL 도 없다. 그래서 12 단계 중 6 · 7 · 9 단계가 해당 없음이 된다(§5).
§2. 요구사항 (확정) + 비목표

① 오류 페이지 상태 문구를 상태 코드에서 파생한다

  1. 상태 코드 → 한국어 문구 조회를 단일 소스로 만들고, Spring Boot 기본 /error 경로와 WebExceptionHandler advice 경로가 그 하나를 함께 쓴다.
  2. ErrorStatusLabels(신규, global/exception/) — 상태 코드 → 한국어 문구 조회. 표 조회이고 분기 증식이 아니며, 미등록 상태는 기본 문구로 떨어진다.
  3. ProvisionErrorAttributes(신규, DefaultErrorAttributes 상속, @Component) — Spring 이 제공하는 확장점이다. 기본 /error 경로의 오류 속성에 statusLabel 을 항상 채운다.
  4. WebExceptionHandler.populate — 지금 넘기는 영어 reason phrase("Conflict" 등)를 같은 ErrorStatusLabels 조회로 바꿔 두 경로의 문구를 일치시킨다.
  5. error.html — fallback 리터럴 'Internal Error' 제거. 표기는 한국어 문구가 주가 되고 코드가 괄호로 따라오는 형태 (페이지를 찾을 수 없습니다 (404))로 바꾼다.

② 병기형 조사를 치환 지점 한 곳에서 해소한다

  1. 치환 이후 문자열에서 "앞 단어 + 병기형 조사" 패턴을 일반적으로 해소하는 공용 함수를 만들고, composeMessage 가 마지막에 한 번 통과시킨다.
  2. korean-particle.js(신규, static/global/) — window.KoreanParticle.resolve(text). 지원 쌍은 을(를) · 이(가) · 은(는) · 와(과) · 으로(로) · 아(야).
  3. 여덟 파일 중 실제로 고치는 것은 confirm-modal-base.js 하나이며, bios-setting-detail.js 는 같은 함수를 직접 부른다.
  4. 앞으로 누가 새 문구에 을(를) 을 써도 자동으로 해소된다 — 새 문구 작성자가 별도 규약을 알 필요가 없다.

③ 자원명 확인의 기대값을 본문에 노출한다

  1. 휴지통 영구삭제 확인 modal 의 선례를 따른다 — 기대 이름을 본문에 텍스트로 노출하고 placeholder 는 짧게 둔다.
  2. 결과적으로 "한 번 틀린 뒤 복사해서 붙여넣기" 가 아니라, 처음부터 기대값을 보고 입력할 수 있게 된다.

④ 바인딩 오류 문구를 한국어로 바꾼다

  1. Spring 이 이미 제공하는 방법을 쓴다. src/main/resources/messages.properties 를 신설하면 Spring Boot 의 MessageSourceAutoConfiguration 이 기본 basename messages 로 자동 등록한다.
  2. 여기에 typeMismatch 계열 코드의 한국어 문구를 넣는다. 새 설정 클래스도, 템플릿 분기도 필요 없다.

검토한 대안과 탈락 사유

#대안판정사유
①템플릿에서 status 별로 Thymeleaf 분기탈락 상태가 늘 때마다 분기가 자라는 패턴이라 "조건분기 legacy 확장 금지" 원칙에 정면으로 걸린다.
①BasicErrorController 를 대체 구현탈락 영향 범위가 슬라이스 규모를 넘고, 얻는 것은 라벨 하나다.
①라벨을 아예 없애고 상태 코드만 노출탈락 "404" 만으로는 무슨 일인지 알 수 없다.
①ErrorStatusLabels + ProvisionErrorAttributes 로 단일 소스화채택 두 경로가 같은 표를 조회하므로 문구가 갈라질 수 없다. 상태 추가는 표에 한 줄이지 분기가 아니다.
②템플릿을 {resource}{을/를} 같은 토큰으로 바꾸고 치환기가 처리탈락 명시적이지만 여덟 파일을 모두 고쳐야 하고, 새 문구를 추가하는 사람이 토큰 규약을 알아야 한다. 앞으로 추가될 문구에서 다시 갈라진다.
②서버가 문구를 완성해 내려보냄탈락 확인 문구 조립이 클라이언트 책임이라는 현행 구조를 바꾸는 큰 변경이고, 이 결함이 요구하는 규모가 아니다.
②치환 이후 문자열을 공용 함수가 일반 해소채택 고치는 파일이 confirm-modal-base.js 하나. 새 문구도 자동 적용.
③선례(confirm-purge.html)를 따라 본문 노출채택 같은 저장소에 이미 옳게 하는 곳이 있는데 한 곳만 갈라진 상태를 정합시키는 것이라, 새 판단이 필요 없다.
④messages.properties 신설 (자동 등록에 위임)채택 Spring primitive 그대로 사용. 신규 설정 클래스 0.
비 목표 :
  • 필드 이름의 한국어 라벨 사전(allowCreateDirectory → "상위 디렉토리 생성 허용") — 필드 전수 조사가 필요하다. MK4 레이아웃 개편에서 화면을 손볼 때 함께 처리한다.
  • 배너 마크업의 fragment 공용화 — 같은 배너 마크업이 일곱 템플릿에 복붙되어 있으나, 일곱 화면 회귀 위험이 있다. 역시 MK4 레이아웃 개편으로 넘긴다.
  • reconciliation 화면 레이아웃 개편 자체 — MK4-1(정보 정의) → MK4-2(데이터 모델) → MK4-3(레이아웃) 순서로 간다(§11).
  • MK4 진단의 나머지 후보 24 건 — 레이아웃 개편과 얽혀 있어 이번에 떼어내지 않는다.
  • 서버가 생성해 내려보내는 문구의 조사(예외 메시지 등) — 이번 해소는 클라이언트 확인창 조립 지점 한 곳에만 적용된다.

엔티티 · Value Object · Enum 신설 0 — 이 슬라이스에는 영속 도메인이 없다. Primitive Obsession 관점의 유일한 판단 지점은 상태 코드이며, ErrorStatusLabels 의 조회 키를 원시 int 가 아니라 HttpStatus 로 받는다. Spring 이 Integer 로 넘겨주는 지점(DefaultErrorAttributes 의 속성 맵)에서만 HttpStatus.resolve(int) 로 승격하고, 해석 불가 값은 기본 문구로 떨어진다.

KoreanParticle — 병기형 조사 해소 규칙 (판정 SSOT)

window.KoreanParticle.resolve(text) 는 치환이 끝난 문자열을 받아, 그 안의 병기형 조사 토큰을 앞 글자의 받침 여부로 골라 바꾸고 조사 앞 띄어쓰기까지 정규화한 문자열을 돌려준다. 판정은 아래 7 항이 전부이며, 🎬 미리보기의 판정 함수가 같은 본체다.

  1. 조사 바로 앞 글자를 본다. 괄호 · 따옴표 · 공백은 건너뛴다.
  2. 한글 음절(U+AC00 ~ U+D7A3)이면 (코드 - 0xAC00) % 28 != 0 일 때 받침 있음.
  3. 숫자면 그 숫자의 한국어 읽기로 판정한다. 받침 있음 = 0(영) · 1(일) · 3(삼) · 6(육) · 7(칠) · 8(팔), 받침 없음 = 2(이) · 4(사) · 5(오) · 9(구).
  4. 라틴 문자면 그 글자의 한국어 읽기 끝소리로 판정한다. 받침 있음 집합 = l(엘) m(엠) n(엔) 셋뿐이고, 나머지는 받침 없음. 대소문자 구분 없음. 예를 들어 r 은 '아르', s 는 '에스', x 는 '엑스', z 는 '제트' 로 모두 받침 없이 끝난다.
  5. 판정 불가(기호 등)면 받침 없는 쪽을 쓴다.
  6. 으로(로) 만 예외다. 받침이 없거나 받침이 ㄹ 이면 '로', 그 밖에는 '으로'.
  7. 띄어쓰기 — 앞 글자가 한글이면 조사를 단어에 붙이고(앞의 공백을 없앤다), 한글이 아니면(영문 · 숫자 · 기호) 조사 앞에 한 칸을 띄운다(공백이 없으면 넣는다).
규칙 7 이 필요한 이유 — 지금 문구 템플릿은 전부 '{resource} 을(를) 복구할까요?' 처럼 공백을 이미 품고 있다. 자원명이 한글로 끝나면 그 공백 때문에 "드리프트 를" 처럼 어색해지고, 영문으로 끝나면 반대로 공백이 있어야 읽힌다. 그래서 조사를 고르는 김에 앞 공백까지 함께 정리한다. 템플릿은 손대지 않는다.
  • 한글로 끝남 : 드리프트 을(를) → 드리프트를
  • 영문으로 끝남 : … -dvd.iso 을(를) → … -dvd.iso 를
  • 숫자로 끝남 : Rocky Linux 9.6 을(를) → Rocky Linux 9.6 을
숫자에 대한 판단 — 사용자 지시는 영문과 한글만 규정했다. 이 저장소의 자원명은 Rocky Linux 9.6 · MS03-CE0 처럼 숫자로 끝나도 전체가 라틴 표기 식별자라, 한글이 아닌 쪽으로 묶어 띄우는 것이 일관적이라고 보았다. 붙이는 편이 낫다고 보시면 규칙 7 의 조건을 "한글 또는 숫자" 로 넓히면 되고, 데모 판정도 한 줄만 바뀐다.

§8. 예상 부산물 / 주의 / 결정 사항

주의 1 — messages.properties 도입이 기존 테스트를 깨뜨릴 수 있다

지금까지 저장소에 messages.properties 가 없었으므로, 검증 메시지를 문자열로 단언하는 기존 테스트가 영어 원문을 하드코딩하고 있을 수 있다. 파일을 신설하는 순간 그 단언들이 한국어로 바뀌어 실패한다. CP4 에서 ./gradlew test 전체를 돌려 전수 확인하고, 깨지는 단언은 문구 대신 오류 코드 · 필드명 기준으로 바꾼다(문구를 다시 하드코딩하지 않는다).

주의 2 — korean-particle.js 의 로드 순서

confirm-modal-base.js 의 composeMessage 가 window.KoreanParticle 을 호출하므로, fragments/management/confirm-modals.html 의 script 목록에서 confirm-modal-base.js 보다 먼저 로드해야 한다. 세 fragment(all · nonPurge · lazyShell) 모두에 넣는다. 방어적으로 resolve 부재 시 원문을 그대로 반환하도록 두어, 누락 페이지에서도 지금과 같은 문구가 나오게 한다.

주의 3 — 곧 다시 그려질 화면을 지금 고치는 것

templates/maintenance/reconciliation/list.html 은 MK4 레이아웃 개편에서 다시 그려진다. 그럼에도 지금 고치는 이유는, 수정 비용이 몇 줄이고 이번에 정하는 표시 방식(선례 준수)을 개편 때 그대로 승계하면 되기 때문이다. 오히려 개편 전에 정본을 하나로 맞춰 두는 편이 개편의 입력이 명확해진다.

Q1 규칙 6(으로(로))의 ㄹ 받침 판정 대상을 §4 표대로 확정할까 — 한글 종성 인덱스 8, 숫자 1 · 7 · 8, 라틴 l. 그대로 채택. 규칙 3 · 4 가 "한국어 읽기로 판정" 이라고 규정하므로 그 읽기의 끝소리를 따르는 것이 일관적이다. 이 표를 확정하지 않으면 구현과 데모가 갈라질 수 있다.
Q2 korean-particle.js 를 static/global/ 에 두고 /global/korean-particle.js 로 서빙 — 기존 공용 JS 가 static/management/common/ 에 모여 있는 것과 위치가 다르다. 그대로 갈까. 그대로 채택. 이 함수는 management 도메인 자산이 아니라 전 영역 공용 문자열 유틸이므로 management/common 아래 두면 이름이 의미를 잃는다. 다만 세 confirm fragment 의 script 목록에 선행 로드를 추가해야 한다(주의 2).
Q3 messages.properties 에 typeMismatch 계열만 넣을까, NotNull · Size 등 Bean Validation 기본 코드까지 함께 넣을까. 이번엔 typeMismatch 계열만. 관찰된 결함이 그것이고, 검증 코드를 넓게 덮으면 각 필드에서 실제로 어떤 문구가 나오는지 전수 확인이 필요해져 슬라이스가 커진다. 나머지는 필드 라벨 사전과 함께 MK4 에서 다룬다.
Q4 error.html 표기를 "한국어 문구 (코드)" 로 바꾸면서 기존 본문 fallback "알 수 없는 오류가 발생했습니다." 는 유지할까. 유지. 라벨은 상태 코드에서 파생되지만 본문 message 는 예외가 실어 보내는 값이라 비어 있을 수 있다. 라벨이 정확해지면 본문 fallback 이 그대로여도 모순이 생기지 않는다.

§11. 다음 마일스톤
  1. HF5 완료 후 feat/MK4_reconciliation-usability 로 복귀 — 이 슬라이스는 MK4 진단에서 떼어낸 전역 공용 결함만 처리하고, 브랜치는 다시 MK4 본류로 돌아간다.
  2. MK4-1 (무엇을 보여줄 것인가) 설계 토론 착수 — 코드보다 정보 정의가 먼저인 슬라이스다. 토론 축은 넷:
    • 드리프트 이력 모델 — 같은 자원의 드리프트가 반복될 때 무엇을 하나로 묶고 무엇을 개별로 볼 것인가
    • 자원 사용 여부 — 세팅 정의서 · 할당에 실제로 쓰이는 자원인지가 조치 우선순위를 바꾸는가
    • 위험도 축 — 자동 해결 가능 여부와 별개로, 방치했을 때의 파급을 어떻게 표현할 것인가
    • 드리프트 카탈로그의 형태 — 종류별로 무엇이 일어났고 무엇을 해야 하는지의 참조 자료
  3. 드리프트 카탈로그는 두 벌로 만든다(사용자 결정) — 앱 안 안내 화면과 저장소 문서. 화면은 조치 중인 운영자가 즉시 참조하는 자리이고, 문서는 접근 권한 없는 인수인계자도 볼 수 있는 자리다.
  4. 이후 MK4-2 (데이터 모델) → MK4-3 (레이아웃 개편) 순서. §2 의 비목표 두 건 (필드 라벨 사전 · 배너 fragment 공용화)은 MK4-3 에서 화면을 손볼 때 흡수한다.
