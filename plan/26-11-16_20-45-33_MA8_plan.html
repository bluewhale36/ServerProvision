§2. 요구사항 + 비목표

요구 (패치 내역 원문)

ADMIN 과 USER 를 포함한 모든 사용자를 관리하는 SUPER_ADMIN 권한을 생성하고, 사용자 관리 페이지를 별도로 신설한다.

사용자 결정 (2026-11-16)

#결정원문 요지
U-1인벤토리 코드 MA8 · 개발 단계 5차 개발M 계열 최신 코드
U-2ADMIN 과 USER 의 권한 차이는 이번에 만들지 않는다추후 시스템 자산 변경 · 자원 영구 삭제 등에서 부여
U-3최초 등록 사용자 = SUPER_ADMIN · 계정 생성도 SUPER_ADMIN 의 사용자 관리로 통합"최초에 등록되는 사용자를 SUPER ADMIN 으로 한다. 계정의 생성도 이제 SUPER ADMIN 이 사용자 관리 기능으로 통합해서 진행한다."

요구 목록

  • R1 Role.SUPER_ADMIN 신설 (SUPER_ADMIN ⊃ ADMIN ⊃ USER)
  • R2 사용자 관리 페이지 /users — SUPER_ADMIN 전용: 목록 · 사용자 추가 · 상세 · 권한 등급 변경 · 비활성화/활성화 · 초기 비밀번호 지정
  • R3 /signup 은 부트스트랩(관리자 부재 시 최초 계정 등록) 전용, 만들어지는 계정은 SUPER_ADMIN
  • R4 기존 실 서버(스테이징 · spv-01)의 관리자 → SUPER_ADMIN 승격, 배포 순간 사용자 관리 공백 0
  • R5 자기 보호 — 자기 자신의 권한 변경 · 비활성화 · 비밀번호 지정 금지, 마지막 SUPER_ADMIN 소멸 금지(동시 요청 포함)
  • R6 권한 변경 · 비활성화 · 비밀번호 지정 대상의 열린 세션 즉시 만료
  • R7 관리 동작 감사 로그(AccountAuditEvent)
비 목표 :
  • ADMIN 전용 권한 신설(자산 변경 · 영구 삭제) — 후속 단계 (U-2)
  • 사용자 hard delete — 곧 착수할 '프로비저닝 집행인 기록' 이 사용자 id 를 참조하면 실제 삭제가 기록을 깨뜨린다. 이번엔 비활성화만
  • 게스트 채널 인증(GuestSecurityConfig · ROLE_GUEST · ROLE_PXE_BOOT) — 건드리면 PXE 부팅이 끊긴다
  • 사용자 정보(이름 · 아이디) 수정 — 요구에 없음. 필요해지면 후속
  • 집행인 기록 자체 — 이 plan 은 그쪽이 쓸 공개 조회 메서드 모양만 정한다(§4)
🎬 미리보기 — 라이브 데모 (판정 JS = §4 도메인 메서드와 같은 식)

로그인 계정(행위자) · 대상 · 동작을 골라 사용자 관리 규칙을 체험한다. 동작 버튼의 차단(disabled + tooltip)과 서버 거절(409)은 같은 UserAction.blockReason(target, actorId) 식에서 나온다. "direct POST 로 강행" 을 켜면 UI 차단을 건너뛰고 서버 가드 경로를 탄다. 프리셋은 누를 때마다 처음 상태로 되돌린 뒤 단계를 자동 적용한다.

판정 식 (서버 UserAction.blockReason(target, actorId) + UserManagementService 잠금 재확인과 같은 식)

blockReason(action, target, actor):
  if (actor.level !== 'SUPER_ADMIN' || !actor.enabled) return '사용자 관리는 최고 관리자만 할 수 있습니다.'   // 403 경로
  CHANGE_ROLE:    target.id === actor.id → '자기 자신의 권한 등급은 바꿀 수 없습니다.'
                  newLevel === target.level → '이미 그 권한 등급입니다.'
  DISABLE:        target.id === actor.id → '자기 자신은 비활성화할 수 없습니다.'
                  !target.enabled → '이미 비활성화된 계정입니다.'
  ENABLE:         target.enabled → '이미 활성 상태인 계정입니다.'
  RESET_PASSWORD: target.id === actor.id → '본인 비밀번호는 비밀번호 변경 화면에서 바꾸십시오.'
                  !target.enabled → '비활성화된 계정입니다. 먼저 활성화하십시오.'
  else null
서버 잠금 재확인(동시성): 활성 SUPER_ADMIN 행 잠금 → 행위자가 여전히 활성 SUPER_ADMIN 인가 → 실행 뒤 활성 SUPER_ADMIN ≥ 1 인가

세션 규칙: CHANGE_ROLE · DISABLE · RESET_PASSWORD 성공 시 대상 세션 '만료됨'. ENABLE 은 세션 없음(비활성 계정은 로그인 불가였으므로).

  • 기존 사용자의 created_at 은 DDL 적용 시각으로 채워진다(실제 등록 시각은 기록된 적이 없어 복원 불가). 기본 1 년 범위에 포함되므로 목록에서 빠지지 않는다.
  • DDL 적용 뒤 구 jar 로 롤백하려면 ddl/MA8_super_admin_rollback.sql 을 먼저 적용한다. 그러지 않으면 승격된 관리자가 로그인하지 못한다(D-13). 추가된 created_at · updated_at 컬럼은 남겨도 구 jar 의 validate 가 거절하지 않는다.

  • 이미 열린 SSE 스트림은 만료 뒤에도 끊길 때까지 유지된다. 다음 재연결이나 일반 요청에서 로그인으로 돌아간다.
  • S22 디자인 스트림과 사이드바 한 줄이 겹친다 — 병합 순서 조정. docs 세션(사용자 매뉴얼)에는 /signup 관리자 모드 폐지와 /users 신설을 알린다.
