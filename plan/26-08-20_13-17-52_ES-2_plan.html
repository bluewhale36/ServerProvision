§0. 요약 — 쉬운 말로

진행 기록이 가리키는 위치가 큰 단계 단위라, 그 안의 작은 단계 중 어디서 멈췄는지는 별도 칸에 한 번 더 적고 있다 — 같은 사실을 두 칸이 말한다. 또 "지금 부팅을 기다리는지 · 작은 단계를 실행 중인지 · 자원이 없어 멈춰 있는지" 를 담는 자리가 없어 서버가 매번 기록을 뒤져 짐작한다.

ES-2 는 기록의 위치를 작은 단계로 낮춰 중복 칸을 없애고 진행 양태 칸을 하나 만든다. 아무도 읽지 않는 칸을 걷어내고, 내용과 어긋난 표 이름을 바로잡고, 실제 데이터베이스가 코드와 다르게 굳은 다섯 자리를 맞춘다. 화면과 게스트 스크립트는 그대로이며, 눈에 보이는 변화는 등록 직후 배지가 "부트스트래핑" 대신 "진단 리눅스" 로 보이는 것 하나다.

§1. 현재 상태 (진단)

토론이 이미 결정한 것

E 실행 준비도 토론(discussion/26-08-13_11-17-47, 2026-08-15 종결)의 확정 D3 · D4 를 코드와 스키마로 옮기는 슬라이스다. 무엇을 할지는 다시 논의하지 않고 어떻게 이행할지만 설계한다.

  • D3 (모델 정리) — 커서 단위를 ProvisioningPhase(8값)에서 ProvisioningPhaseStep(14값)으로 낮추고, 그래서 중복이 되는 칸과 이름이 어긋난 테이블을 함께 정리한다(항목은 §2).
  • D4 (운동 양태 어휘) — 진행 기록에 내부 상태 컬럼 신설(3값). "값이 있다" 가 곧 "실행 창 안" 이 되도록 불변식을 걸고, 착수 후 자원 결손으로 물러서는 전이는 금지한다(대기가 아니라 실패이므로).

왜 E2-1 에 붙이지 않고 떼었는가

검증 줄기가 다르다 — ES-2 는 "모델을 갈아끼웠는데 행동이 그대로다", E2-1 은 "펌웨어 자원을 붙이고 없으면 대기한다" 로 서로 다른 이야기이고, 섞으면 회귀 실패와 신규 결함을 가릴 수 없다. 게다가 E2-1 의 HOLD 대기 · TTL · 준비도 훅이 모두 새 모델을 전제하므로 옛 모델 위에 먼저 얹으면 같은 코드를 두 번 쓴다.

§2. 요구사항 (확정) + 비목표
  1. D3 이행 — phase_meta 제거 · setup_step → provisioning_history 개명 · 커서 단위를 step 으로 낮추고 current_phase → current_step · failed_step_code 제거 · 할당 스냅샷 두 테이블 개명.
  2. D4 이행 — 운동 양태 컬럼 motion 신설(3값) + 불변식 + 수동 DDL 의 CHECK 이중 방어 + 금지 전이 가드.
  3. 실 DB 5건 교정 — §1 표 그대로.
  4. 소비처 판정식 갱신 — 커서를 phase 로 읽던 자리를 step 과 그 phase 파생으로 재배선(§3).
  5. DDL 마이그레이션 산출 · 적용 · ddl/schema.sql 정본 갱신.
  6. 행동 무변경 — 게스트가 받는 스크립트 · 화면 표시 · API 계약이 달라지지 않는 것이 성공 조건이다(정상 흐름 기준 — 비정상 보고를 막는 phase 이탈 게이트는 §4 D-1 대로 새로 선다).
비 목표 (전부 E2-1 소관) :
  • HOLD 를 쓰는 작성자 — 이번에는 값 · 가드 · CHECK 만 선언하고 진입 메서드조차 만들지 않는다. 작성자 없는 진입 메서드는 소비자 없는 추상이다.
  • TTL 값과 그 거처 — 기점이 HOLD 진입이 찍는 last_transition_at 이라는 것까지만 D4 가 정했다.
  • 준비도 훅(READY / DEGRADED / BLOCKED) 과 펌웨어 resolve.
  • 게스트 API 어휘 변경 — 경로 /agent/steps, StepOpenRequest · StepCloseRequest, stepId 는 그대로 둔다. "step" 은 ProvisioningPhaseStep 으로 살아 있는 어휘이고, 게스트 계약은 안정층이라 모델 정비가 건드릴 자리가 아니다.

§4. 도메인 모델 + 설계 결정 (D-1 ~ D-7 · D-6 은 §3 영향 지점에)

D-1. 커서의 의미론 = "도달했거나 향하는 목표 step" (pre-position 방식)

채택 — 커서는 현재 목표 step 을 가리키고, 셋뿐인 시점에서만 움직인다(모두 게스트 신호 트랜잭션 안).

  1. 게스트 step open 보고 — 보고된 step 이 커서와 같은 phase 면 그 step 으로 커서를 옮긴다(같은 step 은 무이동 멱등이고, 앞 · 뒤는 가리지 않는다). 다른 phase 의 step 이면 진짜 비정상이므로 서비스 게이트(AgentReportService)가 AgentReportRejectedException 으로 409 거절한다.
  2. phase 완주 판정(PhaseCursorAdvancer, close 보고 트랜잭션 안) — 다음 보유 phase 의 진입 step 으로 미리 옮겨 세운다. 다음 보유 phase 가 없으면 markCompleted 하고 커서는 그대로 둔다.
  3. 등록 seed — DIAGNOSTIC_BOOTING. BOOTSTRAPPING 의 instant 2행은 등록 트랜잭션에서 즉시 종결되므로 커서가 거기 머물 이유가 없다.
같은 phase 안의 재시작은 관용한다. phase 진행 중 게스트가 예기치 않게 재부팅하면 dispatcher 는 같은 phase 의 스크립트를 다시 주고 에이전트는 그 phase 첫 step 부터 재수행한다 — 커서가 INFORMATION_COLLECTING 인데 DIAGNOSTIC_BOOTING open 이 오는 정상 복구 흐름이고 현행 모델이 이미 관용한다. 역행 금지는 phase 축으로만 유지된다 — 커서의 phase 는 게스트 open 으로 바뀌지 않고 phase 이동은 완주 판정의 pre-position(전진)뿐이다.

근거 — 토론 D1 4차 개정 원문 "TTL 만료 = 실패 전환 — failed_at + 막힌 step 을 가리키는 커서" 가 pre-position 을 요구한다(E2-1 의 HOLD 는 진입 step 을 가리킨 채 대기). 커서가 마지막으로 연 step 을 따라가므로 재시작 뒤 실패에도 "커서 = 실패 지점" 이 맞는다.

탈락 대안 ① 커서 = 마지막으로 연 step 만 두고 완주는 원장 조회로 판정 — 매 폴링 원장 스캔이라 D4 가 HOLD 최소 어휘안을 기각한 이유와 같다. ② 커서 + 완주 boolean 병기 — 이중 권위로 "모순은 표현 불가로" 원칙 위반. ③ 엄격 역행 거부(step 축) — 위 재부팅 복구 흐름을 깨는 회귀.

부수 이득 — BootScriptDispatcher.bootTargetPhase 특례 헬퍼가 소멸한다(커서의 phase 파생이 곧 부팅 목표).

진입 step 규칙 — 선언 순서상 그 phase 의 첫 상수이며 entryOf(phase) 로 한 곳에서만 계산한다(보류 상수 IPMI_SETTING 은 진입 step 이 될 수 없다). 선언 순서가 곧 실행 순서라는 결합은 전 상수 커버리지 테스트로 고정한다 — 소속 phase 순서를 거스르는 상수를 추가하면 빌드가 깨진다. 명시 순서 필드(int order)안은 ordinal 과의 이중 권위로 기각.

재시도(clearFailed)는 커서를 움직이지 않는다 — 실패 step 재수행이고 같은 step 재 open 은 멱등 규칙이 받는다.

D-2. 운동 양태 컬럼 — enum ProvisioningMotion, 컬럼 motion

D4 의 가칭을 확정한다 — AWAITING_BOOT(부팅 · 폴링 대기) / STEP_RUNNING(step 실행 중) / HOLD(자원 결손 대기 · TTL 가동). 불변식은 motion ≠ NULL ⇔ 실행 창 안(started_at ≠ NULL ∧ failed_at = NULL ∧ completed_at = NULL)이고, 배선은 도메인 메서드 안에서만 일어난다.

start() → AWAITING_BOOT step open 처리 → STEP_RUNNING step close(성공) 처리 → phase 경계 전진(pre-position)이면 AWAITING_BOOT (재부팅 대기) phase 내 잔여 step 이 있으면 STEP_RUNNING 유지 (같은 부팅에서 이어감) markFailed / markFailedManually / markCompleted → NULL (실행 창 밖) clearFailed() → AWAITING_BOOT STEP_RUNNING ──▶ HOLD ✕ 금지 (도메인 메서드 가드 · IllegalStateException)

금지 전이를 두는 이유는 "실패인데 대기처럼 보이는 상태" 를 표현 불가로 만들기 위해서다(§1 D4). 다만 진입 메서드는 이번에 만들지 않는다 — 값 · 가드 · CHECK 만 선언하고 작성자는 E2-1 이 데려온다.

ddl-auto=validate 는 CHECK 를 검사하지 않으므로 수동 DDL 로 데이터베이스 쪽 이중 방어를 건다.

CHECK ( (motion IS NULL     AND (started_at IS NULL OR failed_at IS NOT NULL OR completed_at IS NOT NULL))
     OR (motion IS NOT NULL AND started_at IS NOT NULL AND failed_at IS NULL AND completed_at IS NULL) )

탈락 대안 — 전 국면 포괄 어휘안(상태 폭발) · HOLD 단독 어휘안(매 폴링 원장 스캔)은 토론 D4 가 이미 기각했다. 참조만 하고 다시 열지 않는다.

  • isRetryBlocked() — failedStepCode ∈ {BIOS_UPDATING, BMC_UPDATING} → isFailed() && currentStep ∈ {…}. D-1 이 "실패 시 커서 = 실패 step" 을 보장하므로 판정이 같다.
  • IpxeScripts.failed(failedStepCode, q) → failed(currentStep, q). null 분기("operator-marked")가 사라진다.
  • ProvisioningRetryRejectedException.firmwareBlocked(id, step) — 커서 step 전달로 교체.
  • 응답 GuestServerDetailResponse.failedStepCode — 필드 유지, 공급원만 커서로(화면 계약 무변경).

수동 실패 전환 표식의 새 거처 = 원장 instant 행. markFailedManually(GuestServerCommandService)가 ProvisioningHistory.instant(server, 커서 step, FAILED, statusMeta {"origin":"operator"}, now) 를 함께 적고, 화면의 "운영자 전환" 배지는 상세 응답이 이미 로드하는 원장에서 failed_at 과 짝이 되는 최신 FAILED 행의 origin 을 읽어 파생한다(추가 쿼리 0). 원장의 계약이 "실행에 일어난 사실" 이고(instant 행의 서버 적재는 설계상 기존재 — 2026-08-13 브리핑 §4 정정) 운영자의 전환도 그 사실에 속한다.

탈락 대안 — 전용 boolean 컬럼(한 용도만을 위한 스키마 낭비 · D4 어휘 방벽의 취지 위반) · motion 값 추가(실행 창 밖 국면을 실행 창 안 어휘에 들이는 것이라 D4 가 금지).

§7. 예외 계층
  • 신규 없음 — 이 슬라이스는 예외를 만들지 않는다.
  • 개명 SetupStepNotFoundException → ProvisioningHistoryNotFoundException. NotFoundException 하위라는 계층과 404 매핑은 그대로다.
  • 시그니처 ProvisioningRetryRejectedException.firmwareBlocked(id, step) — 인자를 failedStepCode 에서 커서 step 으로 교체. 상태코드와 메시지 형식은 유지.
  • 재사용 AgentReportRejectedException(ConflictException 하위 · 409) — 다른 phase 의 step open 보고를 AgentReportService 게이트가 거절한다. 클래스는 기존 것이고 거절 사유(phase 이탈)를 위한 정적 팩토리 하나가 는다.
  • 재사용 IllegalStateException — motion 금지 전이와, 게이트를 뚫고 들어온 phase 이탈에 대한 엔티티 안전망. 정상 흐름으로는 도달할 수 없고 도달했다면 서버 배선이 깨진 것이므로 삼키지 않고 드러낸다.

#질문권장안
OQ1 스냅샷 엔티티 클래스의 개명 범위. 테이블은 *_snapshot 으로 확정했다. 엔티티 클래스도 SettingAssignmentSnapshot · AssignedProcessSnapshot 으로 함께 개명할지(파생 = repository · 서비스 시그니처, main 19 + test 10 파일), 아니면 클래스명은 두고 @Table 만 바꿀지. 클래스 동반 개명. 코드가 SSOT(Single Source of Truth — 단일 진실 출처)인데 클래스명과 테이블명이 어긋나면 스스로 만드는 drift 다. churn 은 기계적 rename 이라 위험이 낮다. 유지안의 논거는 diff 최소화 하나뿐이다.
OQ2 수동 실패 전환 표식을 원장 instant 행으로 옮기는 §4 D-5 방식 확인. "운영자 전환" 배지의 공급원이 진행 기록 컬럼(null 표식)에서 원장 행 파생으로 바뀐다. 그대로 채택. 표시는 동일하고 추가 쿼리가 0 이며, 전용 boolean 컬럼을 만들지 않아 스키마가 늘지 않는다.

§9. Verification 체크리스트 + CP5 검증 줄기

CP5 가 증명할 한 이야기는 "모델을 갈아끼웠는데 행동이 그대로다 + 새 불변식은 비정상 조작을 막는다" 이다. 화면이 있는 회귀이므로 브라우저가 본체이고 curl 은 B 항목 보조로 쓴다.

A — 정상 회귀

  • A1 mock-guest 등록 → 상세 화면 확인. 배지가 "부트스트래핑" → "진단 리눅스" 로 바뀌는 것만이 의도된 유일한 표시 변화이고 나머지는 종전과 같아야 한다.
  • A2 개시 → 진단 완주(diagnose-cycle.sh) → 원장 표 · 계획 레일 · 종단 배지가 종전과 동일.
  • A3 펌웨어 업데이트를 보유한 게스트가 진단을 완주 → HOLD 스크립트 종전 동일 + 커서가 BIOS_UPDATING(진입 step)에 pre-position.
  • A4 실패 보고 → 실패 배지 + 실패 지점 step 표시(커서에서 파생).
  • A5 수동 실패 전환 → "운영자 전환" 배지 + 원장 FAILED 행.
  • A6 재시도(clearFailed) → 커서 무이동으로 재개.
  • A7 phase 진행 중 재부팅 재시작 관용 — 진단 step 을 연 상태에서 재부팅을 가정해 그 phase 의 첫 step 을 다시 연다 → 200 수용 + 커서가 그 step 으로 되돌아가고 완주까지 이어지는지 회귀 확인.

B — 비정상 조작

  • B1 직접 SQL 로 motion 불변식을 위반하는 INSERT / UPDATE → CHECK 가 거부.
  • B2 다른 phase 의 step open 보고(curl) → 409 거절(AgentReportRejectedException). 같은 phase 재시작 open 은 200 으로 수용되는 것과 대조한다.
  • B3 사칭 토큰 · 없는 stepId → 404 회귀.

C — 표시 · 안내

  • C1 상세 화면 배지 3종(진행 · 실패 · 종단) 스크린샷.
  • C2 원장 표 — 테이블 개명 후에도 동일 표시.
