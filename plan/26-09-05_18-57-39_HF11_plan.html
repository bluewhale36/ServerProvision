§0. 한눈 요약

2026-09-04 Windows 실기 2호에서 결함 셋이 나왔다. 성격이 서로 다르고 고치는 자리도 다르지만, 셋 다 앱 안에서 재현과 검증이 닫힌다는 공통점이 있다 — 실기를 다시 잡지 않아도 고칠 수 있다는 뜻이다. 그래서 한 브랜치 · 한 PR 로 묶고, 다음 실기(Run 2) 앞에 배포한다. HF4 묶음이 같은 방식을 썼다.

  • HF11-2 — 재진입한 게스트가 다시 수집하지 않는다. 진단 리눅스로 다시 부팅해도 체크인 지시가 WAIT 라 인벤토리가 옛값에 머문다. 고치는 자리는 DiagnoseLinuxExecutor.directiveFor 한 줄이다
  • HF11-3 — 첫 조립이 500 으로 끊겼다. 사전 판정이 $OEM$ 디렉토리 자신의 쓰기 권한만 보고 그 안의 기존 항목은 보지 않아, 막혔어야 할 버튼이 활성이었다. 실패가 남긴 빈 디렉토리도 치우지 않았다
  • HF11-1 — 완료 보고가 drivers=0 problems=0 이었다. 보고 스크립트가 pnputil 의 영문 출력을 정규식으로 찾는데, ko-KR Windows 는 한국어로 찍는다
진행 순서 · 범위 — 사용자 지시에 따라 재현 확실성이 높은 순서인 HF11-2 → HF11-3 → HF11-1 로 진행한다. 엔티티 · Repository · DDL 은 건드리지 않고, 새 URL 도 새 예외 클래스도 만들지 않는다. 바뀌는 것은 판정 규칙 셋과 그것을 검증하는 테스트다.
§1. 현재 상태 (진단)

아래는 2026-09-04 실기에서 관찰한 것과, 그 관찰이 코드의 어느 줄에서 나오는지를 대조해 확인한 내용이다. 셋 다 "무엇이 잘못 보였는가" 가 아니라 "어떤 판정식이 그렇게 답하도록 되어 있는가" 까지 짚는다.

1-1. HF11-2 — 재진입한 게스트가 다시 수집하지 않는다 (F-R13)

수집을 끝낸 미개시 게스트가 하나 있었다. GuestServerDetail 은 DIAGNOSTIC_ENRICHED 였고 커서는 INFORMATION_PERSISTING 에서 개시를 기다리고 있었다. 이 상태에서 운영자가 RAID 볼륨을 지우고 같은 장비를 진단 리눅스로 다시 부팅시켰다. 목적은 분명하다 — 바뀐 실물 구성을 다시 읽히려는 것이다.

실제로 일어난 일은 이렇다. 에이전트가 DIAGNOSTIC_BOOTING 단계를 열고 닫았고, 그에 따라 커서가 DIAGNOSTIC_BOOTING · STEP_RUNNING 으로 되돌아갔다. 그런데 이어진 체크인의 지시는 WAIT 였다. 게스트는 대기 루프로 들어갔고 재수집은 일어나지 않았다. 카드의 RAID 인벤토리는 볼륨 2 개인 옛값 그대로였다. 운영자가 쓴 우회는 회수 후 재등록이었고 5 분이 들었다.

코드에서 이 답이 나오는 자리는 셋이다.

  • DiagnoseLinuxExecutor.directiveFor 가 isDiagnosticEnriched ? WAIT : COLLECT 로 판정한다. 보는 것이 GuestServerDetail 하나라, 한 번이라도 적재된 게스트는 그 뒤로 영원히 WAIT 를 받는다
  • AgentReportService.openStep 이 재진입한 단계로 positionAt 한다. 이것은 정상 동작이다 — ES-2 가 "커서 = 마지막으로 연 step" 으로 정의했고, 화면이 재부팅 사실을 보이게 하는 것도 이 규칙이다
  • GuestServerCommandService.startProvisioning 의 소급 전진 조건이 currentStep == INFORMATION_PERSISTING 이다. 커서가 진단 초입으로 되돌아간 상태에서 개시하면 이 조건이 거짓이라 전진하지 않고, 게스트는 계속 WAIT 만 받는다 — 개시했는데 아무 일도 일어나지 않는 상태다
WAIT 를 없애면 안 된다 — 이 지시가 있는 이유는 루프 종료다. 한 세션 안에서 수집을 마친 게스트의 다음 체크인이 다시 COLLECT 를 받으면 무한 재수집이 된다. 그러므로 고칠 것은 "WAIT 를 언제 주는가" 이지 "WAIT 를 줄 것인가" 가 아니다.

1-2. HF11-3 — 첫 조립이 권한 오류로 끊겼다 (F-OEM)

대시보드의 [드라이버 페이로드 조립] 을 처음 눌렀을 때 500 이 났다. 예외는 AccessDeniedException: …/$OEM$/$$ 였다. 09-02 에 손으로 만들어 둔 $$ 와 $1 이 spvadmin 소유에 755 였던 것이 원인이다.

조립기는 새 트리를 임시 디렉토리에 다 쓴 뒤 $$ · $1 · 매니페스트를 하나씩 rename 으로 바꿔 끼운다. 옛 것은 .old-<ts> 아래로 비켜 둔다. 여기서 걸린다 — 디렉토리를 다른 부모로 옮기는 rename 은 옮기는 디렉토리 자신의 쓰기 권한을 요구한다. 부모인 $OEM$ 에 쓸 수 있어도, 옮겨질 $$ 에 쓸 수 없으면 실패한다.

사전 판정이 이것을 잡지 못했다. WindowsOemPayloadAssembler.blockReason 은 $OEM$ 디렉토리 자신이 쓰기 가능한지만 검사한다. 그래서 버튼은 활성이었고 사용자는 누를 수 있었으며, 결과는 사유 없는 500 이었다. 게다가 swap 은 실패 경로에서 옮긴 것만 되돌리고 자기가 만든 빈 .old-<ts> 디렉토리는 남겼다. 실기 우회는 chown -R 이었고 런북 §14-1 에 반영됐다.

1-3. HF11-1 — 완료 보고의 두 수치가 모두 0 이었다 (F-W1)

설치는 성공했는데 완료 보고가 drivers=0 problems=0 으로 올라왔다. 보고 스크립트 WindowsOemTemplates.SPV_REPORT_PS1 이 pnputil 의 영문 출력을 정규식으로 찾기 때문이다. 찾는 것은 셋 — Added driver packages:\s+(\d+) · Instance ID: · Device Description: 이다. ko-KR Windows 는 같은 자리에 한국어로 찍는다.

[en-US]  Added driver packages:  175
[ko-KR]  추가된 드라이버 패키지:  175

[en-US]  <problem device list>   Instance ID: … / Device Description: …
[ko-KR]  시스템에서 장치를 찾을 수 없습니다

세 정규식이 모두 빗나가므로 드라이버 수는 0 이 되고, 문제 장치 목록도 비어 0 이 된다. 문제 장치가 실제로 있었더라도 0 으로 보고됐을 구조라는 점이 더 중요하다 — 이번에는 마침 문제 장치가 없어서 오보가 무해했을 뿐이다.

대신 쓸 재료는 실기 로그에 이미 있다. 맥으로 가져온 ~/Desktop/fieldwork-2/setupcomplete.log 에서 게시 이름 oemNN.inf 의 고유 개수는 47 이고, 이는 3 호 실측의 47 과 일치한다. 위 로그의 175 는 pnputil 이 패키지의 변형 폴더(W2K12R2 · W2K16 · Windows10 x64 · x86)마다 "추가" 를 다시 센 집계라 같은 드라이버가 여러 번 들어간 값이고, 47 은 게시 이름으로 묶은 고유 개수다 — 새 산출식은 후자를 쓴다. 같은 채증의 devices.txt 에서 Get-PnpDevice -PresentOnly 중 Status 가 OK 가 아닌 장치는 0 건이다. 둘 다 표시 언어에 좌우되지 않는 값이다.

1-4. 셋을 한 묶음으로 다루는 근거

세 결함은 도메인이 다르지만 검증 성격이 같다. HF11-2 는 하네스와 브라우저로, HF11-3 은 파일 권한을 만들어 브라우저로, HF11-1 은 실기 로그를 재료로 앱 안에서 확인이 끝난다. 유일하게 앱 밖으로 나가는 것은 HF11-1 의 PowerShell 실제 실행인데, 파싱 논리 자체는 실기 로그로 검증할 수 있고 실행 확인은 Run 2 가 받는다. 배포 단위도 하나다 — Run 2 앞에 한 번 올린다.

4-1. DiagnoseLinuxExecutor.directiveFor — 판단 근거를 detail 에서 커서로

BEFORE

boolean enriched = guestServerDetailRepository
        .findByServerIdWithBoardModel(server.getId())
        .map(GuestServerDetail::isDiagnosticEnriched)
        .orElse(false);
return enriched ? WAIT : COLLECT;

AFTER

return progress.getCurrentStep()
        == ProvisioningPhaseStep.INFORMATION_PERSISTING
    ? AgentDirective.WAIT
    : AgentDirective.COLLECT;

enriched 는 "이 게스트를 언젠가 한 번 읽었다" 는 누적 사실이고, 커서는 "지금 이 게스트가 진단 절차의 어디에 서 있는가" 라는 현재 위치다. 재진입은 위치를 되돌리는 사건이므로, 위치를 보는 쪽이 맞다. 네 입력에 대한 답은 이렇다.

커서상황정정 전정정 후
DIAGNOSTIC_BOOTING첫 등록 — 등록 seed 가 세운 커서COLLECTCOLLECT
DIAGNOSTIC_BOOTING재진입 — 에이전트가 다시 연 step 으로 커서 회귀WAITCOLLECT
INFORMATION_COLLECTING보고 해석 불가 — 적재 없이 반환COLLECTCOLLECT
INFORMATION_PERSISTING수집 완주 — 루프 종료 지점WAITWAIT

달라지는 행은 하나뿐이고, 나머지 셋은 답이 같다. 그래서 첫 등록과 재시도 흐름은 회귀하지 않는다 — 커서를 세우는 규칙(등록 seed · positionAt)이 이미 그 답을 보장한다. guestServerDetailRepository 는 onStepClosed 의 소비 훅에서 계속 쓰이므로 의존 자체는 남고, directiveFor 안의 조회 한 번만 사라진다.

등록 seed ─▶ DIAGNOSTIC_BOOTING ──COLLECT──▶ INFORMATION_COLLECTING ──적재──▶ INFORMATION_PERSISTING ──WAIT(루프 종료) 재진입 ─▶ DIAGNOSTIC_BOOTING ──COLLECT──▶ … (정정 후: 같은 경로를 다시 탄다)

R2 는 코드 변경 없이 성립한다. onStepClosed 는 수집이 닫힐 때 isStarted() 를 보고 PhaseCursorAdvancer.advanceOrComplete 를 부르거나 유보한다. 재진입 뒤 개시한 게스트는 개시 시점에 커서가 INFORMATION_PERSISTING 이 아니라 전진하지 않지만, 곧이어 재수집이 닫히면서 그 자리에서 전진한다. 즉 정정 전에는 갇히던 순서가, 정정 후에는 스스로 풀린다.

4-2. WindowsOemPayloadAssembler — 사전 판정에 자식 항목 추가, 잔존 정리

blockReason 에 검사를 하나 더 얹는다. $OEM$/$$ 와 $OEM$/$1 이 존재한다면 각각 Files.isWritable 을 확인하고, 아니면 사유를 낸다.

"$OEM$ 안의 기존 항목($$ · $1)에 쓰기 권한이 없습니다
 — 런북 §14-1 (chown -R provisioning:spvadmin)"

매니페스트 파일은 검사 대상이 아니다. 일반 파일의 rename 은 부모 디렉토리의 쓰기 권한만 요구하고 파일 자신의 권한과 무관하기 때문이다. 검사를 넓힐수록 정확해지는 것이 아니라, 실패하는 조건과 검사하는 조건이 정확히 같아야 사유가 신뢰를 얻는다.

정리는 두 자리에 넣는다. sync 시작 시점에 $OEM$ 바로 아래의 .tmp-* · .old-* 잔존물을 deleteQuietly 로 치우고, swap 의 실패 경로에서 자기가 만든 .old-<ts> 를 삭제한다. 전자는 이전 실행이 비정상 종료로 남긴 것을, 후자는 이번 실행이 남길 뻔한 것을 담당한다. Windows Setup 은 $OEM$ 바로 아래의 $$ · $1 만 읽으므로 이 디렉토리들이 남아도 설치를 깨지는 않지만, 남은 흔적은 다음 사람이 상태를 오독하게 만든다.

4-3. WindowsOemTemplates.SPV_REPORT_PS1 — 언어 무관 산출로 교체

  • 드라이버 수 — setupcomplete.log 에서 (?i)oem\d+\.inf 에 맞는 고유 게시 이름의 개수. 게시 이름은 Windows 가 붙이는 식별자라 표시 언어와 무관하다. 실기 로그로 계산하면 47 이다
  • 문제 장치 — Get-PnpDevice -PresentOnly | Where-Object { $_.Status -ne 'OK' }. 항목은 FriendlyName (InstanceId) 형태로 200 자에서 자르고, 목록은 50 개까지, 개수는 전체를 보낸다. cmdlet 이 없는 환경을 위해 try/catch 로 감싸고 빈 목록 + 기록 한 줄로 떨어뜨린다
  • pnputil /enum-devices 호출과 영문 정규식 셋을 제거한다. 파일은 계속 ASCII 로 쓴다 — 조립기가 US_ASCII 로 기록하므로 한글을 넣으면 기록 자체가 실패한다

스크립트 본문이 바뀌면 scriptsHash 가 달라진다. 그래서 배포 뒤 대시보드 chip 문구가 "갱신 필요 — 설치 후 스크립트 변경" 으로 바뀌고, 운영자는 조립을 한 번 다시 눌러야 한다. 이것이 R6 이며 기존 비교 로직을 그대로 쓰므로 코드 변경은 없다.

4-4. 카드 라벨의 뜻을 문서로 고정

§8. 결정 사항 / 주의 / Open Questions

D-1 (HF11-2) 지시 판정을 커서 기준으로 바꾼다

채택 — 커서 == INFORMATION_PERSISTING ? WAIT : COLLECT. 재진입은 커서를 되돌리는 사건이므로, 되돌아간 위치를 보는 판정이 곧 "다시 수집해야 한다" 와 같은 뜻이 된다.

  • 탈락 ① 미개시면 항상 COLLECT — 수집을 마친 직후의 체크인도 COLLECT 를 받아 한 세션 안에서 무한 재수집이 된다. 루프 종료자를 없애는 안이다
  • 탈락 ② 개시의 소급 전진 조건을 enriched 로 바꾸기 — 갇힘만 풀고 인벤토리는 옛값에 머문다. 운영자가 재부팅한 이유(바뀐 실물을 다시 읽히기) 자체를 충족하지 못한다. 게다가 D-1 을 적용하면 onStepClosed 가 개시 여부로 전진하므로 이 변경은 불필요해진다
  • 탈락 ③ 재진입 openStep 이 커서를 되돌리지 않게 하기 — ES-2 의 "커서 = 마지막으로 연 step" 정의를 깨고, 화면에서 재부팅했다는 사실이 사라진다. 증상을 감추는 방향이다

재수집의 적재는 최신값 덮어쓰기(GuestServerDetail.enrich · enrichRaidInventory)라 멱등이다. 같은 게스트가 보드 시리얼을 다시 보고해도, 중복 필터가 자기 자신을 제외하므로 통과한다.

D-2 (HF11-3) 사전 판정에 자식 항목 쓰기 가능을 더하고 잔존물을 정리한다

채택 — 실패하는 조건과 검사하는 조건을 일치시키고, 실패가 남긴 흔적을 다음 실행이 치운다.

  • 탈락 ① rename 대신 복사 — 쓰기 불가한 디렉토리에는 복사도 되지 않는다. 문제를 옮길 뿐이다
  • 탈락 ② 앱이 chown 을 수행 — 권한 상승이자 운영 경계 침범이다. 소유권 조정은 런북의 몫이고, 앱은 그 조건이 갖춰지지 않았음을 정확히 말하는 데까지가 책임이다

D-3 (HF11-1) 게시 이름 개수와 PnP 상태로 산출한다

채택 — 드라이버 수는 oemNN.inf 고유 개수, 문제 장치는 Get-PnpDevice 의 상태. 둘 다 표시 언어에 좌우되지 않는다.

  • 탈락 ① 다국어 문자열 정규식 — 언어가 하나 늘 때마다 깨진다. 지금 겪은 결함을 언어 수만큼 반복하는 안이다
  • 탈락 ② 서버 측 파싱 — 전체 로그를 보내야 하는데 현재 계약은 꼬리 4 KB 다. 계약을 넓히는 대가가 크다
  • 탈락 ③ pnputil /enum-drivers 개수 — 이번에 설치한 것이 아닌 기존 패키지까지 센다

이 결정과 함께 "드라이버 n" 의 의미를 게시된 드라이버 패키지 수로 정의한다. 실기 3 호에서 확인된 47 과 같은 뜻이다.

D-4 하나의 브랜치 · 하나의 PR 로 낸다

채택 — HF4 묶음이 같은 방식을 썼고, 배포 단위가 Run 2 앞 한 번이다. 탈락 은 결함마다 PR 을 여는 안으로, 스테이징 배포가 세 번이 되고 그 사이의 중간 상태를 아무도 쓰지 않는다.

  • directiveFor 변경은 진단 phase 전체에 적용된다. 첫 등록과 재시도 흐름은 커서를 세우는 규칙(등록 seed · positionAt)이 이미 같은 답을 보장하므로 회귀하지 않는다
