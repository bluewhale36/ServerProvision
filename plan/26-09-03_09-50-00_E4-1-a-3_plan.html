§1. 현재 상태 (진단)

이 슬라이스는 커서가 OS_INSTALLING 에 이르렀을 때 게스트에게 무엇을 내줄지가 비어 있는 자리를 채운다. 아래는 그 자리 주변에서 지금 실제로 무슨 일이 벌어지는지를 코드에서 확인한 것이다.

1-1. phase 는 있고 실행기가 없다 — 무한 대기

ProvisioningPhase.OS_INSTALLING 과 그 하위 ProvisioningPhaseStep.OS_INSTALLING(step 1개)은 이미 정의돼 있다. 그런데 그 phase 를 맡는 ProvisioningPhaseExecutor 빈이 없으므로, 커서가 여기에 도달하면 BootScriptDispatcher 의 7행이 IpxeScripts.hold(OS_INSTALLING) 를 돌려준다 — 게스트는 30초 주기로 phase OS_INSTALLING not implemented yet (HOLD). 만 반복해 읽으며 영원히 그 자리에 선다.

커서가 실제로 여기까지 온다는 것도 확인했다. SettingProcessPhaseMapper 는 정의서의 OS_INSTALLATION 단계를 OS_INSTALLING 으로 사상하고, 이 phase 는 OwnedPhases 의 NON_ASSIGNABLE 집합(BOOTSTRAPPING · DIAGNOSE_LINUX · TESTING)에 들지 않는다. 따라서 할당이 이 phase 를 보유할 수 있고 PhaseSequence.nextAfter 의 전진도 이쪽을 향한다.

1-2. 실행기 SPI 의 선례 넷

ProvisioningPhaseExecutor(SPI = Service Provider Interface, 도메인이 구현해 끼우는 확장점)는 훅 다섯을 연다 — bootScript · onStepClosed · readiness · directiveFor · raidApplyPayloadFor. 이 중 넷이 이미 실물로 구현돼 있어 이번 실행기가 따라야 할 관용구를 정해 준다.

1-3. 착수 신호의 공백 — 이 슬라이스의 핵심 결손

다른 phase 는 게스트 에이전트가 POST /api/pxe/v1/agent/steps(openStep)로 "이제 시작한다" 를 알리고, 서버는 그 보고를 받아 커서를 STEP_RUNNING 으로 옮긴다. WinPE 에는 그 보고 수단이 없다 — Setup PE(boot.wim index 2)에는 curl 도 where 도 findstr 도 없다는 것이 실측 1호의 F-1 · N5 로 확인됐다.

그렇다고 서버 쪽에 착수를 적을 자리가 있는 것도 아니다. /boot 는 BootService.boot(트랜잭션 경계) → PhaseEntryGate.evaluate(전이 담당) → BootScriptDispatcher.dispatch(읽기 전용 판정, DEC-2) 순으로 흐르고, dispatcher 는 String 하나만 돌려준다. "누구의 스크립트를 내주기로 했는가" 라는 사실이 반환값에 남지 않아, 그 직후에 착수를 기록할 훅을 걸 자리가 없다.

결손 요약 — 게스트는 보고할 수 없고, 서버는 자기가 내준 것을 붙잡을 수 없다. 이 슬라이스는 서버가 스크립트를 내준 사실 자체를 착수 신호로 삼는 방향으로 이 공백을 메운다(§8 D-1).

1-4. 게이트의 사다리 — 착수 전과 후가 다르다

PhaseEntryGate 는 motion == STEP_RUNNING 이면 준비도를 아예 묻지 않는다. 착수한 뒤의 재료 결손은 대기가 아니라 실패 소관이라는 토론 D1 의 결론이 코드로 굳어 있다. 착수 전 결손은 holdForShortage(AWAITING_BOOT 에서만 허용) → HoldTtlPolicy(48시간) 만료 시 실패 전환의 사다리를 탄다. 이 비대칭이 재PXE 설계를 좌우한다 — 설치 중인 게스트는 구조적으로 대기로 세울 수 없다.

1-5. 종단 exit 와 재부팅 무장의 공백

IpxeScripts.completedExit() 는 exit 한 줄로 iPXE 를 끝내 펌웨어 부트 순서로 넘긴다. 지금은 dispatch 4행(종단)에서 OS 설치까지 갔던 커서만 이 응답을 받는다. 한편 E2.5 는 전원 투입과 설정 재시작 두 자리에서만 NextBoot.PXE_ONCE 를 무장하므로, Windows Setup 이 스스로 하는 재부팅에는 무장이 없다 — 그 재부팅은 펌웨어 순서를 따르고, UEFI 는 설치 도중 새로 만든 Windows Boot Manager 를 앞에 두는 것이 보통이다. 다만 네트워크가 앞에 있는 펌웨어에서는 매 재부팅마다 재PXE 가 일어난다.

1-6. 토큰 서빙의 선례

FirmwareImageTokenRegistry 가 UUID 토큰을 파일 경로에 묶고 (게스트, 축) 키로 회수하며, urlFor 가 URL 끝에 실제 파일명을 붙인다(BMC 가 확장자로 이미지 형식을 판별하기 때문). 서빙은 FirmwareImageRestController 의 GET /api/pxe/v1/firmware/{token}/{fileName} 이 FileSystemResource 로 하고, 미발급 · 회수 토큰은 404 로 같이 다룬다. 반대로 진단 자산은 /api/pxe/v1/assets/** 무인증 정적 서빙이다 — 비밀값이 없기 때문에 가능한 선택이었다.

1-7. E4-1-a-2 가 남긴 재료

  • WindowsInstallProperties — sourceRoot · shareUnc · shareUser · sharePassword · timeZone · productKeys
  • WindowsImageCatalog.snapshot() — 소스 install.wim 의 이미지 목록(이름 · editionId · language · build)
  • WindowsInstallationRequest — 정의서 payload. imageName 과 administratorPassword(평문 저장)
  • WindowsInstallSourceArea — 대시보드 관측 영역. 지금 슬롯 셋(boot.wim · install.wim · setup.exe)

1-8. 실측이 고정한 계약 (변경 불가)

실측 1호가 실기에서 성공시킨 파일 넷의 모양이 이 슬라이스의 렌더 대상이다. 우리는 구조를 바꾸지 않고 값만 채운다.

  • win.ipxe — kernel wimboot 뒤에 winpeshl.ini · install.bat · autounattend.xml · boot.wim 을 initrd 로 얹고 boot
  • winpeshl.ini — [LaunchApps] 의 cmd.exe, /k X:\Windows\System32\install.bat
  • install.bat — wpeinit → ping 대기 → wpeutil WaitForNetwork → LanmanWorkstation 재시작 → net use N: 20회 재시도 → N:\sources\setup.exe /unattend:X:\Windows\System32\autounattend.xml. 파일 전체가 ASCII
  • autounattend.xml — windowsPE 패스(언어 · ProductKey · DiskID 0 WillWipeDisk · EFI 260 / MSR 128 / Primary · MetaData 의 /IMAGE/NAME) · specialize 패스(ComputerName · TimeZone) · oobeSystem 패스(AdministratorPassword · AutoLogon · OOBE 숨김 · FirstLogonCommands)

비밀번호 두 자리는 Base64 인데, 대상 문자열이 평문이 아니라 평문 + 부모 노드명("AdministratorPassword" 또는 "Password")을 이어 붙인 뒤 UTF-16LE 로 인코딩한 것이다. 실측 스크립트가 그렇게 만들었고 실기가 그것으로 로그인에 성공했다.

1-9. 화면에 자리가 없다

GuestServerDetailResponse 는 phase 카드를 셋(firmwarePlan · firmwareFlash · firmwareSetting)과 RAID 계획을 담지만 OS 설치 카드는 없다. 시한을 화면에 표시하는 관용구는 이미 있다 — FlashTimeoutPolicy 가 Environment 키를 DurationStyle 로 읽고 상세가 stageRemainingMinutes 로 남은 분을 보여준다. 이 슬라이스는 그 관용구를 그대로 따른다.

        아래 수는 계획값이며 CP4 잔여 구간에서 실제 작성 수와 대조한다.

      §7. 예외 계층
      

        
신규 예외 없음. 이 슬라이스가 다루는 비정상은 셋인데 어느 것도 예외가 적절한 자리가 아니다.

        
    
          
  • 토큰이 없거나 회수됐다 — WindowsInstallAssetRestController 가 ResponseEntity.notFound() 를 돌려준다.
          FirmwareImageRestController 가 이미 같은 선택을 했고, 위조와 만료를 같은 응답으로 다루는 편이 정보 노출이 적다.
          게스트는 iPXE 라 예외 바디를 읽지도 못한다.
    • 
          
  • 설치 시한 · 재진입 상한 초과 — 원장 사유 코드 INSTALL_TIMEOUT · REPXE_LOOP 로 남기고 markFailed 로 전환한다.
          E3 SettingLedger 와 RaidLedger 가 세운 관례다. 예외로 올리면 운영자에게 보일 자리가 사라진다 —
          실패는 화면에서 재시도 버튼과 함께 읽혀야 하는 상태이지 스택 트레이스가 아니다.
    • 
          
  • 발급되지 않은 토큰의 URL 조립 같은 내부 모순 — IllegalStateException 을 그대로 던진다.
          집행 흐름의 버그이지 사용자 입력 문제가 아니므로 흡수하지 않는다(FirmwareImageTokenRegistry.urlFor 의 선례).
    • 
        

        
HTTP 매핑도 기존 그대로다. /api/pxe/v1/** 는 PXE 한정 advice 가 처리해 어떤 예외든 iPXE 대기 스크립트(retryAfterError)로 흡수한다 —
        JSON 오류 바디가 iPXE 로 새면 게스트가 파싱에 실패해 부팅 자체가 멎기 때문이다.
        관리자 화면 경로는 기존 advice 를 그대로 탄다.

      

    


    
    

      §8. 예상 부산물 / 주의 / 결정 사항
      

        
D-1 착수 전이는 onBootScriptServed 훅 + BootDispatch 로 잡는다

        
채택 — dispatcher 의 반환형을 BootDispatch(script, delegated) 로 넓히고, BootService 가 위임된 실행기에게 훅을 건다.
        전이는 여전히 BootService 트랜잭션 안에서 일어나고 dispatcher 는 읽기 전용을 지킨다.

        
대안 ① dispatcher 안에서 직접 전이 — 탈락 DEC-2 의 "상태를 일절 바꾸지 않는 읽기 전용 판정" 을 깬다.
        이 규약이 있어서 dispatch 매트릭스를 단위 테스트로 자유롭게 돌릴 수 있었다.

        대안 ② 실행기 bootScript 안에서 전이 — 탈락 스크립트 생성 함수가 부수효과를 갖게 되고,
        HOLD 경로에서도 호출되는지가 호출자마다 달라 보인다. 순수 함수로 두어야 재PXE 판정 테스트가 쉽다.

        대안 ③ iPXE imgfetch 로 착수 GET 을 한 번 더 — 탈락 서버가 이미 아는 사실을 게스트가 되돌려 알리는 왕복이고,
        그 요청이 실패하면 스크립트는 받았는데 상태는 안 열린 불일치가 남는다.


        
D-2 재PXE 는 시한 + 상한으로 다루고 초과만 실패로 전환한다

        
채택 — 정상 재부팅은 통과시키고(exit), 설치 시한 60분과 재진입 상한 5회를 넘을 때만 실패로 전환한다. 둘 다 설정 키다.

        
토론 D1 의 "3회째 HOLD" 를 정정한다. Windows Setup 은 정상 설치에서도 두세 번 재부팅하므로 3회는 정상 구간과 겹치고,
        무엇보다 holdForShortage 가 STEP_RUNNING 에서 거부하므로 대기라는 표현 자체가 불가능하다.
        실패 + 운영자 재시도는 이 시스템이 이미 쓰는 회복 UX 다.

        대안 설치 중에는 BMC 부팅 순서를 디스크로 바꾼다 — 탈락 Q4 에서 이미 걸러졌다.
        Redfish 쓰기가 늘고, 설치가 실패했을 때 부팅 순서를 되돌릴 책임이 새로 생긴다.


        
D-3 서빙은 게스트당 일회용 토큰 번들로 한다

        
채택 — 토큰 하나가 파일 다섯을 가리키고, 재발급 시 앞의 토큰은 그 자리에서 죽는다.
        542 MB 짜리 boot.wim 도 이 토큰 아래에 둔다.

        
대안 ① 게스트 토큰을 URL 에 그대로 — 탈락 게스트 수명만큼 긴 토큰이 URL 과 접근 로그에 남는다.

        대안 ② 소스를 정적 서빙 — 탈락 렌더본에 비밀값이 들어 있고, 정적 서빙을 열면 소스 루트 전체가 열람 대상이 된다.


        
D-4 준비도는 의존 0 인 정적 판정 + SPI 역전으로 만든다

        
채택 — WindowsInstallReadiness 는 인자 넷만 받는 순수 함수이고, 정의서 조회는 SPI 구현이 provisioning 쪽에서 한다.
        FirmwareResolution.toReadiness 와 같은 결이다.

        
리눅스 정의서가 이 phase 로 들어오면 조용히 REBOOT 시키지 않고 BLOCKED 로 드러낸다.
        조용한 통과는 "왜 아무 일도 안 일어나는가" 를 만들고, 그 질문은 로그를 뒤져야 답이 나온다.


        
D-5 wimboot 은 소스 루트의 파일로 두고 슬롯 · 해시 chip 으로 관측한다

        
채택 — InstallSourceSlot 에 네 번째 항목을 더하고 SHA-256 앞 12자를 chip 으로 보여준다.

        
대안 앱 자산(마커 봉인)으로 승격 — 탈락 wimboot 은 운영 절차가 교체하는 파일이고
        Windows 설치 소스 영역은 관측 전용이다. 승격하면 같은 파일이 자산 모델과 소스 영역 두 곳에 살아 이중 모델이 된다.
        Authenticode 서명 검증은 이 슬라이스의 비목표이고, 런북 §14-4 의 해시와 눈으로 대조하는 것으로 대신한다.


        
D-6 언어와 이름은 매핑 표 없이 결정적으로 만든다

        
채택 — 언어는 이미지의 language 태그를 UILanguage · SystemLocale · UserLocale · InputLocale 넷에 그대로 넣는다.
        ComputerName 은 SPV- + systemUUID 뒤 8 hex 다.

        
매핑 표를 두면 이미지가 늘 때마다 표를 고쳐야 하고, 표에 없는 언어에서 조용히 빈 값이 나간다.
        대안 ComputerName 을 *(Windows 가 무작위 생성) — 탈락 이름이 매번 달라져
        E4-1-a-4 의 완료 보고와 게스트를 대조할 열쇠가 사라진다.


        
D-7 비밀번호 인코딩은 서버가 한다

        
채택 — UnattendPassword.encode 가 Base64(UTF-16LE(평문 + 노드명))를 만든다.
        Base64 값도 난독화일 뿐이므로 평문과 같은 비밀로 취급해 로그 · 원장 · 화면 어디에도 남기지 않는다.
        렌더본은 메모리에만 있고 토큰이 회수되면 함께 사라진다.


        
D-8 phase 종결은 이 슬라이스가 하지 않는다

        
채택 — 설치에 성공한 게스트도 STEP_RUNNING 에 머문다. 상세 카드는 "설치 중 · 완료 보고 대기(E4-1-a-4)" 로 그 사실을 드러낸다.

        
알려진 공백 : 부트 순서가 디스크 우선인 펌웨어에서는 재PXE 가 아예 없어 시한 판정이 일어나지 않는다.
        회복 경로는 둘이다 — 상세 조회 시 잔여 0 을 표시해 운영자가 알아채게 하고, 운영자 수동 실패 전환(UC-4)으로 닫는다.
        시한을 스윕하는 워커를 둘지는 완료 보고가 생기는 E4-1-a-4 에서 판단한다.


        
D-9 게스트 접점의 검증 수단은 하네스뿐이다

        
채택 — CP5 의 E 계열 예외를 그대로 따른다. 실제 WinPE 부팅은 CP7 실기 일괄로 넘긴다.
        관리자 화면(상세 카드 · 대시보드 슬롯)은 브라우저로 검증한다.


        
주의 · 잔존 책임

        

          
    
            
  • RetryPolicy 는 펌웨어 phase 실패만 재시도 차단 후보로 삼는다(isFirmwarePhaseFailure 술어 하나 — 09-03 코드 확인). origin windows-install 의 INSTALL_TIMEOUT · REPXE_LOOP 실패는 그대로 재시도 가능이므로 술어 추가는 없다. CP4 의 실행기 단위 테스트가 "실패 → 재시도 → 재서빙" 으로 이 전제를 고정한다.
    • 
            
  • ProvisioningHistory.updateMeta 를 새로 두되, RUNNING 행을 닫는 E4-1-a-4 가 서빙 메타를 덮지 않도록 제약을 인계한다.
    • 
            
  • 토큰 회수 시점은 E4-1-a-4 소관이다. 이 슬라이스에서는 재서빙 · 실패 전환 때만 회수되므로, 완료한 게스트의 토큰이 남는 구간이 생긴다.
    • 
            
  • 로그에 렌더본 전문과 비밀값이 실리지 않는지 CP5 에서 전수 검색한다(로그 · 원장 · 상세 · 대시보드 넷).
    • 
            
  • BootDispatch 도입으로 BootScriptDispatcherTest 의 시그니처가 바뀐다 — 기존 테스트 갱신이 따라온다.
    • 
            
  • PhaseSequence 가 OS_INSTALLING 으로의 전진을 허용하는지(TESTING 앞자리) CP2 에서 확인한다.
    • 
            
  • 샌드박스에서 Windows 실행기는 조건 없이 로드되지만, 진단 실행기가 없으면 커서가 전진하지 않는다 — 하네스에는 PXE_ASSETS_ROOT 가 필요하다.
    • 
            
  • 브리프와 코드가 어긋나 보인 지점 : BootScriptDispatcher 의 클래스 Javadoc 은 dispatch 매트릭스를 "6행 HOLD → 7행 위임" 으로,
            같은 파일의 인라인 주석은 "7행 HOLD / 8행 위임" 으로 적는다. 이 문서는 인라인 주석 쪽 번호를 따랐다. 클래스 Javadoc 이 E2-1-b 의 결손 대기 행 삽입 전 번호를 그대로 둔 것이므로, CP2 에서 반환형을 바꾸는 김에 Javadoc 을 인라인 쪽(7행 HOLD · 8행 위임)으로 맞춘다.
