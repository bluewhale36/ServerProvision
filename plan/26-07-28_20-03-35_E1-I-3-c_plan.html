§1. 현재 상태 (진단)

E1-I-3 은 "프로비저닝 서버가 PXE 부팅에 쓰는 dhcpd(DHCP 서버) 구성을 관리 화면에서 다룬다"는 우산 작업이다. 세 조각으로 나눠 앞의 둘(a, b)은 이미 끝나 커밋됐고, 이 c 가 마지막이다.

분할한 일DB 변경상태
a범용 버전 저장소(자산 이력) 도입없음완료·커밋
bdhcpd 상태를 관측만(읽기 대시보드) — 신규 예외 0없음완료·커밋
cdhcpd 조각을 쓴다(관리자 폼 → 조각 파일 반영)있음(엔티티 1개)본 plan
쉬운 말 요약 — b 까지는 "지금 dhcpd 가 어떤 상태인지 들여다보기"만 했다. c 는 관리자가 화면 폼에 네트워크 값(어느 대역에 어떤 IP 범위를 나눠줄지 등)을 입력하면, 그 값을 dhcpd 가 읽는 설정 조각 파일로 만들어 실제로 반영한다. "읽기"에서 "쓰기"로 넘어가는 순간이라, 여기서부터 진짜 실패가 생긴다.

쓰기가 되면서 새로 생기는 실패 모드

  • 렌더한 조각이 문법 오류일 수 있다 → dhcpd 문법 검사(dhcpd -t)가 거절.
  • 반영 후 dhcpd 재기동이 실패할 수 있다.
  • 실패해서 이전 조각으로 되돌리는 것마저 실패할 수 있다.
핵심 설계 난제 — 이중 쓰기(dual-write)
DB 의 PxeNetworkConfig 1행은 @Transactional 로 롤백되지만, 조각 파일 쓰기(파일시스템)와 systemctl restart(외부 명령)는 트랜잭션이 아니다. 이 셋을 잘못 엮으면 "화면(DB)은 새 구성인데 dhcpd(파일시스템)는 옛 구성" 같은 괴리가 생긴다. 이 슬라이스 설계의 절반은 그 괴리를 어떻게 없애느냐다.

진입 전제 (b 까지 갖춰진 것)

  • 외부 명령 화이트리스트 AllowedCommand(DHCPD_SYNTAX_CHECK, DHCPD_SERVICE_STATUS 보유, sudoersLine() 데이터가 c 의 소비를 기다리며 예약돼 있음).
  • 명령 실행기 SystemCommandRunner + 결과 CommandResult/CommandOutcome, 서비스 상태 조회 SystemServiceInspector.
  • 자산 버전 이력 AssetHistoryService + AssetVersionKey, 파일 권한 재봉인 FileSystemHardener.
  • 진단 자산 활성화 DiagnosticAssetActivationService.activate() — "temp 실체화 → archive → 원자 교체 → 권한 → 재봉인" 순서의 선례. c 가 이 중 원자 교체 3단을 부품으로 추출해 공유한다.
  • 대시보드 관측 전용 DhcpdConfigInspector(ConfigFileCondition 반환) — c 에서 무변경 유지.
§2. 요구사항 (확정) + 비목표 + 범위

적용 파이프라인 (확정 순서)

폼 저장 → 조각 렌더 → 원자 교체 → dhcpd -t 게이트 → 재기동 → is-active verify → (실패 시) 이전 조각 자동 복원 + 재기동

요구사항

  1. dhcpd -t 출력 원문 노출 — 문법 거절 사유를 가공하지 않고 그대로 화면에 보여준다(관리자가 어디가 틀렸는지 즉시 안다).
  2. 원자 교체 — 조각을 덮어쓰는 도중 부팅한 게스트가 잘린 파일을 받지 않도록, temp 에 완성한 뒤 원자적 이동(ATOMIC_MOVE)으로 "옛 조각 아니면 새 조각"만 보이게 한다.
  3. 3 실패경로 모두 처리 — 게이트 거절 / 재기동 실패 / 복원 실패 각각에 결과·복원·HTTP 응답을 정의한다.
  4. 실패도 기록 — 실패해도 관리자가 입력한 desired 와 마지막 결과(appliedResult)를 DB 에 남긴다.
비 목표
  • 다중 subnet — 이 슬라이스는 서빙 대역 1개(단일행). 다중 대역은 "갈라지는 시점에" 자식 테이블로 분리(후속).
  • iPXE 스크립트 본문(boot.ipxe) — E1-0b 소관.
  • 조작 감사 이력 테이블 — 누가 언제 어떤 구성으로 바꿨는지의 감사 로그는 후속 마일스톤(E8).
  • 관측 캐싱 — 대시보드 성능 최적화는 범위 밖.
검증 상한 — 조각 반영이 실제로 먹히는지는 실 Rocky Linux 서버(T3)에서 재기동·include 반영을 확인해야 한다(스텁으로는 파이프라인 분기까지만). 이 T3 검증은 CP5 에서 사용자와 합동으로 수행한다.

VO / Enum (Primitive Obsession 차단)

record SubnetCidr(String value) {          // 신규 — 교차불변·파생의 SSOT
    boolean contains(IpAddressVO ip);      // range ⊆ subnet 검사
    boolean containsRange(IpAddressVO start, IpAddressVO end);
    String  netmask();                     // prefix → dotted netmask (결정적 순수 함수)
    int     prefixLength();
}
record LeaseSeconds(long value) {          // 신규 — 양수 가드, max ≥ default 비교
    static LeaseSeconds of(long v);        // v ≤ 0 → IllegalArgumentException
}
enum ApplyResult { APPLIED, REJECTED, ROLLED_BACK, RESTORE_FAILED }  // 판정 SSOT

SubnetCidr ↔ DB 는 SubnetCidrConverter(@Converter(autoApply=false)) 로 VARCHAR 매핑. IpAddressVO/IpAddressConverter 는 재사용.

ApplyResult — method-per-constant (분기 없는 예외 생성)

enum ApplyResult {
    APPLIED        { void throwIfNotApplied() { /* no-op */ } },
    REJECTED       { void throwIfNotApplied() { throw new DhcpConfigInvalidException(gateOutput); } },
    ROLLED_BACK    { void throwIfNotApplied() { throw new DhcpServiceControlFailedException(...); } },
    RESTORE_FAILED { void throwIfNotApplied() { throw new DhcpConfigRestoreFailedException(...); } };
    abstract void throwIfNotApplied();     // switch 없음 — 상수가 자기 예외를 안다
}
// ApplyOutcome : { ApplyResult result, String gateOutput, Long appliedVersionId, ... }
//   → outcome.throwIfNotApplied() 는 트랜잭션 밖에서 호출(D3)

검증 술어의 단일 SSOT (D12)

클래스레벨 @ValidPxeNetworkConfig(400 필드에러) 와 정적 팩토리 PxeNetworkConfig.create() 의 서버 안전망 if-throw 가 같은 SubnetCidr 술어(containsRange/contains)와 LeaseSeconds 비교를 호출한다. 잘못된 CIDR/range 는 예외가 아니라 @Valid+BindingResult 필드에러로 떨어진다.

§8. 설계 결정 D1~D12 / 열린 질문 / 부산물
이 슬라이스 CP1 의 핵심은 아래 D1~D12 다. 각각 채택안 / 왜 / 비채택안+탈락사유 / 잔여로 편다. 적대적 자기비판의 6개 결함(트랜잭션 롤백·실패 미저장·inspector 재사용 불가·복원 이동 실패·동시성 괴리·최초삭제 dangling)을 전부 반영한 확정본이다.

D1 · 파이프라인 순서 = swap-then-gate + apply-then-persist, 종단 1회 커밋

  • 채택 — DhcpdConfigApplyService(비트랜잭션)가 render→temp → swap(archive+ATOMIC_MOVE+권한) → restorecon(비치명) → gate(dhcpd -t) → restart → verify(+복원)를 수행해 ApplyOutcome 만 반환. 그 뒤 PxeNetworkConfigService(유일 @Transactional)가 desired + appliedResult + appliedVersionId + appliedAt 를 1회 종단 커밋.
  • 왜 — DB 쓰기가 FS/명령 파이프라인의 완전 귀결(복원 포함) 뒤에 오므로 이중 쓰기가 소멸(2PC·saga·DB 보상 불필요). 외부 명령(수 초)이 트랜잭션 밖이라 커넥션·락 미점유. 게이트를 원자 교체 후 dhcpd 가 실제 로드하는 실 dhcpd.conf 전체 트리에 실행 → 조각 단독 검증이 못 잡는 교차선언 충돌(중복 subnet 등)까지 포착. 재기동은 게이트 통과 뒤에만 하므로 운영 중 dhcpd 는 무효 조각에 노출되지 않음.
  • 비채택 — (a) DB 커밋 우선+보상: APPLIED 선커밋이 실패 시 보상 트랜잭션을 필수화하거나 재기동 동안 트랜잭션 개방(커넥션 점유). (B) gate-before-swap: E5 열린 질문으로 병기.
  • 잔여 — swap↔gate 사이 미검증 조각이 디스크에 존재하는 초 단위 창(restorecon ≤5s + dhcpd -t ≤3s). 단일비행 락으로 최소화하되 완전 제거는 아님 — 이 창이 운영상 위험하면 E5(대안 B)로 전환.

D2 · 실패도 appliedResult 로 기록

  • 채택 — REJECTED/ROLLED_BACK/RESTORE_FAILED 여도 desired + appliedResult 저장. ("실패 시 미저장" 문구 폐기.)
  • 왜 — 엔티티 appliedResult enum 이 그 세 값을 가진 이상, 미저장이면 그 값이 DB 에 영원히 안 나타나는 죽은 값이 됨. 저장해야 "DB(desired, REJECTED) vs FS(옛 조각 서빙 중)" 괴리를 화면이 설명할 수 있음.
  • 잔여 — "저장된 desired ≠ 현재 서빙 구성"을 Response/화면이 명시해 폼 프리필 오해를 차단.

D3 · throwIfNotApplied() 는 트랜잭션 밖에서 호출 핵심

  • 채택 — @Transactional save() 는 엔티티/ApplyOutcome 를 정상 리턴만. 비-APPLIED 를 예외로 승격하는 outcome.throwIfNotApplied() 는 트랜잭션 밖(비-tx 오케스트레이터 또는 컨트롤러)에서 save 리턴 후 호출.
  • 왜 — RuntimeException(DomainException)이 @Transactional 메서드 본문에서 던져지면 프록시가 그 트랜잭션을 롤백 → 방금 저장한 REJECTED 행이 사라짐. 커밋은 메서드 리턴(프록시 경계)에 일어나 "커밋 후 throw"는 단일 tx 메서드로 물리적 불가. D2 의 "실패 기록 보존"이 성립하려면 필수 정정.
  • 잔여 — 컨트롤러 try/catch 0 · 신규 advice 0 유지(오케스트레이터/컨트롤러가 단순 재throw → 기존 handleDomain 매핑).

D4 · 게이트는 inspector 재사용이 아니라 CommandResult 직접 소비

  • 채택 — 게이트는 SystemCommandRunner.run(DHCPD_SYNTAX_CHECK, dhcpdConfPath) 를 ApplyService 가 직접 호출해 CommandResult 를 받아 (a) stdout/stderr 원문을 REJECTED 예외 message 에 실어 화면 원문 노출, (b) COMPLETED & exit≠0→REJECTED(400), NOT_FOUND/TIMED_OUT→게이트 실행불능(500 인프라). DhcpdConfigInspector.inspect() 는 게이트에 쓰지 않고 대시보드 관측 전용으로 무변경 유지.
  • 왜 — 실코드 inspect() 는 ConfigFileCondition enum 만 반환하고 CommandResult 를 폐기 → 원문 소실(요구 위반). 또 NOT_FOUND/TIMED_OUT→UNKNOWN 으로 접어 dhcpd 미설치·hang(인프라 500급)을 SYNTAX_ERROR 와 구분하는데, "gate≠SYNTAX_OK→REJECTED(400)"로 뭉개면 인프라 장애가 빈 메시지 400 으로 오분류.
  • 비채택 — inspect() 재사용(중심 재사용안): 원문 노출 요구와 양립 불가.

D5 · AtomicAssetSwap 부품 — 복원도 materialize-then-move, restoreFrom 폐기

  • 채택 — global/asset/AtomicAssetSwap(무상태 부품). SwapResult swap(Path target, Path staged, AssetVersionKey key) = archive(현재 target) → ATOMIC_MOVE(REPLACE_EXISTING) → FileSystemHardener 기본권한. 복원은 별도 restoreFrom 대신 archivedPath 바이트를 temp 로 copy → ATOMIC_MOVE(temp→조각) → 권한(진단 activate 와 동형), history 파일은 move 금지·필요 시 historyService.remove 로 정리.
  • 왜 — history 루트가 조각 디렉토리와 다른 파일시스템이면 archivedPath→조각 직접 ATOMIC_MOVE 가 AtomicMoveNotSupportedException(진단 선례가 temp 를 자산 루트 하위에 만든 이유). history 파일 move 는 asset_version 행을 dangling 으로. materialize-then-move 로 수렴하면 단일-호출자 restoreFrom 도 소멸(부품 표면 축소).
  • 잔여 — staged 를 조각과 같은 디렉토리에 렌더(같은 FS + SELinux 컨텍스트 상속)해야 ATOMIC_MOVE 성립. fsync 는 진단 선례대로 생략(ATOMIC_MOVE 가 torn-read 배제).

D6 · 동시성 — ReentrantLock 이 apply()+persist() 를 함께 감쌈, @Version 제거

  • 채택 — DhcpdConfigApplyService 에 프로세스 단일비행 ReentrantLock(blocking, 관리자 저빈도). 임계구역이 apply()+persist() 를 함께 감쌈(오케스트레이터가 락 안에서 둘 다 호출, @Transactional 은 persist 메서드에만). @Version 은 추가하지 않음.
  • 왜 — 락을 apply() 리턴에서 풀면 A-FS→B-FS→A-persist→B-persist 인터리브로 FS=B·DB=A 괴리. FS 는 커밋 전에 적용되므로 @Version 충돌 시 FS 는 롤백 안 됨 → "409인데 dhcpd 는 새 구성" 괴리 = @Version 은 거짓 안심.
  • 잔여 — 단일 인스턴스 관리 앱 전제.

D7 · 최초 적용 게이트 실패 = 조각 삭제 대신 주석-only 유효 빈 조각

  • 채택 — archivedPath 가 비는(최초, 이전본 없음) 복원에서 조각을 삭제하지 않고 주석-only 유효 빈 조각을 씀(include 유효 유지).
  • 왜 — ISC dhcpd 에서 include "managed.conf"; 대상이 없으면 파싱 fatal → 운영자가 include 를 미리 넣은 상태에서 최초 apply 가 REJECTED 되어 조각이 삭제되면 이후 모든 dhcpd 재기동 실패 = 서빙 중단.
  • 잔여 — 구축 문서에 최초 include 삽입·빈 조각 안내.

D8 · 예외 3종 + 게이트 실행불능 매핑

  • 채택 — ApplyResult enum{APPLIED, REJECTED, ROLLED_BACK, RESTORE_FAILED} = 판정 SSOT, 각 상수가 method-per-constant 로 자기 예외 생성(switch 없음). 신규 예외 3종 전부 DomainException 상속 → 기존 WebExceptionHandler.handleDomain 이 코드 추가 없이 매핑: REJECTED→DhcpConfigInvalidException(400, dhcpd -t 원문) / ROLLED_BACK→DhcpServiceControlFailedException(500) / RESTORE_FAILED→DhcpConfigRestoreFailedException(500, 수동복구 안내) / 게이트 실행불능(NOT_FOUND/TIMED_OUT)→DhcpServiceControlFailedException 재사용(E4).
  • 왜 — DomainException 상속 + @ResponseStatus 다형 라우팅이 기존 handleDomain 을 무변경 재사용 → 컨트롤러 try/catch 0 · 신규 advice 0.

D9 · 명령 경계 — AllowedCommand 2상수 추가 (data 확장)

  • 채택 — DHCPD_SERVICE_RESTART(/usr/bin/systemctl restart dhcpd, ArgShape.NONE, sudo, timeout ≈20s, sudoers 라인) + RESTORE_SECURITY_CONTEXT(/usr/sbin/restorecon, ArgShape.ONE_PATH, sudo, 5s, sudoers 라인). 재기동 후 verify 는 SystemServiceInspector.status() 재사용. restorecon 실패는 CommandResult 로 흡수·로그(비치명). sudoers 두 줄은 AllowedCommand.sudoersLine() 에서 생성(b 가 예약해 둔 데이터를 c 가 소비 — 코드↔문서 drift 0).
  • 왜 — enum data 확장은 분기 확장이 아님, method-per-constant·b 의 2상수 무손상. 재기동 timeout 은 dhcpd -t 의 3s 를 답습 금지 — systemctl restart 는 유닛 active 도달까지 블록해 3s 면 정상 재기동을 TIMED_OUT 오판 → 불필요 복원 유발.
  • 잔여 — SELinux 1차 기전은 컨텍스트 상속, restorecon 은 보조. Rocky enforcing 여부에 따라 restorecon 자체가 불필요할 수 있음(E3).

D10 · 엔티티/VO — 단일행 평면 + SubnetCidr·LeaseSeconds 신규 VO + IpAddressVO 재사용

  • 채택 — §4 참조. 단일행 평면 엔티티 + 신규 VO 2종 + Converter, Repository=findFirstByOrderByIdAsc().
  • 왜 — 스코프가 단일 서빙 subnet — 단일행 평면이 폼·렌더러·리포지토리를 최소로 유지(본 동기 = 명확한 사용성 + 단순한 구현). next-server/filename/authoritative/subnet-mask 는 필드에서 제외 → 앱 소유 상수·CIDR 파생(SubnetCidr.netmask())으로 렌더러 고정 출력, mask 이중출처 drift 차단.
  • 비채택 — 다중 subnet 자식 테이블: over-abstraction("갈라지는 시점에 분리"). VO 최소화(IP/lease 원시): Primitive Obsession 위반.
  • 잔여 — lease-time 필드는 우산 엔티티표에 누락돼 있음 → CP3 에서 LeaseSeconds 필드·컬럼 보강. dnsServer 단일 vs 2필드는 E1.

D11 · 렌더러 — 순수 Java text block, 골든 결정성 규율

  • 채택 — DhcpdConfigRenderer.render(PxeNetworkConfig):String = IO·throws 없는 순수 함수. Java 21 text block + VO 접근자 명시 순서 삽입. renderToTemp 는 얇은 래퍼. pxeclients 분기(next-server=bootServerIp / filename=자산계약 고정 상수)를 조각에 포함, iPXE 스크립트 본문은 제외(E1-0b).
  • 왜 — 골든 비교의 성립 조건(바이트 결정성 + 얇은 테스트) + over-abstraction 금지가 순수 Java 를 가리킴. 조각은 기계 문법이라 Thymeleaf/외부 리소스 이점 0이고 엔진·리소스 변수만 골든 안정성을 훼손.
  • 비채택 — Thymeleaf TEXT 모드(공백·이스케이프가 결정성·세미콜론/브레이스에 취약), 외부 템플릿+치환(SSOT 2곳 분산).
  • 잔여(골든 규율) — (1) "직접수정 금지" 머리말은 정적 문자열(가변값 금지) (2) prefix→netmask 결정적 순수 함수 (3) 삽입 순서 리터럴 고정, Map/Set 순회 배제 (4) trailing newline 포함 (5) secondaryDns·domainName null 유무 4조합 골든 픽스처. filename 상수·pxeclients 문법은 T3 잠정.

D12 · 검증 SSOT — 클래스레벨 ConstraintValidator + 정적 팩토리 가드 공유 술어

  • 채택 — 포맷·교차불변(range⊆subnet, start≤end, defaultLease≤maxLease)을 SubnetCidr 가 contains()/containsRange()/netmask()/prefixLength() 로 보유(SSOT). 정적 팩토리 PxeNetworkConfig.create() 의 if-throw 서버 안전망과 클래스레벨 @ValidPxeNetworkConfig ConstraintValidator(400 필드에러)가 같은 도메인 술어 호출. 잘못된 CIDR/range 는 예외가 아닌 @Valid+BindingResult 필드에러.
  • 왜 — "UI 차단·서버 가드 단일 SSOT" + "잘못된 입력은 예외 아닌 필드에러"를 동시 충족. 조건분기 없이 Spring primitive(Bean Validation + AttributeConverter)로 흡수.
  • 잔여 — 술어 복제 시 drift → 둘이 반드시 같은 SubnetCidr 술어 호출. IpAddressVO 는 IllegalArgumentException 을 던지므로 Request 는 String 보유 → 바인딩 변환 실패가 400 필드에러로 자동 매핑됨을 테스트로 고정(IPv6 입력이 400 으로 떨어지는지 명시 검증).
