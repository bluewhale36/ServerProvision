§1. 현재 상태 (진단)

이 슬라이스는 ServerProvision-ue 스트림이 여덟 회차에 걸쳐 진행한 U4-1(디스크 관련 기능) 토론에서 파생했다. 착수 브리핑은 discussion/26-08-17_19-56-31_MA-raidcard-resource_briefing.md 다. U4-1-1 이 세팅 정의서에 RAID 구성 지정을 더하는데, RAID 를 실제로 거는 명령이 카드마다 다르고 만들 수 있는 RAID 레벨도 카드마다 다르다. 그래서 정의서가 "이 정의서는 어떤 카드를 전제하는가" 를 적어야 하고, 그러려면 카드가 참조 가능한 자원이어야 한다.

처음에는 카드 목록을 enum 으로 두려 했으나 다음 네 가지로 자원이 맞다고 결론냈다. ① 모델이 늘어나는 것이 확정이다 — MVP 대상인 GIGABYTE 4종 보드가 아닌 서버는 대부분 다른 카드를 쓴다. ② 식별 키가 문자열 하나가 아니라 PCI Subsystem ID 라 필드가 여럿이어서 enum 상수에 담기 어렵다. ③ enum 이면 정의서에 상수 이름이 저장되고, 나중에 자원으로 승격할 때 그 값을 마이그레이션해야 한다. ④ BoardModel 이 정확히 같은 형태라는 선례가 있고 BasicUpdateRequest 가 boardModelId 로 그것을 참조한다.

진입 전제

선행 슬라이스에 대한 대기는 없다. 자원 등록은 사람이 적는 정보만으로 성립하고, 관측으로 채우는 정보는 그 뒤다. 진단 에이전트가 lspci 를 옵션 없이 불러 Subsystem 을 수집하지 않는 것과 DiagnosticReportParser.kindOf 가 CRA3338 을 ETC 로 떨어뜨리는 것은 ServerProvision-ue 소관이며, 이 슬라이스는 그 둘을 기다리지 않는다.

F1 을 풀어 쓴다. Markable 은 무결성 인터페이스이기만 한 것이 아니라 휴지통으로 가는 통로이기도 하다. BoardModel 은 디스크 파일이 없는데도 Markable 을 구현하고 getResourcePath() · getManifestHash() · getMarkerSignature() 를 null 로, reissueMarker 를 no-op 으로 둔다. ResourceType 에는 metadata boolean 플래그가 이미 있고 OS_IMAGE · BOARD_MODEL 두 상수가 그 값을 true 로 갖는다. 휴지통 화면이 MarkableScanner 를 통해서만 자원을 보므로, 구현하지 않으면 삭제된 RAID 카드가 휴지통에 나타나지 않는다.

F3 이 이 슬라이스의 비용을 결정한다. PathReconciliationService 는 if (!scanner.supportedType().isMetadata()) 로 메타 자원을 드리프트 분류에서 제외한다 — 파일 실체가 없어 resourcePath 가 null 이므로 넣으면 NullPointerException 이거나 유령 오탐이 된다. 휴지통 컨트롤러도 cascade 옵션 수신과 trashed_path=null 을 정상으로 판정하는 데 같은 플래그를 쓴다. 즉 메타 자원 여부에 따른 분기가 이미 다형화되어 있어, 세 번째 메타 자원이 늘어도 그 두 파일은 고치지 않는다.

F4 는 이 슬라이스가 물려받지 않을 부채다. board_model 테이블의 CREATE TABLE 에는 PRIMARY KEY (id) 뿐인데, BoardModelRepository 와 DuplicateBoardModelException 의 주석은 둘 다 "DB 레이어의 uk_vendor_model_name 과 이중 가드를 이룬다" 고 적었다. 주석과 실제가 어긋나 있고, 실제로는 서비스 레이어의 existsBy… 하나가 유일한 가드다. 동시에 같은 모델명으로 등록하면 점검-사용 시점 사이의 창(TOCTOU — Time Of Check To Time Of Use)이 남는다.

브리핑의 예상 하나를 정정한다 — 브리핑 §5 는 "RAID 카드는 파일이 없으니 마커 인프라가 필요 없을 것" 으로 봤다. 절반만 맞다. HMAC 서명을 기록하는 *MarkerWriter 는 필요 없지만, Markable 과 MarkableScanner 는 휴지통이 자원을 보는 유일한 통로이므로 구현해야 한다(F1 · D1).
§2. 요구사항 (확정) + 비목표
  1. 자원 등록 · 조회 · 수정 — RAID 카드를 다른 관리 자원과 같은 방식으로 등록하고 목록 · 상세에서 확인하고 수정한다.
  2. 등록 입력 — 제조사 · 모델명 · 지원 RAID 레벨(복수 선택, 최소 1개 — 전체 선택/해제 제공) · 캐시 용량(GB, 0 = 없음) 은 필수, 설명과 PCI Subsystem ID 는 선택. CP6 개정 캐시는 유무가 아니라 용량으로 적는다(사용자 지시). 캐시 0 + RAID5 이상 조합은 경고 모달로 확인받되 차단하지 않는다 — RAID5 이상을 만들 수 있는 컨트롤러는 일반적으로 캐시를 갖기 때문(오기입 방지). 목록 C2 하단 등록 버튼은 현재 제조사를 프리셀렉트해 폼에 진입한다.
  3. lifecycle — 활성 토글 · Deprecated 표시와 해제 · 휴지통 이동 · 복구 · 영구 삭제(자원명 직접 입력 검증)를 다른 자원과 같게 제공한다.
  4. 유일성 — 삭제되지 않았고 Deprecated 도 아닌 카드는 제조사 · 모델명 조합이 유일하다(비활성 카드는 일시적으로 꺼 둔 것이므로 이름 점유를 유지한다). 서비스 검사만이 아니라 DB 불변식으로 강제한다.
  5. 등록 충돌 안내 — 이미 있는 이름으로 등록하면 무엇과 충돌했고 무엇을 할 수 있는지(진행 · 교체 · 취소) 모달로 안내한다.
  6. 휴지통 노출 — 삭제한 RAID 카드가 휴지통 화면에 나타나고 거기서 복구 · 영구 삭제할 수 있다.
  7. U4-1-1 에 주는 것 — 선택지 목록을 주는 조회(지원 RAID 레벨 동봉 — 작성 폼의 disabled 판정 재료), id 로 참조할 수 있는 안정된 키, 그리고 "이 카드로 이 RAID 레벨을 만들 수 있는가" 를 판정하는 도메인 메서드. 정의서는 카드의 id 와 이름만 얼리고 레벨 집합은 렌더 시마다 재조회한다.
  8. 화면 진입점 — 최상위 메뉴 "RAID 카드"(/management/raidcard).

이미 있는 것을 쓴다 (새로 만들지 않는 것)

목록 화면은 management/board/list.html 의 3단 Miller 구조와 miller.css 를 그대로 재사용한다. 등록 충돌 안내는 NudgeRegistry · IntentMetaNudgePayload · fragments/management/nudge-modal.html · global/nudge-modal.js 라는 공용 인프라가 이미 있어 도메인 쪽에서 상수 하나를 더하고 끼우는 비용이다. 점검 · 휴지통의 메타 자원 분기도 F3 대로 이미 다형화되어 있다. 이 슬라이스에서 새로 만드는 공용 CSS · 공용 JS 는 없다.

비 목표 :
  • '정밀 등록'(직접 관측) — 등록한 카드를 장착한 게스트 서버에 연결해 하드웨어 스펙을 관측해 채우는 기능. MVP 이후의 별도 슬라이스다(D3).
  • 관측 메타 컬럼 — 관측 시각 · 칩 계열 · 구성 명령 계열. 채우는 곳도 읽는 곳도 없으므로 지금 파지 않는다(D3).
  • 세팅 정의서의 RAID 구성 지정 — U4-1-1 이 한다. 이 슬라이스는 그것이 참조할 자원과 판정 메서드만 낸다.
  • 삭제된 카드를 참조하는 정의서의 처리 — 참조는 구조적으로 소프트참조다(D10). 사라진 카드를 가리키는 정의서를 화면에서 읽히게 만드는 일은 U4-1-1 소관이다.
  • board_model 의 유니크 제약 부재 교정 — F4 는 기록만 하고 고치지 않는다. 다른 도메인의 스키마 변경은 이 슬라이스의 검증 줄기 밖이다.
  • nav 그룹핑 · 반응형 개편 — 메뉴가 12개가 되며 F8 의 가로 오버플로가 소폭 악화되지만, nav 개편은 반응형 도입 단계 소관이다(D9).
  • 진단 수집 쪽 수정 — lspci -nn 전환과 파서 분류 교정은 ServerProvision-ue 소관이다.
🎬 미리보기 — 라이브 UX 데모 (지원 RAID 레벨을 어디에 둘 것인가)

이 데모의 주제는 D2 다. 브리핑은 지원 RAID 레벨을 관측으로 채우는 값(B 겹)으로 보는 쪽에 무게를 뒀고, 이 plan 은 그것을 뒤집어 등록 시 입력값으로 둔다. 아래에서 지원 RAID 레벨을 축을 관측값 쪽으로 옮겨 보면, 정밀 등록이 없는 지금 상태에서 화면이 아무것도 막지 못하게 되는 것을 직접 볼 수 있다. 판정 코드는 서버의 SupportedRaidLevels.blockReasonFor(RaidLevel) 와 같은 식이다(드리프트 0).

드리프트 0 — 데모의 disabled 판정 = 화면의 버튼 차단 = 서버 거절 사유가 모두 SupportedRaidLevels.blockReasonFor(RaidLevel) 단일 바디다. 최소 디스크 수 판정은 RaidLevel.minimumDisks(cardHasCache) 로 카드의 캐시 유무가 관여한다 — 캐시 없는 카드의 RAID0 은 2개 강제이지만 캐시 보유 카드는 단일 디스크 RAID0 구성이 실무에 존재한다(CP6 사용자 교정). AVAGO 9361-8i(캐시 2GB)를 RAID0 · 디스크 1개로 두면 통과하고 CRA3338(캐시 없음)은 차단되는 것을 데모에서 볼 수 있다.

마지막 행이 D7 의 요점이다. 서비스의 유일성 검사는 사용자에게 친절한 안내를 만들기 위한 것이고, 동시 요청이 그 검사를 함께 통과했을 때 실제로 막는 것은 DB 의 유니크 인덱스다. 두 가드가 같은 조건("삭제되지 않았고 Deprecated 도 아닌 것")을 본다.

§4. 도메인 모델 (SSOT) 
RaidCard extends LifecycleEntity implements Markable      // 테이블 raid_card
  id                   Long                    PK
  vendor               RaidCardVendor          NOT NULL   enum(STRING)
  modelName            String(128)             NOT NULL
  supportedRaidLevels  SupportedRaidLevels     NOT NULL   AttributeConverter → varchar
  cacheCapacity        CacheCapacity           NOT NULL   Converter → cache_capacity_gb INT, 0 = 없음 (CP6 개정)
  description          String(1024)            nullable
  pciSubsystemId       PciSubsystemId          nullable   @Embeddable → 2 컬럼
  (+ LifecycleEntity 상속: is_enabled · is_deleted · is_deprecated · own_enabled ·
     own_deprecated · deprecated_at · trashed_at · trashed_path · ttl_extension_days ·
     created_at · updated_at)

LifecycleEntity 를 상속하면 lifecycle 4 boolean 과 own/effective 분리, 휴지통 메타, 부모-자식 가드가 상위 클래스에서 온다. RAID 카드는 부모가 없는 루트 자원이라 parentLifecycle() 이 null 을 반환하고, 그러면 recomputeEffective() 에서 effective 값이 곧 own 값이 된다. 자식 자원도 없으므로 BoardModel 이 갖는 BoardScopedChildLifecycle 같은 cascade 어댑터가 필요 없다 — 자원 한 벌로서 BoardModel 보다 단순하다.

PciSubsystemId 는 Vendor 와 Device 를 하나로 감싼다. Device ID 단독으로는 어떤 카드도 가리키지 못하고 Vendor 와 쌍일 때만 카드 하나를 식별하기 때문이다. lspci -nn 의 출력도 [1458:0011] 처럼 쌍이다. parse(String) 이 "1458:0011" 과 "0x1458:0x0011" 을 함께 흡수하고 0x0000~0xFFFF 범위를 검증하며, toDisplay() 가 소문자 4자리 16진수 쌍으로 정규화해 돌려준다. 표기 차이 때문에 같은 카드가 다른 값처럼 비교되는 사고를 타입에서 막는 것이며, 이는 execution/vo/MacAddressVO.java 가 이미 쓰는 방식이다.

U4-1-1 과의 계약이 되는 도메인 메서드 (SSOT)

// SupportedRaidLevels
boolean supports(RaidLevel level);

// RaidLevel

                                           // 캐시 보유 카드는 RAID0=1 — 단일 디스크 RAID0 실무 구성 (CP6 교정)

Set<RaidLevel> 을 맨손으로 두지 않고 VO(Value Object — 값 자체가 정체성인 객체)로 감싸는 이유는 판정이 호출부마다 contains 로 흩어지는 것을 막기 위해서다. VO 에 supports 와 blockReasonFor 를 두면 U4-1-1 의 화면 disabled 플래그와 서버 가드가 그 메서드 하나를 함께 호출해 단일 출처(SSOT — Single Source of Truth)가 성립한다. 반환 규약은 provisioning/setting/vo/RequiredBoardModel.blockReasonFor(...) 에서 가져온다 — null 이면 통과, 아니면 그 문자열이 화면 안내이자 서버 거절 사유다. 단 선례와 시점 · 대상이 다르다는 것을 분명히 한다: RequiredBoardModel 의 판정은 정의서와 서버를 대조하는 할당 시점 판정이고(소유자는 AssignmentBlockKind.evaluate), SupportedRaidLevels 의 판정은 카드의 능력과 정의서가 요구하는 레벨을 대조하는 작성 시점 판정이라 서버가 등장하지 않는다. 같은 것은 반환 규약뿐이다. U4-1 토론에서 할당 시점의 카드 대조는 두지 않기로 확정됐으므로(AUTO 비활성 · 대조는 E 단계 소관) AssignmentBlockKind 에 카드 축 상수를 미리 파지 않는다. enum 집합을 VO 로 감싸 컬럼 하나에 저장하는 저장 형태의 선례는 provisioning/assignment/vo/OwnedPhases 와 OwnedPhasesConverter 다.

이 계약의 소비 형태도 선례를 따른다. U4-1-1 은 엔티티를 들지 않고 RequiredBoardModel(id, name) 을 본뜬 VO 를 세울 것이며, 그 VO 는 리포지토리를 모른다(RequiredBoardModel.from 이 Function<Long, String> 으로 이름 조회를 공급받는 것과 같은 방식). 따라서 MA7 의 조회 응답(RaidCardResponse)이 지원 RAID 레벨을 함께 실어야 한다 — 정의서 작성 폼이 카드 선택 시 disabled 플래그를 만들려면 목록 조회 시점에 레벨이 함께 와야 하기 때문이다. id → 이름, id → 지원 레벨의 단순 조회도 열어 둔다.

Markable 구현

getResourceId() 는 id 를, getResourceType() 은 ResourceType.RAID_CARD 를 돌려준다. getResourcePath() · getManifestHash() · getMarkerSignature() 는 파일이 없으므로 null 이고 reissueMarker 는 no-op 이다. displayName() 은 vendor.getDisplayName() + " " + modelName 이며, 이 값이 영구 삭제 시 자원명 직접 입력 검증의 기준값이자 확인 모달에 표시되는 이름이 된다.

Service 분할

조회 · 등록 · 수정 · 충돌 확인 완결을 맡는 RaidCardMetadataService 와 LifecycleService 를 구현하는 RaidCardLifecycleService 둘로 나눈다. R3-3 의 BoardModel 3분할 선례를 따르되 자식 cascade 가 없어 둘로 충분하다. 자원명 직접 입력 검증은 의존성이 없는 static TypedNameGuard.verify(Markable, String) 을 쓴다 — service 에 TypedNameVerifier 나 scanner 나 ObjectProvider 를 주입하면 R7 이 제거한 생성자 순환이 재생성되므로 금지다.

D1 — 마커 인프라를 절반만 만든다

ResourceType 에 RAID_CARD(MarkerLayout.SIDECAR, true, "RAID 카드") 를 더해 OS_IMAGE · BOARD_MODEL 에 이은 세 번째 메타 자원으로 둔다. 엔티티는 Markable 을 구현하되 경로 · 해시 · 서명을 null 로, reissueMarker 를 no-op 으로 둔다. 스캐너는 F2 대로 조회(MarkableInventory)를 빈 리스트로, 재조정(MarkableDriftApplier)을 no-op 으로 두고 휴지통(MarkableTrashOperator) 쪽 메서드만 실제로 동작시킨다. 자식 자원이 없으므로 findDeletedChildLabels 는 default 구현(빈 리스트)을 그대로 쓴다. R7-1 이 God-interface 를 4 sub-interface 합성으로 쪼갠 덕분에 새 도메인이 끼어드는 비용이 "19 메서드를 전부 채우기" 에서 "실제로 쓰는 것만" 으로 줄어 있다.

D2 — 지원 RAID 레벨을 등록 입력으로 둔다 (브리핑의 잠정 판단을 뒤집음)

브리핑 §3-1 은 "사용자가 등록 시 적을 수 있는 것은 캐시 유무이므로 지원 레벨은 관측 또는 별도 입력으로 가는 것이 자연스럽다, 이 판단은 CP1 에서 확정하라" 고 했다. 뒤집는 근거는 셋이다.

① U4-1-1 의 화면 차단이 이 값을 즉시 필요로 한다. 세팅 정의서가 RAID5 구성을 지정할 때 고른 카드가 RAID5 를 만들 수 없으면 화면이 먼저 막아야 한다 — CLAUDE.md 의 불가침 "UX 모순은 UI 1차 차단" 이 요구하는 바다. 이 값을 관측 필드로 두면 '정밀 등록' 이 없는 현재는 모든 카드의 값이 비어 있어 차단할 근거 자체가 없다. 🎬 미리보기의 관측값 토글이 그 상태를 재현한다.

② 관측으로 얻기 어려운 값이다. PCI Subsystem ID 는 lspci -nn 한 줄이면 나오지만 "이 컨트롤러가 RAID5 를 만들 수 있는가" 는 StorCLI 류 벤더 도구로 물어야 안다. 반면 카드 데이터시트에는 적혀 있어 사람이 아는 값이다 — 브리핑 §3-1 의 표가 이미 CRA3338 을 "RAID0 · RAID1 만, 최소 2개 디스크" 로 적었다.

③ 캐시 유무가 오히려 파생값이다. 브리핑 스스로 "같은 스펙 디스크 3개 이상이면 캐시 있는 카드" 라는 업무 관례의 진짜 이유가 캐시가 아니라 RAID5 를 만들 수 있는 컨트롤러인가라고 했다. 의사결정에 실제로 쓰이는 값을 선택 입력에 두고 그 상관물인 캐시를 필수 입력으로 두면 관계가 거꾸로다. 캐시 유무는 운영자가 카드를 식별하는 표기이므로 남기되 참고 정보로 둔다.

U4-1 토론 스트림(ServerProvision-ue)이 이 전환을 확인했다. U4-1-1 은 OS_INSTALLATION 폼 안에서 묶음 규칙의 RAID 레벨과 RAID 카드 지정을 같은 화면에 두므로, 카드를 고른 순간 그 카드가 못 만드는 레벨이 선택지에서 죽어야 한다 — 근거 ① 의 화면 차단이 실제 계획이다. 단 지원 레벨 집합을 정의서에 얼리지 않는다. 카드 판정은 정의서 작성 시점에 이미 끝나므로(통과하지 못한 조합은 저장되지 않는다) 정의서가 들 것은 카드의 id 와 이름뿐이고, 레벨 집합은 폼이 렌더될 때마다 이 자원에서 다시 읽는다. 운영자가 카드의 지원 레벨을 교정하면 다음 편집부터 그 값으로 재판정되어 교정이 자연히 전파된다.

D3 — 관측이 채울 값 중 pciSubsystemId 하나만 둔다 (브리핑 요구를 일부 뒤집음)

브리핑 §2-1 은 "B 겹 필드는 nullable 이고, 아직 관측하지 않음과 관측했고 값이 이렇다가 구분되어야 하며, 관측 시각 같은 것이 함께 남는 편이 자연스럽다" 고 했다. 채택안은 pciSubsystemId 하나만 nullable 로 두고 관측 시각 · 칩 계열 · 구성 명령 계열을 두지 않는 것이다.

① 지금 만들면 채우는 곳도 읽는 곳도 없는 컬럼이다. '정밀 등록' 은 MVP 이후이고 그때까지 값이 들어올 경로가 없다. CLAUDE.md 의 "미래에 갈라질 수 있으니 미리 분리 금지 — 갈라지는 시점에 분리한다" 가 그대로 적용된다. ② '정밀 등록' 이 실제로 필요로 할 것은 시각 하나가 아니다. 관측 대상 서버가 무엇이었는지, 어떤 방법으로 관측했는지, 사람이 적은 값과 관측값이 어긋났을 때 무엇을 정답으로 볼지가 함께 설계되어야 한다. 지금 시각 컬럼 한 칸을 파 두면 그때의 설계가 그 칸을 물려받는 형태로 제약된다. ③ 브리핑이 요구한 미관측 · 관측 구분은 이미 제공된다 — pciSubsystemId 가 null 인가 아닌가가 그 구분이다.

④ PCI Subsystem ID 는 등록 폼의 선택 입력으로 둔다. 데이터시트에 적혀 있는 값이므로 사람이 넣을 수 있다. 그러면 정밀 등록이 없는 지금도 값을 가질 수 있고, 정밀 등록은 "불가능한 것을 가능하게 하는 기능" 이 아니라 "번거로운 것을 없애는 기능" 으로 위치가 잡힌다. 브리핑 §2 가 "등록이 고통스러워진다" 고 썼지 "불가능하다" 고 쓰지 않은 것과 부합한다.

D2 · D3 이 함께 확정되면 브리핑 §2 의 "두 겹으로 채워지는 특별한 자원" 이라는 틀은 사실상 기각된다 — 지원 레벨이 등록 입력으로 올라오면 관측이 채울 값은 pciSubsystemId 하나뿐이라, 남는 것은 BoardModel 과 같은 부류의 메타데이터 자원에 선택 입력 필드가 하나 있는 형태다. 두 겹 틀은 브리핑의 잠정 가설이었고 이 plan 의 탈락 대안으로 남는다. 같은 귀결로 '정밀 등록' 의 주된 목적은 빈 칸 채우기가 아니라 사람이 적은 값의 대조(검증)가 된다 — 사람이 적는 값은 틀릴 수 있고, 그 위험은 다른 자원과 같은 부류이지만 실물로 확인할 길이 있는 것이 이 자원의 남는 특수성이다.

D4 · D5 · D6 — 타입화

D4 의 탈락안 둘을 적는다. 16비트 값 하나를 감싼 PciId VO 를 두 필드로 두면 반쪽만 채워진 상태가 가능해지고 유일성 표현이 어색해진다. String 두 개는 불가침 "Primitive Obsession 금지" 위반이다. 하나의 VO 로 두면 반쪽 채움이 타입 차원에서 차단되고, 미확인은 임베디드 전체가 null 인 상태로 자연히 표현된다.

D5 에서 기존 management/board/enums/Vendor 를 재사용하지 않는 이유는 그 enum 이 ipxeName 필드와 canonicalizeReportedModel 메서드를 갖기 때문이다. 이 둘은 PXE 부팅 시 iPXE 가 보고한 문자열을 카탈로그 모델명으로 정규화하기 위한 것인데, RAID 카드는 PXE 가 보고하지 않으므로 의미 없는 필드를 상속하게 되고 메인보드 제조사 목록에 AVAGO 를 넣는 도메인 오염이 생긴다. 자유 문자열은 목록 화면의 제조사 그룹핑이 표기 흔들림("AVAGO" · "Avago" · "Broadcom")으로 깨진다. 같은 회사(GIGABYTE)가 두 enum 에 나타나는 것은 중복이 아니다 — 자원 도메인이 다르고 각 enum 에 붙는 책임이 다르다. 불가침의 "분리하려는 추상이 도메인을 가로질러 의미를 잃으면 분리하지 않는다" 를 뒤집어 읽으면 합치면 의미를 잃는 경우는 합치지 않는다가 된다.

D6 의 탈락안도 둘이다. @ElementCollection 조인 테이블은 값이 5~6개로 고정이고 지금 검색 조건으로 쓰이지 않아 조회 조인만 늘어난다. 최대 레벨 하나만 저장하는 안은 RAID 레벨이 순서가 아니라는 사실에서 무너진다 — RAID10 을 지원하면서 RAID6 은 못 만드는 카드가 있다.

D7 — 유일성을 DB 불변식으로

is_deleted = 0 AND is_deprecated = 0 일 때만 vendor 와 model_name 을 조합한 값을 갖고 아니면 NULL 인 PERSISTENT 생성 컬럼에 UNIQUE 를 건다. MariaDB 의 유니크 인덱스가 NULL 중복을 허용하는 성질을 이용하는 것으로, U3-2-a 가 같은 방식으로 "살아 있는 것만 유일, 밀려난 것은 얼마든 공존" 을 만들었다(F5). 조건에 is_enabled 를 넣지 않는 것은 의도다 — 비활성 토글은 일시적으로 꺼 둔 상태이지 자원이 밀려난 상태가 아니므로, 꺼 둔 카드도 이름 점유를 유지해야 같은 이름의 새 카드가 나란히 등록되는 일이 없다. 반면 Deprecated 는 nudge 의 '진행' 경로가 "구버전을 남기고 같은 이름으로 새로 등록" 을 허용해야 하므로 조건에 들어간다.

전역 유니크로 두지 않는 이유는 nudge 의 '진행'(PROCEED) 경로가 "구버전을 Deprecated 로 남기고 같은 이름으로 새로 등록" 을 허용하기 때문이다. 전역 유니크면 그 경로가 DB 제약에 걸려 실패한다. 휴지통에 있는 같은 이름의 자원도 여럿 공존해야 한다. 생성 컬럼 방식은 이 둘을 모두 허용하면서 "지금 쓸 수 있는 카드" 만 유일하게 만든다. F4 가 여기 연결된다 — BoardModel 은 주석이 말하는 제약이 실 DB 에 없어 서비스 레이어 검사 하나에 의존하는데, MA7 은 그 창을 처음부터 DB 불변식으로 막는다. BoardModel 자체의 교정은 이 슬라이스 범위 밖이며 기록만 한다.

D8 · D9 · D10 — 사용성과 경계

D8 — NudgeResourceType 에 RAID_CARD 를 더하고 nudge 확인 컨트롤러와 페이지 스크립트를 붙인다. 없으면 삭제된 카드를 다시 등록하려는 운영자가 "이미 등록된 카드입니다" 만 보고 막힌다 — 휴지통에 있다는 것도, 어떻게 복구하는지도 알 수 없다. MK2 가 nudge 를 만든 이유가 정확히 그 마찰이다.

D9 — 자원 도메인은 최상위 메뉴를 갖는다는 기존 통일성을 따라 nav 에 "RAID 카드" 를 더한다. 메인보드 화면 안에 배치하는 안은 RAID 카드가 보드에 종속되지 않는데도 잘못된 계층을 암시해 탈락했고, nav 그룹핑 도입은 반응형 도입 단계 소관이라 이 슬라이스가 손댈 자리가 아니다. 동작하지 않는 '정밀 등록' 버튼을 disabled 로 미리 두지 않는 이유는 동작하지 않는 버튼이 사용자에게 거짓말이기 때문이다. 대신 상세 화면에서 PCI Subsystem ID 가 비어 있으면 "미확인" 으로 표시하고, 등록 · 수정 폼에서 직접 입력할 수 있게 한다.

D10 — 영구 삭제 시 참조 검사를 넣지 않는다. 지금 이 자원을 참조하는 것이 없을 뿐 아니라, 하드참조의 가능성이 구조적으로 없다. 정의서의 각 단계는 SettingProcess.payload 가 ProcessPayloadConverter 를 거쳐 JSON 문자열 컬럼(payload_json) 하나로 저장되고, RAID 카드 지정이 들어갈 자리는 BoardModelSelectionRequest 와 같은 그 payload 안이다 — JSON 컬럼에는 외래 키를 걸 수 없다. 메인보드 참조가 이미 그렇게 살고 있고 RAID 카드도 같은 자리이므로 소프트참조 외의 선택지가 없다(U3-5-d 의 standard_definition_id 는 별개 컬럼이라 걸 수 있는데도 안 건 경우이고, 여기는 걸고 싶어도 못 거는 경우다). 따라서 참조 가드 자리를 예고할 필요도 없다 — 사라진 카드를 가리키는 정의서를 화면에서 읽히게 만드는 것은 U4-1-1 소관이다.

부산물 · 주의

  • nav 가 12개가 된다. 좁은 화면에서 nav 내용이 문서 폭을 늘려 페이지가 통째로 밀리는 문제(F8)가 소폭 악화된다. 숨기지 않고 여기 적어 둔다 — 해소는 반응형 도입 단계다.
  • board_model 유니크 제약 부재(F4) 는 이 슬라이스가 고치지 않는다. 주석과 실제가 어긋난 상태이므로 별도 단계에서 DDL 과 주석을 함께 맞춰야 한다.
  • FormSubmissionConventionTest 기대값이 하나 늘어난다. 수정 폼만 data-native-submit 마커를 갖고 등록 폼은 JSON XHR 이라 갖지 않는다(F6).
  • CLAUDE.md 개정 항목 없음. 새 인벤토리 계열도, 새 규약도 만들지 않는다 — MA7 은 기존 관리 자원 계열의 다음 번호다(F9).
  • D7 생성 컬럼이 vendor enum 상수명 문자열에 결합된다. RaidCardVendor 의 상수명을 나중에 바꾸면 생성 컬럼 값이 통째로 바뀌므로, Step 9 DDL 작성 시 이 결합을 인지하고 상수명 변경을 스키마 변경으로 취급한다.
  • 코드 주석 여러 곳이 "메타 자원 (OS_IMAGE / BOARD_MODEL)" 로 두 상수를 손으로 나열한다. 로직은 isMetadata() 로 다형화되어 있어 동작 영향은 없으나(F3), RAID 카드가 세 번째가 되면 낡는 주석이므로 Step 8 에서 지나는 김에 갱신한다.
