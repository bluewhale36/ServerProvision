§0. 요약
  • RAID 카드 자원의 PCI Subsystem ID 가 비어 있으면(미확인) 집행의 카드 대조와 게스트 상세의 예고가 모두 "대조 불가" 로 끝납니다(E3.5-5-a 의 UNVERIFIABLE). 이 슬라이스는 게스트가 관측한 값을 카드 화면에 보여 주고, 운영자가 [관측값으로 확정] 을 눌러 채우는 확인형 경로를 만듭니다.
  • 관측은 저장하지 않고 파생합니다 — "이 카드를 지정한 활성 할당의 게스트들" 이 저장해 둔 RAID 인벤토리(guest_server_detail.raid_inventory_json, E3.5-5-a 가 진단 시점부터 채웁니다)에서 감지 카드를 읽습니다. DDL 0 · 엔진 훅 0.
  • 관측이 하나로 모이면 확정 버튼이 열리고, 서로 다르거나 이미 확정값과 다르면 배지가 그 사실을 보이고 버튼을 잠급니다(UI 1차 차단 · 서버 가드 같은 판정 RaidCardObservationStatus).
  • 대조(CARD_MISMATCH)와 예고는 종전대로 확정값만 봅니다. 확정은 pciSubsystemId 채움 한 가지입니다 — RaidCard 는 마커 없는 메타 자원이라 재서명이 없습니다(토론 실태 5 의 정정).
  • 이유: 09-01 실기에서 카드 자원에 Subsystem 이 없어 카드 대조가 전 사이클 생략됐고, 값은 게스트가 이미 보고하고 있었습니다.
§1. 배경 · 진단 (실측 2026-09-03 · dev 167afc0)

출발점

토론 §1 의 공백 ② 입니다 — raid_card 에 PCI Subsystem 이 미등록이면 cardMatches 가 생략되고 WARN 만 남습니다. E3.5-5-a 가 진단 시점 채집 · 예고를 만들었으므로 지금은 게스트 상세가 "카드 자원 {0} 에 Subsystem 이 확정되지 않아 대조할 수 없습니다" 를 띄우고 수정 폼 링크만 줍니다 — 운영자가 값을 손으로 옮겨 적어야 합니다.

실태 (코드 실측 — 번호는 본문에서 인용합니다)

  1. RaidCard 는 메타 자원 — getManifestHash() · getMarkerSignature() 가 null, reissueMarker 는 no-op 입니다(BoardModel 부류).
  2. PciSubsystemId 는 @Embeddable record(vendorId, deviceId) 입니다 — parse() 가 표기 차이를 흡수하고 toDisplay() 가 1458:0011 정규형을 냅니다. 미확인 = 임베디드 전체 null.
  3. 지정 카드의 해석은 RaidConfigurationResolutionProviderImpl.activeRaidRequest 입니다 — SettingAssignmentSnapshotRepository.findByGuestServer_IdAndSupersededAtIsNull 의 RAID 구성 payload(RaidConfigurationRequest.getRaidCardId). 활성 = supersededAt IS NULL(소비된 스냅샷도 재할당 전까지 활성).
  4. 역방향 조회(카드 → 지정한 게스트들)는 없습니다. findBySupersededAtIsNull()(processes fetch join)이 전체 활성 스냅샷을 줍니다.
  5. 게스트의 관측 카드는 GuestServerDetail.raidInventoryJson → RaidInventory.card().pciSubsystemId()(소문자 정규형, DetectedRaidCard) 입니다. 진단 시점(E3.5-5-a) · RAID phase 모두 같은 컬럼에 최신 관측을 씁니다. 관측 시각은 따로 없습니다(detail.updatedAt 은 다른 갱신에도 움직입니다).
  6. 카드 대조 SSOT(Single Source of Truth — 단일 진실 출처) RaidCardMatch.judge 는 target.pciSubsystemId(자원 확정값)만 봅니다 — 관측값을 대조에 쓰지 않는 Q3 결정과 이미 일치합니다.
  7. 카드 화면은 Miller 3열 management/raidcard/list.html 이고, C3 상세 표에 "PCI Subsystem ID" 행(값 또는 n-badge-gray 미확인)이 있습니다. 상태 전이 폼은 BindingResult 없는 POST → 전역 가로채기입니다(new-form.md: 마커 없음). 컨트롤러는 3분할입니다(메타 · lifecycle · nudge).
  8. 게스트 상세 UNVERIFIABLE 배너 링크는 수정 폼(/management/raidcard/{id}/edit)으로 갑니다.
  9. 주 흐름(R13 자동 진단 · 7-b 토론 Q1')은 PXE 등록 → 미할당 상태에서 자동 진단(인벤토리 적재) → 정의서 할당 → 계획 확인 → 개시 입니다. 즉 인벤토리가 적재되는 순간에는 할당이 없습니다.
  10. 관리 → 프로비저닝 방향 의존은 SPI(Service Provider Interface — 소비 측이 선언하고 공급 측이 구현하는 확장점) 역전으로 풉니다. 선례는 RaidConfigurationResolutionProvider(execution 선언 · provisioning 구현) · BiosRegistryCapturePort 이고, provisioning.assignment 가 execution.repository 를 읽는 선례도 다수입니다(AssignmentQueryService 등).
토론 실태 5 의 정정 — "Subsystem 은 마커 manifest(ATTR_PCI)에 포함되므로 갱신은 재서명" 은 오인입니다. ATTR_PCI 는 RaidCardMetadataService 의 nudge payload 속성 키입니다. 따라서 이 슬라이스의 확정은 pciSubsystemId 채움뿐이고 마커 경로는 없습니다.
§2. 요구사항 (확정) · 비목표
  1. 카드 화면(C3)에 관측을 표시합니다 — 값 · 관측한 서버 목록(게스트 상세 링크) · 상태 배지.
  2. [관측값으로 확정] 을 둡니다 — 관측이 하나로 모이고 미확정일 때만 열리며, 확정하면 pciSubsystemId 를 채웁니다.
  3. 관측이 상충하거나 확정값과 다르면 배지로 그 사실을 보이고 버튼을 잠급니다(tooltip 사유).
  4. 서버 가드는 같은 판정을 씁니다 — direct POST 는 409 입니다.
  5. 게스트 상세의 UNVERIFIABLE 링크를 카드 화면(selectId)으로 돌립니다.
  6. 테스트는 단위 · 통합 두 레이어로 씁니다(§9).
  7. CP5 는 브라우저 검증으로 합니다(mock-guest 진단 + 관리 화면).

§3. 설계 대안 비교 — 관측을 어디에 두는가
안저장기록 시점DDL복수 관측
A 관측 3컬럼 (가안)raid_card 최신 1건인벤토리 적재 훅 + 할당 훅3~4 컬럼표현 못 함(플래그 필요)
B 관측 테이블게스트당 1행같은 훅 2테이블 1표현함
C 파생 (채택)없음없음(조회 시 계산)0표현함

A(토론 가안) 탈락 — 실태 9 의 주 흐름에서 인벤토리 적재 시점에는 할당이 없어 적재 훅이 걸리지 않습니다. 할당 시점 훅을 하나 더 두어야 하고, 최신 1건은 상충을 표현하지 못해 충돌 플래그와 해제 규칙이 따라붙으며, 재할당 뒤 옛 관측이 남습니다(stale). 마커 재서명 전제도 실태 1 로 사라졌습니다.

B 탈락 — 훅 문제는 A 와 같고 엔티티 · 리포지토리 · DDL 이 늘어납니다.

C 채택 — "이 카드를 지정한 활성 할당의 게스트" 가 이미 관측을 들고 있으므로(실태 3 · 5) 읽기만 하면 됩니다. 항상 현재 할당과 정합하고, 상충은 distinct 값이 둘 이상이면 그 자체로 드러납니다. 비용은 목록 렌더 시 활성 스냅샷 1 쿼리 + 게스트 detail 1 쿼리 + 인벤토리 JSON 파싱 N(활성 할당 수에 비례, 수십~수백)이며 CP5 에서 로그 타이밍으로 측정합니다. 관측은 재할당(superseded)으로 사라지지만 소비된 스냅샷은 남으므로 프로비저닝 완료 뒤에도 보이고, 게스트 상세의 인벤토리는 그대로입니다.

확정의 범위 — 미확정일 때만(채택) vs 확정값 교체 허용(탈락)

잘못 지정된 게스트의 관측이 올바른 확정값을 덮어쓸 수 있습니다(Q3 의 오염 우려). 확정값이 있으면 화면은 일치 · 불일치 배지만 보이고, 정정은 수정 폼(의도적 행위)으로 한정합니다.

판정 SSOT — 도메인 enum 하나(채택) vs 뷰 · 서비스 각자 판정(탈락)

RaidCardObservationStatus.of(confirmed, observations) 하나를 뷰모델(배지 · 버튼 · tooltip)과 서비스 가드(409)가 함께 호출합니다 — 선례는 childEnableBlockReason() 입니다.

의존 방향 — SPI 역전(채택) vs 관리 서비스가 provisioning 리포지토리 직접 주입(탈락)

management.raidcard 가 인터페이스를 선언하고 provisioning.assignment 가 구현합니다(실태 10 선례). 직접 주입은 management → provisioning 방향 의존을 만들어 계층을 거꾸로 세웁니다.

§4. 도메인 모델 (SSOT)

D1 — SPI RaidCardObservationProvider (management.raidcard.service)

Map<Long, List<RaidCardObservation>> observationsByCard(Set<Long> raidCardIds);

record RaidCardObservation(UUID guestServerId, String guestLabel, String pciSubsystemId)   // management.raidcard.vo

구현은 RaidCardObservationProviderImpl(provisioning.assignment.service)입니다. findBySupersededAtIsNull() 로 활성 스냅샷을 받아 RAID 구성 payload 의 raidCardId 가 대상이면 게스트를 모으고, GuestServerDetailRepository.findAllByServerIdInWithBoardModel 로 상세를 읽어 raidInventoryJson 을 ObjectMapper 로 RaidInventory 관용 파싱합니다(실패 · card null · subsystem null 은 건너뜁니다). 결과는 카드별로 묶습니다. guestLabel 은 GuestServer.name → serialNumber → id 앞 8자 순으로 고릅니다.

D3 — 뷰모델 RaidCardObservationSummaryResponse

  → !status.confirmable()
        ? throw new RaidCardObservationConfirmRejectedException(status.blockReason())   // 409
        : raidCard.confirmObservedPciSubsystemId(PciSubsystemId.parse(agreed))

RaidCardObservationConfirmRejectedException 은 ConflictException 을 상속하므로 advice 등록이 따로 필요 없습니다(new-exception.md 표). 도메인 메서드 confirmObservedPciSubsystemId 는 확정값이 이미 있으면 IllegalRaidCardStateException 을 던지는 안전망입니다.

D5 — 컨트롤러 · 화면

RaidCardMetadataController.list 가 observationByCard(Map<Long, RaidCardObservationSummaryResponse>)를 모델에 더합니다. POST /management/raidcard/{id}/confirm-observed 는 확정 뒤 redirectToListWithSelect(id) 로 돌아옵니다. BindingResult 가 없으므로 폼 마커도 없고, 전역 가로채기가 처리하며 409 는 안내 모달로 뜹니다.

C3 의 "PCI Subsystem ID" 행 아래에 관측 블록을 둡니다 — 상태 문구(#{management.raid-card.observation.<status>}, 인자는 값과 서버 수) · 관측 목록(값별로 "1000:9361 — G1 · G2", 게스트명은 /provisioning/server/{id} 링크) · 버튼(n-btn n-btn-sm n-btn-primary "관측값으로 확정", CONFLICTING 이면 disabled + title=blockReason). 미확인 배지 tooltip 문구는 "수정에서 직접 입력하거나, 이 카드를 지정한 서버가 진단되면 관측값으로 확정합니다." 로 개정합니다.

D6 — 게스트 상세 예고 링크

UNVERIFIABLE 배너 링크를 @{/management/raidcard(selectId=${cc.raidCardId})} "카드 자원에서 확정" 으로 바꿉니다. 문구 execution.raid-card-check.unverifiable 의 끝은 "카드 자원 화면에서 관측값으로 확정하면 대조합니다." 가 됩니다.
