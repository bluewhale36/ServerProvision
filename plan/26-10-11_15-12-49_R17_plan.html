§0. 요약 · 재설계 동기 (v1 → 개정판)
  1. RAID 카드의 제어 계열(MEGARAID · MPT_IR)을 사람이 칩 ID 를 등록해서가 아니라, 진단 리눅스 커널이 그 카드에 붙인 드라이버로 자동 판별합니다. megaraid_sas → MEGARAID · mpt3sas → MPT_IR 후보(IR 펌웨어 확인) · 그 밖(mpi3mr 등) → RAID 미지원.
  2. 근거는 진단 이미지 modloop-lts(커널 6.12.94-lts) 실측입니다. 커널 장치 ID 표 modules.alias 에 1000:10e2(CRA4760) · 1000:005d(9361-8i) → megaraid_sas, 1000:0097(CRA3338) → mpt3sas 가 이미 들어 있습니다. HF22 의 누락은 커널은 알던 칩을 앱의 사본 목록이 몰라서 생겼습니다.
  3. 그래서 코드의 칩 ID 목록(RaidChipFamily.chipPciIds())을 없애고, 계열이 소유하는 것은 드라이버 이름 하나(kernelDriver())로 줄입니다. 칩 표 · 등록 화면 · DDL 은 만들지 않습니다.
  4. 같은 계열의 새 칩은 커널이 알면 아무것도 바꾸지 않아도 붙습니다. 커널이 모르면 칩 표가 있어도 storcli · sas3ircu 가 카드에 닿지 못하므로, 답은 진단 이미지(modloop) 갱신입니다 — 앱 재배포가 아니라 시스템 자산 교체입니다.
  5. 미채집 경고(HF22)는 "왜 못 읽었는가" 를 드라이버 관측으로 가릅니다(지원 계열인데 실패 · RAID 미지원 HBA · 커널이 모르는 칩 · 옛 보고).
v1 은 칩 ID ↔ 계열 대응을 데이터(등록 표 · 화면 · DDL)로 옮기는 안이었습니다. 개정판은 그 대응을 소유하지 않고 커널에 맡깁니다. 폐기 사유는 §8 축 1 에 있습니다.
§1. 배경 · 진단 (실측 2026-10-11)

출발점 — HF22(10-02): CRA4760(SAS3908 1000:10e2)이 RaidChipFamily.MEGARAID.chipPciIds() 에 없어 에이전트가 RAID 보고를 생략했고, 디스크 인벤토리가 통째로 빠졌습니다. 고치는 데 코드 한 줄 · 빌드 · 운영 배포가 필요했습니다.

실태 (번호는 본문 인용용)

  1. 현재 판별 사슬: 서버 RaidChipFamily.agentChipHint() → 응답 raidChips("1000:0097=MPT_IR 1000:005d=MEGARAID 1000:10e2=MEGARAID") → agent detect_raid_family 가 lspci -nn -d 1000: 와 대조 → FAMILY → ensure_raid_driver 가 판별 뒤에 그 계열 모듈만 modprobe. 서버 RaidInventoryParser.familyOf 는 봉투의 lspci 원문에 RaidChipFamily.fromLspci() 를 다시 적용합니다.
  2. 진단 이미지 실측(앵커 샌드박스 자산 sbx-e35/pxe-assets-lab/modloop-lts · squashfs 목록): 커널 6.12.94-0-lts, megaraid_sas.ko · mpt3sas.ko · mpi3mr.ko 모두 있음. modules.alias: pci:v00001000d000010E2… megaraid_sas · …d0000005D… megaraid_sas · …d00000097… mpt3sas.
  3. 실기 원문(~/e35-fieldwork · 2026-08-31): 9361-8i = RAID bus controller [0104] · Kernel driver in use: megaraid_sas / CRA3338 = Serial Attached SCSI controller [0107] · mpt3sas. 참고(앵커 기록): Fujitsu D2616 1000:0079 = [0104] · megaraid_sas.
  4. 두 드라이버(+ mpi3mr)는 각자의 PCI ID 표로만 바인딩하므로 함께 로드해도 충돌하지 않습니다(앵커 회신 C · 일반 배포판 커널 동작).
  5. BMC: Gigabyte AMI 의 Chassis/Self/PCIeDevices → PCIeFunctions 가 있으나, 표준 PCIeFunction 에는 드라이버 정보가 없습니다(드라이버는 호스트 OS 개념). 얻을 수 있는 것은 ID · ClassCode = lspci -nn 수준입니다. E3.5-0 실측에서 Storage Members 는 두 BMC 모두 0 이었습니다.
  6. lspci 옵션(Alpine pciutils 3.12 실행 · 실기 원문 대조): -nn = 칩 ID 만 · Subsystem 은 -v/-vv/-vmm/-mm 에서만. RAID 봉투는 이미 -nn -vv -d 1000: 이라 채집되는 카드의 Subsystem 은 지금도 들어옵니다.
  7. COLLECT 에서 지원 칩이 없으면 agent 가 RAID 봉투를 버립니다(RAID_ENV=… || RAID_ENV="") → 서버는 "왜 못 읽었는지" 를 모릅니다. HF22 경고 uncollectedRaidCards() 는 원인 무관(PCIe kind RAID + 인벤토리 없음)입니다.
미확인 · 실측 대기
  1. CRA4760 실물이 실제로 megaraid_sas 에 바인딩되는가 — alias 표는 그렇다고 말하지만 실기 원문이 없습니다. 운영 spv-01 진단 보고 원문 조회는 사용자 지시로 보류 중입니다.
  2. 운영 modloop 이 위 샌드박스 자산과 같은 커널 판인가.
  3. IT 펌웨어 SAS3008(HBA)에서 sas3ircu 가 어떻게 응답하는가(IR 여부 판정 문구).
  4. BMC PCIeFunction 필드의 실제 채움 여부(비목표라 판정에 영향 없음).
§2. 요구사항 (확정) + 비목표
  1. RaidChipFamily 에서 chipPciIds() · agentChipHint() · fromLspci() 제거, kernelDriver() 추가(MEGARAID = megaraid_sas · MPT_IR = mpt3sas).
  2. 서버 힌트를 raidDrivers("<driver>=<FAMILY>" 공백 연결 — §4 D1)로 교체합니다.
  3. agent: RAID 클래스 장치(0104 · 0107)마다 그 장치의 modalias 로 modprobe(커널 alias 표가 고르는 드라이버 — mpi3mr 포함) → /sys/bus/pci/devices/*/driver 로 계열 판정 → 봉투에 driver · slot 을 싣습니다. COLLECT 에서도 판정 실패 사유를 버리지 않고 보고합니다.
  4. agent 진단 보고에 raidDevices(RAID 후보 장치별 슬롯 · 드라이버 — 드라이버 없음 포함)를 추가합니다.
  5. 서버 파서: 봉투의 driver 로 계열을 정하고, 없으면 tool 로 폴백합니다(옛 봉투 관용).
  6. 미채집 경고 4 갈래(§4 D4).
  7. 테스트 두 레이어(§6).
  8. CP5: mock-guest 하네스 + 게스트 상세 화면(§9).
비 목표 :
  • 칩 등록 표 · 화면 · DDL(v1 안 — 폐기).
  • BMC 를 판별 근거로 쓰기(실태 5).
  • 진단 PCIe 목록의 Subsystem 수집(-mm -nn 전환) — 2026-10-11 사용자 확정 — 비목표(§8 Q1).
  • 새 계열 추가 — 지금처럼 코드 변경으로 합니다.
  • 한 서버에 RAID 카드 둘 이상 — 지금처럼 첫 판정 카드 하나만 다룹니다.
  • R17-1(RAID10 스팬 · 수량 · 폼 최소치) · R17-2(typicallyRequiresCache 제거) — 각자 별도 CP1.

§4. 도메인 모델 (SSOT)

D1 RaidChipFamily

구분멤버값 · 규칙
제거chipPciIds() · agentChipHint() · fromLspci()-
추가String kernelDriver()MEGARAID = "megaraid_sas" · MPT_IR = "mpt3sas"
추가static Optional<RaidChipFamily> fromKernelDriver(String)드라이버 이름 → 계열
추가static String agentDriverHint()선언 순서 "<driver>=<FAMILY>" 공백 연결
유지나머지 멤버불변

D2 agent.sh

  • detect_raid_family: PCI 클래스 0104 · 0107 장치마다 modprobe "$(cat /sys/bus/pci/devices/<장치>/modalias)"(관용 — 커널 alias 표가 고르는 드라이버를 그대로 로드하므로 계열 밖 mpi3mr 도 붙는다) → 보강으로 힌트 raidDrivers 의 모듈도 로드 → mdev -s → …/driver 의 basename 이 힌트의 드라이버와 같은 첫 장치 → FAMILY · SLOT · DRIVER. RAID 클래스 장치가 없으면 봉투를 생략(종전 관용 — 카드 없는 서버). 장치는 있는데 계열 드라이버가 아니면 reason NO_RAID_DRIVER. 미확인 · 실측 대기 BusyBox modprobe 가 modalias 문자열을 modules.alias 로 풀어 로드하는지.
  • ensure_raid_driver 는 이 앞단으로 흡수합니다(판별 뒤 로드 → 판별 전 로드).
  • MPT_IR 은 sas3ircu LIST 로 IR 을 확인하고, 아니면 reason NOT_IR 입니다. 미확인 · 실측 대기 IT 펌웨어 응답 문구.
  • 봉투에 "driver" · "slot" 을 추가합니다.
  • collect_raid_devices: PCI 클래스 0104 · 0107 장치마다 slot · driver(없으면 빈 값) → 보고의 raidDevices.
  • COLLECT 에서 판정 실패 사유 봉투도 버리지 않고 싣습니다(서버가 원장 filtered 에 흡수 — 종전 경로).

D3 서버 수신

  • AgentReportService.raidChipsFor → raidDriversFor(응답 필드 raidDrivers).
  • RaidInventoryParser.familyOf: 봉투 driver → fromKernelDriver, 없으면 tool(storcli* → MEGARAID · sas3ircu → MPT_IR) 폴백.
  • DiagnosticReportParser: raidDevices → HardwareSpec.raidDevices(List<RaidDeviceBinding(slot, driver)> · null 관용).

D4 미채집 경고 판정 SSOT RaidCollectionNotice

위치 execution.vo · method-per-constant · 상수가 문구 키를 소유합니다. 판정 대상은 PCIe kind RAID 장치가 있고 RAID 인벤토리가 없을 때이며, 장치의 raidDevices 바인딩으로 가릅니다.

조건상수문구
raidDevices 없음 (옛 보고 · 옛 agent)UNKNOWN종전 HF22 문구 그대로 (execution.raid-inventory.uncollected)
계열 드라이버 (megaraid_sas · mpt3sas)SUPPORTED_NOT_COLLECTED지원하는 RAID 카드이지만 디스크 정보를 채집하지 못했습니다 — 채집 도구가 없거나 RAID 펌웨어가 아닙니다. 서버 이력의 사유를 확인한 뒤 다시 PXE 부팅하십시오.
드라이버 있음 · 계열 밖 (mpi3mr 등)UNSUPPORTED_CONTROLLERRAID 를 지원하지 않는 컨트롤러({driver})입니다 — 디스크는 OS 가시 장치로만 보입니다.
드라이버 없음DRIVER_NOT_BOUND진단 이미지 커널이 이 RAID 칩을 인식하지 못했습니다 — 진단 이미지(modloop)를 갱신해야 채집할 수 있습니다.

GuestServerDetailResponse.uncollectedRaidCards() 는 카드별 (PcieDevice, RaidCollectionNotice) 목록으로 대체합니다. 판정은 조회 서비스가 채워 넘깁니다 — 레코드가 판정 로직을 품지 않게 하고, 문구 키는 상수가 소유합니다.

화면 반영

§8. 설계 결정 (대안 비교) · 리스크 · 열린 질문

축 1 — 판별의 SSOT(Single Source of Truth) (핵심 · v1 개정)

  • v1 폐기: 칩 표는 커널이 이미 가진 "칩 → 드라이버" 지식의 손 사본입니다. HF22 는 그 사본이 낡아서 생겼고, 표를 데이터로 옮겨도 사본이라는 성질은 그대로입니다. 게다가 커널이 모르는 칩은 표에 등록해도 storcli · sas3ircu 가 장치에 닿지 못해 쓸모가 없습니다(드라이버가 먼저입니다).
  • B 탈락: 클래스는 계열의 상관물입니다. IT 펌웨어 HBA 도 0107 이고, MegaRAID 의 eHBA 개성도 있을 수 있습니다. R17-2 의 캐시 플래그가 상관물을 판정에 쓴 실패와 같은 함정입니다.
  • C 탈락: BMC 는 드라이버를 모르고(실태 5) 제조사마다 데이터 품질이 고르지 않습니다. 진단 리눅스는 모든 서버가 거치므로 진단 전에 아는 이점도 작습니다(앵커 회신 B).
  • A 채택: 판별의 원천이 실제로 카드를 다루는 주체(커널 드라이버)라서 상관물이 아니라 원인입니다.

축 2 — 판정 주체

채택: agent 가 판정하고 결과(driver · family 또는 사유)를 보고합니다. 드라이버 바인딩은 게스트 안에서만 관측됩니다. 서버는 계열 ↔ 드라이버 대응(kernelDriver())을 힌트로 내려 주는 것만 소유합니다 — 스크립트에 계열 이름 · 모듈 이름을 박지 않는 현 원칙(서버가 SSOT)을 유지합니다. 탈락: 서버가 lspci -k 원문을 받아 판정(봉투가 커지고 sysfs 가 더 직접적).

축 3 — MPT 의 IR / IT 구분

mpt3sas 는 IR(RAID 가능)과 IT(HBA)를 모두 다룹니다. 채택: sas3ircu 로 컨트롤러가 IR 로 잡히는지 확인 — 잡히지 않으면 reason NOT_IR. 미확인 · 실측 대기 IT 펌웨어에서의 sas3ircu 출력 문구. 탈락: 펌웨어 버전 문자열 추측.

축 4 — 미채집 사유를 서버에 남기는 자리

채택: 진단 보고 JSON 에 raidDevices 배열 추가 → HardwareSpec 에 저장. 예: [{"slot":"ae:00.0","driver":"megaraid_sas"}, {"slot":"c6:00.0","driver":""}]. JSON 컬럼 안이라 DDL 이 없고, 옛 보고는 필드 없음(null)으로 관용합니다. 탈락: 새 컬럼(DDL · 실 DB 적용 부담) · 원장 filtered 문자열을 화면이 파싱(취약 — 5-a F-2 의 교훈).

축 5 — 배포 이행

옛 agent 는 raidChips 만 압니다. 새 서버가 raidDrivers 만 보내면 옛 agent 는 RAID 를 생략합니다(카드 없는 것처럼 정상 보고 — 종전 관용과 같은 결). 채택: 배포 = jar 교체 + 시스템 자산 화면에서 AGENT 교체를 함께, RAID 단계 진행 중 게스트가 없을 때 합니다(RAID_APPLY 중 옛 agent 는 TOOL_MISSING 실패). 탈락: 한 릴리스 동안 raidChips 병행 송신(칩 목록을 다시 코드에 남기게 되어 이 단계의 목적과 정면 충돌).
