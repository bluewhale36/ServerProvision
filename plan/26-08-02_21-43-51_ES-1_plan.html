§0. ES-1 이 무엇인가 · 단일 슬라이스 판단 · 교차 의존 0

ES-1 = 엔진이 활성 할당의 ownedPhases 를 실제 소비해 phase 커서를 전진시키는 배선. U3-1 이 만든 공급자(OwnedPhasesProvider)와 조합 함수(PhaseSequence.nextAfter)는 이미 존재하고, 엔진의 판정 호출부가 Set.of()(빈 집합) 로 눌려 있어 "진단만 완주하면 무조건 종단" 에 머문다. ES-1 은 그 Set.of() 자리에 실 공급자를 흘려 넣고, 소유 phase 가 있으면 커서를 전진시킨다.

분할 : 없음 (단일 슬라이스)

ES-1 은 새 알고리즘을 만들지 않고 기존 seam 3개(OwnedPhasesProvider · PhaseSequence.nextAfter · ProvisioningProgress.advanceTo) 를 연결한다. 각 후속 phase 의 실행기(FirmwareUpdatingExecutor 등)는 ES-n · E2 소관으로 ES-1 범위 밖이다 — 그래서 ES-1 후 게스트는 다음 phase 에서 명시적 HOLD 에 머문다(정상). 규모가 작고 응집돼 분할이 불요하다.

교차 의존 0 — ES-1 은 execution.engine 내부에서 이미 존재하는 OwnedPhasesProvider 빈(구현은 provisioning.assignment, 인터페이스는 execution.engine 소유 = dependency inversion(의존성 역전 — 상위 계층이 인터페이스를 소유하고 하위 계층이 구현을 끼운다))을 주입할 뿐이다. 새 도메인 의존을 만들지 않는다.
§1. 현재 상태 (배선 전 · 조사로 확정)

쉬운 말 요약

서버가 PXE 로 부팅되면 먼저 진단 리눅스가 올라와 하드웨어 정보를 수집한다. 지금은 이 진단이 끝나면 그 서버가 무엇을 더 해야 하는지와 상관없이 무조건 "끝(종단)" 으로 처리한다. 실제로는 서버마다 "펌웨어를 갱신해라", "OS 를 설치해라" 같은 할 일 목록(ownedPhases) 이 U3-1 에서 정의서로 할당돼 있는데, 엔진이 그 목록을 아직 안 읽고 있어서다(코드에 Set.of() 라는 빈 목록이 하드코딩돼 있다).

이번 슬라이스는 엔진이 그 실제 할 일 목록을 읽어 진단 다음에 할 일이 남았으면 커서를 그 phase 로 전진시키고(예: 펌웨어 갱신), 남은 일이 없으면 지금처럼 종단 시킨다. 전진한 서버는 진단 리눅스를 떠나 재부팅한 뒤 다음 단계 스크립트를 받으러 다시 폴링한다. 다만 그 다음 단계의 실제 실행기(예: 펌웨어 갱신기)는 아직 안 만들어져(ES-n · E2 몫) 서버는 그 단계에서 명시적 대기(HOLD) 에 멈춘다 — 이것이 ES-1 의 정상 종착점이다.

phase 순서 (ProvisioningPhase ordinal · 전진 기준축)

BOOTSTRAPPING(0) → DIAGNOSE_LINUX(1) → FIRMWARE_UPDATING(2) → FIRMWARE_SETTING(3) → OS_INSTALLING(4) → OS_SETTING(5) → TESTING(6)

U3-1 이 심어둔 seam · 현재 배선 상태

대상현황
PhaseSequence.nextAfter(current, ownedPhases)조합 함수는 이미 있다. current 가 BOOTSTRAPPING 이면 ownedPhases 무관하게 무조건 DIAGNOSE_LINUX; 그 외엔 current.ordinal()+1 부터 선언 순 스캔해 ownedPhases 에 속하는 첫 phase 반환(TESTING 만나면 중단), 없으면 empty(= 종단).
ProvisioningProgress.currentPhase (커서 SSOT)전진은 advanceTo(next, now)(전진 전용 · 역행 금지 · 실패 / 종단 / 미개시 가드), 종단은 markCompleted(now). markCompleted 는 currentPhase 를 바꾸지 않고 completedAt 만 찍는다.
현재 유일한 실전진AgentReportService.checkin 의 BOOTSTRAPPING → DIAGNOSE_LINUX 최초 1회. 이후 전진은 미배선.
OwnedPhasesProvider (execution.engine SPI(Service Provider Interface — 도메인이 구현해 끼우는 확장점))Set<ProvisioningPhase> ownedPhasesOf(UUID guestId)(무할당 = 빈 Set) + OwnedPhasesProviderImpl(@Component, 활성 스냅샷 supersededAt IS NULL 의 동결 ownedPhases 반환). 공급 측 준비 완료 · 미주입 — 어떤 엔진 클래스도 아직 이 provider 를 주입 / 호출하지 않는다.
OwnedPhases VO 의 NON_ASSIGNABLEBOOTSTRAPPING · DIAGNOSE_LINUX · TESTING 을 소유 불가로 거절. 따라서 ownedPhases ⊆ {FIRMWARE_UPDATING, FIRMWARE_SETTING, OS_INSTALLING, OS_SETTING}. 진단은 항상 선행하는 무조건 phase.
Executor SPI + registryProvisioningPhaseExecutor(phase() / bootScript() / default onStepClosed()) 를 PhaseExecutorRegistry 가 phase() 키로 수집. 현재 구현은 DiagnoseLinuxExecutor 1개뿐. 미등록 phase 는 dispatch 가 IpxeScripts.hold(target)(명시 HOLD, silent 아님) 반환.
핵심 배선점 (진단 완주 판정) — DiagnoseLinuxExecutor.onStepClosed(약 119행): 
if (PhaseSequence.nextAfter(DIAGNOSE_LINUX, Set.of()).isEmpty()) progress.markCompleted(now);
Set.of() 가 비어 있어 nextAfter 는 항상 empty → 항상 markCompleted(즉시 종단). 전진(else) 분기 자체가 없다. (주석 "보유 phase 실공급자는 U3, 배선은 ES-1".)
부수 결함 (directiveFor) — AgentReportService.directiveFor 는 지금 ① isCompleted() → REBOOT ② 커서 진단 + 미수집 → COLLECT ③ 그 외 → WAIT 로 판정한다. 커서를 진단 이후로 전진시키면 isCompleted 는 false 이고 커서가 진단이 아니라 directiveFor 가 WAIT 로 떨어진다 → 게스트가 진단 리눅스를 안 떠나 다음 phase 스크립트를 못 받는다. ES-1 이 전진을 켜면 이 결함이 드러나므로 DES-2 로 함께 고친다.

무해 지점 — BootScriptDispatcher.bootTargetPhase(약 62행)의 nextAfter(BOOTSTRAPPING, Set.of()). BOOTSTRAPPING 분기는 ownedPhases 를 아예 안 보므로(무조건 DIAGNOSE_LINUX) 이 Set.of() 는 결과 불변 — 형식적 자리표시자다(DES-3 에서 주석 명확화).

§2. 요구사항 (확정) + 비목표
  1. 진단 완주 판정 실배선 — DiagnoseLinuxExecutor.onStepClosed 의 진단 완주 판정을 실 ownedPhases 로 배선한다. 소유 다음 phase 가 있으면 advanceTo(next), 없으면 markCompleted(현 동작 보존).
  2. 전진 판정을 재사용 가능한 협력자로 추출 — 모든 후속 executor 가 공유할 커서 전진 SSOT(Single Source of Truth, 단일 진실 출처). 신규 PhaseCursorAdvancer(DES-1).
  3. directiveFor 보강 — "진단 이후로 전진 시 REBOOT" 를 추가해, 전진한 게스트가 진단 리눅스를 떠나 /boot 재폴링으로 다음 phase 스크립트(또는 HOLD) 를 받게 한다(DES-2).
  4. (일관성) 자리표시자 정리 — BootScriptDispatcher 의 무해한 Set.of() 자리표시자를 주석으로 명확화한다(동작 변경 0 · DES-3).
비 목표 (다음 슬라이스로) :
  • 후속 phase 실행기(FirmwareUpdatingExecutor 등) 구현 = ES-n · E2. ES-1 후 게스트는 첫 소유 phase 에서 명시 HOLD 에 머문다(정상 · 실증 대상).
  • 진행 중 게스트 재할당의 커서 리셋 = E cluster(U3-2-a 에서 이미 차단).
  • 실패 · 재시도 · 회수 흐름은 기존 유지(변경 0).

§4. 도메인 모델 · 배선 (SSOT) · 상태 흐름
Primitive Obsession 없음 — ES-1 은 원시 필드를 새로 만들지 않는다. phase 는 ProvisioningPhase enum, 커서는 ProvisioningProgress.currentPhase(enum), 소유 집합은 Set<ProvisioningPhase> / OwnedPhases VO 다. 신규 협력자 PhaseCursorAdvancer 는 이 타입들만 다루며 int / String 커서를 도입하지 않는다.

핵심 배선점 before / after (DiagnoseLinuxExecutor.onStepClosed 완주 판정)

BEFORE — 항상 종단

// Set.of() 가 비어 nextAfter 는 항상 empty
if (PhaseSequence.nextAfter(
      ProvisioningPhase.DIAGNOSE_LINUX,
      Set.of()).isEmpty()) {
    progress.markCompleted(now);
}
// 전진(else) 분기 자체가 없음

AFTER — ownedPhases 기반 전진 / 종단

// 협력자에 위임 (DES-1)

    progress, server.getId(), now);
// present → advanceTo(next)
// empty   → markCompleted(now)

신규 협력자 PhaseCursorAdvancer (커서 전진 SSOT · DES-1)

// execution/engine/PhaseCursorAdvancer.java  (@Component · OwnedPhasesProvider 주입은 여기 1곳)
public void advanceOrComplete(ProvisioningProgress progress, UUID guestId, LocalDateTime now) {
    Set<ProvisioningPhase> owned = ownedPhasesProvider.ownedPhasesOf(guestId);
    PhaseSequence.nextAfter(progress.getCurrentPhase(), owned)
        .ifPresentOrElse(next -> progress.advanceTo(next, now),   // 소유 phase 있음 → 전진
                         ()   -> progress.markCompleted(now));    // 없음 → 종단(현 동작 보존)
}

directiveFor 보강 (DES-2) — REBOOT 조건 확장 (분기 추가 아님)

// AgentReportService.directiveFor  (약 152행)
// 게스트가 진단 리눅스를 떠나야 하는 조건 = 종단 OR 커서가 진단 이후로 전진
return progress.isCompleted()
    || progress.getCurrentPhase().ordinal() > ProvisioningPhase.DIAGNOSE_LINUX.ordinal()   // ← 추가
    ? Directive.REBOOT
    : (cursor == DIAGNOSE_LINUX && !enriched ? Directive.COLLECT : Directive.WAIT);

ordinal 비교라 BOOTSTRAPPING(0) 오검출 없음. PhaseSequence 의 ordinal 축과 정합. 이는 기존 REBOOT 분기의 조건 확장(같은 책임에 흡수) 이지 새 분기 줄 추가가 아니다.

§8. 설계 결정 (DES-1~DES-4) · 잔여 · 열린 질문

확정 결정 — 채택안 + 비채택 대안 + 탈락 사유 (불가침)

#결정 (채택)비채택 대안 · 탈락 사유
DES-1 치명 커서 전진 판정을 협력자로 추출(inline 아님). 신규 execution/engine/PhaseCursorAdvancer.java(@Component) 의 advanceOrComplete(progress, guestId, now) 가 OwnedPhasesProvider 로 ownedPhases 를 읽고 nextAfter 로 판정해 present → advanceTo(next), empty → markCompleted. OwnedPhasesProvider 주입은 여기 1곳. DiagnoseLinuxExecutor 는 이 협력자를 주입해 호출한다. 왜 — "진단 완주 → 소유 다음 phase 로 전진 / 없으면 종단" 은 진단 전용이 아니라 모든 phase 완료가 공유하는 커서 전진 규칙(SSOT) 이다. ES-n 은 executor 를 계속 추가하며 각자 같은 전진 판정을 필요로 하므로, 협력자 1곳에 두면 종단 / 전진 규칙이 단일 SSOT 가 되고 단위 테스트도 격리된다. ① DiagnoseLinuxExecutor 에 인라인 — 지금은 executor 1개라 단순하나, ES-n 이 executor 를 추가하는 순간 전진 규칙이 복제돼 drift(불가침 중복 금지 위반). "갈라지는 시점에 분리" 관점에서도 전진 규칙은 이미 공유가 확정된 규칙이라 지금 분리가 정당(speculative 아님). ② ProvisioningPhaseExecutor 의 default 메서드 — default 메서드는 OwnedPhasesProvider 를 주입 못 받아(인터페이스 정적 문맥) 협력자를 또 넘겨야 함 → 협력자 빈이 결국 필요. 협력자 직접 호출이 단순.
DES-2 치명 directiveFor 에 "진단 이후 전진 → REBOOT" 추가. 게스트가 진단 리눅스를 떠나 재폴링해야 하는 조건 = 진단 작업이 이 게스트에게 끝남 = 종단(isCompleted) 또는 커서가 진단 이후로 전진. 판정 보강 = progress.isCompleted() || progress.getCurrentPhase().ordinal() > DIAGNOSE_LINUX.ordinal() → REBOOT. 전진 후 REBOOT → 게스트 /boot 재폴링 → bootTargetPhase = 현재 커서(FIRMWARE_UPDATING 등) → registry.find → executor 미구현이면 IpxeScripts.hold(명시 HOLD). 즉 게스트가 다음 phase 에서 정상 대기. executor 가 별도 플래그 / 상태를 세워 directiveFor 를 우회하는 방식 — directiveFor 는 지시 판정 단일 지점(E1-2 규약) 이라 그 SSOT 안에서 조건을 보강하는 것이 옳다. 우회는 판정을 분산시켜 drift 원인. 미채택.
DES-3 주의 BootScriptDispatcher 의 Set.of() 자리표시자 정리. bootTargetPhase 의 nextAfter(BOOTSTRAPPING, Set.of()) 는 결과 불변(BOOTSTRAPPING 은 ownedPhases 무관). ES-1 이 다른 Set.of() 를 실배선하면서 이 잔존 Set.of() 만 남으면 "미배선처럼" 오해될 수 있다. 권장 = 이 자리를 유지하되 "BOOTSTRAPPING → 진단은 보유 무관(의도적 빈 집합, 배선 대상 아님)" 주석을 명확화(또는 nextAfter 의 BOOTSTRAPPING 전용 헬퍼로 표현). 동작 변경 0. 여기에도 provider 를 주입해 실 ownedPhases 를 넘기는 것 — 결과가 같은데 불필요한 의존만 늘림(over-wiring). 미채택.
DES-4 중대 소유 다음 phase 에 executor 가 없으면 HOLD(전진은 함). ES-1 은 커서를 소유 첫 phase(예: FIRMWARE_UPDATING) 로 전진시키지만 그 executor 는 미구현(ES-n) 이다. 게스트는 재폴링 시 dispatch 의 명시 HOLD 스크립트를 받아 그 phase 에서 대기한다. 이것이 ES-1 의 정상 종착(전진 실증 + 안전 대기). executor 있는 phase 까지 건너뛰며 전진 — phase 순서 의미(FIRMWARE_UPDATING 소유 게스트는 펌웨어에서 대기해야 함)를 깨고 소유하지 않은 phase 로 점프. 절대 안 됨. 소유 첫 phase 에서 HOLD 가 정확.
