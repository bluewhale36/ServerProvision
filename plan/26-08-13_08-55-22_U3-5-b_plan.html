§0. 이 단계가 어떻게 생겼는가

U3-5-a 의 CP6 report 를 제출한 직후 사용자가 요구를 냈다 — "정의서를 할당할 때 이름만 나열하지 말고 내용을 같이 볼 수 있으면 좋겠다."

이 요구를 U3-5-a 에 얹을지 별도 슬라이스로 뺄지를 두고 판단이 갈렸는데, 얹으면 CP5 를 통째로 다시 해야 한다는 점이 결정적이었다. U3-5-a 의 샌드박스 검증에서 A5 · A6 · C1 · C3 은 전부 <select> 의 disabled 옵션과 그 라벨을 대상으로 확인한 항목이다. 고르는 UI 자체가 바뀌면 그 넷은 무엇을 확인한 기록인지 성립하지 않게 되므로 재실시가 불가피하다. 반대로 분리하면 판정 로직은 이미 굳어 있으므로 이 단계의 CP5 는 화면만 보면 된다. 2026-08-13 사용자 판단으로 분리했다.

순서도 함께 뒤집었다 — 그룹 단위 일괄 할당(구 U3-5-b)을 U3-5-c 로 밀고 이 단계를 앞에 놓았다. 그쪽도 정의서를 고르는 화면을 갖기 때문이다. 순서를 그대로 두면 일괄 할당을 <select> 로 한 번 만들고 곧 갈아끼우게 되는데, 그것이 방금 U3-5-a 에서 겪은 것과 같은 형태의 낭비다.
§1. 현재 상태 (실측)

지금 어떻게 고르나

서버 상세 화면의 할당과 재할당은 <select> 하나로 처리한다. fragments/provisioning/definition-options.html 이 <option> 을 그리고, U3-5-a 가 거기에 잠금과 차단 사유를 얹었다. 실제로 그려지는 형태는 이렇다.

<option value="2" disabled title="…">bios-ms03 — 이 정의서는 메인보드 MS03-CE0 전용입니다 — 이 서버는 ASUS-Z13PE 입니다.</option>
두 가지가 아쉽다.
  • 정의서가 무엇을 하는지는 이름으로만 짐작한다. bios-ms03 이 어떤 단계를 밟고 어떤 값을 넣는지 보려면 할당 화면을 떠나 정의서 상세로 나갔다가 돌아와야 한다.
  • 차단 사유가 <option> 라벨에 눌려 붙어 있다. 네이티브 select 는 옵션 안에 서식을 줄 수 없으므로 사유가 이름과 한 줄로 이어지고, 길면 잘린다.

.n-miller-item-disabled 가 이미 있다는 것이 중요하다. 사용자 요구의 "비활성화 처리처럼 보이게 만들되" 가 정확히 그 클래스이고, 클릭 가능 여부는 그 클래스가 정하지 않으므로 "클릭해서 왜 비활성인지 볼 수 있게" 도 같은 자산 위에서 그대로 성립한다. 새 CSS 를 만들 이유가 없다.

정리하면 이 단계에서 새로 만드는 CSS 는 없고, 새 조회도 없다. 모달 골격은 U3-4 의 서버 넣기 모달이 쓰는 방식(cm-card-wide + 조각 fetch)을 따르고, 2 열 miller 는 miller.css 를 그대로 쓰며, 무엇이 막히는지는 U3-5-a 가, 정의서가 무슨 내용인지는 SettingQueryService.findDetail 이 이미 답한다. 남는 일은 그 넷을 한 화면에 나란히 놓는 것이다.

조각화의 실측 경계

어떤 절을 조각으로 뗄 수 있는지는 그 절이 페이지 밖의 무엇에 기대고 있는지에 달렸다. 그래서 참조하는 모델 속성을 먼저 셌다.

templates/provisioning/setting-detail.html 의 '프로비저닝 단계' 절은 132~393 행이고 th:fragment 가 하나도 없다. 안쪽 구조는 이렇다.

<div class="n-detail-section">        ← 132
  <div class="n-section-title">프로비저닝 단계</div>
  <div th:if="empty">단계 없음</div>
  <div class="n-card n-process-card" th:each="process : ${setting.processList}">   ← 145~392
      BASIC_UPDATE / BASIC_SETTING / OS_INSTALLATION / OS_SETTING 다형 렌더
  </div>
</div>

이 절이 참조하는 모델 속성은 setting 하나뿐이다 — SettingController.detail 이 넣는 유일한 속성이다. 카드가 실제로 쓰는 것은 setting.processList · setting.deprecatedUsages · setting.executionWarnings · setting.references 넷이고, 넷 모두 그 하나 안에 들어 있다. 조각으로 떼어낼 때 파라미터가 하나로 끝난다는 뜻이며, 이것이 §8 DEC-A 의 근거가 된다.

§2. 요구사항 (확정) + 비목표
  • R1 — [정의서 할당] 을 누르면 큰 모달이 열린다.
  • R2 — 모달은 2 열 miller 다. 좌측이 정의서 목록, 우측이 고른 정의서의 상세다.
  • R3 — 선택은 하나뿐이므로 고르면 우하단 [할당] 버튼이 활성화된다.
  • R4 — 할당할 수 없는 정의서는 비활성처럼 보이되 클릭은 되고, 클릭하면 우측에서 왜 안 되는지를 읽을 수 있다.
  • R5 — 재할당도 같은 모달을 쓴다. 제목과 제출 대상만 다르다.
  • R6 — 우측 상세는 정의서 상세 화면과 한 벌을 공유한다(조각화).
비 목표 :
  • 할당 가능성 판정 규칙 — U3-5-a 확정분을 그대로 호출한다. 이 단계는 판정을 만들지 않는다.
  • 그룹 단위 일괄 할당 — U3-5-c.
  • 정의서 작성 · 수정 화면(U2)의 편집 경험 — 건드리지 않는다. 이 단계가 U2 화면을 손대는 것은 조각화까지이며 렌더 결과는 같아야 한다.
  • 정의서 목록 화면(setting-list)의 UI — 무관하다.

여섯 요구 중 U2 화면을 건드리는 것은 R6 하나이고, 그것도 조각으로 떼어내는 데까지다. 나머지 다섯은 서버 상세와 그 위에 뜨는 모달 안에서 끝난다.

🎬 미리보기 — 모달 안에서 고르기

아래 툴바로 서버의 하드웨어를 바꾸면 좌측 목록에서 어느 정의서가 잠기는지가 뒤바뀐다. 잠긴 항목도 눌린다 — 누르면 우측 패널에 사유와 내용이 함께 뜬다. 데모의 판정 함수는 U3-5-a 가 확정한 서버 판정과 같은 바디다(드리프트 0).

  • 툴바 — 이 서버가 실제로 가진 메인보드를 MS03-CE0 · ASUS-Z13PE · 수집 전 셋으로 바꾼다.
  • 좌측 — 정의서 세 건을 흉내낸 목록이다. os-only-auto(보드 AUTO) · bios-ms03(MS03-CE0 전용) · fw-asus-z13(ASUS-Z13PE 전용). 통과면 선택 가능, 차단이면 잠김 이 붙고 행이 흐려지되 고르기 버튼은 그대로 눌린다.
  • 우측 — 고른 정의서의 요약을 보여준다. 차단된 것을 골랐으면 사유가 위에 붙고 그 아래 내용은 그대로 보인다.
  • [할당] — 아무것도 고르지 않았거나 차단된 것을 골랐으면 disabled 이고, 마우스를 올리면 이유가 tooltip 으로 뜬다.
서버 하드웨어 :

판정 JS (서버와 1:1)

function demoBlockReason(def, board) {
    if (def.board === null || board === null) return null;   // 보드 AUTO 이거나 수집 전이면 막지 않는다
    return def.board === board ? null
        : '이 정의서는 메인보드 ' + def.board + ' 전용입니다 — 이 서버는 ' + board + ' 입니다.';
}

U3-5-a 의 RequiredBoardModel.blockReasonFor 와 같은 식이다. 회수된 서버는 이 모달이 아예 열리지 않으므로(할당 폼 자체가 닫힌다) 데모에서 다루지 않는다 — 그 판단의 근거는 §8 DEC-D 에 있다.

체험시키고 싶은 것

서버 하드웨어를 바꾸면 어느 정의서가 잠기는지가 뒤바뀐다. 그리고 잠긴 것을 눌러도 목록에서 사라지지 않고 우측에 사유와 함께 내용이 뜬다 — 지금 <select> 에서는 사유가 이름 뒤에 이어붙어 잘리던 것이다. 수집 전 로 바꾸면 보드 전용 정의서도 전부 열리되 대조하지 못했다는 표식이 붙는다.

주체는 셋이다 — 조작하는 운영자, 모달을 띄우고 좌우를 전환하는 서버 상세 화면, 목록과 상세를 조립해 내려주는 서버. 화면이 조각을 한 번 받아 온 뒤로는 4 · 5 번의 좌우 전환이 전부 브라우저 안에서 끝나고 서버로 돌아가지 않는다. 서버가 다시 등장하는 것은 [할당] 을 눌러 기존 XHR 경로를 탈 때뿐이며, 그때 U3-5-a 가드가 화면이 이미 막아 둔 것을 한 번 더 확인한다.

§8. 결정

DEC-A. 조각 경계 = 카드 루프. 섹션 제목은 페이지가 갖는다

안범위판정
①절 전체 (132~393) — 섹션 제목 · 빈 상태 · 카드탈락
②카드 루프 + 빈 상태 (140~392) — 내용만채택
③카드 하나 (145~392) — 루프는 호출자가탈락

①이 탈락하는 이유는 '프로비저닝 단계' 라는 섹션 제목이 상세 화면의 문서 구조이기 때문이다. 모달은 자기 제목 체계(세팅 정의서 할당 → 우측 패널)를 갖는데, 그 안에 또 섹션 제목이 들어오면 층위가 겹친다.

③은 루프를 호출자마다 다시 쓰게 만든다. 그러면 빈 상태 처리("등록된 프로비저닝 단계가 없습니다")까지 두 곳에 복붙된다. 조각 안에 넣으면 한 번이다.

②의 파라미터는 setting 하나다. 카드가 쓰는 넷(processList · deprecatedUsages · executionWarnings · references)이 전부 SettingDetailResponse 안에 있고, 상세 화면도 모델에 그 하나만 얹는다(§1 실측). 파라미터를 넷으로 풀면 호출자가 매번 네 개를 정확히 넘겨야 하고, 하나라도 빠지면 조각이 예외 없이 조용히 빈 값을 그린다.

DEC-B. 상세 패널을 전부 미리 렌더하고 .active 만 토글한다

대안은 좌측을 클릭할 때마다 그 정의서의 상세를 fetch 하는 것이었다.

miller.css 의 설계 의도가 전자다. 파일 머리말이 .n-miller-detail-panel 을 "3열 내 항목별 상세 패널 (JS 가 .active 토글)" 로 정의하고 있고, management/os · board · bios · bmc · subprogram 다섯 화면이 그 방식으로 동작한다. 여기서만 fetch 방식을 쓰면 같은 CSS 를 쓰면서 혼자 다르게 동작하는 화면이 하나 생긴다.

값의 크기도 그쪽이다. 정의서는 조직당 수십 개 규모이고, 이 모달은 필요할 때만 열린다 — 목록 화면처럼 매번 그리는 자리가 아니다. 반대로 클릭마다 왕복하면 고르면서 비교하는 흐름이 끊긴다.

다만 정의서가 많아지면 이 판단이 뒤집힐 수 있다. 조각 fetch 로 옮기는 일은 좌측 목록과 우측 패널을 나누는 작업이라 나중에도 할 수 있으므로, 지금 미리 나누지 않는다.

DEC-C. 차단된 정의서도 상세를 보여준다

사용자 요구는 "왜 비활성인지 그 내용을 볼 수 있게" 다. 사유만 보여주는 안과 사유 + 상세를 함께 보여주는 안 중 후자를 택한다.

막힌 이유를 알아도 그 정의서가 무엇인지 모르면 다음 판단을 못 한다. "메인보드가 다르다" 를 읽은 운영자가 다음에 할 일은 "그럼 이 정의서가 하려던 것을 다른 정의서로 할 수 있나" 인데, 그러려면 내용을 봐야 한다. 구현상으로도 이쪽이 단순하다 — 조각은 차단 여부와 무관하게 같은 패널을 그리고, 사유 배너만 얹는다.

DEC-D. 회수된 서버는 이 모달을 열지 않는다

U3-5-a 가 회수된 서버의 할당 폼 자체를 닫았고, 그 판단은 그대로 유지한다. 어떤 정의서를 골라도 막히므로 전부 잠긴 모달을 열어 주는 것은 조작할 수 없는 화면을 보여주는 일이다. [정의서 할당] 버튼도 나타나지 않는다.

DEC-E. 재할당은 같은 모달을 공유한다

지금도 두 폼이 같은 <option> 조각을 쓴다. 모달도 같다 — 다른 것은 제목("세팅 정의서 할당" / "다른 정의서로 재할당")과 제출 URL 뿐이라 조각에 파라미터로 넘긴다. 두 벌을 만들면 한쪽만 고치는 드리프트가 생긴다.

DEC-F. definition-options.html 은 삭제한다

<select> 가 사라지면 이 조각은 쓰이지 않는다. 남겨 두면 "어느 것이 진짜인가" 를 다음 사람이 판단해야 한다. U3-5-a 가 그 파일에 넣은 잠금 · 사유 라벨 로직은 모달 좌측 목록으로 옮겨간다 — 판정 자체(DefinitionOptionResponse)는 그대로다.
