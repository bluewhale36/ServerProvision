§1. 현재 상태 (진단) — 왜 지금 이 슬라이스인가

엔진이 게스트의 전원을 넣거나 재부팅하기 직전에 Redfish 로 "다음 한 번은 PXE" 를 무장(BootSourceOverride · Once · Pxe · UEFI)해, 디스크에 OS 가 남은 서버도 부트 순서와 무관하게 프로비저닝 서버로 돌아오게 한다. 화면 · 원장 · DDL 변경은 없다.

사건 — 2026-08-27 실기 통합 테스트

OS 가 남아 있던 서버 아이티인포 (하)(MD72-HB3)가 BMC flash 를 마치고 PowerOnStep 이 전원을 넣자 디스크의 OS 로 부팅했다. 서버는 게스트가 PXE 로 돌아오기를 20분(provision.execution.return-timeout) 기다리다 RETURN_TIMEOUT 으로 실패했고, 첫 PXE DHCP 요청은 전원 투입 35분 뒤 운영자가 F12 로 network boot 를 골라 수동 재시작한 시점에야 들어왔다. 실측 부트 순서는 FBO101='Hard Disk' 가 1순위였다.

왜 지금까지 드러나지 않았나

빈 서버는 디스크 부팅이 실패해 부트 순서의 다음 항목(네트워크)으로 떨어지므로 "상시 PXE 우선" 처럼 보였다. 2026-08-19 4호 실측(J1)에서 "OS 설치 서버는 boot priority 가 OS 1순위" 가 관찰돼 K1 로 신설됐고, E1.5 토론 R-3 은 K1 미실측을 이유로 후속 분리(P3)했다. 08-27 이 그 후속의 착수 사유가 됐다. U6 회수 서버 재투입처럼 OS 가 남은 서버는 앞으로 늘어난다.

수동 PXE 우선 설정으로는 막지 못한다 — 3호 실측(2026-08-19)이 펌웨어 flash 가 BIOS 설정을 기본값으로 초기화함을 실증했다. 랙킹 때 PXE 를 1순위로 잡아 두어도 E2 의 flash 한 번에 무효가 된다. 재부팅 직전에 Redfish 로 강제하는 길만 남는다.

엔진이 게스트 전원을 움직이는 자리 (현행 코드 실측 · 2026-08-28)

자리호출다음에 부팅하는가
E2 BeginFlashStep (4행)RedfishPowerService.reset(FORCE_OFF)아니오 — 꺼진 채 굽는다
E2 PowerOnStep (6 · 7행)powerState 로 이미 켜졌으면 생략 · 아니면 powerOnAndVerify예 — 복귀 시한 20분 대기
E3 BeginSettingStep (6행)pending PATCH 뒤 reset(OFF 면 ON · 아니면 FORCE_RESTART)예 — rebootAt 뒤 readback 대기
E1 진단 완료 AgentDirective.REBOOT게스트가 스스로 재부팅(Redfish 아님)예 — 단 다음 phase 가 곧 끄거나(E2) 재시작(E3)한다
화면 E1.5 GuestServerPowerRestController운영자 단발 reset운영자 의도에 따름

굵은 두 행이 이 슬라이스의 자리다. 둘 다 RedfishPowerService 를 부르므로 무장 한 번을 서비스 안에 두면 두 자리가 함께 고쳐진다(Notion 페이지 ① 의 "구현 자리" 와 일치).

실측이 준 계약 (E0-4-1 · GET /redfish/v1/Systems/Self 전문 · 2026-08-18 · MS04-CE0 · BMC 13.06.27)

  • Boot.BootSourceOverrideEnabled = "Disabled", 허용값 Disabled · Once · Continuous.
  • Boot.BootSourceOverrideTarget = "None", 허용값에 Pxe 실재(그 외 Hdd · Usb · BiosSetup · UefiShell · UefiHttp …).
  • Boot.BootSourceOverrideMode = "Legacy", 허용값 Legacy · UEFI. 현재값이 Legacy 인데 이 플랫폼의 부트 옵션은 전부 UEFI(FBO201_BootOption1 = "UEFI Hard Disk" … FBO204_BootOption4 = "UEFI Network")이고 우리 PXE 사슬은 ipxe.efi 다 — Mode 를 함께 보내지 않으면 Legacy PXE 를 찾다 부트 순서로 폴스루할 수 있다(D-2 의 근거).
  • Systems/Self 에 @Redfish.Settings.SettingsObject = /redfish/v1/Systems/Self/SD 가 있다 — ComputerSystem 에도 pending 객체가 존재한다(3호에서 "ComputerSystem(Boot 등) pending" 으로 확인). PATCH 를 Systems/Self 에 직접 넣을 때 즉시 반영되는지, SD 를 거쳐 다음 리셋에 적용되는지는 미실측(K1-d).
  • If-Match 요구 여부 미실측. 선례 — Accounts/{id} 는 fresh ETag 필수(없으면 412) · Bios/SD 는 * 수락.
  • Reset 은 202 + Task 경로를 준다(기존 RedfishPowerService.issueReset 이 판독).

미실측으로 남는 것 (T3 · CP7 실기에서 닫는다)

K1-b(Once + Pxe PATCH 수락과 실제 PXE 진입 · Once 소진) · K1-d(직접 vs SD · If-Match) · Mode UEFI 명시의 필요 여부 · BMC flash(PreserveConfiguration) 뒤 boot flag 잔존 여부. 이 plan 은 표준(DMTF) 계약으로 구현하고 실기 결과가 코드의 관찰 로그로 드러나게 설계한다(D-4 readback) — 실측 없이 규칙을 굳히지 않되, 실측을 기다리느라 배선을 미루지도 않는다(사용자 결정 · 08-27).

동반 발견 — E2 복귀 대기의 재시도 기점 (코드 읽기 중 발견 · D-7)

PowerOnStep 은 복귀 시한의 기점을 FlashContext.lastAxisClosedAt()(원장의 마지막 축 행 종료 시각)으로 잡는다. 운영자가 RETURN_TIMEOUT 뒤 재시도(ProvisioningProgress.clearFailed — 08-27 RetryPolicy 정정으로 허용)하면 lastTransitionAt 만 갱신되고 원장 시각은 그대로라, 실패 뒤 20분이 더 지나 재시도하면 다음 주기에 즉시 다시 RETURN_TIMEOUT 이 된다. 08-27 실기는 운영자가 F12 로 먼저 돌려보낸 뒤 재시도해 VerifyFlashStep 이 매칭됐으므로 드러나지 않았다.

§2. 요구사항 (확정) + 비목표
  1. R1 — E2 PowerOnStep 의 전원 투입과 E3 BeginSettingStep 의 재부팅 직전에 PATCH /redfish/v1/Systems/Self {"Boot":{"BootSourceOverrideEnabled":"Once","BootSourceOverrideTarget":"Pxe","BootSourceOverrideMode":"UEFI"}} 를 한 번 발행한다.
  2. R2 — 무장은 전원 명령과 같은 자격증명 사다리(BmcCredentialsFallback) · 같은 결과화(PowerControlResult) 안에서 일어난다. 호출자가 순서를 빠뜨릴 수 없다.
  3. R3 — PATCH 가 리소스 단위로 거절돼도(4xx · 412 재시도 실패 · 404) 전원 명령은 계속한다(best effort). 연결 불가 · 자격증명 거부는 종전대로 FAILED 결과다(다음 호출도 같은 이유로 실패하므로).
  4. R4 — PATCH 뒤 Systems/Self 를 되읽어 반영 여부를 관찰하고(실패 판정 아님) 결과 메시지 · 로그에 남긴다 — 실기(CP7)가 K1-d 를 로그로 답하게.
  5. R5 — 화면(E1.5 운영자 전원 제어)의 동작은 바뀌지 않는다(PATCH 0건).
  6. R6 — 원장 사유 · 컬럼 · DDL · 설정 키를 늘리지 않는다.
  7. R7 — (동반) E2 복귀 대기 기점을 "마지막 축 종료와 마지막 전이 중 늦은 시각" 으로 정정한다(D-7).
  8. R8 — 모의 BMC(scripts/mock-redfish/mock-redfish.py)가 Boot 객체 · PATCH · Once 소진 · 거절 모드를 재연해 CP5 하네스가 전 경로를 돈다.
비 목표 (어디로 가는지 함께) :
  • 영구 부트 순서 변경(FBO* 속성) — BIOS 세팅 템플릿(U2 · E3-1) 소관.
  • UC-4 원격 복구 화면 · 화면 재시작 버튼의 "PXE 로" 옵션 — O-2(U 후속).
  • 진단 완료 REBOOT 지시(게스트 자가 재부팅) 직전 무장 — 지금은 불필요(D-6). E4 OS 설치 진입이 생길 때 그 phase 가 자기 진입 재부팅 직전에 무장한다.
  • 재시도 뒤 디스크 OS 안에 켜져 있는 서버의 강제 재시작 — D-7 비채택(표식 필요) · E2-4 와 함께.
  • 원장 표기(무장 결과를 상세 화면에) — E2-4 집행 현황 상세화.
  • Continuous 모드 · 해제(Disabled) PATCH — 쓰지 않는다(Once 는 POST 1회에 소진).
🎬 미리보기 — 다음 부팅이 어디로 가는가 (라이브 데모)

이 슬라이스에는 사용자가 누르는 버튼이 없다 — 워커가 전원을 움직이기 직전에 스스로 무장한다. 그래서 아래 버튼은 차단 사유가 아니라 서버가 대신 돌리는 일을 라벨로 달았다(마우스를 올리면 무엇을 대신 돌리는지 뜬다). 조작면에서 게스트 디스크 · 부트 순서 · BMC 의 PATCH 응답 · 무장 정책 · 진입 자리를 바꾸면 표시면의 Redfish 왕복 · Boot 객체 · 게스트 부팅처 · 엔진 판정 · 결과 메시지가 함께 갱신된다. 판정 JS 는 §3 진리표와 D-3 · D-4 · D-5 · D-7 을 그대로 옮긴 것이다(드리프트 0).

        }
    };
    public abstract BootOverrideOutcome arm(RedfishClient client, String bmcIp, BmcCredentials credentials);
}

BootOverrideOutcome.Status 는 NONE · APPLIED · UNCONFIRMED · REJECTED 넷이고, summary() 가 결과 메시지의 접두를 만든다 — "다음 부팅 PXE 강제 : 반영 확인" / "미확인 — pending 경유 가능" / "거절(…) — 부트 순서대로 부팅될 수 있음". NONE 은 접두가 없다.

RedfishError.resourceSpecific() 는 PRECONDITION_FAILED · NOT_FOUND · PROTOCOL = true(그 리소스만의 거절이라 다음 호출은 성립할 수 있다), CONNECT_FAILED · AUTH_FAILED = false(다음 호출도 같은 이유로 실패한다)이다. best effort 의 경계를 switch 가 아니라 상수가 든다.

patchJsonRefreshingEtag(String bmcIp, BmcCredentials credentials, String patchPath, String etagSourcePath, Map<String, ?> body) 의 사다리 자체는 E3-1 의 RedfishBiosService.patchPending 에 이미 있던 것이다. 두 번째 사용처가 생기는 지금이 추출 시점이므로 RedfishClient 로 끌어올리고(중복 금지), RedfishBiosService.patchPending 은 이 메서드를 부르도록 바꾼다 — 동작은 같고 ETag 원천만 다르다(Bios 는 Bios, 시스템은 Systems/Self).

§7. 예외 계층 — 신규 없음

관문 대상 없음 — 새 예외 클래스를 만들지 않으므로 .claude/domain-conventions/new-exception.md 를 여는 조건에 해당하지 않는다. 분기를 늘리지 않고 resourceSpecific() 라는 상수 속성으로 흡수 여부를 표현한 것이, 조건분기 legacy 확장 금지 원칙에 대한 이 슬라이스의 답이다.
§8. 부산물 / 주의 / 설계 결정 D-1 ~ D-10 · Open Questions

D-1. 무장의 자리 = RedfishPowerService 안

(A) 채택 — 서비스 안

채택

  • 전원 메서드가 NextBoot 인자를 받아 서비스 안에서 무장 → 전원 순서를 고정한다.
  • 무장과 전원은 같은 자격증명 · 같은 결과화 · 정해진 순서(무장이 먼저)가 생명이다.
  • 호출자(step)가 순서를 빠뜨릴 수 없고, E4 처럼 세 번째 호출자가 생겨도 인자 하나로 합류한다.

(B) 별도 BootService

탈락

  • RedfishBootService.overrideNextBoot(target) 를 두고 두 step 이 각자 전원 직전에 부른다.
  • "무장 → 결과 판독 → WARN → 전원" 시퀀스가 두 곳에 복붙된다.
  • 새 호출자가 무장을 잊어도 컴파일은 통과한다 — 빠뜨림이 조용히 지나간다.

(C) 엔진 협력자

탈락

  • execution.engine 의 "돌아오게 하는 재부팅" 컴포넌트가 서비스를 감싼다.
  • 호출자 둘을 위해 한 겹을 더 얹고, 화면 경로와 진입점이 갈라진다.
  • 갈라질 시점이 아니다.

적대적 검토 — RedfishPowerService 가 Boot 객체를 알게 되면 이름과 어긋나지 않는가. Boot 도 같은 ComputerSystem 리소스(SYSTEM_PATH)의 속성이고, Javadoc 을 "전원 · 다음 부팅 제어" 로 고친다. 이름 교체(RedfishSystemService)는 참조 12곳 churn 이라 하지 않는다.

D-2. 의도 표현 = NextBoot enum(상수별 arm) · Mode 는 UEFI 상수

채택 — AS_CONFIGURED · PXE_ONCE 두 상수. wire 바디 · 경로 · readback 판정을 상수가 든다(E3-2 BmcSettingItem 선례). boolean 인자 · 문자열 모드 · 메서드 4벌(resetViaPxe …)은 탈락이다 — 무명 boolean 금지이고, 메서드를 늘리면 조합이 폭발한다.

Mode 를 명시해 UEFI 로 보낸다. 실측 현재값이 Legacy 인데 플랫폼 부트 옵션과 PXE 사슬(ipxe.efi)은 전부 UEFI 다. Mode 없이 Target 만 바꾸면 Legacy PXE 를 찾다 폴스루할 수 있다. 설정 키로 빼지 않는다(추측 설정 금지 — 실기에서 Legacy 가 필요한 보드가 나오면 그때).

Continuous 는 쓰지 않는다 — 소진되지 않아 프로비저닝 완주 뒤(OS 설치 후 completedExit) 매 부팅 PXE 를 타게 되고, 해제 PATCH 라는 책임이 새로 생긴다. Once 는 POST 1회에 BIOS 가 지운다.

D-3. PATCH 경로 = Systems/Self 직접 + If-Match 사다리 · 사다리는 RedfishClient 로 공유

채택 — DMTF 표준은 ComputerSystem 자체 PATCH 다. Systems/Self/SD(pending) 경유가 실체더라도 "다음 리셋에 적용" 이고 우리는 곧 리셋하므로 결과가 같다. 직접 PATCH 가 405 · 400 으로 거절되는 펌웨어면 그때 SD 로 갈라진다(CP7 · K1-d).

If-Match 는 Accounts 가 fresh 필수 · Bios/SD 가 * 수락으로 갈리는데 Systems/Self 는 미실측이라 사다리로 둘 다 받는다. 사다리는 E3-1 RedfishBiosService.patchPending 에 이미 있으므로 두 번째 사용처가 곧 추출 시점이다(중복 금지) — RedfishClient.patchJsonRefreshingEtag(patchPath, etagSourcePath, body) 로 올리고 Bios 는 위임한다.

탈락 — SD 우선 : 표준을 버리고 실측 없는 추정을 고르는 것. 탈락 — 사다리 없이 * 만 : 412 가 나면 무장이 통째로 REJECTED 로 떨어진다.

D-4. 거절은 best effort(전원은 계속) + readback 관찰을 결과 · 로그에

채택 — 리소스 단위 거절(RedfishError.resourceSpecific() = true)은 BootOverrideOutcome.REJECTED 로 흡수하고 전원 명령을 낸다. 빈 서버는 무장 없이도 돌아오고(디스크 부팅 실패 → 폴스루), OS 잔존 서버는 종전 안전망(복귀 시한 → RETURN_TIMEOUT · 재시도 가능)이 받는다. readback 은 실패 판정이 아니라 관찰이며(E3-1 pending 관찰과 같은 규율), APPLIED / UNCONFIRMED 를 결과 메시지에 접두해 실기 로그가 K1-d 를 답하게 한다.

탈락 (a) 거절 = 실패 전환(새 사유 BOOT_OVERRIDE_REJECTED) : override 를 못 받는 펌웨어에서 빈 서버까지 막아, 지금 돌던 흐름을 퇴행시킨다. 탈락 (b) 조용히 무시 : 왜 안 돌아왔는지 사후 판독이 불가능하다(08-27 처럼 35분 뒤에야 안다).

연결 불가 · 자격증명 소진은 best effort 대상이 아니다 — 다음 Reset 도 같은 이유로 실패한다. 종전 guarded 규칙대로 FAILED 결과다(E2 는 다음 주기 재시도 · E3 는 행이 rebootAt 없이 남아 다음 주기).

D-5. 무장 시점 = 전원을 움직이는 호출마다 직전 1회(폴백 포함)

채택 — powerOnAndVerify 의 On 직전과 PowerCycle 폴백 직전 각각. Once 는 POST 1회에 소진되는데, "On 성공 응답 · 전원 불변"(실측 실패 모드) 뒤 폴백 때 flag 가 남아 있는지 없는지는 알 수 없다(POST 를 지났는데 폴링이 놓쳤을 수도 있다). 재무장은 멱등(Once 덮어쓰기)이라 GET 1 + PATCH 1 의 비용뿐이다.

탈락 — 한 번만 : 폴백 경로에 부트 순서로 새는 구멍이 남는다.

D-6. 적용 범위 = 엔진 두 자리. 화면 · 진단 REBOOT 지시 · FORCE_OFF 는 제외

PowerOnStep(E2) · BeginSettingStep(E3)만 PXE_ONCE 다. 화면 reset 2-arg 는 AS_CONFIGURED — 운영자 재시작의 의도는 다양하고(OS 설치 완료 서버를 OS 로 재시작하는 것 포함) 그 선택은 O-2(화면 옵션)로 넘긴다. BeginFlashStep 의 FORCE_OFF 는 부팅이 없다.

진단 완료 AgentDirective.REBOOT(게스트 자가 재부팅) 직전 무장은 하지 않는다 — 다음이 E2 면 BeginFlashStep 이 곧 끄고, E3 면 BeginSettingStep 이 무장 뒤 재시작하며, 종단이면 부트 순서대로가 맞다. E4(OS 설치) 진입이 게스트 재부팅으로 시작하게 되면 그 phase 가 자기 직전에 무장한다(§11).

D-7. (동반) E2 복귀 대기 기점 = returnWaitSince(); 재시도 뒤 강제 재시작은 비채택

채택 — FlashContext.returnWaitSince() = max(lastAxisClosedAt, progress.lastTransitionAt). clearFailed 가 lastTransitionAt = now 로 놓으므로 재시도 시각이 새 기점이 된다. 정상 흐름에선 positionAt(축 착수)이 축 종료보다 앞서므로 값이 바뀌지 않는다. guestReturned() 도 같은 기점을 쓴다 — 재시도 전에 돌아온 게스트는 30초 폴링이 lastSeenAt 을 곧 갱신해 다음 주기에 VerifyFlashStep 으로 간다. 1줄급 변경이고, 이 슬라이스의 CP5 시나리오(⑥ 재시도)가 의미를 가지려면 필요하다.

비채택(별도 · E2-4 와 함께) — 재시도 뒤 PowerState = On 인 서버(디스크 OS 안)를 무장 + ForceRestart 하는 안. PowerOnStep 은 "이미 켜짐 = POST 중" 으로 멱등 판단하는 설계라(컬럼 0), 재시작을 한 번만 내리려면 "이번 재시도에서 이미 재시작했다" 는 표식(원장 행 또는 컬럼)이 필요하다. 표식 없이 넣으면 30초마다 재시작하는 루프가 된다. 원장 표기 확장은 E2-4 소관이므로 거기서 함께 정한다. 그동안 운영자는 F12 로 돌려보낸 뒤 재시도한다(08-27 방식).

D-8. 실기 미실측 4건은 코드가 답하게 설계한다 (T3 · CP7)

K1-b(수락 · PXE 진입 · Once 소진) · K1-d(직접 vs SD · If-Match) · Mode 명시 필요 여부 · BMC flash 뒤 flag 잔존 — 결과 메시지의 outcome(APPLIED / UNCONFIRMED / REJECTED + 사유)과 [flash] · [setting] 로그 한 줄이 실기에서 그대로 증거가 된다. 실측 결과에 따라 갈라질 코드는 상수 하나(경로) · enum 상수 하나(Mode)다.

D-9. PowerControlResult 필드 추가 없음

outcome 은 message 접두로만 싣는다. 필드를 더하면 화면 JSON 에 화면이 쓰지 않는 필드가 노출된다. 서비스가 REJECTED · UNCONFIRMED 를 스스로 WARN / INFO 로 남기므로 step 은 message 만 INFO 로 잇는다.

D-10. 원장 · 설정 무변경

새 사유 없음(REJECTED 는 실패가 아니다 — D-4) · 컬럼 없음 · 설정 키 없음(Mode 는 상수 — D-2). 원장에 무장 사실을 남기는 일은 E2-4 의 표기 확장에서 한다.
