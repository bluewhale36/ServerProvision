§1. 배경 · 유래

R13 실기 통합 테스트(2026-08-25)에서 회수(decommission)한 실기 게스트를 재투입하려다 불가함을 실증했다. 현 구조의 인과:

  1. PXE 등록 멱등(GuestServerRegistrationService.initialRegistry 의 findBySystemUUID)이 회수된 행에 계속 붙는다
  2. dispatch 최우선 행(BootScriptDispatcher)이 회수 마커를 보고 대기 스크립트만 내린다
  3. 회수 해제와 게스트 삭제 액션이 모두 없다

U1 설계가 회수를 "프로비저닝 대상 영구 제외 마커" 로만 정의해 재입고 유스케이스가 빠져 있었다.

임시 조치 — 착수 전까지는 DB 직접 삭제로 우회 중이다. 이 단계가 그 우회를 해소한다.
§2. 확정된 방향 (사용자 결정, Notion U6 본문 2026-08-25)

Notion 페이지의 원 쟁점은 "⑴ 회수 해제 vs ⑵ 회수 게스트 삭제" 두 안이었으나, 사용자가 본문에 통합안을 이미 확정했다 — 이 plan 은 그 방향을 코드 현실과 대조해 세부를 채운 것이다:

  1. 회수 = 이력화 — 자원 soft-delete 처럼 목록 기본 숨김 + '회수된 서버 보기' 체크박스로 노출. 복원(restore) 개념 없음 → 복원 유도 nudge 도 없음.
  2. 같은 systemUUID 재등장 = "회수 후 재시도" — 자원 soft-delete 후 동명 재등록 허용과 같은 결로, 다음 PXE 부팅이 신규 등록으로 이어진다.
  3. 회수 조치 시 모달 경고 — 이후 영향을 고지하는 확인 과정.
  4. 삭제는 회수 서버 한정 — 상세 화면 최하단 버튼. 확인 입력 = 자원명 대신 SMBIOS UUID 의 마지막 - 다음 값(현행 형식 기준 12 hex — MVP 이후 형식이 다른 서버가 나오면 그때 수정, 사용자 명시).
주의 (오독 방지) — "nudge 를 쓰지 않는다" 는 복원 유도 nudge 가 없다는 뜻이다. 삭제 확인의 typed 입력(suffix)은 별개이며 유지된다.
활성(active) ──[회수 + 모달 경고]──▶ 회수됨(이력 · active_system_uuid = NULL) │ │ │ 같은 UUID PXE 부팅 │ 같은 UUID PXE 부팅 ▼ ▼ 기존 행 재사용(재부팅 멱등) 새 행 등록(회수 후 재시도) — 회수 행은 이력으로 잔존 │ └─[삭제 · suffix 확인]──▶ 소멸(자식 6 FK ON DELETE CASCADE)
🎬 미리보기 — 회수 → 재부팅 → 재시도 등록 → 삭제 수명 주기

아래 시뮬레이터의 판정은 이 슬라이스가 세우는 서버 로직과 같은 바디다 — 등록 멱등의 활성 한정(findBySystemUUIDAndDecommissionedAtIsNull, D-3)과 GuestServerStatus.derive 진리표(회수 > 실패 > 종단 > 개시, 변경 0). 각 행에는 active_system_uuid 파생값(활성 = UUID / 회수 = NULL)을 함께 찍어, DB 활성 유일성(D-1)이 어떻게 성립하는지 눈으로 보이게 했다.

§3. 설계 결정 D-1 ~ D-8

D-1. system_uuid 활성 유일성 = PERSISTENT generated column + UNIQUE (U3-2-a 선례 재적용)

현행 guest_server.system_uuid 에는 DB UNIQUE(uk_guest_server_system_uuid)가 있어 같은 UUID 의 신규 행 자체가 불가능하다. 재시도 등록을 열려면 이 제약의 재설계가 필요하다.

적용 실측 정정(2026-08-25, CP2 중 오류 1091 계기) — 실 DB 에는 이 UNIQUE 인덱스가 애초에 없었다(schema.sql 스냅샷과의 드리프트 — 엔티티의 unique = true 는 ddl-auto=validate 에서 인덱스를 만들지 않는다). 즉 활성 유일성은 지금까지 앱 가드(등록 멱등)만이 지켜 왔고, 아래 채택안은 재설계가 아니라 DB 강제의 최초 부여다 — TOCTOU 방어가 비로소 생기므로 설계 필요성은 오히려 커졌다. DDL 의 DROP 은 IF EXISTS 로 환경 편차를 방어한다. 적용 후 3단 실측(같은 UUID 회수 2행 허용 · 활성 1행 허용 · 활성 중복 1062 거절) 완료 — U3-2-a 이래 T3 적립 항목이던 generated column 실동작이 이 DB 에서 확인됐다.

채택 — 기존 UNIQUE 를 내리고, active_system_uuid = IF(decommissioned_at IS NULL, system_uuid, NULL) PERSISTENT generated column 에 UNIQUE 를 건다. 회수 행(NULL)은 얼마든 쌓이고 활성 행은 UUID 당 1개만 DB 가 강제한다. setting_assignment.active_guest_id(U3-2-a)와 완전히 같은 기법이며, 그 DDL 의 설계 근거(서비스 가드만으론 TOCTOU 창이 남는다)가 그대로 적용된다. JPA 매핑은 하지 않는다(순수 DB 파생 컬럼 — ddl-auto=validate 는 잉여 컬럼을 문제 삼지 않음, 선례 검증 완료). 엔티티의 @Column(unique = true) 속성은 제거한다(validate 는 인덱스를 검사하지 않으나 의미 정합).

BEFORE

UNIQUE uk_guest_server_system_uuid (system_uuid)

→ 같은 UUID 의 신규 행 자체가 불가능

AFTER — 활성만 유일

active_system_uuid AS (IF(decommissioned_at IS NULL,
                       system_uuid, NULL)) PERSISTENT
UNIQUE (active_system_uuid)

→ 회수 행(NULL) 다중 허용 · 활성은 UUID 당 1
  • 비채택 1 — UNIQUE 단순 제거 + 앱 가드 : 동시 부팅(같은 UUID 두 요청)의 TOCTOU 창에서 활성 중복이 생길 수 있다. U3-2-a 가 정확히 이 이유로 기각한 안.
  • 비채택 2 — 복합 UNIQUE(system_uuid, decommissioned_at) : MariaDB UNIQUE 는 NULL 다중을 허용하므로 활성(NULL) 중복을 못 막는다 — 역효과.

D-2. board_serial UNIQUE 는 제거 + 앱 가드 활성 한정 (이번 조사의 실질 발견)

사용자 본문에 없던 쟁점을 코드 대조가 찾아냈다: guest_server_detail.board_serial 에도 DB UNIQUE 가 있다. 재시도 게스트의 진단이 같은 보드 시리얼을 보고하면 — 물리적으로 같은 장비이므로 반드시 같다 — 회수 행이 시리얼을 쥔 채라 적재가 막힌다.

현행 관용 로직(DiagnoseLinuxExecutor 의 existsByBoardSerialAndGuestServer_IdNot 가드 → WARN + 적재 생략)이 흡수는 하지만, 그 결과 재시도 행의 boardSerial 이 영영 비고, E2-2 신원 확인(보드 시리얼 대조)과 E1.6 공장 기본 자격(비밀번호 = 시리얼)이 함께 무력화된다. 재투입한 서버는 펌웨어를 굽지 못하는 반쪽이 된다.

채택 — ① DB UNIQUE 를 내린다 ② 앱 가드를 활성 한정으로 바꾼다(existsByBoardSerialAndGuestServer_IdNotAndGuestServer_DecommissionedAtIsNull — 활성 행끼리의 시리얼 중복만 WARN + 생략). 회수 행의 시리얼은 이력으로 보존된다.

  • 비채택 1 — D-1 과 같은 generated column : decommissioned_at 은 guest_server 테이블, board_serial 은 guest_server_detail 테이블 — MariaDB generated column 은 같은 테이블 컬럼만 참조할 수 있어 불성립.
  • 비채택 2 — 회수 시 시리얼 NULL 화 : 회수 행의 상세를 볼 때 시리얼이 사라져 이력 가치가 훼손된다.
  • 비채택 3 — 적재 생략 유지(현행) : 위에 쓴 대로 재투입 서버의 펌웨어 경로가 무력화 — 기각.

잔여 위험 — 활성 시리얼 중복의 DB 강제가 사라진다. 이 중복은 진단 보고 동시 2건이라는 좁은 창에서만 생기고, 기존에도 앱 가드 + WARN 관용이 1차 방어였다. system_uuid(D-1)와 달리 시리얼은 등록 정체성이 아니라 수집 속성이라 DB 불변식의 무게가 다르다.

D-3. 등록 멱등의 활성 한정

GuestServerRegistrationService.initialRegistry 의 findBySystemUUID → findBySystemUUIDAndDecommissionedAtIsNull. 활성 행이 있으면 기존 동작 그대로(재부팅 멱등 — 토큰 lazy 발급 + 반환), 회수 행만 있으면 신규 등록으로 흘러 "회수 후 재시도" 를 로그에 명시한다. R13(등록 즉시 진단 자동)에 의해 재시도 행은 곧바로 무인 수집을 돈다 — 재입고가 등록 한 번으로 끝나는 그림이 여기서 완성된다.

BootScriptDispatcher 의 회수 분기(IpxeScripts.decommissioned 대기 스크립트)는 이 변경으로 정상 경로에서 도달 불가가 된다 — 등록이 회수 행을 돌려주지 않기 때문이다. 분기는 안전망으로 유지하고 주석만 갱신한다(U6 이후 도달 불가 · 비정상 경로 방어). 서버 가드 유지 원칙과 같은 결.

D-4. 목록 숨김 + '회수된 서버 보기' 토글

GuestServerQueryService.findAll 을 기본 활성만으로 바꾸고(findAllByDecommissionedAtIsNullOrderByCreatedAtDesc), 쿼리 파라미터 includeDecommissioned=true 면 전체를 준다. OS 목록의 includeDeleted 휴지통 모드(OSControllerSupport — 상태 전이 후에도 보기 유지)가 확립된 선례다. 회수 행 노출 시 상태 배지는 기존 GuestServerStatus.derive(회수 > 실패 > 종단 > 개시)가 이미 DECOMMISSIONED 를 내므로 화면 로직 신설이 없다.

그룹 화면과의 관계 — 회수 멤버의 그룹 멤버십은 이 단계에서 건드리지 않는다. 그룹 단위 일괄 할당은 사전 분류(U3-5-c)가 서버별 blockReason SSOT 를 타므로 회수 서버는 이미 배제된다 — CP2 에서 이 배제의 실동작을 확인 항목으로 둔다(어긋나면 그때 보고).

D-5. hard-delete — 회수 서버 한정 · suffix 확인 · CASCADE

  • UI : 상세 최하단, 회수 상태에서만 렌더(활성 서버에는 버튼 자체가 없다 — UX 모순 UI 1차 차단). 확인 입력 = systemUUID 의 마지막 - 다음 값.
  • 서버 가드(안전망) : ① 회수 상태가 아니면 거절 ② 입력 suffix 불일치면 거절. 가드는 정적 메서드(의존성 0 — TypedNameGuard.verify 선례의 결)로 두고 UI 차단 조건과 같은 SSOT 를 쓴다.
  • 실행 : guestServerRepository.delete — schema.sql 실측으로 guest_server 를 참조하는 FK 6개 전부(detail · nic · progress · history · assignment · group member) ON DELETE CASCADE 확인 완료. 애플리케이션 cascade 배선이 불요하다.
  • 성공 후 이동 : 보던 자원이 사라지는 액션이므로 window.AsyncSubmitResult 를 덮어써 서버 redirect 도착지(목록)로 이동한다 — static/provisioning/setting-lifecycle.js · static/maintenance/trash/trash-action.js 선례(new-form.md).
  • 신규 엔드포인트 1건(POST /provisioning/server/{id}/delete) — 통합 테스트 4범주(2xx · 400 · 409 · 404) 적용 대상.

D-6. 회수 모달 경고 — ConfirmModal 자산 재사용

현행 회수 폼은 경고 없이 즉시 제출된다. ConfirmModal.bindFormSubmit(확인 모달 자산 — 승인 후 전역과 같은 전송 구현으로 넘김, 별도 배선 불요)으로 경고를 끼운다. 경고 4문: ① 목록에서 숨겨진다('회수된 서버 보기' 로만 노출) ② 세팅 정의서 할당 등 조작이 막힌다 ③ 이 서버가 다시 PXE 부팅하면 새 서버로 등록된다(회수 후 재시도) ④ 복원은 없다. 폼 마커 판정(new-form.md): 회수 · 삭제 핸들러 모두 BindingResult 를 받지 않으므로(성공 redirect · 실패 예외 → 모달 수렴) data-native-submit 을 붙이지 않는다.

D-7. 두지 않는 것

  • 복원(un-decommission)
  • 복원 유도 nudge
  • 회수 이력 별도 아카이브 — 삭제 전 이력은 행 자체가 담고, 삭제하면 사용자 확정대로 소멸
  • 회수 자체의 원장(ProvisioningHistory) 기록 신설 — 현행도 마커만 있고 기록은 없다. 그 상태를 유지한다

D-8. DDL — U6_guest_reintake.sql (실 DB ALTER 대기 행렬 등재)

  1. guest_server : uk_guest_server_system_uuid DROP → active_system_uuid PERSISTENT generated column + UNIQUE 추가 (D-1)
  2. host_nic_binding : host_mac UNIQUE DROP — CP5 A7 FAIL 로 발견(CP1 조사가 놓친 세 번째 UNIQUE). D-2 와 같은 성격(같은 장비 = 같은 MAC · 다른 테이블이라 generated column 불가) · 활성 중복은 D-1 이 상위 불변식으로 막아 별도 가드 불요
  3. guest_server_detail : board_serial UNIQUE(UKlhbawogtag8eoi0d1rtx2p57c) DROP (D-2)

U3-2-a 의 "generated STORED + UNIQUE + NULL 중복 허용" MariaDB 실동작은 T3 검증 항목으로 이미 적립돼 있다 — 이번 DDL 도 같은 항목에 합류한다.

§4. 스코프 제외 (행선지)
비 목표 :
  • 종단(completed) 게스트의 할당 재개(reopen) — E1-3 로드맵 소관(페이지 비목표). 인접 결정이라 정합만 확인한다 — 종단 서버도 회수 → 재시도 경로로 재입고 가능하므로 reopen 없이도 재투입 자체는 막히지 않는다.
  • 회수 이력 별도 아카이브 — 만들지 않음(D-7). 페이지 비목표의 "삭제안 채택 시 판단" 을 불요로 종결한다.
  • 그룹 멤버십 자동 정리 — 이번 범위 밖(D-4).
  • SMBIOS UUID 형식이 다른 서버의 suffix 규칙 — MVP 이후(사용자 명시).

§7. 예외 · 거절 매핑

이 슬라이스가 새로 만드는 거절 지점은 삭제 엔드포인트 하나이며, 그 거절 조건은 D-5 의 서버 가드 둘과 대상 부재 하나다. UI 가 1차로 막으므로(활성 서버에는 삭제 버튼 자체가 없다) 아래 거절은 direct POST · stale 화면 같은 비정상 경로에서만 발동하는 안전망이다.

§8. 위험 · 미해결
  • generated column 의 MariaDB 실동작(NULL 다중 + 활성 UNIQUE)은 U3-2-a 부터 T3 실기 검증 항목이다 — 샌드박스 MariaDB 로 CP5 에서 1차 확인한다.
  • 활성 시리얼 중복의 DB 강제 상실(D-2 잔여 위험) — 좁은 동시성 창 · WARN 관용 유지로 수용한다.
  • 회수 직후 같은 서버가 계속 켜져 있는 경우: 다음 PXE 부팅 시점에 즉시 새 행이 생긴다 — "회수했는데 목록에 새 행이 나타났다" 는 인상을 줄 수 있다. 모달 경고의 ③번 문장("이 서버가 다시 PXE 부팅하면 새 서버로 등록된다")이 정확히 이를 고지한다(경고가 UX 방어).
  • systemUUID suffix 는 현행 실측 형식(마지막 세그먼트 12 hex) 기준 — 형식이 다른 장비는 MVP 이후(사용자 명시, §4).

§11. 다음 마일스톤
  1. 실 DB ALTER 대기 행렬 등재 — ddl/U6_guest_reintake.sql 을 등재하고, generated column 의 MariaDB 실동작을 U3-2-a 부터 이어져 온 T3 검증 항목에 합류시킨다 (D-8).
  2. 종단 게스트의 할당 재개(reopen) — E1-3 로드맵이 받는다. U6 는 재투입 경로만 열고 reopen 은 열지 않는다 (§4).
  3. 그룹 멤버십 자동 정리 — 이번 범위 밖. 회수 서버가 그룹 일괄 할당에서 배제되는 것은 U3-5-c 의 사전 분류가 이미 처리하므로, CP2 에서 그 실동작만 확인한다 (D-4).
  4. SMBIOS UUID 형식 확장 — 마지막 세그먼트가 12 hex 가 아닌 장비가 나오면 그 시점에 suffix 규칙을 수정한다. MVP 이후 (§4).
