§0. 한눈 요약

현재 시각에 기대는 테스트 두 건을 결정적으로 만든다. 대상 서비스 둘에 java.time.Clock 을 주입하고 — 기본 빈은 시스템 시계다 — 테스트는 고정 Clock 을 넣는다. 운영에서 읽히는 시각은 지금과 같고, 달라지는 것은 그 시각을 어디서 받아 오는가 하나다.

전역 시각 추상화는 하지 않는다. 지금 흔들리는 지점이 둘이므로 그 둘만 고친다. 스키마 변경은 없고(DDL 0), 설정 파일도 화면도 건드리지 않는다.

대상 둘 — ① DriftBulkApplyService 의 보관(snooze) 만료 판정 ② GuestServerQueryService 의 시간 묶음 · 잔여 시한 · 접촉 판정. 두 서비스 모두 @RequiredArgsConstructor 생성자 주입이라 필드 하나를 더하면 스프링이 빈을 넣어 준다.
§1. 현재 상태 (진단)

① 보관 만료 판정 — 한 번 발화했고, 임시로 막아 둔 상태다

DriftBulkApplyService.openTargets 는 Instant.now() 를 읽어 Drift.isListed(now) 에 넘긴다. 이 도메인 메서드는 드리프트가 열려 있거나 보관 기한이 지났을 때 목록에 남긴다고 판정하므로, 기준 시각이 판정을 가른다.

테스트는 2026-08-12 고정 시각에 7일 보관 창을 세워 두고 있었다. 8월 19일에 실제 달력이 그 창을 넘어서면서 창이 과거가 되었고, 그때부터 테스트가 영구히 실패했다. 시한폭탄이라 부르는 형태다. 임시 조치(커밋 6f5e775)로 기준을 Instant.now() 상대 시각으로 바꾸어 지금은 통과한다.

그러나 테스트와 서비스가 서로 다른 순간의 실 시계를 읽는 구조는 그대로다. 픽스처가 기준을 잡은 순간과 서비스가 Instant.now() 를 부르는 순간이 다르므로 창 경계 근처에서는 여전히 흔들릴 수 있고, 무엇보다 "언제 돌려도 같은 결과" 라는 테스트의 성질이 없다.

② 시간 묶음 — 전체 실행에서만 간헐로 깨진다

GuestServerQueryServiceGroupingTest 는 픽스처 서버의 등록 시각을 LocalDateTime.now().minusSeconds(n) 으로 만든다. 서비스는 목록을 조립할 때 자기 LocalDateTime.now() 를 읽어 경과 시간을 계산하고, 그 경과를 내림 눈금으로 묶는다. 두 now 사이에 눈금 경계가 끼면 같은 묶음에 들어가야 할 서버가 다른 묶음으로 떨어져 단언이 깨진다.

단독 실행은 픽스처 생성과 조회 사이가 거의 붙어 있어 잘 통과한다. 전체 실행에서는 그 사이가 벌어지므로 간헐 실패가 된다. 재현이 어렵고, 실패했을 때 코드가 아니라 실행 시점을 의심하게 만든다는 점이 이 결함의 실질적 비용이다.

③ 지금 저장소의 상태

  • java.time.Clock 을 쓰는 코드가 본 소스에도 테스트에도 없다. Clock 빈도 없다.
  • global/config 에는 AsyncConfig · RestClientConfig 둘이 있다.
  • GuestServerQueryService 안의 LocalDateTime.now() 호출은 9 곳이다.
  • 눈금 규칙 자체는 값 객체 RegistrationAge 가 소유하고 기준 시각을 인자로 받으므로, 이번 변경의 대상이 아니다.
핵심 진단 — 두 결함의 원인은 같다. 한 판정에 시계가 둘이라는 것이다. 픽스처가 하나를 읽고 서비스가 다른 하나를 읽으니, 둘 사이의 간격이 판정 경계를 넘는 순간 결과가 바뀐다. 경계값을 넉넉히 잡는 것으로는 확률만 낮아진다.
§2. 요구사항 (확정) + 대안 비교 + 비목표

요구사항

  1. 두 서비스가 시각을 주입된 Clock 한 곳에서만 읽는다.
  2. 운영 동작은 변하지 않는다 — 기본 빈이 시스템 시계이므로 실제로 읽히는 값이 지금과 같다.
  3. 테스트는 고정 Clock 을 넣어 언제 돌려도 같은 결과를 낸다.
  4. DriftBulkApplyServiceTest 의 기준 시각을 고정 상수로 되돌린다. 서비스가 같은 고정 시계를 보므로 더는 시한폭탄이 아니다.
  5. 스키마 · 설정 · 화면 변경 0.

대안 비교

안요지결과
① Clock 주입 두 서비스에 Clock 을 생성자 주입하고 테스트는 고정 Clock 을 넣는다. 채택 자바 표준 · 결정적 · 다른 코드 무변경.
② 정적 mock 테스트에서 LocalDateTime.now 를 정적으로 mocking 한다. 탈락 정적 mock 은 스레드 · 범위에 취약하고, 프로덕션 시그니처는 그대로라 근본 정정이 아니다.
③ 경계값 여유 확대 단언 경계를 초에서 분으로 넓혀 흔들릴 여지를 줄인다. 탈락 실패 확률만 낮추고 결정적이지 않다. 8월 19일 선례가 "경계 조정으로는 안 된다" 를 이미 보였다.
④ 전역 TimeProvider 시각 조회를 전용 추상 타입으로 감싸 전 코드를 일괄 치환한다. 비목표 지금 필요한 지점이 둘이다. "갈라지는 시점에 분리" 원칙에 어긋난다.
비 목표 :
  • 전역 시각 추상화(대안 ④) — 세 번째 지점이 생기는 시점에 다시 판단한다.
  • 두 서비스 바깥의 LocalDateTime.now() · Instant.now() 호출 — 이번에는 손대지 않는다(§8 잔존).
  • 시간대 정책 변경 — 기본 빈은 시스템 기본 시간대를 그대로 쓴다.
  • 눈금 규칙 자체의 변경 — RegistrationAge 는 유지한다.

간헐 실패가 어떻게 생기는지는 말로 설명하는 것보다 지연을 직접 밀어 보는 편이 빠르다. 아래 슬라이더는 픽스처가 등록 시각을 만든 순간과 서비스가 조회 시각을 읽는 순간 사이의 지연이다. 단독 실행이면 이 값이 거의 0 이고, 전체 실행이면 앞선 테스트들이 소비한 시간만큼 벌어진다.

왼쪽 카드는 종전 — 두 실 시계, 오른쪽 카드는 정정 후 — 고정 Clock 하나다. 두 카드는 같은 픽스처를 받는다. 슬라이더를 밀면 왼쪽에서만 묶음이 갈라지는 구간이 나타나고, 오른쪽은 어떤 지연에서도 한 묶음 그대로다. 갈라지는 구간과 다시 붙는 구간이 번갈아 오는 것이 이 결함을 "가끔 실패" 로 만든다.

바뀌는 코드의 모양

BEFORE — 실 시계를 그 자리에서

// DriftBulkApplyService
Instant now = Instant.now();

// GuestServerQueryService (9 곳)
LocalDateTime now = LocalDateTime.now();

AFTER — 주입된 Clock 하나

private final Clock clock;   // 생성자 주입

// DriftBulkApplyService
Instant now = clock.instant();

// GuestServerQueryService (9 곳)
LocalDateTime now = LocalDateTime.now(clock);

호출부의 모양이 거의 그대로라는 점이 이 안의 장점이다. 판정 로직 · 시그니처 · 반환 타입이 하나도 바뀌지 않으므로, 회귀가 생길 수 있는 자리가 "시각을 어디서 읽는가" 한 줄로 좁혀진다.

§4. 도메인 모델 (SSOT) — 엔티티 · Enum · DDL 변경 0

엔티티도 값 객체도 새로 만들지 않는다. 판정 규칙은 이미 도메인이 소유하고 있고 기준 시각을 인자로 받는다 — 그래서 이번 변경이 서비스 층에서 끝난다.

내림 눈금 사다리 — RegistrationAge (변경 없음)

경과 < 1분 → 10초 눈금 floor(경과/10)*10 초 ("방금" · "10초 전" · "50초 전") 경과 < 1시간 → 1분 눈금 floor(경과/60) 분 경과 < 24시간 → 1시간 눈금 floor(경과/3600) 시간 경과 < 7일 → 1일 눈금 floor(경과/86400) 일 그 이상 → 1주 눈금 floor(경과/604800) 주

눈금이 경과에 따라 성기어지는 이유는 운영자가 구분해야 하는 폭이 시간대마다 다르기 때문이고, 그 판단은 값 객체가 가진다. 이번 슬라이스가 바꾸는 것은 그 now 인자를 누가 만들어 넘기는가일 뿐이다.

§6. 테스트 배선 — 고정 Clock 을 어떻게 넣는가

고정 시각은 Clock.fixed(Instant.parse("2026-09-05T10:00:00Z"), ZoneId.of("Asia/Seoul")) 하나를 쓴다. 넣는 방법은 테스트가 서비스를 어떻게 만들고 있는가에 따라 둘로 갈린다.

테스트현재 배선이번 조치
DriftBulkApplyServiceTest @InjectMocks @Spy 고정 Clock 추가. 기준 시각 NOW 를 고정 상수로 되돌림
GuestServerQueryServiceGroupingTest @InjectMocks @Spy 고정 Clock 추가. 픽스처를 LocalDateTime.now(CLOCK).minusSeconds(n) 으로
GuestServerQueryServiceTest @InjectMocks @Spy 고정 Clock 추가
GuestServerQueryServiceWindowsInstallTest 수동 new GuestServerQueryService(...) 생성자 인자에 고정 Clock 추가
GuestServerQueryServiceExecutionViewTest 수동 new GuestServerQueryService(...) 생성자 인자에 고정 Clock 추가

왜 @Mock 이 아니라 @Spy 인가

@Mock 은 아무것도 하지 않는 껍데기를 만든다 — instant() 가 기본값을 돌려주므로 판정이 성립하지 않는다. 필요한 것은 실제로 동작하는 고정 Clock 이고, 그것을 @InjectMocks 의 생성자 주입 후보에 올리려면 @Spy 로 실물을 감싸야 한다. Mockito 5 의 inline mock maker 가 이를 처리한다.

같은 패턴이 이미 GuestServerQueryServiceGroupingTest 안에 있다 — ObjectMapper 를 @Spy 실물로 얹어 주입 후보로 쓰고 있다. 새 관례를 들이는 것이 아니라 그 자리에 하나를 더 놓는 것이다.

DriftBulkApplyServiceTest 의 기준 시각을 고정 상수로 되돌릴 수 있는 이유는 하나다 — 서비스가 같은 고정 시계를 보기 때문이다. 임시 조치가 상대 시각을 쓸 수밖에 없었던 것은 서비스가 실 시계를 읽고 있어서였고, 그 전제가 사라진다.
§7. 예외 계층 — 변경 0

신규 예외 없음, 기존 예외의 매핑 변경 없음. 이 슬라이스는 판정의 입력을 바꿀 뿐 판정의 결과 종류를 늘리지 않는다. DriftReportNotFoundException · DriftResolutionNotAllowedException · GuestServerNotFoundException 은 유지 이며, 발생 조건과 HTTP 매핑이 지금과 같다.

§8. 결정 사항 / 잔존 책임 / Open Questions
#결정근거
D-1 global/config/ClockConfig 에 @Bean Clock clock() 을 두고 Clock.systemDefaultZone() 을 돌려준다. 운영 동작이 변하지 않는다 — 같은 시스템 시계를 한 겹 거쳐 읽을 뿐이다. 공용 인프라이므로 global/config 가 자리다.
D-2 두 서비스에 private final Clock clock 을 더한다. DriftBulkApplyService 는 clock.instant(), GuestServerQueryService 는 9 곳 전부 LocalDateTime.now(clock). 한 클래스 안에 시각 소스를 둘 두지 않는다. 다른 클래스는 건드리지 않는다.
D-3 테스트는 고정 Clock 2026-09-05T10:00:00Z · Asia/Seoul 하나를 공유한다. @InjectMocks 셋은 @Spy, 수동 생성 둘은 인자 추가. 배선 방식이 다른 것은 테스트가 서비스를 만드는 방식이 다르기 때문이고, 넣는 값은 같다.
D-4 검증은 전체 테스트 3회 연속 green + 두 테스트 클래스 20회 반복 green. 여기에 빈 기동 1회와 화면 1컷을 더한다. 결정성은 반복해서 통과하는 것으로만 보일 수 있다. 화면이 없는 슬라이스라 브라우저 검증을 이것으로 대체한다(§9).

잔존 책임

두 서비스 바깥의 LocalDateTime.now() · Instant.now() 호출은 그대로 둔다. 지금 그 지점들이 테스트를 흔들고 있지 않기 때문이다. 흔들리는 지점이 새로 나타나면 같은 방식으로 그 클래스에 Clock 을 하나 더 주입한다 — 그때도 전역 치환으로 가지 않는다.

주의

  • 고정 Clock 은 흐르지 않는다. 시간의 경과 자체를 검증하는 테스트가 생기면 Clock.offset 으로 진행시킨다.
  • 기본 빈이 systemDefaultZone() 이므로 시간대는 지금과 같다 — 이 슬라이스에서 시간대 정책을 정하지 않는다.
