§1. 현재 상태 (진단)

이 슬라이스는 상위 단계 E4-1-a(Windows Server 2025 설치)의 두 번째 조각이다. 앞선 토론 1호 (discussion/26-09-02_14-22-42_E4-windows-install-integration_discussion.md)가 §8 에서 확정한 결정과, 같은 날 실측 1호 (report/26-09-02_14-14-54_WIN-fieldwork-1_report.html)가 확보한 재료가 입력이다. 아래 표는 착수 시점의 코드 실태를 관측한 것이다.

계열 enum 이 둘이고 Windows 만 사상이 비어 있다

management.os.enums.OSFamily 는 RHEL_BASED · DEBIAN_BASED · WINDOWS_BASED 셋을 갖지만 provisioning.setting.enums.OSFamily 는 앞의 둘뿐이다. 두 enum 을 잇는 것이 JpaSettingQueryService.FAMILY_MAPPING 이고, Windows 는 사상이 없어 OS 선택지에 osFamily = null 로 실린다. setting 쪽 enum 의 Javadoc 은 "상수를 여기 미리 두지 않는 이유도 같다: 소비자(구현 클래스 · 화면)가 생기는 시점에 추가한다" 로 자리를 예약해 두었다. 이 슬라이스가 그 소비자를 만든다.

R11 이 남긴 식별 전용 타입이 현행 저장 형태다

R11(OS 섹션 축소)은 Windows 정의서를 PlannedOSInstallationRequest(osMetadataId · isoId 둘만)로 저장하게 했다. 해석기 ProcessRequestDeserializer 의 IDENTIFICATION_SUBTYPES 가 판별자 없는 본문을 이 타입으로 보내고, PlannedInstallTargetPolicy.blockReason(OSName) 이 "리눅스는 선택 불가" 판정을 옵션 disabled(화면)와 서버 가드 (UnsupportedPlannedInstallTargetException, 400 · 필드 osMetadataId) 양쪽에 공급한다. 폼 카드 안내문은 "이 단계는 설치할 OS 의 예정 기록만 담습니다" 이고 상세 카드는 "설치 예정 기록" 배지를 보인다. 폼 JS 는 OS 설치 payload 에 osFamily 를 아예 싣지 않는다.

저장은 JSON 왕복이고 해석기가 그 SSOT 다

단계 payload 는 setting_process.payload_json 과 할당 스냅샷 assigned_process_snapshot.payload_json 둘 다 JSON 컬럼이며 ProcessPayloadConverter 가 Boot 의 ObjectMapper 로 왕복시킨다. 요청과 저장본을 같은 해석기가 읽으므로, 판별자가 없는 저장본은 해석기가 거절한다 — 조용히 흡수되는 경로가 없다는 뜻이고, 뒤의 D-3(저장본 치환)이 필요한 이유이기도 하다.

실측 1호가 확정한 재료

실측에서 뜯어 본 install.wim 의 XML 자원은 이미지 4 종을 담고 있었다 — index 1 SERVERSTANDARDCORE · 2 SERVERSTANDARD · 3 SERVERDATACENTERCORE · 4 SERVERDATACENTER. EDITIONID 는 ServerStandard 와 ServerDatacenter 둘, INSTALLATIONTYPE 은 "Server Core" 와 "Server" 둘이며, DISPLAYNAME 에는 한국어 "(데스크톱 환경)" 이 들어 있다. LANGUAGES/DEFAULT 는 ko-KR, VERSION 은 10.0.26100.1742 다. 파일 구조로는 WIM 헤더가 208 바이트이고 XML 자원 헤더가 오프셋 72 에 있으며 XML 본문은 UTF-16LE(BOM 포함) 비압축이다. 이 네 값이 §4 의 파서 계약을 그대로 결정한다.

ISO 에서는 읽을 수 없다 (2026-09-02 실측) — 앱은 스테이징에서 provisioning 시스템 계정으로 도므로 mount -o loop 권한이 없고, bsdtar 는 UDF 를 읽지 못해 Windows ISO 에서 항목 2 개(README.TXT)만 본다(맥 bsdtar 3.5.3). 기존 IsoPreparationService 는 mount 실패 시 7z · bsdtar 로 폴백하므로, 이것을 Windows ISO 에 쓰면 잘못된 트리를 조용히 만든다. 그래서 이미지 목록의 출처를 ISO 가 아니라 설치 소스로 정했다(D-1).

Windows 요청은 리눅스 전용 경로를 자연히 비켜간다

OsVolumeTargets.describe · SettingSaveRequest · SettingController 의 리눅스 분기는 모두 instanceof LinuxInstallationRequest 로 걸러진다. 식별 전용 타입이 지나던 자리를 새 Windows 타입이 그대로 지나므로 이 세 곳은 변경이 없다. 이것이 D-3(타입 퇴역)의 파급을 작게 유지해 주는 조건이다.

§2. 요구사항 (확정) + 비목표

아래 일곱 항목은 토론 1호 §8 의 권장안을 사용자가 2026-09-02 에 "Q3 제외 전부 권장안" 으로 확정한 결과다. Q3(디스크 선택 계약)만 보류되어 E4-1-a-6 으로 넘어갔다.

  1. R1 계열 실체화 — provisioning.setting.enums.OSFamily.WINDOWS 를 만들고 해석기에 등록한다. Windows 정의서는 WindowsInstallationRequest(osMetadataId · isoId · imageName) 로 저장된다.
  2. R2 설치 이미지는 타이핑하지 않는다 — 에디션은 설치 소스의 sources/install.wim XML 에서 자동 채집한 목록에서 고른다. 토론 D9 층 B 의 "이름 타이핑 없음" 약속을 실현한다.
  3. R3 정의서 OS 섹션 재확장 = 설치 이미지 + Administrator 비밀번호(필수) CP1 정정 — 토론 Q8 은 "에디션만" 이었으나, CP1 승인 시 사용자가 Administrator 비밀번호를 전역 운영 설정(F 층)에서 정의서(D 층)로 옮기도록 정정했다(2026-09-02). 시간대 · 제품 키 · 공유 접속 정보(UNC · 계정 · 비밀번호)는 그대로 전역 운영 설정(Q7 = 환경변수)이고 화면에는 "설정됨 / 미설정" 만 보인다. 자세한 근거는 D-11 에 적었다.
  4. R4 설치 소스 추출은 운영 절차(Q9 · 런북 §14) — 앱은 경로만 알며 ISO 를 풀지 않는다.
  5. R5 차단 판정 SSOT — 리눅스 OS 차단(기존)과 설치 소스 미준비 차단(신설)을 한 정책 메서드가 판정해 옵션 disabled(화면)와 서버 가드가 같은 문장을 쓴다.
  6. R6 대시보드 영역 — 시스템 자산 대시보드에 "Windows 설치 소스" 영역을 추가한다. 파일 3 종 존재 · 이미지 목록 · 운영 설정 상태를 보이되 값은 노출하지 않는다.
  7. R7 식별 전용 타입 퇴역 — R11 이 넣은 PlannedOSInstallationRequest 를 걷고 기존 저장본을 치환한다(D-3).

§4. 도메인 모델 (SSOT)

새 기능은 com.example.serverprovision.execution.wininstall 한 패키지에 모으고(D-9), 정의서 쪽은 기존 provisioning.setting 안에서 계열 하나가 늘어나는 형태로 확장한다. VO = Value Object(원시값 대신 도메인 의미를 담는 타입), SPI = Service Provider Interface(도메인이 구현해 끼우는 확장점), SSOT = Single Source of Truth(단일 진실 출처)를 뜻한다.

요청 모델 — 설치 이미지 + Administrator 비밀번호 CP1 정정

Windows 정의서 단계는 축 둘을 받는다. 설치 이미지는 목록에서 고르고(R2), Administrator 비밀번호는 정의서에서 입력한다(R3 정정). 비밀번호를 중첩 record 로 감싸는 것은 기존 RHEL 의 RootPasswordRequest 관용구를 그대로 따른 것이다 — 다만 isPasswordEncrypted 는 두지 않는다. Windows 응답 파일은 평문 대신 Base64 로 인코딩된 값을 요구하고, 그 인코딩은 E4-1-a-3 의 렌더 단계가 서버에서 수행하므로 사용자가 형식을 고를 이유가 없다.

public class WindowsInstallationRequest extends OSInstallationRequest {
    @NotNull(message = "설치 이미지를 선택해야 합니다.")
    private final WindowsImageName imageName;

    @NotNull(message = "Administrator 비밀번호를 입력해야 합니다.")
    @Valid
    private final WindowsAdministratorPasswordRequest administratorPassword;
}

public record WindowsAdministratorPasswordRequest(String password, boolean keepExistingPassword) {

    @Size(max = 127)
    @Pattern(regexp = "^[\x21-\x7E]+$",
             message = "비밀번호에는 공백 · 제어문자를 쓸 수 없습니다.")
    public String password() { return password; }

    @AssertTrue(message = "Administrator 비밀번호를 입력하거나 기존 비밀번호 유지를 선택해야 합니다.")
    public boolean isEitherProvidedOrRetained() {
        return keepExistingPassword || (password != null && !password.isBlank());
    }
}

비밀값 다형 훅 두 개 (조건분기 대신 다형성)

비밀번호가 정의서에 들어오면 두 자리에서 "타입마다 다른 처리" 가 필요해진다 — 수정 폼에 내려보낼 때 값을 지우는 일과, 수정 저장에서 기존 값을 이어받는 일이다. 여기에 instanceof 분기를 늘리지 않고 AbstractProcessRequest 에 default 메서드 둘을 두어 각 타입이 자기 몫만 override 한다.

훅기본LinuxWindows
withoutSecrets()this 기존 withPatchedPasswords 로 위임 password null · keep true 사본

withoutSecrets() 는 수정 폼 pre-fill 용이다. 지금 SettingController.withoutPasswords 안에 있는 사용자 비밀번호 패치 로직이 LinuxInstallationRequest 로 옮겨 가고, 컨트롤러의 instanceof LinuxInstallationRequest 분기는 process.withoutSecrets() 호출 한 줄로 줄어든다. Windows 사본은 password 를 null 로, keepExistingPassword 를 true 로 만들어 내려보내므로 폼은 "기존 비밀번호 유지" 가 켜진 상태로 열린다.

withSecretsRetainedFrom(AbstractProcessRequest existing) 는 수정 저장 병합용이다. JpaSettingCommandService.update 가 attachProcesses 를 부르기 전에 같은 processType() 의 기존 payload 를 찾아 이 메서드에 넘긴다. Windows 구현은 keepExistingPassword 가 true 일 때 기존 비밀번호를 복사하고 플래그를 false 로 정규화한다 — 저장본에는 항상 실값이 들어가고 플래그는 요청 전용으로 남는다. 기존 payload 에 비밀번호가 없으면(구 저장본이거나 단계 타입이 바뀐 경우) RetainedPasswordUnavailableException(400 · administratorPassword)을 던진다. 정상 UX 에서는 기존 값이 있을 때만 "기존 유지" 체크가 보이므로, 이 예외는 direct POST 안전망이다.

setting-form.js 는 onInstallOsChange 에서 선택 옵션의 data-os-family 를 읽어 oiWindowsImageWrap.hidden = family !== 'WINDOWS' 로 토글하고, payload 빌더의 OS_INSTALLATION 을 {type, osFamily, osMetadataId, isoId, imageName, administratorPassword} 으로 만든다 (WINDOWS 가 아니면 뒤의 두 필드를 싣지 않는다). precheck 는 WINDOWS 인데 imageName 이 없으면 "설치 이미지를 선택해야 합니다." 를, 비밀번호가 비었는데 "기존 비밀번호 유지" 도 꺼져 있으면 "Administrator 비밀번호를 입력해야 합니다." 를 paintFieldError 로 그리고 전송하지 않는다. prefill 은 저장된 proc.imageName 을 select 에 세팅하되 옵션에 없으면 placeholder 를 유지하고 "저장된 설치 이미지가 현재 설치 소스에 없습니다: <name>. 다시 선택하십시오." 를 보인다. 비밀번호는 서버가 withoutSecrets() 로 이미 지워 보내므로 pre-fill JSON 에 값이 없고, keepExistingPassword: true 만 실려 온다 — 폼 JS 는 그 플래그로 체크박스를 켜고 입력칸을 잠근다.

상세 카드는 setting-process-cards.html 의 OS_INSTALLATION 분기에서 null 계열 갈래를 걷고 th:switch 에 WINDOWS case 를 더해 새 fragment fragments/provisioning/setting/os-installation/detail-windows.html 을 부른다. 행은 대상 OS · 설치 ISO · 설치 이미지(NAME 을 n-mono 로, 아래 줄에 DISPLAYNAME) · 상태 배지 · Administrator 비밀번호 행이며, 비밀번호 행은 "설정됨"(n-badge-green) 또는 "미설정"(n-badge-orange — 구 저장본에서만 나오고 "정의서를 수정해 비밀번호를 입력하십시오." 를 덧붙인다) 배지만 보인다. 값은 어떤 경우에도 표시하지 않는다. 배지가 정상이 아닐 때 다음 행동 문장을 덧붙인다. 문구는 서술 합니다체 · 명령 하십시오체 · 배지는 명사형이며 코드 이름을 노출하지 않는다(new-user-copy.md).

-- 치환 전 대상 확인 (Windows OS 의 식별 전용 저장본만이어야 한다)
SELECT sp.id, sd.name, om.os_name FROM setting_process sp
  JOIN setting_definition sd ON sd.id = sp.setting_definition_id
  JOIN os_metadata om ON om.id = JSON_VALUE(sp.payload_json, '$.osMetadataId')

UPDATE setting_process sp JOIN os_metadata om ON om.id = JSON_VALUE(sp.payload_json, '$.osMetadataId')
   SET sp.payload_json = JSON_SET(sp.payload_json, '$.osFamily', 'WINDOWS')
 WHERE sp.process_type = 'OS_INSTALLATION' AND JSON_VALUE(sp.payload_json, '$.osFamily') IS NULL
   AND om.os_name IN ('WINDOWS', 'WINDOWS_SERVER');

UPDATE assigned_process_snapshot aps JOIN os_metadata om ON om.id = JSON_VALUE(aps.payload_json, '$.osMetadataId')
   SET aps.payload_json = JSON_SET(aps.payload_json, '$.osFamily', 'WINDOWS')

   AND om.os_name IN ('WINDOWS', 'WINDOWS_SERVER');

JSON_VALUE 는 키가 없을 때와 JSON null 일 때 모두 NULL 을 돌려주므로 술어 하나로 둘을 함께 잡는다. 치환된 행은 imageName 이 없어 화면에 "설치 이미지 미지정" 으로 드러나고, 사용자가 수정 · 저장하면 정상 저장본이 된다. 적용 순서는 코드 배포보다 먼저다 — 치환 전 코드는 null 계열을 해석하지만 치환 후 코드는 null 계열을 400 으로 거절하므로, 순서가 뒤집히면 상세 페이지가 열리지 않는다. 샌드박스 DB(CP5)와 실 DB(배포 시) 각각 한 번씩 적용한다.

  • 성공 2xx — 저장 201 에서 captor 로 WindowsInstallationRequest 타입과 imageName 값을 확인한다. 폼 · 상세 · 대시보드 GET 200 은 뷰 테스트 8 건이 함께 본다.
  • 400 — 일곱 갈래 전부 트리거한다. ① Bean Validation 의 imageName 누락 ② 해석기의 osFamily 판별자 부재(구 형식 본문) ③ InvalidWindowsImageSelectionException ④ UnsupportedOsInstallTargetException(리눅스 위조) ⑤ 같은 예외의 소스 미준비 갈래 ⑥ administratorPassword 누락(@NotNull)과 빈 값 · 공백 · 초과 길이(Layer A) ⑦ RetainedPasswordUnavailableException(유지 플래그인데 기존 값 없음). 필드 결속은 fieldErrors[imageName] · fieldErrors[osMetadataId] · fieldErrors[administratorPassword] 로 확인한다.
  • 404 — 해당 없음 이 슬라이스가 새로 만드는 조회 경로가 없다. OS · ISO 의 미존재는 1 단 검사기가 기존대로 처리하며 그 테스트는 그대로 둔다.
  • 409 — 해당 없음 신설 ConflictException 하위가 없다. 설치 소스는 lifecycle 자원이 아니라 중복 · 상태 충돌 개념이 없다.
  • 500 — 해당 없음 파일 읽기 실패는 예외가 아니라 UNREADABLE 판정으로 흡수되고 (WimFormatException 은 HTTP 경계에 닿지 않는다), 요청 해석 실패는 전부 400 으로 수렴한다.
  • 회귀 — 전체 테스트 green. 기준은 착수 시점 dev 의 테스트 수를 유지한 채 위 59 가 더해진 값이며, 삭제되는 식별 전용 시나리오 2 건은 빠진다.
신규 예외마다 통합 시나리오가 붙는다 — InvalidWindowsImageSelectionException 은 SettingRestControllerSaveFlowTest 의 400 시나리오가, UnsupportedOsInstallTargetException(개명)은 리눅스 위조 · 소스 미준비 두 갈래가, RetainedPasswordUnavailableException 은 "기존 유지" 플래그를 든 채 기존 값이 없는 수정 저장이 실제로 발생시킨다.

UnsupportedOsInstallTargetException 은 기존 UnsupportedPlannedInstallTargetException 의 개명이다 — "설치 예정 기록" 이라는 어휘가 D-3 으로 사라지므로 클래스 이름도 함께 정리한다. InvalidWindowsImageSelectionException 은 팩토리 notInSource(WindowsImageName) 를 두고 메시지는 "현재 Windows 설치 소스에 없는 설치 이미지입니다: <name>. 설치 이미지를 다시 선택하십시오." 로 한다.

RetainedPasswordUnavailableException 은 수정 저장 병합에서만 나온다 — "기존 비밀번호 유지" 플래그를 받았는데 같은 단계 타입의 기존 payload 에 비밀번호가 없는 경우다(구 저장본이거나 단계 타입이 바뀐 경우). 메시지는 "기존 Administrator 비밀번호가 없어 유지할 수 없습니다. 비밀번호를 새로 입력하십시오." 로 한다.

셋 다 FieldBoundBadRequestException 하위라 advice 에 개별 등록할 필요가 없다 — 계층 탐색으로 흡수된다 (.claude/domain-conventions/new-exception.md §1~2). 정상 UX 에서는 옵션 disabled 와 폼 precheck, 그리고 "기존 유지" 체크박스를 기존 값이 있을 때만 보이는 규칙이 먼저 막으므로 이 세 400 은 direct POST · 낡은 저장본 · 소스 교체 경합 같은 비정상 경로의 안전망으로만 발동한다. 4xx 는 스택 없이 WARN 으로 남기는 기존 로그 정책을 그대로 따르며, 비밀번호 값은 로그에 실리지 않는다.

WimFormatException 은 catalog 안에서만 오간다. 헤더 · XML 이 어긋나면 이 예외가 던져지고 WindowsImageCatalog 가 그 자리에서 잡아 UNREADABLE 판정으로 바꾼다 — "조회는 실패하지 않는다" 는 SystemAssetArea.inspect 의 계약을 지키기 위한 구조다.

아래 열한 건이 이 슬라이스의 설계 결정이다. 각각 채택안과 함께 비채택 대안과 그 탈락 사유를 적었다. D-1 ~ D-10 은 CP1 승인 시점의 원안이고, D-11 은 그 자리에서 사용자가 낸 정정이다(2026-09-02).

D-1 설치 이미지 목록의 출처 = 설치 소스의 sources/install.wim XML

채택 — 공유 루트에 놓인 설치 소스를 앱이 직접 읽어 이미지 목록을 만든다. 대안 A "ISO 자원 등록 시 채집"(백그라운드 job · 새 테이블 · Windows 전용 PostCreationTaskStrategy)은 탈락했다 — 앱 계정에 loop mount 권한이 없고 bsdtar 가 UDF 를 읽지 못해(실측에서 항목 2 개만 보였다) 7z 의존과 4.8 GB 스트리밍 job 이 필요해지는데, 그 대가로 얻는 것(ISO 를 SSOT 로 삼기 · 다중 버전)은 MVP 범위에 없다. 대안 C "이름 타이핑" 도 탈락했다 — 오타가 setup 중단으로만 드러나 토론 D9 의 약속을 어긴다. 채택안은 setup.exe 가 실제로 읽는 실물을 읽으므로 거짓 양성이 없다. 버전이 여럿 필요해지면 ISO 별 하위 디렉토리 규약으로 확장한다(설정 하나 → 규약 하나).

D-2 저장값 = /IMAGE/NAME 문자열 (VO WindowsImageName)

채택 — setup 이 요구하는 값을 그대로 저장한다. 대안 index 는 빌드가 바뀌면 가리키는 이미지가 달라져 탈락했고, EDITIONID + INSTALLATIONTYPE 조합은 setup 에 넘기려면 다시 NAME 으로 조립해야 해서 탈락했다.

D-3 R11 식별 전용 타입 퇴역 + 저장본 치환

채택 — PlannedOSInstallationRequest 를 삭제하고 기존 저장본에 osFamily: "WINDOWS" 를 채워 넣는다. 대안 "legacy 타입 유지" 는 탈락했다 — 데이터가 dev 와 스테이징뿐이라 지금이 가장 싸고(실배포 전), E3.5-7-a 가 이미 JSON 치환 선례를 남겼으며, 무엇보다 "설치 예정 기록" 이라는 어휘가 죽은 뒤에도 코드와 화면에 분기가 남는다. 치환 후 남는 상태는 imageName 없는 Windows 저장본이고, 화면은 "설치 이미지 미지정" 으로, E4-1-a-3 의 준비도는 BLOCKED 로 그것을 드러낸다. 저장 데이터를 건드리는 결정이므로 CP1 승인 항목으로 명시한다(OQ-1).

D-4 UI 차단과 서버 가드의 SSOT = OsInstallTargetPolicy.blockReason(OSName, boolean)

채택 — 의존성 0 의 정적 판정을 유지한 채 축 하나를 늘린다(TypedNameGuard 관용구). 소비처는 셋이다 — 옵션 조립 toOSOption · 계열 검사기 · 🎬 데모. 대안 "검사기 안에 if 두 줄" 은 탈락했다 — 옵션 tooltip 문장과 서버 거절 문장이 갈라져 같은 상황에 다른 말을 하게 된다.

D-5 운영 설정 = 항상 존재하는 @ConfigurationProperties record + configured()

채택 — BmcStandardSettings 와 같은 형태다. 대안 @ConditionalOnProperty 로 빈 자체를 없애는 방식 (진단 자산 · TFTP · dhcpd 선례)은 탈락했다 — 그 선례들은 실행기 빈을 통째로 빼야 해서 필요했지만 여기는 뺄 빈이 없고, 오히려 "미설정" 상태를 화면에 보여야 한다. 반쪽 설정(루트만 있고 비밀번호가 없는 상태)은 기동을 막지 않고 대시보드에 미설정으로 드러난다 — 대안 기동 시 fail-fast 는 운영 마찰이 크고, 실행을 막는 일은 E4-1-a-3 의 준비도 판정이 맡으므로 탈락했다. 환경변수 이름은 ${ENV:} 자리표시자로 application.properties 에 명시한다.

D-6 제품 키 = EDITIONID 별 고정 2 키 · 코드 기본값 없음

채택 — serverStandard · serverDatacenter 두 자리를 고정한다. 대안 "키 하나" 는 탈락했다 — Datacenter 이미지에 Standard 키가 조용히 들어가 setup 이 키 검증에서 멈춘다. 대안 "자유 맵" 은 환경변수 relaxed binding 이 키를 소문자로 만들고 열거도 되지 않아 탈락했다. 대안 "GVLK 를 코드 기본값으로" 는 값이 공개라 허용은 되지만 라이선스 경로가 사용자 몫이므로(토론 Q11) 운영자 입력으로 둔다. 대시보드는 소스에 실제로 있는 에디션의 키만 chip 으로 보인다.

D-7 시간대 기본값 Korea Standard Time 을 코드에 둔다

채택 — 공개된 Windows 시간대 식별자이고, BMC_STANDARD_TIMEZONE=Asia/Seoul 선례와 성격이 같다. 비밀이 아니므로 기본값을 두어 운영자가 채워야 할 항목을 하나 줄인다. 로케일은 설정 항목으로 두지 않는다 — install.wim 의 언어 값에서 E4-1-a-3 이 파생시킨다(OQ-2 로 확인받는다).

D-8 대시보드 영역은 관측 전용 (봉인 미지원)

채택 — supportsSeal() 을 false 로 두고 봉인 URL 을 노출하지 않는다(DhcpdAssetArea 선례). 봉인은 파일 봉인 기반 영역에만 의미가 있고, 설치 소스는 운영 절차가 통째로 교체하는 자산이다. wimboot 는 성격이 다른 별개 자산이라 E4-1-a-3 에서 진단 이미지처럼 등록한다.

D-9 패키지 = execution.wininstall (config · catalog · vo · spi)

채택 — 한 기능을 한 feature 패키지에 모은다(pxeinfra 선례). 대안 provisioning.setting.service.reference.os 아래 두기는 탈락했다 — E4-1-a-3 의 실행기(execution 영역)가 이것을 소비하므로 의존 방향이 역전된다. 대안 execution.config 와 execution.asset.area 로 분산하기도 탈락했다 — 한 기능이 세 곳으로 흩어진다.

D-10 상세 카드의 드리프트 배지(WindowsImagePresence)를 이 슬라이스에 포함

채택 — 조회 시점에 판정해 배지로 드러낸다. 사용자가 말한 유지보수성 우려의 실체가 "소스가 바뀌었는데 정의서는 그것을 모른다" 이므로, 저장 시점이 아니라 보는 시점에 답을 준다. 비용은 references 맵 항목 하나뿐이다. 대안 "다음 슬라이스로 미루기" 는 E4-1-a-3 의 준비도 BLOCKED 가 실행 직전에야 알려 주므로 정의서 화면에서 미리 알 방법이 없어져 탈락했다.

D-11 Administrator 비밀번호 = 정의서 필수 입력 + 다형 훅 두 개 CP1 정정

채택 — 비밀번호를 전역 운영 설정(F 층)에서 정의서(D 층)로 옮기고, 수정 흐름을 위해 withoutSecrets() · withSecretsRetainedFrom(existing) 두 훅을 AbstractProcessRequest 에 둔다. 대안 ① 전역 환경변수(이 plan 의 원안)는 사용자 정정으로 탈락했다 — 비밀번호는 게스트마다 다를 수 있는 값이고, 그것을 정하는 사람은 서버를 준비하는 운영자가 아니라 정의서 작성자다. 시간대 · 제품 키 · 공유 접속 정보는 환경 전체에 하나면 충분해 F 층에 남지만, 비밀번호는 그 성격이 다르다. 대안 ② 병합 없이 매 수정마다 재입력하게 하는 방식도 탈락했다 — 재입력을 잊으면 @NotNull 이 400 을 내어 UX 가 나쁘고, 그렇다고 병합 없이 keepExistingPassword 플래그만 받으면 저장본의 비밀번호가 조용히 사라진다. 그래서 플래그와 병합을 한 벌로 도입한다.

발견 — 현행 리눅스 계열의 잠재 결함 : RHEL · Ubuntu 요청도 keepExistingPassword 플래그를 이미 받지만, 저장 시 서버가 병합하지 않는다. 그래서 수정 저장을 하면 root 비밀번호와 사용자 비밀번호가 null 로 사라진다. E4-L(리눅스 설치 실행)이 아직 없어 소비처가 없으므로 지금은 드러나지 않을 뿐이다. 이 슬라이스의 범위 밖이라 고치지 않고 HF 로 적립한다(§11) — 이번에 만드는 withSecretsRetainedFrom 훅이 그 수정의 자리를 미리 마련해 둔다.

주의

  • 치환 SQL 은 코드 배포보다 먼저 적용한다. 순서가 뒤집히면 기존 Windows 단계의 상세 페이지가 열리지 않는다.
  • 앵커 dev 에 미커밋 파일 3 건(실측 보고서 · 토론 문서 · 런북 §14)이 있다 — 브랜치 전환 전에 커밋 지시가 필요하다.
  • 대시보드 영역의 정렬은 빈 주입 순서를 따르고 현재 @Order 가 없다. 새 영역이 어디에 끼는지 CP5 에서 확인하고, 필요하면 @Order 부여를 CP4 에서 결정한다.
  • RHEL · DEBIAN 요청이 Windows OS 를 가리키는 위조는 지금도 검사하지 않는다 — 이 슬라이스 범위 밖이며 S 계열로 적립한다.
  • 비밀값 비기재 원칙을 유지한다. 픽스처로 배포하는 XML 은 이미지 메타만 담는다.
  • ReferenceNamesResponse 는 record 라 필드를 더하면 생성자 호출부를 전수 갱신해야 한다(테스트 포함).
  • RHEL · Ubuntu 의 keepExistingPassword 가 저장 시 병합되지 않는 잠재 결함(D-11 발견)은 이번에 고치지 않는다 — HF 로 적립하고 §11 에 남긴다.
  • SettingController.withoutPasswords 의 로직이 LinuxInstallationRequest 로 이동하므로, 그 컨트롤러를 거치는 기존 리눅스 수정 폼 회귀를 CP5 A7 에서 함께 본다.
  • 기존 PlannedInstallTargetPolicy.LINUX_BLOCK_REASON 문장은 "설치 예정으로 기록할 수 있습니다" 였다. D-3 으로 그 어휘가 사라지므로 "설치할 수 있습니다" 로 함께 교체한다 — 문구 변경이 있는 지점이니 CP5 에서 눈으로 확인한다.
