§1. 현재 상태 (진단)

ProvisioningPhase.RAID_CONFIGURATION 은 U4-1-1 v2 가 신설했지만 실행기가 없다. 그래서 이 phase 에 커서가 놓인 게스트는 dispatch 의 6행 HOLD 로 떨어져 "not implemented yet" iPXE 대기 스크립트를 받는다. 게스트 주도 집행의 기반은 이미 다 있으므로, 이 슬라이스가 채워야 할 것은 실행기 하나와 그 실행기가 내리는 지시가 게스트에게 닿는 경로 둘이다.

핵심 진단 — 실행기만 등록해서는 루프가 풀리지 않는다.
RAID phase 커서를 가진 게스트가 진단 리눅스로 부팅해 체크인하면, 현행 판정은 "커서가 진단 phase 를 넘어섰다" 는 이유 하나로 REBOOT 를 돌려준다. 게스트는 다시 부팅하고 다시 체크인해 다시 REBOOT 를 받는다 — 부팅 · 체크인 · 재부팅이 끝나지 않는다. 0-3 결정 D-2 가 이 정정(지시 판정의 실행기 다형화)을 확정했고, 이번 슬라이스의 R1 이 그 이행이다.

§2. 요구사항 (확정) + 비목표
  1. R1 지시 다형화 (D-2) — ProvisioningPhaseExecutor.directiveFor(server, progress) 기본 메서드를 신설한다(기본값 REBOOT). AgentReportService 에는 셋만 남는다: 종단이면 REBOOT · 커서 phase 실행기가 있으면 위임 · 미등록 phase 면 REBOOT. DiagnoseLinuxExecutor 가 현행 규칙(미수집이면 COLLECT · 그 외 WAIT)을 override 로 옮겨받는다 — 동작은 바뀌지 않으며 기존 테스트가 그 증인이다.
  2. R2 RaidConfigurationExecutor 신설 — phase() 는 RAID_CONFIGURATION, bootScript 는 진단 Alpine 체인로드(R3 공용 빌더), directiveFor 는 이 phase 의 인벤토리 성공 행이 원장에 없으면 신규 지시 RAID_INVENTORY · 있으면 WAIT, onStepClosed 는 인벤토리 보고 소비(R5 · R6).
  3. R3 부팅 스크립트 공용화 — DiagnoseLinuxExecutor 안의 체인로드 text block 을 공용 빌더(예: execution.engine.boot.DiagnoseLinuxBootScript static 팩토리 — 토큰 · base URL 인자)로 추출해 두 실행기가 함께 쓴다. "갈라지는 시점에 분리" 의 그 시점이 지금이다.
  4. R4 에이전트 인벤토리 수집 — agent.sh 가 RAID_INVENTORY 지시를 처리한다. lspci -n 으로 칩을 판별(1000:0097 → sas3ircu / 1000:005d → storcli64 우선 · storcli(alias) 폴백 탐색)하고 원문을 채집해(storcli: /c0 show all J · /c0/eall/sall show all J · /c0/vall show all J / sas3ircu: 0 display) RAID_INVENTORY_COLLECTING step 의 statusMeta 로 통째 보고한다 — 진단 수집과 같은 "원문 보고 · 서버 파싱" 계약이다. 도구가 없거나 실행이 실패하면 FAILED + 사유 문자열. 두 바이너리는 build-assets.sh 의 apkovl 에 동봉한다(D-11 — 실행 여부는 CP5 실측).
  5. R5 서버 파서 — RaidInventoryParser(신설 패키지 execution.engine.raid)가 storcli JSON(tools.jackson)과 sas3ircu 텍스트를 정규화 Value Object 로 옮긴다. 관용 원칙 — 모르는 필드는 무시하고, 해석 불가한 항목은 적재를 생략하며, 원문은 원장에 보존한다. 파서 픽스처는 실측 원문이다(CP2 에서 src/test/resources/ 배치).
  6. R6 카드 대조 + 적재 + 화면 — 소비 훅이 ① 파싱 ② 활성 할당의 RAID payload 를 SPI 로 읽어(R7) raidCardId 카드의 pciSubsystemId 와 감지 Subsystem 을 대조 — 불일치면 원장 FAILED CARD_MISMATCH + markFailed, 카드 미지정(null)이면 대조 생략 ③ 정합이면 인벤토리 JSON 적재 ④ 게스트 상세에 "RAID 인벤토리" 섹션(카드 한 줄 + 물리 디스크 표 + 기존 볼륨 표) 렌더. 카드를 지정했는데 lspci 에 없으면 CARD_NOT_DETECTED, 도구 실패는 TOOL_MISSING — 사유 코드는 E3 SettingLedger 관례를 따른 RaidLedger 최소본으로 표현한다.
  7. R7 SPI — RaidConfigurationResolutionProvider 를 execution 이 선언하고 provisioning 이 구현한다(BiosSettingResolutionProviderImpl 과 같은 자리). 활성 스냅샷에서 RaidConfigurationTarget 을 Optional 로 공급한다. 규칙 목록까지 넘기는 확장은 E3.5-2 다.
  8. R8 step 3분할 DDL (D-10) — ProvisioningPhaseStep 의 RAID_CONFIGURATION 을 RAID_INVENTORY_COLLECTING · RAID_APPLYING · RAID_VERIFYING 으로 교체한다(§8 D-1). DDL 은 ENUM 값 3 추가 + RAID_CONFIGURATION 제거(적재 행 0 확인 후)이며, 대상은 U4-1-1 DDL 이 만든 step ENUM 컬럼이다.
비 목표 :
  • 계획 산출(매칭) — E3.5-2. 볼륨 생성 · 멱등 · raid_volume 표 — E3.5-3. E4 인계 · 정의서 "기존 구성" 축 — E3.5-4.
  • 인벤토리 성공 후 phase 전진 없음 — 계획 단계가 아직 없으므로 게스트는 WAIT 로 명시 대기한다. HOLD 보다 한 걸음 나아간 상태이며, 화면이 그 사실을 보인다.
  • IR 볼륨 이름 규약(영숫자 제약) 결정 — E3.5-3 plan. 이 슬라이스는 이름을 원문 그대로 보여줄 뿐이다.
  • Redfish — 사전 조사에서 종결.
🎬 미리보기 — RAID phase 한 바퀴 · 인벤토리까지

왼쪽은 게스트 · 에이전트, 오른쪽은 프로비저닝 서버 다. 서버 구성 프리셋과 정의서의 카드 지정을 바꿔 가며 부팅 → 체크인 → 인벤토리 보고 를 눌러 보면, 서버가 어떤 지시를 내리고 무엇을 근거로 적재하거나 거절하는지가 그대로 드러난다. 처음이라면 아래 원클릭 시나리오 5 개를 순서대로 눌러 보는 편이 빠르다 — 세팅과 안내 배너가 함께 붙는다. 툴바를 바꾸면 진행 중인 한 바퀴는 초기화된다.

판정 JS 는 서버 도메인 규칙과 1:1 이다 — demoDirective() 가 AgentReportService.directiveFor 의 위임을, demoConsume() 이 RaidConfigurationExecutor.onStepClosed 의 카드 대조를 같은 순서로 재현한다. 버튼의 disabled 사유(마우스를 올리면 tooltip)도 같은 판정에서 나온다.

D-3지시 payload이번엔 값만 (RAID_INVENTORY)계획 전달용 GET 엔드포인트를 지금 미리 신설
D-4파서 위치서버 RaidInventoryParser — 원문 보고 · 서버 파싱에이전트가 정규화 JSON 을 조립해 보고

D-1 — 커서 pre-position(PhaseCursorAdvancer 의 phase 진입 step)이 첫 step 을 가리키므로 진입 step 은 RAID_INVENTORY_COLLECTING 이어야 한다. RAID_CONFIGURATION 상수를 남기면 "phase 이름과 같은 유령 step" 이 화면과 원장에 계속 보인다. 실 DB 와 샌드박스 모두 이 step 의 적재 행이 0 이라(그 phase 에 도달한 게스트가 없고 DDL 로 값만 존재) 교체가 안전하며, DDL 은 값 추가 후 제거 순서로 적는다.

D-2 — 상세 화면과 후속 슬라이스(계획 산출이 최신 인벤토리를 입력으로 받는다)가 조회할 자리가 필요하다. 원장 statusMeta 는 원문 보존용이지 조회 모델이 아니다. hardware_spec 에 합치면 갱신 주기가 얽힌다 — 진단 수집은 등록 시점, RAID 인벤토리는 phase 진입 시점이다.

D-3 — "미리 분리 금지" 를 그대로 적용했다. payload 가 필요한 첫 실물은 E3.5-2 의 계획 전달이므로 그때 만든다. D-4 — 진단 수집과 같은 관례이고, 파서를 서버에 두면 실측 원문 픽스처로 단위 테스트가 된다. D-5 — 게이트(커서 phase 검사) · 멱등(중복 close 는 no-op) · S7 신호가 전부 기존 경로에 이미 있다.

주의

에이전트가 채집한 원문(수십 KB)이 statusMeta 문자열 컬럼에 실린다. 진단 수집과 같은 계약이므로 새 설계는 필요 없지만, 크기 상한은 CP5 에서 실측 확인한다. provision.execution 계열 신규 설정은 없다.
