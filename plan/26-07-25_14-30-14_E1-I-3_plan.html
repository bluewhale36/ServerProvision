§2. 요구사항 (확정 후보) + 비목표 + 분해 제안

요구사항

  1. 대시보드 다중 자원화 — 인프라 영역마다 자기 자산과 무결성 모델을 등록하는 확장점을 두고, 대시보드는 영역과 카테고리별로 집계한다. 새 영역 추가 비용은 구현체 1개이며 기존 enum 편집은 필요 없다.
  2. 무결성 이질성 수용 — 정적 파일형(봉인, 해시 드리프트)과 구성 파일형(존재, 문법, 서비스 상태)을 같은 대시보드에 담되, 집계 코드에는 영역별 분기를 만들지 않는다.
  3. TFTP 자산 등록 — ipxe.efi 를 슬롯 1개로 등록하고 읽기와 봉인만 제공한다. 갱신은 파일 복사 후 재봉인으로 완결된다.
  4. PXE 인프라 관측 — dhcpd 조각 파일 존재와 dhcpd -t 문법 결과, systemctl is-active dhcpd 서비스 상태, dhcpd.leases 임대 목록을 화면에 표시한다.
  5. dhcpd 구성 조각 반영 — 폼 입력을 조각 파일로 렌더하고, dhcpd -t 게이트를 통과할 때만 원자 교체하며, 재기동 후 활성 확인에 실패하면 이전 조각으로 자동 복원한다.
  6. 특권 명령 경계 1개 — 외부 명령은 SystemCommandRunner 포트와 AllowedCommand enum 을 통해서만 실행한다. 절대 경로 고정, 타임아웃 강제, sudoers 라인 생성의 근거를 동일 enum 이 갖는다.
  7. URL 이전 — 통합 대시보드는 /system/asset 으로 신설하고 구 대시보드는 302 로 넘긴다. 상세, 교체, 롤백은 진단 경로에 잔류한다(Q7).
비 목표 :
  • OMAPI 예약 — 이번 범위에서 제외를 권고한다(Q2). 고정 IP 예약이 실제 운영 요구로 확인되면 host 블록 선언형을 먼저 검토한다.
  • boot.ipxe 와 kickstart 의 동적 생성 — 각각 E1-0b 와 E4 소관으로 이미 로드맵에 들어 있다.
  • 이미 관리되는 자원(OS ISO, BIOS, BMC, Subprogram) — reconciliation 소관이므로 통합 대시보드는 중복 관리하지 않고 링크만 둔다.
  • ipxe.efi 의 UI 교체와 롤백 — 활성화 확장점 합의를 지키기 위해 읽기와 봉인 전용으로 둔다(Q4, §8).
  • 활성화 골격의 확장점 추출, verify() 5중 복제 회수, 패키지 재편 — 전부 R* 이연(§8 의 R* 이월 6항목).
  • 조작 감사 이력 테이블과 슬롯 메타데이터의 DB 일반화 — 이번 작업량 0. 근거와 도입 트리거는 §8.

안내용판정
안 1단일 슬라이스 (쪼개지 않음)탈락 CP5 전체가 실 서버에 묶인다. 진단 자산 테스트가 즉시 검증해 줄 수 있는 리팩터까지 미병합으로 장기 체류하며, 오래 묶일수록 후속 코드와의 충돌 비용이 커진다

§4. 도메인 모델 (SSOT)

확장점 — SystemAssetArea (Service Provider Interface, 도메인이 구현해 끼우는 확장점)

계약은 읽기(현황 보고)와 봉인이며 쓰기(교체, 롤백)는 담지 않는다. 쓰기 계약을 지금 만들지 않는 것이 잘못된 모양을 굳히지 않는 길이고, 활성화 확장점 추출을 R* 로 미룬 합의와도 어긋나지 않는다(§8).

public interface SystemAssetArea {

    /** 라우팅 키. URL 세그먼트이자 표시 순서의 식별자. 예: DIAGNOSTIC, TFTP, PXE_DHCPD */

    String displayName();

    AreaAvailability availability();

    List<SystemAssetSlot> slots();

    /** 슬롯 단건 조회. 없으면 empty — 404 판정은 호출자가 한다. */
    Optional<SystemAssetSlot> findSlot(String slotKey);

    /** 슬롯의 현재 상태 판정. 판정 모델의 이질성이 이 한 지점으로 흡수된다. */
    AssetCondition inspect(SystemAssetSlot slot);

    /** 영역 헤더에 함께 노출할 컨텍스트 항목(서비스 상태, 활성 임대 건수 등). 최대 3개. */
    default List<AssetContextItem> context() { return List.of(); }

    /** 봉인 지원 여부. UI 의 버튼 disabled 와 서버 가드가 이 판정 하나를 공유한다. */
    default boolean supportsSeal() { return false; }

    /** 봉인 미지원 영역이 호출되면 409 로 거절. 지원 영역만 재정의한다. */
    default SealResult seal() {
        throw new SystemAssetSealNotSupportedException(areaKey());
    }

    /** 영역 고유 관리 화면 경로. 공용 층은 도메인 페이지 경로를 모른다. */
    default Optional<String> manageHref() { return Optional.empty(); }
}

세 가지 설계 규약은 기존 선례를 그대로 따른다. 첫째, 능력 선언은 boolean default 로 두고 미지원 구현은 default throw 로 안전망을 만든다 (MarkableTrashOperator.supportsTrashTtlExtension() 선례). 둘째, 화면 이동 경로는 공용 층이 아니라 도메인 구현이 조립한다 (OrphanRecoverySpi 가 redirect URL 을 도메인에 맡긴 선례). 셋째, 새 영역은 default 덕분에 최소 구현만으로 안전하게 합류한다.

무결성 이질성의 다형 — AssetCondition

정적 파일과 구성 파일은 정상의 정의가 다르다. 정적 파일은 봉인 시점의 해시와 현재 해시가 같아야 정상이지만, dhcpd 조각은 운영자가 정당하게 편집할 수 있어 해시 대조가 의미를 잃는다. 대신 파일이 있는지, 문법이 유효한지, 서비스가 살아 있는지를 본다. 이 차이를 집계 코드의 if 로 표현하면 영역이 늘 때마다 분기가 자란다. 그래서 판정 결과 타입 자체를 다형으로 둔다.

public sealed interface AssetCondition
        permits SealedFileCondition, ConfigFileCondition, ServiceCondition {

    /** 집계용 정상 여부. 대시보드는 이 한 줄만 쓴다. */
    boolean healthy();

    /** 표시 라벨. 예: 원본 유지 / 문법 오류 / 중지됨 */
    String displayLabel();

    /** 배지 색 키. 표시 문자열만 오가므로 뷰는 enum 을 모른다. */

조건분기 확장 금지를 어떻게 만족하는가 — 대시보드 집계 코드에는 영역 종류를 묻는 분기가 없다. 집계는 condition.healthy() 와 condition.displayLabel() 만 호출하고, 어떤 판정 모델이 그 값을 만들었는지 알지 못한다. 네 번째 영역(예: httpd)이 붙어도 집계 코드는 한 줄도 바뀌지 않고 새 AssetCondition 구현과 SystemAssetArea 구현만 추가된다. 뷰 계층도 안전하다. 기존 SystemAssetSlotResponse 가 enum 을 노출하지 않고 표시 문자열(statusLabel, badgeClass)만 담는 레코드라 DTO 변경 없이 다른 판정 모델이 들어온다.

  • 서브넷, 임대 범위, 라우터, DNS, 부트 서버 주소, pxeclients 분기를 렌더한다. 생성 파일 머리에는 직접 수정 금지 경고를 넣는다

빼는 것

  • OMAPI 예약(Q2) — 선행 조건(omapi-port 선언과 서비스 재기동)이 아직 없고, 고정 IP 예약이 지금 운영 요구인지 확인되지 않았다. ISC DHCP 는 수명 종료(EOL)라 결합을 얇게 유지한다
  • 메인 dhcpd.conf 전체 생성(Q3) — 운영자가 직접 편집하는 항목을 앱이 덮어쓸 위험이 있다
  • 임대 파일 쓰기 — 읽기 전용으로만 다룬다

운영자 책임으로 남는 항목은 셋이다. 메인 dhcpd.conf 에 include /etc/dhcp/dhcpd.d/managed.conf; 를 넣는 것, 기존 subnet 선언을 조각으로 이관해 중복 선언을 피하는 것, 그리고 sudoers 규칙 두 줄이다. 앱이 스스로 만들 수 없으므로 c 착수 시 구축 문서로 산출한다.

기존 합의는 "DiagnosticAssetActivationService 의 도메인 무관 골격 추출은 E1-I-3 이 끝난 뒤 단계 신설 없는 R* 로, 구현자가 둘 이상 실재할 때" 였다. 긴장은 이번 슬라이스가 두 번째 교체 대상을 만들 때 생긴다. 만들면 지금 추출하거나(합의 파기) 60행을 복붙하거나(중복 금지 불가침 파기) 둘 중 하나를 골라야 한다.

채택안은 두 번째 교체 대상을 만들지 않는 것이다. 근거는 셋이다.

  1. ipxe.efi 는 dnf install ipxe-bootimgs 가 설치한 파일의 복사본이라 갱신 주기가 패키지 업데이트에 묶여 있고, 갱신 절차는 복사 후 재봉인이다. 재봉인은 이미 만들 POST /system/asset/TFTP/seal 이 수행하므로 기능 손실이 없다. 업로드 폼이 없을 뿐 갱신 경로는 완결된다.
  2. c 의 조각 반영은 업로드 교체가 아니라 폼 입력에서 렌더, 검증 게이트, 재기동으로 이어지는 다른 파이프라인이다. 교체 가능 여부 가드나 버전 롤백 같은 활성화 계약을 구현하지 않으므로 활성화 확장점의 구현자가 되지 않는다.
  3. 결과적으로 활성화 구현자는 E1-I-3 종료 시점에도 1개다. 중복이 0이면 확장점을 뽑을 근거가 없고 합의가 그대로 유지된다.

겹치는 3단만 AtomicAssetSwap 부품으로 회수한다(§4). 부품은 확장점이 아니므로 R* 범위를 선점하지 않으며 오히려 R* 의 재료가 된다.

결정 2 — R* 로 넘기는 항목 6가지

  1. 활성화 코어의 골격 추출과 훅 4종(루트 공급, 슬롯 해석, history category, 재봉인 위임).
  2. HISTORY_CATEGORY 상수의 2중 복제 해소(활성화 서비스 46행, 버전 서비스 29행).
  3. DiagnosticAssetIntegrityService 와 DiagnosticSystemAssetArea 어댑터의 병합 — 아래 자기비판 2에서 지적한 이중 구조의 해소.
  4. execution/asset 하위 서브패키지 재편(diagnostic/ 이동) — 3번과 같은 커밋에서.
  5. verify() 판정 사다리 5중 복제의 global/marker 승격과 IntegrityStatusView 의 global 이동.
  6. 읽기 확장점(SystemAssetArea)과 새로 뽑을 쓰기 확장점의 정합 검토 — 두 계약의 결이 어긋나지 않게 함께 본다.

슬롯 메타데이터의 DB 화하지 않음슬롯 집합은 부트 스크립트와 커널 인자에 결합된 코드 계약이지 운영자가 런타임에 추가하는 데이터가 아니다. DB 로 옮기면 enum 과 테이블이 이중 SSOT 가 되고, 경로 허용 목록과 정합성 스윕과의 격리 관계를 다시 설계해야 한다슬롯 집합이 운영자 편집 대상이 되는 시점(예: 서브넷 다중화로 조각이 여러 개가 될 때)
보존 개수의 카테고리 분리하지 않음조각은 수 KB 라 208MB 자산과 같은 보존 개수를 써도 비용이 없다. 분리하려면 스키마 변경이 필요하고, 엔티티 주석이 이미 필요해지는 시점에 분리한다고 못박아 두었다영역별 보존 정책이 실제로 갈라지는 시점
조작 감사 이력 테이블하지 않음인증 주체가 없어 누가에 해당하는 열을 채울 수 없다. 기록 지점(활성화 코어와 특권 명령 러너)도 아직 흩어져 있어 지금 만들면 insert 를 여러 곳에 복붙하고 R* 가 다시 모으게 된다. 감사 대상 행위는 이번에 1종만 늘고 그 이력은 asset_version 행이 이미 답한다선결 조건은 인증 주체 도입, 시점은 활성화 확장점 R* 와 동시. 그때 write 지점이 한 곳으로 모여 @EventListener(커밋 후) 또는 AOP 로 분기 추가 없이 감사층을 얹을 수 있다

대신 이번에는 봉인, 조각 적용, 특권 명령 실행을 고정 접두([system-asset], [pxe-infra])의 구조화 로그로 남긴다. c 의 PxeNetworkConfig 가 반영 시각과 결과, 보관 버전 식별자를 갖고 있으므로 마지막 반영이 언제 어떤 결과였는지는 테이블 추가 없이 답해진다.

적대적 자기비판과 대응

비판 1

TFTP 를 읽기 전용으로 두면 두 번째 구현자가 관측만 하는 껍데기라 확장점의 모양이 검증되지 않는다.

대응 — 부분적으로 타당하다. 다만 이번 확장점의 계약은 애초에 읽기와 봉인이지 쓰기가 아니다. b 에서 dhcpd 영역이 세 번째 구현자로 붙어 읽기 계약이 3회 검증되고, 세 번째는 파일이 아닌 관측치까지 가진 이질 영역이라 계약의 스트레스 테스트로는 TFTP 교체보다 강하다. 잔여 위험 — R* 에서 쓰기 확장점을 설계할 때 읽기 확장점과 결이 어긋날 수 있어, R* 이월 6번에 정합 검토를 명시했다.

비판 2

어댑터로 기존 서비스를 감싸는 것은 일반화를 흉내 낸 이중 구조다.

대응 — 정당한 비판이다. 다만 어댑터는 표시 조립만 하는 20행대이고 진짜 로직은 부품으로 내려가 TFTP 와 실제로 공유된다. 중복은 회수되고 층만 남으며, 그 대가로 회귀 안전망 791행이 온전히 보존된다. 방치하면 영구 이중 구조가 되므로 R* 이월 3번에 병합을 필수로 적립하고 Notion 잔존 책임에 해소 시점을 적는다. 해소 시점을 적지 않은 임시 구조는 만들지 않는다.

비판 3

슬롯을 파일로 한정하려고 서비스 상태와 임대를 컨텍스트로 밀어낸 것은, 대시보드가 인프라 현황을 한눈에 보여주지 못한다는 뜻 아닌가.

대응 — 영역 헤더의 컨텍스트 항목이 배지를 가지므로 서비스 상태와 활성 임대 건수는 대시보드에서 바로 보인다. 어느 MAC 이 어느 IP 를 받았는지 같은 상세 목록만 영역 화면으로 간다. 대시보드는 상태, 상세는 액션이라는 기존 3분할 원칙과도 일치한다. 잔여 위험 — 컨텍스트 항목이 늘면 헤더가 비대해지므로 영역당 3개 상한을 표시 규약으로 못박는다.

비판 4

3분할은 슬라이스 인플레이션이다.

대응 — 분할축이 검증 Tier 경계와 일치하고, a 만이 기존 테스트를 안전망으로 쓸 수 있는 구간이다. 따라서 a 분리는 양보하지 않되 b 와 c 를 합치는 2분할은 차선으로 수용 가능하다(Q1).
