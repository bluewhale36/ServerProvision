§0. 요약
  • 최초 진단(INFORMATION_COLLECTING)에서 에이전트가 RAID 카드 뒤 물리 디스크 · 기존 볼륨을 계열 CLI 로 채집해 진단 보고 JSON 의 raid 하위 봉투로 보냅니다. 봉투 · 파서 · 저장 컬럼은 RAID phase 의 것과 같습니다(RaidInventoryParser · raid_inventory_json).
  • 서버는 COLLECT 지시 응답에도 칩 판별 힌트(raidChips)를 실어 에이전트가 계열을 판별하게 합니다. 채집 실패는 관용합니다 — 적재를 생략하고 원장에 기록하되 진단 자체는 성공으로 유지합니다.
  • 게스트 상세는 RAID 구성 단계 전에 RAID 인벤토리와(할당이 있으면) 계획 미리보기를 보이고, 지정 카드 대 관측 카드 대조 예고 한 줄을 더합니다. 상태 변경은 없습니다 — 집행 대조 cardMatches 의 판정을 순수 함수로 분리해 공유합니다.
  • 디스크 표 · 빈 상태 문구의 "RAID 단계에 진입해야 수집" 비대칭을 걷어냅니다. 하네스에 RAID 봉투 옵션을 더하고 apkovl 을 재포장합니다.
  • 이유: 2026-09-01 실기에서 RAID 단계 전에는 카드 뒤 디스크가 비어 보였고, 계획 · 카드 불일치를 집행 시점에야 알았습니다.
§1. 배경 · 진단

출발점 — 2026-09-01 RAID 실기(CP7)에서 드러난 두 공백

  1. 최초 진단의 디스크 수집이 lsblk 가시분이라 RAID 카드 뒤 물리 디스크가 비어 나옵니다(원장 disks: []).
  2. raid_card 자원에 PCI Subsystem 이 등록돼 있지 않아 집행의 카드 대조(CARD_MISMATCH)가 전 사이클에서 생략됐습니다.

E3.5-7-b(집행 전 확인 게이트)는 plan 만 산출한 채 보류하고 이 단계를 선행합니다(사용자 지시).

실태 (2026-09-02 코드 실측 — dev 8ee80fb)

  1. 진단 수집 보고는 JSON 한 벌입니다(build_report_json → DiagnosticReportParser → HardwareSpec). PCIe 행 분류로 RAID 카드의 존재 · 모델은 이미 알지만, lspci 를 -nn 없이 돌려 PCI id 는 없습니다.
  2. 카드 뒤 디스크 채집은 RAID phase 의 step 에서만 일어납니다 — collect_raid_report 봉투(tool · lspci_b64 · pd_b64 · vd_b64 · c0_b64 | display_b64) → RaidInventoryParser → guest_server_detail.raid_inventory_json. 상세의 RAID 인벤토리 · 계획 카드는 JSON 이 있으면 phase 와 무관하게 렌더합니다.
  3. raidChips 힌트는 RAID 지시 응답에만 실립니다(AgentReportService.raidChipsFor).
  4. 카드 대조는 RAID phase 의 인벤토리 소비에서, 자원에 Subsystem 이 있을 때만 합니다(cardMatches — null 이면 대조 생략 후 WARN).
  5. 자원 Subsystem 은 관리 폼으로만 들어가며 HMAC 서명 마커 manifest(ATTR_PCI)에 포함됩니다. 갱신은 관리 서비스를 경유한 재서명입니다.
  6. 도구(storcli64 · sas3ircu)는 apkovl 에 동봉돼 있고 ensure_raid_driver 가 관용적으로 로드합니다. agent.sh 변경은 apkovl 재포장을 부릅니다(KEYS_DIR 함정).
  7. 하네스 diagnose-cycle.sh 는 수집 JSON 을 문자열로 이스케이프합니다 — RAID 봉투를 같은 방식으로 덧붙일 수 있습니다.

§2. 요구사항 (확정) · 비목표
  1. 에이전트가 최초 진단(COLLECT) 보고에 RAID 봉투를 동봉합니다. 계열 판별은 서버가 응답에 실어 준 힌트로 하며, 지원 칩이 없으면 봉투를 생략합니다.
  2. COLLECT 응답에 raidChips 를 싣습니다 — 지금 RAID 지시에만 실리는 힌트를 같은 값 그대로 넓힙니다.
  3. 서버가 봉투를 RaidInventoryParser 로 정규화해 raid_inventory_json 에 적재합니다. 실패는 관용하고 사유를 원장 absorbed 에 남기되 진단은 성공으로 유지합니다.
  4. 게스트 상세에 지정 카드 대 관측 카드 대조 예고를 답니다. 판정은 순수 함수 하나를 집행과 화면이 함께 씁니다.
  5. 디스크 표 헤더와 RAID 인벤토리 빈 상태 문구를 개정해 "RAID 단계에 진입해야 수집" 이라는 비대칭을 걷어냅니다.
  6. 모의 게스트 하네스에 RAID 봉투 옵션을 더해, 화면 밖에서 오가는 이 슬라이스의 동작을 재연할 수 있게 합니다.
  7. 에이전트 스크립트가 바뀌므로 apkovl 을 재포장합니다(CP5 이후 · 실기 확인은 CP7 일괄).
  8. 단위 · 통합 두 레이어 테스트를 씁니다(§7).
비 목표 :
  • 카드 관측 채움 — E3.5-5-b 로 갑니다(관측 3컬럼 · 확정 버튼 · 재서명).
  • 집행 로직 변경, 그리고 카드 대조의 실패 승격 위치 변경 — RAID phase 에 그대로 둡니다.
  • 할당 모달 미리보기 — 상세 카드로 충족합니다.
  • BMC System Inventory 합류 — 워밍업 실측이 선행입니다.
  • fast init 등 집행 옵션.
  • HardwareSpec.DiskInfo(lsblk) 확장 — 그대로 두고 RAID 인벤토리와 병기합니다.

      §3. 설계 대안 비교
      

        

          
쟁점채택탈락

          
            
채집 보고 방식진단 보고 JSON 의 raid 하위 봉투진단 phase 새 step

            
봉투 생성에이전트 조립 함수 분리 후 공유복붙 두 벌

            
대조 판정순수 RaidCardMatch.judge 공유화면 전용 복제

            
저장 자리같은 raid_inventory_json · 최신 관측별도 컬럼

            
채집 실패관용 흡수진단 실패 승격

          
        


        
채집 보고 방식 — 진단 보고 JSON 의 raid 하위 봉투

        
토론 Q1 의 결정을 그대로 따릅니다. 채택안은 이미 있는 진단 보고 JSON 에 raid 키 하나를 더하는 것입니다. 탈락안은 진단 phase 에 새 step 을 두는 것이었는데, RAID phase 소속 step 상수는 phase 이탈 가드에 걸리고 새 상수를 만들면 DDL 의 enum 을 바꿔야 합니다. 봉투 · 파서 · 저장 컬럼을 그대로 재사용하는 편이 변경 면적이 작습니다 — 새로 만드는 것은 보고를 나르는 필드 하나뿐입니다.


        
봉투 생성의 단일화 — 에이전트

        
에이전트의 collect_raid_report 는 RAID step 용이라 봉투 조립과 report_step 호출을 함께 합니다. 여기서 봉투 문자열 조립만 raid_envelope_json 함수로 분리합니다. COLLECT 경로는 그 문자열을 진단 보고의 "raid": 필드에 넣고, RAID step 은 종전대로 report_step 을 이어 갑니다. 조립 코드를 복사해 두 벌로 두는 안은 탈락입니다 — 채집 명령이 바뀔 때 한쪽만 고쳐질 자리가 생깁니다.


        
카드 대조 판정의 SSOT

        
현재 cardMatches 는 판정과 원장 실패 기록을 한 몸으로 합니다. 화면은 실패를 기록하면 안 되므로 그대로는 못 씁니다. 그래서 순수 판정 RaidCardMatch.judge(target, inventory) 를 떼어내고, 집행은 그 판정을 받아 실패를 기록하며 화면은 같은 판정으로 한 줄을 표시합니다. 화면 전용으로 판정을 복제하는 안은 탈락입니다 — 지금은 같아도 대조 규칙이 자라면 갈라집니다.


        
저장 자리

        
토론 Q2 의 결정대로 같은 raid_inventory_json 컬럼에 최신 관측을 씁니다. 진단에서 한 번, RAID phase 에서 다시 한 번 채집되면 나중 것이 앞의 것을 덮습니다. 원문은 각 단계의 원장 statusMeta 가 보존하므로 이력이 사라지지 않습니다. 별도 컬럼을 두는 안은 우선순위 규칙과 이중 화면을 부릅니다.


        
실패 처리 — 관용

        
토론 Q4 의 결정대로 채집 실패가 진단을 실패시키지 않습니다. 카드가 없는 서버가 정상 다수이기 때문입니다. 에이전트는 지원 칩이 없으면 raid 키를 생략하고, 도구가 없거나 드라이버 로드에 실패하면 {"reason":"TOOL_MISSING", …} 형태의 reason 봉투를 보냅니다(RAID step 과 같은 어휘). 서버는 reason 봉투와 해석 불가를 모두 적재 생략 + WARN + 원장 absorbed 기록으로 흡수합니다.

      

    


    
    

      §4. 도메인 모델 (SSOT)
      

        
D1 — 진단 보고 계약 확장

        
{ …기존 필드…,
  "raid": {"tool":"storcli64","lspci_b64":…,"pd_b64":…,"vd_b64":…,"c0_b64":…}
        | {"tool":"sas3ircu","lspci_b64":…,"display_b64":…}
        | {"reason":"TOOL_MISSING","detail":…,"lspci_b64":…} }

        
raid 키가 없으면 지원 칩이 없다는 뜻이며 정상입니다. 첫 두 모양은 계열 CLI 원문을 base64 로 담은 정상 봉투이고, 셋째는 채집에 실패했을 때의 reason 봉투로 RAID step 이 이미 쓰는 어휘와 같습니다.

        
DiagnosticReportParser.Parsed 에 String raidEnvelope(원문 JSON 문자열 또는 null)를 더합니다. 파서는 내용을 해석하지 않고 통과시킵니다 — 관용 원칙이며, 해석은 RaidInventoryParser 의 몫입니다. 진단 파서가 RAID 문법까지 알게 되면 채집 명령이 바뀔 때마다 두 곳을 고쳐야 합니다.


        
D2 — 적재 (DiagnoseLinuxExecutor.onStepClosed)

        

          
봉투 상태처리원장

          
            
정상 (reason 없음)RaidInventoryParser.parse → detail.enrichRaidInventory(json)기록 없음

            
reason 봉투적재 생략 · WARNabsorbed raid(<reason>)=<detail>

            
해석 불가 (ReportUnparsableException)적재 생략 · WARNabsorbed raid(unparsable)=<message>

            
키 없음아무 것도 하지 않음기록 없음

          
        

        
카드 대조도, 실패 승격도 하지 않습니다 — 진단은 집행의 전제가 아닙니다. 대조를 진단으로 옮기면 그 판정이 진단의 성패를 좌우하게 되는데, 이 슬라이스가 원한 것은 미리 알려 주는 것이지 미리 막는 것이 아닙니다. absorbed 기록은 persistingMeta 의 filtered 목록에 실립니다(기존 구조 재사용).


        
D3 — 힌트

        
AgentReportService.raidChipsFor 가 COLLECT 에도 RaidChipFamily.agentChipHint() 를 붙입니다. 값은 지금 RAID 지시가 쓰는 것과 같은 1000:0097=MPT_IR 1000:005d=MEGARAID 입니다. 에이전트 do_collect 는 응답 바디를 받아 detect_raid_family "$CHIPS" 를 돌리고, 성공하면 ensure_raid_driver 뒤 봉투를 조립하며 실패하면 생략합니다.

        
칩 id 의 정본은 서버(RaidChipFamily)에 있고 에이전트는 그것을 받아 쓰기만 합니다. 그래서 지원 칩이 늘어도 apkovl 을 다시 굽지 않아도 되며, 이것이 에이전트가 스스로 판별하는 안을 버린 이유입니다.


        
D4 — 카드 대조 판정 SSOT RaidCardMatch

        
execution/engine/raid 의 순수 static 유틸입니다. judge(RaidConfigurationTarget target, RaidInventory inventory) 가 RaidCardMatchVerdict 를 돌려줍니다.

        

          
지정 카드자원 Subsystem관측 카드판정

          
            
없음 (할당 없음 · 카드 미지정)——NOT_APPLICABLE

            
있음null—UNVERIFIABLE

            
있음있음없음 (card null · Subsystem null)NOT_DETECTED

            
있음있음다름MISMATCH

            
있음있음같음 (대소문자 무시)MATCH

          
        

        
집행의 cardMatches 는 이 판정을 받아 NOT_DETECTED 는 CARD_NOT_DETECTED 실패로, MISMATCH 는 CARD_MISMATCH 실패로 옮기고, UNVERIFIABLE 은 WARN 뒤 통과시킵니다. 종전과 같은 동작이며 문구도 그대로입니다. 화면은 같은 판정을 한 줄로 표시합니다.


        
D5 — 화면 계약

        
GuestServerDetailResponse.raidCardCheck 를 record 로 둡니다(필드 = verdict · 지정 카드명 · 지정 Subsystem · 관측 Subsystem · 문구). GuestServerQueryService 가 resolveFor 와 저장 인벤토리로 채우며, 인벤토리가 없으면 null 입니다.

        

          
판정문구 (execution.raid-card-check.*)

          
            
MATCH지정 카드와 감지 카드가 일치합니다(1000:9361)

            
MISMATCH지정 {카드}({sub}) ≠ 감지 {sub} — 집행 시 CARD_MISMATCH 로 실패합니다. 정의서의 카드를 확인하십시오

            
NOT_DETECTED지정 카드를 감지하지 못했습니다 — 집행 시 CARD_NOT_DETECTED 로 실패합니다

            
UNVERIFIABLE카드 자원에 Subsystem 이 확정되지 않아 대조할 수 없습니다(E3.5-5-b 관측 채움)

          
        

        
위치는 "RAID 구성 계획" 카드 상단입니다. 함께 디스크 표 헤더를 "디스크 (OS 가시 장치 — RAID 카드 뒤 물리 디스크는 아래 RAID 인벤토리)" 로 바꾸고, RAID 인벤토리 빈 상태 문구를 "RAID 인벤토리가 아직 없습니다 — 진단 수집에서 RAID 카드가 감지되면 채워집니다(카드가 없는 서버는 비어 있는 것이 정상)" 로 바꿉니다.


        
D6 — 하네스 · 이미지

        
diagnose-cycle.sh 에 RAID_MODE=mr|mrclean|ssd6|cra|toolmissing 환경변수를 둡니다. 값이 있으면 fixtures-raid/ 픽스처로 봉투를 조립해 INNER 에 "raid": 로 이스케이프해 동봉합니다. 조립 함수는 raid-inventory-cycle.sh 의 것을 공용 스크립트 raid-envelope.sh 로 뽑아 둘이 공유합니다 — 복붙하지 않습니다. 하네스 쪽 봉투와 에이전트 쪽 봉투가 갈라지면 검증이 실제 동작을 대변하지 못하므로, 이 공유는 편의가 아니라 검증의 전제입니다.

        
apkovl 재포장은 build-assets.sh apkovl 이며 KEYS_DIR 복사가 선행돼야 합니다 — 토론이 "함정" 으로 적어 둔 지점입니다. CP5 뒤에 굽고, 실기 확인은 E 단계 관례대로 다른 슬라이스와 함께 일괄로 합니다.
