§1. 현재 상태 (진단)

E3.5-1 이 카드 뒤를 보게 했고, E3.5-2 가 인벤토리에서 계획을 산출했으며, E3.5-3 이 그 계획을 실물 카드에 걸고 결과를 대조해 raid_volume 에 기록하는 데까지 왔다. 남은 것은 양쪽 끝이다 — 앞쪽에서는 정의서가 아직 기존 구성을 어떻게 할지 말하지 않고, 뒤쪽에서는 기록된 실물이 화면에도 다음 단계에도 닿지 않는다. 이 슬라이스가 그 둘을 잇고 E3.5 계열을 닫는다.

E3.5-3 의 판정 ③ 은 외부 기존 볼륨(이름이 spvR 규약이 아닌 것)이 있는데 보존 · 파괴 축이 없으면 집행을 개시하지 않는다. 되돌릴 수 없는 삭제를 시스템이 임의의 기본값으로 고를 수 없기 때문이다(0-3 토론 결정 D-7 — 기본값 없는 필수 선택). 실기의 두 카드가 모두 이 상태라, E3.5-3 의 CP7 은 운영자가 기존 볼륨을 수동으로 지운 뒤 실측한다는 전제로 승인됐다. 이 슬라이스가 축을 도입하면 그 전제가 사라진다 — 정의서에서 "파괴" 를 고르는 것만으로 실카드 집행을 관찰할 수 있다.

같은 성격의 미룬 것이 하나 더 있다. E3.5-2 의 결정 7 은 "선행 규칙에 완전히 포섭되어 어떤 디스크도 만나지 못하는 후행 규칙" 을 작성 시점에 막자고 하면서, 그 판정을 이 슬라이스로 넘겼다. 지금은 그런 규칙을 저장할 수 있고, 저장된 뒤에는 계획 미리보기의 consumedNothing 표시로만 드러난다 — 사람이 화면을 열어야 보이는 결함이다. E3.5-2 의 결정 4 가 남긴 두 갈래 병기도 "축이 아직 없어서" 였던 잠정 조치이므로 여기서 정리된다.

raid_volume 의 처지도 같다. E3.5-3 이 "현재 카드에 무엇이 올라가 있는가" 를 담는 표를 만들고 검증 통과 시 replace 로 기록하지만, 그 행을 읽는 곳은 아직 아무 데도 없다. E4(OS 설치)가 "이 서버의 OS 영역 볼륨" 을 물을 경로도 RaidVolume.volumeRole 이라는 계약만 있고 조회 메서드가 정리되지 않았다. 기록만 하고 읽지 않는 표는 다음 단계에서 급하게 배선되며 모양이 흔들린다.

§2. 요구사항 (확정) + 비목표
  1. R1 기존 구성 축 — 정의서 RAID 구성 단계에 기본값 없는 필수 선택 축 "기존 구성 : 보존 / 파괴" 를 둔다(D-7). 폼 라디오 · payload 필드 · 서버 검증 · 상세 표시 넷을 함께 만든다. 필수 여부의 판정 재료는 RAID 를 구성하는 묶음이 있는가(requiresRaidCard 와 같은 재료)이고, 묶음이 0 이면 축은 뜻이 없으므로 요구하지 않는다(결정 2).
  2. R2 실행 배선 — 공급 SPI(Service Provider Interface — 도메인이 구현해 끼우는 확장점)에 policyOf(guestServerId) 를 더해 정의서의 축을 실행기에 공급한다. 축이 있으면 명시 정책이 보류를 대체하고, PRESERVE 인데 외부 볼륨이 실재하면 보류가 아니라 정직한 실패로 전환한다(결정 3).
  3. R3 사각 규칙 정적 차단 — DiskGroupRules 에 8번째 규칙을 더해, 후행 규칙의 수용집합이 선행 규칙에 완전히 포섭되면 저장을 거절한다. 폼은 같은 진리표를 미러해 행을 편집하는 즉시 강조와 사유를 보여 준다(UI 1차 차단 · 서버 가드는 안전망 — 결정 4).
  4. R4 실물 표 — 게스트 서버 상세에 "RAID 구성 실물" 섹션을 둔다. raid_volume 의 행을 이름 · 레벨 · 멤버 슬롯 · 유효 용량 · 역할(OS 배지) · 상태 · 기록 시각으로 보여 주고, 행이 없으면 "검증 통과 전" 을 안내한다(결정 5).
  5. R5 미리보기 3분기 — 계획 미리보기를 정책 명시 = 단일 갈래 / 축 없음 + 기존 볼륨 = 두 갈래 병기 / 축 없음 + 무볼륨 = 정책 무관 단일 로 가른다. 두 갈래 병기는 사라지지 않는다 — 구 저장본(축 null)이 남아 있는 동안 그것이 정확한 설명이기 때문이다.
  6. R6 E4 인계 조회 — RaidVolumeRepository 에 OS 영역 볼륨 조회 파생 메서드를 정리해 다음 단계가 읽을 계약을 고정한다. 같은 execution 영역이라 SPI 는 두지 않는다(경계를 넘는 역전이 없다 — "미리 분리 금지").
  7. R7 볼륨 WWN 채집 · 기록 증보 2026-09-01 — 검증 재채집 파싱에서 볼륨의 WWN(World Wide Name — 저장 장치의 전역 고유 식별자)을 뽑아 raid_volume.wwn 에 남기고, 상세 실물 표에 WWN 열을 더하며, E4 인계 조회 계약에 이 값을 포함한다. 실측 원문에 값이 이미 있다 — MegaRAID 는 볼륨의 SCSI NAA Id, IR 은 Volume wwid 다.
비 목표 :
  • 실카드 집행 — CP7 의 E 단계 일괄 실기로 넘긴다. 다만 축 도입으로 기존 볼륨 수동 삭제 전제는 해소되어, 그때 "파괴" 를 골라 집행을 관찰할 수 있다.
  • E4 OS 설치 자체 — 이 슬라이스는 조회 계약까지다. 리눅스 설치는 계획 개정으로 장기 과제이며, 소비 배선은 그 슬라이스의 몫이다.
  • 두 갈래 병기의 완전 제거 — 구 저장본(축 null)이 있는 한 병기는 유지된다. 없애는 것이 아니라 분기 하나로 좁히는 것이 이번 범위다.
  • 기존 저장본 일괄 마이그레이션 — 값을 임의로 주입하지 않는다(결정 2).
🎬 미리보기 — 정의서 폼과 실행 분기

데모는 두 파트다. ① 정의서 폼에서는 묶음 규칙 행을 직접 고쳐 가며 사각 규칙이 어떻게 즉시 잡히는지와, 축을 고르지 않은 채 저장하면 무엇이 막는지를 본다. ② 실행 분기에서는 카드의 실물 상태와 정의서 축을 조합해 집행 · 실패 · 보류 가운데 무엇이 나오는지, 그리고 상세 화면의 계획 미리보기가 몇 갈래로 보이는지를 본다. 처음이라면 원클릭 시나리오 P1~P6 을 차례로 눌러 보는 편이 빠르다 — 세팅과 안내 배너가 함께 붙는다.

판정 JavaScript 는 서버 규칙의 미러다 — demoRuleFindings() 가 DiskGroupRules 의 8번째 규칙(포섭)과 4번째 규칙(중복)을, demoPolicyOk() 가 RaidConfigurationRequest.isExistingPolicyPresentWhenRequired 를, demoExecJudge() 가 RaidConfigurationExecutor.directiveFor 의 축 도입 후 판정 순서를 같은 순서로 재현한다. §4 의 실행 분기 표는 이 함수가 그대로 렌더한 것이라 표와 데모가 구조적으로 어긋날 수 없다.

A 가 탈락한 이유는 원칙의 문제다. 기본값 없는 필수 선택(D-7)을 지키기로 해 놓고 시스템이 기존 정의서에 값을 채워 넣으면, 그것이 마이그레이션이라는 이름을 달고 있어도 기본값을 창출하는 것이다. 그리고 그 값이 DESTROY 라면 사람이 고른 적 없는 삭제가 조용히 예약된다. B 에는 선례도 있다 — volumePriorities 가 이미 같은 관례를 쓴다(상세 fragment 의 "미지정 — 구 저장본" 문구 · 편집 시 채움). 실행 의미도 안전하다. 축이 null 이면 종전과 완전히 같은 보류가 되므로 이 슬라이스가 기존 게스트의 동작을 바꾸지 않는다(퇴행 0).

결정 3. 실행 배선 — 정책의 공급과 보류 · 실패의 경계

안내용판정
AplanFor 시그니처에서 policy 를 빼고 Impl 이 내부에서 결정탈락
BSPI 에 Optional<RaidExistingConfigPolicy> policyOf(guestServerId) 추가 — planFor 는 호출자 지정 그대로채택

A 는 얼핏 깔끔해 보이지만 미리보기가 죽는다. 구 저장본에서 두 갈래를 병기하려면 같은 인벤토리로 DESTROY 와 PRESERVE 를 각각 한 번씩 산출해야 하는데, A 는 호출자가 정책을 지정하는 경로 자체를 없앤다. B 는 공급(축이 무엇인가)과 산출(그 축으로 계획하면 무엇이 되는가)을 분리해 둘 다 살린다.

  • 실행기 — policyOf 가 값을 주면 그 정책으로 진행한다. PRESERVE + 외부 볼륨은 planner 가 EXISTING_CONFIG 로 거절하고 실행기가 그것을 failInstant 로 승격한다. DESTROY 는 외부 볼륨을 포함해 전부 선행 삭제한 뒤 재구성한다. 값이 없으면(empty) 현행 그대로다.
  • 미리보기 — 정책 명시는 단일 갈래, null + 기존 볼륨은 두 갈래 병기, null + 무볼륨은 정책 무관 단일이다.
  • 경계 — EXISTING_CONFIG 만 실패로 승격한다. 나머지 거절은 정의서를 고치면 풀리므로 보류가 옳다.

결정 4. 사각 규칙 정적 차단 (E3.5-2 결정 7 이행)

DiskGroupRules 의 8번째 규칙으로 둔다. 판정은 §4 의 두 표가 전부이고, 폼 JavaScript 가 같은 진리표를 미러해 행을 추가 · 편집하는 즉시 강조와 사유를 보여 준다. 레벨과 역할을 판정에서 뺀 것이 이 결정의 요체다 — 소비는 다섯 축이 정하므로, 레벨이 다르더라도 선행 규칙이 그룹을 먼저 흡수해 버리면 후행은 영영 매칭되지 않는다. RAID5 AT_LEAST 3 뒤의 RAID6 AT_LEAST 4 가 바로 그 예이며, 지금은 이것이 저장되고 나서 미리보기의 "소비 0" 표시로만 드러난다. 판정을 엄격 일치로 좁게 잡은 것은 E3.5-2 결정 6 의 소비 규칙과 같은 기준을 쓰기 위해서다 — 소비가 엄격 일치인데 도달 가능성 판정만 느슨하면 두 규칙이 서로 다른 세계를 말하게 된다.

왜 저장 시점에 막는가 — 실행 시점에 알려 주는 방법도 있다. 그러나 그때는 이미 서버가 프로비저닝 중이고, 잘못은 정의서를 쓰던 사람의 것이며 고칠 자리도 정의서다. 쓰는 순간에 막으면 사람이 자기 손으로 방금 만든 모순을 바로 본다.

결정 5. 실물 표와 E4 인계

상세 화면의 계획 섹션 뒤에 "RAID 구성 실물" 섹션을 둔다. 계획이 "무엇을 만들 것인가" 라면 이 표는 "지금 카드에 무엇이 있는가" 이고, 둘을 나란히 두면 운영자가 대조할 것이 한 화면에 모인다. 행이 없을 때는 비워 두지 않고 "검증 통과 전" 을 안내한다 — 빈 표는 "없다" 와 "아직 모른다" 를 구분해 주지 못한다.

증보(사용자 확정 2026-09-01) — 인계에는 값이 하나 더 필요하다.
DB 의 "OS 영역"(volume_role)은 논리 지정일 뿐, 설치기가 그대로 받아 쓸 값이 아니다. 두 설치기가 서로 다른 것을 요구한다. Windows 의 autounattend.xml 은 정수 DiskID 만 받으므로, 이 표의 WWN 은 설치기에 전달되는 값이 아니라 조회 키다 — WinPE 단계에서 WWN 을 보고 그 자리의 DiskID 를 런타임에 해석해야 하며, 그 해석은 Windows 설치 슬라이스의 몫이다. 반면 Linux 의 kickstart 는 WWN 을 직결한다(ignoredisk --only-use=/dev/disk/by-id/wwn-… — 0-3 토론 Q7 원안). 어느 쪽이든 WWN 이 없으면 다리가 놓이지 않는다. 그런데 실측 원문에는 값이 이미 있었고(MegaRAID 볼륨의 SCSI NAA Id · IR 의 Volume wwid) E3.5-3 의 파서가 그것을 버리고 있었다. 채집이 이미 지나간 자리에서 값을 다시 얻으려면 게스트를 한 바퀴 더 돌려야 하므로, 지금 같은 파싱에서 함께 담는 것이 옳다.

E4 인계는 RaidVolumeRepository 의 파생 메서드로 정리한다(findFirstByGuestServer_IdAndVolumeRole 류 — 반환 행이 wwn 을 함께 싣는다). SPI 를 두지 않는 이유는 경계를 넘는 역전이 없기 때문이다 — OS 설치 실행기도 raid_volume 도 같은 execution 영역에 있어, 확장점을 만들면 같은 패키지 안에서 자기 자신을 향해 인터페이스를 세우는 꼴이 된다("미리 분리 금지"). 갈라지는 시점, 즉 provisioning 쪽이 이 값을 물어야 할 때 분리한다.

리스크

  • 용량 축의 포섭을 "동일 (size, unit)" 로 좁게 잡았다. ±3% 계급 동등(480 GB 지정과 0.48 TB 지정 같은 것)은 포섭으로 보지 않는다. 폼의 단위가 GB · TB 둘뿐이라 교차 표기의 실익이 복잡도에 못 미친다고 판단했다 — 1 TB = 1000 GB 교차만 후속 관찰 대상으로 남긴다. 결과는 덜 막는 쪽이라 정당한 규칙을 잘못 거절하는 위험은 없다.
  • PRESERVE 실패 승격은 EXISTING_CONFIG 한 코드에만 적용된다. 거절 코드가 늘면 코드마다 승격 여부를 정해야 하는 자리이므로, 그 사실을 주석으로 명시해 다음 사람이 조용히 else 로 흘려 보내지 않게 한다.
  • 안내 문구가 새로 생긴다(축 라벨 · 오류 메시지 · "미지정 — 구 저장본" · "검증 통과 전"). CLAUDE.md 의 작업 전 체크리스트에 따라 .claude/domain-conventions/new-user-copy.md 와 new-form.md 를 CP2 착수 전에 연다.
  • 단독 디스크(패스스루)의 WWN 은 볼륨과 원천이 다르다 증보 — 볼륨의 WWN 이 볼륨 정보에서 나오는 것과 달리, 단독 디스크의 것은 물리 디스크 쪽에서 나온다(IR 은 display 의 물리 디스크 GUID, MegaRAID 는 물리 디스크 상세의 WWN 필드). 실측 원문에 그 부분이 담겨 있는지가 미확정이라, 이 슬라이스는 볼륨 WWN 을 필수 범위로 하고 단독 디스크의 것은 원문에 있으면 함께 담되 없으면 null 로 관용한다 — 확인은 CP7 실측이다.
  • IR 계열이 볼륨 이름을 내지 않으면 잔여 판별이 보수적으로 막힌다(E3.5-3 리스크의 계승 — Q1 확정으로 이 plan 의 관심사가 됐다). 이름 미노출 볼륨은 isProvisionOwned() 가 외부로 간주해 IR 재시도가 보류에 걸릴 수 있다. 폴백 후보 = 이력 보조 신호(원장의 직전 RAID_APPLYING FAILED 존재 — 사용자 제안 2026-09-01): 1차(이름) 판별이 불가능한 좁은 창에서만 쓰면 정황 증거의 위험도 최소화된다. CP7 실측에서 IR 이름 미노출이 확정되면 그때 추가한다 — 미확정 전제 위의 선분리는 하지 않는다.
