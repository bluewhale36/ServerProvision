§1. 현재 상태 (진단)

1-1. 자료 파일 경로 (현행)

지금 BIOS 세팅 편집기가 무엇을 고를 수 있는지, 저장할 때 어떤 값이 통과하는지는 전부 저장소에 두고 온 자료 파일이 정한다. 설정 provisioning.bios.boards[i]{key, registry, setup-data} 가 보드 5종(MS03-CE0 · MS73-HB1 · MS04-CE0 · MS74-HB0 · MD72-HB3[2026-08-27 하드코딩 추가])의 파일 짝을 들고 있고, BiosResourceProperties.findBoard(modelName) 가 보드명으로 그 짝을 찾는다.

로딩은 BiosSetupLoader.load(boardKey) 한 자리다. ConcurrentHashMap 으로 보드당 한 번만 읽고 캐시하며, 안에서 BiosRegistryParser.parse(JSON) 가 ParsedRegistry(attributes, dependencies) 를 만들고 BiosSetupDataParser.parse(XML, registry) 가 그것을 메뉴 골격에 얹어 BiosSetupMenu(boardKey, menuBarOrder, pages, registry, dependencies) 를 낸다. 이 결과를 쓰는 곳은 셋이다 — BiosSettingTemplateQueryService 의 editorView · findDetail · findBoards(보드 카드의 catalogAvailable 은 properties.findBoard 존재 여부로 정한다), 그리고 생성 · 수정 저장 검증을 맡는 BiosSettingTemplateCommandService.validateAndCoerce.

집행은 다른 길로 간다. BiosSettingResolutionProviderImpl.resolveFor(guestId) 가 활성 할당 스냅샷의 FrozenBiosSettings.templates 중 감지 보드와 boardModelId 가 같은 것들의 values 를 병합해 BiosSettingTarget(Map<String,Object>) 을 만들고, BeginSettingStep 이 RedfishBiosService.patchPending 으로 PATCH /redfish/v1/Systems/Self/Bios/SD 를 던진다. 이 경로에는 자료 파일이 끼지 않는다 — 값의 최종 검증자는 BMC 다.

1-2. 실기 사고 (2026-08-27 통합 테스트)

게스트 아이티인포 (상) (1)(보드 MD72-HB3 · BMC 192.168.1.130)의 BIOS 를 F33 에서 F44 로 굽는 데 성공한 직후, BIOS 설정 PATCH 가 3회 연속 거절됐다. 그런데 로그와 원장에는 "BMC 가 요청을 거절했습니다" 만 남아 있어 사유를 보려면 curl 로 다시 재현해야 했다. 그 관측 결함 자체는 같은 날 RedfishClient.classify 정정으로 해소했다 — 이제 상태코드와 error.@Message.ExtendedInfo[].Message 를 함께 싣는다.

드러난 사유는 이것이었다.

The value 'Disabled' for the property Whitley0000 is not in the list of acceptable values.

복구는 전부 수동이었다. VM 의 자료 파일을 실기에서 받은 것으로 교체하고(원본은 백업 보존), 템플릿 5 의 값 다섯을 정정하고, 활성 할당 6~9 의 동결 스냅샷을 SQL 로 직접 고쳤다. 마지막 것이 없으면 안 된다는 사실은 실패로 배웠다 — 템플릿만 고쳤을 때 (하) 게스트가 같은 사유로 한 번 더 거절됐기 때문이다.

1-3. 구조적 결함 셋

위 사고는 조작 실수가 아니라 구조에서 나온다. 세 겹이다.

  1. 정본이 둘이다. 편집기와 저장 검증은 파일을 보고, 집행은 BMC 를 본다. AMI 레지스트리는 보드 하나가 아니라 보드 × BIOS 버전에 종속인데, 파일은 채집한 시점의 버전에 고정된 채 굳는다. 굽기가 성공할수록 파일은 낡는다.
  2. 파일에 버전 표식이 없다. RegistryVersion 은 어느 BIOS 에서 뽑아도 0.1.0 이라 판별에 쓸 수 없다. 그래서 "이 파일이 굽기 목표 버전과 맞는가" 를 검사할 재료 자체가 없다.
  3. 할당 스냅샷은 동결이다. U3-1 의 deep-freeze 원칙대로 할당 시점의 값이 그대로 얼어붙으므로, 템플릿을 고쳐도 이미 걸린 할당에는 닿지 않는다. 따라서 드리프트는 할당하기 전에 잡아야 한다.

1-4. 이미 갖춘 것 (재사용)

새로 만들 것보다 이미 있는 것이 많다. 이 슬라이스는 그것들을 잇는 일에 가깝다.

  • 레지스트리 발견 체인이 실측됐다. RedfishBiosService.bios(target) 응답에 AttributeRegistry: "BiosAttributeRegistry" 가 실린다. 그 id 로 GET /redfish/v1/Registries/BiosAttributeRegistry → Location[0].Uri = /redfish/v1/Registries/BiosAttributeRegistry.json → 전문 순으로 도달한다. E3 우산 페이지의 지침 "레지스트리 경로를 하드코딩하지 않는다" 와 그대로 맞는다.
  • 파서는 양방향 결손을 이미 견딘다. 레지스트리에만 있는 속성은 BiosPageResponse.of 의 orphan skip 으로 편집기에 안 뜨고, XML 에만 있는 속성도 skip 된다. 실측으로 제공 파일에서도 XML(176 속성) 밖 170 속성이 있었지만 정상 로드됐고, F44 로 교체한 뒤 215 속성이 밖이어도 정상 로드됐다. XML 을 그대로 두고 레지스트리만 갈아끼울 수 있다는 뜻이다.
  • 굽기 목표 버전 술어가 있다. FirmwareResolver.firstEnabled(biosRepository.findAllByBoardModel_IdAndIsDeletedFalseOrderByVersionRankAsc(boardId)) 가 version_rank 1위 활성 BoardBIOS 를 고른다. 화면의 BiosService.latestOf 와 같은 술어다.
  • 할당 차단이 이미 다형이다. AssignmentBlockKind{DECOMMISSIONED, BOARD_MISMATCH}.evaluate(AssignmentEligibility) 에 상수를 더하면 화면 옵션 disabled · 서버 409 · 예외 매핑이 함께 편입된다.
  • 상세 화면에 경고 행 자리가 있다. StaleEntry(attributeName, storedRaw) 로 "카탈로그에 없는 속성" 을 이미 낸다.
  • execution → provisioning 역전 SPI 선례가 있다. BiosSettingResolutionProvider 가 execution 에서 선언되고 provisioning 이 구현한다.
  • 하네스가 절반 준비돼 있다. scripts/mock-redfish/mock-redfish.py 가 Systems/Self/Bios(AttributeRegistry 포함)와 Bios/SD 를 모사하고 patch-reject 모드를 갖는다.
핵심 진단 — 값이 틀린 것이 아니라 값을 판정하는 정본이 낡은 사본이라는 것이 문제다. 그래서 이 슬라이스는 검증 규칙을 더 짜는 것이 아니라, BMC 가 쥔 정본을 만나는 김에 받아 적립하고 그 적립본을 모든 판정의 입력으로 돌려놓는다.
§2. 요구사항 (확정) + 비목표

R3출처 가시화편집기 · 상세 · 보드 카드에 출처 배지
R4드리프트 가시화속성 부재 · 값 불허 두 경우를 상세 경고 행으로. 값 불허는 허용 목록 동봉
R5할당 시 차단어긋난 템플릿을 가진 정의서는 옵션 disabled + tooltip, direct POST 는 409

R7DDL새 테이블 1 (bios_registry_snapshot) — 로컬 · VM 적용

R1 채집은 멱등이다. 같은 (보드, 버전) 키가 이미 있으면 건너뛴다. 그리고 채집 실패는 집행을 막지 않는다 — 레지스트리를 못 받아왔다는 이유로 굽기 뒤 설정이 멈추면 그것이 곧 회귀이므로, 실패는 로그와 폴백으로 흡수한다.

R2 해석의 순서가 "목표 버전 우선" 인 이유는 설정 값이 적용되는 시점이 굽기 이후라서다. 지금 게스트에 얹힌 BIOS 가 무엇이든, 이 정의서로 프로비저닝하면 결국 목표 버전이 올라간다. 그래서 화면이 보여줘야 할 허용값은 목표 버전의 것이다. 다만 그 버전을 아직 한 번도 만난 적이 없으면 스냅샷이 없으므로 최신 채집분으로, 그것도 없으면 파일로 내려간다.

R3 배지 문구는 세 갈래다 — F44 · 2026-08-27 채집 · 192.168.1.130 / 최신 채집 F44 · 목표 F45 미채집 / 파일 · 버전 미상. 마지막 문구가 중요하다. 파일 폴백이라는 사실 자체가 "지금 보이는 허용값은 틀릴 수 있다" 는 신호이기 때문이다.

R5 와 R6 의 관계는 이 슬라이스의 UX 원칙 그대로다. 정상 흐름에서 어긋난 템플릿은 할당 화면에서 먼저 막고(UI 1차 차단), direct POST 같은 비정상 경로만 409 로 떨어진다. R6 은 그보다 더 안쪽의 안전망으로, 화면을 통과한 값이 실제 굽힌 버전에서 거절될 경우를 도메인 언어로 잡는다.

비 목표 :
  • SetupData XML 의 라이브 채집(AMI 웹 API — 관리자가 BMC 웹 화면에서 수작업 확보하는 그 요청의 재연) — 후속 슬라이스. 이번에는 XML 을 메뉴 골격으로 그대로 유지한다. 레지스트리 MenuPath 로 메뉴 트리를 대체하는 안은 기각했다 — 실기 F44 레지스트리 391 속성 중 MenuPath 는 0건이라 트리를 만들 재료가 없다(2026-08-28 확인).
  • 채집 결과를 보드 자원으로 저장하고 보드 등록 화면의 '검증' 절차로 노출하는 것 — MA6 소관 (E3 우산 페이지가 그은 경계).
  • 온디맨드 "BMC 에서 레지스트리 받기" 버튼 — D-7 로 기록하되 후순위 선택 사항, 이번 범위 밖.
  • 값 자동 번역 (Disabled → Disable) — silent 흡수라 채택하지 않는다.
  • 기존 활성 할당 스냅샷의 자동 정정 — 동결 원칙을 유지하고 재할당으로 해소한다.
🎬 미리보기 — 레지스트리 정합 시뮬레이터

이 슬라이스에는 새 화면이 없다. 대신 어느 레지스트리를 정본으로 보느냐가 편집기 · 상세 · 할당 · 집행 넷의 답을 한꺼번에 바꾼다. 아래 시뮬레이터는 그 하나의 변수를 직접 돌려볼 수 있게 만든 것이다. 왼쪽 조작면에서 스냅샷 보유 · 굽기 목표 버전 · 템플릿 값 · 게스트 실제 BIOS 를 바꾸면, 해석된 레지스트리와 그에 딸린 상세 경고 · 할당 버튼 차단 · 집행 전 검증이 함께 갱신된다.

먼저 원클릭 시나리오 다섯을 순서대로 눌러보는 것을 권한다. 각 버튼이 상태를 통째로 세팅하고, 바로 아래 배너가 지금 무엇을 보고 있는지 설명한다. 판정 JS 는 §4 의 도메인 메서드(BiosRegistryResolver.resolve · BiosSettingTemplate.staleAgainst · AssignmentBlockKind.TEMPLATE_STALE.reasonFor · BeginSettingStep 의 집행 전 검증)를 1:1 로 옮긴 것이다.

값 객체 · enum

  • BiosRegistrySource enum {SNAPSHOT_TARGET, SNAPSHOT_LATEST, FILE} — 상수별 badgeLabel(version, capturedAt, bmcIp) 로 배지 문구를 낸다. 문구 조립을 뷰에 두면 세 화면에 복사되므로 enum 이 쥔다.
  • ResolvedBiosRegistry(BiosSetupMenu menu, BiosRegistrySource source, String biosVersion, LocalDateTime capturedAt, String sourceBmcIp) record.
  • BiosStaleValue(BiosAttributeName name, String storedRaw, BiosStaleKind kind, List<String> allowed) record.
  • BiosStaleKind enum {MISSING_ATTRIBUTE, VALUE_NOT_ALLOWED} — 상수별 message().

도메인 메서드 (SSOT)

BiosSettingTemplate
  .staleAgainst(Map<BiosAttributeName, BiosAttribute> registry) → List<BiosStaleValue>
      · 속성 부재                  → MISSING_ATTRIBUTE
      · ENUMERATION 값 불허        → VALUE_NOT_ALLOWED (allowed 동봉)
      · INTEGER  → bounds 재검
      · BOOLEAN  → true/false 재검

이 메서드 하나가 세 곳의 정본이다 — 상세 화면의 경고 행(R4) · 할당 차단(R5) · 집행 전 검증(R6, 포트 구현이 같은 규칙을 호출). 세 곳이 각자 비교하면 그것이 곧 D-4 가 배제한 drift 다.

  • AssignmentBlockKind.TEMPLATE_STALE — BOARD_MISMATCH 뒤에 선언한다. reasonFor(context) = context.templateStaleReason() · toException = BiosTemplateStaleException · hardwareIncompatible = false. 상수 하나로 화면 disabled · 서버 409 · 예외 매핑이 함께 편입되는 것이 기존 다형의 이득이다.
  • AssignmentEligibility 에 templateStaleReason(String, nullable) 필드를 더한다. 조립은 AssignmentQueryService 와 AssignmentCommandService 가 BiosTemplateStaleInspector.reasonFor(definitionId, boardModelId) 로 한다.

서비스 · SPI

  • BiosRegistryResolver(provisioning.biossetting.service) — resolve(BoardModel) → ResolvedBiosRegistry. 목표 버전 술어는 FirmwareResolver.firstEnabled 와 같은 것을 써야 하므로, management.bios 의 BoardBiosCatalog.latestEnabled(List<BoardBIOS>) 로 추출해 둘이 공유한다(D-3 · Q1).
  • BiosSetupLoader — load(boardKey)(파일, 유지)에 load(boardKey, snapshotId, registryJson) 를 더한다. 스냅샷 JSON 을 같은 파서 · 같은 XML 로 결합하고 캐시 키는 boardKey#snapshotId 로 분리한다.
  • RedfishBiosService.registry(target) → RedfishRegistry(String registryId, String rawJson) — 체인 3 GET, 하드코딩 경로 없음.
  • SPI BiosRegistryCapturePort(execution.engine.setting 에서 선언) — 
    RegistryCheck captureAndCheck(UUID guestServerId, RedfishTarget target,
                              Map<String,Object> attributes);
void          captureIfAbsent(UUID guestServerId, RedfishTarget target);

record RegistryCheck(boolean captured, String biosVersion, List<String> violations)
    구현 BiosRegistryCapturePortImpl(provisioning.biossetting.service)이 BMC 버전 판독(FirmwareInventory/BIOS.Version — RedfishUpdateService.firmwareInventory) → 스냅샷 upsert-if-absent → 파서 → staleAgainst 규칙으로 위반 산출까지 맡는다. 모든 예외를 삼키고 RegistryCheck.unavailable() 로 답한다 — 채집이 집행을 막지 않는다는 R1 이 여기서 지켜진다.
  • SettingLedger 에 VALUE_NOT_IN_REGISTRY 사유를 신설한다. PATCH_REJECTED 와 구분하는 이유는 운영자가 할 일이 다르기 때문이다 — 전자는 템플릿을 고치고, 후자는 BMC 를 본다.
  • BeginSettingStep — 신원 확인 뒤 · 원장 열기 뒤 · PATCH 전에 captureAndCheck. violations 가 비어 있지 않으면 ledger.close(row, FAILED, VALUE_NOT_IN_REGISTRY, 상세) + progress.markFailed. RegistryCheck.unavailable 이면 종전대로 PATCH 하고, 안전망은 BMC 400 사유 로그가 맡는다.
  • VerifyFlashStep — BIOS 축 성공 시 captureIfAbsent(검증 없음).

화면 응답

  • BiosSettingTemplateDetailResponse — registrySource(BiosRegistrySource) · registryLabel 추가, StaleEntry 를 (attributeName, storedRaw, kind, allowed) 로 확장.
  • BiosSettingTemplateEditViewResponse 와 생성 편집기 — registryLabel.
  • BiosSettingBoardCardResponse.catalogAvailable — 스냅샷 존재 or 파일 존재.
