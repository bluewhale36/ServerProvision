§0. 이 단계가 어떻게 지금 모양이 되었는가

구 U3-4 는 스펙 그룹 단위 세팅 정의서 일괄 할당이었다. 그 전제는 "묶음 = 하드웨어 스펙이 같은 서버들" 이었는데, 사용자가 요구를 풀어 설명하면서 전제가 어긋났음이 드러났다. 요구된 묶음은 사람이 만들고 멤버를 넣고 빼는 영속 개념이지 조회 시점 계산 결과가 아니었다. 그래서 단계가 둘로 갈렸다 — U3-4 가 그룹이라는 개념 자체를 세우고(2026-08-12 완료), U3-5 가 그 위에서 일괄 할당을 다룬다.

재편 토론(discussion/26-08-11_16-25-25_U3-4-server-group-concept_discussion.md)은 할당 의미론으로 팬아웃 + 그룹 기본 정의서를 권고했다. 그 문서는 동시에 "권고는 방향 제시이지 확정이 아니다 — CP1 plan 에서 대안을 정식 비교한 뒤 승인으로 확정한다" 고 적어 두었다.

이 plan 은 그 권고를 뒤집는다. 코드를 실측하며 U3-4 가 확정한 다른 결정들과 맞춰 보니, 그룹에 기본 정의서를 저장하는 것이 U3-4 의 성질 하나를 망가뜨린다는 것이 드러났기 때문이다. 근거는 §8 DEC-A 에 전부 적었다. 권고를 유지하는 편이 문서로는 매끄럽지만, 매끄러움 때문에 설계를 굳히지 않는다.
§1. 현재 상태 (실측 진단)

있는 것 — 단일 서버 할당은 완성돼 있다

AssignmentCommandService.assign(guestId, definitionId) 이 게스트와 정의서를 로드하고, 정의서 할당 가능 가드(SettingDefinition.assignBlockReason, 비활성이면 409)와 활성 유일성 가드(이미 활성 스냅샷이 있으면 409)를 통과하면 deriveSnapshot 이 정의서를 행 단위로 복사해 얼린다. 각 SettingProcess 가 AssignedProcess 로 무변환 복사되고, BASIC_SETTING 은 참조 BIOS 세팅 템플릿을 resolve 해 FrozenBiosSettings 로 deep-freeze 한다. ownedPhases 는 SettingProcessPhaseMapper 가 derive 해 얼린다.

reassign 은 미개시 활성 스냅샷만 논리 종료(supersede)하고 현재 정의서로 새 활성을 만든다. 차단 판정은 SettingAssignment.reassignBlockReason() 하나이고, 서버 가드와 서버 상세의 버튼 disabled + tooltip 이 그 한 메서드를 함께 부른다.

AssignmentStartService.startProvisioning 은 개시와 활성 스냅샷 소비(markConsumed)를 한 트랜잭션으로 묶는다 — execution 을 직접 고치지 않고 provisioning 이 오케스트레이터를 소유하는 형태이며, 이 슬라이스가 그대로 본뜰 선례다.

있는 것 — 그룹은 U3-4 가 세웠다

GuestServerGroup(이름 유일 · 멤버는 guest_server_id UNIQUE 로 서버 대 그룹 N 대 1 을 구조로 강제) · GuestServerGroupCommandService(생성 · 이름 변경 · 멤버 추가 · 제외 · 삭제) · 상세 화면(멤버 표 · 서버 넣기 모달 · 구성 혼재 배너) · 목록 화면 · 서버 목록의 그룹 배지.

없는 것 — 그룹과 할당은 아직 만난 적이 없다

그룹 상세 어디에도 세팅 정의서라는 말이 없다. 멤버 표는 이름 · SMBIOS UUID · 보드 모델 · 구성 · 현재 단계 · 운영 상태 · 제외 버튼을 보여줄 뿐 그 서버가 어떤 정의서를 할당받았는지 알려주지 않는다. 그룹 20 대에 같은 정의서를 주려면 서버 상세를 20 번 열어 20 번 제출해야 한다. 이 단계가 없애려는 것이 그것이다.

없는 것 — 회수된 서버의 할당을 막는 것이 하나도 없다 (실측 발견)

AssignmentCommandService 의 assign 과 reassign 어느 쪽에도 decommissionedAt 검사가 없다. 화면도 마찬가지다 — templates/provisioning/server-detail.html 의 할당 폼 노출 조건은 th:unless="${phaseRail.assigned}" 하나뿐이라 회수된 서버에도 할당 폼이 그대로 열린다.

이것이 지금 문제가 되지 않은 이유는 아무도 회수된 서버에 정의서를 줄 이유가 없었기 때문이지, 막혀 있어서가 아니다. Notion U3-5 페이지의 ③ 은 "회수된(DECOMMISSIONED) 서버는 이 단계의 할당 가드에서 배제한다" 고 정해 두었는데, 일괄 경로만 막고 단일 경로를 열어두면 같은 금지가 경로에 따라 갈린다. §8 DEC-F 가 이 처리를 정한다.

없는 것 — 정의서가 요구하는 메인보드와 서버의 실제 보드를 대조하지 않는다 (실측 발견)

정의서의 펌웨어 업데이트(BasicUpdateRequest)와 BIOS 설정(BasicSettingRequest) 단계는 메인보드 선택을 들고 있다 — BoardModelSelectionRequest 의 AUTO(실행 시점 감지) 또는 SPECIFIED(boardModelId)(특정 보드 고정)다. 두 단계가 함께 있으면 같은 선택이어야 한다는 것을 SettingSaveRequest.isBoardSelectionConsistent 가 강제하고, 보드를 지정하면 BIOS 세팅 템플릿이 그 보드 것만 남도록 setting-form.js 가 목록을 걸러낸다.

그 대조는 정의서를 만들 때까지만이다. 할당 선택지를 만드는 JpaSettingQueryService.findAssignable() 은 인자를 받지 않고 isDeleted · assignBlockReason() 만 본다 — 어느 서버에 할당하는지를 알지 못한다. AssignmentCommandService 의 assign · reassign 에도 보드 대조가 없다. 그래서 메인보드 X 전용 정의서를 보드 Y 서버에 할당할 수 있고, 그것을 막는 것이 코드에도 화면에도 없다.

회수 가드와 같은 성질의 공백이다 — 제약은 도메인에 실재하는데(보드가 다르면 그 BIOS 세팅도 그 펌웨어도 적용할 수 없다) 그것을 확인하는 자리가 정의서를 쓰는 화면에만 있고 서버에 붙이는 순간에는 없다. §8 DEC-L 이 이 처리를 정한다.

§2. 요구사항 (확정) + 비목표
  • R1 한 번의 조작으로 팬아웃. 그룹 하나 · 정의서 하나를 고르면 멤버 전원에게 각자의 스냅샷이 생긴다.
  • R2 누르기 전에 무엇이 일어날지 보인다. 몇 대가 새로 할당되고 몇 대가 교체되며 어느 서버가 왜 빠지는지를 실행 전에 표로 본다.
  • R3 멤버별 할당 상태가 그룹 상세에서 보인다. 어떤 정의서를 받았는지, 아직 못 받았는지.
  • R4 순차 입고가 눈에 띈다. 나중에 합류한 서버가 아직 정의서를 못 받았다는 사실이 그룹을 열면 바로 드러난다.
  • R5 대상이 아닌 서버는 사유와 함께 빠진다. 회수된 서버 · 이미 개시된 서버 · 정의서가 요구하는 메인보드와 다른 서버.
  • R6 프로비저닝이 불가한 멤버는 적색으로 드러난다. 구성이 갈린 것을 노란색으로 알리는 것과 같은 자리에, 지금 든 정의서로는 진행할 수 없는 서버를 적색으로 표시한다. 그룹 전체의 조작을 막지는 않는다.
비 목표 (어디로 가는지 함께 적는다) :
  • 그룹 엔티티 · 멤버십 · 화면 골격 — U3-4 소관(완료).
  • 단일 서버 할당 · 재할당의 원자성 규칙 재설계 — U3-1 · U3-2 확정분을 그대로 호출하고 손대지 않는다.
  • 그룹 단위 개시(start) — 이 단계는 할당까지다. 개시는 서버별 조작으로 남는다. 개시는 게스트가 실제로 부팅해 체크인하는 실행 영역과 맞물리므로 일괄 조작의 실패 의미가 할당과 다르다.
  • 그룹 단위 진행 현황 요약(그룹 N 대 중 몇 대가 어느 phase 인지) — 멀티 서버 swimlane 과 합류하는 후속.
  • 태그 · 다중 소속 — U3-4 DEC-B 가 서버 대 그룹을 N 대 1 로 확정했다.
🎬 미리보기 — 일괄 할당 미리보기 라이브 데모

상단에서 일괄 할당할 정의서를 고르고, 각 멤버 행의 세그먼트로 그 서버의 현재 상태를 바꿔 보세요. 행마다 분류 배지(할당 / 교체 / 이미 동일 / 제외)와 판정식이 즉시 갱신되고, 적용할 대상이 하나도 없으면 실행 버튼이 잠깁니다.

일괄 할당할 정의서
확정

판정 JS (서버 도메인 메서드와 1:1 — 드리프트 0)

function demoClassify(row, target) {
    const def = DEMO_DEFS[target];
    if (row.state === 'decommissioned') {
        return {action: 'BLOCKED', reason: '회수된 서버에는 세팅 정의서를 할당할 수 없습니다'};
    }
    if (row.state === 'started') {
        return {action: 'BLOCKED', reason: '이미 개시되어 재할당할 수 없습니다(회수 후 재등록 필요)'};
    }
    if (def.board !== null && row.board !== null && def.board !== row.board) {
        return {action: 'BLOCKED', incompatible: true,
                reason: '이 정의서는 메인보드 ' + def.board + ' 전용입니다 — 이 서버는 ' + row.board + ' 입니다'};
    }
    // 보드를 아직 모르면 막지 않는다 — 수집 전 서버에 미리 할당해 두는 흐름을 끊지 않기 위해서다(DEC-L).
    const unknownBoard = (def.board !== null && row.board === null);
    if (row.state === 'none') {
        return {action: 'ASSIGN', unknownBoard: unknownBoard};
    }
    return row.state === target
        ? {action: 'UNCHANGED'}
        : {action: 'REPLACE', unknownBoard: unknownBoard};
}

이 순서와 문자열은 서버의 MemberAssignmentAction.classify 및 GuestServer.assignBlockReason() · SettingAssignment.reassignBlockReason() · RequiredBoardModel.blockReasonFor(...) 가 돌려주는 것과 같다. 회수 판정이 개시 판정보다 앞서는 것은 GuestServerStatus.derive 가 회수를 신호와 무관한 최우선으로 두는 것과 같은 순서다. 보드 대조가 그 뒤인 것은 이미 개시된 서버에는 보드가 맞든 아니든 손댈 수 없기 때문이다 — 운영자가 지금 할 수 있는 일을 사유로 보여주는 것이 낫다.

데모에서 체험시키고 싶은 것 — 정의서 세그를 db-node 로 바꾸면 srv-02 와 srv-03 의 판정이 서로 뒤바뀐다. 같은 멤버 구성이라도 무엇을 고르느냐에 따라 교체 대상이 달라진다. srv-04 를 회수 로 바꾸면 사유 문구가 바뀌지만 결과는 여전히 제외다. 모든 행을 개시 나 회수 로 바꾸면 실행 버튼이 잠기고 이유가 tooltip 으로 뜬다 — 이 화면이 "실행해 보고 실패를 알려주는" 방식이 아니라 누르기 전에 결과를 확정해 보여주는 방식임을 보여주는 자리다.
보드 호환을 확인하는 자리 — bios-ms03 (MS03-CE0 전용) 을 고르면 보드가 X11SPM 인 srv-05 만 적색 '보드 불가' 로 떨어지고 나머지는 그대로 진행된다. 그룹 전체의 조작은 막히지 않는다 — 맞는 멤버는 할당되고 안 맞는 한 대만 사유와 함께 빠진다. 보드를 아직 모르는 srv-01 은 막지 않고 '보드 확인 전' 회색 표식만 단다. 수집 전 서버에 미리 할당해 두는 흐름을 끊지 않기 위해서다(DEC-L).

§4. 도메인 모델 (SSOT)

REPLACE다른 정의서가 미개시로 걸려 있다reassign(guestId, definitionId)
UNCHANGED이미 같은 정의서다없음
BLOCKED대상이 아니다없음

BLOCKED 를 사유별로 쪼개지 않은 것은 의도다. 사유 문자열은 이미 도메인 SSOT 메서드가 돌려주므로(회수는 GuestServer.assignBlockReason(), 개시는 SettingAssignment.reassignBlockReason(), 보드 불일치는 RequiredBoardModel.blockReasonFor(...)) enum 이 사유를 다시 열거하면 같은 지식이 두 곳에 생긴다. 차단 사유가 둘에서 셋으로 늘어난 이번 개정에서 상수가 하나도 늘지 않은 것이 이 설계의 값어치다.

다만 보드 불일치인지 아닌지는 화면이 알아야 한다 — 적색으로 표시할 대상이기 때문이다(DEC-L). 그래서 분류 결과를 담는 행 DTO 가 사유 문자열과 함께 incompatible 불리언을 싣는다. 분류 상수가 아니라 행의 부가 정보로 두는 이유는, 그것이 도메인 판정의 갈래가 아니라 표시 방식의 갈래이기 때문이다.

실행 동작은 상수별 메서드로 둔다(apply(...)) — 분기문에 줄을 늘리지 않는 CLAUDE.md 불가침 규칙 그대로다. UNCHANGED 와 BLOCKED 는 아무것도 하지 않는 구현을 갖는다.

판정은 static 진입점 하나다:

MemberAssignmentAction.classify(String serverBlockReason,
                                String boardBlockReason,
                                SettingAssignment active,
                                Long targetDefinitionId)

미리보기와 실행이 이 한 메서드를 함께 부른다. 두 곳이 각자 조건을 만들면 "미리보기에는 할당이라 나왔는데 실제로는 교체가 됐다" 같은 어긋남이 생긴다. 두 차단 사유를 이미 판정된 문자열로 받는 것은 이 메서드가 엔티티 그래프를 타지 않게 하기 위해서다 — 판정은 각 도메인이 하고, 이 메서드는 순서를 정한다.

보드 대조가 개시 판정 뒤인 것에는 이유가 있다. 이미 개시된 서버는 보드가 맞든 아니든 손댈 수 없으므로, 운영자에게 보여줄 사유는 "지금 무엇 때문에 아무것도 할 수 없는가" 여야 한다. 회수가 맨 위인 것은 GuestServerStatus.derive 가 회수를 신호와 무관한 최우선으로 두는 것과 같은 순서다.

도메인 메서드 신설 — GuestServer.assignBlockReason()

회수됐으면 "회수된 서버에는 세팅 정의서를 할당할 수 없습니다", 아니면 null. SettingAssignment.reassignBlockReason() · GuestServerGroup.addBlockReason() · SettingDefinition.assignBlockReason() 과 같은 형태다 — null 이면 통과, 문자열이면 그것이 화면 tooltip 이자 서버 거절 사유다.

이 한 메서드를 세 곳이 함께 부른다: ① 일괄 할당의 사전 분류 ② 단일 할당 · 재할당의 서버 가드 ③ 서버 상세의 할당 폼 1차 차단.

새 타입 — RequiredBoardModel (Value Object, provisioning/setting/vo/)

"이 정의서가 요구하는 메인보드" 를 이름 있는 값으로 세운다. Long boardModelId 를 컨트롤러와 서비스가 맨손으로 들고 다니면 그 값이 서버의 보드인지 정의서가 요구하는 보드인지 타입이 말해 주지 않는다(Primitive Obsession 금지).

구성내용
필드Long id · String name
추출static RequiredBoardModel from(List<AbstractProcessRequest>) — 보드를 지정한 단계가 없거나 전부 AUTO 면 null
판정String blockReasonFor(Long serverBoardId, String serverBoardName) — 통과면 null

추출을 List<AbstractProcessRequest> 에서 하는 것이 중요하다. 정의서 원본(SettingDefinition.getProcesses())과 할당 스냅샷(SettingAssignment.getProcesses())이 같은 payload 타입을 들고 있으므로(U3-1 이 무변환 복사한다) 같은 추출 코드가 양쪽에 그대로 쓰인다. 미리보기는 원본에서, 멤버 표의 적색 판정은 스냅샷에서 뽑는다 — 얼린 정의서가 요구하는 보드는 원본이 나중에 바뀌어도 스냅샷이 들고 있는 그 값이어야 하기 때문이다.

보드를 지정하는 단계는 펌웨어 업데이트와 BIOS 설정 둘뿐이고, 둘이 함께 있으면 같은 선택이어야 한다는 것을 SettingSaveRequest.isBoardSelectionConsistent 가 이미 강제한다. 그래서 정의서 하나가 요구하는 보드는 최대 하나이고, 추출이 모호해질 자리가 없다.

  • SettingDefinition.assignBlockReason() — 비활성 정의서 차단(선택지 필터와 서버 가드가 이미 공유)
  • GuestServerStatus.derive — 운영 상태 도출

재사용

GuestServerGroupNotFoundException(404) · SettingNotFoundException(404) · DefinitionNotAssignableException(409) · GuestServerNotFoundException(404) · MethodArgumentNotValidException(400).

사용자가 이 예외를 보게 되는 경로

정상 흐름에서는 보이지 않아야 한다. 회수된 서버는 미리보기에서 사유와 함께 제외로 표시되고 서버 상세에서는 할당 폼 자체가 닫힌다. 보드가 맞지 않는 정의서는 서버 상세의 선택지에서 disabled 로 잠기고 사유가 라벨에 붙으며, 일괄 할당 미리보기에서는 적색 제외로 뜬다. 예외가 실제로 뜨는 것은 direct POST · 동시 조작 · 다른 탭에서 회수되거나 하드웨어가 갱신된 뒤의 stale 제출뿐이다.

선택지에서 지우지 않고 잠그는 것은 의도다. 목록에서 조용히 사라지면 운영자는 그 정의서가 없어진 것인지 자기 서버에 안 맞는 것인지 알 수 없다. definition-options 조각이 이미 사용 중단 권고를 라벨에 덧붙이고 있으므로 같은 자리에 사유를 붙인다 — "왜 막혔는지 알 수 있는가" 를 CP5 에서 확인한다(C 계열 항목).

폼 규약 (new-form.md)

일괄 할당 폼의 핸들러는 BindingResult 를 받지 않는다(성공은 redirect, 실패는 예외). 따라서 data-native-submit 을 붙이지 않는다 — 전역 인터셉터가 fetch 로 보내 안내 모달로 수렴한다. 성공 후 이동도 기본 동작(현재 페이지 재적재)이 맞다. 재적재하는 곳이 그룹 상세이고 결과가 거기 있기 때문에 AsyncSubmitResult 를 덮어쓸 이유가 없다. FormSubmissionConventionTest 의 기대값은 변하지 않는다.

§8. 결정 · Open Questions

DEC-A. 할당 의미론 = 팬아웃. 그룹에 기본 정의서를 저장하지 않는다

검토한 대안 셋:

안내용판정
① 팬아웃그룹은 도구. 할당하면 멤버 각각에 스냅샷이 생기고 그룹은 관여를 끝낸다채택
② 그룹이 주체할당이 그룹을 가리키고 멤버는 실행 시점에 조회탈락
③ 팬아웃 + 저장된 기본 정의서그룹이 정의서를 기억해 새 멤버에게 자동 적용탈락(권고를 뒤집음)

②가 탈락하는 이유는 U3-1 의 스냅샷 원칙과 정면으로 부딪히기 때문이다. 정의서를 할당 즉시 얼린 것은 정의서가 나중에 수정돼도 진행 중인 서버가 흔들리지 않게 하려는 것이었는데, 그룹을 경유하면 "언제의 정의서인가" 가 서버가 그룹에 들어온 시점인지 그룹에 할당한 시점인지로 갈려 정의되지 않는다. 진행 중인 서버를 그룹에서 뺐을 때의 의미도 규정할 수 없다.

③은 재편 토론이 권고한 안인데 이 plan 에서 뒤집는다. 뒤집는 근거 넷:

첫째, 가입과 탈퇴가 비대칭이 된다. 그룹에서 빼는 것과 할당을 해제하는 것은 별개 행위로 둔다(DEC-K, 아래). 여기에 "가입하면 자동 할당" 을 더하면 가입은 스냅샷을 만들고 탈퇴는 그것을 지우지 않는 구조가 된다. 지금 그룹 가입은 값싸고 되돌리기 쉬운 조직 행위다 — U3-4 DEC-E 가 그룹을 지워도 서버와 그 서버의 할당은 그대로 남게 한 것이 그 성질이다. 자동 할당이 붙는 순간 잘못 넣은 서버 한 대가 스냅샷을 남기고, 운영자는 그것을 따로 찾아 되돌려야 한다.

둘째, 자동 적용의 실패가 침묵이다. 새로 들어온 멤버가 이미 활성 할당을 갖고 있거나 이미 개시됐다면 자동 적용은 건너뛸 수밖에 없다. 그러면 "그룹 멤버는 모두 기본 정의서를 따른다" 는 약속이 말없이 깨진다. 반대로 덮어쓰게 하면 더 나쁘다 — 운영자가 개별로 정한 선택을 가입이 지운다.

셋째, 정의서 lifecycle 과 새 결합이 생긴다. 저장된 기본 정의서는 소프트참조가 되고, 그 정의서가 비활성화되거나 삭제되면 그룹이 쓸 수 없는 참조를 들고 있게 된다. U3-2-b 가 assignBlockReason 으로 정리한 판정을 그룹 쪽에서 되풀이해야 하고, 화면에 표시할 상태가 하나 더 는다.

넷째, 순차 입고 시나리오는 저장 없이도 풀린다. 아래 DEC-B 가 그 방법이다.

③은 나중에 얹을 수 있다는 점도 판단에 넣었다. 저장된 기본 정의서는 "기준 정의서를 어떻게 정하는가" 만 바꾸고 팬아웃 기구 자체는 그대로 쓰므로 가산적이다. 지금 넣지 않는 쪽이 되돌리기 쉽다.

DEC-B. 그룹의 기준 정의서는 저장하지 않고 파생한다

멤버들의 활성 할당에서 다수파 정의서를 계산해 일괄 할당 select 의 기본 선택으로 제시하고, 아직 할당받지 못한 멤버 수를 배너로 알린다. 자동 실행은 없다 — 제안까지다.

U3-4 가 구성 혼재를 판정할 때 이미 같은 방식을 쓴다(majorityKeyOf 로 다수파 구성을 구해 소수파를 표시). 같은 화면에서 같은 형태의 판정이 둘이 되므로 읽는 사람에게 새 개념이 아니다.

순차 입고 시나리오는 이렇게 풀린다. 나중에 서버 세 대가 등록되어 그룹에 합류하면, 그룹 상세는 "3 대가 아직 정의서를 할당받지 않았습니다" 를 띄우고 select 는 나머지 멤버가 쓰는 정의서를 이미 가리키고 있다. 운영자는 [미리보기 후 할당] → [확정] 두 번을 누른다. 자동 적용보다 클릭이 두 번 많은 대신, 일어난 일이 전부 보이고 조작 없이 상태가 바뀌는 일이 없다.

DEC-C. 사전 분류 → 미리보기 → 실행

차단 사유가 전부 실행 전에 알 수 있는 결정적 도메인 술어다(회수 여부 · 개시 여부 · 현재 정의서). 그러므로 "실행해 보고 실패를 보고" 할 필요가 없다. 실행 전에 분류해 보여주면 운영자는 확정 전에 결과를 안다.

이것이 아래 DEC-E(부분 실패 정책)를 단순하게 만든다 — 예측 가능한 실패가 전부 사전 분류에 흡수되므로, 실행 시점에 남는 실패는 동시 조작과 stale 뿐이다.

DEC-D. 미개시 활성 할당은 교체 대상에 포함한다

대안은 "미할당 서버만 건드리고 이미 할당된 것은 손대지 않는다" 였다. 안전하지만 그룹을 하나의 정의서로 수렴시킬 수 없다.

채택 근거는 사용자가 설명한 운영 모델이다 — 세팅 도중 요구가 바뀐 몇 대는 그룹에서 빼는 것으로 처리한다. 그룹에 남아 있다는 것은 그룹의 정의서를 따른다는 뜻이다. 그러므로 일괄 할당은 그룹 전체를 고른 정의서로 수렴시키는 것이 맞다.

침묵 파괴의 위험은 미리보기가 없앤다 — "2 대는 db-node 에서 web-standard 로 교체됩니다" 를 확정 전에 본다. 개시된 것은 reassignBlockReason() 이 막으므로 진행 중인 서버가 다칠 자리는 없다.

DEC-E. 부분 실패 정책 = 전부 아니면 전무 (단일 트랜잭션)

GroupAssignmentCommandService.assignAll 이 @Transactional 하나이고, AssignmentCommandService.assign · reassign 은 기본 전파(REQUIRED)로 그 트랜잭션에 조인한다. 하나가 실패하면 통째로 롤백된다. AssignmentStartService 가 개시와 소비를 한 트랜잭션으로 묶은 것과 같은 형태다.

대안은 서버마다 별도 트랜잭션으로 돌려 성공분을 유지하고 실패 목록을 보고하는 것이었다. 탈락 이유 둘 — 그룹이 반쯤 할당된 상태로 남아 운영자가 그것을 머릿속에서 정리해야 하고, 결과 보고 화면을 새로 만들어야 한다. 사전 분류가 예측 가능한 실패를 이미 걷어냈으므로 그 복잡도를 살 값이 없다.

전부 롤백됐을 때 운영자가 하는 일은 새로고침 후 다시 미리보기를 보는 것이다. 그때 미리보기는 바뀐 현실을 반영한다.

DEC-F. 회수 서버 할당 가드를 도메인 SSOT 로 신설하고 단일 경로에도 적용한다

§1 에서 실측한 결함이다 — 지금은 회수된 서버에 정의서를 할당할 수 있고 그것을 막는 것이 코드에도 화면에도 없다.

Notion U3-5 ③ 은 회수된 서버를 이 단계의 할당 가드에서 배제하라고 정해 두었다. 일괄 경로만 막으면 같은 금지가 경로에 따라 갈린다 — 그룹에서는 제외되는 서버가 서버 상세에서는 할당된다. 그래서 판정을 GuestServer.assignBlockReason() 하나로 두고 일괄 · 단일 · 화면이 함께 부른다.

이것이 U3-1 이 만든 경로를 건드리는 것은 맞다. 다만 범위 확장이 아니라 일관성 복구로 본다 — 새 기능을 얹는 것이 아니라 이 단계가 정한 규칙을 이미 있는 같은 성격의 경로에 같이 적용하는 것이다. 그럼에도 U3-1 을 손대는 일이므로 승인 대상으로 명시한다(OQ-1).

DEC-G. 코드 배치 = group → assignment 단방향

일괄 할당 서비스를 provisioning/group/service/ 에 둔다. 그룹 상세가 멤버의 할당을 보여줘야 하므로 group → assignment 참조는 어차피 필요하고, 반대로 assignment 가 group 을 알게 되면 양방향이 된다. 실측으로 확인했다 — provisioning/assignment 와 execution 어느 쪽도 provisioning.group 을 참조하지 않는다.

의존 방향은 group → assignment → execution 한 줄이 된다. R7 이 제거한 생성자 순환을 되살리지 않는다.

DEC-H. 분류는 enum 다형, 판정은 진입점 하나

실행 동작은 MemberAssignmentAction 의 상수별 메서드가 갖는다. 새 분류가 생기면 컴파일이 그 자리를 채우도록 강제한다. 판정 자체(classify)는 한 곳의 순차 판정이고, 그것이 도메인 invariant 판정이므로 정당하다 — 금지 대상은 도메인이 늘 때마다 여러 곳에서 함께 자라는 분기다.

DEC-I. 화면 배치

그룹 상세에 '세팅 정의서 일괄 할당' 섹션을 둔다. 정의서 select(다수파 기본 선택) + [미리보기 후 할당] 버튼 → 모달에 조각을 채워 분류표를 보이고 → [확정] 으로 제출한다. U3-4 의 서버 넣기 모달과 같은 형태다 — 사용자가 그때 "진입 시퀀스를 한두 단계 더 가져가라" 고 요구한 것이 이 자리에도 그대로 적용된다.

멤버 표에 '할당된 정의서' 열을 더하고, 그룹 목록에 할당 진척(예: 3/5)을 더한다. 목록에서 손볼 그룹이 있는지 열어보기 전에 알 수 있게 하는 것으로, 구성 혼재를 목록에서 알리는 것과 같은 자리다.

DEC-J. 정의서 선택지는 기존 조각을 재사용한다

fragments/provisioning/definition-options :: definitionOptions 와 SettingQueryService.findAssignable() 을 그대로 쓴다. 삭제 · 비활성 정의서가 애초에 목록에 없고 사용 중단 권고는 라벨에 붙는 규칙이 서버 상세와 같아진다. 새로 만들면 두 화면의 라벨 규칙이 갈린다.

DEC-K. 그룹에서 빼는 것과 할당을 해제하는 것은 별개 행위다

재편 토론이 U3-5 로 넘긴 쟁점(Q4)이다. 멤버를 그룹에서 빼면 그 서버의 활성 할당은 그대로 남는다. 제외가 뜻하는 것은 "이 그룹의 일괄 조작 대상이 더는 아니다" 까지이고, 정의서를 실제로 바꾸거나 없애는 일은 U3-2 가 만든 재할당 경로(미개시일 때만 가능)로 한다.

대안은 제외와 동시에 할당을 해제하는 것이었다. 탈락 이유는 진행 중인 서버가 다치기 때문이다 — 이미 개시된 서버를 그룹에서 빼는 순간 그 서버가 밟고 있던 계획이 사라지면, 실행 엔진이 참조할 스냅샷이 없어진다. 게다가 그룹 제외는 지금 값싸고 되돌리기 쉬운 조직 행위인데(U3-4 DEC-E 가 그룹을 지워도 서버와 할당을 남긴 것이 그 성질이다) 여기에 파괴적 부작용이 붙으면 성질이 달라진다.

사용자가 든 "세팅 도중 특정 몇 대만 요구사항이 바뀌는" 상황이 이 분리로 풀린다. 그 몇 대를 그룹에서 빼면 이후 일괄 할당이 건드리지 않게 되고, 새 요구에 맞는 정의서는 서버 상세에서 개별로 재할당한다. 이 슬라이스가 추가하는 코드는 없다 — 제외는 U3-4 가 만든 그대로이고, 이 결정은 그 동작을 바꾸지 않기로 한 것이다.

DEC-L. 보드 호환을 할당 시점에 대조하고, 불가한 멤버를 적색으로 표시한다

정의서의 펌웨어 업데이트 · BIOS 설정 단계가 특정 메인보드를 지정했다면(SPECIFIED) 그 정의서는 그 보드의 서버에만 적용할 수 있다. §1 에서 실측했듯 이 대조는 정의서를 만드는 화면에만 있고 서버에 붙이는 순간에는 없다. 이 슬라이스에서 할당 시점으로 옮긴다.

차단이 아니라 표시인 것이 핵심이다. 구성이 갈렸다고 그룹 조작을 막지 않은 것(U3-4 DEC-I)과 같은 판단이며, 다만 색이 다르다 — 노란색은 "의도한 것일 수 있다", 적색은 "이대로는 프로비저닝이 진행되지 않는다" 다. 한 행이 둘 다에 해당하면 적색이 이긴다. 갈렸다는 사실보다 진행이 불가하다는 사실이 무겁기 때문이다.

보드를 아직 모르는 서버는 막지 않는다. 수집 전 서버에 미리 정의서를 할당해 두고 부팅시키는 흐름이 실재하는데, 모른다는 이유로 막으면 그 흐름이 끊긴다. 대신 미리보기 행에 보드 확인 전 회색 표식을 달아 대조하지 못했다는 사실 자체를 보이게 한다 — 조용히 통과시키는 것과 다르다.

대안으로 맞지 않는 멤버가 하나라도 있으면 일괄 할당 전체를 거절하는 안을 검토했다. 탈락 이유는 그룹이 보드를 섞을 자유를 갖기 때문이다(U3-4 DEC-A 가 스펙을 정체성에서 뺐다). 20 대 중 1 대가 다르다고 19 대의 할당을 막으면, 운영자는 그 1 대를 그룹에서 빼야만 진행할 수 있게 되어 그룹 편성이 할당에 종속된다. 사용자가 요구한 것도 "그룹 자체에 할당을 막는 것은 아니다" 였다.
