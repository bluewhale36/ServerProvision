§1. 배경
  • 자원 등록 중 같은 이름 · 같은 내용이 감지되면 '중복 확인 창'(nudge)이 [그래도 등록] · [기존 영구 삭제 후 등록] · [취소] 를 묻는다. 창 설명은 "그래도 등록 : 새 자원으로 등록 (기존 자원은 그대로 보존)" · "기존 영구 삭제 후 등록 : 기존 자원을 영구 삭제하고 새 자원을 등록".
  • docs 세션(DOC-7 매뉴얼)이 이 버튼들이 실패하거나 설명과 다르게 동작하는 결함을 찾았고(C-3 · C-10 · C-17), 앵커가 RAID 카드와 HF27 CP5 관찰 두 건을 더해 M 홈에 넘겼다. 매뉴얼은 지금 이 버튼들을 쓰지 말라는 경고를 싣고 있다.
  • 선례: 앵커 HF26(#103) 메인보드 — 창을 없애고 (제조사, 모델명) 복합 UNIQUE(휴지통 행도 점유) + 상태별 409 안내(DuplicateBoardModelException.againstRegistration).

§3. 결론
  • 공통 원인: "창을 띄우는 조건" 과 "[그래도 등록] · [기존 영구 삭제 후 등록] 을 받아 주는 조건" 이 자원마다 다른 코드에 따로 있고 서로 어긋난다. 그리고 영구 삭제 버튼이 영구 삭제 공통 경로를 지나지 않는다.
  • 자원 성격이 두 갈래다: 메타 자원(OS 버전 · RAID 카드 · 메인보드)은 키가 곧 정체라 '같은 것을 하나 더' 가 성립하지 않고, 파일 자원(ISO · BIOS · BMC · 드라이버)은 같은 이름의 새 버전 · 휴지통의 옛것과 별개인 새 업로드가 정상이다.

#채택비채택사유
D1 create 가 같은 키를 상태 무관 1 건이라도 찾으면 409 + 상태별 다음 행동(휴지통 → 복구 또는 영구 삭제 / Deprecated → 해제 / 활성 → 이미 등록됨) · 중복 확인 창 · OSMetadataNudgeService · RaidCardNudgeService · 컨트롤러 · JS 처리 · NudgeResourceType.OS_IMAGE · RAID_CARD 제거 창 유지 + 조건 맞춤U1 · U2
D2 상태별 다음 행동 문구는 LifecycleStage 상수별 메서드 한 곳이 소유하고 OS 버전 · RAID 카드 예외가 쓴다(메인보드 againstRegistration 의 if 세 갈래를 자원마다 복제하지 않음). 메인보드의 같은 판정도 이 메서드로 옮길지는 앵커 판단(HF26 소유) 자원별 예외에 if 세 갈래 복제CLAUDE.md 조건분기 확장 금지 · 같은 문장 SSOT
D3 DDL ddl/HF30_meta_identity.sql: os_metadata UNIQUE (os_name, os_version) · raid_card 는 생성 컬럼 active_identity UNIQUE 를 (vendor, model_name) UNIQUE 로 교체. 적용 전 같은 키 다건 조회 SELECT 를 같은 파일 머리에 두고, 다건이 있으면 적용을 멈추고 사람에게 넘긴다(자동 삭제 안 함). 이름 · 인덱스 명은 환경마다 다를 수 있어 찾아서 처리(HF26 방식) 다건 자동 정리어떤 행을 남길지는 사람 판단 · HF26 선례
D4 복구 · Deprecated 해제 경로: UNIQUE 가 휴지통까지 점유하므로 같은 키 두 행이 생길 수 없다 — 기존 '살아 있는 같은 키면 409' 가드는 안전망으로 둠 ——

HF30-2 파일 자원 (ISO · BIOS · BMC · 드라이버)

#채택비채택사유
D5 창 후보 = 휴지통 행만(업로드 전 intent · 업로드 뒤 내용 창 모두). Deprecated · 활성 같은 키는 창 없이 409 + 상태별 안내(D2 와 같은 문구 SSOT). 단 ISO 의 '활성 같은 내용' 은 범위 밖 callout 대로 업로드 전이 아니라 배경 안전망(ⓑ)에서 막는다 Deprecated 를 창에 남기고 replace 때 휴지통을 거쳐 영구 삭제U3 — 한 번의 클릭으로 살아 있는 자원이 사라지지 않게
D6 [기존 영구 삭제 후 등록] = PurgeExecutor + PurgeRequest.forNudgeReplace(NUDGE_REPLACE) — 감사 기록(purge_log) · 휴지통 실물 정리 · 도메인 거절 비감싸기(HF26 정정)를 그대로 얻는다. 대상은 휴지통 행뿐이라 PurgeExecutor 의 '휴지통 자원만' 전제와 맞는다 각 *NudgeService 가 lifecycle purge 직접 호출(현행)R7 · 앵커 HF31 제안
D7 드라이버: intent 요청에 이름을 넣어 사전 검증 키를 (종류, 범위, 이름, 버전)으로 등록 본체와 같게 하고, 활성 · Deprecated 같은 키는 업로드 전에 409. 등록 본체는 같은 키 휴지통 행을 거절하지 않는다(휴지통 옛것과 새것의 공존 — 창이 이미 물었다) intent 는 그대로 두고 본체만 완화업로드가 끝난 뒤 실패하는 것이 결함의 본체
D8 ISO: 배경 finalize 의 같은 내용 검사 범위를 같은 OS 로 좁힘(U4). 업로드 전 판정이 같은 OS 의 휴지통 · Deprecated 를 지문으로 보도록 보강한다 — 경로 창 [그래도 등록] 뒤 재발급(issueAfterNudge)이 지문을 버려 내용 판정을 건너뛰던 것을 고쳐, 경로 창 다음에도 내용 판정을 이어 한다. 그래야 배경 단계의 휴지통 nudge(ⓒ)를 제거해도 다른 경로의 같은 내용 휴지통 ISO 를 놓치지 않는다. ⓒ 는 제거 → 화면 미연결(docs 결함 D7)도 함께 사라짐. 배경의 '살아 있는 같은 내용' 검사(ⓑ)는 경합 안전망으로 같은 OS 범위에서 유지 배경 nudge 를 화면에 연결두 단계 판정이 결함의 원인 — 판정을 업로드 전 한 곳으로
D9 같은 경로를 다시 쓴 새 업로드 트리를 replace 가 지우는 경로(코드상 성립): 앵커 HF31 의 마커 판정(isMarkedAs · purgeOwnedTree)이 도메인 purge 에 들어오면 막힌다 → HF30-2 는 HF31 병합 뒤 그 위에서 진행 HF30 이 따로 가드 추가같은 판정을 두 번 만들지 않음(HF31 소유)
