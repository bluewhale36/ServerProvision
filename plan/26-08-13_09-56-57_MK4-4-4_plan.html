§1. 현재 상태 (진단)

MK4-4-2 가 첫 화면 · 회차 상세 · 드리프트 상세를 다시 그리며 reconciliation 영역의 시각 언어를 정했다. 운영 설정만 그 언어를 따르지 않는다 — MK4-3-1 이 만든 옛 모양 그대로다.

이 슬라이스의 유래. 본래 MK4-4-3 이 보관 화면과 함께 담고 있었다. 구현을 마치고 갈래별 규모를 재 보니 설정 계열이 보관 계열의 약 5 배였고(아래 표), 두 화면이 공유하는 도메인 개념이 없어 CP5 검증이 두 줄기로 갈렸다. 한 report 안에 서로 무관한 검증 두 묶음이 들어가면 어느 한쪽이 얕아져도 전체 분량에 묻히므로 2026-08-13 에 떼어냈다.

2026-08-11 분할 때 "MK4-4-3 이 커지면 다시 나눈다" 는 조건을 미리 걸어 두었고 그것이 실제로 발동했다. 다만 무거운 쪽은 예상과 반대였다 — 그때는 보관을 중심으로 보았는데, 보관은 도메인이 이미 다 있어 화면만 붙이면 됐고 설정은 화면을 통째로 다시 그리는 일이었다.

실측 ① 항목 7 개가 묶음 없이 평평하다

settings.html 은 ReconciliationSettingItem 의 일곱 상수 (AUTO_APPLY_KINDS · RESOLUTION_ENABLED · REPORT_RETENTION_COUNT · EXTRA_SCAN_ROOTS · STARTUP_SCAN_ENABLED · SCAN_INTERVAL · DEEP_SCAN_INTERVAL)를 한 줄로 늘어놓는다. 무엇끼리 관련 있는지가 보이지 않고, 채택된 구조의 양식(n-glist 바깥 묶음 → 흰 판 → 내용)을 쓰지 않는다.

평평함이 특히 아픈 자리가 있다. RESOLUTION_ENABLED 는 그 자체로 "드리프트를 고치는 행위 전체의 차단기" 인데(ReconciliationSettingItem 의 설명 원문), 그것이 AUTO_APPLY_KINDS 와 나란히 평평하게 놓이면 둘이 대등한 항목처럼 읽힌다. 실제로는 앞의 것이 꺼지면 뒤의 것이 아무 효과가 없다.

실측 ④ 저장 버튼에 이중 제출 가드가 없다

MK4-3-2 CP5 에서 결함 ③ 으로 잡힌 것이다. 이 폼은 data-native-submit 이라 전역 fetch 경로(form-submit.js)를 타지 않는다 — 검증에 실패하면 서버가 BindingResult 를 실어 폼을 다시 렌더해야 하기 때문이다. 그래서 전역 가드의 보호도 받지 못했고, 응답이 오기 전에 버튼을 다시 누르면 요청이 두 번 나갔다.

전역 가드 자체가 없었다는 것도 이때 드러났다. form-submit.js 의 주석은 "이중 제출을 막는다" 라고 적혀 있었으나, 그것이 가리키던 것은 핸들러 중복 등록이지 사용자의 연타가 아니었다. 즉 native 폼만 구멍이 난 것이 아니라 fetch 경로에도 실제 가드가 없었다.

이 데모가 보여 주는 것 셋

  1. 차단기가 무엇을 가두는지는 배치가 말한다 — [시스템 해결 끄기] 를 눌러 보라. 묶음 배치에서는 자동 처리 카드 전체가 흐려져 "이 안이 통째로 무의미해졌다" 가 한눈에 보인다. 평평한 배치에서는 체크박스만 흐려지고 그것이 왜 흐려졌는지 옆에 아무 단서가 없다.
  2. 오류의 자리 — 잘못된 값을 넣고 저장하면 위쪽 배너가 "무엇인가 잘못됐다" 를 말하고, 해당 필드 옆의 n-error 가 "무엇이" 를 말한다. 묶음 배치에서는 어느 카드인지까지 보인다.
  3. 저장은 한 번에 일어난다 — 어느 묶음을 고쳤든 저장 버튼은 하나다(§4 D2). 오류가 하나라도 있으면 전부 저장되지 않는다 — 부분 저장이 없으므로 화면에 보이는 값과 저장된 값이 갈라지지 않는다.
드리프트 0 — 데모의 판정식 = 서버 검증 규칙. ReconciliationSettingsRequest 의 어노테이션을 그대로 옮겼다 : 보관 개수 1 ~ 10000, 점검 주기 ScanInterval.MIN_MINUTES(1) ~ MAX_MINUTES(43200), 추가 경로는 Path.of(line).isAbsolute(). 데모가 규칙을 따로 재구현하지 않는다.

§4. 설계 결정 (D1~D5) + 도메인 SSOT

도메인 신설 0 — 배치만 바꾼다

엔티티 · Value Object · Enum 을 새로 만들지 않는다. 설정 항목의 신원 · 설명 · 값 형태 · 기본값은 전부 ReconciliationSettingItem 이 들고 있고, 경계값은 ScanInterval 의 컴파일 상수가 SSOT 다. 이 슬라이스가 더하는 것은 보는 순서다.

있는 것무엇이 SSOT 인가
ReconciliationSettingItem항목 이름 · 사용자 설명 · 효과 시점 · 값 형태 · 기본값
ScanInterval.MIN_MINUTES / MAX_MINUTES점검 주기 경계값 (1 · 43200). 어노테이션이 이 상수를 직접 참조하므로 숫자가 두 곳에 적히지 않는다
DriftKind.isAutoApplicable() · isReversible()자동 처리 후보 목록과 되돌림 가능 배지
ReconciliationSettingsRequest 의 @AssertTrue경로 절대성 · 알 수 없는 종류 차단
화면이 항목 이름을 하드코딩하지 않는다. 자동 처리 후보는 settings.autoApplyCandidates 를 th:each 로 돌린다 — 자동 처리 등급의 종류가 늘면 화면에 저절로 나타난다. 재배치가 이 성질을 깨뜨리지 않아야 한다(§9 회귀).

D1 — 성질로 넷으로 묶는다

묶음묻는 것항목
점검 주기언제 · 얼마나 자주 도는가STARTUP_SCAN_ENABLED · SCAN_INTERVAL · DEEP_SCAN_INTERVAL
점검 범위어디를 뒤지는가EXTRA_SCAN_ROOTS
자동 처리시스템이 손을 대는가RESOLUTION_ENABLED · AUTO_APPLY_KINDS
기록 보관지난 회차를 얼마나 남기는가REPORT_RETENTION_COUNT

묶는 축은 "언제 · 어디 · 무엇을 · 얼마나" 라는 질문이지 자료형이 아니다. 자료형으로 묶으면 (불리언끼리 · 숫자끼리) 기동 직후 점검과 시스템 해결이 한자리에 오는데 둘은 아무 관계가 없다.

  • 비채택 ① — 자료형별 묶음. 탈락 : 위와 같이 무관한 것이 붙는다.
  • 비채택 ② — 효과 시점(IMMEDIATE / NEXT_SCAN / NEXT_BOOT)별 묶음. 탈락 : 효과 시점은 항목의 부수 성질이지 사용자가 설정을 찾는 단서가 아니다. "점검을 덜 자주 돌리고 싶다" 는 사람이 효과 시점을 먼저 떠올리지 않는다. 다만 버리지는 않는다 — 각 항목 안에 「효과 시점」 보조 문구로 남긴다.

RESOLUTION_ENABLED 와 AUTO_APPLY_KINDS 를 한 묶음에 두는 것이 D1 의 핵심이다. 앞의 것이 차단기이고 뒤의 것이 그 안의 선택이라는 포함 관계가 배치로 드러난다(§1 실측 ①).

D2 — 저장은 묶음별로 나누지 않고 지금처럼 한 번에 한다

묶음별 저장은 폼이 넷이 되고 검증 오류의 자리도 넷으로 갈린다. 설정은 함께 바꾸는 일이 많아 (주기를 늘리며 보관 개수도 줄이는 식) 한 번에 저장하는 편이 조작이 적다.

  • 비채택 — 묶음별 저장. 탈락 : 폼 넷의 상태를 서로 맞추는 비용이 이득보다 크고, 부분 저장 상태가 생긴다 — 셋은 저장되고 하나는 실패한 화면에서 무엇이 실제 값인지 알 수 없다.

D3 — 미정의 클래스는 국지 둘만 정의한다

n-form-label · n-form-hint 를 css/form-validation.css 에 넣는다. 전역 둘(n-form-banner · n-btn-outline)은 빼서 S* 단계로 옮긴다.

기준은 "고치는 범위와 검증하는 범위가 같은가" 다. 전역 둘의 정의를 여기서 넣으면 20 개 넘는 화면이 동시에 바뀌는데 이 슬라이스의 CP5 는 reconciliation 화면만 본다. 나머지 화면이 어떻게 바뀌었는지 아무도 보지 않은 채 커밋되는 것이라, 통과했다는 사실이 근거가 되지 못한다.

D4 — 이중 제출 가드를 두 층에 둔다

이 폼만 막으면 같은 구멍이 다른 native 폼에 그대로 남는다. 그래서 두 곳을 손댄다.

층파일막는 것
이 화면static/maintenance/reconciliation/settings.js 신규native submit 직후 버튼 비활성 + 「저장 중…」
전역static/global/form-submit.jsfetch 경로의 재진입 — WeakSet 으로 in-flight 표시

전역 가드가 WeakSet 인 이유는 폼 요소를 키로 쓰면서 DOM 에서 사라진 폼을 붙들지 않기 위해서다. 일반 Set 은 제거된 폼을 계속 참조해 누수가 된다.

브라우저 기본 검증(required · min · max)에 걸리면 submit 이벤트가 아예 발생하지 않으므로, 이 화면의 가드가 도는 시점은 요청이 실제로 나가는 순간이다 — 값이 틀려서 막힌 사용자가 버튼이 잠긴 채 갇히는 일은 없다.

  • 비채택 — 이 폼에도 전역 fetch 경로를 태운다. 탈락 : 그러면 BindingResult 재렌더가 도달하지 못해 필드별 오류 표시를 잃는다.

D5 — 인라인을 걷으며 새 클래스 이름을 만든다 (계획 정정)

분할 전 계획은 "이미 쓰이고 있는 이름에 정의만 채운다" 였는데, 실제로는 그것으로 부족했다. 인라인 21 곳이 표현하던 배치(토글 한 줄 · 좁은 숫자 입력 · 체크박스 옵션 행 · 경고 문구)는 기존 이름이 없는 형태였다. 정의만 채우고 나머지를 인라인으로 남기면 규약 위반이 그대로 남으므로, form-validation.css 안에 이름을 새로 만들었다.

§8. 예상 부산물 · 주의 · 결정 사항

주의 ① 전역 둘은 세는 일까지가 이 슬라이스의 몫이다

2026-08-13 실측으로 n-form-banner(템플릿 19 · JS 4) · n-btn-outline(템플릿 21 · JS 8)이 전역임이 확정됐고, 그 결과가 비 목표 분리다. 정의를 넣는 일은 S* 단계가 맡으며 그 단계의 검증은 두 클래스를 쓰는 화면 전수를 훑어야 한다 — 특히 n-btn-outline 은 파생 넷과 시각이 어긋나지 않게 기본형을 잡아야 한다.

주의 ② 오류는 배너와 필드 두 곳에 뜨고, 묶음이 넷이면 그 둘이 멀어진다

분할 전 계획이 이 위험을 data-error-field 로 서술했는데 그것은 다른 화면의 기법이다. 실측하면 data-error-field 는 provisioning/setting-form.js 계열에서만 쓰이고 settings.html 에는 없다. 실제 기법은 Thymeleaf 의 th:errors 다.

실제 구조는 이렇다.

자리무엇을 말하는가실측
폼 최상단 배너"무엇인가 잘못됐다" — #fields.errors('*') 전부를 목록으로n-form-banner + n-error-list
각 필드 옆"이것이 잘못됐다"th:errors 4 자리 (점검 주기 · 점검 범위 · 자동 처리 · 기록 보관 — 네 묶음에 하나씩)

필드 오류는 필드를 따라 카드 안으로 함께 들어가므로 매핑이 깨지지는 않는다. 위험은 다른 데 있다 — 카드가 넷이면 화면이 길어져, 최상단 배너를 읽은 사용자가 어느 카드를 봐야 하는지 모른 채 스크롤하게 된다. 종전의 평평한 배치에서는 화면이 짧아 이 거리가 문제되지 않았다. 재배치가 만든 새 위험이라 CP5 가 반드시 본다(§9 v4).

주의 ③ 이중 제출을 막는 이유는 데이터가 아니라 사용자다

설정 저장은 멱등이다 — 같은 값으로 두 번 저장해도 결과가 같다. 그런데도 가드를 넣는 이유는 눌렀는데 아무 반응이 없으면 사용자가 다시 누르게 되고, 그때 화면이 무엇이 진행 중인지 말하지 않기 때문이다. 가드의 산출물은 중복 방지가 아니라 「저장 중…」 이라는 응답이다.
