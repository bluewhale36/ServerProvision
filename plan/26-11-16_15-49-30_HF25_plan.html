§1. 배경

버그 수정 plan 형식이라 표준 11 섹션과 인터랙티브 데모를 두지 않는다. 배경, 실측, 결론, 수정 방향, 결정과 열린 질문, 검증, Critical Files, 남은 일 순으로 적는다.

1-1. 사용자 요청

2026-10-23 사용자 판단: BIOS 와 BMC 설정 단계는 첫 시도에 실패했다가 다시 시도하면 문제없이 적용되는 경우가 있다. 그때마다 운영자가 수동 [재시도] 로 이었다.

요청은 "설정 단계 실패 시 자동 재시도(최대 3회, 하드코딩)" 이다. 공통화는 R19 로 미뤘다(Notion HF25, R19).

1-2. 이번 CP1 에서 확인한 것

실패가 왜 나는지부터 확인했다. 결과적으로 실패의 원인은 BIOS 가 아니라 엔진의 복귀 판정이었다(§2). 그래서 원인 정정을 먼저 하고, 자동 재시도는 남는 실패를 위한 안전망으로 둔다.

2-3. 원인 (코드)

  1. BeginSettingStep 은 재부팅 시각(rebootAt)을 주기가 시작한 시각(context.now())으로 적는다. 실제 재시작(reset) 발행은 그 뒤 신원 확인, 레지스트리 대조, PATCH, pending 확인, 전원 상태 확인을 모두 마친 뒤다.
  2. 설정 단계 동안 게스트는 iPXE 대기 스크립트(IpxeScripts.awaitingBiosSetting)에서 30 초마다 /boot 를 다시 부른다. BootService 가 그때마다 lastBootAt 을 갱신한다.
  3. ReturnReadbackStep 은 lastBootAt 이 rebootAt 보다 뒤면 복귀로 본다. 그래서 주기 시작과 재시작 발행 사이에 대기 루프의 /boot 가 하나라도 들어오면, 다음 워커 주기(기본 30 초)에 복귀로 오판하고 POST 중인 BMC 의 BIOS 값을 읽어 READBACK_MISMATCH 로 닫는다.
주기 시작 context.now() 가 rebootAt 으로 적힐 시각 │ 신원 확인, 레지스트리 대조, PATCH, pending 확인, 전원 상태 확인 │ ← 이 사이에 대기 루프의 /boot 가 오면 lastBootAt 이 rebootAt 보다 뒤가 된다 reset 발행 │ 다음 워커 주기 (기본 30 초) ReturnReadbackStep : lastBootAt 이 rebootAt 보다 뒤 → 복귀로 오판 POST 중인 BMC 의 BIOS 값을 읽음 → READBACK_MISMATCH 로 닫음
이 오판 창은 HF24 조사(10-13 로그의 READBACK_MISMATCH 2 건)와 10-23 재시도 조사(sbx-hf25/retry-survey.json 비판 절)에서 이미 지목됐지만 정정되지 않았다. HF24 v2 는 무장만 뺐고 이 판정은 손대지 않았다.

§3. 결론
설정 단계 실패(10~11 월 7 건 전부)는 BIOS 가 값을 거부한 것이 아니라, 엔진이 대기 루프의 /boot 를 재부팅 복귀로 오판한 결과다.
  • 정정 1 (원인): 재부팅 시각을 실제 재시작 명령이 성공한 직후의 시각으로 적는다. 그 전에 대기 루프가 보낸 /boot 는 더 이상 복귀로 읽히지 않는다.
  • 정정 2 (안전망, 사용자 요청): 재시도로 풀릴 수 있는 사유로 실패하면 최대 3 회까지 그 축을 처음부터 다시 한다. 진행을 실패 상태로 바꾸지 않는다.
§4. 수정 방향

4-1. 바꾸는 곳

#무엇을어디서바뀐 뒤
1재부팅 시각BeginSettingStep (ledger.markRebooted) 재시작 명령이 성공한 직후의 시각을 적는다
2복귀 판정ReturnReadbackStep 판정 규칙은 그대로(lastBootAt 이 rebootAt 뒤면 복귀). 주석의 오판 원인 설명만 정정
3실패 처리BeginSettingStep, ReturnReadbackStep, BeginBmcSettingStep, ReconnectReadbackStep 의 private fail, close 4 벌과 BeginSettingStep 이 직접 닫는 2 곳(VALUE_NOT_IN_REGISTRY, PATCH_REJECTED) 새 협력자 SettingFailure 하나로 모은다
4재시도 가능 사유SettingFailure 안의 한 집합 READBACK_MISMATCH(BIOS, BMC), WRITE_REJECTED(BMC). 그 밖은 즉시 실패
5회차 세기SettingContext 원장 행으로 센다. 새 컬럼 없음
6시한 기점BeginSettingStep, BeginBmcSettingStep 의 BMC 미응답 시한 SettingContext 의 새 기점을 쓴다
7설명 정정ProvisioningProgress.clearFailed Javadoc 자동 재시도와 실패 해제의 구분을 적는다

4-2. 재부팅 시각과 복귀 판정 (#1, #2)

  • 재부팅 시각은 주기 시작 시각 대신 재시작 명령이 성공한 직후의 시각이다. 시각은 주입한 Clock 에서 읽는다(ClockConfig 빈).
  • 복귀 판정 규칙(lastBootAt 이 rebootAt 뒤)은 바꾸지 않는다. 가짜 복귀의 /boot 는 모두 재시작 명령 전에 대기 루프가 보낸 것이므로, 기준 시각만 바로 적으면 걸러진다.
  • 재시작이 실제로 걸린 뒤에는 호스트가 POST 중이라 /boot 를 보내지 않는다. 다음 /boot 는 POST 를 마치고 PXE 로 돌아온 진짜 복귀다.

4-3. 실패 처리 (#3, #4)

축 실패 (사유) ├─ 재시도 가능한 사유이고 남은 횟수가 있음 │ 행만 FAILED 로 닫는다 │ meta autoRetry = 회차, detail 끝에 "자동 재시도 n/3" │ 진행은 실패로 바꾸지 않는다 │ → 다음 워커 주기가 새 행을 열어 축을 처음부터 다시 한다 └─ 그 밖 지금처럼 행을 닫고 진행을 실패로 바꾼다

4-4. 회차와 시한 기점 (#5, #6)

  • 회차: 이 축 step 의 FAILED 행 중 progress.lastTransitionAt 뒤에 닫힌 행의 수.
    • 자동 재시도는 진행 전이를 만들지 않으므로 회차가 쌓인다.
    • 축 진입과 운영자 재시도(clearFailed)는 lastTransitionAt 을 옮기므로 회차가 0 으로 돌아간다.
  • 시한 기점: BMC 미응답 시한은 progress.lastTransitionAt 대신 SettingContext 의 새 기점을 쓴다.
    • 새 기점 = lastTransitionAt 과 이 축의 마지막 닫힌 행 시각 중 늦은 쪽.
    • 재시도한 시도도 20 분 창을 새로 받는다.
    • 같은 모양의 선례: FlashContext.returnWaitSince.

4-5. Javadoc 정정 (#7)

ProvisioningProgress.clearFailed Javadoc 의 "자동 재시도는 없다 — 운영자 액션만" 을 고친다. 축 안 자동 재시도(HF25)는 실패 상태를 거치지 않으며, 실패 해제는 여전히 운영자 액션만이라는 뜻으로 적는다.

§5. 결정과 열린 질문

5-1. 결정

결정채택안근거, 비채택 대안과 탈락 사유
D-1원인 정정을 함께 한다 자동 재시도만 넣기(사용자 원 요청 그대로): 오판이 그대로 남아 매번 PATCH 와 재시작을 한 번 더 한다(BIOS 축 재시도 1 회 = 재시작 1~2 회). 자동 재시도가 원인을 덮어 다음 사람이 못 본다.
D-2재부팅 시각을 재시작 명령 성공 직후로 적는 것만으로 정정한다 (a) "최소 POST 시간(60 초)" 하한 추가: 초안에 있었으나 뺐다(사용자 지적, 11-16). POST 도중에는 /boot 가 오지 않으므로 POST 시간을 기준으로 삼을 이유가 없다. 남는 틈은 BMC 가 재시작 명령을 받고 실제로 호스트를 재시작하기까지의 몇 초뿐이고, 이 틈은 실측된 적이 없다. 실측 없는 장치를 넣지 않고, 그 틈으로 가짜 복귀가 생기면 자동 재시도가 받는다.
(b) 주기 시작 시각 기록을 유지하고 하한만 두기: 주기 시작부터 재시작 발행까지 걸리는 시간에 상한이 없어 BMC 가 느리면 다시 뚫린다.
(c) 대기 루프의 /boot 와 새 부팅의 /boot 를 질의 문자열로 구분: iPXE 스크립트와 엔드포인트를 함께 바꿔야 해 범위가 커진다.
D-3자동 재시도는 진행을 실패로 바꾸지 않고 축 안에서 한다 (a) markFailed 뒤 곧바로 clearFailed: 실패 시각이 찍혔다 지워지고 화면과 알림에 실패로 잡히며, clearFailed 의 운영자 전용 의미와 부딪힌다.
(b) ProvisioningProgress 에 회차 컬럼 추가: 스키마 변경이 필요하고, 원장 행이 이미 사실을 갖고 있다.
(c) R19 의 공통 재시도 정책으로 바로 가기: 범위 밖(R19).
D-4재시도 가능 사유는 READBACK_MISMATCH 와 WRITE_REJECTED 로 한정한다 READBACK_MISMATCH: 실측 7 건 전부의 사유.
WRITE_REJECTED: BMC 쓰기 안의 일시 오류가 들어오는 자리라 넣는다 (DATE_TIME 쓰기 안의 GET 이 일시 오류 code 1334 와 같은 DATA_REJECTED 를 받으면, 쓰기 위치의 오류라 HF15-7 의 TRANSIENT 가 아니라 거절로 분류됨. 같은 오류라도 되읽기 위치에서는 TRANSIENT). BMC 축 재시도는 재시작이 없어 비용이 작다.
HF15-7 과의 관계: HF15-7 은 한 행 안에서 항목 단위로 일시 오류를 3 번까지 다시 쓰고 넘어간다(meta retries). HF25 는 행이 실패로 닫힌 뒤 축 전체를 새 행으로 다시 한다. 새 행은 retries 를 0 부터 센다. 두 계층은 겹치지 않고 차례로 동작한다.
제외: PATCH_REJECTED(대부분 데이터 거절, 연결 실패는 직전 신원 확인 직후라 드묾), BMC_UNREACHABLE(이미 20 분 기다린 뒤의 실패), 그리고 2-4 의 결정적 사유들.
D-5최대 3 회 (첫 시도 포함 4 번) Notion HF25 의 사용자 결정 그대로.
BIOS 축은 재시도마다 PATCH 와 재시작을 하므로 최악이면 재시작이 4 번(BIOS 가 설정 적용으로 한 번 더 재시작하면 8 번)이다.
