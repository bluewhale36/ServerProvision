§1. 배경

버그 수정 plan 형식이라 표준 11 섹션과 인터랙티브 데모를 두지 않는다. 배경, 실측, 결정, 테스트 · CP5, 범위 밖 · 조율, Critical Files 순으로 적는다.

초기 비밀번호 계정은 비밀번호를 바꾸기 전까지 다른 화면으로 갈 수 없는데, 첫 로그인 안내가 있는 사용 매뉴얼도 열 수 없고, 사이드바 메뉴는 보이지만 누르면 이유 없이 되돌아오며, 사이드바로 변경 화면에 들어오면 강제 상태가 풀린 것처럼 보인다. 셋 다 고친다.

1-1. 출처

  • docs 스트림(DOC-7)이 넘긴 2차 결함 B-1 · B-2(샌드박스 7880 에서 docs.check 계정으로 실측)와 3차 결함 C-25.

1-2. 사용자 결정 (2026-11-16)

우선순위 제안 순서대로 진행한다(HF27 다음).

§2. 실측
결함실태근거
B-1 강제 변경 인터셉터(MustChangePasswordInterceptor)의 제외 목록(MustChangePasswordWebConfig)에 /manual/** 이 없다. 초기 비밀번호 계정이 매뉴얼을 열면 변경 화면으로 되돌아간다 제외 목록 = 변경 화면 · /login · /logout · /error · 정적 자산 · /api/pxe/** · /jobs
B-2 변경 화면이 일반 레이아웃(사이드바 전체)을 쓴다. 메뉴를 누르면 인터셉터가 변경 화면으로 되돌리고 이유 안내가 없다(UX 모순 UI 1차 차단 원칙과 어긋남) templates/security/password-change.html 이 navbar 조각을 그대로 씀
C-25 화면의 강제 여부(forced — 경고 문구 · 취소 버튼 숨김 등)를 주소의 ?first=1 로 판정한다. 사이드바의 '비밀번호 변경' 링크로 들어오면 강제 계정인데도 강제 아님으로 그려지고, 취소하면 다시 되돌아오는 왕복이 생긴다 PasswordChangeController.form · 제출의 @RequestParam("first"). 인터셉터는 세션 principal 의 mustChangePassword() 로 판정
  • 매뉴얼(/manual/**)은 docs 브랜치에 있고 아직 dev 에 병합되지 않았다. 사이드바의 매뉴얼 링크도 docs 브랜치가 더한다.
§3. 결정 (채택 · 비채택 · 탈락 사유)
ID결정채택비채택탈락 사유
D-1매뉴얼 허용(B-1) 제외 목록에 /manual · /manual/** 추가. 매뉴얼은 정적 문서라 비밀번호 변경 전에 읽어도 위험이 없다 매뉴얼을 로그인 없이 공개 사용자 결정(매뉴얼은 로그인 사용자만)과 어긋난다
D-2강제 여부의 단일 판정(C-25) 화면 · 서버 모두 세션 principal 의 mustChangePassword() 하나로 판정(인터셉터와 같은 값). ?first=1 은 더 이상 판정에 쓰지 않는다(링크 호환을 위해 받아도 무시) 주소 파라미터 유지 + 사이드바 링크에 파라미터 추가 주소는 사용자가 바꿀 수 있고, 같은 사실을 두 곳에서 판정하면 오늘처럼 어긋난다
D-3메뉴 사전 차단(B-2) 강제 상태(currentUser.mustChangePassword)이면 사이드바 메뉴 링크를 잠근 모양(비활성 · 흐림 · 누를 수 없음)으로 그리고 메뉴 위에 "비밀번호를 바꾼 뒤 메뉴를 이용할 수 있습니다." 한 줄. 잠그지 않는 링크는 표식(data-nav-always)으로 고른다 — 매뉴얼 링크(docs 브랜치가 표식을 단다)와 로그아웃 강제 상태에서 사이드바를 아예 숨김 매뉴얼 링크까지 사라져 B-1 을 고친 의미가 없다. 잠금은 판정(D-2)과 같은 값을 쓰므로 인터셉터(서버 가드)와 화면이 어긋나지 않는다
D-4판정 값의 전달 CurrentUserModelAdvice.CurrentUser 에 mustChangePassword 를 더한다(레이아웃이 이미 읽는 값) 컨트롤러마다 모델에 싣기 사이드바는 모든 화면에 있어 공용 advice 가 맞다
