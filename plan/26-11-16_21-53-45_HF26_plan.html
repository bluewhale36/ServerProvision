§1. 배경

버그 수정 plan 형식이라 표준 11 섹션과 인터랙티브 데모를 두지 않는다. 배경, 실측, 결정, 실 서버 확인 · 이관, 테스트 · CP5, 범위 밖, Critical Files 순으로 적는다.

메인보드를 영구 삭제하면 그 보드로 등록된 서버의 하드웨어 기록과 BIOS 세팅 템플릿이 DB 연쇄 삭제로 함께 지워지고, Deprecated 동명 모델이 있을 때 '그래도 등록' 하면 같은 모델이 활성으로 둘이 되어 그 보드의 서버가 PXE 등록에 실패한다. 둘 다 고친다.

1-1. 출처

  • docs 스트림(DOC-7 사용자 매뉴얼 집필)이 메인보드 화면을 코드와 대조하다 발견해 앵커에 인계한 결함 9 건 중 중대 2 건(A-7 · A-8).
  • 원본 ServerProvision-docs/sbx-docs/facts/defects-for-anchor.md, 기준 커밋 698162f.

1-2. 사용자 결정 (2026-11-16)

R20 을 마친 뒤 HF 로 진행한다.

1-3. 같은 목록의 나머지

  • A-1~A-6 문구 · UI, A-9 등록 진행 중 분류는 범위 밖(§6).
  • 단 A-1 의 "영구 삭제 버튼 사전 차단 없음" 은 이번 가드와 같은 판정을 쓰므로 함께 고친다.

2-3. 같은 모델 활성 중복 (A-8)

  • BoardModelMetadataService.create: 활성 동명이 있어도 그것이 Deprecated 면 막지 않고 중복 확인 창(nudge)을 띄운다.
  • 창의 [그래도 등록](completePendingBoardFromNudge)은 "기존 자원 보존 · 새 자원 등록" 이라 같은 (제조사, 모델명) 의 비삭제 행이 둘이 된다.
  • board_model 에 (제조사, 모델명) UNIQUE 가 없다. DuplicateBoardModelException javadoc 이 말하는 uk_vendor_model_name 은 실재하지 않는다.
  • PXE 등록 GuestServerRegistrationService.resolveBoardModel 은 findByVendorAndModelNameAndIsDeletedFalse 의 Optional 단건 조회다. 행이 둘이면 조회가 실패해 그 보드의 서버가 등록되지 않는다.
  • 파일 자원(ISO · 펌웨어)은 같은 이름의 새 버전이 정상이라 nudge 의 "그래도 등록" 이 맞지만, 메인보드는 (제조사, 모델명) 자체가 정체라 "새 버전" 개념이 없다.
§3. 결정 (채택 · 비채택 · 탈락 사유)
ID결정채택비채택탈락 사유
D-1보드 영구 삭제를 막는 참조 서버 하드웨어 기록 · BIOS 세팅 템플릿이 하나라도 있으면 거절 레지스트리 스냅샷까지 막기 스냅샷은 그 보드에만 딸린 채집 기록이다. 서버 기록이 남아 있으면 D-1 이 이미 막고, 서버가 모두 사라진 뒤의 스냅샷은 보드와 함께 지워지는 것이 맞다
D-2판정 위치 management.board 에 SPI BoardModelPurgeBlocker(사유 문구 또는 null)를 두고 execution(서버 기록) · provisioning.biossetting(템플릿)이 구현. BoardModelLifecycleService 는 기존 자식 잔존 검사와 함께 목록을 순회 BoardScopedChildLifecycle 에 어댑터 추가 그 SPI 는 soft-delete · 복구 · 라벨까지 함께 따라오는 lifecycle 자식 계약이다. 서버 기록 · 템플릿은 보드를 따라 휴지통에 가지 않는다
D-3두 영구 삭제 경로 하나의 가드(BoardModelLifecycleService 의 판정 메서드)를 목록 · 휴지통 · 중복 확인 창 교체 경로가 모두 호출 교체 경로만 따로 검사 같은 질문("이 보드를 지워도 되나")이 두 곳에 복제되면 오늘처럼 한쪽이 빠진다
D-4DB 안전망 보드 FK 5 개(board_bios · board_bmc · subprogram · guest_server_detail · bios_setting_template)를 ON DELETE RESTRICT 로. 스냅샷은 CASCADE 유지(D-1). 엔티티의 @OnDelete(CASCADE) 표기도 함께 정리. 수동 DDL ddl/HF26_board_fk_restrict.sql 애플리케이션 가드만 이번 결함 자체가 "가드를 거치지 않는 삭제 경로" 였다. 앞으로 새 경로가 생겨도 DB 가 지우지 않게 한다
D-5같은 모델 중복 (제조사, 모델명) 의 비삭제 행(활성 · Deprecated)이 있으면 등록 거절(409 DuplicateBoardModelException). 문구가 Deprecated 면 "목록에서 Deprecated 를 해제하십시오" 로 안내. 중복 확인 창은 휴지통 후보가 있을 때만 뜬다. 활성 행과 Deprecated 행이 같은 이름으로 함께 있을 때 지금은 창으로 넘어가는 빈틈도 이것으로 함께 막힌다 창은 그대로 두고 PXE 조회를 여러 건에 관대하게 조회를 관대하게 하면 어느 행에 서버가 붙을지 정할 근거가 없고 중복 자체가 남는다
D-6DB 유일성 v2 개정 (제조사, 모델명) 복합 UNIQUE 하나(uk_board_model_vendor_model_name). 같은 모델명이 제조사만 다르면 허용. 메인보드 등록의 중복 확인 창은 없앤다(§3-1) 비삭제 행에만 걸리는 UNIQUE(생성 열) · 애플리케이션 가드만 §3-1 비교표
D-7사전 차단(A-1 포함) 같은 판정 메서드가 사유를 내고, 메인보드 목록 · 휴지통 목록의 [영구 삭제] 가 disabled + tooltip. 휴지통은 보드 스캐너에 사유 훅(기본 null, 보드만 구현)을 더해 다른 도메인은 그대로 서버 거절 + flash 만 CLAUDE.md "UX 모순은 UI 1차 차단 · 서버 가드와 SSOT 공유"
D-8거절 문구 "이 메인보드 모델로 등록된 서버 N 대 · BIOS 세팅 템플릿 M 개가 있어 영구 삭제할 수 없습니다." 처럼 남은 것과 개수를 적고, 자식 잔존 문구에서 코드 이름 'Subprogram' · '해주세요' 체를 고친다(화면 문구 em dash 금지 · 하십시오체) 기존 문구 유지 사용자가 다음에 무엇을 지워야 하는지 알 수 있어야 한다

3-1 복합 UNIQUE 검토 (사용자 질문 반영, v2)

사용자: "메인보드 명에 UNIQUE 를 넣지 않은 이유는 제조사별로 같은 이름을 쓸 수 있기 때문이다. 제조사 명과 메인보드 명을 묶은 UNIQUE 를 검토하라." 세 안 모두 키는 (제조사, 모델명) 이라 제조사가 다르면 같은 모델명을 허용한다. 갈리는 지점은 휴지통에 든 행을 UNIQUE 에 넣느냐다.
안DB휴지통에 같은 모델이 있을 때 새 등록중복 확인 창평가
A 복합 UNIQUE (채택 권고)UNIQUE(vendor, model_name) 하나거절. "휴지통에서 복구하거나 영구 삭제한 뒤 등록하십시오" 안내메인보드에서 없앤다정체가 (제조사, 모델명) 인 자원에 맞는 표준 제약. 판정을 거치지 않던 [기존 영구 삭제 후 등록] 경로가 통째로 사라진다
B 비삭제 행만 복합 UNIQUE생성 열 + UNIQUE 인덱스허용(현행 '그래도 등록')휴지통 후보에만 유지현행 흐름 보존. 대신 같은 모델이 활성 · 휴지통에 함께 있는 상태가 남아, 휴지통 쪽은 복구할 수 없고(활성 중복 검사) 자식 BIOS · BMC 와 함께 묶여 있다
C 애플리케이션 가드만없음현행휴지통 후보에만 유지이번 결함처럼 가드를 거치지 않는 경로가 생기면 다시 뚫린다

A 를 고르면 함께 바뀌는 것:

  • D-3 영구 삭제 경로가 목록 · 휴지통(· TTL) 둘로 준다. 중복 확인 창 교체 경로(BoardModelNudgeService · BoardModelNudgeController · purgeBoardForNudge)는 제거한다.
  • D-5 같은 (제조사, 모델명) 이 어떤 상태로든 있으면 등록을 409 로 거절하고, 상태별로 안내한다: 활성 "이미 등록된 모델입니다" · Deprecated "목록에서 Deprecated 를 해제하십시오" · 휴지통 "휴지통에서 복구하거나 영구 삭제한 뒤 등록하십시오". 이름 수정(update)도 같은 검사로.
  • 휴지통에 든 보드를 복구할 때의 활성 중복 검사는 그대로 둔다(UNIQUE 상 생기지 않지만 안전망).
  • 운영 DB 확인(§4)이 넓어진다: 비삭제 중복뿐 아니라 휴지통 행까지 포함한 (제조사, 모델명) 중복이 있으면 UNIQUE 생성이 실패한다.
  • A-2(메인보드 중복 확인 창의 "업로드 취소" 문구)는 창이 사라져 함께 해소된다.
비교 대상 밖으로 둔 것: 휴지통 행을 이름 변경(예: 접미사)으로 비켜 두는 방식. 휴지통 복구 시 원래 이름으로 되돌리는 규칙이 새로 필요해 HF 범위를 넘는다.
보드 영구 삭제 요청 (목록 · 휴지통 · TTL · 중복 확인 창 교체 A 채택 시 제거) └─ BoardModelLifecycleService 판정 메서드 (D-3, 단일 가드) ├─ BoardScopedChildLifecycle.hasAny BIOS · BMC · 드라이버 (기존) └─ BoardModelPurgeBlocker 목록 (D-2, 신규 SPI) ├─ execution 서버 하드웨어 기록 └─ provisioning.biossetting BIOS 세팅 템플릿 사유 있음 → 거절 (D-8 문구) · 같은 사유로 [영구 삭제] disabled + tooltip (D-7) 사유 없음 → 삭제 · 스냅샷만 DB CASCADE (D-1, D-4)
§4. 실 서버 확인 · 이관 (CP4 에서 수행)
  • 운영 DB(spv-01)에 (제조사, 모델명) 중복 행이 있는지 읽기 전용으로 먼저 확인한다. §3-1 A 를 채택하면 휴지통 행까지 포함해 본다.
    • 있으면 D-6 의 UNIQUE 생성이 실패한다.
    • 어느 행을 남길지(서버 · 자식이 붙은 쪽)를 사용자 판단으로 정한 뒤 이관 SQL 을 따로 낸다.
  • 운영 DB 의 FK 이름 · 규칙이 샌드박스와 같은지 확인한다(DDL 은 이름으로 DROP · ADD). 4 개가 Hibernate 자동 이름(FK…)이라 환경마다 다를 수 있다.
  • board_bmc 에는 FK 없는 옛 열 board_model_id(NOT NULL, 엔티티 미매핑)가 샌드박스에 남아 있다. 삭제 연쇄와 무관해 이번 범위 밖이지만, 운영 DB 에도 있는지 함께 본다.
DDL 은 샌드박스와 로컬 DB 에만 적용하고, 운영 적용은 배포 때 사용자 지시로.
