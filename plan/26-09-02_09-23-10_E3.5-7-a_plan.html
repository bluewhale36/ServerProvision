§1. 현재 상태 (진단)

현행은 2026-09-01 커밋 22b9045(PR #63)로 들어간 배수 분할 개정이다. 이 개정의 계기는 09-01 실기였다 — HDD 6대를 RAID5 3+3 두 볼륨으로 만들려면 같은 조건의 규칙을 두 줄 써야 했는데, 그 두 줄이 규칙 8(선행이 후행을 완전 포섭하면 후행은 도달 불가)에 걸려 저장 자체가 거절됐다. 그래서 한 줄이 배수만큼 나눠 담도록 EXACT 의 뜻을 바꿨다.

#제기한 조합현행 결과판정
(a)RAID0 · SSD · SATA · AUTO · EXACT 1한 장짜리 RAID0 볼륨이 장수만큼예측대로
(b)[RAID1 EXACT 2] → [RAID5 AT_LEAST 3] · SSD 4장규칙 1 이 4장을 전부 소비, 규칙 2 는 빈손순서 문제
(c)SSD 6장 · OS 는 RAID1 2장 · 나머지는 RAID5표현 불가모드 필요

(a) 의 근거 — 크기를 1 로 나눈 나머지는 항상 0 이므로 매칭된 SSD SATA 가 전부 선택되고, 배수 분할이 1장씩 잘라 담는다. 큰 RAID0 하나가 아니라 디스크 한 장짜리 RAID0 볼륨이 장수만큼 생긴다. 코드대로의 동작이다.

(b) 의 근거 — 규칙 1 이 4장을 RAID1 두 볼륨으로 전부 가져가므로 규칙 2 는 볼 디스크가 없다. 여기서 소비 방식을 "처음 한 묶음만" 으로 바꿔도 이 예시는 RAID5 가 되지 않는다. 규칙 1 이 2장을 가져가면 남는 2장은 AT_LEAST 3 에 미달해 미배정으로 남기 때문이다. 사용자가 원한 "4장이면 RAID5 · 2장이면 RAID1" 은 규칙 순서를 뒤집으면 지금 코드로 이미 나온다 — AT_LEAST 3 이 4장 전체를 한 볼륨으로 먹고, 규칙 8 도 AT_LEAST 3 이 EXACT 2 를 포섭하지 않아(3 ≤ 2 가 거짓) 저장을 막지 않는다. 즉 이것은 모드 문제가 아니라 순서 문제이며, 그래서 적용 순서 가시화가 같은 슬라이스로 들어온다.

(c) 의 근거 — 같은 스펙 SSD 6장에서 OS 용 RAID1 2장을 떼고 나머지 4장을 RAID5 로 묶는 조합은 현행으로 표현할 수 없다. EXACT 2 는 6이 2의 배수라 여섯 장을 전부 삼키고, 장수가 홀수면 반대로 한 장도 가져가지 않아 전부 후행 RAID5 로 흐른다. "첫 묶음 한 번만" 을 뜻하는 모드가 있어야 풀린다.

진단 요약 — 제기 셋 중 (a)·(b) 는 코드대로의 동작이고 (c) 만 표현 불가다. 그러나 (a)·(b) 가 예측대로라는 사실이 사용자에게 보이지 않았다는 점이 함께 드러났다 — 한 줄의 뜻이 하나뿐이라 고를 수 없었고(모드), 위 규칙이 먼저 가져간다는 사실이 화면에 없었다(순서). 이 슬라이스는 그 둘을 함께 처리한다.

2026-09-02 사용자 결정 — 체크박스 대안 대신 모드 세 값으로 가고, 신규 행 기본은 '개' 로 한다. 게스트 서버별 볼륨 계획 수정(E3.5-7-b)은 후행 슬라이스로 미룬다.

A 탈락 사유 — 체크박스는 '개 이상' 과 조합하면 뜻이 없어 무효 조합이 생기고, 그것을 막는 UI 잠금이 한 줄 더 붙는다. 저장소 규칙(무명 boolean 인자 금지 · 도메인 다형)에도 어긋난다. 무엇보다 판정이 (모드, 플래그) 2차원으로 갈라져 계획 소비 · 규칙 8 · 표시 세 곳이 전부 두 배로 늘어난다.

B 채택 사유 — 필드가 하나라 무효 조합이 0 이다. 계획 소비 · 규칙 8 · 표시 세 곳이 이미 모드 하나로 분기하고 있으므로 값 추가만으로 함께 늘어난다. Java 의 switch 식이 enum 전수 처리를 요구하므로, 세 곳 중 한 곳이라도 새 값을 빠뜨리면 컴파일이 실패한다 — 누락이 런타임이 아니라 빌드에서 잡힌다.

C 탈락 사유 — 사례 (c)(6장에서 OS 2장만 떼고 나머지를 RAID5 로)는 순서를 어떻게 바꿔도 표현되지 않는다.

순위 가시화순위 열(배지) + 상시 안내 + 도움말안내문만 / 순위 숫자 입력란요구 미달 / 이중 SSOT

B1 대 B2 — B2 는 마이그레이션이 0 이라는 이점이 있다. 그러나 "EXACT" 라는 이름이 '개씩' 을 뜻하는 왜곡이 코드에 영구히 남고, 새 기본값 '개' 가 EXACT 가 아닌 상수가 되어 읽는 사람마다 되묻게 된다. 이름과 뜻을 맞추는 쪽(B1)을 택하고, 그 대가인 저장본 치환은 SQL 한 벌(§4 D5)로 갚는다.

'개' 의 선택 조건 — 09-01 이전의 엄격 일치(크기 == n)로 되돌리면 사례 (c) 를 여전히 못 풀고, "6대인데 EXACT 3 이 한 장도 안 가져간다" 는 09-01 문제가 그대로 재발한다. 그래서 '개' 는 크기가 n 이상이면 첫 그룹에서 슬롯 순으로 n 장만 떼어 간다.

순위 가시화 — 같은 화면의 볼륨 우선순위 표가 이미 순위 배지 패턴을 쓰고 있다(CP6 검수로 도입). 같은 패턴을 묶음 규칙 표에 쓰면 두 표의 읽는 법이 하나가 된다. 순위를 숫자로 직접 입력받는 안은 드래그 순서와 숫자가 각자 진실을 주장하는 이중 SSOT 가 되어 드리프트를 부르므로 택하지 않는다.

D1. DiskCountMode — 값 셋

상수접미사뜻
EXACT개발견 순 첫 그룹에서 슬롯 순 n 장 한 묶음. 나머지는 후행으로
EACH 신규개씩그룹 크기가 n 의 배수면 n 개씩 전부(현행 EXACT)
AT_LEAST개 이상크기 ≥ n 이면 그룹 전체를 한 볼륨으로(현행 유지)

선언 순서가 곧 폼 select 의 옵션 순서이고, 첫 옵션인 '개' 가 신규 행의 기본값이 된다. DiskCountRequirement.toDisplay() 는 값 + 접미사 조합("2개씩")으로 그대로 확장된다.

D2. 계획 소비 진리표 — RaidPlanner

모드그룹 선택소비볼륨 수pool 제거
EXACT n크기 ≥ n · 첫 그룹만슬롯 순 n 장1슬라이스만
EACH n크기 % n == 0그룹 전체크기 / n그룹
AT_LEAST n크기 ≥ n그룹 전체1그룹

원칙 개정 — 어떤 규칙도 그룹을 부분 소비하지 않는다 → '개' 만 부분 소비하며, 남은 디스크는 같은 스펙 그룹으로 후행에 흐른다. 구현상으로는 현행의 pool.removeAll(group) 을 EXACT 에서만 슬라이스 제거로 바꾸는 것이다. EXACT 가 한 묶음을 소비한 뒤 다른 스펙 그룹은 건드리지 않으며, 그 그룹의 사유는 "규칙 r 은 한 묶음만 — 이미 소비" 로 남는다.

미소비 사유 문구 — 현행 문장 골격("규칙 N · <조건> 조건에 K대(…)라 미소비")은 그대로 두고 괄호 안만 모드별로 갈린다 — EXACT · AT_LEAST 는 "n 장 미만"(조건이 같으므로 표현도 하나), EACH 는 "배수 아님", 그리고 EXACT 가 이미 한 묶음을 소비한 뒤 남은 다른 그룹은 "한 묶음 소비 완료" 다. RAID 없음(패스스루) 규칙도 같은 표를 따른다 — EXACT 1 이면 첫 1장만 패스스루, EACH 1 과 AT_LEAST 1 이면 전부다. RaidRuleOutcome 의 모양은 바꾸지 않는다. 볼륨 이름 규칙 spvR{r}V{k} 도 그대로이며, EXACT 는 볼륨이 하나뿐이라 항상 V1 이다.

D3. 규칙 8 포섭 진리표 — DiskGroupRules.countCovers · 폼 coversRule

선행 \ 후행EXACT mEACH mAT_LEAST m
EXACT n✗✗✗
EACH n✗n == m✗
AT_LEAST nn ≤ mn ≤ mn ≤ m

'개' 행이 전부 ✗ 인 이유 — '개' 는 한 묶음만 가져가고 나머지를 남기므로, 후행이 볼 디스크가 원리적으로 남는다. 어떤 후행도 완전히 가려지지 않는다.

'개씩' 이 같은 n 의 '개씩' 만 덮는 이유 — '개씩' 은 크기가 n 의 배수인 그룹만 통째로 가져간다. 배수가 아닌 그룹은 손대지 않고 후행에 넘기므로, 후행이 '개' 나 '개 이상' 이면 그 그룹에서 살아난다. 반면 같은 n 의 '개씩' 은 선행이 가져가는 그룹 집합과 후행이 요구하는 그룹 집합이 정확히 같아 항상 선점된다.

'개 이상' 행이 현행 공식 그대로인 이유 — '개 이상' 은 크기 ≥ n 인 그룹을 전부 가져간다. 후행이 요구하는 크기(m 이상 또는 정확히 m, 단 m ≥ n)는 모두 그 안에 들어가므로 세 모드 모두를 덮는다. 축 포섭(종류 · 전송 · 용량) 판정은 바꾸지 않는다.

서버가 포섭을 발견하면 던지는 문장은 폼 미러의 안내와 같은 모양이다 — "N번 묶음은 M번 묶음에 가려 도달할 수 없습니다 — 순서를 바꾸거나 조건을 좁히십시오."

D4. 순위 가시화

  • 순위 열 — 묶음 표(#rcDiskGroupTable)의 핸들 열 다음에 배지 숫자 열을 넣는다. 볼륨 우선순위 표(#rcPriorityTable)의 순위 열과 그 재번호 JavaScript(행 추가 · 삭제 · 드래그) 패턴을 재사용한다. 열 폭 재배분(합계 100 유지)은 CP2 에서 실측해 정한다.
  • 상시 안내 — 제목 "디스크 묶음 규칙" 아래에 n-hint 한 줄을 항상 띄운다: "위 규칙부터 순서대로 디스크를 가져가고, 남은 디스크는 아래 규칙으로 흐릅니다. 어느 규칙에도 맞지 않는 디스크는 미배정으로 남습니다." 도달 불가 안내(rcUnreachableHint)는 그 아래에 지금처럼 조건부로 뜬다.
  • 도움말 — 개 · 개씩 · 개 이상의 뜻을 한 줄씩 적고 "행 순서 = 적용 순서" 를 덧붙인다.
  • 상세 카드 — setting-process-cards.html 의 묶음 표에서 '#' 헤더를 '순위' 로 바꾸고 개수 표기를 "2개씩" 형태로 낸다.

D5. 저장본 처리

B1 을 택했으므로 09-01 의 뜻(배수)으로 저장된 EXACT 규칙은 개정 후 동작이 달라진다. 이를 막기 위해 ddl/E3.5-7-a_count_mode_each.sql 로 setting_process.payload_json 과 assigned_process_snapshot.payload_json 의 "mode":"EXACT" 를 "mode":"EACH" 로 치환한다(UPDATE 2문). 치환 대상은 RAID 구성 payload 로 한정하며, 용량 축의 capacity.mode 는 AUTO/SPECIFIED 어휘라 값이 겹치지 않는다. 실행 전 SELECT COUNT 로 대상 건수를 확인하고, 실기 VM 데이터베이스의 대상 건수는 CP2 에서 실측한다. 적용 시점은 배포와 동시다(스테이징 VM · 샌드박스). 실기 VM 실측(09-02)으로 대상은 setting_process 6행(정의서 6건 · EXACT 규칙 10개) · assigned_process_snapshot 9행이다.

저장본 "mode":"EXACT" (09-01 배수 뜻) └─ 치환 SQL ──▶ "mode":"EACH" (같은 결과 3+3 보존) 신규 입력 기본값 ──▶ "mode":"EXACT" (새 뜻 = 개 · 첫 묶음 한 번)

  • 임시 비대칭 — 저장본 치환은 배포와 동시에 한 번 적용하는 일회성 조치다. 적용 전후로 같은 정의서가 다른 계획을 낼 수 있는 창이 생기므로, 적용 시점을 배포와 붙여 그 창을 닫는다.
  • CLAUDE.md 수정 — 없다. 네이밍 · 레이어 경계 · 테스트 규율 어느 것도 이 슬라이스가 어기지 않는다.
