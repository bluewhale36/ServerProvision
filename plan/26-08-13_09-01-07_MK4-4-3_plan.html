§1. 현재 상태 (진단)

MK4-4-2 가 첫 화면 · 회차 상세 · 드리프트 상세를 다시 그렸다. 그런데 보관한 드리프트를 볼 화면이 아직 없다. 미루는 기능은 MK4-1 이 만들어 두었는데 미룬 것을 읽을 자리가 없어, 보관은 사실상 잊는 것과 같아져 있다.

2026-08-13 분할. 이 슬라이스는 본래 보관 화면과 운영 설정 화면을 함께 담았다. 구현을 마치고 갈래별 규모를 재 보니 설정 계열이 보관 계열의 약 5 배(+301/−142 대 +63/−21)였고, 두 화면이 공유하는 도메인 개념이 없어 CP5 검증이 두 줄기로 갈린다. 한 report 에 무관한 검증 두 묶음이 들어가면 어느 한쪽이 얕아져도 분량에 묻히므로, 운영 설정을 MK4-4-4 로 떼었다. 2026-08-11 분할 시 걸어 둔 조건("커지면 다시 나눈다")이 실제로 발동한 것이며, 다만 무거운 쪽은 예상과 반대인 설정이었다.

실측 ① 보관한 것을 볼 자리가 없다

Drift.snooze() 는 기간과 사유를 받아 상태를 SNOOZED 로 바꾼다. 그런데 첫 화면의 목록은 PathReconciliationService.openDrifts() 이고, 그 필터는 Drift.isListed(now) 다 — 열려 있거나 만료된 보관만 통과한다. 보관 중인 것은 어느 화면에도 나오지 않는다.

화면 라우트 (실측 넷)무엇보관을 모아 볼 수 있나
/첫 화면아니오 — isListed(now) 가 거른다
/reports점검 이력 목록아니오 — 점검 회차의 목록이다
/reports/{id}회차 상세아니오
/drifts/{id}드리프트 상세id 를 알면 한 건씩 열리지만 목록에서 닿을 길이 없다

그래서 보관은 미룬 순간 잊힌다. 만료돼 목록에 다시 뜰 때까지 무엇을 몇 건 미뤘는지 알 수 없다. MK4-1 이 '보고 닫기'(다음 점검에 그대로 다시 뜨는 착시)를 '보관'(기간과 사유를 남기고 그동안만 내림)으로 바꾼 목적이 "왜 방치됐는지 나중에 설명이 된다" 였는데, 그 설명을 읽을 자리가 없다.

실측 ② 미룬 것을 앞당길 수 없다

DriftHandlingAction.UNSNOOZE("보관 해제") 와 Drift.reopen() 은 MK4-1 이 만들어 두었다. 그런데 이를 부르는 곳은 PathReconciliationService.reopenExpiredSnoozes 하나뿐이고, 그것은 기간 만료 자동 처리다. 사용자가 "생각이 바뀌었으니 지금 처리하겠다" 를 할 경로가 없다.

정리하면 보관은 걸 수는 있는데 볼 수도 풀 수도 없는 상태다. 이 슬라이스가 더하는 것은 그 둘 — 읽는 자리와 앞당기는 경로다.

§2. 요구사항 (확정) + 비목표

하는 일 하나

보관 화면을 만든다 — 목록 · 진입 · 해제. 셋이 한 덩어리인 이유는 하나만 있으면 쓸모가 없기 때문이다. 목록만 있으면 미룬 것을 보기만 하고 되돌릴 수 없고, 해제만 있으면 무엇을 해제할지 고를 자리가 없으며, 진입로가 없으면 앞의 둘에 닿지 못한다.

이 데모가 보여 주는 것 셋

  1. 보관하면 첫 화면에서 사라진다 — 그런데 지금은 어느 화면에도 나타나지 않는다(현재 결함). 보관 화면을 켜면 거기 나타난다(이 슬라이스의 결과).
  2. 보관 해제하면 즉시 첫 화면으로 돌아온다 — 지금은 이 경로가 없다. 해제 버튼은 보관 목록의 행에만 있으므로(§4 D4), 보관 화면을 켜야 눌린다.
  3. 기간이 만료되면 해제하지 않아도 돌아온다 — 이것만 지금도 된다. 만료된 것은 보관 목록에서 빠지므로 두 화면에 동시에 뜨지 않는다(§8 주의 ②).

첫 화면 위의 보관 중 N 건 안내도 함께 보라 — 보관이 0 건이 되면 안내 자체가 사라진다(§4 D3). 해제하거나 만료시켜 0 건을 만들어 보면 확인된다.

드리프트 0 — 데모의 판정식 = 서버 도메인 메서드. 첫 화면에 보이는 조건은 Drift.isListed(now) 를 그대로 옮긴 status == OPEN || (status == SNOOZED && snoozeUntil <= now) 이고, 보관 목록의 조건은 그 부정 중 SNOOZED 인 것이다. 데모가 규칙을 따로 재구현하지 않는다.

§4. 설계 결정 (D1~D4) + 도메인 SSOT

도메인 신설 0 — 있는 것을 화면으로 꺼낸다

엔티티 · Value Object · Enum 을 새로 만들지 않는다. 보관은 이미 Drift 가 들고 있고, 필요한 도메인 메서드도 MK4-1 이 만들어 두었다. 새 값이 생기지 않으므로 Primitive Obsession 을 판단할 새 지점도 없다 — 이 슬라이스가 더하는 것은 읽는 자리다.

있는 것무엇이 슬라이스가 하는 일
Drift.status열림 · 보관 · 해결보관 목록의 필터 조건
Drift.snoozeUntil보관 만료 시각정렬 키 · 남은 기간 표시
Drift.snoozeWindow보관 기간목록에 표시
Drift.snoozeReason미룬 사유목록에 표시
Drift.reopen()보관을 풀어 다시 열기수동 해제가 호출
DriftHandlingAction.UNSNOOZE처리 이력의 갈래수동 해제를 이력에 남김

판정 규칙 (SSOT — 🎬 데모가 그대로 쓴다)

첫 화면에 보이는가 = status == OPEN || (status == SNOOZED && snoozeUntil <= now)   // Drift.isListed(now)
보관 목록에 있는가 = status == SNOOZED && snoozeUntil >  now                       // 만료된 것은 빠진다 (§8 주의 ②)

두 조건이 서로를 배제하므로 같은 드리프트가 두 화면에 동시에 뜨지 않는다. 이 성질이 §8 주의 ② 의 근거다.

D1 — 보관 상세를 따로 만들지 않는다

2026-08-11 분할 시 범위는 "보관 목록 · 보관 상세" 였다. 그때는 드리프트 상세 화면이 없었다. MK4-4-2 가 만들었고 보관 중인 드리프트도 그 화면으로 열리며 상태 배지가 「보관」 으로 뜬다. 따로 만들면 같은 내용의 화면이 둘이 된다.

  • 비채택 — 보관 전용 상세(사유 · 만료를 크게). 탈락 : 그 둘은 이미 드리프트 상세의 「위험도」 구획에 있다. 화면을 늘리는 대신 그 자리를 손보면 된다.

D2 — 보관 목록은 첫 화면에 섞지 않고 별도 화면으로 둔다

첫 화면의 주인공은 "지금 처리할 것" 이고 보관은 "지금 처리 안 하기로 한 것" 이다. 섞으면 MK4-4-2 가 세운 축이 흐려진다.

  • 비채택 ① — 첫 화면에 탭(미해결 / 보관 중). 탈락 : 탭은 둘이 같은 무게라는 신호인데 아니다.
  • 비채택 ② — 목록에 보관 행을 흐리게 함께 표시. 탈락 : 급한 순 정렬에 섞이면 순서의 뜻이 깨진다.

D3 — 진입은 헤더 버튼이 아니라 첫 화면의 안내다

헤더에는 이미 [점검 이력] · [운영 설정] 둘이 있다. 셋이 되면 버튼 묶음이 다시 무거워진다. 보관은 상시 확인할 것이 아니라 있으면 알려 주면 되는 것이라, 첫 화면 목록 위에 보관 중 N 건 안내로 두고 거기서 들어간다. 0 건이면 안내 자체가 없다.

D4 — 수동 보관 해제를 잇는다

UNSNOOZE 와 reopen() 은 이미 있고 부르는 곳만 없다. 보관 목록의 각 행에서 [보관 해제] 를 누른다. 처리 이력에 남으므로 "왜 앞당겼나" 가 이력에 기록된다.

D5 · D6 은 MK4-4-4 로 옮겼다 (2026-08-13 분할). 각각 "운영 설정을 성질로 묶는다" · "저장은 묶음별로 나누지 않는다" 로, 둘 다 설정 화면의 결정이라 보관 화면과 맞물리는 지점이 없다. 번호는 그쪽에서 다시 매겨진다.

§7. 예외 계층

보관 해제가 거절되는 경우는 하나다 — 보관 중이 아닌 것을 해제하려 할 때. 정상 흐름에서는 보관 목록에만 [보관 해제] 가 있으므로 도달하지 않는다(UI 1 차 차단). direct POST · stale 화면에서만 발동하는 안전망이라 예외가 맞다.

§8. 예상 부산물 · 주의 · 결정 사항

주의 ① 보관 목록의 정렬

급한 순(DriftPriority)이 아니라 만료가 임박한 순이 맞다. 보관 화면에서 묻는 것은 "무엇이 급한가" 가 아니라 "무엇이 곧 돌아오는가" 이기 때문이다. 조건형 보관(UNTIL_NEXT_DEEP_SCAN)은 만료 시각이 없으므로 뒤로 민다.

주의 ② 만료된 것은 보관 목록에 없다

isListed(now) 가 만료를 이미 열린 것으로 치므로 첫 화면에 나타난다. 보관 목록은 아직 만료되지 않은 것만 담는다 — 두 화면에 같은 것이 동시에 뜨면 어느 쪽이 사실인지 흔들린다.

주의 ③ 보관 목록의 [보관 해제] 는 조건형 보관에도 있다

조건형 보관(UNTIL_NEXT_DEEP_SCAN)은 만료 시각이 없어 시간으로는 풀리지 않고 사건으로 풀린다. 그렇다고 해제 버튼을 막으면 "정밀 점검을 돌려야만 되돌릴 수 있다" 가 되는데, 그것은 사용자가 마음을 바꿀 권리를 시스템 일정에 묶는 것이다. 그래서 조건형도 같은 버튼으로 풀린다 — Drift.unsnoozeBlockReason() 이 보는 것은 기간이 아니라 지금 보관 중인가 하나다.
