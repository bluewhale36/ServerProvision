이 문서의 성격 — U3 전체를 3 슬라이스로 나누는 분할안(§0) 과, 그 첫 슬라이스인 U3-1 의 착수 계획(§1~§11) 을 함께 담는다. 분할과 결정 D-A~D-G 는 확정 제안이고, OQ1~OQ6 (§8) 은 사용자 확정 대기다. 승인하면 얼어붙는 계약이 아니라 제안-수정 매개로 읽어달라 — 형제 슬라이스 U3-2 · U3-3 은 각자 CP1 을 따로 갖는다.
§0. U3 하위 단계 분할 (이 슬라이스의 위치)

U3(세팅 정의서 → 서버 할당) 를 3 슬라이스로 분할한다(분할안 B′). 세 관심사가 서로 다른 균열선을 가진다 — 신규 엔티티 · 스냅샷 도출층, mutation · lifecycle 층, read-only 프런트 층이 각각 다른 이유로 바뀌므로 한 슬라이스로 묶으면 응집이 무너진다.

슬라이스담는 것완료 조건 · 성격
U3-1 이 문서 할당 core + 할당 시점 스냅샷 + ownedPhases 도출 · 공급 + 계획 phase rail(상세 화면) 신규 엔티티 도입 · ES-1 · E2 의 엄격한 선행 의존을 푸는 foundational 층. 할당 UI E2E + 계획 rail 육안 + seam 테스트로 검증
U3-2 재할당 이력(DEC-18) + 원본 정의서 삭제 soft-delete + 지연 purge(DEC-19) 'consumed 스냅샷 · active 게스트' 술어를 공유하는 mutation · lifecycle 층. DB-only reaper
U3-3 서버 목록의 cross-server 현재단계 가시화(SSE) U3-1 core 산출만 소비하는 read-only 프런트 층. 독립 뷰파일 · 독립 유저가치

분할 근거 — detail rail 만 U3-1, 목록 뷰는 U3-3

가시화를 통째 한 슬라이스로 묶지 않고 detail rail 만 U3-1 에 넣은 이유: ownedPhases 도출은 U3-1 의 핵심 산출인데, 사람이 눈으로 확인할 표시가 없으면 CP5 검증이 성립하지 않는다 — detail rail 은 core 의 필수 검증 장치다. 반대로 목록의 cross-server 뷰는 다른 뷰파일 · 독립 유저가치라 U3-3 으로 분리해, server-detail 을 두 슬라이스가 중복 편집하는 churn 을 없앤다.

비채택 분할안 :
  • 단일 U3 — 신규 엔티티 + DB-only purge 인프라 + 재할당 + 뷰 2종이 10단계 / plan 1건 응집 단위를 초과하고, 실행 엔진 unblock 이 지연된다.
  • 2분할 — U3-1 이 뷰 2종 + SSE 까지 떠안아 과대해진다.
착수 순서 권장: U3-1 → U3-2(correctness 우선) → U3-3.
§1. 현재 상태 (진단)

쉬운 말 요약

세팅 정의서는 지금 서버에 연결할 방법이 없다. U2 에서 정의서를 만들고 편집하는 것까지는 됐지만, "이 정의서로 이 서버를 프로비저닝하라" 고 지정하는 화면과 데이터가 아예 없다. 그래서 물리 서버가 PXE 로 부팅해 등록돼도, 실행 엔진은 "이 서버가 어느 단계(phase) 를 밟아야 하는지" 를 알 도구가 없어 지금은 빈 목록(Set.of()) 을 하드코딩으로 넘긴다. 결과적으로 어떤 서버든 진단 리눅스까지만 가고 끝난다.

이번 슬라이스는 네 가지를 만든다. (1) 운영자가 정의서를 서버에 할당하는 화면, (2) 할당하는 순간 그 정의서 내용을 서버 쪽에 사진 찍듯 복사해 두는 스냅샷, (3) 그 스냅샷에서 "이 서버가 밟을 phase 목록(ownedPhases)" 을 뽑아 실행 엔진에 넘겨주는 공급 통로, (4) 서버 상세 화면에 "앞으로 밟을 phase 계획" 을 보여주는 rail. 다만 실제로 엔진이 그 목록을 소비해 다음 단계로 전진하는 배선은 이번이 아니라 ES-1 이 한다 — 이번엔 공급까지다.

§2. 요구사항 (확정) + 비목표
  1. 운영자가 세팅 정의서를 게스트 서버(1개 이상) 에 할당한다.
  2. 할당 시점 스냅샷(DEC-16 즉시 · DEC-17 setting_process 행 단위 복사): process_type + payload 복사. BASIC_SETTING 의 BIOS 템플릿 값은 deep-freeze(결정 D-C).
  3. SettingProcessType→ProvisioningPhase 매핑으로 ownedPhases(Set<ProvisioningPhase>) 를 derive-then-freeze 로 영속한다.
  4. OwnedPhasesProvider SPI 로 게스트별 ownedPhases 를 공급한다(엔진 소비 계약, 배선은 ES-1).
  5. 개시(start) 시 활성 스냅샷을 markConsumed 한다.
  6. server-detail 에 '계획 phase rail'(밟을 예정 phase + '계획 vs 실제' 라벨 구분) 을 표시한다.
비 목표 :
  • 재할당 이력 · 원본 삭제 lifecycle(DEC-18 / DEC-19) = U3-2.
  • 서버 목록 cross-server 가시화(SSE) = U3-3.
  • Set.of() 실제 커서 전진 배선 = ES-1(U3 는 공급까지, DiagnoseLinuxExecutor:119 · BootScriptDispatcher:62 두 파일 안 건드림).
  • 진행 중 게스트 재할당의 커서 리셋 / 재개 의미론 = E cluster(U3-1 은 데이터 구조만).

§4. 도메인 모델 (SSOT)

테이블 관계도 (ERD)

신규 테이블 2개(setting_assignment · assigned_process) 와 기존 테이블의 관계다. 이 plan 은 자체완결 단일 파일(외부 JS 참조 0) 이고 Notion sandboxed iframe 에서 열리므로 mermaid 는 이 문서 안에서 다이어그램으로 렌더되지 않는다 — 아래 관계도가 어디서나 렌더되는 본체이고, 이어지는 mermaid 소스는 Artifact 등 지원 뷰어용이다.

guest_server        --1:N-->      setting_assignment   [NEW]   (FK: guest_server_id)
setting_assignment  --1:N-->      assigned_process     [NEW]   (FK: assignment_id)
setting_assignment  ..soft-ref..> setting_definition           (definition_id, FK 아님)
assigned_process    --X (no FK)   bios_setting_template        (값은 payload_json 에 인라인 deep-freeze)
관계도가 담은 핵심 설계 결정
  • definition_id = 소프트참조(JPA / DDL FK 아님) — 원본 정의서가 purge 돼도 소비 스냅샷은 생존한다(DEC-18 · 결정 D-C 자족성).
  • assigned_process → bios_setting_template FK 없음 — BASIC_SETTING 은 BIOS 템플릿 값을 할당 시 payload_json 에 인라인 deep-freeze 하므로 자족한다(결정 D-C). 템플릿을 이후 편집 · 삭제해도 이력이 불변이다.
  • owned_phases = SettingProcessType → ProvisioningPhase 매핑의 derive-then-freeze(OwnedPhases VO · 안정 코드) — 유일 권위(결정 D-G).
  • 활성 스냅샷 술어 = superseded_at IS NULL(결정 D-A). 관계 계층은 guest_server 1:N setting_assignment 1:N assigned_process.

공급 지점 + 변경

OwnedPhasesProvider — execution.engine 이 소유하는 SPI(dependency inversion: 소비자가 인터페이스 소유, 할당 도메인이 impl, MarkableScanner 선례). 활성 스냅샷(supersededAt IS NULL) 의 동결 OwnedPhases 를 read, 활성이 없으면 immutable 빈 Set 을 반환한다 — 빈 Set → nextAfter 가 DIAGNOSE_LINUX 후 empty → 진단 완주 종단이라는 현 동작을 분기 추가 0 으로 재현한다.

// execution.engine — 소비자(엔진)가 소유하는 SPI, 할당 도메인이 구현
public interface OwnedPhasesProvider {
    Set<ProvisioningPhase> ownedPhasesOf(UUID guestId);   // 활성 없으면 Set.of()
}

// SettingAssignment — 상태 컬럼 없이 파생 (GuestServer §D4 하우스스타일)
public AssignmentState state() {
    if (supersededAt != null) return AssignmentState.SUPERSEDED;
    return consumedAt != null ? AssignmentState.ACTIVE_CONSUMED
                              : AssignmentState.ACTIVE_UNCONSUMED;
}
