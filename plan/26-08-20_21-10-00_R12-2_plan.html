§1. 현재 상태 (진단)

선행 결과 — R12-1 이 무엇을 끝냈는가

R12 캠페인은 펌웨어 자원의 파일 계약을 "벤더 패키지 디렉토리 한 벌" 에서 "펌웨어 파일 한 개" 로 내리는 작업입니다. 첫 슬라이스인 R12-1 이 BIOS 도메인을 단일 폼으로 이행해 2026-08-20 완료됐습니다. 등록 화면은 경로 한 칸과 선택적 파일 한 칸만 두고, 파일이 첨부되면 그 경로에 저장하며, 첨부되지 않으면 그 경로에 이미 있는 파일을 등록(claim)합니다. 함께 제조사별 파일 정책 SPI(Service Provider Interface — 도메인이 구현해 끼우는 확장점)를 도입해 GIGABYTE 보드에만 허용 확장자와 금지 파일명 제약을 걸었습니다.

R12-2 는 같은 이행을 BMC 도메인에 적용합니다. 여기에 더해 R12-1 이 "BMC 가 아직 쓰고 있어서" 손대지 못하고 남겨 둔 자산을 정리하는 것이 이 슬라이스의 두 번째 축입니다.

BMC 현행 실태 (실측)

등록 구조는 BIOS 와 대칭입니다. BmcUploadController 가 세 엔드포인트(/upload-intent · /upload · /register-existing)를 열고, 업로드 경로는 BmcUploadIntentService 가 1 회용 토큰을 발급한 뒤 BmcRegistrationService 가 모드별 추출 → 진입점 자동 탐지 → manifest 집계 → 해시 충돌 중복 확인 → 2 단계 저장과 마커 기록을 수행합니다. 화면도 같은 탭 넷(폴더 · Zip · 단일 파일 · 기존 디렉토리 등록)으로 나뉘어 있고 uploadMode 값을 hidden 으로 실어 보냅니다.

BIOS 와 다른 네 가지

첫 항목이 이번 설계에 가장 큰 제약입니다. BoardBMC 는 실 테이블에 아직 NOT NULL 로 남아 있는 두 컬럼을 필드로 미러링합니다 — legacyFilePath 가 file_path VARCHAR(255) NOT NULL 에 트리 루트를 그대로 복사하고, boardModelIdMirror 가 board_model_id NOT NULL 에 부모 식별자를 숫자로 복사합니다. 엔티티의 주 컬럼은 firmware_path VARCHAR(1024) 인데, 같은 문자열이 255 자 컬럼에도 들어가야 하므로 실효 제약은 255 자입니다. BIOS 는 legacy 미러가 없어 1024 자를 그대로 씁니다.

두 번째 항목은 조건 분기 확장 금지 원칙과 정면으로 부딪칩니다. uploadBundle 은 NotFoundException · FieldBoundConflictException · ConflictException · DomainException 을 차례로 잡아 각각 404 · 409(fieldErrors 동봉) · 409 · 500 으로 변환합니다. 클래스 주석이 밝히듯 R5-1 당시 "동작 보존 우선" 으로 advice 승급을 후속 슬라이스에 이월한 흔적이며, 같은 자리의 BIOS 코드는 이미 정리돼 @RestControllerAdvice 가 일괄 처리합니다. 이번 슬라이스가 파일 정책 예외를 새로 들여오므로, 이 상태를 그대로 두면 catch 절이 한 단 더 늘어납니다.

공유 자산 실측 — 일소 범위의 정정

R12-1 의 서술을 정정합니다. R12-1 은 비목표 절에 "공유 자산의 폴더 · 압축 경로와 벤더 진입점 전략 dead code 일소 → R12-2 완료 후" 라고 적었습니다. 실측해 보니 일소할 수 있는 것과 없는 것이 갈립니다 — 진입점 탐지 계열은 BMC 가 마지막 사용자라 함께 걷어낼 수 있지만, 추출 서비스와 공유 스크립트는 Subprogram 자원이 계속 씁니다.

갈리는 이유는 도메인의 성격이 다르기 때문입니다. Subprogram 은 드라이버와 유틸리티를 담는 자원이고, 그 자원의 본래 형태가 여러 파일의 묶음입니다. 설치 스크립트와 바이너리가 한 디렉토리에 함께 있어야 의미를 갖는 것이라 폴더 · 압축 업로드와 모드 탭이 그 도메인에서는 여전히 옳은 모델입니다. 이번 캠페인이 폐기하는 것은 "번들" 이라는 개념 자체가 아니라 펌웨어 자원의 파일 계약이 번들이어야 한다는 전제입니다. R12-1 의 서술은 이 구분을 하지 못한 채 "일소" 라고 적었고, 여기서 정정합니다.

공유 스크립트에서 제거 불가로 판정된 함수는 collectSizeInfo · validateFolderWrapping · buildBundleFormData 셋과 부트스트랩의 bindModeTabs 입니다. BMC 페이지가 이들을 호출하지 않게 되어도 Subprogram 페이지가 그대로 부르므로 파일과 함수는 남습니다. 남은 함수를 Subprogram 전용 자산으로 옮기는 정리는 이번 범위에 넣지 않습니다(§8 Q3).

R12-1 이 남긴 잔여 위험 (실측 재현)

R12-1 은 "경로 끝에 / 가 없으면 마지막 세그먼트를 저장할 파일명으로 해석" 하는 함정을 고치면서, UploadPathResolver.resolveForUpload 에 마지막 세그먼트에 점이 없으면 디렉토리로 간주하는 추론을 넣었습니다. 파일명은 확장자를 갖는 것이 정상이라는 전제였습니다. 그런데 실제 운영 관례에서 펌웨어를 담는 디렉토리 이름은 버전 번호이고, 버전 번호에는 점이 있습니다. 2026-08-20 실측입니다.

경로 …/gigabyte/2.03 + image.RBU 첨부
→ 400 "경로의 마지막 이름 '2.03' 이 저장할 파일명으로 해석됐습니다. …"

문구는 R12-1 의 개선 덕에 무엇을 고쳐야 하는지 알려 주지만, 사용자는 여전히 매번 슬래시를 손으로 붙여야 합니다. 폼의 placeholder 가 …/ms03-ce0/2.03/image.RBU 인 것 자체가 버전 디렉토리를 한 층 두는 것이 표준 관례임을 보여 줍니다. 즉 가장 흔한 입력이 가장 자주 걸리는 상태입니다. 개선안은 §8 D8 에서 다루며, 리졸버가 공유 자산이라 채택하면 BIOS 도 함께 개선됩니다.

§2. 요구사항 (확정) + 비목표
  1. BMC 등록을 단일 폼으로 통합합니다. 경로 한 칸과 선택적 파일 한 칸만 둡니다. 파일이 있으면 그 경로에 저장하고, 없으면 그 경로에 이미 있는 파일을 등록(claim)합니다. BmcUploadMode · BmcRegisterExistingRequest · POST /register-existing 이 함께 폐지됩니다.
  2. 제조사별 파일 정책을 BMC 에 적용합니다. GIGABYTE 는 허용 확장자 .ima_enc 하나이며, 이는 Redfish 실측에서 실집행을 완주한 형식입니다. ASUS · FUJITSU 는 제약을 두지 않습니다. 금지 파일명은 BMC 에서 실측된 사례가 없어 빈 목록으로 둡니다.
  3. 진입점 탐지 계열을 완전히 제거합니다. BMC 가 마지막 사용자이므로 BundleEntrypointDetector · EntrypointDetectionStrategy · 전략 3 종 · EntrypointDetectionSupport · 진입점 예외 4 종을 함께 걷어냅니다.
  4. 컨트롤러 multi-catch 를 advice 로 승급합니다. 조건 분기 확장 금지 원칙이 요구하는 정리이며 BIOS 가 이미 같은 형태입니다.
  5. 목록 상세의 진입점 · 파일 수 표기를 제거합니다. 엔티티 필드 · DB 컬럼 · Response 필드는 그대로 두고 화면에서만 감춥니다 — BIOS 와 같은 방침입니다.
비 목표 — 각 항목이 어디로 가는지 함께 적습니다.
  • 집행 배선(Redfish SimpleUpdate 호출 · 진행 관찰 · 전원 오케스트레이션) → ue 스트림의 E2-3.
  • Subprogram 자원의 번들 모델 → 유지합니다. 그 도메인에서는 여러 파일 묶음이 자원의 본래 형태입니다.
  • BundleExtractionService 의 폴더 · 압축 경로와 공유 스크립트의 모드 분기 → Subprogram 전용으로 잔존합니다. 그쪽으로 옮겨 정리하는 일은 별도 슬라이스 후보입니다(Q3).
  • legacy 컬럼 제거와 경로 길이 255 완화 → DDL 이 필요하므로 이번에도 제외합니다(D4).
  • 네 도메인 공통 문구 · 응답 계약 정비 → S16-2.

upload-intent — 요청 필드를 firmwarePath · fileName · fileSize · version · allowCreateDirectory 로 재구성합니다. uploadMode · fileCount · entrypointRelativePath 는 제거되고, 기존 targetDirectory 는 firmwarePath 로 개명합니다. 길이 제한은 255 자를 유지합니다 — legacy 컬럼이 그 길이를 강제하므로 화면에서 더 긴 값을 받아 두면 저장 단계에서야 실패합니다(D4). 하드 검증 목록에 제조사 파일 정책 검사를 편입하되 검사 대상은 두 이름입니다. 업로드 파일의 원본 파일명과, 경로 해석을 마친 최종 파일명입니다. 경로에 확장자가 다른 파일명을 직접 적어 넣는 입력도 같은 자리에서 걸러야 하기 때문입니다. 이 핸드셰이크는 업로드가 있을 때만 호출됩니다.

upload — multipart 파라미터를 firmwareFile 하나로 줄이고 required=false 로 받습니다. 파일이 있으면 X-Upload-Token 을 1 회용으로 소비한 뒤 경로 해석 결과의 이름으로 저장하고, 없으면 토큰 없이 그 경로의 기존 파일을 등록합니다. 어느 쪽이든 본체에서 제조사 파일 정책을 다시 검사합니다. 화면을 거치지 않은 요청과, 토큰을 받은 뒤 다른 파일을 실어 보내는 요청을 막는 안전망입니다. 동시에 multi-catch 를 걷어냅니다 — 도메인 예외는 @RestControllerAdvice 가 받아 같은 상태 코드로 변환합니다.

register-existing — 삭제합니다. 이 엔드포인트가 하던 일은 "업로드 파일 없이 upload 를 호출" 하는 것과 같아졌습니다. 요청 DTO BmcRegisterExistingRequest 와 서비스의 registerExisting 진입점도 함께 사라지고, 그 안의 검증 · 중복 확인 · 저장 흐름은 단일 경로로 합류합니다.

GET /new — 위치는 BmcUploadController 그대로 두고(D7), 모델 속성에 vendor 파생 값을 더합니다. 파일 입력의 accept 속성, 금지 파일명 목록, 확장자 안내 문구 셋이며 모두 정책 전략에서 파생됩니다. 보드를 지정하지 않고 진입하는 /management/bmc/new 는 먼저 메인보드 모델을 고르게 하는 화면이므로 제조사가 정해지기 전이고, 이 값들은 보드 선택 후 /{boardId}/new 에서 채워집니다.

중복 확인(nudge) 배선은 현행 그대로입니다. 메타 충돌은 intent 에서, 내용 해시 충돌은 등록 본체에서 각각 409 로 분기하며 사용자의 진행 · 교체 · 취소 결정을 기다립니다. 기존 파일을 등록하는 경로에는 intent 가 없으므로 단계 A 가 발동하지 않고, 그 경로의 동일 (board, version) 중복은 본체의 활성 중복 검사와 단계 B 가 받습니다. 이는 현행 register-existing 과 같은 성질이며 새로 생기는 비대칭이 아닙니다.

500 행을 0 으로 두는 근거는 이렇습니다. 신설한 BmcFirmwareFilePolicyMissingException(500)은 사용자 액션이 아니라 전략 등록 누락을 개발자에게 드러내는 가드라 통합 시나리오로 재현할 대상이 아니고, 파일 시스템 오류로 500 이 되는 경로는 기존 추출 서비스 소관이며 이번 슬라이스가 새로 만들지 않습니다.

BIOS 회귀도 함께 봅니다. 공용 SPI 로 인터페이스를 옮기고 BIOS 전략 3 종을 마커 인터페이스 구현으로 바꾸는 변경이 들어가므로, 기존 BIOS 정책 테스트가 그대로 green 이어야 합니다. 알고리즘 본문은 이동만 하고 내용이 바뀌지 않으므로 기대값 수정 없이 통과해야 정상이며, 통과하지 못하면 이동 과정에서 무언가 달라진 것입니다. 신규 예외 InvalidBmcFirmwareFileException 은 위 400 범주 네 항목이 모두 트리거하므로 새 예외 관문의 요구를 충족합니다.

기존 결함 하나를 미리 적어 둡니다. DriftBulkApplyServiceTest 는 2026-08-19 13:00 KST 이후 항상 1 건 실패합니다(고정 시각과 Instant.now() 기반 만료가 어긋난 것으로 별도 hotfix 후보). CP4 의 green 판정에서 이 실패는 제외합니다.

재사용 예외들에서 실제로 달라지는 것은 예외가 HTTP 응답이 되는 경로입니다. 지금은 uploadBundle 의 catch 절이 예외를 받아 컨트롤러 안에서 상태 코드와 바디를 조립합니다. 승급 후에는 예외가 컨트롤러를 그대로 통과해 @RestControllerAdvice 에 도달하고, 거기서 타입별 매핑이 응답을 만듭니다. 응답의 겉모습은 같아야 하며 그것이 §6 의 회귀 항목입니다.

승급하지 않으면 신규 예외 둘은 catch 절을 한 단 더 얻거나, 얻지 못해 DomainException catch 에 흡수되어 500 으로 새는 두 갈래 중 하나가 됩니다. 후자는 과거 실제로 겪은 사고 유형입니다(§8 D5).

삭제되는 진입점 예외 넷은 자동 탐지가 사라지면서 발생 지점 자체가 없어집니다. EntrypointStrategyMissingException 이 하던 "전략 등록 누락을 즉시 드러낸다" 는 역할은 신설 BmcFirmwareFilePolicyMissingException 이 파일 정책 쪽에서 같은 방식으로 이어받습니다.

§8. 예상 부산물 / 주의 / 결정 사항

D1 — 정책 SPI 공유 = 공용 인터페이스 + 자원별 마커 서브인터페이스

채택. 알고리즘을 담은 FirmwareFilePolicyStrategy 를 management/common/firmware/ 로 올리고, BIOS · BMC 는 각각 아무 메서드도 더하지 않는 마커 인터페이스를 상속시켜 타입만 가릅니다. 비채택 대안 ① 은 supports(ResourceType, Vendor) 형태의 단일 SPI 로 통합하는 것입니다. 탈락 사유 — 구현 여섯이 한 목록에 섞이므로 조회마다 두 인자를 함께 검사해야 하고, 검사를 하나라도 빠뜨리면 BIOS 정책이 BMC 파일을 판정하는 조용한 오작동이 됩니다. 컴파일러가 잡아 주지 않는 종류의 실수라 더 나쁩니다. 비채택 대안 ② 는 BMC 에 인터페이스를 복제하는 것입니다. 탈락 사유 — assertAllowed 의 default 본문이 두 벌이 되어 중복 금지 불가침을 위반하고, 검사 순서를 바꿀 일이 생기면 고칠 자리가 둘이 됩니다.

D2 — dispatcher 공통화 = 추상 클래스 FirmwareFilePolicySupport<S>

채택. vendor 매칭과 뷰 파생 문자열 생성을 추상 클래스에 모으고, 두 도메인의 dispatcher 는 자기 타입의 전략 목록과 "전략 없음" 예외만 공급합니다. 근거는 분량입니다 — dispatcher 의 공개 메서드가 일곱이고 그 대부분이 "전략을 골라 데이터 메서드를 위임" 하는 같은 모양입니다. 비채택 대안 은 각 도메인이 dispatcher 를 복제하는 것이며 탈락 사유 는 중복입니다. 제네릭 타입 인자로 전략 타입을 받는 이유는 하위 dispatcher 가 자기 마커 타입의 목록을 그대로 다룰 수 있게 하려는 것입니다.

D3 — BMC 허용 확장자 = GIGABYTE .ima_enc 단일

채택. 근거는 E0-4 Redfish 실측입니다. UpdateService 의 SimpleUpdate 로 BMC 펌웨어의 실집행을 완주한 형식이 .ima_enc 이며 7 분 37 초가 걸렸습니다. 집행하지 못할 파일을 등록 단계에서 끊는 것이 이 제약의 목적입니다. 금지 파일명은 실측된 사례가 없어 빈 목록으로 둡니다 — BIOS 의 PFR 같은 사례가 관측되면 그때 GIGABYTE BMC 전략에만 추가합니다. "제조사 관례에서 온 제약은 그 제조사 안에서만 집행한다" 는 R12-1 의 원칙을 그대로 잇습니다.

D4 — legacy 컬럼 무변경 · 경로 길이 255 유지

채택. file_path VARCHAR(255) NOT NULL 과 board_model_id NOT NULL 을 그대로 미러링하고 경로 입력 길이 제한도 255 자를 유지합니다. 비채택 대안 은 두 컬럼을 제거하고 길이를 1024 로 복원해 BIOS 와 맞추는 것입니다. 탈락 사유 — DDL 이 필요하고, 병행 세션이 데이터베이스를 손보는 중이라 충돌을 피한다는 R12-1 의 방침이 이어집니다. 해소는 실행 데이터 모델 정비 계열에서 다룹니다. 다만 제한이 있다는 사실은 화면에 드러내야 합니다 — 사용자가 긴 경로를 다 적은 뒤에야 거절당하는 것은 UX 를 해칩니다(Q4).

D5 — multi-catch 를 advice 로 승급

채택. uploadBundle 의 catch 4 단을 걷어내고 도메인 예외를 advice 로 흘려보냅니다. 근거는 조건 분기 확장 금지 원칙과 BIOS 선례입니다. 비채택 대안 은 유지하는 것이며 탈락 사유 는 이번이 하필 새 예외가 둘 들어오는 슬라이스라는 점입니다. 분기를 늘려야 하는 시점에 분기를 정리하지 않으면 그 자리는 계속 자랍니다. 승급의 대가는 회귀 위험이고, 그것은 §6 의 전용 검증 항목과 §9 의 C4 로 감당합니다.

D6 — 일소 범위 정정 (진입점 계열만)

채택. 진입점 탐지 계열은 제거하고 추출 서비스와 공유 스크립트는 유지합니다. §1 의 실측이 근거입니다. R12-1 이 "번들 잔재를 일소한다" 고 적은 것은 펌웨어 자원의 계약 변경과 번들 개념 자체를 구분하지 않은 서술이었고, 실제로는 Subprogram 이 번들 모델의 정당한 사용자로 남아 있습니다. 이 정정을 plan 에 명시하는 이유는, 정정 없이 진행하면 구현 중에 "일소하기로 했는데 왜 남기는가" 라는 되물음이 생기고 그 판단이 기록되지 않은 채 흘러가기 때문입니다.

D7 — GET /new 위치 유지

채택. 폼 진입점을 BmcUploadController 에 그대로 둡니다. 비채택 대안 은 BIOS 대칭을 위해 BmcMetadataController 로 옮기는 것입니다. 탈락 사유 — 이번 요구 다섯 중 어느 것도 이 이동을 필요로 하지 않고, 컨트롤러 간 메서드 이동은 URL 매핑 · 테스트 · fragment 반환 경로를 함께 건드립니다. plan 범위 밖의 churn 이며, 배치 비대칭은 기능에 영향을 주지 않습니다.

D8 — 경로 해석 휴리스틱 개선 사용자 결정 필요

현행 규칙은 "마지막 세그먼트에 점이 없으면 디렉토리" 입니다. 그런데 펌웨어 디렉토리 이름이 버전 번호(2.03)인 관례에서는 점이 있으므로 이 규칙을 빠져나가고, 정상 파일을 첨부했는데도 400 으로 거절됩니다(§1 실측).

제안 — 허용 확장자 목록이 있는 제조사에서는 "마지막 세그먼트의 확장자가 허용 목록에 없으면 디렉토리로 간주" 로 바꿉니다.
