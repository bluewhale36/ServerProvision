§0. 이 단계가 어떻게 생겼는가

U3-5(그룹 단위 일괄 할당)의 CP1 을 진행하며 코드를 실측하다가, 일괄 할당의 사전 분류가 소비할 판정 두 가지가 코드에 아예 없다는 것이 드러났다. 회수된 서버를 할당에서 배제하는 규칙과, 정의서가 요구하는 메인보드를 서버의 실제 보드와 대조하는 규칙이다. 둘 다 도메인에는 실재하는 제약인데 확인하는 자리가 없거나 엉뚱한 곳에만 있었다.

그 둘을 세우는 일과 그룹 일괄 할당을 한 슬라이스에 담으면 수정 파일 17 건 · 검증 항목 28 건이 된다. 2026-08-12 사용자 판단으로 U3-5-a(판정) → U3-5-b(일괄 할당) 로 나눴다. 나눈 기준은 코드 안에 이미 그어져 있었다 — 일괄 할당의 분류기는 두 판정을 소비할 뿐 만들지 않는다.

분할이 설계를 하나 개선했다 — 판정을 독립 슬라이스로 떼어내자 판정들을 순서대로 묶는 자리가 필요하다는 것이 분명해졌고(§8 DEC-B), 그 결과 일괄 할당 쪽 분류기의 시그니처가 인자 넷에서 셋으로 줄었다. 한 슬라이스 안에 있었다면 분류기가 두 판정을 직접 들고 순서까지 아는 형태로 굳었을 것이다.

분할 전 우산 계획은 plan/26-08-12_11-52-30_U3-5_plan.html 로 고정했다.

§1. 현재 상태 (실측 진단)

할당 경로에 지금 있는 가드

AssignmentCommandService.assign 은 셋을 본다 — 게스트가 존재하는가(404), 정의서가 활성이며 삭제되지 않았는가(SettingDefinition.assignBlockReason, 409), 이미 활성 스냅샷이 있는가(409). reassign 은 여기에 개시 여부(SettingAssignment.reassignBlockReason, 409)를 더한다.

서버 자신의 상태를 보는 가드는 하나도 없다. 정의서의 상태는 보는데 서버의 상태는 보지 않는다.

없는 것 ① — 회수된 서버의 할당을 막지 않는다

assign 과 reassign 어디에도 decommissionedAt 검사가 없다. 화면도 같다 — templates/provisioning/server-detail.html 의 할당 폼 노출 조건은 th:unless="${phaseRail.assigned}" 하나뿐이라 회수된 서버에도 할당 폼이 그대로 열린다.

회수는 GuestServerStatus.derive 가 신호와 무관한 최우선으로 두는 상태다. 회수된 서버는 개시도 막히고(ProvisioningStartRejectedException.decommissioned) 수동 실패 전환도 막힌다. 할당만 열려 있다.

없는 것 ② — 정의서가 요구하는 보드를 서버와 대조하지 않는다

정의서의 펌웨어 업데이트(BasicUpdateRequest)와 BIOS 설정(BasicSettingRequest) 단계는 BoardModelSelectionRequest 를 들고 있다 — AUTO(실행 시점 감지) 또는 SPECIFIED(boardModelId)(특정 보드 고정)다. 둘이 함께 있으면 같은 선택이어야 한다는 것을 SettingSaveRequest.isBoardSelectionConsistent 가 강제하고, 보드를 지정하면 BIOS 세팅 템플릿이 그 보드 것만 남도록 setting-form.js 가 목록을 걸러낸다.

그 대조는 정의서를 만들 때까지만이다. 할당 선택지를 만드는 JpaSettingQueryService.findAssignable() 은 인자를 받지 않아 어느 서버에 할당하는지 알지 못하고, isDeleted 와 assignBlockReason() 만 본다. 그래서 메인보드 X 전용 정의서를 보드 Y 서버에 할당할 수 있다.

같은 뿌리

둘은 같은 형태의 공백이다 — 판정이 한 화면 안에 갇혀 있으면 다른 경로가 생길 때 따라오지 못한다. setting-form.js 안의 필터는 정의서 작성 화면 밖으로 나가지 못하고, 회수 여부는 개시 · 수동 실패 전환 경로에만 배선돼 있다. 이 단계가 하는 일은 두 판정을 이름 있는 도메인 규칙으로 끌어올려 화면과 서버 가드가 같은 것을 부르게 하는 것이다.

뒤엣것을 '보드 대조'가 아니라 '하드웨어 대조'로 부른다. 지금 대조하는 축은 메인보드 하나뿐이지만, U4 에서 세팅 정의서에 디스크 구성에 따른 파티셔닝 · RAID 구성이 들어오면 그것도 같은 일의 다른 축이 된다. 이름에 '보드'를 새기면 그때 개념부터 어긋난다. 다만 축이 하나인데 추상 계층을 미리 만들지는 않는다 — 그 판단의 근거와 U4 가 실제로 무엇을 건드리게 되는지는 §8 DEC-H 에 적었다.

§2. 요구사항 (확정) + 비목표
  • R1 — 회수된 서버에는 신규 할당도 재할당도 되지 않는다.
  • R2 — 정의서가 특정 메인보드를 요구하면 그 보드의 서버에만 할당된다.
  • R3 — 막힐 조작은 화면이 먼저 막고 왜 막혔는지 알린다. 서버 가드는 안전망으로만 발동한다.
  • R4 — 보드를 아직 수집하지 못한 서버는 막지 않되, 대조하지 못했다는 사실이 보인다.
  • R5 — 이미 만들어진 할당에는 소급하지 않는다. 다만 지금 든 정의서가 이 서버의 하드웨어와 맞지 않으면 서버 상세가 경고한다.
  • R6 — 판정 결과는 차단 종류를 구분해 돌려주고, 그것이 하드웨어 불일치인지를 종류 스스로가 답한다 — U3-5-b 가 적색으로 칠할 대상을 고를 때 종류 이름을 비교하지 않게 하기 위해서다.
  • R7 — 하드웨어 축이 늘어날 자리를 남긴다. U4 의 디스크 구성 대조가 상수 하나와 요구사항 값 하나를 더하는 것으로 들어와야 하고, 그 때문에 지금 추상 계층을 미리 만들지는 않는다.
비 목표 :
  • 그룹 단위 일괄 할당 — U3-5-b.
  • 이미 만들어진 스냅샷의 소급 무효화 — 하지 않는다. 스냅샷은 할당 시점 복사본이라 원본 상태 변화와 독립이라는 U3-2-b DEC-G 의 결을 따른다.
  • AUTO 보드 선택의 실행 시점 감지 — 실행 엔진(E 계열) 소관.
  • 메인보드 외의 하드웨어 축(디스크 구성 · CPU · 메모리 등) — U4 의 세팅 정의서 기능 확장 소관이다. 이 단계는 축을 하나만 구현하되 축이 늘어날 자리를 남긴다(§8 DEC-H).
  • 정의서 작성 화면의 보드 필터 개선 — 이미 동작하며 이 단계가 건드리지 않는다.
  • 하드웨어가 나중에 갱신되어 구성이 바뀐 서버의 기존 할당 재검사 — 경고까지이고 자동 조치는 없다.

판정 JS (서버 도메인과 1:1)

function demoEvaluate(server, def) {
    if (server.state === 'decommissioned') {
        return {kind: 'DECOMMISSIONED', reason: '회수된 서버에는 세팅 정의서를 할당할 수 없습니다'};
    }
    if (def.board !== null && server.board !== null && def.board !== server.board) {
        return {kind: 'BOARD_MISMATCH',
                reason: '이 정의서는 메인보드 ' + def.board + ' 전용입니다 — 이 서버는 ' + server.board + ' 입니다'};
    }
    return null;   // 통과. def.board 가 있는데 server.board 가 null 이면 '보드 확인 전' 표식만 단다
}

차단 종류를 문자열이 아니라 이름 있는 값으로 돌려주는 것이 요점이다 — 화면이 색을 정하려면 "무엇 때문에 막혔는가" 를 알아야 한다.

체험시키고 싶은 것

서버 보드를 X11SPM 으로 바꾸면 bios-ms03 이 잠기고 fw-x11 이 열린다. 같은 서버라도 정의서마다 결과가 다르므로 옵션 단위로 잠근다. 서버 상태를 회수됨 으로 바꾸면 세 정의서가 한꺼번에 잠긴다 — 이때는 옵션을 잠그는 것이 아니라 폼 자체를 닫는 것이 맞다는 것을 메시지가 말한다. 보드 확인 전 으로 바꾸면 보드 전용 정의서도 열리되 회색 표식이 붙는다.

새 타입 ① — RequiredBoardModel (Value Object, provisioning/setting/vo/)

"이 정의서가 요구하는 메인보드" 를 이름 있는 값으로 세운다. Long boardModelId 를 맨손으로 들고 다니면 그것이 서버의 보드인지 정의서가 요구하는 보드인지 타입이 말해 주지 않는다.

구성내용
필드Long id · String name
추출static RequiredBoardModel from(List<AbstractProcessRequest>) — 보드를 지정한 단계가 없거나 전부 AUTO 면 null
판정String blockReasonFor(Long serverBoardId, String serverBoardName) — 통과면 null

추출을 List<AbstractProcessRequest> 에서 하는 것이 중요하다. 정의서 원본(SettingDefinition.getProcesses())과 할당 스냅샷(SettingAssignment.getProcesses())이 같은 payload 타입을 들고 있으므로(U3-1 이 무변환 복사한다) 같은 추출 코드가 양쪽에 쓰인다. 선택지 잠금은 원본에서, 이미 든 할당의 경고는 스냅샷에서 뽑는다 — 얼린 정의서가 요구하는 보드는 원본이 나중에 바뀌어도 스냅샷이 든 그 값이어야 하기 때문이다.

보드를 지정하는 단계는 펌웨어 업데이트와 BIOS 설정 둘뿐이고 둘이 함께 있으면 같은 선택이어야 하므로, 정의서 하나가 요구하는 보드는 최대 하나다. 추출이 모호해질 자리가 없다.

새 타입 ② — AssignmentBlockKind (enum, provisioning/assignment/enums/)

상수무엇 때문에 막히는가하드웨어 불일치화면
DECOMMISSIONED서버가 회수됐다아니다폼 자체를 닫는다
BOARD_MISMATCH정의서가 요구하는 메인보드와 다르다그렇다옵션을 잠그고 적색 표시

상수마다 세 메서드를 갖는다.

  • String reasonFor(AssignmentEligibility context) — 해당하면 사유, 아니면 null
  • RuntimeException toException(UUID guestId, String reason) — 서버 가드가 던질 예외
  • boolean hardwareIncompatible() — 화면이 적색으로 칠할 것인가

세 번째가 확장을 위한 자리가 아니라 지금도 옳은 설계다. 이것이 없으면 화면이 kind == BOARD_MISMATCH 로 색을 정하게 되는데, 그러면 "왜 적색인가" 라는 지식이 상수가 아니라 호출자에 산다. 상수가 스스로 대답하게 두면 하드웨어 축이 늘어도 호출자는 그대로다(§8 DEC-H).

그리고 static 진입점 하나를 갖는다.

static AssignmentBlock evaluate(AssignmentEligibility context)   // 통과면 null

values() 를 선언 순으로 순회해 처음 null 이 아닌 사유를 만나면 그 종류와 함께 돌려준다. 판정 순서가 곧 상수 선언 순서이고, 새 차단 사유는 상수 하나를 더하는 것으로 순회에 자동 편입된다.

AssignmentBlock 은 AssignmentBlockKind 안의 중첩 record 다 — record AssignmentBlock(AssignmentBlockKind kind, String reason).

새 타입 ③ — AssignmentEligibility (record, provisioning/assignment/vo/)

판정 입력 묶음이며 셋을 든다.

필드무엇비고
GuestServer server회수 여부의 출처—
GuestServerDetail detail서버가 실제로 가진 하드웨어수집 전이면 null
List<AbstractProcessRequest> processes정의서 원본 또는 할당 스냅샷의 단계들요구사항 추출의 재료

요구사항을 미리 추출해 담지 않는 것이 요점이다. 컨텍스트가 RequiredBoardModel 을 필드로 들면 하드웨어 축이 늘 때마다 필드가 함께 는다. 대신 단계 목록을 그대로 넘기고 추출은 그 축을 아는 상수가 한다 — BOARD_MISMATCH.reasonFor 안에서 RequiredBoardModel.from(context.processes()) 를 부른다.

GuestServerDetail 을 통째로 드는 이유도 같다. 메인보드는 구조화 FK(board_model_id)로, 디스크 · CPU · 메모리 · PCIe 는 hardware_spec JSON 안에 있어 둘 다 이 엔티티 하나에 모여 있다. 보드 식별자 두 개를 풀어서 담았다면 디스크 축이 올 때 컨텍스트를 다시 열어야 한다.

도메인 메서드 신설 — GuestServer.assignBlockReason()

회수됐으면 "회수된 서버에는 세팅 정의서를 할당할 수 없습니다", 아니면 null. SettingAssignment.reassignBlockReason() · SettingDefinition.assignBlockReason() · GuestServerGroup.addBlockReason() 과 같은 형태다. AssignmentBlockKind.DECOMMISSIONED 가 이것을 호출한다 — enum 이 회수 규칙을 직접 알지 않고 엔티티에 묻는다.

둘을 하나로 합치지 않는다. 앞은 서버 자신의 상태이고 뒤는 두 대상의 짝이 맞지 않는 것이다. 운영자가 취할 다음 행동도 다르다 — 앞은 서버를 다시 등록해야 하고 뒤는 맞는 정의서를 고르거나 맞는 서버를 골라야 한다.

반대로 뒤엣것을 하드웨어 축마다 쪼개지도 않는다. 지금 축은 메인보드 하나뿐이지만 U4 가 디스크 축을 더할 때 DefinitionDiskMismatchException 을 또 만들면, HTTP 상태도 같고 운영자의 다음 행동도 같은 예외가 축 수만큼 늘어난다. 예외를 나누는 기준은 상태 코드와 운영자의 다음 행동이지 내부 원인이 아니다 — 구체적인 원인은 메시지가 싣고, 그 메시지는 각 축의 reasonFor 가 만든다.

advice 에 명시 등록하지 않는다 — 상위 타입 핸들러가 @ResponseStatus 를 계층 탐색으로 읽어 흡수한다(new-exception.md §2 의 세 조건 모두 미해당).

예외 생성을 enum 상수가 맡는다. 서버 가드가 kind 로 분기해 예외를 고르면 새 차단 종류가 생길 때 그 분기가 자란다. AssignmentBlockKind.toException(...) 이 상수별 메서드이므로 상수를 더하면 컴파일이 예외 매핑을 강제한다.

폼 규약 (new-form.md)

할당 · 재할당은 @ResponseBody 로 JSON 을 돌려주고 server-assignment.js 가 처리하는 XHR 폼이다. 판정 표에서 아무것도 붙이지 않는 칸이며, 그 스크립트가 이미 기본 동작을 취소하므로 전역 인터셉터가 비켜간다. 거절은 window.FormError 가 배너 · 인라인으로 매핑한다. FormSubmissionConventionTest 의 기대값은 변하지 않는다.

§8. 결정

DEC-A. 판정은 도메인이 갖고 화면과 서버 가드가 함께 부른다

대안 셋을 비교했다.

안내용판정
①서비스 안 if-throw — AssignmentCommandService 에 검사 두 줄탈락
②도메인 메서드 + 조합 지점 — 각 도메인이 사유를 돌려주고 한 곳이 순서를 안다채택
③검사 전담 서비스 — AssignabilityInspector 가 전부 판정탈락

①이 탈락하는 이유는 화면이 같은 판정을 부를 수 없기 때문이다. 서비스 안의 if 는 밖에서 재사용되지 않으므로 화면이 조건을 복붙하게 되고, 그것이 이 프로젝트가 반복해 겪은 drift 다(childEnableBlockReason 선례가 이 문제를 푼 방식이 ②다).

③은 도메인 지식이 서비스로 새고 엔티티가 자기 규칙을 모르게 된다. 뷰가 판정 하나 하려고 서비스를 주입받아야 하는 것도 무겁다.

DEC-B. 판정들을 순서대로 묶는 자리를 둔다 — 없으면 네 곳에 복붙된다

판정 순서를 필요로 하는 곳이 넷이다. 단일 할당 가드 · 재할당 가드 · 서버 상세 뷰모델 · (다음 단계) 일괄 할당 분류기. 조합 지점이 없으면 "회수 먼저 보고 그다음 보드" 가 네 번 적힌다.

AssignmentBlockKind.evaluate 가 그 자리다. 이것이 U3-5-a 를 독립 슬라이스로 떼어낸 덕에 드러난 설계다 — 한 슬라이스 안에 있었다면 일괄 할당 분류기가 두 사유를 각각 인자로 받아 순서까지 아는 형태로 굳었을 것이다. 실제로 분할 전 계획의 분류기 시그니처는 인자가 넷이었고 지금은 셋이다.

DEC-C. 조합은 if-chain 이 아니라 enum 순회다

두 방식을 비교했다.

방식새 차단 사유가 생길 때
if-chain 두 줄조합 지점에 줄 추가 + 예외 매핑 분기에도 줄 추가
enum 순회상수 하나 추가 — 순회 · 예외 매핑이 컴파일로 강제

CLAUDE.md 는 "신규 케이스가 추가될 때 분기문에 줄을 늘리지 않는다" 를 불가침으로 둔다. 여기서 그것을 미래 예측이 아니라 이미 일어난 사실로 정당화할 수 있다 — 차단 사유는 이번에 하나(회수)에서 둘(회수 + 보드)로 늘었다. AssignmentStateView.badgeClass 가 exhaustive switch 로 색 누락을 컴파일 시점에 막는 것과 같은 층위이며, 여기서는 매핑이 아니라 동작이므로 상수별 메서드를 쓴다.

DEC-D. 회수는 폼을 닫고 보드 불일치는 옵션을 잠근다 — 비대칭에 이유가 있다

회수는 서버의 상태라 어떤 정의서를 골라도 막힌다. 선택지를 전부 잠근 폼을 보여주는 것은 조작할 수 없는 화면을 그려 놓고 이유를 옵션 툴팁에 숨기는 셈이다. 그래서 폼 자리에 사유를 적는다.

보드는 정의서마다 다르다. 같은 서버에서 어떤 정의서는 되고 어떤 것은 안 되므로 옵션 단위로 잠그고 사유를 라벨에 붙인다.

지우지 않고 잠그는 것도 의도다. 목록에서 조용히 사라지면 운영자는 그 정의서가 없어진 것인지 자기 서버에 안 맞는 것인지 알 수 없다. definition-options 조각이 이미 사용 중단 권고를 라벨에 덧붙이고 있으므로 같은 자리에 사유를 붙인다.

DEC-E. 보드를 모르면 막지 않고 표식만 단다

수집 전 서버에 미리 정의서를 할당해 두고 부팅시키는 흐름이 실재한다. 모른다는 이유로 막으면 그 흐름이 끊긴다.

대신 대조하지 못했다는 사실 자체를 보이게 한다 — 조용히 통과시키는 것과 다르다. 실제로 보드가 어긋난 채 프로비저닝이 시작되면 실행 엔진이 그때 막아야 하며, 그것은 E 계열 소관으로 남긴다.

DEC-F. 이미 만들어진 할당에는 소급하지 않는다

할당 스냅샷은 할당 시점 복사본이고 원본 상태 변화와 독립이다 — U3-2-b DEC-G 가 "비활성 정의서는 신규 할당만 차단하고 기존 스냅샷은 건드리지 않는다" 로 정한 것과 같은 결이다.

다만 경고는 한다. 서버 상세가 지금 든 할당의 얼린 보드를 서버의 실제 보드와 대조해 어긋나면 알린다. 이 판정이 그대로 U3-5-b 의 그룹 멤버 표 적색 표시가 된다.

소급 무효화를 검토했으나 탈락시켰다. 무효화하면 진행 중이던 서버의 계획이 사라져 실행 엔진이 참조할 스냅샷이 없어지고, 하드웨어 재수집으로 보드 정보가 바뀌는 것만으로 운영 중인 할당이 대량 소멸할 수 있다.

DEC-G. 차단 종류를 값으로 돌려준다

사유 문자열만 돌려주면 화면이 색을 정할 수 없다. U3-5-b 는 보드 불일치를 적색으로, 다른 차단은 일반 제외로 표시해야 한다.

AssignmentBlock(kind, reason) 이 그래서 종류와 사유를 함께 든다. 종류는 화면이 보고 사유는 사람이 본다. 기존 *BlockReason() 메서드들이 String 을 돌려주는 관례와 어긋나 보이지만, 그 메서드들은 한 가지 이유만 갖는 단일 판정이고 이것은 여러 판정의 조합 결과다. 층위가 다르다.

다만 화면은 종류를 직접 비교하지 않는다. kind == BOARD_MISMATCH 로 색을 정하면 하드웨어 축이 늘 때 그 비교가 함께 자란다. 화면이 묻는 것은 kind.hardwareIncompatible() 하나다.

DEC-H. 하드웨어 대조로 이름 짓되 추상 계층은 지금 만들지 않는다

이 단계가 대조하는 하드웨어는 메인보드 하나다. 그런데 U4 에서 세팅 정의서에 디스크 구성에 따른 파티셔닝 · RAID 구성이 들어올 예정이고, 그것은 "정의서가 요구하는 하드웨어와 서버가 가진 하드웨어를 대조한다" 는 같은 일의 두 번째 축이다. 그래서 개념의 이름을 '보드 대조' 가 아니라 '하드웨어 대조' 로 둔다 — 지금 축이 하나인 것은 사실이지만, 그 사실을 개념 이름에 새기면 두 번째 축이 올 때 이름부터 어긋난다.

그렇다고 HardwareRequirement 인터페이스를 지금 만들지는 않는다. 구현이 하나뿐인 인터페이스는 CLAUDE.md 가 금지하는 사전 분리다. 디스크 요구사항이 실제로 생겨 RequiredBoardModel 과 그것의 공통 형태가 실측으로 드러날 때 뽑는다 — 보드는 식별자 하나를 비교하지만 디스크는 개수 · 용량 · 인터페이스를 함께 볼 가능성이 커서, 지금 공통 인터페이스를 상상해 만들면 그때 맞지 않을 확률이 높다.

지금 인터페이스를 만들지 않는 비용이 0 인 이유 — 호출자(서버 가드 · 화면 · 다음 단계의 분류기)는 AssignmentBlockKind.evaluate 하나만 부른다. 나중에 인터페이스를 뽑아도 호출자는 한 줄도 바뀌지 않는다. 확장을 위해 미리 치를 값이 없으므로 미루는 것이 이득이다.

U4 가 디스크 축을 더할 때 무엇을 건드리는지 미리 짚어 둔다. 이 표가 이 설계가 확장 가능한지에 대한 실제 답이다.

대상U4 에서
AssignmentBlockKind상수 1 개 추가 — reasonFor · toException · hardwareIncompatible()=true
요구사항 Value ObjectRequiredDiskLayout 신설(RequiredBoardModel 옆)
AssignmentEligibility변경 없음 — 단계 목록과 GuestServerDetail 을 이미 든다
예외변경 없음 — DefinitionHardwareMismatchException 재사용
서버 가드 · 화면변경 없음 — evaluate 와 hardwareIncompatible() 만 본다
테스트그 축의 진리표 추가

변경 없음이 셋인 것은 우연이 아니다. 축마다 달라지는 것(무엇을 요구하고 어떻게 비교하는가)만 새로 만들고, 축과 무관한 것(순서 · 결과 모양 · 예외 · 표시 규칙)은 이미 축을 모르게 두었다. 이것이 인터페이스 없이 확보한 확장성이며, 다형성을 더 얹지 않은 이유이기도 하다.

열린 질문 없음 — 분할 시점에 OQ-1 · OQ-4(단일 경로 적용 여부)가 확정됐고 나머지는 U3-5-b 로 넘어갔다. 이 단계에서 사용자 판단을 기다리는 항목은 없다.

식별자는 CP5 규약을 따라 A = 정상 흐름, B = 비정상 조작, C = 막는 방식으로 나눈다.
