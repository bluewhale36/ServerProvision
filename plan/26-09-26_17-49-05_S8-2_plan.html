§1. 현재 상태 (2026-09-26 · feat/S8-1_list-query 작업 트리 실측)

게스트 서버 목록은 전 서버를 읽은 뒤 메모리에서 거르고 묶습니다. 필터는 진행 단계 하나(단일 값)뿐이고, 링크 칩의 URL 은 컨트롤러가 조립합니다. 아래 표가 현행입니다.

항목현행이 슬라이스에서
진입점 GET /provisioning/server → GuestServerController.list. 파라미터 phase(단일) · pending(open) · includeDecommissioned 수정 파라미터 확장
조회 GuestServerQueryService.findGrouped(phase, includeDecommissioned) — findAllByOrderByCreatedAtDesc 또는 회수 제외판으로 전수 수정 Specification 으로
조립 assembleGroups — 상세 · 대표 NIC · 진행을 id 묶음으로 한 번씩 읽고, matchesPhase 로 메모리 필터 뒤 등록 진행 중 / 시간 구간 × 스펙으로 묶는다 제거 matchesPhase
칩 링크 n-chip-link. URL 은 listUrl(phase, pendingOpen, includeDecommissioned) 가 조립(chipUrls EnumMap · allChipUrl · pendingToggleUrl) 제거 폼 + ListLinks
회수 토글 머리의 체크박스 data-include-deleted-toggle="includeDecommissioned" + include-deleted-toggle.js 이동 폼 필드로
실시간 server-stream.js 가 SSE 신호마다 fetch(location.href) → [data-live="server-list"] 만 교체(DEC-E). 필터 띠는 영역 밖 유지 영역 이름 불변
행 조각 fragments/provisioning/server-rows :: head / row(server) — 열 10 · data-nav-key · n-table-servers 고정 레이아웃 유지 표 보기도 이것
소속 그룹 배지 컨트롤러가 GuestServerGroupQueryService.findBadges(보이는 서버 id) 로 받아 모델에 얹는다(DEC-C) 유지 같은 합성
CSS S8-1 에서 .n-filter-bar · .n-chip-link 가 전역(style.css §16)으로 이동. CP5 C4 회귀 없음 · O-9 치수 미세 변화 제거 .n-chip-link

1-1. 필터가 SQL 로 옮겨질 수 있는가 — 엔티티 관계와 도출값

엔티티관계필터가 쓰는 속성
GuestServerDetail1:1 · 자식 → GuestServerboardModel(FK) · bmcIp(VO) · boardSerial
HostNicBindingN:1 · 자식 → GuestServeripAddress(VO) · isPrimary
ProvisioningProgress1:1 · 자식 → GuestServercurrentStep · startedAt · failedAt · completedAt

셋 모두 자식이 GuestServer 를 가리키고 GuestServer 쪽 역참조가 없습니다. 그래서 필터는 join 이 아니라 상관 서브쿼리 exists 로 풉니다(S8-1 의 hasProcessType 과 같은 방식).

도출값 둘은 컬럼 조합이라 SQL 술어가 됩니다 — 현재 단계는 currentStep.getPhaseType() 이고(ProvisioningPhaseStep 16 상수 → ProvisioningPhase 8), 운영 상태는 GuestServerStatus.derive(progress, decommissionedAt) 입니다. derive 의 우선순위는 회수됨(decommissionedAt) → 실패(failedAt) → 완료(completedAt) → 등록됨(progress 없음 또는 startedAt 없음) → 프로비저닝 중입니다. 단계는 step 목록의 IN 으로, 상태는 네 null 조합의 술어로 옮겨집니다(§4-3).
§2. 요구사항 (확정) + 비목표

2-1. 사용자 결정 (누적)

  1. B 안 — 기존 묶음 보기(등록 진행 중 + 상대 시간 × 스펙)를 기본으로 두고 표 보기를 더합니다. 페이징 · 정렬은 표 보기에만 있습니다.
  2. 서버 필터에 최초 등록 시각 범위(from · to)를 추가합니다.
  3. 검색 · 필터 축 · 쪽 크기(20 · 50 · 100)는 세션 제안대로 확정됐습니다(2026-09-21).
  4. S8-1 의 UI 규칙을 따릅니다 — 조회 띠 = GET 폼 · 정렬 = 항목 + 방향 셀렉트 둘 · 검색 입력은 Enter 가 주 경로('검색' 버튼은 남김) · 다중 선택 칩 + "전체" 해제 버튼.
  5. S8-4(가칭) 예고(2026-09-26) — 모든 목록의 기본 필터 "생성 일시 1 년 이내" + '검색' 버튼이 여는 상세 조회 창, 그리고 조회 띠의 필터를 전부 그 창 안으로 옮기는 일입니다. S8-2 는 이것을 앞당겨 만들지 않고, 필터를 낱개 n-filter-group 블록으로 두어 옮기기 쉽게만 합니다.

2-2. 공통 규칙 (S8-1 그대로)

GET 폼 · 칩 · 셀렉트는 즉시 제출 · 검색은 Enter · 빈 값과 기본값은 URL 에서 생략 · 제출은 첫 쪽으로 · 쪽 이동만 링크 · 알 수 없는 값은 400 입니다.

2-4. 화면 규칙

  1. R1 묶음 보기에도 검색 · 필터가 똑같이 걸립니다. 현행 phase 필터가 묶음 보기에서 동작하므로 빼면 회귀입니다.
  2. R2 묶음 보기는 쪽 · 정렬이 없습니다. 순서는 시간 구간이 정하므로 정렬 셀렉트와 쪽 이동 줄을 그리지 않습니다.
  3. R3 표 보기의 행은 기존 server-rows 조각을 그대로 씁니다(열 10 · 그룹 배지 · 연결 배지 · nav-key).
  4. R4 결과 건수는 SSE 교체 영역 안에 둡니다(교체 때 함께 갱신). 검색 입력 · 칩 · 셀렉트는 영역 밖입니다(입력 중인 글자 보존).
  5. R5 빈 결과는 두 갈래입니다 — 조건으로 비었음(초기화 유도) / 아예 없음(현행 PXE 안내). S8-1 R8 과 같습니다.
  6. R6 기간이 거꾸로(from > to)면 결과가 비고 "시작일이 종료일보다 늦습니다. 기간을 다시 고르십시오." 를 안내합니다. UI 는 두 입력의 min · max 로 거꾸로 고를 수 없게 막습니다(주소창 직접 입력만 이 경로에 닿습니다).

가짜 서버 30 대(결정적 생성 · 난수 없음)를 두 보기로 그립니다. 기준 시각은 2026-09-26 17:40 입니다. 위 세그먼트로 묶음 / 표 를 바꾸고, 조회 띠의 칩 · 셀렉트 · 기간 · 체크박스를 바꾸면 아래 결과와 캡션이 함께 바뀝니다.

캡션 셋째 줄까지가 판정입니다. URL 은 §2 규칙대로 조립한 경로이고(빈 값 · 기본값 생략, view=GROUPED 생략, 묶음 보기면 sort · dir · page · size 없음), Specification 은 지금 살아 있는 술어의 합성과 저장소 호출입니다. 표 · 묶음을 거르는 술어와 캡션의 술어는 같은 목록 하나에서 나옵니다. 운영 상태는 demoStatus() 한 함수가 판정하며, 그 본문은 GuestServerStatus.derive 의 우선순위(회수됨 → 실패 → 완료 → 등록됨 → 프로비저닝 중)를 그대로 옮긴 것입니다. 셋째 줄 술어 대조는 §4-3 의 SQL 술어를 30 대 전부에 적용해 demoStatus() 와 어긋나는 서버 수를 셉니다.

진행 단계와 운영 상태 칩은 여럿 고를수록 넓어집니다(축 안 OR · D6). 축과 축 사이는 AND 라 다른 축을 더하면 좁아집니다. '펌웨어 두 단계' 프리셋이 이 차이를 건수로 보여줍니다.

그룹 조건은 이 record 에 두지 않습니다(CP1 세션 판정). GroupFilter 는 provisioning 타입이라 execution 의 record 가 들면 D5 가 막으려던 역방향 의존이 생깁니다. 컨트롤러(provisioning)가 @RequestParam(value = "group", required = false) GroupFilter group 으로 따로 받아 scopeOf(group) 로 ServerScope 를 만들고, 화면의 "조건이 걸렸는가" 는 query.isFiltered() || group.isSet() 를 모델 filtered 로 넘겨 판단합니다.

statuses 에서 DECOMMISSIONED 를 무시하는 이유는 회수 여부를 체크박스 한 축이 맡기 때문입니다(D7). 주소창에 status=DECOMMISSIONED 를 직접 넣어도 400 이 아니라 조용히 빠집니다(CP5 B2).

4-3. GuestServerSpecifications.of(query, scope)

술어조건
searchAny(q)name · cast(systemUUID as String) · serialNumber LIKE ∨ exists 대표 NIC ipAddress LIKE ∨ exists 상세(bmcIp LIKE ∨ boardModel.modelName LIKE)

phaseIn 의 step 목록은 손으로 적지 않고 ProvisioningPhaseStep.values() 를 getPhaseType() 으로 걸러 만듭니다. step → phase 매핑의 SSOT 가 enum 한 곳에 남습니다.

운영 상태술어 (진행 p 는 상관 서브쿼리)
회수됨decommissionedAt 있음
실패회수 아님 ∧ exists p(failedAt 있음)
완료회수 아님 ∧ exists p(failedAt 없음 ∧ completedAt 있음)
등록됨회수 아님 ∧ not exists p(startedAt 있음 ∨ failedAt 있음 ∨ completedAt 있음)
프로비저닝 중회수 아님 ∧ exists p(startedAt 있음 ∧ failedAt 없음 ∧ completedAt 없음)
등록됨 술어 정정(에이전트 발굴 · CP1 세션 채택) — 브리프 원안은 "회수 아님 ∧ not exists p(startedAt 있음)" 입니다. 그런데 ProvisioningProgress 에는 R13 이 만든 미개시 실패가 있습니다 (startedAt null 인 채 진단 창에서 게스트가 FAILED 를 보고한 경우 — isStartableWith 주석). derive 는 실패를 등록됨보다 먼저 보므로 이 서버를 실패로 판정하지만, 원안 술어는 같은 서버를 등록됨으로도 잡아 두 상태에 동시에 걸립니다. 그래서 등록됨에서 실패 · 완료 신호가 있는 진행을 함께 빼는 형태로 적었습니다. completedAt 은 markCompleted 가 미개시를 막아 실제로는 startedAt 없이 생기지 않지만, §6-3 의 조합 전수 대조가 그 조합도 만들므로 술어에 포함했습니다. 데모의 셋째 캡션 줄이 원안 술어였을 때의 불일치 수를 함께 보여줍니다.

8-2. 탈락 사유

D1 — 별도 경로는 SSE 범위 · nav-stack · 링크를 둘로 만듭니다. JS 전환은 URL 상태 원칙(DEC-E)을 깨서, 새로고침이나 SSE 재조회 때 보기가 풀립니다.

D2 — 현행 phase 필터가 묶음 보기에서 동작하므로, 필터를 표 보기에만 두면 그 기능이 사라지는 회귀입니다.

D3 — 메모리 필터를 남기면 표 보기 페이징의 총 건수가 틀어집니다(DB 가 센 건수와 메모리가 거른 건수가 다릅니다). step → phase 매핑은 enum 에서 파생하므로 SQL 로 옮겨도 SSOT 가 유지됩니다.

D4 — 운영 상태는 저장하지 않는 도출값(U1 §D4)이라, 컬럼을 두면 진행 신호와 상태 컬럼 두 곳이 갈라질 자리가 생깁니다. 메모리 필터는 D3 과 같은 이유로 페이징과 양립하지 않습니다.

D5 — execution 의 Specification 이 그룹 멤버 엔티티를 join 하면 execution → provisioning 역방향 의존이 생겨 DEC-C 를 어깁니다.

D6 — 서버의 단계와 상태는 한 값이라 AND 면 두 개를 고르는 순간 항상 빈 결과입니다. 규칙은 "여러 값을 갖는 속성(정의서의 단계들)은 AND, 한 값인 속성은 OR" 이고, 이 문장을 DESIGN.md 에 적습니다.

D7 — 상태 칩에 회수됨을 두면 두 축이 같은 사실을 서로 다르게 말하게 됩니다(체크 해제 + 회수됨 칩 = 모순).

D8 — 조용히 뒤바꾸면 사용자가 모르는 조건으로 조회됩니다. 400 은 주소창 한 글자 실수에 오류 페이지를 보입니다. UX 모순은 UI 가 1차로 막고(min · max), 서버는 빈 결과 + 안내로 안전망만 둡니다.

D9 — S8-1 비목표와 같습니다. 필드별 조건은 S8-4 의 상세 조회 창에서 다룰 수 있습니다.

D10 — 조회 띠를 영역 안에 두면 SSE 교체 때 입력 중이던 글자와 포커스가 사라집니다.

D11 — 묶음 보기의 순서는 시간 구간 자체가 뜻이라, 정렬을 걸면 묶음의 의미가 흐려집니다.

D12 — 축이 넷 이상이면 컨트롤러의 URL 조립이 축 × 값의 곱으로 자랍니다(S8-1 D2).

D13 — 등록된 보드 전부를 두면 고르는 순간 항상 빈 결과가 되는 선택지가 생깁니다.

D14 — 연결은 90 초 판정으로 시간이 지나면 바뀌는 값이라, SQL 로 거른 결과와 SSE 갱신이 어긋납니다.

D15 — 상세 조회 창과 기본 1 년 필터는 S8-4 가 모든 목록에 들이는 일입니다. 이번에는 필터를 낱개 블록으로 두어 옮길 자리만 준비합니다.
