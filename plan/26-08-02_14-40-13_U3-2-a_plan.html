§0. U3-2 2분할 결정 · setting↔assignment 순환 회피 (이 슬라이스의 위치)

U3-2 는 원래 세 관심사를 한 덩이로 예고했다 — ① 재할당 이력(DEC-18) ② 원본 정의서 삭제 lifecycle ③ 지연 purge(DEC-19, DB-only reaper). CP1 정밀 조사 결과 2 분할을 권장한다.

슬라이스담는 것완료 조건 · 성격
U3-2-a 이 문서 재할당(supersede-then-new) + 재할당이 만들어내는 미소비 supersede 행의 지연 purge reaper correctness 축 — provisioning.assignment 도메인 내부의 mutation · 위생. 재할당 UI 브라우저 검증 + reaper 단위 · 하네스로 검증
U3-2-b 원본 정의서(SettingDefinition) 삭제 soft-delete / purge + 삭제 시 "이 정의서를 참조하는 할당 N개" 역참조 경고 새 도메인(provisioning.setting) lifecycle 도입. 독립 UI · Controller · 테스트. assignment 와는 읽기 전용 역참조 하나로만 엮임

재할당과 reaper 를 왜 같은 슬라이스에 묶나

두 관심사는 supersededAt 술어와 AssignmentState.SUPERSEDED 를 공유한다. reaper 는 재할당이 만들어내는 SUPERSEDED · 미소비 행을 청소하는 역할이라, 같이 가야 반쪽짜리(수거 대상 없는 reaper / 쓰레기만 쌓는 supersede) 가 안 된다.

비채택 분할안 (불가침 — 되묻지 않아도 최적 설계가 담기게):
  • 탈락 A · 무분할(단일 U3-2) — 재할당 mutation 과 완전히 새로운 도메인 lifecycle(정의서 soft-delete / purge / typed-name / UsageChecker / UI) 을 한 슬라이스에 섞으면 두 도메인이 한 CP5 검증에 뭉쳐 커지고 테스트 4 범주가 두 배로 불어난다. "갈라지는 시점에 분리" 원칙 위반.
  • 탈락 B · 3분할(재할당 / reaper / 정의서삭제) — reaper 를 독립 슬라이스로 떼면 supersededAt · AssignmentState.SUPERSEDED 를 재할당과 공유하는데 물리적으로 갈라져 인위적 seam 이 생긴다. reaper 는 OrphanQuarantineReaper 재사용으로 작아서 단독 슬라이스 값을 못한다.
채택 · 2분할 — correctness 축(재할당 + reaper, assignment 도메인 내부) 과 새 도메인 lifecycle 도입(정의서 삭제) 을 가른다. U3-1 OQ5 가 확정한 "U3-2 correctness 우선" 과 정합.

순환 회피가 이 분할을 정당화한다

assignment → setting 의존은 이미 존재한다(AssignmentCommandService 가 SettingDefinitionRepository · SettingDefinition · SettingProcessType 를 import). setting → assignment 는 없다. U3-2-b 의 "정의서 삭제 시 할당 역참조 경고" 를 setting 도메인이 직접 assignment 를 호출해 구현하면 setting ↔ assignment 순환(R7 이 제거한 종류) 이 재생성된다.

해소는 U3-1 의 OwnedPhasesProvider 선례와 동형인 Service Provider Interface(SPI, 도메인이 구현해 끼우는 확장점) 역전이다 — 인터페이스(AssignmentUsageInspector, boolean isReferenced(Long definitionId) / long countReferencing(Long)) 는 provisioning.setting 이 소유하고, 구현은 이미 setting 에 의존하는 provisioning.assignment 가 제공한다.

이 슬라이스(U3-2-a) 에 미치는 결론 — 이 SPI 역전은 U3-2-b 소관이다. 여기서 확정하는 사실은 두 가지뿐: (1) U3-2-a 는 새 교차 의존을 도입하지 않는다(assignment → setting 단방향 유지). (2) U3-2-b 가 이 역전을 반드시 써야 순환이 안 생긴다는 점을 미리 못박는다.
§1. 현재 상태 (진단)

쉬운 말 요약

U3-1 에서 세팅 정의서를 서버에 할당하는 것까지는 됐다. 그런데 지금은 서버 하나에 할당이 한 번 되면 그걸 바꿀 방법이 없다 — 다른 정의서로 다시 걸려고 하면 시스템이 "이미 할당돼 있다" 며 막기만 한다(409 거절). 실제 현장에선 "아, 이 서버엔 다른 정의서를 걸었어야 했다" 며 갈아끼우는 일이 흔하다.

이번 슬라이스는 그 갈아끼우기(재할당) 를 정식 기능으로 연다. 단, 아직 프로비저닝을 시작하지 않은(미개시) 서버에만 — 이미 설치가 돌기 시작한 서버는 도중에 정의서를 바꾸면 진행 위치가 꼬이므로 막는다(그 처리는 나중 E 단계 몫). 갈아끼울 때 옛 할당은 지우지 않고 "종료됨(supersede)" 으로 접어 이력으로 남기고, 현재 정의서로 새 할당을 활성으로 만든다. 이렇게 접힌 옛 할당 중 한 번도 개시된 적 없는 순수 쓰레기 행은 일정 시간(TTL) 이 지나면 청소부(reaper) 가 자동으로 지운다. 그리고 "한 서버엔 활성 할당이 딱 1개" 라는 규칙을 서비스 코드뿐 아니라 DB 가 직접 보장하도록 못박아 동시 요청에도 안 깨지게 한다.

§2. 요구사항 (확정) + 비목표
  1. 재할당(supersede-then-new) — 이미 활성 할당이 있고 그게 미개시(ACTIVE_UNCONSUMED) 면, 기존을 supersede 하고 현재 정의서로 새 활성 스냅샷을 derive-then-freeze 로 생성한다.
  2. 활성 유일성 DB 강제 — MariaDB PERSISTENT generated-column + UNIQUE 로 "게스트당 활성 1개" 불변식을 DB 가 보장한다(U3-1 OQ4 해소). 서비스 가드는 친절한 409 · UX 용으로 유지.
  3. 미소비-supersede 행 지연 purge reaper(DB-only) — @Scheduled 얇은 트리거 → purgeExpired() → SUPERSEDED ∧ 미소비 ∧ TTL 경과 행 hard-delete. OrphanQuarantineReaper 패턴 재사용.
  4. 재할당 UX — Single Source of Truth(SSOT, 단일 진실 출처) 도메인 메서드 reassignBlockReason() 를 서버 가드 + 뷰모델(disabled + tooltip) 이 공유. server-detail 의 할당 폼을 미개시 활성일 때 "재할당" 으로 개방, 개시된 활성이면 disabled.
비 목표 (다음 슬라이스로) :
  • 원본 정의서 삭제 soft-delete / purge + 역참조 UsageChecker + AssignmentUsageInspector SPI = U3-2-b.
  • 진행 중(ACTIVE_CONSUMED, 이미 개시) 게스트의 재할당 — 커서 리셋 의미론이 필요해 E cluster. U3-2-a 는 개시된 활성의 재할당을 차단한다.
  • 소비된(consumed) supersede 이력 행의 장기 보존 / 수거 상한 · 삭제 대기 목록 표면화 = 미도입(§8 잔여). 서버 목록 cross-server 가시화 = U3-3.
  • Set.of() 커서 전진 실배선 = ES-1.

§4. DB 변경 · 상태 다이어그램 · 도메인 메서드 (SSOT)

스키마 변경 — 신규 테이블 없음(기존 setting_assignment ALTER)

ddl/U3-2-a_active_uniqueness.sql — 활성(superseded_at IS NULL) 일 때만 guest_server_id, 아니면 NULL 인 PERSISTENT generated column 에 UNIQUE. NULL(supersede 행) 은 중복 허용되어 게스트당 활성 1개만 강제한다.

ALTER TABLE setting_assignment
  ADD COLUMN active_guest_id UUID
    GENERATED ALWAYS AS (IF(superseded_at IS NULL, guest_server_id, NULL)) STORED,
  ADD UNIQUE KEY uk_active_assignment_per_guest (active_guest_id);
JPA 매핑 안 함 — active_guest_id 는 순수 DB 파생 컬럼이라 엔티티 필드가 불요하다. ddl-auto=validate 대비 DDL 을 ddl/ 에 수동 산출하고, 샌드박스는 update 로 자동 생성한다. MariaDB 에서 UUID generated STORED + UNIQUE + NULL 중복 허용 실동작은 실기(T3) 검증 항목이다(docs/T3-checklist.md 적립).

도메인 메서드 (SSOT) — U3-1 훅 + 이번 신규 reassignBlockReason()

// SettingAssignment — U3-1 이 심어둔 훅(현재 실호출 0/1) 을 U3-2-a 가 배선
public void supersede(LocalDateTime now) {            // 멱등 — 재할당이 처음 호출
    if (supersededAt == null) this.supersededAt = now;
}
public void markConsumed(LocalDateTime now) {         // 활성 행만 — supersede 행은 안전망 예외
    if (supersededAt != null) throw new IllegalStateException("종료된 할당 스냅샷은 소비 불가");
    if (consumedAt == null) this.consumedAt = now;
}
public AssignmentState state() {                       // 파생 — 저장 컬럼 없음
    if (supersededAt != null) return SUPERSEDED;
    return consumedAt != null ? ACTIVE_CONSUMED : ACTIVE_UNCONSUMED;
}

// [U3-2-a 신규] 재할당 차단 사유 SSOT — 서버 가드 + 뷰모델 disabled 가 함께 호출(drift 0)
public String reassignBlockReason() {                  // childEnableBlockReason 선례 동형
    return state() == ACTIVE_CONSUMED
        ? "이미 개시되어 재할당할 수 없습니다(회수 후 재등록 필요)"
        : null;   // ACTIVE_UNCONSUMED → 재할당 가능
> null 이면 재할당 허용, 문자열이면 그게 UI tooltip 이자 예외 메시지
reaper 수거 술어(AssignmentReapService.purgeExpired()) — supersededAt IS NOT NULL AND consumedAt IS NULL AND supersededAt < (now - TTL). 즉 한 번도 개시 안 된 채 재할당으로 밀려난 행 = 순수 쓰레기만 지운다. 소비된(consumed) supersede 행은 실제로 개시됐던 프로비저닝 이력이라 감사 가치가 있어 보존한다.

§8. 설계 결정 (DA1~DA5) · 잔여 · 열린 질문

확정 결정 — 채택안 + 비채택 대안 + 탈락 사유 (불가침)

#결정 (채택)비채택 대안 · 탈락 사유
DA1 치명 재할당 = supersede-then-new, 단 미개시 활성에만. 현재 활성이 ACTIVE_UNCONSUMED 일 때만 허용 — 기존 supersede(now) + 현재 정의서로 새 활성 스냅샷(U3-1 assign 과 같은 derive-then-freeze). ACTIVE_CONSUMED(개시) 면 차단 → ReassignAfterStartException(409). 개시 후 정의서 교체는 진행 커서 리셋 / 재개 의미론(E cluster) 을 요구하므로 U3-2-a 경계 밖. ① 물리 삭제 후 재삽입(delete-then-insert) — 개시 tx 의 markConsumed 와 delete 경합(delete-vs-update race) + DEC-18 이력 유실. 그래서 supersede(논리) 로 통일. ② 개시된 활성도 재할당 허용 — E cluster 의 커서 리셋을 U3-2-a 로 끌어와 scope 폭발. 차단이 옳음.
DA2 치명 활성 유일성 DB 강제 — MariaDB PERSISTENT generated-column + UNIQUE(§4 DDL). 활성일 때만 guest_server_id, 아니면 NULL 인 파생 컬럼에 UNIQUE — NULL(supersede 행) 은 중복 허용, 활성 행은 게스트당 1개. DB 불변식이라 동시성에 무결. 서비스 가드(existsBy + reassignBlockReason) 는 유지 → 위반을 DB 예외 전에 친절한 409 · UX 로 선차단. ① 서비스 가드 + @Version 만 — @Version 은 기존 행 supersede(UPDATE) 는 직렬화하나 "활성 0개→2개 동시 삽입"(최초 동시 할당 2건) 은 경합할 기존 행이 없어 못 막음. Time-Of-Check-To-Time-Of-Use(TOCTOU, 점검-사용 시점 사이 창) 남음. ② 비관적 잠금(SELECT … FOR UPDATE) — 최초 할당엔 잠글 행이 없어 별도 lock 테이블 필요. generated-column UNIQUE 가 가장 단순 · 무결.
DA3 중대 reaper 수거 = SUPERSEDED ∧ 미소비 ∧ TTL 경과 만. 소비된 supersede 행은 보존(개시됐던 프로비저닝 이력 — 감사 가치). TTL 지연은 재할당 직후 즉시 삭제 시 개시 tx 와 경합하기 때문 — supersede(논리 종료) 후 TTL 창이 지나 아무도 안 건드릴 때 물리 삭제. 설정은 application.properties 프로퍼티(assignment.reap.ttl / cron / enabled). @Scheduled :45 슬롯(기존 :00 / :30 과 안 겹침). ① DB single-row 설정 엔티티(TrashSettings 류) — 사용자 편집 대상 아닌 내부 위생 작업이라 프로퍼티로 충분(단순한 구현 원칙). 미채택. ② purge_log DB 감사행 편입(resource_type='SETTING_ASSIGNMENT') — 개시된 적 없는 쓰레기 행이라 감사 가치 낮음. 일관성은 오르나 저가치 로그 팽창. 미채택(§ 잔여에 재검토 여지 기록), 대신 수거 건수 INFO 로깅.
DA4 중대 재할당 UX SSOT — 도메인 메서드 SettingAssignment.reassignBlockReason()(ACTIVE_CONSUMED→사유 문자열 · 그 외 null) 를 서버 가드(AssignmentCommandService.reassign) 와 뷰모델(재할당 버튼 disabled + tooltip) 이 공유 → drift 0(childEnableBlockReason 선례 동형). server-detail: 미개시 활성이면 "재할당" 노출, 개시됐으면 disabled + 사유 tooltip, 활성 없으면 기존 "할당". UI 와 서버에 판정을 복붙하는 대안은 두 곳이 갈리는 drift 원인이라 금지(불가침 "UI 차단 = 서버 가드 단일 SSOT"). 재할당 폼은 입력 폼이므로 [data-live] 영역 밖에 둔다 — SSE 재렌더가 폼 핸들러를 소실시키던 U3-1 버그(commit 107bbd0) 재발 방지.
DA5 주의 재할당 시 새 활성 스냅샷은 재할당 시점의 현재 정의서로 새로 derive-then-freeze(OwnedPhases 재계산 · payload 재복사 · BASIC_SETTING 이면 BIOS 값 재동결). 기존 supersede 행은 자기 시점 동결값 유지 → 두 이력이 각자 자족. 원본 정의서가 그새 바뀌었으면 새 스냅샷이 새 값 반영(할당은 항상 "지금 이 정의서" 스냅샷). U3-1 assign 의 derive-then-freeze 로직을 공통 추출해 재사용한다 — 복붙하면 중복 · 갈라짐(불가침 중복 금지). 별도 규칙을 새로 만드는 대안은 U3-1 과 규칙이 갈려 스냅샷 재현성이 흔들리므로 미채택.
