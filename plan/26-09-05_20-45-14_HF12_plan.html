§0. 한눈 요약

정의서 수정 저장의 결함 둘을 한 브랜치에서 닫는다. 두 결함은 서로 다른 자리에 있지만 같은 저장 트랜잭션 안에서 일어난다는 공통점이 있어 재현도 검증도 한 화면 · 한 요청으로 닫힌다.

  • A — 이름을 바꾸지 않으면 수정일시가 멈춘다. 단계만 고쳐 저장해도 setting_definition.updated_at 이 생성 시각 그대로다. E4-1-a-2 CP5 의 O-4 로 적립돼 있었고, 2026-09-04 실기에서 정의서 10 을 09:25 KST 에 수정했는데 updated_at 은 07:49 였다
  • B — 리눅스 비밀번호 "기존 유지" 가 병합되지 않는다. RHEL · Ubuntu 설치 단계에서 유지를 켜고 저장하면 root · 사용자 비밀번호가 빈 값으로 저장된다. E4-1-a-2 가 병합 훅을 Windows 축에만 구현했기 때문이다
범위 — 스키마 변경 0 · 운영 설정 변경 0 · 프론트엔드 변경 0 · 신규 예외 클래스 0 (기존 예외에 생성자 하나를 더한다). 바뀌는 것은 엔티티의 감사 시각 유발 한 줄과, 리눅스 요청 계층의 비밀값 병합 훅이다.
§1. 현재 상태 (진단)

아래는 관찰된 증상에서 출발해 "어떤 코드가 그렇게 답하도록 되어 있는가" 까지 내려간 내용이다. 두 결함 모두 JpaSettingCommandService.update 한 메서드를 지나간다.

1-1. A — 이름이 그대로면 부모 행의 UPDATE 가 없다

정의서 수정은 전체 교체 의미론(U2-3 D4)이다. update 는 SettingDefinition.changeNameAndClearProcesses(name) 로 이름을 갱신하면서 기존 단계 행을 떼어내고, repository.flush() 로 그 삭제를 먼저 반영한 뒤 attachProcesses 로 새 단계 행을 장착한다. 같은 flush 안에서 Hibernate 가 INSERT 를 DELETE 보다 먼저 내보내 UNIQUE(definition, type) 와 충돌하는 것을 피하려고 둔 순서다.

여기서 정의서 엔티티 자신의 컬럼 중 바뀔 수 있는 것은 name 하나다. 단계만 고치면 부모 행에는 바꿀 값이 없어 Hibernate 가 부모의 UPDATE 문을 만들지 않고, 움직이는 것은 자식 SettingProcess 행의 DELETE 와 INSERT 뿐이다.

수정 시각은 BaseTimeEntity 의 @LastModifiedDate 가 채운다. 이 필드는 AuditingEntityListener 가 @PreUpdate 콜백에서 채우는데, 부모의 UPDATE 가 없으면 그 콜백 자체가 돌지 않는다. 그래서 updated_at 이 생성 시각에 멈춘다. 단계 컬렉션이 부모의 dirty 로 잡히지 않는 것은 이 연관이 단방향 @OneToMany + @JoinColumn 이기 때문이다 — 자식의 외래키 열을 자식 쪽에서 쓰므로 부모 행은 건드릴 이유가 없다.

사용자가 이 값을 보는 자리는 정의서 상세 화면의 "수정일시" 다. 목록에서 최근 수정 순으로 감을 잡는 운영자에게는 고친 사실 자체가 화면에서 사라지는 셈이다.

1-2. B — 리눅스에는 병합 훅이 없다

E4-1-a-2 의 D-11 은 비밀값 처리를 AbstractProcessRequest 의 다형 훅 둘로 정리했다. 하나는 수정 폼 pre-fill 용 withoutSecrets() — 저장본의 값을 화면으로 내보내지 않고 "기존 유지" 플래그로 대체한다. 다른 하나는 수정 저장 병합용 withSecretsRetainedFrom(existing) — 유지 플래그가 켜진 항목의 값을 같은 단계 타입의 저장본에서 이어받는다. 둘 다 기본 구현은 this 라, 비밀값이 없는 단계 타입은 아무것도 하지 않는다.

리눅스 중간층 LinuxInstallationRequest 는 이 중 앞의 하나만 구현했다. 사용자 목록의 비밀번호를 지우고 계열별 withPatchedPasswords(users) 로 사본을 재조립하며, RHEL 은 그 안에서 자신의 root 비밀번호도 new RootPasswordRequest(null, false, true) 로 함께 지운다. 병합 훅은 override 하지 않았으므로 기본 this 가 그대로 돌아온다.

프론트엔드는 유지 체크가 켜진 항목을 {password: null, keepExistingPassword: true} 로 보낸다 — root 와 사용자 모두 같다. 서버가 병합하지 않으므로 그 값이 그대로 새 저장본이 된다. 이 정의서로 설치가 돌면 Kickstart 의 rootpw 와 autoinstall 의 사용자 항목에 빈 비밀번호가 들어간다.

같은 자리의 Windows 축은 이미 짝이 맞다. WindowsInstallationRequest.withSecretsRetainedFrom 이 저장본에서 값을 복사하고, 복사할 값이 없으면 RetainedPasswordUnavailableException 으로 400 을 낸다 (필드 administratorPassword 직결). 리눅스에 없는 것이 이 짝이다.

1-3. 접근 규칙과 순서 — 여기서는 문제가 없다

RHEL 계열 검사기 RHELInstallationFamilyInspector 는 "root 비밀번호도 사용자도 없으면 설치 후 접근 불가" 를 막는다. 그런데 이 판정은 rootPassword == null, 즉 객체의 부재만 본다. 유지 플래그가 켜진 요청은 객체가 있으므로 그대로 통과한다. 검증(validateReferences)이 병합보다 먼저 도는 것도 사실이지만, 판정에 비밀번호 값이 관여하지 않으므로 순서 때문에 생기는 문제는 없다. 즉 B 를 고치기 위해 검사기나 호출 순서를 손댈 이유가 없다.

§2. 요구사항 (확정) + 비목표
  1. 정의서 수정 저장이 성공하면 이름을 바꾸었는지와 무관하게 updated_at 이 저장 시각으로 이동한다.
  2. 실제 저장 값은 감사 리스너가 정한다 — 도메인 코드가 시각을 직접 확정하지 않는다.
  3. 리눅스 설치 단계의 "기존 비밀번호 유지" 는 저장본에서 값을 복사해 새 저장본에 싣고, 유지 플래그는 해제한다.
  4. 유지할 값이 저장본에 없으면 조용히 비우지 않고 400 으로 거절하며, 사유가 해당 필드에 직결된다.
  5. Ubuntu 는 root 개념이 없으므로 사용자 축만 병합한다. Windows 축의 현행 동작은 회귀 없이 그대로다.
  6. 계열이 늘어도 병합 규칙을 instanceof 사다리로 늘리지 않는다 — 중간층의 다형 훅 하나로 흡수한다.
비 목표 :
  • 비밀번호 평문 저장 — 정의서 payload 가 비밀번호를 평문으로 담는 구조 자체는 이 슬라이스에서 바꾸지 않는다(Notion HF12 ②).
  • 정의서 이력화 — 무엇이 언제 어떻게 바뀌었는지의 변경 이력은 별개 주제다. 여기서는 마지막 수정 시각 한 값만 바로잡는다.
  • 생성(POST) 경로의 유지 플래그 — 병합 대상이 없는 생성 요청에 유지 플래그를 직접 실어 보내는 경로는 손대지 않는다(§8-3 잔존 참조).
  • 화면 변경 — 폼 · 상세 화면의 마크업과 스크립트는 건드리지 않는다.
🎬 미리보기 — 라이브 UX 데모 (저장본 · 요청을 바꿔 병합과 수정일시를 확인)

왼쪽의 저장본(수정 전 DB 에 있는 정의서)과 오른쪽의 요청(폼이 만들어 보내는 payload)을 직접 바꾼 뒤 [저장] 을 누르면, 그 조합에서 서버가 무엇을 저장하고 무엇으로 응답하는지가 나온다. 판정 함수는 §4 의 RETAIN 규칙과 touch() 규칙을 그대로 옮긴 것이다.

§3. URL / 데이터 흐름

새로 생기거나 바뀌는 URL 은 없다. 두 결함은 모두 기존 수정 저장 경로 PUT /provisioning/setting/{id} 위에 있다. 아래는 그 한 요청이 지나가는 자리를 주체별로 편 것이다 — 바뀌는 지점 둘에 표시를 달았다.

병합이 clear 보다 먼저 있어야 하는 이유는 단순하다 — 저장본의 단계 payload 를 읽어야 값을 복사할 수 있는데, changeNameAndClearProcesses 가 지나가면 그 컬렉션이 비기 때문이다. 현행 update 가 이미 그 순서로 되어 있어 서비스 코드는 바뀌지 않는다.

실패 경로도 기존 계약을 그대로 쓴다. 병합할 값이 없으면 RetainedPasswordUnavailableException 이 FieldBoundBadRequestException 으로서 400 과 필드명을 함께 싣고, 폼 스크립트의 renderServerErrors 가 processList[i].rootPassword · processList[i].users 를 해당 단계 카드 안으로 좁혀 인라인 표시한다(기존 매퍼 · 변경 0).

§4. 도메인 모델 (SSOT) — 엔티티 필드 · DDL 변경 0

새 필드도 새 값 객체도 없다. 더해지는 것은 기존 감사 필드를 움직이는 수단 하나와 리눅스 요청 계층의 비밀값 변환 훅 하나다.

4-1. BaseTimeEntity.touch() — 부모를 dirty 로 만드는 최소 수단

// global/entity/BaseTimeEntity
protected void touch() {
    this.updatedAt = LocalDateTime.now();   // 값이 아니라 "바뀌었다"는 사실이 목적
}

// provisioning/setting/entity/SettingDefinition
public void changeNameAndClearProcesses(String name) {
    this.name = name;
    this.processes.clear();
    touch();   // 이름이 그대로면 자식 교체만으로는 부모 UPDATE 가 나가지 않는다
}

여기서 넣는 시각은 결과에 영향을 주지 않는다. 자기 컬럼을 건드려 부모 행을 dirty 로 만드는 것이 목적이고, flush 시점에 AuditingEntityListener 가 @LastModifiedDate 를 다시 덮으므로 실제 저장 값은 언제나 감사 시각이다. 그래서 이 한 줄은 HF13 의 Clock 주입과 무관하다 — 시각의 출처가 바뀌면 감사 리스너 쪽에서 바뀔 뿐이다.

가시성은 protected 다 — 도메인 수정 메서드가 자기 aggregate 안에서 부르는 수단이지 서비스가 밖에서 시각을 조작하는 통로가 아니다. 호출 지점도 changeNameAndClearProcesses 하나이며, flush() 앞이라 같은 flush 에 실린다.

4-2. LinuxInstallationRequest.PasswordPatch — 제거와 보존이 같은 길을 탄다

// 중첩 인터페이스 — user · root 두 변환을 한 묶음으로 전달한다
protected interface PasswordPatch {
    UserRequest        user(UserRequest user);
    RootPasswordRequest root(RootPasswordRequest root);
}

public abstract LinuxInstallationRequest withPatchedPasswords(PasswordPatch patch);

@Override public LinuxInstallationRequest withoutSecrets()                              { return withPatchedPasswords(STRIP); }
@Override public LinuxInstallationRequest withSecretsRetainedFrom(AbstractProcessRequest existing) { return withPatchedPasswords(retainFrom(existing)); }

계열 구현이 갖는 재조립 메서드는 계열당 하나로 유지된다. RHEL 은 patch.root(rootPassword) 와 patchUsers(patch) 를 자기 생성자에 넘기고, Ubuntu 는 root 개념이 없으므로 patchUsers(patch) 만 넘긴다. 무엇을 하는 patch 인지는 중간층이 정하고, 어디에 꽂는지는 계열이 정하는 분담이다.

값 보유 판정 hasPassword() 와 복사 retaining(...) 은 UserRequest · RootPasswordRequest 자신이 갖는다. Windows 축의 WindowsAdministratorPasswordRequest.retaining 이 이미 쓰는 관용구를 리눅스 쪽에 맞춰 두는 것이다.

4-3. RETAIN 규칙 진리표 (판정 SSOT)

대상요청저장본결과
사용자유지 켬같은 username 에 값 있음값 복사 · 유지 플래그 해제
사용자유지 켬같은 username 이 없거나 값이 없음400 users
사용자유지 끔보지 않음요청 값 그대로
root유지 켬RHEL 이고 root 값 있음값 복사 · 유지 플래그 해제
root유지 켬RHEL 이 아니거나 root 값 없음400 rootPassword
root유지 끔보지 않음요청 값 그대로(없으면 root 잠금)
공통유지 켬리눅스 요청이 아님 — 단계 신설 · 타입 변경값 없음으로 본다 → 400

사용자 대조 기준을 username 으로 잡는 이유는 사용자 목록에 안정된 식별자가 그것뿐이기 때문이다. 행 순서는 폼에서 자유롭게 바뀌므로 위치로 짝지을 수 없다. 이름을 바꾸면서 유지를 켠 행은 "저장본에 없는 사용자" 가 되어 400 으로 걸린다 — 조용히 다른 계정의 비밀번호를 옮겨 붙이지 않는다.

RHEL 재조립이 root 를 먼저, 사용자를 나중에 적용하므로 둘 다 실패할 수 있는 요청은 rootPassword 로 응답한다. 첫 실패에서 예외가 나가는 구조라 응답 하나에 사유 하나다.

§6. Step 8 테스트 시나리오

§7. 예외 계층

새 예외 클래스를 만들지 않는다. Windows 축이 쓰던 예외에 대상을 지정하는 생성자 하나를 더해 리눅스 축이 함께 쓴다. 메시지는 대상 이름만 갈아 끼우고 필드명은 인자로 받는다.

§8. 설계 대안 · 결정 · 잔존

8-1. A 의 대안 — 부모 행을 어떻게 움직일 것인가

안요지결과
①BaseTimeEntity.touch() 를 도메인 수정 메서드가 호출해 부모를 dirty 로 만든다채택 감사 리스너가 그대로 값을 정한다 · DDL 0
②@Version 컬럼을 두어 변경마다 증가시킨다탈락 — DDL 변경 · 낙관적 락 의미 도입 · 그래도 dirty 가 있어야 증가한다
③서비스가 네이티브 UPDATE 로 updated_at 을 직접 쓴다탈락 — 감사 리스너를 우회하는 두 번째 시각 소스 · 레이어 경계 위반
④양방향 매핑으로 바꿔 자식 변경이 부모에 닿게 한다탈락 — 매핑 churn 이 크고 문제의 본질(부모 dirty)과 무관하다

②가 걸리는 지점을 풀어 두면 이렇다 — 버전 컬럼은 부모 행이 UPDATE 될 때 증가한다. 지금 문제는 그 UPDATE 자체가 없는 것이므로, 컬럼을 더해도 같은 자리에서 멈춘다. ③은 값이 맞더라도 시각을 정하는 곳이 둘이 되어 이후 어느 쪽이 정본인지 알 수 없게 된다.

8-2. B 의 대안 — 병합 훅을 어디에 어떤 모양으로 둘 것인가

안요지결과
①중간층의 추상 훅을 withPatchedPasswords(PasswordPatch) 로 일반화한다채택 제거 · 보존이 같은 재조립 경로를 탄다 · 계열당 재조립 1개
②withRetainedPasswords(users, previous) 추상 메서드를 따로 더한다탈락 — RHEL · Ubuntu 에 거의 같은 재조립 메서드가 둘씩 생긴다
③서비스에서 instanceof 로 계열을 갈라 병합한다탈락 — 조건분기 legacy 확장 금지 위배 · 계열 추가마다 줄이 는다

②를 택하면 재조립 코드가 두 벌이 된다. RHEL 의 재조립은 생성자 인자 열 개를 그대로 옮겨 적는 일이라, 같은 목록이 두 번 있으면 필드가 늘 때 한쪽만 고치는 사고가 난다. patch 를 인자로 받으면 바뀌는 것은 변환 함수뿐이다.

8-3. 결정 D-1 ~ D-5

  • D-1 — BaseTimeEntity.touch() 를 protected 로 두고 SettingDefinition.changeNameAndClearProcesses 한 곳에서 부른다. 넣는 시각은 flush 때 감사 리스너가 덮으므로 결과 값은 언제나 감사 시각이다.
  • D-2 — 리눅스 중간층에 중첩 인터페이스 PasswordPatch 와 추상 withPatchedPasswords(PasswordPatch) 를 두고, 기존의 사용자 목록 인자 시그니처를 대체한다. withoutSecrets() 는 STRIP, withSecretsRetainedFrom(existing) 은 RETAIN 을 넘긴다.
  • D-3 — RETAIN 규칙은 §4-3 진리표가 SSOT 다. 값 보유 판정과 복사는 UserRequest · RootPasswordRequest 의 hasPassword() · retaining(...) 이 맡는다.
  • D-4 — RetainedPasswordUnavailableException(fieldName, subject) 생성자를 더하고 Windows 무인자 생성자는 그것에 위임한다. 프론트엔드의 오류 매핑은 기존 매퍼가 그대로 처리한다.
  • D-5 — 프론트엔드 · DDL · 운영 설정 변경 0. Windows 축은 pre-fill 이 값이 있는 저장본에만 유지 체크박스를 노출해 UI 가 1차 차단한다. 리눅스 축은 입력 자체가 화면에 없어(R11) 지금은 direct PUT 만 도달하며, 서버 예외가 그 안전망이다. 400 사유는 resolveErrorTarget 이 필드 요소를 못 찾으면 해당 단계 카드에 붙는다.

8-4. 잔존 · 주의

생성(POST) 경로의 유지 플래그 — 생성 요청에 유지 플래그를 직접 실어 보내면 병합할 저장본이 없으므로 비밀번호가 null 로 저장된다. Windows 축도 같다 — 생성 경로는 병합 훅을 지나지 않는다. 정상 UX 에서는 생성 폼에 유지 체크박스가 없어 도달하지 않는 경로이므로 이 슬라이스에서 닫지 않고 S 계열 후보로 적립한다.

Open Questions 는 없다. 두 결함 모두 원인과 고칠 자리가 코드에서 확정됐고, 선택이 필요한 지점은 §8-1 · §8-2 에서 닫혔다.
