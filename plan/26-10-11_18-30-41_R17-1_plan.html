§0. 요약
  • 정의서의 RAID10 묶음에 스팬당 디스크 수(storcli pdperarray)를 지정할 수 있게 합니다. 지금은 agent.sh 가 MegaRAID RAID10 에 pdperarray=2 를 고정으로 붙입니다.
  • "이 카드 계열로 이 레벨을 디스크 몇 대로 만들 수 있는가" 를 계열이 내는 값 객체 하나(MemberCountRule — 최소 · 최대 · 단위)로 모읍니다. 폼 잠금 · 저장 가드 · 계획 검증이 같은 객체를 봅니다.
  • 그래서 세 어긋남이 함께 풀립니다: ① 스팬 고정 ② MegaRAID 의 수량 규칙 부재(홀수 RAID10 · 홀수 RAID1 이 집행에서야 카드에 거절됨) ③ 폼 최소치 불일치(RAID10 하한이 레벨 고정 4 라 MPT_IR 의 3대 RAID10 을 폼이 막음).
  • storcli 인자는 지금처럼 서버가 조립합니다(createOpts 에 pdperarray=N 추가) — agent 는 고정값 한 줄만 지우고 파싱은 그대로입니다.
  • DDL 없음(규칙은 정의서 JSON 안). 지원 레벨은 0 · 1 · 5 · 6 · 10 그대로 — 카드가 00 · 50 · 60 을 지원해도 추가하지 않습니다(사용자 지시 10-11).
§1. 배경 · 진단 (실측 · 문서 2026-10-11)

실태(번호는 본문 인용용):

  1. agent.sh MegaRAID 집행: [ "$LEVEL" = "RAID10" ] && EXTRA="pdperarray=2" 뒤 storcli /c0 add vd type=raid10 drives=… $CREATE $EXTRA. 스팬 구성을 정의서가 말할 자리가 없습니다.
  2. 같은 파일 주석의 원칙(E3.5-6): "createOpts · setOps · init 어휘는 서버가 조립해 오고 에이전트는 전달 · 실행만 한다 — 항목이 늘어도 이 스크립트는 불변." 위 1 의 고정값은 이 원칙의 유일한 예외입니다.
  3. RaidChipFamily.memberCountBlockReason(level, n): MPT_IR = RAID1 정확히 2 · RAID10 3~10 · RAID0 ≤10. MEGARAID = 항상 null("실측 표본이 생기면 채운다"). 그래서 MegaRAID RAID10 7대 · RAID1 3대 계획이 통과하고 집행의 storcli 가 거절합니다.
  4. 이 판정은 계획(RaidPlanner)에서만 호출됩니다. 폼과 저장 가드(DiskGroupRules.validateRaidRule)는 RaidLevel.minimumDisks(cardHasCache) 하나만 봅니다 — 계열을 모릅니다.
  5. RaidLevel.RAID10 의 baseMinimumDisks = 4. MPT_IR 은 3대 RAID10(IR 의 홀수 허용 방식)을 만들 수 있는데 폼과 저장 가드가 4 미만을 막습니다. 반대로 MPT_IR RAID1 3대는 폼이 통과시키고 계획에서야 거절됩니다. → 폼과 계획이 서로 다른 표를 봅니다.
  6. 폼은 레벨 옵션의 data-min-disks · data-min-disks-cached(카드 무관 · 레벨 고정)로 하한을 그립니다. 카드 메타(raidCardMetaJson)에는 hasCache · blockReasons(레벨 지원 여부) · chipFamily · supportsVdParameters 가 있습니다.
  7. 9361-8i 실측 원문(mr-c0-show-all.json): "RAID Level Supported : RAID0, RAID1(2 or more drives), RAID5, RAID6, RAID00, RAID10(2 or more drives per span), RAID50, RAID60".
  8. 문서 「Broadcom 12Gb/s MegaRAID Tri-Mode Software User Guide」: RAID 10 드라이브 그룹은 스팬 최대 8개 · 스팬당 최대 32대 · 스팬마다 짝수 대. RAID 1 은 짝수 2~32대 단일 스팬. 단일 스팬 최대 32대. RAID 6 최소 3대(문서) — 현행 하한 4 는 이 단계에서 바꾸지 않습니다(기록만).
  9. HF22 실기(10-02): CRA4760(SAS3908) 의 기존 VD(Virtual Drive) 가 6대 RAID10 이었습니다(스팬 구성 원문 미보존).
미확인 · 실측 대기
  1. SAS39xx(CRA4760) 펌웨어가 위 8 의 스팬 한도를 그대로 따르는가(문서는 Tri-Mode 계열 공통이라 그렇다고 말하지만 실기 원문 없음).
  2. storcli 가 drives 수가 pdperarray 의 배수가 아닐 때 내는 오류 문구.
§2. 요구사항 · 비목표
  1. 정의서 RAID10 묶음(MegaRAID 카드)에 스팬당 디스크 수 지정 — 짝수 2~32, 기본 2(구 저장본 = 2, 현행 동작과 같음)
  2. 계열별 디스크 수 규칙을 MemberCountRule 로 일원화 — 폼 · 저장 가드 · 계획이 공유
  3. MegaRAID 수량 규칙 신설(RAID1 짝수 2~32 · RAID10 = 스팬당 p × 스팬 2~8 · 단일 스팬 레벨 최대 32)
  4. MPT_IR RAID10 하한 3 을 폼 · 저장 가드도 인정
  5. storcli pdperarray 를 서버가 createOpts 에 조립 · agent 고정값 제거
  6. 상세 화면(정의서 묶음 요약 · 계획 볼륨)에 스팬 표시
  7. 테스트 두 레이어
  8. CP5(정의서 폼 브라우저 + mock-guest RAID 사이클 + agent BusyBox 가짜 storcli)
비 목표 :
  • RAID00 · 50 · 60(사용자 지시 — 카드가 지원해도 추가 안 함)
  • typicallyRequiresCache 제거(R17-2)
  • RAID6 MegaRAID 하한 3 반영(문서상 3 이나 이 단계 밖 — 기록만)
  • MPT_IR RAID10 의 스팬(IR 은 스팬 개념이 없다 · sas3ircu 에 인자 없음)
  • 3대 RAID10(=RAID1E) 의 유효 용량 셈 보정(usableDisks 는 내림이라 하한으로는 안전 — 기록만)
  • 스팬마다 다른 디스크 수(storcli pdperarray 는 단일 값)

§3. 설계 대안 비교

축 1 — 스팬을 무엇으로 지정하나

안지정값'개 이상' 과의 궁합판정
A 스팬당 디스크 수 pstorcli pdperarray 그대로그룹 크기가 바뀌어도 p 고정 · 스팬 수만 늘어남채택

A: p 는 카드 명령의 실제 인자이고 미러 묶음의 구조(한 스팬 = 한 미러 그룹)를 정합니다. '개 이상' 규칙에서 그룹이 커져도 의미가 유지됩니다(스팬만 늘어남). B 탈락: 스팬 수를 고정하면 p 가 그룹 크기에 끌려 다니며 짝수 조건을 깨기 쉽습니다. C 탈락: 사용자 확정(10-11) "스팬 구성 지정" — 미러 구조는 운영자가 정하는 결정입니다. 기본값 2 는 C 의 효과(지금 동작)를 그대로 줍니다.

축 2 — 스팬 값을 어디에 담나

안자리agent 영향
A 규칙의 새 필드 drivesPerSpan(VO) + 서버가 createOpts 에 토큰 조립 채택DiskGroupRuleRequest고정 한 줄 삭제만 · 파싱 불변
B VdParameters 의 9번째 축 탈락VD 파라미터 서브 행동일
C payload 에 별도 필드 pdPerArray 탈락RaidApplyPayload 볼륨정규식 파싱 변경

A: 스팬은 디스크 수 판정의 재료라(축 3) 규칙의 구조 값입니다. 조립은 실태 2 의 원칙(어휘는 서버가 조립)에 맞춰 PlannedVolume.createOpts 뒤에 붙입니다. B 탈락: VdParameters 는 HII(Human Interface Infrastructure) "CONFIGURE VIRTUAL DRIVE PARAMETERS" 8축이라는 정체를 갖고, 디스크 수 판정이 VD 파라미터를 열어 보게 되면 책임이 엉킵니다. C 탈락: agent 파싱 정규식을 바꾸게 되어 실태 2 의 원칙을 깹니다.

축 3 — 디스크 수 규칙의 SSOT(Single Source of Truth)

안폼저장 가드계획

B 현행 유지 + 계획에만 MegaRAID 규칙 추가 탈락레벨 고정 하한레벨 고정 하한계열 규칙
C 폼이 XHR 로 서버에 판정 질의 탈락서버 질의같은 메서드같은 메서드

A: 실태 4 · 5 의 어긋남은 "폼과 계획이 서로 다른 표를 본다" 는 한 원인에서 나옵니다. 규칙 객체 하나를 세 곳이 보면 원인이 사라집니다(UI 차단 조건과 서버 가드 조건의 단일 SSOT 원칙 — childEnableBlockReason() 선례). B 탈락: ② 는 고치지만 ③ 이 남고 폼 · 계획 드리프트가 그대로입니다. C 탈락: 판정 재료가 카드 하나 · 레벨 다섯 · 스팬 16 으로 유한해 렌더 시 다 실어 보낼 수 있습니다 — 왕복 지연과 오류 경로만 늡니다.

축 4 — '개 이상' 그룹이 계획 시점에 규칙을 어길 때

안그룹 7대 · RAID10 p=2판정
A 계획 전체 거절 MEMBER_COUNT거절 + 사유채택
B 맞는 만큼만 소비(6대) · 1대 미배정볼륨 3스팬 · 1대 남음탈락
C 그룹 미소비 → 후행 규칙으로 흘림볼륨 없음탈락

A: MPT_IR 에서 이미 쓰는 경로(RaidPlanRejection.MEMBER_COUNT)라 화면 · 원장 · 문구가 준비돼 있고, 집행 전에 사람이 봅니다. B 탈락: "개 이상 = 그룹 전체를 한 볼륨으로"(E3.5-7-a D2)의 뜻을 바꾸고, 남는 디스크가 조용히 생깁니다. C 탈락: 계획은 성공으로 보이는데 의도한 볼륨이 없어 OS 영역 판정 등 뒤 단계에서 엉뚱한 사유로 드러납니다.

축 5 — 계획 시점의 캐시 유무

MemberCountRule 의 최소치는 카드 캐시(RAID0 단일 디스크)에 따라 갈리는데, 계획 엔진(RaidPlanner)은 관측 인벤토리만 알고 캐시를 모릅니다. 계획은 cardHasCache = true(가장 느슨한 최소치)로 규칙을 받습니다(채택) — 최소치는 저장 가드가 이미 보장했고(개 · 개씩 = n, 개 이상 = 그룹 ≥ n ≥ 최소치) 계획이 새로 잡아야 하는 것은 최대 · 단위뿐이기 때문입니다. 탈락: 계획 엔진에 카드 스냅숏을 새로 넘기기(호출 사슬 변경 대비 얻는 판정 없음).

축 6 — 정의서 폼에서 스팬을 어디서 정하나 사용자 결정 10-11

안자리발견성판정
A 개수 셀 둘째 줄MegaRAID × RAID10 행의 개수 셀 아래RAID10 을 고르는 즉시 보임채택
B 독립 '스팬' 열표에 열 추가항상 보임탈락
C VD 파라미터 서브 행⚙ 로 펼치는 줄기본 접힘탈락

A: 스팬은 디스크 수와 한 몸인 값이라(스팬 수 = 개수 ÷ 스팬당 디스크) 개수 바로 아래가 의미상 제자리입니다. 용량 셀의 "직접 지정 → 둘째 줄에 값 · 단위" 와 같은 기존 패턴(n-cell-stack)이라 새 레이아웃이 없습니다. B 탈락: RAID10 이 아닌 모든 행에 '—' 열이 생겨 이미 넓은 표가 더 넓어집니다. C 탈락(초안의 안): 기본 접힘이라 RAID10 을 고른 사람이 스팬을 정할 수 있다는 사실을 놓치고, HII VD 파라미터 8축과 성격이 다른 구조 값이 섞입니다.

§4. 도메인 모델

D1 DrivesPerSpan 신규 VO management.raidcard.vo

record(int value) — 생성자 가드: 짝수 · 2~32(IllegalArgumentException). DEFAULT = 2. cliToken() = "pdperarray=" + value. static List<DrivesPerSpan> options() = 2 · 4 · … · 32(폼 선택지). toDisplay() = "스팬당 N대". Jackson 은 숫자 하나로 직렬화(@JsonValue · @JsonCreator).

D2 MemberCountRule 신규 VO management.raidcard.vo — 판정 진리표

record(int min, Integer max, int step, String display) — max null = 상한 없음. display 표기: 기본 "최소~최대대" · 최소 = 최대면 "N대" · 상한 없음 "N대 이상" · 단위가 2 이상일 때만 " · S대 단위" 를 붙인다(예 "4~16대 · 2대 단위" · MPT_IR RAID1 "2대" · MegaRAID RAID5 "3~32대"). 두 판정:

  • blockReasonFor(DiskCountRequirement count) (저장 · 폼): 개(EXACT) · 개씩(EACH) → n 이 min ≤ n ≤ max 이고 n % step == 0 이어야 · 개 이상(AT_LEAST) → min ≤ n(≤ max) 만 — 단위는 계획 시점 그룹 크기의 몫.
  • blockReasonFor(int members) (계획): min ≤ g ≤ max · g % step == 0.

반환 규약 = null 통과 · 문자열 = 화면 안내이자 거절 사유(SupportedRaidLevels.blockReasonFor 와 같은 규약).

D4 DiskGroupRuleRequest 수정

필드 추가 DrivesPerSpan drivesPerSpan(nullable — null = 스팬 지정 없음 · 구 저장본). @JsonIgnore DrivesPerSpan effectiveSpan() = null 이면 DEFAULT. 중복 판정(DiskGroupRules.identity)에는 넣지 않습니다(vdParameters · role 불포함과 같은 사유). 호환 생성자(6 · 7 인자) 유지.

D5 DiskGroupRules (저장 가드) 수정

  • validateRaidRule: level.minimumDisks 대신 card.getChipFamily().memberCountRule(level, card.hasCache(), rule.effectiveSpan()).blockReasonFor(rule.count()) → 거절이면 InvalidDiskGroupException.memberCount(ruleNo, reason)(기존 tooFewDisks 를 대체 — 팩토리 교체, 새 예외 클래스 아님).
  • 규칙 10(새): drivesPerSpan 은 RAID10 × MEGARAID 묶음에서만 → 아니면 InvalidDiskGroupException.spanNotApplicable(ruleNo). UI 는 스팬 select 잠금으로 먼저 막습니다(규칙 9 · VD 파라미터와 같은 구조).

D6 RaidPlanner 수정

family.memberCountBlockReason(level, n) → family.memberCountRule(level, true, rule.effectiveSpan()).blockReasonFor(n)(축 5). MegaRAID 볼륨의 createOpts 뒤에 RAID10 이면 " " + span.cliToken() 을 붙입니다(조립 SSOT = DrivesPerSpan.cliToken). PlannedVolume 에 DrivesPerSpan span(RAID10 · MEGARAID 만, 그 밖 null) 추가 — 상세 표시용.

EXTRA="" · [ "$LEVEL" = "RAID10" ] && EXTRA="pdperarray=2" 두 줄 삭제, add vd … $CREATE 만. 파싱 정규식 불변. 배포 이행: jar 와 AGENT 를 함께 교체(R17 과 같은 묶음 — 새 jar + 옛 agent 면 pdperarray 가 두 번 붙어 storcli 가 거절할 수 있다).

D8 폼 · 화면 수정

  • 카드 메타(SettingRaidCardOptionResponse)에 memberRules(레벨 → {min, max, step, display}) · spanMemberRules(MEGARAID 만: p → RAID10 규칙)를 서버가 계산해 싣습니다. 레벨 옵션의 data-min-disks(-cached) 는 제거(카드에 따라 갈리므로).
  • 스팬 입력 = 개수 셀 둘째 줄(축 6): tplDiskGroupRow 의 개수 셀을 n-cell-stack 으로 바꾸고, 둘째 줄에 "스팬당 [p ▾]대" select(dgSpan · 선택지 = DrivesPerSpan.options() · 기본 2)를 둡니다. MegaRAID 카드 × RAID10 행에서만 보이고, 그 밖(레벨 변경 · 카드 해제 · MPT_IR 카드로 교체)에는 숨기고 제출 JSON 에서 drivesPerSpan 을 빼서 보냅니다(서버 규칙 10 에 걸릴 값을 UI 가 만들지 않는다). 개 · 개씩 n 과 맞지 않는 p 옵션은 disabled + 그 p 의 규칙 문구.
  • 구성 미리보기: 스팬 select 아래 한 줄 — 개 · 개씩이면 "→ 스팬 3개 × 2대", 개 이상이면 "→ 그룹 크기 ÷ 2 = 스팬 수(2~8개)". 규칙 위반이면 미리보기 대신 규칙 문구가 같은 자리에 has-error 로 뜹니다.
  • MPT_IR × RAID10 안내: 둘째 줄에 스팬 select 대신 짧은 안내 "IR 방식 · 3~10대(홀수 허용) · 스팬 지정 없음" — 문구는 서버 MemberCountRule.display + 고정 꼬리.
  • 수정 폼(setting-edit.html — 같은 조각 재사용): SETTING_INITIAL 의 drivesPerSpan 으로 select 를 미리 채우고, 필드가 없는 구 저장본은 기본 2 로 보입니다(저장하면 2 가 명시됨 — 동작 동일).
  • 개수 입력: min · max · step 을 input 속성과 placeholder("4~16 · 2 단위")로, 위반은 has-error + title = 규칙 문구(서버 MemberCountRule.display 를 그대로 씁니다 — JS 는 문구를 짓지 않습니다). 개 이상 + 단위 있는 규칙이면 보조 안내 "계획 시점 그룹이 2대 단위가 아니면 계획이 거절됩니다".
  • 표시: OsVolumeTargets.summarize = "RAID10(스팬당 2대) · HDD · SAS · 자동 탐지 · 4개 이상"(스팬 지정 묶음만) · 게스트 상세 계획 볼륨 레벨 칸 "RAID10 · 스팬 3 × 2대".
§5. 흐름 (정의서 작성 → 계획 → 집행)
