재시도 커서		 [재시도] 가 커서를 실패 step 에 둔 채 실패 플래그만 지웠다. 다음 체크인의 계획이 첫 진단 때의 옛 인벤토리(볼륨 0) 위에서 세워졌다. deleteExistingFirst=false 로 잔여 spvR1V1 위에 add vd → disk doesn't have enough capacity(2/2). 우회는 콘솔에서 VD 를 손으로 지우는 것뿐이었다.
F-8 의 본질 — RAID 계획은 저장된 인벤토리의 함수인데, 실패한 집행이 카드에 남긴 볼륨을 그 저장본이 모른다. 커서가 RAID_APPLYING 에 머물면 재채집 지시가 나갈 자리가 없으므로, 서버는 낡은 사실 위에서 같은 계획을 다시 세우고 게스트는 같은 이유로 다시 거절한다. "재시도가 실패를 되풀이한다" 는 증상은 커서 위치의 결과다.

진입 전제 — RAID 구성 계열의 선행 슬라이스는 모두 서 있다: E3.5-1(인벤토리 채집 · 적재), E3.5-3(집행 · 검증 · 계획 동결), E3.5-5(진단 시점 사전 파악), E3.5-6(VD 파라미터 축), E3.5-7-a(개수 모드). 이 슬라이스는 그 위에서 지시 상태기계 두 줄과 재시도 진입점만 고친다.

§2. 요구사항 (확정) + 비목표
  1. 재시도는 재채집부터 — RAID 구성 phase 의 운영자 재시도는 커서를 RAID_INVENTORY_COLLECTING 으로 되감아, 다음 부팅의 실물 위에서 계획이 다시 선다.
  2. 되감기는 같은 phase 안에서만 — phase 를 벗어나는 되감기는 역행 금지 invariant 위반이므로 엔티티가 거절한다.
  3. 되감기 지점의 소유자는 실행기 — 명령 서비스에 phase 분기를 늘리지 않는다. 기본값은 "실패 지점 그대로" 이고 RAID 만 override 한다.
  4. 첫 진입도 재채집 — 진단 때 채집한 인벤토리는 그 사이(펌웨어 갱신 · 설정 적용 · 실패한 집행)에 낡을 수 있다. 계획은 항상 이 부팅의 실물로 세운다.
  5. 검증 지시는 "성공한 집행 + 그 뒤 검증 행 없음" 일 때만 — 검증이 실패로 닫힌 뒤의 재시도가 잔여 위에서 검증만 되풀이하지 않게 한다.
  6. VD 배경 초기화 토큰 정정 — bgi=on|off → autobgi=on|off. CLI 어휘의 소유자는 VdBackgroundInit.cliToken() 한 곳이다.
비 목표 :
  • 자동 재시도 — 재시도는 여전히 운영자 액션만이다(전진 전용 가드 체계의 유일한 명시 예외).
  • 서버가 잔여 볼륨을 직접 지우는 명령 — 삭제는 계획의 "기존 구성 처리" 축이 게스트 CLI 로 집행한다. 서버가 별도 파괴 명령을 내지 않는다.
  • 다른 phase 의 되감기 — 훅의 기본값(현 커서)을 그대로 둔다. 필요해지는 phase 가 나오면 그 실행기가 override 한다.
  • storcli 외 계열 어휘 확장 — 새 카드 계열의 CLI 어휘는 enum 매핑 추가로 열려 있으나 이번 scope 밖이다.
  • 화면 · 엔드포인트 계약 변경 — 상세 화면의 [재시도] 버튼과 그 경로 · 응답은 그대로다.

default ProvisioningPhaseStep retryEntryStep(ProvisioningProgress progress) {
    return progress.getCurrentStep();              // 기본 = 실패 지점 그대로
}

// RaidConfigurationExecutor
@Override
public ProvisioningPhaseStep retryEntryStep(ProvisioningProgress progress) {
    return ProvisioningPhaseStep.RAID_INVENTORY_COLLECTING;
}

// GuestServerCommandService.retry — 판정 지점은 여기 하나
ProvisioningPhaseStep entry = phaseExecutorRegistry.find(progress.currentPhase())
        .map(executor -> executor.retryEntryStep(progress))
        .orElse(progress.getCurrentStep());

되감기 invariant — ProvisioningProgress.clearFailed

public void clearFailed(LocalDateTime now) { clearFailed(now, currentStep); }   // 기존 계약 보존

public void clearFailed(LocalDateTime now, ProvisioningPhaseStep entryStep) {
    if (!isFailed())                       throw new IllegalStateException("실패 상태가 아닌 …");
    if (entryStep == null || currentStep == null
        || entryStep.getPhaseType() != currentStep.getPhaseType())
        throw new IllegalStateException("재시도 되감기는 같은 phase 안에서만 …");
    this.failedAt = null;
    this.currentStep = entryStep;
    this.motion = ProvisioningMotion.AWAITING_BOOT;
    this.lastTransitionAt = now;
}

되감기는 같은 phase 로만 허용되므로, RAID 아닌 phase 에서 실행기가 잘못된 step 을 돌려주면 재시도가 500 으로 끊긴다. 이 실패는 의도된 것이다 — 조용히 커서를 옮겨 다른 phase 의 스크립트를 발급하는 것보다 낫다.
