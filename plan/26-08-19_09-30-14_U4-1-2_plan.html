§1. 현재 상태 (진단)

U4-1-1(완료 2026-08-19)이 만든 RAID 구성 단계는 카드 전제와 묶음 규칙 5 축 ({raidLevel, diskType, transport, capacity, count})만 적는다. 어느 볼륨이 OS 영역인지 적을 자리가 없다. 파티션은 아직 장치명(PartitionRequest.diskName)을 가리킨다 — U4-1-3 이 이것을 역할 참조로 바꾸려면 역할이 먼저 있어야 한다.

토론 입력 (U4-1 토론 1~8 회차)

  • E7 OS 영역은 정확히 하나. E15 묶음마다 역할을 명시한다.
  • E18 · E19 묶음은 규칙이라 조건에 맞는 조합 전부에 적용돼 볼륨이 여럿 생긴다.
  • E23~E27 우선순위 조건식(기본 NVMe SSD → SATA SSD → HDD, 작은 용량부터)을 정의서가 값으로 갖고 생성 시 기본값을 채운다.
  • E32 우선순위의 대상은 RAID 볼륨 + 단독 디스크.

붙일 자리

DiskGroupRuleRequest(역할 축) · RaidConfigurationRequest(우선순위 목록) · DiskGroupRules(7 번 규칙) · 폼 묶음 표(역할 열) + 새 우선순위 표 · 상세 fragment. 드래그 코드 bindDiskGroupDrag 는 컨테이너만 인자로 빼면 두 표가 같이 쓴다. DDL · phase · 자원 신설은 없다.

§2. 요구사항 (확정) + 비목표
  1. 묶음 규칙마다 역할 우선순위에 따름 / OS 영역 / Data 영역 / 영역 할당 없음.
  2. 볼륨 우선순위 표 — 행 = 종류 · 전송 · 용량 순서, ☰ 순서 변경, 추가 · 삭제, 진입 시 기본 행이 채워져 있고 기본 행으로 되돌리기 버튼.
  3. OS 고정 묶음 최대 1 개(UI 1 차 차단 + 서버 가드).
  4. 상세 · 피커에 역할과 우선순위 표시.
  5. payload 왕복 보존 · 판정 메서드 미유출.
비 목표
  • 규칙 → 볼륨 매칭과 OS/Data 실제 결정 — E 영역.
  • 파티션 대상 장치명 → 역할 — U4-1-3. Data 영역 파티셔닝 — U4-1-4.
  • 할당 시점 디스크 대조 — U4-1-1 D8 그대로 보류.
  • 상세의 OS/Data 예측 표시 — 볼륨은 실행 시 생긴다.

4-1. VolumePriorityRuleRequest 의 검증 · 메서드

  • @JsonIgnore @AssertTrue isConcrete() — 종류 · 전송이 AUTO 가 아니다(“우선순위 행에는 자동 탐지를 쓸 수 없습니다”). 묶음 규칙의 enum 을 그대로 쓰되 AUTO 만 막는다 — 새 enum 둘을 더 만들면 SSD/HDD · SATA/SAS/NVMe 표기가 두 벌이 된다.
  • @JsonIgnore @AssertTrue isTransportCompatible() — HDD × NVMe 아님(U4-1-1 규칙 6 과 같은 사실).
  • static List<VolumePriorityRuleRequest> defaults() — 기본 5 행(§3 payload 순서). 기본값의 단일 진실 출처이며 폼 채움 · 되돌리기 · 테스트가 이것만 본다.
  • toDisplay() — “SSD · NVMe · 작은 용량부터”.
  • VolumePriorityRules.rankOf(rows, diskType, transport)(static, 신설 클래스) — 매칭되는 첫 행 index, 없으면 Integer.MAX_VALUE. 정의서가 적은 값의 뜻이며 E 가 볼륨 정렬에 그대로 쓴다.

RaidConfigurationRequest.isVolumePriorityDistinct() — (종류, 전송) 조합 중복 없음(“우선순위 행의 종류 · 전송 조합이 중복됩니다”). DiskGroupRules 7 번 규칙 — OS 규칙 둘 이상 → InvalidDiskGroupException.multipleOsRules(ruleNo, firstRuleNo) “N번 묶음: M번 묶음이 이미 OS 영역으로 고정되어 있습니다 — OS 영역은 한 묶음만 고정할 수 있습니다.” 중복 identity 는 5 축 그대로(역할 미포함).

단계 간 정합 — SettingSaveRequest.isOsVolumeDeterminable()(@AssertTrue, 기존 isOsSelectionConsistent · isProcessTypeUnique 옆). 정의서에 OS 설치 단계가 있고 묶음 규칙이 1 개 이상이면 OS 고정 규칙이 있거나, BY_PRIORITY 규칙이 1 개 이상이면서 우선순위 행이 1 행 이상이어야 한다 OQ3 권장안 반영. 메시지 “OS 설치 단계가 있으면 OS 영역이 될 수 있는 묶음(OS 고정 또는 우선순위에 따름 + 우선순위 행)이 있어야 합니다.” 묶음 규칙이 0 개면 볼륨이 없어 적용하지 않는다(설치기 자동 — U4-1-1 그대로). OQ3 미채택 시 BY_PRIORITY 규칙 조건이 빠지고 우선순위 행 1 행 이상만 남는다.

4-2. 실행 해석 계약 (E 인계)

  1. 볼륨 = 규칙 매칭 결과(RAID 볼륨 · 단독 디스크 각각).
  2. OS 후보 = OS 고정 규칙이 있으면 그 규칙의 볼륨만, 없으면 BY_PRIORITY 규칙 볼륨 전부. DATA · NONE 규칙 볼륨은 제외.
  3. 후보를 우선순위로 정렬(rankOf → 행의 용량 순서) → 첫째가 OS 영역. 후보 0 이면 OS 미지정 — 설치기 자동 선택인지 실패 전환인지는 E 가 정한다.
  4. OS 와 NONE 규칙 볼륨을 뺀 나머지를 같은 정렬로 Data 1, 2, … 순번(U4-1-4 입력).
  5. 어느 행에도 안 맞는 볼륨은 맨 뒤, 동률은 장착 순서(D6 · T3).
  6. NONE 볼륨은 마운트하지 않는다 — U4-1-4 파티셔닝 대상도 아니다.

§7. 예외 계층

신규 클래스 없음. InvalidDiskGroupException(400 · field diskGroups)에 multipleOsRules 팩토리만 추가한다.

D1 — E15 의 “정확히 하나만 OS” 는 E18(규칙 → 볼륨 여럿) 뒤 성립하지 않아 E23 이 우선순위를 더했다. 합치면 “우선순위에 맡김 / OS 고정 / Data 로 제외 / 영역 할당 없음” 넷이며, index 포인터는 ☰ 드래그로 어긋난다.

D2 — 고정이 둘이면 뜻이 흐려진다(원하면 둘 다 BY_PRIORITY). Data 만 정하는 정의서는 정당하다(U4-1-1 D14). 다만 OS 설치가 있으면 어느 볼륨이 OS 인지 정의서에서 결정돼야 한다(사용자 확정 2026-08-19).

D3 — 사용자 지시. 유동 행이라 SAS SSD · SAS HDD 같은 조합도 운영자가 넣거나 뺀다.

D4 — 표기 두 벌을 피한다.

D5 — 서버가 빈 값을 조용히 기본으로 바꾸면 direct POST 에서 사용자가 모르는 값이 저장된다. 정의서에는 폼이 채운 값이 언제나 있다.
