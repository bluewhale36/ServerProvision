§1. 현재 상태 (진단)

2026-09-01 RAID 구성 계열의 CP7 실기 직후 사용자가 제기한 요구에서 출발한다. 처음 지목된 것은 MegaRAID 9361-8i 의 HII 설정 화면 "CONFIGURE VIRTUAL DRIVE PARAMETERS" 중 실무에서 실제로 조정하는 네 항목이었다 — Write Policy, Drive Cache(하드디스크 문맥), Disable Background Initialization, Default Initialization. 이후 사용자 지시로 scope 가 확장되어, 이 화면에서 지정 가능한 항목 전체 8종을 다룬다. 현재 정의서에는 이 축들을 지정할 자리가 전혀 없어, 집행은 카드 기본값과 코드에 고정된 초기화 정책으로만 볼륨을 만든다.

핵심 진단 — 이 축들은 MegaRAID 계열에만 대응 개념이 있고 MPT IR 계열에는 없다. 그런데 정의서 화면도 서버 검증도 선택된 RAID 카드가 어느 계열인지 알 방법이 없다. 계열을 모른 채 축을 열면 IR 카드에서 "지정했는데 조용히 무시" 되는 상태가 되므로, 값 모델보다 계열 식별이 선결 과제다.

초기화 정책의 현행값도 함께 확인해 둔다. 지금 집행은 start init force(fast) 를 볼륨 전체에 일괄 적용하며, 이는 2026-09-01 사용자 지시로 확정하고 실기에서 실증한 동작이다. 이번 슬라이스는 이 동작을 없애는 것이 아니라 축으로 승격해, 지정이 없으면 그대로 유지되게 한다.

§2. 요구사항 (확정) + 비목표
  1. 8축 지정 — Strip Size · Read Policy · Write Policy · I/O Policy · Access Policy · Drive Cache · Background Initialization · Default Initialization 을 정의서에서 고르고 집행까지 전달한다. scope 확장 최초 요구는 4항목이었고, 사용자 지시로 HII 화면의 지정 가능 항목 전체로 넓혔다.
  2. 배치는 묶음 규칙 행마다 — 디스크 묶음 규칙 각 행이 자기 파라미터를 갖는다(사용자 확정). 카드 수준 공통값이나 2단 상속은 두지 않는다.
  3. 기본은 HII 기본값 2026-09-02 개정 — 고르지 않은 축은 9361-8i HII 화면의 기본 선택(Strip 256KB · Read Ahead · Write Back · Direct · Read Write · Drive Cache Unchanged · Disable BGI No · Default Initialization No)으로 채워져 항상 명시 전송된다. 최초 안(미지정 = 옵션 미전달 = 카드 펌웨어 기본에 맡김)은 CP6 검수에서 폐지했다 — 정의서가 값을 확정한다.
  4. 사내 표준값은 코드에 싣지 않는다 — 표준 세팅 값이 비공개이므로 기본값 · 상수 · 프리셋 어디에도 넣지 않고, 표준 적용은 운영자가 정의서에서 명시 선택하는 방식으로 흡수한다. 각 enum 의 DEFAULT 는 공개된 HII 기본 선택이라 이 제약에 걸리지 않는다.
  5. 계열 연동 — MegaRAID 계열 카드에서만 축을 노출한다. IR 계열 카드를 고르면 화면이 먼저 막고(서브 행 숨김 · 값 잠금), 화면을 우회한 요청은 서버가 400 으로 거절한다.
  6. 어휘 조립은 서버가 — 서버가 storcli 형태로 조립해 payload 에 담고 게스트 에이전트는 전달 · 실행만 한다. 항목이 더 늘어도 에이전트는 바뀌지 않는다.
비 목표 :
  • RaidResultVerifier 의 4축 대조에 VD 파라미터 검증을 추가하지 않는다 — 설정 실패는 집행 단계의 storcli 출력 검사(Failed|Failure)가 잡는다.
  • Emulation Type(펌웨어 의존 · 512e) · Spares(VD 파라미터가 아니라 구성 요소 — 디스크 소비에 영향) · CacheCade(Cbsize · Cbmode — 미사용 기능)는 제외한다. "지정 가능한 값 전부" 의 기준은 HII CONFIGURE VIRTUAL DRIVE PARAMETERS 의 8항목이다.
  • IR 계열 기능 추가 없음. 사내 표준값의 어떤 형태의 내장도 없음.

§4. 도메인 모델 (SSOT)

D1. 값 모델 — enum 8종, 기본은 HII 기본값 2026-09-02 개정

개정(CP6 검수 · 사용자 지시) — 최초 안은 각 enum 에 UNSPECIFIED(옵션 미전달 = 카드 기본값)를 두는 것이었다. 검수에서 "UNSPECIFIED 를 없애고 BIOS 에서 기본 선택된 값이 기본값으로 들어가게" 지시가 내려 각 enum 이 DEFAULT 상수(HII 기본 선택)를 갖고, 비운 축은 VdParameters 생성자가 그 값으로 채운다. Default Initialization 의 기본은 HII 그대로 No 로 확정했다(세션 질의에 사용자 답 — 소거가 필요한 정의서는 Fast 를 고른다). 아래 표 · 데모는 개정판이다.

여덟 축을 provisioning.setting.enums 에 enum 으로 신설한다. 문자열로 실어 나르지 않는다(Primitive Obsession 금지). 사용자 지시가 "지정 가능한 값은 다 정의" 였으므로 8종 전부를 정의한다. 표의 순서는 폼(D2)과 같은 HII 화면 순서다.

굵은 값이 각 enum 의 DEFAULT 다. 화면 항목 이름은 "Disable BGI" 지만 축은 ON / OFF 대칭으로 두고 표기만 HII 어휘(Yes = BGI 끔 / No = BGI 켬)를 따른다. 초기화 축은 HII "Default Initialization" 과 1:1 — NONE(No, 기본)은 init 을 생략해 디스크의 기존 데이터가 남고, FAST 는 start init force(2026-09-01 실기의 소거 방식), FULL 은 start init full force 를 낸다. 사내 표준값은 여전히 코드에 없다 — HII 기본은 공개 사양이고, 표준이 그와 다른 축은 운영자가 정의서에서 고른다.

Strip Size 의 지원 집합 — 카드마다 지원하는 값이 다르다(9361-8i 는 64KB~1MB 계열). 이번에는 전 값을 노출하고, 카드가 지원하지 않는 값은 집행 단계의 storcli 오류 검사가 잡게 둔다. 지원 집합 질의는 아래 확장성 쟁점 ②의 확장 경로로 미룬다.

확장성 쟁점 (사용자 제기 — CP1 토론 반영) : enum 이 다른 카드로의 확장을 막지 않는가? 세 가지로 답한다.
  1. 이 축들은 MegaRAID 고유가 아니라 RAID 컨트롤러 일반 개념이다(Adaptec arcconf · HPE ssacli · Dell PERC 모두 보유). 그래서 enum 값은 CLI 문자열이 아니라 중립 개념으로 명명했고(WRITE_BACK 이지 "wb" 가 아니다), CLI 어휘 변환은 카드 계열별 집행 계층(D4)에 둔다. 새 카드를 붙이는 일은 RaidChipFamily 상수 + 어휘 매핑 + agent 어댑터 추가이며, 어댑터는 어차피 필요하므로 enum 이 병목이 아니다.
  2. 진짜 확장 지점은 카드마다 값 집합이 다른 경우다(예: AWB 가 없는 카드, Strip Size 지원 폭이 다른 카드). 그 시점에 supportsVdParameters() 를 "지원 값 집합" 질의(supportedWritePolicies() 류 method-per-constant)로 넓혀 흡수한다. 지금 미리 만들지 않는 이유는 "미리 분리 금지" 원칙 — 현재 지원 계열이 MEGARAID 하나라 boolean 으로 충분하다.
  3. 탈락 대안 : 자유 key-value 문자열 맵. 확장성은 최대지만 Primitive Obsession 금지(불가침) 위반이고, 폼이 자유 입력이 되어 오타를 막지 못하며 검증도 불가능하다. "정해진 선택지에서 확정적으로 고른다" 는 실무와도 맞지 않는다.

D3. 카드 계열 SSOT — RaidCard.chipFamily 신설

채택 — RaidCard 에 chipFamily(enum 컬럼 · NOT NULL)를 신설한다. 등록 · 수정 폼에 select 로 노출하고 값은 RaidChipFamily(MEGARAID · MPT_IR)를 쓴다. 스키마 변경은 DDL 1문이며, 기존 자원 2건은 같은 DDL 의 UPDATE 로 실측값을 부여한다(9361-8i = MEGARAID · CRA3338 = MPT_IR). 판정은 RaidChipFamily.supportsVdParameters() 를 method-per-constant 로 두어 MEGARAID 만 true 를 돌려준다.

폼 메타 RAID_CARD_BY_ID.chipFamily ─▶ JS 진리표 ─▶ IR 이면 서브 행 숨김 + 값 잠금 (UI 1차 차단) └────────────────▶ DiskGroupRules 검증 ─▶ IR + 지정값 = 400 (서버 안전망) 같은 판정 : RaidChipFamily.supportsVdParameters()

두 층이 같은 메서드를 본다는 점이 이 결정의 핵심이다 — 화면이 막는 조건과 서버가 던지는 조건이 갈라지면 그 순간 드리프트다. RaidChipFamily 는 execution.engine.raid 소속이고 provisioning 이 execution 을 참조하는 것은 허용 방향이다(OwnedPhasesProvider 선례). 역방향 참조는 만들지 않는다.

탈락 대안사유
pciSubsystemId 로 계열 도출실물 카드 2건 다 미채움(실기에서 "Subsystem 미확보" 경고) — 채움은 E3.5-5 소관
supportedRaidLevels 간접 추정도메인 의미 왜곡 · 부정확
계열 연동 생략 (전 카드 노출 + IR 집행 무시)"지정했는데 조용히 무시" 는 UX 원칙(모순은 UI 1차 차단) 위반

D4. 계약 — VdParameters record 하나로 운반, payload 는 3필드 조립

DiskGroupRuleRequest 에 @Valid VdParameters vdParameters 를 추가한다. VdParameters 는 여덟 enum 을 담는 record 이며 비운 필드는 생성자가 DEFAULT 로 채운다(개정). record 자체가 null 인 구 저장본은 "축 없음" 으로 읽고, MegaRAID 볼륨이면 RaidPlanner 가 VdParameters.DEFAULTS 로 조립한다 — 마이그레이션이 없다.

중복 판정에는 넣지 않는다 — DiskGroupRules.identity 에 vdParameters 를 포함하지 않는다. 다섯 축이 같으면 파라미터가 달라도 같은 디스크 집합을 겹쳐 잡는 것이며, 이는 role 을 identity 에서 뺀 것과 같은 사유다.

계획 단계는 매칭 로직을 건드리지 않는다 — RaidPlanner 는 지원 계열이면 규칙의 vdParameters(없으면 DEFAULTS)를 조립해 PlannedVolume 에 싣고, 축 없는 계열은 비워 둔다. 집행 payload 에서는 8축을 항목별 필드로 늘어놓지 않고 서버가 storcli 형태로 조립해 3필드로 동봉한다.

필드내용비어 있을 때
createOptsadd vd 뒤에 그대로 붙는 인라인 옵션 문자열 — 예 "wb ra direct strip=256 pdcache=default". MegaRAID 는 항상 5토큰null = 축 없는 계열(IR)
setOps생성 후 per-VD set 명령 인자 목록 — 예 ["bgi=on","accesspolicy=rw"]. MegaRAID 는 항상 2인자빈 목록 = 축 없는 계열(IR)
init"none" | "fast" | "full"null = 축 없는 계열(IR) · MegaRAID 기본은 "none"

어휘의 SSOT 는 서버 enum 의 cliToken 이며, 이는 E3.5-3 이 세운 "생성체는 서버" 원칙의 연장이다. 에이전트는 전달 · 실행만 하므로 파라미터 항목이 이후 더 늘어도 에이전트는 바뀌지 않는다 — 확장성 쟁점의 실천이다.

초안 개정 사유 — 항목별 4필드(초안)를 3필드 조립 전달로 바꾼 이유는 둘이다. ① 축이 8개가 되면서 파이프 계약이 11필드로 비대해진다. ② 새 항목이 생길 때마다 에이전트의 sed 와 분기가 함께 자라는 구조가 되는데, 이는 조건분기 legacy 확장에 해당한다. 조립 문자열이 불투명해지는 대가는, PLANNED 동결 시 statusMeta 에 같은 형태가 저장되어 원장으로 추적 가능하다는 점으로 상쇄한다.

BEFORE — 현행 agent.sh

VOL_LINES = NAME|LEVEL|SLOTS

add vd type=raidN name=… drives=…
storcli /c0/vall start init force   일괄

AFTER — 조립 문자열 전달 · 볼륨별 실행

VOL_LINES = NAME|LEVEL|SLOTS|CREATEOPTS|SETOPS|INIT

add vd … drives=… $CREATEOPTS
for op in $SETOPS: /c0/v$IDX set $op
storcli /c0/v$IDX start init [full] force

MEGARAID 분기에서 생성 루프의 인덱스가 곧 VD 번호가 된다 — 기존 구성을 del force 로 지운 뒤 만들기 때문에 0부터 순서대로 붙으며, 실측(spvR1V1 = VD0)과 정합했다. 초기화는 vall 일괄에서 per-VD 로 재편한다 — none(HII 기본)은 생략, fast/full 은 force 로 실행하고 Failure 출력 검사는 그대로 둔다. IR 분기는 파라미터를 무시한다 — 서버 가드 때문에 도달할 수 없는 경로이며 이중 안전으로 남긴다.

리스크

  • FULL init 의 소요 시간 — 수 시간이 걸린다. start 는 즉시 반환하므로 초기화가 끝나기 전에 후속 phase(OS 설치)와 경합할 수 있다. E4 진입 시 재검토 대상으로 적립한다.
  • 인자 위치 — 정책 옵션이 drives= 뒤라는 규칙은 문서 기반이다. CP7 실기 1회로 확정한다.
  • WB 강등 — 배터리 백업이 없으면 카드가 스스로 WT 로 낮춘다. 카드 동작이므로 코드가 아니라 안내 문구(도움말)로만 다룬다.
  • VD 번호 = 생성 순서 전제 — del force 로 비운 카드에서의 실측(spvR1V1 = VD0)과 정합했다. 결과 검증은 이름 매칭이라 이 전제와 무관하다.

잔존 책임 · 경계

  • pciSubsystemId 채움은 이 슬라이스가 하지 않는다 — E3.5-5 소관.
  • chipFamily 컬럼의 실 DB 적용(ALTER + UPDATE 2건)은 Step 9 에서 ddl/ 산출 후 적용하고 SHOW CREATE TABLE 로 확인한다.
  • 초기화 명령이 vall 일괄에서 per-VD 로 재편되므로, 볼륨이 여럿인 구성에서 출력 검사 지점도 볼륨 수만큼 늘어난다.
  • 카드가 지원하지 않는 Strip Size 값은 화면이 막지 않는다 — 집행의 storcli 오류 검사로 드러난다.
