§0. 배경 — 화면에는 자물쇠가 생겼고 게스트 채널에는 아직 없다

S18 로 웹 화면에 로그인이 들어왔다. 그 슬라이스는 브라우저로 들어오는 요청에 자격을 요구하게 만들었지만, 게스트 서버가 쓰는 통로인 /api/pxe/v1/** 는 손대지 않았다. SecurityConfig 에 .requestMatchers("/api/pxe/v1/**").permitAll() 한 줄이 그대로 남아 있고, 그 주석에도 "PXE 채널에 대한 인증 수단 추가하기 전까지 무인증 허용" 이라고 적혀 있다. 즉 인증 수단을 만드는 것이 남은 일이고, 이 슬라이스가 그 첫 단계다.

지금 이 통로가 열려 있다는 말은 구체적으로 이렇다. 사내망에 있는 누구든 다음 한 줄을 치면 게스트 서버 한 대가 실제로 등록된다.

curl "http://<프로비저닝 서버>/api/pxe/v1/boot?systemUUID=00000000-0000-0000-0000-000000000001\
&macAddress=aa:bb:cc:dd:ee:ff&ipAddress=10.0.0.99&vendor=…&boardModel=…"

/boot 는 이름과 달리 읽기 전용이 아니다 — 처음 보는 시스템 UUID 면 게스트를 등록하고 게스트 토큰을 발급한다. 이것은 추정이 아니라 실기에서 겪은 일이다(누적 메모리 · "/boot 는 읽기 전용이 아니다": 확인용 curl 한 번이 RUNNING 행과 토큰을 기록했다).

왜 두 단계로 나누는가 — 게스트에게 자격을 요구하려면 그 게스트에게 자격이 이미 있어야 한다. 그런데 게스트 토큰은 /boot 의 최초 등록 트랜잭션에서 발급되므로, /boot 와 부팅 자산(/assets/**)은 정의상 자격이 생기기 전의 요청이다. 여기에 토큰을 요구하면 부팅 자체가 성립하지 않는다. 그래서 1단계는 토큰이 이미 있는 요청(에이전트 보고 · 서빙 자산)을 필터로 끌어올리고, 첫 접촉에는 별도의 자격(2단계의 PXE 부팅 계정과 출발지 제한)을 따로 붙인다.

§2. 요구사항 (1단계 확정) + 비목표
  1. 게스트 채널 전용 SecurityFilterChain 을 웹 체인과 분리한다 — 세션을 만들지 않고, 로그인 화면으로 되돌리지 않는다(D-1).
  2. 헤더 토큰과 경로 토큰을 Spring Security 인증으로 승격한다 — AuthenticationConverter 가 자격을 읽고, AuthenticationProvider 가 판정하고, AuthenticationFilter 가 배선한다(D-2 · D-3 · D-4).
  3. 인증 실패와 자격 부재는 401 JSON 이다 — 본문 형식은 기존 ApiErrorResponse 를 그대로 쓴다(D-1 · D-7).
  4. 컨트롤러는 문자열 토큰이 아니라 principal 로 게스트를 받는다 — 도메인 가드(미개시 · 회수 409 · 진입 게이트)는 있던 자리에 그대로 둔다(D-6).
  5. /boot 와 /assets/** 는 게스트 체인 안에서 permitAll 이다 — 열어 두되 웹 체인이 아니라 게스트 체인의 규칙으로 연다(D-5).
  6. 웹 체인에서 /api/pxe/v1/** permitAll 한 줄을 뺀다 — 그 경로는 이제 앞 체인이 가져간다(D-1).
  7. 하네스와 테스트의 계약을 갱신한다 — 404 를 단언하던 자리를 401 로 옮기고, 체인 경계 자체를 잠그는 테스트를 새로 만든다(D-7 · D-9).
  8. 인증 판정 · 토큰 발급 · 회전 정책은 바꾸지 않는다 — 게스트 토큰은 여전히 등록 시 1회 발급되는 고정 값이고, 대조 규칙도 그대로다. 옮기는 것이지 바꾸는 것이 아니다.
비 목표 — 아래는 이 슬라이스에서 하지 않는다.
  • 첫 접촉의 인증(/boot · /assets/**) — 2단계(S19-2) 의 PXE 부팅 계정과 LAN 출발지 제한이 받는다. 1단계에서는 permitAll 로 남으므로, §0 의 curl 로 유령 게스트를 등록하는 일은 이 슬라이스가 끝나도 여전히 가능하다(D-8 에 명시).
  • 게스트 토큰의 회전 · 만료 · 재발급 — 고정 토큰 전제를 유지한다. 수명 정책은 이 슬라이스의 판단 대상이 아니다.
  • TLS 종단 · 상호 TLS 인증(mTLS — 서버와 클라이언트가 서로 인증서를 제시하는 방식) — 외부망 배포 시 검토 대상이며 2단계 예고에 적는다.
  • CSRF(Cross-Site Request Forgery) 활성화 · 세션 정책 · 웹 체인의 인증 판정 — S18 이 정한 자리 그대로다. 이번에 웹 체인에서 지우는 것은 permitAll 한 줄뿐이다.
  • 레지스트리의 영속화 — 서빙 토큰이 메모리에만 사는 것은 기존 설계이며(재기동 시 새 토큰), 여기서 바꾸지 않는다.
🎬 미리보기 — 요청 시뮬레이터 (경로 × 자격 → 체인 → Converter → Provider → 인가 → HTTP)

위 두 줄이 요청 하나를 만든다 — 어느 경로로 오는가와 무엇을 들고 오는가. 이 둘을 바꾸면 아래 파이프라인이 즉시 다시 계산된다. 어느 체인이 이 요청을 잡았는지(@Order(1) 게스트 / @Order(2) 웹), GuestCredentialConverter 가 자격을 무엇으로 읽었는지(서빙 경로면 경로 토큰, 그 밖이면 헤더 토큰 · D-2), GuestTokenAuthenticationProvider 가 그것을 GuestPrincipal 로 세웠는지 아니면 BadCredentialsException 으로 떨어뜨렸는지, 인가 규칙이 무엇을 요구했는지, 그래서 게스트가 받는 HTTP 응답이 무엇인지가 한 줄씩 나온다.

맨 아래 판정 표는 장식이 아니라 같은 함수로 36칸을 전부 돌려 그린 것이다 — 지금 고른 조합이 표에서 파랗게 표시된다. 표의 값은 체인이 내는 판정(D-1 ~ D-5)이고, 컨트롤러가 그 뒤에 무엇을 하는지는 파이프라인 마지막 줄에 따로 나온다.

successHandler 가 "아무것도 하지 않는 것" 이 핵심이다 — Spring Security 의 기본 성공 핸들러는 리다이렉트를 한다(로그인 폼을 전제로 설계됐기 때문이다). 게스트 채널에서는 인증이 성공했다고 해서 요청이 끝나면 안 된다 — 그 요청은 계속 흘러가 컨트롤러에 닿아야 한다. 그래서 성공 핸들러를 "체인을 계속 진행" 으로 바꾼다.
§4. 도메인 모델 (SSOT) — 자격 · 토큰 · principal

이 슬라이스는 엔티티를 만들지 않는다. 새로 생기는 것은 전부 인증 경계의 타입이며, DDL 도 0 이다. 아래 타입들이 "게스트란 무엇인가" 를 표현하는 SSOT(Single Source of Truth — 단일 진실 출처)가 된다.

자격 — GuestCredential (sealed interface)

public sealed interface GuestCredential
        permits GuestCredential.HeaderToken, GuestCredential.ServingToken {

    /** X-Guest-Token 헤더로 온 게스트 신원 토큰(32 hex 고정 값). */
    record HeaderToken(String value) implements GuestCredential {}

    /** 경로 세그먼트로 온 서빙 토큰 — 어느 레지스트리에 물을지가 kind 로 갈린다. */
    record ServingToken(UUID value, ServingKind kind) implements GuestCredential {}

    enum ServingKind { WINDOWS, FIRMWARE }
}

sealed 로 닫는 이유는 자격의 종류가 늘 때 분기문이 자라지 않게 하기 위해서다. 공급자는 switch 패턴 매칭으로 두 갈래를 남김없이 다루고, 새 자격이 생기면 컴파일러가 빠진 갈래를 알려 준다. ServingKind 를 따로 둔 것은 경로 접두(/windows/ · /firmware/)가 어느 레지스트리에 물어야 하는가를 이미 말해 주기 때문이다 — 토큰 값만으로는 누구 것인지 알 수 없다는 것은 FirmwareImageTokenRegistry 주석이 이미 지적해 둔 성질이다.

touchSeen 이 공급자가 아니라 서비스 트랜잭션에 남는 이유 — lastSeenAt 갱신은 쓰기다. 공급자는 인증 필터 안에서 도는 코드라 서비스의 트랜잭션 경계 밖이고, 여기서 쓰기를 하면 도메인 가드가 409 로 롤백해도 갱신만 살아남는 비대칭이 생긴다. 기존 GuestTokenAuthenticator 는 호출자의 트랜잭션에 참여해 그 비대칭이 없었고(주석에 그 판단이 적혀 있다), 그 성질을 그대로 물려받는다. 공급자는 읽기 전용 조회만 한다.

체인 분리		 GuestSecurityConfig 를 새로 두고 @Order(1) SecurityFilterChain guestChain 을 정의한다 — securityMatcher("/api/pxe/v1/**") · sessionManagement(STATELESS) · csrf 비활성 · formLogin 과 httpBasic 없음 · securityContext 는 명시 저장 기본 · exceptionHandling 의 진입점은 GuestAuthenticationEntryPoint(401 · application/json · ApiErrorResponse("게스트 인증이 필요합니다.", code "GUEST_UNAUTHENTICATED")) · accessDeniedHandler 는 403 JSON. 기존 SecurityConfig 는 @Order(2) 로 두고 /api/pxe/v1/** permitAll 한 줄만 뺀다 (a) 지금 체인 하나에 매처만 더한다
(b) 현행(permitAll + 컨트롤러 대조)을 유지한다		 (a) 한 체인 안에서 진입점(로그인 302 대 JSON 401) · 세션 생성(만든다 대 안 만든다) · CSRF 규칙이 서로 얽힌다 — 경로별로 갈라야 할 것이 셋이나 되는데 체인은 하나라 전부 조건 분기가 된다.
(b) 필터 경계가 아예 없어 새 엔드포인트를 만들 때마다 대조를 잊을 수 있고, 대조 코드가 컨트롤러 · 서비스에 흩어진다
D-2
자격 모델		 GuestCredential sealed interface — HeaderToken(String) 과 ServingToken(UUID, ServingKind). GuestCredentialConverter 하나가 요청에서 어느 쪽이든 읽어 GuestAuthenticationToken.unauthenticated(credential) 을 만들고, 자격이 없으면 null 을 돌려준다(필터가 건너뛰고 인가가 401 로 끝낸다). 어느 자격을 읽을지는 경로가 정한다 — 서빙 경로(/windows/{token}/… · /firmware/{token}/…)에서는 경로 토큰이 자격이고 X-Guest-Token 은 읽지 않는다. 그 밖의 경로에서는 헤더 토큰만 본다 (a) 자격마다 필터를 하나씩 둔다
(b) 경로 토큰은 지금처럼 컨트롤러 대조로 남긴다
(c) 둘 다 오면 헤더 우선		 (a) 필터 · ProviderManager · 실패 핸들러 배선이 통째로 복제된다 — 같은 것이 둘이 되는 전형.
(b) 인증 경계가 둘로 갈린다 — 헤더는 필터가, 경로는 컨트롤러가 본다면 "어디서 막히는가" 를 두 곳에서 읽어야 한다. 다만 컨트롤러가 번들 · 파일 경로를 푸는 일 자체는 그대로 둔다 — 체인은 신원만 세운다.
(c) 헤더 우선이면 서빙 경로에서 신원과 번들이 어긋난다 — 체인은 헤더가 가리키는 게스트로 신원을 세우는데 컨트롤러는 경로 토큰으로 번들을 푸니, 둘이 다른 게스트를 가리켜도 통과하거나 자원만 404 가 되는 어긋남이 생긴다. 그 엔드포인트의 자격은 경로 토큰이므로 그것 하나만 읽는 것이 신원과 자원을 한 값에 묶는다
D-3
인증 공급자		 GuestTokenAuthenticationProvider implements AuthenticationProvider. HeaderToken 은 GuestPrincipalResolver.byGuestToken(findByGuestToken · 읽기 전용 트랜잭션)로, ServingToken 은 레지스트리의 guestOf(token) 으로 푼다. 성공은 GuestAuthenticationToken.authenticated(GuestPrincipal(guestServerId, systemUUID), ROLE_GUEST), 실패는 BadCredentialsException. touchSeen 은 공급자가 아니라 서비스 트랜잭션에서(D-6) 공급자가 GuestServer 엔티티를 그대로 principal 로 싣고 touchSeen 까지 한다 인증 필터는 서비스 트랜잭션 밖이다. 엔티티를 여기서 꺼내면 준영속 상태로 컨트롤러까지 흘러가고, touchSeen 쓰기가 도메인 가드의 롤백과 분리돼 "거절당했는데 관찰 로그만 갱신" 이라는 비대칭이 생긴다
D-4
필터 배선		 Spring Security 의 AuthenticationFilter(ProviderManager(provider), converter) 를 쓴다 — successHandler 는 체인을 계속 진행(no-op), failureHandler 는 진입점과 같은 401 JSON, securityContextRepository 는 RequestAttributeSecurityContextRepository(세션 없음). http.addFilterBefore(filter, AuthorizationFilter.class). permitAll 경로라도 제시된 자격이 틀리면 401 이다 — failureHandler 가 인가에 닿기 전에 체인을 끝내기 때문이며, 이는 의도한 거동이다(틀린 자격은 어디서든 오류다. iPXE 는 헤더를 보내지 않으므로 /boot 의 실무 흐름에는 영향이 없다) OncePerRequestFilter 를 직접 써서 헤더를 읽고 SecurityContextHolder 에 넣는다 프레임워크가 이미 같은 모양의 primitive 를 제공한다 — Converter · ProviderManager · 성공 · 실패 핸들러라는 확장점을 직접 만든 필터는 다시 갖추지 못한다. "조건분기 legacy 확장 금지 → 다형성 · Framework primitive" 의 직접 적용
D-5
인가 규칙		 게스트 체인 안에서 — /boot 와 /assets/** 는 permitAll(1단계 한정 · 2단계에서 PXE 부팅 계정이 받는다), dispatcherTypeMatchers(ERROR, ASYNC) 는 permitAll, 나머지 전부(/agent/** · /windows/** · /firmware/** · 앞으로 생길 경로)는 hasRole("GUEST") 엔드포인트를 하나씩 열거해 hasRole 을 붙인다 열거 방식은 새 엔드포인트가 기본으로 열리는 구조다 — 빠뜨리면 무인증으로 열린다. "나머지 전부 hasRole" 은 반대로 새 엔드포인트가 기본으로 닫히고, 열려면 명시해야 한다
D-6
컨트롤러 · 서비스 치환		 CurrentGuestArgumentResolver(HandlerMethodArgumentResolver)를 WebMvcConfigurer 로 등록하고, 컨트롤러의 @RequestHeader(TOKEN_HEADER) String token 을 @CurrentGuest GuestPrincipal guest 로 바꾼다. 서비스 시그니처의 String presentedToken 은 GuestPrincipal guest 가 되고, GuestTokenAuthenticator.requireByToken(String) 은 GuestPrincipalLoader.require(GuestPrincipal)(findById · 부재면 IllegalStateException · touchSeen)이 된다. Windows · 펌웨어 자산 컨트롤러는 경로 토큰으로 번들 · 경로를 푸는 현행을 그대로 둔다 — D-2 에서 그 경로의 자격이 경로 토큰으로 확정됐으므로 체인이 세운 신원과 컨트롤러가 푸는 번들이 같은 토큰에서 나온다. 따로 대조할 것이 없다 (a) @AuthenticationPrincipal 을 쓴다
(b) 서비스가 계속 토큰 문자열을 받는다		 (a) S18 실측 — @WebMvcTest 슬라이스에서 해석되지 않아 컨트롤러 테스트가 principal 을 받지 못한다. 직접 만든 resolver 는 WebMvcConfigurer 로 등록되어 슬라이스에 포함된다.
(b) 토큰 대조가 필터로 올라갔는데 서비스가 여전히 문자열을 받으면 인증이 두 곳에 남는다 — 옮긴 의미가 없어지고 죽은 코드가 생긴다
D-7
계약 변경		 위조 · 누락 · 회수된 토큰은 404 가 아니라 401 JSON 이다. 회수된 Windows 번들 토큰(완료 뒤)과 펌웨어 토큰도 같다. 영향 — 테스트 3 파일의 404 단언을 체인 테스트로 이관(401), 하네스 3 곳(diagnose-cycle.sh 7단계 · windows-install-cycle.sh 의 B1 · token 모드 · complete 4단계) 기대값 갱신, docs/T3-checklist.md 의 "옛 토큰 404" 표기 갱신 진입점이 404 를 내어 기존 계약을 지킨다 401 은 필터 계층의 표준이고, 게스트 토큰이 32자 16진수 랜덤이라 "존재 숨김" 의 실익이 없다(추측으로 맞힐 수 없는 값이다). 반대로 404 를 유지하면 헤더를 아예 안 보낸 요청까지 "없는 자원" 이 되어 뜻이 어긋난다 — 자원은 있고 자격이 없는 것이다
D-8
웹 세션 ≠ 게스트 자격		 로그인 쿠키로 /api/pxe/v1/agent/** 를 부르면 401 이다 — 체인이 다르고 그 체인은 세션을 읽지 않는다. 그리고 운영자가 브라우저로 /boot 를 열어 착수를 기록하던 사고는 1단계에서 그대로 남는다(permitAll). 2단계의 PXE 부팅 계정이 그것을 막는다 — 대안을 두고 고른 항목이 아니다. D-1 · D-5 의 귀결이며, 특히 두 번째 문장은 이 슬라이스가 무엇을 못 막는지를 미리 밝히는 범위 선언이다
D-9
테스트 전략		 체인을 실제로 얹는 GuestChainSecurityTest 를 새로 만들고(@Import + apply(springSecurity())), Converter · Provider · ArgumentResolver 단위 테스트를 각각 둔다. 기존 컨트롤러 테스트 3 은 principal 주입 방식으로 갱신하며 404 단언을 걷어낸다. 서비스 테스트는 시그니처만 갱신한다 — 대안 비교 항목이 아니라 D-7 의 계약 변경이 어디를 깨는지에 대한 대응 목록이다. 상세는 §6
D-10
CP5 검증 계획		 A(정상) A1 진단 사이클 무회귀(diagnose-cycle.sh 완주 · 상세 화면에 채집 반영) · A2 RAID 인벤토리 · 적용 사이클 무회귀 · A3 Windows 서빙 · 완료 무회귀(windows-install-cycle.sh 의 serve · complete) · A4 lastSeenAt 갱신 확인. B(비정상) B1 헤더 없음 → 401 JSON 본문 · B2 위조 → 401 · B3 회수된 Windows 토큰 → 401 · B4 로그인 쿠키로 /agent/checkin → 401 · B5 게스트 토큰으로 웹 화면 GET → 302 /login. C(막는 방식 · 무회귀) C1 웹 회귀(S18 로그인 + 관리자 화면 3) · C2 앱 로그 ERROR 0 — 대안 비교 항목이 아니다. E 단계 예외를 적용한 검증 항목 계획이며, CP5 에서 이 식별자 그대로 수행 · 채증한다

D-8 · D-9 · D-10 은 대안을 두고 고른 것이 아니라 앞 결정들의 귀결 · 대응 · 범위를 명시한 항목이다 — 표의 모양을 맞추려고 없는 대안을 지어내지 않았다.

#질문권고
Q1 브랜치 기반 — S18 이 아직 커밋되지 않았고 이 슬라이스는 SecurityConfig 를 함께 고치므로 S18 위에 쌓인다. feat/S19-1_guest-chain 을 feat/S18_login-signup 에서 딸 것인가, dev 병합을 기다릴 것인가 권고 — S18 PR 을 먼저 열고 그 위에 스택한다. CP7 을 모아서 받는 관례(E 계열 일괄)와 맞고, dev 병합을 기다리면 같은 파일을 두 브랜치가 만지는 기간이 길어진다
Q2 401 계약(D-7) 승인 여부 — 위조 · 누락 · 회수 토큰의 응답을 404 에서 401 로 바꾼다. 테스트 3 파일과 하네스 3 곳, T3 체크리스트 표기가 함께 움직인다 권고 — 승인. 32자 랜덤 토큰에는 존재 숨김의 실익이 없고, 헤더 부재까지 404 가 되는 현행이 의미상 어긋난다. 다만 바꾸는 범위가 문서 · 하네스까지라는 점을 함께 봐 주셔야 한다
Q3 경로 토큰을 체인 안으로 넣을 것인가(D-2 · D-3) — Windows 번들과 펌웨어 이미지의 서빙 토큰까지 인증으로 승격한다. 부르는 쪽이 iPXE · wimboot · BMC 라 헤더를 붙일 수 없어 경로가 유일한 자격이다 권고 — 포함. 빼면 인증 경계가 헤더와 경로로 갈려 "어디서 막히는가" 가 두 곳이 되고, 지금 404 로 끝나던 회수 토큰 접근이 여전히 필터 밖에 남는다
Q4 인벤토리 표기 — S19 를 S19-1(체인 분리) · S19-2(PXE 부팅 계정 · LAN 제한)로 나누고 Notion 하위 페이지를 따로 만들 것인가 권고 — 만든다. 두 단계는 상태가 따로 움직인다 — 1단계는 이번 주에 끝나고 2단계는 iPXE 스크립트 자격 · apkovl 재포장 · nginx 헤더까지 걸쳐 있어 착수 시점이 다르다

주의 · 부산물

  • 하네스는 git 추적 자산이다 — diagnose-cycle.sh · windows-install-cycle.sh 의 기대값을 고치면 그 자체가 계약 문서의 변경이다. 주석의 설명 문구까지 함께 고친다(코드만 고치면 다음 사람이 옛 주석을 믿는다).
  • GuestTokenAuthenticator 는 이름이 사라진다 — 토큰 대조가 공급자로 올라가고 남는 책임은 "인증된 principal 로 엔티티를 꺼내고 lastSeenAt 을 찍는 것" 이므로 GuestPrincipalLoader 가 실체에 맞는 이름이다. 옛 클래스를 남겨 두지 않는다.
  • /boot 의 200 재시도 변환과 필터의 관계는 §7 의 경고대로 2단계에서 정면 과제가 된다. 1단계에서는 permitAll 이라 접점이 없지만, 2단계 plan 의 입력으로 적어 둔다.
  • 샌드박스 포트는 동시 세션과 겹치지 않게 스트림마다 다른 값을 쓴다. 이 슬라이스는 PXE_ASSETS_ROOT 와 PXE_SERVER_BASE_URL 이 있어야 진단 · Windows 하네스가 돈다(E 계열 선례).
  • 환경변수 · DDL 변경 0 — 배포 시 추가로 넣을 값이 없다. 2단계는 반대로 PXE 부팅 계정 자격을 환경변수로 받는다.

§11. 다음 마일스톤 — S19-2 (2단계)

1단계가 끝나면 토큰이 있는 요청은 전부 필터를 지난다. 남는 것은 토큰이 생기기 전의 요청 둘 — /boot 와 /assets/** 다. 2단계는 여기에 게스트 개별 신원이 아닌 채널 자격을 붙인다.

PXE 부팅 계정

  • httpBasic · ROLE_PXE_BOOT · 자격은 환경변수로 주입
  • iPXE 체인 스크립트 URL 에 자격을 실어야 한다
  • DiagnoseLinuxChainload 의 provision_base 에 자격 반영
  • agent.sh 의 wget 헤더 · apkovl 재포장(조각만) — RAID CLI 바이너리 동봉이라 통째 재조립은 금지

출발지 제한

  • IpAddressMatcher 로 LAN 대역 밖 차단
  • nginx 앞단이 있으므로 forward-headers 설정이 먼저 맞아야 실제 출발지가 보인다

외부망 배포 시

  • TLS 종단 + 상호 TLS 인증(mTLS) 검토
  • 사내망 전제가 깨지는 시나리오에서만 필요 — 1 · 2단계와 별개 판단
2단계가 반드시 먼저 풀어야 할 것 — /boot 는 모든 예외를 200 + 재시도 스크립트로 바꾸는 채널이다(iPXE 가 2xx 본문만 실행하기 때문). 여기에 자격을 요구하면 필터가 컨트롤러보다 앞이라 401 본문이 그대로 iPXE 에 닿는다 — 스크립트가 아닌 것을 받은 iPXE 가 어떻게 행동하는지부터 정해야 한다. 1단계에서는 permitAll 이라 접점이 없으므로 이 문제를 그대로 2단계 plan 의 입력으로 넘긴다(§7).
