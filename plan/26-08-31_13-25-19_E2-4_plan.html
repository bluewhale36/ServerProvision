§1. 현재 상태 (진단)

집행 한 사이클은 펌웨어를 굽고 · 전원을 내렸다 넣고 · 게스트가 돌아오기를 기다리고 · 반영을 확인한 뒤 · 설정을 적용하는 순서로 흐른다. 이 슬라이스는 그 흐름을 화면만 보고 따라갈 수 있게 만든다. 판정과 전이 로직은 바꾸지 않는다 — 기록을 더하고, 이미 원장과 진행 상태에 들어 있는 사실을 화면으로 꺼낸다.

아래는 토론 아카이브 §2 의 실태 대조를 압축해 전재한 것이다. 전문은 아카이브가 정본이다.

이미 해소된 것 · 다른 단계로 간 것

  • 기해소 2 — 상세 화면의 rail 은 U3-5-a 가 이미 세웠고, flash 시작 시점의 실시간 갱신은 FirmwareFlashCycle 이벤트가 담당한다.
  • 이관 1 — 목록 화면의 SSE 배선은 S7-1 소관이다. 이 슬라이스는 목록에 표시할 값만 응답에 싣는다.

남아 있는 화면 공백 다섯

  • 설정 phase 는 카드가 없다 — 원장 meta 에 들어 있는 pendingSeen · rebootAt · items · bondAt 가 화면에 나오지 않는다.
  • Task 관측이 버려진다 — 워커가 굽는 동안 읽어 온 관측을 화면이 받지 못한다.
  • 축이 전부 닫힌 뒤 화면은 "완료" 에 머문다 — 그 뒤로 전원 투입 · 복귀 대기 · 반영 확인이 이어지는데 표시가 따라가지 않는다.
  • 세부 단계 이력에 사유가 없다 — 무슨 일이 있었는지가 행에 남지 않는다.
  • BeginSettingStep 의 신원 대기는 침묵이다 — 워커가 기다리는 중인지, 멈춘 것인지 화면으로 구분할 수 없다.
표시 결함 1 — GuestServerQueryService.flashRemainingMinutes 가 복귀 대기 구간에도 축 시한(limitFor(axis))과 progress.lastTransitionAt 을 쓴다. 굽는 중의 기점도 원장 행의 startedAt(엔진 PollFlashTaskStep 의 판정 기점)과 어긋난다. 표시와 판정이 다른 시계를 본다 — 남은 분이 화면과 엔진에서 서로 다른 값이 된다.

재해석 — 재시도는 이미 게스트를 다시 세운다

운영자 재시도는 이미 전원 사이클과 PXE 무장으로 게스트를 다시 세운다(Q3 승인). 그러므로 이 슬라이스에서 재시도에 새 동작을 붙일 이유가 없고, 남은 것은 그 사실을 화면이 말하게 하는 가시화뿐이다.

원장 실태 — 두 계열의 표기가 갈라져 있다

계열origin 표기meta 키
flash소문자-하이픈 (flash-completed 등)origin · detail · target · firmwareId · task
setting대문자 (APPLIED 등)origin · axis · target · pendingSeen · rebootAt · items · bondAt · detail

두 계열은 표기 관례가 다르지만 화면은 한 자리(세부 단계 이력)에서 함께 읽힌다. 그래서 표시용 판독을 하나로 통일해야 한다 — §4 의 ProvisioningHistory.displayNote() 가 그 자리다.

§2. 요구사항 (확정) + 비목표
  1. R1 (Q1) — 설정 phase 현황 카드 신설. 축 2행(BIOS_SETTING · BMC_SETTING), 행마다 상태와 사유 + 부속 정보. BIOS 는 pending 관찰 · 재부팅 시각 · 복귀 대기, BMC 는 항목 진행("N/4 적용") · Bond 재접속 대기.
  2. R2 (Q2) — 워커 하트비트. 마지막 관측(문구 · 시각)을 인메모리로만 들고 카드에 "HH:MM:SS 확인 — 굽는 중" 으로 표시한다. 저장 0 · 재기동 소실 무해.
  3. R3 (⑵-b) — 구간 문구 파생(굽는 중 → 전원 투입 · 복귀 대기 N분 → 복귀 — 반영 확인 대기 → 다음 단계 전진)과 남은 분 계산 정정(기점 · 시한을 엔진 판정과 같은 식으로).
  4. R4 (Q4 ①) — 전원 사건의 원장 instant 행. 차단(power-off) · 투입(power-on, 무장 outcome 을 detail 에) 각 1행. E3 재부팅은 기존 행 meta 에 무장 요약(arm) 키를 더한다(행 증가 0). FlashLedger.isPhaseLevel 에 두 사유를 등록해 축 상태 오염을 막는다.
  5. R5 (E3-3 CP5 O-3) — 세부 단계 이력에 사유 표시. Step 응답에 note 필드를 더한다(meta 의 detail 우선, 없으면 origin 코드).
  6. R6 (E3-3 CP5 O-1) — 대기 사유 파생 표시. BMC 호출 없이 DB 사실만으로 만든다(커서 · 시한 잔여 · 보드 시리얼 부재 힌트). 엔진의 침묵 대기에도 로그 1줄을 더한다.
  7. R7 (decisions 2) — 자원이름 (버전) 표기. AxisResolution 에 resourceName 을 더하고 원장 meta 에 name 키를 더한다. 버전 비교 재료(flashTargetVersion)는 버전 그대로 유지(회귀 함정 — §8 D-7).
  8. R8 (Q6 · decisions 8) — '집행 중 · 전원 꺼짐'. 상세 화면의 접촉 배지와 목록 행에 표시한다(요약 응답에 disruptionBlocked 추가).
  9. R9 (Q3 · Q5 · ⑴) — 안내 문구 보강. 재시도 버튼 안내에 전원 사이클을 명시(펌웨어 단계 한정) · BMC 라벨 보강 · 정의서 미리보기 rail 안내 문구.
  10. R10 — 실시간성. 신설 카드와 표는 기존 data-live 교체 체계에 합류한다(S7 규약 — 폼은 마킹하지 않는다).
비 목표 (어디로 가는지 함께) :
  • 판정 · 전이 · step 매칭 로직 변경 — 기록과 로그 추가만 허용한다(Notion 페이지의 비목표 ② 를 이 문면으로 개정 · CP1 승인 후 반영 — D-10).
  • SSE 목록 배선 — S7-1. FlashPercentage 대체 원천 재탐색 — 불필요(다시 찾지 않는다 · 2026-08-31 확정 — O-1). 원장 스키마 · DDL 변경 · 운영자 알림 채널 — P5 계열 별도 기능.
  • 상세 화면 rail 자체 개편 — U3-5-a 기구현을 그대로 둔다.

드리프트 0 — 데모의 구간 판정은 §3 진리표 6행과 같은 순서 · 같은 조건이고, 남은 분의 기점은 "굽는 중 = 그 행 startedAt · 복귀 대기 = returnWaitSince()" 로 엔진과 같은 식이며(D-3), 사유 열은 detail 우선 · origin 폴백 · meta 없음이면 생략(D-5), 목록 배지는 disruptionBlocked ∧ !contactActive(D-8) 한 줄이다. 서버 구현이 이 판정의 정본이 된다.
데모가 가정한 것 · 지어내지 않은 것 :
  • 시한 값은 데모 가정이다 — 축 시한 30분 · 복귀 시한 20분(provision.execution.return-timeout 기본값) · 기준 시각 14:00:00. 실제 값은 설정에서 온다.
  • 자원 이름 · 버전, 하트비트 문구, 재시도 안내 문장은 예시 · 초안이다. 관측 문구의 실제 원천은 FlashTaskState.getUserDetail() 이고, 안내 문장은 messages.properties 키로 등록한다(§4).
  • 실패 사유 코드는 이 슬라이스가 바꾸지 않는다. RETURN_TIMEOUT 만 실제 코드이고, Task 예외 쪽은 "집행 실패" 라는 표시 문구로 두었다 — 진리표 6행은 기존 실패 표시를 유지하는 것이 규칙이다.
  • 굽기가 열린 상태의 행은 origin 없이 두었다(닫힐 때 flash-completed 가 붙는다). 그래서 사유 열이 세 갈래 — 문장(detail) · 코드(origin) · 생략(meta 없음) — 모두 화면에 나온다.
  • 축 사이 간극 — 전사 검수가 드러낸 틈을 규칙으로 확정했다 : 축 하나만 닫히고 다음 축이 아직 열리지 않은 사이는 초안 진리표의 1 · 2행 어디에도 없었다. 1b행("다음 축 착수 대기(다음 워커 주기)")으로 확정해 §3 표와 데모에 반영했다.

§8. 부산물 / 주의 / 설계 결정 D-1 ~ D-10 · Open Questions

D-1. 설정 카드 = 별도 record · 템플릿 조각

(A) 채택 — 나란한 두 카드

채택

  • 펌웨어 집행 카드와 설정 카드를 별도 record · 별도 템플릿 조각으로 두고 화면에 나란히 놓는다.
  • 공유하는 것은 상태 어휘(AxisFlashState)와 스타일(class)뿐이다.

(B) 단일 추상 카드

탈락

  • 두 phase 를 한 추상 카드가 덮는다.
  • 내용이 다르다 — 축 · Task · 전원 vs PATCH · pending · items · bond. 추상이 도메인을 가로지르며 의미를 잃는다(over-abstraction 금지).

D-2. 하트비트 = 혼합 기록

채택 — Cycle 이 주기 시각을 적고, PollFlashTaskStep 이 관측 내용을 덧쓴다. 탈락 (a) 모든 step 에 주입 : 침습이 과하다. 탈락 (b) Cycle 만 : 시각은 갱신되는데 내용이 없다. Q2 확정대로 저장은 하지 않는다.

D-3. 구간 파생의 기점 = 엔진과 같은 식

채택 — 조회 서비스가 최소 FlashContext(resolution · provider null)를 만들어 returnWaitSince() · guestReturned() 를 재사용한다. 표시와 판정이 같은 시계를 보는 것이 SSOT(Single Source of Truth — 단일 진실 출처)다. 탈락 — 계산 복제 : §1 의 표시 결함이 바로 그 복제에서 나왔다.

D-4. 전원 사건 기록

flash 는 instant 2행(차단 · 투입)이고, 투입 행의 detail 에 PowerControlResult.message(무장 outcome 포함)를 담는다. setting 재부팅은 기존 행의 arm 키로 적어 행을 늘리지 않는다 — 이미 열린 행이 있는데 별도 행을 내면 같은 사건이 두 자리로 갈라진다. 두 사유를 isPhaseLevel 에 등록해 축 상태 · 대조가 오염되지 않게 한다. 투입이 FAILED 결과(연결 불가 — 전원이 움직이지 않음)면 기록하지 않는다 — 사건이 없었기 때문이다.

D-5. note = detail 우선 · origin 폴백

문구 매핑 테이블을 새로 만들지 않는다 — detail 에 사람이 읽는 문구가 들어가는 것이 원장 규약이고, 코드가 그대로 노출되는 것은 폴백뿐이다(기술 코드 표기 허용). 판독은 ProvisioningHistory.displayNote() 도메인 메서드가 든다(기존 flashDetail 판독 관례 자리) — 조회 서비스에 JSON 파싱을 중복시키지 않는다.

D-6. 대기 사유 = BMC 무호출 파생

조회가 BMC 를 부르면 열람마다 왕복이 생기고 재기동 창에서 오류가 난다(Q2 ③ 탈락과 같은 사유). 커서 · 열린 행 부재 · lastTransitionAt · returnLimit · boardSerial == null 이라는 DB 사실만으로 문구를 만든다.

D-7. 자원이름 표기의 회귀 함정

VerifyFlashStep.sameVersion 이 원장의 flashTargetVersion 을 비교 재료로 쓴다. 표시 문자열(자원이름 (버전))을 거기에 넣으면 반영 확인이 전부 불일치로 깨진다. 그래서 이름은 별도 필드(resourceName · meta name)로 나르고 버전 재료는 불변으로 둔다. 테스트로 고정한다(§6).

D-8. 목록 표기 조건

disruptionBlocked ∧ !contactActive 일 때만 '집행 중 · 전원 꺼짐' 이다. 연결 중이면 기존 배지를 그대로 쓴다 — 굽는 중에도 접촉이 있으면 사실대로 보여야 한다. 상세 화면의 접촉 배지도 같은 조건식을 쓴다(요약 · 상세 모두 진행 상태의 같은 메서드 값 — 판정 SSOT 하나).

D-9. 재시도 안내

retryable ∧ isFirmwarePhaseFailure 일 때 기존 안내 문장에 전원 사이클 문장을 잇는다(Q3 의 가시화). 억제 가드는 넣지 않는다(Q3 ② 탈락) — 재시도가 이미 하고 있는 일을 말해 주는 것이 이 요구의 전부다.

D-10. 비목표 개정

Notion 페이지의 비목표 ② 를 "판정 · 전이 로직 변경 없음(기록 · 로그 추가는 허용)" 으로 개정한다 — CP1 승인 후 notion-sync 로 반영한다.
