§1. 현재 상태 (진단)

2026-08-06 개발 머신에서 개발 DB(localhost:3306/server_provision)와 휴지통 디렉토리 (/opt/provisioning/.soft-deleted)를 대조하다가, DB 에 대응 행이 없는 실물 약 22 GB 가 휴지통에 잔존하는 것이 발견됐다. 휴지통 화면은 "자원 없음" 을 표시한다 — 화면이 틀린 것이 아니라, 화면은 DB 의 삭제 행을 조회하는데 그 행이 0 건이기 때문이다.

※ 합계 약 22 GB. 빈 디렉토리 개수는 발견 브리핑의 실측 원장(14개)을 정본으로 적었다. 대조의 정합성은 두 방향에서 확인된다 — 빈 디렉토리의 ID 는 전부 DB 에 활성으로 존재하고(삭제 후 복원한 자원), 실물이 남은 ID 는 전부 DB 에 없다. iso 테이블의 현재 ID 가 28 · 29 · 30 · 32 로 27 · 31 을 건너뛰며 이어지므로 테이블 초기화가 아니라 개별 행의 영구삭제가 일어난 것이다.

핵심 진단 — purge_log 는 0 행이다. 이 다섯 건의 영구삭제는 감사 기록조차 남기지 않았다. 그리고 뒤에 정리한 다섯 기구(화면 · TTL 자동 정리 · 무결성 점검 · 드리프트 11종 · 미등록 마커) 중 어느 것도 이 상태를 보지 못한다. 디스크는 차는데 화면은 깨끗하다.

원인 — 코드에서 세 겹으로 규명됐다

① 과거의 영구삭제는 휴지통 실물을 정리하지 않았다 (주 원인). PurgeExecutorImpl.execute() 안에 S6-2-3 이 남긴 주석이 이 사실을 그대로 자인한다 — "여기서 휴지통 실물을 함께 정리하지 않으면 영구삭제가 끝나도 파일이 휴지통(점검 수색 제외 구역)에 영원히 남는다". 잔존 실물 다섯 건의 타임스탬프(6월 13일 ~ 6월 28일)가 전부 그 보강(2026-07 완료) 이전이고 purge_log 0 행(감사 배선 이전)과도 부합한다. 이 부분은 이미 지나간 사건이라 코드 수정으로 소급되지 않는다.

② 현행 코드도 디렉토리형 자원에는 무력하다 (살아 있는 결함).

// PurgeExecutorImpl.deleteQuietly — 현행
java.nio.file.Files.deleteIfExists(java.nio.file.Path.of(rawPath));

Files.deleteIfExists 는 비어 있지 않은 디렉토리를 지우지 못하고 DirectoryNotEmptyException 을 던진다. 그런데 BIOS 번들과 BMC 펌웨어의 trashedPath 는 개명된 디렉토리를 가리킨다 (실측 예: BIOS_BUNDLE/17/AB_CC_260628-…_3b5445ce/ 안에 파일 23개). 그 예외는 best-effort 설계에 따라 경고 로그만 남기고 삼켜진다. 재현 조건은 디렉토리형 자원의 영구삭제 매번이다 — 과거 잔재가 아니라 지금 재현되는 현행 결함이다.

③ 부모 ID 디렉토리 정리가 설계에 없다 (경미). 단일 파일 정리가 성공해도 <휴지통루트>/<자원종류>/<ID>/ 껍데기가 남고, 복원(TrashService.moveBack)도 파일만 꺼내고 껍데기를 남긴다(실측 14개). 용량은 0 이라 실해는 없으나, 운영자가 셸에서 휴지통을 열었을 때 "화면엔 없다는데 디렉토리가 잔뜩 있다" 는 혼란을 만든다.

왜 어떤 기구에도 잡히지 않는가

기구못 잡는 이유
휴지통 화면DB 삭제 행 기준 조회 — 행이 없다
TTL 자동 정리 (trash.ttl.*)DB 행 기준으로 만료를 계산 — 대상 자체가 없다
자원 무결성 점검 (quick · deep)스캔 범위가 활성 자원의 부모 디렉토리 + extra-roots — 휴지통은 설계상 "점검 수색 제외 구역"
드리프트 11종TRASH_LOST · GHOST_DB_ROW 는 모두 반대 방향(행은 있고 파일이 없음). "파일만 있고 행이 없음 × 휴지통" 조합은 어느 종류에도 없다
미등록 마커 (ORPHAN)정상 소프트 삭제는 마커를 지우므로 휴지통 실물에는 마커가 없다 + 애초에 스캔 범위 밖

휴지통을 점검 범위에서 뺀 것 자체는 타당한 결정이었다(휴지통 안 파일이 MISSING 이나 ORPHAN 으로 오탐되면 안 되므로). 그런데 그 결정의 이면 — "그러면 휴지통 안의 실물과 DB 는 누가 대사(對査)하는가" — 에 아무도 배치되지 않았다. 본 슬라이스는 그 공백의 두 갈래 중 "신규 발생을 멈추는" 쪽만 맡는다. 이미 이탈한 실물의 대사는 §11 로 넘긴다.

삭제 전 실물에서 확정한 설계 전제

개발 머신의 22 GB 는 앵커 세션이 이미 수동 정리했다(DB 참조 0 이라 앱 동작 영향 없음). 삭제 전에 확인해 둔 사실은 다음과 같고, 이것이 본 설계의 입력이다.

  • 휴지통 실물에는 마커가 없다(전수 0). 이탈 실물의 신원은 경로(종류/ID)와 파일명 rename 접미뿐이다 — 대사 기능 설계의 입력이며 본 슬라이스 범위 밖이나 기록해 둔다.
  • 파일 mtime 은 원본 업로드 시각이라 삭제 시각의 소스가 아니다.
  • 잡파일(.DS_Store)이 휴지통 곳곳에 있다 — 정리 로직이 잡파일에 관대해야 한다.
§2. 요구사항 (확정) + 비목표
  1. 실물 정리를 재귀 삭제로 교체 — 디렉토리 트리 전체를 삭제한다. 심볼릭 링크는 따라가지 않고 링크 자체만 지운다.
  2. 안전 가드 신설 — 재귀 삭제는 위험 연산이다. trashedPath 가 휴지통 루트 밖을 가리키면(DB 오염 · 변조 · 설정 변경) 절대 삭제하지 않고 경고 로그를 남긴 뒤 건너뛴다.
  3. 빈 ID 디렉토리 정리 — 영구삭제 · 복원 성공 후 <루트>/<종류>/<ID>/ 가 비어 있으면 삭제한다. 비어 있지 않으면(잡파일 · 다른 잔존물) 보존한다 — 그건 대사의 몫이다.
  4. 감사 3경로 고정 — purge_log 가 세 진입 경로(화면 영구삭제 · TTL 자동 만료 · 드리프트 휴지통 소실 해소) 전부에서 남는 배선을 통합 테스트로 못 박는다.
비 목표 :
  • 휴지통 대사 기능 — DB 삭제 행과 휴지통 실물을 대조해 "DB 에 없는 실물" 을 보고하는 기능. MK4 의 점검 커버리지 축으로 넘긴다(§11).
  • 이탈 실물의 소급 정리 — 본 수정은 신규 발생을 멈출 뿐 이미 남은 것을 지우지 않는다.
  • 잡파일 강제 정리 — .DS_Store 등이 든 ID 디렉토리는 보존한다(§4 대안 비교 참조).
  • relocate 경로 변경 — 오펀 격리 · 복원의 이동 경로 규칙은 건드리지 않는다.

§4. 도메인 규칙 (구현 명세 SSOT)
엔티티 · Value Object · Enum 신설 0. 이 슬라이스에는 영속 도메인 변경이 없다. 그래서 도메인 모델 대신 판정 규칙 자체를 SSOT 로 문서화한다 — 🎬 데모 JS 와 구현이 같은 본체를 공유해야 하므로 아래 절차표가 곧 드리프트 방지 장치다.

정리 절차 — deleteQuietly 를 대체하는 6단계 (순서 그대로)

#단계규칙실패 시
1경로 해석rawPath 를 Path 로 해석한 뒤 normalize().toAbsolutePath()InvalidPathException 이면 경고 로그 후 종료(현행 유지)
2가드TrashPolicy.getTrashRoot() 를 같은 방식으로 정규화한 것의 하위가 아니면 거부. 루트 자신도 거부[purge-executor] 휴지통 루트 밖 경로 — 정리 거부 경고 로그 후 종료
3존재 확인존재하지 않으면 종료 (멱등)실패 아님 — 조용히 종료
4재귀 삭제Files.walkFileTree + SimpleFileVisitor — visitFile 에서 파일 삭제, postVisitDirectory 에서 디렉토리 삭제. walkFileTree 는 기본이 심볼릭 링크 비추적이라 링크는 파일로서 지워지고 타깃은 보존된다경고 로그 + purge 결과 불변
5부모 정리삭제 성공 후 부모가 정확히 루트/<종류>/<ID> 깊이(루트 기준 상대 경로 이름 수 2)면 Files.deleteIfExists(parent) 1회 시도. 종류 디렉토리 · 루트는 절대 건드리지 않는다DirectoryNotEmptyException 은 조용히 보존 (보수 정책)
6결과 반영모든 실패는 경고 로그 + purge 결과 불변(best-effort 유지)—
best-effort 는 이번에 바꾸지 않는다. 근거 두 가지 — ① 파일시스템 일시 장애가 영구삭제 자체를 막으면 UX 회귀다. ② DB 와 파일시스템의 원자성은 어차피 확보 불가라, 정리 실패는 감사 로그 + 향후 대사가 받는 것이 옳은 자리다.

복원 정리 — TrashService

  • moveBack(trashedPath, originalPath) 성공 후 같은 부모 정리 규칙(5번)을 재사용한다. TrashService 도 TrashPolicy 를 이미 주입받고 있어 새 의존성이 필요 없다.
결정적 제약 — 이 슬라이스에서 가장 놓치기 쉬운 지점. 역보상 moveBackReverse(originalPath, trashedPath) 는 파일을 휴지통 안으로 되돌리는 경로인데, 내부의 moveWithRetry 는 부모 디렉토리를 만들지 않는다(실측 — moveToTrash 만 Files.createDirectories 를 호출한다). moveBack 이 ID 디렉토리를 지우고 나면 역보상이 NoSuchFileException 으로 깨진다. 따라서 moveBackReverse 에 Files.createDirectories(trashedPath.getParent()) 를 선행시킨다. 정리와 재생성은 반드시 한 커밋에서 짝으로 들어간다.

Primitive Obsession 판단 지점

정리 대상 경로는 LifecycleEntity.getTrashedPath() 가 주는 String 이다. 본 슬라이스는 해석 직후 즉시 Path 로 승격해 이후 모든 판정(가드 · 재귀 · 부모)을 Path 로만 수행한다 — 문자열 startsWith 비교로 루트 포함 여부를 판정하면 /opt/x 와 /opt/xyz 를 혼동하므로, 정규화된 Path.startsWith(Path) 를 쓴다. 필드 자체를 Value Object 로 바꾸는 것은 스키마 · 엔티티 무변경 전제를 깨므로 범위 밖이다(§8).

주의

  • 가장 놓치기 쉬운 지점은 D5 다. 부모 정리(요구 3)와 역보상 부모 재생성은 한 쪽만 넣으면 회귀가 된다.
  • 가드는 문자열 비교가 아니라 정규화된 Path.startsWith 로 한다. /opt/provisioning/.soft-deleted-old 같은 이름이 문자열 접두사로는 통과해 버린다.
  • 휴지통 루트 조회 메서드의 실명은 TrashPolicy.getTrashRoot() 다(설계 초안의 trashRoot() 는 축약 표기). 구현 · 테스트 모두 실명을 쓴다.
  • 심볼릭 링크 정책은 링크만 삭제 · 타깃 보존이다. walkFileTree 의 기본값이 그러하므로 FOLLOW_LINKS 옵션을 추가하지 않는 것이 곧 정책 준수다 — 무심코 추가하지 않도록 테스트 U7 로 고정한다.

잔존 책임 / 미루는 것

  • 이미 이탈한 실물은 소급 정리되지 않는다. 개발 머신의 22 GB 는 앵커 세션이 수동 삭제했고, 실서버에 같은 잔재가 있으면 대사 기능이 생길 때까지 수동 처리 대상이다.
  • trashedPath 의 Value Object 화(현재 String)는 엔티티 · 스키마 무변경 전제를 깨므로 범위 밖이다. 본 슬라이스는 사용 지점에서 즉시 Path 로 승격하는 것으로 대신한다(§4).
  • CLAUDE.md 수정 없음 — 새 규약 · 새 인벤토리 계열 · 새 디렉토리가 생기지 않는다.
  • 동반 수정 페이지 없음 — 화면 · 문구 변경 0. 휴지통 화면의 표시 내용은 그대로다.
