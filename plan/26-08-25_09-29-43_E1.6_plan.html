§1. 배경 · 문제 — 30초마다 한 줄씩 쌓이는 401

쉬운 말 요약

새 서버를 랙에 꽂고 전원을 켜면 진단 리눅스가 올라와 하드웨어 정보를 보고하고, 그 보고 안에 서버 관리용 통신 장치(BMC)의 주소가 들어 있다. 지금은 그 주소를 받아 적어 두기만 하고, 이후 원격 제어는 비밀번호를 두 개 차례로 넣어 보는 방식으로 이뤄진다 — 사내 표준 비밀번호를 먼저 넣고, 거부당하면 공장에서 나온 그대로의 비밀번호(그 보드의 시리얼 번호)를 넣는다. 신품 장비는 앞의 것에서 항상 거부당하므로, 30초마다 도는 펌웨어 집행 워커가 30초마다 "거부당했다" 는 로그를 한 줄씩 쌓는다. 이번 슬라이스는 진단이 BMC 주소를 알아낸 바로 그 순간에 앱이 스스로 접속해 비밀번호를 사내 표준으로 바꾸고, 한 번 성공한 비밀번호를 기억해 다음부터는 그것을 먼저 넣게 한다. 운영자가 눌러야 하는 버튼은 없고, 화면도 새로 만들지 않는다 — 서버 상세의 세부 단계 이력에 줄 하나가 늘어날 뿐이다. 표준화가 실패해도 프로비저닝은 그대로 진행된다.

유래 — R13 실기 캠페인에서 관측된 사실

이 슬라이스는 R13 실기 캠페인(2026-08-24 ~ 25, MS74-HB0 신품 보드)에서 관측된 사실에서 출발한다. 신품 BMC 는 공장 기본 자격증명(계정 admin, 비밀번호 = 보드 시리얼 11자)만 유효하다. 그런데 앱의 모든 Redfish 호출은 후보를 "사내 표준 계정 → 공장 기본" 순서로 시도하므로(BmcCredentialsResolver), 신품 장비에서는 매 호출이 표준 계정 401 을 먼저 맞고 폴백으로 넘어간다. 펌웨어 집행 워커가 30초마다 폴링하므로 30초마다 로그 한 줄("표준 계정 자격증명 거부(401)")이 쌓이고 Redfish 왕복도 두 배가 된다.

핵심 진단 — 노이즈는 로그 가독성만의 문제가 아니다. 폴링 주기마다 쓸모없는 401 왕복이 한 번씩 더 발생하고, 그 401 이 계정 lockout 정책과 만나면 실제 위험이 된다(§8).

사용자 결정과 두 축

사용자 결정(2026-08-25): BMC IP 확인 후 자격증명을 변경할 것. 이 슬라이스는 그 결정의 설계 · 구현이며 축은 둘이다.

  1. 계정 표준화(본 기능) — 진단이 BMC IP 를 수집한 뒤 Redfish AccountService 로 비밀번호를 사내 표준으로 교체한다.
  2. 성공 자격 캐시(단기 처방 겸 보완) — 성공한 자격증명을 기억해 다음 호출부터 그것을 먼저 시도한다. 표준화 이전 장비와 혼재된 환경에서도 노이즈가 사라진다.

근거를 셋으로 푼다.

  1. R13 이후 진단은 등록 즉시 무인으로 돈다. 계정 표준화가 운영자 액션이면 "등록만 하면 준비 끝" 이라는 자동화 결이 여기서 끊긴다.
  2. 신원 위험의 역전 — 되돌리기 어려운 조작을 무인으로 하는 것이 걱정되지만, 실제 위험(주소 드리프트로 남의 BMC 를 만지는 사고)은 시간이 지날수록 커진다. 수집 직후는 BMC IP 와 보드 시리얼이 같은 진단 보고서에서 방금 나온 순간이라 드리프트 확률이 최소다. 운영자 버튼은 며칠 뒤 눌릴 수 있고 그 사이 DHCP 재배정이 일어날 수 있다 — 자동이 오히려 안전한 쪽이다.
  3. 실패의 하방이 얕다 — 표준화가 안 되어도 폴백 체계가 기능을 지탱한다(fail-soft). 무인 시도가 실패해서 잃는 것은 로그 한 줄뿐이다.

비채택 1 — 운영자 액션(서버 상세 버튼) : 신품 N 대 도입 시 N 회 클릭 노동이 들고, "아직 안 한 게스트" 를 화면이 알려줘야 하므로 상태 추적(컬럼 또는 집계)이 따라온다. 위 2의 드리프트 위험도 더 크다.
비채택 2 — 워커 sweep(FirmwareFlashWorker 방식) : "미표준화 게스트" 선별에 상태 컬럼(DDL)이 필요하거나, 매 주기 전 게스트에 Redfish GET 을 던져야 한다. 30초 GET 폭탄과 DDL 모두 이 기능의 크기에 비해 과하다.

재시도 정책 — 이벤트당 1회 시도. 일시 실패(연결 불가 등)는 다음 진단 재실행(재부팅 · 재등록) 때 자연 재시도된다. 그 사이 노이즈는 D-3 캐시가 억제한다. 전용 재시도 큐를 두지 않는 이유는, 실패의 대부분이 사람이 개입해야 풀리는 종류(제3 비밀번호)거나 다음 부팅에 자연 회복되는 종류(일시 불통)라 큐가 해결하는 구간이 얇기 때문이다.

비동기 배선의 함정 회피 — @Async 는 Spring proxy 경유 호출에서만 동작하므로(IsoVerificationLauncher 선례 · E2-2 의 FirmwareFlashCycle 분리 선례), 리스너 진입점(BmcAccountStandardizationLauncher)과 트랜잭션 본체(BmcAccountStandardizationService)를 별도 빈으로 분리한다.

D-2. 표준화 사다리 — idempotent 절차

#관측판정원장
0표준 비밀번호 미설정(env)시도 생략없음(로그 1줄)
1표준 자격 GET 200이미 표준 — no-op없음
2표준 401 → 공장 기본 GET 200신원 대조 → ETag → PATCH → 반영 확인SUCCEEDED
3표준 401 → 공장 기본 401알 수 없는 자격 — 운영자 개입 필요FAILED
4연결 불가 · 412 · 그 외일시 상태 — 다음 진단 기회없음(로그)

판정 기준은 시도 순서가 아니라 "어느 자격으로 열렸는가" 다. D-3 캐시는 일반 호출의 후보 순서를 재정렬하므로, 순서에 기댄 판정("첫 GET 200 = 이미 표준")은 캐시가 공장 기본을 앞세운 순간 오판이 된다. 그래서 사다리는 폴백 · 캐시를 우회해 두 자격을 명시적으로 직접 시도한다 — 사다리의 목적 자체가 "어떤 자격이 유효한가" 의 판별이므로 순회 규칙에 맡기지 않는다. 표준 자격으로 열리면 1행, 공장 기본으로 열리면 2행이다. 위 🎬 데모의 판정도 같은 기준을 쓴다.

1행이 이 사다리를 idempotent 로 만든다 — 진단이 재실행될 때마다 이벤트가 다시 오지만, 이미 표준화된 게스트는 GET 한 번으로 조용히 끝난다. 그래서 "표준화 완료" 상태를 DB 에 저장할 필요가 없다(무상태 판정). 성공 원장 행도 남기지 않는다 — 매 진단마다 성공 행이 쌓이면 이력이 노이즈가 된다. 최초 전환(2행)만 기록한다.

2행 절차 — ① 신원 대조(D-5) ② Accounts 목록에서 admin 계정 URI 확인 ③ 그 계정 GET 으로 fresh ETag 채집 ④ PATCH + If-Match + 새 비밀번호 → 204 ⑤ 반영 확인 — 표준 자격으로 GET 1회. ⑤는 E2-2 F-1 교훈의 적용이다: 반영 확인은 "바꿨다는 응답" 이 아니라 "새 자격으로 실제로 열린다" 가 유일한 증거다. ⑤ 실패 시 FAILED 를 기록해, 비밀번호가 어중간한 상태일 수 있음을 운영자에게 알린다.

3행과 4행의 구분 기준은 자연 회복 가능성이다. 둘 다 401 인 상태는 사람이 비밀번호를 알아내 개입해야만 풀리므로 원장 FAILED 로 화면에 노출한다. 연결 불가는 BMC 재기동 · 망 문제처럼 시간이 풀어주는 상태라 로그만 남긴다. 412(ETag 경합)도 4행이다 — 동시 사다리 두 개가 겹친 경우 한쪽이 밀리는 정상 경합이며, 다음 기회에 1행(no-op)으로 수렴한다.

FAILED 원장 행은 ProvisioningProgress 의 실패 신호(failedAt)를 건드리지 않는다 — BMC 계정은 부가 기능이라 프로비저닝 진행을 막을 이유가 없다(BmcCredentialsResolver 가 fail-fast 를 두지 않는 것과 같은 철학).

불가침 — 비밀번호 값은 로그 · 원장 statusMeta · 예외 메시지 어디에도 싣지 않는다. env provision.bmc.password 주입 계약을 그대로 유지한다.

D-3. 성공 자격 캐시 = global/redfish 인메모리, 키 = 보드 시리얼

채택 — BmcCredentialsMemory(신규 컴포넌트, ConcurrentHashMap<String, String> — boardSerial → 성공한 후보 source). BmcCredentialsFallback.attempt 가 성공 시 기억하고, 시도 전에 후보 목록을 재정렬(기억된 source 를 앞으로)한다. 전원 제어 · 펌웨어 집행 등 폴백을 지나는 일반 호출이 자동 수혜를 본다(계정 표준화 사다리는 자격의 판별이 목적이라 캐시를 우회한다 — D-2).

키를 boardSerial 로 하는 이유 — BMC IP 는 DHCP 재배정으로 바뀔 수 있지만 보드 시리얼은 그 장비의 안정 식별자다. RedfishTarget 이 이미 boardSerial 을 담고 있어 global 층에서 도메인 id 없이 키를 얻는다. boardSerial 이 null 인 호출(진단 전)은 캐시를 적용하지 않는다 — 그 경우 후보가 표준뿐이라 노이즈도 없다.

비채택 1 — DB 영속(GuestServerDetail 컬럼) : DDL 이 필요한데, 재기동 후 잃는 것이 "첫 호출 1회의 401" 뿐이라 영속의 가치가 낮다. 실 DB ALTER 대기 행렬(ES-2 · E2-1-a)에 하나 더 얹을 이유가 안 된다.
비채택 2 — BmcCredentialsResolver 에 캐시 내장 : resolver 는 "설정에서 후보를 산출한다" 는 무상태 단일 책임을 유지한다. 기억과 재정렬은 순회 규칙의 소관이므로 fallback 쪽이 자연스럽다.
비채택 3 — 캐시 없이 표준화만 : 표준화 실패 · 미완 게스트가 남는 동안 30초 401 이 지속된다. 사용자 브리핑이 캐시를 "단기 처방 겸 보완" 으로 명시 요구한 이유가 이것이다.

자기 갱신 성질 — 표준화 성공의 반영 확인(⑤)이 표준 자격으로 성공하므로, 그 순간 캐시가 "공장 기본" → "표준" 으로 스스로 갱신된다. 별도 무효화 코드가 없다.

D-4. 원장 기록 = 기존 IPMI_SETTING step 재사용 (DEC-11 개정)

채택 — 표준화의 최초 전환 성공(SUCCEEDED)과 운영자 개입 필요 실패(FAILED)를 ProvisioningHistoryRecorder.recordInstant 로 IPMI_SETTING(DIAGNOSE_LINUX phase) instant 행에 남긴다. statusMeta 에 계정명 · 판정 사유를 싣는다(비밀번호 금지).

배경을 푼다. setup_step.step_code 는 MySQL ENUM 컬럼이다. Java enum 에 새 상수를 추가하면 MODIFY COLUMN DDL 이 강제된다 — E1-1 이 정확히 이 함정("Data truncated" 500)을 기록했다. 한편 ProvisioningPhaseStep.IPMI_SETTING 은 "ipmitool 로 커스텀 정보를 저장하는 단계" 로 예약됐다가 DEC-11(2026-07-12)로 보류된 상수다 — 소비자가 없어 실 원장에 이 step 행이 존재하지 않는다. BMC 계정 표준화는 의미상 "진단 중 BMC(IPMI) 측 설정 작업" 이므로 이 상수의 첫 실소비자로 정합하고, 기존 ENUM 값에 이미 있으므로 DDL 0 이 유지된다. Javadoc 은 개정한다(DEC-11 보류 문구 → E1.6 이 첫 소비자, 원 용도 재개 시 공존).

비채택 1 — 새 상수(BMC_ACCOUNT_STANDARDIZING 류) : DDL 이 강제된다(샌드박스 + 실 DB, ALTER 권한 계정 필요). 이름 정합성의 이득이 실 DB ALTER 대기 행렬 추가 + 25자 컬럼 한계 압박보다 작다.
비채택 2 — 로그만 : 3행(운영자 개입 필요)이 화면에 닿지 않는다. 서버 상세의 세부 단계 이력 표는 step 이름과 상태 배지를 그대로 출력하므로, IPMI_SETTING 행은 화면 변경 0 으로 자동 노출된다.

D-5. 신원 확인 — 이중 증명 (PATCH 직전)

이 조작이 두려운 이유는 하나다 — BMC 주소는 진단이 한 번 읽은 스냅샷이고, 갱신 경로가 없으며, DHCP 고정 예약도 없다. 그 주소에 지금 다른 게스트의 BMC 가 앉아 있으면 남의 장비 비밀번호를 바꾸게 된다.

  • 증명 1(내재) — 공장 기본 비밀번호가 곧 그 보드의 시리얼이다. 우리가 이 게스트의 시리얼로 인증에 성공했다는 사실 자체가 "응답한 BMC 는 그 보드에 붙어 있다" 는 증명이다. PATCH 는 이 인증 성공(2행) 뒤에만 진행된다.
  • 증명 2(명시) — 그래도 PATCH 직전 Chassis/Self 의 Oem 보드 시리얼(GBTChassisOemProperty."Board Serial Number" — E2-2 D-11 이 확정한 원천)을 GET 한 번으로 대조한다. 불일치면 즉시 중단하고 FAILED 를 기록한다.

"되돌릴 수 없는 조작 직전에는 보드 시리얼로 신원을 확인한다" 는 원칙(E2-2 D-11)의 일관 적용이며 비용은 GET 한 번이다.

증명 1이 있는데 2가 필요한가에 대한 자기 반박 — 시리얼 인증만으로 충분해 보이지만, 원칙에 예외를 만들면 다음 사람이 "여기는 왜 안 하지" 를 고민하게 된다. 비용이 GET 한 번으로 싸므로 일관성을 산다.

D-6. 미실측 관용 — PasswordChangeRequired (C5)

Redfish 표준에는 신품 첫 접속 시 비밀번호 변경을 강제하는 PasswordChangeRequired 메커니즘이 있다(강제 시 대부분의 GET 이 403). 이 보드의 강제 여부는 미실측이다(C5 — 실측 장비가 이미 전환된 상태였다). 설계는 이렇게 관용한다: 403 등 미지 응답은 사다리 4행(일시 상태 · 로그)으로 흡수하고, 실기에서 관측되면 그때 사다리에 403 갈래를 정련한다. T3 체크리스트에 실측 항목으로 적립한다. 미리 403 처리 분기를 만들지 않는 이유는, 계약을 모르는 채 짠 분기는 추측 코드이고 이 프로젝트는 실측 스키마를 따르기 때문이다(E2-R 교훈).

D-7. 배치 — global 계약 / execution 오케스트레이션

E2-2 CP4 검수("engine 패키지가 어질러져 호출 흐름이 안 보인다")의 교훈을 적용해, 신규 파일의 자리를 계열로 명확히 한다.

com.example.serverprovision/ ├── global/redfish/ (도메인 무관 Redfish 계약) │ ├── RedfishAccountService.java (신규) 목록 GET · 계정 GET(ETag) · 비밀번호 PATCH(If-Match) │ ├── BmcCredentialsMemory.java (신규) boardSerial → 성공한 후보 source │ ├── RedfishClient.java (수정) ETag 동반 GET · If-Match PATCH 프리미티브 2개 │ └── BmcCredentialsFallback.java (수정) 기억 · 재정렬 배선 └── execution/ ├── event/BmcEndpointDiscoveredEvent.java (신규) record — serverId ├── engine/diagnose/DiagnoseLinuxExecutor.java (수정) bmcIp 적재 시 이벤트 발행 ├── service/BmcAccountStandardizationService.java (신규) 사다리 본체 · @Transactional · 원장 ├── service/BmcAccountStandardizationLauncher.java (신규) @Async @TransactionalEventListener └── enums/ProvisioningPhaseStep.java (수정) IPMI_SETTING Javadoc 개정

D-8. 동시성 · 멱등 (락을 두지 않는 근거)

같은 게스트의 진단 보고가 겹치면 이벤트가 두 번 발행되어 사다리 두 개가 동시에 돌 수 있다. 사다리는 idempotent(1행)이고, PATCH 는 If-Match 라 경합 시 한쪽이 412 로 밀린다 — 밀린 쪽은 4행으로 흡수되고 다음 기회에 1행으로 수렴한다. 이 수렴 구조가 있으므로 분산 락 · synchronized 를 두지 않는다(과설계).

§4. 스코프 제외 (비 목표 + 행선지)
비 목표 :
  • 운영 계정 신설(POST Accounts) — admin 유지가 현 표준이다. 필요해지면 별도 슬라이스.
  • lockout 정책 대응 — 연속 401 로 계정이 잠기는 시나리오. 캐시가 401 횟수 자체를 줄이므로 우선순위가 낮다. 실기 관측 시 승격한다.
  • 표준화 현황의 화면 상세화(집행 현황 카드 등) — E2-4(집행 현황 상세화) 소관. 이 슬라이스는 기존 세부 단계 이력 표 자동 노출까지만이다.
  • DHCP 고정 예약(주소 드리프트의 근본 해결) — pxeinfra(E1-I 계열) 소관.
  • Redfish 세션 인증 전환 — Basic 우선 결론(E1.5)을 유지한다.

2 — 실기 검증은 E 단계 방침대로 CP7 에서 일괄한다. 2행을 실증하려면 아직 공장 기본 상태인 신품이 있어야 한다. 표준화가 이미 끝난 장비로는 1행(no-op)만 실증되므로, 그 한계를 report 에 명시한다.

3 — 제3 비밀번호 게스트가 방치되면 30초 폴링이 계속 401 을 두 번씩 만든다. 캐시는 성공만 기억하므로 이 경우엔 무력하다. 실기에서 잠금이 관측되면 "FAILED 게스트는 폴링 후보에서 제외" 를 후속 정련으로 올린다(§4 스코프 제외의 lockout 항목과 연결된다). 데모의 시나리오 ③ 에서 폴링을 반복해 보면 이 누적을 눈으로 확인할 수 있다.

4 — 원장 IPMI_SETTING 행은 커서가 이미 다음 phase 로 전진(또는 종단)한 뒤에 비동기로 append 될 수 있다 — DiagnoseLinuxExecutor 가 커밋 시점에 커서를 옮기고 표준화는 그 커밋 뒤에 돌기 때문이다. ProvisioningHistoryRecorder.recordInstant 는 append-only 라 커서를 건드리지 않아 진행 역행은 없지만, 세부 단계 이력 표의 정렬 기준에 따라 행 순서가 어색하게 보일 수 있다 — CP2 착수 시 화면 정렬을 확인한다.

§9. CP5 검증 계획 (하네스) + Verification

화면이 없는 슬라이스이므로 E 단계 예외를 적용해 브라우저 대신 mock-redfish 하네스로 검증하고, 결과가 닿는 서버 상세의 세부 단계 이력만 화면으로 확인한다. 항목 식별자는 CP5 진입 시 확정하되 골격은 다음과 같다.
