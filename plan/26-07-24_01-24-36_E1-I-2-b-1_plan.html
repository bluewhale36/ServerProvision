§1. 현재 상태 (진단)

E1-I-2-a 의 교체는 순수 덮어쓰기다 — 새 파일이 원자적 스왑으로 옛 파일을 지운다. 새 버전에서 예상치 못한 문제(부팅 실패·버그)가 나도 이전 버전으로 되돌릴 수단이 없다. a 는 이 공백을 알고 seam 을 예약해 뒀다:

// DiagnosticAssetReplaceService.replace — 현재(a)
requireServingRoot() → guards → target = slot.resolve(root)
  → [스왑: temp 완성 → ATOMIC_MOVE] → sealOne(재봉인)
//                    ↑ b-1 이 이 앞에 archive(현재 파일 → 버전 저장소)를 끼운다 (Javadoc 이 예약한 seam)
능력있음비어 있음 (이 슬라이스가 채움)
교체·재봉인E1-I-2-a (원자적 스왑 + sealOne)—
이전 버전 보존—없음 — 교체 즉시 옛 파일 소실. 롤백 불가
보존/복원/FIFO 인프라global/trash (moveWithRetry·relocate 원자 이동 / PurgeLog DB 감사로그 / DriftReport FIFO prune / ResourceKey 키 / BaseTimeEntity) — 전부 성숙이걸 범용 버전 저장소로 조립해 재사용
이 자산 영역의 DB 엔티티없음 (E1-I-1/2-a 는 엔티티 무 — DEC-14)AssetVersion 이 첫 엔티티 — 6·7·9 단계(Repository·Entity·DDL)가 되살아난다
핵심 진단 — "교체 후 문제 시 롤백" 요구를 위해 파일 버전 이력이 필요하다. 이걸 진단 자산 전용으로 짜지 않고 도메인 무관 저장소(global/history)로 만들어, 교체 시 옛 버전을 아카이브하고 자산별 최근 N개만 남긴다. dhcpd/tftp(E1-I-3)는 키만 바꿔 이 저장소를 그대로 재사용한다 — 이게 확장성의 실체다. 롤백 UI·복원 액션은 E1-I-2-b-2이고, 이 슬라이스는 저장소 + 아카이브 배선까지다.
§2. 요구사항 (확정) + 비목표
  1. 범용 버전 저장소 global/history — AssetVersionKey(category, name)(최상위 record) · AssetVersion 엔티티(첫 DB 엔티티) · AssetHistoryService(archive/list/openVersion/prune). 도메인을 모른 채 "임의 파일의 버전을 키로 보존·조회·정리"만 안다.
  2. 비 web-served 이력 루트 — provision.asset.history.root(PROVISION_ASSET_HISTORY_ROOT, 기본 /opt/provisioning/.asset-history). trash.root·orphan.quarantine.root 미러. allowed-roots 에 넣지 않고 pxe.assets.root 아래도 아니다 — 옛 버전이 게스트에 서빙되거나 reconciliation 스윕에 잡히지 않게.
  3. 교체 시 자동 아카이브(seam 이행) — DiagnosticAssetReplaceService.replace 의 스왑 앞에 archive(key, 현재 파일) 삽입. 순서 = archive → 스왑 → sealOne → prune. 현재 파일이 존재할 때만(최초 생성 교체는 아카이브할 옛 버전 없음).
  4. 보존 = 자산별 최근 N개 FIFO — provision.asset.history.retention-count(기본 3). 아카이브 직후 그 (category,name) 의 버전이 N 초과면 가장 오래된 것부터 삭제(파일 + 행). DriftReport prune(count−N → page oldest → deleteAll) 미러.
  5. 아카이브 실패 = 교체 중단(불가침) — 옛 버전을 보존하지 못하면 덮어쓰지 않는다(500). "롤백 가능하도록 보존" 이 목적이므로, 보존 실패 상태로 스왑을 진행해 옛 버전을 소실시키지 않는다.
비 목표 :
  • 롤백 UI · 복원(활성화) 액션 — E1-I-2-b-2. 저장소의 openVersion(key,id)(버전 바이트를 여는 능력)은 b-1 에 두되, 복원(그 버전을 스왑해 되살리고 재봉인)의 진단 특화 배선은 b-2. 대시보드 버전 목록도 b-2.
  • dhcpd/tftp 적용 — E1-I-3. 저장소는 범용이라 그때 키(category="PXE")만 바꿔 재사용. 활성화가 도메인별로 갈리면 그 시점에 SPI 화(OrphanRecoverySpi 선례).
  • 시간 기반 TTL — 이번엔 개수 기반(최근 N). 기간 만료는 필요 시 후속(TrashSettings/TTL 워커 선례 있음).
  • 최초 원본(build-assets.sh 산출본) 사전 아카이브 — 안 한다. 첫 교체 시 그 원본이 v1 으로 아카이브된다(원본 재생성은 빌드 스크립트로 가능).
  • DB 설정 화면(보존 개수 UI) — config property 로 충분. TrashSettings 형 DB 설정은 과잉(필요 시 후속).
🎬 미리보기 — 버전 저장소 시뮬레이터 (아카이브·FIFO·복원 preview)

한 자산(modloop-lts)을 반복 교체하며 옛 버전이 저장소에 쌓이고 최근 N개(기본 3)만 남는 것을 본다. 「교체」마다 현재 활성본이 아카이브되고 활성본은 새 버전이 된다. N 을 넘으면 가장 오래된 버전이 FIFO 로 사라진다. 「롤백(preview)」은 b-2 미리보기 — 현재 활성본을 아카이브한 뒤 고른 버전으로 되돌린다(이 슬라이스는 저장소만, 활성화 배선은 b-2).

보존 N :
modloop-lts 활성본
버전 저장소크기해시아카이브 시각 (최근 → 오래)
↑ 롤백은 여기서 버전을 골라 되돌린다(b-2). 활성본은 저장소에 없다 — 다음 교체 때 아카이브된다.
드리프트 0 — 시뮬레이터의 교체 순서(archive → 스왑 → sealOne → prune)와 FIFO(count−N 초과분 오래된 것부터 삭제)는 §4 서버 규약과 1:1 이다. 아카이브 실패 시 스왑을 진행하지 않는다(옛 버전 소실 방지, 요구사항 5). 활성본은 저장소에 없고 다음 교체 때 v(n)으로 들어간다.
§3. URL / 데이터 흐름
새 엔드포인트 없음 — 아카이브는 교체(POST /{slot}/replace) 내부 동작이다. 이 슬라이스는 뷰·컨트롤러를 추가하지 않는다(롤백 UI 는 b-2). 순수 백엔드 인프라 + 배선.

교체 흐름 (b-1 적용 후 — 회색이 b-1 추가분)

POST /system/diagnostic-asset/{slot}/replace   (multipart: file)
  root = requireServingRoot()          (409 서빙 비활성)
  guards: replaceable(409) · 비어있지 않음(400)
  target = slot.resolve(root)          (현재 활성 파일)
  ┌─ b-1 ──────────────────────────────────────────────────────────────
  │ if Files.exists(target):
  │     historyService.archive(AssetVersionKey("DIAGNOSTIC", slot.filename()), target)
  │       ├ copy target → /DIAGNOSTIC//-   (COPY_ATTRIBUTES)
  │       ├ sha256 + size 계산 · 0644
  │       ├ AssetVersion 행 저장(category·name·archivedRelPath·sha256·size·archivedAt)
  │       └ prune(key): 그 (category,name) 버전 count−N 초과 → 오래된 것부터 파일+행 삭제
  │     아카이브 IO 실패 → AssetVersionArchiveFailedException(500) — 여기서 중단(스왑 안 함)
  └────────────────────────────────────────────────────────────────────
  스왑: temp 완성 → Files.move(ATOMIC_MOVE, REPLACE_EXISTING)   (a 기존)
  sealOne(slot, root)                                          (a 기존)
  → redirect (PRG)
아카이브 = copy (move 아님) — 아카이브 시점의 현재 파일은 아직 활성본이라 저장소로 복사만 한다(활성본은 직후 스왑이 덮어쓴다). TrashService 는 move(삭제 격리)지만 여기는 활성본을 남겨야 하므로 copy.

AssetVersion — 엔티티 (PurgeLog 감사로그 미러, append-only)

@Entity @Table(name="asset_version", indexes=@Index(name="idx_asset_version_key", columnList="category, name, id"))
@Getter @NoArgsConstructor(access=PROTECTED)
public class AssetVersion {              // BaseTimeEntity 상속 안 함 — append-only 라 updatedAt 무의미(PurgeLog 선례)
    @Id @GeneratedValue(strategy=IDENTITY) Long id;   // 삽입 순서 = 아카이브 순서(단조·유일) → 정렬/FIFO 키. 별도 seq 불요

    @Column(nullable=false, length=255) String name;
    @Column(name="archived_rel_path", nullable=false, length=512) String archivedRelPath;  // historyRoot 기준 상대
    @Column(nullable=false, length=64)  String sha256;
    @Column(name="size_bytes", nullable=false) long sizeBytes;
    @Column(name="archived_at", nullable=false, columnDefinition="TIMESTAMP(6)") Instant archivedAt;
    @Builder ...; public static AssetVersion of(AssetVersionKey key, String relPath, String sha256, long size, Instant at) {...}
}

Optional archive(AssetVersionKey key, Path currentFile);  // 존재 시 복사·기록·prune. 부재면 empty

FIFO 보존 — DriftReport prune 미러

// prune(key): 자산별로 최근 N개만.
long over = repo.countByCategoryAndName(cat, name) - retentionCount;   // 초과분
if (over > 0) {
    Page oldest = repo.findByCategoryAndNameOrderByIdAsc(cat, name, PageRequest.of(0,(int)over));
    oldest.forEach(v -> Files.deleteIfExists(historyRoot.resolve(v.archivedRelPath())));  // 파일 먼저
    repo.deleteAll(oldest.getContent());                                                   // 행 삭제
}
// retentionCount = @Value("${provision.asset.history.retention-count:3}")  (reconciliation.report.retention-count 선례)

결정 비교

(1) DB 엔티티 — 채택

  • 버전 로그는 관계형(순서·개수·prune 쿼리) — PurgeLog 선례
  • FS 사이드카 메타는 순서/정리가 clunky

(2) id(IDENTITY) 순서 — 채택

  • 단조·유일 = 아카이브 순서. 별도 seq 컬럼·max+1 쿼리·경합 회피

(2 대안) per-asset seq — 탈락

  • max+1 조회 + 동시 아카이브 경합. id 로 충분

(3) 아카이브 실패 = 중단 — 채택

  • 보존 못 하면 덮어쓰지 않음(옛 버전 소실 방지)
  • 요구 "롤백 가능하도록 보존" 정합

(3 대안) WARN 후 진행 — 탈락

  • 보존 없이 스왑 = 그 교체는 롤백 불가(요구 위반)

(4) archived_at 명시 컬럼 — 채택

  • append-only 라 BaseTimeEntity updatedAt 무의미(PurgeLog 선례)

(5) 이력 루트 = 비 web-served·비 allowed-roots — 채택

  • 옛 버전이 게스트 서빙·스윕에 안 잡히게(trash.root 미러)

잔존 책임 · 주의 (정직 기록)

  • 활성화(복원 살리기)는 b-1 에 없다 — 저장소의 openVersion(버전 바이트 열기)까지가 b-1. 그 버전을 스왑해 되살리고 재봉인하는 진단 특화 복원과 목록 UI 는 b-2. b-2 는 a 의 스왑 로직을 재사용(복원 = 현재 archive → 버전 스왑 → sealOne)하므로, 필요하면 b-2 에서 replace 의 스왑을 작은 재사용 메서드로 추출한다(지금은 미추출 — 갈라지는 시점에).
  • 첫 DB 엔티티 — DDL·validate 규율 — ddl-auto=validate라 asset_version 테이블을 ddl/ 수동 DDL 로 만들고 schema.sql에 반영해야 기동이 통과한다. ALTER 권한 계정 필요(claude_code 불가) — 적용은 사용자 몫, CP4 에서 DDL 산출 + SHOW CREATE 검증.
  • 저장 비용 — 자산별 최근 N개(기본 3). modloop 198MB × 3 ≈ 600MB/자산. 이력 루트 디스크는 자산 루트와 별개 볼륨이어도 됨(설정 분리).
  • 이력 루트 격리 전제 — allowed-roots 에 넣지 않고 pxe.assets.root 아래도 아니게 배치(§2-2). 넣으면 옛 버전이 게스트 서빙되거나 reconciliation ORPHAN 오탐. SecurityPropertiesValidator 변경 불요(웹 서빙 allow-list 만 검증).
  • category 는 도메인 공급 — 진단 = 상수 "DIAGNOSTIC"(replace 서비스가 공급). enum 의 Category(NETBOOT/CONFIG/AGENT — 대시보드 분류)와는 다른 개념이라 혼동 주의 — 버전 이력 category 는 도메인 그룹 1개.
  • sha256 유틸 중복 — sha256File 이 DiagnosticAssetIntegrityService private 로 존재. 저장소도 필요 → 공용 유틸로 승격(예: global/… static)하거나 저장소에 소형 재사용. CP4 에서 승격 결정(중복 금지 원칙).
