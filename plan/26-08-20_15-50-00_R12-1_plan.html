§1. 현재 상태 (진단)

이 슬라이스가 지금 필요한 경위

BIOS 자원이 지금과 같은 "벤더 패키지 번들" 형태로 등록되도록 설계된 이유는 집행 방식의 원안에 있다. 2026-08-01 의 E2-R 펌웨어 flash 조사 시점에 확정돼 있던 집행 원안은 가상 USB(FAT32 이미지)를 만들어 서버에 붙이고 UEFI Shell 에서 벤더 flash 유틸리티를 실행하는 것이었다. 그 방식은 파일 하나만으로 성립하지 않는다 — flash 유틸리티(AfuEfix64.efi) · 실행 스크립트(f.nsh) · 롬 파일이 한 디렉토리에 함께 있어야 UEFI Shell 이 그 트리를 그대로 실행할 수 있기 때문이다. 그래서 관리 자원의 파일 계약이 "디렉토리 트리 한 벌" 로 정해졌고, 업로드 화면도 폴더 · 압축 · 단일 파일 세 모드를 갖게 되었다.

그 전제가 2026-08-18 ~ 19 의 BMC Redfish 실측(Notion E0-4 계열)에서 무너졌다. UpdateService 의 SimpleUpdate 로 BIOS(image.RBU, 47 초 ~ 2 분 22 초)와 BMC(.ima_enc, 7 분 37 초)의 실집행이 모두 성공했다. 유일하게 남아 있던 결격 — 로고 변경본이 반영되지 않는 현상 — 도 조사 결과 "로고가 들어 있지 않은 파일을 구운 것" 으로 판명됐다(구운 파일과 정본의 SHA-256 이 동일). 이후 벤더가 제공한 로고 포함 RBU 를 수령해 그 결격도 해소됐다. 2026-08-20 사용자가 가상 USB 경로를 철폐하고 Redfish 를 최종 집행 수단으로 확정했다.

집행이 Redfish 한 갈래로 좁혀지면 서버로 보낼 것은 펌웨어 파일 한 개뿐이다. 유틸리티도 스크립트도 게스트에 올릴 필요가 없다. 따라서 관리 자원의 파일 계약을 "번들" 에서 "펌웨어 파일 1 개" 로 내리는 것이 R12 캠페인이며, 그 첫 슬라이스가 BIOS 를 다루는 R12-1, 뒤이어 BMC 를 다루는 것이 R12-2 다.

등록 화면은 이 네 경로를 탭으로 나눠 보여주고 uploadMode 값을 hidden 으로 실어 보낸다. 업로드 세 경로는 2 단 핸드셰이크를 쓴다. 먼저 POST /management/bios/{boardId}/upload-intent 가 JSON 으로 하드 조건(보드 존재 · 활성 (board, version) 중복 · 대상 디렉토리 정책)을 검사하고 1 회용 토큰을 발급한다. 그 다음 POST /management/bios/{boardId}/upload 가 X-Upload-Token 헤더와 함께 multipart 로 바이트를 싣는다. 서버는 모드별로 페이로드를 전개한 뒤 BundleEntrypointDetector 가 벤더별 전략으로 진입점을 자동 탐지하고, BundleManifestService 가 manifest 를 집계하며, 해시 충돌이 있으면 nudge 세션을 발급하고, 마지막에 2-phase save 와 마커 기록을 수행한다. 네 번째 경로인 POST /management/bios/{boardId}/register-existing 은 핸드셰이크 없이 단발 POST 로 이미 채워진 트리를 claim 한다.

엔티티 BoardBIOS 는 이 트리 전제를 그대로 담고 있다 — treeRootPath · entrypointRelativePath · manifestHash · markerSignature · fileCount · totalBytes. 업로드 용량 상한은 provision.upload.max-file-size=15GB 이므로 64 MB 짜리 RBU 는 설정 변경 없이 통과한다.

파일 형식 검사가 어디에도 없다. 압축 업로드에 accept=".zip" 이 붙어 있을 뿐이고, 폴더 업로드와 단일 파일 업로드는 제한이 전혀 없다. 이번 슬라이스는 이 자리를 벤더별 파일 정책으로 채운다(§8 D3 · D10) — GIGABYTE 보드는 .RBU 확장자만 허용하고 PFR 사본 파일 두 개를 막으며, ASUS · FUJITSU 보드는 제약을 두지 않는다.

비교 대상 — ISO 등록의 단일 폼 방식 (실측)

같은 저장소 안에 이미 다른 방식의 선례가 있다. ISO 등록은 탭이 없고 폼 하나에 경로 한 칸과 선택적 파일 한 칸만 둔다. IsoUploadController.uploadIso 는 파일 파라미터를 required=false 로 받고, 파일이 실제로 있을 때만 X-Upload-Token 을 소비한다. IsoRegistrationService.prepare 는 hasFile 분기로 갈라져 파일이 있으면 저장하고, 없으면 Files.isRegularFile(target) 로 그 경로의 파일이 실재하는지 확인한 뒤 등록한다. 경로 해석은 IsoPathResolver.resolve 가 맡아 / 로 끝나는 경로에는 업로드 파일명을 이어 붙이고, 파일 경로면 그대로 쓴다. 사용자는 이 방식을 BIOS 에도 그대로 쓰기로 결정했다(§8 D2).

§2. 요구사항 (확정) + 비목표

사용자 지시 원문은 "기존의 bundle/zip upload 방식을 제거하고 파일 확장자를 검사한다" 였다. 2026-08-20 CP1 검수에서 등록 UX 를 ISO 방식으로 통합하는 결정과 도메인 전역 확장자 검사를 철회하는 결정이 더해졌고, 이어 구현 중에 정책을 벤더별로 나누면서 GIGABYTE 한정 확장자 요구로 다시 들어왔다(§8 D3 · D10 · 정정 이력). 확정된 요구는 다음 넷이다.

  1. 폴더 · 압축 업로드 모드 제거. 가상 USB 조립용 패키지를 서버에 쌓아 둘 이유가 없어졌다.
  2. 등록 UX 를 단일 폼으로 통합한다. 경로 한 칸과 선택적 펌웨어 파일 한 칸만 둔다. 경로가 / 로 끝나면 디렉토리로 보고 업로드 파일명을 이어 붙이고, 파일 경로면 그대로 쓴다. 업로드 파일이 있으면 그 경로에 저장하고, 없으면 그 경로에 이미 있는 파일을 등록(claim)한다. 별도의 "기존 디렉토리 등록" 기능은 폐지한다 — /register-existing 엔드포인트 · 탭 UI · BiosRegisterExistingRequest 가 함께 사라진다.
  3. 검사는 벤더별 파일 정책으로 한다. 정책은 두 축이다 — 금지 파일명과 허용 확장자. GIGABYTE 는 .RBU 확장자만 허용하고 PFR1.RBU · PFR2.RBU(둘 다 대소문자 무시)를 막으며, ASUS · FUJITSU 는 제약을 두지 않는다. 검사 지점은 세 층 — 브라우저 폼의 JS 사전 검사, upload-intent 하드 검증(업로드 경로에만 해당), 등록 본체 안전망.
  4. 목록 상세의 화면 표기를 줄인다. "진입점" 과 "파일 수 N 개 · B" 표기를 제거한다. 엔티티 필드 · DB 컬럼 · Response 필드는 그대로 두고 화면에서만 감춘다.
비 목표 — 각 항목이 어디로 가는지 함께 적는다.
  • 집행 코드(SimpleUpdate 호출 · Task 폴링 · 전원 오케스트레이션) → ue 스트림의 E2-2 · E2-3.
  • BMC 도메인 개편 → R12-2.
  • 공유 자산의 폴더 · 압축 경로와 벤더 진입점 전략 dead code 일소 → R12-2 완료 후.
  • 엔티티 · DB 컬럼 정리(entrypointRelativePath · fileCount 등) → 하지 않는다. 다른 세션이 데이터베이스를 대규모로 손보는 중이라 충돌을 피한다(§8 D9).
  • Subprogram 자원 → 대상 아님. MVP 축소로 Windows 계열과 함께 후순위다.
  • 이미 등록된 번들형 자원의 이관 · 재등록 → 운영 절차(코드 무변경). 집행 시점의 유효성 판단은 E2-2 소관.
  • 기존 화면 문구 전면 정비 → S16-2.
🎬 미리보기 — 파일 후보 × 요청 경로 → 3 층 판정 라이브 데모

축이 둘이다. 파일 후보를 고르면 세 층(① 브라우저 폼 ② upload-intent ③ 업로드 본체)의 판정이 갱신되고, 요청 경로를 바꾸면 어느 층이 실제로 발동하는지가 달라진다. 기존 파일 등록 은 업로드가 없으므로 층 ②(업로드 전용 핸드셰이크)가 건너뛰어지고, direct POST 는 화면과 핸드셰이크를 모두 우회해 층 ③ 안전망만 남는다. 판정 로직은 GIGABYTE 보드의 정책(GigabyteFirmwareFilePolicyStrategy)을 그대로 옮긴 것이며(드리프트 0), 이 데모는 GIGABYTE 보드를 가정한다 — ASUS · FUJITSU 보드는 금지 목록과 허용 확장자가 모두 비어 있어 어떤 파일이든 통과한다(§8 D3 · D10).

upload-intent — 요청 필드를 firmwarePath · fileName · fileSize · version · allowCreateDirectory 로 재구성한다. uploadMode · fileCount · entrypointRelativePath 는 제거된다. 하드 검증 목록에 벤더 파일 정책 검사(금지 파일명 + 허용 확장자)를 편입하되, 검사 대상은 두 이름이다 — 업로드 파일의 원본 파일명과, 경로 해석을 마친 최종 파일명. 경로에 PFR1.RBU 를 직접 적어 넣거나 확장자가 다른 파일명을 적는 입력도 같은 자리에서 걸러야 하기 때문이다. 이 핸드셰이크는 업로드가 있을 때만 호출된다. 기존 파일을 등록하는 경우에는 보낼 바이트가 없으므로 사전 관문을 둘 이유도 없다 — ISO 가 같은 구조다.

upload — multipart 파라미터를 firmwareFile 하나로 줄이고 required=false 로 받는다. 파일이 있으면 X-Upload-Token 을 1 회용으로 소비한 뒤 경로 해석 결과의 이름으로 저장하고, 없으면 토큰 없이 그 경로의 기존 파일을 등록한다. 어느 쪽이든 본체에서 벤더 파일 정책을 다시 검사한다. 화면을 거치지 않은 요청과, 토큰을 받은 뒤 다른 파일을 실어 보내는 요청을 막는 안전망이다.

register-existing — 삭제한다. 이 엔드포인트가 하던 일(이미 있는 것을 자원으로 등록)은 "업로드 파일 없이 upload 를 호출" 하는 것과 같아졌다. 요청 DTO BiosRegisterExistingRequest 와 서비스의 registerExisting 진입점도 함께 사라지고, 그 안의 검증 · nudge · 저장 흐름은 단일 경로로 합류한다.

nudge 배선은 현행 그대로다. 메타 충돌(단계 A)은 intent 에서, 내용 해시 충돌(단계 B)은 등록 본체에서 각각 409 로 분기하며 사용자의 proceed / replace / cancel 결정을 기다린다. 다만 기존 파일을 등록하는 경로에는 intent 가 없으므로 단계 A 가 발동하지 않는다 — 이 경로에서 동일 (board, version) 중복은 본체의 활성 중복 검사와 단계 B 가 받는다. 이는 현행 register-existing 과 같은 성질이며 새로 생기는 비대칭이 아니다.

부모 디렉토리 배타 검증 — IN_TREE 마커의 구조적 요구

BIOS 자원의 마커는 트리 안에 .provision.json 으로 기록된다(IN_TREE 방식). 이 파일 하나가 디렉토리 전체를 "이 자원의 것" 으로 주장하므로, 한 디렉토리를 두 자원이 나눠 가질 수 없다. 두 자원이 같은 디렉토리를 쓰면 마커가 서로를 덮어쓰고, 드리프트 탐지는 어느 자원의 트리인지 판정할 수 없게 되며, 휴지통 격리는 남의 파일까지 함께 옮긴다. 그래서 등록 시점에 부모 디렉토리의 배타성을 확인해야 한다.

  • 업로드 경로 — 전개 전에 부모 디렉토리가 비어 있어야 한다(현행 TargetDirectoryPolicyService 의 업로드 검사와 같은 성질).
  • claim 경로 — 등록 대상 파일 · 무시 가능 파일(.DS_Store · Thumbs.db) · 마커(.provision.json) 를 제외하고 다른 파일이 없어야 한다.

위반은 필드 직결 400 으로 거절한다. 사용자가 경로를 고치면 해결되는 입력 문제이지 서버 내부 오류가 아니기 때문이다.

신규 — 금지 파일명 정책 SPI (판정 SSOT) D10 반영

금지 파일명 두 개는 GIGABYTE 벤더 패키지의 관례에서 기원한 제약이다. 한 클래스에 하드코딩하면 다른 제조사의 파일에도 같은 제약이 번지므로, 진입점 탐지의 EntrypointDetectionStrategy 선례와 같은 vendor 매칭 SPI(Service Provider Interface — 도메인이 구현해 끼우는 확장점)로 나눈다(§8 D10).

인터페이스를 데이터 메서드 + 알고리즘 default 로 나눈 것이 이 구조의 요점이다. 검사 순서(금지 파일명 먼저, 허용 확장자 나중)와 예외 조립은 assertAllowed 의 default 본문 한 곳에만 있고, 벤더 구현체는 목록과 문구라는 데이터만 공급한다. 벤더가 늘어도 알고리즘이 복제되지 않고, 검사 순서를 바꿔야 할 때 고칠 자리도 하나다. 빈 목록을 "제한 없음" 으로 읽기 때문에 제약이 없는 벤더는 supports 하나만 선언하면 된다 — ASUS 와 FUJITSU 가 그렇다.

GIGABYTE 전략이 UI 차단 조건과 서버 가드 조건의 단일 SSOT(Single Source of Truth, 단일 진실 출처) 다. 호출부 셋 — upload-intent 의 하드 검증, 등록 본체의 재검, 등록 폼을 여는 GET /new 의 모델 속성 적재 — 이 모두 vendor 를 인자로 넘겨 같은 전략을 거친다. 서버 쪽 검사 호출부는 확장자 축이 더해져도 바뀌지 않았다. assertAllowed 가 두 축을 함께 관장하므로 intent · 등록 본체 · claim 경로가 코드 변경 없이 확장자 검사를 함께 얻는다 — 검사 한 축을 늘리는 일이 전략의 데이터 한 줄로 끝난다는 것이 이 템플릿의 실익이다.

화면에 드러나는 효과는 셋이다. ① 파일 입력의 accept 속성이 acceptAttribute(vendor) 에서 파생된다 — GIGABYTE 는 ".rbu,.RBU", 제한이 없는 벤더는 속성 자체를 붙이지 않는다. 대문자 변형을 함께 적는 이유는 브라우저마다 확장자 매칭의 대소문자 처리가 달라, 한쪽만 적으면 정상 파일이 선택되지 않는 환경이 생기기 때문이다. ② 안내 hint 가 "확장자 제한 없음" 과 벤더 확장자 문구 사이에서 조건부로 갈리고, PFR 금지 안내도 GIGABYTE 보드에서만 나타난다. 사용자에게 자기 보드와 무관한 주의사항을 보이지 않는다는 뜻이다. ③ JS 사전 검사에 확장자 축이 더해지며, 업로드 원본 파일명과 경로 해석 최종 파일명을 둘 다 검사한다 — 업로드가 없는 claim 경로도 이 검사를 받는다.

CLAUDE.md 의 테스트 규율이 필수로 정한 것은 네 범주(성공 2xx · 400 · 404 · 409)다. 파일 시스템 오류로 500 이 되는 경로는 기존 BundleExtractionService 소관이며 이번 슬라이스가 새로 만들지 않는다. 신설한 FirmwareFilePolicyMissingException(500)은 사용자 액션이 아니라 벤더 전략 등록 누락을 개발자에게 드러내는 가드라 통합 시나리오로 재현할 대상이 아니다(§7). 그래서 500 행은 비워 둔다. 위의 시나리오 수는 열거한 항목을 그대로 센 값이고, CP4 에서 분기가 더 드러나면 늘 수 있다.

성공 범주의 ASUS 보드 .cap 업로드 와 400 범주의 GIGABYTE 보드 확장자 위반 은 한 쌍으로 읽어야 한다. 같은 파일 형식이 보드에 따라 갈린다는 사실을 두 방향에서 고정하는 것이며, 둘 중 하나만 있으면 "정책이 벤더별" 이라는 성질이 테스트로 지켜지지 않는다. 한쪽이 빠지면 나중에 누군가 확장자 검사를 도메인 전역으로 되돌리거나 반대로 통째로 지워도 깨지는 테스트가 없다. 400 범주의 본체 direct POST 두 건은 또 다른 방향의 확인이다 — 화면과 핸드셰이크를 모두 우회한 요청을 본체 재검이 두 축 모두에서 잡는지 본다.

신규 예외에는 반드시 트리거 시나리오가 붙는다. InvalidFirmwareFileException 의 사유 네 가지가 위 400 범주 다섯 항목에 모두 실려 있다. 새 예외 관문(.claude/domain-conventions/new-exception.md)이 요구하는 조건이며, 이것이 빠진 묶음은 CP4 승인 대상이 아니다.

부수 확인 셋. ① UploadPathResolver 이동 후 기존 ISO 테스트가 그대로 green 인지 확인한다 — import 만 바뀌는 이동이지만 ISO 등록 경로 전체가 이 클래스를 통과하므로 회귀 확인 없이 넘기지 않는다. ② FormSubmissionConventionTest 의 기대값에는 영향이 없다. BIOS 폼은 XHR 로 제출되고 페이지 JS 가 응답을 처리하므로 data-native-submit 대상이 아니며 그 성격이 이번에도 유지된다. ③ DriftBulkApplyServiceTest 는 2026-08-19 13:00 KST 이후 항상 1 건 실패하는 기존 결함이다(고정 시각과 Instant.now() 기반 스누즈 만료가 어긋난 것으로 별도 hotfix 후보). CP4 의 green 판정에서 이 실패는 제외한다.

InvalidFirmwareFileException 이 담는 사유는 넷이다 — 금지 파일명, claim 대상 파일 부재, 디렉토리 경로인데 업로드 없음, 부모 디렉토리 비배타. 넷 모두 사용자가 입력을 고치면 해결되는 문제라 400 이 맞다. 필드명을 생성자 인자로 받는 이유는 같은 예외가 두 화면 자리(파일 입력 · 경로 입력)에 붙기 때문이다. 예외를 넷으로 쪼개는 대신 붙일 자리를 인자로 받는다.

FirmwareFilePolicyMissingException 은 성격이 다르다. 사용자 액션으로는 도달할 수 없고, 새 Vendor 값을 추가하면서 그 벤더의 전략을 등록하지 않았을 때만 발동한다. 이 가드가 없으면 등록 누락이 "제약 없음" 으로 조용히 흘러가 금지 파일이 통과해 버린다 — 침묵하는 대신 즉시 500 으로 터뜨려 개발 규칙을 강제한다. 같은 이유로 만들어진 EntrypointStrategyMissingException 선례를 따른다. 사용자 액션이 아니므로 §6 의 통합 시나리오 대상이 아니며, 새 벤더를 추가하는 시점에 개발자가 만나는 예외다.

삭제되는 예외는 없다. BundleExtractionException 과 EmptyBundleException 은 BIOS 경로에서 발생 빈도가 줄지만 extractSingleFile 이 여전히 던질 수 있고 BMC 도메인이 같은 서비스를 쓰므로 그대로 둔다.

D1 — 저장 모델은 "파일이 하나뿐인 트리" 를 유지한다

채택. 엔티티와 마커 형식을 그대로 두고 fileCount=1 인 트리로 단일 파일을 표현한다. 비채택 대안 은 ISO 자원처럼 단일 파일 모델로 엔티티를 개편하고 마커를 sidecar 로 전환하는 것이다. 탈락 사유 — 집행 단계(E2-2)는 treeRootPath 와 entrypointRelativePath 만으로 파일을 특정할 수 있어 개편의 실익이 없다. 반대로 개편하면 스캐너 · 휴지통 · reconciliation · orphan · 마커 인프라를 전면 재작업하고 DDL 까지 동반되는데, 얻는 것은 개념의 순수성뿐이다. 등록 UX 를 ISO 와 같게 만들되(D2) 저장 모델까지 ISO 를 따라가지는 않는다는 뜻이다.

D2 — 등록 UX 를 ISO 방식 단일 폼으로 통합한다 정정

채택(사용자 결정 2026-08-20). 탭을 없애고 경로 한 칸 + 선택적 파일 한 칸의 단일 폼으로 간다. 파일이 있으면 저장, 없으면 그 경로의 기존 파일을 claim 한다. /register-existing 엔드포인트 · BiosRegisterExistingRequest · BiosUploadMode 가 함께 사라진다.

비채택 대안 ① — 폴더 · 압축만 지우고 "단일 파일 업로드" 와 "기존 디렉토리 등록" 두 탭을 남기는 것(초안이 채택했던 안). 탈락 사유 — 두 탭이 하는 일이 "파일을 올려서 등록" 과 "이미 있는 파일을 등록" 으로 갈릴 뿐인데, 사용자가 그 차이를 먼저 판단해 탭을 고르게 만든다. ISO 는 같은 문제를 "파일을 첨부했는가" 라는 사실 하나로 서버가 스스로 판정해 해결하고 있고, 그 코드가 이미 검증돼 있다. 화면이 둘로 갈리면 검증 · 문구 · nudge 배선도 두 벌로 갈라진다. 비채택 대안 ② — 기존 파일 등록 자체를 없애 경로를 하나로 만드는 것. 탈락 사유 — 미리 배치해 둔 파일을 등록하거나 드리프트 복구 과정에서 다시 붙이는 실제 쓰임이 있다.

D3 — 확장자 검사 = vendor 정책 (GIGABYTE .RBU 단일) 재개정

이 결정은 세 번 바뀌었다. 흐름을 그대로 적는다.

  1. CP1 원안 — 도메인 전역에 허용 확장자 목록 .rbu 하나를 둔다. 논거는 "Redfish SimpleUpdate 로 실집행을 완주한 파일이 GIGABYTE 의 image.RBU 뿐이므로 집행 못 할 파일은 등록 단계에서 미리 끊는다" 였다.
  2. CP1 검수 — 사용자가 확장자 검사 철회. 전역 목록은 실측이 한 벤더 한 모델에 그친 상태에서 다른 제조사의 정상 펌웨어(ASUS 의 .cap 등)까지 막는다. 전역 검사의 부작용이 이득보다 컸다.
  3. 구현 중 — 사용자가 vendor 별 허용 확장자로 재도입 지시. D10 의 vendor SPI 가 들어오면서 전제가 바뀌었다. 목록을 벤더 안에 가둘 수 있게 됐으므로 GIGABYTE 만 .RBU 를 요구하고 ASUS · FUJITSU 는 제약을 두지 않는다.

결과적으로 ② 의 우려는 vendor 격리로 소멸했다. 전역 목록이 다른 제조사에 번지는 일이 구조적으로 불가능해졌기 때문이다 — ASUS .cap 은 ASUS 전략에 제약이 없으므로 여전히 등록된다. 동시에 ① 의 이득은 그대로 살아난다. GIGABYTE 보드에 .zip 이나 확장자 없는 파일을 올리면 등록 단계에서 끊긴다. "제조사 관례에서 온 제약은 그 제조사 안에서만 집행한다" 는 것이 세 번의 변경을 관통하는 원칙이며, 금지 파일명(D4)과 허용 확장자가 같은 자리(벤더 전략)에 놓인 이유이기도 하다.

비채택 대안은 ② 의 상태에 머무르는 것, 즉 확장자를 아예 보지 않는 것이다. 탈락 사유 — vendor 격리가 갖춰진 뒤에는 전역 검사의 부작용이 사라지므로, 확장자를 보지 않을 이유도 함께 사라진다. GIGABYTE 보드에 압축 파일이 등록되도록 두면 집행 시점(E2-2)에야 실패를 알게 되는데, 그 실패는 등록 시점에 확실히 알 수 있었던 것이다.

확장자 거절 문구 정본(GIGABYTE 전략 보유) — "GIGABYTE BIOS 펌웨어는 .RBU 형식 파일만 등록할 수 있습니다."

D4 — PFR1.RBU · PFR2.RBU 는 하드 거절한다 원안 유지 · 사용자 승인

채택. 금지 파일명 목록으로 차단하고 폼에 사전 안내를 상시 노출한다. 근거는 실측이다 — 이 두 파일은 PFR active/recovery 사본 경로 전용이며 전송 금지로 확인됐다. 등록되면 집행 사고 위험이 실재한다. 비채택 대안 ② 는 경고만 띄우고 진행을 허용하는 것으로, 사용자가 무시할 수 있어 사고 여지가 남는다. 대안 ③ 은 안내 문구만 적어 두는 것으로, 조용히 등록되는 경로가 그대로 열려 있어 더 나쁘다. UI 가 1 차로 막고 서버 가드가 안전망으로 남는 구도라 예외 사용 원칙과도 맞는다. 확장자 검사가 철회됐던 구간(D3 ②)에도 이 검사만은 남아 있었다 — 그때 확장자는 "집행될지 모르는" 추정이었지만 이 두 이름은 "보내면 안 된다" 는 실측이었기 때문이다. 지금은 둘 다 GIGABYTE 전략 안에서 나란히 집행된다.

D5 — 공유 자산은 R12-1 에서 건드리지 않는다

채택. BIOS 쪽 호출부만 전환하고 공유 자산은 그대로 둔다. BundleExtractionService.extractSingleFile 과 BundleManifestService 는 계속 쓴다. BundleEntrypointDetector 는 BIOS 경로에서 호출을 멈추지만(경로 해석 결과의 파일명이 곧 진입점이므로) 클래스와 전략 3 종은 BMC 가 공유하므로 잔존한다. bundle-upload-shell.js 는 단일 폼 개편 범위에서 판단한다 — 탭 · 모드 분기를 걷어내면 BIOS 페이지가 이 helper 를 거의 쓰지 않게 될 수 있어, 손대야 할지는 화면 작업(Step 2)에서 확정한다. 어느 쪽이든 BMC 가 쓰는 기존 함수는 고치지 않는다. 비채택 대안 은 R12-1 에서 폴더 · 압축 경로를 즉시 지우는 것이다. 탈락 사유 — BmcRegistrationService 가 그 경로를 그대로 쓰고 있어 곧바로 깨진다.

D6 — intent 핸드셰이크는 업로드 전용으로 유지한다 정정

채택. 2 단 핸드셰이크를 없애지 않고 "업로드가 있을 때만 호출" 하는 구조로 좁힌다. 바이트를 보내기 전에 하드 조건을 먼저 본다는 취지가 금지 파일명 검사와 맞물리고, 메타 nudge(단계 A) 배선이 intent 안에 있다. 기존 파일 등록에는 보낼 바이트가 없으므로 핸드셰이크가 필요 없다 — ISO 가 정확히 이 구조다(hasFile 일 때만 토큰 소비). 비채택 대안 은 핸드셰이크를 폐지하고 단발 POST 로 단순화하는 것이다. 탈락 사유 — nudge 를 다시 배선하는 비용에 비해 얻는 것이 없다. 다만 IntentMetaNudgePayload 의 attributes 구성과 reconstructRequestFromAttributes 는 새 필드 구성에 맞춰 함께 개정해야 한다. 여기를 빠뜨리면 nudge 이후 재발급 경로에서 없어진 필드를 읽으려 든다.

채택(사용자 결정 2026-08-20). "진입점" 과 "파일 수 · 총 바이트" 표기를 목록 상세에서 없애되 엔티티 필드 · DB 컬럼 · Response 필드는 그대로 둔다. 명시된 사유는 충돌 회피다 — 다른 세션이 데이터베이스를 대규모로 손보는 중이라, 이 슬라이스가 컬럼을 건드리면 그쪽 작업과 부딪친다. 부수 효과로 이 슬라이스의 DDL 0 건 원칙이 한층 단단해진다. 비채택 대안 은 표기와 함께 컬럼 · Response 필드까지 정리하는 것이다. 탈락 사유 — 지금 정리해도 얻는 것은 스키마의 깔끔함뿐인데 충돌 위험이 실재한다. 필드 정리가 필요해지는 시점은 집행 배선(E2-2)이 이 값들을 어떻게 쓰는지 확정된 뒤이며, 그때 별도 슬라이스로 다룬다.

D10 — 금지 파일명 정책을 vendor 별 SPI 로 분리한다 신설

채택(사용자 지시 2026-08-20). FirmwareFilePolicyStrategy 인터페이스와 벤더별 구현 3 종을 management/bios/firmware/ 에 두고, BiosFirmwareFilePolicy 는 vendor 매칭 dispatcher 로 개편한다. 금지 파일명 두 개가 GIGABYTE 벤더 패키지의 관례에서 나온 제약이기 때문이다. 이 자리가 생기자 허용 확장자도 같은 곳에 들어왔다(D3 ③) — 제조사 관례에서 온 제약을 그 제조사 안에서만 집행한다는 원칙이 두 축에 함께 적용된다.

비채택 대안 ① — 단일 클래스에 금지 목록을 하드코딩(정정 전 초안이 채택했던 안). 탈락 사유 — 한 제조사의 패키지 관례에서 기원한 제약이 모든 제조사의 파일에 번진다. ASUS 나 FUJITSU 가 PFR1.RBU 라는 이름을 다른 의미로 쓴다면 정당한 파일이 막히고, 그 사실을 알아채더라도 목록을 벤더별로 갈라야 하므로 결국 같은 분리를 나중에 하게 된다. 비채택 대안 ② — Vendor enum 에 method-per-constant 로 정책을 붙이는 것. 탈락 사유 — Vendor 는 board 도메인의 열거형인데 이렇게 하면 그것이 bios 도메인의 파일 정책을 역참조하게 된다. 도메인 경계를 거스르는 의존이 생기고, 나중에 BMC 가 자기 정책을 더할 때 같은 enum 이 두 도메인 정책을 함께 이고 있게 된다.

새 Vendor 값이 늘 때 전략 등록을 잊으면 FirmwareFilePolicyMissingException(500)이 즉시 터진다. 조용히 "제약 없음" 으로 흘러가 금지 파일이 통과하는 것보다 낫다는 판단이며, 진입점 탐지의 EntrypointStrategyMissingException 이 같은 이유로 이미 존재한다.

구현 중 확정된 것 (CP2 ~ CP4)

① EntrypointDetectionStrategy 에 @Deprecated 부착(사용자 직접 편집). 번들 폐지로 이 인터페이스는 기능상 제외됐다. 다만 BMC 도메인이 R12-2 까지 계속 쓰므로 클래스 제거는 하지 않고 표시만 남긴다 — 지금 지우면 BMC 가 깨진다는 D5 의 판단은 그대로다. 실제 일소는 R12-2 에서 수행한다. @Deprecated 는 그때까지 "이것을 새로 쓰지 말라" 는 신호로 컴파일 경고를 남긴다.

② claim 취소가 사용자 파일을 삭제하는 잠복 결함을 차단했다. 해시 충돌 nudge 에서 사용자가 "취소" 를 고르면 BiosNudgeService.cancel 이 트리를 물리 삭제한다. 업로드 경로에서는 그 트리가 방금 올린 임시물이라 옳은 동작이지만, claim 경로에서는 사용자가 원래 갖고 있던 파일이다. 취소를 눌렀을 뿐인데 자기 파일이 사라지는 것이다. 구 register-existing 시절부터 있던 잠복 결함이며, 이번 개편에서 claim 흐름을 단일 경로로 재설계하다 드러났다.

처리는 이렇게 했다. issueHashNudge 가 payload attributes 에 claimExisting 플래그를 기록하고, 취소 시 정리 책임을 BiosRegistrationService.cleanupNudgeCancelled(payload) 로 옮긴다. claim 이면 트리를 보존하고 업로드 임시물일 때만 삭제한다. 정리 판단에 필요한 맥락(이 트리가 우리가 만든 것인가)을 아는 쪽이 등록 서비스이므로 책임을 그쪽에 두는 것이 맞다. BiosNudgeService 는 취소 사실만 알리고 정리 방식은 모르게 된다.
