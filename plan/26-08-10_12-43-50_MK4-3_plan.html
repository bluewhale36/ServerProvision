§1. 현재 상태 (진단)

점검의 동작을 좌우하는 값이 전부 application.properties 에 있다. 바꾸려면 파일을 고치고 애플리케이션을 다시 띄워야 하므로 운영자는 사실상 바꿀 수 없다. 실측한 키는 일곱이다.

설정 키기본값무엇을 정하나값을 언제 읽나
reconciliation.auto-apply.kinds빈 값점검 도중 시스템이 사람 확인 없이 스스로 처리할 드리프트 종류. 여기 없는 종류는 발견만 하고 그대로 둔다점검마다
reconciliation.resolution-enabledtrue드리프트를 고치는 행위 전체의 차단기. 끄면 수동 [해결] 과 점검 중 자동 처리가 모두 멈추고 탐지만 계속한다해결 요청마다
reconciliation.report.retention-count100점검 보고서를 몇 회분까지 남길지. 넘으면 오래된 것부터 지운다점검 끝 정리 시
reconciliation.scan.extra-roots빈 값기본 점검 범위(활성 자원이 등록된 폴더들) 밖에서 추가로 뒤질 경로. 백업 폴더처럼 자원을 옮겨 두는 자리를 범위에 넣어 '자원 소실' 대신 '경로 이동됨' 으로 잡히게 한다점검 시작 시
reconciliation.scan.startup-enabledtrue애플리케이션이 뜬 직후 한 번 점검할지. 꺼져 있는 동안 디스크가 바뀌었을 수 있어 기동 시 한 번 맞춰 본다기동 시 1 회
reconciliation.scan.interval-ms3600000 (1 시간)일반 점검을 얼마나 자주 돌릴지. 일반 점검은 마커와 위치만 보고 파일 내용은 보지 않는다기동 시 고정
reconciliation.scan.deep-interval-ms86400000 (24 시간)정밀 점검을 얼마나 자주 돌릴지. 정밀 점검은 파일 내용의 지문까지 다시 계산해 변조를 잡는다기동 시 고정

두 가지가 더 있다.

자동 처리가 사실상 꺼져 있다. 다섯 종류가 무인 처리 대상으로 설계돼 있는데(해결 등급 AUTO) 기본값이 빈 값이라 아무것도 자동으로 처리되지 않는다. 그런 선택지가 있다는 사실조차 화면 어디에도 없어, 마커 한 장 지우면 끝나는 정리까지 운영자가 매번 손으로 눌러 왔다.
첫 화면 안내가 설정 키 이름을 그대로 노출한다. 점검 범위 안내문에 reconciliation.scan.extra-roots 가 코드 조각으로 적혀 있는데, 정작 화면에서 바꿀 방법은 주지 않는다.

선례가 있고, 그 선례에 알려진 구멍이 있다

휴지통에는 운영 설정 화면이 이미 있다(/maintenance/trash/settings). 단일행 엔티티 + 요청 record + 서비스 + 컨트롤러 구성이며 이 단계가 따를 형태다.

다만 그 선례는 주기 설정에서 화면과 실제가 어긋나 있다. 영구삭제 주기를 cron 식으로 데이터베이스에 저장하고 화면에서 바꾸게 해 두었지만, 실행부는 @Scheduled(cron = "${trash.ttl.purge-cron:...}") 로 시작 시점에 문자열이 고정되어 저장된 값이 적용되지 않는다. 코드 주석이 그 한계를 적어 두고 후속 검토로 남겨 두었다. 반면 자동 삭제 사용 여부와 보관 기간은 실행 시점에 조회하므로 제대로 적용된다.

이 사실이 이 단계의 항목 선정 기준을 정한다.

§2. 요구사항 (확정) + 비목표

요구사항

  • R1 운영 중에 판단해 바꾸는 값을 화면에서 조작하게 한다.
  • R2 자동 처리 기본값을 켠다. 어떤 종류를 자동으로 처리할지 화면에서 조정한다.
  • R3 자동 처리 대상 목록은 종류의 해결 등급에서 파생한다. 화면이나 설정에 종류 이름을 하드코딩하지 않는다.
  • R4 설정 키 이름이 사용자 문구에 드러나는 자리를 설정 화면 안내로 바꾼다. 노출 지점은 둘이다 — 첫 화면의 점검 범위 안내, 그리고 DriftKind.MISSING 의 "직접 해야 할 일" 문구다. 뒤엣것은 CP1 전사 중 발견해 범위에 넣었다.
  • R5 저장된 값이 실제로 적용되지 않는 항목을 화면에 조작 가능한 모습으로 두지 않는다.
비 목표 :
  • 점검 로직 자체는 바꾸지 않는다. 무엇을 어떻게 탐지하고 해결할지는 그대로 두고, 그 동작을 좌우하는 값을 운영자가 다루게 하는 데까지다.
  • 화면 배치와 디자인은 최소로 한다. 다음 하위 단계가 화면을 전면 개편하므로, 이 단계는 항목이 무엇인지와 그 값이 어떻게 저장 · 적용되는지에 집중하고 요소 배치는 기존 폼 관례를 그대로 쓴다.
  • 휴지통 설정과 통합하지 않는다. 두 화면을 하나로 합치는 것은 배치 문제이고 다음 단계 소관이다.
  • 휴지통의 주기 미적용 문제를 이 단계에서 고치지 않는다. 이 단계가 만드는 기구를 나중에 그쪽이 가져다 쓸 수는 있으나, 남의 화면을 함께 고치면 두 변경의 책임이 섞인다.
🎬 미리보기 — 라이브 UX 데모

두 가지를 체험시킨다. 데모 A 는 어떤 설정이 언제 효과를 내는지를, 데모 B 는 자동 처리 기본값을 어디까지 켤 것인지를 직접 바꿔 보게 한다.

데모 A — 이 설정은 언제 효과가 나는가

각 행의 [값을 바꿨다] 를 누르면 그 값이 실제로 언제부터 효과를 내는지가 행 아래에 나타난다. 툴바의 실행 구조 를 바꾸면 주기 두 항목의 판정이 함께 달라진다 — 주기 두 항목을 어떻게 할 것인가라는 갈림(§8 의 Q1)의 두 갈래를 눈으로 견주게 하는 것이 이 데모의 목적이다.

실행 구조 :
행의 [값을 바꿨다] 를 눌러 보세요. 저장이 언제부터 효과를 내는지가 그 행 아래에 나타납니다.

데모 B — 자동 처리 기본값을 어디까지 켤 것인가

해결 등급이 AUTO 인 다섯 종류다. 각 행의 켬 / 끔 을 바꿔 보면 저장될 값이 아래 판정 패널에 그대로 반영된다. 종류 이름에 마우스를 올리면 그 종류의 [해결] 이 실제로 무엇을 하는지가 뜬다.

자동 처리 대상 :
되돌릴 수 있는 넷이 기본으로 켜져 있습니다. 되돌릴 수 없는 종류를 켜면 경고가 뜹니다.

기본값 판정은 새 축을 만들지 않고 종류가 이미 들고 있는 성질(DriftKind.reversible)을 그대로 쓴다.

// 서버 기본값 산정과 동일 — 되돌릴 수 있는 것만 기본으로 켠다
function demoDefaultOn(kind) { return kind.reversible; }
드리프트 0 — 데모 B 의 기본값 판정 = 서버 기본값 산정 = DriftKind.isReversible() 단일 소스. 자동 처리 후보 다섯도 DriftKind.values() 중 해결 등급이 AUTO 인 것으로 걸러낸 목록이며, 데모에 별도 하드코딩 목록을 두지 않는다.

§6. Step 8 통합 테스트 시나리오

단위

  • 기본값 산정 — 되돌릴 수 있는 종류만 켜진 상태로 초기 행이 만들어지는가.
  • 자동 처리 후보 목록이 DriftKind 의 AUTO 등급에서 파생되는가(하드코딩 금지의 안전망). AUTO 종류를 새로 추가하면 후보에 자동으로 나타나야 한다.
  • 경로 목록 검증 — 절대 경로가 아닌 값 · 빈 줄 · 중복 처리.
  • PathReconciliationService 가 설정 파일이 아니라 설정 서비스에서 값을 읽는가.

§7. 예외 계층

신규 예외는 두지 않는 것을 원칙으로 한다. 입력 오류는 @Valid + BindingResult 로 처리하고, 설정 행이 없으면 예외 대신 기본값으로 만들어 준다(운영자가 손댄 적 없는 상태는 오류가 아니다).

구분처리결과
신규 0입력 오류 → @Valid + BindingResult400 + 같은 뷰 재렌더(필드 메시지)
신규 0설정 행 부재 → 기본값 생성정상 렌더 (예외 아님)
§8. 결정 · Open Questions

채택한 결정

D1 — 화면에 올릴 자격은 "그 값이 실행 시점에 읽혀 즉시 효과가 나는가" 로 가른다.
근거는 휴지통 선례의 실측이다. 주기를 저장하고 화면에서 바꾸게 해 두었지만 실행부가 시작 시점에 고정해 적용되지 않고, 그 사실이 코드 주석에만 남아 있다. 화면이 거짓말하는 상태를 하나 더 만들지 않는다. 조작 가능한 모습으로 두려면 실제로 적용되게 만들거나, 적용되지 않는다면 조작 가능한 모습으로 두지 않는다.

D2 — 자동 처리 기본값은 "되돌릴 수 있는가" 로 정한다.
해결 등급이 AUTO 인 다섯 중 되돌릴 수 있는 넷을 기본으로 켜고, 되돌릴 수 없는 유령 DB 기록만 기본으로 끈다. 새 축을 만들지 않고 종류가 이미 들고 있는 성질을 쓴다. 무인으로 맡기는 판단의 기준이 "잘못돼도 되돌릴 수 있는가" 라는 한 문장으로 설명된다.
비채택 — 다섯을 모두 켜기(되돌릴 수 없는 영구 삭제를 무인에 맡기게 된다) · 다섯을 모두 끄기(지금과 같아 이 단계의 목적이 사라진다).

D3 — 자동 처리 후보 목록은 종류의 해결 등급에서 파생한다.
화면에도 설정에도 종류 이름을 하드코딩하지 않는다. 새 AUTO 종류가 생기면 후보에 저절로 나타난다. 앞 단계가 위험도를 종류 속성으로 둔 것과 같은 원칙이며, 과거 네 종류를 화면 세 곳에 하드코딩했다가 서버 다섯 종류와 갈라져 버튼이 누락된 사고가 있었다.

D4 — 추가 점검 경로는 줄바꿈 구분으로 저장하고 형식을 검증한다.
콤마 구분은 경로에 콤마가 들어가면 깨진다. 검증은 절대 경로일 것 · 정규화 후 중복 제거 · 빈 줄 무시까지 한다. 존재하지 않는 경로는 거절하지 않고 화면에 경고만 표시한다 — 아직 마운트되지 않은 백업 경로를 미리 등록하는 것이 정당한 운영이기 때문이다.

D5 — 저장 형태는 단일행 엔티티.
휴지통 선례와 같다. 자동 처리 대상은 별도 조인 테이블 대신 이름 목록 문자열로 둔다 — 종류는 코드의 열거형이 SSOT 라 테이블로 정규화해도 참조 무결성을 얻지 못하고, 읽는 쪽이 어차피 열거형으로 되돌린다.

문자열은 저장 형식일 뿐 계약이 아니다. 원시 타입 집착 금지 원칙과 부딪히지 않도록 경계를 명시한다 — 컬럼은 문자열이지만 서비스가 노출하는 타입은 Set<DriftKind> 와 List<Path> 이고, 호출부는 문자열을 보지 않는다. 파싱과 조립은 서비스 안에 가둔다. 휴지통 설정이 알림 D-day 목록을 같은 방식으로 다루는 선례가 있다.

  • Q1 확정 — 안 '나'(동적 스케줄) 채택. 단 단계를 둘로 나눈다. MK4-3-1(설정 화면과 즉시 반영 항목)이 값을 옮기고, MK4-3-2(점검 주기 동적 적용)가 실행 구조를 바꾼다. 이 순서인 이유는 주기를 저장할 자리와 조작할 화면이 먼저 있어야 하기 때문이며, 반대로 MK4-3-1 은 주기 없이도 완결된다 — 자동 처리 기본값을 켜는 것이 본래 목적이고 그것은 주기와 무관하다.
  • Q2 확정 — 기동 직후 점검은 화면에 두되 "다음 기동부터 적용" 을 명시한다. 효과 시점이 분명히 안내되면 D1 의 기준(화면이 거짓말하지 않는다)을 지키면서도 운영자가 다룰 수 있다.
  • Q3 확정 — 시스템 해결 차단은 화면에 두고, 꺼진 상태를 목록 화면에 상시 배너로 알린다. 이 스위치는 탐지는 계속하되 고치는 행위만 전부 멈추는 비상 차단기다(수동 [해결] 과 점검 중 무인 처리 양쪽을 막고, 삭제 거절 뒤의 "위치 정정 후 삭제" 흐름만 사용자 명시 액션이라 통과한다). 비상 차단기는 켤 수 있어야 의미가 있으므로 설정 파일에 남기지 않고, 켜 둔 사실이 계속 보여야 잊히지 않으므로 배너로 알린다. 앞 단계가 "안 본 것은 안 봤다고 밝힌다" 를 세웠는데 여기서는 "안 고치는 중이면 안 고치는 중이라고 밝힌다" 로 같은 원칙이 이어진다.

확정 전 원문 (판단 근거 보존)

Q1 — 점검 주기 두 항목을 어떻게 할 것인가. 이 단계의 크기를 좌우한다.
안내용장단
가 이번 범위에서 빼고 설정 파일에 남긴다. 화면에는 현재 주기를 읽기 전용으로 보여 주고 바꾸는 방법을 안내한다 비용 0. 거짓말하지 않는다 이 단계가 내건 "운영자가 못 바꾼다" 중 하나가 그대로 남는다
나 동적 스케줄로 바꿔 저장 즉시 다음 발동부터 적용되게 한다 scope 를 온전히 달성. 뒤에 휴지통도 같은 기구를 쓸 수 있다 실행 구조를 바꾸는 일이라 이 단계가 커진다
다 저장은 하되 다음 기동부터 적용 구현이 가장 쉽다 채택 불가 — 휴지통이 지금 그 상태이고 그것이 결함으로 남아 있다

현재 판단으로는 나 가 scope 에 충실하다. 이 단계의 정의가 "설정 파일에 갇힌 값을 화면으로 꺼낸다" 이고 주기가 그 목록의 첫 줄이기 때문이다. 다만 실행 구조 변경이라 가 로 좁히는 것도 정당하며, 그 경우 주기는 별도 단계로 뗀다.

Q2 — 기동 직후 점검 여부를 화면에 둘 것인가.

값은 다음 기동에만 효과가 난다. 현재 안은 화면에 두되 "다음 기동부터 적용" 을 명시하는 것이다. 효과 시점이 분명히 안내되면 D1 의 기준(거짓말하지 않는다)을 지키면서도 운영자가 다룰 수 있다.

Q3 — 시스템 해결 차단 스위치를 화면에 두는 것이 맞는가.

이 값을 끄면 모든 해결 버튼이 막힌다. 화면에서 끌 수 있게 하면 실수로 끄고 이유를 잊을 여지가 있다. 현재 안은 두되 끄는 순간 그 결과를 확인 창으로 알리는 것이다.
