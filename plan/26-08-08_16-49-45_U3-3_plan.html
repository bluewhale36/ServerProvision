§0. scope 개정 (2026-08-10 갱신)

이 단계는 원래 "core 산출만 소비하는 read-only 프런트 층" 으로 정의됐다. 그런데 스펙 그룹의 비교 기준 여섯 가지 중 CPU 개수가 수집되지 않는다는 것이 CP1 조사에서 드러났다. 진단 에이전트가 첫 소켓만 읽고 있어 화면에서는 메울 수 없는 결핍이다. 사용자가 2026-08-08 에 수집 확장을 이 슬라이스 안에 포함하기로 정했고, 그래서 read-only 라는 자기 정의는 개정된다 — 이 슬라이스는 진단 수집 계약(에이전트 보고 → 파서 → HardwareSpec)까지 건드린다.

2026-08-10 에 그룹 표시 규칙 두 가지가 추가로 확정됐다. '등록 진행 중' 은 목록 최상단에 접힌 채로 두고, 수집이 끝난 그룹은 서버가 실제로 들어 있는 것만 펼친 채로 그린다. 상세는 §2 와 DEC-H 에 있다.

미루는 선택지를 왜 버렸나 — 수집 확장을 별도 E 계열 슬라이스로 떼면 단계 경계는 깨끗해지지만, 그 슬라이스가 끝날 때까지 U3-3 은 여섯 기준 중 다섯만으로 그룹을 만들게 된다. 같은 모델 CPU 를 1소켓과 2소켓으로 꽂은 서버가 한 그룹으로 묶이는데, 이것은 입고 단위로 서버를 갈라 보려는 이 화면의 목적을 정면으로 훼손한다. 반쪽 기준으로 먼저 내놓고 나중에 고치는 것보다 한 번에 맞추는 편이 낫다고 판단했다.
§1. 현재 상태 (진단)

무엇이 있고 무엇이 없나

게스트 서버 목록 화면은 이미 있고 실시간 갱신도 붙어 있다. 없는 것은 묶어 보여주는 층과 그 층이 딛고 설 판정이다.

진단 하나 — 판정이 사유지에 갇혀 있다

"이 서버의 스펙을 알고 있는가" 를 묻는 판정은 이미 구현돼 있다. AgentReportService 의 isEnriched() 가 discoveryStage == DIAGNOSTIC_ENRICHED 를 그대로 본다. 문제는 그것이 private 이라는 점이다.

이 화면은 같은 질문에 답해야 하고, 후속 U3-4 의 그룹 할당 가드("스펙 없는 서버 배제")도 같은 질문에 답해야 한다. 세 곳이 각자 판정을 만들면 어긋날 자리가 생긴다. 과거 childEnableBlockReason 이 같은 구도를 먼저 겪었고, 그래서 프로젝트는 "UI 조건과 서버 가드는 단일 SSOT 를 공유한다" 를 불가침으로 두고 있다.

스펙 그룹은 여섯 가지로 서버를 비교한다. 그중 다섯은 이미 수집되지만 CPU 개수는 어디에도 없다.

§2. 요구사항 (확정) + 비목표

목록을 그룹으로 바꾼다

여러 대가 한꺼번에 들어오는 실제 상황 — 주문서 단위 입고 — 에서 운영자는 "방금 들어온 같은 스펙 묶음" 을 눈으로 골라내고 있다. 그룹 표시는 그 인지 작업을 화면이 대신하게 만드는 것이다. 후속 U3-4 가 이 그룹을 그대로 조작 단위로 삼아 일괄 할당을 얹는다.

  1. 상대 시간 그룹 — 프로비저닝 서버에 인식된 시점을 기준으로 상대 시간을 표시하며 그 시간대별로 묶는다. 경계는 방금(10분) · 1시간 이내 · 오늘(24시간) · 그 이전이다.
  2. 스펙 그룹 — 같은 시간대 안에서 같은 하드웨어 스펙끼리 묶는다. 비교는 위 여섯 기준이며, 슬롯 위치와 나열 순서는 무시한다.
  3. 그룹 대상 자격 — 진단 수집으로 스펙이 채워진 서버만 그룹에 들어간다.
  4. per-server 현재 phase 배지 와 phase 필터.
  5. SSE 실시간 갱신 유지.
  6. CPU 소켓 인벤토리 수집 확장 — 메모리 · 디스크와 같은 꼴로 맞춘다.

그룹을 어떤 모습으로 그리나 (2026-08-10 확정)

블록위치기본 상태서버가 0대일 때
등록 진행 중목록 최상단접힘 — 헤더에 대수와 내역('등록만 됨' n대 · '수집 중' m대)이 보인다블록 자체를 그리지 않는다
상대 시간 구간등록 진행 중 아래, 최근순펼침구간 제목도 그리지 않는다
스펙 그룹각 시간 구간 안펼침해당 없음(멤버가 있어야 그룹이 생긴다)

빈 그룹 헤더를 그리지 않는다. 그룹은 있는 것을 묶어 보여주는 장치이지 시간축을 완주해 보여주는 장치가 아니다. 비어 있는 구간을 자리표시로 남기면 실제로 서버가 있는 구간을 찾는 데 눈이 한 번 더 든다.

접힘 여부가 곧 "지금 볼 것인가" 를 뜻한다. 운영자가 목록에서 찾는 대상은 스펙이 확인돼 조작할 수 있는 서버다. '등록 진행 중' 은 성격이 다른 주의 환기용 알림이라, 눈에 먼저 들어오되(최상단) 화면 높이를 잡아먹지 않아야(접힘) 한다. 아래로 내리면 스크롤 밖으로 밀려 못 보고, 펼쳐 두면 정작 본 목록이 밀린다. 나머지가 모두 펼침이므로 접혀 있다는 사실 자체가 신호가 된다.

  • 미완주 등록의 정리 정책 — DEC-G 참조. 이 슬라이스에서 정하지 않는다.

§3. URL / 데이터 흐름

목록 하나에 질의 파라미터가 둘 붙는다. 새 엔드포인트는 만들지 않는다.

메서드URL하는 일응답

GET/provisioning/server?phase=DIAGNOSE_LINUX그 phase 인 서버만 남긴 목록200 · 필터 상태가 URL 에 남는다

흐름은 세 걸음이다. 컨트롤러가 phase · pending 을 받아 조회 서비스에 넘기고, 조회 서비스가 서버와 그 상세를 함께 읽어 스펙 보유 여부로 두 갈래를 나눈 뒤 그룹을 조립하며, 뷰가 그 결과를 받아 접힘 상태만 반영해 그린다. 그룹 조립은 조회 서비스의 책임이고 뷰는 판단하지 않는다.

응답 구조는 GuestServerListResponse 하나로 모은다 — pending(등록만 됨 · 수집 중 두 묶음)과 timeGroups(각 구간 안에 스펙 그룹 목록)를 담고, 둘 다 비어 있으면 아예 원소가 없다. 뷰가 "비었으니 그리지 말자" 를 판단할 필요가 없게 만드는 것이 이 구조의 목적이다.

§4. 도메인 모델 (SSOT)

판정을 한 곳으로 모은다

스펙 보유 판정은 수집 축 자신이 답하게 하고, 엔티티가 그것을 위임 호출한다.

// DiscoveryStage — 상수가 자기 답을 갖는다(분기를 늘리지 않는다)
IPXE_REGISTERED    { public boolean isSpecAvailable() { return false; } },
DIAGNOSTIC_ENRICHED{ public boolean isSpecAvailable() { return true;  } };
public abstract boolean isSpecAvailable();

// GuestServerDetail — 호출부가 매번 enum 을 꺼내지 않게 하는 진입점
public boolean isDiagnosticEnriched() { return discoveryStage.isSpecAvailable(); }

호출부는 셋이 된다 — 엔진의 AgentReportService.isEnriched()(기존 판정을 이 메서드 호출로 교체), 이 화면의 조회 서비스, 그리고 후속 U3-4 의 그룹 할당 가드다. GuestServerDetail 행 자체가 없는 서버는 호출부가 흡수한다(§8 Q3).

그룹 키

여섯 기준을 정렬된 정규형 문자열로 만들어 비교한다. 슬롯 위치와 나열 순서는 키에 들어가지 않는다 — 같은 부품을 다른 슬롯에 꽂았다고 다른 그룹이 되면 안 되기 때문이다.

보드 모델 | CPU(모델 × 소켓 수) | 메모리(용량별 개수) | PCIe(kind × model) | 디스크(type · transport · size)
        ↑ 각 다중집합을 정렬한 뒤 결합한다

§7. 예외 계층

신규 예외 0. 이 슬라이스는 조회 전용이라 도메인 규칙을 어길 요청이 없다. 알 수 없는 phase 값은 Spring 의 MethodArgumentTypeMismatchException 이 400 으로 매핑하고, 새 분기를 만들지 않는다(§8 Q2).

DEC-A — 판정의 위치

후보는 셋이었다. 엔티티 도메인 메서드 단독, 수집 축 enum 의 상수별 구현, 그리고 GuestServerStatus.derive 를 본뜬 새 도출 enum 신설이다.

채택안은 enum 상수별 구현 + 엔티티 위임이다. DiscoveryStage 에 상수가 늘어날 때 — 미래에 OS 설치 완료 같은 수집 축이 붙는다면 — switch 를 늘리는 대신 새 상수가 자기 답을 들고 온다. "조건분기 legacy 확장 금지" 원칙이 정확히 이 형태를 요구한다.

새 도출 enum 신설은 버렸다. GuestServerStatus(운영 상태)와 차원이 겹치지 않는데 이름만 비슷한 도출 enum 이 둘 생겨 읽는 사람이 헷갈린다. 무엇보다 DiscoveryStage 가 이미 그 축이라 새로 만들 이유가 없다. 조회 서비스에 판정을 두는 안도 버렸다 — 도메인 지식이 서비스로 새면 U3-4 가 그 서비스를 다시 주입받아야 한다.

DEC-B — '등록 진행 중' 의 경계

그룹에 들어갈 자격은 스펙이 있는가 하나로 본다. 그룹 키를 계산할 재료의 유무가 곧 자격이므로 다른 축을 끌어올 이유가 없다. BOOTSTRAPPING 통과 여부로 판정하는 안은 버렸다 — 통과와 스펙 적재 사이에 "부팅은 됐으나 수집 중" 구간이 있어, 그 서버가 그룹 조립에 끌려 들어가면 키를 만들 수 없다.

다만 화면에서는 스펙 없는 서버를 한 덩어리로 뭉치지 않고 등록만 됨과 수집 중으로 나눈다. 앞은 PXE 만 찍고 진단으로 못 넘어간 서버라 부팅 · 네트워크를 봐야 하고, 뒤는 그냥 기다리면 되는 서버다. 조치가 다른 둘을 같은 칸에 넣으면 운영자가 매번 상세로 들어가 확인해야 한다. 두 축(DiscoveryStage × ProvisioningPhase)을 조합하면 새 도메인 개념 없이 나뉘므로 비용이 0 이다.

DEC-C — CPU 인벤토리 구조

CpuInfo cpu 단수를 List<CpuSocket> cpuSockets 로 바꾼다. HardwareSpec 문서가 "요약 통계가 아니라 슬롯 단위 인벤토리" 라고 못박았고 메모리 · 디스크 · PCIe 가 모두 그 원칙을 따르는데 CPU 만 예외로 남아 있었다. 개수는 행 수가 말하므로 count 필드 같은 파생 상태를 저장하지 않으며, 소켓별로 모델이 다른 비대칭 구성도 표현된다.

count 필드만 추가하는 안은 인벤토리 원칙을 깨고 비대칭 구성을 못 담아 버렸다. 새 필드를 만들고 기존 cpu 를 병존시키는 안도 버렸다 — 두 표현이 영구히 남으면 어느 쪽이 진실인지 모호해진다.

하위 호환은 파서가 흡수한다. 이미 저장된 행의 JSON 은 "cpu": { ... } 객체인데, 파서가 cpuSockets 배열과 구 cpu 객체를 둘 다 받아 구 형식은 1소켓 리스트로 승급해 읽는다. 관용 파싱 원칙(모르는 필드 무시 · 누락 null)과 정합하며 데이터 마이그레이션이 필요 없다. 재수집되면 실제 소켓 수로 갱신된다.

DEC-D — 그룹 키 산출 위치

hardware_spec 이 JSON 문자열 컬럼이라 SQL GROUP BY 가 불가능하다. 조회 후 애플리케이션에서 파싱해 묶는다 — 조회 서비스가 이미 관용 파싱을 하고 있어 새로 만들 인프라가 없고, 게스트 서버 수는 입고 단위(수십~수백)라 이 방식으로 충분하다.

그룹 키를 generated column 으로 물질화하는 안은 버렸다. JSON 경로 추출 컬럼이 되어 스키마가 수집 계약에 결합되고, 수집 항목이 바뀔 때마다 DDL 이 따라붙는다. "갈라지는 시점에 분리" 원칙상 지금 물질화할 근거가 없다.

한계 — 서버가 수천 대로 늘면 이 방식은 전건 로드가 된다. 그 시점에 물질화나 정규화 테이블로 승격한다(§11).

DEC-E — 필터와 SSE 의 공존

목록은 [data-live] 영역이 통째 교체되므로, 필터 입력을 그 안에 두면 상태가 바뀔 때마다 입력값과 핸들러가 사라진다. U3-1 에서 할당 폼으로 실제로 겪은 결함이다.

필터를 영역 밖에 두고 상태를 URL 에 싣는다. 결정적 근거는 server-stream.js 의 refetch 가 fetch(location.href) 라는 점이다 — 필터가 URL 에 있으면 서버가 필터된 목록을 그대로 다시 렌더해 주므로 복원 코드가 0 이다. 프레임워크가 이미 하는 일에 얹는 것이지 새로 만드는 것이 아니다.

영역 안에 두고 재렌더 후 복원하는 안은 버렸다. 같은 결함을 코드로 되막는 방식이라, 복원 로직이 빠지는 순간 사고가 재발한다. 클라이언트 사이드 필터링도 버렸다 — 서버 필터와 클라이언트 필터가 두 벌 판정이 되어 SSOT 를 깬다.

DEC-F — 시간 구간의 경계

고정 구간을 쓴다. 연속 등록 간격으로 입고 세션을 군집화하는 안은 임계값이라는 매직 상수를 낳고 운영자가 결과를 예측할 수 없다("왜 이 둘이 다른 그룹이지?"). 고정 구간은 화면만 보고도 규칙을 안다. 실사용에서 부족하다고 드러나면 그때 승격한다.

DEC-G — 미완주 등록의 정리 정책

이 슬라이스에서 정하지 않는다. 화면 작업에 회수 정책을 얹으면 슬라이스가 가시화와 생명주기 두 성격으로 갈라지고, 며칠 방치면 무엇을 할지는 실기 운영 관찰이 있어야 정할 수 있다.

미루면서 드러나는 문제는 적어 둔다 — '등록 진행 중' 이 화면의 일급 개념이 되면, PXE 로 행만 만들고 체크인에 실패한 게스트가 그 칸에 영구히 잔류한다. lastSeen 은 이미 기록되고 있으므로 나중에 정책을 얹을 재료는 보존돼 있다.

DEC-H — 접힘 상태의 보존 (2026-08-10 신설)

아코디언을 넣자 DEC-E 와 같은 문제가 따라왔다. 접힘 상태도 [data-live] 교체에 지워진다. 전부 URL 에 싣는 안, 전부 화면에만 두는 안, 그리고 비대칭으로 가르는 안을 놓고 비교했다.

채택안은 '등록 진행 중' 의 펼침만 URL(?pending=open)에 싣고, 스펙 그룹의 접힘은 싣지 않는 것이다. 근거는 기본값이 다르다는 데 있다. '등록 진행 중' 은 접힘이 기본이라 사용자가 연 것은 "지금 이걸 보고 있다" 는 의도가 분명하고, 갱신 때마다 닫히면 작업이 끊긴다. 스펙 그룹은 펼침이 기본이라 접은 것은 일시적 정리이고, 갱신 시 되돌아와도 잃는 것이 적다.

전부 URL 에 싣는 안은 버렸다. 그룹이 여러 개라 질의 문자열이 길고 지저분해지며, 그룹 키가 스펙 변경으로 바뀌면 URL 에 남은 값이 어느 그룹을 가리키는지 알 수 없게 된다. 전부 화면에만 두는 안도 버렸다 — 펼쳐 놓고 들여다보던 '등록 진행 중' 이 SSE 신호마다 닫히는 것은 실사용에서 곧 불평이 된다.

DEC-I — 회수된 서버의 그룹 편입 (2026-08-11 · CP5 발견에서 확정)

CP5 에서 회수된(DECOMMISSIONED) 서버가 스펙 그룹에 그대로 남는 것을 발견했다. 그룹은 후속 U3-4 가 일괄 할당의 조작 단위로 쓸 것이므로, 조작할 수 없는 서버가 섞이면 그 단계에서 문제가 된다.

채택 — 그룹에는 그대로 두고, 배제는 U3-4 의 그룹 할당 가드가 맡는다. 이 목록의 일은 "무엇이 있는지 보여주는 것" 이고 회수된 서버도 운영자가 보아야 할 대상이다. "무엇을 조작할 수 있는가" 는 조작하는 쪽이 판정하는 편이 낫다 — 세팅 정의서의 assignBlockReason() 이 이미 같은 구도다 (화면은 후보를 보여주고, 차단 판정은 할당 경로가 소유한다).

탈락 — 그룹에서 빼는 안은 회수된 서버가 목록에서 아예 사라져 운영자가 회수 이력을 확인할 수 없게 된다. 별도 '회수됨' 블록을 새로 만드는 안은 이 슬라이스의 화면 구조를 한 축 더 늘리는 일이라, 필요가 실제로 드러난 시점에 정하는 편이 맞다.

U3-4 로 넘기는 조건 — 그룹 할당 가드는 스펙 유무뿐 아니라 회수 여부도 함께 보아야 한다. 이 조건을 모르고 시작하면 그대로 새는 자리다(§11).

Q1 은 되돌리기 비용이 낮은 값이다. 입고는 수 분 안에 여러 대가 몰려 들어오므로 10분 버킷이 "방금 들어온 묶음" 과 "아까 것" 을 실제로 갈라 주며, 값은 RegistrationAgeBucket 상수 한 곳만 고치면 된다.

Q2 를 열어 두었던 이유는 2026-08-07 관찰 때문이었다 — 브라우저 Accept 의 */* 탓에 JSON advice 가 이겨 주소창 진입에도 raw JSON 이 노출됐다. 그러나 그 뒤 병합된 S10 이 원인을 고쳤다. DocumentNavigationAcceptFilter 가 Sec-Fetch-Dest: document 요청의 Accept 를 좁혀 보고하므로 주소창 진입은 HTML 오류 페이지를 받는다. 그래서 400 을 그대로 채택하되, CP5 항목 B1 에서 실제 화면을 눈으로 확인한다 — 프레임워크가 고쳤다는 말을 검증 없이 믿지 않는다.

Q3 은 작성 브리프의 오류를 바로잡은 항목이다. 브리프는 "엔티티 메서드가 detail 부재까지 흡수한다" 고 적었으나 인스턴스 메서드는 수신자가 null 이면 호출 자체가 불가능하다. 실제로 호출부 둘 다 이미 부재를 다루고 있어(엔진은 Optional.map(...).orElse(false), 조회 서비스는 맵 조회의 null 검사) 판정 본문은 어차피 한 곳이며, 엔티티에 static 을 늘리지 않는 쪽을 택했다.
