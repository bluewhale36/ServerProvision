§1. 현재 상태 (진단)

이 슬라이스는 상위 계획서 plan/26-08-10_12-43-50_MK4-3_plan.html 아래의 마지막 구현 슬라이스다. MK4-3-1 이 설정 일곱 중 다섯을 데이터베이스로 옮겼고, 남은 둘 — 점검 주기 — 이 여기 대상이다. 들어가서 보니 알려진 문제 하나 옆에 셋이 더 있었다.

#문제지금 어떻게 드러나는가
1주기를 화면에서 못 바꾼다설정 파일 수정 + 재기동이 유일한 경로
2다시 띄울 때마다 주기가 처음부터 다시 센다하루 한 번 재기동이면 정밀 점검이 영영 안 돈다
3두 스케줄이 겹치면 정밀이 조용히 버려진다debug 로그 한 줄만 남고 그 회차는 사라진다
4주기가 실제로 어떻게 도는지 확인할 방법이 없다관찰하려면 설정 파일을 고치고 다시 띄워야 한다

문제 1 — 주기를 화면에서 못 바꾼다

PathReconciliationService 에 주기 점검이 둘 걸려 있다.

@Scheduled(
        fixedRateString = "${reconciliation.scan.interval-ms:3600000}",
        initialDelayString = "${reconciliation.scan.interval-ms:3600000}")
public void scheduledQuickScan() { ... }

@Scheduled(
        fixedRateString = "${reconciliation.scan.deep-interval-ms:86400000}",
        initialDelayString = "${reconciliation.scan.deep-interval-ms:86400000}")
public void scheduledDeepScan() { ... }

이 문자열은 빈을 만들 때 한 번 해석되고 그대로 굳는다. 그래서 주기를 바꾸려면 application.properties 를 고치고 애플리케이션을 다시 띄워야 한다. 운영자에게는 불가능한 절차다.

MK4-3-1 은 이 사정 때문에 다른 다섯 항목만 데이터베이스로 옮기고 주기 둘은 저장 대상에서 뺐다. 화면에는 읽기 전용으로 남기고 EffectTiming.RESTART_REQUIRED("설정 파일에서만 변경 가능") 를 붙였다. 저장할 수 있게 해 놓고 반영되지 않는 상태 — 휴지통 설정이 지금 그 상태다 — 를 만들지 않으려는 조치였고, 해소 시점을 이 단계로 못박아 두었다.

문제 2 — 다시 띄울 때마다 주기가 처음부터 다시 센다

initialDelayString 이 주기와 같은 값이다. 그래서 기동 후 첫 발동이 일반은 1시간 뒤, 정밀은 24시간 뒤다. 하루에 한 번이라도 배포나 재기동이 있으면 정밀 점검은 영영 발동하지 않는다. 기동 직후 점검(onStartup)은 일반만 돌린다 — triggerScan(false) 로 고정돼 있다. MK4-2 가 목록 화면에 "남아 있는 정밀 점검 기록이 없습니다" 를 띄우게 만든 원인 중 하나가 여기 있다.

문제 3 — 두 스케줄이 겹치면 정밀 점검이 조용히 버려진다

둘 다 기동 시점부터 세므로 일반은 +1h, +2h, … 정밀은 +24h 에 발동하고 24시간마다 정확히 겹친다. spring.task.scheduling.pool.size 를 설정하지 않아 스케줄러 스레드는 1개다(실측 — application.properties 에는 spring.task.execution.thread-name-prefix 만 있다). 이 저장소의 @Scheduled 는 열둘이고 전부 그 한 스레드를 나눠 쓴다 — 겹침이 이 둘만의 사정이 아니다. 두 작업은 같은 스레드에서 잇달아 실행되고, 앞의 일반 점검이 running 을 세운 직후 정밀 점검이 그것을 보고 돌아간다.

public void scheduledDeepScan() {
    if (running.get()) {
        log.debug("[reconciliation] deep 주기 스캔 skip (이전 스캔 RUNNING)");
        return;   // 다음 기회는 24시간 뒤
    }
    ...
}
debug 로그 한 줄만 남고 그 회차는 사라진다. 남는 흔적이 없어 운영자는 정밀 점검이 걸러졌다는 것을 모른다. 이 문제는 조건부다 — 두 발동이 같은 순간에 몰릴 때만 일어난다. 위 계산대로면 몰리지만, 실측 재현은 CP5 에서 시도한다(주기를 화면에서 바꿀 수 있게 되면서 비로소 재현이 가능해진다).

문제 4 — 주기가 실제로 어떻게 도는지 확인할 방법이 없다

짧은 주기로 바꿔 관찰하려면 설정 파일을 고치고 다시 띄워야 한다. 그래서 문제 2 · 3 은 코드를 읽어야만 보인다. 이 단계가 주기를 화면으로 꺼내면 관찰 자체가 가능해진다.

지금 화면이 하는 말

설정 화면 아래에 "점검 주기" 카드가 읽기 전용으로 있고 이렇게 적혀 있다 — "아래 둘은 아직 화면에서 바꿀 수 없습니다. … 다음 단계에서 화면으로 옮겨 옵니다." 이 단계가 그 문장을 지우는 단계다.

§2. 요구사항 (확정) + 비목표

이 단계가 하는 일

  1. 점검 주기 두 값을 데이터베이스로 옮기고 화면에서 바꾸게 한다.
  2. 저장이 다시 띄우지 않고 반영되게 실행 구조를 바꾼다.
  3. 그 과정에서 문제 2 · 3 을 구조적으로 없앤다 — 고치는 것이 아니라 일어날 자리를 없앤다.
  4. 화면이 다음 점검 예정 시각을 밝힌다.

요구를 두 줄로 못박고 설계에 들어간다.

  • R1 — 저장이 다시 띄우지 않고 반영된다.
  • R2 — 반영이 언제 되는지 화면이 말할 수 있다(MK4-3 의 D1 — 화면은 거짓말하지 않는다).

점검 깊이 배관 전면 정비performScan · runAsync · DriftReport.deep 까지는 손대지 않는다
이 단계의 원칙 — 언제 다음에 볼지 시각으로 밝힌다.
MK4-2 가 "안 본 것은 안 봤다고 밝힌다" 를, MK4-3-1 이 "안 고치는 중이면 안 고치는 중이라고 밝힌다" 를 세웠고 여기서 셋째가 온다. 셋 다 같은 뿌리다 — 화면은 거짓말하지 않는다.
🎬 미리보기 — 라이브 UX 데모

체험시키는 것은 하나다 — 같은 설정에서 현행 구조와 개편 구조가 어떻게 다르게 도는가. 주기 두 값을 넣고 시간을 흘려 보면 사건 로그에 무슨 일이 있었는지 한 줄씩 쌓인다. 버려진 정밀 점검은 붉게 표시된다.

실행 구조 :
점검 주기 (분) :
시간 · 조작 :

세 가지를 눌러 보면 된다

  1. 주기를 바꿔 본다. 개편 모드에서는 다음 예정 시각이 즉시 다시 계산되지만, 현행 모드에서는 아무 일도 일어나지 않는다.
  2. 현행 모드에서 [재기동] 을 24시간 안에 반복해 본다. 정밀 점검이 한 번도 안 돈다(문제 2).
  3. 현행 모드에서 두 주기를 같게 둔다.(예 : 둘 다 10 으로 바꾸고 [재기동] 한 뒤 [10분 경과]) 겹치는 순간 정밀이 버려진다(문제 3). 같은 값으로 개편 모드를 돌리면 정밀이 돌고 일반도 함께 만족된다.

개편 모드의 판정 — ScanSchedule.dueDepth 와 같은 규칙

function dueDepth(now, lastAnyScan, lastDeepScan, quickMin, deepMin) {
    const deepDue  = lastDeepScan === null || now >= lastDeepScan + deepMin;
    const quickDue = lastAnyScan  === null || now >= lastAnyScan  + quickMin;
    if (deepDue)  return 'DEEP';    // 정밀이 일반을 덮는다
    if (quickDue) return 'QUICK';
    return null;
}

현행 모드는 현재 코드를 그대로 흉내 낸다 — 기동 시점부터 initialDelay 만큼 기다린 뒤 fixedRate 로 발동하고, 같은 분에 둘이 겹치면 정밀을 버린다. [재기동] 은 두 타이머를 0 으로 되돌린다.

§4. 도메인 모델 (SSOT)

ScanDepth — enum, maintenance/reconciliation/enums/

상수뜻
QUICK마커와 위치만 본다
DEEP파일 내용의 지문까지 다시 계산한다

도메인 메서드 — boolean covers(ScanDepth other). DEEP.covers(QUICK) 은 참이다. 정밀 점검은 일반 점검이 보는 것을 모두 보기 때문이며, 이 관계가 심박의 결정 규칙이자 "정밀을 돌리면 일반도 만족한다" 의 근거다.

지금은 triggerScan(false) · triggerScan(true) 로 부른다. 호출부만 보면 참이 무엇인지 알 수 없어 가독성 규약이 금지하는 무명 boolean 인자에 해당한다.

ScanInterval — record VO, maintenance/reconciliation/vo/

Duration 을 감싼다. 주기는 하한 · 상한이 있고 사람이 읽는 표기가 붙는 값이라 long ms 로 들고 다니면 그 셋이 코드 곳곳으로 흩어진다(원시 타입 집착 금지).

메서드하는 일
isDue(Instant lastScanAt, Instant now)만기인가. lastScanAt 이 null 이면 항상 참
nextDueAt(Instant lastScanAt)다음 예정 시각. 화면이 그대로 보여 준다
toMinutes()저장 · 입력 단위
display()"60분 (1시간)" 같은 사람이 읽는 표기

lastScanAt 이 null 일 때 항상 만기인 이유 — 한 번도 안 봤으면 지금 봐야 한다.

"아무것도 할 게 없다" 를 세 번째 상수로 만들지 않고 Optional 로 둔다.

기준 시각을 무엇으로 잡는지가 이 모델의 결정이다.

  • 일반의 기준은 마지막 점검(정밀 포함)
  • 정밀의 기준은 마지막 정밀 점검

정밀이 일반을 덮으므로 정밀 점검은 일반의 시계도 되돌린다. 반대는 아니다.

수동 점검도 기준 시각에 든다. 주기의 뜻이 "최소 이 간격마다 한 번은 본다" 이므로 방금 사람이 돌린 점검을 못 본 척할 이유가 없다. 지금은 타이머가 수동 점검을 모른다 — 사람이 12시 55분에 돌려도 13시에 또 돈다.

조회는 이미 있다. DriftReportRepository.findFirstByOrderByScannedAtDesc 와 findFirstByDeepTrueOrderByScannedAtDesc — 뒤엣것은 MK4-2 가 커버리지 배너를 위해 만든 것이다. 새 repository 메서드는 없다.

보관 개수 하한이 여기서 두 번째 역할을 한다

기준 시각을 drift_report 에서 읽으므로 보고서가 전부 잘려 나가면 기준을 잃는다. 보관 개수 하한이 1 이라 최소 한 건은 남고, 마지막 정밀 점검 기록이 잘려 나간 경우에는 정밀이 만기로 판정되어 곧 한 번 돈다. 모르면 본다는 안전한 방향이다.

Step 9 가 N/A 인 이유 — MK4-3-1 의 D5 개정이 값을 치른다

reconciliation_setting 은 항목별 행이고 열거형 상수가 기본키다. 주기 둘은 이미 그 열거형에 있고 저장만 안 했을 뿐이라, 저장 대상으로 바꾸는 데 DDL 이 필요 없다. 행이 없는 항목은 기본값으로 돌고 첫 저장에 행이 생긴다.

단일 행 엔티티였다면 컬럼 둘을 더하는 ALTER TABLE 이 필요했다. MK4-3-1 에서 저장 형태를 단일 행에서 항목별 행으로 되돌린 결정이 한 단계 만에 값을 치렀다.

§8. 결정 · 주의 · Open Questions

D1 — 실행 구조는 짧은 고정 심박 + 만기 판정으로 간다

안방식R1R2판정
가SchedulingConfigurer + Trigger△△탈락
나저장 시 취소 후 재등록○△탈락
다짧은 고정 심박 + 만기 판정○○채택
라외부 스케줄러(Quartz 등)○○탈락

안 '가' 탈락 사유. Spring 이 "간격이 상수가 아닐 때" 를 위해 둔 정식 확장점이다. Trigger.nextExecution 이 매 실행 직후 호출되므로 그 안에서 설정을 읽으면 다음 간격은 새 값으로 잡힌다. 그런데 이미 대기 중인 발동은 옛 값으로 잡혀 있고 저장은 그것을 깨우지 못한다. 정밀 점검을 24시간에서 1시간으로 줄여도 최대 24시간을 기다린다 — 이 단계가 없애려는 바로 그 체감이 남는다. 대기 중인 발동을 다시 잡으려면 결국 취소 · 재등록(안 '나')이 필요하므로 이 안은 손으로 하는 부분을 없애지 못하고 자리만 옮긴다. 재기동 시 마지막 점검 시각을 모른다는 문제 2 도 그대로 남는다.

안 '나' 탈락 사유. 저장 즉시 반영된다. 대신 ScheduledFuture 보관 · 취소 의미(실행 중인 점검을 죽일 것인가) · 동시 저장 경합을 직접 다뤄야 한다. 더 나쁜 것은 저장이 주기를 처음부터 다시 세게 만든다는 점이다. 1시간 주기에서 50분마다 설정 화면을 눌러 저장하면 점검은 영영 돌지 않는다. 운영자가 설정을 만지는 행위가 점검을 굶기는 구조는 받아들일 수 없다.

안 '다' 채택 사유. 1분 고정 주기로 도는 심박이 매번 묻는다 — "마지막 점검으로부터 설정 간격이 지났는가." 지났으면 점검한다.

  • R1 — 심박이 설정을 매번 읽으므로 저장은 1분 안에 반영된다.
  • R2 — 다음 발동이 마지막 점검 시각 + 간격 이라는 계산 가능한 값이 된다. 화면이 그 시각을 그대로 보여 준다. 안 '가' · '나' 는 발동 시각이 스케줄러 내부에 있어 화면이 알 수 없다.
  • 문제 2 해소 — 기준 시각을 drift_report 에서 읽으므로 재기동해도 이어진다. 밀렸으면 뜨자마자 돈다.
  • 문제 3 해소 — 한 번의 심박이 하나의 결정을 내린다. 두 스케줄이 경합할 자리가 사라진다.
  • 판정이 순수 함수가 되어 스케줄러를 구동하지 않고 진리표로 덮을 수 있다.
  • 비용 — 1분마다 조회 두어 번. 이미 같은 주기의 심박이 셋 있다(NudgeRegistry · DeleteIntentRegistry · BackgroundJobService).

안 '라' 탈락 사유. 단일 JVM · 작업 둘에 도입할 물건이 아니다.

프레임워크에 맡길 것과 도메인이 쥘 것. 채택안도 @Scheduled 를 쓴다. 다만 프레임워크에는 변하지 않는 부분(1분마다 깨워 달라)만 맡기고, 변하는 부분(지금이 점검할 때인가)은 도메인이 쥔다. "분기는 프레임워크에 올린다" 는 원칙과 어긋나지 않는다 — 여기서 프레임워크가 대신해 줄 수 있는 분기가 없기 때문이다. 안 '가' 가 그 시도이고, 대기 중 발동을 못 깨워 요구를 못 채운다.

D2 — 심박 주기는 1분 고정이고 설정으로 열지 않는다

설정으로 열면 누군가 1시간으로 두고 "저장은 1분 안에 반영된다" 는 약속이 조용히 깨진다. 이름 붙인 상수로 둔다. 첫 심박은 1분 뒤로 미뤄 기동 직후 점검과 겹치지 않게 한다 — 겹쳐도 running 가드가 막지만, 막히는 것과 안 겹치는 것은 다르다.

D3 — 주기의 저장 단위는 분이다

심박 해상도가 1분이라 그보다 잘게 설정할 수 있게 하면 설정한 값과 실제 동작이 어긋난다. 밀리초는 화면에서 세 자리 오타를 부른다(3600000 과 360000 은 눈으로 구별되지 않는다).

D4 — 효과 시점은 IMMEDIATE("저장 즉시") 를 쓰고 새 상수를 만들지 않는다

저장하는 순간 다음 예정 시각이 다시 계산되고 화면이 그것을 보여 준다. 심박까지의 최대 1분은 구현 사정이지 운영자가 셀 시각이 아니다.

D5 — EffectTiming.RESTART_REQUIRED 를 제거한다

쓰는 항목이 없어지는데 "설정 파일에서만 변경 가능" 이라는 상수를 남기면 다음 사람이 그리로 새 항목을 넣는다. 함께 무의미해지는 isPersisted() · isEditable() 도 제거하고, 응답의 editable 과 템플릿의 읽기 전용 분기도 걷는다.

비채택 남겨 둔다. 탈락 사유 : 휴지통 cron 이 나중에 쓸지 모른다는 것은 "갈라질 수 있으니 미리 분리" 이고 규약이 금지한다. 필요해지는 시점에 되살리면 된다.

D6 — 설정 파일 값을 한 번 이관한다

행이 없을 때 reconciliation.scan.interval-ms 를 분으로 환산해 쓴다(나머지는 올림). 30분으로 맞춰 돌던 환경이 저장 한 번 없이 60분으로 늘어나면 안 된다. MK4-3-1 이 다른 다섯에 적용한 기준과 같다.

D7 — 트리거를 한 곳에 모은다

@Scheduled 둘과 @EventListener(ApplicationReadyEvent) 하나가 ReconciliationScheduler 로 옮겨 온다. 지금은 점검을 여는 문이 셋으로 흩어져 있고, 문제 3 이 오래 안 보인 이유가 거기 있다. PathReconciliationService 는 triggerScan 을 그대로 갖고 트리거 책임만 덜어낸다(1200줄 서비스에서 책임을 떼는 R4~R6 의 분할 방향과 같다).

옮겨 온 뒤에도 기동 직후 점검은 일반 점검으로 돈다. 그 항목의 뜻이 "꺼져 있는 동안 디스크가 바뀌었을 수 있어 한 번 맞춰 본다" 이고, 마커와 위치를 보는 것으로 그 물음에 답이 되기 때문이다. 정밀 점검이 밀려 있다면 1분 뒤 첫 심박이 그것을 판정해 돌리므로, 기동 점검이 정밀까지 떠안을 이유가 없다.

D8 — 짧은 주기는 거절하지 않고 경고한다

DriftReport 에 scanDurationMs 가 이미 있다. 설정하려는 주기가 같은 깊이의 지난 점검 소요 시간보다 짧으면 화면이 알린다 — "지난 정밀 점검은 4분 12초 걸렸습니다. 주기를 그보다 짧게 두면 일부 회차가 건너뛰어집니다." 막지는 않는다. 운영자가 사정을 알고 그렇게 두는 경우가 있고, 실제로 일어나는 일은 회차 건너뜀뿐이라 되돌릴 수 없는 손해가 없다.

이 경고는 추측이 아니라 그 설치 환경의 실측값에서 나온다는 점이 중요하다 — 자원이 10개인 환경과 1000개인 환경에 같은 숫자를 권할 수 없다.

주의

MK4-3-1 계획서의 한 문장을 정정한다. ReconciliationSettingsService.initialValueOf 의 주석에 "MK4-3-2 가 주기를 옮겨 올 때는 옮겨 올 설정 파일 값이 이미 이 화면 밖에 있으므로 여기에 줄이 늘지 않는다" 고 적혀 있다. 틀렸다. 이관 원본(reconciliation.scan.interval-ms)이 설정 파일에 있으므로 다른 다섯과 똑같이 두 줄이 는다. 구현 시 그 주석도 함께 고친다.
  • 폼 규약은 그대로다. .claude/domain-conventions/new-form.md 의 판정은 "핸들러가 BindingResult 를 받는가" 이고, 설정 화면은 이미 받는다. 필드가 늘어도 data-native-submit 개수는 변하지 않으므로 FormSubmissionConventionTest 의 기대값도 그대로다.
  • 여러 인스턴스는 가정하지 않는다. 지금도 AtomicBoolean running 이 단일 JVM 을 전제한다. 심박도 같은 전제 위에 선다 — 새로 생기는 제약이 아니다.
  • 스케줄러 스레드 풀이 1이다. 이 저장소에는 @Scheduled 가 열둘 있고 전부 한 스레드에서 차례로 돈다. 어느 하나가 오래 붙들면 나머지 일정이 함께 밀린다. 영역 횡단이라 이 단계에서 건드리지 않고 관찰만 남긴다.
