§0. 한눈 요약

E4-1-a-3 은 게스트에게 Windows 설치 스크립트를 내주는 데까지 갔고 거기서 멈췄다. 설치에 성공한 게스트도 원장의 RUNNING 행에 그대로 서 있고, 드라이버는 아무도 넣어 주지 않으며, 다 쓴 토큰은 회수되지 않는다. 이 슬라이스는 그 뒤를 잇는다 — 설치 이후에 일어나야 할 일 넷을 채운다.

  • 앱이 sources/$OEM$ 을 조립한다 — Subprogram(DRIVER) 자원의 디렉토리 트리를 복사하고, 첫 로그온 스크립트 둘과 매니페스트를 함께 쓴다
  • 첫 로그온 스크립트가 앱에 완료를 보고한다 — 게스트 토큰을 들고 전용 엔드포인트로 결과(문제 장치 수 · 설치된 드라이버 수 · 컴퓨터 이름)를 올린다
  • 완료가 원장 행을 닫고 토큰을 회수하고 커서를 종단시킨다 — 서빙 시점에 적어 둔 메타는 지우지 않고 완료 메타를 덧댄다
  • 재PXE 가 없는 게스트도 닫힌다 — 시한과 유예를 넘긴 설치 중 게스트를 스윕 워커가 실패로 전환한다
변경 범위 — 엔티티 · Repository · DDL 은 건드리지 않는다. 원장은 기존 ProvisioningHistory 를 그대로 쓰고, 새 ProvisioningPhaseStep 도 만들지 않는다. 추가되는 것은 설정 키 둘과 자바 클래스 열하나다.
§1. 현재 상태 (진단)

아래는 이 슬라이스가 손대는 자리 주변에서 지금 실제로 무슨 일이 벌어지는지를 코드와 실측 기록에서 확인한 것이다.

1-1. E4-1-a-3 이 남긴 공백 넷

앞 슬라이스는 자기 경계를 명시하고 멈췄다. 그 경계가 그대로 이 슬라이스의 착수 지점이다.

#공백지금 남는 결과
①완료 보고를 받는 경로가 없다설치에 성공한 게스트도 카드가 "설치 중" 으로 남는다
②토큰은 재서빙 · 실패 때만 회수된다완료한 게스트의 토큰이 계속 살아 있다
③RUNNING 행을 닫는 쪽이 서빙 메타를 보존해야 한다는 제약이 인계됐다지키지 않으면 이미지 · 서빙 시각 · 재진입 수가 close 때 사라진다
④부트 순서가 디스크 우선이면 재PXE 가 없다시한 판정이 영원히 일어나지 않는다 (앞 슬라이스 D-8 이 적어 둔 공백)

1-2. 실측 2 · 3호가 고정한 계약 — 구조를 바꾸지 않는다

드라이버를 어디에 두면 Windows Setup 이 알아서 집어 가는지는 실기에서 이미 확인됐다. sources\$OEM$\$1\SPV\Drivers\<묶음> 아래 INF(Setup Information File — 장치 드라이버 설치 정보 파일) 세트를 두고, $$\Setup\Scripts\SetupComplete.cmd 가 묶음 폴더를 돌며 pnputil /add-driver "<폴더>\*.inf" /subdirs /install 을 부른다. 로그는 C:\SPV\setupcomplete.log 에 쌓이고, 끝에서 pnputil /enum-devices /problem 으로 남은 문제 장치를 센다. 이 절차로 문제 장치가 92 개에서 0 개로 떨어졌고 드라이버 47 개가 설치됐다.

주의할 조건이 둘 있다. SetupComplete.cmd 는 OEM 제품 키로 설치할 때만 건너뛰어진다 — 볼륨 라이선스 키(GVLK)로 설치하는 우리 경로에서는 실행된다. 그리고 설치된 Windows Server 2025 에는 curl.exe 와 PowerShell 이 내장돼 있다. WinPE 에는 없었던 그 둘이 설치 후에는 있으므로, 완료 보고를 게스트가 직접 보낼 수 있다.

1-3. 드라이버는 이미 자원으로 등록돼 있다

드라이버는 Subprogram 자원이다. kind 가 DRIVER 또는 UTILITY 이고, boardModel 이 null 이면 보드 무관 공용이다. 파일은 단일 파일이 아니라 treeRootPath 아래 디렉토리 트리이고, manifestHash · fileCount · totalBytes 로 내용이 요약돼 있으며 own/effective 라이프사이클을 탄다. 조회는 findAllByKindAndIsDeletedFalse · findByKindAndCommonScope · findByKindAndBoardId 가 이미 있다.

OS 구분 속성이 없다 — Subprogram 에는 "이 드라이버가 Windows 용인가" 를 적는 자리가 없다. Windows 드라이버인지는 트리 안에 *.inf 가 있는가 로만 알 수 있다(토론 Q10). 이 사실이 §8 D-2 의 대상 선정과 제외 목록 설계를 좌우한다.

1-4. 보고 창구는 있는데 완료를 여기로 받을 수 없다

게스트 에이전트의 보고 창구는 GuestAgentRestController 의 셋이다 — /api/pxe/v1/agent/checkin · /agent/steps · /agent/steps/{id}/close. 모두 X-Guest-Token 헤더로 신원을 확인하고, 처리는 AgentReportService(engine.diagnose 패키지)가 한다. 토큰으로 게스트를 찾는 requireByToken 은 그 클래스의 private 메서드이고, 게이트는 GuestServerStatus.derive 가 PROVISIONING 인지를 본다. close 는 onStepClosed 훅과 directiveFor 를 부른다.

완료를 close 로 받으려면 게스트가 stepId 를 알아야 한다. 그런데 Windows 설치의 서빙 행은 렌더가 끝난 뒤 훅에서 열린다 — 렌더본에 그 id 를 담을 방법이 없다. 이것이 §8 D-4 에서 전용 엔드포인트를 고르는 이유다.

1-5. 종결 규칙은 이미 서 있다

커서 전진과 종단은 PhaseCursorAdvancer.advanceOrComplete 하나가 맡는다 — 다음 소유 phase 가 있으면 그 앞에 pre-position 하고, 없으면 markCompleted 로 닫는다. 종단에 이른 게스트는 dispatch 4행이 받아 completedExit(exit 한 줄)를 돌려준다. OwnedPhases 는 TESTING 을 소유하지 않으므로, OS 설치만 담은 Windows 정의서에서는 완료가 곧 종단이다. 이 슬라이스는 규칙을 새로 만들지 않고 이 메서드를 부르기만 한다.

1-6. 대시보드와 스케줄에는 따라 쓸 관용구가 있다

1-7. 운영 계정 경계 — 지금은 앱이 못 쓴다

런북 §14-1 은 /srv/pxe/win2025 를 spvadmin 소유로 둔다. 추출 절차가 그 계정으로 도는 디렉토리이기 때문이다. 앱은 provisioning 계정으로 도는데, 이 슬라이스에서 앱이 sources/$OEM$ 을 직접 쓰게 되므로 그 디렉토리에 한해 쓰기 권한이 필요하다. 소스 전체를 열지 않는다(§8 D-9).

§2. 요구사항 (확정) + 비목표

토론 1호의 D4 · D9(층 A · 층 C) · Q2 · Q5 · Q10 확정과 실측 2 · 3호의 계약, E4-1-a-3 이 인계한 제약 넷을 합쳐 일곱 줄로 고정한다.

#요구판정 · 기록 지점
R1앱이 sources/$OEM$ 을 조립한다 — 드라이버 트리($1\SPV\Drivers\<자원>) + 스크립트 둘($$\Setup\Scripts\SetupComplete.cmd · $1\SPV\spv-report.ps1) + 매니페스트WindowsOemPayloadAssembler.sync
R2조립 상태를 관측한다 — 대시보드 슬롯 둘(스크립트) + chip "드라이버 페이로드"(최신 n종 / 갱신 필요 / 미조립 · 제외 k) · 준비도 12행(스크립트 미조립이면 BLOCKED)WindowsOemManifest.compare · WindowsInstallReadiness
R3첫 로그온 스크립트가 앱에 완료를 보고한다 — POST /api/pxe/v1/agent/windows/complete(X-Guest-Token · JSON 은 computerName · osVersion · driversAdded · problemDeviceCount · problemDevices[] · setupCompleteLogTail)WindowsInstallCompletionService.complete
R4완료는 열린 서빙 행을 SUCCEEDED 로 닫되 서빙 메타를 보존하고 완료 메타를 덧댄다 — 토큰 회수 · 커서 전진/종단 · 중복 보고는 200 무동작WindowsInstallCompletionService + PhaseCursorAdvancer
R5재PXE 가 없는 게스트의 시한도 닫힌다 — 서빙 시각 + 시한 + 유예를 지난 STEP_RUNNING 게스트를 INSTALL_TIMEOUT 으로 실패 전환하고 토큰을 회수한다WindowsInstallTimeoutSweeper.sweep
R6카드가 완료 상태를 보인다 — 완료 시각 · ComputerName · 드라이버 n · 문제 장치 n(목록) · 종단 또는 다음 phaseGuestServerQueryService.windowsInstallOf
R7게스트 접점 검증은 하네스 windows-install-cycle.sh 의 complete 모드로 하고, 대시보드 조립 버튼과 상세 카드는 브라우저로 본다CP5

R2 와 R4 는 성격이 다르다. 드라이버가 낡은 것(STALE)은 설치를 막지 않는다 — 옛 드라이버로도 설치는 되기 때문에 chip 경고로 알리는 데서 그친다. 반면 스크립트 둘이 아예 없으면 완료 보고 자체가 불가능하므로 준비도가 막는다. 차단은 "그것이 없으면 절차가 성립하지 않는 것" 에만 건다는 기준을 그대로 따른다.

비 목표 — 이 슬라이스에서 다루지 않고 어디로 가는지 :
  • 자원 등록 시 INF 존재 경고(관리 폼) — 등록 화면 소관이라 S 계열로 적립한다. 여기서는 조립 시점의 제외 목록으로만 드러낸다
  • spvout 같은 별도 쓰기 공유 — 완료 보고가 HTTP 로 오므로 필요 없다
  • 보드별 $OEM$ 분기 — 토론 Q2 가 공용 하나로 확정했다
  • 드라이버 서명 검증 — 운영 절차가 담보한다
  • BurnInTest 등 TESTING phase → E5-W
  • Secure Boot · 리눅스 설치

4-5. 스윕 — WindowsInstallTimeoutSweeper.sweep

        
대상  progress 중 currentStep == OS_INSTALLING · motion == STEP_RUNNING · !failed · !completed
판정  ledger.latestRunning(guestId) 의 served + installTimeout + grace < now
처리  ledger.failRunning(server, progress, row, INSTALL_TIMEOUT, "재진입 · 보고 없음 — 스윕(유예 30분)", now)
      tokenRegistry.revoke(guestId)
주기  provision.windows-install.sweep-interval  (기본 5m)
유예  provision.windows-install.sweep-grace     (기본 30m)

        
유예를 두는 이유는 재PXE 가 있는 게스트와 겹치지 않기 위해서다.
        시한 60분은 이미 WindowsInstallingExecutor 가 재진입 때 보는 눈금이므로,
        스윕이 같은 60분에 달려들면 어느 쪽이 먼저 닫았는지가 실행 순서에 좌우된다.
        30분을 더 기다리면 재PXE 가 있는 게스트는 실행기가 닫고, 없는 게스트만 스윕이 닫는다.
        워커 하트비트는 두지 않는다 — 로그로 충분하고, 상태를 하나 더 만들면 그것을 관측할 화면이 또 필요해진다.

      §8. 예상 부산물 / 주의 / 결정 사항
      

        
D-1 조립은 대시보드의 명시 액션으로 한다

        
채택 — 운영자가 대시보드에서 누르는 동기 액션(PRG)으로 조립하고, 결과는 매니페스트로 관측한다.

        
대안 ① 서빙할 때 자동 조립 — 탈락 /boot 트랜잭션 안에서 수백 MB 를 복사하게 되고,
        게스트가 그동안 기다린다. 게다가 조립 실패가 곧 서빙 실패가 되어 원인이 뒤엉킨다.

        대안 ② 자원이 바뀔 때 이벤트로 자동 조립 — 탈락 management 가 execution 을 깨우는 결합이 생긴다.
        이 결합을 만들지 말지는 이 슬라이스가 판단할 문제가 아니다.

        대안 ③ 운영 절차가 손으로 복사 — 탈락 토론 D9 의 층 C "앱이 조립한다" 를 정면으로 어긴다.


        
D-2 대상은 활성 DRIVER 전부, INF 없는 것은 제외 목록으로

        
채택 — kind = DRIVER · 미삭제 · effective 활성 · 보드 무관 전부를 넣는다(토론 Q2 가 공용 하나로 확정).
        트리에 *.inf 가 없으면 조립에서 빼고 제외 목록에 이유와 함께 적는다.

        
§1-3 에서 봤듯 Subprogram 에는 OS 구분이 없다.
        그래서 "Windows 드라이버인가" 를 판별할 유일한 근거가 INF 의 존재다.
        조립을 실패시키지 않고 제외로 다루는 이유는, INF 없는 DRIVER 가 등록돼 있다는 사실이
        조립을 막을 만한 오류가 아니라 등록 화면에서 고칠 일이기 때문이다.
        등록 시점의 경고는 비목표로 두고 S 계열에 적립한다.

        
후속(CP1 검수 · 2026-09-03) — Subprogram 에 대상 OS 계열 속성을 더하면 이 판별은
        "kind DRIVER ∧ Windows 계열" 로 명시적이 되고 INF 검사는 등록 경고로 내려가며, UTILITY 도 같은 페이로드에 실을 수
        있다(TESTING 의 BurnInTest 자리). 사용자 결정 "구분은 나중에 넣는다" — 속성 도입은 별도 관리 슬라이스로 두고 이 슬라이스는
        INF 판별을 잠정 규칙으로 쓴다. 속성이 생기면 WindowsOemPayloadAssembler 의 선택 술어 한 줄만 바뀌고
        페이로드 배치(Drivers/<id>_<슬러그>)는 그대로다.


        
D-3 스크립트 둘은 앱 내장 템플릿, 게스트별 값은 인자로

        
채택 — SetupComplete.cmd 와 spv-report.ps1 은 앱이 가진 템플릿을 그대로 쓰고,
        base URL 과 토큰은 FirstLogonCommands 인자로 넘긴다.

        
대안 ① 토큰 번들의 여섯 번째 파일로 서빙 — 탈락
        WinPE 가 받은 파일은 설치된 OS 로 넘어가지 않는다. 첫 로그온 시점에는 그 파일이 없다.

        대안 ② cmd + curl 로 보고 — 탈락
        배치에서 JSON 을 조립하면 따옴표 이스케이프가 취약하다. PowerShell 이 내장이므로 ConvertTo-Json 을 쓰는 편이 안전하다.


        
D-4 완료 보고는 전용 엔드포인트로 받는다

        
채택 — POST /api/pxe/v1/agent/windows/complete 를 새로 연다.

        
대안 ① 기존 steps/{id}/close 재사용 — 탈락
        게스트가 stepId 를 모른다. 서빙 행은 렌더가 끝난 뒤 훅에서 열리므로 렌더본에 담을 수 없다(§1-4).

        대안 ② Windows 설치용 step 코드를 새로 만든다 — 탈락
        enum 이 늘고 기존 이력 판독에 영향이 간다. 완료 보고 하나 때문에 원장 어휘를 늘릴 이유가 없다.


        
D-5 토큰 인증을 GuestTokenAuthenticator 로 뽑는다

        
채택 — 두 창구(에이전트 보고 · Windows 완료 보고)가 같은 인증기를 공유한다.
        AgentReportService.requireByToken 을 복붙하지 않는다.

        
추출은 동작을 바꾸지 않는다. 기존 테스트가 그대로 green 인 것이 그 증명이다.


        
D-6 관측은 슬롯 · chip · 영역 조건부 버튼 + 전용 컨트롤러

        
채택 — 대시보드에 스크립트 슬롯 둘과 "드라이버 페이로드" chip 을 더하고,
        조립 버튼은 DHCPD 링크와 같은 영역 조건부 방식으로 붙인다. 액션은 전용 컨트롤러가 받는다.

        
대안 ① 자산 영역 SPI 에 액션을 일반화 — 탈락
        액션이 하나뿐인데 확장점을 만드는 것은 과추상이다. 두 번째 액션이 생기는 시점에 분리한다.

        대안 ② 기존 seal 을 재사용 — 탈락
        봉인은 "지금 상태를 정본으로 굳힌다" 는 뜻이다. 파일을 새로 만드는 조립에 그 이름을 쓰면 의미가 왜곡된다.


        
D-7 시한 스윕 워커를 신설한다

        
채택 — 5분 주기 · 유예 30분. E4-1-a-3 이 D-8 로 남긴 공백을 여기서 닫는다.

        
대안 ① 상세를 조회할 때 판정 — 탈락 아무도 화면을 열지 않으면 영원히 안 닫힌다.
        관측이 상태 전이의 조건이 되면 "보지 않으면 일어나지 않는" 시스템이 된다.

        대안 ② 두지 않는다 — 탈락 디스크 우선 부트 환경에서 설치 실패가 영구히 "설치 중" 으로 남는다.


        
D-8 완료는 닫고 · 회수하고 · 종단시킨다

        
채택 — 서빙 행을 SUCCEEDED 로 닫으면서 서빙 메타를 보존하고,
        토큰을 회수하고, advanceOrComplete 로 커서를 옮긴다.
        Windows 정의서는 OS 설치만 담으므로 다음 소유 phase 가 없어 종단으로 닫히고, 이후 /boot 는 dispatch 4행의 exit 를 받는다.


        
D-9 운영 설계 — 소스 전체가 아니라 $OEM$ 만 연다

        
채택 — 런북 §14-1 에 sources/$OEM$ 에 대한 provisioning 계정 쓰기 권한을 명시하고,
        Setup 이 $OEM$ 를 자동으로 복사한다는 것과 OEM 제품 키로 설치하면 SetupComplete 가 생략된다는 것을 함께 적는다.
        나머지 소스는 spvadmin 소유 그대로 둔다.


        
주의 · 잔존 책임

        

          
    
            
  • 조립 소요 시간 — 1 GB 급 LAN 드라이버가 들어오면 동기 PRG 가 버거울 수 있다. 실측 뒤 비동기 job 전환을 판단한다
    • 
            
  • AgentReportService 손질은 추출만 한다. 동작을 바꾸지 않고 기존 테스트가 green 인 것을 확인한다
    • 
            
  • 완료 보고가 종단시킨 게스트의 다음 /boot 는 dispatch 4행의 exit 다 — 재진입이 아니므로 카운트가 오르지 않는다
    • 
            
  • 토큰은 설치된 OS 의 Panther 에 남은 unattend.xml 안에 있다. 게스트 자신의 자격이고 Base64 비밀번호와 같은 층의 노출이다
    • 
            
  • 스윕이 실패시킨 뒤 늦게 도착한 완료 보고는 409 다(이미 실패 상태). 회복은 운영자 재시도 후 재설치다
    •

    •
