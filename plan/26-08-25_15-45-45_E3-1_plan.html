§1. 배경 · 유래 — 지금 이 슬라이스인 이유
개정 이력 (파일 경로는 Notion 임베드 · 후속 report 참조를 지키려 고정한다)
  • 개정 1 (2026-08-25 KST · CP1 검수 반영) — 착수 절차에서 생략 판단(diff 계산 · ALREADY_CURRENT · pending 선확인)을 제거했다. 요청된 설정은 현재값과 같아도 무조건 다시 쓴다. 근거는 D-4 의 "왜 생략 판단을 하지 않는가" 소절이며, 펌웨어 쪽에서 E2-2 가 버전 비교 skip 을 제거한 것과 같은 원칙이다. 개정 1
  • 개정 2 (2026-08-25 KST) — ① 크래시 재개 경로에서 ③ openRunning 만 생략하고 신원 대조부터 다시 한다(D-6 이 재개에도 적용된다) ② pending 확인을 실패 판정에서 관찰 기록으로 낮췄다 — pendingSeen 을 meta 에 적을 뿐이고 최종 증거는 readback 하나다. 사유 상수 PENDING_MISSING 삭제(→ 8 종). 개정 2

E2-2(펌웨어 집행)가 완주하면 커서는 다음 소유 phase 로 전진한다. 정의서에 BASIC_SETTING 프로세스가 있으면 그 phase 가 FIRMWARE_SETTING 이고(SettingProcessPhaseMapper), 지금은 실행기가 없어 dispatch 가 HOLD 대기 스크립트를 내린다(DEC-6 — 미구현 phase 는 silent 통과 금지). E3-1 은 그 HOLD 를 실행기 빈 하나로 푼다.

왜 지금인가. F27 → F29 flash 가 전원 계열 설정(SpeedStep · PackageCState · EPB)을 기본값으로 초기화한 것이 실측됐다(E0-4-3, 2026-08-19). "펌웨어 업데이트 → 설정 소실 → 재적용" 이 실제 공정이고, 표준 이미지 flash + Redfish 설정 재적용 파이프라인이 사내 커스텀 이미지 요구의 대체 경로다.

ES-3 선행은 불요다(브리핑 §2) — 커서 전진(PhaseCursorAdvancer) · 실행기 라우팅(PhaseExecutorRegistry 빈 등록 = 위임) · 정의서 매핑이 이미 있다. E3-0(자격증명)은 E1.6 이 흡수했고, E3-R 은 실측으로 종결됐다.

§3. 설계 결정 D-1 ~ D-12 (채택 · 비채택 · 탈락 사유)

D-1. 골격 = 최소 공통 추출 — 제네릭 step SPI · registry 만 engine/worker/ 로

E2-2 가 만든 워커 주도 골격(step SPI order · matches · execute + 순서 중복 fail-fast registry + worker/cycle 분리)은 E3-1 도 그대로 필요하다. 세 갈래를 비교했다.

(A) 전면 일반화 — 탈락

FlashContext · Ledger · Timeout · IdentityGuard 까지 phase 무관 추상으로.

  • E2-2 리팩토링이 커지고 검증 줄기가 둘(E2 회귀 + E3 신기능)이 된다.
  • 추상이 도메인을 가로질러 의미를 잃는 지점이 있다 — Context 가 resolution · provider 를 품는 것은 flash 특화다.

(B) 동형 신설 — 탈락

engine/setting/ 에 SettingStep · SettingStepRegistry 를 나란히 둔다.

  • step SPI 와 registry(순서 중복 fail-fast · 첫 매칭 실행)가 글자 그대로 복붙된다 — 중복 금지 위반.

(C) 최소 공통 추출 — 채택

WorkerStep<C> 와 WorkerStepRegistry<C, S extends WorkerStep<C>> 만 뽑는다.

  • FlashStep 은 WorkerStep<FlashContext> 를 상속하고 FlashStepRegistry 는 제네릭 registry 에 위임한다.
  • 행동 무변경이며 기존 51 테스트가 회귀를 방어한다.

워커 · 사이클은 phase 별로 둔다 — sweep 대상 step 집합과 컨텍스트 조립이 phase 특화라, 30줄 남짓의 추출 이득보다 결합 비용이 크다.

적대적 검토 — registry 하나 때문에 E2 를 건드리는 churn 인가. 변경은 파일 4 · 20행 내외이고, E3-2(BMC 설정) · 향후 RAID 도 같은 워커 주도형이라 세 번째 사용처가 확실하다. 지금이 갈라지는 시점이다. 공통화는 CP2 첫 단계로 먼저 하고 기존 테스트 green 을 확인한 뒤 E3 step 을 얹는다.

D-3. 소비 입력 = BiosSettingResolutionProvider SPI ← provisioning 측 구현

FirmwareResolutionProvider(SPI 는 execution, 구현 FirmwareResolutionProviderImpl 은 provisioning/assignment — 순환 회피) 선례 그대로다. 구현은 활성 스냅샷의 BASIC_SETTING 프로세스 frozenBiosSettings(U3-1 deep-freeze)를 읽어, 감지 보드(detail.boardModel.id)와 boardModelId 가 일치하는 템플릿만 선언 순서로 병합(같은 속성은 후행 우선)해 BiosSettingTarget(Map<BiosAttributeName, BiosAttributeValue>) 로 돌려준다. FrozenBiosTemplate.boardModelId 의 Javadoc 이 정확히 이 용도("실행 시 감지 보드 일치 판정")를 예약해 두었다. 일치 템플릿이 0 이면 empty 를 돌려준다 — 이 보드에 적용할 설정이 없다는 뜻이다.

탈락 — ① 첫 템플릿만 쓰는 안은 정의서가 보드별 템플릿을 여럿 담는 구조와 어긋난다. ② 전부 병합하는 안은 다른 보드의 속성 키를 PATCH 하게 되어 BMC 가 거절하거나 엉뚱한 속성을 건드린다(AMI 키는 보드 · BIOS 버전마다 다르다).

D-4. 상태 기계 — 진리표

순서가 곧 우선순위다. E2 의 교훈대로 "이미 진행 중인가" 를 먼저 본다.

5행 착수 절차 개정 1

  1. 신원 대조(D-6).
  2. GET Bios — ETag 확보. 현재값은 생략 판단에 쓰지 않는다.
  3. openRunning(meta: target · rebootAt 은 아직 없음) — 되돌리기 어려운 조작보다 먼저 원장을 연다. E2-2 가 굽기 시작 전에 여는 것과 같은 이유다: 뒤에 열면 그 사이 크래시에 원장이 진행 중을 잃는다.
  4. PATCH Bios/SD If-Match: * 로 목표 전체를 그대로 쓴다(현재값과 같은 항목 포함 — 무해). 412 면 fresh ETag 로 1 회 재시도, 그래도 실패면 PATCH_REJECTED FAILED.
  5. 개정 2 GET Bios/SD 로 pending 을 읽어 RUNNING 행 meta 에 pendingSeen: true/false 로 기록만 한다 — 실패로 치지 않는다.
  6. ForceRestart(E1.5) → RUNNING 행 meta 에 rebootAt 갱신.

왜 pending 부재를 실패로 치지 않는가 개정 2 — 값이 바뀌지 않는 PATCH 도 pending 을 만드는지가 미실측이다(§9). 그래서 pending 부재를 실패로 치면 정상 경로가 오판된다 — 목표가 이미 현재값이라 BMC 가 pend 할 것이 없는 경우가 그렇다. 최종 증거는 readback 하나로 충분하다: pending 이 정말 안 걸렸으면 재부팅 후 readback 이 옛값을 읽어 READBACK_MISMATCH 로 드러나고, 이미 목표값이라 pend 할 것이 없었던 경우면 readback 이 일치해 SUCCEEDED 로 닫힌다. 둘 다 정직하고, 치르는 값은 재부팅 1 회다. F-1 계열 교훈("바꿨다는 응답" 을 믿지 않는다)은 그대로이며 — 믿을 실물이 pending 에서 재부팅 후의 실제 값으로 옮겨갈 뿐이다.

탈락(개정 2 로 폐기) — pending 부재 · Bios/SD 404 를 PENDING_MISSING FAILED 로 닫기. 미실측 전제 위에서 정상 경로를 실패로 만든다.

왜 생략 판단을 하지 않는가 개정 1 — diff 판단은 "BMC 가 보고하는 현재값이 진실" 이라는 전제 위에 서는데, 그 전제가 바로 미실측 항목이다(BMC Bios 리소스가 POST 후 언제 갱신되는가). flash 가 설정을 초기화한 직후 BMC 가 아직 옛값(초기화 전 사내 표준값)을 보여주면 diff 가 비어 "설정을 안 하고 SUCCEEDED" 로 닫힌다 — E3 가 막으려는 "펌웨어 업데이트 → 설정 소실" 이 성공 표식 뒤에 숨는 최악의 실패다.

readback(적용 후 대조)과 diff(적용 전 생략 판단)는 같은 GET 을 쓰지만 실패 방향이 반대다 — readback 이 옛값을 읽으면 "불일치 → FAILED" 로 드러나고, diff 가 옛값을 읽으면 "일치 → 생략 → SUCCEEDED" 로 숨는다. 아끼려던 것은 재부팅 1 회(수 분)이고 잃을 수 있는 것은 설정 적용 자체다. E2-2 가 같은 버전 표기의 다른 바이너리(로고 변경본 실측) 때문에 버전 비교 skip 을 제거한 것과 같은 결론이다 — 요청된 것은 무조건 적용한다.

탈락(개정 1 로 폐기) — ① 목표 중 현재값과 다른 항목만 diff 해 PATCH ② diff 가 비면 재부팅 없이 ALREADY_CURRENT 로 닫기 ③ PATCH 전 pending 선확인으로 중복 PATCH 회피. 셋 다 "BMC 현재값이 진실" 을 전제하며, 그 전제가 깨지는 방향이 하필 실패를 감추는 쪽이다.

크래시 수렴 개정 1 개정 2 — ⑥ 안에서 재부팅은 걸렸는데 rebootAt 이 남지 않으면, 다음 주기는 rebootAt 없는 RUNNING 행을 보고 그 행을 이어 재수행한다. 이때 생략하는 것은 ③ openRunning 하나뿐이고 ① 신원 대조 → ② GET Bios(ETag) → ④ → ⑤ → ⑥ 은 다시 한다 — D-6 의 "되돌리기 어려운 조작 직전 신원 대조" 는 재개에도 적용된다. 재개 시점에 BMC 가 다른 장비로 바뀌어 있을 수 있고, ④ 는 여전히 되돌리기 어려운 조작이기 때문이다. 같은 값을 다시 쓰고 재부팅이 한 번 더 걸리는 무해한 반복이며 상한은 1 회다. 외부 IO 와 DB 원자성에는 절대 해법이 없으므로 수렴으로 다룬다.

행 3(목표 없음)이 행 4(BMC 미검출)보다 위인 이유 — 이 보드에 적용할 설정이 없으면 BMC 유무와 무관하게 할 일이 없다. 실패가 아니라 건너뜀이다. D-12 의 "BMC 결손은 실패" 는 목표가 있을 때의 판정이며, 두 행의 순서가 그 전제를 코드로 고정한다. 착수 단계에서 BMC 가 불통이면(① 신원 대조부터 실패) 행 1d 와 같은 규칙으로 다음 주기에 재시도하고, 시한은 phase 진입 시각(progress.lastTransitionAt — E2-2 BmcIdentityGuard 와 같은 기준)부터 잰다.

readback 신호는 게스트 접촉 시각이다. POST 가 끝나 PXE 로 돌아온 것이 새 설정이 부팅에 반영됐다는 가장 정직한 신호이고, BMC 의 Bios 리소스가 POST 후 언제 갱신되는지는 미실측이라 BMC 폴링만으로는 이르게 읽을 위험이 있다. E2-2 PowerOnStep 과 같은 신호 재사용이다.

탈락 — ① BMC PowerState 폴링만으로 readback(위 사유). ② 재부팅 전 readback — pending 은 재부팅 전엔 반영되지 않는다(실측).

D-5. 원장 = BIOS_SETTING RUNNING 행 + 목표 보존 (E2-2 F-1 교훈)

개정 1 개정 2 openRunning(statusMeta = {target, rebootAt, pendingSeen}) 로 열고(diff 항목은 개정 1 에서 제거 — 생략 판단을 하지 않으므로 적을 것이 없다. pendingSeen 은 개정 2 에서 추가 — 판정에는 쓰지 않고 실기 관측을 위해 남기는 사실이다), 종결 시 closeSetting(result, reason, detail) 이 target · rebootAt · pendingSeen 을 보존한 채 결과를 덧씌운다 — E2-2 F-1(close 가 meta 를 통째 교체해 반영 확인이 대조 대상을 잃은 사고)의 재발 방지다. ProvisioningHistory 에 setting 메타 접근자(settingTargetMeta · settingRebootAt · closeSetting)를 flash 메타와 나란히 신설한다. 두 번째 사용처이므로 JSON 메타 조립 · 판독의 공통 헬퍼 추출은 CP2 에서 행동 무변경으로 판단한다.

사유 상수는 SettingLedger(FlashLedger 결)에 8 종을 둔다 — 개정 1 에서 ALREADY_CURRENT 삭제(생략 경로가 없어졌으므로 그 사유로 닫히는 자리도 없다), 개정 2 에서 PENDING_MISSING 삭제(pending 부재가 실패가 아니게 됐다). isPhaseLevel 은 이번엔 축이 하나라 불요다.

D-6. 신원 확인 — PATCH 직전 + readback 직전 (E2-2 D-11 두 갈래 그대로)

되돌리기 어려운 조작 직전(PATCH → 재부팅)과 종결 판정의 근거 읽기(readback) 직전, 두 자리에서 확인한다. E2-2 BmcIdentityGuard 는 FlashContext 결합이라 그대로 못 쓴다. 판정 자체(FirmwareUpdateProvider.verifyIdentity — Chassis Oem 보드 시리얼 대조)와 도달 불가 시 주소 재발견(BmcAddressRediscovery)을 컨텍스트 무관 BmcIdentityProbe 로 뽑고, 원장 기록(불일치 = 즉시 실패 · 시한 실패)은 phase 별 가드가 각자 한다. E2 의 Guard 가 Probe 를 쓰도록 바꾸는 것은 행동 무변경이다. 이중 증명 논리(E1.6 D-5)는 여기 해당 없다 — 표준 계정으로 열리므로 명시 대조가 유일한 증명이다.

D-7. 재부팅 = ForceRestart · 전원 상태 선확인

E2 종료 직후 게스트는 PowerOn 으로 켜져 PXE 대기 루프 중이므로 정상 경로는 ForceRestart 다. PowerState 가 Off 면 On 을 쓴다(pending 은 다음 부팅에 적용된다). On 경로의 폴링 검증 · PowerCycle 폴백은 E1.5 가 이미 갖고 있다.

D-8. 시한 = E2 return-timeout(20m) 재사용

재부팅 후 PXE 복귀 대기는 E2-2 의 "전원 켠 뒤 복귀 대기" 와 같은 성격이라 FlashTimeoutPolicy.returnLimit() 을 그대로 쓴다. PATCH 왕복은 즉시라 시한이 없다. 탈락 — E3 전용 시한 키. 값이 같은데 키만 늘린다.

D-9. 레지스트리 런타임 조회 = 범위 제외

적용 왕복은 레지스트리 없이 성립한다 — PATCH 는 스냅샷의 목표 전체를 그대로 보내고, 허용값 검증은 템플릿 저장 시 biossetting 이 담당한다. readback 은 표준 경로 Systems/Self/Bios 고정이라 Notion(2026-08-07)의 "레지스트리 경로 하드코딩 금지" 는 이 슬라이스에 해당 없다. 런타임 조회(AttributeRegistry 링크 따라가기 · 파일 의존 해소)는 검증 줄기가 다르므로 별도 슬라이스(E3-1-b 또는 MA6 연계)로 보낸다.

D-10. BIOS 전용 — 축 enum 은 E3-2 가 승격

E2 의 FirmwareAxis 는 E2-1-b 가 두 축의 resolve 를 동시에 필요로 해 생겼다. E3-1 은 BIOS 하나뿐이라 축 enum 을 미리 만들지 않는다. E3-2 가 BMC_SETTING 을 낼 때 SettingAxis 로 승격한다(갈라지는 시점). 커서는 BIOS_SETTING 성공 시 advanceOrComplete — phase 완주 후 다음 소유 phase 로 전진한다.

D-11. 화면 변경 0 · DDL 0

세부 단계 이력 표가 BIOS_SETTING 행(RUNNING → 결과)을 자동 노출하고 phase rail 이 FIRMWARE_SETTING 을 이미 표기한다. 집행 카드 류 상세화는 E2-4 소관이다. BIOS_SETTING 상수는 setup_step.step_code ENUM 값에 실재하므로 DDL 이 없고, 엔티티도 무변경이다(원장 메타는 기존 JSON 컬럼).

D-12. BMC 미검출 = FAILED(BMC_REQUIRED)

E2-2 는 지원 provider 가 없으면 집행을 시작하지 않는다(D-6 — 보류). E3 는 다르게 판단한다 — 설정 적용이 BMC 없이 불가한 것은 확정 사실이고, 보류하면 시한 없이 멈춘다. 정의서가 BIOS 설정을 요구했는데 BMC 가 없으면 그것은 운영자가 알아야 할 실패다.

§9. 위험 · 미해결
  • BMC 의 Bios 리소스가 POST 후 갱신되는 시점이 미실측이다 — 게스트 접촉 신호로 우회한다(D-4). 실기에서 접촉 직후 readback 이 옛값을 읽으면 짧은 유예(예: 접촉 후 N초)를 정련한다.
  • 개정 1 위 미실측은 이제 readback(드러나는 실패)에만 걸린다 — 생략 판정이 없어져 같은 미실측 때문에 숨는 실패 경로가 사라졌다(D-4 "왜 생략 판단을 하지 않는가").
  • 개정 2 무변경 PATCH 의 pending 생성 여부가 미실측이다 — T3 에 적립한다. 어느 쪽이든 readback 이 판정하므로 설계는 이 미실측과 무관하고, pendingSeen 은 실기에서 답을 얻기 위한 관측 기록이다.
  • Dependencies 위반 속성을 PATCH 하면 BMC 가 어떻게 답하는지 미실측이다 — PATCH_REJECTED 로 흡수하고 실기에서 관측한다.
  • If-Match: * 가 MegaRAC 전 버전에서 통하는지는 이 펌웨어 실측뿐이다 — 412 폴백이 방어한다.
  • 정의서에 같은 보드 템플릿이 여럿이면 병합 순서(후행 우선)가 사용자 기대와 맞는지 — plan 데모로 체험시키고 확인한다.
  • 실기 검증은 CP7 일괄이다 — 무해 속성 1 개 + 원복 세트(E0-4-3 안전 수칙).
