§0. 개편 동기 (R15 토론 종결분)

이 개편은 E4-1-a-4(Windows $OEM$ 조립 · 완료 보고)가 만든 조립 · 설치 경로 위에 놓인다. 당시 조립은 Subprogram 에 OS 구분이 없어 "트리에 INF 가 하나라도 있으면 대상" 으로 판별했고, 그 한계를 CP1 후속으로 명시해 두었다. 실기 4호 뒤 사용자가 이를 문제로 제기했다.

  1. OS 에 따라 드라이버가 다르면서 보드에 따라서도 다른데, 분류 기준이 보드뿐이다.
  2. 같은 OS 라도 버전에 따라 실행할 파일이 다르다 — ASPEED 한 패키지 안의 Win10 · Win11 · Server 2022 · Server 2025 MSI.

R15 는 이를 모델 · 등록(R15-1) / 조립 · 설치 선별(R15-2) / 현황 · 경고 · 자동 조립(R15-3) 셋으로 나눴다(검증 줄기가 각각 등록 화면 · 설치 하네스 · 대시보드로 다르다). 본 문서는 첫째다.

본 슬라이스 한 줄 — Subprogram 에 OS 축(osName · null = OS 무관)을 더하고, 벤더 패키지 안의 버전별 변형을 SubprogramVariant(OS 버전 · 진입점 상대 경로 · 인자 · 재부팅 플래그)로 선언한다. 선언한 변형을 실제로 고르고 실행하는 것은 R15-2 다.

§2. 요구사항 (확정) + 비목표
  1. OS 축 — Subprogram.osName(OSName · nullable · null = OS 무관). 등록 시 선택(필수 아님 · 기본 OS 무관) · 수정 가능. 마커 attribute 에는 넣지 않는다.
  2. 변형 — 신규 엔티티 SubprogramVariant(OS 버전 · 진입점 상대 경로 · 인자 · 재부팅 플래그 · 정렬 · 시각). 한 패키지에 여러 행.
  3. 진입점 SSOT 는 변형 — 자원 단위 entrypointRelativePath 를 엔티티 · DTO · 응답 · 수정 폼 · 컬럼에서 제거한다. 변형이 하나뿐인 패키지도 변형 1 행으로 표현한다.
  4. 설치 방식은 진입점 확장자가 정한다 — enum InstallEntrypointKind(INF · MSI · EXE). 별도 "설치 방식" 선택 필드를 두지 않는다. 그 외 확장자는 400 필드 메시지로 거절.
  5. 변형 편집은 수정 폼(MA5-D5 와 같은 결) — 표 편집(행: OS 버전 · 진입점 · 인자 · 재부팅) · [행 추가] · [삭제] · variants[i].* 인덱스 바인딩 · 서버는 전체 교체(삭제 후 삽입).
  6. 변형 유일성 — UNIQUE(subprogram_id, os_version) + OS 버전을 비운 변형(그 OS 의 모든 버전)은 1 행 이하(서비스 가드).
  7. 등록 3 경로(업로드 · 기존 트리 · nudge 재등록) 모두 osName 을 나른다.
  8. 화면 표시 — 목록(Miller) 자원 행에 OS 라벨("OS 무관" 포함) · 상세 패널에 OS + 변형 표(버전 · 종류 배지 INF/MSI/EXE · 진입점 · 인자 · 재부팅). 변형 0 이면 "변형 없음 — 트리 전체(INF)로 다룸(현행)".
  9. 마이그레이션 — ddl/R15-1_subprogram_os_variant.sql 5 문(§8 D-8) + schema.sql 동기.

🎬 미리보기 — 변형 표 편집기 (라이브 데모)

ASPEED 트리의 실측 파일에서 진입점을 고르고 OS 버전을 적어 변형 행을 쌓는 데모다. 확장자 위반 · 같은 버전 중복 · 버전 비운 행 2 개는 즉시 거절된다(데모의 거절 판정 = 서버 SubprogramService 가드 = 같은 SSOT). 아래 "대상 OS 버전" 을 바꾸면 어느 행이 뽑히는지 미리 볼 수 있다 — 이 선택 규칙은 R15-2 의 예고이며 본 슬라이스에서 구현하지 않는다.

InstallEntrypointKind — 설치 방식의 SSOT

public enum InstallEntrypointKind {
    INF, MSI, EXE;

    public static InstallEntrypointKind fromPath(String relativePath);  // 확장자 → 상수, 미지원이면 거절
    public String label();                                              // 화면 배지 문구
}
// R15-2 가 constant 별 메서드로 실행 명령(pnputil · msiexec · 직접 실행)을 붙인다. 본 슬라이스는 분류 + 검증만.

변형 교체 가드 (서비스 · 🎬 데모와 같은 판정)

replaceVariants(sp, requests):
    for r in requests:
        kind = InstallEntrypointKind.fromPath(r.entrypointRelativePath)   // null → 400 (확장자)
        path = entrypointPolicyService.validateAndNormalize(Path.of(sp.treeRootPath), r.entrypointRelativePath)
        v    = trim(r.osVersion)                                          // blank → null
    if 중복(v)         → 400   // UNIQUE(subprogram_id, os_version) 선행 가드
    if null 버전 2 행  → 400
    기존 변형 전부 삭제 → 신규 삽입

Primitive Obsession 판단 — 설치 방식은 문자열이 아니라 InstallEntrypointKind enum 으로, OS 는 OSName enum 으로 타입화한다. 반대로 osVersion 은 의도적으로 문자열이다 — 매칭 상대인 OSMetadata.osVersion 이 이미 문자열이고, FK 로 묶으면 드라이버 버전마다 OS 메타를 먼저 등록해야 하기 때문이다(D-6). 진입점 경로는 자유 문자열이 아니라 EntrypointPolicyService 정규화를 통과한 값만 저장한다.

잔존 책임 · 위험

  • R15-2 전까지 변형은 선언만 되고 조립 · 설치는 현행(트리 전체 INF) 경로를 탄다 — 의도된 임시 비대칭.
  • 자원 단위 진입점 제거는 실 DB DDL(DROP)이 앱 배포와 같은 순간에 있어야 한다(ddl-auto=validate). 9 · 10 차 재배포 절차에 DDL 선적용을 넣는다.
  • osName 을 마커 밖에 두므로 파일 이동 재조정(reconciliation)에서 OS 는 DB 값이 유지된다(마커로 복원되지 않음) — 의도.
