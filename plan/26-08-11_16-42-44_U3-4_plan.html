§0. 재설계 동기

이 슬라이스는 신규가 아니라 재정의다. 구 U3-4 는 스펙 그룹 단위 세팅 정의서 일괄 할당 이었고, 그룹을 하드웨어 스펙 묶음 그 자체로 잡고 있었다.

U3-3 이 완료된 직후 사용자가 요구를 풀어 설명하면서 전제가 어긋남이 드러났다. 요구된 그룹은 사람이 만드는 결정이다 — 게스트 서버 여러 대를 논리적으로 묶어 하나의 세팅 정의서를 할당하거나 한데 보되, 원하면 서버를 넣고 뺄 수 있어야 한다. 넣고 빼는 일이 실제로 필요한 상황이 둘이다.

  • 같은 구성의 물량이 많아 순차적으로 제작될 때, 나중에 올라온 서버를 기존 묶음에 합류시킨다.
  • 세팅이 진행되는 도중 특정 몇 대만 요구사항이 바뀌어 떼어낸다.

스펙으로 시스템이 묶음을 고정해버리면 두 상황 모두 표현할 수 없다. 스펙이 같은 한 떼어낸 서버가 계속 다시 편입되기 때문이다.

그렇다고 U3-3 의 스펙 묶음이 쓸모를 잃지는 않는다. 그 화면의 값어치는 할당이 아니라 실물 대조에 있다 — 랙에 방금 꽂은 서버들이 화면에 같은 크기의 묶음으로 뜨면, SMBIOS UUID 를 하나씩 맞춰보지 않고도 물리 서버와 탐지 결과가 대응하는지 알 수 있다. 사람이 손댈 수 없다는 성질이 여기서는 장점이고, 유지 비용이 0 이며 언제나 현재 사실이다.

그래서 둘의 관계는 동일성이 아니라 씨앗으로 정리됐다. 스펙 묶음이 "이 N 대를 그룹으로 만들까" 를 제안하고, 사람이 수락하면 그 시점의 멤버 명단이 복사되어 독립된 그룹이 시작된다. 이후 그룹은 스펙을 다시 보지 않는다.

재편으로 단계가 둘로 갈렸다. 이 슬라이스(U3-4)는 그룹이라는 개념 자체를 세우고, U3-5 가 그 위에서 일괄 할당을 다룬다. 토론 아카이브는 discussion/26-08-11_16-25-25_U3-4-server-group-concept_discussion.md 다.

구 U3-4 가 꼽았던 설계 난제 둘 중 하나는 이미 없어졌다. "스펙 그룹 키의 Value Object 화" 는 U3-3 이 SpecGroupKey 를 산출하며 해결했고, 남은 "부분 실패 정책" 은 U3-5 로 넘어갔다.
§1. 현재 상태 (진단)

실측 기준은 커밋 84f7846(U3-3 완료분)이다.

서버를 여러 대 묶어 다루는 수단이 하나도 없다. 목록 화면은 상대 시간과 하드웨어 스펙 두 축으로 보여주지만, 그 묶음은 조회할 때마다 계산되는 관찰이라 사람이 손댈 수 없다. 이름도 없고, 넣고 뺄 수도 없으며, 다음 조회에서 같은 묶음이 나온다는 보장도 없다 — 서버 스펙이 바뀌면 소리 없이 다른 묶음으로 옮겨간다.

그 결과 지금은 세팅 정의서를 서버 한 대마다 반복 할당해야 한다. 같은 구성 12 대가 들어오면 같은 조작을 12 번 하고, 한 대를 빠뜨려도 화면이 알려주지 않는다.

할당 인프라는 이미 서 있다. SettingAssignment 는 게스트 서버 한 대마다 한 행이고 할당 시점에 정의서를 행 단위로 복사해 얼린다. 활성 스냅샷은 서버당 하나이며 서비스 가드와 @Version 이 그 불변식을 지킨다. 즉 부족한 것은 할당이 아니라 "여러 대를 하나로 부를 이름" 이다.

동치 판정 재료도 이미 있다. SpecGroupKey 가 보드 모델 · CPU · 메모리 · 디스크 · PCIe 여섯 축을 정규화해 비교하고, 다중집합을 정렬해 슬롯 위치와 부팅 순서를 동치에서 뺀다. 이 슬라이스는 이것을 씨앗 제안과 스펙 이탈 알림 두 곳에 쓴다.

§2. 요구사항 + 비목표

요구사항

  1. 그룹을 만든다. 목록 화면의 스펙 묶음에서 그 멤버를 씨앗으로 받아 만들거나, 빈 그룹을 먼저 만든다.
  2. 이름을 준다. 만들 때 정하고 나중에 바꿀 수 있다. 이름은 시스템 안에서 유일하다.
  3. 멤버를 넣는다. 그룹 상세에서 아직 어느 그룹에도 없는 서버를 골라 넣는다.
  4. 멤버를 뺀다. 그룹 상세에서 제외한다. 서버 자체와 그 서버의 할당은 건드리지 않는다.
  5. 그룹을 본다. 그룹 목록(이름 · 멤버 수 · 만든 시각)과 상세(멤버 표)를 제공한다.
  6. 어느 그룹인지 목록에서 알아본다. 서버 목록의 각 행에 소속 그룹 배지를 붙인다.
  7. 그룹을 지운다. 지우면 멤버는 무소속으로 돌아가고 서버는 그대로 남는다.
  8. 스펙이 섞이면 알린다. 그룹 멤버의 스펙 키가 둘 이상이면 상세에서 안내한다. 막지는 않는다.
비목표
  • 그룹에 세팅 정의서를 할당하는 것 — U3-5. 이 슬라이스는 할당 코드를 한 줄도 건드리지 않는다.
  • 그룹 기본 정의서 — U3-5 의 열린 쟁점이다. 이 단계의 엔티티에 자리를 미리 파두지 않는다.
  • 멤버십 이력 — 언제 넣고 뺐는지는 남기지 않는다.
  • U3-3 목록 화면의 그룹화 골격 변경 — 시간 × 스펙 2단 구조는 그대로다. 배지 한 칸과 버튼 하나만 더한다.
  • 한 서버의 다중 그룹 소속 — DEC-B 로 기각한다.
🎬 미리보기 — 라이브 데모

좌측에 서버 카드 6 장, 우측에 그룹 패널. 상단에 조작 버튼, 하단에 판정 로그. 스펙 A = MS03-CE0 · 6338 ×2 · 32GB ×8, 스펙 B = MS03-CE0 · 6338 ×1 · 32GB ×4. 그룹 초기값 : 8월 2차(멤버 srv-05). 카드를 그룹 패널로 끌어 넣거나 [넣기] 를 눌러본다 — 이미 다른 그룹에 속한 서버는 버튼이 disabled 이고 tooltip 에 사유가 뜬다.

관찰 포인트
  • 회수된 서버(srv-06)도 그룹에 들어간다. 그룹은 운영 이력을 지우지 않는다. 배제는 할당 시점(U3-5)의 몫이다.
  • 스펙 B 서버를 스펙 A 그룹에 넣으면 경고 배너가 뜨지만 들어간다. 스펙은 정체성이 아니므로 섞인 것 자체는 위반이 아니다.
  • disabled 와 서버 거절은 같은 함수가 판정한다. 화면이 먼저 막고, 서버 가드는 direct POST 용 안전망으로만 남는다.

판정 JS (서버 도메인 메서드와 동일 식)

// GuestServerGroup.addBlockReason(server) 와 같은 식
function addBlockReason(server, group) {
  if (server.groupId !== null && server.groupId !== group.id) {
    return '이미 다른 그룹(' + groupName(server.groupId) + ')에 속해 있습니다';
  }
  return null;   // null 이면 넣을 수 있다
}

// GroupNameConflictException 과 같은 판정
function nameConflict(name, selfId) {
  return groups.some(g => g.id !== selfId && g.name === name);
}

// 스펙 이탈 알림 — 차단이 아니라 안내
function specDiverged(group) {
  return new Set(group.members.map(s => s.specKey)).size > 1;
}

그룹 배지 합성 (제자리 서술)

서버 목록 화면의 컨트롤러는 provisioning.controller.GuestServerController 이고, 그룹 조회 서비스도 provisioning 에 있다. 그래서 컨트롤러가 두 서비스를 각각 불러 모델 단계에서 합성한다 — 조회 서비스(execution)가 그룹을 알 필요가 없고, 따라서 execution → provisioning 역방향 의존이 생기지 않는다. OwnedPhasesProvider 같은 SPI(Service Provider Interface — 도메인이 구현해 끼우는 확장점) 역전을 새로 만들지 않아도 되는 이유가 여기 있다.

Value Object 를 만들지 않는 것

그룹 이름은 String 으로 둔다. GuestServer.name 과 SettingDefinition.name 이 이미 그렇고, 이름에는 형식 규칙이나 파생 연산이 없어 Value Object 가 담을 도메인 규칙이 없다. Primitive Obsession 금지는 의미 있는 값을 타입화하라는 것이지 모든 문자열을 감싸라는 것이 아니다 — 도메인을 가로질러 의미를 잃는 추상은 만들지 않는다는 원칙이 여기 적용된다.

§8. 결정 · 부산물 · 주의

DEC-A. 그룹은 영속 엔티티, 스펙 묶음은 씨앗.

재편에서 확정된 전제다. 스펙 묶음은 계산 결과로 남고 그룹만 저장된다. SpecGroupKey 를 컬럼으로 물질화하지 않는 U3-3 의 DEC-D 는 유지된다 — 씨앗은 한 번 쓰이고 버려지므로 저장할 이유가 늘지 않았다.

DEC-B. 서버 : 그룹 = N : 1.

멤버십 테이블의 guest_server_id 에 UNIQUE 를 걸어 구조로 강제한다.

기각 ① N : M — 그룹의 주 용도가 할당인데(U3-5) 두 그룹에 속하면 어느 정의서를 따르는지 모호해지고, 서버당 활성 할당 1 개라는 기존 불변식과 어긋난다. 함께 보기만을 위한 다중 소속은 나중에 태그 같은 별도 개념으로 얹는 편이 낫다.

기각 ② guest_server 테이블에 group_id 컬럼 — 가장 단순해 보이지만, GuestServer(execution)가 그룹(provisioning)을 @ManyToOne 으로 들게 되어 execution → provisioning 역방향 의존이 생긴다. R7 이 제거한 생성자 순환이 재생성되는 경로다.

DEC-C. 패키지는 provisioning.group.

SettingAssignment 와 같은 형태 — 그룹이 GuestServer 를 @ManyToOne 으로 참조하는 provisioning → execution 단방향이다.

기각 execution.group — 방향만 보면 성립한다. 그러나 U3-5 가 논의 중인 "그룹 기본 정의서" 를 그룹에 얹는 순간 execution 이 provisioning 의 정의서를 참조하게 되어 방향이 뒤집힌다. 그때 가서 옮기는 것보다 지금 provisioning 에 두는 편이 싸다. 그룹의 존재 이유가 할당이라는 점도 같은 쪽을 가리킨다.

DEC-D. 목록 화면은 골격을 유지하고 배지만 더한다. 그룹은 별도 화면이 갖는다.

기각 ① 목록 최상단에 그룹 섹션을 두고 무소속 서버만 시간 × 스펙으로 묶기 — 재편 시점에는 이쪽을 권고했으나, 설계를 진행하며 그룹이 시간 축을 가로지른다는 것이 드러나 철회했다. 나중에 합류한 서버는 다른 시간 묶음에 속하므로, 시간 → 스펙 계층 안에 그룹이 들어갈 자리가 없다. 그룹을 시간 밖으로 빼면 한 화면에 성격이 다른 두 계층이 겹친다.

기각 ② 보기 전환 탭(스펙 기준 · 그룹 기준) — 화면 복잡도를 올리고, 방금 검증을 마친 U3-3 골격에 churn 을 만든다.

채택안은 각 행에 소속 그룹 배지를 붙이고 그룹 자체는 전용 화면에서 다룬다. 두 화면이 서로 다른 렌즈를 갖되 어느 쪽도 다른 쪽을 흉내내지 않는다.

DEC-E. 그룹 삭제는 하드 삭제 + 확인 모달.

그룹을 지워도 서버 · 할당 · 스냅샷은 무사하고, 잃는 것은 이름과 멤버 명단뿐이다. 다시 만들면 복구된다.

기각 ① soft-delete + 휴지통 — 휴지통과 마커 인프라는 디스크 파일을 가진 자원을 위한 것이다. 그룹은 순수 DB 메타데이터라 격리할 실체가 없다.

기각 ② typed-name 확인 — 자원 영구삭제급 파괴력이 아니다. 확인 모달로 충분하다.

DEC-F. 이름은 전역 유일, 타입은 String.

유일성이 필요한 이유는 운영자가 이름으로 그룹을 지칭하기 때문이다. 강제 방식은 DB 제약 UNIQUE 하나로 끝난다 — GuestServer.name 이 같은 형태다.

같은 이름 문제를 SettingDefinition 이 다르게 푼 이유를 짚어둘 만하다. 그쪽은 U3-2-b 에서 soft-delete 를 얻으면서 UNIQUE 를 떼고 활성 행에 한정한 애플리케이션 검사(existsByNameAndIsDeletedFalse)로 바꿔야 했다. 삭제된 정의서가 이름을 계속 붙들면 같은 이름을 다시 쓸 수 없기 때문이다. 그룹은 하드 삭제라(DEC-E) 지워진 행이 남지 않으므로 그 우회가 필요 없다 — DEC-E 가 DEC-F 를 단순하게 만든다.

DEC-G. 폼은 전부 전역 인터셉터 경로 — data-native-submit 을 붙이지 않는다.

핸들러가 BindingResult 를 받지 않기 때문이다(성공은 redirect, 실패는 예외). new-form.md 판정표의 첫 줄에 해당하고, 거절은 안내 모달로 수렴한다.

함께 확인한 사실 하나 — static/global/form-submit.js:93 은 document.addEventListener('submit', ...) 로 위임 등록이다. 그래서 [data-live] 안에 폼을 둬도 SSE 재렌더 후 살아남는다. U3-1 에서 할당 폼이 죽었던 것은 페이지 로컬 스크립트가 폼 엘리먼트에 직접 바인딩했기 때문이고, 위험한 것은 [data-live] 자체가 아니라 직접 바인딩이다. 따라서 [그룹으로 만들기] 를 스펙 묶음 헤더 안에 둘 수 있다.

DEC-H. 회수된 서버도 그룹에 넣을 수 있다.

U3-3 의 DEC-I 를 잇는다 — 목록의 묶음에 그대로 두어 운영 이력을 지우지 않는다. 그룹에 있어도 U3-5 의 할당 가드가 배제하므로 무해하고, 여기서 막으면 예외가 하나 늘 뿐 얻는 것이 없다.

DEC-I. 스펙 이탈은 알림이지 차단이 아니다.

그룹 상세에서 멤버의 SpecGroupKey 가 둘 이상이면 배너로 알린다. 스펙은 정체성이 아니므로(DEC-A) 섞인 것 자체는 위반이 아니고, 엉뚱한 서버를 넣은 실수를 잡는 값만 취한다. 판정에 필요한 키는 GuestServerSummaryResponse 에 실어 보낸다 — 그 키는 목록 조립에서 이미 계산하므로 파싱 비용이 늘지 않는다.

DEC-J. 생성 진입점은 둘 — 씨앗과 빈 그룹.

빈 그룹은 물량이 순차 입고될 때 첫 서버가 오기 전에 자리를 잡아두는 용도다.

기각 목록에서 체크박스로 임의 선택해 만들기 — 선택 UI 를 목록에 더해야 하고 U3-3 골격 변경 폭이 커진다. 씨앗과 개별 추가로 같은 결과에 도달할 수 있어 지금은 넣지 않는다.

DEC-K. 멤버 추가 picker 는 무소속 서버만 보여준다.

다른 그룹의 서버를 옮기려면 먼저 빼야 한다. 두 단계지만 어느 그룹에서 빠지는지가 명시적이고, 화면이 조용히 남의 그룹을 건드리지 않는다.

DEC-L. 멤버십 이력은 남기지 않는다.

언제 넣고 뺐는지를 기록할 자리를 지금 만들지 않는다. "미래에 갈라질 수 있으니 미리 분리" 는 금지된 변명이고, 필요해지는 시점에 만든다. 현재 합류 시각은 멤버 행의 createdAt 이 담는다.

접근 자체의 대안 (기각)

  • 태그 · 라벨 방식 — 서버에 자유 라벨을 여러 개 붙이고 라벨로 거른다. 다중 소속이 자연스럽다는 장점이 있으나, 라벨은 "묶음" 이 아니라 "속성" 이라 멤버 명단을 하나로 다루는 조작(추가 · 제외 · 삭제)이 흩어지고, 이름을 바꾸면 사실상 다른 라벨이 되어 정체성이 없다. 요구 4 번("빼도 서버와 할당은 그대로")을 표현하기 어렵다.
  • 정의서에 서버를 매다는 방식(그룹 없이) — 새 개념이 0 이라는 점이 매력이지만, 정의서를 할당하기 전에는 묶을 수 없어 "함께 보기" 가 성립하지 않고, 정의서를 바꾸면 묶음이 사라진다. 그룹이 결정이라는 전제(DEC-A)와 어긋난다.
