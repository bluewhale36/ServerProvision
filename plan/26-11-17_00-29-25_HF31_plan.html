§1. 배경

버그 수정 plan 형식이라 표준 11 섹션과 인터랙티브 데모를 두지 않는다. 배경, 실측, 결정, 테스트 · CP5, 범위 밖 · 조율, Critical Files 순으로 적는다.

자원 화면의 [영구 삭제] 가 휴지통 화면과 다른 길을 타서 휴지통 실물과 감사 기록이 남지 않았고(C-1), 어느 화면에서든 영구 삭제가 원래 경로를 무조건 지워 그 사이 같은 경로에 등록한 다른 자원의 파일을 지울 수 있었다(C-15). 두 경로를 하나로 모으고, 원래 경로는 그 자원의 것일 때만 지운다.

1-1. 출처

  • docs 스트림(DOC-7 사용자 매뉴얼)이 코드와 대조해 넘긴 3차 결함 C-1(원료 D1) · C-15(데이터 손실 위험, 원료 N1).

1-2. 사용자 결정

  • 2026-11-17: "HF31 도 자동으로 진행하라" → CP1 · CP4 승인 게이트 없이 진행한다. 결정은 세션이 판정해 이 plan 에 기록한다.
§2. 실측
결함실태근거
C-1 ① 자원 화면 7 곳(OS 버전 · ISO · 메인보드 · BIOS · BMC · 드라이버 · RAID 카드)의 [영구 삭제] 가 도메인 *LifecycleService.purgeWithTypedNameCheck 를 직접 부른다. 휴지통 실물 정리와 감사 기록(purge_log)은 PurgeExecutor 에만 있어 빠진다 휴지통 화면 = TypedNameVerifier.verify → PurgeExecutor.execute
자원 화면 = TypedNameGuard.verify → 도메인 purge
C-1 ② 휴지통 화면에서 OS 버전을 영구 삭제해도 휴지통에 있는 하위 ISO 의 실물이 남는다. 실행기는 대상 자원 자신의 휴지통 실물만 지우고, 하위 ISO 행은 FK cascade 로 함께 사라져 경로를 잃는다 PurgeExecutorImpl.execute 의 실물 정리 = snapshot.getTrashedPath() 하나
C-15 도메인 purge 가 원래 경로를 무조건 지운다(BIOS · BMC · 드라이버 = 트리 재귀 삭제, ISO = 본체 + sidecar). 삭제(휴지통 이동) 때 원래 경로는 비므로, 그 뒤 같은 경로에 등록한 다른 자원의 파일이 영구 삭제 때 지워진다. 세 진입 경로(자원 화면 · 휴지통 화면 · 30 일 자동) 모두 해당 BundleTreeCleanupService.purgeExistingTree(treeRootPath)
IsoLifecycleService.cleanupArtifacts
부수 모든 사용자 영구 삭제가 실행기를 지나면, 활성 자원에 대한 direct POST 가 종전 409("먼저 휴지통으로")가 아니라 503(PurgeIoFailedException, 입출력 실패)이 된다 PurgeExecutorImpl.persistMissingSnapshot

D-3휴지통에 없는 자원 새 PurgeTargetNotInTrashException(409 ConflictException, "휴지통에 있는 자원만 영구 삭제할 수 있습니다. 목록을 새로 고친 뒤 다시 확인하십시오.", 내부 id 없음). 진입점이 휴지통 조회에서 먼저 던지고(실행기 · 감사 기록에 닿지 않음), 실행 중 다른 경로가 먼저 지운 경우는 실행기가 같은 예외를 원인으로 돌려준다 PurgeIoFailedException(503) 유지 활성 자원 · 이미 지워진 자원은 상태 충돌이지 입출력 실패가 아니다. 정상 화면에서는 [영구 삭제] 가 휴지통 행에만 있어 닿지 않는다(direct POST · 동시성 전용)
D-4원래 경로 보호(C-15) ProvisionMarkerService.isMarkedAs(Markable): 원래 경로의 마커가 이 자원(종류 · id)을 가리킬 때만 true. BIOS · BMC · 드라이버는 BundleTreeCleanupService.purgeOwnedTree, ISO 는 cleanupArtifacts 첫머리에서 이 판정을 거친다. 마커가 없거나 깨졌거나 다른 자원을 가리키면 지우지 않고 로그만 ① 원래 경로 정리를 아예 없앰
② DB 에서 같은 경로의 다른 자원 행을 찾아 판정		 ① 중복 확인 창의 [기존 영구 삭제 후 등록] 은 Deprecated(살아 있는) 자원도 지우는데, 그 파일은 원래 경로에 있어 고아가 된다
② 등록되지 않은 파일을 못 보고, 도메인마다 조회가 갈린다. 마커는 점검(reconciliation)이 이미 쓰는 파일 쪽 신원이다
D-5OS 버전의 하위 ISO 실물(C-1 ②) MarkableTrashOperator.dependentTrashedPaths(id) default 빈 목록, OS 버전 스캐너만 구현(휴지통 하위 ISO 의 실물 경로). 실행기가 도메인 purge 전에 모아 성공 뒤 자기 실물과 같은 가드로 지운다. 실패하면 지우지 않는다 OS lifecycle service 가 직접 휴지통 파일을 지움 휴지통 루트 가드(레이아웃 밖 · 얕은 경로 거부)가 실행기 밖에 한 벌 더 생긴다

§5. 범위 밖 · 조율
  • 중복 확인 창의 [기존 영구 삭제 후 등록](각 *NudgeService 가 lifecycle purge 를 직접 부름)은 감사 기록 · 휴지통 실물 정리가 여전히 빠진다 → M 세션 HF30(중복 확인 창 묶음)에 전달함. 원래 경로 보호(D-4)는 이 경로에도 적용된다(같은 도메인 purge 를 지나므로).
  • 마커가 없는 원래 경로 잔여물은 지우지 않으므로, 손으로 마커를 지운 자원의 원래 경로 파일은 남는다(점검 · 고아 정리 소관).
  • 매뉴얼의 C-1 · C-15 경고 문구 제거는 docs 세션 몫(병합 해시를 알린다).
