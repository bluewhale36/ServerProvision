§0. 요약
  • 무엇 : 세팅 정의서의 OS 후처리 설정(OS_SETTING) 단계를 RHEL 계열 정의서에서만 다시 열고, 설치 중 kickstart 로 적용하고, 첫 부팅 보고 한 번으로 결과를 받아 OS_SETTING phase 를 열고 닫는다.
  • 갈래 둘
    1. 기본 설정(SELinux 모드, systemd 서비스 지시, 추가 패키지)은 kickstart 고유 명령으로 싣는다. 관측값이 정의서와 다르면 실패.
    2. 사용자 쉘 스크립트(여러 개, 순서대로, bash)는 스크립트마다 chroot %post 로 싣는다. 종료 코드가 하나라도 0 이 아니면 실패.
    모두 맞아도 적용 여부는 사용자가 직접 확인해야 한다는 안내를 보인다.
  • 출발 : 토론 종결(2026-11-21, discussion/26-11-21_15-39-07_E4-1-b-7-os-setting_discussion.md). 선행 HF34(PR #128) · U9(PR #131) 모두 dev 병합. 브랜치 feat/E4-1-b-3_kickstart-generator 가 origin/dev 를 받음(f62bf5d, 전체 테스트 4,081 통과).
  • DB 스키마 변경 없음 : 정의서 payload · 할당 스냅숏 · 원장 meta 가 모두 json 컬럼.
  • 사용자에게 묻는 것 3 건 : O-1 ~ O-3(§8).

3-2. D-1 사용자 스크립트를 kickstart 에 싣는 방법

        

          
안내용판정

          
            
채택 (a) base64 로 실어 풀고 bash 로 실행%post --log=/root/spv-script-N.log 안에서 base64 를 풀어 /etc/spv/scripts/N.sh 로 쓰고 실행, 종료 코드를 N.rc 로내용 무관하게 kickstart 안 깨짐(%end 줄 · heredoc 구분자 줄 · 한글 · 따옴표). 종료 코드 파일로 남김

            
탈락 (b) 원문을 %post --interpreter=/bin/bash 본문으로원문 그대로종료 코드 남길 자리 없음(anaconda 는 로그만). % 시작 줄이 kickstart 를 깸

            
탈락 (c) 원문을 heredoc 으로 파일에 쓴 뒤 실행원문 heredoc구분자와 같은 줄이면 깨짐, % 줄 거부 + 구분자 줄 거부 둘 필요

          
        

        
%post --log=/root/spv-script-N.log
base64 -d > /etc/spv/scripts/N.sh <<'SPV_EOF'
(스크립트 내용의 base64)
SPV_EOF
cd /root && /bin/bash /etc/spv/scripts/N.sh
echo $? > /etc/spv/scripts/N.rc
%end

        
    
          
  • 결과: 토론의 "% 로 시작하는 줄 거부" 규칙은 (a) 에서 필요 없다 → O-3 으로 폐지를 묻는다.
    • 
          
  • CRLF: 저장 때 \r\n → \n. Windows 에서 만든 파일이 bash 에서 $'\r' 오류를 내는 것을 막는다. 내용 의미가 바뀌지 않으므로 화면에 알리지 않는다.
    • 
          
  • /etc/spv/scripts/ 는 b-5 보고 셸의 remove_all 이 /etc/spv 째 지운다(우리가 심은 파일). 로그 /root/spv-script-N.log 는 남는다.
    • 
          
  • 스크립트가 멈추면 설치가 멈추고, OS 설치 서빙 시한(RhelInstallTimeoutPolicy)이 OS_INSTALLING 을 실패로 닫는다. 스크립트별 시한은 두지 않는다(토론 범위 밖, 위험 표).
    •

3-4. D-3 관측을 어디서 하고 누가 판정하는가

        

          
안내용판정

          
            
채택 (a) 첫 부팅에서 셸이 원시 관측값만 보내고 서버가 판정report.env 에 관측 목록, 보고 셸이 getenforce · systemctl is-enabled <이름> · rpm -q --whatprovides --quiet <이름> · /etc/spv/scripts/N.rc 를 읽어 JSON osSetting 에판정 규칙이 서버 한 곳(SSOT, Single Source of Truth). 테스트 · 화면 · 데모가 같은 표. SELinux 실제 모드는 부팅 뒤에만 참

            
탈락 (b) 셸이 판정해 성패만 보냄셸에 판정 규칙규칙이 셸과 서버 두 곳, 화면에 관측값 못 보임

            
탈락 (c) %post 시점에 관측설치 중 관측SELinux 모드 · 서비스 상태가 부팅 뒤 값과 다를 수 있음

          
        

        
    
          
  • report.env 추가 키: SPV_CHECK_SELINUX='1'(OS_SETTING 있을 때만), SPV_CHECK_SERVICES='a b', SPV_CHECK_PACKAGES='x y', SPV_SCRIPT_COUNT='N'. OS_SETTING 이 없으면 키가 없고 JSON 에 osSetting 이 없다(지금 동작 그대로).
    • 
          
  • 패키지는 --whatprovides 로 본다. 사용자가 vim 처럼 제공 이름을 적어도 실제 패키지 vim-enhanced 를 찾는다.
    • 
          
  • 관측 실패는 "state":"unknown", 종료 코드 파일 없음은 null.
    • 
        

        
"osSetting":{"selinux":"enforcing","services":[{"name":"chronyd","state":"enabled"}],"packages":[{"name":"vim","installed":true}],"scriptExitCodes":[0,3]}


        
3-5. D-5 OS_SETTING phase 를 여닫는 자리 (R10)

        

          
안내용판정

          
            
채택 (a) 완료 처리 공통 흐름에 '전진 뒤' 훅, RHEL 이 OS 설정을 닫음OsInstallCompletionService.complete 가 advanceOrComplete 다음에 afterAdvanced(server, progress, report, now)(기본 없음) 호출. RhelInstallCompletionService 가 RhelOsSettingCloser 에 넘김같은 트랜잭션 · 보고 한 번. 공통 흐름 순서 그대로, 계열이 붙이는 일만 늘어남

            
탈락 (b) OS_SETTING 을 phase 실행기(ProvisioningPhaseExecutor)로/boot 디스패치설치 뒤 서버는 PXE 를 타지 않아 불릴 일 없음

            
탈락 (c) OS 설정 전용 보고 창구두 번째 보고토론 Q2 (c) 탈락(실패 지점 증가)

          
        

        
RhelOsSettingCloser
  커서가 OS_SETTING 진입이면
    → OsSettingVerdict 판정
    → 원장 단발 행 ProvisioningHistoryRecorder.recordInstant (step OS_SETTING, SUCCEEDED/FAILED, meta)
    → 성공: 다시 advanceOrComplete
    → 실패: progress.markFailed

        
    
          
  • 중복 보고: 공통 흐름이 먼저 no-op 으로 끝나므로 OS 설정도 다시 판정하지 않는다.
    •
