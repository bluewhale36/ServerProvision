§1. 현재 상태 (진단)

지금 Drift 한 행은 두 가지를 겸한다 — "무엇이 잘못되어 있다"(문제)와 "언제 그것을 보았다"(관측). 둘은 수명이 다르다. 문제는 고칠 때까지 살아 있고 관측은 점검마다 하나씩 생긴다. 한 테이블이 둘을 겸하니 문제의 수명을 적을 자리가 없다.

한 행이 겸하고 있는 두 역할

역할현재 필드 (maintenance/reconciliation/entity/Drift.java)수명
문제 (무엇이 잘못되어 있나) resourceType · resourceId · kind 운영자가 고칠 때까지 — 여러 점검에 걸쳐 지속
관측 (언제 그것을 보았나) report(@ManyToOne DriftReport) · detectedAt · oldPath · newPath · detail · observedHash 점검 1 회 — 다음 점검이 새 행을 만든다

그래서 지금 벌어지는 일 (코드 좌표)

#증상원인이 되는 코드
2-1 같은 자원의 같은 문제가 세 번의 점검에서 잡히면 서로 무관한 세 행이 되고, 각 행의 발견 시각은 자기 점검 시각이다. 화면은 이것이 어제부터 있던 문제인지 방금 생긴 것인지 알 수 없다. PathReconciliationService.performScan() 의 분류 루프가 매 회차 buildDrift(...) 로 새 Drift 를 만들고, detectedAt 에 그 스캔의 now 를 넣는다. 이전 회차 행과의 연결은 없다.
2-4 하나를 해결하면 그 행이 보고서에서 떨어져 나가 지난 보고서의 건수가 사후에 줄어든다. 동시에 이전 회차 보고서는 이미 고친 문제를 여전히 미해결로 보여준다. PathReconciliationService.apply() · dismiss() 가 drift.getReport().removeDrift(drift) 를 호출하고, DriftReport.drifts 는 orphanRemoval=true 라 DB 행이 사라진다. 화면의 "미해결" 은 DriftReport.getDriftCount() = 남은 자식 수다.

이미 안정된 부분 — 보고서 자체는 흔들리지 않는다

drift_report 는 점검 이력을 담는 별도 테이블이고, 점검 시각(scannedAt) · 정밀 여부(deep) · 점검 자원 수(totalChecked) · 탐지 수(detectedDriftCount) 는 그 시점 값으로 굳어 변하지 않는다. 탐지 수 스냅샷은 HF4-4 가 이미 넣었고 DriftReport.addDrift() 안에서만 증가하며 removeDrift() 는 감소시키지 않는다. 흔들리는 것은 거기 매달린 드리프트 목록과 그로부터 세는 "미해결" 뿐이다.

보관 한도는 reconciliation.report.retention-count 기본 100 건이고 (PathReconciliationService.pruneOldReports() 의 FIFO 삭제), reconciliation.scan.interval-ms 기본 1 시간이라 약 나흘이면 오래된 이력이 사라진다. 이 수치는 §8 의 과거 데이터 처리 결정에서 다시 쓰인다.

핵심 진단 — 문제의 수명을 적을 자리가 없는 것이 원인이고, "언제부터인지 모른다"(2-1)와 "과거 기록이 사후에 바뀐다"(2-4)는 같은 뿌리에서 나온 두 증상이다. 화면 배치를 바꿔서는 해소되지 않는다 — 데이터 모델을 나눠야 한다.

진입 전제

  • MK4 사용성 진단(2026-08-02 ~ 08-03)에서 개선 후보 28 건 + 범위 밖 관찰 3 건이 나왔고 사용자가 전부 채택했다.
  • 그중 전역 공용 문구 결함 4 건은 HF5 로 분리되어 완료되었다 — 이 슬라이스는 그 4 건을 다시 다루지 않는다.
  • MK4 토론 2 라운드에서 이 슬라이스가 담을 항목 6 가지가 확정되었다(§2).
  • 선행 코드는 전부 존재한다 — 탐지(S6-1 ~ S6-3) · 해결 전략 디스패치(S6-2-1) · 재점검(S6-3-3) · 내용 수용(S6-3-4) · 중복 해소(HF4-5). 이 슬라이스는 그 위에 지속 모델을 얹는다.
§2. 요구사항 (확정) + 비목표

MK4 토론 2 라운드에서 확정된 것 중 이 슬라이스가 담는 것.

  1. 신원의 분리 — 자원 종류 · 자원 번호 · 드리프트 종류로 신원을 갖는 지속되는 문제와, 점검별 관측을 나눈다.
  2. 수명의 기록 — 최초 발견 시각 · 마지막 관측 시각 · 관측 횟수를 갖고, 이번 점검에서 처음 보인 문제를 구분한다.
  3. 자동 해소 — 이번 점검이 커버한 범위에서 더 이상 보이지 않는 문제는 자동으로 해소 처리한다.
  4. 과거 불변 — 지난 점검 보고서를 사후에 바꾸지 않는다.
  5. '보고 닫기' → '지금은 두고 보기' — 기간 또는 조건 동안 목록에서 내리고 사유를 남긴다.
  6. 되돌리기의 재료 — 되돌리기에 필요한 이전 값을 기록한다.
비 목표 :
  • 되돌리기의 실행과 화면 — 이번에는 기록만 남긴다. 되돌리기 실행은 기록이 쌓인 뒤 별도 슬라이스로.
  • 우선순위 계산과 점검 커버리지 표시 — MK4-2 로.
  • 화면 배치 변경 — MK4-4 로. 이 슬라이스는 §5 에 적은 최소 표시만 얹는다.
  • 프로비저닝 가드(드리프트 있는 자원의 사용 차단) — 별도 토론 후 결정.
🎬 미리보기 — 점검 회차 시뮬레이터 (지금 방식 vs 새 방식)

이 슬라이스의 값어치는 여러 번의 점검에 걸쳐 무엇이 어떻게 이어지는가에 있어서 한 시점 화면으로는 보이지 않는다. 아래에서 점검 종류를 고르고 [점검 실행] 을 누르면 회차가 하나 진행된다. 자원의 상태를 바꾼 뒤 다시 점검을 돌려 보면, 같은 조작에 지금 방식과 새 방식이 어떻게 다르게 반응하는지가 좌우로 나란히 보인다.

점검 종류 :

지금 방식 — 점검마다 새 기록

새 방식 — 문제 + 관측

드리프트 0 — 데모의 커버 범위 판정은 DriftKind.coveredBy(boolean deep) 의 JS 1:1 재현이다. 스캔의 자동 해소 대상 판정(§4 판정 규칙 4) · 화면의 "이번 점검이 보지 않은 종류" 표시 · 이 데모가 같은 한 메서드를 소스로 한다. 데모에서 일반 점검이 HASH_MISMATCH 를 해소하지 않는 것과 서버가 해소하지 않는 것은 같은 판정이다.
데모에서 꼭 해 볼 것 :
  1. [점검 실행] 을 두세 번 반복 — 새 방식의 관측 N회 만 늘고 문제는 하나로 유지되는지.
  2. 어떤 자원에 [운영자가 직접 되돌림] 을 누른 뒤 점검 — 관측되지 않은 문제가 자동 해소되는지.
  3. 내용 변경이 있는 자원을 두고 일반 점검만 반복 — 그 문제가 해소되지도 관측되지도 않는지(규칙 4의 커버 범위).
  4. 어떤 문제에 [해결] — 지금 방식에서 그 회차의 미해결 수가 사후에 줄고, 이전 회차는 이미 고친 문제를 계속 미해결로 보여주는지(후보 2-4).
  5. [두고 보기] 후 점검 두 번 — 목록에서 내려갔다가 만료되어 다시 열리는지(규칙 5).

§4. 도메인 모델 (SSOT)

두 갈래 비교 — 승격(채택) vs 강등(탈락)

채택 : 승격

  • 기존 Drift 가 그대로 문제가 된다.
  • 관측을 담는 엔티티 DriftObservation 을 새로 만든다.

탈락 : 강등

  • 문제 엔티티를 새로 만들고 기존 Drift 를 관측으로 내린다.
기준승격 (채택)강등 (탈락)
문제를 다루는 코드 해결 전략 · 재점검 전략 · 컨트롤러 · 화면이 받는 타입 그대로 전부 새 타입으로 교체 (본문 18 파일 · 테스트 15 파일이 Drift 를 참조)
화면 주소의 선택 식별자 문제 번호라 점검을 넘어 유지 — 처리 후 선택이 풀리던 마찰(후보 4-3)이 완화된다 관측 번호라 점검마다 값이 달라진다
이름과 의미 Drift 가 문제를 뜻하게 된다. 화면이 이미 그렇게 부르고 있어 어휘는 맞으나, 이름만 보면 관측으로도 읽힌다 이름과 의미가 정확히 일치
기존 행 이관 같은 신원이 점검 횟수만큼 중복돼 있어 접어야 한다 기존 행이 그대로 관측이 되어 이관 불필요
이관 비용은 판단 근거가 되지 못한다. 드리프트 행은 디스크와 데이터베이스를 대조해 매번 새로 계산하는 값이라 다음 점검이 그대로 복원한다. 재생성되지 않는 것은 점검 보고서 행뿐인데 그마저 100 건 · 나흘만 유지되고(retention-count 100 · 주기 1 시간) 담긴 정보는 "언제 · 몇 건 봤다" 수준이다. 그래서 강등의 유일한 이점이 사라지고, 설계 적합성과 변경 폭이 모두 승격을 가리킨다.

운영자가 화면에서 다루는 것은 지금 있는 문제다. 해결도 · 순서도 · 두고 보기도 · 되돌리기도 문제에 붙고, 관측은 "언제 봤는지" 를 설명하는 이력일 뿐 직접 다루지 않는다. 1 급 개념이 문제여야 코드가 읽힌다.

이름 변경은 하지 않는다. Drift 를 문제에 맞는 이름으로 바꾸면 의미는 또렷해지지만 승격의 최대 이점인 "소비처 무변경" 이 대부분 사라진다. 새로 생기는 관측 쪽에 또렷한 이름 (DriftObservation)을 주는 것으로 충분하다고 본다. 이 판단은 §8 에 결정으로 남긴다.

DriftStatus 신규 OPEN(열림) · RESOLVED(해결됨) · SNOOZED(두고 보기) 상태는 화면 배지 · 목록 필터 · 전이 가드가 함께 쓰는 도메인 값. boolean resolved 두 개로 쪼개면 resolved=true·snoozed=true 같은 불법 조합이 표현 가능해진다(DriftResolutionMode 3 단 도입 때와 같은 논거).
DriftHandlingAction 신규 APPLY · RECHECK_RESOLVED · ACCEPT_HASH · RESOLVE_DUPLICATE · SNOOZE · UNSNOOZE · SCAN_UNOBSERVED 처리 종류는 사용자 문구(라벨) · 되돌리기 가능 판정을 함께 지닌다. 문자열로 두면 이력 조회가 오타에 뚫린다. 라벨과 판정은 상수 메서드로 — DriftKind 선례.
SnoozeWindow 신규 DAYS_7 · DAYS_30 · UNTIL_NEXT_DEEP_SCAN "기간 또는 조건" 을 int days 로 받으면 조건형을 표현할 수 없고 0 · 음수 검증이 흩어진다. 각 상수가 expiresAt(Instant now) 를 스스로 계산한다.
DriftKind 필드 2 추가 deepOnly · reversible 커버 범위와 되돌리기 가능 여부가 종류가 이미 갖고 있는 성질이다. 서비스에 if (kind == HASH_MISMATCH) 분기를 늘리지 않고 데이터 필드 + 메서드로 흡수한다(recheckable 축 신설 선례).
경로 Value Object 는 이번에 도입하지 않는다. oldPath · newPath 가 String 인 것은 마커 인프라 · 스캐너 SPI · 자원 도메인 전반에 걸친 표기라, 여기서 VO 로 바꾸면 이 슬라이스가 자원 전 도메인 리팩터로 번진다. 새로 생기는 previousPath · movedToPath 는 기존 표기와 같은 형태를 유지하고, 경로 VO 화는 별도 R* 캠페인으로 미룬다(§8 에 잔존 책임으로 기재).

§4 판정 규칙 — 데모와 구현의 단일 명세

#점검 한 회차가 도는 순서
1지금처럼 디스크와 데이터베이스를 대조해 이번에 발견된 문제들의 신원 목록을 만든다.
2각 신원에 대해 열린 문제가 이미 있으면 그것을 쓰고, 없으면 새로 만들며 최초 발견 시각을 이번 점검 시각으로 둔다.
3문제의 마지막 관측 시각과 관측 횟수를 갱신하고 최신 스냅샷을 덮어쓴다. 관측 행을 하나 만들어 이번 보고서에 붙인다.
4이번 점검이 커버한 종류 중, 열려 있는데 이번에 발견되지 않은 문제는 해소로 처리한다.
5두고 보기 기간이 지난 문제는 다시 열림으로 되돌린다.
4 번의 "커버한 종류" 가 이 규칙의 핵심이다. 일반 점검은 파일 내용을 보지 않으므로 (performScan 의 if (deep) 블록 안에서만 HASH_MISMATCH 가 생성된다) 일반 점검 결과로 내용 변경 문제를 해소하면 안 된다. 이 규칙이 없으면 일반 점검이 돌 때마다 내용 변경 문제가 사라졌다 정밀 점검에서 되살아나기를 반복한다. 커버 범위는 DriftKind.coveredBy(deep) 에서 파생하고 새 분기를 만들지 않는다.

왜 기존 예외에 factory 를 더하지 않는가 — DriftResolutionNotAllowedException 의 문구는 전부 "시스템이 해결할 수 없습니다 / 해결 옵션이 꺼져 있습니다" 계열이고, 설정 키 (reconciliation.resolution-enabled)와 어휘를 맞춰 S6-2-1 에서 개명된 것이다. 두고 보기는 해결이 아니라 보류라 같은 이름 아래 두면 그 어휘 정합이 다시 깨진다. 비채택 대안: 기존 예외에 snoozeNotAllowed() 추가 — 파일은 안 늘지만 예외 이름이 실제 의미를 배신하고, 화면 오류 문구가 "해결" 을 말하게 되어 탈락.
§8. 예상 부산물 / 주의 / 결정 사항

D1. 과거 데이터 처리 채택 = 1 안

1 안 (채택) — 드리프트 행만 비운다

  • 기존 drift 행을 비우고 새 구조로 간다.
  • 과거 보고서는 남지만 눌러도 목록이 비어 보인다.
  • 점검 이력의 값(언제 · 몇 건 봤다)은 보존된다.

2 안 (탈락) — 보고서까지 비운다

  • 화면이 깔끔하다.
  • 나흘치 점검 이력이 사라진다.

채택은 1 안이다. 점검 이력의 값은 남고, 다음 점검 한 번이면 현재 상태가 복원된다 (드리프트는 디스크와 DB 를 대조해 매번 새로 계산하는 값이다). 다만 첫 점검 전까지는 화면이 비어 보이므로 그 사실을 배포 시 알려야 한다 — release note 와 report 의 "배포 시 주의" 에 명시한다.

D2. 동시성 — 같은 신원의 열린 문제가 둘 생기지 않게 채택 = 조회로 보장

문제를 만드는 경로는 점검 회차 하나뿐이고, 동시 점검은 PathReconciliationService 의 AtomicBoolean running + ReconciliationAlreadyRunningException 으로 이미 막혀 있다 (수동 · 주기 · 시작 시 트리거가 전부 triggerScan 을 지나고, 마커 재발급도 같은 잠금을 공유한다). 그래서 (자원 종류, 자원 번호, 종류, 열림) 부분 유일 제약을 새로 걸지 않고, 규칙 2 의 조회로 보장하는 쪽을 채택한다.

안이점비용 · 위험
조회로 보장 (채택)MariaDB 는 부분 인덱스가 없어 "열린 것만 유일" 을 표현하려면 상태를 인덱스 키에 넣는 우회가 필요한데 그 우회 없이 간다. 스키마가 단순해진다.점검 잠금이 깨지면(다중 인스턴스 배포 등) 중복 문제가 생길 수 있다. 이 시스템은 단일 인스턴스 admin 이고 다중화 계획이 없다 — 그 전제가 깨지는 시점에 제약을 추가한다(잔존 책임).
유일 제약 (탈락)DB 가 불변식을 지킨다."열린 것만" 을 표현하려면 resolved_at 을 키에 넣거나 status 를 포함해야 하는데, 그러면 해결된 같은 신원이 여러 번 쌓이는 정상 상황과 충돌한다. 회피하려 sentinel 값을 넣는 순간 도메인이 스키마 사정에 오염된다.

여기에 더해 Drift.@Version 낙관적 락은 그대로 유지한다 — 점검의 상태 전이와 운영자의 처리가 겹치는 순간은 여전히 있고, 그 충돌은 409 로 표면화되는 편이 낫다.

D3. 이름 변경 보류 채택 = Drift 유지

Drift 를 문제에 맞는 이름(DriftIssue 등)으로 바꾸면 의미는 또렷해지지만, 승격을 택한 최대 이유인 "소비처 무변경" 이 대부분 사라진다 — 해결 전략 · 재점검 전략 · 두 컨트롤러 · 화면 · 테스트가 전부 타입 이름을 따라 바뀌어 강등안과 변경 폭이 비슷해진다. 새로 생기는 관측 쪽에 또렷한 이름을 주는 것(DriftObservation)으로 충분하다고 본다. 엔티티 Javadoc 첫 줄에 "이 타입은 지속되는 문제다 — 관측은 DriftObservation" 을 명시해 이름이 남기는 모호함을 문서로 덮는다.
