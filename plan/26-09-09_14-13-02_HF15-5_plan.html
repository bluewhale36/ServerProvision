§2. 요구사항 (확정) + 비목표
  1. 번호의 근거를 실물 관측으로 — RAID 검증 재채집이 lsblk(순서 · WWN)를 동봉하고, OS 영역 볼륨의 SCSI 식별자를 가진 장치의 인덱스를 디스크 번호로 쓴다. BMC 가상 미디어(USB · 크기 0B)는 세지 않는다.
  2. 계열 순서 규칙은 폴백으로 남긴다 — 재채집이 없거나(구 에이전트) 식별자를 못 찾으면 계열별 나열 규칙(MPT_IR = ID 내림차순 · MEGARAID = 나열 순)으로 계산한다. 둘 다 안 되면 BLOCKED 로 서빙을 막는다.
  3. 확증 기준을 계열 변환으로 — 설치 뒤 Get-Disk UniqueId 와 대조할 값은 볼륨 WWN 원문이 아니라 계열별 변환의 결과다. 이 변환은 서빙 시점에 원장 meta 에 박아 두고 완료 보고가 그것을 읽는다.
  4. RAID 단계가 남았으면 계획으로 판정 — 실물 볼륨이 없어도 계획에 OS 영역이 있으면 "RAID 구성 뒤 확정"(DEFERRED)이고 준비도는 READY 다. 계획에도 없을 때만 BLOCKED 로 미리 알린다.
  5. 수집 불가 값은 띄우지 않는다 — 컨트롤러 뒤 볼륨 행은 종류 · 전송을 비우고 "RAID 볼륨 · spvR1V1" 로 표기한다. 가상 미디어 행은 화면에서도 숨긴다(번호 계산과 같은 걸러내기).
  6. 안내는 다음 할 일을 짚는다 — Windows 카드의 "설치 대상 디스크" 줄은 확정이면 번호와 근거를, 미확정이면 무엇을 기다리는지를 문장으로 말한다.
비 목표 :
  • WinPE 사전 게이트(설치 직전 diskpart 로 번호를 재확인) — E4-1-a-7 로 넘긴다. 이번에는 "설치 전 판정 + 설치 후 확증" 두 지점만 다룬다.
  • 물리 디스크 직결(passthrough) 지원 — 그 순서는 미실측이라 종전대로 BLOCKED 를 유지한다.
  • 볼륨 3개 이상의 IR 나열 순서 — 실기 표본이 2개까지다. 규칙은 그대로 두고 실측 항목으로 적립한다.
  • 진단 시점 디스크 목록의 갱신 주기 일반화 — 이번 갱신은 RAID 검증 통과 시점 한 곳에서만 일어난다.

§4. 도메인 모델 (SSOT)

설계 대안 — 번호의 근거를 어디서 얻을 것인가

안요지판정
① 계열별 순서 규칙카드 계열마다 "CLI 나열 순서 → OS 번호" 변환을 둔다보조로 채택 — 볼륨 2개까지는 실측(3/3 + 2/2)이지만 3개 이상은 가설이다. 관측이 없을 때의 폴백으로만 쓴다
② lsblk 재채집 + SCSI 식별자 매칭볼륨을 만든 뒤 다시 부팅한 리눅스가 본 순서를 그대로 쓴다본안 채택 — 계열 분기가 없고, Linux 와 Windows 가 같은 SAS 타깃 탐색 순서를 따른다는 실기 2호 Run 3 D1 근거가 있다
③ WinPE 사전 게이트설치 직전 diskpart 로 번호를 다시 확인탈락 — 가장 정확하지만 설치 스크립트 계약을 늘린다. E4-1-a-7 로 분리
핵심 발견 — 계열별 변환 windowsUniqueIdOf(볼륨 wwn) 하나가 두 문제를 동시에 푼다. ② 의 lsblk WWN 매칭과 F-7 의 설치 뒤 UniqueId 확증은 같은 SCSI NAA 식별자를 다른 쪽에서 읽은 것이기 때문이다. 변환을 한 곳에 두었으므로 매칭과 확증이 어긋날 수 없다.

판정 순서 (WindowsDiskSelection.judge)

osVolume 없음                      → BLOCKED "os volume missing"
inventory 없음 · 빈 목록           → BLOCKED "raid inventory missing"
RAID 레벨 없는 볼륨(passthrough)   → BLOCKED "passthrough not supported"

expected = uniqueIdOf(family, osVolume.wwn)
① lsblk 인덱스  = 컨트롤러 디스크만 세어(USB · 0B 제외) expected 와 일치하는 위치
   ≥ 0  → CONFIDENT(diskId, expected, basis=lsblk)
② 계열 순서 규칙 = family.windowsDiskOrder(inventory.volumes) 에서 식별자(우선) · 이름으로 찾은 위치
   ≥ 0  → CONFIDENT(diskId, expected, basis=inventory-order)
그 외                              → BLOCKED "os volume not in inventory"

준비도 합류 (F-1)

실물 OS 볼륨 있음 ──judge──▶ CONFIDENT / BLOCKED 실물 없음 + RAID 단계 남음 ──계획에 OS 영역 있음──▶ DEFERRED (준비도 READY · 서빙은 아직) 실물 없음 + RAID 단계 남음 ──계획에도 없음────────▶ BLOCKED "os volume missing in plan" (+ osAbsenceReason) 실물 없음 + RAID 단계 지남 ──judge──▶ BLOCKED "os volume missing"

WindowsInstallReadinessResolver.combine 은 BLOCKED 만 막고 DEFERRED 는 통과시킨다. RAID 분기를 WindowsInstallReadiness 진리표에 늘리지 않고 resolver 에서 합류시킨 이유는, 그 진리표가 "소스 · 이미지 · 운영 설정" 축이라 디스크 축을 섞으면 칸 수가 곱으로 늘기 때문이다.
