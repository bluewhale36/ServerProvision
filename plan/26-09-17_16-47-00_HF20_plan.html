§1. 배경

이 문서는 버그 수정(HF) 슬라이스의 CP1 산출물이다. 표준 11 섹션 대신 상황 파악과 해결책 탐색에 필요한 네 절만 둔다 — 배경 · 실측 · 결론 · 수정 방향이다.

1-1. 무엇이 멈췄나

2026-09-17 사내망 실기에서 같은 기계(MS04-CE0 · CRA3338)가 정의서 9 를 거듭 돌릴수록 BIOS 의 Fixed Boot Order (FBO201 ~ FBO205 · 셋업 메뉴의 Boot Option #1 ~ #5)에서 내장 셸(UEFI AP)이 위로 올라왔다. 셸이 1순위가 되자 오버라이드 없이 도는 Windows Setup 의 재부팅이 UEFI 셸로 떨어져 설치가 멈췄다 (1호기 · 2호기의 3번째 사이클). 운영자가 BootOrder PATCH 로 살렸다.

1-2. 직전 두 슬라이스가 남긴 자리

HF17(2026-09-16)은 Continuous 오버라이드가 Fixed Boot Order 를 영구 교체하는 부작용을 Once 로 회귀시켜 막았다고 보았다. 그러나 Once 도 그룹 순서를 남긴다는 것이 이번 계측으로 드러났다.

HF19 는 BIOS 설정 단계에서 Fixed Boot Order 5속성을 기본값으로 PATCH 하는 증상 방어였다. 계측 결과 그 뒤에 오는 Once 가 다시 맞바꾸므로 근본이 아니며, 이 plan 이 대체한다.

§2. 실측 (2026-09-17)

계측 방식 — 사내망 VM 에서 30초마다 BMC 의 PowerState · Override · BootOrder · FBO201 ~ FBO205 를 읽어 변화가 있을 때만 기록하는 루프를 돌렸다. 대상은 2호기 BMC 10.1.1.9 이고, 시각은 VM 시계 기준이다.

2-5. 코드 · 이력

앱은 UefiShell · BiosSetup 을 대상으로 한 오버라이드를 쓴 적이 없다. BootOrder PATCH 는 AMI 가 If-Match 를 요구한다(428) — 앱의 RedfishClient 는 이미 If-Match: * → 412 시 fresh ETag 사다리(E0-4-1)를 가지며, RedfishBiosService.patchPending 이 그것을 쓴다.

§3. 결론
이 AMI BIOS 는 POST 때 BootOrder 첫 항목이 속한 그룹을 Fixed Boot Order 1순위로 올리고, 종전 1순위 그룹을 그 자리로 내린다(맞바꿈). 그리고 그 결과를 되돌리지 않는다.

행위자 셋 — 사이클마다 다음 셋이 BootOrder 첫 항목을 바꾸고, BIOS 가 그것을 그룹 순서로 옮겨 적는다.

  1. 우리의 Once = Pxe — 그 POST 의 첫 항목이 PXE 가 되므로 Network 가 1순위로 올라간다.
  2. BIOS 설정이 실제로 적용되는 POST(pending 이 있을 때)가 부팅 항목 목록을 숫자 순으로 재구성해 셸(Boot0001)이 첫 항목이 되고, 그 POST 에서 AP 가 1순위로 올라온다(실측 6 · 02:59:18). 굽기 뒤 POST 는 항목 번호를 옮기지만 첫 항목(PXE)은 유지했다. 두 POST 모두 Once 오버라이드를 타지 않고 지나가(4분 미도착), 재무장의 다음 POST 가 다시 Network 를 1순위로 올린다.
  3. Windows Setup 의 항목 생성 — Hard Disk 가 1순위로 올라간다.

사이클마다 ①이 누적되고 거기에 ②가 끼면 셸이 위로 올라오며, ③이 마지막에 오면 기본값으로 되돌아온다.

따라서 정정은 "Fixed Boot Order 를 써 두는 것"(HF19)이 아니라 BootOrder 첫 항목을 우리가 원하는 그룹으로 두고 BIOS 의 맞바꿈이 그대로 따라오게 하는 것이다. 셸이 첫 항목이 될 길을 막고(무장 전 셸을 맨 뒤로), 종단 때 디스크를 첫 항목으로 되돌린다.
