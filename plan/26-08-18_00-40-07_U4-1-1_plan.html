§1. 현재 상태 (진단)

이 슬라이스는 세팅 정의서의 OS 설치 단계에 “어떤 디스크를 어떤 RAID 로 묶는가”(디스크 묶음 규칙)와 “어떤 RAID 카드를 전제하는가”를 적을 수 있게 한다. 실제로 RAID 를 거는 집행은 E 영역에 남는다. 입력은 U4-1 토론 8 회차의 결정(D1~D9 · E1~E35)과, RAID 카드 자원을 등록하는 MA7(PR #39 병합)이 넘긴 계약이다. 아래는 착수 전에 코드에서 확인한 사실이다.

payload 가 JSON 이라 필드를 더해도 테이블이 바뀌지 않는다. 대신 반대 방향의 부담이 생긴다 — 이미 저장된 정의서에는 새 키가 없어, 역직렬화에서 그 자리를 빈 목록으로 메우지 않으면 기존 정의서의 상세와 수정 폼이 깨진다. 요청 객체는 베이스(공통) · 중간층(계열) · 잎(@JsonCreator 생성자) 세 층이고, 검증도 그 층에 맞춰 자원 참조와 계열 필드로 나뉘어 있다. 베이스의 javadoc 은 “모든 OS 설치의 진짜 공통만 베이스에 둔다” 를 원칙으로 적어 두었다.

선택지 응답은 비활성 자원을 렌더에서 빼고 deprecated 는 배지 메타와 함께 남기며, 상세는 id 를 표시명으로 바꾸고 못 찾으면 #id 로 폴백한다. MA7 은 판정을 이미 넘겼다 — SupportedRaidLevels.blockReasonFor 가 화면 안내이자 거절 사유가 되는 문구를, RaidLevel.minimumDisks(cardHasCache) 가 캐시 보유 카드에서 RAID0 만 1 로 낮아지는 최소 디스크 수를 돌려준다. 다만 카드 참조는 소프트참조라 “참조한 카드가 사라진 상태” 를 보이게 하는 일이 이 슬라이스로 남는다.

할당 판정에는 디스크 축이 들어올 자리가 AssignmentEligibility 의 javadoc 으로 예고돼 있지만 대조할 재료가 없다. 진단 에이전트가 lspci 를 옵션 없이 불러 Subsystem ID 를 남기지 않으므로 카드 모델 대조가 불가능하고, RAID 분류가 문자열 규칙이라 Serial Attached SCSI controller 로 보고되는 CRA3338 은 ETC 로 떨어져 존재 대조마저 오판한다.

진단 결론 — 정의서 쪽의 표현 · 검증 · 화면은 선례가 전부 있고, 없는 것은 “서버의 실제 카드와 대조할 재료” 하나다. 그래서 이 슬라이스는 표현까지 하고, 대조는 재료가 생기는 E 계열 뒤로 보낸다(§8 D8).

§4. 도메인 모델 (SSOT)

4-1. 요청 계약 (신규 — provisioning.setting.dto.request · enums)

DiskGroupRuleRequestraidLevel · diskType · transport · capacity · count묶음 규칙 하나 · buildsRaid() = raidLevel != null

raidLevel 은 nullable 이고 null 이 곧 ‘RAID 없음’(화면 표기 — 디스크를 그대로 사용) 이다 — 래퍼를 두지 않는 이유는 §8 D2 에 있다. DiskCapacityRequirement 는 BoardModelSelectionRequest 의 관용구를 따라 @AssertTrue 로 “SPECIFIED ⇔ size · unit 있음” 정합을 스스로 검사한다.

// OSInstallationRequest (베이스, 수정)
Long raidCardId;                                 // nullable · 소프트참조
List<@Valid DiskGroupRuleRequest> diskGroups;     // null → 빈 목록

boolean requiresRaidCard();                      // diskGroups 중 buildsRaid() 가 하나 이상
@AssertTrue(message = "RAID 를 구성하는 묶음이 있으므로 RAID 카드를 지정해야 합니다.")
boolean isRaidCardPresentWhenRequired();         // !requiresRaidCard() || raidCardId != null

오류 필드 경로는 processList[i].raidCardPresentWhenRequired 로 오므로, 폼의 카드 그룹 컨테이너가 data-error-field="raidCardPresentWhenRequired" 로 정확히 일치시켜 받는다(firmwareSelectionCoherent 가 쓰는 resolveErrorTarget 관례). 반면 InvalidDiskGroupException 의 field 는 맨 경로 diskGroups 여서 partitions 처럼 문서 전역의 data-error-field="diskGroups" 에 매핑된다. 잎 요청 둘은 생성자에 두 파라미터를 더하고 withPatchedPasswords 가 복사 때 함께 옮긴다.

4-2. 값 규칙 DiskGroupRules (신규 · static · 의존 0 · service/reference/os/)

validate(List<DiskGroupRuleRequest> rules, RaidCard card /* nullable */) 가 다섯 가지를 본다.

  1. RAID 를 구성하는 규칙에서 card.getSupportedRaidLevels().blockReasonFor(level) 가 사유를 돌려주면 → unsupportedLevel(i, reason)
  2. RAID 를 구성하는 규칙에서 count.value < level.minimumDisks(card.hasCache()) → tooFewDisks(i, level, min, given)
  3. RAID 없음 규칙에서 count.value < 1 → singleDiskCountBelowOne(i)
  4. 다섯 축이 모두 같은 규칙이 둘 → duplicateRule(i, j)
  5. 용량이 SPECIFIED 인데 size < 1 → invalidCapacity(i)

3 번은 record 의 @Min(1) 이 1 차로 걸러내므로 안전망이다. 카드가 null 인데 RAID 규칙이 있는 상황은 @AssertTrue 가 먼저 400 으로 끊어 여기까지 오지 않으며, 그래도 오면 1 번을 건너뛴다.

4-3. 참조 검사 (OSInstallationReferenceInspector 수정 — 1 단 = 베이스 필드 책임)

  • raidCardId != null → raidCardRepository.findById + !isDeleted. 없으면 RaidCardNotFoundException(404)
  • !isEnabled 면 DisabledResourceReferenceException("raidCardId", "RAID 카드 …")(409)
  • 통과한 카드로 DiskGroupRules.validate 호출
  • describeDeprecatedReferences 에 deprecated 카드명을 더한다 — ISO 관례대로 저장은 허용하고 상세에서 경고한다
  • referencedResources(MK4-2 드리프트용)는 파일 자원 전용이므로 카드를 넣지 않는다

4-5. 화면 계약

setting-new.html 의 OS_INSTALLATION 카드에서 ISO · 타임존 다음, 파티션 구성 앞에 “디스크 구성” 그룹을 넣는다. 위는 RAID 카드 select(선택 안 함 / vendor optgroup, 옵션 data-* 로 has-cache · levels · block-reason-<LEVEL> · deprecated), 아래는 디스크 묶음 표(n-tbl-list — RAID 레벨 · 종류 · 전송 · 용량 · 개수 · 삭제)와 + 묶음 추가 버튼이며, 행은 파티션 표의 관례대로 tplDiskGroupRow 템플릿을 복제한다. 수정 폼 prefill 에서 저장된 카드가 선택지에 없으면 bsPrefillWarning 관례의 경고 줄을 띄운다.

setting-process-cards.html 의 상단 표에는 RAID 카드 행이 붙는다 — 미지정은 muted “지정 안 함”, 있으면 이름과 캐시 배지, 참조가 끊겼으면 muted “(사라진 카드 #id)”, deprecated 면 배지다. 그 아래 “디스크 구성” 소절 표에서 레벨 없음은 “RAID 없음” 배지, AUTO 는 muted “자동 탐지”, 개수는 “2개” 또는 “3개 이상” 으로 읽히고, 빈 목록이면 muted “설정 안 함 — 설치기가 자동 선택” 한 줄이다. 두 miller 피커는 이 fragment 를 공유하므로 자동 반영된다.

setting-form.js 는 stepBuilders.OS_INSTALLATION 에 두 필드를 더하고 stepPrefillers.OS_INSTALLATION 을 대응시키며, §8 D7 의 진리표 함수를 갖는다. 판정 재료는 전부 option 의 data-* 에서 읽어 문구를 새로 짓지 않는다.

4-6. 무변경 확인

D1 — 필드 위치. 묶음과 카드는 베이스 OSInstallationRequest 에 둔다. RAID 는 OS 가 올라오기 전 카드가 하는 일이고 Windows 도 같은 전제를 가지므로(토론 D3), “진짜 공통만 베이스” 원칙에 실제로 맞는다. 중간층으로 내리면 Windows 지원 시점에 같은 필드를 옆에 복제해야 한다. 새 SettingProcessType 안은 phase 매핑 골격까지 건드리게 되어 탈락했다 — 토론 R-5 ① 을 정한 이유와 같다.

D2 — 표현. 이름은 ‘RAID 묶음’ 이 아니라 ‘디스크 묶음’ 이다 — 레벨이 없는(‘RAID 없음’) 규칙도 같은 목록에 담긴다. RaidLevelSelection(mode, level) 래퍼를 만들지 않은 것은 표현할 의도가 ‘없음’ 하나뿐이어서, BoardModelSelectionRequest 가 래퍼로 피하려던 AUTO · SPECIFIED 모호성이 이 축에는 없기 때문이다. 용량 단위는 SizeUnit(이진 GiB)을 재사용하지 않고 DiskCapacityUnit(십진 GB · TB)을 신설한다 — 같은 이름의 다른 것을 한 enum 에 두면 표시가 어긋난다. 480GB SSD 가 lsblk 에서 447G 로 보이는 허용 오차는 매칭(E)의 문제다.

D3 — 카드 참조. Long raidCardId 소프트참조 · 지정만 받는다. 지금 RaidCardSelectionRequest(mode, id) 를 도입하면 계약이 AUTO 를 광고하면서 서버가 400 으로 거절하는 동작하지 않는 계약이 된다. 나중에 AUTO 를 열 때 raidCardMode 를 null-coalesce(기본 SPECIFIED)로 덧붙이면 저장 payload 마이그레이션이 없다. 이름은 저장하지 않고 렌더 시 references.raidCards 로 해석하되, 참조 검사가 없는 자원이라 #id 폴백만으로는 부족해 U3-5-d 의 어법대로 “(사라진 카드 #id)” 로 명시한다.

D4 — 요구 방향. “RAID 규칙이 있으면 카드가 있어야 한다” 한 방향만 강제한다. 카드만 고른 상태를 허용하는 이유는 정의서가 “이 카드를 전제한다” 고 말하는 것 자체는 해롭지 않고, iff 로 묶으면 카드-먼저 폼에서 규칙을 적기 전부터 위반 상태가 되어 제출 시점에 마찰이 생기기 때문이다.

D5 · D6 — 규칙과 참조 검사의 자리. 값 규칙은 static DiskGroupRules 로 LinuxPartitionRules 옆에 두고 카드 엔티티를 인자로 받아 의존 0 을 지킨다. 참조 검사는 ISO 가 쓰는 형태 그대로 — 없으면 404, 비활성이면 409, deprecated 면 저장을 허용하고 상세에 경고를 싣는다.

D7 — 폼 UX 는 카드 먼저. 순서는 [카드 select] → [묶음 표] 다. <option> 의 hover tooltip 은 브라우저마다 달라 사유는 option 의 title 과 select 아래 n-hint 줄에 함께 보인다. 반대 순서를 택하지 않은 이유는 규칙이 전제하는 것이 카드가 만들 수 있는 레벨이라 물리적 인과와 순서가 뒤집히고, 나중에 카드를 고를 때 이미 적힌 규칙과의 충돌 처리 지점이 늘어나기 때문이다.

D8 — 할당 시점 대조는 이번에 하지 않는다. 토론 E28 은 “보드와 같은 규칙에 축을 더하되 표식만” 을 예고했으나 R-13 · E33 이후 사정이 갈렸다. 모델 대조는 Subsystem ID 가 없어 불가능하고, 존재 대조는 kindOf 가 CRA3338 을 ETC 로 분류해 주력 카드를 쓰는 서버를 오차단하거나 상시 표식이 된다 — 둘 다 잘못된 신호다. lspci -nn 과 파서 보강(E 계열) 뒤 RequiredRaidCard 축과 AssignmentBlockKind 상수를 더하며, 그때 기존 골격을 그대로 쓸 수 있음은 실측으로 확인했다. Open Question 1.

D9 · D10 · D11 · D12. 옵션 조회는 setting 에서 management.raidcard 로 향하는 단방향이고(boards 선례) 차단 문구는 서버가 채워 보낸다. 상세와 두 피커는 fragment 를 공유하므로 피커 쪽 코드가 0 이다. 스키마는 없고 구 형식 저장본은 null-coalesce 로 그대로 읽힌다. RAID 없음 규칙의 count 는 RAID 규칙과 같은 뜻이다 — 묶음 하나에 들어가는 디스크 수(매칭 단위)이며, E19 처럼 조건에 맞는 묶음을 만들 수 있는 만큼 만든다. 레벨이 없다는 것은 그 묶음을 RAID 로 묶지 않는다는 뜻이고, LVM 이 범위 밖(D9)이라 묶음 안 디스크는 각각 하나의 볼륨이 된다(E32). 예: RAID 없음 · HDD · SATA · 4TB · 2개 + 4TB HDD 2장 → 묶음 1 · 볼륨 2. 3장이면 묶음 1(2장) + 1장은 규칙 밖(E18 — 오류가 아니다). RAID 없음 · NVMe · 1개 + NVMe 2장 → 묶음 2 · 볼륨 2. 이 해석은 U4-1-2 볼륨 도출의 입력이 된다. Open Question 2.
