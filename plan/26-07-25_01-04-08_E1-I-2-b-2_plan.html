§0. 재구성 동기 (단일 화면 → 3화면)

직전 plan(26-07-24_23-04-54_E1-I-2-b-2_plan.html)은 진단 자산을 한 화면에 다 담았다. 무결성 현황표, 상단 보존 개수 인라인 폼, 슬롯 행마다 접히는 버전 이력과 롤백 버튼, 봉인·재검증 버튼이 모두 대시보드 하나에 얹혀 있었다. 그 설계로 서비스 계층(활성화·롤백·버전 저장소·보존 설정)은 이미 구현·검증까지 끝났다.

사용자 지시로 화면 구조만 다시 나눈다. 서비스·엔티티·DDL 은 손대지 않는다. 재구성의 두 축은 아래와 같다.

  1. 대시보드는 현황만(status-only) — 한눈에 무엇이 어떤 상태인지 보는 화면이다. 상태를 바꾸는 액션(교체·롤백·봉인·보존 개수 수정)은 대시보드에서 뺀다. 자원을 바꾸는 일은 그 자원의 상세 화면에서 한다.
  2. 보존 개수 수정에 한 단계를 더한다 — 인라인 폼을 없애고 별도 설정 화면에서 고친다. 휴지통의 TrashSettings 설정 페이지 구조를 그대로 미러한다. 자주 바뀌지 않는 전역 튜너블을 대시보드 상단에서 실수로 건드리는 일을 줄인다.
본질 — 이 슬라이스는 단일 화면에 조회와 변경을 섞음 을 현황(대시보드) · 자원 액션(상세) · 전역 튜너블(설정) 세 관심사로 분리 하는 재배치다. 새 도메인 능력은 없다. 핵심 산출물은 사용자가 이 구조를 직접 눌러 보고 승인 판단 하도록 만드는 §2 직후의 3화면 라이브 미리보기다.
§1. 현재 상태 (진단)

서비스 계층과 단일 화면은 이미 동작한다. 재구성은 그 위에 뷰와 컨트롤러 모델·redirect 를 다시 배선하는 일이다.

구성 요소상태재구성에서
DiagnosticAssetActivationService.replace / rollback (활성화 코어)구현 완료무변경 — 재사용만
DiagnosticAssetIntegrityService.loadDashboard / seal / requireServingRoot구현 완료무변경 — 상세·설정이 loadDashboard 재사용
DiagnosticAssetVersionService.listReplaceableVersions구현 완료무변경 — 상세가 슬롯별 목록만 뽑아 씀
AssetHistorySettingsService + asset_history_settings 테이블구현 완료무변경 — 설정 화면이 소비
DiagnosticAssetController (6 엔드포인트)단일 화면 기준수정 — 모델 축소 · GET 2개 신설 · redirect 3개 변경

핵심 진단 — 능력은 다 갖춰졌고 배치만 어긋나 있다. 대시보드 하나에 (a) 현황 조회, (b) 슬롯별 교체·롤백, (c) 전역 봉인, (d) 전역 보존 개수 수정이 뒤섞여 있다. b·c·d 를 성격에 맞는 화면으로 옮기면 대시보드가 "현황만" 이 되고, 자원 액션은 그 자원 문맥에서, 전역 튜너블은 설정 문맥에서 이뤄진다. 서버 판정(FIFO 정리 · 롤백 승격·제거 · 서빙 게이트)은 그대로다.

확정 요구 규칙

  1. 대시보드에 mutation 버튼 0 — 교체 · 롤백 · 봉인 · 보존 수정 어느 것도 대시보드에 두지 않는다. 남는 상호작용은 재검증(비변경 새로고침)과 링크(행→상세, "운영 설정 →")뿐이다.
  2. 상세는 슬롯 단위 액션의 집 — 교체 가능한 4슬롯(VMLINUZ · INITRAMFS · MODLOOP · AGENT)은 교체 폼 · 버전 이력 · 행별 롤백을 상세에서 제공한다. 비교체 2슬롯(APKOVL · REPO)의 상세는 읽기전용이며 "빌드 스크립트로 교체" 안내만 둔다.
  3. 봉인(seal-all)은 설정 화면으로 — 6슬롯 마커를 일괄 기록하는 전역 mutation 이라 status-only 대시보드에서 빼고, per-slot 개념이 없어 상세로도 못 간다. 비교체 2슬롯은 교체 경로가 없어 seal-all 이 유일한 기준선 확립 수단이므로 설정 화면이 자연스러운 집이다.
  4. 보존 개수 수정은 별도 설정 화면 + 한 단계 추가 — 인라인 폼을 없애고 GET /settings 폼에서 고쳐 POST /settings 로 저장한다(TrashSettings 설정 페이지 미러). retentionCount 는 @Min(1) @Max(20).
  5. redirect 규약 — 교체 · 롤백 성공은 redirect:/{slot}(상세 복귀), 봉인 · 보존 저장 성공은 redirect:/settings(self-PRG), 재검증은 redirect:/(대시보드 잔류).
  6. 서빙 비활성 UI 1차 차단 — 서빙이 꺼져 있으면 상세의 교체 · 롤백 버튼과 설정의 봉인 버튼을 disabled + tooltip 으로 막는다. 이 조건은 서버 가드 requireServingRoot()(409)와 단일 SSOT(servingActive 플래그)로 같은 판정을 공유한다.
  7. 인라인 style 청산 + native confirm 미사용 — 현 dashboard.html 의 인라인 style 약 28곳을 재사용 CSS 클래스로 바꾼다. 롤백은 현재 활성본을 archive 하므로 가역이라 native confirm() 대신 버튼 title 경고로 안내한다.
비 목표 :
  • 서비스 계층 변경 — 활성화 · 롤백 · 버전 저장소 · 보존 설정은 이미 결정 · 구현됐다. 이번엔 손대지 않는다.
  • 상세용 loadSlot() 최적화 — 상세는 loadDashboard() 를 재사용한다(Detail-A). 슬롯 하나만 다시 해시하는 최적화는 지연이 체감될 때 별도 리팩토링으로 이연한다.
  • dhcpd · tftp 등 PXE 인프라 자산 화면 — E1-I-3.
  • 활성화 코어의 SPI 일반화 — dhcpd/tftp 구현자가 실재하는 E1-I-3 이 끝난 뒤 단계 신설 없는 리팩토링(R* 계열)으로 미룬다.
🎬 미리보기 — 3화면을 실제로 오가며 확인

아래 위젯 하나에 대시보드 · 상세 · 설정 세 화면이 들어 있고, 한 번에 한 화면만 보입니다. 위젯 안에서 직접 이동하세요. 대시보드의 자산 행을 클릭하면 그 자산 상세로, 운영 설정 → 로 설정 화면으로 갑니다. 상세에서 교체 · 되돌리기, 설정에서 보존 개수 · 전 슬롯 봉인을 눌러 결과를 보세요. 공유 상태 하나(서빙 · 보존 개수 · 슬롯별 활성본/이력/무결성)를 세 화면이 함께 읽습니다. 판정 로직(FIFO 정리 · 롤백 승격·제거 · 서빙 게이트)은 서버 구현과 1:1 입니다.

전역 서빙 : 현재 화면 : 대시보드

표기 주의 : 미리보기의 버전 #N 은 어느 바이트인지 눈으로 따라가기 쉽게 붙인 미리보기 전용 라벨이며, 실제 화면에는 세대 번호가 없습니다. 실제 상세는 버전을 아카이브 시각 · 크기 · 해시로 표시하고(AssetVersionView), 식별 키는 재사용되지 않는 자동 증가 asset_version.id 입니다. 미리보기의 번호도 같은 성질을 따르도록 단조 증가시켜 롤백 뒤에도 번호를 재사용하지 않습니다.

위젯 캡션 : 대시보드에는 상태를 바꾸는 버튼이 없습니다. 교체 · 롤백은 각 자산 상세에서, 봉인 · 보존 개수는 설정에서 합니다. 서빙을 비활성으로 바꾸면 상세의 교체 · 되돌리기와 설정의 봉인 버튼이 disabled + tooltip 으로 막히는데(UI 1차 차단), 이 조건은 서버 requireServingRoot() 가드(409)와 같은 SSOT 입니다.

드리프트 0 — 미리보기 판정 = 서버 도메인 규칙. FIFO 정리 = versions.size > N → id 오름차순 (size−N)개 삭제 = 서버 AssetHistoryService.prune(). 롤백 불변식 = archive(현재) → 활성=X → remove(X) = 서버 DiagnosticAssetActivationService.rollback()(openVersion 이 temp 로 바이트를 먼저 실체화해 순서 안전). UI 버튼 disable = !servingActive = 서버 requireServingRoot() throw(409).

§4. 도메인 모델 (SSOT)

§8. 예상 부산물 / 주의 / 결정 사항

핵심 결정 (채택 · 비채택 대안 · 탈락 사유)

D1 · 재검증(recheck)은 대시보드 잔류
채택 재검증은 서비스를 호출하지 않고(GET 재렌더가 곧 재검증) 상태를 바꾸지 않는 현황 새로고침이라 status-only 대시보드에 속한다. 엔드포인트 · redirect(redirect:/) 무변경.
탈락 설정으로 이동 — 재검증은 mutation 이 아니라 조회 갱신이므로 전역 튜너블 화면에 둘 이유가 없다. 현황을 보는 그 자리에서 다시 확인하는 게 자연스럽다.

D2 · 봉인(seal-all)은 설정 페이지
채택 6슬롯 마커를 일괄 기록하는 전역 mutation 이라 status-only 대시보드에서 제거한다. per-slot 개념이 없어 상세로도 못 간다. 특히 비교체 2슬롯(apkovl · repo)은 교체 경로가 아예 없어 seal-all 이 유일한 기준선 확립 수단이므로 설정 페이지가 자연스러운 집이다. 봉인 후 redirect:/settings(self-PRG)로 카드의 okCount/total 이 새 값으로 피드백된다.
탈락 ⓐ 대시보드 잔류 — status-only 원칙 위배.
탈락 ⓑ per-slot seal(각 상세에서 봉인) — 초기 6슬롯 기준선을 세우려면 상세를 6번 순회해야 하는 회귀 + 신규 엔드포인트 churn + 읽기전용 슬롯(apkovl · repo)의 상세에 mutation 버튼을 놓는 의미 충돌이 생긴다.

D3 · replace / rollback 성공 redirect = /{slot}(상세 복귀)
채택 교체 · 롤백을 상세에서 개시하므로, 직후 새 버전이 그 상세 이력에 뜨는 것이 자연스럽다(GuestServer 액션의 redirect:/{id} 선례와 동형). flash 메시지로 결과 안내.
탈락 대시보드 복귀(현 동작) — 상세에서 시작한 액션이 현황 화면으로 튕겨 방금 만든 버전을 다시 상세로 들어가 확인해야 한다.

D4 · 상세 데이터 = loadDashboard() 재사용 (Detail-A)
채택 상세는 loadDashboard() 결과에서 key 로 슬롯 1행을 필터한다. 신규 서비스 메서드 0, 신규 DTO 0. servingActive 게이트 플래그가 loadDashboard 에만 있어 loadSlot 을 따로 추출하면 오히려 서비스 메서드가 3개(loadSlot · servingRoot · versions)로 갈라지는 churn 이 생긴다.
트레이드오프 상세 진입마다 6슬롯을 재해시한다 — 그러나 대시보드가 이미 그렇게 하므로 신규 회귀가 아니다. 단일 슬롯만 해시하는 loadSlot 추출은 지연이 체감될 때 별도 리팩토링으로 이연(§비목표).

D5 · 부수효과 (전부 준수)
