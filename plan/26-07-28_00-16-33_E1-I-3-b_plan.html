§1. 현재 상태 (진단)

E1-I-3-a(선행, 완료·커밋)는 격리돼 있던 진단 리눅스 자산 화면을 여러 자산 종류를 한 대시보드로 집계하는 통합 화면(/system/asset)으로 승격했고, 자산 종류 하나가 자기 슬롯·판정·봉인을 스스로 제공하는 확장점 SystemAssetArea(Service Provider Interface — 도메인이 구현해 끼우는 확장점)를 열었다. 지금 진단 리눅스와 TFTP 두 영역이 등록돼 있고, 둘 다 파일 봉인(해시 마커) 판정 모델(SealedFileCondition 사다리)을 쓴다.

a 가 갖춰 놓은 것 (b 의 진입 전제)

자산상태설명
SystemAssetArea있음영역 하나가 슬롯·판정·봉인을 스스로 제공하는 확장점. supportsSeal()/seal() 이 default 로 대칭화됨
SystemAssetDashboardService있음List<SystemAssetArea> 를 EnumMap 으로 라우팅. toGroup(area) 는 영역 종류를 묻지 않고 균일 순회(조건분기 없음)
AssetCondition있음슬롯 1개의 판정 인터페이스 — label()/badgeClass()/healthy(). okCount 는 healthy()==true 슬롯 수
등록 영역2개SystemAssetAreaKey = {DIAGNOSTIC, TFTP}. 둘 다 파일 봉인 판정

b 의 도전 — dhcpd 는 파일 봉인으로 판정할 수 없는 이질 영역

PXE 부팅 인프라의 핵심인 dhcpd(DHCP 서버)의 건강은 해시 드리프트가 아니라 서로 다른 축으로 판정된다:

  1. 구성 조각 파일의 존재와 문법 — managed.conf 가 있는가 + dhcpd -t 가 통과하는가
  2. systemd 서비스의 라이브니스 — systemctl is-active dhcpd 가 active 인가
  3. 임대 현황 — dhcpd.leases 의 활성 임대 건수
핵심 진단 : 이 이질 영역을 같은 통합 대시보드에 담되 집계 코드(SystemAssetDashboardService.toGroup)에 영역별 분기를 만들지 않는 것이 b 의 설계 도전이다. a 가 연 확장점이 실제로 이질 영역을 흡수하는지가 확장점 계약의 스트레스 테스트가 된다. 파일 유효성(슬롯)과 데몬 라이브니스(관측)는 독립축이라 "파일은 유효한데 데몬은 다운" 같은 상태를 표현할 수 있어야 한다.

§4. 도메인 모델 (SSOT)

모든 도메인 의미값을 Value Object / Enum 으로 타입화한다(Primitive Obsession 금지). 원시 String mac / int exitCode 를 SPI·대시보드로 전파하지 않는다 — 종료양태·서비스 상태·임대 binding 은 각각 enum 으로, IP·MAC 은 기존 VO 로 잠근다.

① 조각 슬롯 판정 — ConfigFileCondition (implements AssetCondition)

NOT_CONFIGURED ──▶ ABSENT ──▶ SYNTAX_ERROR ──▶ UNKNOWN ──▶ SYNTAX_OK (서빙 비활성) (조각 없음) (구성 문법 오류) (문법 미검사) (구성 유효 · 유일한 healthy)
enum ConfigFileCondition implements AssetCondition {
    NOT_CONFIGURED("서빙 비활성",   "n-badge-gray"),
    ABSENT       ("조각 파일 없음", "n-badge-gray"),
    SYNTAX_ERROR ("구성 문법 오류", "n-badge-red"),   // ⚠ 아래 시맨틱 주의
    UNKNOWN      ("문법 미검사",    "n-badge-orange"),
    SYNTAX_OK    ("구성 유효",      "n-badge-green");  // healthy() == (this == SYNTAX_OK)

    // 서버 판정 (D4·D6) — availability 게이팅은 호출자(DhcpdAssetArea.inspect)가 NOT_CONFIGURED 로 흡수
    static ConfigFileCondition of(boolean fragmentPresent, CommandResult syntaxCheck) {
        if (!fragmentPresent) return ABSENT;
        return switch (syntaxCheck.outcome()) {
            case NOT_FOUND, TIMED_OUT -> UNKNOWN;                       // 종료양태 우선
            case COMPLETED -> syntaxCheck.exitedZero() ? SYNTAX_OK : SYNTAX_ERROR;
        };
    }
}
중요 시맨틱 (D6 잔여) : dhcpd -t 는 조각이 아니라 dhcpd.conf 전체를 검사한다 — 조각과 무관한 기존 오류도 조각 슬롯을 문법 오류로 만든다. 그래서 라벨을 "조각 문법"이 아니라 "구성 문법 오류"(전체 구성)로 쓴다.

② 서비스 상태 — ServiceState (plain enum, AssetCondition 미구현)

enum ServiceState {                 // AssetCondition 을 구현하지 않는다 (슬롯 아님 → healthy() 불요, ISP)
    ACTIVE, INACTIVE, FAILED, UNKNOWN;

    static ServiceState from(CommandResult r) {         // 서버 판정 (D4·D8)
        return switch (r.outcome()) {
            case NOT_FOUND, TIMED_OUT -> UNKNOWN;
            case COMPLETED -> switch (r.stdout().strip()) {
                case "active"   -> ACTIVE;
                case "inactive" -> INACTIVE;
                case "failed"   -> FAILED;
                default         -> UNKNOWN;
            };
        };
    }
    ObservationSeverity severity() { ... }  // ACTIVE→OK / INACTIVE·FAILED→WARN·CRITICAL / UNKNOWN→INFO
}

데모·§4 표는 구체값으로 ACTIVE→OK · INACTIVE→WARN · FAILED→CRITICAL · UNKNOWN→INFO 를 쓴다(failed 가 inactive 보다 위중). INACTIVE/FAILED 의 WARN/CRITICAL 정확한 배분은 CP2 확정 여지로 표기(D8·Q5).

⑤ 특권 명령 경계 — 포트 + enum + 경화된 CommandResult

interface SystemCommandRunner { CommandResult run(AllowedCommand cmd, List<String> callerArgs); }

enum CommandOutcome { COMPLETED, TIMED_OUT, NOT_FOUND }   // 3-상태 종료양태를 상호배타 타입화
record CommandResult(CommandOutcome outcome, int exitCode, String stdout, String stderr) {
    boolean exitedZero() { return outcome == COMPLETED && exitCode == 0; }   // exitCode 는 COMPLETED 에서만 의미
}

enum AllowedCommand {                                      // 지금은 2상수만 (restart/restorecon 은 c 착수 시 추가)
    DHCPD_SYNTAX_CHECK ("/usr/sbin/dhcpd", List.of("-t","-cf"), ArgShape.ONE_PATH, Duration.ofSeconds(3), "..."),
    DHCPD_SERVICE_STATUS("/usr/bin/systemctl", List.of("is-active","dhcpd"), ArgShape.NONE, Duration.ofSeconds(3), "...");
    List<String> assembleArgv(List<String> callerArgs);   // 절대경로·고정플래그·인자형(ArgShape) 조립
    Duration timeout();                                    // 비-null 3초 강제
    String sudoersLine();                                  // sudoers 근거를 enum 이 SSOT 로 보유
}
enum ArgShape { NONE, ONE_PATH }                           // 경로 루트 위반만 invariant if-throw (IllegalArgumentException)
운영 빈 ProcessSystemCommandRunner 주의 (D3 잔여) : IsoPreparationService(선례: waitFor() 후 readAllBytes())의 데드락 패턴을 답습하지 않도록 stdout/stderr redirect 또는 배수(drain)를 설계에 명시한다. waitFor(timeout) 초과 시 destroyForcibly() + CommandResult 를 TIMED_OUT 으로(예외 아님).

⑥ 영역 확장점 — DhcpdAssetArea implements SystemAssetArea

areaKey()      -> SystemAssetAreaKey.DHCPD
displayName()  -> "dhcpd (DHCP 부트 서버)"
availability() -> 프로퍼티 존재 ? CONFIGURED : NOT_CONFIGURED
slots()        -> [ 조각 슬롯 1개 (managed.conf) ]
inspect(slot)  -> 미구성이면 ConfigFileCondition.NOT_CONFIGURED,  else ConfigFileCondition.of(present, syntaxCheck)
supportsSeal() -> false   // ⚠ 실코드 default 는 true → 반드시 override (안 하면 default seal() throw 에 걸림)

                   ? [ {서비스 상태 chip}, {"활성 임대","N건",INFO} ]   // D5 게이팅
                   : List.of()                                        // 미구성이면 빈 목록 (chip 없음, 특권 명령 미노출)

inspect 3분할(DhcpdConfigInspector = dhcpd -t→ConfigFileCondition / SystemServiceInspector = is-active→ServiceState / DhcpLeaseParser = String→LeaseSnapshot)은 각자 distinct 소비처를 가져 얇은-어댑터 선례(SealedFileInspector)와 정합한다. 단일 오케스트레이터로 묶을지는 CP2 확정.

§8. 설계 결정 D1~D11 / 예상 부산물 / 결정 사항

각 결정을 채택안 / 왜 / 비채택안+탈락사유 / 잔여·잠정 4항목으로 편다.

D1 · 영역 관측 surface 단일화 — context() 채택, observation() 폐기

채택SystemAssetArea 에 default List<AssetContextItem> context() { return List.of(); } 하나만 새 관측 surface 로 추가(우산 plan 이 선공표한 방향 계승). 진단·TFTP 는 default 빈 목록 → 무변경.

왜이 하나로 두면 집계 서비스가 area.context() 를 균일 map 할 뿐이라 영역이 늘어도 toGroup 에 if/switch 가 자라지 않는다(조건분기 legacy 확장 금지). 관측치를 슬롯과 물리 분리해 okCount/totalCount 오염을 원천 차단.

비채택(a) dhcpd 고유형 AreaObservation(ServiceState, int leaseCount) 를 공용 SPI 반환형으로 → 4번째 영역이 다른 관측(worker 수·TLS 만료)을 내면 필드 불일치 + 도메인 무관 SPI 에 dhcpd 개념을 구움(일반성 상실). (b) 가상 슬롯으로 관측 표현 → 파일 계약(present/sizeBytes/modifiedAt)에 sentinel 을 채워 거짓 데이터 + okCount 오염 + 뷰 분기 부활. (c) 공용 헤더 DTO 에 관측별 타입 필드 직접 추가 → 관측 종류마다 DTO 필드·분기 성장.

잔여SystemAssetAreaGroupResponse 에 List<AssetContextItemResponse> context 한 필드만 추가. 빈 목록이면 뷰가 chip 을 안 그리게 degrade.

D2 · 관측 배지 타입화 — ObservationSeverity 단일 배지 출처

채택AssetContextItem(String label, String value, ObservationSeverity severity) + ObservationSeverity{OK,INFO,WARN,CRITICAL}(각 badgeClass() 보유). 응답엔 AssetContextItemResponse(label,value,badgeClass) 문자열만 실어 뷰 경계 유지.

왜헤더 chip 배지 어휘(n-badge-*)의 SSOT 를 한 곳으로. ServiceState 가 자체 배지를 들면 출처가 둘로 갈린다. severity 를 raw badge String 으로 SPI 에 넘기면 Primitive Obsession.

비채택ServiceState/ServiceCondition 이 AssetCondition 을 구현 → 서비스 상태는 슬롯이 없어 healthy()(okCount 집계용)가 소비처 없는 speculative 구현(ISP — Interface Segregation Principle, 관측은 healthy 불요). AssetCondition 이 non-sealed 라 강제되지 않으므로 구현 안 함.

잔여 (CP2)ObservationSeverity.badgeClass() 와 AssetCondition.badgeClass() 가 같은 n-badge-* 4문자열을 병렬 보유. 로직 중복은 아니나 공용 상수로 뽑을지 vs 과추상인지 CP2 판단(Q5).

D3 · 특권 명령 경계 — 포트 + enum + CommandOutcome 경화

채택SystemCommandRunner.run(AllowedCommand, List<String>): CommandResult 포트 + CommandOutcome{COMPLETED,TIMED_OUT,NOT_FOUND} + CommandResult(outcome,exitCode,stdout,stderr) + exitedZero() + AllowedCommand.assembleArgv()/ArgShape + 운영 빈 ProcessSystemCommandRunner(1개) + test StubSystemCommandRunner. 절대경로·고정플래그·타임아웃(비-null 3초)·sudoersLine() 을 enum 이 SSOT 보유. 지금 DHCPD_SYNTAX_CHECK·DHCPD_SERVICE_STATUS 2상수만(restart/restorecon 은 c 착수 시 같은 enum 에 추가 = 갈라지는 시점 분리).

왜우산 원안 CommandResult(int exitCode, …, boolean timedOut) 은 두 결함 — ① 명령 부재를 표현할 필드가 없어 소비처가 종료코드 매직 상수로 오분류(완료② "0/비0/타임아웃/부재 4분기"를 타입이 보장 못 함), ② int exitCode + boolean timedOut 이 하나의 3-상태 종료양태를 직교 원시 2개로 쪼개 무효 조합(timedOut=true 이면서 exit=0)을 표현 가능하게 함(Primitive Obsession). CommandOutcome enum 하나로 상호배타 타입화, exitCode 는 COMPLETED 에서만 의미로 가드(dhcpd -t 의 운영체제 반환값이라 int 유지가 정직 — 더 추상하면 의미 손실).

비채택우산 원안 그대로(위 두 결함) / 명령별 전용 포트로 AllowedCommand 폐기 → "특권 경계 1개"를 깨고 명령마다 포트 메서드 증식, sudoers 자동생성 근거 분산.

잔여ProcessSystemCommandRunner 는 IsoPreparationService 데드락 패턴을 답습하지 않도록 stdout/stderr redirect 또는 배수(drain)를 설계에 명시. waitFor(timeout) 초과 시 destroyForcibly() + TIMED_OUT(예외 아님).

D4 · 종료양태 소비 — 모든 판정 of/from 은 CommandResult 경유

채택ConfigFileCondition.of(boolean fragmentPresent, CommandResult syntaxCheck), ServiceState.from(CommandResult) — 둘 다 outcome 우선 분기(NOT_FOUND / TIMED_OUT → UNKNOWN), COMPLETED 에서만 exitedZero() 로 exitCode 접근.

왜raw exit 만 받으면 systemctl 이 부재·타임아웃(exitCode 자리값)일 때 그 값을 실제 종료코드로 오독. exitedZero() 강제 경유로 raw exitCode 가 SPI·대시보드로 새지 않게.

비채택raw int exit 를 판정 메서드에 직접 전달.

D5 · 미구성 게이팅 — context() 는 CONFIGURED 일 때만 chip 조립

채택DhcpdAssetArea.context() 는 availability()==CONFIGURED(프로퍼티 존재)일 때만 서비스·임대 chip 을 만들고, NOT_CONFIGURED 면 빈 목록 반환. 조각 슬롯 inspect() 도 미구성이면 ConfigFileCondition.NOT_CONFIGURED 로 흡수.

왜무조건 관측하면 미구성이어도 systemctl(특권 명령)을 매 GET spawn 하고 leases 를 읽는다 — 완료조건 "미구성이 예외 아닌 미구성 상태로 표시"의 취지에 어긋나고, 앱이 관리 안 하는 영역에 특권 명령 불필요 노출. 실코드 선례(DiagnosticSystemAssetArea·TftpAssetArea 는 프로퍼티 부재면 즉시 흡수, 프로브 안 함)와 동형.

D6 · 판정축 직교 분리 — 조각=슬롯, 서비스·임대=헤더 관측

채택조각 파일(managed.conf)은 슬롯 1개(ConfigFileCondition = 존재 + dhcpd -t 문법, okCount 참여). 서비스 상태·활성 임대 건수는 슬롯이 아닌 헤더 관측(context(), okCount 불참).

왜파일 유효성과 데몬 라이브니스는 독립축("파일 유효 + 데몬 다운"을 표현해야). 완료조건 ④(헤더 표시) 위치와 일치. AssetSlotStatus(present/sizeBytes/modifiedAt)는 파일 계약이라 서비스·임대에 sentinel 을 채우면 거짓 데이터 + okCount 오염.

비채택가상 슬롯 / 슬롯 0개 영역 / 헤더 DTO 관측별 필드(D1 비채택과 동일 사유).

잔여 (중요 시맨틱)dhcpd -t 는 조각이 아닌 dhcpd.conf 전체를 검사 — 조각과 무관한 기존 오류도 조각 슬롯을 문법 오류로 만든다. 라벨을 "구성 문법 오류"(조각 문법이 아니라 전체 구성)로 쓰고 이 시맨틱을 plan 에 명시(§4 참조).

D7 · dhcpd.leases 파서 — 순수 DhcpLeaseParser 분리

채택DhcpLeaseParser.parse(String raw): LeaseSnapshot — 무상태·Spring 의존 0. lease <ip> { … } 블록 단위 try/catch 로 VO invariant throw·손상 블록·미지 binding state·빈 파일을 전부 흡수(절대 throw 안 함). 파일 부재는 호출자(Files.readString 실패 → 빈 snapshot)가 흡수. LeaseEntry(IpAddressVO ip, MacAddressVO mac[nullable], Instant starts, Instant ends, LeaseBindingState state), LeaseSnapshot.activeCount(Instant now).

왜완료조건 ①(binding state 4종·손상 블록·빈 파일 픽스처 통과)이 순수 String→LeaseSnapshot 소비처를 요구 — Spring 부팅·IO 목킹 없이 픽스처를 직접 먹임. 기존 IpAddressVO(IPv4 전용)·MacAddressVO 재사용, LeaseBindingState·LeaseSnapshot 신규 VO 로 타입화(원시 String/int 전파 0). activeCount(now) 가 도메인 메서드라 헤더 chip 과 향후 상세가 단일 SSOT 공유.

비채택파서를 어댑터 private 메서드로 → 픽스처 문자열 직접 테스트 불가(완료① 정면 위반), IO+파싱+명령러너+조립 혼재(검증/변환/IO/조립 분리 위반), SealedFileInspector 얇은-어댑터 선례 이탈.

잠정 (Rocky 9 실측 전)파서 문법 구조는 dhcpd 버전 무관 안정 → 타입·사다리·구조는 지금 확정. 실측이 채우는 것은 픽스처 리터럴뿐. 손으로 쓴 픽스처를 "잠정" 표기 후 b CP4 서명 전 실측 캡처로 교체.

D8 · 조건 명칭 통일

채택조각 슬롯 = ConfigFileCondition(implements AssetCondition, NOT_CONFIGURED → ABSENT → SYNTAX_ERROR → UNKNOWN → SYNTAX_OK, SYNTAX_OK 만 healthy). 서비스 = ServiceState(plain enum ACTIVE/INACTIVE/FAILED/UNKNOWN, AssetCondition 미구현, ObservationSeverity 로 매핑: ACTIVE→OK / INACTIVE·FAILED→CRITICAL·WARN / UNKNOWN→INFO). 임대 = LeaseBindingState.

왜-Condition 접미사는 이 코드베이스에서 AssetCondition 구현을 뜻한다(SealedFileCondition 선례). AssetCondition 을 구현 안 하는 서비스 상태는 ServiceState 가 정직한 이름.

잔여INACTIVE/FAILED 의 CRITICAL/WARN 정확한 배분은 CP2 확정 여지(§4·Q5). 데모·§4 는 INACTIVE→WARN · FAILED→CRITICAL 를 구체값으로 쓴다.

D9 · 패키지·페이지 구조

채택dhcpd 고유 자산은 execution.pxeinfra.*(우산 SSOT). 공용 관측 표시 타입만 execution.asset.spi(AssetContextItem·ObservationSeverity)·execution.asset.dto.response(AssetContextItemResponse)에 둔다(pxeinfra 가 asset.spi 를 의존하는 방향). SystemAssetAreaKey 에 상수 DHCPD 1개 추가(TFTP/DIAGNOSTIC 무접두 관례).

D10 · 정직 표기 — "무변경" 범위 한정

채택진단·TFTP production 어댑터와 진단 무결성 테스트는 무변경(default 흡수). 그러나 다음은 가산적 기계 갱신이며 plan 에 정직 표기:

가산 갱신(a) SystemAssetAreaGroupResponse 필드 추가 → SystemAssetControllerTest 의 record 생성 인자(7→8) 갱신. (b) 등록 영역 2→3 → "영역 개수" 단언 + SystemAssetAreaKey.DHCPD 추가. (c) supportsSeal() 실코드 default=true → DhcpdAssetArea 가 false 명시 override(안 하면 default seal() throw 에 걸림). (d) SystemAssetAreaDefaultsTest 에 context() 기본 빈 목록 케이스 추가. (e) "구성 문법 오류" 라벨 시맨틱.

D11 · DB·엔티티 무변경 확인

채택b 는 엔티티·리포지토리·스키마 무변경(우산이 PxeNetworkConfig·SubnetCidr·repository 를 c 로 명시). 슬라이스 6·7·9 단계 N/A.
