§0. 이 단계가 어떻게 생겼는가

U3-5 는 원래 한 덩어리였다. 계획을 쓰다가 세 가지 성격이 다른 일이 섞여 있음이 드러나 셋으로 나눴다 — 할당 가능성 판정(a) · 고르는 화면(b) · 여러 대에 한 번에(c). c 를 마지막에 둔 이유는 c 가 b 의 화면을 쓰기 때문이다. 순서를 뒤집으면 <select> 로 한 번 만들고 곧 갈아끼우게 된다.

이제 a 와 b 가 끝났으므로 c 가 쓸 것이 다 있다. 판정은 새로 만들지 않는다 — U3-5-a 의 AssignmentBlockKind.evaluate 를 그대로 부른다. 그 클래스의 주석이 이미 이 단계를 내다보고 있었다:

"여기서 회수 여부와 하드웨어를 각각 검사하면 같은 순서가 화면 · 그룹 일괄 할당에도 복붙되고, 축이 늘 때 네 곳이 함께 자란다."
§1. 현재 상태 (실측)

지금 그룹에서 할 수 있는 것

GuestServerGroupController 는 그룹 생성 · 이름 변경 · 멤버 추가 · 멤버 제거 · 삭제를 갖는다. 세팅 정의서에 관한 것은 하나도 없다. 정의서를 붙이려면 멤버를 하나씩 열어 개별 할당해야 한다.

없어서 만들어야 하는 것

  • SettingAssignmentRepository 에 여러 서버의 활성 할당을 한 번에 조회하는 메서드가 없다(단건 findByGuestServer_IdAndSupersededAtIsNull 만 있다). 파생 질의 하나 추가.
  • GuestServerSummaryResponse 는 boardModelName 은 갖지만 boardModelId 는 없다. 하드웨어 판정은 id 로 대조하므로 멤버 요약만으로는 판정할 수 없고 GuestServerDetail 을 따로 읽어야 한다.

패키지 참조 방향 (중요)

group 과 assignment 는 서로를 전혀 참조하지 않는다. 실측했다 — 양방향 모두 import 0 건이다. 둘을 엮는 것은 provisioning.controller 뿐이다. 이 단계는 그 관계를 새로 만들 수 있는 자리이므로 의식적으로 만들지 않는다(DEC-F).

실측으로 드러난 결함 하나 (범위 밖)

flashMessage 를 쓰려다 S10 전역 폼 가로채기와 조합되면 메시지가 사라진다는 것을 브라우저로 확인했다. form-submit.js 의 sendAsync 가 fetch(..., redirect:'follow') 로 리다이렉트를 fetch 안에서 따라가며 flash 를 소비하고, 이어지는 onSuccess: () => window.location.reload() 는 빈 손으로 온다.

같은 페이지 · 같은 액션에서 data-native-submit 만 붙였더니 문구가 떴다 — 원인이 확정된다. 영향받는 화면은 system/asset/dashboard(액션 2), system/diagnostic-asset/detail(액션 2), system/asset/settings(2 중 1). 이 단계 범위 밖이므로 고치지 않고 HF* 후보로 기록하되, 이 단계의 결과 통지 설계는 이 실측 위에서 정한다(DEC-E).
§2. 요구사항 (확정) + 비목표
  • R1 — 그룹 상세에 [정의서 일괄 할당] 이 있고, 누르면 U3-5-b 와 같은 형태의 2 열 miller 모달이 열린다.
  • R2 — 정의서를 고르면 우측에 이 그룹에 어떻게 적용되는지가 먼저 보이고, 그 아래에 정의서 내용이 온다.
  • R3 — 미리보기는 멤버를 셋으로 나눈다 — 할당됨 · 이미 있음(건너뜀) · 막힘(사유).
  • R4 — 좌측 목록은 정의서마다 몇 대에 붙는지를 보여준다. 0 대인 정의서도 눌러서 왜 아무에게도 안 붙는지 볼 수 있되, [일괄 할당] 은 열리지 않는다.
  • R5 — 확정하면 붙는 멤버에만 할당하고, 결과를 사유와 함께 알린다.
비 목표 :
  • 일괄 재할당 — 이미 할당된 멤버의 스냅샷을 갈아엎지 않는다(DEC-C). 재할당은 개별 서버 화면(U3-5-b 모달)의 일이다.
  • 일괄 개시 — 프로비저닝 개시는 E 계열 소관이다.
  • 할당 가능성 판정 규칙 — U3-5-a 확정분을 그대로 호출한다.
  • flashMessage 소실 결함의 수정 — 자산 화면 계열이며 별도 HF*.
  • 그룹 자체의 CRUD · 멤버 관리 — U3-4 가 끝냈다.
🎬 미리보기 — 그룹에 붙여 보기

툴바로 정의서 3 종을 바꾸고, 멤버 행의 버튼 둘로 그 서버의 상태를 바꾼다 — 왼쪽 버튼은 이미 할당이 있는지(할당 있음 ↔ 할당 없음), 오른쪽 버튼은 회수 여부(회수 ↔ 복구)다. 정의서와 멤버 상태를 함께 흔들어야 분류가 왜 바뀌는지 체험된다.

정의서 :

판정 JS (서버와 1:1)

function demoOutcome(def, member) {
    if (member.assigned)      return {kind: 'ALREADY', reason: '이미 세팅 정의서가 할당되어 있습니다.'};
    if (member.decommissioned) return {kind: 'BLOCKED', reason: '회수된 서버에는 세팅 정의서를 할당할 수 없습니다.'};
    if (def.board === null || member.board === null) return {kind: 'ASSIGN', reason: null};
    return def.board === member.board
        ? {kind: 'ASSIGN', reason: null}
        : {kind: 'BLOCKED', reason: '이 정의서는 메인보드 ' + def.board + ' 전용입니다 — 이 서버는 ' + member.board + ' 입니다.'};
}

순서가 중요하다 — 이미 할당됨을 먼저 본다. 이미 있는 멤버는 하드웨어를 대조할 이유가 없다(어차피 건너뛴다). 서버도 같은 순서다(DEC-G).

체험시키고 싶은 것

정의서를 바꾸면 같은 그룹이 다르게 갈린다. os-only-auto(AUTO)는 회수 · 기존 할당만 걸러내고 하드웨어로는 아무도 막지 않는다. bios-ms03 으로 바꾸면 ASUS 보드 멤버가 추가로 빠진다. 멤버 상태를 흔들면 같은 정의서인데 분류가 바뀐다 — 막는 것이 정의서 하나의 성질이 아니라 정의서 × 서버의 조합임이 드러난다. srv-01 의 할당 있음 을 켜면 같은 정의서인데 그 멤버만 이미 있음으로 빠진다 — 막는 것이 하드웨어이고 건너뛰는 것이 기존 할당이라는 두 층이 갈린다.

객체가 어떻게 이어지는가

도식 A — 조회 경로 (모달을 열 때)

모달을 열 때 무엇이 무엇을 부르는지다. 리포지토리 조회는 각각 한 번씩만 일어난다 — 멤버가 늘어도 질의 수는 그대로다.

GuestServerGroupController.assignmentPicker(groupId) │ ├─▶ GuestServerGroupQueryService.findDetail(groupId) │ └── 멤버 id 목록 (그룹 상세 화면이 부르는 것과 같은 메서드 — 새로 만들지 않는다) │ ├─▶ SettingQueryService.findAssignable() ─── List<SettingSummaryResponse> │ └─▶ SettingQueryService.findDetailsOf(ids) ─── List<SettingDetailResponse> [U3-5-b 신설분 재사용] │ ├─▶ AssignmentQueryService.groupPreview(멤버 id 목록, 정의서 요약 목록) │ │ │ ├── GuestServerDetailRepository.findAllByServerIdInWithBoardModel(멤버 id) [1 회] │ ├── SettingAssignmentRepository.findByGuestServer_IdInAndSupersededAtIsNull(…) [1 회 · 신설] │ │ │ └── 정의서 × 멤버 조합마다 (질의 없음 — 위에서 읽은 것만 쓴다) │ ├── 이미 활성 할당이 있나 ──▶ MemberApplyOutcome.ALREADY_ASSIGNED │ └── AssignmentBlockKind.evaluate(AssignmentEligibility) [U3-5-a 재사용] │ ├── null ──▶ WILL_ASSIGN │ └── block ──▶ BLOCKED + block.reason() │ └── 사유 문구는 도메인이 만든다(서버 가드와 같은 문자열) │ └─▶ GroupPickerResponse.of(미리보기 목록, 상세 목록) ← 조립은 응답 record 가 한다(U3-5-b 선례) └── 화면: fragments/provisioning/group-definition-picker :: picker

판정은 이 단계가 만들지 않는다. 하드웨어 · 회수 축은 AssignmentBlockKind 를 그대로 부르고, 이 단계가 더하는 것은 그 앞에 오는 질문 하나(이미 활성 할당이 있나)뿐이다. 조립을 서비스가 아니라 응답 record 의 정적 팩터리가 맡는 것도 U3-5-b 와 같다 — 하는 일이 조회가 아니라 id 로 짝짓기라서 트랜잭션도 리포지토리도 필요 없다.

도식 B — 실행 경로 (orchestrator)

확정을 누른 뒤다. GroupAssignmentService 는 스스로 할당하지 않는다 — 멤버마다 기존 AssignmentCommandService.assign 을 부르고 결과를 모으는 지휘자다. 새 할당 로직이 없다는 것이 이 설계의 값이다.

GuestServerGroupController.assignBatch(groupId, definitionId) │ └─▶ GroupAssignmentService.assignToMembers(멤버 id 목록, definitionId) ◀── orchestrator (별도 빈) │ │ 이 메서드에는 @Transactional 이 없다 — 여기서 트랜잭션을 열면 │ 멤버 전체가 한 트랜잭션에 묶여 한 건 실패가 전부를 되돌린다 │ ├── 멤버 1 ─┐ ├── 멤버 2 ─┤ ├── 멤버 3 ─┤ 각각 아래를 독립적으로 탄다 ├── 멤버 N ─┘ │ ▼ ╌╌╌╌╌╌╌╌╌┼╌╌╌╌╌╌╌╌╌ Spring AOP 프록시 경계 │ ◀── 이 선을 지나야 @Transactional 이 열린다 │ ▼ AssignmentCommandService.assign(guestId, definitionId) @Transactional ├── assertAssignableTo(guest, definition) [U3-5-a 가드 — 재판정] └── assignmentRepository.save(deriveSnapshot(…)) │ ├── 성공 ──▶ assigned++ └── ConflictException ──▶ skipped++ · 사유는 예외가 실어 온 도메인 문구 │ └─▶ BatchAssignResult(assigned, skipped, 사유별 집계) │ ▼ Controller ──▶ addFlashAttribute("flashMessage", 요약 문구) ──▶ redirect:/provisioning/server-group/{groupId} └── 폼에 data-native-submit 이 있어야 이 flash 가 산다(DEC-E)

왜 별도 빈인가 — before/after

✗ 같은 빈 안에 두면

AssignmentCommandService
 ├ assignToMembers()   ← 여기서
 └ assign()            ← this.assign() 으로 부른다

호출이 프록시를 거치지 않는다(self-invocation)
  → @Transactional 이 무시된다
  → 멤버 N 대가 호출자의 트랜잭션 하나에서 돈다
  → 한 건 실패가 나머지를 되돌린다

✓ 별도 빈으로 두면

GroupAssignmentService ──(주입)──▶ AssignmentCommandService
 └ assignToMembers()                └ assign()  @Transactional

호출이 프록시를 거친다
  → 멤버마다 트랜잭션 하나
  → 9 대 성공 + 1 대 실패가 그대로 남는다

미리보기로 걸렀으므로 실행 중 실패는 경합뿐이고 드물다. 그 드문 한 건이 아홉 건을 되돌리면, 다시 눌러도 상태가 같아 영원히 못 한다. 그래서 트랜잭션 경계를 멤버에 두고, 그 경계가 실제로 서려면 프록시를 지나야 하므로 지휘자를 별도 빈으로 뺀다. 이것은 취향이 아니라 Spring AOP 의 동작 조건이다.

재사용 (신설하지 않는다)

AssignmentBlockKind.evaluate · AssignmentEligibility · RequiredBoardModel · AssignmentCommandService.assign · setting-process-cards 조각 · SettingQueryService.findAssignable · findDetailsOf · GuestServerDetailRepository.findAllByServerIdInWithBoardModel.

§8. 결정

DEC-A. 그룹 전용 picker 조각 — 상세 카드 조각만 공유

안방식판정
① DefinitionPickerItemResponse.blockReason 재사용"8 대에 할당됩니다" 를 그 필드에 담는다탈락
② picker 를 대상 N 개로 완전 일반화1 대 화면도 N=1 로탈락
③ 그룹 전용 조각 + 카드 조각 공유좌측 표기 · 우측 판정만 새로채택

①이 탈락하는 이유는 blocked() 가 blockReason != null 이기 때문이다. 부분 적용(8/10)인데 잠긴 것으로 표시된다 — 이름이 거짓말을 한다.

②는 이미 검증을 마친 U3-5-b 화면을 흔들면서 "1 대 중 1 대" 같은 무의미한 표기를 만든다. 지금 필요 없는 추상이다.

③에서 겹치는 것은 miller 껍데기 마크업 25 행 남짓인데, 그것은 CSS 클래스 조합이지 로직이 아니다. management 다섯 화면도 각자 자기 miller 마크업을 갖는다 — 이 저장소의 확립된 관용구다. 반대로 값나가는 공유 자산인 단계 카드 조각은 그대로 재사용한다.

잠긴 항목을 눌러 사유를 읽게 하는 것은 U3-5-b DEC-C 를 그대로 잇는다. 그룹에서는 사유가 멤버마다 달라 우측에 모아 보여주는 값이 더 크다.

DEC-B. 사전 분류 미리보기 → 확정 → 통과분만 실행

안방식판정
① all-or-nothing한 대라도 막히면 전부 거절탈락
② best-effort + 사후 보고눌러 보고 결과를 안다탈락
③ 미리보기 → 확정 → 통과분 실행누르기 전에 안다채택

①이 탈락하는 이유는 그룹의 혼재가 정상이기 때문이다. U3-4 가 specDiverged 를 "차단이 아니라 안내" 로 못 박았고, 회수된 멤버가 섞이는 것도 흔하다. 한 대 때문에 아홉 대를 못 붙이면 기능이 쓸모없다.

②는 되돌리기 어려운 조작을 눈 감고 누르게 한다. ③이면 "부분 실패" 가 아니라 "부분 적용을 미리 알고 승인" 이 된다 — 불가침 원칙 "UX 모순은 UI 1차 차단" 의 배치판이다.

DEC-C. 이미 할당된 멤버는 건너뛴다

재할당은 기존 스냅샷을 supersede 하는 파괴적 조작이다. 일괄로 하면 운영자가 의도치 않게 여러 대의 계획을 한 번에 갈아엎을 수 있고, 그중 하나라도 개시됐으면 그 대는 막히므로 결과가 더 섞인다.

사용 패턴과도 맞는다 — 그룹에 서버가 추가될 때마다 일괄 할당을 돌리면 기존은 건너뛰고 새 것만 붙는다. 이것이 이 기능을 쓰는 가장 흔한 방식이다.

비채택: "재할당 포함" 체크박스 — 무명 boolean 인자이고 기본값을 어느 쪽으로 두어도 위험하다.

DEC-D. 멤버별 독립 트랜잭션 — orchestrator 는 별도 빈

미리보기로 걸렀으므로 실행 중 실패는 경합뿐이고 드물다. 그런데 한 트랜잭션으로 묶으면 그 드문 한 건이 아홉 건을 되돌리고, 상태가 그대로면 다시 눌러도 같은 결과다.

그래서 멤버마다 독립 트랜잭션으로 AssignmentCommandService.assign 을 부른다. 그 메서드가 이미 @Transactional 이라 새 트랜잭션 설계가 필요 없다.

다만 orchestrator 를 AssignmentCommandService 안에 두면 안 된다 — 같은 빈 안에서 this.assign(...) 을 부르면 Spring AOP 프록시를 우회해 새 트랜잭션이 열리지 않는다(self-invocation). GroupAssignmentService 를 별도 빈으로 두고 AssignmentCommandService 를 주입해 프록시를 통해 부른다.

경합으로 던져지는 예외는 ConflictException 하나의 상위 타입으로 잡아 사유를 결과에 담는다. 차단 종류가 늘어도 여기 줄이 늘지 않는다 — 사유 문구는 AssignmentBlockKind 가 만들기 때문이다. 조건분기를 늘리는 패턴이 아니다.

이 관계는 §4 의 도식 B 와 그 아래 대조가 그림으로 보여 준다.

DEC-E. 결과 통지 = data-native-submit + flash (실측 근거)

flashMessage + PRG 가 관용구이지만, S10 전역 폼 가로채기와 조합되면 메시지가 사라진다(§1 실측). fetch 가 리다이렉트를 안에서 따라가며 flash 를 소비하고 이어지는 location.reload() 는 빈 손이다.

안방식판정
① 가로채기 그대로 + flash지금 관용구탈락 — 문구가 안 뜬다(실측)
② XHR + 모달 안에 결과 렌더비동기 유지탈락
③ data-native-submit + flash네이티브 POST채택

②가 탈락하는 이유는 결과를 본 뒤 결국 화면을 새로 고쳐야 하고(멤버 표가 바뀐다), 그러면 단계가 하나 더 늘기 때문이다. ③은 마커 한 개로 끝나고 이미 두 화면이 그 마커를 쓴다.

③의 대가는 거절 시 오류 모달 대신 HTML 오류 페이지로 이동하는 것이다. 감수할 만하다 — 이 폼의 거절 사유는 그룹 · 정의서 부재나 비활성뿐이고, 그것들은 화면이 이미 1차 차단하므로 direct POST · 경합에서만 나온다. 그때 전체 페이지 오류를 보는 것이 부정확한 성공보다 낫다.

DEC-F. group 과 assignment 는 계속 서로를 참조하지 않는다

실측상 둘은 import 0 건이고 컨트롤러만 엮는다. 이 단계에서 한쪽이 다른 쪽을 참조하게 만들면 그 방향이 굳는다.

컨트롤러가 조립한다 — 멤버 id 목록은 GuestServerGroupQueryService 에서, 판정과 실행은 assignment 에서 받아 잇는다. U3-5-a · b 에서 이미 쓴 방식과 같다(컨트롤러가 settingQueryService.findAssignable() 을 받아 assignmentQueryService 에 넘긴다).

DEC-G. ALREADY_ASSIGNED 를 AssignmentBlockKind 에 넣지 않는다

얼핏 세 번째 차단 종류로 보이지만 아니다. 단건 화면에서 "이미 할당됨" 은 차단이 아니라 재할당으로 가는 갈림길이고, AssignmentBlockKind 는 "이 정의서를 이 서버에 붙일 수 있는가" 만 답한다. 여기에 기존 할당 축을 넣으면 AssignmentEligibility 가 바뀌고 U3-5-a · b 의 판정이 함께 흔들린다.

그룹 문맥에서만 뜻이 있는 분류이므로 MemberApplyOutcome 이라는 별도 열거로 둔다. 분류기는 두 질문을 순서대로 한다 — ① 이미 활성 할당이 있나 ② AssignmentBlockKind.evaluate 가 막나. 이미 있는 멤버는 어차피 건너뛰므로 하드웨어를 대조할 이유가 없다.
