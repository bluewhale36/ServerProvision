§1. 현재 상태 (진단)

E3.5-1 이 카드 뒤를 보게 만들었고 E3.5-2 가 그 인벤토리에서 계획을 산출하는 데까지 왔다. 그런데 지금 RaidConfigurationExecutor.directiveFor 는 인벤토리가 적재된 게스트에게 WAIT 를 돌려준다 — 계획은 조회 미리보기까지만 존재하고, 그 계획을 실물 카드에 거는 손이 없다. 이 슬라이스가 채워야 할 것은 셋이다. 계획을 게스트에게 실어 보내는 길, 중립 계획을 계열 명령으로 옮기는 어댑터, 그리고 집행 결과가 정말 계획대로인지 판정하는 검증이다.

지금까지의 지시는 전부 값 하나였다. COLLECT · REBOOT · WAIT · RAID_INVENTORY 는 "무엇을 하라" 만 말하면 되었고 그 내용은 게스트가 스스로 만들었다. 집행은 다르다 — 어떤 슬롯으로 어떤 레벨의 볼륨을 어떤 이름으로 만들라 는 내용이 서버에서 게스트로 건너가야 한다. E1-2 의 Javadoc 이 "신규 지시 = 값 추가 + agent.sh 갱신" 으로 예고한 확장 자리가 바로 여기이고, 이번에는 값만이 아니라 응답 DTO(Data Transfer Object)의 필드까지 함께 넓힌다.

집행 모델은 E3.5-0-3 토론의 결정 D-1 이 정한 하이브리드다 — 머리(계획 산출 · 결과 판정)는 서버가, 손(계열 CLI 실행)은 게스트가 맡는다. 이 문서의 결정 1 · 4 는 그 하이브리드를 각각 "내려보내는 쪽" 과 "돌려받는 쪽" 에서 구체화한 것이다.

§2. 요구사항 (확정) + 비목표
  1. R1 지시 payload — 지시 값 RAID_APPLY(집행 명령 동봉) · RAID_VERIFY 를 신설하고, 응답 record 2종(AgentCheckinResponse · StepCloseResponse)에 RaidApplyPayload raidApply 필드를 더한다(없으면 null). payload 는 에이전트가 소비하는 축약형이다 — 계획 전체가 아니라 집행에 필요한 것만 담는다(결정 1).
  2. R2 계열 어댑터 — agent.sh 에 do_raid_apply 를 두고 그 안에서 계열별 함수 mr_apply(MegaRAID) · ir_apply(IR)가 중립 명령을 storcli64 · sas3ircu 문자열로 번역한다. 볼륨 이름은 spvR{규칙번호}V{순번} 규약을 따르고, 실행 로그 원문은 base64 로 인코딩해 close 에 동봉한다.
  3. R3 계획 동결 — 집행 지시를 내리기 직전에 PLANNED instant 원장 행을 남긴다. statusMeta 는 동결 계획 JSON 이며, 이 행이 검증 단계의 유일한 대조 기준이다(결정 2).
  4. R4 검증 — 에이전트가 재채집한 원문을 RaidInventoryParser 로 다시 해석해 동결 계획과 대조한다. 일치하면 raid_volume 기록 + 인벤토리 재적재 + 커서 전진(PhaseCursorAdvancer) + REBOOT, 불일치하면 RESULT_MISMATCH 실패 전환이다(결정 4).
  5. R5 원장 사유 확장 — RaidLedger 에 PLANNED · POLICY_UNDECIDED · PLAN_REJECTED · CREATE_REJECTED · RESULT_MISMATCH 5종을 더한다. 앞의 셋은 실패가 아니라 기록과 보류이고, 뒤의 둘만 실패 전환을 동반한다(§7).
  6. R6 raid_volume 전용 표 — 엔티티 RaidVolume + RaidVolumeRepository + DDL. "현재 실물" 을 담는 표이므로 검증 성공 시 그 게스트의 기존 행을 전부 지우고 다시 쓴다(append 원장이 아니다 — 결정 D-8).
비 목표 :
  • 게스트 서버 상세의 볼륨 표 렌더 · E4 인계 조회 SPI(Service Provider Interface — 도메인이 구현해 끼우는 확장점) · 정의서의 "기존 구성 : 보존 / 파괴" 축 · 사각 규칙 정적 차단 — 넷 모두 E3.5-4.
  • 실카드 집행 — CP7 실기 일괄. 이 슬라이스의 CP5 는 하네스와 픽스처로 사이클을 재연한다.
  • 동기화 완료 대기 — RAID5 · RAID6 초기 동기화가 끝날 때까지 기다리지 않는다. 재채집한 상태 문자열을 그대로 raid_volume.state 에 남길 뿐이다(결정 D-9).
🎬 미리보기 — 집행 사이클 한 바퀴

왼쪽이 프로비저닝 서버(커서 step · 동결 계획 · 원장 행 스트림), 오른쪽이 게스트 · 에이전트 콘솔(수신 지시 · 번역된 CLI 문자열 · 보고)이다. 아래 버튼으로 체크인 → 집행 → 검증 을 한 칸씩 밀면, 서버가 무엇을 동결해 내려보내고 에이전트가 그것을 어떤 명령으로 옮기며 서버가 무엇을 근거로 기록하거나 거절하는지가 그대로 드러난다. 처음이라면 원클릭 시나리오 P1~P6 을 순서대로 눌러 보는 편이 빠르다 — 세팅과 안내 배너가 함께 붙는다. 툴바를 바꾸면 진행 중인 한 바퀴는 초기화된다.

이 데모는 E3.5-1 인벤토리 적재가 끝난 지점에서 시작한다. 판정 JavaScript 는 서버 규칙의 미러다 — demoDirective() 가 §4 의 directiveFor 5단계 상태기계를, demoVerify() 가 RaidResultVerifier 의 4축 대조를 같은 순서로 재현한다. 버튼의 disabled 사유(마우스를 올리면 tooltip)도 같은 판정에서 나온다.

지시 payload 계약 (RaidApplyPayload)

{
  "deleteExisting": true,
  "volumes": [
    { "name": "spvR1V1", "level": "RAID1", "slots": ["252:0","252:1"] },
    { "name": "spvR2V1", "level": "RAID5", "slots": ["252:2","252:3","252:4","252:5","252:6","252:7"] }
  ],
  "jbod": []
}

이 직렬화가 agent.sh 어댑터와의 SSOT(Single Source of Truth) 계약이다. deleteExisting 은 볼륨 생성 전에 기존 볼륨을 전부 지울지를 가리키며, 이 슬라이스에서 집행이 개시되는 조건은 외부 기존 볼륨 0 이므로(결정 3 — 우리 이름 규약 spvR* 의 잔여는 허용) 실제로 지우는 대상은 직전 시도가 남긴 잔여 볼륨이다 — 그것이 결정 5 의 멱등이다. 정의서의 "기존 구성 : 보존 / 파괴" 축이 이 필드와 어떻게 연결되는지는 그 축을 도입하는 E3.5-4 가 정한다.

어댑터가 하는 일은 번역과 실행과 정직한 보고 뿐이다. 실행이 실패하면 그 자리에서 삼키거나 되돌리려 시도하지 않고 FAILED 로 닫으면서 로그 원문을 그대로 올려보낸다 — 무엇이 왜 안 됐는지의 판단은 서버와 사람의 몫이다.

§4. 도메인 모델 (SSOT)

directiveFor 판정 순서 — 데모와 진리표의 SSOT

순서조건지시원장
1인벤토리 미적재RAID_INVENTORY— (E3.5-1 현행 유지)
2적재 + 검증 성공 (raid_volume 최신 존재)REBOOT (공통 규칙)— (커서 전진은 onStepClosed 가 이미 수행)
3적재 + 외부 기존 볼륨(이름이 spvR 규약이 아닌 것) 존재 + 축 부재WAITPOLICY_UNDECIDED instant · 중복 억제
4적재 + 계획 거절WAITPLAN_REJECTED instant · 중복 억제
5적재 + 계획 성립RAID_APPLY + payloadPLANNED 동결

우리 잔여의 판별 — 판정 3 의 "기존 볼륨" 은 외부 볼륨만 가리킨다. 직전 시도가 만들다 만 볼륨은 이름이 spvR{규칙}V{순번} 규약이라 우리 것임이 카드만 보고 판별되고, 이런 잔여만 있는 상태는 보류가 아니라 판정 5 로 진행한다 — payload 의 deleteExisting 이 true 가 되어 선행 삭제 후 재구성한다(결정 5 멱등 · 진리표 V2 · 데모 P6 의 성립 근거). 결정 D-7 개정이 파괴 정책을 채택하면서도 이름 규약을 유지한 이유가 바로 이 판별이다. IR 계열이 이름을 내지 않는 경우(실측 미확정)의 잔여는 보수적으로 외부로 간주해 보류한다 — CP7 실측에서 이름 노출이 확인되면 완화한다.

중복 억제는 "최신 원장 행이 이미 그 사유면 새로 남기지 않는다" 는 규칙이다. 게스트는 지시를 받으려 주기적으로 체크인하므로, 억제가 없으면 보류 상태의 게스트 하나가 같은 사유의 행을 무한히 쌓는다. 3 · 4 는 실패가 아니라 보류다 — 둘 다 정의서를 고치거나 축을 도입하면 저절로 풀리는 상태이므로, 실패로 낙인찍어 사람이 손으로 되돌리게 만들지 않는다(결정 3).

RaidVolume 엔티티 · raid_volume 표

CREATE TABLE raid_volume (
    id               uuid         NOT NULL PRIMARY KEY,
    guest_server_id  uuid         NOT NULL,
    name             varchar(32)  NOT NULL,
    raid_level       enum('RAID0','RAID1','RAID5','RAID6','RAID10') NULL,
    member_slots     longtext     NOT NULL CHECK (json_valid(member_slots)),
    usable_bytes     bigint       NULL,
    volume_role      enum('OS','DATA','NONE') NOT NULL,
    rule_no          int          NULL,
    state            varchar(64)  NULL,
    created_at       datetime(6)  NOT NULL,
    updated_at       datetime(6)  NOT NULL,
    KEY idx_raid_volume_guest (guest_server_id),
    CONSTRAINT fk_raid_volume_guest FOREIGN KEY (guest_server_id)
        REFERENCES guest_server (id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

기존 표 관례를 그대로 따랐다 — uuid 기본키 · 부모 삭제 시 함께 지워지는 외래키 · datetime(6) · JSON 컬럼의 json_valid 체크. raid_level 이 null 을 허용하는 이유는 볼륨에 넣지 않은 단독 디스크도 이 표에 실릴 수 있기 때문이다. state 는 재채집한 상태 원문(동기화 진행률 등)을 해석하지 않고 그대로 담는 자리라 문자열이 맞다 — 이 슬라이스는 동기화를 기다리지 않고 상태만 기록한다(결정 D-9). 참조 표 · 컬럼의 정확한 이름과, 위에 명시되지 않은 컬럼의 null 허용 여부는 CP2 · CP3 에서 엔티티와 함께 확정한다.

검증 성공 시 그 게스트의 기존 행을 전부 지우고 다시 쓴다. 이 표는 시간순 원장이 아니라 "지금 카드에 무엇이 올라가 있는가" 를 담는 현재 상태 표이기 때문이다. 재집행이 일어나도 표가 과거 시도의 잔재로 오염되지 않는다.

결정 1. 계획 운반

안내용판정
Aclose · 체크인 응답에 집행 payload 동봉채택

B 는 왕복이 한 번 늘고 신규 엔드포인트가 하나 생긴다. 더 나쁜 것은 지시와 계획이 서로 다른 시점에 읽힌다는 점이다 — 그 사이에 정의서가 바뀌면 게스트가 받은 지시와 조회한 계획이 어긋날 표면이 생긴다. A 는 E1-2 가 예고한 확장 자리(응답 DTO 넓히기)이고, REBOOT 를 close 응답이 유일하게 운반해 온 선례와도 같은 결이다. payload 는 계획 전체가 아니라 집행에 필요한 것만 담은 축약형이며, 그 직렬화가 agent.sh 어댑터와의 계약이 된다.

결정 2. 계획 동결의 자리

안내용판정
aRAID_APPLYING RUNNING 행의 statusMeta 에 계획 동봉 (E2-2 openRunning 변형)탈락
b집행 지시 직전 PLANNED instant 행 (recordInstant · statusMeta = 동결 계획 JSON)채택
a 를 탈락시킨 근거는 E2-2 F-1 의 실측 교훈이다 — 원장 close 가 statusMeta 를 결과로 덮는다. 그때 남긴 교훈은 이렇게 정리돼 있다: "열림 시점에 적은 사실에 기대는 판정은 닫힌 뒤에도 남는지 확인한다." 이 슬라이스의 검증(RESULT_MISMATCH 대조)은 RAID_APPLYING 이 닫힌 뒤에 일어나므로, 계획을 열림 시점의 statusMeta 에 적어 두는 a 는 정작 대조할 때 그 기준을 잃는다.

b 는 불변 단발 행이라 나중에 덮일 일이 없고, 집행 도중에 정의서가 재할당되어도 대조 기준이 흔들리지 않는다. E3.5-2 가 세운 무저장 재산출 원칙(결정 3)과의 경계도 여기서 그어진다 — 미리보기는 언제나 재산출이고, 집행과 검증만 동결본을 쓴다. 조회할 때마다 최신 정의서를 반영하는 이점은 그대로 두면서, 되돌릴 수 없는 조작을 하는 순간에만 시점을 고정하는 것이다.

A 는 파서와 정규화가 E3.5-1 에 이미 있으므로 추가 비용이 재채집 지시 하나뿐이고, 부수 효과로 집행 후 최신 인벤토리가 다시 적재되어 상세 화면이 실물과 같아진다. 대조 축은 볼륨 수 · 레벨 · 멤버 슬롯 집합 · 이름 넷이며, IR 이 이름을 내지 않는 경우에는 레벨과 멤버로 폴백한다. 동기화 완료는 기다리지 않고 상태만 기록한다(D-9).

결정 5. 멱등

원안이었던 이름-스킵 멱등(같은 이름의 볼륨이 이미 있으면 건너뛴다)은 D-7 개정으로 소멸했다. 재시도 · 재집행의 멱등은 DESTROY 선행 삭제가 보장한다 — 전부 지우고 다시 만드니 같은 입력이면 같은 결과가 된다. PRESERVE 는 기존 볼륨 0 을 전제로 하므로 재집행도 안전하다. 그래서 별도의 멱등 장치를 만들지 않는다. 상태를 하나 더 두고 그것을 관리하는 것보다, 이미 있는 삭제 동작이 멱등을 떠맡게 하는 편이 구현이 단순하고 오작동 표면도 작다.

결정 6 — 에이전트 계열 판별의 SSOT (CP4 검수 반영)

안내용판정
Aagent.sh 가 칩 PCI id 를 하드코딩해 스스로 판별(구현 초판)폐기
B정의서 지정 카드의 계열을 서버가 확정 동봉탈락
C서버가 "칩 → 계열" 판별 맵(raidChips)을 RAID 지시에 동봉 — 에이전트는 받은 맵으로만 판별채택

CP4 검수에서 사용자가 지적했다 — A 는 새 카드(칩)가 올 때마다 셸 스크립트를 고쳐 이미지를 다시 구워야 하고, 같은 id 가 RaidInventoryParser 의 패턴에도 있어 판별 SSOT 가 둘이었다. B 는 RaidCard 관리 엔티티에 계열 축이 없어 등록 폼 · DDL · 이관이 따라오는 데다 결정적 결함이 있다 — 지정 카드를 믿고 도구를 고르면 실물에 다른 계열이 꽂혔을 때 엉뚱한 도구가 실패해 CARD_MISMATCH 를 영영 판별하지 못한다(대조는 채집이 성공해야 가능하다). C 는 칩 id 를 RaidChipFamily.chipPciIds()(method-per-constant) 한 곳에 모으고, 파서와 에이전트 힌트 (agentChipHint() — "1000:0097=MPT_IR 1000:005d=MEGARAID")가 같은 집합 · 같은 순서로 판별한다. 새 칩 추가 = 서버 enum 한 곳 수정 · 스크립트 불변이고, 실물 기준 판별이라 불일치도 정상 채집되어 서버 대조가 정직하게 잡는다. 계열 자체(새 도구)가 늘 때만 어댑터 함수가 스크립트에 추가된다 — 그것은 본질적 변경이다.

리스크

실기 두 카드가 모두 기존 볼륨을 갖고 있다. 결정 3 에 따라 축(E3.5-4)이 없으면 이 카드들에서는 집행이 개시되지 않으므로, CP7 실기에서 집행 관찰이 불가능하다. 완화는 ② 운영자가 실기에서 기존 볼륨을 수동으로 지운 뒤 실측으로 확정했다(사용자 확정 2026-08-31 — CP1 승인). E3.5-4 선행 배치(①)는 채택하지 않는다.
  • sas3ircu 의 볼륨 이름 한계가 미실측이다(길이 · 허용 문자). 이름이 그대로 보존되지 않으면 이름 축 대조가 실패하므로, IR 에서는 레벨 + 멤버 폴백을 기본으로 둔다. E3.5-1 이 "IR 볼륨 이름 규약 결정" 을 이 슬라이스로 넘겼으나, 실측 표본이 없어 규약을 확정하는 대신 폴백 대조 규칙으로 대신한다.
  • storcli 의 JBOD 슬롯 보장은 컨트롤러 personality 에 의존한다. 실측 전이므로 실패하면 어댑터가 조용히 삼키지 않고 CREATE_REJECTED 로 정직하게 보고한다.
  • RAID10 의 span 구성(pdperarray)은 디스크 4대를 넘는 실측 표본이 없다. 진리표와 픽스처는 4대만 다룬다.
  • 실행 로그 원문(base64)이 statusMeta 문자열 컬럼에 실린다. 인벤토리 원문과 같은 계약이므로 새 설계는 필요 없으나 크기는 CP5 에서 실측 확인한다.
