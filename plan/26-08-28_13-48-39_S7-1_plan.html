§1. 현재 상태 (진단)

1-1. 증상

2026-08-27~28 베어메탈 통합 테스트에서 사용자가 기록한 항목(decisions.rtf 1번)이다. 게스트 서버 목록 화면이 서버 등록과 상태 변화를 실시간으로 반영하지 않았다. 새로고침하면 최신 상태가 보였고, 브라우저 콘솔에는 오류가 없었다.

같은 기능이 샌드박스에서는 문제를 보인 적이 없다. 샌드박스는 앱에 직접 접속하는 환경이며, S7 의 CP5 · CP7 이후 지금까지, 그리고 2026-08-28 의 E3-3 CP5 에서도 실시간 반영은 정상이었다.

1-3. 실기 접속 경로

실기 스테이징 VM 은 2026-08-15 부터 HTTPS 단일 창구다(docs/staging-vm-bootstrap.md §12, 저장소 메모리 DPL-1). nginx 1.20 이 443 에서 TLS 를 종단해 127.0.0.1:8080 으로 프록시하고, 앱은 server.address=localhost 로 루프백 전용이며 방화벽의 8080 은 회수됐다. 그러므로 실기 브라우저 트래픽은 전부 nginx 를 지났다.

런북 §12 의 nginx 설정에는 client_max_body_size 20g · proxy_request_buffering off(업로드 스트리밍) · proxy_read_timeout 300s 와 proxy_set_header 넷이 있고, 응답 버퍼링에 관한 지시어는 없다. 즉 proxy_buffering 은 기본값 on 이고 proxy_http_version 은 기본값 1.0 이다. 앱 쪽도 SSE(Server-Sent Events) 응답에 Content-Type: text/event-stream 외의 헤더를 내지 않는다.

S7 원 plan(2026-07-19)은 프록시의 idle 절단 만 대비했다 — 25초 heartbeat 가 그것이다. 프록시의 응답 버퍼링 은 다루지 않았고, S7 의 CP5 · CP7 은 직접 접속이었으며, nginx 는 그 뒤 DPL-1 에서 들어왔다. 그래서 두 슬라이스 모두 자기 검증에서는 옳았다.

1-4. 재현 (2026-08-28 13:43 KST, 세션 실측)

샌드박스 e33 앱(포트 7818) 앞에 nginx 1.20.2 docker 를 세우고, 런북 §12 의 설정을 TLS 세 줄만 빼고 그대로 옮겼다. 80 은 런북 그대로, 81 은 proxy_buffering off 한 줄을 더한 대조군이다. 세 경로를 동시에 20초 청취하고, 5초 시점에 모의 게스트 부팅 요청(GET /api/pxe/v1/boot)으로 신규 등록 = GuestServerChangedEvent 를 일으켰다.

1-5. 기전 — 세 조건이 겹친다

  1. nginx 는 업스트림에 HTTP/1.0 으로 요청한다(proxy_http_version 기본값). Tomcat 은 HTTP/1.0 요청에 chunked 전송을 쓸 수 없으므로 Connection: close 의 identity 본문으로 응답한다. 실측으로도 직접 curl --http1.0 은 Connection: close 를, curl 의 1.1 요청은 Transfer-Encoding: chunked 를 받았다.
  2. nginx 의 proxy_buffering 기본값은 on 이다. identity 본문은 proxy_buffer_size(기본 4k 또는 8k, 메모리 페이지 1장)가 찰 때까지 클라이언트로 내보내지 않으며, 이때 응답 헤더도 함께 붙든다.
  3. 앱의 프레임은 작다 — :connected 11 B 한 번, :ping 7 B 를 25초마다, event:changed 약 58 B. 4 KB 를 채우려면 수 시간이 걸린다. 그동안 heartbeat 가 업스트림 읽기를 계속 일으켜 proxy_read_timeout 300s 도 만료되지 않는다.
결과 — 브라우저의 EventSource 는 응답 헤더를 못 받아 CONNECTING(readyState 0)에 머문다. open 도 error 도 발생하지 않으므로 server-stream.js 는 아무것도 기록하지 않는다. 이것이 콘솔 침묵의 정체다. 재연결이 일어나도 같은 버퍼에 다시 갇힌다. 아주 오래 두면 4 KB 가 차는 순간 쌓인 프레임이 한꺼번에 쏟아져 "가끔 몰아서 갱신되는" 것처럼 보일 수 있다.

1-6. 정정 후보의 기전 검증 (같은 nginx, 최소 SSE 서버)

identity 본문을 내는 최소 서버로 Tomcat 이 HTTP/1.0 요청에 내는 모양을 재현하고, 같은 nginx 뒤에 두어 헤더만 바꿨다.

업스트림 응답응답 헤더nginx(버퍼링 기본) 5초 통과

identityX-Accel-Buffering: no120 B — 전 프레임 즉시

X-Accel-Buffering: no 는 nginx 가 응답 단위로 버퍼링을 끄는 표준 헤더다. proxy_ignore_headers 로 무시하지 않는 한 존중하며, 런북에는 그런 줄이 없다. 세 번째 행(chunked)은 §8 의 탈락 대안 B2 가 성립하는 근거이기도 하다.

§2. 요구사항 (확정) + 비목표
  1. R1 앱이 SSE 응답에 전달 조건을 스스로 선언한다 — GuestServerStreamController.stream() 이 X-Accel-Buffering: no 와 Cache-Control: no-cache 를 응답 헤더로 낸다. 런북의 nginx 설정은 바꾸지 않는다.
  2. R2 통합 테스트가 두 헤더를 고정한다(GuestServerStreamControllerTest).
  3. R3 런북 docs/staging-vm-bootstrap.md §12 에 "왜 stream 경로의 location 분기가 없는가" 를 기록한다 — 앱이 선언하므로 설정이 필요 없다는 사실, nginx 가 업스트림에 HTTP/1.0 으로 요청한다는 사실, 다른 프록시로 바꾸면 그 프록시의 규약을 다시 확인해야 한다는 주의.
  4. R4 프록시 검증 하네스 scripts/proxy-lab/ 를 git 추적 자산으로 둔다 — nginx 1.20 docker 와 런북 §12 설정의 거울(TLS 세 줄 제외). CP5 와 이후 회귀 재현에 쓴다.
  5. R5 CP5 는 브라우저로, nginx 를 경유해, 정정 전 · 후를 대조한다.
비 목표 :
  • SSE 를 WebSocket 으로 바꾸는 일(Notion ②).
  • nginx 설정 쪽 정정(location 분기 · proxy_http_version 1.1) — §8 D-1 의 탈락 대안이다.
  • heartbeat 주기 · 30분 구독 타임아웃 조정 — 원인이 아니다.
  • nginx 외 프록시(Apache httpd · HAProxy) 대응 — 채택 시 런북에서 다룬다.
🎬 미리보기 — 프록시 버퍼 시뮬레이터

접속 경로를 고르고 앱이 프레임을 내보내면, 그 프레임이 브라우저에 닿는지 nginx 버퍼에 갇히는지를 그대로 따라갈 수 있다. 판정은 §1-5 의 기전을 그대로 옮긴 한 줄이다 — passThrough = path === 'direct' || path === 'unbuffered' || path === 'http11' || headerDeclared. 임계값 4096 B, 프레임 크기 11 · 7 · 58 B 도 §1-5 의 실측값이다.

읽는 법 — 접속 경로 버튼을 누르면 구독이 새로 시작된다(브라우저가 EventSource 를 다시 연 것과 같다). 헤더 선언 토글을 바꾸면 구독이 새로 시작된다 — 응답 헤더는 첫 프레임 전에 확정되므로(§8 주의 참조), 토글은 "정정 전 앱" 과 "정정된 앱" 중 어느 쪽에 다시 붙는가를 고르는 조작이다.

구독 엔드포인트는 인자 없는 GET 이고 성공 시 스트림을 연다. 이 URL 에서 200 이 아닌 응답이 나오는 유일한 기존 경로는 S10 이 넣은 Accept 정규화가 문서 이동 요청을 거절하는 406 이며, 그것은 이번 변경의 대상이 아니라 §9 의 B2 에서 회귀 가드로 확인만 한다.

D-1 — 왜 앱이 선언하는가

A 는 앱이 "이 응답은 버퍼링하면 안 된다" 를 자기 응답에 적는 방식이다. 이번 사고의 구조가 "런북에 없어서 났다" 이므로, 정정을 다시 런북에 두면 같은 구조가 남는다 — 설정을 옮겨 적는 다음 환경에서 그대로 재발한다. B 는 stream 경로마다 location 을 따로 만들어야 하고 그 안에서 proxy_set_header 넷을 다시 적어야 해 설정의 SSOT(Single Source of Truth)가 갈라진다. B2 는 §1-6 의 chunked 행처럼 실제로 통하지만, 역시 기능의 정상 동작이 운영 설정 한 줄에 걸린다. C 는 같은 사실을 두 곳에 적는 중복이다.

A 의 한계도 분명하다. X-Accel-Buffering 은 nginx 의 규약이다. 프록시 제품을 바꾸면 그 제품의 규약(예: Apache httpd 는 기본 비버퍼링, HAProxy 도 기본 비버퍼링)을 런북에서 다시 확인해야 한다. 이 주의를 R3 의 문단에 적는 것이 A 를 택하면서 지불하는 비용이다.

D-2 — Cache-Control: no-cache 를 함께 내는 이유

SSE 응답에 Cache-Control: no-cache 를 붙이는 것은 표준 권고다. 중간 캐시나 proxy_cache 가 스트림을 저장하려는 것을 막으며, 비용이 없다.

D-3 — 하네스를 저장소에 두는 이유

CP7 과 이후 회귀에서 같은 재현을 누구나 할 수 있어야 한다. scripts/mock-guest/ · scripts/pxe-lab/ 가 같은 이유로 git 추적 자산이 되어 있다. 드리프트를 막기 위해 scripts/proxy-lab/nginx.conf 머리에 "런북 §12 의 거울, TLS 세 줄만 제외 — 둘을 함께 고친다" 를 적는다.

scripts/proxy-lab/ ├── nginx.conf 80 = 런북 §12 그대로 · 81 = proxy_buffering off 대조군 ├── run.sh docker run nginx:1.20 (앱 포트를 인자로 받는다) └── README 두 줄 — 무엇을 재현하는가 · 런북과 함께 고친다

D-5 — 반환형으로 헤더를 싣는 이유

ResponseEntity<ResponseBodyEmitter> 는 Spring MVC 가 공식 지원하는 반환형이라 컨트롤러가 서블릿 API 를 직접 만지지 않는다. 필터나 인터셉터로 일괄 적용하는 방식은 스트림 응답의 생산자가 하나뿐인 지금 "미리 분리 금지" 원칙에 걸린다.

주의

  • nginx 에 proxy_ignore_headers X-Accel-Buffering 이 들어가면 이 헤더는 무시된다. 런북에 그런 줄이 생기지 않도록 R3 문단에 적는다.
  • 응답 헤더는 첫 프레임 전에 확정돼야 한다. ResponseEntity 반환이 그 순서를 보장한다.
