§0. 한눈 요약

S10 이 도입한 전역 폼 가로채기는 상태 변경 폼의 제출을 fetch 로 보낸다. 그 fetch 는 redirect: 'follow' 로 설정돼 있어, 서버가 PRG(Post-Redirect-Get — 쓰기 요청을 처리한 뒤 리다이렉트로 조회 화면에 돌려보내는 관례)로 내려보낸 302 를 fetch 안에서 따라간다. 이때 발생하는 목적지 GET 이 세션에 저장된 flash 를 꺼내 소비하고, 그 응답 HTML 은 스크립트가 쓰지 않고 버린다. 이어지는 window.location.reload() 는 두 번째 GET 이며 그 시점에 flash 는 이미 없다. 결과적으로 재검증 완료 · 무결성 봉인 · 드라이버 페이로드 조립 결과 · 일괄 할당 결과 · 드리프트 적용 완료 같은 성공 안내가 화면에 닿지 못한다.

지금까지의 우회는 문제가 드러난 폼마다 data-native-submit 을 붙여 가로채기에서 빼는 것이었다. 현재 그렇게 빠져 있는 폼이 넷이고, 규약 테스트 FormSubmissionConventionTest 의 예외 목록 NATIVE_FOR_FLASH 에 이름으로 올라 있다. 이 방식은 두 가지를 대가로 치른다 — 새 지점이 생길 때마다 사람이 기억해야 하고(2026-08-13 자산 화면 3곳 실측 이후 E4-1-a-4 CP5 F-3 이 네 번째 지점이었다), 네이티브로 빠진 폼은 서버가 거절했을 때 오류 모달 대신 HTML 오류 페이지를 띄운다(U3-5-c 의 결정 DEC-E 가 감수한 대가다).

이 슬라이스가 하는 일은 셋이다.

  1. 서버가 XHR(XMLHttpRequest 로 대표되는 스크립트 요청) 의 리다이렉트를 200 과 X-Redirect-Location 헤더로 바꿔 내려보내고, 이동은 브라우저가 한다. 브라우저가 이동하면 그 GET 이 flash 를 소비해 화면에 표시된다. 컨트롤러도 템플릿도 바뀌지 않고 마커도 필요 없어진다.
  2. PRG 뒤 탭이 첫 탭으로 돌아가는 것을 location.hash 로 유지한다.
  3. 편입한 F-1 — 같은 자리에 떨어진 400 사유가 서로 덮어써 마지막 한 건만 남는 것을 누적 표시로 고친다.
S10 의 기본값은 유지한다. "가로채는 것이 기본, 네이티브가 예외" 라는 방향을 되돌리지 않는다(Notion HF9 ② 비목표). 바꾸는 것은 가로챈 요청이 리다이렉트를 어떻게 받느냐이며, 그 결과로 예외 목록이 비워진다.
§1. 현재 상태 (진단)

1-1. flash 가 사라지는 경로

static/global/form-submit.js 의 send 가 폼을 이렇게 보낸다.

resp = await fetch(url, {
    method, body,
    headers: {'X-Requested-With': 'XMLHttpRequest', 'Accept': 'application/json,text/html;q=0.9,*/*;q=0.5'},
    redirect: 'follow'
});
…
if (resp.ok || resp.redirected) { h.onSuccess(form, resp); return; }   // onSuccess = window.location.reload()

반대편의 컨트롤러는 관례대로 flash 를 담고 리다이렉트한다. SystemAssetController 의 recheck · seal, DiagnosticAssetController, WindowsOemPayloadController, GuestServerGroupController 는 RedirectAttributes.addFlashAttribute("flashMessage", …) 뒤 redirect: 를 돌려주고, ReconciliationRestController.apply 는 같은 일을 RedirectView 로 한다.

Spring 의 RedirectView 는 flash 를 세션 FlashMap 에 저장한 뒤 리다이렉트를 낸다. 그래서 fetch 가 302 를 따라가 목적지를 GET 하는 순간 FlashMapManager 가 그 요청에서 flash 를 꺼내 소비한다. 화면이 되어야 할 그 HTML 을 스크립트는 쓰지 않고 버리고, resp.redirected 가 참이라 onSuccess → window.location.reload() 로 넘어간다. 이 두 번째 GET 에는 꺼낼 flash 가 남아 있지 않다.

서버 로직의 결함이 아니라는 것은 2026-08-13 에 확인했다 — 같은 세션으로 curl 이 POST 와 뒤이은 Location GET 두 단계를 밟으면 flash 는 정상적으로 표시된다. 소비 지점이 사용자가 보는 화면이 아닐 뿐이다.

1-2. 영향 범위

영향을 받는 것은 마커 없이 가로채지는 POST 폼 가운데 PRG 와 flash 로 답하는 컨트롤러로 가는 것이다. 마커로 이미 빠져 있는 넷은 flash 는 뜨지만 거절 시 오류 모달을 잃은 상태다.

규약 테스트는 이 비대칭을 그대로 안고 있다. FormSubmissionConventionTest 의 핵심 가드는 "재렌더(BindingResult) 핸들러 수 = data-native-submit 폼 수" 인데, 위 넷은 재렌더가 아닌 이유로 네이티브이므로 NATIVE_FOR_FLASH 목록에 이름으로 올려 빼두었다. 목록은 파일명이 아니라 폼 하나마다 한 줄이라 server-group-detail.html 이 세 번 적혀 있다.

1-3. 탭이 첫 탭으로 돌아가는 이유

static/global/n-tab.js 는 click 만 처리한다 — 같은 그룹의 aria-selected 를 토글하고 대응 패널에 .is-active 를 옮길 뿐, URL 이나 저장소에 아무것도 남기지 않는다. 서버는 th:attr aria-selected=${iter.first} 로 항상 첫 영역을 선택된 탭으로 그린다. 그래서 PRG 로 화면이 다시 그려지면 사용자가 어느 탭에서 눌렀든 첫 탭이다(탭 그룹은 대시보드 하나 · n-tab.js 도 그 화면에서만 적재). Windows 설치 소스 탭에서 [드라이버 페이로드 조립] 을 누르면 진단 탭으로 튀고, [봉인] 과 게스트 상세의 [재시도] 도 같은 방식으로 위치를 잃는다.

1-4. F-1 — 400 사유가 서로 덮어쓴다

HF12 의 CP5 에서 관측했다. 정의서 폼 전용 매퍼(setting-form.js 의 paintFieldError)와 전역 매퍼(form-error.js 의 applyFieldErrors)가 똑같이 이 한 줄을 갖고 있다.

anchor.querySelectorAll(':scope > .field-error-message').forEach(el => el.remove());   // 기존 메시지 제거 후 1건 부착

서로 다른 필드의 사유가 같은 앵커로 떨어지면 — 정의서 폼에서 경로를 좁히지 못한 사유는 카드 본문으로 폴백하므로 흔하다 — 뒤엣것이 앞엣것을 지우고 마지막 한 건만 남는다. 리눅스 정의서를 저장할 때 partitions · environmentId · timezone 세 사유가 함께 내려오면 사용자는 한 건만 본다. 더 나쁜 것은 mapped = 3 · overflow = 0 이라 "전부 인라인 매핑되면 요약 배너를 생략한다" 는 규칙까지 발동해, 나머지 두 사유를 볼 통로가 아예 없다는 점이다.

렌더 시작에서 FormError.clear(form) 가 폼 안의 모든 .field-error-message 를 이미 지운다. 즉 앵커별 재삭제는 처음부터 필요가 없었다 — 같은 렌더 안에서 자기가 방금 붙인 것을 지우는 동작이다.

세 결함의 공통 뿌리 — 화면에 도달해야 할 정보(성공 안내 · 보던 위치 · 거절 사유)가 중간 단계에서 소비되거나 덮어써진다. 셋 다 사용자 눈에는 "눌렀는데 아무 말이 없다" 로 보이며, 빌드와 테스트로는 드러나지 않아 화면 검증에서만 잡혔다.
§2. 요구사항 (확정) · 비목표 + 설계 대안
  1. 가로채진 제출도 성공 안내(flash)가 화면에 표시돼야 한다. 컨트롤러의 flash 사용 관례는 바꾸지 않는다.
  2. 그 결과로 data-native-submit 우회가 필요 없어져야 한다 — 넷을 회수하고 예외 목록을 비운다.
  3. 가로채기로 돌아온 폼은 서버가 거절할 때 오류 모달을 되찾는다(HTML 오류 페이지가 아니다).
  4. PRG 로 화면이 다시 그려져도 보던 탭이 유지된다. 새로고침 · 뒤로가기 · URL 공유에서도 같아야 한다.
  5. 400 사유가 여럿이면 여럿 다 보인다. 같은 문장은 한 번만 붙는다.
  6. 비 XHR 경로(문서 이동 · curl · PXE 게스트)는 지금과 완전히 같다.
비 목표 :
  • S10 의 기본값 전환 — "가로채는 것이 기본" 은 그대로 둔다. 되돌리는 순간 U3-2-b 의 raw JSON 노출 사고 구조로 돌아간다.
  • flash 표시 위치 · 문구 표준 — 배너를 어디에 어떤 문장으로 띄울지는 S16-2 어휘 · 문체 표준의 몫이다.
  • 모달 카피 — 오류 모달의 문구 정비는 S12 다.
  • 리눅스 입력 부활 · 오류 앵커 복원 — E4-L 소관이다. 여기서는 이미 내려온 사유를 지우지 않는 것까지만 한다.

2-1. flash 를 살리는 네 가지 길

안요지결과
① 마커 확대폼마다 data-native-submit탈락 지점마다 잊음 · 예외 목록 증식 · 거절 시 오류 모달 상실
② manual 리다이렉트fetch 를 redirect:'manual' 로탈락 응답이 opaqueredirect — 상태 0 · Location 판독 불가
③ JSON + 토스트컨트롤러가 XHR 에 flash 를 JSON 으로탈락 컨트롤러 6 수정 · 안내 채널 이원화 · 화면 갱신은 별도
④ 응답 변환 필터XHR 의 리다이렉트를 200 + X-Redirect-Location 으로, 이동은 브라우저가채택 컨트롤러 · 템플릿 무변경 · flash 보존 · 마커 불요 · 오류 모달 유지

②가 안 되는 이유를 한 번 더 풀면 이렇다. redirect:'manual' 로 받은 응답은 브라우저가 내용을 가리는 opaqueredirect 라 상태 코드가 0 이고 Location 헤더를 읽을 수 없다. 리다이렉트가 있었다는 사실만 알 뿐 어디로 가야 하는지를 모르므로 스크립트가 이동을 대신할 수 없다. ③은 동작은 하지만 안내가 도달하는 통로를 flash 와 토스트 둘로 갈라 놓는다 — 같은 성공 문구가 요청 종류에 따라 다른 자리에 뜨게 되고, 화면 갱신은 여전히 별도로 해야 한다.

④를 고르면서 3xx 를 Location 없이 내는 변형은 배제했다. 표준에서 벗어난 응답이라 중간 프록시가 어떻게 다룰지 보장되지 않는다. 상태 코드는 200 으로 두어 fetch 의 resp.ok 가 참이 되게 하고, 본문은 비운다.

2-2. 탭 위치를 기억하는 세 가지 길

안요지결과
① location.hash클릭 시 replaceState · 로드 시 복원 · PRG 가 hash 를 이어붙임채택 공유 · 새로고침 · 뒤로가기에 자연스럽고 두 모듈이 서로를 모름
② sessionStorage활성 탭을 저장소에탈락 새 탭 · URL 공유 불가 · 화면별 키 설계 필요
③ 서버 파라미터제출 시 활성 탭을 실어 보냄탈락 두 모듈이 결합 · 서버가 화면 내 위치를 알게 됨

①의 장점은 결합이 생기지 않는다는 데 있다. n-tab.js 는 자기 탭을 hash 에 적을 뿐 누가 그것을 읽는지 모르고, form-submit.js 는 "같은 화면으로 돌아오는 PRG 는 화면 내 위치를 유지한다" 는 일반 규칙만 알 뿐 탭이라는 개념을 모른다. 둘 사이의 계약은 URL 하나다.

2-3. 400 사유를 살리는 두 가지 길

안요지결과
① 앵커 누적지우는 줄을 빼고 붙이기만 · 같은 문장은 1회채택 clear() 가 이미 전부 지우므로 삭제 줄만 덜어내면 됨
② 배너 폴백폴백 앵커로 간 사유는 overflow 로 돌려 배너에탈락 인라인과 배너로 갈라져 읽기 어렵고, 한 필드에 2 사유인 경우는 여전히 덮임

②가 남기는 사각지대가 결정적이다. 앵커를 정상적으로 찾은 필드에 사유가 둘 붙는 경우(같은 입력에 대한 서로 다른 위반)는 폴백 경로를 타지 않으므로 배너로 보낼 수 없고, 덮어쓰기는 그대로 남는다.

§4. 결정 D-1~D-7 (SSOT) — 엔티티 · DDL 변경 0

새 엔티티도 새 값 객체도 없다. 더해지는 것은 서블릿 응답을 한 겹 감싸는 필터 하나와, 그 필터가 내려보낸 헤더를 읽는 클라이언트 계약 하나다. 나머지는 기존 파일에서 줄을 덜어내는 일이다.

com.example.serverprovision.global.web/ ├── RequestCorrelationFilter.java (기존) └── XhrRedirectFilter.java (신규 — 필터 + 응답 래퍼 내부 클래스)

D-1 — XhrRedirectFilter : XHR 의 리다이렉트를 200 + 헤더로

@Component
@Order(Ordered.HIGHEST_PRECEDENCE + 1)          // DocumentNavigationAcceptFilter 바로 다음
public class XhrRedirectFilter extends OncePerRequestFilter {

    public static final String REDIRECT_HEADER = "X-Redirect-Location";

    doFilterInternal(req, resp, chain) {
        chain.doFilter(req, isXhr(req) ? new XhrRedirectResponse(resp) : resp);
    }

    // 래퍼 — 리다이렉트가 만들어지는 두 방식을 모두 가로챈다
    static final class XhrRedirectResponse extends HttpServletResponseWrapper {
        sendRedirect(location)            → 200 · REDIRECT_HEADER=location · 본문 없음 · flushBuffer
        sendRedirect(location, sc, clear) → 같음 (Servlet 6.1 의 3인자 변형)
        setStatus(3xx) + setHeader("Location", …) → 같음
    }
}

두 방식을 모두 덮는 이유는 Spring 이 둘 다 쓰기 때문이다. RedirectView.sendRedirect 는 보통 서블릿의 sendRedirect 를 부르지만, 핸들러에 @ResponseStatus 가 붙었거나 http10Compatible 이 꺼진 경우에는 상태 코드를 직접 설정하고 Location 헤더를 붙이는 경로를 탄다(Spring 7.0.9 바이트코드로 확인). 한쪽만 덮으면 그 경로에서 변환이 조용히 비껴간다.

적용 여부의 판정은 요청 헤더 X-Requested-With: XMLHttpRequest 하나다. 이것은 폼 가로채기가 이미 모든 제출에 실어 보내는 표식이고, BiosMetadataController 와 BmcUploadController 가 fragment 응답과 풀 페이지를 가르는 데 쓰는 것과 같은 표식이다 — 새 규약을 만들지 않고 이미 있는 SSOT 를 쓴다. 문서 이동 · curl · PXE 게스트는 이 헤더가 없으므로 래퍼조차 장착되지 않는다.

순서는 Ordered.HIGHEST_PRECEDENCE + 1 이다. 같은 자리의 DocumentNavigationAcceptFilter 가 HIGHEST_PRECEDENCE 로 요청의 Accept 를 먼저 정규화하고, 그 바로 다음에서 응답을 감싼다. 둘은 각각 요청과 응답을 건드리므로 서로 간섭하지 않는다.

현재 컨트롤러가 리다이렉트를 만드는 관례는 둘뿐이다 — redirect: 접두 49곳과 ReconciliationRestController 의 RedirectView 4곳이며, ResponseEntity 로 3xx 를 직접 만드는 곳은 없다(구현 시 재확인). 두 관례 모두 위 두 방식 중 하나를 지나므로 필터가 덮는다.

D-2 — form-submit.js : 헤더가 있으면 브라우저가 이동한다

const to = resp.headers.get('X-Redirect-Location');
if (to) {
    // 같은 화면으로 돌아오는 PRG 는 화면 내 위치를 유지한다 (탭을 모른다 — 일반 규칙)
    const keepHash = (pathname(to) === location.pathname) && !to.includes('#') ? location.hash : '';
    window.location.assign(to + keepHash);
    return;
}
if (resp.ok) { h.onSuccess(form, resp); return; }        // resp.redirected 분기 제거
… 거절 처리 (오류 모달) 그대로

resp.redirected 분기를 남기지 않는 이유는 그 조건이 더 이상 성립할 수 없기 때문이다 — XHR 요청에 3xx 가 오지 않게 되므로 fetch 가 리다이렉트를 따라갈 일이 없다. 남겨 두면 아무도 지나지 않는 죽은 분기가 되어 다음 사람이 판단을 잘못할 여지를 만든다.

확인 모달을 거치는 폼도 함께 고쳐진다. ConfirmModal.approveAndSubmit 이 결국 FormSubmit.sendAsync 를 부르고 그것이 같은 send 를 지나기 때문이다 — 모달 경로를 위한 별도 수정이 없다.

CP5 뒤 정정(F-1) — 위 초안은 이어붙인 목적지가 현재 URL 과 문자 단위로 같아지는 경우를 빠뜨렸다(탭을 한 번 누른 뒤의 같은 화면 PRG). 같은 URL 로 location.assign 을 부르면 브라우저는 프래그먼트 이동으로 처리해 재요청이 없고 flash 도 닿지 않는다. 구현은 navigateTo(target) 로 — 경로 · 쿼리가 현재와 같으면 location.reload() 로 GET 을 강제하고, 다른 화면이면 assign. report §8 참조.

D-3 — n-tab.js : 활성 탭을 hash 에 적고 hash 에서 되살린다

// 클릭 시 — 히스토리 항목을 늘리지 않는다
history.replaceState(null, '', '#' + panelId);

// DOMContentLoaded 시 — hash 가 어떤 탭과 맞으면 그 탭을 활성화
const tab = document.querySelector('.n-tab[data-panel="' + panelId + '"]');
if (tab) { aria-selected 이동 · .is-active 이동 }        // 맞지 않으면 무시 → 첫 탭

기본 켜짐이고 제외 속성은 두지 않는다 — 탭 그룹 마크업과 n-tab.js 적재는 현재 system/asset/dashboard.html 하나뿐이다(실측). 모달 안 탭 그룹처럼 화면 내 위치로 볼 수 없는 탭이 생기는 시점에 제외 속성을 추가한다 — 지금 미리 두면 지킬 대상 없는 규약만 남는다("미리 분리 금지"). 맞지 않는 hash(다른 화면에서 온 값, 손으로 고친 값)는 무시하고 첫 탭을 그린다 — 오류로 다루지 않는다.

replaceState 를 쓰는 이유는 탭 전환마다 히스토리 항목이 쌓이면 뒤로가기가 탭을 하나씩 되짚는 지루한 동작이 되기 때문이다. 현재 위치의 표기만 갱신한다.

D-4 — 마커 회수와 가드 교체

네 폼에서 data-native-submit 을 뗀다 — server-group-detail.html 의 157 · 209 · 374 행과 system/asset/dashboard.html 의 91 행이다. 떼는 순간 이 폼들은 가로채기로 돌아오고, 서버가 거절하면 HTML 오류 페이지 대신 오류 모달을 받는다.

규약 테스트에서는 예외 목록 NATIVE_FOR_FLASH 를 삭제한다. 목록이 비었으므로 핵심 가드 "재렌더(BindingResult) 핸들러 수 = data-native-submit 폼 수" 가 예외 없이 성립한다. 대신 우회가 다시 들어오는 것을 막는 가드를 하나 더한다 — data-native-submit 의 사유 문구에 flash 를 근거로 든 폼이 없어야 한다. 다음 사람이 같은 증상을 만나 같은 우회를 붙이면 그 자리에서 빨간불이 뜨고, 이 슬라이스가 왜 있었는지를 되짚게 된다.

§7. 예외 계층 — 신규 0

신규 예외 클래스가 없으므로 .claude/domain-conventions/new-exception.md 의 관문은 열지 않는다. 세 지점 모두 예외를 만들지도 삼키지도 않는다.

  • 필터 — XhrRedirectFilter 와 그 래퍼는 상태 코드와 헤더만 바꾼다. 판단이 필요한 자리가 없고 실패할 여지도 없어 던지는 예외가 없다. 요청이 XHR 이 아니면 래퍼조차 장착하지 않는다.
  • 거절 경로 — 409 · 400 의 매핑은 기존 advice 그대로다. 달라지는 것은 그 응답을 누가 받느냐이며, 마커를 회수한 네 폼이 문서 이동 대신 가로채기로 돌아오면서 HTML 오류 페이지가 아니라 오류 모달을 받게 된다. advice 자체는 손대지 않는다.
  • Accept 협상 — DocumentNavigationAcceptFilter 가 문서 이동의 Accept 를 text/html 로 좁히는 규칙은 그대로다. XHR 은 그 필터의 대상이 아니므로 지금처럼 JSON advice 를 받는다.
예외 계층이 그대로라는 사실은 이 정정이 전달 경로만 손댄다는 것을 뒤에서 확인해 준다. 도메인 판정이 바뀌었다면 여기에 무언가 적혔어야 한다.
§8. 예상 부산물 · 주의 · 잔존

8-1. 잔존 — 필터가 덮지 못하는 3xx

리다이렉트를 만드는 관례는 현재 redirect: 접두(49곳)와 RedirectView(4곳) 둘이고 ResponseEntity 로 3xx 를 직접 만드는 곳은 없다. D-1 의 래퍼는 이 둘이 지나가는 두 방식 (sendRedirect · setStatus(3xx) + Location)을 모두 덮는다. 다만 앞으로 그 어느 쪽도 아닌 방식으로 3xx 를 내는 컨트롤러가 생기면 변환이 비껴간다.

이에 대해 규약 테스트에 "컨트롤러가 정해진 방식 외로 3xx 를 내지 않는다" 가드를 두는 안이 있다. 구현 시 결정한다 — 지금은 위반 사례가 0 이라 가드가 지킬 대상이 없고, 필요 이상으로 스캔 규칙을 늘리면 규약 테스트의 초점이 흐려질 수 있기 때문이다. CP4 에서 실제 코드를 두고 판단한다.

8-2. 주의 — 마커 회수가 되돌리는 것

마커를 뗀 네 폼은 거절 응답을 오류 모달로 받게 된다. 이것은 U3-5-c DEC-E 가 flash 를 얻기 위해 포기했던 것을 되찾는 것이므로 회귀가 아니라 복구다. 다만 그 폼들의 거절 문구가 모달에서 어떻게 읽히는지는 이번에 처음 화면에 오르므로 CP5 의 B3 에서 실제로 확인한다.

8-3. 주의 — hash 가 붙는 URL

대시보드에서 탭을 누르면 주소창에 #asset-panel-TFTP 가 붙는다. 이 URL 을 공유하면 상대도 같은 탭에서 화면을 열게 되는 것이 의도된 동작이다. 반대로 탭 그룹이 없는 화면에는 hash 가 생기지 않아야 하며, 그것이 CP5 의 C2 다.

8-4. 다른 단계로 넘기는 것

  • flash 표시 위치 · 문구 표준 — S16 어휘 · 문체 표준 계열의 S16-2 로 넘긴다. 이번에는 배너가 뜨는지까지만 본다.
  • 모달 카피 — 오류 모달의 문구 정비는 S12 다.
  • 리눅스 입력 부활 · 오류 앵커 복원 — E4-L 이다. D-5 는 이미 내려온 사유를 지우지 않는 데까지이며, 사유가 원래 가야 할 필드로 정확히 가게 하는 일은 그쪽에서 다룬다.
§9. Verification — CP5 검증 항목 계획 (A 8 · B 5 · C 2)

브라우저 검증은 Opus 하위 에이전트에 위임하고, 샌드박스는 HF12 에서 세운 것을 재사용한다 (DB 3379 · 앱 7888 · HF9 빌드 jar). 에이전트는 결함을 발견해도 고치지 않고 재현 기록과 함께 보고하며, 수정 여부는 세션이 판단한다.
