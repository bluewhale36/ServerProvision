§1. 현재 상태 (진단)

E1-1/E1-2 로 진단 리눅스 부팅 체인은 완성됐다. 부팅에 쓰이는 자산 6종은 scripts/diag-image/build-assets.sh 가 조립하고(dl-cdn 다운로드 + Docker apk 저장소 빌드 + apkovl 조립), PxeAssetsConfig 의 Spring resource handler 가 /api/pxe/v1/assets/** 로 정적 서빙한다. 그런데 이 자산들은 마커 추적도, 무결성 검증도, 관리 화면도 없다 — 운영자는 부팅 인프라가 정상인지 볼 눈이 없다.

자산 / 능력있음 (E1-2 까지)비어 있음 (이 슬라이스가 채움)
6종 자산 실체pxe.assets.root 아래 파일로 존재 — ①vmlinuz-lts ②initramfs-lts ③modloop-lts ④diag.apkovl.tar.gz ⑤repo/(부분 apk 저장소) ⑥agent.sh (E1-R 포인트 3 확정)존재 여부를 화면에서 확인할 길 없음 — 자산이 빠졌는지, 서빙이 켜졌는지 서버 로그/셸로만 안다
무결성(변조 · 손상 탐지)HMAC 마커 엔진 ProvisionMarkerService + IntegrityStatus 완비 — os/bios/subprogram 자원이 이미 사용진단 자산엔 마커가 하나도 없다 — 부분 업로드·비트 손상·교체 실수를 탐지할 기준선이 없다
관리 화면 · 접근 격리—화면 자체가 없음. DEC-14 는 "교체만 가능한 시스템 자산 화면 + 접근 격리" 를 요구하나 MA 자원 도메인엔 넣지 않기로 확정(삭제·신규 생성이 제한돼야 하므로)
서빙 활성 여부PxeAssetsProperties 가 @ConditionalOnProperty("pxe.assets.root") — 미설정이면 서빙·실행기가 통째로 빠진다(HOLD)지금 서빙이 켜졌는지 화면에 안 나옴 — base-url 반쪽 설정 등은 기동 fail-fast 로만 드러난다
핵심 진단 — 부팅 인프라의 가시성이 0 이다. 이 슬라이스는 6종 자산에 "존재 · 크기 · 무결성 · 서빙 준비" 를 비추는 조회 화면을 얹고, 무결성 판정의 기준선(마커)을 확립한다. 자산을 바꾸지 않는다(교체는 E1-I-2) — 오직 본다. 기존 마커·무결성 엔진을 그대로 재사용하므로(DEC-14) 신규 엔진 코드는 없다. 물리 서버·Docker·Rocky 불요 — 파일시스템만 있으면 샌드박스에서 완전 검증된다.
§2. 요구사항 (확정) + 비목표
  1. 진단 자산 대시보드(조회) — 6종 슬롯을 고정 목록으로 표시. 슬롯당: 존재 여부 · 파일 크기 · 최종 수정 시각(mtime) · 무결성 상태 · (참고) 교체 주기(①~③ Alpine 업그레이드 / ④⑤ 구성 변경 / ⑥ 에이전트 수정). 전용 URL 네임스페이스 + 전용 nav 항목으로 격리한다.
  2. 무결성 = 기존 마커 엔진 재사용(DEC-14, 엔티티 없음) — 슬롯마다 파일 옆 .provision.json 사이드카(디렉토리인 ⑤repo/ 는 in-tree)를 두고 ProvisionMarkerService.read → verifySignature → 해시 재계산 → verifyManifestHash 로 판정. 판정 결과는 기존 IntegrityStatus(ORIGINAL/TAMPERED/SIGNATURE_INVALID/MARKER_MISSING) 재사용 + 자산 부재(ABSENT)·서빙 미구성(OFF) 상태. 새 JPA 엔티티·스캐너·reconciliation 편입은 없다 — 6 슬롯은 고정 enum 이라 DB 열거가 불필요하고, 자원 도메인이 아니다.
  3. 무결성 봉인(baseline 기록) — 현재 디스크 자산을 신뢰 기준으로 삼아 마커를 기록/갱신하는 액션. 자산 파일은 건드리지 않는다 — 오직 사이드카 마커만 쓴다(reconciliation 의 "서명 재발급" 과 동형). 봉인이 없으면 무결성은 영원히 MARKER_MISSING 이라 대시보드가 무의미하므로, 조회를 유의미하게 만드는 최소 쓰기다.
  4. 재검증(recheck) — 디스크를 다시 해시해 마커와 대조, 상태를 즉시 갱신하는 조회 액션.
  5. 서빙 준비 상태(graceful off) — pxe.assets.root/pxe.server.base-url 설정 여부를 배지로 표시. 대시보드 컨트롤러는 조건부 빈 PxeAssetsProperties 에 강결합하지 않는다(ObjectProvider/Environment) — 서빙 미구성이면 오류가 아니라 "서빙 비활성" 상태로 조용히 안내한다.
비 목표 :
  • 자산 교체(replace/upload) — E1-I-2. 이 슬라이스는 자산 파일을 바꾸는 경로가 전무하다(마커 사이드카만 쓴다).
  • PXE 인프라 구성(dhcpd/tftp) — E1-I-3(DEC-13 2단계). leases 조회·OMAPI·config 는 실 Rocky 서버(T3) 시점.
  • reconciliation 자동 스윕 편입 — 의도적 제외. pxe.assets.root 를 스캔 루트/allowed-roots 에 넣지 않는 것이 격리의 전제다(§8 주의). 진단 자산은 자체 verify 만 갖는다.
  • SystemAsset 엔티티 · MarkableScanner · 휴지통 · deprecate · soft-delete — 자원 도메인이 아니다(DEC-14). lifecycle 5분할·typed-name·nudge 전부 미적용.
  • 서명 키 회전 · 자산 빌드의 앱 내장 — build-assets.sh 가 계속 조립 주체. 앱은 결과물을 관찰·봉인만 한다.
  • 자산 서빙 주체 재판단(외부 httpd 이관) — DEC 상 "E1-I 에서 재판단" 이나, 현행 resource handler 로 대시보드가 성립하므로 이 슬라이스에선 유지. 이관은 URL 원천이 base-url 하나라 후속 설정 변경으로 족하다.
🎬 미리보기 — 무결성 대시보드 시뮬레이터 (판정표를 직접 굴린다)

아래는 대시보드 미니어처다. 각 슬롯의 디스크 상태를 바꾸고(정상 / 변조 / 삭제), 「🔒 무결성 봉인」으로 기준선을 기록한 뒤 「↻ 재검증」을 누르면 — 서버의 verify 판정이 그대로 돌아 무결성 배지가 일치 → 드리프트(변조) → 기준 미설정 사이를 오간다. 「서빙」토글을 끄면 대시보드가 오류 없이 "서빙 비활성" 으로 내려앉는 것도 확인한다.

서빙 :
진단 리눅스 자산 서빙 ● 활성
슬롯레이아웃디스크 상태무결성
드리프트 0 — 시뮬레이터의 verify() 우선순위(OFF→ABSENT→MARKER_MISSING→SIGNATURE_INVALID→TAMPERED→ORIGINAL)는 §4 서버 판정표와 1:1 이다. 봉인 = 현재 해시를 마커로 기록, 재검증 = 디스크 재해시 후 마커 대조 — 둘 다 자산 파일은 불변. "변조된 슬롯을 봉인하면 변조가 기준이 된다" 는 경고도 실제 서버 UX 문구와 같다.

§4. 도메인 모델 (SSOT)

고정 슬롯 목록 — enum DiagnosticAsset (DB 열거 불요)

// 6 슬롯은 고정이라 엔티티가 아니라 enum 이 SSOT (자원 도메인 아님 — DEC-14).
// build-assets.sh 의 산출물 파일명과 1:1 (그 스크립트가 조립 SSOT).
public enum DiagnosticAsset {
    VMLINUZ  ("vmlinuz-lts",         SIDECAR, "커널",        NETBOOT),  // ① Alpine 업그레이드 시 교체
    INITRAMFS("initramfs-lts",       SIDECAR, "초기 램디스크", NETBOOT),  // ②
    MODLOOP  ("modloop-lts",         SIDECAR, "커널 모듈",     NETBOOT),  // ③ (208MB)
    APKOVL   ("diag.apkovl.tar.gz",  SIDECAR, "설정 가방",     CONFIG),   // ④ 구성 변경 시
    REPO     ("repo",                IN_TREE, "부분 apk 저장소", CONFIG),   // ⑤ 디렉토리 → in-tree 마커
    AGENT    ("agent.sh",            SIDECAR, "진단 에이전트",  AGENT);    // ⑥ 에이전트 수정 시(가장 잦음)
    // filename, MarkerLayout layout, String label, Category category
}
// 파일명이 컴파일 상수라 사용자 입력 경로가 없다 → path traversal 표면 0. 슬롯은 경로 변수로 노출하지 않는다.

무결성 판정표 — verify (분기 아닌 우선순위 규약, 기존 IntegrityStatus 재사용)

OFF            : !servingActive                         — 서빙 미구성(대시보드는 조회 가능, 자산 위치 불명)
ABSENT         : !Files.exists(path)                     — 자산 파일 없음(빌드 미수행/유실) — 예외 아님, 상태
MARKER_MISSING : 마커 사이드카 없음                        — 기준선 미설정 → [무결성 봉인] 유도
SIGNATURE_INVALID : !verifySignature(marker)             — 마커 자체 변조/키 불일치
TAMPERED       : !verifyManifestHash(marker, 재계산 해시)   — 자산 바이트가 봉인 이후 바뀜(손상·교체 실수)
ORIGINAL       : 그 외                                    — 봉인 기준과 일치(정상)
// 해시: 단일 파일 = SHA-256(IsoRegistrationService.computeFileSha256 선례),
//       디렉토리(repo) = 정렬된 멤버 해시 manifest(기존 무결성 엔진의 in-tree 해시 재사용).
// 뷰 배지: management/common/view/IntegrityStatusView.badgeClass 재사용 + ABSENT/OFF 는 gray.

마커 조립 — MarkerContent (엔티티 없이 엔진 직접 호출)

// ProvisionMarkerService 는 Markable 엔티티 없이 임의 경로에 write/read/verify 가능 — 이게 재사용의 핵심.
// resourceType 은 String 필드라 ResourceType enum 을 건드리지 않는다(스캐너 계약 오염 회피).
new MarkerContent(
    /*resourceType*/ "DIAGNOSTIC_ASSET",     // 자유 문자열 — reconciliation 스윕 대상 아님
    /*resourceId*/   (long) slot.ordinal(),  // 고정 슬롯 식별(0~5) — DB PK 아님
    /*attributes*/   Map.of("filename", slot.filename(), "alpineBranch", "v3.22"),
    /*createdAt*/    Instant.now(),
    /*manifestHash*/ recompute(path, slot.layout()),
    /*signature*/    null)                    // computeSignature 후 withSignature 로 채움(2-phase 아님 — PK 불요)
// write(path, SIDECAR|IN_TREE, signed) → .provision.json 사이드카 / repo/.provision.json 인트리.

설계 결정 비교 — 3개 축 (§8 Open Questions 의 근거)

(축1) 엔티티 없음 — 채택

  • 엔진(ProvisionMarkerService)만 재사용, 6 슬롯은 enum
  • DDL·Repository·Entity(6·7·9단계) N/A
  • DEC-14 "자원 도메인 아님" 정합 — 휴지통/deprecate/스캐너 불요

(축1 대안) SystemAsset 엔티티 + 스캐너 — 탈락

  • read 슬라이스에 엔티티+5서비스+스캐너 과잉
  • reconciliation 의 trash/ghost/path-drift 가 고정 슬롯엔 무의미

(축2) 봉인은 앱 — 채택

  • canonical JSON 직렬화를 앱이 소유(키 정렬 등)
  • 셸에서 HMAC 재현은 취약 + build 호스트에 마커 비밀 노출

(축2 대안) build-assets.sh 가 마커 기록 — 탈락

  • 무결성이 셸에 결합 + 재현 취약

(축3) 서빙 미구성 = graceful off — 채택

  • 대시보드는 항상 조회 가능(ObjectProvider)
  • fail-fast 는 서빙 실행 경로의 몫(현행 유지)

(축3 대안) 조건부 빈 강결합 — 탈락

  • 미설정 환경에서 컨트롤러 자체가 빠져 화면 부재

§8. 예상 부산물 / 주의 / 결정 사항

잔존 책임 · 주의 (정직 기록)

  • reconciliation 스윕 제외가 격리의 전제 — PathReconciliationService 는 스캔 루트 아래 *.provision.json 을 훑어 DB 자원과 대조한다. pxe.assets.root 를 스캔 루트/allowed-roots/DB 경로에 넣으면 진단 자산 마커가 ORPHAN 오탐으로 뜬다. 넣지 않는 것이 격리(자체 verify 만)의 조건 — CP2 배선 시 확인.
  • 봉인은 "현재를 신뢰" — 이미 오염된 자산을 봉인하면 오염이 기준선이 된다. 봉인 버튼에 확인 문구("현재 디스크 상태를 신뢰 기준으로 기록합니다") 필수. 최초 봉인 전이라면 build-assets.sh 직후(신선한 상태)에 봉인하는 것이 정석 — 운영 안내에 명기.
  • 디렉토리(repo) 무결성은 멤버 목록·바이트 기준 — 부분 apk 저장소의 빌드 재현성(서명 키·arch 일치)은 build-assets.sh 소관이지 이 화면이 보증하지 않는다. 대시보드는 "봉인 이후 바뀌었나" 만 답한다.
  • 패키지 배치 = feature-first execution.asset — 자산은 execution 도메인(pxe.assets.root·PxeAssetsProperties)의 것이라 코드는 execution/asset/. URL 네임스페이스(/system/**)는 nav 그룹 목적의 UI 관심사로 분리(패키지≠URL 은 정상).
  • size/mtime 은 조회 시점 스냅샷 — 실시간 스트림 아님. 대량 파일(modloop 208MB)의 해시 재계산은 재검증/봉인에서만 수행(대시보드 조회는 존재·크기·마커 대조까지, deep 해시는 명시 액션) — 조회가 208MB 재해시로 느려지지 않게 CP4 에서 얕은/깊은 검증 분리 확정.
