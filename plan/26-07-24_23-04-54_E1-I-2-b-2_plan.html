§1. 현재 상태 (진단)

진단 리눅스 자산 관리는 조회에서 교체, 다시 버전 보존까지 네 슬라이스로 쌓여 왔다. 이번 b-2 는 그중 마지막으로 남은 소비 화면을 붙인다.

선행 슬라이스상태남긴 능력 / seam
E1-I-1 자산 현황·무결성 대시보드완료슬롯 6종 조회 + 무결성 봉인 + 재검증. DB 없는 entity-free 대시보드(loadDashboard())
E1-I-2-a 단일 파일 교체완료업로드 → 원자적 스왑(ATOMIC_MOVE) → 자동 재봉인. 스왑 로직이 DiagnosticAssetReplaceService.replace 안에 상주
E1-I-2-b-1 범용 버전 저장소완료도메인 무관 AssetHistoryService(archive / list / openVersion / prune) + asset_version 테이블 + AssetVersionKey + retention property. 교체가 스왑 앞에서 archive 호출

지금 갖춰진 것 vs 비어 있는 것

능력백엔드(b-1)화면 노출
슬롯별 버전 목록 조회 list(key)있음없음
버전 바이트 경로 열기 openVersion(key,id)있음없음
보존 상한 FIFO 정리 prune(key)있음없음(값 고정)
되돌린 버전 활성화(스왑·재봉인)없음없음
핵심 진단 — b-1 이 버전 저장소를 완성했지만 그 능력을 소비하는 화면이 없다. 이력을 볼 수도, 특정 버전으로 되돌릴 수도, 보존 개수를 조정할 수도 없어 list/openVersion/prune 이 죽은 능력으로 남아 있다. 또 b-1 은 저장소까지만이라 "되돌린 버전을 실제로 활성화(스왑·재봉인)하는 배선"은 아직 어디에도 없다. b-2 가 이 둘(소비 화면 + 활성화 배선)을 이어 슬라이스를 닫는다.
§2. 요구사항 (확정) + 비목표
  1. 슬롯별 버전 목록 — 교체 대상 4슬롯(VMLINUZ · INITRAMFS · MODLOOP · AGENT)의 각 대시보드 행에 버전 이력을 <details> 로 접어 표시한다. 비대상 조립 자산(APKOVL · REPO)은 이력·롤백을 노출하지 않는다.
  2. 버전 행 표시 — 각 버전은 아카이브 시각, 크기, 짧은 sha, 현재 활성본과 동일한지 플래그, 롤백 버튼을 갖는다. 목록은 최신 순(OrderByIdDesc).
  3. 롤백 시맨틱 = 선택 버전 승격(제거) — 롤백은 현재 활성본을 이력에 archive 하고, 고른 버전을 활성화한 뒤, 그 버전을 이력에서 제거한다(D2 3A). 결과 불변식 = "이력 = 현재 활성본이 아닌, 되돌릴 수 있는 과거 버전들".
  4. 롤백 = 교체와 동일 활성화 코어 — 원자적 스왑 + 재봉인은 교체와 한 코어(activate)로 통일한다. 소스만 업로드 스트림 ↔ 버전 파일 스트림으로 다르다(D1 · D5).
  5. 보존 개수 설정 화면 — 대시보드 상단 인라인 폼으로 자산별 보존 버전 상한을 조정한다(retention_count ≥ 1, PRG). prune 이 읽는 실효값 소스를 이 설정으로 둔다.
  6. 서빙 비활성 UI 1차 차단 — 자산 서빙이 꺼져 있으면 롤백·교체 버튼을 disabled + tooltip 으로 막는다. 이 차단 조건은 서버 가드 requireServingRoot()(409)와 단일 SSOT 로 같은 판정을 공유한다.
  7. 파괴적 확인 없음 — 롤백은 현재 활성본을 archive 하므로 가역이다. native confirm() 은 쓰지 않고(E1-I-1 에서 테스트로 금지 확인) 버튼 title 경고로 안내한다.
비 목표 :
  • dhcpd.conf · tftp 등 PXE 인프라 자산 롤백 — E1-I-3. 저장소(AssetHistoryService)는 이미 도메인 무관이라 그대로 재사용하고, 활성화 코어는 E1-I-3 이 끝난 뒤 별도 리팩토링에서 SPI 로 추출·공유한다.
  • 시간 기반 TTL 정리 — 이번은 개수 기반 FIFO 만. 시간 만료 정리는 도입하지 않는다.
  • 활성화 로직의 SPI 일반화 — 이번 활성화 코어는 진단 자산 특화다. SPI 추출은 E1-I-3 그 시점이 아니라, dhcpd/tftp 자산이 실재하는 E1-I-3 이 끝난 뒤 단계 신설 없는 리팩토링(R* 계열)으로 미룬다(§8 잔존).
  • 게스트 실시간 반영 — 롤백은 자산 파일만 되돌린다. 부팅 중인 게스트로의 반영은 다음 부팅 사이클에서 일어난다.

§4. 도메인 모델 (SSOT)

활성화 단일 서비스 — DiagnosticAssetActivationService (신규, DiagnosticAssetReplaceService 흡수)

// 교체·롤백이 공유하는 원자적 스왑 + 재봉인 SSOT. 소스는 InputStream 하나로 추상화(D5).
// public 트리거 2개(replace=업로드 / rollback=버전 저장본) + private 공용 코어 activate 1개.
void replace(DiagnosticAsset slot, MultipartFile file):    // (DiagnosticAssetReplaceService 에서 이관)
    root = integrityService.requireServingRoot()    // 비활성 → 409
    if (!slot.replaceable()) throw NotReplaceable    // 비대상 → 409
    activate(slot, root, file.getInputStream())     // 소스 = 업로드 스트림

void rollback(DiagnosticAsset slot, Long versionId):
    root = integrityService.requireServingRoot()    // 비활성 → 409
    if (!slot.replaceable()) throw NotReplaceable    // 비대상 → 409
    key = new AssetVersionKey("DIAGNOSTIC", slot.filename())
    Path versionFile = historyService.openVersion(key, versionId)  // 없음/타키 → 404 (forging 차단)
    activate(slot, root, Files.newInputStream(versionFile))        // 소스 = 버전 저장본 → 승격
    historyService.remove(key, versionId)           // 제거(멱등)

private void activate(DiagnosticAsset slot, Path root, InputStream source):
    temp = root.resolve(slot.filename()+".activate-"+uuid+".tmp")
    Files.copy(source → temp)                       // ① 바이트 먼저 실체화
    archive(new AssetVersionKey("DIAGNOSTIC", slot.filename()), target)  // ② 현재본 보관(실패 시 스왑 전 중단)
    Files.move(temp → target, ATOMIC_MOVE, REPLACE_EXISTING)             // ③ 원자적 교체
    fileSystemHardener.applyDefaultPermissionsForFile(target)            // ④ 0644
    integrityService.sealOne(slot, root)                                 // ⑤ 재봉인

Primitive Obsession 점검 — 도메인 의미값은 이미 타입화돼 있다: 슬롯 식별 = DiagnosticAsset enum, 버전 키 = AssetVersionKey record, 마커 배치 = MarkerLayout enum, 버전 식별 = Long PK. retentionCount 는 도메인 의미값이 아닌 순수 수량이라 TrashSettings.ttlDays 선례대로 int + @Min(1) 로 둔다(VO 미도입). sha·size·경로는 뷰 표시 문자열로만 노출한다.

§7. 예외 계층

§8. 예상 부산물 / 주의 / 결정 사항

설계 결정 (채택 · 비채택 대안 · 탈락 사유)

D1 · 활성화 단일 서비스 통합 (replace · rollback · private activate)
채택 하나의 DiagnosticAssetActivationService 가 replace(slot, MultipartFile file)(트리거 소스=업로드) · rollback(slot, Long versionId)(트리거 소스=openVersion 저장본 + remove) · private activate(slot, root, InputStream source)(공용 코어: 현재본 archive → temp 완성 → ATOMIC_MOVE → 권한 0644 → sealOne)를 모두 보유한다. 기존 DiagnosticAssetReplaceService 는 이 서비스로 흡수되어 사라진다(그 책임·의존이 여기로 이관, 기존 9개 테스트는 대상 클래스만 새 서비스로 재지정).
탈락 ⓐ 롤백이 스왑 로직을 복붙 — 중복 금지(불가침) 위반.
탈락 ⓑ replace 와 활성화를 두 서비스로 분리(직전 초안) — "왜 롤백은 activation 인데 replace 는 아닌가"라는 임의적 경계가 생기고, replace·rollback 이 사실 둘 다 "슬롯에 새 버전을 활성화"하는 트리거(소스만 다름)라는 본질이 흐려진다. 하나로 모으면 이 서비스 자체가 E1-I-3 이후 SPI 구현체로 승격되는 깔끔한 경계가 된다.

D2 · 롤백 시맨틱 = 선택 버전 승격(제거)
채택 3A openVersion(X) → activate(X 바이트) → remove(key, X). 현재 활성본을 archive 하고 X 를 활성화한 뒤 X 를 이력에서 제거한다. 롤백을 반복하면 직전 활성본이 이력에 들어오고 방금 되살린 버전은 빠져 핑퐁이 정합.
탈락 3B X 를 남기고 순수 교체처럼 취급 — 현재 바이트와 동일한 이력 항목이 목록에 중복 노출되고, 다음 교체가 그것을 또 복제해 누적된다. 프로젝트 핵심 동기(명확한 사용성)에 반한다.

순서 안전성 — activate 가 source 를 temp 로 먼저 실체화하므로, ②의 archive→prune 이 하필 롤백 소스(같은 계열의 오래된 버전 파일)를 지우더라도 temp 에 바이트가 이미 있어 안전하다. remove(key,X) 는 멱등(prune 이 먼저 지웠으면 no-op).

D3 · 버전 목록 노출 = 컨트롤러 합성 + <details>
채택 loadDashboard()(무결성, entity-free)는 그대로 두고, 컨트롤러가 별도로 versionsBySlot 를 Model 에 담는다. 뷰는 교체 셀에 <details> 로 버전 목록을 접어 표시(trash/settings.html 의 <details> 관례 재사용)하고 각 행에 롤백 버튼.
탈락 ⓐ loadDashboard 에 이력을 결합 — E1-I-1 이 의도적으로 세운 entity-free 대시보드 원칙(DB 안 읽음)을 깬다.
탈락 ⓑ 별도 /versions 페이지 — 무결성·버전·롤백 문맥이 갈린다.
탈락 ⓒ XHR 프래그먼트 — 불필요한 JS, 프로젝트는 SSR 우선.

D4 · 보존 개수 설정 = 경량 DB 백업 인라인 폼
채택 4D (권장) 단일행 AssetHistorySettings(retentionCount) — TrashSettings 의 singleton + defaults() 시드 + @PostConstruct 캐시 패턴만 축소 미러(필드 1개) + 리포지토리 + 축소 서비스. AssetHistoryProperties.getRetentionCount() 는 시드 기본값으로만 남기고, prune 이 읽는 실효값 소스는 이 설정 서비스로 교체. 화면은 대시보드 상단 인라인 폼(POST /settings, PRG). 이력 루트(root)는 web-served 아닌 파일시스템 위치라 @Value 유지(튜닝 대상 아님).
대안 4C trash/settings 전체 미러(별도 설정 페이지 = 엔티티+리포+서비스+컨트롤러+뷰+DTO 2+validator ≈ 8~10 파일) — 단일 필드에 과중.
대안 4B property 유지·화면 없음(가장 단순, 신규 엔티티/DDL 0) — 단, Notion 승인 scope 가 '보존 개수 설정 화면'을 명시하므로 4B 는 그 scope 미충족. 사용자가 단순화를 택하면 축소 가능(Q1).

D5 · 스왑 소스 추상화 (D1 귀결)
채택 activate(slot, root, InputStream source) 하나로 업로드 교체(file.getInputStream())와 롤백(Files.newInputStream(openVersion(X)))을 통일. 원자적 스왑·재봉인·fail-closed 규율이 두 경로에 한 번만 존재한다.

D6 · 예외·동시성·UI 1차 차단
채택 신규 예외 0(재사용). 서빙 비활성 중 롤백은 UI disabled+tooltip 으로 차단하고 requireServingRoot 서버 가드와 동일 조건을 단일 SSOT 로 공유. 롤백은 현재 활성본을 archive 하므로 가역 — native confirm() 대신 버튼 title 경고.

D7 · remove(key, versionId) 추가 (D2 귀결)
채택 AssetHistoryService 에 멱등 remove 추가(이미 없으면 no-op, 이력 파일+행 삭제). 롤백 승격에서 되살린 버전을 이력에서 뺀다.
