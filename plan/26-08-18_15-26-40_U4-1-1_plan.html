§0. 재설계 동기 — 이 문서가 v2 인 이유
개정 이력 — v1(26-08-18_00-40-07)은 CP1 승인 후 CP2~CP6 까지 진행했고, CP6 검수에서 사용자가 배치 개정을 지시했다. 이 v2 는 그 지시를 반영한 계획서이며 v1 문서 · v1 report 는 이력으로 그대로 둔다.

무엇이 바뀌었나. v1 은 디스크 묶음 규칙과 RAID 카드를 OS 설치 단계(OSInstallationRequest 베이스) 안의 한 절로 두었다(v1 D1). CP6 검수에서 사용자가 지시했다 — “RAID 구성을 OS 설치에 같이 넣지 말고 BIOS 설정 이후의 항목으로 별도로 분리시킬 것.” 이어 실행 phase 는 (b) ProvisioningPhase.RAID_CONFIGURATION 과 ProvisioningPhaseStep.RAID_CONFIGURATION 신설을 택했고, 자리는 “FIRMWARE_SETTING 또는 BMC_SETTING 다음이자 OS_INSTALLING 전” 으로 정했다.

v1 이 그 대안을 탈락시킨 사유와 그 정정. v1 D1 은 “새 단계 타입은 phase 골격(SettingProcessPhaseMapper)에 영향” 을 탈락 사유로 적었다. 실측하니 그 판단은 정확하지 않았다 — 매핑 표는 경계 클래스 한 줄로 격리돼 있고 그러라고 만든 클래스다. 진짜 비용은 DB 에 있었다. process_type · current_phase · step_code 가 MariaDB ENUM 컬럼이라 상수 추가가 곧 DDL 이다. E1-1 이 step_code 에서 같은 것을 겪었다 — 확장을 빠뜨리면 저장 시점에 “Data truncated” 로 500 이 난다. 그래서 v1 의 “DDL 없음”(v1 D11)은 v2 에서 DDL 있음으로 바뀐다.

v1 산출의 처리와 재진입. v1 의 CP2~CP4 구현(요청 계약 · 값 규칙 · 화면 · 테스트 34 건) · CP5 19 항목(결함 F1 수정 후 재검증) · CP6 report(report/26-08-18_14-47-50_U4-1-1_report.html)는 v1 의 산출로 남긴다. 값 규칙 · record · enum · 옵션 응답 · 카드 참조 검사 · 폼 진리표 · 화면 조각은 그대로 새 단계 카드로 옮겨 재사용하며, 바뀌는 것은 “어느 단계에 사는가” 와 그 배선이다. 진행은 이 v2 로 CP1 을 다시 받고 → CP2~CP4 무중단 재구현 → CP4 중간 승인 → 테스트 → CP5 전면 재실시 → CP6 report v2 순이다.

§1. 현재 상태 (진단)

이 슬라이스는 세팅 정의서에 ‘RAID 구성’ 이라는 단계를 새로 만들고, 그 안에 “어떤 디스크를 어떤 RAID 로 묶는가”(디스크 묶음 규칙)와 “어떤 RAID 카드를 전제하는가”를 적을 수 있게 한다. 단계의 자리는 BIOS 설정 다음 · OS 설치 전이고, 실제로 RAID 를 거는 집행은 E 영역에 남는다. 입력은 U4-1 토론 8 회차의 결정(D1~D9 · E1~E35), RAID 카드 자원을 등록하는 MA7(PR #39 병합)이 넘긴 계약, 그리고 v1 CP6 검수에서 사용자가 내린 배치 결정이다. 아래는 착수 전에 코드와 DB 에서 확인한 사실이다.

payload 가 JSON 이라 단계 내부의 필드를 더하는 데는 테이블 변경이 없다. 단계 타입 자체는 사정이 다르다 — 타입 이름과 phase 이름이 ENUM 컬럼의 값으로 들어가기 때문이다. 반면 provisioning_progress.failed_step_code 는 E1-0a 에서 VARCHAR(25) 가 되었고 assigned_process.owned_phases 는 안정 코드 CSV 를 담는 VARCHAR(128) 이라 둘 다 손댈 것이 없다. 다만 ddl/ 의 U2-3 · U3-1 파일은 이 컬럼들을 VARCHAR(32) 로 적고 있어 실제 DB 와 어긋날 수 있어, DDL 은 각 문 앞에서 SHOW CREATE TABLE 로 실제 타입을 먼저 보게 만든다(§4 4-7).

단계 타입을 하나 더할 때 손이 닿는 자리는 다섯 곳뿐이다. SettingProcessType 의 선언 순서가 요약 배지 · 폼 카드 · 상세 카드의 표시 순서이고, ProcessRequestDeserializer.FLAT_SUBTYPES 가 판별자에서 요청 클래스로 가는 맵, ProcessReferenceInspectors 가 target() 으로 검사기를 고른다. SettingProcessPhaseMapper 는 타입에서 phase 로 1:1 대응하고 누락되면 IllegalStateException 을 던져 커버리지 테스트가 그것을 못박으며, OwnedPhasesConverter 가 phase 를 안정 코드(FW_UPDATE · FW_SETTING · OS_INSTALL · OS_SETTING)로 바꿔 CSV 로 저장한다. OwnedPhases 는 BOOTSTRAPPING · DIAGNOSE_LINUX · TESTING 을 제외하는 방식이라 새 phase 가 자동으로 허용된다. 실행 쪽도 안전하다 — ProvisioningPhase 는 선언 순서가 곧 전진 순서(PhaseSequence.nextAfter)이고, BootScriptDispatcher 는 PhaseExecutorRegistry.find 가 비면 여섯 줄짜리 경로로 HOLD 를 돌려준다. 오늘 FIRMWARE_UPDATING 이 그 상태다.

정의서 쪽 나머지 재료는 v1 진단 그대로다. 선택지 응답은 비활성 자원을 렌더에서 빼고 deprecated 는 배지 메타와 함께 남기며, 상세는 못 찾은 id 를 #id 로 폴백한다. MA7 은 판정을 이미 넘겼다 — SupportedRaidLevels.blockReasonFor 가 화면 안내이자 거절 사유가 되는 문구를, RaidLevel.minimumDisks(cardHasCache) 가 캐시 보유 카드에서 RAID0 만 1 로 낮아지는 최소 디스크 수를 돌려준다. 카드 참조는 소프트참조라 “참조한 카드가 사라진 상태” 를 보이게 하는 일이 이 슬라이스로 남는다. 할당 판정에는 디스크 축의 자리가 AssignmentEligibility 의 javadoc 으로 예고돼 있으나 대조할 재료가 없다 — lspci 가 옵션 없이 불려 Subsystem ID 가 없으니 모델 대조가 불가능하고, CRA3338 이 ETC 로 분류돼 존재 대조마저 오판한다.

진단 결론 — 정의서 쪽의 표현 · 검증 · 화면은 선례가 전부 있고 단계 타입과 phase 를 더하는 비용도 코드에서는 작다. 비용이 실제로 있는 곳은 DB 의 ENUM 컬럼 네 개다. 없는 것은 여전히 “서버의 실제 카드와 대조할 재료” 하나이므로, 이 슬라이스는 표현까지 하고 대조는 E 계열 뒤로 보낸다(§8 D8).

묶음 하나는 다섯 축의 조합 {RAID 레벨, 디스크 종류, 전송 방식, 용량, 개수} 이고, 레벨을 비우면(‘RAID 없음’) RAID 를 구성하지 않고 디스크를 그대로 쓴다. 이 목록은 볼륨이 아니라 규칙의 목록이라 맞는 조합이 여럿이면 전부에 적용된다 — 저장까지가 이 슬라이스이고 실제 디스크와 맞춰 보는 일은 E 가 한다. 카드는 MA7 자원을 id 로 참조하며 지정(SPECIFIED)만 받고, R8 대로 폼은 관례를 미리 채우지 않는다(빈 목록이면 설치기의 자동 선택).

R9 가 v1 과 갈라지는 지점이다. RAID 구성은 OS 설치 단계 안의 절이 아니라 스스로 하나의 단계이므로 OS 설치와의 결합 규칙을 두지 않는다 — RAID 구성만 있는 정의서도, OS 설치만 있는 정의서도 유효하고, 같은 타입을 두 번 넣지 못하는 것은 기존 isProcessTypeUnique 가 이미 막는다. R10 의 phase 는 FIRMWARE_SETTING 다음, phase step 은 BMC_SETTING 다음이며 둘 다 OS_INSTALLING 앞이다. 실행기는 만들지 않으므로 게스트는 그 phase 에서 HOLD 하고, 소유 phase 의 안정 코드는 RAID_CONFIG 다. v1 스모크로 샌드박스에만 남은 “OS 설치 안의 raidCardId · diskGroups” 저장본은 샌드박스 리셋으로 정리한다 — 실 DB 에는 없다.

4-2. 값 규칙 DiskGroupRules (static · 의존 0 — v1 에서 그대로 가져온다)

validate(List<DiskGroupRuleRequest> rules, RaidCard card /* nullable */) 가 다섯 가지를 본다.

  1. RAID 를 구성하는 규칙에서 card.getSupportedRaidLevels().blockReasonFor(level) 가 사유를 돌려주면 → unsupportedLevel(i, reason)
  2. RAID 를 구성하는 규칙에서 count.value < level.minimumDisks(card.hasCache()) → tooFewDisks(i, level, min, given)
  3. RAID 없음 규칙에서 count.value < 1 → singleDiskCountBelowOne(i)
  4. 다섯 축이 모두 같은 규칙이 둘 → duplicateRule(i, j)
  5. 용량이 SPECIFIED 인데 size < 1 → invalidCapacity(i)

3 번은 record 의 @Min(1) 이 1 차로 걸러내므로 안전망이다. 카드가 null 인데 RAID 규칙이 있는 상황은 @AssertTrue 가 먼저 400 으로 끊어 오지 않으며, 그래도 오면 1 번을 건너뛴다.

4-3. 참조 검사 — 검사기를 새 단계로 옮긴다

RaidConfigurationReferenceInspector implements ProcessReferenceInspector 를 service/reference/ 에 새로 만들고 target() 이 RAID_CONFIGURATION 을 돌려주게 한다. v1 이 OSInstallationReferenceInspector 에 넣었던 카드 코드는 원복한다.

  • 카드 id 가 null 이면 저장소를 부르지 않고 규칙만 본다 — DiskGroupRules.validate(rules, null)
  • 카드 id 가 있으면 findByIdAndIsDeletedFalse 로 찾고, 없으면 RaidCardNotFoundException(404)
  • !isEnabled 면 DisabledResourceReferenceException("raidCardId", …)(409)
  • 통과한 카드로 DiskGroupRules.validate(rules, card)
  • describeDeprecatedReferences 는 deprecated 카드명을 서술한다 — ISO 관례대로 저장은 허용하고 상세에서 경고한다
  • referencedResources 는 빈 목록이다 — RAID 카드는 디스크 파일이 없는 메타 자원이라 드리프트 추적 대상이 아니다

OS 설치 카드에서는 그 표기를 제거한다. 요약 배지는 enum 선언 순을 따라 제자리에 뜨고 두 miller 피커는 이 fragment 를 공유하므로 자동 반영된다.

D1 — 위치(개정). 디스크 묶음 규칙과 RAID 카드는 독립 단계 타입 RAID_CONFIGURATION 에 담고 자리는 BIOS 설정 다음 · OS 설치 전이다. v1 이 채택한 “OS 설치 베이스” 는 사용자 지시로 폐기했다 — 이렇게 두면 현장 순서(펌웨어 → BIOS 설정 → RAID → OS 설치)와 화면 단계가 1:1 로 맞고 RAID 만 잡는 정의서나 OS 설치만 하는 정의서가 억지 없이 표현된다. 중간층(LinuxInstallationRequest)안은 v1 때와 같은 이유로 탈락한다 — RAID 는 OS 가 올라오기 전에 카드가 하는 일이라 계열에 매달 근거가 없다.

D13 — 실행 phase(신설). 정의서 단계가 갈라졌으니 실행 phase 도 가른다는 사용자 결정 (b) 다. 탈락한 (a) 는 새 단계를 OS_INSTALLING 에 매핑하는 안으로, 정의서는 갈라졌는데 실행 원장에서는 하나로 뭉쳐 보이는 비대칭이 남는다. 실행기는 만들지 않으므로 그 phase 에서 HOLD 하며 이는 오늘 FIRMWARE_UPDATING 이 놓인 상태와 같다. 안정 코드는 RAID_CONFIG 다.

D11 — 스키마(개정). v1 의 “payload 가 JSON 이므로 DDL 없음” 은 단계 내부 필드에는 맞지만 단계 타입 자체에는 맞지 않는다 — 타입 이름과 phase 이름이 ENUM 컬럼의 값이기 때문이다. ddl/U4-1-1_raid_configuration.sql 로 네 문을 산출하고 각 문 앞에서 실제 타입을 대조하게 하며, 실 DB 적용은 ALTER 권한을 가진 사용자가 한다.

D14 · D15 — 단계 사이의 관계. 두 단계는 서로를 전제하지 않으므로 함께 넣도록 요구하지 않고, 같은 타입이 두 번 들어가지 못하는 것만 기존 규칙이 막는다. 화면의 순서는 어디에도 따로 적지 않는다 — SettingProcessType 의 선언 순서 하나가 폼 카드 배치 · 요약 배지 순 · 상세 카드 순을 모두 정한다. 순서를 화면마다 적으면 세 곳이 갈라질 여지가 생기므로 SSOT 를 코드 한 곳에 둔다.

D2 — 표현. 이름은 ‘RAID 묶음’ 이 아니라 ‘디스크 묶음’ 이다 — 레벨이 없는 규칙도 같은 목록에 담긴다. RaidLevelSelection(mode, level) 래퍼를 만들지 않은 것은 표현할 의도가 ‘없음’ 하나뿐이라 BoardModelSelectionRequest 가 피하려던 AUTO · SPECIFIED 모호성이 이 축에는 없기 때문이다. 용량 단위는 SizeUnit(이진 GiB) 재사용 대신 DiskCapacityUnit(십진 GB · TB)을 신설한다 — 같은 이름의 다른 것을 한 enum 에 두면 표시가 어긋난다. 480GB SSD 가 lsblk 에서 447G 로 보이는 허용 오차는 매칭(E)의 문제다.

D3 · D4 — 카드 참조와 요구 방향. Long raidCardId 소프트참조 · 지정만 받는다. 지금 RaidCardSelectionRequest(mode, id) 를 도입하면 계약이 AUTO 를 광고하면서 서버가 400 으로 거절하는 동작하지 않는 계약이 되고, 나중에 AUTO 를 열 때 raidCardMode 를 null-coalesce 로 덧붙이면 payload 마이그레이션이 없다. 이름은 저장하지 않고 references.raidCards 로 해석하되 참조 검사가 없는 자원이라 “(사라진 카드 #id)” 로 명시한다(U3-5-d 어법). 요구는 “RAID 규칙이 있으면 카드가 있어야 한다” 한 방향만 강제한다 — iff 로 묶으면 카드-먼저 폼에서 규칙을 적기 전부터 위반 상태가 되어 마찰이 생긴다.

D5 · D6 — 규칙과 참조 검사의 자리. 값 규칙은 static DiskGroupRules 로 LinuxPartitionRules 옆에 두고 카드 엔티티를 인자로 받아 의존 0 을 지킨다. 참조 검사는 ISO 가 쓰는 형태 그대로(404 · 409 · deprecated 경고)이되, v2 에서는 그것이 새 단계 전용 검사기에 산다.

D7 · D16 — 폼 UX 는 카드 먼저, 중복은 입력 중에 막는다. 순서는 [카드 select] → [묶음 표] 이고, <option> 의 hover tooltip 이 브라우저마다 달라 사유는 option 의 title 과 select 아래 n-hint 줄에 함께 보인다. 반대 순서를 택하지 않은 것은 규칙이 전제하는 것이 카드가 만들 수 있는 레벨이라 물리적 인과와 순서가 뒤집히고, 나중에 카드를 고를 때 충돌 처리 지점이 늘기 때문이다. 진리표의 마지막 줄은 v1 CP5 의 결함 F1 을 고친 결과다 — 중복을 서버 400 에만 맡기지 않고 입력 중에 행을 강조하고 제출을 막는다.

D8 — 할당 시점 대조는 이번에도 하지 않는다. 토론 E28 은 “보드와 같은 규칙에 축을 더하되 표식만” 을 예고했으나 R-13 · E33 이후 사정이 갈렸다. 모델 대조는 Subsystem ID 가 없어 불가능하고, 존재 대조는 kindOf 가 CRA3338 을 ETC 로 분류해 주력 카드를 쓰는 서버를 오차단하거나 상시 표식이 된다 — 둘 다 잘못된 신호다. lspci -nn 과 파서 보강(E 계열) 뒤 RequiredRaidCard 축과 AssignmentBlockKind 상수를 더하며, 그때 기존 골격을 그대로 쓸 수 있음은 실측으로 확인했다.

D9 · D10 · D12. 옵션 조회는 setting 에서 management.raidcard 로 향하는 단방향이고(boards 선례) 차단 문구는 서버가 채워 보낸다. 상세와 두 피커는 fragment 를 공유하므로 피커 쪽 코드가 0 이다. RAID 없음 규칙의 count 는 RAID 규칙과 같은 뜻 — 묶음 하나에 들어가는 디스크 수(매칭 단위)이며 조건에 맞는 묶음을 만들 수 있는 만큼 만든다(E19). 레벨이 없다는 것은 RAID 로 묶지 않는다는 뜻이고 LVM 이 범위 밖(D9)이라 묶음 안 디스크는 각각 하나의 볼륨이 된다(E32). 예로 RAID 없음 · HDD · SATA · 4TB · 2개 에 4TB HDD 3장이면 묶음 1(2장) + 1장은 규칙 밖이다(E18 — 오류가 아니다). 이 해석은 U4-1-2 의 입력이 된다.

예상 부산물 / 주의

  • ddl/schema.sql 은 dump 시점의 사본이라 이번 ALTER 뒤 다시 stale 해진다 — 갱신은 CH 계열로 따로 다룬다.
  • v1 의 계획서와 report(report/26-08-18_14-47-50_U4-1-1_report.html)는 이력으로 보존한다 — 지우지 않는다.
  • v1 스모크로 샌드박스에만 남은 “OS 설치 안의 카드 · 묶음” 저장본은 샌드박스 리셋으로 정리한다. 실 DB 에는 없다.
  • RaidLevel.typicallyRequiresCache 는 MA7 등록 폼의 경고 전용 — 정의서 폼은 지원 레벨 집합만 본다.
  • 폼을 열어 둔 사이 카드가 삭제되는 경합에서는 화면이 404 · 409 를 모달로 받고 입력값은 유지된다(S10 폼 가로채기).
  • 할당 스냅샷은 payload 를 통째로 얼리므로 할당 후 카드가 사라져도 얼린 id 가 남고, 이름 해석이 상세와 같은 맵이라 “(사라진 카드)” 로 보인다.
