§2. 요구사항 (확정) + 비목표

바뀐 뒤 사용자에게 보이는 것

  1. 모달 맨 위에 S8-6 과 같은 검색 줄: 입력칸 (placeholder "입력 후 [Enter]", 키 common.list.search-placeholder) + [Search] 버튼 (키 common.list.search-open).
  2. 그 아래 표 (S8-6 .n-lookup-table 모양). 열은 아래 표와 같다.
  3. 행 클릭 = 그 정의서를 고른다 (하나만). 고른 행은 강조하고, 표 아래에 지금 오른쪽 패널에 있던 내용을 그대로 펼친다.
  4. 잠긴 행도 고를 수 있다 (사유를 읽어야 하므로). 고르면 사유가 상태줄과 제출 버튼 tooltip 에 뜨고 제출은 닫힌다. 지금 규칙 그대로.
  5. 검색 결과 0 건: 표 자리에 "검색 결과가 없습니다." (키 common.lookup.empty). 고른 것이 풀리고 제출이 닫힌다.
  6. 제출 경로는 바꾸지 않는다 (서버 XHR · 그룹 브라우저 제출 그대로).
모달표 열표 아래 펼침

비 목표 :

  • 제출 경로와 도메인 규칙 (할당 가능 판정, 재할당 차단, 그룹 미리보기) 은 바꾸지 않는다 (D-6). v2 개정 v2 에서 RAID 카드 축만 개정 — §12

🎬 미리보기 — 라이브 UX 데모

같은 가짜 데이터로 [지금] 과 [바뀐 뒤] 를 번갈아 본다. 화면 탭은 모달을 여는 네 버튼이며, 탭마다 제목과 제출 문구가 바뀐다. 바뀐 뒤 모양에서는 검색칸 Enter 또는 [Search] 로 표를 거르고, 행을 눌러 고르면 표 아래에 내용이 펼쳐진다. 시나리오 버튼은 누를 곳을 주황 테두리로 짚으며 재생하고, 끝난 뒤 이어서 직접 조작할 수 있다. 가짜 서버의 메인보드는 MS74-HB0, 가짜 그룹의 멤버는 3 대다.

설계 결정

#채택비채택탈락 사유
D-1모달은 두고 안을 검색 표로 (사용자 결정)S8-6 의 "돋보기 · 입력칸 · 칩" 줄을 할당 자리에 두기정의서 내용과 잠김 사유를 보고 고르는 지금의 장점이 표 열 몇 개로 줄어든다
D-2고른 행의 내용은 표 아래 전체 폭으로 펼친다. 내용 = 지금 상세 화면 · 오른쪽 패널과 같은 단계 카드 전체(setting-process-cards :: processCards 재사용). 잠긴 행 · 0 대 행도 고르면 내용이 펼쳐진다(사용자 요구 11-16: 이름만 보고 고르지 않게)오른쪽 2 단 유지표 열이 좁아져 대상 보드 · 단계 구성 열이 잘린다
행을 펼치는 아코디언내용 패널이 길어 (단계 카드) 표가 밀리고 다른 행을 비교하기 어렵다
D-3검색은 서버에서 (q · from · to 파라미터). 다른 검색 입력과 같이 이름만 보고(대소문자 무시), 검색 줄 안에 등록 시각 기간을 두며 기본은 최근 1 년이다(사용자 결정 11-16). 기간은 S8-5 의 DateRange · ListDateRangeDefaults · fragments/ui/date-range-row 를 재사용한다. 일치 판정은 두 모달이 함께 부르는 Java 메서드 하나브라우저에서 이미 받은 행 걸러 내기즉시 반응은 좋지만 "조회 로직 수정" 요구와 S8-6 의 서버 조회 방식에서 벗어나고, 일치 규칙이 JS 와 Java 두 곳에 생긴다
D-4공통 동작 (검색 요청 · 마지막 응답만 쓰기 · 행 선택 강조 · 펼침 패널 전환 · 0 건 처리) 은 새 공용 스크립트 하나로. 각 모달 스크립트는 자기 몫만S8-6 의 list-lookup.js 를 그대로 재사용그것은 조회 조건 창의 칩 · 여러 개 고르기 · popover 용이라 단건 선택 · 모달 · 펼침 패널과 맞지 않는다
D-5잠긴 행도 고를 수 있다 (U3-5-b 이래 요구). 행은 S8-6 비활성 행처럼 흐리게, 상태 열에 배지—사유를 보려면 눌러야 한다
D-6제출 경로 · 도메인 규칙 (할당 가능 판정, 재할당 차단, 그룹 미리보기) 은 바꾸지 않는다 v2 개정 할당 가능 판정은 RAID 카드 축만 개정 — §12——
D-4 의 근거: 지금 두 파일에 같은 선택 로직이 복사돼 있어 공통화한다 (CLAUDE.md 중복 금지). CSS 는 .n-lookup-search · .n-lookup-table · .n-lookup-row-disabled 를 재사용하고, 새 클래스는 선택 강조와 펼침 영역만 둔다. 그 이름은 구현 때 DESIGN.md 와 명세에 맞춘다.

§12. v2 · RAID 카드 판정 v2

12-1 배경

사용자 질문(2026-11-16): "'할당 가능' 판정에서 RAID 구성 단계가 있으면 RAID 카드 일치도 보는가?" — 실측 답: 보지 않는다. 현행 할당 판정(AssignmentBlockKind)의 차단 사유는 셋뿐이다: DECOMMISSIONED(회수) · BOARD_MISMATCH(메인보드) · TEMPLATE_STALE(BIOS 템플릿 값이 레지스트리와 어긋남).

카드 일치는 집행 시점에만 본다: RAID 구성 phase 진입 시 RaidConfigurationExecutor.cardMatches 가 RaidCardMatch.judge(지정 카드, 감지 인벤토리) 로 대조해 다르면 원장 CARD_MISMATCH · 감지 못 하면 CARD_NOT_DETECTED 로 실패한다. 그래서 지금은 카드가 맞지 않는 정의서도 모달에서 "가능"으로 보이고 할당 · 개시가 되며, 개시 뒤 RAID 단계에서야 실패가 드러난다. 서버 상세의 RAID 계획 미리보기에 같은 판정의 "개시 전 예고" 한 줄(E3.5-5-a)이 있지만 할당을 막지는 않는다.

사용자 결정 : R20 범위에 포함("본 단계에서 진행"). → plan 비 목표였던 "할당 가능 판정은 바꾸지 않는다"를 이 항목에 한해 개정한다(§2 비 목표 · §4 D-6 · §9 회귀 항목에 개정 표시).

12-4 문구 (서버 가드 409 사유 = 화면 문구, 같은 문자열)

상황문구
MISMATCH이 정의서는 RAID 카드 {지정 모델}({지정 Subsystem}) 전용입니다 — 이 서버의 RAID 카드는 {감지 모델}({감지 Subsystem}) 입니다.
NOT_DETECTED이 정의서는 RAID 카드 {지정 모델}({지정 Subsystem}) 전용입니다 — 이 서버에서는 RAID 카드가 감지되지 않았습니다.
대조 전 · 인벤토리 미수집이 정의서는 RAID 카드 {지정 모델} 을 요구하는데 이 서버의 RAID 카드는 아직 확인되지 않았습니다.
대조 전 · Subsystem 미등록RAID 카드 {지정 모델} 에 PCI Subsystem 이 등록되지 않아 이 서버의 카드와 대조할 수 없습니다.
대조 전 · 카드 자원 영구 삭제정의서가 지정한 RAID 카드(#{id})를 찾을 수 없어 이 서버의 카드와 대조할 수 없습니다.
대조 전 · 보드 미수집(현행 유지)이 정의서는 특정 메인보드를 요구하는데 이 서버의 하드웨어는 아직 수집 전입니다.
경고 상자 꼬리 문장은 기존 그대로: "할당은 막지 않되, 수집 후 맞지 않으면 개시할 때 경고가 뜹니다." (D-R5 로 카드도 이 경고에 포함되므로 사실과 맞는다.) 대조 전 사유가 둘이면 두 문장을 잇는다. 기존 보드 문구 "이 정의서는 메인보드 X 전용입니다 — 이 서버는 Y 입니다." 와 같은 틀이다.
