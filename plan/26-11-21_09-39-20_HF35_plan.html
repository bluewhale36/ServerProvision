§1. 배경
한 줄 요약 : 프로비저닝 LAN 대역이 세 곳에 따로 선언돼 어긋날 수 있다. 시스템 설정의 '프로비저닝 허용 대역'(U7)을 정본으로 두고, dnsmasq 조각과 게스트 채널 출발지 제한이 그 값을 읽게 한다(출처: 2026-11-21 사용자 지적, A 안 사용자 선택).

1-1. 세 값이 생긴 순서와 각자 풀던 문제

생긴 단계값저장풀던 문제
S19-2(09-15) env PXE_GUEST_ALLOWED_CIDRS → pxe.guest.allowed-cidrs 환경 파일, 쉼표 목록, 비우면 제한 없음 게스트 채널 /api/pxe/v1/** 를 프로비저닝 LAN 밖에서 부르지 못하게
R16(09-16) PXE 네트워크 설정 '게스트 서브넷 CIDR' subnetCidr DB pxe_network_config.subnet_cidr dnsmasq 가 PXE 응답을 낼 서브넷(AUTHORITATIVE 는 배정 범위 경계, PROXY 는 dhcp-range=네트워크,proxy,넷마스크)
U7(11-16) 시스템 설정 '프로비저닝 허용 대역' DB system_setting(키 PROVISIONING_ALLOWED_RANGE, 최소 권한 SUPER_ADMIN) 개시 직전 BMC 주소 · primary NIC 주소가 대역 밖이면 개시를 막음

1-2. 어긋나면 생기는 일(예)

어긋남의 결과 :
  • 허용 대역 10.1.1.0/24, dnsmasq 서브넷 10.1.2.0/24 → 10.1.2.x 서버가 PXE 로 부팅해 등록 · 진단까지 가고 개시에서야 막힌다. 운영자는 왜 막혔는지 PXE 화면에서 알 수 없다.
  • env 를 예전 대역(192.168.1.0/24)으로 남겨 둔 채 사내망으로 옮김 → 게스트 채널 전체가 403(실제로 R16 실기 1차 때 env 세 개가 192.168.1.x 로 남아 있었다는 기록이 있다).
  • 문서가 이 분리를 규칙으로 적고 있다: docs/pxe-dnsmasq-setup.md 64 행 "화면의 서브넷과 이 값은 따로 관리한다".
§2. 실측 (11-21, 코드 판독)
항목사실
같은 VO U7 의 ProvisioningAllowedCidr 는 R16 의 SubnetCidr 를 감싼다(record ProvisioningAllowedCidr(SubnetCidr subnet)). RFC 1918 · prefix 26 이하 · 네트워크 주소 검증이 더 붙은 것뿐이라, 허용 대역 값은 그대로 dnsmasq 서브넷으로 쓸 수 있다
허용 대역 읽기 SystemSettingService.provisioningAllowedRange()(권한 판정 없는 내부 읽기). 소비처는 지금 StartNetworkPolicy 하나
dnsmasq 렌더 DhcpMode 상수별 메서드가 config.getSubnetCidr() 의 networkAddress() · netmask() 로 dhcp-range 줄을 만든다(AUTHORITATIVE 22 ~ 24 행, PROXY 64 ~ 65 행)
PXE 설정 저장 PxeNetworkConfigController.submit → PxeNetworkConfigMapper.toEntity(desired) → DhcpConfigApplyService.applyAndRecord(락 안에서 렌더 · 검사 · 교체 · 기록) → PxeNetworkConfigService.save. 저장과 적용이 한 동작("저장 및 적용")
서브넷 검증 PxeNetworkConfigValidator 가 SubnetCidr.of + AUTHORITATIVE 의 리스 범위가 서브넷 안인지(containsRange). 엔티티 assertInvariants 도 같은 술어
적용 상태 표시 appliedResult(APPLIED · REJECTED · ROLLED_BACK · RESTORE_FAILED) · appliedAt · driftFromServing(마지막 적용 실패로 이전 구성 서빙 중). 허용 대역이 바뀌었는지는 보지 않는다
출발지 제한 ProvisioningLanPolicy(AuthorizationManager, GuestSecurityConfig 가 게스트 체인에 건다): 생성자에서 env 문자열을 IpAddressMatcher 목록으로 한 번 만든다. 비우면 제한 없음 + 기동 WARN. 거절은 Denied → GuestAccessDeniedHandler 가 403 PXE_LAN_FORBIDDEN, AuthenticationEventLogger 가 로그
출발지 판정 주소 request.getRemoteAddr(). nginx 뒤에서는 server.tomcat.remoteip.* 가 X-Forwarded-For 로 바꿔 둔다(같은 호스트 127.0.0.1 프록시만 신뢰)
env 를 적은 문서 docs/pxe-dnsmasq-setup.md 64 · docs/staging-vm-bootstrap.md 173 · docs/pxe-server-install.md 262 · 310 · docs/T3-checklist.md 63
배포 상태 U7 은 dev 병합(c1c938d, 11-19)됐지만 운영 · 스테이징 미배포(DDL · 시드 대기, docs/deploy/pending/U7.md). 이 HF 는 U7 과 같은 배포에 실린다
§3. 결론
세 값은 같은 사실("프로비저닝 LAN 이 어느 대역인가")을 세 번 선언한 것이다. 각 단계가 자기 문제만 풀며 새로 선언했고, 서로 대조하는 코드가 없다.

정본으로 가장 알맞은 것은 U7 의 허용 대역이다.

  • 화면에서 바꿀 수 있다(env 와 달리 재기동 불필요).
  • 검증이 가장 엄격하다(사설 대역 · prefix 상한).
  • 최고 관리자만 바꿀 수 있다.

지금 : 선언 셋, 대조 없음

  • env PXE_GUEST_ALLOWED_CIDRS → 게스트 채널 출발지 제한
  • pxe_network_config.subnet_cidr(사용자 입력) → dnsmasq dhcp-range
  • system_setting PROVISIONING_ALLOWED_RANGE → 개시 판정

바뀐 뒤 : 정본 하나, 소비처 셋

  • system_setting PROVISIONING_ALLOWED_RANGE → 개시 판정(그대로)
  • 같은 값 → "저장 및 적용" 때 dnsmasq 서브넷(subnet_cidr = 마지막 적용 대역)
  • 같은 값 → 게스트 채널 출발지 제한(env PXE_GUEST_ALLOWED_CIDRS 삭제)
SystemSettingService.provisioningAllowedRange() 시스템 설정 '프로비저닝 허용 대역' ├── StartNetworkPolicy 개시 판정 (지금과 같음) ├── PxeNetworkConfigMapper.toEntity "저장 및 적용" 때 서브넷을 채움 │ └── DhcpConfigApplyService.applyAndRecord 렌더 · 검사 · 교체 · 기록 │ └── DhcpMode (AUTHORITATIVE · PROXY) dhcp-range 줄 └── ProvisioningLanPolicy 첫 authorize 때 지연 적재, 저장 커밋 뒤 이벤트로 교체 └── GuestSecurityConfig 게스트 체인 대역 밖 → 403 PXE_LAN_FORBIDDEN
§4. 수정 방향

4-1. dnsmasq 서브넷 = 허용 대역

  • PXE 네트워크 설정 화면에서 '게스트 서브넷 CIDR' 입력을 없애고, 그 자리에 허용 대역을 읽기 전용으로 보인다(시스템 설정 화면 링크).
  • "저장 및 적용" 때 서버가 SystemSettingService.provisioningAllowedRange() 로 서브넷을 채운다. 요청 DTO 의 subnetCidr 필드를 지운다(direct POST 로 보내도 무시된다).
  • 허용 대역이 비어 있으면 저장 버튼 disabled + 사유 "프로비저닝 허용 대역을 먼저 시스템 설정에서 저장해야 합니다." · 서버 가드도 같은 판정(정상 흐름에서는 UI 가 막고, direct POST 는 409).
  • pxe_network_config.subnet_cidr 컬럼은 남기되 뜻을 "마지막 적용에 쓴 대역" 으로 바꾼다(사용자 입력이 아니라 적용 때 서버가 기록). DDL 없음.

4-2. 대역이 바뀌면 재적용 필요를 보인다

  • 판정 PxeNetworkConfig.rangeChangedSince(ProvisioningAllowedCidr current): 저장된 적용 대역 ≠ 현재 허용 대역.
  • PXE 네트워크 화면: 경고 "프로비저닝 허용 대역이 바뀌었습니다. 저장 및 적용을 다시 해야 dnsmasq 에 반영됩니다."
  • 시스템 설정 화면: 허용 대역을 저장한 뒤 flash 에 같은 안내 + PXE 네트워크 화면 링크(구성이 있을 때만).
  • AUTHORITATIVE 의 리스 범위가 새 대역 밖이면 재적용 때 기존 교차 검증(containsRange)이 rangeEnd 필드 오류로 막는다(새 코드 없음).
  • 자동 재적용은 하지 않는다(D3).

4-3. 게스트 채널 출발지 제한 = 허용 대역

  • ProvisioningLanPolicy 가 env 대신 허용 대역을 읽는다. 매 요청 DB 를 읽지 않도록 정책 안에 현재 값을 담아 둔다(AtomicReference).
  • 값은 생성자에서 읽지 않는다. 첫 authorize 때 지연 적재하고(담긴 값이 비어 있으면 읽음), 허용 대역 저장이 커밋된 뒤(@TransactionalEventListener(AFTER_COMMIT) + 새 이벤트 ProvisioningAllowedRangeChangedEvent) 새 값으로 교체한다. 이유: security 빈을 만드는 시점에 DB 를 읽지 않게, 그리고 기동 순서에 기대지 않게.
  • env 문자열 파싱과 기동 fail-fast(잘못된 CIDR 이면 IllegalStateException)는 사라진다. 허용 대역은 이미 검증된 VO(ProvisioningAllowedCidr)라 다시 검사할 것이 없다.
  • unrestricted() 는 main 호출처가 없고 테스트에서만 쓰인다. 판정 술어로 남기되 뜻을 "현재 허용 대역 없음" 으로 바꾸고 테스트를 고친다.
  • 허용 대역이 비어 있으면 지금 env 가 비었을 때와 같이 제한 없음 + WARN(로그 문구에서 env 이름을 시스템 설정으로 바꿈).
  • 루프백(127.0.0.0/8 · ::1)은 언제나 허용한다(Q1).
  • pxe.guest.allowed-cidrs 속성 · env 를 삭제한다. 기동 시 env 가 남아 있어도 읽지 않는다(무해).

4-4. 문서

§2 의 env 문서 다섯 곳을 "시스템 설정의 프로비저닝 허용 대역이 dnsmasq 서브넷과 게스트 채널 출발지 제한을 함께 정한다" 로 고친다. docs/pxe-dnsmasq-setup.md 64 행의 "따로 관리한다" 문장은 삭제.

SELECT subnet_cidr, dhcp_mode, applied_result FROM pxe_network_config;

§5. 결정 · 질문

5-1. 결정

D채택비채택 · 사유
D1 정본 위치 시스템 설정 허용 대역 PXE 네트워크 설정을 정본으로: 최소 권한 · 검증이 더 느슨하고 U7 개시 판정이 PXE 화면 저장에 끌려감 / env 를 정본으로: 화면에 보이지 않고 재기동이 필요함
D2 dnsmasq 서브넷 컬럼 남기고 "마지막 적용 대역" 으로 뜻을 바꿈(재적용 필요 판정 재료) 컬럼 삭제: 대역이 바뀐 뒤 적용 전인지 알 길이 없어 경고를 못 냄 · DDL 필요 / 입력 유지 + 허용 대역과 같아야 저장(B 안): 같은 값을 두 번 입력, 사용자가 A 안을 고름
D3 대역 변경 시 경고 + 안내만, 재적용은 운영자가 허용 대역 저장 때 자동 재적용: dnsmasq 재시작(sudo)이 설정 저장의 부작용이 되고, AUTHORITATIVE 리스 범위가 새 대역 밖이면 설정 저장 자체가 실패
D4 출발지 제한 갱신 정책 안 값 + 첫 authorize 때 지연 적재 + 저장 커밋 뒤 이벤트로 교체(생성자에서 읽지 않음: security 빈 생성 시점에 DB 를 읽지 않고 기동 순서에 기대지 않게) 매 요청 DB 조회: 게스트 체크인 · 보고마다 쿼리 / 재기동 필요(지금 env 방식): 화면 값의 장점이 사라짐
D5 대역 미설정 출발지 제한 없음 + WARN(지금 env 미설정과 같음), dnsmasq 저장은 막음 미설정이면 게스트 채널 전부 거절: 배포 직후 시드 전 순간에 모든 게스트가 403

5-2. 질문 (CP1 에서 답을 받는다)

Q질문권고
Q1 루프백 출발지를 늘 허용할까. 같은 호스트의 nginx 는 X-Forwarded-For 로 실제 주소를 넘기므로, 루프백으로 보이는 것은 같은 서버의 프로세스(로컬 샌드박스의 모의 게스트 하네스 등)뿐이다 허용. 허용 대역은 사설 대역만 받아 127.0.0.0/8 을 넣을 수 없으므로, 막으면 샌드박스 하네스가 동작하지 않는다
Q2 출발지 제한이 대역 하나로 충분한가. env 는 쉼표 목록이었다(문서와 운영 기록은 모두 한 대역) 하나로 충분. 여러 대역이 필요해지면 허용 대역 자체를 목록으로 넓힌다(그때 개시 판정 · dnsmasq 도 함께)
Q3 BMC 망과 LAN 이 다른 대역인 현장이 있는가(U7 은 BMC 와 LAN 을 같은 대역 하나로 검사한다) 없다는 전제로 진행. 있으면 별도 단계
