§1. 현재 상태 (진단)

계기

U3-2-b 의 CP7 사용자 브라우저 E2E 에서, 삭제된 세팅 정의서를 복원할 때 서버가 거절한 응답의 본문이 화면에 그대로 노출됐다. 사용자에게는 안내 없이 {"message":"같은 이름의 활성 정의서가 있어 복원할 수 없습니다. …"} 라는 원문과 낯선 주소만 남았다.

같은 부류가 과거에 둘 있었다. catch(DomainException) 이 보안 예외를 흡수해 silent 500 으로 새던 사고, MissingFilenameException 이 500 으로 새던 사고다. 후자 때문에 "사용자 액션 통합 테스트" 규율이 생겼다. 규약은 이미 있었고 지켜지지 않았다 — 이 사실이 이 슬라이스의 설계를 좌우한다.

실측으로 확정한 원인

착수 브리핑은 @ExceptionHandler(Exception.class) 최종 폴백 부재를 주 원인으로 지목했다. 조사 결과 사실이 아니다. 예외는 정상적으로 잡혀 409 로 매핑됐고, 형식만 틀렸다. 폴백이 있었어도 이 사고는 그대로 났다.

진짜 원인은 content negotiation 구조 결함이다. @WebMvcTest 로 BoardModelLifecycleController 와 BoardModelMetadataController 를 측정했다.

요청 Accept*/* 포함선택된 advice응답
text/html—Webtext/html, view=error
text/html,application/xhtml+xml;q=0.9—Webtext/html, view=error
text/html,*/*;q=0.8있음Apiapplication/json
실제 크롬 내비게이션 헤더있음Apiapplication/json
헤더 없음있음Apiapplication/json
기전 : 두 advice 가 모두 @Order(HIGHEST_PRECEDENCE) 로 동순위라 등록 순서로 결정되고 ApiExceptionHandler 가 먼저 조회된다. Spring 은 선호도(q값) 최적을 고르는 것이 아니라 훑는 순서대로 "요청이 받아줄 수 있는 형식이면 채택" 한다. */* 는 모든 형식과 호환되므로 JSON advice 가 무조건 먼저 합격한다. 실제 브라우저는 */*;q=0.8 을 항상 붙인다.

결과 — WebExceptionHandler(advice)가 실제 브라우저에서 도달 불가능하다. 폼 제출뿐 아니라 주소창 진입도 raw JSON 이 뜬다.

주소창 진입도 함께 측정했다. GET /management/board/999/edit 에 실제 브라우저 헤더와 Sec-Fetch-Dest: document 를 실어 보낸 결과는 404 application/json 이었다. 오류 페이지가 아니라 JSON 원문이다.

혼동하기 쉬운 지점 — 실패 경로가 둘이다

같은 404 라도 advice 가 잡는 예외인지에 따라 정반대로 동작한다. 이 구분을 놓치면 "어떤 주소는 오류 페이지가 잘 뜨는데" 라는 관찰로 결함을 없는 것으로 오판하게 된다.

경로 A — advice 가 잡는 예외경로 B — advice 가 못 잡는 예외
예/management/os/999/edit
→ OSMetadataNotFoundException		/management/os/3 (매핑 없음)
→ NoResourceFoundException
성격도메인 예외 121 개(DomainException 하위)Spring 내장. 코드에 등장하지 않음
처리 주체두 advice 의 content negotiation둘 다 통과 → 기본 /error → BasicErrorController
결과JSON — 결함HTML — 정상

왜 B 는 되고 A 는 안 되나. BasicErrorController 는 평범한 컨트롤러라 정상 요청 매핑을 탄다. 정상 매핑은 Accept 의 선호도(q값)를 제대로 지켜 text/html(q=1.0)을 고른다. 반면 예외 advice 선택은 선호도를 보지 않고 등록 순서대로 "받아줄 수 있으면 채택" 하므로 */* 에서 JSON 이 먼저 걸린다. 같은 프레임워크 안에서 두 메커니즘이 다르게 동작하는 것이 이 결함의 뿌리다.

따라서 error.html 템플릿 자체는 이미 살아 있다(경로 B 로 렌더된다). 죽어 있는 것은 WebExceptionHandler advice 이고, 이 슬라이스는 경로 A 를 경로 B 와 같은 결과로 맞추는 일이다.

왜 지금까지 드러나지 않았나

두 가지가 겹쳐 가리고 있었다.

  • 프런트엔드가 우회하고 있었다. 관리 도메인 폼은 data-async-submit 마커를 달고 fetch 로 보낸다. fetch 는 페이지를 이동시키지 않으므로 JSON 을 받아도 화면이 바뀌지 않고, ErrorModal 이 message 를 꺼내 모달로 띄운다. JSON 이 오는 것이 오히려 편한 경로였고, 그래서 결함이 결함으로 보이지 않았다. 템플릿의 POST 폼 68 개 중 마커가 붙은 것은 13 개다.
  • 테스트가 브라우저를 흉내내지 않았다. AdviceExceptionMappingTest 는 Accept: text/html 순수값으로 검증한다. 그 값에는 */* 가 없으니 HTML 이 나오고 테스트는 통과한다. 브라우저는 그런 값을 보내지 않는다. SSR lifecycle 의 @WebMvcTest 들도 status().isConflict() 만 볼 뿐 응답 형식을 단언하지 않는다.

U3-2-b 는 마커 없이 SSR lifecycle 폼을 추가한 첫 슬라이스였다. 가려주던 것이 없어지자 잠복 결함이 그대로 드러났다.

HF5 병합 이후 재확인

HF5 가 WebExceptionHandler 를 건드렸기에 병합된 dev(18f1752) 에서 다시 측정했다. HF5 의 변경은 statusLabel 을 ErrorStatusLabels 에서 파생하도록 바꾼 것뿐이고 @Order 와 produces 는 그대로다. 결함은 유지된다.

브라우저 네이티브 제출 -> 409  application/json   view=null
fetch(async) 제출     -> 409  application/json   view=null
Sec-Fetch-Dest 동반   -> 409  application/json   view=null

세 번째 줄이 중요하다. Sec-Fetch-Dest: document 를 보내도 라우팅이 바뀌지 않는다 — Spring 이 그 헤더를 보지 않기 때문이며, 판별기를 직접 만들어야 한다는 뜻이다.

문서가 반대로 기록하고 있다. docs/dev/global.md 의 "응답 포맷과 두 어드바이스" 절은 "Accept 와의 호환으로 자연 분리된다", "브라우저 내비게이션이면 HTML 핸들러가 선택되어 오류 페이지가 된다" 고 적는다. 두 문장 다 실측과 반대다. 두 advice 클래스의 v3 주석도 같다. 근거 자료가 없는 것보다 틀린 근거 자료가 더 나쁘므로 정정 대상이다.
§2. 요구사항 + 비목표

이 슬라이스가 세우는 원칙

응답 형식은 사용자가 무엇을 하던 중이었나로 정한다. 종전의 "SSR 이면 HTML, XHR 이면 JSON" 은 실제 필요와 어긋난다.

상황머무를 페이지옳은 처리필요한 응답
화면 안에서 액션을 눌렀다있다 — 방금 보던 화면페이지 유지 + 안내 모달JSON
주소로 페이지에 진입했다없다 — 아직 아무 화면도 없다전체 오류 페이지HTML

첫 번째가 압도적 다수이고 거기서는 JSON 이 정답이다. 서버가 JSON 을 주는 것은 결함이 아니라 의도대로다. 두 번째는 드물지만 없앨 수 없다 — 모달은 띄울 host 페이지가 있어야 성립하는데, 진입 자체가 실패한 상황엔 그 페이지가 없다.

요구사항

  1. R1 진입 경로 정정. 문서 이동으로 도달한 요청이 도메인 예외를 만나면 error.html 이 렌더된다.
  2. R2 액션 폼 전면 전환. 상태를 바꾸는 액션 폼 49 개 전부가 자동으로 가로채여 fetch 로 나가고, 거절은 안내 모달로 수렴한다. 개별 폼에 마커를 붙이는 일이 사라진다.
  3. R3 입력 폼 불변. BindingResult 로 뷰를 다시 렌더하는 입력 폼 11 개는 네이티브 제출을 유지한다. 필드별 오류 표시가 지금 그대로 동작해야 한다.
  4. R4 비브라우저 클라이언트 불변. PXE 게스트(/api/pxe/v1/*) 와 XHR 은 지금과 같은 JSON 을 받는다.
  5. R5 강제 장치. 위 넷이 깨지면 CP4 에서 빨간불이 뜬다. 문서를 읽었는지와 무관해야 한다.
비 목표
  • 커스텀 도메인 예외 121 개를 advice 에 명시 등록하지 않는다. 상위 타입 핸들러의 다형 흡수가 설계 의도이며, 명시 등록은 고유 상태코드나 응답 몸체가 필요한 경우로 한정한다. 전수 등록은 "조건분기 대신 다형성" 불가침에 정면으로 어긋난다.
  • @ExceptionHandler(Exception.class) 최종 폴백을 도입하지 않는다. 이번 사고의 원인이 아니었다(§1). 두 advice 를 모두 빠져나가는 예외를 사용자에게 어떻게 보일지는 별도 사안으로 남긴다 — RequestCorrelationFilter 가 이미 최후 기록 안전망이고, HF5 의 ProvisionErrorAttributes 가 기본 /error 경로의 문구를 맞춘다.
  • 입력 폼을 fetch 로 전환하지 않는다. R3 참조.
  • harness hook 을 도입하지 않는다. 아키텍처 테스트로 얻는 것이 더 확실하고 hook 은 설정 영역이라 별도 판단이 필요하다.
  • advice 의 @Order 값을 바꾸지 않는다. 사고 이력이 둘이다(§8 D1).
  • 체크리스트는 예외 항목만 확정한다. 자원 도메인 · 드리프트 종류 · 특권 명령 · phase 항목은 실측 분량에 따라 후속 단계로 넘길 수 있다.

§4. 판정 계약 (SSOT)
엔티티 변경 0 · DB 변경 0 · URL 변경 0. 이 슬라이스에 도메인 모델 변경은 없다. SSOT 로 세우는 것은 판정 두 개이며, 서버와 클라이언트에 하나씩 있고 서로 독립이다.

판정 1 (서버) — 이 요청은 문서 이동인가

브라우저는 주소창 이동 · 링크 클릭 · 네이티브 폼 제출에 Sec-Fetch-Dest: document 를, fetch 와 XMLHttpRequest 에 empty 를 보낸다. 정확히 이 구분을 위해 표준화된 헤더라 Accept 같은 모호성이 없다. 비브라우저 클라이언트는 이 헤더를 보내지 않으므로 자동으로 JSON 기본값에 남는다.

문서 이동 = "Sec-Fetch-Dest" 헤더가 "document"

  주소창 진입      document   → HTML
  링크 클릭        document   → HTML
  네이티브 폼 제출  document   → HTML
  fetch / XHR      empty      → JSON (불변)
  PXE 게스트       (없음)      → JSON (불변)

판정이 참이면 요청 래퍼가 Accept 를 text/html 로 좁혀 보고한다. 그 뒤는 기존 협상이 의도대로 동작한다 — §1 실측에서 */* 없는 헤더가 Web advice 로 가는 것이 이미 확인됐다.

안전성 확인(실측). 문서 이동으로 도달하면서 HTML 이 아닌 응답을 내는 엔드포인트가 있으면 이 정규화가 406 을 만든다. 전수 조사 결과 그런 경로는 없다 — 파일 다운로드 엔드포인트가 없고(Content-Disposition · OCTET_STREAM · Resource 반환 0건), 비 HTML 생산자는 SSE 스트림(text/event-stream, EventSource 는 Sec-Fetch-Dest: empty)과 PXE /boot(text/plain, 비브라우저)뿐이다. 이 전제는 §6 의 테스트로 고정한다.

판정 2 (클라이언트) — 이 폼을 가로챌 것인가

기준은 서버 핸들러가 실패 시 뷰를 다시 렌더하는가 다. 임의 재량이 아니라 컨트롤러 코드에서 읽히는 성질이다.

부류수실패 시 서버 동작가로채기근거
액션 폼
toggle · delete · restore · purge · deprecate · seal · retry …		49도메인 예외 → 상태코드 + 메시지대상그릴 화면이 없다. 모달이 맞다
입력 폼
new · edit · settings		11BindingResult 를 담아 같은 뷰 재렌더제외그릴 화면(오류 붙은 폼)이 있다

입력 폼을 가로채면 서버가 돌려준 재렌더 HTML 을 버리게 되어 필드별 오류 표시가 사라진다. 전형이 이렇다.

// BoardModelMetadataController.update
if (bindingResult.hasErrors()) {
    ...
    return "management/board/edit";   // 오류를 담아 폼을 다시 그린다
}
boardModelService.update(id, request);
return BoardControllerSupport.redirectToListWithSelect(id);

두 판정의 관계

액션 폼 ──가로챔──▶ fetch ──Sec-Fetch-Dest: empty──▶ JSON ──▶ 안내 모달 입력 폼 ──그대로──▶ 네이티브 ──Sec-Fetch-Dest: document─▶ HTML ──▶ 폼 재렌더 / 오류 페이지 주소창 ──그대로──▶ 네이티브 ──Sec-Fetch-Dest: document─▶ HTML ──▶ 오류 페이지 API ──그대로──▶ 직접호출 ──헤더 없음────────────────▶ JSON ──▶ 클라이언트 파싱

두 판정이 서로를 참조하지 않는다. 클라이언트가 가로채면 전송 수단이 fetch 가 되고, 서버 판정은 그 결과로 자연히 empty 를 본다. 한쪽이 바뀌어도 다른 쪽 계약이 깨지지 않는 것이 이 배치의 이점이다.

D1 — 서버 판별 방식

채택 : Sec-Fetch-Dest: document 판별 + Accept 정규화 필터.

안내용판정사유
A필터가 문서 이동 요청의 Accept 를 text/html 로 좁혀 보고. advice 무변경채택분기가 한 줄도 안 는다. 기존 협상 구조를 그대로 두고 입력만 바로잡는다. @Order 를 건드리지 않아 v1 · v2 사고 재현 여지가 없다. 판별을 Spring primitive 가 떠맡는다

A 에 대한 자기 비판과 답. 정규화가 정상 응답의 협상까지 바꾼다는 것이 유일한 위험이다. 문서 이동으로 도달하면서 HTML 이 아닌 응답을 내는 엔드포인트가 있으면 406 이 난다. §4 에서 전수 조사로 그런 경로가 없음을 확인했고, 그 전제 자체를 §6 T2 가 테스트로 고정한다. 앞으로 다운로드 엔드포인트를 추가하면 그 테스트가 먼저 깨진다.

D2 — 가로채기 배치

채택 : 전역 레이아웃에 적재하는 독립 스크립트.

안판정사유
전역 fragments/layout.html 에 독립 스크립트채택모든 화면이 layout 을 쓰므로 누락이 구조적으로 불가능하다. 확인 모달과 책임이 분리된다
confirm-modal-base.js 확장탈락이 파일은 일부 페이지에만 적재된다(관리 fragment 3곳 + provisioning 3곳). 여기 얹으면 적재되지 않은 화면이 그대로 구멍으로 남는다 — 이번 사고의 구조를 그대로 재생산한다

기존 ConfirmModal.approveAndSubmit 의 data-async-submit 분기는 유지한다. 확인 모달을 거치는 폼은 그 경로로, 거치지 않는 폼은 전역 스크립트로 같은 submitAsync 에 도달한다. 두 진입점이 한 구현을 공유하므로 드리프트가 생기지 않는다.

D3 — 대상 분류 기준

채택 : "핸들러가 실패 시 뷰를 재렌더하는가". 마커 목록이 아니라 코드에서 읽히는 성질이라 §6 T3 가 기계적으로 검증할 수 있다. 대안이던 "마커 유지" 는 이번 사고의 원인 그 자체라 탈락이다 — 잊을 수 있는 관례는 다시 잊힌다.

D4 — 실패 방향 반전

기본값을 뒤집는 것이 이 슬라이스의 본질이다.

AS-IS

마커를 잊으면 → raw JSON 노출
안전하지 않은 기본값

TO-BE

표기를 잊으면 → 모달로 안내
안전한 기본값

입력 폼이 opt-out 표기를 빠뜨리면 가로채여 검증 오류 표시가 깨진다 — 이는 즉시 눈에 띄는 실패이고 T3 가 CP4 에서 먼저 잡는다. 반대 방향의 실패(raw JSON)는 조용하고 사용자에게 도달했다. 시끄러운 실패로 바꾸는 것이 목적이다.

D5 — error.html 존치

존치한다. 주소창 진입 실패에는 모달을 띄울 host 페이지가 없다. 이 템플릿은 이미 사용 중이다 — 매핑 없는 주소(NoResourceFoundException) 처럼 advice 를 거치지 않고 기본 /error 로 흐르는 요청이 이것을 렌더한다(§1 경로 B). 이 슬라이스는 advice 가 잡는 도메인 예외(경로 A)도 같은 화면에 도달하게 만들어, 사용자가 구분할 이유가 없는 두 상황의 결과를 일치시킨다. HF5 가 정비한 statusLabel 파생과 ProvisionErrorAttributes 가 두 경로에 함께 적용된다.
