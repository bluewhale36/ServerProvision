§0. 한눈 요약

Windows 무인 설치는 지금 항상 디스크 0 을 지우고 거기에 설치한다. 응답 파일에 그 번호가 상수로 박혀 있어서 게스트마다 달라지지 않는다. 데이터 디스크가 함께 꽂힌 서버에서 컨트롤러가 그 디스크를 0 번으로 노출하면, 지워지지 말아야 할 디스크가 지워진다.

  • 서버가 디스크 번호를 계산한다 — RAID 인벤토리의 볼륨 순서에서 OS 영역 볼륨의 인덱스를 찾아 그것을 DiskID 로 삼는다
  • 계산이 서지 않으면 서빙하지 않는다 — OS 영역 볼륨이 없거나 · 인벤토리가 없거나 · 볼륨을 목록에서 못 찾거나 · 물리 디스크 직결이 섞이면 준비도가 BLOCKED 로 막는다
  • 응답 파일의 두 자리가 계산값으로 렌더된다 — DiskConfiguration 의 DiskID 와 InstallTo 의 DiskID
  • 설치 뒤 WWN 으로 확증한다 — 첫 로그온 스크립트가 C: 디스크의 UniqueId 를 실어 보고하고, 서버가 OS 볼륨 WWN 과 대조해 원장에 남긴다
변경 범위 — 엔티티 · Repository · DDL(Data Definition Language — 스키마 정의문) 은 건드리지 않는다. 새 예외도 만들지 않는다. 추가되는 것은 정적 판정 클래스 하나와 완료 보고 필드 하나 · 응답 파일 자리표시자 하나다.
§1. 현재 상태 (진단)

아래는 이 슬라이스가 손대는 자리에서 지금 실제로 무슨 일이 벌어지는지를 코드와 실기 기록에서 확인한 것이다.

1-1. 디스크 0 이 상수로 박혀 있다

자리현재결과
WindowsInstallTemplates.AUTOUNATTEND_XML <DiskID>0</DiskID> · <WillWipeDisk>true</WillWipeDisk> · <InstallTo> 의 DiskID 0 · PartitionID 3 게스트가 달라도 같은 번호가 나간다
AutounattendRenderer.render 자리표시자 8종(__UI_LANGUAGE__ · __PRODUCT_KEY__ · __IMAGE_NAME__ · __COMPUTER_NAME__ · __TIME_ZONE__ · __REPORT_BASE_URL__ · __GUEST_TOKEN__ · 비밀번호 둘) 디스크 번호를 넣을 자리가 없다
WindowsInstallTemplates.INSTALL_BAT diskpart /s X:\dp.txt 로 list disk 를 콘솔에 찍기만 한다 출력을 파싱하지도 · 번호를 치환하지도 않는다
위험 — WillWipeDisk=true 와 DiskID=0 이 함께 있으면 0 번으로 노출된 디스크의 내용이 사라진다. 그리고 응답 파일의 DiskConfiguration · InstallTo 는 정수 번호만 받는다 — WWN(World Wide Name — 저장장치 전역 고유 식별자)이나 크기로 대상을 지정할 수 없다. 그래서 "번호를 안 쓰는 길" 은 없고, 올바른 번호를 정하는 길만 있다.

1-2. 실기 2호 Run 3 (2026-09-08 · 체크리스트 §9-2)이 고정한 근거

항목결과이 슬라이스가 기대는 부분
D1O 진단 리눅스 lsblk(sda 446.6G → sdb 18.2T) 와 WinPE diskpart list disk(0 = 446 GB · 1 = 18 TB · 2~5 = BMC 가상 미디어 0 B) 의 열거 순서가 일치 볼륨 순서 = 디스크 번호 순서. 0 B 가상 미디어는 실디스크 뒤에 서므로 실디스크 번호에 영향이 없다(Run 1 은 1~4 · Run 3 은 2~5 로 실디스크 수만큼 밀렸다)
D4O WillWipeDisk=true · DiskID=0 이 디스크 0(RAID1 spvR1V1)만 지웠다 18 TB 볼륨(디스크 1)의 표식 파일이 살아남았다 — wipe 범위가 지정 디스크에 한정된다는 실증
D2부분 Windows Get-Disk 의 UniqueId 가 RAID 볼륨 WWN 과 두 디스크 모두 정확히 일치(0 = 600605b0…791d = VD0 · 1 = …97db = VD1) 사후 확증의 대조 키가 성립한다. 같은 모델 물리 디스크 직결(JBOD)은 이 구성에 없어 미실측

표본이 하나라는 사실은 이 계약의 설계를 좌우한다. 순서 전제가 성립하는 것을 한 번 봤을 뿐이므로, 계산에 확신이 서지 않는 조건에서는 아예 서빙하지 않는 쪽으로 설계한다(§4 진리표).

§2. 요구사항 (확정) + 비목표

실기 Run 3 의 D1 · D4 · D2 가 고정한 사실과, 표본이 하나뿐이라는 제약을 함께 반영해 일곱 줄로 고정한다.

#요구판정 · 기록 지점
R1서버가 OS 영역 볼륨의 Windows 디스크 번호를 계산한다 — RAID 인벤토리 볼륨 목록에서 WWN(우선) 또는 이름으로 찾은 인덱스가 DiskIDWindowsDiskSelection.judge
R2계산이 서지 않으면 서빙하지 않는다 — 사유를 준비도의 notes · wire 로 흡수해 HOLD 로 내보낸다WindowsInstallReadinessResolver.resolve
R3응답 파일의 DiskID 두 자리(DiskConfiguration · InstallTo)가 계산값으로 렌더된다AutounattendRenderer.render · WindowsInstallTemplates
R4첫 로그온 스크립트가 C: 가 들어간 디스크의 UniqueId 를 완료 보고에 싣는다 — 조회 실패는 관용(null)WindowsOemTemplates.SPV_REPORT_PS1 · WindowsInstallCompletionRequest
R5서버가 보고값을 OS 볼륨 WWN 과 대소문자 무시로 대조해 원장 close 메타에 남긴다 — 어긋나도 완료는 완료WindowsInstallCompletionService.complete · WindowsInstallLedger
R6게스트 상세의 Windows 카드가 대상 디스크 번호와 확증 결과(확증 O · 어긋남 · 미보고)를 보인다GuestServerDetailResponse.WindowsInstall
R7게스트 접점 검증은 하네스 windows-install-cycle.sh 로, 카드 표시는 브라우저로 본다CP5

R2 와 R5 는 성격이 정반대다. R2 는 사전 판정이라 막을 수 있다 — 확신이 없으면 설치를 시작하지 않는 것이 최소 파괴다. R5 는 사후 판정이라 막을 것이 남아 있지 않다 — 설치는 이미 끝났으므로 확증이 어긋나도 실패를 만들지 않고 사실만 남긴다. 이 비대칭이 이 슬라이스 설계의 중심이다.

비 목표 — 이 슬라이스에서 다루지 않고 어디로 가는지 :
  • WinPE 사전 게이트(설치 직전에 diskpart 로 크기 · 식별자를 대조해 이중 방어) → E4-1-a-7. 실기 list disk · detail disk 출력 형식을 실측한 뒤에 설계한다(§4 D-1)
  • 물리 디스크 직결(JBOD · passthrough) 지원 → 그 구성의 서버가 나오면 순서 · 식별을 재실측한 뒤. 이번에는 BLOCKED 로 막는다
  • 대상 디스크만 clean 하는 방식(접근 C) → 번호 판정이 여전히 필요해 별도 이득이 없다(§4 D-1)
  • 스키마 변경 · 새 엔티티 · 새 예외 · 새 ProvisioningPhaseStep
  • 리눅스 설치 경로의 디스크 선택
🎬 미리보기 — 라이브 데모 (볼륨 구성을 바꿔 DiskID · 준비도 · 확증을 체험)

4-1. WindowsDiskSelection — 새 정적 판정 (의존 0)

        
WindowsInstallReadiness 옆에 같은 성격의 클래스를 하나 더 둔다. 스프링 빈이 아니고 저장소도 부르지 않는 순수 함수라 단위 테스트가 표의 칸과 1:1 로 붙는다.

        
// execution/engine/windows/WindowsDiskSelection.java   (신규 · 정적 · 의존 0)
DiskSelection judge(Optional<RaidVolume> osVolume,      // RaidVolumeRepository.findFirstBy…VolumeRole(id, OS)
                    RaidInventory inventory,             // guest_server_detail.raid_inventory_json
                    List<DiskInfo> disks)                // hardware_spec.disks (lsblk 순서 · 교차 확인용)

record DiskSelection(int diskId,          // 인벤토리 volumes 에서 찾은 인덱스
                     String expectedWwn,  // 그 볼륨의 WWN (소문자)
                     long expectedBytes,  // RaidVolume.usableBytes
                     Confidence confidence,
                     List<String> notes,  // 한국어 사유 (사용자 노출)
                     List<String> wire)   // 영문 코드 (기계 판독)

enum Confidence { CONFIDENT, BLOCKED }

        
규칙은 셋이다. ① 인벤토리의 volumes 는 컨트롤러 VD 번호순(VD0 · VD1 …)이고 그 순서가 diskpart 디스크 번호순과 같다(D1).
        0 B 가상 미디어는 실디스크 뒤에 서므로 실디스크 번호에 영향이 없다.
        ② OS 영역 볼륨을 wwn(우선) 또는 name(spvR 로 시작하는 이름)으로 그 목록에서 찾아 인덱스를 diskId 로 삼는다.
        ③ expectedWwn 은 그 볼륨의 WWN(소문자), expectedBytes 는 RaidVolume.usableBytes 다.

        
확신도에 중간이 없다 — Confidence 는 CONFIDENT 와 BLOCKED 둘뿐이다.
        "아마 0 번일 것" 으로 설치를 시작하면 그 아마가 wipe 를 부른다.
        WindowsInstallReadiness 가 세운 "절반만 갖춘 설치란 없다" 와 같은 결이다 (D-2).


        
Primitive Obsession 경계 — diskId 를 int 로 두는 이유는 그 값이
        응답 파일이 정수만 받는 자리에 그대로 들어가는 외부 계약이기 때문이다. 그 대신 도메인 의미를 지닌 나머지 값은 전부 타입으로 감싼다 —
        판정 결과는 DiskSelection record, 확신도는 Confidence enum, WWN 과 크기는 RaidVolume 의 필드에서 그대로 온다.
        int 하나가 서비스 시그니처를 떠도는 형태(bundleFor(…, int diskId) 를 여기저기 넘기는 식)는 만들지 않고, 항상 DiskSelection 을 들고 다닌다.


        
4-2. 준비도 편입 — 기존 진리표를 늘리지 않는다 (D-3)

        
WindowsInstallReadinessResolver.resolve 가 OS 볼륨과 인벤토리를 읽어 WindowsDiskSelection.judge 를 부르고,
        그 결과가 BLOCKED 면 사유(notes · wire)를 기존 PhaseReadiness 에 합류시킨다.
        WindowsInstallReadiness.judge 의 바디에는 줄을 늘리지 않는다 — 새 도메인 의미가 늘 때마다 기존 분기문이 같이 자라는 것을 CLAUDE.md 가 금지하기 때문이다.
        합류는 조립 지점에서 리스트를 한 번 병합하는 것이고, 판정 SSOT(Single Source of Truth — 단일 진실 출처)는 DiskSelection 하나다.
        게이트(서빙) · 상세 카드 · 하네스가 모두 그 하나를 본다.

        
judge(osVolume, inventory, disks)
    ├─ CONFIDENT ──▶ readiness READY ──▶ 서빙 (autounattend 의 DiskID = selection.diskId)
    └─ BLOCKED ────▶ readiness BLOCKED(+notes/wire) ──▶ HOLD 스크립트 · 카드에 대기 사유

D-1접근 A(서버 계산) + 사후 WWN 확증을 채택하고 B · C 는 E4-1-a-7 로 분리검증 줄기가 하나 · 배치 파서는 실기 형식 미실측 (§4 4-0)

            
D-2확신도는 CONFIDENT · BLOCKED 둘뿐 — 중간이 없다"아마 0 번" 으로 시작한 설치가 wipe 를 부른다

            
D-3판정은 별도 정적 클래스에 두고 resolve 가 합류시킨다. 기존 WindowsInstallReadiness.judge 에 줄을 늘리지 않는다분기문 확장 금지 원칙 · 판정 SSOT 를 하나로 유지

            
D-4확증 어긋남은 실패를 만들지 않는다 — 원장 경고 + 카드 표시사후라 되돌릴 수 없다. 실패로 만들면 설치된 게스트가 미완으로 남는다

            
D-5스키마 변경 0 — 완료 보고 필드는 JSON, 원장 두 필드는 status_meta JSON 안엔티티 컬럼이 늘지 않아 DDL 이 필요 없다

            
D-6물리 디스크 직결 혼재는 지원이 아니라 차단순서 · 식별이 미실측(D2 부분). 실측 후 E4-1-a-7 에서 연다

          
        


        
주의 — 배포 후 한 번 더 해야 하는 일

        
scriptsHash 가 바뀐다 — WindowsOemTemplates.SPV_REPORT_PS1 의 원문이 바뀌므로
        해시가 달라지고 대시보드 chip 이 "갱신 필요" 를 띄운다. 배포 후 [조립] 을 한 번 다시 실행해야
        게스트가 새 보고 스크립트를 받는다. 재실행 전에 설치된 게스트는 installedDiskUniqueId 를 보내지 않으므로
        확증이 미보고 로 남는다(오류가 아니다). Run 3 의 F-R3-1 과 같은 성질이므로 report 와 런북에 같은 자리에 적는다.

#질문권고

          
            
Q1카드의 targetDiskId 를 어디서 가져오는가 — 서빙 시점 값을 원장 메타에 남길 것인가, 조회 시 resolve 로 재계산할 것인가서빙 메타에 남긴다. 재계산은 인벤토리가 그 사이 바뀌면 실제로 나간 값과 달라진다 — 카드가 보여야 하는 것은 "무엇이 나갔는가" 다

            
Q2확증 어긋남을 카드에서 얼마나 강하게 보일 것인가경고색 배지 + 한 줄 설명까지. 알림 · 차단은 두지 않는다(사후 관측이므로)

            
Q3구 보고 스크립트로 이미 설치를 마친 게스트의 표시"미보고" 로 적고 경고로 취급하지 않는다. 조립 재실행 이후 게스트부터 확증이 붙는다

            
Q4직결 혼재 판별을 볼륨 수와 디스크 수 비교로만 할 것인가이번에는 그 하나로 한다(차단이 목적이라 과탐지가 안전 쪽). 실측 후 E4-1-a-7 에서 정밀화
