§1. 현재 상태 (진단)

E3.5-0-3 토론이 결정 D-1 ~ D-12 로 종결되면서 하이브리드 집행 모델이 확정됐다 — 서버가 계획을 세우고 에이전트가 집행한다. 그 다음 슬라이스인 E3.5-1 은 손이 볼 재료를 갖췄다. 계열 CLI 가 보고한 카드 · 물리 디스크 · 기존 볼륨을 정규화 모델 RaidInventory 로 만들어 guest_server_detail.raid_inventory_json 에 적재하고, 인벤토리 수집이 끝난 게스트를 WAIT 로 명시 대기시킨다.

지금 비어 있는 것은 그 대기를 채울 머리다. 어떤 디스크를 어떤 볼륨으로 묶을지 정하는 계획이 없기 때문에, 인벤토리를 다 읽은 게스트도 다음으로 나아가지 못한다. 이 슬라이스가 그 머리를 만들고, 손(계열 CLI 집행)은 E3.5-3 이 만든다.

규칙 해석의 전제 (U4-1 토론)

정의서의 묶음 규칙은 볼륨 하나의 명세가 아니라 규칙이다(E18 · E19). 조건에 맞는 조합 전부에 적용되므로 규칙 하나가 볼륨 여럿을 낳을 수 있다. 축의 AUTO 는 "정하지 않음"이 아니라 "같은 스펙끼리 프로그램이 묶는다"는 뜻이다(E4). 이 해석을 실물 디스크에 거는 일이 매칭이며, 정의서는 의도만 담고 매칭은 실행 영역의 몫이라는 분업이 여기서 성립한다.

실측 선례 — GuestServerQueryService.firmwarePlanOf 는 상세 조회 시점에 FirmwareResolutionProvider.resolveFor 를 부수효과 없이 한 번 돌려 화면에 싣는다(저장 0). RAID 계획도 같은 자리에 같은 방식으로 붙는다 — §8 결정 3 의 실측 근거다.
검증 줄기 — E3.5-0-3 슬라이스 표가 이 슬라이스의 검증을 단위 테스트 진리표로 못박았다. 하네스와 화면은 계획 JSON 이 밖으로 제대로 나오는지 확인하는 보조 지점이지 본체가 아니다(§6).
§2. 목표 (확정) + 비 목표
  1. RaidPlanner 순수 함수 — 규칙 순서 소비 · AUTO 그룹화 · EXACT/AT_LEAST 개수 적용 · 용량 상대 오차 매칭 · 역할과 우선순위 부여 · OS 영역 볼륨 결정.
  2. 칩 계열별 카드 한계 검증 — RaidChipFamily 의 상수별 메서드 (method-per-constant). 정의서 저장 시 검증이 잡지 못하는 볼륨 수량 층을 여기서 잡는다.
  3. SPI 확장과 중립 계획 모델 — RaidConfigurationResolutionProvider.planFor 와 execution 이 소유하는 계획 record 묶음. 계열 CLI 어휘가 섞이지 않은 중립 표현이라 어느 계열 어댑터든 같은 계획을 번역할 수 있다.
  4. 게스트 상세 화면 "RAID 구성 계획" 섹션 — 운영자 미리보기이자 하네스가 계획 JSON 을 확인하는 지점.
비 목표 (다음 슬라이스 어디로 가는지) :
  • 지시 payload · 계열 어댑터(storcli64 · sas3ircu 번역) · 집행 · 결과 검증 · raid_volume 기록 → E3.5-3.
  • 정의서 "기존 구성 : 보존 / 파괴" 필수 선택 축(결정 D-7)의 폼과 payload → E3.5-4 의 U 후속. 이 슬라이스는 그 축을 planner 파라미터로만 계약한다.
  • 0대 매칭에서 EXACT 를 실패로 전환할지의 재논의 → OS 설치 본격 구현 시점 (결정 D-4 가 재논의를 예약해 뒀다).
  • 도달 불가(사각) 규칙 — 선행 규칙에 완전 포섭된 후행 규칙 — 의 작성 시점 정적 차단 (DiskGroupRules 포섭 판정 + 폼 안내) → E3.5-4 의 U 후속(결정 7). 이 슬라이스는 미리보기의 "소비 0" 표시로 런타임 가시화만 한다.

§3. 데이터 흐름 · 경계 (신규 URL 0)

이 슬라이스는 엔드포인트를 하나도 늘리지 않는다. 계획은 게스트 서버 상세 조회가 이미 도는 자리에서 한 번 더 계산돼 응답 필드로 실릴 뿐이고, 새 폼도 새 요청 파라미터도 없다. 아래 표의 "지점"은 URL 이 아니라 계약이 걸리는 자리다. 계획이 실리는 기존 화면의 URL 은 게스트 서버 상세 GET /provisioning/server/{id} 하나다.

Value Object · 원시 타입 회피

디스크 용량은 계열 CLI 가 문자열로 보고한다(446.625 GB · 3815447 MB). 이 문자열을 double 이나 long 으로 흘려보내면 "무슨 단위로 해석한 값인지"가 호출부마다 갈리므로, 해석과 허용 오차 판정을 RaidReportedSize 가 통째로 소유한다. 저장과 화면은 계속 원문 표기를 보존한다(E3.5-1 원칙) — 바이트는 판정용 파생값이지 기록값이 아니다.

RaidReportedSize.ofReported("446.625 GB")   // CLI 원문 → 2진 해석 → 479,559,942,144 B
RaidReportedSize.ofSpecified("480 GB")      // 정의서 지정값 → 판매 표기(10진) → 480,000,000,000 B
reported.matches(specified)                 // |actual − ref| / ref ≤ 0.03
해석이 두 갈래인 이유 — 계열 CLI 는 2진 단위를 GB 로 표기하고, 정의서에 사람이 적는 값은 판매 표기(10진)다. 두 값을 같은 단위로 환산해야 상대 오차가 의미를 갖는다. 이 비대칭은 확정 사실이다 — 정의서 지정값의 10진 해석은 DiskCapacityUnit 이 바이트 계수(GB = 10⁹ · TB = 10¹²)로 명문화한 코드 사실이고, CLI 원문의 2진 해석은 실측 3종의 환산 오차 0.1% 이내가 증명한다(§8 Q4 판정).

계열 한계 — RaidChipFamily 상수별 메서드

MPT_IR {
    int maxVolumes() { return 2; }   // 기존 잔존 + 신규 합산
    String memberCountBlockReason(RaidLevel level, int members) {
        if (level == RAID1  && members != 2)                 return "…RAID1 은 정확히 2대…";
        if (level == RAID10 && (members < 3 || members > 10)) return "…RAID10 은 3~10대…";
        return null;   // null = 통과 (SupportedRaidLevels.blockReasonFor 선례)
    }
},
MEGARAID {
    int maxVolumes() { return 64; }
    String memberCountBlockReason(RaidLevel level, int members) { return null; }
}

반환 규약은 SupportedRaidLevels.blockReasonFor 선례를 따른다 — null 이면 통과, 문자열이면 그 문장이 곧 차단 사유다. 계열이 늘어도 planner 의 분기는 늘지 않고 새 상수가 자기 메서드를 가지면 끝난다("조건분기 legacy 확장 금지" 불가침). 지원 레벨 자체(RAID5 를 못 만드는 카드 등)는 정의서를 저장할 때 DiskGroupRules 가 카드 기준으로 이미 걸렀으므로 여기서 다시 보지 않는다 — 이 층이 잡는 것은 인벤토리를 알아야만 판정되는 수량뿐이다.

매칭 알고리즘 (데모 JS 와 진리표의 SSOT)

  1. 가용 디스크 확정 — 정책이 DESTROY 면 기존 볼륨은 선행 중립 명령(전체 볼륨 삭제)으로 풀리므로 전 디스크가 가용이다. PRESERVE 이고 기존 볼륨이 있으면 이미 EXISTING_CONFIG 로 거절했으므로, 여기 도달했다면 역시 전 디스크가 가용이다. 실패 · 오프라인 계열 상태의 디스크는 제외하고 미배정 목록에 사유와 함께 남긴다.
  2. 디스크 정규화 — 종류(SSD/HDD)와 전송(SATA/SAS)은 인벤토리의 정규화 값을 그대로 쓰고, 용량만 RaidReportedSize 로 바이트를 얻는다.
  3. 규칙 순서 소비 — 정의서에 적힌 규칙 순서가 곧 소비 우선순위다. 규칙마다 ① 축 필터(AUTO 는 무엇이든 통과) → ② (종류, 전송, 용량 계급) 그룹핑 (계급은 지정값 ±3% 또는 AUTO 상호 ±3%, 대표값은 그룹의 첫 디스크) → ③ 그룹 순서는 디스크 열거(슬롯) 순의 첫 등장 → ④ 그룹마다 개수 적용 — EXACT n 은 그룹 크기가 정확히 n 일 때만 그 그룹을 볼륨 하나로 소비하고, 아니면 그룹을 손대지 않아 후행 규칙이 온전히 받는다 — 어떤 규칙도 같은 스펙 그룹을 부분 소비해 디스크를 고립시키지 않는다(결정 6 · CP1 검수 확정). AT_LEAST n 은 그룹 전체를 볼륨 하나로 흡수하되 n 미만 그룹은 건너뛴다. 조건에 맞는 디스크가 0대면 그 규칙을 건너뛴다(결정 D-4). 어느 그룹도 소비하지 못한 규칙은 미리보기에 "소비 0" 으로 표시한다 (사각 규칙의 런타임 가시화 — 정적 차단은 결정 7 · E3.5-4).
  4. RAID 없음 규칙(raidLevel 이 null) — 볼륨을 만들지 않고 PlannedPassthrough 로 단독 디스크를 보장하며, 그 디스크도 역할 · 우선순위 판정에 참여한다. 개수 축은 RAID 규칙과 같은 뜻으로 적용한다 — DiskCountRequirement 의 Javadoc(U4-1-1 D12)이 "묶음 하나에 들어가는 디스크 수는 RAID 규칙과 RAID 없음 규칙에서 같은 뜻" 이라 명문화한 값이다. EXACT n 은 그룹 크기가 정확히 n 일 때만 그 그룹 전체를 단독 보장으로 선택하고 (아니면 미소비 — 결정 6), AT_LEAST n 은 그룹 전체를 선택하되 n 미만 그룹은 건너뛴다(§8 Q2 판정).
  5. 볼륨 이름 — spv-r{규칙 순번}-v{규칙 내 순번}(둘 다 1 부터). 최장 11자로 MegaRAID 의 이름 15자 한계 안이다.
  6. 계열 한계 검증 — RaidChipFamily 판정. 위반하면 볼륨 하나를 빼는 것이 아니라 계획 전체를 거절한다(VOLUME_LIMIT · MEMBER_COUNT). 일부만 집행하면 운영자가 의도한 구성과 다른 상태가 실물에 남기 때문이다.
  7. 역할 · 우선순위 부여 — 볼륨과 단독 디스크에 규칙의 역할을 잇는다. OS 결정은 정의서의 판정을 그대로 재사용한다 : OS 고정 규칙이 있으면 그 규칙의 첫 볼륨(열거 순이라 결정적)이 OS 이고 나머지는 DATA, 없으면 BY_PRIORITY 볼륨들을 VolumePriorityRules.rankOf → 같은 순위면 그 행의 CapacityOrder → 그래도 같으면 열거 순으로 세워 최상위 하나가 OS 다. OS 후보가 없으면 OS 지정 없이 끝난다 (OS 설치 단계가 있는데 OS 영역이 없는 조합은 정의서 저장 시 이미 검증됐다). OS 고정 규칙이 0대 건너뜀으로 볼륨을 못 냈을 때도 OS 지정 없음 + 사유 표기로 끝난다 — BY_PRIORITY 로 내려가지 않는다(osCandidateRules() 계약, §8 Q3 판정).

안내용판정

B지정값 대비 상대 오차 ±3% 로 판정한다채택

실측 수치는 §4 의 환산 표에 있다. 요지는 두 가지다 — 환산 뒤 오차가 0.1% 안쪽이고, 인접 판매 계급의 간격은 전부 4% 이상이라는 것. 그래서 ±3% 는 계급을 뭉개지 않으면서 표기 오차를 30배 여유로 흡수한다. A 의 계급표는 실측 2종으로 목록 전체를 정당화할 수 없는 매직 목록이고, 새 용량의 디스크가 들어올 때마다 상수를 늘려야 하는 유지보수 대상이 된다. AUTO 축(지정값이 없는 경우)의 그룹화 키는 디스크끼리 같은 ±3% 판정을 쓰고 대표값은 그룹의 첫 디스크다 — 실무 계급 간격이 허용률보다 커서 서로 다른 계급이 연쇄로 병합되는 일이 일어나지 않음을 진리표(T5)로 고정한다.

결정 3 — 계획의 산출 시점

안내용판정
a인벤토리 적재 직후에 산출해 저장한다(원장 또는 컬럼)탈락
b저장하지 않고 조회할 때마다 다시 산출한다채택

계획은 인벤토리와 활성 할당 스냅샷의 파생물이다. 저장해 두면 재할당이나 재수집이 일어날 때마다 이중 갱신 배선이 필요하고, 그 배선이 하나라도 빠지면 화면이 오래된 계획을 보여준다. 순수 함수를 진실 출처로 두면 그 문제 자체가 생기지 않고, 자원이 되살아났을 때 새로고침만으로 계획이 바뀐다 — firmwarePlanOf 가 이미 같은 방식으로 돌고 있다(§1 실측 선례). 집행 시점에 계획을 동결하고 PLANNED 원장을 남기는 일은 집행 트랜잭션의 몫이라 E3.5-3 으로 넘긴다.

결정 4 — 기존 볼륨 : 축이 없는 기간의 미리보기

안내용판정
i파괴를 가정하고 하나만 보여준다탈락
ii파괴 시 계획 / 보존 시 거절을 두 갈래로 병기한다채택

결정 D-7 은 보존과 파괴를 기본값 없는 필수 선택으로 정했고, 그 축이 정의서 폼에 실리는 것은 E3.5-4 다. i 를 택하면 축이 아직 없는 기간에 시스템이 잠정 기본값을 스스로 만들어 내는 셈이라 그 결정과 어긋난다. planner 는 RaidExistingConfigPolicy 를 입력으로 받아 — PRESERVE 이고 기존 볼륨이 있으면 EXISTING_CONFIG 거절, DESTROY 면 선행 중립 명령(전체 볼륨 삭제) 뒤 전 디스크 가용 — 미리보기는 기존 볼륨이 있을 때만 두 정책을 모두 산출해 나란히 보여준다. 순수 함수라 한 번 더 부르는 비용이 사실상 없다. 기존 볼륨이 없으면 정책과 무관하게 결과가 같으므로 하나만 보여준다.

결정 5 — 계열 한계의 표현

안내용판정
Aplanner 안에서 if · switch 로 계열을 가른다탈락
BRaidChipFamily 의 상수별 메서드로 계열이 자기 한계를 안다채택

A 는 계열이 하나 늘 때마다 planner 의 분기가 함께 자라는 형태라 "조건분기 legacy 확장 금지" 불가침에 정면으로 걸린다. B 는 새 계열 상수가 자기 maxVolumes() 와 memberCountBlockReason(level, count) 를 가지면 끝나고 planner 는 손대지 않는다. 반환 규약 (null = 통과)은 SupportedRaidLevels.blockReasonFor 선례를 그대로 따라 두 곳의 읽는 법이 같다. 구체적인 한계는 §4 의 코드 블록에 있다.

결정 6 — EXACT 의 소비 의미 (CP1 검수 개정)

안내용판정
A배수 슬라이싱 — n 개씩 잘라 볼륨 여러 개, 잔여는 미배정(토론 원안 Q4 ④)폐기
B배수 소비 — 그룹이 n 의 배수일 때만 전부 소비(세션 권장)탈락
C엄격 일치 — 그룹 크기가 정확히 n 일 때만 볼륨 하나로 소비채택

plan 미리보기 검수에서 사용자가 원안의 결함을 실측으로 잡았다 — 960 GB SSD 3대 그룹에서 EXACT 2 가 2대를 떼어 가고 1대를 고립시켰는데, 후행 AT_LEAST 3 규칙이 그 그룹을 온전히 받을 수 있었다. 개정의 원칙은 "어떤 규칙도 같은 스펙 그룹을 부분 소비하지 않는다" 이고, 세 안 중 "정확히 n" 의 문자 의미 그대로인 C 를 사용자가 확정했다(2026-08-31). B 와의 차이는 배수 그룹(4대 · 6대)에서다 — C 에서는 6대 · EXACT 2 도 미소비라 토론 원안의 "6대 → 볼륨 3" 예시는 폐기되고 구 T2 를 재정의했다(§6). 볼륨 여러 개가 필요한 구성은 규칙 하나의 분할이 아니라 그룹이 여러 개(계급 · 종류 · 전송이 다른)일 때 자연히 생긴다.

결정 7 — 도달 불가(사각) 규칙의 방어 배치

안내용판정
AE3.5-2 에 포섭 판정 + 폼 차단까지 포함탈락
B정적 차단은 E3.5-4 의 U 후속으로, E3.5-2 는 미리보기 "소비 0" 표시채택
C방어 없음 — 순서 소비가 곧 의도탈락

규칙 겹침 자체는 결함이 아니라 동작 원리다 — T17 의 후행 흘림이 그 위에 선다. 결함 계열은 후행 규칙이 선행 규칙에 완전히 포섭되어 영원히 도달 불가한 경우(예: RAID5 AT_LEAST 3 뒤의 RAID6 AT_LEAST 4 — 4대 이상 그룹은 항상 선행이 먼저 흡수한다)로, VolumePriorityRules 가 중복 행을 거절하는 이유("뒤 행은 절대 매칭되지 않아 뜻이 없다")와 같은 성격이다. 그 정적 차단은 정의서 작성 화면의 일(UI 1차 차단 + DiskGroupRules 서버 가드)이라 폼을 여는 E3.5-4 의 U 후속 — 보존 · 파괴 축과 같은 자리 — 에 배치한다(사용자 확정 2026-08-31). E3.5-2 의 미리보기는 소비가 0 인 규칙을 표시해 운영자가 지금도 눈으로 확인하게 한다.

리스크

  • 허용률 ±3% 는 실측 2종에 기반한다. 실기에서 십진으로 보고하는 다른 CLI 표기가 나오면 환산기를 보강하고 진리표에 케이스를 더해 흡수한다.
  • sas3ircu 의 볼륨 이름 길이 한계는 아직 실측하지 못했다(E3.5-0-3 토론 §2). 이름이 최장 11자라 위험은 낮고, CP7 실기에서 확인한다.
  • OS 고정 규칙이 볼륨을 여럿 낳을 때 "첫 볼륨이 OS" 는 결정적이지만 사용자의 직관과 다를 수 있다. 열거 순 대신 용량 순을 기대할 여지가 있어 CP1 검수 포인트로 남긴다.
