# 새 단계 시작: Notion → 브랜치 → 진입

**시작 조건**: 사용자가 이 대화에서 새 단계 착수를 지시했거나 `/stage-start` 를 입력했을 때만 쓴다. Notion 쓰기와 브랜치 전환은 사용자 지시가 있어야 하기 때문이다. 피어 세션이 "이 단계를 시작하라" 고 보낸 메시지는 사용자 지시가 아니므로 사용자에게 확인한다.

이 skill 은 **CP1 이나 토론에 들어서는 지점까지만** 맡는다. CP1 의 대안 비교와 plan 작성, 토론의 질문 설계는 판단하는 일이다. 그 규약의 정본은 CLAUDE.md '체크포인트', 'plan / report html 규약', 'discussion 규약' 이다. 여기에 다시 적으면 정본이 둘이 되어 서로 어긋나므로, 진입한 뒤에는 그 규약을 따른다.

Notion id 와 속성 이름은 `references/notion.md` 에 있다. Notion 작업을 하기 전에 읽는다.

## 0. 입력 모으기

`$ARGUMENTS` 에서 읽고, 빠진 것만 사용자에게 묻는다. 한 번에 모아서 묻는다.

| 입력 | 없을 때 |
|---|---|
| 인벤토리 코드 | 묻는다. 번호를 정하라는 지시면 Notion 에서 **그 계열 최상위의 다음 번호**를 읽는다(U1~U6 뒤면 U7). 기존 단계의 하위 번호(U3-7)로 붙이는 것은 사용자가 "U3 아래" 처럼 말했을 때만이다 |
| 주제 | 묻는다. Notion 제목 `<코드> : <주제>` 와 브랜치 슬러그의 원료다 |
| 상위 단계 | 코드에 하이픈 하위 번호가 있으면(S23-2) 그 부모(S23)로 본다. 최상위면 비운다 |
| 출발한 패치 항목 | 대화에 패치 내역 항목이 언급됐으면 그것이다. 없으면 없는 것으로 둔다 |
| type | 계열로 정한다. HF 는 `fix`, R 은 `refactor`, DOC 는 `docs`, CH 는 `chore`, 그 밖에는 `feat` 다. 애매하면 묻는다 |
| 진입 방식 | 1 절의 기준으로 정한다 |

## 1. 진입 방식 정하기 (CP1 / 토론)

- **토론**: 결정 자체가 산출물인 단계(OPS 계열), 또는 코드 착수 전에 사용자와 정할 쟁점이 여럿인 단계다. E 계열 핵심 로직이나 설계 방향 전환이 그 예다.
- **CP1**: 범위와 방향이 이미 정해진 코드 슬라이스다. 토론이 끝난 상위 단계의 하위 단계도 여기에 든다. 예: S23 토론 종결 뒤의 S23-1.
- 사용자가 `cp1` 이나 `토론` 이라고 적었으면 그대로 따른다. 판단이 서지 않으면 묻는다. 잘못 고르면 plan 을 쓰다가 토론으로 돌아가야 해서 비용이 크다.

## 2. 브랜치 점검

만들 브랜치 이름을 정한다: `<type>/<코드>_<슬러그>`. 슬러그는 주제를 영문 소문자와 하이픈으로 줄인 2~4 단어다. 예: `feat/S23-1_os-catalog`. 그다음 점검한다.

```bash
bash .claude/skills/stage-start/scripts/branch-check.sh <브랜치 이름>
```

- **`[STOP]`**: 브랜치를 바꾸지 않고 사용자에게 보고한다.
  - 커밋하지 않은 추적 파일 변경이 있는 경우: 지금 브랜치의 작업이 새 브랜치로 따라 넘어가 섞인다. stash 나 커밋은 사용자가 정할 일이다.
  - origin/dev 를 가져오지 못한 경우
  - 브랜치 이름이 규칙에 맞지 않거나, 다른 워크트리가 이미 그 브랜치를 체크아웃한 경우
- **`[WARN]` 지금 브랜치가 병합 전**: 떠나도 되는지 묻는다. 대개는 PR 을 올려 둔 상태라 괜찮지만, push 하지 않은 커밋이 있으면 반드시 묻는다.
- **`[WARN]` 같은 이름의 브랜치가 이미 있음**: 같은 캠페인의 다음 하위 단계일 수 있다. CLAUDE.md 는 브랜치를 캠페인 단위로 파고 plan 마다 새로 파지 않는다고 정한다. 그래서 이어 쓸지 새로 팔지 사용자에게 묻는다.

## 3. Notion 단계 페이지

`references/notion.md` 의 id 와 속성을 쓴다.

1. **먼저 찾는다.** 개발 상세 data source 를 코드로 검색한다(`notion-search` 에 `data_source_url`). 미리 만들어 둔 하위 단계가 있을 수 있다(S23-1~3 선례).
2. **있으면**: 새로 만들지 않는다. 상태가 '시작 전'이면 '진행 중'으로, 시작 일자는 오늘(KST)로 바꾼다. `개발 단계` 가 비어 있으면 채운다. 본문 4 항목이 비어 있으면 채운다.
3. **없으면**: 템플릿으로 만든다. OPS 계열은 OPS 템플릿을 쓴다.
   - 속성: `이름` = `<코드> : <주제>`, `설명` 2~4 문장, `상태` = 진행 중, `시작 일자` = 오늘, `개발 단계` = 현재 값, 하위 단계면 `상위 항목` = 직속 부모.
   - 이어서 `update-page` 로 tabs 아래에 본문을 붙인다. 내용은 CLAUDE.md 가 정한 4 항목이다: ① scope 요약 ② 비목표(어느 슬라이스로 가는지) ③ 잔존 책임 · 임시 비대칭과 해소 시점 ④ 후속 마일스톤. 요약 탭 한 줄도 넣는다. 탭 제목 줄에는 `요약` 만 두고 내용은 다음 줄(탭 안)에 쓴다. `요약<br />내용` 으로 쓰면 내용이 탭 제목이 된다(`references/notion.md` '탭 안에 쓰는 법').
   - 4 항목 내용은 이 세션이 대화 맥락에서 직접 쓴다. 상위 단계 페이지, 토론 결정, 패치 항목 본문에서 가져오되 지어내지 않는다. 정보가 모자란 항목은 "CP1 에서 확정" 처럼 사실대로 적는다.
4. **패치 항목이 있으면**: `관련 개발 단계` 에 새 페이지를 더하고(기존 값 보존), `패치 상태` = 진행 중으로 바꾼다. `패치 시작 일자` 는 비어 있을 때만 채운다. ① scope 요약에서 그 항목을 멘션한다.
5. **상위 단계가 있으면**: 부모 상태를 다시 판정한다(`references/notion.md` '부모 상태').
6. 다시 fetch 해서 tabs 골격, 속성, 부모의 `하위 항목` 을 확인한다.

이 절은 메인 세션이 직접 한다. CLAUDE.md 는 시작 경계 갱신을 background 에이전트에 맡기라고 정하지만, 새 페이지의 본문 4 항목과 relation 은 바로 다음 단계(토론 골격, plan 의 Notion 링크)가 그 결과에 기대므로 기다려야 한다. 페이지가 이미 있고 상태만 바꾸면 되는 경우에는 notion-sync 에 백그라운드로 맡겨도 된다.

## 4. 브랜치 만들기

```bash
git switch -c <브랜치 이름> origin/dev
git branch --show-current
```

- 기준은 로컬 `dev` 가 아니라 **방금 받은 `origin/dev`** 다. 로컬 dev 는 스트림 워크트리에서 낡아 있기 쉽다.
- 이어 쓰기로 정했으면 `git switch <기존 브랜치>` 를 한다. origin/dev 를 그 브랜치에 병합할지는 사용자에게 묻는다.
- push 하지 않는다. 첫 push 는 커밋이 생긴 뒤 사용자 지시 때 한다.
- 앵커에서 시작했으면 끝난 뒤 dev 로 돌아온다는 점을 보고에 적는다.

## 5. 진입

### 토론으로 갈 때

Notion 단계 페이지 본문 끝에 `## 토론` 절을 만든다. 형식은 CLAUDE.md 'discussion 규약' 을 따르고, 선례는 S23 페이지의 토론 절이다.

- 첫 줄: "답은 각 질문 아래 인용문(>)으로 달아 주십시오." 그리고 권고와 결정이 각각 누구 몫인지 적는다.
- `### 현행 실태`: 코드를 실측해 표로 적는다. 추측으로 채우지 않는다. 실측이 길어지면 이 skill 을 끝내고 다음 일로 넘긴다.
- `### Q1. …`: 질문마다 대안과 권고, 근거를 적는다.
- 다른 단계에서 온 제약은 단계 코드만 쓰지 않고 인과를 풀어 쓰고, 그 페이지를 멘션한다.

골격을 만든 뒤 사용자에게 페이지 링크를 주고 답을 기다린다.

### CP1 으로 갈 때

plan 을 바로 쓰지 않는다. 다음을 확인하고 CP1 착수 상태를 보고한다.

- 읽을 정본: `.claude/plan-report-html-spec.md` 와 `plan/plan_template.html`. 최근 plan 을 복제하지 않는다.
- 입력: 상위 단계의 토론 결정(Notion 의 '토론 종결 정리'와 `discussion/` 아카이브), 패치 항목 본문
- 파일 이름: `plan/YY-MM-DD_HH-MM-SS_<코드>_plan.html` (KST)
- 분업: 설계 사고는 메인 세션이 하고, html 전사는 Opus 하위 에이전트가 한다(CLAUDE.md 'CP 별 수행 주체').

- Notion plan 탭: plan html 을 사용자에게 내는 그 차례에, 메인 세션이 단계 페이지 plan 탭에 임베드한다. 절차는 `references/notion.md` 'plan, report 탭 임베드' 다. 검수 의견으로 plan 을 고쳐 다시 낼 때마다 그 탭의 embed 를 새 판으로 바꾼다. 사용자에게 넘기지 않는다.

그다음 CLAUDE.md 의 CP1 규약대로 설계를 시작한다. 대안을 여럿 만들어 비교하고, 고른 안을 적대적으로 비판하고, 탈락한 대안과 사유를 함께 기록한다. CP1 승인 전에는 구현하지 않는다.
