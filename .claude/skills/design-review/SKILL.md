# 디자인 규약 점검

규약의 정본은 저장소 루트의 `DESIGN.md` 다. 이 스킬은 규약을 담지 않고 **점검하는 순서**만 담는다. 규칙 문장을 여기에 옮겨 적지 않는다(정본이 둘이 되면 어긋난다). 판정에 쓰는 문장은 매번 `DESIGN.md` 에서 연다.

규약을 바꾸는 판정(DESIGN.md 행 추가, 새 컴포넌트 변형)은 디자인 스트림(`ServerProvision-design-experiment`)이 내린다. 다른 스트림은 이 스킬로 1차 점검을 하고, 규약을 바꿔야 하면 디자인 스트림에 diff 와 함께 묻는다.

## 절차

### 1. 원문을 연다

점검 대상에 해당하는 절을 `DESIGN.md` 에서 연다. 어느 절인지는 `references/checklist.md` 의 표를 본다.

- 판정 근거는 원문 문장을 그대로 옮겨 인용한다. 기억으로 풀어 쓴 말을 따옴표로 감싸지 않는다(2026-11-17, 풀어 쓴 문장을 원문처럼 인용해 두 번 정정했다). 풀어 쓸 때는 따옴표 없이 쓰고 절과 행 번호를 붙인다.
- 원문이 낡았으면(코드와 다르면) 판정과 별도로 그 사실을 적는다. 예: Miller 절이 이미 없어진 모달을 사용처로 적고 있었다.

### 2. 새 이름을 받기 전에 기존 부품을 찾는다

새 `n-` 클래스나 새 부품이 제안되면, 받기 전에 같은 뜻의 기존 부품이 있는지 찾는다.

```bash
# 같은 계열 접두로 정의와 사용처를 본다
rtk proxy grep -rn "n-lookup-" src/main/resources/static | grep -v "\.js:"
rtk proxy grep -rln "n-option-row" src/main/resources/templates
```

- 같은 뜻의 이름이 이미 있으면 두 번째 이름을 만들지 않는다(8절). 2026-11-17 에 제안된 `n-lookup-row-blocked` 는 `n-lookup-row-disabled` 와 같은 뜻이었고, "라디오 카드" 는 이미 있는 `n-option-row` 였다.
- 쓰는 곳은 있는데 5절 고르기 표에 행이 없는 부품은 규약의 빈칸이다. 판정과 별도로 적는다.
- 다단 선택은 `n-miller` 를 통째로 재사용하는 경우인지 본다(9절). 개별 `n-miller-*` 를 떼어 쓰지 않는다.

### 3. 같은 커밋 규칙을 본다

- 새 클래스의 CSS 정의, 그 클래스를 쓰는 마크업, `DESIGN.md` 의 행은 한 커밋에 들어간다. 정의 없는 `n-` 클래스가 마크업에 있으면 `DesignConventionTest` 가 막는다.
- 그래서 다른 스트림의 기능 커밋에 들어갈 규약 행은 그 스트림이 같은 커밋에 넣고, 디자인 스트림은 커밋 전 diff 를 검수한다. 디자인 스트림이 따로 넣으면 병합 순서에 따라 규약과 코드가 어긋난 상태가 dev 에 생긴다.
- 화면 CSS 가 컴포넌트를 덮을 때는 치수만 덮는다(9절). 줄바꿈 여부나 선 처리처럼 동작을 바꾸는 것은 컴포넌트 시트에 변형으로 더한다.
- 스크립트 표지는 `data-*` 다. 시각 규칙이 없는 감싸기 요소에는 클래스를 달지 않는다.

### 4. CSS 는 렌더해서 확인한다

제안하는 CSS 와 마크업은 보내기 전에 앱 시트 위에 렌더한다. 앱을 띄우지 않아도 된다.

```bash
cd scripts/design-audit
node snippet-check.mjs <조각.html> <출력 폴더> 1440,1024,390 --sheets css/miller.css --css <제안.css>
```

- 조각 파일은 body 안 마크업만 담는다. 스크래치 폴더에 둔다.
- 결과로 폭마다 스크린샷, 겹친 구분선(5절), 페이지와 칸 넘침, 7절 표기 의심이 나온다.
- **스크린샷은 눈으로도 본다.** 검사는 숫자로 안 잡히는 것을 놓친다. 2026-11-17 에 말줄임에 가려 사라진 사용 중단 점, 1024 이하에서 폭이 0 이 된 목록 열을 스크린샷으로 찾았다.
- 1024 이하 배치(열 쌓임)와 넓은 폭을 둘 다 본다. 컴포넌트의 좁은 폭 규칙은 새 조합에서 숨은 결함을 드러낸다.
- 화면 단위 점검(로그인한 샌드박스)은 같은 폴더의 `copy-scan`, `line-scan`, `overflow-scan` 이다(`scripts/design-audit/README.md`).

### 5. 문구는 7절에 대어 본다

화면 문구는 물론, **판정 회신에 예로 드는 문구도** 7절에 대어 본다(2026-11-17, 빈 상태 예시로 '~음' 꼴을 들었다가 정정했다).

- 문체, 금지 꼴, 기호, 내부 식별자, 같은 사실 되풀이를 `references/checklist.md` 의 문구 항목대로 본다.
- 막는 사유가 흐린 글자나 브라우저가 띄우지 않는 자리(셀렉트 option 의 title, disabled 요소의 tooltip)에만 있지 않은지 본다. 사유는 보이는 글자로 막힌 조작 곁에 둔다(7절 위계 표의 차단 사유 행).
- 서버 문장을 화면에서 잘라 쓰지 않는다. 화면에 일부만 필요하면 도메인이 그 부분을 따로 내주고, 서버 문장은 그 부분을 조립해 만든다.

### 6. 보고받은 것은 직접 확인한다

다른 세션이 "반영했다", "고쳐졌다" 고 보고하면, 판정 전에 그 워크트리의 파일을 직접 연다.

- 고친 줄이 실제로 그 자리에 있는지 본다(`rtk proxy grep -n`).
- 스크린샷과 코드가 어긋나면 파일 수정 시각과 스크린샷 시각을 견준다(`stat -f "%Sm %N" <파일>`). 코드가 먼저 고쳐졌다면 원인은 실행 중인 빌드나 저장된 데이터다.
- 조건과 출력이 같은 출처를 쓰는지 본다. 예: 사유 줄을 보이는 조건과 찍는 값이 늘 함께 참인지.

### 7. 회신 형식

항목마다 아래를 쓴다. 첫 줄에 결론(통과, 고칠 것 몇 건)을 둔다.

| 칸 | 내용 |
|---|---|
| 판정 | 통과, 고칠 것, 사용자 판단 몫 중 하나 |
| 근거 | `DESIGN.md` 원문 인용과 절, 행 번호. 실측이면 파일과 행 |
| 정의 | 고칠 것이면 그대로 붙일 수 있는 CSS 와 DESIGN.md 문구, 넣을 자리 |
| 확인 | CP5 에서 무엇을 어느 폭으로 볼지 |

- 정책이나 UX 갈림길(예: 막을 자리를 OS 단계로 올릴지)은 판정하지 않는다. 두 길과 각각의 결과를 적어 사용자에게 넘긴다.
- 넣을 자리를 말할 때는 주석까지 포함해 말한다. "미디어 쿼리 앞" 은 그 미디어 쿼리를 설명하는 주석보다 앞이라는 뜻이다(2026-11-17, 이 모호함으로 블록이 주석과 규칙 사이에 끼었다).
- 저장소 문서에 들어갈 새 글에는 '·' 와 '—' 를 쓰지 않는다. 옛 행에 남은 것은 따라 쓰지 않는다.

## 점검 뒤

- 디자인 스트림이 점검한 발견은 `docs/design-audit.md` 의 표에 번호(D-n)를 이어 적는다.
- 규약을 바꿨다면 `DESIGN.md` 와 `DesignConventionTest` 를 같은 커밋에서 고친다.
- 이 스킬의 절차가 틀렸거나 빠진 것을 실제로 겪었으면, 그 일을 근거로 이 파일을 고친다. 날짜와 겪은 일을 한 줄로 남긴다.
