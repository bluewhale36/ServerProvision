# 로컬 샌드박스

CP5 마다 손으로 `run.sh` 를 짜던 일을 스크립트 하나로 바꾼다. 손으로 짤 때 반복해서 겪은 함정을 스크립트가 처리한다.

- env 가 하나라도 빠지면 기동 단계에서 바로 실패한다. 빈 값이라도 넣어야 하는 `RECONCILIATION_SCAN_EXTRA_ROOTS` 가 대표적이다.
- 실행 중인 jar 를 빌드가 같은 inode 로 덮어쓰면 JVM 이 `NoClassDefFoundError` 로 죽는다. 그래서 jar 를 복사해 그 복사본을 실행한다.
- PATH 의 기본 java 는 17 이다. 그래서 스크립트가 Java 21 을 찾아 쓴다.
- 다른 세션의 샌드박스와 포트가 겹치지 않게 빈 포트를 고른다. 떠 있는 프로세스, 컨테이너, 멈춰 있는 샌드박스의 `run.sh` 를 모두 확인한다.

## 새로 만들기 전에 (2026-11-21 사용자 지시)

- **세션마다 샌드박스는 하나만 둔다.** 새 슬라이스를 검증할 때는 그 세션이 이미 가진 샌드박스에 `restart <이름>` 으로 새 jar 를 올려 다시 쓴다. 슬라이스 DDL 은 그 DB 에 적용한다(`sql <이름>`).
- **`up` 으로 새로 만드는 것은 사용자 허가를 받은 뒤에만 한다.** 두 슬라이스를 동시에 띄워야 하는 경우처럼 다시 쓸 수 없는 사정이 있을 때 그 사정을 적어 묻는다. 샌드박스마다 jar 와 DB 볼륨이 쌓여, 11-21 정리 때 앵커에만 폴더 22 개와 컨테이너 4 개가 남아 있었다.
- 끝난 샌드박스는 `down <이름> --rm-db` 로 내리고 폴더는 휴지통(~/.Trash)으로 옮긴다.

새 DB 에는 관리자가 없어서 `/signup` 이 열린다(MA8 부트스트랩). 스크립트는 기동하자마자 그 화면으로 관리자 계정을 만들고, 첫 계정은 최고 관리자가 된다.

## 쓰는 법

```bash
S=.claude/skills/sandbox/scripts/sbx.sh
$S up hf33                         # 새 샌드박스(빈 DB, ddl-auto=update 로 스키마 생성). 사용자 허가 뒤에만
$S up s23-1 --clone spv-sandbox-db-s8   # 기존 샌드박스 데이터를 복제해 시작
$S restart hf33                    # 코드를 고친 뒤: 재빌드 → jar 복사 → 앱만 재기동
$S restart hf33 --no-build         # 같은 jar 로 재기동
$S down hf33                       # 앱 정지 + DB 컨테이너 정지(데이터 유지)
$S down hf33 --rm-db               # DB 컨테이너까지 삭제
$S status                          # 이 머신의 샌드박스 컨테이너 · 앱 포트
$S sql hf33 -e "SELECT ..."        # 샌드박스 DB 접속
```

- 이름은 인벤토리 코드를 소문자로 쓴다(`hf33` · `s23-1`). 디렉토리는 `<워크트리>/sbx-<이름>/` 이고 컨테이너는 `spv-sandbox-db-<이름>` 이다.
- 세션 쿠키 이름은 샌드박스마다 `SPV_SBX_<이름 대문자>` 다(예: `SPV_SBX_S23_2_1`). 같은 브라우저로 여러 샌드박스에 로그인해도 서로의 세션을 덮어쓰지 않는다. `up` 때 `run.sh` 에 들어가므로 그 전에 만든 샌드박스는 `extra.env` 에 `SERVER_SERVLET_SESSION_COOKIE_NAME` 을 직접 적는다.
- 슬라이스 고유 env(Windows 설치 소스, mock-redfish 주소 등)는 `sbx-<이름>/extra.env` 에 `export …` 로 적는다. `run.sh` 가 그 파일을 읽는다. 그런 다음 `restart --no-build` 로 반영한다.
- 공용 자료(BIOS 자료 · PXE 자산 · 보드 목록 덮어쓰기)는 앵커의 `sbx-e33/` 을 기본으로 쓴다. 다른 위치면 `SBX_SHARED=<경로>` 로 넘긴다. 없으면 경고만 내고 띄운다. 이 경우 게스트 상세와 PXE 화면 일부가 동작하지 않는다.

## 계정과 비밀값

- 계정과 DB 비밀번호는 **저장소 밖** `~/.config/serverprovision/sandbox.env` 에서 읽는다(권한 600). 파일이 없으면 스크립트가 틀을 만들고 멈춘다. 관리자 비밀번호를 채운 뒤 다시 실행한다.
- 로컬 샌드박스 계정은 콘솔 답변에 그대로 적어도 된다(사용자 지시, 2026-11-16). report html · Notion · 커밋 대상 파일에는 적지 않는다.
- 이 파일에 실 서버(스테이징 · 운영) 계정을 넣지 않는다.

## CP5 와 이어 쓰기

1. CP4 승인 뒤 전체 테스트가 green 이면 `up` 으로 띄운다. 코드를 고친 뒤면 `restart` 를 쓴다.
2. 브리프를 `sbx-<이름>/cp5-brief.md` 에 쓰고 `cp5-verifier` 에이전트를 부른다. 브리프에는 검증 대상, 결정 사항, 허용한 데이터 변경 범위를 적는다. 샌드박스 주소와 `sql.sh` 경로는 위 출력에서 옮긴다.
3. 에이전트 결과의 자기 점검 값(시작 · 끝 shasum)이 같은지 본다. 같아야 에이전트가 저장소를 건드리지 않았다는 것이 확인된다.
4. CP6 제출 때 사용자에게 주소와 계정을 안내한다(CP7 E2E 용).
5. CP7 이 끝나면 `down` 으로 내린다. `--rm-db` 는 그 데이터로 다시 볼 일이 없을 때만 쓴다. 디렉토리는 지우지 않는다. 스크린샷과 브리프가 남아 있어야 하기 때문이다.

## 하지 않는 일

- 공유 개발 DB(localhost:3306)나 실 서버에 연결하지 않는다.
- 다른 세션의 샌드박스를 내리지 않는다. `status` 에 보이는 다른 이름은 그 세션의 것이다.
- `ddl-auto=update` 로 만든 스키마는 Hibernate 가 생성한 것이라 실 DB 의 수동 DDL 과 세부가 다를 수 있다. 그래서 Step 9 스키마 검증 용도로는 쓰지 않는다. 화면과 도메인 동작 검증 전용이다.
