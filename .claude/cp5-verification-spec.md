# CP5 샌드박스 검증 명세

CLAUDE.md 의 '샌드박스 브라우저 검증(Step 10 · CP5)' 절이 요구하는 것을 어떻게 설계하고 수행하는지의 상세다. CLAUDE.md 에는 판정 가능한 최소 기준만 두고 설계 지침은 여기 둔다.

**기준 구현**: `report/26-08-07_10-22-42_MK4-1_report.html`. 아래 서술이 애매할 때는 그 파일의 §2~§6 을 본다. 최근 report 를 무작정 복제하지 않는다 — 이 명세와 기준 구현을 따른다(plan/report html 규약의 '복제 금지' 와 같은 원칙).

## 1. 왜 브라우저여야 하는가

이 단계의 존재 이유는 **빌드와 테스트가 통과해도 화면에서만 드러나는 결함**을 잡는 것이다. 과거 전수 점검에서 direct POST 로 폼 마커가 빠지면 오류가 조용히 삼켜지던 결함(silent 200)을 이 방식으로 잡았다.

API 를 직접 호출해 응답 코드만 확인하면 그 층을 통과해 버린다. 그래서 **화면이 있는 슬라이스에서 API 확인만으로 CP5 를 대체하지 않는다.** 실제로 2026-08-07 에 이 대체가 일어나 결함이 그대로 넘어간 사례가 있다 — curl 로 오류 반환만 확인하고 스크린샷 없이 report 에 한 줄로 적어 CP6 을 통과했다.

**API 확인이 대체 수단이 되는 경우는 하나뿐이다** — 게스트가 화면 없이 HTTP 로만 상호작용하는 E 계열 슬라이스(CLAUDE.md 의 CP5 · CP7 E 단계 예외). 그 경우에도 **관리자 화면이 딸린 부분은 그 화면만이라도 브라우저로 검증**한다.

## 2. 검증 항목 설계 — 세 갈래

항목에는 반드시 식별자를 붙인다. 계획과 수행이 1:1 로 대조되어야 빠진 것이 보이기 때문이다.

### A — 정상 흐름

의도한 동작이 실제로 되는지. 슬라이스가 새로 만들거나 바꾼 **사용자 목표 하나당 한 항목**으로 나눈다. "저장이 된다" 같은 뭉뚱그린 항목이 아니라 "필수값만 채워 저장 → 목록에 반영된다" 처럼 조작과 관측 가능한 결과가 붙어야 한다.

### B — 비정상 조작

의도하지 않은 조작을 일부러 시도해 애플리케이션이 어떻게 막는지 본다. CLAUDE.md 가 나열한 다섯이 출발점이다.

- 잘못된 값 입력
- 순서를 건너뛴 요청
- 이미 삭제된 자원 조작
- 권한 없는 경로 접근
- 중복 제출

**이 다섯은 최소 집합이지 완결 목록이 아니다.** 슬라이스 고유의 비정상 경로를 추가로 찾는다. 찾는 방법은 셋이다.

1. **이 슬라이스가 새로 만든 상태 전이를 뒤집어 본다.** 전이가 A→B 라면 B 상태에서 A 를 요구하는 조작을 시도한다.
2. **새로 추가한 예외 클래스마다 그것을 실제로 터뜨리는 조작을 항목으로 만든다.** 테스트 규율이 요구하는 통합 시나리오와 같은 목록이므로 재사용된다.
3. **화면에서 막아 둔 것(버튼 disabled 등)을 우회해 본다.** direct POST 나 URL 직접 입력이 여기 해당하며, 위 silent 200 사고가 정확히 이 부류였다.

### C — 막는 방식

거절하는 것으로 끝이 아니라 **UX 를 해치지 않고 유도하는지**를 평가한다. 불가침 원칙 "UX 모순은 UI 1차 차단" 의 실지 확인이다. 세 질문으로 판정한다.

- 사용자가 **왜 막혔는지** 알 수 있는가
- **다음에 무엇을 해야 하는지** 안내되는가
- 애초에 막힐 행동을 **UI 가 먼저 차단**했는가(버튼 disabled + tooltip)

세 번째가 핵심이다. 서버가 예외로 거절하는데 UI 가 그 행동을 열어 두고 있다면, 그것은 통과가 아니라 **결함**이다.

## 3. 커버리지 기준 — 몇 개면 충분한가

**화면의 조작 가능한 요소가 A 또는 B 중 하나에는 등장해야 한다.** 이 슬라이스가 건드리지 않은 기존 요소는 제외한다.

기준 구현(MK4-1)은 **17 항목**(A1~A8 · B1~B6 · C1~C3)이었다. 이것은 목표 수치가 아니라 규모 감각이다 — 화면 하나를 바꾼 슬라이스에서 A 가 2~3 개뿐이라면 정상 흐름을 뭉뚱그린 것이 아닌지 되돌아본다.

## 4. 수행과 채증

**계획을 먼저 제시하고 시작한다.** 즉흥적으로 클릭하며 훑지 않는다. 계획 없이 시작하면 무엇이 빠졌는지 스스로도 알 수 없다.

**항목마다 스크린샷을 남긴다.** 식별자와 1:1 이다. 항목 수보다 스크린샷이 적으면 검증이 덜 된 것이다. B 항목은 **거절 화면**이 증거이고, C 항목은 **안내 문구나 disabled 상태**가 보이는 화면이어야 한다.

**결함을 발견하면 그 자리에서 고치고 재검증한다.** 무엇을 발견해 어떻게 처리했는지를 report 에 남긴다 — 결함을 찾은 사실 자체가 이 단계의 성과이므로 숨기지 않는다. 기준 구현은 이 절(§6)에서 결함 4 건을 다뤘다.

**샌드박스 환경**은 누적 메모리의 레시피를 따른다. 동시 세션과 포트가 겹치지 않게 스트림마다 다른 포트를 쓴다.

## 5. report 에 어떻게 옮기는가 (CP6)

기준 구현의 섹션 구성을 따른다.

```
§ CP5 검증 항목 계획 — 무엇을 확인하려 했는가
§ 검증 환경 — 무엇을 어떻게 배치했는가
§ 정상 흐름 검증 (A1~An) — 실제로 한 조작과 결과
§ 비정상 조작 검증 (B1~Bn) · 막는 방식 (C1~Cn)
§ 검증 중 발견한 결함과 처리
```

**계획 절의 식별자와 수행 절의 식별자가 같아야 한다.** 계획에 있는데 수행에 없으면 미검증이고, 그 사실을 감추지 말고 사유와 함께 적는다.

CP6 승인 판정은 CLAUDE.md 의 기준을 쓴다 — 식별자가 계획과 수행에 모두 나타나고, 항목 수만큼 스크린샷이 있으며, 항목마다 실제 조작과 결과가 서술돼야 한다.

## 6. 흔한 이탈

- **API 로 응답 코드만 확인하고 끝낸다** → §1. 화면 있는 슬라이스에서는 대체 불가.
- **정상 흐름만 본다** → B 와 C 가 이 단계의 본론이다. A 만 있는 검증은 통합 테스트와 다를 바 없다.
- **스크린샷을 대표 한두 장만 남긴다** → 항목별 1:1 이어야 무엇이 검증됐는지 대조된다.
- **결함을 발견하고 조용히 고친다** → 발견 사실이 성과다. report 에 남긴다.
- **계획 없이 훑고 나서 사후에 항목을 지어낸다** → 계획이 먼저다. 사후 정리는 빠진 것을 드러내지 못한다.
