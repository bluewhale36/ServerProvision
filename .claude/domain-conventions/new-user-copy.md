# 새 안내 문구 · 화면 라벨을 만들기 전에

새 문구(안내 · 오류 · 도움말 · placeholder · 확인 모달)나 화면 라벨(버튼 · 링크 · 제목 · 배지)을 만들 때 이 문서를 먼저 연다. 어휘의 정본과 금지 표기는 `docs/glossary.tsv` 가 SSOT 다 — 라벨을 짓기 전에 그 표에서 대상 동사 · 용어를 검색한다. 이 파일은 UTF-8 BOM 인코딩을 유지한다(Excel 이 한글을 바르게 읽기 위한 조건 — BOM 을 제거하면 스프레드시트에서 깨져 보인다). 근거 실측과 결정 경위는 `discussion/26-08-18_14-34-33_S16-1-vocabulary-audit_briefing.md`.

## 문체 규칙 (S16-1 확정, 2026-08-18)

1. **서술은 합니다체, 요청 · 명령은 하십시오체.** "~해요" · "~하세요" · "~해주세요" 금지. (예: "부모부터 복구하십시오.")
2. **같은 상황에는 같은 문장 하나.** 서버 렌더와 클라이언트 모달이 같은 정본 문장을 쓴다 — 실현 수단은 아래 MessageSource 활용 계획.
3. **placeholder 는 `예: ` 예시형이 정본.** 예시를 만들 수 없는 자유 서술 필드만 명사구 허용. 명령형 · 조건형 금지 — 조건 안내는 도움말(`n-hint`) 자리로.
4. **상태 배지는 명사형 + 진행만 "~ 중".** (조치 필요 · 해결 · 완료 · 프로비저닝 중)
5. **모달 이탈 버튼**: 작업을 포기하는 확인 모달 = "취소" / 파괴적 액션 없는 조회 패널 = "닫기". "나중에" 는 orphan-recovery 한 곳의 등재된 예외.
6. **버튼 라벨 = "재시도"**, 산문 = "다시 시도하십시오" 허용.
7. **코드 이름(영문 식별자)을 사용자 문구에 노출하지 않는다.** (nudge → "중복 확인"). 기술 표준 약어(PXE · TFTP · BMC · BIOS · iPXE · TTL · ISO)는 노출 허용.
8. **새로 만드는 동작의 동사는 대상별 배타**: 등록(실물 자원) · 작성(정의서 등 내용 문서) · 생성(그룹 등 구조물). "신규" 수식어 금지.

## MessageSource 활용 계획 (키 체계와 소비 경로)

원칙: **문구의 소유자는 서버의 MessageSource 이고, JS 는 문구를 소유하지 않는다.** 현행 `messages.properties` 는 Spring 폼 검증 코드 키(`typeMismatch.*` · `required` 등) 전용이며 그 키 모양은 Spring 해석 규칙이 정하므로 그대로 둔다. 그 위에 두 네임스페이스를 새로 연다.

### 키 명명 체계

| 네임스페이스 | 용도 | 예 |
|---|---|---|
| `action.<동작>` | 정본 동사 라벨 사전 — 버튼 · 링크 라벨은 이 키로 쓴다 | `action.register` = 등록, `action.write` = 작성, `action.create` = 생성, `action.restore` = 복구, `action.purge` = 영구 삭제, `action.retry` = 재시도, `action.cancel` = 취소, `action.close` = 닫기, `action.save` = 저장, `action.edit` = 수정 |
| `<영역>.<맥락>.<상황>` | 문장형 문구(안내 · 오류 · 확인). 키는 상황을 명명한다 — 문구를 고쳐도 키는 불변 | `common.error.request-failed`, `trash.restore.blocked-by-deleted-parent`, `management.duplicate-check.session-expired` |
| (Spring 검증 코드 키) | 폼 바인딩 오류 — Spring 해석 규칙이 키를 정함 | `typeMismatch.driftSnoozeRequest.window` |

`action.*` 사전이 사용자 첨언(동사 · 표현의 MessageSource 엄격 구분)의 실체다 — 라벨이 키 뒤로 숨으므로 금지 동의어가 화면에 등장할 수 없고, **조건부 단순화 조항이 발동하면 이 사전의 값만 고쳐 전 화면이 한 번에 바뀐다.** 영역 접두는 도메인 패키지와 정렬한다(common · management · maintenance · provisioning · execution).

### 소비 경로 3가지

1. **Thymeleaf** — `th:text="#{action.register}"` · 파라미터는 `#{key(${arg})}`. 표준 경로.
2. **Java** — advice · flash 문구는 `MessageSource` 해석(선례 `ApiExceptionHandler`). 예외를 메시지 문자열 대신 키 + 인자를 들게 하는 전면 전환은 S16-2 에서 범위를 확정한다(`new-exception.md` 와 연계). 그 전의 신규 Java 문구는 문체 규칙 준수가 최소선이다.
3. **JS** — 두 갈래로 나눈다.
   - **화면 문맥 문구**(확인 모달 본문 등): 템플릿이 `#{key}` 렌더 결과를 `data-*` 속성이나 DOM 에 실어 주고 JS 는 읽어 표시만 한다 — 현행 `data-resource-extra` · `data-confirm-*` 패턴(16곳 실재)의 공식화. 신규 JS 문구의 기본 경로다.
   - **순수 클라이언트 발화 문구**(서버 응답이 아예 없는 통신 실패 · 타임아웃): 공용 레이아웃 fragment 가 `<script type="application/json" id="app-messages">` 로 공용 문구 사전을 `#{...}` 렌더로 내려주고 JS 전역 헬퍼가 읽는다. **이 인프라는 S16-2 의 첫 산출물** — 생기기 전까지 신규 클라이언트 발화 문구는 문체 규칙만 준수하고 키화는 S16-2 일괄 이관에 합류한다.

### 신규 문구의 등록 기준

- **문장형 문구와 반복 사용 동사 라벨은 키 등록이 기본**이다 — 문장 복제가 문체 이탈의 진원지였다는 것이 진단의 실증이다(같은 오류 문장이 서버와 모달에서 다른 문체로 복제).
- **화면 고유의 1회성 명사 라벨**(표 컬럼 헤더 · 페이지 제목 등)은 템플릿 직접 표기를 허용한다 — 단 glossary 의 정본 · 금지 표기를 따른다. 키 폭발을 막는 실용선이다.

## 조건부 단순화 조항 (사용자 확정, 2026-08-18)

동사 · 표현의 구분은 MessageSource 를 이용해 엄격하게 유지한다. 단 다음 중 하나가 발생하면 구분을 단순화한다 — ① 유지 비용이 과다해짐 ② 정본 단어의 가짓수가 더 늘어남 ③ 단어의 구분이 애매한 상황 발생. 단순화의 예비안(현재는 기각 상태): 각 도메인의 신규 진입은 "신규" 버튼, 신규 화면의 제출은 "저장" 으로 일원화. 발동 시 실행 = `action.*` 사전의 값 수정.

## 적용 시점의 분업

- **신규 문구**: 이 관문이 즉시 적용된다(불일치 유입 차단). 키 체계 · 소비 경로도 신규분부터 따른다.
- **기존 문구의 정비 · 일괄 이관**: S16-2 소관 — 디자인 실험 승격에 합류. `app-messages` 인프라 신설 · 예외 키화 범위 확정 · 금지 표기 검사 스크립트가 그 산출물이다.
- **enum 라벨 개정**(해결 라벨 · 배지 등): S13(사용자 노출 enum 표시 정비) 소관.
- **CSS 클래스 명명**: 디자인 실험 종료 후 별도 확정.
