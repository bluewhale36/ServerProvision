# Javadoc 과 주석을 쓴다

Javadoc 은 짧기만 하면 되는 것이 아니다. 매뉴얼 문장처럼 간단하지만, 읽는 사람이 한 번에 뜻을 알아야 한다. 짧게 줄이다 뜻이 흐려지면 실패다.

길이와 금지 패턴은 `CodingConventionTest` 가 막는다(J1 ~ J5). 이 문서는 기계가 판정하지 못하는 명료성을 다룬다. 코드 검수에서 이 문서의 점검 순서로 본다.

## 1. 기계가 막는 것

| 규칙 | 내용 |
|---|---|
| J1 | 멤버(메서드, 생성자, 필드, enum 상수) Javadoc 본문은 4 줄 이하다. 빈 줄과 @param, @return, @throws 줄은 세지 않는다 |
| J2 | 타입(클래스, 인터페이스, enum, record) Javadoc 본문은 8 줄 이하다 |
| J3 | 첫 문장을 단계 코드("S23-1 —", "E4-1-b-2 D-21 —")로 시작하지 않는다 |
| J4 | 화살표(→, ->, =>)를 쓰지 않는다. `{@code}`, `{@link}` 같은 인라인 태그와 `<pre>` 안은 검사하지 않는다 |
| J5 | 괄호 안에 괄호를 넣지 않는다. 검사하지 않는 자리는 J4 와 같다 |

이미 있는 위반은 `src/test/resources/convention/baseline.txt` 에 있다. 그 Javadoc 을 고치면 기준선 줄도 지운다.

## 2. 점검 순서 (검수)

1. **무엇을 하는가.** 첫 문장이 이 코드가 지금 하는 일을 말하는가. 주어와 대상이 분명한가.
2. **왜 그런가.** 코드만 봐서는 알 수 없는 이유가 있을 때만 한 문장으로 덧붙였는가. 코드가 이미 말하는 것을 되풀이하지 않는가.
3. **사실인가.** 비유, 설계 어휘("축", "흐름을 탄다"), 과장("핵심", "결정적")이 아니라 실제 동작을 적었는가.
4. **풀어 썼는가.** 약어와 클래스 줄임말이 없는가(`SoftDeleteIntentService` 를 `SDIS` 로 쓰지 않는다). 설계 용어 약어는 처음에 풀어 쓴다.
5. **지금의 사실인가.** 발견 경위, 단계 이력, 바뀌기 전 모습은 커밋과 plan 에 있다. Javadoc 은 지금의 동작만 말한다. 근거가 꼭 필요하면 문장 끝에 "(2026-11-18 실기)" 정도로 줄인다.
6. **한 곳에 있는가.** 긴 설계 배경은 타입 Javadoc 한 곳에 두고, 메서드 Javadoc 과 인라인 주석에 같은 말을 다시 쓰지 않는다.

문체는 '~한다' 평서형이다. 짧은 요약은 명사형으로 끝내도 된다("ISO 를 등록한다", "등록 화면의 빈 폼").

## 3. 예

나쁜 예 1. 단계 코드로 시작하고 화살표로 잇는다.
```java
/** S23-1 — 원장 origin → 판정 → 409. */
```
좋은 예 1. 하는 일과 결과를 문장으로 쓴다.
```java
/** 원장 출처가 다른 설치 기록이면 409 로 거절한다. */
```

나쁜 예 2. 경위를 늘어놓아 무엇을 하는지가 묻힌다.
```java
/**
 * 처음에는 컨트롤러에서 처리했으나 R4 에서 옮겼고, 이후 HF12 에서 실기 중 null 이 들어와
 * (BMC 가 (가끔) 빈 값을 줌) 이렇게 바꿨다. 이 메서드는 값을 확인한다.
 */
```
좋은 예 2. 지금 하는 일과 이유 한 가지만 남긴다.
```java
/** BMC 가 빈 시리얼을 주면 null 로 둔다. 빈 문자열로 저장하면 다른 서버와 같은 시리얼로 보인다. */
```

나쁜 예 3. 너무 줄여 뜻이 흐리다.
```java
/** 판정. */
```
좋은 예 3. 무엇을 판정하는지 말한다.
```java
/** 버전이 고른 OS 의 메이저와 맞는가. Rocky Linux 9 는 "9.6" 을 받고 "10.0" 을 거절한다. */
```

## 4. 인라인 주석

`//` 주석은 WHY 가 비자명할 때만 쓴다. J 규칙은 인라인 주석에 적용하지 않지만 점검 순서 2 ~ 5 는 그대로 적용한다. 파일 머리에 AI 작성 표지를 두지 않는다(S4).
